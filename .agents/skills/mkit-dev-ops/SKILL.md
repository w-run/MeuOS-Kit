# 多 Worker 快速迭代开发方法论（Goal-Driven Dev-Ops）

> 抽象自 MeuOS-Kit mcc/m++ 重构实战（2026-08-02），适用于任何软件项目。
> 核心：**goal 驱动 → 团队语义化分工 → 细颗粒度任务并行 → 质量门禁 → 文档纪律**。

## When to invoke

- 用户要求"设置 goal"、"开启/恢复工作"、"多 worker 并行"、"快速迭代"、"拆任务"、"建团队"
- 用户要求处理复杂、跨组件、可并行的大型开发任务
- 用户要求迭代式推进（每轮验收、持续交付）

## 核心机制（八件套）

### 1. Goal 声明机制（loop 定时 + 约束）

每轮工作开始前，把 **goal 作为循环提示词**注册（`/loop` 或 CronCreate），定期自动重申约束，防止漂移。

标准 goal 模板（按项目替换目标）：

```
设置goal：[项目名]；
【注意：你是指挥官，不是士兵】必须使用团队并行多路工作；
完全自主决策；禁止残留缺陷不处理（哪怕非阻塞问题）；
未彻底完成[核心交付物]前，仅允许提交到本分支的远程，不允许合并到 main；
最终实现[覆盖目标]（如 C++ 98~23 / C 90~23）；
能够完全自举、端到端 pass、代码结构清晰；
在实现完标准的同时，应做到自主特性优化、性能优化、质量提升，
以实现现代化[工具/产品]的目标。
```

**通用化要求**（从 m++ 抽象）：
- `禁止残留缺陷`：每个缺陷必须闭环（修复+测试+记录），不留半成品
- `分支纪律`：主交付完成前只推工作分支远程，不合并主分支
- `覆盖目标`：明确语言/平台/API 覆盖范围
- `自主迭代`：不阻塞、不留尾巴、持续交付

### 2. 团队语义化分工机制

Worker 按**角色**命名（不是 general-purpose-N），每类 worker 专职：

| 角色 | 类型 | 职责 |
|---|---|---|
| **planner** | 调研型 | 参考实现探索、社区调研、可行性分析、**复杂缺陷根因+方案先行** |
| **auditor** | 验收型 | 独立代码验证、质量检测、提交审查、门禁回归 |
| **worker-<域>** | 执行型 | 按领域划分（如 worker-cpp/worker-toolchain/worker-libc），写代码 |
| **worker-test** | 执行型 | 测试矩阵扩充、缺陷发现、边界用例 |
| **doc-sync** | 支持型 | docs/.issues/ARCHITECTURE 文档同步，零滞后 |

**分工铁律**：
- **文件区域隔离**：每个 worker 只动自己的文件区域（src/opt/ vs src/cpp/ vs test/ vs .md），避免冲突
- **调研先行**：复杂任务先派 planner 调研（收集信息/参考/分析根因），输出方案文档，再派执行 worker 实施——执行 worker 拿到的是完整方案而非半成品
- **提交互不干扰**：worker 用文件级 `git add <文件>`，禁止 `git add -A`（防夹带他人改动）

### 3. 任务分配机制

- **细颗粒度拆分**：大任务拆成独立小任务，每任务可独立提交+验证+回退
- **优先级排序**：按严重度/收益/依赖排序（如 缺陷 C→D→B→E，每项单独提交）
- **归属明确**：每任务指定 owner，并发时防止重复实现（可声明"缺陷 X 归属给 worker-Y"）
- **任务池**：维护 .issues/ 下的任务队列文档，worker 完成一个领下一个

### 4. 快速迭代机制

- **每步提交 + push**：完成一小步立即提交推送（`<组件>: <描述>`），不憋大提交
- **每步回归**：提交前跑对应组件的 `make check` / 验收脚本
- **多 worker 并行**：独立文件区域的任务同时跑
- **双 worker 竞争**（可选）：对"方案明确但实现有风险"的任务，派两个 worker 独立实施，谁先提交验证通过谁赢（如缺陷 H：worker-test 竞争胜出，1 行修复快速闭环）
- **阶段性收尾**：每轮完成后清理半成品（stash 保护 or 回退）、记录 stash、重启新 worker

### 5. 质量门禁 + 文档纪律

- **验收门禁**：建立 `verify-all.sh`（聚合 check/单测/回归/自举），每提交必跑，任一失败即非零退出
- **auditor 独立审查**：定期派 auditor 审查最近提交（格式/调试残留/未实现声明/回归），输出 audit-report.md
- **文档同步**：doc-sync 专职同步 docs/.issues/ARCHITECTURE，每技术提交后更新，标注对应 commit 哈希
- **缺陷登记**：测试/审计发现的问题统一登记到 .issues/<date>.md 缺陷队列，修复后标记哈希闭环

## 会话恢复流程

1. 读取 memory 中该项目的工作方式偏好
2. 用 EnterWorktree 进入目标工作树（若用户要求）
3. 确认 branch 状态（git status/pull/push 同步）
4. 重新声明 goal（/loop 或直接）
5. 检查任务队列（.issues/）续接未完成任务

## 6. 进度记录更新机制

**每个任务节点后必须更新进度记录**（不是完成时，是每节点），文档是"状态权威来源"：

- **.issues/<日期>.md**：当天所有技术提交、缺陷、决策的时间线记录。每节标注 commit 哈希。
- **docs/ 组件文档**：ARCHITECTURE.md（目录/模块/Phase Status）、各专项报告（roadmap/audit/acceptance）。
- **worker-deployment.md**：worker 角色/状态/在途/stash 记录，会话中断后恢复上下文用。
- **更新时机**：每提交、每缺陷闭环、每 worker 状态变化，doc-sync worker 专职同步，避免文档滞后于代码。

## 7. 工作树（Worktree）使用机制

- **长期开发分支**用独立 worktree（如 `.agents/worktrees/<name>/`），与主仓库隔离，避免互相干扰。
- **EnterWorktree**：用户明确要求 worktree 时用该工具创建，自动建分支 + 切会话目录。
- **并发 worker 冲突规避**：
  - 多个 worker 改同一批文件时，可给冲突方**另开独立 worktree**（如 c2fix 修复与主分支 vtable 工作冲突 → worker 自建 worktree 独立推进）。
  - 会话活跃团队上下文可能漂移（spawn 后团队目录变化），注意用 SendMessage 验证 worker 可达性。
- **stash 管理**：中断的半成品 stash 保护（标注内容+来源），恢复时 pop；过时 stash 可清理但不误删仍在用的恢复点。

## 8. Git 提交规则

- **禁止在 main 直接开发**：新任务必须建分支（`worktree-<描述>` 或 `feat/fix/doc-<描述>`），main 只接收一次性修复/文档/状态更新。
- **提交格式**：`<组件>: <描述>`（如 `mcc: fix va_list alignment on i386`、`libc: add strtof`）。
- **完成即推送**：每提交后 push 工作分支远程，不积压。
- **合并纪律**：核心交付未完成前，只提交到工作分支远程，**不合并 main**（AGENTS.md 约束）。
- **提交粒度**：单组件粒度，每逻辑单元一个提交；复杂改动拆小步（收集→计算→合并 分步提交，可回退）。
- **文件级 add**：多 worker 并发时用 `git add <具体文件>`，**禁止 `git add -A`**（防夹带他人改动）。
- **提交前回归**：跑对应组件 `make check` 或验收门禁，确认无回归。
- **合后清理**：分支合并 main 后删本地分支，保留远程分支（历史）。

## 实战模板（可直接套用）

### 缺陷闭环工作流
```
planner 调研（根因+方案文档）→ 执行 worker 实施（或双 worker 竞争）→
worker-test 加回归测试 → auditor 验证 → doc-sync 同步文档 → 队列标记 ✅
```

### 特性开发工作流
```
planner 可行性调研（参考源+社区+路线）→ 拆细颗粒度任务 →
多执行 worker 按文件区域并行 → 每步提交+回归 → 验收门禁 → doc-sync
```

### 性能优化工作流
```
调研定位根因（量化基线）→ 设计保守方案（可回退+回退预案）→
实施+量化对比（前后数据）→ 未达目标则记录二期方向，不阻塞
```

## 禁止事项

- 禁止单 worker 串行承担多个大任务（用户明确反对——导致进度慢+工作区被占+中间态缺陷）
- 禁止 `git add -A` 提交（多 worker 并发必冲突）
- 禁止在 main 直接开发（必须工作分支）
- 禁止遗留半成品不处理（stash 或回退，不留垃圾）
- 禁止跳过验收门禁提交
- 禁止文档滞后（每节点更新 .issues/docs/ARCHITECTURE，不攒到结束）
- 禁止并发 worker 同文件区冲突（文件区域隔离或独立 worktree）

## 参考实践（MeuOS-Kit mcc/m++，2026-08-02）

- C++ 98~23 覆盖：C++11 核心 + C++14/17 五项 + C++20 三项，每项独立提交
- 缺陷队列 A/B/C/D/E/G/H：全部闭环（auditor 捕获门禁回归、worker-test 发现、planner 调研、执行 worker 修复）
- P2 性能优化：栈帧 3944→2152B（-46%），保守方案 + 回退预案
- 双 worker 竞争案例：缺陷 H（限定虚调用）1 行修复快速闭环
- 文档同步：ARCHITECTURE/roadmap/0802 三份零滞后
