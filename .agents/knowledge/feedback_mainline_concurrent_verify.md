name: 主线高速推进下的判断纪律
description: 主线并发合并很快，任何基于旧 HEAD 的判断（是否回归、谁合的、成果是否还在）都有极短保质期，下结论前必须先 fetch
type: feedback
---

遇到任何"异常"（门禁变红、worktree 消失、成果疑似被覆盖、某改动疑似被 revert），
判断次序必须是：**先 `git fetch` 对齐 HEAD → 再确认目标改动是否真的不在树上 → 最后才怀疑回归**。

**Why:** mxx-work 主线在多 worker 并发下推进极快（曾出现单次 fetch 间隔内连推 4 笔合并）。
已经吃过三次亏：
1. grace 复跑出 FAIL=3 三项全红，第一反应"合并引入回归"，实为卡在**"测试先到、配套修复后到"的时间窗**——测试文件随 a13dd2c 进树时 cpp_parse.c 修复还没到，对齐最新主线重建后全绿。
2. 我的 worktree `/tmp/mxx-wt-chloe-r7` 中途消失，以为工作丢了，实为分支已被合并后清理，成果在分支上完好。
3. 我把某笔 merge 的归属记错到 grace 头上，实际是 team-lead 合的——她任务结束后就没再动主线。

三者本质同一类问题：**拿一个已经过期的 HEAD 快照去解释当下现象**。

**How to apply:**
- 汇报"成果存活"时不要只信别人结论，用 `git merge-base --is-ancestor <我的commit> origin/<主线>` 验祖先，
  再逐文件 `git show <HEAD>:<path> | grep` 点名核对关键改动的出现次数与行号。
- 不要凭记忆断言"某某合的"——归属用 `git log` 查，记错会误伤同事。
- 为了往文档补一句话而开分支再归并，收益通常不抵时间窗风险；这类小修等下次有人动同一模块时顺手带上。
- 流程改进方向：测试与配套修复应同 commit 归并（已由 grace 向 team-lead 提出），可根除"假红"。
