## 0. 一句话结论（先给答案）

MeuOS 的隔离**第一性不是「容器」也不是「VM」，更不是 Linux 的 uid/namespace 叠加**，而是 **capability 句柄集 + Job 账本** 这一对**一等隔离原语**：沙箱 = 一个进程/Job 所持有的**受限 capability 集合**（句柄 + rights + namespace 视图），VM = 该集合之外、额外持有 `guest`/`vcpu` 一等对象以跑**不可信/异构内核**的受限 guest。**容器与 VM 都是同一对原语的两实例化**，落在唯一一条 capability 信任边上。基于此：Day 1 即提供**跨五架构一致的进程级/容器级隔离（L0/L1）**；VM（L2）是跨内核的强故障封闭外推，仅在具备硬件虚拟化扩展的架构上启用。**V1 不提供原生 KVM 接口，但完全允许用户态 hypervisor**——因为用户态 VMM 本质只是持 `GUEST_CREATE`/`VM_MANAGE` 能力的普通进程，被 capability 与 Job 账本约束；被否决的只是把内核内部焊死到 KVM ioctl ABI 的兼容层，而非「在用户态跑 hypervisor」这件事本身。

## 2. 多系统参照对比（隔离原语谱系）

> 横轴：各系统「隔离第一性 / 沙箱实现 / VM 形态 / 跨架构一致性做法 / 与 MeuOS 取舍」。结论列给 MeuOS 取舍。

| 系统 | 隔离第一性 | 沙箱 / 容器实现 | VM 形态 | **MeuOS 取舍** |
|------|-----------|----------------|---------|----------------|
| **Linux** | 身份（uid/gid）+ 事后七机制叠加（DAC/MAC/cap/seccomp/namespace/cgroup） | cgroups（资源）+ namespace（视图）+ seccomp（syscall 过滤）事后挂接 | KVM（单体内核子系统，原生硬件虚拟化，`/dev/kvm` ioctl ABI） | **不借**身份模型与七机制叠加；**不借** KVM ABI（V1 已否决）；**借**「硬件虚拟化能力」但改形态为「用户态 VMM + guest 设施」 |
| **gVisor** | 用户态拦截内核（Sentry 拦截 Linux syscall）+ 独立地址空间 | 无需硬件虚拟化的强沙箱：在用户态重实现 syscall 语义，guest 应用与 host 零内核共享 | **无传统 VM**：用「用户态内核」替代，运行开销低、无需 VT-x | **借其目标（不靠 HW virt 也能强隔离不可信代码），但不借其手段（syscall 拦截/重实现 syscall 面）**——MeuOS 用 capability 边界达成同效，无需第二个 syscall 面；gVisor 式拦截是 seccomp-bpf 思路的延伸，已被 07 否决 |
| **Firecracker** | microVM（极简 KVM guest，每函数一 VM） | 每个隔离单元 = 一个最小 VM（快速启动、小内存占用） | KVM-based microVM；强故障封闭、VM 崩溃不波及 host | **借其「轻量 VM 用于不可信函数隔离」的用例**，但 MeuOS 用**用户态 VMM + 薄 guest 设施**（非 KVM）承载同样用例；多数「不可信函数」场景在 MeuOS 用 L1 容器（capability 集合）即可，无需真 VM |
| **WSL2** | 真 Linux 内核跑在 Hyper-V VM 内，以 VM 提供 Linux 兼容 | 兼容 = 整 VM 承载 guest Linux | Hyper-V 分区（guest Linux） | **明确否决**（08 已定：兼容层是薄翻译面非 VM）；Linux 二进制在 L0/L1 跑，不进 L2。WSL2 是「以 VM 承载兼容」的反面教材，MeuOS 不重复 |
| **Windows Hyper-V 隔离** | 分区（partition）+ 虚拟信任级（VTL/VBS）；Job 对象作资源/生命周期隔离 | ① Job 对象（资源隔离）② Hyper-V 隔离容器（utility VM 底层）③ VBS 把关键面放到更可信层 | Hyper-V 父分区管理 guest 分区，VMBus 半虚拟化 | **借**「Job 对象作隔离单元」思想（与 04 Job 账本同源）；**不借** VBS/VTL 式「用 hypervisor 造可信层」——MeuOS 靠 capability + 最小 TCB 在软件层即得同效信任边界 |
| **Fuchsia** | capability（handle+rights）+ Job 树嵌套 | Component 经 namespace + rights 隔离；Job 树 = 嵌套资源/生命周期边界，父 Job 终止传播杀子树 | 受限 VM（restricted VM）：guest 只拿 VMO，内核只给 vCPU + GPA 基于 VMO | **最贴**隔离第一性 + Job 嵌套 + VM 形态：本文 §3/§5 直接同构 |
| **seL4** | capability（CSpace）形式化验证隔离 | 无容器；进程间只靠显式 cap 委托；VM 也是一等可 revoke 的 cap 对象 | guest 经 passthrough（iommu/设备 cap 交给 guest VM） | **借**「VM 也是一等 cap 对象、可 revoke」思想（接 03 revoke 即回收）；隔离可形式化（接 20 I1–I7） |
| **Android 应用沙箱** | 每 app 独立 UID + SELinux + 命名空间 + ART 沙箱 | 每 app 受限域；后续 pKVM 把强隔离升级为「受保护 VM」 | pKVM（受保护 VM，host 不可窥视 guest） | **借**「每 app=受限域」映射为「每 Job=受限 capability 集」；**借** pKVM「强隔离=受保护 VM」思想映射为 MeuOS L2 restricted VM |
| **MeuOS（本文）** | capability 边界（句柄+rights+namespace）+ Job 账本 | 沙箱 = 受限 capability 集合；容器 = 受限 Job + 收窄 rights + 独立命名空间 + 可选 rootfs CoW | 用户态 VMM + 薄内核 guest 设施；设备经 device VMO（03） | 隔离第一性 = cap+Job；VM 仅跑不可信/异构内核；兼容层非 VM（接 08）；V1 不提供 KVM 接口但允许用户态 hypervisor |

**对比收口**：
- **隔离第一性**借 seL4/Fuchsia/07 的「capability 即边界」+ Windows「Job 对象作隔离单元」——这是地基，已在 04/06/07/29 落地。
- **沙箱手段**拒绝 Linux 七机制叠加与 gVisor 式 syscall 拦截（二者都依赖「身份/系统调用面」这一被 07 否决的第一性）；MeuOS 用 capability 集合直接表达沙箱，**不需要第二个 syscall 解释层**。
- **VM** 借 Fuchsia restricted VM / Android pKVM / Firecracker 的「轻量 VM 隔离不可信负载」用例，但实现为 **用户态 VMM + 薄 guest 设施**（非 KVM）；WSL2 明确不借（兼容层非 VM）。
- **跨架构一致性**借各系统「host 内核跑在最高特权级、guest 跑低特权级」的通行做法，但把「隔离第一性」固化为 capability（与硬件虚拟化无关），故 L0/L1 跨五架构一致，仅 L2 随硬件虚拟化扩展有无而变。

## 3. 隔离原语设计：capability + Job 账本作为一等隔离原语

### 3.1 解构：「应该基于什么原语」

在 Linux 里，隔离是**事后拼装**的：root 万能 → uid/gid → DAC → MAC → capabilities → seccomp → namespace → cgroups，七套机制正交叠加（见 07 §3.1），容器 = cgroups + namespace + seccomp 三件事后挂接。隔离的「第一性」模糊——边界是「我创建了哪些 namespace、挂进了哪个 cgroup」，权限仍隐式来自身份。

在 MeuOS 里，权限**只**来自 capability 句柄（07 §4.1：句柄即 capability，无 root、无隐式权限）。由此推演：**隔离的第一性 = capability 边界本身**，而把边界「量化、审计、生命周期化」的载体是 **Job 账本（04 §4.4 / 29 §3 T8、I4）**。二者不是叠加的两套机制，而是**同一隔离单元的两个互补维度**：

- **capability 集合（07）** 决定「这个主体**能做什么**」：可见哪些对象、能用哪些 rights、能 reveal 哪些路径。
- **Job 账本（04/29）** 决定「这个主体**能占多少、活多久**」：CPU 权重/带宽、内存上限、句柄数、IO 带宽、进程/线程数，以及父 Job 终止传播杀子树的**生命周期边界**。

> **判语**：隔离第一性 = **capability 集合 ∩ Job 账本**。二者在 `00-A5`（Job 账本 Day 1 内建、与权限同源）已互锁，是 MeuOS 的**一等隔离原语**——比 Linux 的 uid/namespace 叠加更根本，因为权限不来自身份、资源不来自事后附加。

### 3.2 三个已在地基里的事实（无需新建，只需组合）

| 地基（已有子文档结论） | 在隔离中的角色 | 来源 |
|---|---|---|
| `Job`（资源账本 + 生命周期单元，29 称其为威胁收敛的「账本不超额」边界 I4） | 隔离的**资源与生命周期边界**——配额、句柄数、进程数 Day 1 内建，父 Job 终止传播杀子树（04 §4.1/§4.4/§4.5；29 §3 T8、I4） | 04 / 29 |
| `rights` 位图 + pledge/unveil（07，29 称 sandbox escape = capability escape） | 隔离的**权限边界**——进程创建即最小权限，pledge 只能收缩、越界即终止、unveil 决定可见路径（07 §4.2/§4.3；29 §1） | 07 / 29 |
| 每进程统一命名空间（默认全不可见、spawn 组装，C3 已采纳每进程独立） | 隔离的**视图边界**——进程只看到显式 reveal 的路径能力，无全局 `/proc`（06 §4；00-C3） | 06 / 00-C3 |

### 3.3 沙箱 = 受限 capability 集合（原语级定义）

> **定义（沙箱）**：一个进程/Job 的沙箱 = 其被显式授予的 `Σ(handle_i, rights_i)` ∪ `namespace_reveal_set` ∪ `Job_quota`。任何试图访问不在该集合内的对象、或以超出 rights 的方式使用句柄，即触发 fail-closed（越权返回 `EPERM` / 触发 pledge 越界 `SIGABRT`，07 §4.2）。

这与 29 §1「攻击面 = 显式授予的句柄集合」互为表里：**沙箱的边界 = 攻击面的边界 = capability 集合的边界**。最小权限（least privilege）不是「最佳实践」而是「攻击面最小化」的直接手段（29 §1.3 公理 2）。由此：

- **容器形态（L1）** = 同一内核谱系内，用一个受限 Job 把上述集合整体收窄 + 独立命名空间视图 + 可选 rootfs CoW 快照（06 §4.3）划出的隔离域；域间共享内核，但彼此不可越权、资源受限、视图受限、生命周期由 Job 树传播控制。
- **VM 形态（L2）** = 在上述集合之外，额外持有 `guest`/`vcpu` 一等对象（26 §5），让**另一个内核**在内部跑；guest 与 host 内核之间只有 capability 一条信任边。VM 是 capability 边界在「需要跑另一个内核」时的外推，不是另一种隔离哲学。

## 4. 与 capability 模型（07）及 Job 账本（29）的协同

### 4.1 与 07：沙箱即受限 capability 集合（三个表现维度收口）

07 §4.3 提出「一个范式、三个表现维度」：维度 A 进程沙箱（pledge/unveil）、维度 B spawn 资源账本、维度 C 统一命名空间。本文把这三维度**提升为隔离的统一原语**：
- **维度 A（pledge/unveil）= 权限边界**：决定沙箱内进程「能碰哪些子系统、哪些路径」。
- **维度 B（Job 账本）= 资源/生命周期边界**：决定「能占多少、活多久」。
- **维度 C（namespace）= 视图边界**：决定「能看到什么」。

三者在**同一个 handle/rights 模型**下，可联合推理（07 §4.3）——审计一个沙箱只需看其初始句柄集 + pledge/unveil 收缩 + namespace reveal，无需像 Linux 交叉核对 uid/capability/SELinux/seccomp/namespace 五套东西。

### 4.2 与 29：Job 账本是威胁收敛的量化边界

29 把 Job 账本作为 **I4（账本不超额）** 的机检不变量（`Σ allocated ≤ quota`，超额 `REJECT(EAGAIN/ENOMEM)`），并作为 T8（IPC 洪泛 DoS）的主挡点（句柄数/消息队列深度计入 Job 账本，29 §3 T8）。本文据此把 Job 账本定义为隔离的**资源与生命周期边界**，使「沙箱爆内存/爆句柄」在边界处即被拒，而非在全局引发 DoS。这与 29 的纵深防御（TCB 最小 → Rust 类型 → 形式化 I1–I7 → 否定式测试）同构：Job 账本是 I4 在隔离维度的运行时实例化。

### 4.3 与 C4（兼容层不绕过 Day 1 沙箱）的衔接

00 C4 已采纳「Linux 二进制默认不允许绕过 pledge 默认沙箱」。这正面约束本维度：**沙箱（受限 capability 集合）是 Day 1 最高优先边界，对原生进程与兼容层二进制一视同仁**（08 §3、29 T10）。具体协同：
- 兼容层把 Linux 二进制期望的权限语义**翻译**为 MeuOS capability（root 是合成视图、不授予超越 capability 集的权限，08 §1.3/§4.4）；翻译失败即 `ENOSYS`/`EPERM`，绝不悄悄降级。
- 即便存在逃生通道，也只是「该 Job 的 capability 投影范围」**显式扩大**（按包粒度 manifest 声明、记入 Job 账本、可撤销），**绝不存在 root 万能**（00 C4）。即兼容层二进制所受隔离 = 它所在 Job 的 L0/L1 受限集合。

### 4.4 与 C15（网络栈 Day 1 完全用户态）的衔接

C15 已采纳网络栈 Day 1 即完全用户态（netstack3 风格），内核只保留四类机制：NIC 设备能力（10）+ VMO 零拷贝数据通路（03）+ **socket 句柄 capability（`NET_*` rights，见 38 §3.1 统一位图：NET_CONNECT=28 / NET_BIND=29 / NET_LISTEN=30 / NET_RAW=31）** + EventPort 就绪通知（05）。

由此 **网络沙箱是 capability 边界的自然延伸**：一个进程的「能否联网、能否绑特权端口、能否发原始套接字」完全由它持有的 `NET_*` right 决定，**无需 seccomp 过滤 syscall 号**。Day 1 沙箱集必须包含 `NET_*` right 作为受限集合的一部分（见 §7）。这把 C15 的「网络完全用户态」与本文「沙箱 = 受限 capability 集合」无缝闭环：网络访问权 = 又一个受 rights 约束的句柄，与文件/设备句柄同构、同审计、同 revoke。

## 5. VM 与容器策略（及与 V1 / KVM 的关系）

### 5.1 关键澄清：V1 不提供 KVM 接口，**但允许用户态 hypervisor**

这是本维度相对 `26` 必须补清的一点。`26` §5/§9 已定「VM = 用户态 VMM + 薄内核 guest 设施、不提供原生 KVM 兼容接口（V1 已采纳）」，但未正面回答「**用户态 hypervisor 是否被允许**」。结论：

- **被否决的是「内核暴露 `/dev/kvm` 式 ioctl ABI 兼容层」**——理由（26 §9.2 / 00 V1）：KVM 大 ioctl ABI 会锁死内核内部（与 23「保留破坏权」冲突）、把设备/中断模拟逻辑拉进 TCB、与「尽快交权、最小 TCB」铁律相悖。
- **被允许的是「用户态 hypervisor / VMM」**——因为用户态 VMM 本质只是一个普通进程：它持有 `GUEST_CREATE` / `VM_MANAGE` 专属 capability（26 §7.2 V2 待 07 定稿 rights 位图时回填，建议按 38 §3.2「新增专属 bit、不复用 MANAGE/GRANT」原则分配，如 bit 39/40），经 `meu_spawn` 创建 guest 子 Job，用内核提供的极薄 `guest`/`vcpu` 一等对象跑 guest 内核。它**受 capability 与 Job 账本双重约束**（CPU 时间走 Job 账本、设备经 device VMO 授予），与容器落在**同一条信任边**上。
- **结论句**：V1 否决的是「KVM ABI 兼容」这一内核契约，不是「在用户态跑 hypervisor」这一能力。Firecracker 式 microVM 在 MeuOS 上的等价实现 = 用户态 VMM + `guest`/`vcpu` 设施，而非 KVM。

### 5.2 容器（L1）：capability+Job 的声明式实例化

- 容器 = 一个**容器根 Job**，由 manifest 组装（26 §4.2）：`job_quota`（CPU/内存/句柄/IO/进程数）+ `capability_set`（收窄后的初始句柄 rights）+ `namespace_view`（unveil 锁定的 reveal 集）+ `pledge_default` + 可选 `rootfs_vmo`（子树 CoW 快照，06 §4.3）。
- 与 OCI 兼容：OCI `config.json` 经容器管理器**翻译**为上述 manifest（不模拟 cgroup 内核接口，04 §5.3 待决），避免引入 cgroup 兼容负担。
- **绝大多数「隔离不可信代码」用例在 L1 即可满足**（对应 Firecracker 的「每函数一 VM」用例在 MeuOS 用 L1 容器达成，无需真 VM 的启动成本）——只有「需跑另一个内核 / 异构 ISA / 强故障封闭」才升 L2。

### 5.3 VM（L2）：用户态 VMM + 薄内核 guest 设施

- 内核 guest 对象（Rust 入 TCB）：`guest`（GPA 由一组 VMO 支撑，接 03 §4.4 device VMO）、`vcpu`（CPU 时间计入 VMM 所属 Job 账本，26 §5.1）。
- 用户态 VMM（Rust 但排除出 TCB，类比 02 §4.2 兼容层）：设备模拟、guest 启动、trap 转发；须持 `GUEST_CREATE`/`VM_MANAGE` 能力。
- **设备授予**：经 device VMO + IRQ cap（接 00 C8），guest 直通须 IOMMU 隔离（10 §5.2）；未经 capability 的设备对 guest 不可见。
- **撤销**：`close` guest/vcpu 句柄即触发派生链回收（07 §4.5 / 03 §4.4），等价于 seL4 `Revoke`。
- **VM 用途边界**：跑 capability 模型容纳不了的负载（不可信第三方内核、隔离测试、异构 OS）；**绝不**用于跑 Linux 二进制（接 08，否决 WSL2）。
- **TCB 归属**：guest 设施核心入 TCB；VMM 排除出 TCB，以 fuzz/sandbox 补偿（02 §5.3）。

## 6. 跨架构（五架构）隔离一致性

### 6.1 核心命题：隔离第一性与硬件虚拟化解耦

MeuOS 的隔离第一性（capability + Job）是**纯软件、与硬件虚拟化扩展无关**的。因此：

- **L0/L1（进程级 / 容器级隔离）在五架构上语义完全一致**——沙箱 = 受限 capability 集合，不依赖 VT-x/NV/H-ext。同一份 manifest、同一套 rights 位图、同一套 Job 账本，在 x86_64 / aarch64 / riscv64 / loongarch64 / i386 上表达相同的隔离语义。差异只在于底层页表/中断语义的薄后端（01 §5-6、03 §2.1「统一抽象 + 每架构薄后端」）。
- **只有 L2（VM）随硬件虚拟化扩展有无而变**——这是隔离谱系里唯一「架构相关」的一层。

### 6.2 五架构隔离一致性表

| 架构 | L0/L1 沙箱（capability+Job） | L2 VM（硬件虚拟化） | 一致性处理 |
|------|------------------------------|---------------------|-----------|
| **x86_64** | ✅ 完全一致 | ✅ 原生（VT-x/VMX、EPT） | guest 设施抽象 `arch/vm/` 提供 VMX 后端 |
| **aarch64** | ✅ 完全一致 | ✅ 原生（VHE 作 host EL2、NV 嵌套） | `arch/vm/` 提供 EL2 后端 |
| **riscv64** | ✅ 完全一致 | 🟡 原型期可支持（H-extension，依赖 QEMU/硬件） | 优先级次于 x86/aarch64；抽象层预留 |
| **loongarch64** | ✅ 完全一致 | 🟡 后置（LSVZ/LVZ 扩展，工具链/验证成熟度低） | 内核 guest 设施抽象预留后端，原型期不实现 |
| **i386** | ✅ 完全一致 | ❌ 不支持（32 位 x86 无虚拟化扩展） | `arch/vm/` 后端直接返回 `ENOSYS`，不模拟；i386 仅跑 L0/L1 |

> **跨架构一致性结论**：Day 1 最小隔离集（§7）在五架构上**完全等价**——这是 capability 模型相对「依赖 KVM 的 Linux 容器/VM」的根本优势：隔离不绑定硬件虚拟化。i386 仍能获得完整的进程级/容器级隔离（其 sandbox 与 x86_64 同源），只是不能跑真 VM。统一抽象原则（01 §5-6）确保五架构的薄后端差异不侵蚀用户态看到的隔离语义。

## 7. Day 1 最小隔离集

> 本节给出 Day 1 必须落地的**最小隔离集**（务实、可自举、不超 TCB）。它须与 C4（兼容层不绕过）、C15（网络用户态，含 `NET_*` right）、V1（用户态 VMM）自洽。

### 7.1 Day 1 必含（M0–M2 即可用）

| 隔离能力 | Day 1 形态 | 来源 / 对齐 |
|----------|-----------|-------------|
| **进程级最小权限（L0）** | 每个进程 spawn 即最小 rights 集；pledge/unveil 默认 deny、只能收缩、越界即终止（07 §4.2） | 07（Day 1 最小集）、29 §1 |
| **Job 资源账本（L0/L1 边界）** | 每个进程/Job 带 CPU 权重、内存上限、句柄数上限、进程/线程数上限；超额即失败/限流不杀（04 §4.4；29 I4） | 04 / 29 |
| **每进程命名空间视图** | 默认全不可见，unveil 显式 reveal、可锁定；无全局 `/proc`（C3 已采纳，06 §4） | 06 / 00-C3 |
| **兼容层默认沙箱（C4）** | Linux 二进制与原生进程同受 L0/L1 受限集合；fork 默认全量 CoW；逃生通道 = 显式扩大该 Job capability 投影、记入 Job 账本、可撤销 | 00 C4 / 08 |
| **网络沙箱（C15）** | socket 句柄持 `NET_*` right（NET_CONNECT/LISTEN/BIND/Raw）；默认 deny、显式授予；无 seccomp 过滤 | 25 / C15 / 38 §3.1 |
| **调试权默认 deny** | `DBG_*` 全 deny（含 `DBG_POKE` 永不默认），无调试 root（17 C9 / 07） | 07 §第四轮回写 C9 |
| **生命周期边界** | 父 Job 终止传播杀子树；监督者经 exception channel 决策 restart/kill（04 §4.5 / 00 A9） | 04 |

### 7.2 Day 1 不强制（演进期补齐）

| 能力 | Day 1 状态 | 演进路径 |
|------|-----------|---------|
| **L1 容器（显式容器根 Job + manifest）** | 机制已具备（Job+capability+namespace 组合），但容器运行时/OCI 翻译器可后置 | 由容器管理器服务翻译 OCI，不阻塞内核自举 |
| **L2 VM（用户态 VMM）** | 内核 `guest`/`vcpu` 设施 + `GUEST_CREATE`/`VM_MANAGE` right；原型期仅在 x86_64/aarch64 启用 | riscv64（H-ext）→ loongarch64 后置 → i386 不支持 |
| **嵌套虚拟化** | 一律不支持 | 后续评估（x86_64 VMX / aarch64 NV） |
| **跨架构 VM guest** | 不支持 | 后续评估（异构 ISA guest） |

> **Day 1 最小集的判语**：隔离的「地基」= L0/L1 的 capability+Job 集合，在五架构上 Day 1 即一致可用；VM 是可选增强，且只在有硬件虚拟化扩展的架构上提供。这与「务实、现代化、最小 TCB」的 MeuOS 取向一致——先把不变的第一性（capability+Job）做扎实，再按需叠加 VM。

## 8. 推荐方案：Day 1 与演进（MeuOS 务实推荐）

### 8.1 推荐方案总览

1. **隔离第一性 = capability 集合 ∩ Job 账本**（本文 §3）。沙箱 = 受限 capability 集合（句柄+rights+namespace 视图），VM = 该集合外额外持 `guest`/`vcpu` 的受限 guest。二者同构、同一条信任边。
2. **Day 1 即提供跨五架构一致的 L0/L1 隔离**（§6/§7），不依赖硬件虚拟化；VM（L2）仅在有虚拟化扩展的架构启用。
3. **VM 采用用户态 VMM + 薄内核 guest 设施**（26 §5 已定稿）；**V1 不提供 KVM ABI，但允许用户态 hypervisor**（§5.1 澄清）。
4. **网络沙箱经 `NET_*` right 表达**（C15 同构），兼容层默认不绕过沙箱（C4 同构）。
5. **拒绝** Linux 七机制叠加、gVisor 式 syscall 拦截、WSL2 式「VM 承载兼容」；**借** Fuchsia job/process 嵌套、seL4 cap 化 VM、Android 应用沙箱、Windows Job 对象、Firecracker 轻量 VM 用例。

### 8.2 Day 1（M0–M2）

- 落地 §7.1 全部 L0/L1 能力：pledge/unveil 默认 deny、Job 账本、每进程命名空间、兼容层默认沙箱（C4）、网络 `NET_*` right 沙箱（C15）、调试权默认 deny、生命周期传播。
- 内核仅保留 `guest`/`vcpu` 一等对象接口（即便 Day 1 不跑 VM，接口预留、TCB 内 Rust 实现）；`GUEST_CREATE`/`VM_MANAGE` right 在 07 rights 位图定稿时回填（接 26 V2 / 38 §3.2 专属 bit 原则）。
- 自举链（mcc/meuos-libc）所需句柄集显式声明（07 §5-7 / 11），避免隐式特权。

### 8.3 演进（M3 之后）

- **容器运行时**：用户态容器管理器把 OCI `config.json` 翻译为 Job manifest（不模拟 cgroup 内核接口）；容器内 OOM 归因落 VMM/子 Job 边界（26 V3）。
- **VM 平台扩展**：x86_64/aarch64 原生 L2 → riscv64 H-ext → loongarch64 后置；i386 永久不涉 VM。
- **强隔离 guest**：对不可信第三方内核/异构 OS 提供 restricted VM（Fuchsia/Android pKVM 思想），guest 与 host 强故障封闭。
- **形式化衔接**：隔离不变量（capability 边界 = 攻击面边界）接入 20 I1–I7（无凭空 capability、revoke 全断、rights 只减、账本不超额），用否定式测试（22）证明越权必失败。
- **可选增强**：CHERI 指针级能力在 RISC-V/Arm Morello 上加固句柄不可伪造（07 §4.4）；远程证明/受保护 VM 待 32 D-SB7 裁决后评估。
