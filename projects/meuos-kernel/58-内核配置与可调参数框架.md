## 1. 一句话结论（先给答案）

MeuOS 的可配置性应当是一座**「能力作用域化、强类型、可版本、可审计、可回滚」的配置框架**，而非一袋散落的旋钮。其 TCB 保全铁律是：**每个 tunable 都是「量变」、绝不「质变」；安全关键不变量只在编译期固定（C16）；错误的配置最坏只导致性能退化 / OOM / 死锁倾向，绝不扩大 TCB 或降级安全模型。** 框架由五件交付物组成——① 分类判定器（任何旋钮先过三格：BUILD / FIXED / RUNTIME）；② Day1 带界最小集（§8）；③ 与 `07` 对齐的「谁可调」矩阵（§5）；④ 误配置安全分类与遏制（§6）；⑤ 配置即版本化子树的 `.msys` 协同协议（§7）。**「灵活」应尽最大可能住在编译期（零运行期 TCB 代价），运行期 tunable 只保留真正需要免重编即可变的那一小撮有界旋钮。**

## 2. 「应该是什么样」——解构型推演（灵活 vs 最小 TCB）

### 2.1 先解构「灵活」与「最小 TCB」这对张力

「内核可配置」听起来是好事，但它与「最小 TCB」存在结构性张力：

- **灵活 = 更多开关 = 更多代码路径 / 更多分支 = 更大的 TCB 与验证面**。一个「可关掉 capability 检查」的开关，本身就是 TCB 的一部分，且是最危险的那种（它决定是否还相信其余 TCB）。
- 因此「灵活」不是越多越好，而是**「灵活住在哪一层、由谁付代价、是否进入 TCB」**的问题。

解构后可见一个被 Linux 颠倒的常识：**编译期灵活是「免费的灵活」**。一个未编入内核镜像的 feature，根本不在运行期二进制里——它不占运行期 TCB、不增加运行期攻击面、不需要运行期校验。而**运行期灵活（tunable）是要付钱的灵活**：每个运行期可变旋钮都是一份「运行期可变状态 + 边界校验 + 授权 + 审计」的永久负担，且构成运行期 TCB 的「数据面」边界。

→ 推演落点（与 `30` §1 同构但更尖锐）：**把灵活尽量推向编译期（免费、运行期 TCB 中性），运行期 tunable 只保留「部署间 / 每-Job 免重编即需变」的那一小撮有界量变旋钮**。这与 Linux 把一切推到运行期 sysctl 的取向恰好相反，是 MeuOS 相对宏内核的结构性机会。

### 2.2 再解构「最小 TCB」——旋钮的「归属」决定它是否在 TCB

TCB = 「若出错就会破坏安全论证的那份代码」。据此可对旋钮做归属判定：

- **旋钮若改变「哪些特权代码被编入 / 链接进 TCB」** → 它属于 TCB 的**出身（provenance）**，必须在**编译期**固定并经 build 契约审计（seL4 立场：配置是验证产物的输入，不是运行期对象）。
- **旋钮若只改变「已编入 TCB 的那份代码用哪个值」** → 它是**数据**，受边界约束后**不在 TCB 内**（错误只影响行为，不破坏「代码正确」的论证）。
- **旋钮若改变「安全不变量本身（capability 检查开关、panic 行为、沙箱默认）」** → 它**根本不是旋钮**，必须在编译期固定且运行期不可见（C16，与 `15` D1「无全局关沙箱」同构）。

→ 得到一条** crisp 规则**（框架分类器的内核，见 §4）：
**若翻转该旋钮会改变「哪份特权代码运行」→ 编译期；若只改变「那份代码用什么值」→ 运行期；若改变「安全不变量」→ 禁止运行期、编译期固定。**

## 3. 多系统参照——聚焦「谁能配」与「能否回滚」两维

> 横轴换一个角度（不同于 `30` §2 的「feature/tunable/可回滚」三列），专看本框架关心的两维：**(a) 配置权的归属模型（root？capability？策略引擎？）**；**(b) 配置是否事务化 / 原子 / 可回滚**；**(c) 配置住在 TCB 内还是外**。结论列给 MeuOS 取舍。

| 系统 | 配置权归属 | 原子/回滚 | 配置住 TCB 内/外 | **MeuOS 借 / 不借** |
|------|-----------|-----------|------------------|---------------------|
| **Linux** | Kconfig=构建期（自由，零运行期代价）；sysfs/sysctl=运行期、**`CAP_SYS_ADMIN`（类 root）全局可变**、无 schema/版本/回滚 | 弱：sysctl 改了即生效、无原生回滚 | sysctl 全局可变内核参数是**运行期 TCB 数据面**的一部分（膨胀即攻击面） | 借 Kconfig 依赖图；**不借** sysctl「root 即改 + 不可回滚」模型 → 代以 capability 守护 + 版本化 + `.msys` 回滚 |
| **Windows** | 注册表=运行期、权限模糊（ACL 但不强制最小权）；**组策略/GPO**=AD 域推送、可强制、结构化、可回滚到上一 GPO | 中：GPO 可回退、注册表可备份但无原子语义 | 注册表是全局可变状态黑洞，权限模型与 capability 世界冲突 | **不借**注册表；组策略的「托管策略可强制 + 可回退」思想可借鉴为 §7 的托管层（managed config）雏形 |
| **Fuchsia** | build-time（GN feature）+ 组件级结构化 manifest 配置；运行期 tunable **受 capability 守护、无全局可变内核参数**；syscall 不稳靠 system ABI revision | 强：包签名 + 组件级 + 可版本化（FIDL） | 运行期配置**在组件私有命名空间**，内核零全局可变参数 → 运行期 TCB 数据面极小 | **最贴切（运行期层）**：capability 守护 + 无全局可变 + 组件私有 |
| **seL4** | **编译期证明配置**，运行期极简（root task 自举后用户态自管） | 强：证明配置确定性、可复现 | 配置权归**构建/证明**权威，运行期无对应开关 → 运行期 TCB 完全不含配置面 | **借**「安全关键参数编译期固定、运行期不可改」；配置权威=证明/构建，非运行期权 |
| **macOS** | 用户 `plist` 偏好（结构化、签名）+ **Config Profile / MDM** 托管覆盖（分层：用户 < 托管，托管可强制） | 中：Profile 可远程移除回退、有 MDM 管理 | 偏好在用户态、托管在配置管线，内核极少可变 | 借「**两层覆盖 + 托管可强制 + 签名**」；对应 `.msys` 发布覆盖 + per-Job 投影 |
| **ChromeOS** | 构建配置 + **企业策略（Policy）引擎**：结构化、版本化、capability 作用域、随签名镜像可回滚 | 强：配置随系统镜像签名、回滚即换卷 | 策略在用户态策略引擎、内核零全局可变 | **最佳综合（托管+回滚）**：结构化策略 + 镜像级原子回滚，正是 `.msys` 协同的范本 |

> 结论骨架：运行期配置权模型取 **Fuchsia/ChromeOS（capability 守护的组件/策略私有作用域，无全局可变内核参数）**；安全关键固定取 **seL4（编译期证明、运行期不可见）**；分层覆盖 + 托管可强制取 **macOS MDM / Windows GPO 的思想**（但权限模型换成 capability，不换成 ACL/root）；回滚杠杆取 **ChromeOS 镜像级原子回退 = MeuOS `.msys` 子树级 CoW repoint（06/23）**。实现全部自主研究，不缝合。

## 4. 编译期 vs 运行期——分类判定框架（框架中心件）

> 本节能让「未来任何新旋钮」都有据可依地分类，是 `30` 留作「待决/设计协同」的 operational 化。判定器输出三格之一：**BUILD / FIXED / RUNTIME**。

### 4.1 判定决策树（按顺序，命中即停）

| # | 提问 | 是 → 归类 | 否 → 下一问 |
|---|------|-----------|-------------|
| Q1 | 翻转它是否改变「**哪份特权代码被编入/链接进 TCB**」？ | **BUILD**（编译期 feature，权威=构建/发布，进 build 契约审计） | Q2 |
| Q2 | 它是否改变「**安全/不变量**」（capability 检查开关、`panic` 行为、沙箱默认、无 root）？ | **FIXED**（编译期固定、运行期不可见不可改，C16） | Q3 |
| Q3 | 它是否需「**免重编**即可变」——部署间不同、或**每-Job 运行期不同**？ | 进 Q4 | **BUILD**（连免重编都不需要 → 编译期定值即可） |
| Q4 | 其变化是「**量变（有界数值/枚举）**」还是「**质变（结构/算法/能力集）**」？ | 量变 → **RUNTIME**（有界 tunable）｜ 质变 → **BUILD** | — |
| Q5 | 若配错，是否可能「**扩大 TCB / 绕过 capability / 打开沙箱**」？ | 任何「是」→ **禁止作 tunable**（须 FIXED 或 BUILD，或整体否决） | 通过 → **RUNTIME** |

### 4.2 三格语义与代价

| 格 | 含义 | 配置权威 | 运行期可见/可改 | 代价承担 | 在 TCB 内？ |
|----|------|----------|----------------|----------|-------------|
| **BUILD** | 决定「镜像能做什么 / 哪些代码在 TCB」 | 构建系统 + `.msys` 签名发布链（**供应链权威，非运行期 right**） | 不可见不可改（只消费 build manifest） | 重、不可逆（重编 + 重发） | 是（作为 provenance，由 build 契约约束） |
| **FIXED** | 安全不变量，编译期固化 | 同 BUILD | 运行期**根本不出现在 tunable 集合** | 同 BUILD | 是（恒编入，不可关） |
| **RUNTIME** | 已编入能力的「跑多猛」量变旋钮 | `CFG_WRITE`（07 §4.1，bit 10）于 config-subtree handle | 可写、有界、可观测、可回滚 | 轻（边界校验 + capability 守护 + 审计） | **否**（是受约束的数据，错误不破坏代码正确性） |

### 4.3 「免费灵活」原则（落实 §2.1）

判定器落到 MeuOS 子系统的取向：

- **尽最大可能归 BUILD**：五架构差异（大页 / ASID 宽度 / NUMA / IOMMU / 页表级数）、i386 纯 C 段裁剪（02 C2、15 C6）、调度/分配器**算法选型**（EEVDF vs RR）、调试/发布构建档、`uname` 报告值（08 C14）——这些「免重编也不变」或「改变 TCB 出身」的，一律 BUILD。
- **RUNTIME 只留真·量变且须免重编可变者**：调度权重、资源账本阈值、分配器水位、看门狗超时、可观测采样——且每个有硬边界（§8）。
- **FIXED 是安全地基**：capability 检查、`panic=abort`、pledge/unveil 默认 deny、无配置 root——C16 清单，运行期集合中无其席位。

## 5. 与 capability（07）的权限边界——「谁可调」矩阵

> `30` §4 已立「配置即 capability 对象」；本节把「**谁在何时对哪棵子树持什么 right**」做成矩阵，并澄清一个 `30` 未强调的点：**BUILD 类配置的权威不是运行期 right，而是发布/签名密钥**。

### 5.1 对齐 07 的冻结 rights（权威位图，来自 `07` §4.1 rights 位图全表）

| right | bit（07 统一冻结） | 作用域 | 默认 | 备注 |
|-------|-------------------|--------|------|------|
| `CFG_READ` | **9** | 读 `kernel/config/` 子树（受子树粒度，可经 inspect 可读节点，12 §4.2） | deny | 与 `DBG_*` 同构；`30` 原草案提议 8/9/10，经 `07` §4.1 冻结顺延为 9/10/11 |
| `CFG_WRITE` | **10** | 写某 tunable 子树（受 `config_version` + 有界校验 + fail-closed） | deny | 只能改 RUNTIME 格旋钮，**绝不**触及 FIXED/BUILD |
| `CFG_GRANT` | **11** | 向其他 Job 授予某子树的 `CFG_*` right（受约束 mint，仿 `GRANT` 派生树，07 §4.5） | deny | 只能**收窄**，不可越类放大 |

> 重要区分：`KERNEL_PRIV`（bit 12，D-T1，永不默认）是内核态生死线高危权；**配置调参不是内核特权**——它是受界数据。两者必须严格分离，否则 `CFG_WRITE` 会被误读为「后门」。配置调参的边界由 §4 判定器 + 有界校验保证，不依赖 `KERNEL_PRIV`。

### 5.2 配置子树 handle 与粒度

- 配置面是 inspect 的**可写子树**（12 §4.4）：`kernel/config/{scheduler,mm,ipc,jobacct,watchdog,observ}` + `jobs/<id>/config` + `services/<name>/config`。
- 每棵子树 handle 携带 `{CFG_READ, CFG_WRITE}`，子树级 `CFG_GRANT` 用于向下委托。
- **默认拒绝**：spawn 出的进程不持任何 `CFG_*`（仿 12 §4.2 调试默认拒绝）；要改配置必须从持 `CFG_GRANT` 的对端（监督者/系统服务）显式获授权。

### 5.3 「谁可调」矩阵

| 行为者 | 全局系统子树（`kernel/config/*`） | 本 Job 子树（`jobs/<id>/config`） | 他 Job / 服务子树 | 说明 |
|--------|----------------------------------|----------------------------------|-------------------|------|
| **meu-supervisor（根 Job）** | `CFG_GRANT` + `CFG_WRITE`（系统子树） | `CFG_WRITE` | 经 `CFG_GRANT` 委托 | 唯一持全局 `CFG_GRANT`；自身也只持所需子集，**无「配置 root」**（30 §4.1） |
| **系统管理/配置服务** | 受 supervisor `CFG_GRANT` 限定的子树 `CFG_WRITE` | — | — | 由 supervisor 显式授权，权限=被授予子集 |
| **per-Job 应用** | deny | `CFG_WRITE`（仅自身子树，受父投影上限） | deny | 可调自己、不可调全局/他人；写超父配额即拒（15 D2 同构） |
| **子进程（spawn 出的）** | deny | deny（除非被显式 mint） | deny | 默认零 `CFG_*`，fail-closed |
| **自动调优服务（autoscaler）** | 受 `CFG_WRITE` 限定的子树 | 受 `CFG_WRITE` 限定的子树 | — | 同系统服务，仅在**有界 tunable + `CFG_WRITE`** 闭环内动，不引入新 feature、不碰 FIXED |

### 5.4 权限边界两条铁律

1. **CFG_GRANT 只能收窄**：委托出的 right ⊆ 委托者持有的 right ∧ 限定的子树（07 §4.5 派生树约束）。配置委托**不能**成为提权通道——这与「无全局关沙箱」（15 D1）同源：配置权是**模型内的量变授权，不是模型外的特权后门**。
2. **BUILD 权威 ≠ 运行期 right**：改变 BUILD 类 feature 的「配置权」是**发布/签名密钥**（供应链权威），任何运行期 capability（含 `CFG_*`、`KERNEL_PRIV`、`MANAGE`）都**无权**改变已发布镜像编入了哪些 feature。运行期能消费的，只是 build manifest 中声明的能力集。这杜绝了「运行期把出核服务拉回内核」式 TCB 膨胀。

## 6. 配置错误的安全影响——误配置分类与遏制

> `30` §4.2 用「三道闸」说明恶意/错误配置不扩 TCB；本节把「**配错了会怎样**」做成可分类、可遏制的 taxonomy，直接呼应 `15` D1 三道封顶闸与 `29` 威胁模型。

### 6.1 五类误配置与遏制矩阵

| 类别 | 表现 | 最坏影响 | 遏制机制 | 是否触及 TCB / 安全模型 |
|------|------|----------|----------|------------------------|
| **A. BUILD feature 配错**（误编入不该编的服务） | 默认 profile 选错、构建矩阵把关漏 | TCB 扩大 / 新攻击面 | 仅能经**重编 + 签名 `.msys` 重发**（审计、非运行期可利用）；受 build 契约 + CI 验证 + Day1 最小 profile（§8）约束 | **是（provenance）**，但**不可运行期触发**，归供应链管控 |
| **B. RUNTIME tunable 配错**（内存上限过大、看门狗过小） | 值越界或不适 | 性能退化 / OOM / 活锁 / 误重启 | **有界校验（fail-closed）** + **Job 账本限定爆炸半径**（04 §4.4）+ 可回滚 + 审计事件流（12 §4.4） | **否**——只损可用性/性能 |
| **C. 试图拨动安全不变量**（「关 capability 检查」） | 请求含 FIXED 项 | 无（结构性不可能） | FIXED 项**根本不在 tunable schema**，写入即 schema 校验拒绝（30 §4.2 有界闸） | 结构性不可达 |
| **D. 权限配错**（`CFG_WRITE` 授权过宽） | 误 mint 给不该给的 Job | 该 Job 可乱调自身/他人子树 | `CFG_GRANT` 只收窄 + 可经派生树 revoke（07 §4.5）+ 审计 trail；爆炸半径限该子树 | **否**——仍是量变旋钮，无安全模型权 |
| **E. 分层配置冲突**（bootinfo / `.msys` seed / per-Job 矛盾） | 三层值打架 | 取错值致行为偏移 | **显式优先级 + 冲突时取最严（fail-safe）**（§7.3），非取最松 | **否**——最严即最安全默认 |

### 6.2 误配置遏制不变量（一句话）

**最坏情况 = 可用性 / 性能损失，绝不 = 安全模型在机密性/完整性上的失守。** 这正是 `15` D1「兼容层不击穿 Day1 安全边界」在配置维度的延伸：tunable 是模型内的量变旋钮，FIXED/BUILD 是模型外的不可运行期触及项；任何「配错即降级安全」的路径都被 §4 判定器 + §5 权限边界在数学上排除。

## 7. 与 `.msys` 原子更新（01/06/23）协同——配置即版本化子树

> `30` §5.6 提到 `.msys` 回滚杠杆；本节把「**配置如何骑乘 `.msys` 实现原子、签名、可灰度、可回滚**」落成协议，是本框架相对 Linux sysctl（改了无回滚）的根本杠杆。

### 7.1 两类配置载体骑乘 `.msys`

1. **BUILD feature**：烤进内核镜像 + 一份**签名 build manifest**（随 `.msys` 卷发布）。发布新 feature 集 = 新 `.msys` 版本；回滚 = 把 rootfs 命名空间 repoint 到上一 `.msys`（06 §4.3、23 §5）。原子 + 签名 + 可审计。
2. **RUNTIME tunable 种子**：`.msys` manifest 内一棵只读 `configseed` 子树（即 `bootinfo` 的「系统默认」覆盖层）——每-Job 运行期可覆写。改种子 = `.msys` 更新（可回滚）；per-Job 现场改写 = inspect 写（可经 per-Job 配置版本或子树 CoW 快照回退，06 §4.3）。

### 7.2 三层优先级（显式、fail-safe）

```
bootinfo 默认（最低，来自 09 Stage 0–2）
   <  .msys manifest 种子（发布覆盖，来自 06 §4.1）
      <  per-Job 现场写（最高，受 CFG_WRITE + 有界 + 可回滚）
冲突裁决：取「最严（most restrictive）」胜，而非最松——fail-safe
```

### 7.3 配置即版本化子树（CoW + 漂移检测）

- 一次 tunable 变更 = 在**配置版本树**上的一次提交：系统级版本由 `.msys` 承载，per-Job 级版本由 Job 账本承载；两者皆 CoW 快照（06）→ **天然可灰度、可回滚**。
- **漂移检测（安全遥测）**：运行期 config（inspect 子树）+ per-Job 现场写，可随时与 `.msys` 发布种子 diff，检测「配置漂移」——异常漂移即 `12` 事件流 + `29` 威胁模型的输入（谁在无发布的情况下改了系统级旋钮？）。
- 这是 MeuOS 相对 sysctl「改了即生效、错了只能手改回」的结构性胜势：**每次配置变更都可命名、可签名、可灰度、可回滚、可审计**。

## 8. Day1 最小集——可交付的编译期 feature + 运行期 tunable 清单

> 把框架落到「**原型期真正 ship 什么**」。凡未列入者 Day1 默认-out 或 FIXED，避免 sysctl 式膨胀（`30` §6）。边界值取自 `03`/`04`/`09`/`12` 接口与 `45`（CAP_RT bit 45）。

### 8.1 Day1 BUILD feature（minimal profile，其余默认-out）

| 类别 | Day1 取值 |
|------|-----------|
| **TCB 恒编入** | capability 监视器 / IPC 端点 / 调度核心 / VFS 抽象 / `panic=abort` / 无配置 root（**恒在，不可关**） |
| **lean hybrid** | FS / 网络 / 驱动 / 监督策略 **Day1 全部出核**为用户态服务（00-A6、C15 已采纳） |
| **五架构** | x86_64 + aarch64 基线；i386 = Rust `.o` 链接交付（15 C6，非降级）；NUMA **off**、IOMMU **有则开**、大页 **off**（编译期定值） |
| **兼容层** | mkit 子集 direct-mapped（08 C12） |
| **调试构建档** | 发布构建：inspect + 事件流编入、符号表外置；调试构建：符号表内嵌（编译期档） |

### 8.2 Day1 RUNTIME tunable 清单（带硬边界、capability 守护、可版本）

| 子树 | 旋钮 | 类型 / 边界 | Day1 默认 | 谁持 `CFG_WRITE`（Day1） |
|------|------|-------------|-----------|--------------------------|
| `kernel/config/scheduler` | EEVDF 公平权重 | int ∈ [1, 1024] | 100 | supervisor |
| 同上 | RR 时间片 | enum/range ∈ [1ms, 100ms] | 10ms | supervisor |
| 同上 | RT 优先级天花板 | int ∈ [0, MAX_RT_PRIO]；**建 RT 线程需 `CAP_RT`（45 bit 45）** | 按架构 | supervisor |
| `kernel/config/mm` | buddy 预留池比例 | ratio ∈ [0%, 15%]（03 §5-3） | 5% | supervisor |
| 同上 | SLUB 尺寸档 | 固定枚举（编译期上限内） | 默认档 | supervisor |
| 同上 | OOM 策略 | enum {notify-supervisor, job-lru} | notify-supervisor | supervisor |
| `kernel/config/ipc` | Channel 最大消息 | ≤ 编译期上限（05） | 编译期上限 | supervisor |
| 同上 | EventPort 阈值 | int ∈ [1, 1024] | 64 | supervisor |
| `kernel/config/jobacct` | CPU/内存/句柄/IO 上限 | 每值 ≤ 父 Job 投影（15 D2） | 由根 Job 派生 | supervisor + **per-Job 应用持自身子树 `CFG_WRITE`** |

| 同上 | 事件流 ring buffer | range ∈ [64KB, 8MB] | 1MB | supervisor |

> 纪律：每个 tunable 写即校验（fail-closed）；读受 `DBG_INSPECT`（12）；写受 `CFG_WRITE`（bit 10）；全部可被 `.msys`/per-Job 版本回滚（§7）。

### 8.3 Day1 **非** tunable（必须 FIXED，列出以正视听）

capability 检查恒开 · `panic=abort` 不可切 unwind · pledge/unveil 默认 deny · 无 root/无配置 root · `CFG_*` 默认 deny · `KERNEL_PRIV`（bit 12）永不默认 · 出核服务不可运行期拉回内核。

## 9. MeuOS 推荐（框架落点）

1. **采纳三格分类判定器（BUILD / FIXED / RUNTIME）作为任何新旋钮的决策框架**，并固化为内核 build 契约 + CI 的 `config-classify` lint（拒绝「触碰安全不变量的 tunable」）。
2. **「免费灵活」原则**：尽最大可能把旋钮归 BUILD（零运行期 TCB 代价），RUNTIME 只留真正免重编即需变的有界量变旋钮——反 Linux 把一切推运行期。
3. **权限边界**：`CFG_READ=9` / `CFG_WRITE=10` / `CFG_GRANT=11`（07 §4.1 冻结）挂在 config-subtree handle；默认 deny；`CFG_GRANT` 只收窄；**BUILD 权威 = 发布/签名密钥，永非运行期 right**；配置调参 ≠ `KERNEL_PRIV`。
4. **误配置遏制不变量**：schema 校验 + Job 限定爆炸半径 + fail-safe 优先级 ⇒ 最坏可用性/性能，绝不安全模型失守（呼应 15 D1）。
5. **.msys 协同**：配置 = 版本化 CoW 子树；BUILD 进签名 manifest、tunable 种子进 `.msys` seed、现场写进 per-Job 版本；可漂移检测。
6. **Day1 最小集**：ship §8 的 minimal profile + 13 项带界 tunable，端到端证明框架，不沾 sysctl 式膨胀。
7. **反目标（重申自 30）**：无全局可变内核参数表；无运行期关沙箱开关；无注册表式全局可变；BUILD 与 RUNTIME 永不混置。
