## 1. 概述与目标

### 1.1 为什么「统一文件系统层」是三大方向的地基之一

「文件系统」在 MeuOS 里不是「磁盘上的目录树」那么窄。方向①把它定义为**统一资源层**：它既要表达普通文件，又要表达设备、进程、网络等一切可被「按名寻址、按权访问」的资源，并且要**天生携带校验和/压缩/加密**与**原子系统更新**能力。换句话说，它是把「统一命名空间」「最小 TCB」「capability 安全」三件事落到一个可操作的平面上的关键子系统。

这一层设计得是否干净，直接决定：
- 方向③的 capability 能否以「路径 = 一种 capability」自然表达（见 07 的「维度C：统一命名空间」）；
- 方向②的 spawn 监督能否绑定「进程运行在哪个 sysroot 版本」做原子切换与回滚；
- 最小 TCB 能否成立——FS 逻辑体量巨大、迭代快，若塞进内核即污染 TCB（见 01 已将其划为用户态服务）。

### 1.2 本文要回答的问题

1. 内核文件系统（统一资源层）**应该是什么样**？统一命名空间如何把设备/进程/网络/普通文件表达为统一对象，而不沦为 `/proc+/sys+/dev` 的拼凑？
2. 内置校验和/压缩/加密应该落在**哪一层**（块层 vs extent 层 vs 卷层），如何与 capability 安全联动（密钥即 capability？）。
3. 原子 `.msys` sysroot 更新机制应该是什么形态（A/B 分区 / overlay / 快照式 repoint），失败时如何回滚，如何与 spawn 监督协同？
4. 与 IPC（05）/ 内存管理 VMO·VMAR（03）/ 安全 capability rights（07）/ 进程 Job 资源账本（04）的**接口边界**在哪，避免与其他子领域重复或冲突？
5. 对标 Linux / Windows NT / macOS / Android / 塞班 / ChromeOS，MeuOS 的**自主取舍**是什么，差异在哪？

### 1.3 不在本文范围内

- 具体磁盘格式字节布局、B-tree 节点实现细节——本文给结构原则，实现细节留给执行层。
- 给 04/05/07/09/10 下结论——本文只**声明依赖与协同点**（§4.4），不替它们拍板。
- 具体 syscall 兼容清单（见 `08-Linux兼容层.md`）。

## 2. 设计约束与上下文

### 2.1 三大方向对统一文件系统的硬约束

| 方向 | 对统一文件系统的直接约束 | 推论：应处的特权层级 |
|------|--------------------------|----------------------|
| ① 统一文件系统层（校验和/压缩/加密 + 原子 `.msys` 更新 + 统一资源命名空间取代 /proc+/sys+/dev） | FS 是策略重、代码量大、迭代快的子系统；它必须是「统一资源命名空间」这一覆盖全系统抽象的承载者 | **用户态服务**（内核仅提供块设备能力句柄、VMO/页错误 pager 原语、capability mint 授权） |
| ② spawn 进程管理（内建监督、资源账本 Day 1） | 监督与资源账本需要把「进程绑定到某个 sysroot 版本」作为一等概念；sysroot 切换要原子、可回滚 | 文件系统提供**快照 + 原子 repoint** 原语；切换决策由用户态监督服务（04）做出 |
| ③ capability-based 安全（Day 1 唯一模型） | 命名空间里的每个节点、每个文件都必须是 capability；权限随句柄走；密钥管理不能独立于 capability | 路径即 capability 的命名维度；**密钥 unwrap 权 = 文件句柄的 right**；撤销句柄即撤销访问与解密权 |

关键张力：方向①②③都希望「把 FS 搬出内核以缩小 TCB、以 capability 统一授权」，而 Linux ABI 兼容（见 2.3）要求 `open/read/write/mmap/stat` 等热路径低延迟。纯微内核式「每次文件操作一次 IPC 到用户态 FS 服务」在热路径上代价过高——这与 01 选定 lean hybrid 的动机完全一致：FS 服务留在用户态（缩 TCB），但内核提供 **VMO + pager** 与 **capability mint**，让数据访问走内核直连（mmap 零拷贝）、仅元数据/控制走 IPC。

### 2.2 与「混合内核 / Rust-C 边界」的对齐（见 01/02）

- **FS 服务本体 = 用户态 Rust 服务**：目录树、命名空间聚合、extent 分配、压缩/加密/校验和逻辑、CoW、快照——全部在用户态，享受内存安全且处于 TCB 之外，可独立重启/升级（契合「升级 = 换一个 `.msys` 文件」）。
- **内核侧只提供 FS 依赖的「机制」**（Rust 关键 + C/asm 底层）：
  - 块设备能力句柄（由 10 的设备驱动服务经 capability 网关授予，FS 服务只拿到它所需块设备的 `READ/WRITE/block-io` 权）；
  - VMO 对象与 **pager 原语**（FS 服务作为某文件 VMO 的 pager，缺页时由内核向 FS 服务请求页面——这是用户态 FS 与内核零拷贝 mmap 的桥梁，详见 §4.4.1）；
  - capability mint 授权（FS 服务可请求内核为其创建「文件句柄 / 文件 VMO」并以受限 rights 转交客户端，内核负责强制 rights）。
- **加密/压缩热路径**：若实测证明 Rust 加密 throughput 不足，压缩/加密的极热函数允许以 C/内联汇编实现并经 Rust 侧 safe 封装（对齐 02 的「底层 C 热点」原则），但密钥管理、权限判定必须留在 Rust/TCB 侧。

### 2.3 Linux ABI 兼容目标带来的张力

MeuOS 要让已有 Linux 二进制可运行（经 08 兼容层）。这带来两条压力：

1. **路径语义保真**：Linux 程序隐含假设 `/proc`、`/sys`、`/dev`、`/`、`/tmp`、`/home` 等全局可见、POSIX 语义（`open` 返回 fd、`read`/`write`/`mmap`、`O_CREAT`/`O_EXCL`/`rename` 原子性等）。MeuOS 的「每进程 capability 命名空间」与 Linux 的「全局共享命名空间」语义不同——兼容层需把 Linux 的全局路径假设**翻译**为「进程在 spawn 时获得的命名空间绑定 + 按需 reveal」（对齐 07 的 unveil 翻译），而非在内核重建全局 `/proc`。
2. **性能**：`read/write/mmap` 高频。靠 §4.4 的 VMO + pager 让 mmap 走内核零拷贝；小 `read/write` 走 IPC 到 FS 服务，必要时 FS 服务把频繁访问的小文件以 VMO 形式下发，避免每次 IPC。

这两条共同说明：MeuOS 不能走「每个 syscall 一次 IPC」的教科书微内核老路，也不能走「FS 全在内核」的宏内核老路——**FS 逻辑在用户态、数据通路在内核（VMO/pager）** 是 lean hybrid 在文件系统上的精确体现。

## 3. 业界方案对比

本节按方法论要求，对至少六类现实系统做「思想取长补短」式参照，结论在 §4 收敛为 MeuOS 自己的取舍。

### 3.1 Linux（VFS / ext4 / btrfs / overlayfs）

- **VFS（虚拟文件系统）**：用 `inode` / `dentry` / `file` / `super_block` 抽象统一不同底层 FS；但「统一」只到「文件系统类型」层——`/proc`、`/sys`、`/dev` 是各自独立的**伪文件系统（procfs/sysfs/devtmpfs）**挂到全局树的不同挂载点，命名空间靠 `mount` 全局可见（除非 per-process mount namespace 隔离）。这不是「统一资源对象模型」，而是「多个独立 FS 拼到一棵树」。
- **ext4**：成熟的 extent 文件系统，但**默认无校验和（仅元数据 checksum 可选）、无透明加密、无原生压缩**；加密靠上层 `fscrypt`（per-file/dir，key 挂在 keyring，与 LSM 耦合），压缩需额外层。
- **btrfs**：COW + **每 extent 校验和（crc32c/xxhash/blake2）覆盖数据与元数据** + **透明压缩（zstd/lzo/zlib）** + **子卷快照**——这是「校验和/压缩在 extent 层、更新靠快照」的正面范本；但其加密仍依赖块层 dm-crypt（整盘一钥）或 fscrypt（per-file），**加密未与 extent/快照深度联动**。
- **overlayfs**：lower/upper 叠加实现「只读底 + 可变顶」，是容器镜像与「原子更新」的常用手段；但它是叠加层而非真 CoW，回滚=丢 upper，且多 lower 查找开销、元数据操作复杂。
- **代价（与 MeuOS 目标冲突点）**：命名空间碎片化（/proc+/sys+/dev 各为政）、加密与 extent/快照割裂、FS 在内核态膨胀 TCB、更新机制（package manager 就地改文件）非原子、无内建「系统级 sysroot 回滚」。
- **结论**：btrfs 的 extent 校验和/压缩/快照是 MeuOS 的**直接借鉴对象**；VFS 的「多 FS 拼树」是**反面教材**（我们要的是 capability-composed 统一命名空间，不是全局挂载拼凑）。

### 3.2 Windows NT（NTFS / 对象命名空间）

- **对象命名空间（Object Manager）**：NT 内核用统一的**对象管理器**管理一切内核对象（文件、设备、进程、端口…），并通过 `\` 开头的**对象命名空间**（含 `\Device`、`\FileSystem`、`\KernelObjects` 等目录）以路径寻址——这是「统一资源命名空间」思想的鼻祖之一，比 Linux 的 /proc+/sys+/dev 拼凑更统一。
- **NTFS**：日志型、支持文件级加密（EFS，per-file 对称密钥由用户证书公钥包装）、ACL（DAC，非 capability）、USN 日志、重解析点（reparse point，类似符号链接/挂载点），但**无原生透明压缩/校验和的强一致保证**，加密是用户态证书体系而非内核 capability 体系。
- **代价**：对象命名空间虽统一，但权限模型是 DAC/ACL（非 capability），且 FS 与对象管理都在内核态（NT 是「重服务留核」的混合内核，见 01）——与 MeuOS 最小 TCB / FS 出核 / capability Day 1 冲突。
- **结论**：借 NT「对象命名空间 = 统一寻址一切资源」的**思想骨架**（路径即对象引用），但不借其「DAC + 留核」之实；权限改由 capability（07）承载。

### 3.3 macOS（XNU：HFS+ / APFS 写时复制）

- **HFS+**：老牌元数据日志 FS，支持文件/卷级加密（FileVault 2 实为块层 CoreStorage 整卷加密）、无强校验和、空间利用率低。
- **APFS（Apple File System）**：现代 **COW 文件系统**——克隆（clone）与**快照（snapshot）**是 O(1) 元数据操作（共享 extent，写时复制）；**原生加密**支持「无加密 / 单密钥 / 多密钥」且按文件级密钥层次（per-file key 由卷密钥或用户密钥派生包装）；空格优化（`clonefile` 即 CoW 克隆）；崩溃一致性靠 COW + 事务。
- **代价**：APFS 加密仍偏「卷/用户密钥」体系，与 capability 模型未挂钩；FS 在 XNU 内核态（XNU 是内部结构混合，见 01），TCB 大。
- **结论**：APFS 的「快照 + 原子 repoint + per-file 密钥层次 + COW clone」是 MeuOS **sysroot 原子更新与 per-file 加密的直接范本**；但其内核态实现与 DAC 模型不照搬。

### 3.4 Android（F2FS / SDCardFS / scoped storage 隔离）

- **F2FS（Flash-Friendly FS）**：为 NAND 闪存量身设计，log-structured、多线程、支持原子写（`atomic write` 避免数据库部分写）、内置 `fsverity`（文件级校验和/签名，用于 app 完整性校验）。是「校验和在文件层（fs-verity）」的范例。
- **SDCardFS / 存储隔离（scoped storage）**：早期用 sdcardfs（ overlay 式 FAT 桥接）暴露 `/sdcard`；Android 10+ 推行 **scoped storage**——每个 app 只能看见自己的沙箱目录与明确授权的媒体集合，**路径可见性即权限**，与 capability 的 unveil 思想高度同源。
- **代价**：F2FS 加密仍走 Linux fscrypt（keyring + DAC），原子更新靠 A/B 分区（见 3.6）；命名空间隔离是应用层策略，非内核 capability 模型。
- **结论**：借 **fs-verity（文件级校验和/签名）** 与 **scoped storage（路径可见性=权限）** 的思想；其 A/B 分区更新是回滚的兜底参考但非 MeuOS 首选形态（见 §4.3）。

### 3.5 塞班（Symbian 文件服务 / EFS）

- **结构**：Symbian 把文件系统实现为**用户态的「文件服务器（File Server）」**，客户端经 IPC（Symbian 的会话/消息机制）与之通信，文件句柄（RFs/RFile）是客户端持有的服务端会话对象——这是「FS 作为用户态服务、句柄经 IPC 传递」的早期工程范例，且 Symbian 有**平台安全（Platform Security）**能力模型（capability 授予进程，类似 MeuOS 的 07）。
- **代价**：年代早、无现代 CoW/加密/校验和/快照；其能力模型粗粒度（进程级 capability 组合，非对象级句柄 rights）。
- **结论**：借其「FS 用户态化 + 句柄经 IPC + 平台安全能力」的**整体架构取向**（与 MeuOS lean hybrid 的 FS 出核一致），但对象级 rights 与 CoW/加密/快照需现代化。

### 3.6 ChromeOS / Fuchsia（加密态 / blobfs / minfs）

- **ChromeOS**：stateful 分区**默认加密**（dm-crypt / eCryptfs 演进），系统更新走 **A/B 双分区（两个 slot）**——更新写非活动 slot，校验签名后原子切换引导项，失败回退旧 slot；这是「签名校验 + 双 slot 回滚」的成熟工业实践。
- **Fuchsia blobfs / minfs + namespace + pager**：
  - **namespace**：Fuchsia 进程在 spawn 时获得一组 `path → 目录能力` 绑定（**每进程命名空间**），由组件框架组装；没有全局 `/proc` 概念，进程只看见被显式授予的目录。这是「统一命名空间 = capability 组合」的最干净现代范本。
  - **pager**：Fuchsia FS 作为用户态服务，把文件以 **VMO** 形式交给客户端，内核在缺页时经 pager 通道向 FS 服务请求页面——**用户态 FS + 内核零拷贝 mmap** 的桥梁。
  - **blobfs**：内容寻址（hash = 名）的不可变 blob 存储，自带校验和（hash 即完整性），天然防篡改；minfs 为可读写小 FS。
- **代价**：Fuchsia 的 namespace 完全每进程、无全局根，对 Linux 兼容层「全局路径」假设移植成本较高；blobfs 是只读/内容寻址，不能直接当可读写 sysroot。
- **结论**：Fuchsia 的 **namespace（每进程、capability 组合）+ pager（用户态 FS 零拷贝 mmap）+ blobfs（hash=完整性）** 是 MeuOS 最直接的对标；其 A/B 双 slot 思想是回滚兜底参考。

| FS 所在层级 | 内核态（TCB 大） | 内核态 | 内核态（XNU 混合） | 内核态 | **用户态服务** | **用户态服务 + pager** | **用户态服务 + 内核 VMO/pager/capability mint** |
| 与 capability 联动 | 弱（DAC/keyring） | 弱（DAC/ACL） | 弱 | 弱 | 进程级能力 | 句柄即能力 | **强：路径=capability 命名维度，密钥=capability** |

> 结论骨架：**命名空间借 Fuchsia/NT 的「统一寻址」思想、借 scoped storage 的「可见性即权限」；CoW/快照/extent 校验和/压缩借 btrfs/APFS；加密的「per-file 密钥 + 层次」借 APFS/fscrypt 但改挂到 capability（密钥即 capability）；原子更新借 APFS 快照 repoint + ChromeOS 签名校验 + A/B 兜底；FS 用户态化 + pager 借 Fuchsia + 塞班。** 实现全部自主研究，不做缝合怪（见 §4 给出 MeuOS 自己的取舍与理由）。

## 4. MeuOS 选型建议（「应该是什么样」的推演与收敛）

### 4.1 统一资源命名空间：应该是 capability-composed 的每进程命名空间

**先推演「应该是什么样」**：从内核哲学出发——统一命名空间要取代 `/proc+/sys+/dev`，覆盖设备/进程/网络/普通文件。那么理想结构里：
- 一切可被「按名寻址」的资源，都应是**同一类对象**：一个「命名空间节点（ns-node）」，带类型（file / dir / device / proc-dir / net-ns / service / capability-object）。
- 节点的可达性**不靠全局可见**，而靠进程**持有通往该节点的 capability**。一个进程看不到某路径，不是因为「权限被拒」，而是因为它**根本没有通往那个节点的 capability**——这比 Linux「全局可见但访问被 EACCES」严格得多，也天然契合 07 的最小权限。
- 命名空间的「根」不应是内核硬编码的全局树，而应是**进程在 spawn 时由 Job/组件 manifest 组装的一组 `path → 节点能力` 绑定**。

**MeuOS 设计（自主收敛）**：
- **命名空间 = capability 组合树，每进程独立**。spawn 时，父进程/监督者按 manifest 给新进程注入一组绑定，例如 `{ "/": rootdir_cap, "/dev": device_svc_dir_cap, "/proc": proc_svc_dir_cap, "/net": net_svc_dir_cap, "/msys": sysroot_cap, "/tmp": tmp_cap }`。进程看到的「文件系统」就是这组绑定的闭包——没有绑定的路径，对进程而言**根本不存在**（unveil 的反面：默认全不可见，显式 reveal）。
- **FS 服务是命名空间的「根聚合者」，不是全局树的独裁者**。MeuOS-FS 服务持有命名空间根（`/`）并负责普通文件/目录树；但 `/dev`、`/proc`、`/net` 等子树是 FS 服务通过**挂载能力（mount capability）**委托给对应服务的目录能力——设备服务给 `/dev`、进程服务给 `/proc`、网络服务给 `/net`。每个挂载是一个**显式 capability 授予**，不是 Linux 式的全局 `mount`。这样「统一命名空间」在逻辑上统一、在信任上分散（各服务只管自己的子树，符合最小 TCB）。
- **节点解析 = capability 路由**：路径 `/dev/tty0` 解析为：进程命名空间里 `/dev` → 设备服务的目录能力 → 在该目录里查 `tty0` → 得到文件/设备能力。整个过程是能力路由，无全局表。
- **与 07 的互锁（维度 C）**：`unveil("/var/lib/app","rwc")` 本质 = 向进程命名空间注入一条 `path → 该目录/文件的 capability 绑定`；pledge 的 `rpath/wpath/cpath` 约束「该进程未来能否新增 reveal 绑定」。路径即 capability 的命名维度，在此闭环。
- **与普通文件的统一**：普通文件、设备、进程目录、网络资源，对客户端而言**都是「命名空间节点 + 句柄（handle）」**——打开任意节点都返回一个 capability 句柄，区别只在类型标签与 rights。这就是「统一资源层」的本意，而非 Linux 的「普通文件是 file、设备是 chrdev、进程是 proc 魔法」三类异构。

> 与参照系统的差异：比 Linux 的「全局树 + 多伪 FS 拼凑」更统一且更隔离；比 NT 对象命名空间多了 capability rights（替代 DAC/ACL）；比 Fuchsia 每进程 namespace 多了「FS 服务作为根聚合者 + 挂载能力委托子树」的明确分工（Fuchsia 由组件框架做，MeuOS 由 FS 服务 + mount-capability 做，语义等价但归属更清晰）。

### 4.2 内置校验和 / 压缩 / 加密：层位与 capability 联动

**先推演「应该是什么样」**：从「文件系统应该是自保护的存储」出发——数据落盘就该自带完整性（校验和）、应按需省空间（压缩）、应静止即密（加密），且三者都应是**存储对象的属性**而非外挂层。关键问题：落在哪一层？

- **块层（dm-crypt / dm-integrity 式）**：整盘一密钥、整盘一校验和。透明但**粒度粗**——无法 per-file 撤销解密（一钥开全盘 = 一个大 TCB），且与 capability 模型割裂（密钥不随句柄走）。
- **extent / 文件层（btrfs / APFS / fscrypt 式）**：per-extent 校验和、per-file 密钥。粒度细、**能与 capability 联动**（文件的密钥 unwrap 权 = 文件句柄的 right）。
- **卷层（zfs/btrfs 集成）**：与 extent 层重合。

**MeuOS 设计（自主收敛）——三层自底向上：**

```
        文件 / 命名空间层（ns-node, 句柄 rights）
                │
        ┌───────▼───────┐
        │ 加密层 (AEAD)  │  per-file/per-extent 密钥；密钥 unwrap 权 = 文件句柄 right（密钥即 capability）
        ├───────────────┤
        │ 压缩层         │  per-extent，加密前压缩（compress → encrypt → checksum）
        ├───────────────┤
        │ 校验和层       │  per-extent 校验和（覆盖密文，检测 bit-rot）；可选文件级 AEAD 认证标签（防篡改）
        ├───────────────┤
        │ extent 分配层  │  映射 extent ↔ 物理块；CoW；引用计数
        └───────┬───────┘
                │  块设备能力句柄（由 10 经 capability 网关授予，仅 READ/WRITE/block-io 权）
        块设备（virtio-blk 等，用户态驱动服务）
```

1. **校验和（integrity）放在 extent 层，覆盖密文**：每个 extent 存一个校验和（建议 BLAKE2b / xxHash3 类强校验和，非仅 crc32c），校验**加密后的密文**。理由：bit-rot/静默损坏可在读路径确定性检测；且覆盖密文意味着即便加密层密钥更换，校验和仍有效（校验和不依赖明文/密钥）。额外：对需要**防篡改**的文件（如 `.msys` 系统组件），用 AEAD 在文件层加认证标签——这正是 fs-verity（Android）思想，但认证密钥 = 文件 capability 派生的密钥，与 07 联动。
2. **压缩放在 extent 层、加密之前**：先 compress 再 encrypt（加密后的数据不可压，故顺序必须 compress→encrypt）。per-extent 透明压缩（zstd 为主，lzo 备选），压缩决策可按文件类型/策略/冷热。这与 btrfs extent 压缩一致。
3. **加密放在 per-file / per-extent 层，密钥即 capability（核心联动）**：
   - 每个文件有一个**文件密钥（file key）**，由**卷密钥（volume key，受 secure boot / TPM 类根信任保护）**或上级目录密钥派生并包装（key wrapping）。
   - 客户端持有的**文件句柄（capability）若含 `READ`/`WRITE` right，则其派生副本隐含「可 unwrap 该文件密钥」的授权**——即「密钥 unwrap 权 = 文件句柄 right」。客户端没有该句柄，就无法 unwrap 文件密钥，自然无法解密。
   - **撤销（revoke）= 收回句柄 → 同时撤销解密权**：这与 07 的 capability 撤销语义完全一致，回答了待决清单里的「加密密钥是否走 capability 撤销」——**是，密钥访问权生命周期绑定到文件句柄的 capability 生命周期**，无需独立的密钥吊销列表（KRL）。
   - 这与块层 dm-crypt（整盘一钥、与句柄无关）形成根本区别，是 MeuOS「统一资源层 + capability」相对于传统加密的最高价值点。

> 与参照系统的差异：btrfs 把校验和/压缩做到 extent 级（借鉴），但加密仍脱节；APFS 做到 per-file 密钥层次（借鉴），但密钥体系是证书而非 capability；MeuOS 的独特取舍是**把「密钥访问权」显式挂到文件句柄的 right 上**，使加密成为 capability 模型的一等公民，而非外挂的安全特性。

### 4.3 原子 `.msys` sysroot 更新：快照式 repoint + 监督协同

**先推演「应该是什么样」**：`.msys` 是 MeuOS 的系统根（sysroot）更新单元（等价于「系统镜像包」）。理想更新应该：要么完全生效、要么完全不生效（原子）；失败时一键回滚；**不要求重启**（至少不要求「全系统重启到另一个分区」）；与进程监督协同（新老进程可短暂共存，旧进程不摔、新进程用新 sysroot）。

**MeuOS 设计（自主收敛）——子树级快照 + 原子 repoint，不用分区级 A/B 作主路径：**

1. **sysroot 是命名空间子树，不是分区**。`.msys` 在 MeuOS-FS 里表现为一个**子卷（subvolume）/ 命名空间根节点**（CoW 能力由 §4.2 的 extent 层支撑）。进程命名空间里的 `/msys` 绑定指向「当前 sysroot 子卷能力」。
2. **更新流程（原子、可回滚）**：
   - (a) **签名校验**：新 `.msys` 镜像带签名；FS 服务先用受信任的**根密钥能力（root-of-trust capability，来自 secure boot 链）**校验签名，失败则拒绝（对齐 ChromeOS 签名校验 + TCB）。
   - (b) **建备份快照**：对当前 sysroot 子卷做 O(1) CoW 快照，得到「已知良好备份」（共享未改 extent，几乎零额外空间）。
   - (c) **建暂存克隆**：对当前 sysroot 做可写 CoW 克隆（staging），把更新应用到 staging。全部失败 → 丢弃 staging，当前 sysroot 完好（all-or-nothing）。
   - (d) **原子 repoint**：通过**单条元数据事务**把命名空间里的 `/msys` 别名从「当前」重指向「staging」——这是 capability 级别的单点原子切换（一次能力重绑，非多步文件改名）。
   - (e) **监督协同（与 04）**：`meu-supervisor` 决定**何时切割**——新 spawn 的进程按 manifest 绑定到新 `/msys`；仍运行的旧进程继续持有旧 sysroot 能力（CoW 共享未改块，空间按需分化）。若新 sysroot 下某服务崩溃，监督者可重启该服务于新 sysroot，或整体 repoint 回备份快照。
3. **回滚（rollback）**：repoint 回备份快照即可，同样原子、无需重启。旧进程不中断（它们持旧能力）；新进程切回旧。
4. **防砖兜底（与 09 协同）**：若担心「sysroot 损坏到连 FS 服务都起不来」，保留 ChromeOS 式 **A/B 双分区/双 slot 作为引导级兜底**——但它是**最后防线**，常规更新走上面的子树快照式，避免 Android A/B 的 2x 空间与必重启代价。
5. **与 spawn 监督的深层协同（方向②）**：因为 sysroot 是 capability，进程「运行在哪个 sysroot 版本」是可审计、可回滚的一等事实。监督者可以「先灰度：让 10% 新进程用新 sysroot，观察崩溃率，再全量」——这是分区级 A/B 做不到的细粒度。

> 与参照系统的差异：Android/ChromeOS A/B 是**分区级、需重启、2x 空间、全有或全无**；APFS 快照是**卷级、但缺监督协同与 per-process 绑定**；MeuOS 的独特取舍是**子树级 CoW 快照 + 命名空间原子 repoint + 由用户态 supervisor 做 per-process 灰度切割**，把「原子更新」从「引导加载器的事」变成「资源命名空间能力的事」，并与 02 方向（spawn 监督）深度互锁。

### 4.4 与 IPC / 内存管理 / 安全 / 进程的接口边界（仅声明依赖与协同点）

> 本节**不下结论**、不替其他子领域拍板，只声明「统一文件系统层依赖什么、向谁暴露什么、协同点在哪」。结论以各子领域文档为准；跨域一致性由 doc-sync 合成 pass 回填。

#### 4.4.1 与 内存管理（03：VMO / VMAR / pager）

- **文件数据访问走 VMO + pager（零拷贝 mmap）**：FS 服务为打开的文件创建一个 **VMO**（内核对象，见 03 的 VMO/VMAR 抽象）作为该文件数据的「视图」，把 VMO 句柄经 IPC cap-transfer 交给客户端；客户端 `mmap` 该 VMO 即零拷贝映射。
- **pager 模型（对齐 Fuchsia）**：FS 服务是该 VMO 的 **pager**。客户端缺页时，内核向 FS 服务发页请求（经一条专用 pager channel），FS 服务读对应 extent → 解压 → 解密 → 校验 → 把页供给内核 VMO。这样**FS 逻辑全在用户态，而数据通路在内核（零拷贝、由内核强制 VMO rights）**，完美契合 lean hybrid。
- **依赖 03**：VMO 的 COW 子（clone）、refcount 单一真相源、VMAR 层级权限（如 `prot_exec` 约束）由 03 提供；FS 服务不重复实现页表/COW，只作为 pager 供货。
- **待协同点**：VMO 的「页供应」语义（pager 接口形状）、COW 与 FS 层 CoW 的 refcount 单一真相源归属（避免双计数）——需与 03 对齐。

#### 4.4.2 与 IPC（05：Channel / EventPort / SHM / Service Registry）

- **FS 服务是用户态服务，经 Channel 暴露接口**：`open/close/read/write/stat/rename/mkdir/...` 的元数据与控制操作走 Channel 消息（对齐 05 的 Channel 原语）。大数据 `read/write` 优先走 VMO（§4.4.1）以避免每次 IPC 拷贝。
- **文件句柄 = capability，经 cap-transfer 传递**：FS 服务「打开」一个节点后，请求内核 mint 一个**文件句柄（kernel object，带 rights）**或把文件 VMO 句柄转交客户端；句柄的 rights 由 FS 服务按客户端权限设定（客户端拿到的通常是 READ/WRITE 子集，FS 服务自身持 MANAGE）。这要求内核提供「受约束的 capability mint」——FS 服务作为委托人，其 mint 权限需被限制（见 §6 待决 2，confused deputy 风险）。
- **命名空间挂载 = Service Registry + mount-capability**：`/dev`、`/proc`、`/net` 子树由对应服务经 05 的 Service Registry 注册目录能力，FS 服务通过 mount-capability 委托——与 05 的「服务名即可声明资源」一致。
- **依赖 05**：Channel / EventPort / SHM / cap-transfer / Service Registry 全部由 05 定义；FS 不另造 IPC。

#### 4.4.3 与 安全模型（07：capability / rights / pledge / unveil）

- **路径即 capability 命名维度（维度 C）**：unveil 一个路径 = 向进程命名空间注入该路径的 capability 绑定（§4.1）；pledge 的 `rpath/wpath/cpath` 约束能否新增绑定。
- **文件句柄 rights 与 07 同构**：文件句柄的 `READ/WRITE/EXECUTE/MANAGE` 复用 07 的 rights 位图；**加密密钥 unwrap 权 = 文件句柄 right**（§4.2.3），故 `revoke(句柄)` 即撤销解密权。
- **根信任能力**：`.msys` 签名校验用的根密钥是 07 的「secure boot / root-of-trust capability」——FS 不内置信任根，只消费 07 提供的根密钥能力。
- **待协同点**：rights 位图是否需新增 `KEY_UNWRAP` 之类位，还是复用 `MANAGE`（§6 待决 1）；revoke 传播（derivation tree）是否覆盖「句柄→密钥 unwrap 权」链（§6 待决 1）。

#### 4.4.4 与 进程 / spawn（04：Job / 资源账本 / 监督）

- **spawn 时组装命名空间**：新进程的命名空间绑定（§4.1）由 04 的 spawn 按 Job/manifest 注入；sysroot 版本（§4.3）作为命名空间绑定的一部分，由 Job 持有。
- **资源账本挂钩**：打开的文件句柄数 / 持有的 VMO 数计入 04 的 Job 句柄配额；文件占用的 page cache 内存计入 Job 内存账本（经 03 的 VMO refcount）。
- **监督协同**：`.msys` 原子更新的切割决策（§4.3）由 `meu-supervisor`（04）做出；FS 服务提供快照/repoint 原语，但不决定「何时切、灰度多少」——那是监督策略（用户态）。
- **依赖 04**：Job 树、资源账本、监督事件模型由 04 定义；FS 只暴露「sysroot 快照/repoint」与「命名空间绑定」原语供监督消费。

#### 4.4.5 与 设备驱动（10：块设备能力句柄）

- **FS 只拿它所需的块设备能力**：FS 服务通过 10 的设备驱动服务获得**块设备的 capability 句柄**（仅 `READ`/`WRITE`/`block-io` 权），经 capability 网关授予（对齐 10 的「驱动最小权限」）。FS 不直接碰 MMIO/IRQ/DMA。
- **依赖 10**：块设备抽象、virtio-blk 等由 10 提供；FS 只消费块设备能力 + 上层做 extent 分配/CoW/校验和/加密。

### 4.5 文件系统自身结构（自主设计要点，非字节级）

「应该是什么样」落到 MeuOS-FS 自身，给出结构原则（留给执行层细化）：

- **对象模型**：一切皆「节点（node）」——inode 式元数据 + 类型标签（file/dir/device-proxy/symlink/...）。目录是「名字 → 节点能力」的映射（capability-backed 目录，非裸 inode 号）。
- **树与索引**：用 COW B-tree（借鉴 btrfs/APFS/ZFS 思路，自主实现）做目录项与 extent 索引；所有写是 COW，元数据事务保证崩溃一致性（无需 fsck 重放，对齐 APFS/btrfs 的「写时复制即一致性」）。
- **extent 为核心分配单元**：文件数据以 extent 组织（对齐 ext4/btrfs），每个 extent 记录 `[物理块范围, 长度, 压缩算法, 密文校验和, (可选) AEAD 标签]`。
- **CoW 即克隆/快照原语**：`clone`（O(1) 子卷/文件克隆）与 `snapshot`（sysroot 备份）都是 extent 共享 + 写时复制（对齐 APFS clonefile / btrfs subvolume），是 §4.3 原子更新的基石。
- **内容寻址可选（blobfs 思想）**：对不可变系统文件（`.msys` 内组件），可用 hash 命名 + 去重（对齐 Fuchsia blobfs），天然防篡改且省空间。
- **崩溃恢复**：无传统 fsck——COW + 事务日志保证「最后一次提交的事务要么完整要么不可见」；挂载即一致。

## 6. 待决清单（含需架构级裁决的点）

以下问题不属于本文能拍板，需后续子领域调研或工程实测后回填（doc-sync 合成 pass 会收敛跨域一致性）：

1. **【架构级·安全】加密密钥是否走 capability 撤销？** 本文倾向「是：密钥 unwrap 权 = 文件句柄 right，撤销句柄即撤销解密权」。但需 07 确认：rights 位图是否新增 `KEY_UNWRAP` 位，还是复用 `MANAGE`？revoke 的 derivation tree（07 §5.4）是否覆盖「句柄→密钥 unwrap 权」链？这是方向①③互锁的最高价值点，需优先裁决。
2. **【架构级·安全】FS 服务作为 capability 委托人的信任边界（confused deputy）**。FS 服务请求内核 mint 文件句柄/VMO 并转交客户端——如何防止 FS 服务被恶意客户端诱导、越权 mint 不该给的 rights？需 07 定义「受约束 mint」的授权模型（FS 服务自身的 rights 上限 + 客户端请求的下限取交集），避免 confused deputy。
3. **【架构级·进程/安全】命名空间是「每进程独立」还是「共享根 + unveil 裁剪」？** 本文倾向每进程 namespace 由 spawn 组装（对齐 Fuchsia/Plan9）。但 Linux 兼容层（08）的「全局路径」语义如何映射？需 04/07/08 协同确认 spawn 时命名空间绑定的来源与继承语义。
4. **【性能·实测】pager 缺页往返开销**。用户态 FS + pager 使每次文件缺页至少一次 IPC 到 FS 服务；热路径（密集小文件随机读）延迟是否可接受？是否需要内核页缓存旁路 / FS 服务预读代理 / 热点文件直接 VMO 下发？需原型基准。
5. **【启动·协同】sysroot 原子更新是否需要 A/B 双分区兜底？** 本文以子树快照式为主路径，但「FS 服务自身损坏」场景是否需引导级 A/B 兜底（与 09 启动/secure boot 协同）？防砖边界需 09 确认。
6. **【架构·接口】多 FS 类型共存的组合语义**。本地 MeuOS-FS 之外，兼容层挂载 ext4/网络 FS/临时 tmpfs 时，是否一律经同一「mount-capability」机制挂入统一命名空间？挂载点的 capability 来源与 revoke 语义需与 05/08 对齐。
7. **【语言·协同】压缩/加密热路径的 Rust/C 边界**。若 Rust 加密 throughput 不足，热函数是否允许 C/内联汇编并经 Rust safe 封装（对齐 02）？密钥管理/权限判定必须留在 Rust/TCB 侧——边界划分需 02 确认。
8. **【存储·协同】命名空间子树（设备/进程/网络）的暴露者**。`/dev`/`/proc`/`/net` 是由对应服务**直接**暴露目录能力，还是由 FS 服务**代理**聚合？前者更解耦（各服务自管），后者更统一（FS 服务做门面）——本文倾向「直接暴露 + FS 服务做 mount-capability 委托」，但代理 vs 直露的边界需与 04/05/10 协同。

> 上述 8 项中，1–3 为**需架构级裁决**的高优先项（直接决定方向①③能否闭环），4–8 为设计/实测协同项。本文结论在这些点回填前为非最终态。
