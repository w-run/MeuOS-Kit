## 1. 「应该是什么样」推演（解构型）

### 1.1 总纲：在混合内核下，RT「应该」是什么样

先不问「MeuOS 现在能多实时」，而问「在『重服务出核』的务实混合内核下，一个**硬实时任务应该**如何既享受用户态服务化（隔离/可重启/小 TCB），又满足硬实时（确定性尾延迟、可证明 WCET）」。

推演起点——MeuOS 已定架构（`00`/`01`/`04`）：
- 调度器 = EEVDF（公平层）+ RT 固定优先级（SCHED_FIFO/RR，0–31）（`04` §4.3）。
- 服务（FS/网络/驱动）大量出核；数据通路靠 VMO/pager/SHM **留核**（lean hybrid 的性能正当性，`19` §1.1 原则 1）。
- capability 是 Day 1 唯一权限模型；创建 RT 线程需特定 capability（`04` §4.3）。

由此推演出理想 RT 画像的六条（解构型基线）：

1. **RT 表达 = 严格优先级 + Zircon 式 deadline 调度，二者在同一 RT 调度域内共存**。固定优先级覆盖「绝对不可被低优先级抢占」的硬 RT；deadline 调度（capacity/deadline/period，EDF 变体）覆盖「周期性、有预算、可预测」的软/中 RT。二者在 `04` 已定的 RT 类上扩展，而非另起炉灶。
2. **关键路径数据通路留核，是硬 RT 不被 IPC 击穿的前提**。硬 RT 任务若必须与某服务交换数据（如音频采样、控制环反馈），该数据平面应走 **VMO/SHM 直连**（对齐 `05`/`19`「数据通路留核」原则），而**不**走 `channel_call` 往返——否则每一次采样都叠加一次 ≤500ns/≤1–2µs 的 IPC（见 `19` §1.2.2），确定性立即被出核服务抖动击穿。控制平面（低频配置/握手）才允许 IPC。
3. **RT 优先级与 CPU 亲和本身应是 capability，而非 uid/cap 式的提权通道**。否则任意进程把自己设为 RT 优先级、绑死某核，即可靠 RT 预算饿死系统（`04` §4.3 已点出「创建 RT 线程需特定 capability」）。RT 预算（带宽/周期/亲和集）与 `04` Job 账本同源——是 Job 的固有属性，而非事后挂接。
4. **缺页是 RT 的头号敌人，必须被「锁定」消除**。硬 RT 任务的代码/数据/栈/VMO 缓冲区应可 `mlock` 式固定（`03` 缺页延迟即便 COW ≤200ns，对 µs 级硬截止期仍是不可接受的抖动源）。这与 `19` §1.2.3 的「mint 时一次、运行期位运算」原则同源——把不确定性在准入期一次性付清。
5. **用户态驱动可以做 RT，但必须改造成「轮询 + 零拷贝 + lock-free 环形缓冲」**。MINIX3 式「每次 I/O 经多次 IPC + 中断转发」（`10` §3.6）是 RT 反模式；敏感中断留核、其余用轮询/中断合并 + SHM 就绪通知（`10` §5-1、AP-2）才能把抖动压进预算。
6. **确定性可分级承诺**：不强行对所有负载承诺硬实时，而是把「可承诺硬 RT 的域」显式圈定（特定 Job、特定 CPU 子集、固定内存），其余交给 EEVDF 尽力而为。是否对全系统承诺硬实时 + 提供 WCET 证明，**是需架构裁决的开放项**（见 §7）。

### 1.2 解构型反问：为什么混合内核的 RT 比纯微内核/纯宏内核都更难也更值得做

- **纯微内核（seL4/MINIX3）**：IPC 是系统调用热点，每一次服务调用都走 IPC。它的 RT 优势是「内核极小、可形式化、调度可证明」（`19` §2.2）；劣势是数据通路也被 IPC 化（Redox/MINIX3 出核过头的代价，`19` §5.1 结论 1）。
- **纯宏内核（Linux PREEMPT_RT）**：数据全在内核、零 IPC，RT 路径天然短；劣势是 TCB 巨大、不可验证，且 PREEMPT_RT 要改写整条自旋锁/中断线程化路径才能压低关中断窗口。
- **MeuOS 务实混合内核**：理想形态 = 借宏内核的「数据通路留核」（VMO/SHM 直连，无 IPC 抖动）+ 借微内核的「RT 调度核心极小可验证」（`19` §3.4(A) 把调度器核心纳入可验证 TCB）。难点在于：**出核服务的控制平面抖动不能泄漏进硬 RT 数据平面**——这正是 §3 的「留核策略」要解决的问题。

### 1.3 硬实时边界与 `19` 基准的映射

`19` §1.2.2 锚定 IPC 快速路径 **同核 ≤500ns / 跨核 ≤1–2µs**。这直接给出硬 RT 的**设计边界**：

- 若硬 RT 任务的周期 **≥ 数十 µs**，且数据平面走 VMO/SHM 直连（零 IPC），则 EEVDF/RT 调度 + 禁抢占临界区 + mlock 足以把尾延迟压到预算内——**这一类 MeuOS 现在就该承诺**。
- 若硬 RT 任务的周期 **< 数 µs**（如高频电机控制环），每次环迭代都需一次 `channel_call` 往返，则 IPC 开销本身就是预算主体，此时必须：要么数据/控制全留核（内核态 RT 任务或长驻用户态 RT + SHM），要么直接判定「该负载不在 MeuOS 硬 RT 域内」。

> 结论先行：**硬 RT 的可达边界 = 「数据通路留核 + 周期 ≥ 数十 µs + 内存锁定 + 非剥夺临界区」**；低于此的亚 µs 闭环，MeuOS 务实定位为「不承诺」，而非强行支持（见 §7 待决项，需架构裁决「是否承诺硬实时及 WCET」）。

## 2. 多系统参照对比表（含硬实时能力列）

### 2.1 实时性参照（硬实时能力横向对比）

| 系统 | RT 调度模型 | 硬实时能力 | 确定性/WCET 手段 | 对 MeuOS 的取舍 |
|---|---|---|---|---|

| **Android (ART / HAL / AAOS)** | ART 实时线程 + HAL 实时队列 + 汽车 Turnkey（AAOS 车载实时）；Linux 内核 PREEMPT_RT 基础上叠车载约束 | 中 RT（触控/音频/车载控制）；车载安全相关走 ASIL 分区 | 核隔离 + 实时优先级 + 供应商 HAL 约束 | **吸收**：分层 RT（应用 RT 线程 → HAL RT 队列 → 车载硬分区）的「域分层」思想 |
| **Symbian** | 实时微内核基因（纳核 + EKA2 抢占式微内核） | 硬 RT（手机基带/实时事件） | 微内核极小核 + 优先级抢占 | **参照**：实时微内核血统证明「小核可硬实时」，`19` §3.4(A) 同调 |

| **ChromeOS / Fuchsia (Zircon)** | Zircon 提供 **deadline 调度**（`zx_thread_set_deadline_params`，capacity/deadline/period）+ 严格优先级 + 锁/分配受限的用户态 RT | 中/软 RT（ChromeOS 实时音频/渲染）；Fuchsia 用户态 RT 经「严格优先级 + 锁与分配受限」保障 | deadline 调度 + 禁止 RT 线程内分配/锁竞争 | **范本**：deadline 调度 API 与「RT 线程禁分配/禁长锁」约束，直接成为 §3/§4 蓝本 |
| **seL4** | 形式化验证的确定性调度（固定优先级 + 时间片）；可验证 WCET | **硬实时（可证明）**：调度器经精化验证，中断延迟可分析 | 形式化调度证明 + 关中断上界分析 + 静态 WCET | **最高标杆**：确定性靠「小核 + 证明」，而非靠调参；§7 待决项「是否承诺 WCET」的对标 |
| **MeuOS（目标）** | 严格优先级（0–31，扩展 `04`）+ Zircon 式 deadline 调度（capacity/deadline/period）；二者同在 RT 域，EDF 在 deadline 子类内 | **务实硬 RT（圈定域）**：特定 Job + RT CPU 子集 + mlock 固定；亚 µs 闭环不承诺 | deadline 预留 + RT 带宽硬分区（QNX APS 式）+ 可验证调度核心（接 `20`）+ 可选 WCET 分析 | 取 QNX 硬分区 + Zircon deadline API + seL4 可验证核心，规避「出核 IPC 击穿」（靠 §3 留核） |

### 2.2 取舍结论

- **拒绝**「把 Linux PREEMPT_RT 全盘搬来」：MeuOS 已是 capability + 混合内核，RT 提权应是 capability 而非 `CAP_SYS_NICE`，且调度核心要小、可验证（对齐 `19` §3.4(A)）。
- **采纳** Zircon 的 deadline 调度 API 作为 RT 第二类（在 `04` 已定 SCHED_FIFO/RR 之上扩展），并用「RT 线程内禁分配/禁长锁」约束防止优先级反转与抖动。
- **采纳** QNX 自适应分区（APS）作为 Job 级 RT CPU 带宽硬预留的对标物——即 §4 的「RT 预算」。
- **跟踪** seL4 式可验证确定性作为 §7 的「是否承诺 WCET」候选项；原型期不做端到端 WCET 证明，但调度核心（RT 选择、deadline 会计、带宽记账）纳入 `19` §3.4(A) 的可验证小核心。

## 3. MeuOS RT 调度与关键路径留核策略

### 3.1 三层调度域（在 `04` 之上扩展）

```
┌──────────────────────────────────────────────────────────────┐
│  RT 域（非剥夺优先，严格优先级 0–31 + deadline 子类）           │
│  ├─ 严格优先级子类 (SCHED_FIFO/RR)：绝对不可被低优先级抢，      │
│  │  用于硬 RT（如控制环、音频回调）；关抢占临界区短。          │
│  └─ deadline 子类 (Zircon 式)：capacity/deadline/period，       │
│      EDF 在子类内选 next；用于中/软 RT（周期任务、可预测预算）。│
│  创建/提权需 RT capability（§4）；预算挂在 Job 账本（§4）。     │
├──────────────────────────────────────────────────────────────┤
│  公平层（EEVDF，`04` §4.3）：默认尽力而为；不抢 RT 域。        │
└──────────────────────────────────────────────────────────────┘
```

- **RT 域对公平层的绝对压制**：只要有 RT 就绪任务且未用尽其 RT 带宽，公平层不被选（对齐 Linux RT > CFS、QNX 实时优先级）。
- **deadline 子类与严格优先级共存**：严格优先级 0–31 内，deadline 任务可置于某个优先级带；子类内用 EDF 选最紧急者。实现上沿用 `04` §4.3 的 `sched_class` 钩子——新增 `rt_deadline_class` 作为 RT 类下的子类，不重写核心。
- **AP 规避（优先级反转）**：RT 域持锁时启用**优先级继承（priority inheritance）**或**优先级天花板（priority ceiling）**，避免低优先级持锁阻塞高优先级 RT（Linux `rt_mutex`、QNX 同调）。这与 `19` §3.4(A) 的「IPC 端点状态机/rights 检查可验证」同源——锁协议本身须进可验证 TCB。

### 3.2 关键路径留核策略（硬 RT 不被 IPC 击穿的核心）

**原则（对齐 `05`/`19`「数据通路留核」）**：硬 RT 任务的数据平面**一律走内核直连的 VMO/SHM**，控制平面才走 Channel/EventPort IPC。具体：

1. **RT 生产者/消费者共用一个 VMO/SHM 环形缓冲**：RT 任务与其协作方（可能是用户态服务，也可能是内核态快速驱动）映射同一 VMO，用 lock-free SPSC/MPSC 环形缓冲（`10` §5-1 轮询 + 零拷贝思想的落地）交换样本/控制量；就绪通知用 EventPort `CHAN` filter 或轮询，**不走 `channel_call` 往返**。
2. **控制平面低频 IPC 不污染数据平面**：配置、握手、错误上报走 Channel，但这类操作发生在 RT 周期之外，且不持 RT 非剥夺锁，故不进入硬截止期预算。
3. **RT 任务与出核服务的耦合最小化**：若 RT 任务确需某用户态服务（如音频混音器），该服务应以「常驻 + 已 mlock + RT 优先级」形态存在，且其数据平面同样 VMO/SHM 化；否则 RT 任务应直接对内核态快速驱动（`10` §4.2 留核驱动：中断控制器、定时器、关键 DMA）闭环。
4. **RT 中断留核**：参与硬 RT 的设备中断（定时器、采样完成、DMA 完成）由内核态快速路径直接派发到 RT 线程，**不**经 `10` 的中断转发 IPC（`10` §5-1 的高频设备留核准则在 RT 下升级为「必须留核」）。

> 与 `19` 的接口：`19` §1.2.2 的 IPC 预算用于**控制平面**度量；§3.2 的数据平面 VMO/SHM 路径**不计入 IPC 预算**，其延迟由 `19` §1.2.3 的 VMO/pager 零拷贝路径与 TLB 暖态保证（≥ 数百 ns 量级，远优于 IPC 往返）。`19` 的 `kernel/ipc/call_latency_ns` 仍用于监控控制平面，避免 RT 任务误用 `channel_call`。

### 3.3 非剥夺临界区与中断延迟

- **关抢占/关中断窗口**：RT 域任务在极短临界区（如环形缓冲 head/tail 更新、调度器内部）才关抢占；窗口长度须有上界（对标 Linux PREEMPT_RT 压缩关中断窗口、`19` §4.4 牵连 C8 内核态驱动 check ≤20ns 量级）。
- **中断延迟上界**：`19` §3.4(A) 把调度核心纳入可验证 TCB；中断控制器为内核态（`10` 附录 A），硬 RT 中断的「硬件 → RT 线程就绪」延迟是可分析、可测的（接 `19` 的 `cyc_lat` cyclictest 等价基准）。
- **RT CPU 子集隔离**：仿 Linux `isolcpus`/`nohz_full`——把若干核划为 RT 子集，其上**只跑 RT 域任务 + 其绑定的内核态驱动**，公平层与出核服务默认不调度进来（对齐 `00` C1 物理内存/CPU 归属思想；CPU 亲和见 §4）。

## 4. capability 化 RT 预算

### 4.1 RT 优先级 / CPU 亲和 = capability（避免提权抢占）

对齐 `04` §4.3「创建 RT 线程需特定 capability」与 `07` 的「无 root、权限随句柄走」：

- **`CAP_RT`**（新增 right，挂在句柄/Job 上）：持有者才能 (a) 把线程设为 RT 域（严格优先级或 deadline 子类）、(b) 提升 RT 优先级、(c) 声明 RT CPU 亲和集。无 `CAP_RT` 的进程调用 `meu_thread_set_rt_priority` 直接 `EPERM`（fail-closed，对齐 `07` pledge 越界即终止语义）。
- **RT 优先级/亲和不可经 Linux 兼容层逃逸**：兼容层 `sched_setscheduler`/`CAP_SYS_NICE` 映射为「持有 `CAP_RT` 受限句柄」（对齐 `07` §4.6：Linux capability 拆到具体对象权限，`CAP_SYS_ADMIN` 式大权不被整体授予）。
- **这避免 PREEMPT_RT 式风险**：任意进程不能靠 `CAP_SYS_NICE` 把自己设为 RT 饿死系统——RT 提权是显式、可审计、可收回的 capability（对齐 `19` §1.1 原则 2「权限获取时一次、运行期位运算」）。

### 4.2 Job 账本含 RT 预算（在 `04` §4.4 之上扩展）

`04` §4.4 的 Job 账本已含 CPU 时间（公平权重 + 可选硬上限）。RT 预算作为**新增维度**，与配额同源挂在 Job 上（对齐 Zircon job 限额 + QNX APS 分区）：

| RT 预算项 | 含义 | 超限行为 | 对应系统 |
|---|---|---|---|
| **RT CPU 带宽**（capacity/period） | 该 Job 下 RT 任务在窗口内可占用的 CPU 时间比例（QNX APS 式硬分区） | 超出则 RT 任务被节流/挂起，不侵入公平层 | QNX APS、Linux `SCHED_DEADLINE` 带宽 |
| **RT 优先级上限** | 该 Job 能设的最高 RT 优先级（防止低特权 Job 抢占高特权 RT） | 超限 `EPERM` | Zircon priority 区间 |
| **RT CPU 亲和集** | 该 Job 的 RT 任务可绑定的核集合（须 ⊆ 系统 RT 子集） | 越界 `EPERM` | Linux `isolcpus`/`sched_setaffinity` |
| **deadline 预留数** | 该 Job 允许并发的 deadline 任务数 / 总 capacity | 超限拒绝 spawn/set | Zircon deadline |

- **与 `04` 账本同源**：RT 预算的检查点分布在调度器（带宽/优先级）、`meu_thread_set_*`（`CAP_RT` + 优先级上限）、`meu_spawn`（亲和集校验）；账本对象由进程管理子系统持有，被 capability 系统校验（`04` §4.4 末段）。
- **可审计、可预测**：RT 预算与句柄权限、资源配额同树，审计一个 RT 进程只需看其 Job 的 RT 预算 + 持有的 `CAP_RT` 句柄（`19` §4.4 牵连 C2/C8 同源）。

### 4.3 RT 预算的准入与回收

- **准入期一次性付清不确定性**：RT 任务的 mlock、亲和绑定、带宽预留都在 `spawn`/set 时完成（对齐 §1.1 原则 4）——运行期不做可能失败/阻塞的分配。
- **回收**：Job 终止 → RT 预算与 RT 线程一并回收（对齐 `04` §4.5 根 Job 终止传播）；`CAP_RT` 句柄 `close`/revoke → 该 Job 后续无法新建/提权 RT 线程（对齐 `07` §4.5 撤销传播）。

### 5.1 缺页（`03`）对 RT 的威胁与 mlock 式固定

`19` §1.2.3 给缺页预算：COW ≤200ns、文件热缓存 ≤200ns、冷 pager ≤2–5µs。这些对 **µs 级硬截止期**仍是非确定抖动源（尤其是冷 pager 一次 IPC 往返）。缓解：

- **RT 线程地址空间准入期全锁定**：代码/数据/栈/VMO 缓冲在 `spawn` 或 `meu_thread_set_rt` 时 `mlock` 式固定到物理页，禁止其后缺页（`03` 页帧数据库 `MmPage.flags` 加 `RT_LOCKED`，回收路径跳过）。
- **RT 的 VMO 缓冲同锁**：RT 数据平面 VMO（`05` SHM）在建立时即提交物理页并固定，避免运行期 pager 往返。
- **与 `03` 演进协同**：大页（2MB/1GB，`03` §4.7 Phase 3）对 RT 友好——单 TLB 项覆盖更大缓冲，减少 TLB 抖动；RT 预算可优先分配大页。

### 5.2 用户态驱动（`10`）做 RT 的代价与缓解

| 代价（RT 反模式） | 缓解（对齐 `10`/本文件） |
|---|---|
| 中断转发 + 每次 IPC 通知（`10` §5-1）→ IPC 抖动击穿 RT | 敏感中断留核（`10` §4.2），RT 设备中断**必须**留核；其余用中断合并 + 轮询混合（`10` §5-1、AP-2） |
| 驱动访问经能力网关 IPC（`10` §4.6）→ 额外往返 | 内核态快速驱动直接 MMIO（check ≤20ns，`19` §4.4 C8）；用户态 RT 驱动走 VMO/SHM 环形缓冲 + 轮询，把 IPC 降到零 |
| 驱动内分配/锁导致优先级反转 | 仿 Zircon/Fuchsia「RT 线程禁分配/禁长锁」（`22` 待决）：RT 驱动路径禁动态分配、用 lock-free 环形缓冲 |
| 驱动崩溃重启（`10` RS 看门狗）引入不可控延迟 | RT 关键驱动优先留核；用户态 RT 驱动须 `mlock` + 常驻，重启窗口计入 RT 预算冗余 |

## 6. 五架构差异（时钟源、确定性、RT 代价）

RT 的确定性高度依赖**稳定时钟源**（deadline 会计、WCET、cyclictest 度量）与**关中断/抢占上界**。五架构差异如下（`03` §2.1 页表差异之外，补充时钟/计时差异）：

| 架构 | 稳定时钟源（RT 计时基准） | 关抢占/中断上界差异 | 对 RT/确定性的影响 | 与 `19` §3.3 crypto 关联 |
|---|---|---|---|---|
| **x86_64** | **Invariant TSC**（`rdtsc`/`rdtscp`，不受频调影响）+ LAPIC Timer + TSC Deadline 模式（单次精确触发） | 成熟；`invpcid`/`pcid` 减 TLB 抖动 | **最佳 RT 基线**：TSC 单调稳定，deadline 会计与 `cyc_lat` 度量最可靠 | AES-NI ≥1GB/s，RT crypto 直接硬件加速 |
| **aarch64** | **Generic Timer**（ARMv8 架构化计时器，`CNTFRQ`/`CNTPCT`，EL1/EL2 物理/虚拟计数器；`CNTP_CVAL` 比较触发） | ASID 8/16-bit；虚拟化计时器成熟 | 与 TSC 同级稳定，deadline/周期预算可直接用物理计数器；虚拟计数器供 VM 用 | ARM CryptoExt ≥1GB/s，对等 |
| **riscv64** | `rdtime`（time CSR）+ CLINT/ACLINT `mtimecmp`；**Sstc** 扩展提供 `stimecmp`（S 态直接设比较值，免陷入 M 态） | 依平台实现；**标准化较弱**（不同 SoC 计时器差异大） | 若缺 `Sstc`/`mtimecmp` 直访，RT 计时需陷入 M 态或依赖平台驱动 → **抖动来源**；需统一 `arch/timer` 抽象并实测上限 | 向量 crypto（Zk/Zvkn）依实现，可能 < x86/aarch（同 `19` §3.3） |
| **loongarch64** | 稳定计数器 CSR（`RDTIME`/稳定计数） | 自有体系，成熟度待验 | M5 后移（`11` §5-4），先保证正确；RT 基线待该架构实测 | 自有 crypto 指令，中等（同 `19` §3.3） |
| **i386** | TSC（老 CPU **可能非 invariant**，需回退 HPET/PIT）；LAPIC/8254 | 无 Rust TCB、纯 C（`02` C2）；计时源最不可靠 | **RT 确定性最弱**：非 invariant TSC 下 deadline 会计需校准；但 i386 非 RT 重点架构，`19` §3.3 已定「慢来自 crypto 缺失而非 Rust 缺失」——RT 同理：慢/不确定来自计时硬件，非语言 | 无 AES-NI，软件 AES ~100–300MB/s（`19` §3.3）；RT crypto 预算须单列 |

**核心论断**：五架构的 RT 差异本质是**时钟源稳定性 + 计时器抽象标准化**的差异，而非调度算法差异（调度核心在 Rust TCB 内统一，`02`/`19`）。x86_64/aarch64 因 invariant TSC / Generic Timer 可作 RT 双验证架构（对标 `19` M5 双架构）；riscv64 的 `Sstc` 可用性、`i386` 的 TSC 不变性是各自 RT 可达性的前置实测项。

## 7. 自主结论 + 待决项（标注是否需架构裁决）

### 7.1 自主结论

1. **RT 表达 = 严格优先级（0–31）+ Zircon 式 deadline 调度，同在 RT 域**，在 `04` 已定 RT 类上扩展（`rt_deadline_class` 子类），沿用 `sched_class` 钩子不重写核心。硬 RT 走严格优先级，周期可预测任务走 deadline 子类。
2. **硬 RT 不被出核 IPC 击穿的唯一正解 = 关键路径数据通路留核**：RT 数据平面走 VMO/SHM 环形缓冲（零 IPC），控制平面才走 Channel/EventPort；敏感中断留核。这是 lean hybrid「数据通路留核」原则（`19` §1.1）在 RT 下的强制化。
3. **RT 优先级/CPU 亲和/预算一律 capability 化**：`CAP_RT` 防止提权抢占；RT 预算进 `04` Job 账本（QNX APS 式 CPU 带宽硬分区 + 优先级上限 + 亲和集），与配额/句柄同源、可审计、可收回。
4. **缺页是 RT 头号敌人，靠准入期 mlock 式固定消除**：RT 线程地址空间与其 VMO 缓冲在 `spawn`/set 时锁定物理页，运行期禁缺页；大页对 RT 友好。
5. **用户态驱动可做 RT，但须改造成轮询 + 零拷贝 + lock-free 环形缓冲 + 禁分配/禁长锁**；否则退化为 MINIX3 式 IPC 抖动反模式（`10` AP-2、`19` AP-2）。
6. **硬 RT 可达边界由 `19` 基准界定**：周期 ≥ 数十 µs + 数据留核 + mlock + 非剥夺短临界区 → **现在就该承诺**；亚 µs 闭环（每次环需 IPC 往返）→ **务实不承诺**。
7. **五架构 RT 差异在时钟源而非调度**：x86_64 invariant TSC / aarch64 Generic Timer 作 RT 双验证架构；riscv64 `Sstc` 可用性、i386 TSC 不变性为各自实测前置项。
