## 1. 定位：本文与 `10` 的边界（深化什么，不重复什么）

`10-设备驱动模型.md` 已确立**双轨驱动 + 能力网关 + MINIX 式看门狗**的总框架，并完成 C8（设备能力签发时序 / 撤销锁 / 早期串口归属）的裁决回写。本文是 `10` 的**深化（deepening）**，不重复其高层结论，而是把四个 `10` 点到即止的维度推到可落地的机制层：

1. **「驱动该在内核还是用户态」从口号变为决策框架**——给出可量化的分类边界（延迟预算 / 故障域 / IOMMU 可用性 / TCB 贡献），而非仅列「敏感留核、其余出核」。
2. **隔离机制的解剖**——capability + device VMO + IOMMU 域三者如何具体构成「每个驱动一个独立故障域」，以及中断如何跨过内核/用户边界抵达驱动。
3. **两层能力模型**——澄清「驱动拿到的设备资源能力（MMIO/IRQ/DMA）」与「驱动向上 mint 的领域 I/O 能力（BLOCK_*/GPU_*）」是**不同层次、不同 right 类**，这是 `10`/`33` 隐含但未显式拆开的关键点。
4. **驱动生命周期 × Job 账本 × 跨架构 × Day 1 最小集**的收口——把 `10` 的「匹配→授权→启动→看门狗」状态机与 `07` §4.3 的 Job 资源账本、`29` 的 T9 挡点、`04` 的 exception channel 串成一条可执行链。

> 新增系统参照：`10` 已覆盖 Linux / Windows WDF / IOKit / Zircon DFv2 / MINIX 3。本文**新增 Genode、UEFI 驱动模型、seL4 用户态驱动实证**，并将 Windows UMDF、Fuchsia devhost/Driver Runner 拆到机制层——这些 `10` 仅一笔带过。

## 2. 解构型推演：「驱动应跑在内核还是用户态」

### 2.1 先推演「应该是什么样」

不问「MeuOS 的驱动怎么抄 Linux 的 `module_init` / Fuchsia 的 `Driver` trait」，而问：在 **capability 世界（07）+ 用户态驱动（10）+ VMO 数据通路（03 A7）+ 尽快交权缩 TCB（00 A6）** 都已落定的前提下，「驱动位置」**应该**由什么决定。

核心洞察：**驱动位置不是意识形态选择（微内核 vs 宏内核），而是四个可量化约束的交点**。任一约束被打破，位置就该换边。

| 约束 | 推「留内核态」 | 推「下沉用户态」 | 在 MeuOS 的判定句 |
|------|----------------|------------------|--------------------|
| **延迟预算** | 亚微秒级中断响应、无法承受 IPC 往返（中断控制器、定时器、看门狗、极端吞吐路径） | 毫秒级可接受的 I/O（块、网络、显示、USB、传感器） | 设备中断到处理完成的时间预算 < 一次 IPC+上下文切换开销 ⇒ 留核 |
| **故障域** | 崩溃即内核死（生死相关设备，无隔离余地） | 崩溃可由监督者重启、不污染他人 | 设备崩溃「可接受重启」⇒ 用户态；崩溃=系统死亡 ⇒ 内核态 |
| **IOMMU 可用性** | 无 IOMMU 平台下用户态 DMA 是逃生舱风险 | 有 IOMMU 才能给用户态驱动做域隔离 | 无 IOMMU ⇒ 仅受信内核态驱动可 DMA（`10` C8 退路） |
| **TCB 贡献** | 驱动代码进 ring 0 ⇒ 扩大 TCB、抵消 Rust 安全收益 | 驱动在独立地址空间 ⇒ 不计入内核 TCB | 驱动缺陷密度高（`10` §1.1 引 ACSAC 2024）⇒ 默认出核缩 TCB |

### 2.2 决策框架（量化边界，可审计）

把 2.1 收敛为一张**驱动分类决策表**，每条规则可机检（供 `22` 测试矩阵消费）：

```
IF   设备 ∈ {中断控制器, 定时器, 看门狗, 早期串口(Stage1)}
THEN 内核态快速路径（生死相关，panic=abort，接 16 C5）

ELSE IF  中断延迟预算 < IPC 往返 + 上下文切换（典型 < 1–2µs，如 NVMe 提交 ring、某些 NIC）
THEN 内核态快速路径（可评估；非 Day1 必需，见 §8 / 33 D5）

ELSE IF  平台无 IOMMU  ∧  设备需要 DMA
THEN 内核态受信驱动（用户态 DMA 风险不可接受；退路，接 10 C8）

ELSE
THEN 用户态驱动服务（默认）：经能力网关获 MMIO/IRQ/DMA cap + IOMMU 域，
     数据走 device VMO，崩溃走 RS 看门狗重启（接 29 T9）
```

> 关键修正 `10` 的隐含偏向：`10` §4.2 把「NVMe 关键路径、GPU 提交 ring（原型后可评估下沉）」标为留核快速路径。本文据 2.1 的**延迟预算**约束，将其定为**优化项而非默认值**——Day 1 一律从用户态起步（§8），待基准证明 IPC 开销不可接受再按决策表第 2 条上提。避免「默认留核」悄悄扩大 TCB。

### 2.3 隔离不是二元的：连续谱

「内核 vs 用户态」是谱的两端，中间有多个**半隔离**档位，MeuOS 应保留接口而非锁死：

| 档位 | 位置 | 隔离强度 | 适用 |
|------|------|----------|------|
| L0 | 内核态、全特权（传统宏内核） | 无 | 不采用 |
| L1 | 内核态、能力约束（仅持自己设备 cap，接 10 §2.4） | 中（能力级） | 中断控制器/定时器/看门狗 |
| L2 | 内核态、快速路径 + 受控 DMA | 中 | 高吞吐优化项（NVMe/GPU 提交） |
| **L3** | **用户态、独立地址空间 + IOMMU 域 + device VMO** | **强（进程级 + 域级）** | **默认驱动（块/网络/显示/USB/串口）** |
| L4 | 用户态、进一步按 seL4 形式化验证的数据通路 | 最强 | 安全关键外设（长期，接 19/20） |

MeuOS Day 1 只实 L1（生死相关）+ **L3（默认）**；L2/L4 为演进档位，接口预留、不强制。

## 3. 隔离机制深解：capability + device VMO + IOMMU 域

### 3.1 两层能力模型（本文核心澄清）

`10`/`33` 反复出现「驱动获 MMIO/IRQ/DMA 能力」与「驱动 mint 块设备 cap」两句话，但**未显式区分这是两类不同的 capability**。本文明确拆开：

```
┌─ 第①层：设备资源能力（device resource cap）───────────────┐
│  由 capability 监视器(TCB) 在 Stage 4 从可信设备拓扑树 mint │
│  Cap(MMIO range) / Cap(IRQ n) / Cap(DMA window) / Cap(IO port) │
│  持有者 = 驱动本身；这是「能碰这块硬件寄存器」的原始权      │
│  与 BLOCK_*/GPU_* 正交——它是硬件访问权，不是 I/O 语义权    │
└────────────────────────────────────────────────────────────┘
              │ 驱动把硬件封装为领域对象，mint 第②层
              ▼
┌─ 第②层：领域 I/O 能力（domain I/O cap）───────────────────┐
│  BLOCK_READ/WRITE/IO/SUBDIVIDE/MINT_SUBDEV (33-D1, bit23–27)│
│  GPU_*/DISPLAY_*/SURFACE_*/INPUT_* (34, bit32–36)          │
│  NET_* (25, bit28–31) / AUDIO_* (35, bit19–22)             │
│  持有者 = 上层服务(FS/组合服务/图形服务/网络栈)             │
│  这是「能对设备提交何种 I/O」的语义权，与硬件布局解耦       │
└────────────────────────────────────────────────────────────┘
```

**为什么必须两层**：
- 第①层是**物理**的（MMIO 物理页区间、IRQ 号）——直接越权即踩别的设备；受能力网关校验（10 §4.6）。
- 第②层是**逻辑**的（「读块设备」）——让 FS 不必知道设备寄存器在哪，且 revoke 第②层即切断 I/O 而不必动硬件映射。
- 驱动是**唯一同时持两层的主体**（持第①层 + 第②层的 `BLOCK_MINT_SUBDEV`/`MANAGE`），但它把第②层收窄后交给上层，**自己不直接用第②层权做 I/O 语义**——这正是 confused deputy 防护的落点（§5.2）。

### 3.2 用户态驱动的地址空间与 device VMO（接 03 C1 / 33 §3.2）

L3 驱动是独立用户态进程，其地址空间构成如下：

- **仅映射自己的 device VMO**：内核从 DMA32/CMA zone 取连续页，封**不可写 device VMO**（`03` C1 已采纳、「折中 C」标志性吸收点），经第①层 DMA cap 下发；驱动对其他设备物理内存**零映射**（页表层面不可见，优于 Linux 驱动共享内核地址空间）。
- **MMIO 经能力网关映射**：`Cap(MMIO range)` 授权后，内核把该物理区间以**仅设备所属页表项**映射进驱动地址空间（uncacheable / device 属性），不暴露其余 MMIO。
- **数据通路**：读 = 设备 DMA 入 device VMO → 驱动按 VMO 拷贝/映射到普通数据 VMO 交给上层；写 = 从数据 VMO DMA 到设备 ring（`33` §3.3 `submit(vmo,...)` 原语）。内核不复制。
- **驱动代码本身 Rust 优先**（`10` §4.4），`unsafe` 仅集中在 MMIO 寄存器访问与 virtqueue 环形队列操作，集中审计——这是把「驱动缺陷密度高」的事实转化为「缺陷被关在独立地址空间 + 不可写 device VMO」的代价可控。

### 3.3 中断如何抵达用户态驱动（接 59 / 10 §5-1）

用户态驱动的 IRQ 不能由硬件直接递达（无 ring 0 处理权），需经内核代理：

1. 设备中断触发 → 内核中断控制器驱动（L1）收 IRQ → 据 IRQ→驱动映射表，**屏蔽该 IRQ 并转发**为对该驱动进程的**中断消息/exception channel 事件**（`59` 中断转发机制）。
2. 驱动进程被唤醒，读取 IRQ 号，处理（清设备中断、取 virtqueue 完成项）。
3. **高频率设备防 IPC 风暴**（`10` 开放议题 1 / 33 D5）：内核侧做**中断合并 + 轮询混合**——低于阈值用转发，高于阈值驱动转轮询（`poll` device VMO 完成环），避免每包一次上下文切换。

> 与 `10` §5-1 协同：`59` 定义「中断转发 + 合并 + 轮询」三态；本文确认用户态驱动的中断语义 = 内核转发 + 驱动侧节流，不引入新抽象。

### 3.4 IOMMU 域与 DMA 隔离

- 每个 L3 驱动分配**独立 IOMMU 域**（VT-d / SMMU / RISC-V IOMMU），其 DMA 窗口仅覆盖自己的 device VMO 物理页；在飞 DMA 越界即被 IOMMU 拦截（而非污染任意内存）。
- 撤销锁序列（§3.5）在 revoke 前先**使该 IOMMU 域失效**，截断在飞 DMA——这是用户态驱动隔离强于「仅进程地址空间隔离」的关键（进程级隔离管不住 DMA）。
- 无 IOMMU 平台：按决策表第 3 条，禁止用户态 DMA，仅 L1 受信内核态驱动可碰（`10` C8 退路，本文 §2.2 收口）。

### 3.5 撤销锁与进程死亡自动回收（接续 10 C8 / 29 T9）

驱动能力回收遵循 `10` §A 的**撤销锁六步**，本文补其「第二重保险」的账本语义：

1. 屏蔽 IRQ 转发（防 revoke 后还来中断）
2. 冻结驱动进程（不再发起新 MMIO）
3. IOMMU 域对该驱动失效/解映射（截断在飞 DMA）
4. revoke 设备 cap 句柄（从进程句柄表移除、记 dead）
5. kill + 释放地址空间
6. 仅全部完成后 fresh-mint 新 cap 并 spawn

**第二重保险（本文深化）**：cap 记录带「holder 回指 + 生命周期绑定持有者 Job」——驱动所在 Job 死亡（`04` exception channel → supervisor）即触发步骤 4–5 自动执行，**无需显式撤销调用**。同一（设备, 资源区间）任一时刻至多一个 live cap（除非显式 `duplicate-with-rights`），杜绝悬垂硬件引用 / 双持。

### 4.2 Genode（★新增，最贴近 MeuOS 哲学）

- Genode 的**设备驱动是用户态组件**，运行在独立的「驱动运行时（driver runtime）」上；每个驱动只通过**能力**（Genode 的 `Capability` + `Session` 接口）与内核/其他组件交互，硬件资源（MMIO/IRQ/DMA）经**平台驱动（platform driver）**中介授权 [Ref-G1]。
- `Platform` 会话把「某设备的 MMIO/IRQ」封装为能力对象下发给具体驱动；驱动不直接碰物理布局——与 MeuOS 第①层设备资源 cap + 能力网关（10 §4.6）同构。
- **借鉴点**：Genode 的「统一驱动运行时 + 每驱动能力沙箱 + 组件树」是 L3 档位（§2.3）的工程化范本；其 `Nitpicker`/`Input`/`Framebuffer` 会话接口可对照 MeuOS 的 `GPU_*`/`INPUT_*` cap 接口（`34`）。
- **不选**：Genode 的 `Nova`/`Fiasco` 微内核底座与 MeuOS 混合内核（00 A6 lean hybrid）不同；Genode 无 VMO 零拷贝叙事（MeuOS 取 Fuchsia 的 VMO 思路更优）。

### 4.3 UEFI 驱动模型（★新增，引导期设备能力的来源）

- UEFI 驱动分 **DXE（Driver Execution Environment）驱动** 与 **UEFI 驱动模型**（基于 `EFI_DRIVER_BINDING_PROTOCOL` 的 `Supported/Start/Stop` 生命周期，按 Controller Handle 匹配）[Ref-U1][Ref-U2]。
- 关键：UEFI 阶段驱动**运行在引导期内核态（无隔离）**，职责是枚举硬件、提供 `BlockIo`/`SimpleFileSystem` 等引导协议；**一旦 MeuOS 内核接管，这些驱动即退出**，其枚举结果（设备拓扑）被 MeuOS 在 Stage 4 吸收为可信设备拓扑树（`10` C8 / `09`）。
- **借鉴点**：UEFI 的 `Driver Binding` 生命周期（Supported→Start→Stop）可直接对齐 MeuOS 驱动的 `probe/match/start/stop` 状态机（`10` §4.3）；其「按 Controller Handle 匹配」对应 MeuOS 的 `bind` 规则（兼容字符串 / VID:PID）。
- **不选**：UEFI 驱动无 capability、无隔离、全特权——仅作**引导期枚举器**，绝不作为运行时驱动模型（与 `00` A2 Day1 唯一 capability 模型冲突）。

### 4.4 Windows UMDF（深解，逾 `10` 一笔带过）

- UMDF（User-Mode Driver Framework）驱动运行在**独立用户态进程（WUDFHost.exe 实例）**，经 **UMDF 反射器（Reflector）** 与内核模式栈通信；崩溃只杀 WUDFHost，系统不蓝屏 [Ref-W1][Ref-W2]。
- **与 MeuOS L3 的同构**：UMDF 进程隔离 + 重启 ≈ MeuOS 用户态驱动 + RS 看门狗（`10` §4.2 / 29 T9）；UMDF 的 **I/O 队列（I/O Queue）对象 + 队列回调** ≈ MeuOS 的 `submit(vmo,...)` + 完成事件。
- **差异**：UMDF 隔离靠 Windows 对象安全描述符（SID/DACL），非 capability；MeuOS 用对象级 rights 位图（`07`）+ 受约束 mint，粒度更细、可形式化（`19`/`20`）。
- **借鉴**：UMDF 的「反射器转发 + 每驱动宿主进程」是中断/IRQ 转用户态的工程范本，印证 §3.3 内核转发路径的成熟性。

### 4.5 Fuchsia devhost / Driver Runner（深解）

- Fuchsia 驱动跑在 **devhost 进程**（同一 devhost 可载多驱动，按隔离需求分 host），由 **Driver Runner** 按 DFv2 绑定规则加载；驱动间、驱动与系统经 **FIDL** 通信 [Ref-F1][Ref-F2]。
- **与 MeuOS 的两层能力模型对照**：Fuchsia 的 `fuchsia.hardware.*` FIDL 协议 ≈ MeuOS 第②层领域 I/O cap（BLOCK_*/GPU_*）；其 `devicetree`/`acpi` 节点能力 ≈ MeuOS 第①层设备资源 cap。
- **借鉴**：DFv2 的「实时驱动（live driver）+ 统一绑定」证明「组件化用户态驱动 + 强类型 IPC 解耦」可承载真实设备栈；MeuOS 取其「组件化」+ 保留 L1 内核快速路径（`00` A6 lean hybrid 差异点）。

### 4.6 seL4 用户态驱动实证（★新增，形式化背书）

- seL4 所有驱动**用户态**，设备寄存器作为 **device-untyped** 能力授权给驱动；数据通路经用户态驱动 + 共享帧（对应 MeuOS device VMO）[Ref-S1]。
- 关键实证：seL4 的 **verify-VMM / 用户态设备驱动** 已被形式化验证为「驱动崩溃不影响内核不变量」——这是 L3 档位隔离强度的**最高证据级**，也是 MeuOS `19`/`20` 可验证性目标的对标 [Ref-S2]。
- **借鉴**：device-untyped「不可写、只能 retype 为可映射 frame」子思想已被 `03` C1 吸收为 device VMO 不可写 right（`10` §引用澄清（来自24）确认非失真）；seL4 的「驱动=用户态 + 设备即能力」是 MeuOS 第①层设备资源 cap 的形式化正名。

### 4.7 macOS IOKit / Linux（简述，已有 `10` 覆盖）

- IOKit（§4.3 在 `10` 已详）：`IOService`/`IORegistry` 设备对象树 + `probe/match/start` 生命周期是 MeuOS 驱动状态机的蓝本，但**崩溃即内核崩**——MeuOS 仅在 L1 生死相关设备接受此代价，L3 必须出核。
- Linux（§3.1 在 `10` 已详）：全内核态、共享地址空间是反面教材；Rust for Linux 证明内核态 Rust 抽象可行，但仍是全特权——MeuOS 取其「Rust 写驱动」可行性，弃其「全特权上下文」。

## 5. 与 BLOCK_*/GPU_* right 的关系（领域 cap 由驱动 mint）

### 5.1 两层 right 的分工（显式化）

基于 §3.1 的两层能力模型，right 类明确分工：

| 层次 | right 类 | 持有者 | 语义 | 撤销影响 |
|------|----------|--------|------|----------|
| 第①层 设备资源 | 隐式资源 cap（MMIO/IRQ/DMA/IO port） | 驱动 | 「能碰硬件寄存器/中断/DMA 窗口」 | 撤销 = 硬件访问断；需撤销锁（§3.5） |
| 第②层 领域 I/O | `BLOCK_*`（bit23–27, 33-D1） | FS/存储组合服务 | 「能向块设备提交读/写/派生子设备」 | 撤销 = I/O 断，不动硬件映射 |
| 第②层 领域 I/O | `GPU_*`/`DISPLAY_*`/`SURFACE_*`/`INPUT_*`（bit32–36, 34） | 图形服务/合成器/输入服务 | 「能向 GPU/显示/输入提交命令/分配 surface/读事件」 | 撤销 = 渲染/输入断 |
| 第②层 领域 I/O | `NET_*`（bit28–31, 25）/ `AUDIO_*`（bit19–22, 35） | 网络栈/音频服务 | 同构 | 同构 |

> **关键澄清（本文增量）**：驱动**持有第①层 + 第②层的 `BLOCK_MINT_SUBDEV`/`MANAGE`**（见 `33` §3.3），但**不持第②层的 `BLOCK_READ`/`BLOCK_WRITE` 去自己做 I/O 语义**——它只负责把硬件封装成领域对象并 mint 收窄后的第②层 cap 给上层。这让「谁能碰寄存器」与「谁能提交 I/O」成为两个可独立审计、独立 revoke 的维度。

### 5.2 受约束 mint 防 confused deputy（接 07 §4.5 / 06 §6-2）

驱动作为第②层 cap 的 mint 委托人，其 mint 受 `07` §4.5 受约束派生约束：

- **mint 权上限 = 自身 rights ∩ 客户端请求下限**：驱动只能 mint 它自己持有的 rights 子集，且不能超过申请者被授予的界限——杜绝驱动越权给某服务「整盘 `BLOCK_SUBDIVIDE`」。
- **子 cap 区间/rights 双向收窄**：`BLOCK_SUBDIVIDE`（整盘 → 分区）产出的子 cap 区间与 rights 都收窄（去 `SUBDIVIDE`，仅留 `READ`/`WRITE`），revoke 传播进 `07` derivation tree（`33` D4）。
- 这与 `33` D8（存储组合服务的 confused deputy 防护）同源——**驱动是第①个、最底层的 mint 委托人**，其受约束性决定了整条 capability 组合树（`33` §3.4 嵌套组合）的起点可信。

## 6. 驱动生命周期与 Job 账本（接 29 / 07 §4.3 / 04）

### 6.1 驱动即一个 Job

每个 L3 驱动服务**本身是一个 Job**（`00` A5 Job 资源账本 Day 1）：其 CPU/内存/fd 上限/句柄数/IO 配额在 spawn 时声明（`07` §4.3 维度 B），与权限同源——「创建时显式声明、运行期不可隐式扩张」。

- **账本防 DoS**：驱动句柄数与消息队列深度计入 Job 账本，超额 `EAGAIN`/`ENOMEM`（`29` T8 / `20` I4）；驱动不得借设备 cap 耗尽系统句柄。
- **账本防爆炸半径**：驱动崩溃的爆炸半径 = 其 Job 持有的句柄边界（`29` §关键推论），而非整个系统——capability 模型把「全或无」翻转为「局部、可枚举、可隔离」（`29` §结论 1）。

### 6.2 启动/匹配/授权/运行/重启的账本语义

| 阶段 | 动作 | Job 账本 / 能力语义 |
|------|------|----------------------|
| 枚举 | 解析 DT/ACPI → 设备拓扑树 | Stage 4 由 capability 监视器 mint 第①层 cap（10 C8） |
| 匹配 | 驱动 `bind` 规则比对设备节点 | 驱动管理器（devmgr）确认驱动声明资源 ⊂ 设备拓扑 |
| 授权 | mint 第①层 cap + 驱动 spawn 时持第②层 `MANAGE`/`MINT_SUBDEV` | devmgr 持受约束 mint right，仅 mint 恰好声明所需（10 C8 §A.1） |
| 启动 | 驱动进程以「仅持上述 cap」启动 | spawn 账本绑定 cap 与配额（07 §4.3） |
| 运行 | 处理 I/O / 响应中断转发 | 看门狗 ping；每 cap 带 holder 回指 Job |
| 重启 | 崩溃/超时 → 撤销锁 → RS 重启新 Job | 旧 Job 死亡自动回收 cap（§3.5 第二重保险）；新 Job 拿 fresh-mint cap |

### 6.3 崩溃 → exception channel → supervisor 重启（接 04 / 00 A9）

- 驱动致命异常（Rust panic=`unwind` 在 L3，接 16 C5）经 **exception channel** 上报 `meu-supervisor`（`00` A9），由策略决定 kill/dump/restart，**不拖内核**。
- supervisor 重启走 §6.2 撤销锁 + 新 Job spawn；重启次数可计入 Job 账本（防重启风暴 DoS），超阈值升级策略（如标记为不可信、禁用该设备）。
- L1 生死相关驱动（中断控制器/定时器/看门狗）不在此路径：其故障 = 内核 panic + 重启策略（16 C5 abort 分支），与「尽快交权缩 TCB」不矛盾——它们本就是不可出核的极小集合。

## 7. 跨架构（x86 / ARM / RISC-V / i386 / CHERI）

### 7.1 各架构的隔离原语映射

| 架构 | 中断控制器 | IOMMU / 地址转换 | 第①层 cap 落地 | MeuOS 驱动隔离档位 |
|------|------------|------------------|----------------|---------------------|
| **x86-64** | APIC / x2APIC | VT-d（IOMMU 域） | MMIO/IRQ/DMA cap + VT-d 域 | L1（APIC/定时器）+ L3（默认，VT-d 强制） |
| **ARM64** | GICv3/v4 | SMMU（IOMMU 域） | 同上 + SMMU 域 | L1（GIC/定时器）+ L3（默认，SMMU 强制） |
| **RISC-V** | PLIC / APLIC / IMSIC | RISC-V IOMMU 规范 | 同上 + IOMMU 域 | L1 + L3（IOMMU 规范较新，需基线支持） |
| **i386（32位）** | PIC / APIC | 多无 VT-d | 早期 C/asm 引导，Rust TCB 受限（C6） | 仅 L1 受信内核态驱动；用户态 DMA 退化（无 IOMMU） |
| **CHERI（RISC-V/Arm Morello）** | 同上 | 同上 + 指针能力 | handle 对齐 CHERI 指针能力（07 §4.4） | L3 加固：句柄硬件不可伪造/越界 |

> 跨架构一致性：无论架构，**第①②层能力模型与 Job 账本语义不变**；变的只是「中断控制器驱动用哪个硬件抽象（HAL）」与「IOMMU 域用哪个后端」。这正是 capability 模型相对 Linux `#ifdef` 驱动碎片化的优势——驱动逻辑与硬件布局解耦（`10` §4.5）。

### 7.2 i386 引导期约束（接 C6）

`00` C6 规定 i386 全程纯 C 下 Rust TCB 范围受限——此时用户态驱动框架的 Rust 部分尚未接管，**仅 L1 受信内核态驱动可用**（中断控制器/定时器/早期串口），且用户态 DMA 因无 IOMMU 退化（§2.2 第 3 条）。一旦 Rust TCB 在 64 位模式下精确接管（C6 裁决时刻），L3 用户态驱动框架即激活。本文确认：**Day 1 最小集不在 i386 上承诺用户态 DMA 驱动**。

## 8. Day 1 最小驱动集（深化落地）

### 8.1 清单（交叉 `10` 附录 A + `33` B1–B5 + `34`）

| 驱动 | 档位 | 第①层 cap | 第②层 mint | 隔离机制 | 优先级 |
|------|------|-----------|------------|----------|--------|
| 中断控制器（GIC/APIC） | L1 | 全局 IRQ cap（仅内核） | — | 无（生死相关） | 必做 |
| 定时器 | L1 | 特定 MMIO | — | 无 | 必做 |
| 看门狗 | L1 | 特定 MMIO | — | 无 | 必做 |
| 早期串口（Stage1→5 交权） | L1→L3 | 临时 MMIO → 撤销后留 emergency-write 窄 cap | `IO` 类（待定） | 撤销锁 + 进程死亡回收（10 C8） | 必做 |
| virtio-blk | L3 | MMIO/IRQ/DMA + IOMMU 域 | `BLOCK_READ/WRITE/IO` + `BLOCK_MINT_SUBDEV` | 独立进程 + device VMO + 看门狗 | 必做（rootfs 依赖） |
| 分区服务 | L3（组合） | 消费整盘 `BLOCK_*` cap | `BLOCK_SUBDIVIDE` → 分区 cap | 独立 Job + 受约束 mint | 必做（B3） |
| virtio-net | L3 | MMIO/IRQ/DMA + IOMMU 域 | `NET_*` | 同 virtio-blk | 必做（netstack 依赖，25 C15） |
| virtio-gpu / 简单 framebuffer | L3 | MMIO/IRQ/DMA | `GPU_*`/`DISPLAY_*`/`SURFACE_*`/`INPUT_*` | 独立进程 + device VMO（34） | P1 |
| virtio-console | L3 | MMIO/IRQ | `IO` 类 | 同串口 | P1 |

> 最小集 = L1（中断/定时/看门狗/早期串口）+ L3（virtio-blk + 分区 + virtio-net）即可支撑 `mcc`+`meuos-libc` 在自研内核自举（rootfs 块设备 → FS → 应用 → 网络），与 `06` F1–F5、`33` B1–B5、`25` C15 协同。`34` GPU / `35` 音频为 P1，不阻塞启动。

### 8.2 启动依赖时序（接 09 / 10 C8 / 33 D6）

```
Stage 1  C/asm 引导：L1 中断控制器+定时器+看门狗直写，早期串口内核直写（cap 未起）
Stage 4  capability 监视器 mint 第①层设备 cap（从可信设备拓扑树，无 root 设备 cap）
Stage 5  驱动管理器匹配 → 授权 → spawn：
           L3 virtio-blk + 分区服务（rootfs 块设备 cap 就绪）→ FS 挂载
           L3 virtio-net → netstack（25）
           早期串口临时 cap 撤销 → 交用户态 console 服务，留 emergency-write 窄 cap
M0/M1    应用经 FS/网络在自研内核自举
```

> rootfs 块设备 cap 是**最早关键依赖**（33 D6），必须在 FS 之前就绪；其 cap 经撤销锁 + 进程死亡回收双保险（§3.5），拔盘/驱动崩溃 fail-closed。

## 9. MeuOS 推荐（收口）

1. **默认 L3 用户态驱动，仅生死相关设备留 L1**——决策由 §2.2 量化框架决定，而非意识形态；Day 1 不默认把 NVMe/GPU 提交环留核（优化项，待基准证明）。
2. **两层能力模型是强制结构**——第①层设备资源 cap（MMIO/IRQ/DMA）与第②层领域 I/O cap（BLOCK_*/GPU_*/NET_*/AUDIO_*）必须分离，驱动是二者唯一的 mint 委托人且受约束（§3.1 / §5）。
3. **L3 隔离 = 独立进程 + IOMMU 域 + 不可写 device VMO 三重**——缺一即退化为弱隔离；无 IOMMU 平台禁用户态 DMA（§3.2–3.4 / §2.2）。
4. **驱动即 Job，生命周期接入账本与 exception channel**——看门狗重启、撤销锁、进程死亡自动回收三位一体（§3.5 / §6）。
5. **跨架构只换 HAL 与 IOMMU 后端，能力模型不变**（§7）。
6. **Day 1 最小集 = L1×4 + L3（virtio-blk/分区/virtio-net）**（§8），其余（GPU/音频/USB）P1 演进。

## 10. 自主结论 + 待决项

### 10.1 自主结论

1. 「驱动位置」是**可量化决策**（延迟预算/故障域/IOMMU/TCB）的交点，非微内核 vs 宏内核意识形态；MeuOS 用 L1（生死）+ L3（默认）两档，预留 L2/L4（§2）。
2. **两层能力模型**（设备资源 cap vs 领域 I/O cap）是 `10`/`33` 隐含未拆的关键结构，必须显式——它是 confused deputy 防护与「硬件布局解耦」的落点（§3.1 / §5）。
3. L3 隔离强度 = 进程级 + IOMMU 域级 + device VMO 不可写，**三重叠加**才是用户态驱动安全的真实边界（§3）。
4. 驱动生命周期与 Job 账本、exception channel、撤销锁、进程死亡自动回收**串成一条链**，是 `29` T9 挡点的可执行落地（§6）。
5. 跨架构一致性由 capability 模型保证，仅 HAL/IOMMU 后端差异（§7）。
6. Day 1 最小集收敛为 L1×4 + L3 三驱动，足以自举（§8）。
