## 0. 核心结论（一句话）

> **容器 = 一个 Job 子树 + 组合 namespace 视图（由 `06` C3 每进程 namespace 与 `04` Job 账本组合而成）；sandbox 默认 deny，capability 委托范围显式 grant，与多 realm 边界（`00` 第八轮 / `56` §7.3 冲突8，下文统称「A7 多 realm」二级标签，与 `00 §2` 地基 A7=VMO/VMAR 零拷贝**无关**）同构；OCI-ish 镜像/manifest 投影为 `.mimg`/`.msys` 载体（C61-1 唯一载体）；并与 `06` C3、`04`、`07`、`46`/`47`、`53` 用户系统衔接——全程复用既有内核原语（Job / namespace / capability / VMO-pager），不引入新原语、不新增 right bit。**

## 1. 容器模型（Job 子树 + namespace 组合视图）

### 1.1 先推演「容器应该是什么」

从内核哲学出发——MeuOS 已有 Job（资源与生命周期单元，`04` §4.1/§4.4）与每进程 namespace（capability 组合树，`06` C3）。那么「容器」在 MeuOS 里不应是一个新原语，而应是**既有两件事的组合闭包**：

- **资源与生命周期边界** = 一棵 Job 子树（`04` §4.1）。容器 init 进程挂在某个 Job 下；其派生的所有进程/子 Job 自然归入该子树；父 Job 终止 → 传播终止整棵容器树（lifetime control，对齐 Zircon）。
- **视图边界** = 一组 namespace 绑定（每个进程在 spawn 时 COW 继承 Job 的 namespace 模板，`06` C3 采纳结论）。容器即「一组进程共享同一份 namespace 模板 + 各自可在模板内 `unveil` 裁剪」——没有绑定的路径对容器内进程「根本不存在」（默认全不可见、显式 reveal，对齐 `06` §4.1）。

二者合一：**容器 = 一个 Job 子树 + 附着于该 Job 的 namespace 模板**。

### 1.2 MeuOS 容器模型（自主收敛）

```
┌─────────────────────────────────────────────┐
│  Job（容器根 Job，即容器身份）                 │
│  - 资源配额 (cpu/mem/handles/io/pid)  §4.4    │
│  - namespace 模板（容器共享视图，C3 COW）      │
│  - capability 委托范围（受约束 mint §4.5）     │
│  - 监督策略（容器 init 崩溃→重启/终止传播）    │
└───────────────┬─────────────────────────────┘
                │ 容器 init 作为首个进程（持有本 Job handle）
┌───────────────▼─────────────────────────────┐
│  Process: container-init (pid 1 角色)         │
│  - 命名空间视图 = Job 模板 COW 继承            │
│  - 后续 spawn 在「本 Job 子树」内，视图同源    │
└───────────────┬─────────────────────────────┘
                │
         ┌──────▼──────┐   ┌──────▼──────┐
         │ 子 Process   │   │ 子 Job      │  ... 容器内部层级
         └─────────────┘   └─────────────┘
```

- **与 `04 §4.1` 衔接**：容器不是「特殊进程」，而是「被 `meu-supervisor` 在指定 Job 下 spawn 的普通进程树」，其 Job handle 决定配额与能力边界（除非显式收窄）。这与 `04` 原生 spawn 模型完全一致——**容器只是 spawn 的一个结构化用法**，而非新一等公民。
- **与 `04 §4.4` 衔接**：容器配额 = Job 账本配额（CPU 权重+可选硬上限 / 内存上限 / 句柄数 / IO 带宽 / pid 数）。限额是 Job 的固有属性，进程诞生即受限，无法「先越权再被关进笼子」（超越 cgroups 事后挂接）。
- **与 `06` C3 衔接**：容器的「文件系统隔离」= 该 Job 的 namespace 模板中 `{ "/": root, "/dev": dev_svc, "/proc": proc_svc, "/net": net_svc, "/msys": sysroot }` 绑定集；容器内部进程 spawn 时 COW 继承并可在自己的命名空间内 `unveil` 裁剪，互不影响（对齐 `06` §4.1 + C3 采纳结论「spawn COW 继承父/Job 模板」）。
- **与 `04 §4.5` 衔接（监督）**：容器 init 由 `meu-supervisor` 拉起并持有其 Job handle；容器 init 崩溃 → 经 exception channel（`00` A9）上行监督者，按策略重启/终止传播。容器自带「监督内监督」层级（`04` §4.5 监督树与 Job 树重合），无需外部 `systemd`/`containerd`。

> 与参照系统的差异：比 Linux「cgroup + namespace + pivot_root 三件套」更统一——MeuOS 把三者收敛为「Job 子树 + namespace 模板」两个本已存在的原语；比 FreeBSD jail 多了 capability 受约束 mint 的细粒度委托；比 gVisor/Firecracker 更轻——sandbox 边界是 capability 而非独立内核/VM（见 §2）。

## 2. sandbox 默认 deny 与 capability 委托（显式 grant）

### 2.1 默认 deny 的落点

MeuOS 的 sandbox 默认 deny 不是「加一层 seccomp 过滤器」，**而是 capability 模型的天然推论**（`00` A1/A2）：进程只持有 spawn 时显式传入/派生的句柄与 rights，没有隐含权限。因此「容器 sandbox 默认 deny」= 容器 init 的 Job 模板只 reveal 最小命名空间绑定、容器子进程只继承收窄后的 capability 集（对齐 `04` §4.2 G4「默认不继承任何句柄」+ `08` 兼容层默认不绕过 pledge）。

- **无「root 逃逸」面**：真实权限源是 capability（`53` 内核模型：无 root、无 uid 权限附着），`setuid` 二进制 = 受限 spawn + 显式 capability（`04` C4 采纳），**永不提权**。容器内「看起来是 root（uid 0）」只是 `53` 合成 uid 视图（`00` C4 / `53` §7.1.4），零权限附着，不突破任何内核不变量。
- **sandbox 收缩 = 派生收窄**：容器子进程 spawn 时，其 capability 集 = 父 Job 能力边界 ∩ 显式收窄声明（`07` §4.5 派生收窄），只能更窄、不可越类放大（与 `06` C2 受约束 mint 同源，破 confused deputy）。

### 2.2 capability 委托范围：显式 grant，与多 realm 边界同构

容器对外（跨 Job、跨 realm、跨命名空间）的任何能力授予，必须**显式 grant**，且遵循 `07` §4.5 受约束 mint（委托人 rights 上限 ∩ 客户端请求下限取交集）。这恰与**多 realm 边界**（`00` 第八轮自主采纳 / `56` §7.3 冲突8）同构：

| 多 realm 边界（已采纳） | 容器 sandbox 委托（本文同构复用） |
|--------------------------|------------------------------------|
| 跨 realm 取消/能力/命名传播**默认 deny、不穿透** | 跨容器能力/命名/job 传播默认 deny、不穿透 |
| realm = namespace 之上的隔离域，capability 边界即 realm 边界 | 容器 = 一个 realm 实例，Job 边界即容器边界 |
| 仅**显式 grant** 跨域，不引入新统一跨 realm 层 | 仅显式 grant 跨容器共享（如 volume/共享 socket/跨 realm 服务），不引入新跨容器层 |
| 不引入新内核原语 | 不引入新内核原语（复用 Job/namespace/capability） |

> **编号注意**：本 § 与 `53 §7.5`、`46 §7.7`、`47 §7.8` 引用的「A7 多 realm」是 `56`/`62` 的二级标签，与 `00 §2` 地基 **A7=VMO/VMAR+pager 零拷贝** 无关——切勿覆盖 A7 地基。容器即该「多 realm 边界」的一个标准实例，而非新概念。

### 2.3 跨容器共享的投影语义

- **共享卷（volume）** = 两个 Job 的 namespace 模板各自 reveal 同一个 `.msys` 子树上的目录能力（`06` mount-capability 委托 / C3 同构），经 cap-transfer 显式 grant，受 `READ`/`WRITE` rights 约束。
- **共享 socket / 服务** = 经 `05` Channel 端点或 socket 句柄的 cap-transfer（`63` §3.1），跨 Job 授予需发送方持 `GRANT` right（`07` §4.5）。
- **网络命名空间视图** = 容器 `/net` 子树 reveal（`06` C3 / `63` N7），由 netstack 服务的每接口/每子网视图提供，容器只看见被授予的子树。
- **以上全部 fail-closed**：未显式 grant 即不可达（对齐 `53 §7.5` realm 默认 deny），映射错误不突破内核不变量。

## 3. OCI-ish 兼容投影（镜像/manifest → `.mimg`/`.msys`）

### 3.1 唯一载体纪律（C61-1）

`00` 第八轮采纳 **C61-1**：`.mimg` 为五架构唯一内核启动载体，`.msys` 为 sysroot/rootfs 唯一载体（取代裸 ELF/multiboot/`06` C-G5）。**容器镜像不得另创容器专属格式**——OCI-ish 镜像/manifest 必须投影为既有 `.mimg`/`.msys` 载体，与系统自举/回滚共用同一条信任链（`32`/`61` §3、§5）。

### 3.2 OCI 构件 → MeuOS 载体映射

| OCI 构件 | MeuOS 投影 | 载体 / 落点 | 说明 |
|----------|------------|-------------|------|
| OCI Manifest（JSON，索引 layers/config） | 容器 manifest = **`.msys` 内容寻址 head Ref + 签名**（`06` §4.3 / C-G5 A 子集） | `.msys` 子树 Ref + ed25519 签名（`61` §3.2 双锚同构） | 镜像指纹 = `.msys` 内容哈希，天然防篡改（`06` C-G5 / `54`） |
| OCI Image Config（args/env/workingDir/entrypoint） | **Job manifest / spawn 输入**（`04` §4.2） | supervisor 声明式服务描述（`04` §4.5） | 进程参数/环境 = spawn argv/env；capability 集 = 容器 Job 能力边界 |
| OCI Layer（tar diff，有序叠加） | **`.msys` 可写子卷的 CoW 层**（`06` §4.3 暂存克隆 + B 主线 extent CoW） | `.msys` 命名空间子树 | 层叠加 = CoW 克隆链，原子 repoint 切层（`06` §4.3 非破坏式） |
| OCI Layer 内容（文件） | 统一命名空间节点 + 句柄 rights（`06` §4.1/§4.2） | MeuOS-FS 服务 | 校验和/压缩/加密在 extent 层、密钥=capability（`06` C2） |
| OCI runtime 启动（runc create/start） | `meu-supervisor` 在容器 Job 下 spawn（`04` §4.5） | supervisor + Job | 不引入 OCI runtime 内核 ABI，仅兼容层翻译 |
| rootfs / pivot_root | `/msys` + `/` 命名空间 repoint（`06` §4.3） | namespace 模板绑定 | 非破坏式，旧持有者续持旧能力（`06` C-G5） |

- **信任链对齐**：容器镜像验签复用 `.msys` 的 ed25519 包签名 + extent Merkle 根（`61` §3.3 / `06` §4.2），与 `.mimg` 双锚对称——容器与系统共用 `32` 信任链，无独立镜像信任根。
- **五架构同源**：`.mimg`/` .msys` 内部承载五架构内核/库；容器镜像**一次打包、五架构同载**（`61` §3.2 Item 0 内含五架构 `arch/<arch>/boot` 入口段），容器运行时无需 per-arch 镜像。

### 3.3 uid 映射投影边界（与 `53 §8.3`/`§8.4` 协同）

- **容器内部 uid 视图** = `53` 合成 uid 兼容投影（`00` C4 / `53` §7.1.4）：容器内「uid 1000」只是合成视图标签，**真实隔离始终由 capability 兜底**（对齐 `53 §8.3`）。
- **「容器内 uid ↔ 宿主」映射** 在 MeuOS 不是内核 userns，而是「容器内部合成 uid 视图 ↔ 真实 capability 作用域」的兼容投影；映射错误不应突破内核不变量（`53 §8.3` 待原型验证项，`C4`/`D6` 协同）。
- **`access()` 模拟返回值**（`53 §8.4`）：兼容层据进程 capability 集合模拟返回值，何时真/何时 `EPERM` 由 `53 §8.4` 定稿，不引入内核新语义。
- **边界纪律**：任何「uid 映射即越权」的反模式被 capability 兜底否决（对齐 `53 §8.3` 实质成本之五）；合成 uid 不携带任何权限（与 `00` C4 / `53` 内核模型严格一致）。

## 4. 资源隔离粒度（CPU/内存/IO/pid 以 Job 为单元）

### 4.1 隔离单元 = Job（与 `04 §4.4` 同构）

容器资源隔离**完全复用** Job 账本（`04` §4.4），无独立 cgroup 式机制：

| 资源 | 计量方式（Job 账本） | 容器语义 | 超限行为 |
|------|----------------------|----------|----------|
| CPU 时间 | 公平权重 + 可选硬上限（带宽） | 容器 CPU 配额 = Job 权重 | 降权重/限流，不杀进程 |
| 内存 | Job 级内存上限（VMAR 映射 + 内核对象） | 容器内存上限 | Job 内选择性 OOM/通知监督者（`04` §5 议题5） |
| 句柄数 | 句柄表上限 | 容器句柄上限 | 拒绝新分配 |
| IO 带宽 | 按设备/层配额（原型期可后置 `05`/`10`） | 容器 IO 配额 | 限流 |
| pid/线程数 | pids/threads 上限 | 容器进程数上限 | 拒绝 spawn |

- **层级天然是树**：容器 Job → 子 Job → Process，与监督树重合（`04` §4.4），「谁该为超限负责」归因与监督/重启策略一体化。
- **与 `06` C-G5 回收归属一致**：容器镜像的自动 CoW 版本链/Blob GC 归 FS 服务自管，**不计入**容器 Job 账本；容器显式快照（含生效 `.msys` sysroot）归 supervisor 经 Job 账本管辖（`06` C-G5 第七轮裁决）。

### 4.2 能耗账本（与 `27`/`40` 弱耦合）

- **能耗原型期不作为 Job 账本硬配额项**（`04` §4.4 第四轮裁决回写 / `27`/`40`）：容器能耗不写入账本、不强制上限。
- **能耗仅作 task packing 输入**：用户态 `powerd`（`27` §3.3）据容器 Job 的 CPU 配额做能耗感知调度（同 Job 内任务聚核、空闲核深 idle）；调度器（EEVDF+RT）的 EAS 子策略（`04` §4.3 / `27` §5.1）在弱耦合下仅做 packing。
- **强耦合待 EAS 议题裁决**：把能耗升级为硬配额（超限限流/降权重）待 `04` §5 议题6（异构核 big.LITTLE EAS）裁决后定；届时扩展 `§4.1` 账本对象与检查点。**不变量**：`27`/`40` 的 thermal 硬限始终是内核 TCB 无条件边界，容器能耗约束不得突破。

## 5. 与用户系统（`53`）及监督者（`04`）协同

### 5.1 与监督者（`04`/`46`/`47`）协同

- **容器生命周期由 `meu-supervisor` 驱动**（`04` §4.5）：supervisor 读取容器 manifest（§3.2），在指定 Job 下 spawn 容器 init，持有其 Job handle；消费进程退出/异常事件（`00` A9 exception channel），按策略重启/升级/降级。
- **监督者自身受约束**：supervisor 持「创建 Job/监督」专属 capability（`04` §4.5），普通容器进程无法冒充；容器 init 崩溃不污染 supervisor（结构化取消，`04` §4.6 / `00` A9）。
- **与 `46`/`47` 衔接**：监督/Job 的详细实现（Job 命名可查询、scoped 标识、生命周期传播语义、异常仲裁）见 `46-进程管理-方案A` / `47-进程管理-方案B`（`47 §7.8` 含 realm 边界监督语义）；本文只承接「容器 = Job 子树 + namespace 模板」的监督落点。

### 5.2 与用户系统（`53`）协同

- **身份 = capability，合成 uid 仅展示层**（`53` §7.1.4）：容器内身份视图由 `53` 合成 uid 翻译层投影（`00` C4 / `53` 第七轮 C-G4 采纳 B），零权限附着；容器「root」只是合成标签。
- **uid 映射投影**（`53 §8.3`/`§8.4`）：容器内部 uid ↔ 真实 capability 作用域的投影边界由 `53` 定稿，本文不重判（见 §3.3）。
- **跨 realm 身份边界**（`53 §7.5`）：容器即 realm 实例，跨容器身份/会话隔离由 capability 派生边界承载（与 `53 §7.5` 多 realm 边界一致），合成 uid 不穿透 realm。
- **认证 broker 协同**（可选）：容器镜像签名校验可复用 `53 §8.5` 的 `AUTH_ISSUE` 受约束 issuer（bit55，`00` 第八轮冻结，Day 1 不触发）——仅当需容器镜像签发身份令牌时启用，本文仅标注衔接点。

## 6. 五架构同源；与既有地基同构（不引入新内核原语）

### 6.1 五架构同源

容器/sandbox 的全部语义（Job 子树 + namespace 模板 + capability 受约束 mint + `.mimg`/`.msys` 载体）**无任何架构相关代码**：

- 容器运行时逻辑 = 纯 capability + Job + namespace 的组合，**与页表格式/中断控制器/ABI 形态无关**（对齐 `01` 同源码异架构、`63` §7 netstack 同源范式）。
- 唯一架构差异点 = **启动载体 `.mimg`**（`61` §3.2 Item 0 内含五架构 `arch/<arch>/boot` 入口段，容器镜像一次打包五架构同载）与 NIC 驱动层（承接 `63` §7）——二者均不侵入容器/sandbox 抽象。
- i386 纯 C 约束（`02` C2）**不影响**容器运行时（它只落在内核早期启动与 NIC 驱动 C 后端），容器逻辑全在 Rust 用户态服务（supervisor / FS / netstack）与内核 capability 监视器（Rust TCB，`00` A3）。

### 6.2 与既有地基同构（无新原语、无新 right）
