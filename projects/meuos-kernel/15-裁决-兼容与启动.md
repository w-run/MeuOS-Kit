## 0. 一句话裁决（先给答案）

- **C4（兼容层是否击穿 Day1 安全边界）**：**不击穿。** 兼容层是 capability 模型的**消费方**，不是特权的发放方；放宽只经 per-package manifest 的 broad-unveil/capability-grant，且受 Job 账本约束与类上限封顶，**不存在全局开关**。
- **D1**：**禁止全局开关**。默认 deny-by-default 的 pledge/unveil 是唯一基线；放宽仅经包清单、记 Job 账本、可审计可撤销、且受"类权限上限"封顶，绝无"运行期关沙箱"的 API。
- **D2**：**全量 CoW 起步（VMO 子快照 + 单线程限定），后续优化**；fork 永远是慢速兼容路径，`meu_spawn` 是原生快路径；多线程 fork 显式拒绝。
- **D6**：**uid/gid 为纯合成视图，零权限附着**；单 Job 单 uid 视图起步，支持"声明式合成 uid 集合"，`setuid` 二进制 = 受限 spawn + 显式 capability，**永不提权**。
- **C6（Rust 接管时刻 + i386 Rust TCB 范围）**：**交接边界定为单一 `arch_boot → kernel_main()`**（采纳 09 §5.7 裁决 A）；i386 上**本应 Rust 的 TCB 不降级为 C**——改以"C 链接 Rust `.o`"（09 裁决 B）交付，仅早期启动/兼容层本就 C；i386 **不是降级架构**，只是构建管线不同；纯 C 退路仅在 `.o` 路径不可行时启用并需补偿控制。

## 1. 「应该是什么样」——解构推演

### 1.1 C4 应该是什么样（兼容层 vs Day1 安全边界）

从第一性原理推：MeuOS 内核内部只有 capability，没有 uid、没有 root、没有"隐式权限"。Linux 二进制却带着一整套"uid 0 万能 / 能 open 任意路径 / fork 免费"的契约进来。兼容层要回答的唯一问题是：**翻译时，权限从哪来？**

- **应该的样子**：权限只能来自该 Job 的 capability 集合。兼容层是一个**纯翻译面**——它把 `open("/etc/passwd")` 翻译成"对统一命名空间做一次 capability 查找"，查不到就 `ENOENT/EACCES`；把 `getuid()` 翻译成"回一个合成 uid 视图"，该视图**不解锁任何 capability**。
- **击穿边界的唯一方式**：引入一个"绕过沙箱"的开关——无论是全局 toggle，还是兼容层私自发特权句柄。一旦存在，capability 的"无隐式权限"前提即被破坏，Day1 安全模型退化为 Linux 式"root/特权后门"。
- **结论性判据**：凡能让一个 Linux 二进制在**不持有对应 capability** 的情况下做成事的设计，都是击穿。因此放宽必须是"capability 投影范围的显式扩大"（可审计、可撤销、有上限），而不是"关掉沙箱"。

### 1.2 C6 应该是什么样（Rust 接管时刻 + i386）

 Rust 的价值是把"能力令牌不可伪造/不可篡改"建立在内存安全之上（07 §4.4）。那么 Rust 应该在**具备 runtime 之后**立即接管所有安全关键路径。问题在两点：

- **接管时刻**：太早（C/asm 阶段无堆无 panic_handler）Rust 前提不满足；太晚则 TCB 早期被 C 侵蚀。唯一正确边界是"runtime 就绪的那一刻"——即 `kernel_main()` 入口。此前的 C/asm 是极薄、固定、可审计的（02 把早期启动归入"极小、固定"），此后的 Rust 把守 capability/IPC/调度/syscall 路由/VFS 抽象。
- **i386 的真相**：i386 缺**裸机 target**，但**不缺"编译 Rust 成 `.o` 并链接"的能力**。Rust TCB 组件（capability 监视器、IPC 端点、调度器、VFS 抽象）可以写成 `#![no_std]` + `extern "C"` 的普通 Rust，由 rustc 产出 `.o`，再经 C 链接器并入内核镜像。这与"裸机 target"是**构建方式**差异，不是"内存安全"差异。也就是说：**i386 没有理由让 TCB 退化为 C**——它只是换了交付管道。
- **真正的退化来源**：若坚决"i386 全程纯 C"（02 约束 C2 的字面解读），则上述 TCB 组件在 i386 上真的是 C，安全损失才真实发生。因此裁决的关键不是"i386 能不能用 Rust TCB"，而是"选哪条交付管道"。

### 2.3 D6 — uid/gid 视图 ↔ capability 精确映射

| 选项 | 做法 | 安全性 | 兼容性 | 多系统参照 | 裁决 |
|------|------|--------|--------|-----------|------|
| **O1 单 uid 视图（合成 0），零权限** | 每 Job/进程回一个合成 uid（默认 0），uid 不解锁任何能力；交叉访问走 capability/Job 成员判定 | **强**——uid 纯视图 | 多数程序（查 geteuid 决定行为）OK；多 uid 程序（su/daemon drop）受限 | Container userns root 映射（但 MeuOS 更强：内部 uid 0 也无权）；Fuchsia 无 uid（koid 标识，06 §C） | **采纳（起步）** |

## 3. 明确推荐裁决

### 3.1 D1 — 禁止全局开关，放宽仅经包清单 + 类上限 + Job 账本

**裁决立场**：**不允许任何全局/运行期"关闭沙箱"开关。** 默认 deny-by-default 的 pledge/unveil 是 Day1 唯一基线，兼容层**不持有也不发放**任何越过该基线的特权。

**理由**：
1. capability Day1 是地基非补丁（07 §2.3）。全局开关 = "特权后门"，直接废掉最小 TCB 与可推理性，与 00-A2/A3 对齐点冲突。
2. 放宽必须是**模型内**操作：把一个 Job 的 capability 投影范围**显式扩大**（broad-unveil + capability-grant），而非"暂停安全模型"。
3. 三道封顶闸，确保放宽不击穿：
   - **来源闸**：仅 per-package manifest 声明，由打包/系统侧审发，非运行期用户可切换。
   - **账本闸**：每次放宽记入该 Job 资源账本（07 维度 B），可审计、可撤销。
   - **类上限闸**：broad-unveil 只能扩展到"该包类别被授权的能力集合"内（如网络类包可 reveal 网络 capability，但**不能** mint 设备 MMIO capability）。即放宽是"路径/视图投影"与"已授予类别内的 capability"，不是"万能令牌"。
4. **fail-closed**：任何未在 manifest 声明、或越出类上限的访问，照常 `EACCES`/越界终止；不存在"运行期授权绕过"API。

### 3.2 D2 — 全量 CoW 起步（VMO 子快照 + 单线程限定），后续优化

**裁决立场**：**fork 起步即全量 CoW**，但用 VMO CoW 子快照实现（fork 时刻只建 VMO child + 地址空间/句柄投影，写时复制），**限定单线程进程**；多线程 fork 显式返回 `EINVAL`/`ENOSYS`。`meu_spawn` 永远是原生快路径，fork 永远是慢速兼容路径。

**理由**：
1. 语义完整性优先：08 §3.3 / 04 §G1 都确认 fork 仅兼容层、且应先保语义。全量 CoW 用 VMO child 实现，与内部 VMO/VMAR 模型一致（00-A7），不引入第二套地址空间机制。
2. 单线程限定是行业共识（glibc 亦禁止多线程 fork 后非 async-signal-safe 调用），规避"fork 后多线程状态撕裂"这一 POSIX 最大坑，也规避大页/多核下 CoW 账本正确性风险（04 §5-2）。
3. **分阶段落地，不与原型期抢跑**：M0–M1（mkit 子集直跑）**不需要 fork**；M2（宿主 mcc 在 MeuOS 跑）才需要 fork/exec——因此全量 CoW 在 Phase 2 落地即可，不阻塞 M0–M1。
4. 优化后置：对"fork 后即 exec"的黄金路径，可后续上 `posix_spawn` 快路径（04 §6.5 提及的 Spork/HotOS 2025 思路）绕开 CoW；性能边界待基准。
5. **鼓励迁移**：提供诊断——频繁使用 fork 的二进制记录遥测，引导生态转向 `meu_spawn`/`posix_spawn`。

### 3.3 D6 — uid/gid 纯合成视图、零权限；setuid = 受限 spawn + 显式 capability

**裁决立场**：
- **uid/gid 是纯合成视图，零权限附着**：`getuid()/geteuid()/getgid()` 返回每 Job/进程的合成 uid（默认 0 作"root 视图"），该视图**不解锁任何 capability**——即便"uid 0"也无法 open 未 unveil 的路径、无法 bind 无网络 capability 的端口。
- **起步单 uid 视图；扩展支持"声明式合成 uid 集合"**：Job manifest 可声明一组合成 uid/gid（纯标识/视图），供 su/daemon drop 类程序。跨 uid 访问（kill/ptrace/signal）**映射为 capability/Job 成员判定**，而非 uid 相等比较——"能否作用于 pid X"=“是否持有 X 所属 Job 的 exception/capability right”。
- **setuid/setgid 二进制 = 受限 spawn + 显式 capability，永不提权**：setuid 位在兼容层翻译为"spawn 子进程（不同合成 uid 视图）+ 包 manifest 显式授予的**具体** capability"；若 manifest 未授予该能力，则特权操作返回 `EACCES`/`EPERM`（对齐 07 §4.5 禁止 setuid 提权）。无"提权到特权再降回"的捷径。

**理由**：
1. "内部无 root"不是口号而是不变量（00-A1/A2）。把 uid 维持续为视图，等于从根上消灭"root 万能"与"CAP_SYS_ADMIN 新 root"（07 §3.1）。
2. 多系统参照一致：Container userns 是把容器 root 映射到宿主非特权 uid（有界）；Fuchsia 彻底无 uid（koid 标识）。MeuOS 取"更强版本"——连内部 uid 0 都无权。
3. setuid 映射为"受限 spawn + 显式能力"是 OpenBSD `execpromises` 思路与 Capsicum 受约束 fd 的同构，保证存量 setuid 程序**能按其真实需要运行，但绝不获得超出声明的能力**。

### 3.4 C6 — 接管边界 + i386 Rust TCB 范围

**裁决立场**：
- **接管边界 = 单一 `arch_boot → kernel_main()`**（采纳 09 §5.7 裁决 A）。runtime 就绪（core/alloc/panic_handler 链接）即 Rust 接管 capability 监视器、IPC 端点、调度/资源账本、syscall 路由、VFS 抽象——这些均入 TCB（对齐 02 §4.2）。此前仅 C/asm（极薄、固定、可审计）。无论何架构，Rust 接管**前**禁止任何依赖 `alloc`/`panic` 的 Rust 路径（硬约束）。
- **i386 的 Rust TCB 不降级为 C**：i386 缺裸机 target，但 TCB 组件以 rustc 产 `#![no_std]` + `extern "C"` 的 `.o`，由 C 链接器并入内核镜像（采纳 09 §5.7 裁决 B，双工具链已被 02 C1 接受）。**仅早期启动（Stage 0–2）/兼容层本就 C**——这部分在所有架构都是 C，与 i386 无关。
- **i386 不是"降级架构"**：它和 64 位在 TCB 安全上等价，差异只在构建管线（自定义 i386 target spec 或复用 `i686-unknown-linux-gnu` 产 `.o`）。接受 i386 为**一等架构**，Rust TCB 以链接 `.o` 交付。
- **C-links-Rust-`.o` 备选可行**：Rust 侧提供 `panic_handler`/`alloc_error_handler` 落地到内核统一故障入口；`extern "C"` 导出 `kernel_main` 与 TCB 组件入口；C 侧经 `bindgen`/`helpers` 调用（02 §4.3）。这是成熟模式（RFL abstractions、Redox/Hubris 均以 Rust 为主）；i386 缺的只是"裸机 target"便利性，不缺"编译 Rust 进内核"能力。
- **纯 C 退路（O3）仅作兜底**：若 `.o` 路径在 i386 实测不可行，则 i386 TCB 退化为 C，但**必须**施加补偿控制（见 §5），且制定"Rust target 成熟即迁移"计划。但**不预先认定 i386 为降级架构**。

| **路线图（00 §4.3）** | M0–M1 不依赖 fork（D2 分阶段）；M2 起启用全量 CoW；C4/C6 不再阻塞 M0–M2。 |

## 5. 风险与退路

### 5.1 C4 风险
- **风险 R1（包清单被滥用）**：恶意/疏漏的 manifest 声明过宽 broad-unveil。
  - **退路**：类上限闸封顶 + manifest 由系统侧审发（非用户运行期随意加）；放宽记入 Job 账本，可审计可撤销；提供"默认拒绝 + 仅白名单包可放宽"开关（系统级、非 per-process）。
- **风险 R2（兼容层成为新特权面）**：兼容层若私自发句柄即击穿。
  - **退路**：兼容层自身运行在受限句柄集下（07 §4.6）；所有 syscall 执行前过 capability 授权（08 §4.4）；兼容层排除出 TCB + fuzz/sandbox 补偿（02 §5-3）。

### 5.2 D2 风险
- **风险 R3（CoW 在大页/多核下的正确性）**：VMO child + 大页 + 多核写时复制需精确 refcount（04 §5-2）。
  - **退路**：先以 4K 页基元实现 CoW，大页作为后续优化；refcount 单一真相源在 MM（00-A7/C1）。
- **风险 R4（多线程 fork 误用）**：老程序多线程后 fork。
  - **退路**：明确 `EINVAL`/`ENOSYS` 拒绝，文档声明支持层级（08 §7）。

### 5.3 D6 风险
- **风险 R5（依赖真实 uid 相等的程序）**：少数程序用 `getuid()==0` 走特殊逻辑或做权限判断。
  - **退路**：合成 uid 视图默认 0 已覆盖大多数"我是 root 就放开"分支；对"uid 相等才授权"的程序，映射为 Job 成员判定（§3.3）。

### 5.4 C6 风险
- **风险 R6（i386 Rust `.o` 构建管线不可行）**：自定义 target spec / `i686-unknown-linux-gnu` 产 `.o` 与内核 C 链接的 ABI/panic 对接出问题。
  - **退路（O3）**：i386 TCB 退化为 C，施加补偿——(a) TCB 内 C 的 unsafe/特权路径极窄、双人评审；(b) 兼容层+TCB 边界 fuzz；(c) 关键不变量形式化/强类型审计；(d) 制定"Rust target 成熟即迁移 TCB"计划。**但仅作兜底，不预设**。
- **风险 R7（双工具链长期维护）**：Rust=LLVM / C=mcc 两工具链并行。
  - **退路**：02 C1 已判定近期可接受；远期跟踪 `rustc_codegen_gcc`/`gccrs`（02 §5-1）。

## 6. 残留需拍板项（交大喵/team-lead 最终定）

1. **【D1 类上限的"类别"划分】**：broad-unveil 的"包类别→可授权 capability 集合"上限表由谁定义、如何分级？（建议：安全模型 07 定 rights 位图后，由 08 出映射表，系统侧审发。）
2. **【D1 系统级白名单开关】**：是否允许"仅白名单包可放宽"的**系统级**（非 per-process）总开关？本裁决建议允许此系统级开关（它不击穿，只是收紧放宽入口），但**禁止 per-process 运行期关沙箱**。请确认。
3. **【D2 多线程 fork 的拒绝码】**：返回 `EINVAL` 还是 `ENOSYS`？前者更精确，后者更利于"显式不兼容"口径（08 §7）。请定。
4. **【D6 合成 uid 集合的声明位置】**：声明式 uid 集合写在 Job manifest 还是包 manifest？与 spawn 绑定来源（C3）如何协同？需 04/07/08 三方确认。
5. **【C6 i386 是否保留"纯 C 退路"为官方选项】**：本裁决主张 i386 以 Rust `.o` 交付、非降级架构；是否同意将 O3（纯 C 退路）仅留作应急、不写入正式支持矩阵？
6. **【C6 双工具链对自举的边界】**："自举"指用户态/工具链跑通（02 C1），内核是否允许 Rust 部分由 rustc 产出——请确认此口径不被未来"内核须 mcc 自举"诉求推翻。
