## 0. 范围与读法

本文聚焦 5 个系统的**机制级（mechanism-level）**事实，而非概述式对比。对每个系统挑 3–5 个对 MeuOS 真正有决策价值的机制，标注「决策价值」(为什么 MeuOS 该取/避/自研)。`01`–`12` 已就这 5 个系统做过引用，本文第 2 节逐条核对真伪并给出修正建议；第 3 节把被借鉴机制映射到 MeuOS 子领域与 `C1`–`C14`；第 4 节列明 MeuOS 不被任何参照系统直接覆盖的设计点；第 5 节列待决项。

## 1. 五个系统机制级精读

### 1.1 Linux（VFS / ext4 / btrfs / overlayfs）

**[决策价值定位]** Linux 是 MeuOS 的「被兼容对象」与「反面教材集合」：其 VFS/页缓存的对象统一能力值得学，但其命名空间碎片化、加密与 extent/快照割裂、FS 在内核态膨胀 TCB 是明确要避的。

1. **VFS 的对象统一抽象（inode / dentry / file / super_block / address_space）**
   - 机制：所有文件系统经同一组操作表（`file_operations` / `inode_operations` / `address_space_operations`）接入；`dentry` 缓存路径解析、`inode` 是统一元数据单元、`address_space` 是页缓存与文件的绑定层。VFS **在对象模型层**是真正统一的——任何 FS（含 procfs、sockfs、btrfs）都表现为同一套内核对象。
   - 决策价值：VFS 证明「用统一对象抽象收敛多种后端」是可行的（MeuOS 的 `ns-node` 继承了这一点）。但 VFS 的**统一止步于对象层**，不止步于命名空间层——见下条。

2. **命名空间与挂载（mount namespace）的碎片化本质**
   - 机制：`/proc`、`/sys`、`/dev`、`/`、`/tmp` 是各自独立伪/实文件系统挂载到全局树的不同点；「可见性」默认全局，靠 `mount namespace` 做 per-process 隔离（且是 opt-in）。这与「每进程显式 reveal」相反：`open` 失败于 `EACCES` 是因为「全局可见但权限被拒」，不是「根本不存在」。
   - 决策价值：这是 `06` 用「capability 组合树 + 默认全不可见 + 显式 reveal」取代的核心痛点。**取 Fuchsia/Plan 9 的「每进程命名空间」思想，避 Linux 的「全局树 + 多伪 FS 拼凑」**。

3. **ext4：extent + 元数据校验和（默认开启）+ 无数据校验和**
   - 机制：extent 组织（替代 block map）；`metadata_csum`（crc32c）自 e2fsprogs 1.43 起**新建文件系统默认开启**；**数据层无校验和**；无透明压缩、无原生加密（fscrypt 在 VFS 之上、keyring + DAC 耦合）。
   - 决策价值：**避**——ext4 印证「元数据校验和 ≠ 数据完整性」。MeuOS 把校验和下沉到 **extent 层、覆盖密文**（见 `06` §4.2），恰好补齐 ext4 的数据层缺口。

4. **btrfs：extent 级校验和 + 透明压缩 + CoW 子卷快照**
   - 机制：每 extent 存校验和（默认 crc32c，可选 xxhash/blake2），**覆盖数据与元数据**；透明压缩 zstd/lzo/zlib（per-extent）；CoW 使子卷快照为 O(1) 元数据操作、共享未改 extent；加密仍依赖 dm-crypt（整盘）或 fscrypt（per-file），**未与 extent/快照深度联动**。
   - 决策价值：**取**——btrfs 是 `06`「extent 校验和 / 压缩 / 快照」的直接范本（决策价值最高的一组机制）。**避**其「加密与 extent 割裂」。

5. **overlayfs：lower/upper 叠加，非真 CoW**
   - 机制：只读 lower + 可写 upper，写时 copy-up；回滚=丢 upper；多 lower 查找开销、元数据操作复杂。容器镜像与「类原子更新」常用，但它是叠加层而非真 CoW 快照。
   - 决策价值：**避**作主路径；仅作「A/B 兜底」思想来源之一（与 ChromeOS A/B 并列）。

### 1.2 Apple APFS（写时复制 / 克隆 / 快照 / per-file 密钥层次 / Space Manager）

**[决策价值定位]** APFS 是 MeuOS 方向①「原子 `.msys` 更新 + per-file 加密」最接近的**正面范本**，但三点必须清醒：无数据校验和、加密体系与 capability 不挂钩、快照回退是破坏式的。

1. **CoW 克隆与快照（extent 共享 + 引用计数）**
   - 机制：`clonefile` 是 O(1) 元数据操作，父子共享 extent，写时复制；快照是只读卷，与活动 FS 共享 extent（空间高效），靠引用计数管理生命周期；崩溃一致性靠 CoW + 事务。
   - 决策价值：**取**——`06` §4.3「子树级 CoW 快照 + 原子 repoint」直接借 APFS 的克隆/快照机制。

2. **per-file 密钥层次（key hierarchy）**
   - 机制：每个文件有 file key，由卷密钥/用户密钥派生的 KEK（key-encryption-key，存于容器 keybag）包装；多密钥体系（无加密/单密钥/多密钥）。
   - 决策价值：**取**层次结构，**改挂**——APFS 的密钥体系是证书/keybag（非 capability）；MeuOS 把「密钥 unwrap 权 = 文件句柄 right」与 capability revoke 联动（`06` §4.2.3，方向①③互锁最高价值点）。

3. **Space Manager（空间管理器，分配位图）**
   - 机制：APFS 用 container → volume 结构 + space manager 以分配位图管理空闲空间（对比 ext4 block bitmap、btrfs chunk tree）。
   - 决策价值：**自研参考**——MeuOS extent 分配层可借鉴分配位图的简洁性；但归于 `06` 自主实现的存储后端，不照搬 APFS 容器模型。

4. **无数据校验和（已知点）**
   - 机制：APFS 对元数据有校验，但**不对文件数据内容做校验和**（业界长期批评点）。
   - 决策价值：**避**——这正是 MeuOS 把 extent 级校验和「覆盖密文」作为差异化价值的原因（见 `06` §4.2）。`06` 现表「APFS 校验和：弱（依赖硬件）」结论正确，但「依赖硬件」措辞偏模糊，建议改为「无数据校验和」更精准。

5. **快照回退是破坏式**
   - 机制：macOS 的 APFS「恢复到快照」会删除该快照之后的所有写入（不可恢复式回退），并非「老进程继续持有老视图、新进程切新视图」。
   - 决策价值：点出 MeuOS 与 APFS 的根本差别——MeuOS 的命名空间原子 repoint 因 capability 是**非破坏式**的（旧持有者续持旧能力，见 §4 自研点 3）。**此差异必须在 `06` 中显式强调，避免被误读为「照搬 APFS revert」**。

### 1.3 NTFS（日志 / 对象命名空间 / MFT / USN 日志 / EFS / 重解析点）

**[决策价值定位]** NT 的**对象命名空间**是「统一寻址一切资源」思想的鼻祖之一；NTFS 的 MFT 把一切存为统一记录。但权限模型是 DAC/ACL（非 capability）、FS 与对象管理均在内核态（TCB 大），这两点与 MeuOS 冲突。

1. **对象管理器与对象命名空间（Object Manager）**
   - 机制：NT 内核用对象管理器统一管理一切内核对象（文件、设备、进程、端口…），经 `\` 开头的命名空间（`\Device`、`\FileSystem`、`\KernelObjects`、`\Global??`）以路径寻址。这是「统一资源命名空间」思想的最早工程范例之一。
   - 决策价值：**取思想骨架**（路径即对象引用），**避实现**（DAC + 留核）。`06` §3.2 此点引用准确。

2. **MFT（主文件表）：一切皆 1KB 固定记录**
   - 机制：每个文件/目录是 MFT 中的一条记录，含元数据 + 数据运行（data runs，即 extent）。MFT 把文件元数据、目录、甚至元数据文件本身统一为同构记录。
   - 决策价值：**取**「统一节点模型」灵感（呼应 `06` 的 `ns-node`）；但 MeuOS 的节点是 capability-backed、类型标签化，与 MFT 的单一物理表不同。

3. **EFS（Encrypting File System）：per-file 加密 + 证书包装**
   - 机制：文件密钥由用户公钥证书包装（DDF/DRF 存于文件）；per-file 对称加密。
   - 决策价值：**取** per-file 加密思想，**避**其证书/用户体系（非 capability）。与 APFS 同属「per-file 但非 cap 绑定」一类。

4. **USN 日志（Update Sequence Number Journal）**
   - 机制：卷级变更日志，记录文件/目录的创建、改名、删改等事件，供备份/索引/同步增量消费。
   - 决策价值：**未被 `01`–`12` 引用，是遗漏的借鉴点**——USN 的「细粒度变更流」可直接喂给 `12` 的可观测性事件流（Event Stream）与审计，比轮询 `/proc` 干净。建议纳入 `12` 的参照清单（见 §5 待决项）。

5. **原生透明压缩（LZNT1）+ 重解析点**
   - 机制：NTFS 自 NT 3.51 起支持**per-file/dir 的原生透明压缩**（LZNT1 算法）；重解析点（reparse point）实现符号链接/挂载点/卷挂载（类似 mount-capability）。
   - 决策价值：**取**重解析点 ≈ mount-capability 委托思想；**纠偏**：`06` §3.2 称 NTFS「无原生透明压缩」是**事实错误**（见 §2 失真 1），真实情况是 NTFS 有压缩、缺的是**数据校验和**（该能力在 ReFS 的 integrity streams，非 NTFS）。

### 1.4 Google Zircon / Fuchsia（微内核 · 精简 syscall · Capability 化 · namespace · blobfs/minfs · inspect）

**[决策价值定位]** 这是 MeuOS 整体最贴近的参照（尤其 `03/04/05/06/07/12`）。其与 MeuOS 的唯一系统性偏差：Fuchsia 是**全微内核**（驱动/FS 全用户态、每 syscall 经 IPC），MeuOS 是 lean hybrid（保留内核态 mkit 薄层）。其余思想高度同构。

1. **句柄即能力（handle + rights）与每进程命名空间**
   - 机制：用户态几乎只经 handle 访问内核对象；每个 handle 带 rights 位图（Zircon 实际约 13 个基础 right：DUPLICATE/TRANSFER/READ/WRITE/EXECUTE/MAP/GET_PROPERTY/SET_PROPERTY/ENUMERATE/DESTROY/SIGNAL/WAIT/INSPECT…）；进程在 spawn 时由组件框架组装一组 `path → 目录能力` 绑定，**无全局 `/proc`**。
   - 决策价值：**取**——`07` 句柄即能力、`06` 每进程命名空间直接借此。注意 Fuchsia 命名空间由**组件框架**组装，MeuOS 改为由 **FS 服务做根聚合 + mount-capability 委托**（语义等价、归属更清晰，`06` §4.1 已自陈此差异）。

2. **VMO / VMAR：CoW child + 层级权限**
   - 机制：`zx_vmo_create_child` 的 `SNAPSHOT` / `COPY_ON_WRITE` 以 VMO 克隆表达 COW/快照（惰性复制）；VMAR 具层级权限模型（父 RWX、子可收紧为仅 RW，禁止后续创建可执行映射）。
   - 决策价值：**取**——`03` §4.4 VMO/VMAR 直接借 Zircon；CoW 即原语、VMAR 层级权限天然契合 capability 沙箱（阻止 JIT 注入）。

3. **pager 模型（用户态 FS + 内核零拷贝 mmap）**
   - 机制：FS 服务把文件以 VMO 交给客户端，内核缺页时经 pager 通道向 FS 服务请求页面；数据通路在内核、逻辑在用户态。
   - 决策价值：**取**——`06` §4.4.1 的 VMO+pager 零拷贝 mmap 直接借 Fuchsia；这是 lean hybrid 在文件系统上的精确体现（FS 逻辑出核、数据通路留核）。

4. **blobfs（内容寻址，hash=完整性）+ minfs**
   - 机制：blobfs 以 hash 为名的不可变 blob 存储，hash 即完整性、天然防篡改；minfs 为可读写小 FS。
   - 决策价值：**取**——`06` §4.5「内容寻址可选（blobfs 思想）」用于不可变 `.msys` 组件去重；但 blobfs 只读、不能直接当可读写 sysroot，故 MeuOS 用「CoW 子卷」而非 blobfs 承载可写 sysroot（差异化）。

5. **inspect 树（层次化强类型可观测性）与 debug 经 capability**
   - 机制：内核/服务状态以层次化强类型 inspect 树暴露（节点属性为 int/string/bytes/histogram/lazy，经 VMO 发布）；调试协议走 channel/capability，debug handle 显式授予。
   - 决策价值：**取**——`12` §4.4 inspect 树 + 调试即 capability 的主参考。`12` 把 `DBG_*` right 细分为 5 类（INSPECT/TRACE/PROFILE/ATTACH/CRASHDUMP），是比 Fuchsia 单 debug handle 更细的自主 refinement（见 §4 自研点 6）。

6. **Zircon 的「无 derivation tree / 无 revoke 传播」**
   - 机制：Zircon 的 rights 是**静态位图**，handle 一旦 duplicate 即独立，**没有 seL4 式的 capability 派生树与递归 revoke 传播**。
   - 决策价值：**关键澄清**——`07` §4.5 想引入「derivation tree（借鉴 seL4）」做 revoke 传播，这是 **MeuOS 自研**，不是 Zircon 有的。Zircon 只提供「rights 可收窄于 duplicate」这一静态能力。`06/07` 在引用 Zircon 时不应暗示其有派生树（见 §2 失真 4）。

### 1.5 seL4（Untyped / Retype 物理内存模型 · Capability Derivation Tree · revoke 语义 · 形式化验证）

**[决策价值定位]** seL4 是 MeuOS「最小 TCB + capability 内核 + 形式化验证心态」的源头。但 MeuOS 在 C1（物理内存归属）上**明确拒绝了纯 seL4 方案**（见 `13` 裁决=折中 C），仅精准吸收其 device-untyped 子思想。

1. **Untyped 内存模型 + Retype + 水位线分配**
   - 机制：所有可用物理内存以 untyped capability 交给 root task；内核**不在运行期动态分配**；`Untyped_Retype` 把一段 untyped 切出子 untyped 或定型为内核对象（frame/CNode/TCB/Endpoint…）；分配从大到小（watermark）以避免对齐碎片。
   - 决策价值：**避整体、取思想**——纯 seL4（物理内存交用户态）破坏 `04` Job 配额单一真相源、`07` revoke 真回收、`01` lean hybrid 热路径免 IPC 三条硬约束（`13` §3.1 已论证）。但「物理页单一真相源 + 分配点即配额强制点」的推演精神被 `13` 折中 C 吸收。

2. **Device Untyped（isDevice，不可写、只能 retype 为 frame）**
   - 机制：`isDevice` 为真的 untyped，内核不可写，只能 retype 为可映射 frame——严格隔离设备内存。
   - 决策价值：**取**——`03`/`10`/`13` 把 device 内存建模为「不可写的 device VMO」，是 MeuOS 从 seL4 精准吸收的子思想（不引入纯 seL4 整体代价）。这是 `C1=折中 C` 的标志性吸收点。

3. **Capability Derivation Tree（CDT）+ Revoke 递归回收**
   - 机制：每次 Copy/Mint/derive 生成 CDT 节点；`CNode_Revoke` 遍历该节点的全部派生能力并删除（含通知），实现「撤销一个能力即回收其整个派生链」。
   - 决策价值：**取语义、自研落地**——`07` §4.5 想用 derivation tree 支持 revoke 传播到 `06` 的「句柄→密钥 unwrap 权」链与 `03` 的 VMO 派生链。这是 MeuOS 把 seL4 的 revoke 哲学落到 capability 世界的**自研衔接点**（Zircon 无此）。

4. **CSpace（CNode 基数树能力存储）**
   - 机制：能力存于 CNode（槽位数组构成的基数树），以 CPtr + guard 寻址；复制/删除/授予是对 CNode 槽位的显式操作。
   - 决策价值：**避**——MeuOS 选 Zircon 式「进程私有 handle 表 + IPC 携带」（`07` §5.1），**未**采用 seL4 的全局可寻址 CSpace（实现复杂）。`07` §4.1 把 adopted 模型称「CSpace（借鉴 seL4）」是**用词不一致**（见 §2 失真 4）。

5. **IPC fastpath（rendezvous + 寄存器直传 + 无 cap 转移时免拷贝）**
   - 机制：`seL4_Call`/`ReplyRecv` 在「无能力转移、无更高优先级线程、小消息」时走 fastpath，消息入寄存器、免内核拷贝。badge 多路复用 + reply capability。
   - 决策价值：**取**——`05` §3.1 直接借 seL4 的 rendezvous + badge + reply capability + fastpath 思想；与 Zircon datagram 消息融合为 MeuOS 的 Channel（`05` §4.1）。

6. **形式化验证（端到端证明功能正确性 + 信息流安全）**
   - 机制：从抽象规约一路证明到 C 实现（原始被证内核约 8,700 行 C；现代 ARMv8/HYP 验证版更大）。验证覆盖功能正确性与隔离/信息流。
   - 决策价值：**取心态、不取全量**——MeuOS 用 Rust 换「证明前先少错」（`01` §2.2、`02` §4.7），对 capability 监视器/IPC 等 TCB 关键组件做半形式化/不变量形式化，而非端到端证明（见 `01` §5-4、`02` §5-4）。`07`/`12` 的「证明与调试分离」立场直接借 seL4。

## 2. 对 01–12 引用失真纠偏清单

> 下列为核对 `01`–`12` 对第 1 节 5 个系统机制的引用后，发现的**失真/不精准**项。格式：原文档说法 → 真实机制 → 建议修正。均只记录于此，不改原文档。

### 失真 1（最高优先级）：NTFS「无原生透明压缩」事实错误
- **原文档说法**：`06` §3.2「NTFS：日志型、支持文件级加密（EFS…）、ACL、USN 日志、重解析点，但**无原生透明压缩/校验和的强一致保证**」。
- **真实机制**：NTFS 自 NT 3.51 起即支持 **per-file/directory 的原生透明压缩（LZNT1）**；其真正缺项是**数据校验和**（data checksum）——该能力在 ReFS 的 integrity streams（CoW + 校验和），不在 NTFS。NTFS 的「强一致保证」短板是**无数据校验和**，而非无压缩。
- **建议修正**：将「无原生透明压缩」改为「**有原生透明压缩（LZNT1, per-file），但无数据校验和（数据完整性在 ReFS）**」。此失真会削弱 `06` 对 NT 的准确取舍判断（NT 的压缩能力其实可借鉴，`06` §4.2 的「压缩在 extent 层」与 NT 压缩思想一致）。

### 失真 2（高优先级）：ext4 校验和「默认无 / 可选」表述误导
- **原文档说法**：`06` §3.1「ext4：…**默认无校验和（仅元数据 checksum 可选）**、无透明加密、无原生压缩」。
- **真实机制**：ext4 的 `metadata_csum`（crc32c）自 e2fsprogs 1.43（2016）起**新建文件系统默认开启**，并非「可选」；ext4 的真实缺口是**数据层无校验和**（非「整个无校验和」）。
- **建议修正**：改为「ext4 元数据校验和（crc32c）默认开启，但**数据层无校验和**；无透明压缩、无原生加密（fscrypt 在 VFS 之上）」。这能让 `06` 与 btrfs 的对比更精准：btrfs 强在「**数据** extent 校验和 + 压缩 + 快照」，ext4 弱在「数据无校验和」。

### 失真 3（中优先级）：VFS「统一只到文件系统类型层」表征偏差
- **原文档说法**：`06` §3.1「VFS（虚拟文件系统）：用 inode/dentry/file/super_block 抽象统一不同底层 FS；但**『统一』只到『文件系统类型』层**——/proc、/sys、/dev 是各自独立的伪文件系统挂到全局树的不同挂载点」。
- **真实机制**：VFS **在对象模型层是真正统一的**——procfs、sysfs、devtmpfs、btrfs 都表现为同一套 inode/dentry/file 内核对象，统一由 VFS 操作表驱动。真正的「碎片化」发生在**命名空间/挂载层**（多个独立 FS 挂到全局树不同点、各自语义独立、可见性默认全局），而非 VFS 对象抽象失败。
- **建议修正**：将「统一只到文件系统类型层」改为「**对象模型层统一（一切皆 inode），但命名空间/挂载层碎片化（多伪 FS 拼全局树、可见性默认全局）**」。`06` 的结论（capability 组合命名空间优于 VFS）仍成立，但理由应落在「命名空间层」而非「对象层」，避免低估 VFS。

### 失真 4（中优先级）：Zircon 被暗示「有派生树/revoke 传播」+ seL4 CSpace 用词混称
- **原文档说法**：`07` §4.1「能力空间（CSpace，借鉴 seL4）：进程持有 handle 表；句柄的复制、授予、回收都是显式…」；`07` §4.5「句柄复制…派生关系可记录为 derivation tree（借鉴 seL4）」；`05`/`03` 多处把 adopted handle 模型称为参考 seL4/Zircon 并列。
- **真实机制**：
  - 实际采纳的模型（见 `07` §5.1）是 **Zircon 式进程私有 handle 表 + IPC 携带**，**不是** seL4 的全局可寻址 CSpace（CNode 基数树）。`07` §4.1 把 adopted 模型标「CSpace（借鉴 seL4）」与 §5.1 的「Zircon 风格」自相矛盾。
  - Zircon **没有** capability 派生树 / 递归 revoke 传播（`07` §3.2 自身也写「rights 是静态位图，动态派生/回收语义较简单」）。derivation tree + revoke 传播是 **seL4 独有**，`07` §4.5 想引入它是 **MeuOS 自研**，不能归到 Zircon。
- **建议修正**：
  - `07` §4.1 把「CSpace（借鉴 seL4）」改为「**进程私有 handle 表（Zircon 风格，可演进为全局 CSpace）**」，与 §5.1 对齐。
  - 在 `07` §4.5 明示「derivation tree 来自 seL4，是 MeuOS 在 Zircon handle 模型之上的**自研增强**（Zircon 本身无派生树）」。

### 失真 5（低优先级）：APFS 快照「回退」语义被静默假设为非破坏式
- **原文档说法**：`06` §4.3 把「APFS 快照 + repoint」作为原子 sysroot 更新的范本，未点明回退语义。
- **真实机制**：macOS 的 APFS「恢复到快照」是**破坏式**——删除快照之后的所有写入；且需重启/离线操作。MeuOS 的命名空间原子 repoint 因 capability 是**非破坏式**（旧持有者续持旧能力、新进程切新视图、无需重启）。
- **建议修正**：在 `06` §4.3 增加一句「与 APFS 破坏式 revert 不同，MeuOS 的 repoint 因 capability 是非破坏式、支持 per-process 灰度（见 §4 自研点 3）」，避免被误读为照搬 APFS。

### 失真 6（低优先级）：seL4「8700 行 C」与 Zircon「~10 right」的数字口径
- **原文档说法**：`07` §3.2「形式化验证（8700 行 C）」；`07` §3.2/§5.2「~10 个基础 right 起步」。
- **真实机制**：原始被证 seL4 内核约 8,700 行（Klein et al. 2009）；现代验证版（ARMv8/HYP）更大。Zircon 实际基础 right 约 **13** 个（含 INSPECT/MANAGE 类）。二者均属**近似可接受**，但建议在 `07` 补注「现代验证版内核规模更大」「Zircon 实际 ~13 right，MeuOS 原型取 ~10–13 子集」。

### 失真 7（低优先级）：Fuchsia namespace「由 FS 服务组装」的归属
- **原文档说法**：`06` §4.1「FS 服务是命名空间的『根聚合者』…`/dev`/`/proc`/`/net` 由对应服务经 mount-capability 委托」。
- **真实机制**：Fuchsia 的每进程命名空间由**组件框架（component framework / appmgr）**组装，并非由 FS 服务自身做根聚合。`06` §4.1 已自陈「比 Fuchsia 多了 FS 服务做根聚合者」的差异，但 §3.6 对比表中未显式点出「Fuchsia 由组件框架而非 FS 服务组装命名空间」。
- **建议修正**：在 `06` §3.6 / §5 对比表补注「Fuchsia 命名空间由组件框架组装；MeuOS 改为 FS 服务做根聚合 + mount-capability 委托（语义等价、归属更清晰）」，使差异外显、避免读者误以为 Fuchsia 也由 FS 服务聚合。

> **Top 3 失真小结（供 team-lead 关注）**：① NTFS 透明压缩事实错误（失真 1）；② ext4 校验和「默认无/可选」误导（失真 2）；③ VFS「统一只到文件系统类型层」表征偏差（失真 3）。三者均影响 `06` 对参照系统的取舍判断准确性，建议后续轮次回写 `06`。

## 4. MeuOS 自主研究点（不被任何参照系统直接覆盖）

> 以下设计点**不能**由 Linux/APFS/NTFS/Zircon/seL4 任一系统直接覆盖，是 MeuOS 必须在执行层自主研究的硬骨头。

1. **统一资源命名空间 = capability 组合树 + 每进程 spawn 组装 + FS 服务做根聚合 + mount-capability 委托子树**
   - 参照覆盖度：Fuchsia 有每进程命名空间但由组件框架组装；NT 有对象命名空间但 DAC+留核；Plan 9 有 rfork 命名空间但无 capability；scoped storage 有可见性=权限但无内核 capability 模型。
   - 自主点：把「FS 服务作为根聚合者、各子树经 mount-capability 显式委托」这一**归属分工**是 MeuOS 独有（既非组件框架、也非内核对象管理器），且把命名空间与 capability 派生树绑定。

2. **密钥 unwrap 权 = 文件句柄 right（密钥即 capability）**
   - 参照覆盖度：btrfs/APFS/fscrypt/EFS 都做 per-file 加密，但密钥访问都挂在 keyring/证书/DAC 上，**无一**把「解密权」绑定到 capability 句柄的 right 并随 revoke 传播回收。
   - 自主点：密钥访问权生命周期 = 文件句柄 capability 生命周期，无需独立 KRL；与 `06`/`07` 互锁，是方向①③最高价值互锁点（对应 C2）。

3. **子树级 CoW 快照 + 命名空间原子 repoint + per-process 灰度切割（非破坏式）**
   - 参照覆盖度：APFS 快照+repoint 是内核级且**破坏式 revert**；ChromeOS A/B 是**分区级、需重启、2× 空间**；overlayfs 回滚=丢 upper。
   - 自主点：因 capability 命名空间，repoint 是**非破坏式**——旧进程续持旧 sysroot 能力、新进程按 supervisor 决策灰度切新 sysroot，把「原子更新」从引导加载器的事变成「资源命名空间能力」的事，并支持 per-process 灰度（连 APFS 都做不到）。

4. **lean hybrid = 微内核基因 + 内核态 mkit 薄层唯一让步**
   - 参照覆盖度：纯微内核（seL4/Fuchsia）每 syscall IPC；NT/XNU 混合是「重服务留核」。二者都无「内核态兼容转译薄层」这一折中。
   - 自主点：相对经典微内核的唯一务实让步=内核态 mkit 薄层，既吸收宏内核 syscall 零往返、又保持 FS/网络/驱动出核。这是 MeuOS 内核形态定义性创新（对应 `01` §4.1）。

5. **Job 资源账本 Day 1 内建 + 与 capability 同源单账本**
   - 参照覆盖度：Zircon job 有资源限额但 capability 集与配额是分别概念；cgroups 是事后挂接；NT 无 job 概念。
   - 自主点：把 Job 配额 + capability 边界 + 句柄表**三者同源挂在 Job 上 Day 1**，统一可审计、不可「先越权再关笼」（对应 `04` §4.4、回扣 C3/C4）。

6. **debug capability 五向细分（DBG_*）+ 监督者优先 / 调试器非阻塞仲裁**
   - 参照覆盖度：Fuchsia 有单一 debug handle；Linux 默认同 uid 可 ptrace、perf 全局。
   - 自主点：把调试权细分为 INSPECT/TRACE/PROFILE/ATTACH/CRASHDUMP，且监督者持 `DBG_CRASHDUMP` 默认订阅、交互式调试器持 `DBG_ATTACH` 且不能阻断监督者崩溃处理（对应 C9、C10）。

7. **VMO child（用户态可见 COW）↔ 内核页表 COW 双轨 + refcount 单一真相源**
   - 参照覆盖度：Zircon 用 VMO child、Linux 用页表写保护，二者机制不同、各自单一。
   - 自主点：MeuOS 用户态 clone 用 VMO child、内核内部用页表 COW，需桥接二者保持 **refcount 单一真相源、避免双计数**（`03` §5-2、C1 关联）。这是执行层必须自主攻关的点。

8. **device VMO = seL4 device-untyped「不可写」思想，但吸收进 VMO capability 视图（非整体 untyped 模型）**
   - 参照覆盖度：seL4 整体 untyped 被 `13` 否决（C1=折中 C）。
   - 自主点：仅取 device-untyped 的「不可写、只能 retype 为可映射 frame」子思想，落地为 device VMO 的固有 right，不引入纯 seL4 整体代价（对应 C1/C8）。

9. **pledge/unveil fail-closed + 越界即终止 + 与 capability 句柄 rights 同构 Day 1**
   - 参照覆盖度：OpenBSD pledge/unveil 是进程沙箱 add-on；MeuOS 把它与 capability handle rights 融为**同一模型 Day 1**（非事后叠加）。
   - 自主点：unveil = 向命名空间注入路径 capability 绑定、pledge 的 rpath/wpath/cpath 约束能否新增绑定，与句柄 rights 同构（对应 `07` §4.3、C3/C4）。

## 6. 一句话结论（草案收口）

MeuOS 的参照策略是**精准取形、拒绝取实**：取 btrfs 的 extent 校验和/压缩/快照、APFS 的克隆/密钥层次、Zircon 的句柄/VMO/pager/inspect、seL4 的 device-untyped/derivation-tree/fastpath/验证心态、NT 的对象命名空间；明确避 Linux 命名空间碎片化、APFS 破坏式 revert 与无数据校验和、seL4 整体 untyped 与 CSpace、Zircon 无 revoke 传播。其真正自主的部分——**密钥即 capability、非破坏式命名空间 repoint、lean hybrid 内核态 mkit 薄层、Job/capability 同源单账本**——是把多个参照系统的「思想碎片」缝合成一个 capability 内核独有形态的关键，且**不被任何单一参照系统直接覆盖**。
