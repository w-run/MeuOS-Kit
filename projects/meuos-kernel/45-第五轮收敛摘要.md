## 2. 第五轮 6 新维度（39–44）一句话汇总

- **39-内核可观测性与追踪**：在内核最小可观测面上统一结构化事件 + 受限 tracing capability，复用 kqueue/EventPort 就绪 + 结构化日志；调试权仍走 `DBG_*`（默认 deny），tracing 不另开特权面、不污染 capability 模型。
- **40-电源管理与能耗**：能耗弱耦合于 Job 账本（第四轮「能耗-Job」已采纳）；仅作用户态 `powerd` 的 task-packing 调度输入，休眠/电源状态经受限设备能力表达，强耦合待 EAS 议题裁决。
- **41-测试与验证方法论**：定义单元 / 集成 / 形式化 / 自举验证四层门禁，以 `mcc + meuos-libc` 在自研内核自举为最高验证基线，统一回归与「可验证性」证据链。
- **42-虚拟化与沙箱隔离**：澄清 V1「不提供 KVM ABI」但**允许用户态 hypervisor**；VM = 用户态 VMM + 薄内核 `guest`/`vcpu` 一等对象；提出 `GUEST_CREATE`/`VM_MANAGE` right（本轮暴露缺口，见 §3 定 bit 46/47）。
- **43-实时性与确定性调度**：RT 域（固定优先级 + deadline 子类）对公平层绝对压制；`CAP_RT` 守护 RT 提权（本轮暴露「R1 落地到 07 的悬空项」，见 §3 定 bit 45）；与 R1 确定性承诺对齐。
- **44-形式化验证与安全论证**：定义可验证小核心（调度核心 / capability 撤销 / revoke 传播）形式化目标，与 `20` 协同；为 rights 位图等「亚稳契约」提供证明锚点。

## 3. ⚠️ 统一 right bit 分配建议表（第五轮修订版）

> **背景冲突（必须解决）**：通读第五轮回写，发现 `bit 39` 被三处同时占用：
> 1. `07` §第五轮裁决回写（C17，line 402）/ `00` §C17（line 140）：`NET_MANAGE` = **bit 39**
> 2. `32` §第五轮裁决回写（D-SB7，line 317/361/365）/ `00` §待升级候选区（line 343）：预留 `ATTEST` = **bit 39**
> 3. `34` §8（line 361–364）：`SURFACE_SUBMIT`=**bit 39**、`SURFACE_MANAGE`=40、`DISPLAY_MODESET`=41、`DISPLAY_LEASE`=42（34 自称 39–42，但 39 已被 `NET_MANAGE`/`ATTEST` 占用）

> 此外 `43` 指出 `CAP_RT` 未进位图（建议 39+）、`42` 提出 `GUEST_CREATE`/`VM_MANAGE`（建议 39/40）、`38` §3 预留 39+ 为 `MEDIA_CAPTURE` 等。

> 本表在 **38 §3 的 bit 0–38（冻结）基础上重排 bit 39+**，消除所有重叠。编排原则与 38 §3.2 裁定一致：**各域新增专属 bit、不复用 `MANAGE`/`GRANT`/`REVOKE`/`DUPLICATE`**，按领域自低向高顺延。

### 3.2 冲突解决小结

- **原 bit 39 三占冲突已消除**：`NET_MANAGE`(C17) 维持 **bit 39**（`07`/`00` 原报即 39，无需移动，恰好作为 bit 39+ 起点）；`ATTEST`(32 D-SB7) 自 39 → **bit 40**；`SURFACE_SUBMIT`(34) 自 39 → **bit 41**、`SURFACE_MANAGE` 自 40 → **42**、`DISPLAY_MODESET` 自 41 → **43**、`DISPLAY_LEASE` 自 42 → **44**。
- **本轮新暴露缺口补位**：`CAP_RT`(43 悬空项) → **bit 45**；`GUEST_CREATE`/`VM_MANAGE`(42 建议) → **bit 46 / 47**。
- **预留区顺延**：38 原「bit 39+ 预留给 MEDIA_CAPTURE 等」顺延为 **bit 48+**。
- **编排一致性**：所有 bit 39–47 均为领域专属 bit（网络管理/远程证明/图形 surface·display/实时/虚拟化），不复用通用 `MANAGE`/`GRANT`，与 38 §3.2 裁定及已采纳的 `KEY_*`/`CFG_*`/`DBG_*`/`BLOCK_*`/`AUDIO_*`/`NET_*` 先例完全一致。
- **标注**：上述 bit 39–47 为「**建议，待回写 07 冻结**」。34 §8 的「bit 39–42」自报值、32 D-SB7 的「bit 39」自报值、43 的「建议 39+」均以本表 39–47 为准。

## 5. 残留最高优先待大喵拍板项

> 区别于第五轮**已自主采纳**的查缺补漏项（C17/33-D1/34-D-G1/G2/37-待决1–3/32-D-SB1/SB7/SB8/公钥根介质/IDL 唯一出口），以下为真正仍需人拍板的最高优先项：

1. **静态 TCB 议题（原 38 的 C17）是否采纳**——是否锁死静态 TCB、彻底否决 LKM/livepatch，仅 A/B 整镜像兜底（`36` §6.3 建议追加候选）。这是关乎最小 TCB 与未来可验证性根基的架构级取舍，**未在本轮采纳**，需大喵拍板（并先解决与网络面 C17 的编号撞车，见 §4）。
2. **bit 39+ 重排表的最终冻结**——45 §3 的 39–47 编排是否为大喵认可的最终方案，还是另有偏好（如 `CAP_RT`/`GUEST_CREATE` 顺序）。此表为后续 `07`/`38` 回写冻结的权威来源，**最高优先**。
