## 0. 一句话核心结论

> **MeuOS 的内核自举应被设计成「一条由固件锁定的公钥根逐跳验签、以统一 `.mimg` 单映像格式（内核 + bootinfo + 可选 initramfs 指针 + 签名/Merkle 元数据）承载、在进入架构无关的 `kernel_main` 前完成最小必要页表/内存与度量累积、进入后立刻把 FS/驱动/监督交权用户态」的最短信任链——五架构的入口差异被收敛进极薄的 `arch/<arch>/boot` 垫片，`.msys` 原子加载复用同一条度量与能力链，Day1 最小集只保「能 spawn 一个受能力约束的 root-job 监督者 + 挂载 `.msys` 根」这一扇门。**

## 1. 解构：从固件交权到内核主线的「最短信任链应该是什么样」

> 大喵铁律第一条：先问「应该是什么样」，再决定怎么落地。本节从第一性原理推演**自举路径上信任链的最小化**，而非复述任一系统的启动流。`09` §3.1 已给出「复位向量→capability 世界就绪」的功能最短链；本节在其上叠加**信任视角的最短链**——即「每一跳的信任从哪来、能否再砍掉一跳」。

### 1.1 问题重述：信任链最小化的三重目标

自举路径上同时压着三条不可调和的成本曲线：

| 目标 | 含义 | 砍错一跳的代价 |
|------|------|----------------|
| **最短可验证** | 从复位到 `kernel_main` 的控制转移步数最少、每步可审计（`09` B1/B2） | 步数多 → TCB 大、审计面大、故障爆炸半径大 |
| **最短信任** | 信任的「源头」尽可能上锁到硬件，中途不引入新的、未被前一跳验证的验签者 | 多一个「未经验证的验签者」= 多一个可被替换的信任锚 |
| **最短交权** | 内核态做完「能 spawn 受约束用户态」即止，余下交权（`09` §3.2） | 留核越多 → 运行期攻击面越大、与方向①③冲突 |

这三条曲线的交汇点正是 `09` 已经点出的 `arch_boot→kernel_main` 单一交接边界——但 `09` 没回答：**这条链上「谁在什么时候相信了谁」能被压到多短**。本节给出答案。

### 1.2 信任链最小化的第一性原理推导

把「信任」还原为最小必要跳，每一跳必须回答「下一跳凭什么被信」且「信任的源头是否已被上一跳锁死」：

```
[硬件只读锚]  ──锁死「公钥根哈希」(档 A) 或「运营公钥」(档 B/C)──▶
  └─ 固件/引导器    验签 bootloader / 直接验签内核映像（.mimg）
        │  度量 extend：PCR[0] = hash(firmware→loader)
        ▼
  └─ 内核映像 (.mimg) 整体验签 + 度量   ← 跳 1：32 §3.1 跳 1
        │  PCR[1] = extend(hash(.mimg))
        ▼
  └─ arch/<arch>/boot 极薄垫片：建栈/页表/MMU on（仅 C/asm，02）
        │  （此层不引入新验签者——它只是把已被验签的映像「跑起来」）
        ▼
  └─ kernel_main (Rust) → monitor 自度量   ← 跳 2：32 §3.1 跳 2 / PCR[2]
        │  PCR[2] = extend(hash(monitor) || hash(init caps))
        ▼
  └─ .msys rootfs 挂载（FS 服务验签 + Merkle 度量）  ← 跳 3：32 §3.1 跳 3
        │  PCR[3] = extend(hash(.msys volume root))
        ▼
  └─ 用户态服务（meu-supervisor / FS / devmgr）逐个验签   ← 跳 4
```

**「最短」的判据**：

1. **信任源头只锁一次**：公钥根哈希在硬件只读锚（档 A）或随已验签 bootloader 进入（档 B）时**只被建立一次**；其后每一跳都是「用已锁定的公钥验下一跳」，不再引入新的、独立的信任源。这直接否定「Linux shim/MOK 允许用户 enroll 新公钥」式后门（`32` §2 / D-SB1 采纳：拒 MOK）。
2. **早期 C/asm 垫片不是信任跳**：`arch/<arch>/boot` 只执行已被验签的映像里的代码，它**自己不被单独验签、也不验别人**——它是「被信代码的执行器」，不是「新的信任裁决者」。因此它在信任链上**不占一跳**，只占功能链的一阶段（`09` Stage 1）。
3. **内核映像整体验签砍掉「按语言分签」缝隙**：mcc 产 C 部分 + rustc 产 Rust 部分**合并为单一 `.mimg` 后整体签名**（`32` §4.3 / `02` §4.3），避免「C 签了、Rust 没签」的半签名缝隙——这是信任链最短化的关键工程落点。
4. **capability 自举与 monitor 自度量同跳完成**：`09` Stage 4 的「第一批能力自举」与 `32` 的「monitor 自度量 PCR[2]」在同一时刻发生——身份根（验签过的 monitor 代码）与权限根（受限令牌）同源建立，不拆成两跳。

### 1.3 与 `09` 阶段链的关系（深化而非重复）

`09` 把启动拆成 Stage 0–6（功能视角）。本节把同一段重排成**信任视角的最短链**，二者是一体两面：

| `09` 功能阶段 | 本节信任视角落点 | 是否新增信任跳 |
|---------------|------------------|----------------|
| Stage 0 固件/引导器接入 | 信任源头建立（档 A/B/C 公钥根锁定） | 是（唯一源头跳） |
| Stage 1 架构相关早期（仅 C/asm） | 被信代码的执行器，**不**新增信任 | 否 |
| Stage 2 早期 C 运行环境（memblock） | 被信代码的执行器，**不**新增信任 | 否 |
| Stage 3 Rust 接管 kernel_main | 信任链「身份根」已就位（映像被验），进入安全关键世界 | 否（验签在跳 1 已完成） |
| Stage 4 capability/monitor 自举 | 权限根建立 + monitor 自度量 PCR[2] | 是（自度量跳，复用已验身份） |
| Stage 5 用户态服务接管 | 逐个服务验签（跳 4） | 是（下游逐服务跳） |
| Stage 6 交权完成 | 信任链冻结，运行期交由 `07`/`20` 管 | 否 |

结论：**整条链只有 4 个信任跳**（源头锁、映像验、monitor 自度量、下游服务验），且源头只锁一次——这是 MeuOS 自举信任链能达到的**理论最短**，与 `32` §1.2「每一跳验签 + 度量累积」完全一致，但明确了「早期 C/asm 不占信任跳」这一 `09` 未点破的事实。

## 2. 多系统参照：内核映像格式与交权路径（聚焦指定系统）

> 大喵铁律第二条：多系统参照，思想取长补短，实现自主研究。本节聚焦用户指定的六类系统的**内核映像格式 + 交权路径 + 信任锚**，为 §3「统一 `.mimg` 格式」与 §7「五架构收敛」提供范本与反例。

### 2.1 Linux：EFI stub / setup

- **映像格式**：`bzImage` = 16/32 位 `setup` 头 + 压缩的 `vmlinux`（含自解压 stub）。现代 x86_64 **EFI stub** 把内核编译为 PE/COFF EFI 应用，UEFI 直接把它当 EFI 程序加载；stub 内做 `ExitBootServices`、建 `boot_params`、跳原生 64 位入口。传统路径（BIOS）走 `setup`：real→protected→long mode 三级跳。
- **交权路径**：UEFI/BIOS → 引导器（GRUB/systemd-boot）加载 `bzImage` → EFI stub 接管内核自解压与页表初建 → `start_kernel`（架构无关）。
- **信任锚**：UEFI Secure Boot 验 `bzImage`（或先验 shim，shim 再验内核）；`shim` 引入 MOK（用户可 enroll 公钥）= **信任后门**（`32` 已否决）。内核模块 `CONFIG_MODULE_SIG` 是运行期签名，密钥仍隐含「内核特权者」。
- **可借鉴**：EFI stub「内核自带 PE 入口、引导器只负责把映像交给固件」的**单映像自举**思想——对应 MeuOS 把内核做成「固件/引导器可直接交权的统一映像」。**不可取**：三级模式切换（real/protected/long）冗余、MOK 后门、模块签名仍依赖特权者。

### 2.2 Windows：Boot Manager / WinLoad

- **映像格式**：`bootmgr`（UEFI 应用）+ `winload.efi`（加载器）+ `ntoskrnl.exe`（内核 PE）+ `hal.dll` + 启动驱动。无单一「内核映像」——**内核与加载器分离**。
- **交权路径**：UEFI → `bootmgr` 读 BCD → 加载 `winload.efi` → **WinLoad 负责建初始页表**（不是 HAL）、加载 ntoskrnl + 启动驱动、移交控制权 → 内核 Phase0/Phase1。
- **信任锚**：UEFI SB → `bootmgr` → WinLoad 经 **Code Integrity (CI)** 验 ntoskrnl/驱动签名；ELAM 早期启动反恶意软件；HVCI/VBS 把验证面隔离到安全内核。
- **可借鉴**：**「加载器先行建页表、再交内核」的权责切分**——与 MeuOS `arch/<arch>/boot` 垫片建早期页表、再交 `kernel_main` 同构；WinLoad 的「Phase0 机制 / Phase1 策略」分阶段思想（`09` §3.3 已引）。**不可取**：内核/加载器/驱动拆分使映像非单一、信任链多跳（bootmgr→winload→krnl 三跳均独立验签），且重服务留核（TCB 大）。

### 2.3 Fuchsia：Zircon boot (ZBI)

- **映像格式**：**ZBI（Zircon Boot Image）**——单一容器 = ZBI 容器头 + 一组 item（内核 item、bootfs item、cmdline item、ACPI/board-data item、RAM disk item…）。内核与 bootfs **打包进同一个 ZBI**，由 bootloader 或 QEMU `-kernel` 整体加载。
- **交权路径**：固件/bootloader 加载 ZBI → **boot shim** 解析 ZBI → 跳内核入口 → 内核启动后拉 **userboot**（首个用户态进程）→ devmgr 等用户态接管。
- **信任锚**：**Verified Boot**——ZBI（内核 + bootfs）整体签名验证；内核启动后对 package 做 verified boot；公钥**构建期嵌入 ZBI**（`32` 档 B 范本）；**无 TPM 依赖但支持**（`32` §3.4）。
- **可借鉴（最强范本）**：① **单一容器映像**把「内核 + 初始用户态 + 配置」合一，天然就是「统一内核映像格式」的成熟实现；② 公钥嵌 ZBI 即档 B；③ 内核自验 + 启动后验 package 的两段式；④ userboot 尽快交权（`09` §3.3 已引）。**不可取**：Zircon 无 capability 形式化（`20` 补）、无 Linux ABI 兼容（MeuOS 需 mkit 薄层让步）。

### 2.4 seL4：启动（验证优先、映像极简）

- **映像格式**：seL4 自身是**静态 ELF 微内核**，无专属「启动映像格式」；由外部 bootloader（u-boot / GRUB / 自带 `elfloader`）加载 ELF，并向 root task 传 **bootinfo**（机器描述：内存区、设备、Caps 空间）。
- **交权路径**：固件/引导器加载 seL4 ELF → 内核极简自举（建初始地址空间、把 bootinfo 交 **root task**）→ root task 是**唯一**首个用户态任务，其余皆由其 spawn。
- **信任锚**：**形式化证明替代部分信任**（`32` §2 已引）——8700 行 C 被证明功能正确 + 信息流安全，使「代码即可信」部分成立；但真实部署仍加签名验签（证明与启动验证正交互补）。
- **可借鉴**：① **bootinfo 抽象**统一机器描述（对齐 `09` Stage 0 `bootinfo`）；② root task 即「首个受约束用户态」范本（对齐 `09` Stage 5 meu-supervisor）；③ **内核极简、信任来自证明 + 验签双层**。`32` 已采纳「证明与启动验证正交且互补」。**不可取**：seL4 的 ELF + 外置 bootloader 模型不解决「多架构单一映像」与「度量基」问题（MeuOS 需 ZBI 式容器补强）。

### 2.5 coreboot / UEFI：固件级最小化与度量起点

- **coreboot 模型**：开源固件，阶段极薄——`bootblock`（ROMCC，最小）→ `romstage`（Cache-as-RAM）→ `ramstage`（C，DRAM 初始化）→ **payload**（可以是内核直启动、GRUB、seaBIOS、或 Tianocore UEFI 载荷）。**verstage** 在 ChromeOS 上做固件自身验签后再跳 ramstage。
- **交权路径**：coreboot 早期 HW 初始化 → 加载 payload → payload 直接把控制权交给内核（**内核直启动 payload**可省掉 GRUB 一跳）；有 TPM 时 coreboot 在 `romstage/ramstage` 即 extend PCR，使**度量从固件最底层开始**（`32` 档 C 升「度量锚定」的路径）。
- **信任锚**：verstage 验签固件（硬件锚）+ TPM 度量累积；coreboot + TPM = i386/无 UEFI 板把第 0 层从「软件比对」升到「度量锚定」（`32` D-SB8 采纳的可选补强）。
- **可借鉴**：① **「bootblock→romstage→ramstage→payload」的极薄阶段模型**是 `arch/<arch>/boot` 垫片的最佳范本（每段只做最小必要事）；② **payload 直启动内核**= MeuOS 把 `.mimg` 作为 coreboot payload 直接交权，砍掉 GRUB 类中间跳；③ verstage 验签 = 信任源头锁在固件最前。**不可取**：coreboot 不解决统一内核映像格式（它加载任意 payload），需 MeuOS 自定 `.mimg`。

### 2.6 Android：bootloader / AVB

- **映像格式**：`boot.img` = 内核 + ramdisk + dtb（GKI 后拆为 `boot.img` + `vendor_boot.img`）；现代还有 `init_boot.img`、`vendor_kernel_boot.img`。**vbmeta** 独立分区/镜像携带「各分区哈希 + 签名」（Merkle 根哈希签名）。
- **交权路径**：Bootloader（ABL / Little Kernel / u-boot）→ 读 `boot.img` → **AVB 验签**（bootloader 验 boot.img 对 vbmeta 的签名）→ 跳内核 → 内核解 ramdisk、挂 `/system` 等。
- **信任锚**：**AVB（Android Verified Boot）**——bootloader 是 AVB 链第一跳，公钥烧 Titan M/eFUSE（`32` 档 A 范本）；**回滚保护**（版本号拒绝降级）；A/B slot 防砖。
- **可借鉴（最强度量基范本）**：① **vbmeta = 分离的「签名 + Merkle 根哈希」元数据镜像**思想——对应 MeuOS 把签名/度量元数据从内核映像**分离或可并列**承载（`32` §3.2 双锚）；② 回滚保护（版本号绑 Merkle root）；③ 公钥烧硬件（`32` 档 A）。**不可取**：AVB 假设 A/B 固定分区 + 硬件密钥芯片，MeuOS 用 `.msys` 子树快照（`06` §4.3），密钥根无 Titan M（`32` §2 已对比）。

### 2.7 对比收口表

| 系统 | 映像格式 | 交权跳数 | 信任锚形态 | 对 `.mimg` 统一格式 | 对信任链最短化 | 不可取（避免缝合） |
|------|----------|----------|------------|---------------------|----------------|-------------------|
| Linux EFI stub | bzImage（setup+压缩 vmlinux）/ PE | 固件→(shim)→内核 | UEFI SB；MOK 后门 | 单映像自举好范本 | 三级模式切换冗余 | MOK、模块特权者 |
| Windows BM/WinLoad | bootmgr+winload+krnl 分离 | 固件→BM→WinLoad→krnl（3 跳） | UEFI SB + CI | 映像非单一 | 加载器先建页表可借鉴 | 拆分多跳、重服务留核 |
| **Fuchsia ZBI** | **单一 ZBI 容器**（内核+bootfs+配置） | 固件→ZBI→userboot | 公钥嵌 ZBI（档 B）、无 TPM 强制 | **最强范本：单容器** | 内核自验+启动后验两段 | 无 cap 形式化 |
| seL4 | 静态 ELF + bootinfo | 固件→ELF→root task | 证明+验签正交 | 需 ZBI 式容器补强 | bootinfo 抽象、root task | 不解决多架构单映像 |
| coreboot/UEFI | payload 任意 | 固件→payload→内核（可砍掉 GRUB） | verstage 验签 + TPM 度量 | payload 直启动内核好范本 | 极薄阶段、度量从底起 | 不定义映像格式 |
| **Android AVB** | boot.img + vbmeta（分离签名/Merkle） | bootloader→内核 | 公钥烧硬件（档 A）、回滚保护 | **签名/度量元数据分离好范本** | 回滚保护、A/B 防砖 | A/B 固定分区假设 |

> **非缝合怪宣言**：MeuOS 不拼接「Linux bzImage + Windows 拆分加载器 + Android A/B 分区 + Fuchsia userboot」——而是取其**共同内核**：① Fuchsia ZBI 的**单一容器映像** + 公钥嵌映像（档 B）；② Android **vbmeta 式分离签名/Merkle 元数据** + 回滚保护（档 A 锁硬件）；③ coreboot 的**极薄阶段 + payload 直启动内核**砍掉中间跳；④ seL4 的 **bootinfo 抽象 + root task 首用户态**；⑤ Windows 的**「加载器先建早期页表再交内核」权责切分**。落到一个由 `02`（早期 C/asm）/ `09`（Stage 链）/ `32`（公钥根/度量）/ `06`（.msys 原子）/ `11`（.mimg 开放议题）唯一决定的 MeuOS 形态：统一 `.mimg` 单容器 + 最短 4 跳信任链。

## 3. 统一内核映像格式（MeuOS Image, `.mimg`）的深化设计

> 本节点对 `11` §5 开放议题 1 与 `21` D1（「`.msys` 还是 `.mimg` 承载内核/设备树/启动配置」）：给出 `.mimg` 的**具体结构提案**，使其同时承载 `09`/`32` 所需的信任与加载信息，并与 `.msys` 协同而非竞争。

### 3.1 为什么需要统一 `.mimg`（而非直接复用 `.msys` 或裸 ELF）

- **`.msys` 的定位是 sysroot/rootfs，不是内核镜像**：`11` §5.1 已明示 `.msys` v2「明确定位为开发工具链 sysroot，不是通用系统镜像格式」。把内核 + DTB + 启动配置塞进 `.msys` 会破坏其「内容寻址 sysroot」语义（`06` §4.3 / 第七轮 C-G5）。
- **裸 ELF 缺信任与 bootinfo 载体**：seL4 式裸 ELF + 外置 bootloader 不解决「签名/Merkle 度量元数据如何随映像携带」「多架构入口如何统一」「bootinfo 如何传递」——`32` 要求度量基双锚随映像走，`09` 要求 `bootinfo` 归一化。
- **结论**：引入**单一 `.mimg` 容器**承载内核 + bootinfo/dtb + 可选 initramfs 指针 + 签名/Merkle 元数据，与 `.msys`（运行时 rootfs）分工——`.mimg` 管「启动期交权与信任」，`.msys` 管「运行期资源与原子更新」。二者经同一条 `32` 信任链衔接（`.mimg` 跳 1、`.msys` 跳 3）。

### 3.2 `.mimg` 结构提案（ZBI 式容器 + vbmeta 式度量元数据）

```
.mimg (MeuOS Unified Boot Image)
┌──────────────────────────────────────────────────────┐
│ Magic: "MEUOSIMG" + 版本号（含回滚保护版本）           │
├──────────────────────────────────────────────────────┤
│ Item 0: 内核映像（mcc C 部分 + rustc Rust 部分合并）   │
│         · 统一 ELF（五架构同一容器，arch 段标识入口）   │
│         · 已被整体签名（ed25519，与 .msys 同源算法）    │
├──────────────────────────────────────────────────────┤
│ Item 1: bootinfo / DTB / ACPI（机器描述，对齐 09 Stage0）│
├──────────────────────────────────────────────────────┤
│ Item 2: cmdline（内核参数，可含 .msys rootfs 位置指针） │
├──────────────────────────────────────────────────────┤
│ Item 3: initramfs 指针（可选）                         │
│         · 指向内置 ZBI 式 bootfs，或                 │
│         · 指向 `.msys` 路径（Stage 5 由 FS 服务挂载）  │
├──────────────────────────────────────────────────────┤
│ Item 4: 度量元数据（vbmeta 式，分离可并列）            │
│         · 内核 item 的 Merkle 根哈希（签名）           │
│         · 版本号（回滚保护，绑 Merkle root）           │
│         · 公钥指纹（指向档 A/B/C 公钥根）              │
└──────────────────────────────────────────────────────┘
```

- **容器思想 = Fuchsia ZBI**（`2.3` 最强范本）：内核 + 机器描述 + 配置合一，bootloader/固件整体加载。
- **度量元数据 = Android vbmeta 式分离**（`2.6` 范本）：签名/Merkle/版本号**不与内核代码混排**，便于 bootloader 在「不解析内核」的情况下先验签/度量（对齐 AVB bootloader 先验 vbmeta 再跳内核）。
- **签名算法复用 Kit ed25519**（`21` §4.1 已在 `.msys` 使用），不引入新算法、不污染编译器 TCB（`32` §3.3）。

### 3.3 签名/度量如何嵌入（衔接 `32` 跳 1）

- **整体签名**：Item 0（合并内核）整体 ed25519 签名，公钥来自档 A/B/C（§1.2 跳 1）。bootloader/固件验签 `.mimg` 后才跳内核——**这是 `32` §3.1 跳 1 的物理载体**。
- **Merkle 度量基**：Item 4 的「内核 item Merkle 根哈希」= 对 Item 0 做块级 Merkle（叶子 = 内核映像分块哈希），根哈希由官方密钥签名（对齐 `32` §3.2 / AVB vbmeta）。支持**按需度量**（仅加载到的内核块才校验），不必全映像扫描。
- **版本号回滚保护**：Item 4 版本号绑 Merkle root 签名，旧版本即使签名有效也被拒（`32` §3.2 已采纳回滚保护）。
- **与 `.msys` 双锚对称**：`.mimg` 自带「ed25519 签名 + 内核 Merkle 根」双锚，与 `.msys` 的「ed25519 包签名 + extent Merkle 根」双锚（`32` §3.2 / `06` §4.2）**同构**——启动期信任链的两大载体用同一套度量基结构。

### 3.4 五架构统一入口（收敛 `09` §5.5）

- **单一 `.mimg` 容器、五架构同源**：Item 0 内核 ELF 内含五架构的 `arch/<arch>/boot` 入口段，容器头用 arch 标识告诉 bootloader 跳哪个入口（`09` §5.5 收敛架构）。这与 `01` §5「同源码异架构」一致。
- **UEFI 路径**：x86_64/aarch64/loongarch64 的 `.mimg` 可包装为 PE/COFF EFI 应用（仿 Linux EFI stub，`2.1`），UEFI 直接交权；或经 Shim-less 直验（拒 MOK，`32` D-SB1）。
- **OpenSBI / EFISTUB 路径**：riscv64 由 OpenSBI 验 `.mimg`（档 B，公钥随 OpenSBI 进入），loongarch64 经 EFISTUB 验。
- **i386 路径**：老 BIOS 无 SB，`.mimg` 仍整体签名，但公钥硬编码进映像做档 C 已知良值比对（`32` D-SB8 采纳）；可选 coreboot + TPM 升度量锚定。

## 4. 早期内存/页表建立（深入 `09` Stage 1–3，衔接 `03`）

> `09` §5.2/§5.3 已给阶段链；本节深化「早期页表的临时→接管契约」与「memblock→buddy 原子转交」，是信任链最短化在**功能链**上的物理落地（早期 C/asm 不占信任跳，但必须正确建立地址空间供跳 2/3 使用）。

### 4.1 早期页表的「临时 → 接管」契约

- **Stage 1 页表是「最小临时」**：仅映射内核映像 + 早期串口 + 页表自身递归所需内存，由 `arch/<arch>/boot` C/asm 直写（`09` §5.3）。此时**无 Rust runtime、无 `03` 类型化页表抽象**——页表是裸硬件结构。
- **Stage 3 Rust 接管 = 唯一真相源切换**：`kernel_main` 进入后调用 `03` 的 `arch/mm/pagetable`（`map/unmap/walk/set_flags`）**重建/接管**页表，把临时映射提升为「内核高半直接映射 + 用户态布局」（`09` §5.3 / `03` §4.3）。
- **契约不变量**：Stage 1–2 的临时页表在 `kernel_main` 入口处**必须仍有效或可无感切换**——Rust 接管后以 `03` 抽象为唯一真相源。这保证「早期 C/asm 跑起来的地址空间」与「Rust 接管后的地址空间」无断裂窗口（防止跳 2 monitor 自度量时地址空间失效）。
- **与度量基协同**：页表本身**不进度量基**（它是被验签映像的执行产物，非独立信任对象）；但页表映射的**内核代码**已被 `.mimg` 跳 1 验签——地址空间只是「已信代码的视图」。

### 4.2 memblock → buddy 原子转交（引用 `11` C7 / `13`）

- **两阶段分配器**（`03` §4.2.1 / `09` §5.3）：Stage 2 `memblock` 临时 reserve/alloc，待 `03` buddy/SLUB 就绪转交。
- **原子边界已裁决（C7=方案 X，`11` §11.1）**：在 `kernel_main` 内 `buddy_init()` **单一调用**中、单线程、关中断完成；以「检测到的全部物理内存 = 保留 + 已分配 + 空闲」全量三类对账为原子边界；早期仍存活对象由 buddy 以 `MmPage[].flags=RESERVED` 认领永久持有；旧早期页表在换顶表后才释放；任一阶段对账失败 → 结构化 panic（`12` CrashReport），绝不留「部分转交」中间态。
- **对信任链的意义**：内存转交的原子性保证「monitor 自度量（跳 2）时物理内存真相源已归 buddy、无并发转交窗口」——`11` M0 进入用户态前真相源已定，跳 2/3 的度量基于一致的内存视图。

### 4.3 五架构页表差异收敛（深化 `09` §5.5）

| 架构 | 早期页表结构 | Rust 接管后 | 收敛点 |
|------|--------------|-------------|--------|
| x86_64 | 4 级 PML4 + PCID | `03` 类型化页表（ASID/PCID） | 进 `kernel_main` 时 MMU on、内核空间有效 |
| i386 | 2/3 级 32-bit 页表、无 PCID | 同（`02` C2 纯 C，Rust 以 no_std `.o` 链接，非裸机 target） | 同上；i386 非降级（`09` 第三轮 C6 回写） |
| aarch64 | TTBRx 4 级 + ASID | `03` 类型化（ASID） | 同上 |
| riscv64 | Sv39/48 + ASID | `03` 类型化（ASID） | 同上（经 SBI 交权） |
| loongarch64 | 多级页表 + ASID | `03` 类型化（ASID） | 同上（CSR） |

- **收敛契约（深化 `09` §5.5）**：无论架构，进入 `kernel_main` 必须满足同一组不变量——`MMU on`、内核地址空间有效、`memblock` 可用、`bootinfo` 已解析、`页表在入口仍有效或可无感切换`。这把架构差异封死在 `arch/<arch>/boot`（Stage 1–2），使 TCB 的 Rust 核心不被架构特化侵蚀，也保证「跳 2 monitor 自度量」对五架构输入一致。

### 4.4 早期页表与「生死相关快速路径」

- **早期串口直写**（Stage 1，`09` 第三轮 C8 回写）：cap 世界未起，内核 bootstrap 上下文直写 MMIO/端口做早期诊断 banner + panic 应急输出，是生死相关快速路径（`10` §4.2 内核态）。此时**不经能力网关**（cap 世界未起），但已是被验签映像的执行器（信任链跳 1 已保证其真实）。
- **Stage 4 串口 cap mint**：monitor 上线时一并 mint 串口 cap，内核持临时副本；Stage 5 用户态 console 接管时内核撤销临时副本、仅留 panic 应急写窄权（`09` C8）——页表/控制台从「bootstrap 直写」平滑过渡到「受能力约束」，不引入新的信任跳。

## 5. 与 `32` 公钥根/度量链的衔接（深化）

> `32` 已从安全启动维度定义信任链；本节把 `32` 的抽象跳**绑定到本文件的 `.mimg` 物理载体与 Stage 阶段**，使「逐跳验签 + 度量累积」在自举路径上**可操作**。

### 5.1 跳 1：bootloader/固件验签 `.mimg` = `32` §3.1 跳 1 的物理落地

- `.mimg` Item 0/4（§3.2/§3.3）是跳 1 的验签对象；公钥来自档 A/B/C（`32` §3.3 / D-SB1 采纳）。
- **度量累积**：`PCR[1] = extend(hash(.mimg))`（`32` §3.1 跳 1）——`.mimg` 整体哈希 extend 进度量寄存器。
- **早期 C/asm 验签器落点**（`32` §4.2）：ed25519 验签器作为**极薄 C 组件**落在 Stage 0–1（属早期 TCB、`02` 允许），不进 Rust TCB 核心（只做「放行/拒绝」布尔，`32` §4.3）。这是信任链跳 1 的**执行器**，但它自身不被单独验签（它是被验签映像的一部分）。

### 5.2 跳 2：monitor 自度量 = `32` §3.1 跳 2 / PCR[2]

- **时机 = `09` Stage 4**（kernel_main 内、spawn 首个用户态前）：monitor 用 boot 期传入的度量累积器**对自己做度量**（hash 自身代码 + 初始 capability 模板），extend `PCR[2]`（`32` §3.1 跳 2）。
- **身份根 × 权限根同源**：monitor 派生的根 Job / 设备 / 命名空间 / `KEY_UNWRAP` 服务端权（`06`/`07` C2），其「受约束」来自 `07` rights（不可扩张），其「确实来自真 monitor」来自 `PCR[2]` 对 monitor 的度量——二者缺一，下游 `.msys`/服务拿到的就是不可信令牌（`32` §3.1 关键点）。
- **与 §1.2 一致**：monitor 自度量**不新增信任源**（公钥已在跳 1 锁定），只是把「已信 monitor」的哈希记录进链——它是信任链的**自证跳**，非**新源头跳**。

### 5.3 跳 3：`.msys` rootfs 挂载的度量协同

- `.msys` 挂载（Stage 5，FS 服务）消费 `07` root-of-trust 能力（来自 boot 链）验签 `.msys` 包（Kit ed25519）+ 卷 Merkle 根哈希（`32` §3.1 跳 3 / `06` §4.2）。
- **度量基双锚对称**：`.mimg` 双锚（§3.3）与 `.msys` 双锚（`32` §3.2）用同一 Merkle 结构，FS 服务验 `.msys` 时复用与验 `.mimg` 同构的验证器（仅公钥/版本号指向不同 item）。
- **PCR[3] = extend(hash(.msys volume root))**：把 rootfs 完整性钉进链，使最终状态能溯及「固件→内核→monitor→rootfs」全链（`32` §1.2 第 2 点）。

### 5.4 公钥根档 A/B/C 在 boot 期的落地（深化 `32` D-SB1/D-SB8）

| 档 | boot 期落地 | `.mimg` 验签者 | 度量 sink |
|----|-------------|----------------|-----------|
| **A（硬件锁根哈希）** | 固件只读区锁公钥根哈希；UEFI SB / eFUSE / OTP | 固件/UEFI 先验 bootloader，bootloader 验 `.mimg`（链式） | 真实 TPM PCR 或软件寄存器 |
| **B（bootloader 内置公钥）** | 公钥随 `.mimg` 或 OpenSBI/EFISTUB 验签进入（`32` 档 B = Fuchsia 公钥嵌 ZBI 范本） | bootloader/OpenSBI 验 `.mimg` | 软件寄存器为主 |
| **C（i386 软件可信根）** | 公钥硬编码进 `.mimg`/内核做已知良值比对 | 内核早期 C 验签器做比对 | 软件度量寄存器（无 TPM 假设） |

- 档 A/B 公钥经 `09` Stage 0–1 锁定传入；档 C 公钥随 `.mimg` 整体签名进入（i386 镜像同样整体签名，`02` C2 不影响验签语义，`32` §4.3）。
- **Day 1 本地自检**（D-SB7 采纳）：无 TPM 架构（含 i386）仅做软件度量寄存器累积 + 冻结 PCR 比对，远程证明（`ATTEST`=bit39）后置——所有五架构 Day1 都拿到「来源/完整性」保证。

## 6. 与 `06` `.msys` 原子加载的协同（深化）

> `09` §5.6 / `11` §4.1 已声明 `.msys` 作为 rootfs 的接入点；本节深化「`.msys` 的**原子加载**如何复用本文件的信任链与能力链」，把 `06` §4.3 的运行时原子更新与 boot 期加载打通。

### 6.1 `.msys` 作为 rootfs 的 boot 期加载路径（信任链跳 3）

- **Stage 0 解析 bootinfo** 拿到 `.msys` 位置（在 `.mimg` cmdline 或 bootinfo 指针，`§3.2` Item 2/3）。
- **Stage 5 FS 服务挂载**：FS 服务（首个用户态服务之一）消费 `07` root-of-trust 能力（来自 boot 链 `32` 跳 1/2）验签 `.msys` 包 + 卷 Merkle 根（`06` §4.3(a)）→ 挂载为 `/msys` 子树。
- **同步于「能 spawn 受约束用户态」**：FS 服务本身持「`.msys` 块设备读 + 命名空间根」能力（`09` §5.4 第 3 类），由 monitor 在 Stage 4 mint——故 `.msys` 挂载从一开始就是**受能力约束**的，与 `07` 模型无缝咬合。

### 6.2 原子 repoint 与 boot 决策的协同

- **运行时原子更新**（`06` §4.3）：新 `.msys` 经「签名校验 → 备份快照 → 暂存克隆 → 原子 repoint → 监督协同」切换。本文件要求：**repoint 前新卷必须先过 Merkle 度量基**（新 root hash 验签通过）才能 repoint（`32` §4.1 协同点）；监督者授权的同代回退豁免于版本防回滚（`32` D-SB3 待协同）。
- **boot 期首次挂载 = 一次「从零 repoint」**：把命名空间 `/msys` 别名首次绑定到 bootinfo 指定的 `.msys`，其信任前提与运行时 repoint **完全一致**（同源验签/度量/能力链）——boot 与运行时不两套逻辑。
- **A/B 防砖兜底协同**（`06` §4.3 / `09` §5.6）：若 `.msys` 损坏到 FS 服务都起不来，引导级 A/B 双 slot 作最后防线（对齐 ChromeOS miniOS）；本文件 `.mimg` 可携带「恢复 `.msys`」指针（Item 3 扩展），使 boot 期也能触发防砖回退。

### 6.3 A 不可变 Blob 子集与启动指纹（深化第七轮 C-G5）

- `06` 第七轮 C-G5 采纳：`/msys` 子树 = **A 不可变 Blob 子集**（内容寻址、hash=名、去重、自认证），嵌入同一 MeuOS-FS 服务。
- **启动指纹内禀化**：A 子集的 hash 兼作 `.msys` 签名校验的**内容指纹**（`06` §7.2 回写）——签名校验对象从「路径集合」收敛为「一组内容哈希」，防篡改证据更内禀。本文件 `.mimg` 跳 3 度量 `.msys volume root` 时，该 root 即 A 子集的内容寻址 head Ref（`06` §7.2），使 boot 期度量与运行时不可变子集共用同一指纹，**不另造度量基**。

## 7. 五架构 boot 差异收敛（深化 `09` §5.5）

> `09` §5.5 已给五架构表；本节补齐**信任锚形态 + 入口交接 + i386 非降级**的收敛细节，使 `.mimg` 单一容器能服务五架构。

### 7.1 入口/特权级/信任锚差异（深化表）

| 架构 | 固件/入口 | 特权级过渡 | Stage 1 关键差异 | 信任锚（档） | 收敛点 |
|------|-----------|-----------|------------------|-------------|--------|
| x86_64 | UEFI/PE 或 multiboot2 | real→protected→long | PML4 + PCID | A（UEFI SB） | `.mimg` PE 包装或 Shim-less 直验 |
| i386 | 32-bit BIOS/multiboot | 保护模式（无 long） | 2/3 级页表、无 PCID | C（软件可信根） | `.mimg` 整体签 + 硬编码公钥比对 |
| aarch64 | UEFI+DT/PSCI | EL2→EL1 | TTBRx 4 级 + ASID | A（eFUSE）或 B | `.mimg` + DT 归一化 |
| riscv64 | OpenSBI(M)→S-mode | M→S | Sv39/48 + ASID | B（OpenSBI 内置） | `.mimg` 经 SBI 交权 |
| loongarch64 | UEFI/EFISTUB+CSR | 特权级→内核态 | 多级页表 + ASID | B（EFISTUB 内置） | `.mimg` + CSR |

### 7.2 收敛契约：进入 `kernel_main` 的不变量（深化 `09` §5.5）

无论架构，`.mimg` 容器头用 arch 标识引导 bootloader 跳对应 `arch/<arch>/boot` 入口；入口垫片完成 Stage 1–2 后跳 `kernel_main`，必须满足：

1. `MMU on`、内核地址空间有效（§4.1 契约）；
2. `memblock` 可用、物理内存真相源待 `buddy_init()` 单点转交（§4.2）；
3. `bootinfo` 已解析（DT/ACPI/multiboot/OpenSBI 归一化，`09` Stage 0）；
4. 信任链跳 1 已完成（`.mimg` 已验签 + `PCR[1]` 已 extend）——若档 C，则为已知良值比对、度量寄存器中；
5. 页表在入口仍有效或可无感切换（§4.1）。

这把架构差异封死在 `arch/<arch>/boot`，五架构**同源 `.mimg`**、**同源 `kernel_main`**（`01` §5 同源码异架构），Rust 安全关键核心不被架构特化侵蚀。

### 7.3 i386 非降级与档 C（深化 `09` 第三轮 C6 / `32` D-SB8）

- **i386 非降级架构**：`09` 第三轮 C6 采纳——i386 TCB 组件以 rustc 产 `#![no_std]` + `extern "C"` 的 `.o` 由 C 链接器并入内核镜像，纯 C 退路仅应急；i386 与 64 位在 TCB 安全上等价，差异仅在构建管线。
- **i386 启动信任档 C 永久基线**（`32` D-SB8 采纳）：无硬件锚，公钥硬编码进 `.mimg`/内核做已知良值比对，不挡持私钥者；威胁模型显式标注降级（`29` D-T6 同类）。可选：有 TPM 的 i386 目标 → coreboot + Measured Boot 升「度量锚定」（§2.5）。
- **不阻塞 M0–M4**：档 C 仅弱化第 0 层 boot 溯源，运行期 capability 模型（`07`）与 `29` 纵深第 1–4 层在 i386 完整（`32` §3.1/§2 论证），故 i386 走「能自举 + 运行期安全完整」务实路径。

## 9. MeuOS 推荐（自主结论）

> 综合 §1–§8，给出本深化维度的明确推荐。铁律：修订式追加不删；跨域项以 `00` 冲突登记表为准。

### 9.1 总体推荐

1. **统一 `.mimg` 单容器映像**：内核（mcc C + rustc Rust 合并）+ bootinfo/dtb + cmdline + 可选 initramfs 指针 + 分离式签名/Merkle 度量元数据，ZBI 式容器 + vbmeta 式度量元数据（§3）。`.msys` 继续管运行时 rootfs 与原子更新，二者经同一条 `32` 信任链衔接。
2. **最短 4 跳信任链**：源头锁（档 A/B/C 公钥根，只锁一次）→ `.mimg` 整体验签（跳 1）→ monitor 自度量 PCR[2]（跳 2，身份根×权限根同源）→ `.msys`/下游服务逐验（跳 3/4）。早期 C/asm 垫片**不占信任跳**（§1.2/§1.3）。
3. **尽早交权 + 单一 `kernel_main` 边界**：架构相关差异收敛进 `arch/<arch>/boot` 极薄垫片（仿 coreboot 阶段模型），进入 `kernel_main` 后 Rust 把守 TCB，立即 mint 根 Job/设备/命名空间能力并拉起 FS 服务 + meu-supervisor（§4/§7）。
4. **早期内存/页表「临时→接管」契约 + buddy 原子转交**：Stage 1 最小临时页表、Stage 3 `03` 接管为唯一真相源、memblock→buddy 单点全量对账（`11` C7），保证跳 2/3 基于一致内存视图（§4）。
5. **与 `.msys` 原子加载共用信任/能力链**：boot 期首次挂载 = 一次「从零 repoint」，与运行时原子更新同源验签/度量/能力；A 不可变子集 hash 兼作启动指纹（§6）。
6. **Day1 本地自检、五架构同构**：无 TPM 架构（含 i386 档 C）仅软件度量寄存器 + 冻结 PCR 比对；远程证明后置；i386 非降级但启动信任显式降级标注（§5.4/§7.3/§8）。

### 9.2 关键决策点（需架构裁决的项）
