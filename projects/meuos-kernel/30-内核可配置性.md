# 30 - 内核可配置性（Configurability：编译期 feature + 运行期 tunable + 可观测驱动自动调优）

> 子领域调研 / 规划设计文档，由 kernel-plan 团队「第三轮新范围拓展调研员」（general-purpose-29，lite / hy3）产出。
> 适用范围：MeuOS 自研内核「哪些可配、如何配、配了有什么代价」——即**编译期 feature 开关**、**运行期 tunable**、以及**可观测性驱动的自动调优**。
> 关联约束（来自 `00-总览与路线图.md` 与各子文档）：外部兼容 Linux ABI（兼容层）、内部自主设计；务实混合内核（01）；Rust+C（02）；capability-based 安全 Day 1（07）；三大方向 = ①统一 FS 层（06）+ ② spawn 进程管理（04）+ ③ capability 安全（07）。

>
> 本文为规划草案，结论可在后续查缺补漏轮次以**修订式追加**更新，不删。跨域项以总览 C1–C14 + 18 为准；凡涉及其他子文档的待决点，本文**只声明依赖、不替其下结论**。

## 0. 一句话结论（先给答案）

MeuOS 的配置必须呈**两层模型**：① **编译期 feature**——决定「哪些服务 / 能力编入内核镜像、哪些留在用户态、i386 纯 C 段如何裁剪」，直接绑定最小 TCB 与五架构差异，是能力世界「能不能存在」的开关；② **运行期 tunable**——经 capability 守护的**结构化配置通道**下发，**不暴露任何全局可变内核参数**（Fuchsia 立场），且每个 tunable 有边界校验、可经 inspect（12 §4.4）观测、可经 `.msys` 原子更新（06 §4.3 / 23 §5）回滚。安全关键不变量（capability 检查、panic=abort）**绝不可运行期关闭**，只能在编译期固定——这是「无全局关沙箱」（15 D1 已采纳裁决）在配置维度上的同构延伸。可观测性（inspect 树 + 事件流）既是配置的**读取面**，也是**自动调优**的反馈面。

## 1. 「应该是什么样」——可配置性推演（解构型思维）

### 1.1 先问：一个 capability 世界、用户态服务化的自主内核，配置「应该」是什么样

解构 Linux 的隐含契约可见：Linux 的配置是**分散、全局、可突变**的——Kconfig 在编译期、sysctl/`/proc/sys` 在运行期、boot cmdline 在启动期，三者无统一模型；sysctl 是「全局可变的内核参数表」，任何有 `CAP_SYS_ADMIN` 的进程都能改，且改了就即时生效、无结构 schema、无版本、无回滚。这套模型在宏内核 + root 特权世界里是「补丁历史」，但在 MeuOS 的处境下是**反模式**：

- MeuOS 内部**只有 capability，没有 root、没有隐式权限**（00-A1/A2/A3），「谁有权改内核配置」本身必须是一张 capability 令牌——不该有「root 一键改 sysctl」的等价物。
- MeuOS 的**服务在用户态、由监督者按 Job 树重启**（00 §1 方向②、04 §4.5），内核态只保留「机制 + 唯一裁决点」（00 §1 收口）。配置「面」不该是一块散落的内核全局变量，而应是一棵**结构化的、可程序消费、可审计、可回滚**的树——与 inspect 树（12 §4.4）同源。
- MeuOS 有 `.msys` 原子更新（06 §4.3、23 §5）作回滚媒介。这给了配置「可回滚」的结构性杠杆：一次配置变更 = 一条命名空间 repoint 或一棵子树原子提交，**天然可灰度、可回滚**，而非 sysctl 那样「改了就是改了、错了只能手动改回去」。

由此推演「应该是什么样」：**配置分两层，且两层都显式、可审计、可回滚**：

1. **编译期 feature**——回答「这个内核镜像**能做什么**」。哪些服务/能力编入、哪些出核、i386 纯 C 段裁掉什么。它决定 TCB 边界（02 §4.2）与五架构差异（01 §5-6），且一旦出核就**运行期无法找回**（正确——安全关键面不该运行期可开关）。
2. **运行期 tunable**——回答「这个已编入的能力**跑多猛**」。调度权重、分配器水位、超时、OOM 策略等**性能/策略类**旋钮。它必须经 capability 守护、**有界**、可观测、可回滚，且**绝不触碰安全模型的开关**（呼应 15 D1「无全局关沙箱」）。

### 1.2 两类「配置命运」对应两种代价

| 配置 | 改变什么 | 配错的代价 | 是否可运行期撤销 |
|------|----------|------------|------------------|
| 编译期 feature | 内核镜像的**能力集 / TCB 边界** | 可能扩大 TCB、引入不可验证面、跨架构不可移植 | 否——需重新编译 + `.msys` 重新发布（23 §5 杠杆） |
| 运行期 tunable | 已编入能力的**运行参数** | 性能退化、OOM、死锁倾向；**不应**导致安全降级 | 是——inspect 写回 + 即时校验 + 可回滚快照 |

**关键判语**：编译期 feature 的「代价」由「编译 + 发布」承担（重、不可逆、需审计），因此只放「结构性、安全相关、架构相关」的开关；运行期 tunable 的「代价」由「边界校验 + capability 守护」承担（轻、可逆、即时），因此只放「量变、不质变」的旋钮。这恰是解构型落点——**把「能不能」和「跑多猛」彻底分开，前者进编译期、后者进运行期**。

### 1.3 与「非缝合怪」对齐：借谁、不借谁

- **借 Fuchsia**：组件级配置经**结构化 manifest**、运行期 tunable **受 capability 守护、无全局可变内核参数**——与本文两层模型的运行期层完全同构，是最贴切参照。
- **借 seL4**：**编译期证明配置、几乎无运行期可调**——其「安全关键参数在编译期即固定、运行期不可改」的立场，是本文「安全关键不变量不可运行期关闭」的根据。
- **借 ChromeOS / Android（系统属性 props / 资源叠加）**：配置分层（系统默认 / 设备 / 用户）与「资源叠加」思想——对应本文「bootinfo 默认 + `.msys` manifest 覆盖 + per-Job 投影」的层级。
- **借 Linux Kconfig**：feature 的**显式依赖图**（feature A 依赖 B、冲突 C）值得借鉴其表达力，但**不借**其「散落、无统一运行期模型」的割裂。
- **不借**：Linux sysctl 的「全局可变内核参数表 + root 即改 + 无 schema/无版本/无回滚」膨胀模式（见 §2 膨胀教训列）；Windows 注册表「全局可变、权限模糊」模式（permission 模型与 capability 世界冲突）。

## 2. 多系统参照对比表（含配置膨胀教训列）

> 横轴：各系统如何管理「编译期 feature / 运行期 tunable / 配置是否可审计可回滚」；纵轴：系统。结论列给 MeuOS 取舍。

| 系统 | 编译期 feature | 运行期 tunable | 配置可审计/可回滚 | **配置膨胀教训（MeuOS 须规避）** | **MeuOS 取舍** |
|------|----------------|----------------|-------------------|-------------------------------|----------------|
| **Linux** | Kconfig（显式依赖图，成熟） | sysctl `/proc/sys` + boot cmdline（**全局可变、无 schema、无版本**） | 弱：无原生回滚、改了即生效、root 可改 | **sysctl 膨胀**：上千个旋钮、语义重叠、无人敢删、ABI 承诺包袱；boot cmdline 成第二 sysctl | 借 Kconfig 依赖图思想；**不借** sysctl 全局可变模式 → 用 capability 守护 + 结构化 tunable |
| **Windows NT** | 构建配置 / 校验开关 | **注册表**（全局可变、权限模糊、可远程改） | 弱：注册表可备份但无原子语义 | 注册表成为「万能可变状态黑洞」，权限模型与 capability 世界冲突 | **不借**注册表模式；运行期配置走 capability 守护的 inspect 子树 |
| **macOS** | build settings | **plist**（系统配置，结构化、签名） | 中：plist 可被 Config Profile 覆盖、有 MDM 管理 | plist 散落多目录、版本漂移难追踪 | 借「plist 结构化 + 签名 + 策略覆盖」思想 → 对应 `.msys` manifest 签名覆盖 |
| **Android** | build flags / Treble | **系统属性 props**（分层：系统/设备/用户，资源叠加）+ 资源叠加 | 中：属性重启即重置、无持久回滚 | props 无强类型 schema、易成「隐藏开关」 | 借「分层叠加 + 资源叠加」；**不借**其无类型、无 capability 守护 |
| **塞班** | 能力/构建配置 | 配置框架（平台安全约束） | 中 | 全局 BC break 管理委员会过重 | 不借其全局委员会；以 `.msys` 同版本升级 + 编译期固定替代 |
| **ChromeOS** | 构建配置 | 组件级配置经**结构化 manifest**、运行期受 capability 守护、**无全局可变内核参数** | 强：配置随系统镜像签名、可回滚 | 相对克制，膨胀控制较好 | **最贴切（运行期层）**：结构化 manifest + capability 守护 + 无全局可变 |
| **Fuchsia** | GN 构建 feature（组件级） | **组件 manifest 配置 + 运行期 tunable 受 capability 守护、无全局可变内核参数**；syscall 不稳、靠 system ABI revision | 强：包签名 + 组件级、可版本化（FIDL，23 §3） | 相对克制，组件自治、无集中 sysctl | **最贴切（整体）**：两层模型 + capability 守护 + 组件级 + 可版本化 |
| **seL4** | **编译期证明配置**、几乎无运行期可调 | 极简（root task 自举后用户态管理） | 强：证明配置确定性 | 无膨胀问题（封闭） | **借**「安全关键参数编译期固定、运行期不可改」立场 |
| **MeuOS（本文）** | 编译期 feature（Kconfig 式依赖图 + TCB 绑定 + 五架构裁剪） | 运行期 tunable（capability 守护的 inspect 可写子树、有界、可回滚） | 强：inspect 可观测（12）+ `.msys` 原子回滚（06/23） | **规避目标**：禁止 sysctl 式膨胀、禁止运行期关沙箱 | 两层模型 + capability 守护 + 可观测驱动自动调优 |

> 结论骨架：Fuchsia / ChromeOS 的「组件级结构化配置 + 运行期受 capability 守护 + 无全局可变内核参数」是运行期层的直接范本；seL4 的「安全关键参数编译期固定」是「哪些开关不能进运行期」的范本；Linux Kconfig 的依赖图表达力可借鉴，但其 sysctl 膨胀是头号反模式。实现全部自主研究，不缝合。

## 3. MeuOS 两层配置模型

> 本节给核心交付物：两层各自的边界、内容、代价、与 TCB/五架构的关系。

### 3.1 第一层：编译期 feature（build-time features）

**本质**：决定「这个内核镜像**能做什么**」——即能力集与 TCB 边界。一旦出核，运行期无法找回（正确，安全关键面不该运行期可开关）。

**承载形式**：一套 Kconfig 式依赖图（显式 `feature → depends on / conflicts with`）+ 一份**内核 build manifest**（随镜像发布、进 `.msys`、可签名、可审计）。不缝合 Linux 的散落模型，只借其依赖图思想。

**内容分类（呼应最小 TCB 与五架构差异）**：

| feature 类别 | 范例 | 为何在编译期 | 关联子文档 |
|--------------|------|--------------|-----------|
| **TCB 服务编入** | capability 监视器 / IPC 端点 / 调度核心 / VFS 抽象 是否编入（这些**恒编入**，不可关） | 安全关键路径恒在 TCB（02 §4.2、00-A3） | 02 / 07 |
| **出核服务裁剪** | FS/网络/驱动/监督策略 是否编入内核（默认**全部出核**为服务，lean hybrid，01 §4.1、00-A6） | 决定 TCB 大小与故障爆炸半径 | 01 / 06 / 10 |
| **五架构差异裁剪** | 大页 / ASID 宽度 / NUMA / IOMMU / 架构特定页表级数的编译期开关 | 五架构语义差异侵蚀最小统一 TCB（01 §5-6、09 §5.5） | 02 / 03 / 09 |
| **i386 纯 C 段裁剪** | i386 上哪些 TCB 组件以「C 链接 Rust `.o`」交付、哪些维持纯 C（15 C6 已采纳：i386 **非降级架构**，TCB 以 Rust `.o` 链接交付） | i386 缺裸机 target，需编译期决定交付管线（02 C2、15 §3.4） | 02 / 15 |
| **调度/分配器算法选型** | EEVDF vs RR+权重（原型期，04 §5-1）；SLUB 尺寸档；是否启用 THP 聚合（03 §5-3） | 算法选型影响 TCB 与正确性，需编译期定 | 03 / 04 |
| **安全关键不变量固定** | capability 检查**强制编入（不可关）**；`panic=abort`（内核核心 Rust，02 §4.5）；无「调试 root」（12 §4.2） | 这些是**地基非补丁**，绝不可运行期关闭（07 §2.3、15 D1） | 02 / 07 / 12 / 15 |
| **兼容层覆盖子集** | 哪些 Linux syscall 子集编入（08 C12：声明子集）；`uname` 报告值（08 C14 / 23 §7） | 决定对外兼容表面积 | 08 / 23 |
| **调试/可观测构建档** | 调试构建内嵌完整符号表、发布构建外置（12 §7-3）；inspect/事件流是否编入 | 影响内核体积与泄露面 | 12 |

**代价与纪律**：编译期 feature 的代价由「重新编译 + `.msys` 重新发布」承担（重、不可逆）。因此**只放结构性、安全相关、架构相关**的开关；凡「量变不质变」的旋钮，**一律不得**进编译期 feature（那是运行期 tunable 的地盘）。这也规避了 Linux 把「feature 与 tunable 混在 Kconfig/sysctl 两套无关联模型」的割裂。

### 3.2 第二层：运行期 tunable（runtime tunables）

**本质**：回答「已编入的能力**跑多猛**」——纯**量变性**旋钮，绝不质变性。经 capability 守护的**结构化配置通道**下发，绑定到 inspect 树（12 §4.4）的**可写子树**，无全局可变内核参数（Fuchsia 立场）。

**承载形式**：一棵 `kernel/config/` inspect 子树 + per-Job/per-service 可写子树（capability 守护）；schema 强类型、可版本化（参照 23 §6 协议版本协商思路，配置 schema 自带 `config_version`）。

**内容分类（呼应 03/04/09/12 的接口）**：

| tunable 类别 | 范例 | 边界（有界校验） | 关联子文档 |
|--------------|------|------------------|-----------|
| **调度参数** | EEVDF 虚拟截止期记账粒度、公平权重上限、RR 时间片、RT 优先级天花板（创建 RT 线程需 capability，04 §4.3） | 权重 ∈ [1, MAX_WEIGHT]；RT 优先级上限封顶防饿死 | 04 |
| **资源账本阈值** | Job 级 CPU 带宽上限、内存上限、句柄数上限、IO 带宽（04 §4.4） | 不得超过父 Job 配额（投影继承，15 D2 同构） | 04 |
| **分配器参数** | buddy 预留 RESERVED 大页池比例（03 §5-3）、SLUB 尺寸档、OOM 策略（Job 内 LRU 回收 vs 通知监督者，04 §5-5） | 预留池比例 ∈ [0, MAX_RESERVE]；OOM 策略枚举受限 | 03 / 04 |
| **IPC 参数** | Channel 消息上限、EventPort 阈值、cap-transfer 超时（05） | 消息尺寸 ≤ 编译期上限；超范围拒绝 | 05 |
| **可观测采样** | inspect 采样周期、事件流 ring buffer 大小、trace 类别开关（12 §4.1/§4.4） | buffer 上限封顶防内存耗尽 | 12 |
| **看门狗/超时** | 驱动看门狗超时（10 §4.2 RS 式自愈）、调度器抢占周期 | 超时下限防误杀、上限防挂死 | 10 |
| **启动/灰度** | 监督者重启退避策略、`.msys` 灰度切割比例（06 §4.3e） | 退避上限防震荡 | 06 / 09 |

**纪律（铁律）**：
1. **有界**：每个 tunable 有编译期确定的合法区间与枚举，写入即校验，越界拒绝（仿 pledge fail-closed，07 §4.5）。
2. **capability 守护**：写任一 tunable 子树需持有该子树的 `CFG_WRITE` right（见 §4），无隐式权限（00-A1）。
3. **可观测**：所有 tunable 同时是 inspect 可读节点（`DBG_INSPECT`，12 §4.2），读受 right 约束。
4. **可回滚**：tunable 变更经 `.msys` 子树级 CoW 快照（06 §4.3）或 per-Job 配置版本提交，可命名空间级原子回退。
5. **不可质变性**：tunable **绝不**能（a）关闭 capability 检查、（b）扩大 TCB、（c）降级安全模型——这些只在编译期固定（呼应 15 D1「无全局关沙箱」）。

### 3.3 第三支：可观测性驱动的自动调优（observability-driven auto-tuning）

> 这是「配置」与「可观测性（12）」的交汇点，也是 MeuOS 相对 Linux sysctl「人工拍脑袋调」的结构性机会。

- **反馈环**：inspect 树（12 §4.1）持续暴露调度/内存/IPC/IO 指标 → 监督者（meu-supervisor，04 §4.5）或专门 autoscaler 服务读指标 → 在**有界 tunable 区间内**微调（如 Job 内存上限、调度权重、看门狗超时）→ 效果回流 inspect。
- **边界**：自动调优**只能动运行期 tunable**，且受同一 `CFG_WRITE` right 与有界校验约束；它**不**能引入新 feature、不**能**触碰安全不变量。即自动调优是「在编译期划定的能力圈内跑多猛」的闭环，不是「自作主张扩权」。
- **可审计**：每次自动调优动作落结构化事件流（12 §4.4，schema 自描述），可被 `DBG_TRACE` 订阅复盘——把 Linux sysctl 的「黑盒手调」变成「白盒可观测闭环」。

## 4. capability 化配置通道

> 本节回答「谁有权改哪个 tunable、恶意/错误配置会不会扩大 TCB 或降级安全」。这是配置维度对 15 D1「无全局关沙箱」的同构延伸。

### 4.1 配置即 capability 对象

把 Linux 的「root 即改 sysctl」翻译为 MeuOS 的 capability 原语（对齐 12 §4.2「调试即 capability」的哲学）：

| MeuOS config right | 含义 | 对应 Linux 概念（仅映射语义，不平移权限） |
|--------------------|------|-------------------------------------------|
| `CFG_READ` | 读 `kernel/config/` 子树（受子树粒度约束） | 读 `/proc/sys` |
| `CFG_WRITE` | 写某 tunable 子树（受 `config_version` + 有界校验） | 写 `/proc/sys`（但**有界、非全局**） |
| `CFG_GRANT` | 向其他 Job 授予某子树的 `CFG_*` right（受约束 mint，07 §4.5） | —（Linux 无等价，sysctl 是 root 全局） |

- 这些 right 挂载在**配置子树 handle** 上（如 `kernel/config/scheduler`、`jobs/<id>/config`），由持 `CFG_GRANT` 的对端（监督者/系统服务）显式授予。
- **默认拒绝**：spawn 出的进程不持任何 `CFG_*` right（仿 12 §4.2 调试默认拒绝）；要改配置必须从监督者/系统侧显式获授权。
- **无「配置 root」**：不存在 uid=0 式全局配置权；即便 meu-supervisor 也只持所需子树 right 子集。

### 4.2 恶意/错误配置不能扩大 TCB 或降级安全（核心不变量）

配置通道的三道闸，与 15 D1 的「三道封顶闸」同源：

1. **来源闸**：`CFG_WRITE` 只能由持 `CFG_GRANT` 的对端显式授予，运行期用户**不能**自赋配置权（无「关沙箱」式自升级 API）。
2. **有界闸**：每个 tunable 写即校验合法区间/枚举；越界拒绝（fail-closed，07 §4.5）。**安全关键不变量（capability 检查、panic=abort、无调试 root）根本不出现在 tunable 集合里**——它们只在编译期 feature 中恒编入、运行期不可见不可改。
3. **账本闸**：每次 tunable 变更记入该 Job 资源账本（04 §4.4 维度 B）+ 结构化事件流（12 §4.4），可审计、可撤销（经 `.msys` 回滚，06/23）。

**由此保证**：恶意/错误配置最坏导致「性能退化、OOM、死锁倾向」——绝**不**导致「TCB 扩大、capability 模型被绕过、沙箱被关」。这正是 15 D1「兼容层不击穿 Day1 安全边界」在配置维度的延伸：**tunable 是模型内的量变旋钮，不是模型外的特权后门**。

### 4.3 编译期 feature 的「配置权」

编译期 feature 本身**不由运行期 capability 守护**（因为它在镜像发布时已固化）——它的「配置权」在**构建/发布期**：由构建系统 + `.msys` 签名链（06 §4.1、23 §5）保证「哪些 feature 编入」是可审计、可回滚的。运行期只消费、不可改。这与 seL4「编译期证明配置」立场一致：安全关键面在编译期即确定，运行期无对应开关。

## 5. 与 02/03/04/09/12/23 的接口

> 本节只声明接口契约，不替各子文档下其内部结论。

### 5.1 与 02-内核语言策略（feature 与 Rust/C 划分）

- **feature ↔ TCB 绑定**：02 §4.2 的组件划分矩阵（哪些 Rust 入 TCB、哪些 C 出核）应映射到编译期 feature——「某服务是否编入」直接决定该语言组件的编译 inclusion，故 feature 清单是 02 语言边界的**编译期投影**。
- **i386 纯 C 段裁剪**：02 C2 / 15 C6 已定「i386 非降级架构、TCB 以 Rust `.o` 链接交付」。编译期 feature 须显式记录「i386 上本组件以 `.o` 交付 vs 纯 C 退路（O3 仅兜底）」，使五架构构建矩阵可追溯（01 §5-6）。
- **调试构建档**：02 §4.5 `panic=abort` 是编译期固定不变量；12 §7-3 调试/发布符号表差异也是编译期 feature——二者在配置模型里同属「不可运行期改」的恒编入项。

### 5.2 与 03-内存管理（分配器参数）

- **分配器 tunable 边界**：03 §5-3（大页预留池）、§5-4（Rust GlobalAlloc 与 SLUB 关系、OOM 策略）、§5-7（验证范围）给出运行期可调点——buddy 预留池比例、SLUB 尺寸档、OOM 回收策略（Job 内 LRU vs 通知监督者）进 **tunable 层**，受有界校验。
- **不可调点**：物理内存归属（C1 折中：内核 buddy 拥有）、VMO/VMAR 抽象（03 §4.4，capability 视图）属**架构固定**，不进 tunable。
- **接口形态**：`kernel/config/mm/{buddy_reserve, slab_sizes, oom_policy}` 为 inspect 可写子树，写受 `CFG_WRITE` + 区间校验。

### 5.3 与 04-进程与调度（调度参数）

- **调度 tunable 边界**：04 §4.3（EEVDF 权重/RT 优先级天花板）、§4.4（资源账本阈值）给出运行期可调点——公平权重、RR 时间片、RT 优先级上限、Job 级 CPU/内存/句柄/IO 配额进 **tunable 层**。
- **不可调点**：调度类钩子结构（enqueue/pick_next）、EEVDF vs RR 选型（04 §5-1）属**编译期算法选型**；RT 线程创建所需 capability（防饿死）属**安全不变量**，运行期不可放宽。
- **与资源账本同源**：tunable 写的配额不得超过父 Job 投影（15 D2 同构），写入即记 Job 账本（04 §4.4）。

### 5.4 与 09-启动与初始化（boot 期配置）

- **boot 期读配置**：09 §5.2 Stage 0–2 解析 `bootinfo`（DT/ACPI/multiboot）。`bootinfo` 是配置的第一入口——携带**初始 feature 使能状态 + 初始 tunable 默认值 + 根 Job manifest**（含初始 capability 集、09 §5.4）。
- **层级归口**：bootinfo 给「系统默认」→ `.msys` manifest（06 §4.1）给「发布覆盖」→ per-Job/per-service 给「运行时投影」。三层叠加（呼应 Android 资源叠加，§2），但**不改变**「feature 编译期固化、tunable 运行期有界」的二分。
- **交接**：Stage 4 capability 世界激活后，配置子树随根 Job 自举为 inspect 可写节点；bootinfo 的初始 tunable 成为该子树的初值。

### 5.5 与 12-调试与可观测性（配置 = inspect 可写子树）

- **配置即 inspect 子树**：12 §4.4 的 inspect 树「替代 `/proc+/sys` 文本」——本文把 `kernel/config/` 直接定为 inspect 的**可写子树**（读 `DBG_INSPECT`、写 `CFG_WRITE`），实现「配置面 = 可观测面」统一。
- **自动调优反馈环**：12 §4.1 指标 + §4.4 事件流是 §3.3 自动调优的反馈源；每次自动调优落结构化事件（12 §4.4 schema），可被 `DBG_TRACE` 复盘。
- **权限模型协同**：12 §4.2 的 `DBG_*` rights 与本文 `CFG_*` rights 同为「句柄即 capability、默认拒绝」（00-A12），共享 07 的授权/撤销机制。

### 5.6 与 23-ABI稳定性与版本（配置接口是否版本化）

- **配置 schema 版本化**：23 §2 ③ 主张用户态服务间 IPC 协议靠版本协商稳。本文的 tunable schema 自带 `config_version`，与 23 §6 协议版本协商同源——配置接口变更走 `min_compatible_version` 协商，避免老客户端写新 schema 崩溃。
- **`.msys` 回滚杠杆**：23 §5 的「`.msys` 同版本升级让内部柔性可行」直接覆盖配置——一次配置发布 = `.msys` 子树级 CoW 快照 + 命名空间 repoint（06 §4.3），**天然可灰度、可回滚**。这是 MeuOS 相对 Linux sysctl（改了无回滚）的根本杠杆。
- **feature 与 ABI**：编译期 feature 改变能力集，可能改变原生 API 表面（23 §2 ② 原生 API 演进期不稳）；但 feature 变更经 `.msys` 整卷同变（23 §5.1），不破坏对外兼容 ABI（23 §2 ①）。配置模型不引入新的 ABI 稳定承诺，仅复用 23 三层分级。

## 6. 反模式（明确不做什么）

| 反模式 | 表现 | MeuOS 对应规避 |
|--------|------|----------------|
| **sysctl 膨胀** | 散落全局可变内核参数、无 schema/无版本/无回滚、语义重叠、无人敢删（Linux 教训，§2 膨胀列） | 两层分离 + tunable 强类型 schema + `config_version` + `.msys` 回滚；不建全局可变参数表 |
| **运行期关沙箱** | 提供开关一键关闭 capability 检查 / pledge / unveil（Linux `setuid`/cap bounding set 反面教材） | **禁止**：安全关键不变量只在编译期 feature 恒编入、运行期不可见不可改；呼应 15 D1 已采纳裁决「无全局关沙箱」 |
| **注册表式全局可变** | Windows 注册表成为「万能可变状态黑洞」、权限模糊 | 不借：配置走 capability 守护的 inspect 子树，无隐式全局写权 |
| **feature 与 tunable 混置** | Linux 把「结构性开关」与「量变旋钮」割裂在 Kconfig/sysctl 两套无关联模型 | 显式二分：结构性/安全/架构 → 编译期；量变 → 运行期；二者经 `.msys` + inspect 统一可见 |
| **配置不可观测** | sysctl 改了无记录、无回滚、出事难复盘 | 每次变更记 Job 账本 + 结构化事件流（12 §4.4），可被 `DBG_TRACE` 复盘；可经 `.msys` 回滚 |

## 7. 自主结论（非缝合怪总结）

1. **配置分两层，且彻底分离**：编译期 feature（能力集/TCB/五架构，重、不可逆）vs 运行期 tunable（量变旋钮，轻、可逆、有界）——前者进「重新编译+`.msys` 发布」、后者进「capability 守护的 inspect 可写子树」。
2. **运行期无全局可变内核参数**（Fuchsia 立场）：所有 tunable 是结构化、强类型、可版本化、有界校验的 inspect 子树，无 sysctl 式全局表。
3. **安全关键不变量不可运行期关闭**（seL4 立场 + 15 D1 同构）：capability 检查 / `panic=abort` / 无调试 root 只在编译期 feature 恒编入，运行期不可见不可改——恶意/错误配置最多性能退化，绝不扩大 TCB 或降级安全。
4. **配置即 capability 对象**：`CFG_READ/WRITE/GRANT` rights 挂载在配置子树 handle，默认拒绝、显式授予、无「配置 root」；与 12 `DBG_*` 同源。
5. **配置可观测、可回滚**：经 inspect（12）读、经 `.msys` 子树级 CoW 快照（06/23）回滚；自动调优在「有界 tunable + `CFG_WRITE`」闭环内跑，且全程落结构化事件流。
6. **i386 纯 C 段即编译期裁剪**：五架构差异（含 i386 的 Rust `.o` vs 纯 C 交付管线）由 feature 矩阵固化，使 TCB 边界在五架构间可审计、可追溯。

## 第四轮裁决回写（C16 已采纳）

> 来源：`31-第三轮收敛摘要.md` §3 将 30 的 §8 待决 1+2 列为候选 **C16**（建议升级总览 C 条目、架构级）；指挥官于第四轮查缺补漏**自主采纳** C16 两项结论，本文据以「修订式追加」回写，原架构级待决升级为「已采纳」。铁律：仅追加、不删改原章节。

### C16 采纳结论（两项均采纳）

**① 编译期固定安全关键参数清单——存在，且运行期不可见不可改。**

确实存在一份「必须编译期固定的安全关键参数清单」，其项在运行期**完全不可见、不可改写**——这不是 tunable，而是内核 build 契约（build contract）的一部分：

- capability 检查**强制编入、不可关**（07 Day 1 唯一模型地基）；
- `panic=abort`（内核核心 Rust，02 §4.5）——不可运行期切回 unwind；
- 无「调试 root」/无「配置 root」（12 §4.2、本文 §4.1）——不存在 uid=0 式特权逃生舱；
- pledge/unveil 默认 deny（07 §4.2、15 D1）——沙箱不可运行期关闭；
- 其余 Day 1 安全边界（无全局关沙箱、无隐式提权、execpromises 禁止 setuid 提权）。

**② `CFG_*` rights 并入 07 rights 位图——是，与 `DBG_*` 同构、互不重叠 bit。**

配置权体系以 capability 原语表达，并入 `07` 统一 rights 位图，建议 bit：`CFG_READ`=8 / `CFG_WRITE`=9 / `CFG_GRANT`=10（紧邻 `KEY_UNWRAP`/`KEY_WRAP`=bit 6/7 之后，与 `DBG_*`（建议置于更高位）互不重叠）。与 `12` 的 `DBG_*`、06 的 `KEY_*` 同源——句柄即 capability、默认拒绝、显式授予。具体位图定义与「编译期固定安全参数不可运行期改写」标注见 `07` 第四轮回写。

### 与原 §8 待决项的对应（升级为已采纳）

- §8 待决 1（是否存在必须编译期固定的安全关键参数清单、运行期完全不可见）：**已采纳**——清单如上，由 `07` 与本文 §3.1 / §4.2–§4.3 共同定稿，写入一份内核 build 契约文档供审计（呼应 seL4 编译期证明配置、15 D1「无全局关沙箱」在配置维度的同构延伸）。
