## 0. 与 27 的边界（本文定位）

`27-电源与热管理.md` 已从「机制层」给出了完整结论：**内核只暴露功耗/热原语 + 不可绕过的热硬限，DVFS/idle 偏向/设备断电/休眠等策略全部用户态 `powerd` 化**（Fuchsia powerman 范式）。那是「电源与热*怎么管硬件*」。

- `40` = **计量与协同面**（能耗怎么被*度量、被谁*读、如何*弱耦合*进 `Job` 账本与调度器、以什么*粒度*、受 capability 如何*守护*）。

## 1. 「能耗」应该由谁管理、以什么粒度（解构型推演）

### 1.1 还原到第一性原理

把「能耗」从「电源管理」中剥离，问三个原始问题：

1. **谁拥有「能耗这个数字」？** 能耗是硬件计数器（RAPL/AMU/PMU/SBI-PMU）的*读数*，物理上只能由内核从 MSR/系统寄存器读取——所以**内核拥有「原始读数」**，但**不拥有「能耗意味着什么」**（那是策略）。
2. **以什么粒度记账？** 可选粒度：每线程 / 每 `Job` / 每 CPU / 每 package / 每设备。粒度过细（每线程）会计语义跨架构不齐、开销大；粒度过粗（每 package）失去调度价值。
3. **调度器与 `Job` 账本如何协同？** 调度器（`04` EEVDF+RT）需要能耗作为*只读信号*来决定「铺满核还是聚核」；`Job` 账本（`04` §4.4）是资源与生命周期单元，能耗若要做约束必须同源。

### 1.2 推演结论（能耗的三层归属）

> **能耗 = 内核只读计数器（原语） + 用户态 `powerd` 聚合为策略信号 + 调度器据 `Job` 账本做 task packing（弱耦合，非硬配额）。**

- **内核**：把每 CPU/每 package/每设备的能耗计数器（RAPL/AMU/PMU/SBI-PMU）**只读**暴露为 capability 对象（`ENERGY_READ`，见 §7），不替用户态做能耗预算。
- **用户态 `powerd`**：聚合计数器 + `Job` 账本 CPU 配额（`04` §4.4）+ 电池/AC 状态，产出「能耗感知调度提示」（同 `Job` 聚核、空闲核深 idle），作为调度器的*输入*，而非*约束*。
- **调度器**：在 `04` §4.3 的 `sched_class` 中读能耗/热/频点信号，做 **task packing**（弱耦合）；**不**把能耗写入 `Job` 账本（强耦合留待 `04` §5 议题 6 裁决）。

### 1.3 为什么「弱耦合」是原型期正确解构

解构后可见：把能耗当**硬配额**（第六类账本资源）会在原型期过早锁定一套**跨架构不齐**的会计语义（x86_64 RAPL 完整、aarch64 AMU/PMU、riscv64 SBI-PMU、loongarch64/i386 未标准化），并迫使 `04` 账本对象与检查点复杂化。而「*只读信号 + task packing*」只需 `powerd` 读既有 CPU 配额即可落地，不阻塞 `27` 的电源管理推进——这正是第四轮「能耗-Job 原型期弱耦合」已采纳结论（`00` §3 / `27` §第四轮裁决回写）的题中之义。

## 2. 多系统参照对比（聚焦「能耗计量与调度协同」）

下表对比各系统在**能耗由谁读、是否进资源账本、如何与调度协同、策略在哪**四个维度（与 `27` §2 的「机制」表正交）。

| 维度 | Linux | Windows | macOS (XNU) | Fuchsia | Android | ChromeOS |
|------|-------|---------|-------------|---------|---------|----------|
| **能耗读数来源** | Intel RAPL（MSR）/ powercap；PMU 计数；bpf 统计 | E3/LPM 计数；平台 MSR | 内部计数器（SMC/PMU） | 内核暴露 energy capability，用户态读 | RAPL/bpf `batterystats`；`energy_model` | 用户态读取 |
| **能耗是否进资源账本** | **否**——cgroups 未把能耗当一等账本（仅有 CPU/内存配额） | 否——PoFx 管设备电源状态，无能耗硬配额 | 否——App Nap 是行为策略非配额 | 否——activity governor 是「活动→电源档」映射，非能耗配额 | 否——Doze/App Standby 是限制策略，非能耗硬账本 | 否——`powerd` 策略，无硬配额 |
| **与调度器协同（EAS）** | **schedutil**（调度器驱动 DVFS，用 CFS `util_avg`/PELT）+ Energy Model（EM）→ EAS 选频省电；`NOHZ` tickless 配合深 idle | 内核协同 PM（PoFx 设备电源状态机），调度器不直接做能耗感知选频 | IOPP / Intel Speed Shift 硬件自治选频；App Nap 内核降低低活进程功耗 | **activity governor + system power manager**：组件活动等级→系统/设备电源等级，经 `fuchsia.power` 协调 | Power HAL 选频 + schedutil；Doze 限制后台唤醒 | 用户态 `powerd` 驱动 cpufreq + 内核 idle |
| **tickless / 深 idle** | `NOHZ` 动态 tick（dyntick-idle / full `NOHZ`）让 CPU 进深 C-state | 现代待机 S0ix（connected standby）下 tick 收敛 | dark wake / Power Nap（低功耗后台） | 组件 inactivity → 系统降档，idle 由内核执行 | 深度 Doze 暂停前台外所有 | `powerd` 决策 suspend-to-idle |
| **策略放哪** | governor 在核内（schedutil/ondemand）+ thermald 用户态补；**策略分裂**（部分核内） | PoFx 内核框架 + 用户态 GUID 电源策略 | 内核 IOPMrootDomain + 用户态 `powermanagementd` | **完全用户态**（power broker / system power manager / activity governor） | 内核 + Power HAL（用户态 HIDL/AIDL）+ Doze | **用户态 `powerd` 主导** |
| **可取** | schedutil 与调度器同址、零额外 IPC；EM 让 EAS 有据可依；`NOHZ` 释放 idle | PoFx 设备电源状态机清晰、ACPI/Modern Standby 标准化 | Speed Shift 硬件自治选频、对用户态友好低功耗态 | **activity governor 把「组件活跃度」直接映射为电源档**——能耗协同的现代化范本 | Doze/App Standby 省电模型 + bpf 统计可观测 | 电源管理用户态化范本 |
| **不可取（避免缝合）** | cgroups 不把能耗当账本；governor 留核膨胀 TCB | 重服务留核、TCB 大 | IOKit 驱动留核无隔离 | 每 syscall IPC 代价高（MeuOS 以 mkit 薄层规避） | HAL 语义分散、碎片化 | 仅 Chrome 场景 |

**关键观察（非缝合怪提炼）**：
- **能耗从不当「硬配额」**——六大系统无一将能耗作为 cgroup/账本式的强制上限；它们用「策略 + 信号 + 活动映射」而非「能耗计费」。
- **调度器同址是省 IPC 的关键**——Linux schedutil、Fuchsia activity governor、ChromeOS powerd 都把能耗决策放在「离调度器/内核最近」处，而非每次决策走 IPC。MeuOS 借 `mkit` 薄层（`00` A10）天然规避「每 syscall IPC」代价，能耗信号应以**只读内核结构**直接喂给调度器（`04` `sched_class`），不进热路径 IPC。
- **活动→电源档映射**是 Fuchsia 对「能耗协同」最现代化的表述：把「组件是否活跃」作为电源状态的一等输入。MeuOS 的等价物是「`Job` 是否活跃 / `Job` 的 CPU 配额余量」→ 聚核/idle 决策。

## 3. 设计原则（解构型）

1. **内核只给读数 + 不可绕过热硬限，策略全用户态**：能耗计数器（`ENERGY_READ`）只读暴露；选频/idle 偏向/聚核决策在 `powerd`（`27` §3.3）。与「重服务出核缩 TCB」（`00` 方向③）一致。
2. **能耗是「信号」不是「配额」（原型期）**：与第四轮「能耗-Job 弱耦合」采纳结论一致——能耗只读、只做 task packing 输入，不写 `Job` 账本、不做硬上限/计费。
3. **与 `Job` 账本同源（A5）**：能耗协同**复用** `04` §4.4 的 CPU 配额作为 task packing 约束源，不另立一套账本；避免双账本不一致。
4. **capability 守护所有写权，读权默认 deny 但轻量可授**：改频/休眠/设备断电须 `POWER_POLICY`/`DEVICE_POWER`（`07` 同构）；能耗/热读须 `ENERGY_READ`/`THERMAL_READ`（`12` 可观测性消费）。热硬限**不是 capability**（内核 TCB，不可 mint/revoke）。
5. **跨架构归一 + 每架构薄后端**：RAPL/AMU/PMU/SBI-PMU 统一为「每核/每 package/每设备 能耗读数」capability 对象（`27` §6 收敛原则）。
6. **EAS 与调度器同址、热路径零 IPC**：能耗/频点/热余量以只读内核结构（`cpu_power_state`）喂给 `04` `sched_class` 的能耗感知子策略；选频*决策*仍归 `powerd`，调度器只做聚核/偏向，避免每 tick IPC（`27` §5.1）。
7. **tickless 是深 idle 的前提**：`NOHZ` 式动态 tick 与 `04` 调度器协同，空闲核才能真正进深 C-state（呼应 Linux `NOHZ` + Fuchsia inactivity 降档）。

## 4. 与 Job 账本（04）的弱耦合协同

> 本节为第四轮「能耗-Job 原型期弱耦合」采纳结论在能耗维度的**落地细化**（呼应 `00` §3 冲突表 `能耗-Job` 行、`04` §4.4 补注、`27` §第四轮裁决回写）。

### 4.1 弱耦合契约（原型期生效）

- **能耗不进账本**：`Job` 账本（`04` §4.4）既有资源种类——CPU 时间 / 内存 / 句柄数 / IO 带宽 / 进程线程数——**保持不变**，能耗**不**作为第六类硬配额（不强制上限、不计入费）。
- **能耗作 task packing 输入**：用户态 `powerd`（`27` §3.3）读某 `Job` 的 **CPU 配额余量**，将**同一 `Job` 内的任务聚到少数核**，释放的空闲核进深 idle（power clustering）；频点选择仍由 `powerd` 全局决定（schedutil 式）。
- **调度器 EAS 子策略只读不写**：`04` §4.3 `sched_class` 的能耗感知子策略在弱耦合下仅做聚核/偏向，不触碰 `Job` 账本写入（`27` §5.1）。

### 4.2 数据流（原型期）

```
[内核] ENERGY_READ 计数器 ──只读──┐
[内核] cpu_power_state(当前频档/thermal headroom) ──只读──┤
[04] Job 账本 CPU 配额 ───────────────────────────────┤
                                                       ▼
                                    powerd (用户态, 持 POWER_POLICY)
                                      聚合 → 产出「聚核提示」
                                                       │
                                                       ▼
                              [04] 调度器 sched_class EAS 子策略 (task packing)
                                      同 Job 任务聚核 / 空闲核深 idle
```

### 4.3 强耦合的升级条件（留待 04 §5 议题 6）

把能耗升级为**硬配额**（超限则限流该 `Job` 的 CPU 功率或降其权重）须等 `04` §5 议题 6（NUMA / 异构核 big.LITTLE EAS）裁决——因为强耦合的语义（「能耗预算」如何与「小核省电/大核性能」的异构调度偏置交互）只有在异构核 EAS 定稿后才能定义清楚。届时再扩展 `04` §4.4 账本对象与检查点。

## 5. idle 与睿频向调度器的暴露接口

### 5.1 暴露什么（只读内核结构）

调度器（`04`）热路径需要**零 IPC** 地读到以下信号，统一经一个只读结构 `cpu_power_state`（每 CPU 一份，内核维护）：

| 字段 | 来源 | 调度器用途 |
|------|------|-----------|
| `cur_freq_bin` | P-state/OPP 当前档（`27` §3.2） | EAS 估算当前功耗/性能档 |
| `avail_idle_depth` | C-state 表 + `powerd` 设的最大 idle 偏向（`27` §4.1） | 判断能否进深 idle |
| `thermal_headroom` | thermal zone 余量（`27` §3.2，只读） | 热压下加速聚核/降频 |
| `pkg_energy_rate` | `ENERGY_READ` 派生（滑动平均） | task packing 的收益估算 |

> **选频决策仍归 `powerd`**：调度器**只读** `cur_freq_bin`，**不**自己选频；它只据读到的信号做「聚核 / 让出空闲核」的布局决策。这与 Linux schedutil（调度器算 `util_avg`→提示 governor 选频）同构，但 MeuOS 把「选频」收敛到 `powerd` 单一策略点，避免 governor 留核（`27` §1.2）。

### 5.2 调度器如何消费（sched_class 钩子）

- 在 `04` §4.3 的 `enqueue_task`/`pick_next_task` 中读 `cpu_power_state`：若某 `Job` 有任务在多核散开且 `thermal_headroom` 偏低 → 触发**同 Job 聚核**（migrate 到已运行该 Job 任务的核）。
- 在 `task_tick` 检测：若某核上无 RT/EEVDF 紧急任务且 `avail_idle_depth>0` → 标记可深 idle，`NOHZ` 收敛 tick（§3.7）。
- **不放纵 IPC**：以上消费全部走内核内只读结构，绝不在调度热路径发起 IPC 到 `powerd`（规避 Fuchsia 每 syscall IPC 代价，`27` §2 注）。

### 5.3 与 tickless（NOHZ）协同

深 C-state 的前提是 CPU 不再被周期 tick 唤醒。`04` 调度器在「该核可深 idle」判定后，启用 `NOHZ` 式动态 tick（参照 Linux `NOHZ` + Fuchsia inactivity 降档）；`powerd` 的 idle 偏向（最大允许 idle 深度）作为 `avail_idle_depth` 的上界。tickless 关闭点 = `arch_boot → kernel_main()` 之后的首次空闲（`09`）。

## 6. thermal 节流的安全边界

> 本节仅从「能耗维度」点明不变量，完整机制见 `27` §4.2（不可绕过热硬限）。

- **热硬限是内核 TCB 内的 fail-closed 边界**：critical thermal trip 无条件触发（passive 节流→critical 关断），映射 RAPL PL MSR / EC / 平台 watchdog（`27` §4.2）。**任何用户态（含 `powerd`、含被攻破服务）不可禁用或抬高 critical trip**——等价于 `07` 的 fail-closed。
- **能耗协同不得突破热硬限（不变量）**：无论弱/强耦合，thermal 硬限始终为内核无条件边界（`27` §第四轮裁决回写「不变量」）。即使强耦合下某 `Job` 能耗配额被放宽，内核热硬限仍优先于任何 `Job` 约束。
- **passive 节流是软策略**：降频档/聚核提示可由 `powerd` 设置，属用户态 `POWER_POLICY` 软权，受硬限压制（`27` §4.3 软权 vs 硬限分界表）。

## 7. 与 capability 模型（07）的兼容

### 7.1 电源相关 right 提议（默认 deny，与既有同构）

电源/能耗策略是否受 capability 守护？**是**——与 `07`「无 root 逃生舱」一致，所有*写*电源状态的能力都是可撤销、可审计的受限 right，而非特权：

| right（提议） | 类别 | 默认 | 说明 |
|------|------|------|------|
| `POWER_POLICY` | 电源策略（软权） | deny | 设全局 DVFS/idle 偏向、决策休眠（`powerd` 持有）；**非 root**，不授予绕过热硬限或修改他 `Job` 资源的能力（`27` §4.1） |
| `THERMAL_READ` | 热读数（只读） | deny（可观测性可授） | 读 thermal zone 温度（`12` 消费） |
| `ENERGY_READ` | 能耗读数（只读） | deny（可观测性可授） | 读 RAPL/AMU/PMU/SBI-PMU 计数器（`12` 消费） |
| `DEVICE_POWER` | 设备电源（派生自 10） | 随设备能力 | 用户态驱动对其*自有设备*请求 D-state 切换（`27` §4.1 / §5.3） |

- **位分配**：提议顺延至 `38` §3 统一 rights 位分配建议表之 `BLOCK_*` 之后，与 `KEY_*`/`CFG_*`/`DBG_*`/`AUDIO_*`/`BLOCK_*` 同构、默认 deny（`POWER_POLICY` 为可撤销软权、`THERMAL_READ`/`ENERGY_READ` 为只读、热硬限*不*占 bit——它是内核 TCB 非 capability 对象）。**本表为建议，待 `07` 回写冻结 bit。**
- **热硬限不是 capability**：critical trip 的强制逻辑（`27` §4.2）是内核 TCB 的一部分，不可 mint、不可 revoke、不可提权——不属于 rights 位图。
- **内核态应急写**：若某架构需内核在紧急热压下直写 MSR/EC（不可交用户态），该操作归入 `29` D-T1 已采纳的 `KERNEL_PRIV`（`38` §3 bit 12，绝不默认、仅内核自持）——与「无 root 逃生舱」不冲突，因 `KERNEL_PRIV` 本身受 `Job` 账本约束且可审计。

## 8. 跨五架构差异处理（能耗计量视角）

复用 `27` §6 的「统一原语 + 每架构薄后端」收敛原则，从**能耗计量粒度**补充：

| 架构 | 能耗计数器可用性 | 原型期能耗会计取值 |
|------|------------------|--------------------|
| **x86_64** | Intel **RAPL**（MSR 0x611/0x639 等）最完整，每 package/每核/每设备 | 一等公民：完整 `ENERGY_READ` |
| **aarch64** | **AMU**（Activity Monitors Unit）能耗近似 + **PMUv3**；big.LITTLE 多簇 | AMU/PMU 近似；**异构核 EAS 刚需**（`04` §5 议题 6），能耗协同价值最高 |
| **riscv64** | **SBI PMU** 扩展计数；平台碎片化、标准化最低 | SBI 抽象屏蔽差异；原型期仅 QEMU/virt 最小计数 |
| **loongarch64** | 平台 thermal sensor；能量计数接口未标准化 | 基础热读 + 近似能耗；原型期不追求精确计量 |
| **i386** | 无 RAPL、无现代能耗计数；仅 ACPI thermal | **最小**：仅热读 + idle（HLT），能耗会计基本放弃 |

**收敛原则**：五架构统一暴露为「每核/每 package/每设备 能耗读数」capability 对象（`ENERGY_READ`），底层后端差异对 `powerd`/`12` 透明；原型期允许「计数缺失」的架构以 `thermal_headroom` + 频档估算替代精确能耗（不阻塞 task packing）。

## 9. Day 1 最小集

### 9.1 内核态机制（最小）

- 启动期（09 Stage 2）**一并抽出**电源/热拓扑：P-state/OPP 表、C-state 表、thermal zone/trip、能耗计数器能力（`27` §5.2）。
- 能力自举（09 Stage 4）：向 `powerd` 签发 `POWER_POLICY`，向观测服务（`12`）签发 `THERMAL_READ`/`ENERGY_READ`（`27` §5.2）。
- **热硬限尽早生效**：critical trip 强制逻辑在 `powerd` 启动前即激活（内核默认保守档 + 硬件 PL），`powerd` 崩溃期间系统不过热（`27` §4.2 / §5.2）。
- 暴露只读 `cpu_power_state` 给调度器（`04` `sched_class`），本地执行 idle、应用 `powerd` 选定频档（`27` §3.2）。
- 基础 `NOHZ` tickless，使空闲核可进深 idle（§5.3）。

### 9.2 用户态策略（最小 `powerd`）

- 保守默认（boot 安全档），读 `Job` CPU 配额做 **task packing**（同 `Job` 聚核、空闲核深 idle）。
- schedutil 式全局选频 + idle 偏向设置（持 `POWER_POLICY`）。
- 聚合 `THERMAL_READ`/`ENERGY_READ` 供 `12` 观测；thermal 压力下向调度器下发聚核提示。

### 9.3 明确**不在** Day 1

- ❌ 能耗硬配额（第六类账本资源）——留待 `04` §5 议题 6 裁决（§4.3）。
- ❌ suspend-to-RAM / hibernate（休眠原语执行可留接口，策略 Day 1 不做）。
- ❌ 每设备精细能耗账本（GPU/NIC 经 device VMO 的能耗，`33`/`34` 演进期）。
- ❌ 场景策略（笔记本/手机/服务器分支）——Day 1 单一保守策略。

### 9.4 capability 最小集

`POWER_POLICY`（`powerd`）、`THERMAL_READ`/`ENERGY_READ`（观测服务 `12`）、`DEVICE_POWER`（用户态驱动，派生自 `10`）。全部默认 deny，与 `07` 同构。

## 10. 演进路线

| 阶段 | 范围 | 与本文/他文协同 |
|------|------|----------------|
| **A（原型·弱耦合）** | 只读能耗/热计数器 + `cpu_power_state` + task packing（据 `Job` CPU 配额）+ 热硬限 + 基础频/idle/tickless | `27` 控制面 + `04` `sched_class` + `12` 观测；第四轮「能耗-Job 弱耦合」落地 |
| **B（异构核 EAS）** | `04` §5 议题 6 定稿后：big.LITTLE 能效偏置；**强耦合选项**开放（能耗硬配额作第六类账本资源，超限限流/降权重） | 扩展 `04` §4.4 账本对象与检查点；仍受 thermal 硬限压制（§6 不变量） |
| **C（完整策略）** | `powerd` 场景策略（笔记本/手机/服务器）；suspend-to-RAM + 设备断电编排（`DEVICE_POWER`）；Fuchsia 式 **activity governor / system power manager** 等价物（组件/`Job` 活跃度→电源档） | 对齐 `27` §3.3 策略层 + `10` 设备电源 + Fuchsia 活动治理范式（§2 关键观察） |
| **D（精细账本）** | 每设备能耗账本（GPU/NIC 经 device VMO，`33`/`34`）；跨架构归一 `EnergyCounter`；可选能耗感知调度类（EDF+energy） | 跨架构薄后端（`27` §6 / §8）+ `12` PMU capability 暴露（`00` §5.9） |

> 推荐方案一句话：原型期**能耗只读 + 与 `Job` CPU 配额弱耦合做 task packing + 内核强制热硬限**，随 `04` 异构核 EAS 裁决再决定是否升级强耦合；策略全用户态 `powerd`、所有写权受 capability 守护——务实、现代化、不与 `27` 缝合。
