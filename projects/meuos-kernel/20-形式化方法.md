# 20 - 形式化方法（Formal Methods for MeuOS Kernel）

> 子领域：MeuOS 自研内核的**形式化方法分层策略**——在「自研工具链（mcc + QBE）+ Rust/C 混合 + 资源有限」的现实下，推演"形式化方法**应该是什么样**"，并给出可落地的分层验证路线。
> 团队：`kernel-plan`（指挥官—调研员模式）；调研员：`k-fm`（general-purpose-12，lite / hy3）。
> 配套文档：`00-总览与路线图.md`、`01-内核架构选型.md`、`02-内核语言策略.md`、`05-IPC机制.md`、`07-安全模型.md`；分工边界声明见 `12-调试与可观测性.md`、`19-性能与可验证性.md`（待定稿）。
>
> **方法论铁律贯穿**：解构型思维（先推演"应该是什么样"，而非照搬 seL4 全量证明）、多系统参照、非缝合怪（思想取长补短、实现自主研究）、修订式追加不删。

## 1. 概述与目标

### 1.1 为什么需要一份独立的"形式化方法"规划

形式化方法（Formal Methods）常被误解为"像 seL4 那样把整个内核用 Isabelle/HOL 证明一遍"。对 MeuOS 而言，这种误解是危险的：

- MeuOS 是**自研工具链驱动**的 OS（`mcc` + QBE 后端 + rustc/LLVM 双工具链），**不能假设有成熟的 CompCert/Coq 生态直接可用**（见 `02` §2.2 约束 C1、§2.3 约束 C2）。
- 内核是**务实混合内核（lean hybrid）**，TCB 以 Rust 关键组件为主、C/asm 底层为辅（`01` §4.2、`02` §4.2），且 i386 全程纯 C（`02` C2）。
- 项目**资源有限、设计仍在演进**，全量证明的投入产出比（ROI）极低。

因此本文的任务不是"规划一次 seL4 式证明"，而是**解构型地推演**：在一个自研工具链、Rust+C 混合、资源有限的独立项目里，形式化方法**应该验证什么、验证到什么程度、投入产出比在哪**——把有限的验证预算精准投到"一击致命"的位置（capability 监视器是 Day 1 唯一裁决点，`07` §4.1/`00` A3）。

### 1.2 目标

1. 给出 MeuOS 自己的**分层验证策略**：哪一层用完全形式化证明、哪一层用模型检验/TLA+、哪一层靠 Rust 类型系统 + 禁 unsafe 白名单、哪一层只靠测试。
2. 对核心安全不变量给出**可被机器检查的命题草案**（rights 只减不增、revoke 后派生链全断、Job 账本不可超额、无凭空产生 capability 等）。
3. 厘清**与自研工具链的信任鸿沟**（mcc/QBE、rustc/LLVM 均未验证），给出 translation validation / 差分测试的兜底思路。
4. 给出**分阶段路线**（原型期做什么、M3 后做什么），并明确"我们不做 seL4 全量证明"的理由。

### 1.3 范围之外

- 不替代 `03`（MM 不变量）、`04`（调度/账本）、`06`（FS）、`12`（观测）、`19`（性能）各自的结论；仅声明依赖与边界（见 §9）。
- 不替 `07` 拍板 rights 位图精确集合、derivation tree 全量与否（见 §7 待决 D5/D6）。
- 不修改任何 `00`–`12` / README / git / `.issues/`。

## 2. ① "应该是什么样"——解构型推演

> 本节先抛开"别人怎么做"，从 MeuOS 自身约束出发推演形式化方法的应有形态。

### 2.1 起点约束（来自已对齐的地基）

| 约束 | 来源 | 对形式化方法的含义 |
|---|---|---|
| capability 监视器是**唯一裁决点**，且是 TCB 核心 | `00` A3、`01` §4.2、`07` §4.4 | 验证预算应**单点聚焦**于此；此处一个 bug = 全局特权失效 |
| 关键组件用 **Rust**，内存安全类缺陷编译期消除 | `02` §4.1–§4.7、`00` A3 | Rust 类型系统是"免费"的验证层，可把 seL4 花在 C 内存安全上的证明工作量挪走 |
| i386 **全程纯 C**，无 Rust 裸机 target | `02` C2、`00` C6 | i386 的 TCB 拿不到 Rust 类型保护，是验证降级区（见 §5.3） |
| 双工具链：Rust=rustc/LLVM，C=mcc/QBE，均**未验证** | `02` §2.2 | "证明到源码级"与"信任编译器"之间存在不可闭合的鸿沟（见 §5） |
| 设计仍在演进，里程碑 M0–M6 滚动 | `00` §4.2 | 形式化目标必须**可渐进投入**，不能在 M3 前就锁定一个会随设计变动的庞大证明 |
| 最小 TCB + 尽快交权用户态 | `00` A6、`01` §4.2 | 用户态服务排除出 TCB，只靠测试/fuzz；内核态验证范围被天然收窄 |

### 2.2 推演结论：MeuOS 形式化方法"应该"长这样

1. **不追求端到端全量证明，只追求"关键不变量可被检查"**。端到端证明的代价（seL4 ~20 人年）对独立项目不可承受，但"capability 核心那一小撮不变量可被机器检查"代价可控、收益极高——因为它恰好是系统权限的 Single Point of Failure。
2. **用 Rust 类型系统吃掉内存安全，把"人证"留给逻辑不变量**。seL4 用 C 写、必须证明无 UAF/溢出；MeuOS 用 Rust，这类缺陷在编译期消失，剩余需形式化处理的只是"权限语义"而非"内存安全"。这是 MeuOS 相对 seL4 的最大杠杆。
3. **协议层用模型检验（TLA+），代码层用类型 + 测试**。IPC rendezvous、revoke 时序、监督者重启状态机这类"并发/时序"问题，用 TLA+ 在写代码前就穷尽状态空间；单点算法（rights 检查、revoke 树）才值得上证明器。
4. **接受"算法证明 ≠ 二进制证明"的诚实姿态**。在 mcc/QBE、rustc/LLVM 未验证的前提下，声称"证明了内核二进制"是伪命题；我们证明的是**参考模型/源码算法**，并用差分测试兜底编译器鸿沟。
5. **验证手段必须零/低运行期开销**。形式化是手段不是目的，任何引入运行期开销的验证（如运行时定理检查）都与 `19-性能与可验证性`（待定稿）冲突——本文据此将其排除。

## 3. ② 多系统参照对比表（含投入成本）

> 成本列为**数量级/公开报道**，仅供 ROI 比较，非精确报价；seL4 的 ~20 人年为学界与工业界广泛引用的估计（含 C 源到规约的精化证明工程）。

| 系统 | 验证手法 | 验证到什么 | 投入成本（量级） | 对 MeuOS 的可借鉴点 | 与 MeuOS 现实的冲突 |
|---|---|---|---|---|---|
| **seL4** | Isabelle/HOL 端到端精化证明（抽象规约→C 实现）+ 信息流安全 | 8700 行 C 的功能正确性 + 访问控制 | **~20 人年**（C 源证明，编译器等为 TCB） | capability 模型即唯一授权、TCB 极小、验证聚焦内核核心 | 全量证明成本对独立项目不可承受；且依赖 C 编译器验证链，MeuOS 无此链 |
| **CertiKOS** | 分层验证（Coq，每层的上下文精化） | 多核 OS 各抽象层功能正确性 | 高（多个博士级人力、数年） | "分层隔离验证面"思想——每层只证明本层不变量 | 分层证明工程量大；需 Coq 生态，与 mcc 工具链脱节 |
| **Hyperkernel** | 设计为**可判定验证**（Z3 SMT，非递归、有界） | 内核核心属性的自动证明 | 低（设计即为了可验证，代码量极小） | "为可验证而设计"——把核心收窄到 Z3 能自动判定的子集 | 需牺牲表达力；MeuOS 内核规模/功能已超此框架 |
| **Komodo** | 研究型微内核，探索**轻量精化证明**路径 | 公开成本数据有限 | 未精确定量（研究阶段） | 作为"小内核轻量证明"的对照样例，提示可把证明范围压到极小 | 验证成本/工具链未公开，无法直接对齐 |
| **Rust for Linux** | **类型系统作轻量验证**（abstractions 层封装 C 边界、编译期消除内存安全类缺陷） | 不证明功能正确性，只消除整类缺陷 | 近乎 0 额外验证成本（成本在 Rust abstractions 工程，持续投入） | MeuOS 直接复用此范式：Rust 类型 = 免费验证层 | 不覆盖"权限语义"逻辑错误，需叠加其他层 |
| **Hubris** | **无 unsafe 策略** + 静态任务 + supervisor 重启；靠 Rust 保证 + 纪律 | 不证明，靠"禁 unsafe + 编译期保证"达高可靠 | 低（纪律 + 工具链门禁） | "unsafe 白名单 + 审计门禁"（对齐 `02` §4.4）是 MeuOS 主力控险手段 | 同 RFL，不证明权限逻辑 |
| **TLA+**（AWS/Azure 实践） | 协议级**模型检验**（PlusCal + TLC/Apalache），穷尽并发/时序状态空间 | 分布式/并发协议正确性（无死锁、无丢消息） | 每协议**数周–数月**（如 DynamoDB、Cosmos DB 用 TLA+ 抓出隐蔽 bug） | IPC/revoke/重启状态机**极适合**模型检验，且零运行期开销 | 只验证模型不验证实现，需差分测试桥接 |
| **Fuchsia/Zircon** | **未做形式化验证**；靠 FIDL **契约 + 强测试**保证 IPC 边界 | 无证明，靠接口契约与测试 | 低（FIDL 工具链 + 测试工程） | handle/rights 模型与"契约即测试"思路可借鉴；证明非必需 | 不提供证明，与本文"核心要证明"立场互补而非替代 |

**对比收口**：没有任何单一参照完美匹配 MeuOS。seL4 给了"验证聚焦唯一裁决点"的范本但成本不可承受；Rust for Linux / Hubris 给了"免费验证层"的范式；TLA+ 给了"廉价且高价值的协议验证"。MeuOS 应**组合**三者（非缝合怪）：Rust 类型吃内存安全 + TLA+ 吃并发/时序 + 极小核心上可选证明器。

## 4. ③ MeuOS 分层验证策略

> 四层从"强保证、高成本"到"弱保证、低成本"递进。核心思想：**把最贵的证明留给最小的面**。

### 4.1 Layer A —— 完全形式化证明（Full machine-checked proof）【仅限极小核心】

- **目标对象（唯一候选）**：
  1. **capability rights 检查**（`check_rights(h, r)` 的判定逻辑）——`07` §4.1 的权限裁决点。
  2. **revoke derivation tree 的完整性**（撤销某节点 ⇒ 其全部派生链回收）——`07` §4.5、`00` C2。
- **为什么只限这两处**：它们是 `00` A3 所述"唯一裁决点"的数学内核，一个逻辑错误即等于全局权限失效；且二者状态空间极小、纯算法、与硬件无关，是可证明的。
- **证明形态（诚实声明）**：在 **host 侧证明器**（Coq / Lean 4 / 或 TLA+ 的TLC 精化）证明**参考模型/算法**；**不声称证明了编译后二进制**（见 §5 工具链鸿沟）。Rust 实现作为该模型的精化，经 §5 的差分测试桥接。
- **ROI 论据**：用 ~1 个核心的算法证明，换取"权限不会凭空产生 / 不会越权 / 撤销必定彻底"的机器保证——这正是 seL4 用 20 人年中最值钱的那一小块，我们以极小代价复现其精华。
- **不在 Layer A**：调度、VM、IPC 数据通路、mkit 兼容层、驱动、FS 后端——这些要么状态空间过大、要么演进过快、要么已排除出 TCB。

### 4.2 Layer B —— 模型检验 / TLA+（Model checking）【协议与状态机层】

- **目标对象**：
  1. **IPC 协议正确性**：rendezvous 无死锁、cap transfer 不丢不重、reply capability 生命周期（`05` §4.1、`05` §5-5）。
  2. **capability revoke 时序**：并发 `revoke` 与 in-flight IPC 消息、与 `close` 的交互（`07` §5-4、`00` C2）。
  3. **监督者重启状态机**：进程崩溃 → kill/dump/restart/升级，且**避免监督者监督自己死锁**（`00` A9、`04` §5-4、`09` §6-10）。
- **工具**：TLA+/PlusCal + TLC（穷尽）/ Apalache（SMT 符号化）；Rust 侧可用 `stateright` / `proptest` 做可执行模型检验作为补充。
- **为什么用 TLA+**：AWS/Azure 实践已证其实用性；**零运行期开销**、**在写代码前就能抓设计缺陷**、成本仅数周/协议。是 MeuOS 性价比最高的验证投资。
- **桥接实现**：TLA+ 模型 = 参考规约；实现须通过 §5 差分测试证明"行为被模型覆盖"。

### 4.3 Layer C —— Rust 类型系统 + 禁 unsafe 白名单【主力验证层】

- **目标对象**：除 Layer A 极小核心外的**全部 Rust TCB 组件**（`02` §4.2：syscall 路由、capability 判定与传播、IPC 端点、调度/账本、VFS 抽象、spawn/supervisor）。
- **手法**（对齐 `02` §4.4、§4.7，Theseus 风格 `02` §3.3）：
  - 句柄**非 `Copy`**、**私有构造**、`borrow` 防 UAF；rights 以**类型层集合 / `PhantomData`** 标记，使"rights 只减不增"在类型上部分可强制。
  - Job 账本生命周期由 Rust 所有权/RAII 包裹（`05` §5-2），防 capability 泄漏。
  - `unsafe` **白名单 + 审计门禁**：`forbid(unsafe_op_in_unsafe_fn)`、`deny(clippy::all)`、`unsafe` 块清单双人评审（`02` §4.4）。
- **定位**：这是 MeuOS 相对 seL4 的最大杠杆——seL4 花在 C 内存安全证明上的工作量，MeuOS 由 Rust 编译期"免费"获得。剩余需人证的只剩**权限语义逻辑**（交给 Layer A/B），验证面被压缩到极致。

### 4.4 Layer D —— 仅测试【排除出 TCB 的部分】

- **目标对象**：驱动、FS 后端、兼容层 `mkit`（C，排除出 TCB，`02` §4.2）、性能热路径。
- **手法**：单元测试、集成测试、**fuzz**（尤其 mkit UAPI 边界、`02` §5-3）、**差分测试**（§5）、`19` 性能回归（待定稿）。
- **为什么只靠测试**：这些组件状态空间大、演进快、已隔离在 TCB 外；其失效爆炸半径由 Layer C 的 capability 边界与 supervisor 重启（`00` A9）兜底，不需要形式化证明。

### 4.5 四层鸟瞰

```
 强保证 / 高成本 ┌─ Layer A  完全证明  ── capability rights 检查 + revoke derivation tree（极小核心）
                 ├─ Layer B  模型检验  ── IPC 协议 / revoke 时序 / 监督者重启状态机（TLA+）
 弱保证 / 低成本 ├─ Layer C  Rust 类型 + unsafe 白名单 ── 全部 Rust TCB 组件（主力）
                 └─ Layer D  仅测试    ── mkit / 驱动 / FS 后端（排除出 TCB）
```

## 5. ④ 核心安全不变量命题草案

> 以下为**可被机器检查的命题草案**。记号：`Handle` 句柄集、`Proc` 进程、`Rights` 权限位图（按位 `⊆` 序）、`Derive ⊆ Handle×Handle` 派生边、`Init` 根 Job 初始句柄集、`Ledger(j)` 作业 j 的资源账本。
> 形式化目标：I1–I3 进 Layer A（证明），I4–I7 进 Layer B/C（模型检验 + 类型强制），全部可被 `stateright`/`proptest`/TLA+ 机检。

### I1 — 无 capability 可凭空产生（No capability ex nihilo）
```
reachable(h) ⇔ h ∈ Init ∨ ∃ chain: Init →* h along Derive
∀ p, h:  usable(p, h)  ⇒  reachable(h) ∧ h ∈ table(p)
```
含义：任一可用句柄必能沿派生链追溯到根 Job 初始令牌；进程表之外的句柄值一律无效（防伪造，对应 `07` §5-1 Zircon 风格私有表）。

### I2 — revoke 后不存在可用派生句柄（Revoke severs descendants）
```
Revoke(h): 删除 h 及所有 h' s.t. Derive*(h, h')（传递闭包）
After Revoke(h):  ¬∃ h'.  (Derive* 路径经过 h) ∧ usable(_, h')
```
含义：撤销一个节点 ⇒ 其全部下游派生立即不可用。直接回应 `07` §4.5 / `00` C2 的"撤销传播完整性"。

### I3 — rights 只减不增（Rights monotonic non-increase）
```
∀ op ∈ {duplicate, mint, grant}:  rights(child) ⊆ rights(parent)
∀ op:  ¬∃ op. rights(out) ⊋ rights(in)        // 无任何操作可 ⊋-扩张权限
```
含义：沿任意派生路径，rights 形成下降链（`⊆`）。这是"无隐式提权"的代数表述，可由 Rust 类型层部分强制（Layer C）。

### I4 — Job 资源账本不可超额（Ledger non-oversubscription）
```
∀ j, r ∈ {cpu, mem, fds, io}:  Σ_{d ∈ descendants(j)} allocated(d, r)  ≤  quota(j, r)
alloc(j, r, n)  ⇒  if Σ + n > quota(j, r) then REJECT(EAGAIN/ENOMEM)
```
含义：资源账本 Day 1 内建（`00` A5）、与权限同源；超额分配必拒。进 Layer B 模型检验 + 单测。

### I5 — 受约束 mint 防 confused deputy（Constrained mint）
```
FS 服务代 client mint 文件句柄:  rights_issued = rights_fs_service ∩ rights_requested_client
```
含义：FS 服务不能超出自身 authority 发权（`00` C2 推荐裁决）。是 I3 在"服务端代理 mint"场景的特化，直接封堵 confused deputy（`07` §3.1）。

### I6 — 无隐式提权（No privilege escalation）
```
∀ op producing handle h' from handle h:  rights(h') ⊆ rights(h)
```
含义：不存在"产出权限超出发出方"的操作。由 I3 + I5 推出，单列以强调其为系统级顶层不变量。

### I7 — 句柄不可伪造 / 表外无效（Handle authenticity）
```
present(p, v) valid  ⇔  v ∈ table(p)
// 内核绝不接受 p 自行构造的 table 外句柄值
```
含义：与 I1 互补——I1 管"来源可追溯"，I7 管"呈现可核验"。二者共同构成 capability 不可伪造性的机检命题。

> **机检落地建议**：I1–I3 用 Coq/Lean 对参考模型证明；I4–I7 用 TLA+/`stateright` 状态空间穷尽；Rust 侧以类型（非 `Copy` 句柄、`PhantomData<Rights>`）把 I3/I7 的相当部分前推到编译期（Layer C）。命题中的 `Derive`、`table`、`Ledger` 抽象需待 `07` 定稿 rights 位图（§7 D5）与 derivation tree 全量与否（§7 D6）后冻结。

## 6. ⑤ 与自研工具链的信任鸿沟（mcc / QBE / rustc / LLVM）

> 本节直面"自研工具链驱动"对形式化方法的特殊含义。

### 6.1 "证明到源码级" vs "信任编译器"的鸿沟

- mcc（cproc + QBE）与 rustc（LLVM 后端）**均未经验证**。因此 Layer A 的"完全证明"只能覆盖**源码/参考模型算法**，无法覆盖编译产物。这与 seL4（证明 C 源、C 编译器在 TCB 内、后续才有二进制验证工作）处境类似但更严峻：**MeuOS 连一个验证过的 C 编译器都没有**。
- 诚实结论：**我们不声称证明了内核二进制**。证明的价值在于"算法正确 + 实现是算法的精化"，编译器鸿沟由 §6.2 兜底。

### 6.2 兜底手段：translation validation / 差分测试

- **差分测试（首选，低成本）**：同一组输入/操作序列，分别驱动 (a) Layer A/B 的参考模型（TLA+ / 证明器提取的可执行规约）与 (b) 实际 Rust/C 实现，断言**可观测迹（observable trace）等价**。鸿沟被收缩为"编译器未偷偷改变可观测行为"。
- **translation validation（远景，高成本）**：为 mcc/QBE 后端做翻译验证器（验证 IR→asm 保语义）。这是编译器工程，非内核团队职责，**本文不建议在 M6 前投入**；仅作为长期选项记录。
- **快照/确定性构建**：`11` 自举验证已关注"验证确定性/可重现性"（`00` §5.8）；可重现构建是差分测试的前置条件。

### 6.3 i386 全程 C 的验证降级

- i386 无 Rust 裸机 target（`02` C2），其 TCB 是 **mcc 编译的 C**（早期启动、asm 边界、及可能的 TCB 组件，`00` C6）。这意味着 i386 **拿不到 Layer C 的 Rust 类型保护**。
- 降级处置：i386 的 C TCB 组件须**额外上模型检验（Layer B 的 C 逻辑）或静态分析/fuzz**，以弥补缺失的类型层保证；这是 i386 相对 64 位目标的验证成本增量，应在 `02` C2 的"i386 是否永久纯 C"裁决（§7 D3）中计入。

### 6.4 CHERI 作为硬件级兜底（可选增强）

- 在 RISC-V / Arm Morello 上，将 handle 与 CHERI 指针能力对齐（`07` §4.4、§5-5），可从硬件层部分覆盖 I7（不可伪造/不可越界）。这是**防御纵深**而非证明替代，不改变软件模型，且非跨架构基线。

## 7. ⑥ 分阶段路线

> 与 `00` §4.2 里程碑 M0–M6 对齐。原则：**验证投资随设计稳定度递增，绝不超前锁死庞大证明**。

### 7.1 原型期（M0–M3：最小可运行集 + 工具链自举）

- **Layer C 默认开启**：Rust TCB 组件即按 `02` §4.4 的 unsafe 白名单 + 类型强制落地；这是"零额外成本"的验证，立即生效。
- **Layer B 前置（高性价比）**：在写 IPC / revoke / supervisor 代码**前**，先用 TLA+/PlusCal 写参考模型，穷尽状态空间抓设计 bug（无运行期开销、`19` 友好）。优先级：监督者重启状态机（`00` A9，防自杀环）> IPC rendezvous > revoke 时序。
- **Layer A 仅建模不证明**：把 capability rights 检查 + revoke tree 的参考模型写出来，但**暂不投入证明器**（设计仍可能变动，过早证明 = 浪费）。
- **Layer D 全面铺开**：mkit fuzz、FS/驱动单测、与 `11` 的 qemu-user 跨架构 ABI 回归联动。
- **不做**：端到端证明、translation validation、i386 专项验证。

### 7.2 M3 后（L2 工具链自举完成，设计趋于稳定）

- **Layer A 启动窄证明**：对**已稳定**的 capability rights 检查 + revoke tree Rust 核心，在 host 侧证明器（Coq/Lean）证明其参考模型；Rust 实现作为精化，经 §6.2 差分测试桥接。范围严格限于 §4.1 两处。
- **Layer B 扩展**：将 TLA+ 覆盖到更多协议（Service Registry realm 隔离 `05` §5-4、reply 生命周期 `05` §5-5）。
- **差分测试常态化**：参考模型 vs 实现的可观测迹等价，纳入 CI 门禁。
- **i386 补偿**（若 C2 裁决保留纯 C）：对其 C TCB 补模型检验/静态分析。

### 7.3 长期（M5/M6+，多架构 + 原子更新）

- 若 Rust 验证后端成熟（gccrs / `rustc_codegen_gcc` 可用，或出现 CompCert 式 Rust 路径），**重估** Layer A 是否可下推到更接近二进制。
- CHERI 硬件能力在支持架构上叠加为 I7 的硬件兜底（`07` §5-5）。
- 持续**拒绝** seL4 全量证明（理由见 §7.4）。

### 7.4 "我们不做 seL4 全量证明"的明确保留

1. **成本不可承受**：seL4 ~20 人年验证 8700 行 C；MeuOS 独立、资源有限、设计演进中，全量证明 ROI 极低。
2. **工具链不支持**：无验证过的编译器（mcc/QBE、rustc/LLVM 均未见证），端到端证明在数学上无法闭合到二进制。
3. **Rust 已免费吃掉最大头**：seL4 花在 C 内存安全证明上的工作量，MeuOS 由 Rust 编译期获得；剩余需人证的"权限语义"极小，只值得 Layer A 的窄证明。
4. **聚焦唯一裁决点即够**：capability 监视器是 Day 1 唯一权限裁决点（`00` A3），把证明预算投到这里，可用 ~1 个核心的代价获得系统级权限正确性的主体保证——这正是"解构型思维"的结论：**验证该验证的，不验证验证不起的**。
