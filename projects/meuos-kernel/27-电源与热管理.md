## 1. 「应该是什么样」推演（解构型思维）

### 1.1 还原到第一性原理

MeuOS 的内核定位（来自 `00` §1、`09` §1.2）：**务实混合内核（lean hybrid）**，内核态只保留「机制 + 唯一裁决点」，其余「策略重、代码量大、需可重启」的子系统下沉为用户态、capability 受控服务。三大内在方向——① 统一文件系统层、② spawn/Job 监督、③ capability 安全 Day 1——要求**任何新子系统都要先问「它该不该出核」**。

把「电源与热管理」还原为最小必要问题：

1. **什么是内核必须做的（机制）**：把硬件暴露的功耗/热**原语**——CPU 频点档（P-state / OPP）、idle 态（C-state）、设备电源状态（D-state）、thermal 传感器读数、能耗计数器（RAPL/PMU/AMU）——**枚举并暴露**出来；在**物理不可绕过**处强制执行硬约束（thermal 硬上限、紧急关断）。
2. **什么是策略（应出核）**：DVFS 选频、idle 偏向、设备断电时机、休眠（suspend/hibernate）决策、按场景（笔记本/手机/服务器）的电源策略——这些是「代码量大、需可调试、需随用户意图变化」的策略，应作为**用户态 `powerd` 服务**（对齐 Fuchsia powerman）存在。
3. **什么是调度器耦合**：调度器（`04` EEVDF+RT）做**能耗感知调度（EAS）**——据 `Job` 账本与功耗约束，决定任务是铺满所有核还是聚到少数核以允许其余核进入深 idle（power clustering），以及是否存在按 Job 的能耗配额。

### 1.2 推演结论：内核只暴露原语，策略放用户态

> **MeuOS 电源/热管理 = 内核态暴露「功耗/热原语 + 不可绕过的热硬限」机制层 + 用户态 `powerd` 策略层；调度器据 `Job` 账本与功耗约束做能耗感知 EEVDF+RT 调度。**

这符合「重服务出核缩 TCB」（方向③）与「尽快交权用户态」（`09` §3.2）。理由：

- **TCB 压缩**：DVFS  governor、suspend 状态机、thermal 缓解策略（passive cooling）都是易变策略，留核会膨胀 TCB 且难可重启；下沉后用 Rust 写、受 capability 约束、崩溃可重启。
- **恶意服务无法榨干系统**：选频/休眠/设备断电的**决策权**集中在受 `POWER_POLICY` capability 约束的 `powerd`；单个恶意服务即便持有自身设备电源能力，也无法越权迫使全局过热或耗尽电池——因为 **thermal 硬上限由内核无条件强制执行**（见 §4），DVFS 全局策略由 `powerd` 独占。
- **与调度器互锁**：调度器的能耗感知（EAS）需要功耗原语作为**只读输入**、需要 `Job` 账本（`04` §4.4）作为约束来源——二者同源，与方向②③一致。

## 3. MeuOS 功耗/热原语与用户态策略分层

### 3.1 分层架构

```
┌──────────────────────────────────────────────────────────────────┐
│ 用户态策略层（Rust 服务，受 capability 约束，可重启）              │
│  powerd / power manager                                            │
│   · DVFS governor（选频策略）  · idle 偏向  · 设备断电编排          │
│   · 休眠(suspend)决策  · 场景策略(笔记本/手机/服务器)              │
│   · 聚合 thermal zone/trip、电池/AC 状态、Job 账本能耗预算          │
│   · 能耗感知调度协调（向调度器(04) 下发功耗约束）                  │
├──────────────────────────┬───────────────────────────────────────┤
│ 设备电源（用户态驱动经能力网关）   │  调度器(04) EEVDF+RT 能耗感知   │
│  driver ⇄ capability gateway ⇄ kernel│  EAS：据 Job 账本+功耗约束   │
├──────────────────────────┴───────────────────────────────────────┤
│ 内核态机制层（仅暴露原语 + 强制执行热硬限）                        │
│   · CPU 频点档(P-state/OPP) 设定接口   · idle 态执行（本地决策）    │
│   · 设备电源状态(D0–D3) 校验与执行     · thermal 传感器读 + 硬 trip  │
│   · 能耗计数器(RAPL/PMU/AMU) 只读暴露 · suspend/hibernate 原语执行  │
│   · 【热硬限】passive throttle + critical shutdown，不可被用户态绕过 │
└──────────────────────────────────────────────────────────────────┘
```

### 3.2 内核态机制层（原语清单）

| 原语 | 内核职责 | 用户态可见性 |
|------|----------|--------------|
| **CPU 频点档 / P-state / OPP** | 枚举可用频点档（来自 ACPI _PSS/_PPC 或 DT operating-points）；仅**应用**用户态选定的档，不替用户态选 | `powerd` 经 capability 选档；调度器只读当前档 |
| **idle 态 / C-state** | 枚举可用 idle 态；**本地执行** idle 进入（避免 IPC 延迟）。策略偏向可由 `powerd` 约束（如「最大允许 idle 深度」） | `powerd` 设偏向；驱动/调度只读可用态 |
| **设备电源状态 / D-state** | 维护设备电源矩阵（D0–D3 ↔ 唤醒延迟/能耗），校验并**执行**状态切换，通知驱动（`10`） | 用户态驱动经设备能力请求切换（§4、§5.3） |
| **thermal 传感器读数** | 暴露各 thermal zone 的当前温度 | **只读 capability**（`THERMAL_READ`） |
| **thermal 硬 trip** | 维护 trip 点；passive（节流）→ critical（关断）**无条件执行** | 用户态可读取/订阅事件，**不可禁用/抬高 critical** |
| **能耗计数器** | 暴露 RAPL/PMU/AMU 读数（每核/每 package/每设备） | **只读 capability**（`ENERGY_READ`） |
| **平台休眠原语** | suspend-to-idle / suspend-to-RAM / hibernate 的**执行**（保存上下文、关设备、唤醒恢复） | `powerd` 决策并发起，内核执行 |

### 3.3 用户态策略层（powerd）

- **输入聚合**：thermal zone 当前温度 + trip 余量、电池/AC 状态、各 `Job` 账本能耗预算（若启用，见 §7 待决 1）、用户场景策略。
- **决策输出**：选 CPU 频点档（DVFS governor）、设 idle 偏向、编排设备断电（`10` 驱动配合）、发起/拒绝休眠、在 thermal 压力下向调度器下发「降频/聚核」约束。
- **可重启**：`powerd` 崩溃由 `meu-supervisor`（`04` §4.5）重启；崩溃期间内核维持保守默认（最高温度档最低、设备按安全态），**不会因此过热**（热硬限独立于 `powerd`）。
- **能耗感知调度协调**：`powerd` 与调度器（`04`）通过 capability 网关通信，下发「某 `Job` 能耗上限」「当前 thermal headroom」等约束；调度器据 `04` 的 `sched_class` 钩子做 EAS（见 §5.1）。

## 4. capability 化与不可绕过的热硬限

### 4.1 谁有权改变功耗状态

- **设备电源能力派生自 `10` 的设备能力**：在 `10` §2.4/§4.6 的 `Cap(MMIO/IRQ/DMA/IO port)` 之外，新增**设备电源能力**——建议作为设备句柄上的 `DEVICE_POWER` right（或独立 `Cap(DevicePowerState)` 对象，二者取一待 §7 待决 2）。驱动（用户态）只对其**自有设备**请求 D-state 切换，能力网关校验设备电源矩阵后执行。
- **系统级策略权受限**：`powerd` 持有 `POWER_POLICY` capability，可设全局 DVFS/idle 偏向、决策休眠；但这是**受限、可撤销、可被错误**的「软权」——它**不是**超级特权，不授予其绕过 thermal 硬限或修改其他 Job 资源的能力（对齐 `07` §4.1「无 root 逃生舱」）。
- **thermal / 能耗读能力**：`THERMAL_READ` / `ENERGY_READ` 为只读 right，可授予可观测性服务（`12`）。恶意服务即使持有 `DEVICE_POWER`，也只能管自己设备、且受全局 thermal 硬限压制。

### 4.2 不可绕过的热硬限（安全边界）

> **thermal 硬上限由内核无条件强制执行，不能被任何用户态（含 `powerd`、含被攻破的服务）禁用或抬高。这是电源管理中的「硬安全边界」，等价于 `07` 的 fail-closed 原则。**

- **实现层次**：critical trip 点对应「紧急节流 + 关断」动作，由内核在 thermal 中断/轮询路径**无条件**触发；在支持硬件上映射到 RAPL 的 PL（Power Limit）MSR、EC/BIOS 关断、或平台 watchdog。
- **与 capability 的关系**：用户态可**读取**当前温度、可**订阅** thermal 事件、可设**passive 缓解策略**（降频档、聚核）——但**critical trip 是不可 mint、不可 revoke、不可提权的内核 TCB 部分**。
- **为何必须内核强制**：若交给用户态，恶意或被攻破服务可压制降频、逼迫 SoC 过热，造成硬件损坏或拒绝服务——这违背方向③「不可被恶意服务榨干 TCB」。**物理/内核硬限是唯一可信边界**，与 Linux RAPL PL1/PL2、Android thermal HAL 内核强制 trip 同理。

### 4.3 软权 vs 硬限 的清晰分界

| 类别 | 持有者 | 可否被恶意服务绕过 | 属 TCB？ |
|------|--------|--------------------|----------|
| DVFS 选频、idle 偏向、休眠决策（软策略） | `powerd`（`POWER_POLICY`） | 否（决策集中、且受硬限压） | 否（用户态） |
| 自有设备 D-state 切换 | 用户态驱动（`DEVICE_POWER` 派生自 `10`） | 否（限自有设备、受硬限压） | 否 |
| thermal/能耗**读** | 观测服务（`THERMAL_READ`/`ENERGY_READ`） | 否（只读） | 否 |
| **thermal 硬限（passive→critical）** | 内核（硬件/MSR 强制） | **不可绕过** | **是（内核 TCB）** |

## 5. 与 04 / 09 / 10 的接口

### 5.1 与 `04-进程与调度`（调度器 EEVDF+RT 的能耗感知）

- **EAS 钩子**：在 `04` §4.3 的 `sched_class`（`enqueue_task`/`pick_next_task`/`task_tick`/`set_next_task`）中新增**能耗感知子策略**：调度器读取（a）当前 CPU 频点档与 thermal headroom（来自 §3.2 原语，只读），（b）`Job` 账本能耗预算（若启用，§7 待决 1），（c）`powerd` 下发的功耗约束。
- **两种耦合强度**：
  - **弱耦合（原型期推荐）**：EAS 仅做「task packing」——thermal 压力下把任务聚到少数核、允许其余核进深 idle（power clustering）；频点选择仍由 `powerd` 全局决定。不把能耗写入 `Job` 账本。
  - **强耦合（待裁决）**：把**能耗配额**作为 `Job` 账本（`04` §4.4）的一类资源（类似 CPU 时间/内存），超限则限流该 Job 的 CPU 功率或降其权重。这需扩展 `04` 账本对象与检查点。
- **big.LITTLE / 异构核**：`04` §5 开放议题 6（NUMA/异构核 EAS）与本维度直接互锁——能耗感知调度天然需要「小核省电、大核性能」的调度偏置，建议合并且交 `04` 协同。

### 5.2 与 `09-启动与初始化`（启动期电源初始化）

- **电源拓扑枚举（Stage 2）**：在 `09` §5.2 Stage 2 解析 DT/ACPI 时，**一并抽出电源/热拓扑**——CPU OPP/P-state 表、idle 状态表（DT `cpu-idle-states` / ACPI `_CST`）、thermal zone 与 trip 点（DT `thermal-zones` / ACPI thermal）、能耗计数器能力（RAPL/PMU）。设备电源矩阵随 `10` 设备节点登记。
- **能力自举（Stage 4）**：`09` §5.4 的第一批 capability 中新增：向 `powerd` 签发 `POWER_POLICY`；向观测服务签发 `THERMAL_READ`/`ENERGY_READ`；设备电源能力随 `10` 设备能力一并下发（§4.1）。
- **热硬限尽早生效**：critical thermal trip 的**强制逻辑在用户态 `powerd` 启动前即已激活**（内核态默认保守档 + 硬件 PL 约束），保证「即使 `powerd` 尚未就绪或崩溃，系统也不会过热」——对齐 `09` §3.2「内核退居机制+裁决点」。
- **保守默认**：boot 期默认最低性能档、设备安全态（D0 按需），待 `powerd` 接管后按策略放开。

### 5.3 与 `10-设备驱动模型`（用户态驱动经能力网关管设备电源）

- **设备电源状态切换**：用户态驱动持有 `DEVICE_POWER`（派生自 `10` 的设备能力）后，经 capability gateway 请求 D-state 切换；gateway 校验设备电源矩阵（D0↔D3 合法性、唤醒延迟），内核执行并通知驱动。
- **系统休眠编排**：`powerd` 发起 suspend 时，经 `10` 驱动管理器/RS 看门狗，将各用户态设备驱动按其 `DEVICE_POWER` 能力有序置 D3，内核态快速驱动（中断控制器/定时器）进入最低必需态，再由内核执行平台 suspend 原语。
- **撤销即回收**：设备拔出/驱动卸载（`10` §4.6）时，设备电源能力随设备能力一并回收，杜绝悬垂电源引用。
- **与 `10` §5 开放议题衔接**：中断转发开销（10 §5-1）影响「设备断电再唤醒」延迟基准；DMA/IOMMU 强制化（10 §5-2）与设备电源态共存——均需在电源维度补齐。

## 6. 五架构差异

| 架构 | 选频(DVFS) 来源 | idle 来源 | thermal / 能耗计量 | 特殊点 / 原型期取舍 |
|------|----------------|-----------|--------------------|----------------------|
| **x86_64** | ACPI `_PSS`/`_PPC` 或 Intel HWP（硬件 P-state）；`intel_pstate`/`acpi-cpufreq` 思路 | ACPI `_CST` / `mwait` C-state | **Intel RAPL**（MSR 0x611/0x639 等）能耗 + MSR `THERM_STATUS`/ACPI thermal zone | 最完整；RAPL 是能耗计量与热硬限的天然载体；HWP 可让硬件自治选频（策略仍可用户态约束范围） |
| **aarch64** | DT `operating-points-v2` (OPP)；big.LITTLE 多簇频点 | PSCI `CPU_SUSPEND` / DT `cpu-idle-states` | DT `thermal-zones` + SoC thermal sensor；**AMU**（Activity Monitors Unit）能耗近似；PMUv3 | **异构核 EAS 刚需**（§5.1）；PSCI 是 CPU 热插拔/深 idle 标准；无 RAPL，能耗靠 AMU/PMU |
| **riscv64** | DT OPP；平台相关（vendor DVFS） | SBI D6 Hart State Management / SBI `suspend` 扩展 | 平台相关 thermal sensor；**SBI PMU** 扩展计数 | 标准化程度最低，平台碎片化；以 SBI 抽象屏蔽差异，原型期先支持 QEMU/virt 的最小 OPP |
| **loongarch64** | LoongArch 频率 CSR / ACPI 式表 | CSR 空闲指令 / ACPI `_CST` | 平台 thermal sensor | 与 x86_64 思路接近（ACPI 体系），但能量计数接口未标准化；原型期仅基础 idle + 硬限 |
| **i386** | 老旧 ACPI `_PSS` 或基本无 DVFS（多数 legacy） | `HLT` 指令 idle（仅 C1 类） | ACPI thermal zone，无 RAPL，无现代能耗计数 | **最小电源管理能力**：仅 idle（HLT）+ ACPI thermal 硬限；DVFS 基本放弃，原型期不追求选频策略 |

**跨架构收敛原则**：所有架构在**机制层抽象为统一原语接口**（`cpu_set_freq_bin` / `cpu_enter_idle` / `thermal_read` / `energy_read` / `device_set_dstate` / `platform_suspend`），每架构一份薄后端（对齐 `09` §5.5「架构相关层极薄」与 `01` §5-6 五架构一致性成本）。能耗计数（RAPL/AMU/PMU/SBI PMU）统一归一为「每核/每 package/每设备 能耗读数」capability 对象。

## 7. 自主结论 + 待决项

### 7.1 自主结论

1. **内核只暴露功耗/热原语 + 不可绕过的热硬限**；DVFS/idle 偏向/设备断电/休眠等**策略全部用户态化**（Fuchsia powerman 范式），与「重服务出核缩 TCB」与「尽快交权用户态」（`09`）一致。
2. **thermal 硬上限是内核 TCB 内的无条件安全边界**——任何用户态（含 `powerd`）不可禁用或抬高 critical trip，恶意服务无法迫使系统过热或耗尽电池。这是电源维度的 fail-closed，等价于 `07` 的安全边界。
3. **capability 化电源**：设备电源能力派生自 `10` 的设备能力；系统级 `POWER_POLICY` 为受限、可撤销的软权（非 root）。
4. **调度器能耗感知（EAS）** 据 `Job` 账本与 `powerd` 约束做 task packing / 频点偏向，与 `04` 的 `sched_class` 互锁；能耗是否计入 `Job` 账本待裁决（见下）。
5. **五架构**统一机制层抽象 + 每架构薄后端；x86_64 RAPL、aarch64 AMU/PSCI/OPP、riscv64 SBI、loongarch64 ACPI 式、i386 仅 idle+硬限。

### 7.2 待决项（标注是否需架构裁决）

1. **【架构裁决·建议新增冲突登记表项】能耗是否计入 `Job` 账本（强/弱 EAS 耦合）**：是否把「能耗配额」作为 `04` §4.4 `Job` 账本的第六类资源（CPU/内存/句柄/IO/进程数 之外）？强耦合需扩展 `04` 账本对象与调度检查点；弱耦合仅做 task packing。建议原型期走**弱耦合**，强耦合待 `04` §5 议题 6（异构核 EAS）一并裁决。**需 `04` 协同、team-lead 拍板是否新增冲突登记表条目。**
2. **设备电源能力表示**：`DEVICE_POWER` right 位（扩展 `07` §5-2 rights 位图）vs 独立 `Cap(DevicePowerState)` 对象（派生自 `10` 设备能力）。建议先随 `10` 设备能力派生，与 `07`/`10` 协同定稿。
3. **idle 态进入的「策略 vs 执行」边界**：内核本地执行 idle（必做，避免 IPC 延迟）与 `powerd` 设「最大 idle 深度偏向」的接口形态——对齐 `09` Stage 设计。
4. **suspend / hibernate（休眠）原型期范围**：原型期是否仅做 suspend-to-idle（freeze + 深 idle），还是含 suspend-to-RAM；hibernate（落盘）后置。关联 `06`/`09` 的 `.msys` 媒介边界。
5. **thermal trip 的可配置层级**：哪些 trip（passive 降频档、温度阈值）可由 `powerd` 设置，哪些（critical 关断）**硬接线不可改**——需定义「可调上限」与「硬限」的分割点（安全边界精确化）。
6. **能耗计数器抽象粒度**：RAPL/AMU/PMU/SBI-PMU 是否统一为一个 `EnergyCounter` capability 类型，还是分 architected 子类型。关联 `12` §5.9（PMU capability 暴露面）。
7. **热硬限与 `powerd` 故障域**：`powerd` 崩溃重启期间的热保护完全由内核硬限兜底——需明确「保守默认档」的具体取值与何时从保守态切到 `powerd` 策略态（衔接 `09` §6 待决 10 监督者自举环）。

> 跨域一致性以 `00` §2（A1–A12）与 `00` §3（**C1–C14**）+ `18-第二轮收敛摘要` 为准；本文不修改 C1–C14，仅在第 1 项提议新增冲突登记表条目，由 team-lead 决定回填 `00`。
