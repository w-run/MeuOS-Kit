# 33-块设备与存储抽象（Block Device & Storage Abstraction）

> 子领域调研 / 规划设计文档，由 kernel-plan 团队「块设备与存储抽象」调研员（general-purpose-38，lite / hy3）产出。

> 方法论铁律贯穿：解构型思维（先推演「应该是什么样」）、多系统参照、非缝合怪、修订式追加不删。

## 1. 「应该是什么样」推演（解构型）

> 先不问「MeuOS 的块层怎么抄 Linux bio/request_queue / device-mapper」，而问「在 capability 世界、用户态驱动、VMO 数据通路的既定前提下，块设备与存储抽象**应该**是什么样」。

### 1.1 从内核哲学出发的三条硬约束

把 MeuOS 已落定的取向推到「块设备」这一层：

1. **capability 世界（07）**：一切资源访问由不可伪造的句柄（handle）+ rights 表达，无 root、无全局命名空间默认可见（`00` A1/A4）。那么「一块磁盘 / 一个分区 / 一个逻辑卷」天然应是一个 **capability 对象**——进程/服务之所以能向它提交 I/O，不是因为它「碰巧跑在内核特权里」，而是因为它**持有该块设备的 capability 句柄且带 `BLOCK_*` right**。
2. **用户态驱动 + 能力网关（10）**：硬件访问经 `10` 能力网关代理，驱动最小权限、可重启（MINIX 3 式看门狗）。那么**块设备驱动（virtio-blk / NVMe 等）应是用户态服务**，经能力网关获 `MMIO/IRQ/DMA`，而非内核内块层巨石的一部分（`10` §4.2 已把 `virtio-blk` 列为用户态驱动）。
3. **VMO 数据通路 + 零拷贝（03 A7 / 06 §4.4.1）**：文件数据走 VMO + pager。那么**块设备与上层之间的数据搬运应经由 VMO**——DMA 缓冲是 device VMO（`03` C1），读出的数据以普通 VMO 交给 FS/应用，内核不复制。

把这三条合起来，得到一句收口：**块设备 = 用户态驱动经能力网关持有的硬件能力，向上暴露为一个个「块设备 capability」；数据通路是 VMO；分区/卷/RAID 不是内核内 device-mapper，而是消费子设备 cap、产出新 cap 的**用户态存储组合服务**。

### 1.2 推演「应该是什么样」的核心命题

| 命题 | 在 MeuOS 取向下「应该」的形态 | 反面（传统内核） |
|------|-------------------------------|------------------|
| 块设备在哪里实现 | **用户态块驱动服务**，经能力网关（10）持有硬件 | Linux 内核 `drivers/block` + `block/`（request_queue 巨石） |
| 块设备的访问令牌 | **capability 句柄**（接 07），带 `BLOCK_READ/WRITE/IO` right | Linux `struct block_device` + 全局可见 + 靠 uid/capability 保护 |
| 上层（FS）怎么读写 | **经 VMO 零拷贝**：FS 拿块设备的 block-io cap + VMO 通路，pager 模型取数据（接 06 §4.4.1） | 内核内 `submit_bio` → 块层 → 驱动，多次拷贝 |
| 分区 / 卷 / RAID 在哪 | **用户态存储组合服务**：输入子设备 cap，输出新 cap（composable，接 06 mount-capability） | 内核内 device-mapper / MD RAID / LVM |
| 加密 / 校验和 / 压缩在哪 | **FS extent 层**为主（密钥=capability，接 06 §4.2）；块层只传 VMO。可选「块层加密卷 cap」组合服务 | dm-crypt（块层整盘一钥，与 capability 割裂） |
| 内核里有没有「块层」 | **没有**传统块层——内核只提供「块设备 capability 对象 + VMO 机制 + capability 强制」三类机制，与 netstack（25）同构 | Linux 有完整 block layer（bio/blk-mq/ elevator） |

### 1.3 推演结论（解构型基线）

> **MeuOS 的块设备与存储抽象应参照 Fuchsia/ChromeOS 的「块设备经能力网关交给用户态驱动、用户态 FS 直连 VMO、无内核块层巨石」思路，并与 netstack（25）/FS（06）出核形成同一套 lean hybrid 叙事：硬件访问留在用户态块驱动（受能力网关约束），块设备以 capability 对象向上暴露，分区/卷/RAID 是消费子设备 cap、产出新 cap 的用户态组合服务，数据通路一律走 VMO 零拷贝，加密/校验和/压缩默认在 FS extent 层（块层只传 VMO）。内核只保留「块设备 capability 对象 + VMO/device VMO 机制 + capability 强制」三类机制，零块层逻辑。**

## 3. MeuOS 块设备/存储抽象（用户态驱动 + capability + VMO）

### 3.1 总体架构：用户态块驱动 + capability 组合存储栈

```
┌──────────────────────────────────────────────────────────────────────┐
│ 用户态 FS 服务 (Rust, 接 06)                                            │
│  目录树 · extent 分配 · CoW · 校验和/压缩/加密(extent 层) · 快照/repoint │
│  由 meu-supervisor(04) 管理，可重启；持有块设备 block-io cap + VMO 通路   │
│       │ mount-capability 委托 /dev /net /proc (接 06 §4.1)   │ VMO pager │
├───────┴───────────────────────────────┴──────────────────────────────┤
│ 用户态存储组合服务 (Rust, 本文新增)  —— capability 组合，可重启           │
│  ├─ 分区服务：整盘 cap → 多个分区 cap (按 offset/len 收窄+派生)          │
│  ├─ 镜像/RAID 服务：N 子 cap → 1 冗余 cap (striping/mirroring/parity)  │
│  └─ 加密卷服务：子 cap + 卷密钥 cap → 加密 cap (密钥=capability, 接06)   │
│       输入=子设备 cap，输出=新 cap（composable，接 06 mount-capability） │
├──────────────────────────────────────────────────────────────────────┤
│ 用户态块驱动服务 (Rust, 接 10 双轨·默认出核)                             │
│  virtio-blk / NVMe 等：MMIO/IRQ/DMA 能力(来自 10 网关) → ring 收发       │
│  把硬件建模为「块设备 cap」：submit(vmo, offset, len, op) 数据走 VMO      │
│       │ 设备能力经能力网关(10 C8)      │ DMA 缓冲= device VMO (03 C1)    │
├──────────────────────────────────────────────────────────────────────┤
│ 内核态（仅机制，Rust TCB）                                               │
│  ① 块设备 capability 句柄对象（来自 10 能力网关，仅 BLOCK_READ/WRITE/IO）│
│  ② VMO / device VMO（接 03 C1）：DMA 缓冲与数据零拷贝通路               │
│  ③ capability 强制 + 撤销锁（接 07 / 10 C8）：revoke 即回收块设备权     │
│  —— 内核不实现任何 bio/request_queue/device-mapper/RAID 逻辑 ——         │
└──────────────────────────────────────────────────────────────────────┘
```

> 与 `25` netstack 同构：netstack 是「NIC 驱动(用户态) → 报文 VMO → netstack(用户态) → socket cap」，本文是「块驱动(用户态) → 数据 VMO → 存储组合服务(用户态) → 块设备 cap → FS(用户态) → 文件 VMO」。二者都是「硬件在用户态、数据走 VMO、对象即 capability、组合服务可重启」，是 `00` A6「重服务出核缩 TCB」在存储子系统的落定。

### 3.2 块设备对象 = capability（接 07 / C1 / C8）

- **块设备内核对象**：每个物理盘 / 分区 / 逻辑卷在内核是一个**带类型的块设备对象**，持有其 **capability 句柄**才能提交 I/O（接 `07` §4.1「内核对象即 capability，权限随句柄」）。
- **rights 位图（建议，待 07 定稿，见 §5 D1）**：在 `07` 基础 `{READ,WRITE,EXECUTE,MANAGE,GRANT,REVOKE,DUPLICATE}` + 服务端 `KEY_*` + `DBG_*` + `CFG_*` 之上，块设备对象建议新增一组 **`BLOCK_*` right**（与 `25` 的 `NET_*` 同构、独立 bit）：
  - `BLOCK_READ`：提交读请求
  - `BLOCK_WRITE`：提交写请求
  - `BLOCK_IO`：持有即代表「可对该设备做 I/O 提交」（READ/WRITE 的父权，对齐 07 收敛后的语义）
  - `BLOCK_SUBDIVIDE`：把整盘 cap 派生/收窄为子区间 cap（分区服务必需，见 §3.4）
  - `BLOCK_MINT_SUBDEV`：向下游服务 mint 子设备 cap（受约束 mint，防 confused deputy，接 06 §6-2 / 07 §4.5）
- **device VMO（03 C1）**：块驱动的 DMA 缓冲区来自内核从 DMA32/CMA zone 取的连续页，封 **不可写 device VMO** 经设备能力下发驱动（`03` C1 回写、`10` §B）。读出的数据再以**普通 VMO** 暴露给 FS/应用（可 map、可 pager 供页）。
- **撤销锁序列（接 10 C8）**：块设备 cap 的回收遵循 `10` §A 的撤销锁六步——屏蔽 IRQ 转发 → 冻结持有驱动/服务 → IOMMU 域对该持有者失效（截断在飞 DMA）→ revoke 块设备 cap 句柄（记 dead）→ kill + 释放地址空间 → 仅全部完成后 fresh-mint 新 cap。进程死亡自动回收为第二重保险（对齐 Zircon handle-close-on-process-death）。

### 3.3 用户态块驱动（接 10 双轨驱动）

- **virtio-blk / NVMe 等作为用户态 Rust 驱动**（接 `10` §4.2 / 附录 A，已列 `virtio-blk` 用户态），经 `10` 能力网关获 `MMIO/IRQ/DMA` 能力，受最小权限约束、崩溃走看门狗重启。
- **驱动把硬件建模为「块设备 cap」**：驱动启动后，向内核请求 mint 一个代表该物理盘的块设备 capability（自身持 `BLOCK_MINT_SUBDEV`/`MANAGE`），并提供 I/O 提交原语，例如：
  `submit(block_cap, vmo, vmo_offset, dev_lba, len, op∈{read,write})`
  数据一律走 VMO——读时 DMA 入 device VMO 再映射/拷贝到数据 VMO，写时从数据 VMO DMA 到设备 ring。内核不复制、不做 request 排队策略（那是驱动/组合服务内部的事）。
- **中断处理（接 10 §5-1 / 19 AP-2）**：高频率设备用「中断合并 + 轮询混合」避免 IPC 风暴；NVMe 等高吞吐是否按 `10` 双轨留核快速路径属优化项，非 Day 1 必需（见 §5 D5）。
- **DMA 与 IOMMU（接 10 §5-2）**：强制 IOMMU 域隔离；无 IOMMU 平台仅允许受信内核态驱动（与 `10` C8 撤销锁退路一致）。

### 3.4 分区 / 卷 / RAID = capability 组合服务（composable，接 06 mount-capability）

这是本文相对传统内核的**核心差异点**：不建内核内 device-mapper，而是把「组合」下沉为用户态服务，每个服务的输入是若干**子设备 cap**，输出是**新 cap**——与 `06` §4.1 的 mount-capability「委托子树」同构（capability 组合树）。

- **分区服务（partition service）**：消费整盘 cap（持 `BLOCK_SUBDIVIDE`），按 GPT/MBR 解析产出多个**分区 cap**。每个分区 cap 是整盘 cap 的**收窄派生**：固定 `[base_lba, length]` 区间、rights 受限（去除 `BLOCK_SUBDIVIDE`、仅留 `BLOCK_READ/WRITE`）。revoke 传播进 `07` derivation tree（见 §5 D4）。
- **镜像 / RAID 服务**：消费 N 个子设备 cap，产出 1 个**冗余 cap**。mirror = 双写双读校验；striping = 按条带映射；parity(RAID5/6) = 计算校验分布到子设备。组合服务自身是用户态、可重启（崩溃由 `meu-supervisor` 拉起，重建内部状态，fail-closed），**不污染 TCB**。
- **加密卷服务（可选）**：消费 1 个子设备 cap + 1 个**卷密钥 cap**（密钥=capability，呼应 `06` §4.2.3），产出 1 个**加密 cap**——读写时透明加/解密。这是「块层加密」的 MeuOS 形态，但它**仍是 capability 组合服务、密钥仍=capability**，与 dm-crypt「整盘一密钥、与句柄无关」有根本区别（见 §3.5 与 §5 D2 的边界澄清）。
- **组合的可嵌套性**：cap 可层层组合——`整盘 cap →(分区) 分区 cap →(加密卷) 加密分区 cap →(RAID) 跨盘冗余 cap →(FS block-io) FS 服务`。每一层都是独立用户态服务、独立崩溃域、独立 capability 约束，这正是 capability 组合树替代内核 device-mapper 的价值。

### 3.5 加密 / 校验和 / 压缩：落 FS 层，块层只传 VMO（自主结论，待 D2 裁决）

任务明确要求回答「加密/校验和落 FS 还是块层」。本文的自主结论：

1. **默认落 FS extent 层（与 06 §4.2 一致）**：per-file/per-extent 密钥 unwrap 权 = 文件句柄 right（C2 已采纳），校验和覆盖密文、压缩在加密前。这是 MeuOS 相对 dm-crypt 的最高价值点——**密钥随句柄走、撤销句柄即撤销解密权**。
2. **块层只传 VMO**：块设备/存储抽象层**不解析、不持有文件语义**，只负责把「设备扇区 ↔ VMO 字节」可靠搬运。加密卷 cap 是可选组合服务，但即便启用，它也是「整卷一密钥」的合规场景（如全盘加密的外部盘），其密钥仍以**卷密钥 cap** 表达、不脱离 capability 模型。
3. **两者不矛盾，分层清晰**：FS extent 加密面向「per-file 密钥 + 句柄 right 联动」（细粒度、与统一命名空间互锁）；块层加密卷 cap 面向「整卷透明加密、密钥=capability」（合规/外部介质）。FS 层加密时，下层块设备 cap 不需要任何加密能力；块层加密卷启用时，上层 FS 仍可在其之上再做 per-file 加密（双重加密，可选）。**块设备层自身永远只传 VMO，不内置 extent 语义。**

### 3.6 与 `.msys` 原子更新的关系（接 06 §4.3）

- **块设备层提供「稳定扇区基」**：块设备 cap 契约保证「向某 LBA 提交写，要么该扇区完整落地、要么对上层不可见（原子扇区写）」；不保证跨扇区事务。
- **`.msys` 是 FS 层概念**：原子更新 = 子树级 CoW 快照 + 命名空间原子 repoint（`06` §4.3），由 FS 服务的 CoW B-tree 与 extent 共享实现，块设备层仅作为不撕裂的底层介质。
- **崩溃一致性分工**：块设备层保证单扇区原子；FS 层用 CoW + 元数据事务保证「最后一次提交要么完整要么不可见、挂载即一致、无 fsck」（`06` §4.5）。A/B 双分区仅作引导级防砖兜底（接 `06` §6-5 / `09`），与本文块设备模型正交——`.msys` 镜像本身即落在一个块设备 cap 之上。

### 3.7 原型期最小集（MVP 清单）

| 编号 | 内容 | 优先级 | 说明 |
|------|------|--------|------|
| B1 | 用户态 virtio-blk 驱动 + 块设备 cap（READ/WRITE/IO） | 必做 | 接 10 双轨；M0/M1 启动依赖 rootfs 块设备 |
| B2 | VMO/device VMO 数据通路（submit(vmo,...)） | 必做 | 接 03 C1、A7 |

## 4. 与 03 / 06 / 10 接口边界

> 本节**只声明依赖与协同点、不替他域拍板**；结论以各子领域文档为准，跨域一致性由 doc-sync 合成 pass 回填。

### 4.1 与 设备驱动模型（10：能力网关 / 双轨 / C8 撤销锁）

- **块设备 cap 由用户态块驱动经能力网关创建并 mint 给上层**：驱动获 `MMIO/IRQ/DMA` 能力（`10` §4.6），把硬件封装为块设备 cap，只把 `BLOCK_READ/WRITE/IO`（及以下派生）交给存储组合服务 / FS。驱动不直接把 MMIO 暴露给 FS。
- **依赖 10**：设备能力签发时序（Stage 4 随根 Job 自举，`10` C8）、撤销锁序列、IOMMU 域隔离、双轨分界（高吞吐快速路径）。块设备抽象不重复定义硬件能力模型。
- **待协同**：高吞吐块设备（NVMe 10G+）是否按 `10` 双轨留核（§5 D5）；中断转发开销（接 `10` §5-1）。

### 4.2 与 内存管理（03：VMO / device VMO / pager）

- **数据通路一律走 VMO（零拷贝，接 03 A7）**：块驱动 DMA 缓冲 = **不可写 device VMO**（`03` C1）；读出的数据以普通 VMO 交给 FS；FS 经 **pager 模型**（`06` §4.4.1）把 VMO 映射给应用，内核只在缺页时向 FS/驱动请求页。
- **依赖 03**：VMO 的 COW 子、refcount 单一真相源、VMAR 层级权限、device VMO 不可写 right。块设备抽象不重复实现页表/COW，只消费 VMO 机制。
- **待协同**：VMO 的「页供应」语义（pager 接口形状，块驱动作为 DMA 供页方 vs FS 作为文件供页方如何接力）、device VMO 与普通 VMO 在 I/O 路径上的衔接（接 `03` §5-6 设备内存建模）。

### 4.3 与 文件系统（06：块设备 cap / extent 加密 / .msys / mount-capability）

- **FS 只拿它所需的块设备 cap（接 06 §4.4.5）**：FS 服务经 `10` 能力网关获得块设备的 `BLOCK_READ/WRITE/IO` cap，不直接碰 MMIO/IRQ/DMA；FS 在其上做 extent 分配 / CoW / 校验和 / 压缩 / 加密。
- **加密/校验和/压缩在 FS extent 层（接 06 §4.2）**：块设备层只传 VMO，不内置 extent 语义（§3.5）。可选「块层加密卷 cap」是组合服务，非块设备层内建（§5 D2）。
- **分区 cap / 加密卷 cap 经 mount-capability 委托（接 06 §4.1 / §4.4.2）**：`/dev/sda`、`/dev/sda1` 等由分区服务经 Service Registry 注册目录能力，FS 服务（根聚合者）经 mount-capability 委托——与 `/net`（25）、`/proc`、`/dev` 同构，统一命名空间视图。
- **依赖 06**：统一命名空间、extent 模型、`.msys` 原子更新（CoW 快照+repoint）、mount-capability 委托、密钥=capability（C2）。块设备抽象提供「稳定扇区基」，`.msys` 的原子性由 FS 层 CoW 负责（§3.6）。
- **待协同**：`/dev` 子树是由块设备/分区服务**直接**暴露目录能力，还是由 FS 服务**代理**聚合（接 `06` §6-8 代理 vs 直露边界）；多 FS 类型（ext4 兼容挂载）是否经同一「块设备 cap + mount-capability」挂入（接 `06` §6-6）。

## 5. 自主结论 + 待决项（标注是否需架构裁决）

### 5.1 自主结论

1. **块设备与存储抽象应完全用户态（用户态块驱动 + 用户态组合服务），内核只给三类机制**：块设备 capability 对象（`07`）+ VMO/device VMO 数据通路（`03`）+ capability 强制与撤销锁（`07`/`10` C8），**内核零块层逻辑**。这与 `00` A6「重服务出核缩 TCB」、FS（`06`）出核、netstack（`25` C15）出核形成同一套 lean hybrid 叙事，是「出核」原则在存储子系统的落定。
2. **块设备对象即 capability**（接 07）：句柄带 `BLOCK_*` right，权限在 mint 时一次收窄，运行期只位运算；revoke 即回收块设备权（接 10 C8 撤销锁）。
3. **分区 / 卷 / RAID = capability 组合服务**（composable，接 06 mount-capability）：输入子设备 cap、输出新 cap，每层独立用户态、可重启、受 capability 约束——用 capability 组合树取代内核 device-mapper。
4. **加密/校验和/压缩默认落 FS extent 层（密钥=capability，接 06 §4.2 / C2），块层只传 VMO**；可选「块层加密卷 cap」组合服务面向整卷透明加密合规场景，其密钥仍=capability，不与 FS 层加密矛盾（§3.5）。
5. **`.msys` 原子更新是 FS 层概念**（CoW 快照+repoint，接 06 §4.3），块设备层只提供「稳定、不撕裂的扇区基」；A/B 双分区仅防砖兜底，与本文模型正交。
6. **数据通路一律 VMO 零拷贝**（接 03 A7 / C1 device VMO）：读 DMA→device VMO→数据 VMO→FS pager→应用，内核不复制。

## 第五轮裁决回写（33-D1）

> 第五轮裁决：将 `38-第四轮收敛摘要.md` §4 登记的待升级候选 **33-D1（候选 C16+1）** 由「待第五轮裁决」升级为「已采纳」。本裁决为**自主采纳**（基于 38 §3.2 建议立场），仅追加、不删改原章节（铁律）。
> 关联：`38` §3.1 统一 rights bit 分配建议表、`38` §3.2 `BLOCK_*`/`GPU_*`/`NET_*` 不复用 `MANAGE`/`GRANT` 裁定；`33` §3.2 / §5.2 D1；`07` §4.1 rights 位图（待据 `38` §3.1 冻结）；`25`（NET_* 同构）；`06`（统一文件系统层衔接）。

### 1. 采纳结论（一句话）

**采纳 33-D1：块设备 capability 的 rights 位图采用 `BLOCK_*` 专属独立 bit，不复用 `MANAGE`/`GRANT`/`REVOKE`/`DUPLICATE` 等句柄生命周期 right；按 `38` §3.1 统一建议表冻结为 bit 23–27（共 5 个）。** 理由与 `NET_*`（`25`）/ `KEY_*`（`07` C2）/ `CFG_*`（`07` C16）/ `DBG_*`（`07` C9）完全同构——每个对象领域持独立 bit，权限随句柄走、可审计、可派生收窄。

### 2. 具体位图（据 38 §3.1 冻结）

| bit | right | 含义 | 默认 | 说明 |
|---|---|---|---|---|
| 23 | `BLOCK_READ` | 提交读请求 | 随对象 | 分区/卷/FS 服务最小读权 |
| 24 | `BLOCK_WRITE` | 提交写请求 | 随对象 | 分区/卷/FS 服务最小写权（按 device VMO 零拷贝） |
| 25 | `BLOCK_IO` | `READ`/`WRITE` 的父权：持有即代表「可对该设备做 I/O 提交」 | 随对象 | 对齐 07 收敛后「领域父权」语义，组合服务只需持 `BLOCK_IO` 即可表达具备底层 I/O 资格 |
| 26 | `BLOCK_SUBDIVIDE` | 把整盘 cap 派生/收窄为子区间 cap（分区服务必需） | 随对象（仅整盘持有者） | 经 `07` §4.5 受约束 mint：子 cap 区间与 rights 双向收窄 |
| 27 | `BLOCK_MINT_SUBDEV` | 向下游服务 mint 子设备 cap（受约束 mint，防 confused deputy） | 随对象（仅驱动/组合服务） | 接 `06` §6-2 / `07` §4.5 受约束委托；mint 权 = 自身 rights 上限 ∩ 客户端请求下限，杜绝提权 |

> **位图余量**：本裁决采用 `38` §3.1 已预留的 **bit 23–27**（该建议表全局用到 bit 38，`BLOCK_*` 居其中段而非末尾，仅为位图分组需要）。注：任务初稿曾建议「从 bit 38 之后顺延新增」，但 `38` §3.1 统一建议表已为 `BLOCK_*` 预留 23–27 中段位（与 `NET_*`/`GPU_*` 分组），本裁决沿用该收敛分配以避免与 `38` 冲突，故不另占 39+。预留 bit 39+ 留给未来设备领域（如 `MEDIA_CAPTURE` 与 `AUDIO_CAPTURE` 同构位，`35` §3.4）。`BLOCK_*`(5) + 基础 7 + `KEY_*`(2) + `CFG_*`(3) + `DBG_*`(6) + `KERNEL_PRIV`(1) + `NET_*`(4) + `GPU_*`/`DISPLAY_*`/`SURFACE_*`/`INPUT_*`(6) + `LOAD`/`VERIFY`(2) = 39 位，未超 63，无需升级 64-bit 位图（`07` §5 粒度一致）。

### 3. 取舍理由（解构型 + 多系统参照）

**3.1 为何不复用 `MANAGE`/`GRANT`（核心取舍）**
- `MANAGE`/`GRANT`/`REVOKE`/`DUPLICATE` 是**句柄生命周期**通用 right（创建/授予/回收/复制，见 `07` §4.1）。`BLOCK_*` 是**对象类型特定的 I/O/能力权**（提交读/写、派生子区间、mint 子设备）。二者语义正交：一个回答「句柄能被怎样流转」，一个回答「拿着句柄能对设备做什么」。若用 `MANAGE` 表达「块设备 I/O 权」，会把「对象能做什么」混进「句柄生命周期」，破坏 `07` §4.1「句柄即 capability、权限随句柄走」的可审计粒度。
- 与已采纳先例一致：`KEY_UNWRAP`/`KEY_WRAP`（C2）、`CFG_READ/WRITE/GRANT`（C16）、`DBG_*`（C9）、`AUDIO_*`（`35`）全都是**领域专属独立 bit、不复用 `MANAGE`/`GRANT`**。`BLOCK_*` 沿用同一范式，避免 «新 root» 式碎片（见 `07` §3.1 对 `CAP_SYS_ADMIN` 的批判）。
- **confused deputy 防护**：`BLOCK_MINT_SUBDEV` 独立成 bit，使「谁有权向谁 mint 子设备 cap」成为显式、可审计、可 revoke 的权限，而非隐含在 `GRANT` 里——直接回应 `07` §3.1 的 confused deputy 教训与 `06` §6-2 受约束 mint。

**3.2 多系统参照（为何专属 bit 是现代正确路径）**
- **Linux block layer / bio**：Linux 块设备无 capability，靠全局 `struct block_device` + uid/capability 碎片化保护，`CAP_SYS_RAWIO` 等碎片可越权（`07` §3.1 反面教材）。MeuOS 选「对象即 cap + `BLOCK_*` 独立 bit」从根上消灭该类特权碎片；分区别名、分区枚举经 `BLOCK_SUBDIVIDE` 派生而非全局可见设备名。
- **Windows storage stack**：Windows 用卷设备对象（`\Device\HarddiskVolumeN`）+ DAC/ACL，权限挂在身份而非句柄，`BitLocker` 整卷密钥与 DAC 割裂。MeuOS 取「卷设备对象 = capability 对象」的抽象思想，但权限用 `BLOCK_*` 位图而非 ACL，密钥=capability（`06` §4.2），与 Windows 整卷密钥体系划清。
- **Fuchsia block / NAND 驱动模型 + Zircon block 协议**：Fuchsia 块设备经**能力网关**交给用户态驱动，块协议（block protocol）以「FIDL 协议 + VMO 数据通路」暴露，句柄带 rights，无内核块层巨石。MeuOS `BLOCK_*` 是其 rights 位图化的直接对标：Fuchsia 的「block device 句柄 + 受控 I/O」在 MeuOS 落成 `BLOCK_IO`/`BLOCK_READ`/`BLOCK_WRITE`；其用户态驱动/NAND 模型印证「块设备驱动出核 + 数据走 VMO」是工程化成熟路径。
- **seL4 设备驱动隔离**：seL4 设备即 capability，驱动完全用户态，数据通路可形式化验证。MeuOS `BLOCK_*` 独立 bit 使「块设备 I/O 权」成为可枚举、可收窄、可形式化追踪的句柄属性，与 seL4「设备能力 + 最小权限」同构，为 `19`/`20` 可验证性预留接口。

**3.3 `BLOCK_IO` 作为父权的设计收益**
- 把 `BLOCK_IO` 设为 `READ`/`WRITE` 的父权（持有 `BLOCK_IO` 即具备底层 I/O 资格），让**存储组合服务（分区/RAID/加密卷）只需传播 `BLOCK_IO` 即可表达「我代理一个块设备」**，而不必在每次委托时展开 `READ`+`WRITE`；子区间权限仍由 `BLOCK_SUBDIVIDE` 单独收窄。这与 `07` 收敛后的「领域父权」语义（如 `AUDIO_*` 的父权思路）一致，降低 cap 组合树的宽度。

### 4. 对周边待决点的收敛（D1 带动的边界澄清）

33-D1 的采纳同时锁定了以下 `33` 周边边界（原 D3/D4/D8 的权限维度据此定稿，不另立裁决）：
- **设备枚举 / 命名**：块设备**不全局可见**（`00` A1/A4）。`/dev/sda`、`/dev/sda1` 等由分区服务经 Service Registry 注册**目录能力**，FS 服务经 `06` §4.1 mount-capability 委托——与 `/net`（`25`）/`/proc` 同构。进程要碰某块设备，必须持其 `BLOCK_*` cap，而非靠「设备名碰巧可见」。
- **I/O 提交模型**：`submit(block_cap, vmo, vmo_offset, dev_lba, len, op)` 原语（`33` §3.3）的**授权门控 = `BLOCK_*` right 位运算**：op=read 要求 `BLOCK_READ`，op=write 要求 `BLOCK_WRITE`，二者均为 `BLOCK_IO` 子集；内核在 syscall 入口做一次 rights 位与，无 request_queue 巨石、无内核内排队策略（那是驱动/组合服务内部事）。
- **与统一文件系统层（06）衔接**：FS 服务经 `10` 能力网关仅获 `BLOCK_READ`/`BLOCK_WRITE`/`BLOCK_IO` cap，不直接碰 MMIO/IRQ/DMA（`33` §4.3）；FS 在其上做 extent 分配/CoW/加密（`06` §4.2）。`BLOCK_*` 定义了「FS 能向设备要什么」的最小权限面，与 `06` §4.4.5「FS 只拿块设备 cap」闭环。
- **capability 边界 / revoke 传播**：`BLOCK_SUBDIVIDE`/`BLOCK_MINT_SUBDEV` 的 mint 受 `07` §4.5 受约束派生约束；revoke 一块 cap 即按 `07`（自研 derivation tree 增强）级联回收其派生子区间/子设备 cap 与在飞 I/O（`10` C8 撤销锁），满足拔盘/驱动崩溃 fail-closed。
