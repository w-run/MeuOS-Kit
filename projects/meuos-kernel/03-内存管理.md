# 03 - 内存管理（Memory Management）

> MeuOS 自研内核设计调研 · kernel-plan 子领域：内存管理
> 立场：外部兼容 Linux ABI（兼容层），内部自主设计；混合内核；Rust + C 混合。
> 本文为设计/规划文档，给出原型期最小集与演进路径，并说明与「统一资源命名空间 / 最小 TCB」的衔接。

---

## 1. 概述与目标

### 1.1 内存管理子系统的职责边界

内存管理（MM）在内核中承担三层职责：

1. **物理内存管理**：把有限的物理页帧（page frame）在启动时探测、登记，运行时分配给内核与进程，并回收。核心抽象是「页帧数据库（page frame database）」+ 分配器（buddy / slab）。
2. **虚拟内存管理**：在 MMU 页表之上建立地址空间（进程/内核），提供分页、大页、ASID/PCID、mmap、COW、缺页处理（page fault）。
3. **策略与隔离**：NUMA 亲和、内存回收压力、与 capability 安全模型对接，使「谁可以访问哪段内存」可由内核以最小 TCB 强制。

### 1.2 设计目标（MeuOS 具体化）

| 目标 | 含义 | 优先级 |
|------|------|--------|
| 可自举 | mcc + meuos-libc 能在自研内核上自举（路线终点） | P0 |
| Linux ABI 兼容子集 | 经兼容层 `mkit` 提供 `mmap`/`munmap`/`mprotect`/`brk`/`madvise` 等语义 | P0 |
| 最小 TCB | 关键分配/映射路径用 Rust，unsafe 收敛在 typed 边界内 | P0 |
| capability 对齐 | 内存对象（VMO 类）可作为统一资源命名空间的 capability 寻址 | P1 |
| NUMA 初步 | 多节点机器可启动并感知节点亲和，不做完整均衡 | P2 |
| 可验证 | 关键不变量（页帧归属、引用计数）可用类型/Rust 借用表达 | P1 |

### 1.3 关键约束（来自内核定位）

- **混合内核**：MM 子系统既包含运行在特权态的内核组件（页表、buddy），也通过 IPC/服务（参考 seL4/Zircon 端点 + kqueue 事件）与用户态内存服务协作。MM 自身不强制微内核化，但对象模型要向 capability/统一命名空间靠拢。
- **Rust + C 混合**：内核关键组件用 Rust（最小 TCB），但需与现有 C 基础设施（libc、兼容层）互操作。MM 是「Rust 所有权如何映射物理资源」的最佳练兵场（见 4.5）。
- **原型期务实**：先跑通「单 CPU、UMA、4 级页表、buddy + 单一 slab」的最小集，再叠加 NUMA/大页/COW 完备化。

## 2. 设计约束与上下文

### 2.1 硬件基线（mcc 已支持的 5 架构）

MeuOS 工具链 `mcc` 已覆盖 5 种架构。MM 必须适配其页表与 TLB 语义差异：

| 架构 | 页大小 | 页表级数 | 地址空间标识机制 |
|------|--------|----------|------------------|
| x86-64 | 4KB（2MB/1GB 大页） | 4 级（PML4→PDPT→PD→PT），48-bit VA | PCID（Process Context ID，Broadwell 起） |
| AArch64 | 4KB（2MB/1GB 块） | 4 级（TTBRx + 48-bit VA，可配置） | ASID（8/16-bit） |
| RISC-V | 4KB（2MB/1GB） | Sv39/Sv48 三级/四级 | ASID（可选） |
| 其余两架构 | 参照对应手册 | — | — |

> 结论：MM 的页表操作必须抽象为 `arch/mm/` 接口；ASID/PCID 统一抽象为「address space id」概念，由 arch 层分配/刷新 TLB。

### 2.2 启动早期约束

内核在 `mmu` 开启前、甚至 `buddy` 建立前就需要分配内存（用于页表本身、早期 `struct page` 数组、设备树解析）。因此需要「早期分配器（boot allocator）」。Linux 用 `memblock`（早期位图/区域分配器，先 reserve/alloc，后转交 buddy）。MeuOS 原型期可直接采用等价的 memblock 式阶段分配器。

### 2.3 兼容层约束（`mkit`）

Linux 兼容层要求 MM 至少语义上支持：`mmap`（匿名/文件/设备）、`munmap`、`mprotect`、`madvise`、`brk`/`sbrk`、`mincore` 子集、`MAP_FIXED`、`MAP_SHARED`/`MAP_PRIVATE`、`MAP_ANONYMOUS`。COW 是 `fork`（spawn 模型下为 copy/clone）与 `MAP_PRIVATE` 写入的基础。

### 2.4 安全模型约束

capability-based 安全是 MeuOS Day 1 唯一模型（`pledge`/`unveil` 沙箱）。MM 必须让「一段物理/虚拟内存」能成为可传递、可撤销的 capability，与「统一资源命名空间」对齐——这与 Zircon 的 VMO/VMAR 抽象高度契合（见 3.3、4.4）。

## 3. 业界方案对比

### 3.1 候选方案

#### A. Linux（宏内核，C，node→zone→page + buddy + SLUB）

- **物理**：`pglist_data`（node）→ `zone`（DMA/DMA32/NORMAL/HIGHMEM/MOVABLE/DEVICE）→ `struct page` 页帧数据库。`free_area[order]` 伙伴分配；per-CPU pageset 加速热路径；watermark（min/low/high）触发 kswapd 与直接回收。
- **小对象**：SLUB（per-CPU `kmem_cache_cpu` slab，降低元数据开销）；`kmalloc` 通用缓存。SLAB/SLOB/SLUB 三选一，现代默认 SLUB。
- **虚拟**：`vm_area_struct`（VMA）红黑树/链表管理区间；缺页处理支持文件映射、匿名、`MAP_SHARED` 写回、`MAP_PRIVATE` COW；大页（hugetlb / THP）。
- **TLB**：x86 PCID、ARM ASID 减少切换时全 TLB 刷新；kernel 直接映射（direct map）位于高半地址。
- **参考**：`docs.kernel.org/mm/physical_memory.html`、`rust.docs.kernel.org/kernel/mm`。

#### B. seL4（微内核，C，capability untyped，无运行期动态分配）

- **物理**：所有可用物理内存以「untyped capability」交给 root task。内核**不在运行期动态分配内存**——除少量静态内存外，物理内存完全由用户态管理。
- **分配语义**：`seL4_Untyped_Retype` 将一段 untyped 切出子 untyped 或定型为内核对象（含 frame 对象）。watermark 贪心分配，从大到小分配以避免对齐碎片；`seL4_CNode_Revoke` 回收派生对象。
- **device untyped**：`isDevice` 为真的 untyped 内核不可写，只能 retype 为 frame 供映射——严格隔离设备内存。
- **特点**：内核 TCB 极小、可形式化验证，但「用户态管理全部物理内存」要求一个有特权的 root task/内存服务，复杂度外移到用户态。
- **参考**：`docs.sel4.systems/Tutorials/untyped.html`。

#### C. Zircon（混合内核，C++，VMO/VMAR 对象）

- **物理/虚拟解耦**：VMO（Virtual Memory Object）是「一段连续虚拟内存容器」，可分页或物理（含 `zx_vmo_create_physical`）；VMAR（Virtual Memory Address Region）是「地址空间中的连续区域」，每个进程有 root VMAR，可递归 `zx_vmar_allocate` 出子 VMAR。
- **分层权限**：VMAR 具层级权限模型（父 VMAR 允许 RWX，子 VMAR 可收紧为仅 RW，禁止后续创建可执行映射）——天然契合 capability 沙箱。
- **COW 即原语**：`zx_vmo_create_child` 的 `ZX_VMO_CHILD_COPY_ON_WRITE` / `SNAPSHOT` 直接以 VMO 克隆表达 COW/快照，页面按需惰性复制。
- **地址随机化**：VMAR 分配默认全宽随机化（`ZX_VM_COMPACT` 备选紧凑随机），并支持 specific 映射做 guard page。
- **参考**：`fuchsia.dev/fuchsia-src/reference/kernel_objects/vm_object`、`vm_address_region`、`vmo_create_child`。

#### D. Theseus（Rust，intralingual 所有权设计，学术参照）

- **核心思想**：用 Rust 所有权/借用模型直接表达 OS 状态——`MappedPages` 类型拥有映射、借用表达共享，组件边界由类型而非特权级保证，live update 与故障恢复零成本。
- **对 MeuOS 的启示**：把「页帧归属」「映射生命周期」编码进类型系统，unsafe 收敛在少数 typed 边界后（如页表写入封装）。MeuOS 不必照搬「单地址空间」，但可借鉴其 ownership 映射思路（见 4.5）。
- **参考**：Theseus OS book `subsystems/memory_mapping.md`、OSDI'20。

### 3.2 取舍表

| 维度 | Linux (A) | seL4 (B) | Zircon (C) | Theseus (D) | 对 MeuOS 的启示 |
|------|-----------|----------|------------|-------------|-----------------|
| 物理内存归属 | 内核集中管理 buddy | 用户态 untyped capability | 内核 VMO，capability 可传递 | 内核+类型所有权 | 内核管理 buddy，但导出 VMO 类 capability（折中 A/C） |
| 小对象分配 | SLUB 成熟 | 无（用户态负责） | VMO 粒度，无 slab | 全局 allocator | 内核用 SLUB 类 slab；用户态服务自管 |
| 虚拟空间抽象 | VMA（内核内部） | 无（用户态建页表） | VMAR 层级 + 权限收缩 | MappedPages 所有权 | 采用 VMAR 式层级（对齐 capability/沙箱） |
| COW 表达 | 页表写保护 + refcount | 无（frame 直给） | VMO child 原语 | 借用/克隆 | VMO child 式 COW（清晰、可共享） |
| TLB 优化 | PCID/ASID 成熟 | 由用户态管理 | ASID（内核管） | 不适用 | 抽象为 arch ASID/PCID 接口 |
| 最小 TCB | 大（mm 复杂） | 极小（可验证） | 中 | 中（Rust 安全） | 关键路径 Rust，收敛 unsafe |
| Linux ABI 兼容 | 原生 | 需完整重构 | 需兼容层（Fuchsia 做法） | 难 | 保留 Linux 式 VMA/mmap 语义于兼容层 |
| NUMA | 完整（node/zone） | 由用户态 | 部分 | 弱 | 原型期 UMA，预留 node 抽象 |

## 4. MeuOS 选型建议

### 4.1 总体立场（折中 + 自主）

> **物理内存：以 Linux 式 buddy + SLUB 为内核内管理底座（务实、可自举）；对象模型：以 Zircon 式 VMO/VMAR 作为对用户态/兼容层暴露的 capability（对齐统一命名空间）；安全：以 seL4 的「设备内存不可写 + 可 revoke」与 Theseus 的所有权类型为精神约束。**

理由：
- 兼容层 `mkit` 需要 Linux 式 `mmap`/`VMA` 语义，buddy + VMA 是最小阻力的底座。
- 统一资源命名空间与 capability 安全要求内存对象「可寻址、可传递、可撤销」，VMO 类抽象最契合。
- 最小 TCB 要求关键路径用 Rust，且 unsafe 边界收敛——由 Rust 类型系统把 MM 不变量编码进去。

### 4.2 物理内存管理

#### 4.2.1 启动早期分配器（Phase 0，必做）
- 实现 `memblock` 式两阶段分配器：阶段一为「reserve/alloc」区域链表（覆盖内核镜像、设备树、早期页表）；阶段二在 buddy 建好后回收空闲区给 buddy。
- 早期页帧数据库（early `page` 数组）在开启 MMU 前用固定映射预留。

#### 4.2.2 页帧数据库（page frame database）
- 每物理页帧一结构体（暂称 `MmPage`，对应 Linux `struct page`），字段：`flags`（reserved/free/slab/locked/device）、`order`（buddy 归属）、`refcount`（映射/共享计数，COW 用）、`mapped_vmo`/私有指针、NUMA `node_id`。
- 原型期连续数组 `MmPage[]`（按最大物理地址/页大小预分配）；演进期考虑稀疏（Discontiguous/Sparsemem）以支持空洞内存。

#### 4.2.3 Buddy 分配器
- `free_area[0..MAX_ORDER]`（`MAX_ORDER` 取 10，覆盖到 4MB；大页另议），每 order 一条空闲块链表。分配：找最小够用块，递归二分；释放：与 buddy 合并。
- 锁：原型期逐 zone 自旋锁；演进期加 per-CPU 空闲页缓存（仿 Linux PCP）减少争用。
- 区分 zone：原型期 `NORMAL` + `DMA32`（DMA 设备兼容）即可；`MOVABLE` 预留给将来内存热插拔/迁移。

#### 4.2.4 SLAB / SLUB（小对象）
- 内核对象（VMA、VMO、页表页、cap 节点等）用 SLUB 式每 CPU slab：`kmem_cache`（每类型对象缓存）+ `kmalloc`（通用尺寸档，如 8/16/32/…/2048）。
- 演进期：`kmem_cache` 染色/per-CPU partial list 优化；考虑 Rust `Box`/`Vec` 在 kernel allocator 上的封装（见 4.5）。

### 4.3 虚拟内存管理

#### 4.3.1 分页与页表
- 统一抽象 `arch/mm/pagetable`：提供 `map(vaddr, paddr, flags)`、`unmap`、`walk`、`set_flags`。各架构实现 4 级（x86-64/AArch64）或 Sv39/48（RISC-V）。
- 原型期仅支持 4KB  base page；2MB/1GB 大页作为 Phase 2（见 4.7）。

#### 4.3.2 地址空间布局
- **内核态**：高半（典型 `[0xFFFF_8000_0000_0000, …]`，x86-64 惯用）存放内核映像、直接映射（direct map，物理内存线性映射，便于 `page_address`）、`vmap`/`vmalloc` 区域、固定映射（early ioremap）、守护空洞。
- **用户态**：低半用户空间，顶部留 guard hole；兼容层 `mkit` 提供 Linux 式布局（文本/数据/堆/`mmap` 区/栈，`vDSO` 等价物）。
- **ASID/PCID**：每地址空间分配一个 ASID/PCID（位宽受架构限制，x86 PCID 12-bit、ARM ASID 8/16-bit）；切换时若 ASID 复用则仅刷新该 ASID 的 TLB（x86 写 CR3 带 PCID + `INVPCID`）。全局（kernel）映射标记 global bit，跨 ASID 共享不刷新。

#### 4.3.3 缺页与 COW
- 缺页路径：匿名映射首访 → 分配零页/惰性提交；文件映射 → 经统一文件系统层读页（衔接 06）；`MAP_PRIVATE` 写 → COW。
- COW 实现：父/子共享物理页，页表项标记只读 + `MmPage.refcount>1`；写入触发缺页 → 分配新页复制、refcount 调整、重映射可写。
- 采用 Zircon 式 VMO child 作为 COW 的「用户态可见原语」（`spawn`/clone 直接用 `vmo_create_child` 语义）；内核内部仍以页表写保护 + refcount 实现。

#### 4.3.4 mmap / mprotect / munmap
- VMA 由红黑树（按地址有序，便于 `find_vma` 与 `/proc`-式查询）管理，对应 Linux `vm_area_struct`。
- `mmap`：匿名（`MAP_ANONYMOUS`）、文件（经统一文件系统的页缓存）、设备（`MAP_PHYS` 类，对接 device untyped 思想）。`MAP_SHARED` 写回共享 VMO；`MAP_PRIVATE` 私有 COW。
- `mprotect`：改 VMA 权限并刷对应 TLB；与 VMAR 层级权限模型一致（不可放宽父 VMAR 已收紧的权限）。

### 4.4 与「统一资源命名空间 / 最小 TCB」的衔接（重点）

MeuOS 三大内在方向之一是「统一资源命名空间」与「capability 安全、最小 TCB」。MM 是其支柱之一：

- **VMO 即命名空间对象**：每个 `vmo` 是一个可被统一命名空间赋予 capability 的「内存资源句柄」。进程持有 VMO capability 才能 map/unmap/clone——这与 07-安全模型 的 Day 1 capability 模型天然对接。
- **VMAR 即沙箱边界**：`pledge`/`unveil` 对内存的约束，可表达为「该进程 root VMAR 仅允许 RW、禁止可执行映射」（对齐 Zircon 的层级权限收缩），从而从类型/能力层面阻止 JIT 注入类攻击。
- **device 内存隔离**：设备 MMIO 以「不可写 untyped / device VMO」建模，内核关键代码（Rust）持有其 capability，普通进程无 capability 则无法映射——缩小 TCB 暴露面。
- **revoke 即回收**：capability 撤销（07 的安全模型）可直接触发 VMO 派生链回收，等价于 seL4 的 `Revoke`，使「内存回收」成为 capability 语义而非启发式回收。

### 4.5 Rust 所有权 / 借用如何映射 MM（避免 unsafe 滥用）

这是 MeuOS「内核关键组件 Rust」在 MM 上的落地要点：

1. **页帧归属用所有权**：`MmPage`/物理页封装为 `OwnedFrame`（拥有某物理页），Drop 时归还 buddy。跨组件传递 = 所有权转移，编译期防双重释放/悬垂。
2. **映射区间用借用**：`MappedPages<'a>` 借用 `OwnedFrame` 或 VMO，生命周期 `'a` 绑定映射有效性；映射销毁前借用不结束——把「映射未解除却释放页」变为编译错误。
3. **共享读用 `Arc`/引用计数能力**：多个 VMAR 映射同一 VMO 时，用内核 `Arc<Vmo>`（对应 `MmPage.refcount` 的 Rust 表达），写时 `Arc::make_mut` 触发 COW。
4. **mmap 锁用 guard 类型**：对齐 Linux Rust 抽象 `MmapReadGuard`/`VmaReadGuard`——持锁 = 持有 guard，锁scope 由 RAII 保证，避免遗漏解锁。
5. **unsafe 收敛边界**：页表位操作、MMIO、ASID 分配等不可避免 unsafe，封装在 `arch/mm` 与 `mm::raw` 模块；上层 `Vmo`/`Vmar`/`MappedPages` 全部 safe。借鉴 Rust-for-Linux `kernel::mm` 的 `Mm`/`MmWithUser`/`VmaRef` 思路（用不同类型区分「有用户态引用/无」的 mm 状态）。
6. **类型即不变量**：用 `VmaNew`（创建中、未插入树）与 `VmaRef`（已插入、只读借用）区分状态（对应 Linux Rust 抽象），把并发/状态错误提前到编译期。

> 注：Theseus 的「单地址空间 + 全局 allocator」过激，MeuOS 保留特权级与每进程地址空间，但吸收其「用类型编码 OS 状态」的方法。

### 4.6 NUMA 初步

- 原型期（Phase 1）：**UMA 假设**，单 node；`MmPage.node_id` 字段预留。
- Phase 2：引入 `pglist_data` 式 node 数组，buddy 每 node 独立；分配策略 `GFP_*` 含 `NODE_LOCAL` 优先_local；兼容层 `madvise(MADV_...)` 钩子对接亲和。
- Phase 3（演进）：页面迁移（`ZONE_MOVABLE` 语义）、kswapd 类异步回收、跨节点回退——仅在做内存热插拔/大机箱时启用。

### 4.7 原型期务实最小集（MVP 清单）

| 序号 | 功能 | 状态 | 说明 |
|------|------|------|------|
| M1 | 早期 memblock 分配器 | 必做 | 启动到 buddy 就绪前 |
| M2 | 页帧数据库 `MmPage` | 必做 | 连续数组，含 refcount/flags |
| M3 | buddy（NORMAL+DMA32） | 必做 | order 0..10 |
| M4 | SLUB 类 slab + kmalloc | 必做 | 内核对象分配 |
| M5 | 4 级页表（arch 抽象） | 必做 | x86-64 先，余架构迭代 |
| M6 | 内核直接映射 + 用户布局 | 必做 | 高半内核 |
| M7 | ASID/PCID 抽象与切换 | 必做 | 减少 TLB 刷新 |
| M8 | VMA + mmap/munmap/mprotect | 必做 | 兼容层基础 |
| M9 | 匿名缺页 + 零页 | 必做 | 匿名 mmap 落地 |
| M10 | COW（页表写保护 + refcount） | 必做 | spawn/clone、MAP_PRIVATE |
| M11 | VMO/VMAR 对象（capability 雏形） | P1 | 对齐统一命名空间 |
| M12 | 文件映射（接统一文件系统） | P1 | 依赖 06 |

> 最小集 = M1–M10 即可支撑 `mcc`+`meuos-libc` 自举（路线终点）。M11/M12 为 capability/文件语义增强。

### 4.8 演进路径

```
Phase 0 (M1-M4)   物理底座：memblock → buddy → slab，可在单 CPU 自举内核
Phase 1 (M5-M10)  虚拟底座：页表/布局/ASID + VMA/mmap/COW，兼容层 mkit 子集可用
Phase 2 (M11-M12) capability 化：VMO/VMAR 接入统一命名空间；文件映射接统一文件系统
Phase 3           NUMA 节点/迁移、大页(2MB/1GB)、THP 式聚合、kswapd 回收、madvise 全量
Phase 4           验证深化：关键路径（buddy/页表/COW）Rust 化 + 不变量形式化/模糊测试
```

## 5. 开放议题

1. **buddy 与 VMO 的边界**：物理内存由内核 buddy 独占管理，还是暴露「untyped」给用户态内存服务（seL4 式）？折中方案是「内核 buddy 拥有物理页，VMO 作为逻辑视图，revoke 触发回收」——需明确 revoke 与 buddy 归还的时序与锁。
2. **COW 与 VMO child 的语义一致性**：Zircon 的 `SNAPSHOT` 是急切/惰性混合，Linux 是纯页表写保护。MeuOS 用户态 clone 用 VMO child，内核内部用页表 COW，二者如何保证 refcount 单一真相源（避免双计数）。
3. **大页与 buddy 碎片**：2MB 大页需要连续 2MB 物理块，buddy 在高碎片下难满足。是否预留 `RESERVED` 大页池（hugetlb 式）还是依赖 THP 式按需聚合（写时升级 4KB→2MB）。
4. **Rust 全局 allocator 与 slab 的关系**：内核 `Box`/`Vec` 直接走 SLUB 还是独立 `GlobalAlloc`？需定义 OOM 时的 panic/降级策略（内核不容许 silent OOM）。
5. **NUMA 与 capability 的耦合**：跨节点 VMO 共享时，物理页归属哪个 node？迁移是否破坏既有 capability 引用？
6. **设备内存建模**：MMIO/帧缓冲以 device VMO 还是独立 `iomem` 子系统管理？前者统一但需防误写，后者隔离但割裂命名空间。
7. **验证范围**：最小 TCB 要求下，哪些 MM 不变量值得形式化（如页帧归属、ASID 唯一性）？是否需要 seL4 式证明辅助。
8. **与 07-安全模型协同**：`unveil` 对内存映射的约束粒度（VMO 级还是 VMAR 级）待与安全子领域对齐。
