# 01-内核架构选型

> 子领域：MeuOS 自研内核的「架构形态」选型。
> 所属团队：`kernel-plan`（指挥官—调研员模式）。
> 配套定位（来自 IMA 知识库「MeuOS / 01-总体架构」与 `projects/meuos-kernel/README.md`）：
> 外部兼容 Linux ABI（已有生态二进制可经兼容层运行），内部完全自主设计——Linux 是参照物，不是目标；
> 三大内在统一方向 = ① 统一文件系统层（内置校验和/压缩/加密 + 原子 `.msys` sysroot 更新 + 统一资源命名空间）、② spawn 模型进程管理（内建监督、资源账本 Day 1、简化信号）、③ capability-based 安全（Day 1 唯一模型、pledge/unveil 沙箱、内核关键组件用 Rust、最小 TCB）；
> IPC 取向：同步端点取 seL4/Zircon、事件通知取 kqueue、服务间通信取 Binder/XPC；
> 现状：Kit 工具链层已完成，内核处于「规划中」。
>
> 本文只论证「采用哪种内核架构形态」以及「内核态/用户态的边界划分」，不展开内存管理、调度、IPC 等子领域的内部设计（见 02–12 文档）。

---

## 1. 概述与子领域目标

### 1.1 为什么架构形态是首要决策

内核架构形态（宏内核 / 微内核 / 混合内核 / 外核）决定了**权限边界落在哪里**、**可信计算基（TCB）有多大**、**一次缺陷的爆炸半径**，以及**为兼容 Linux ABI 要付出多少性能与复杂度代价**。这是后续所有子领域设计的「地基」：内存管理、调度、IPC、文件系统、安全模型、驱动模型都只能在既定的架构边界内做文章。因此本子领域先行，输出一份可被执行层引用的「边界契约」。

### 1.2 本文要回答的问题

1. 宏/微/混合/外核四种形态，面对 MeuOS 的三大方向与 Linux ABI 兼容目标，各自的取舍是什么？
2. 结合「内建进程监督 / 最小 TCB / capability-based 安全」，宏内核的安全代价与微内核的性能/复杂度代价分别有多大，MeuOS 能否回避二者最坏的极端？
3. MeuOS 选「混合内核」时，边界具体怎么划：哪些功能**必须**留在内核态、哪些**应下沉**为用户态服务（驱动、文件系统如何摆位）？
4. 给出原型期（prototype）的**最小边界**与一条可演进到生产形态的**路径**。

### 1.3 不在本文范围内

- 内核内部数据结构、算法与具体代码（各子领域文档负责）。
- 具体 syscall 兼容清单（见 `08-Linux兼容层.md`）。
- Rust/C 的语言级分工细节（见 `02-内核语言策略.md`），本文只在「边界」层面提及语言取向。

## 2. 设计约束与上下文

### 2.1 三大内在统一方向对架构边界的硬约束

| 方向 | 对架构形态的直接约束 | 推论：应处的特权层级 |
|------|----------------------|----------------------|
| ① 统一文件系统层（校验和/压缩/加密 + 原子 `.msys` 更新 + 统一资源命名空间取代 /proc+/sys+/dev） | 文件系统是一个**策略重、代码量大、迭代快**的子系统；把它放进内核会直接膨胀 TCB，且与「统一资源命名空间」这一本应覆盖全系统的抽象相冲突 | **用户态服务**（内核仅提供受 capability 管控的资源句柄与底层块/页 I/O 能力） |
| ② spawn 模型进程管理（内建监督、资源账本 Day 1、简化信号） | 监督与资源账本是「内核机制 + 用户态策略」：内核必须内建 spawn、进程树、资源账本等**原语**，但监督策略引擎本身应是可重启的服务，否则又回到「内核里塞一个 systemd」 | 内核内建**机制**（spawn/账本/监督原语）；监督策略服务在**用户态** |
| ③ capability-based 安全（Day 1 唯一模型、pledge/unveil、关键组件 Rust、最小 TCB） | 权威（authority）必须可被内核**唯一裁决**且**可吊销**；任何「root 万能」的旁路都不允许存在；最小 TCB 要求把一切非必需代码赶出内核 | 安全参考监视器（capability 表、权限检查）**必须在内核态**，且是 TCB 的核心 |

关键张力：方向①与③都希望「把东西搬出内核以缩小 TCB」，而 Linux ABI 兼容（见 2.3）与方向②的「内建监督」又要求内核掌握足以高性能转译 syscall、并强管控进程树的机制。这正是一条**混合内核**才走得出的窄路——纯宏内核牺牲 TCB/隔离，纯微内核在 Linux 热路径上承担 IPC 往返代价，外核则彻底放弃现成 ABI。

### 2.2 与「混合内核 / Rust-C 边界」的对齐

技术选型基线已给定「混合内核；Rust+C 混合（关键组件 Rust，性能热点/底层 C）」。本文的边界划分与之对齐如下：

- **内核态 TCB 用 Rust 实现关键组件**：capability 监视器、IPC 端点、调度核心——这些正是「最小 TCB + 可被证明正确」的候选，Rust 的所有权/借用模型能在编译期消除一整类内存安全问题，降低形式化验证的入口成本（与 seL4 用 C 但需全量证明形成对照：MeuOS 用 Rust 换取「证明前先少错」）。
- **底层/性能热点用 C + 内联汇编**：异常处理、中断派发、页表操作、上下文切换、平台/HAL 汇编——这些贴近硬件、对寄存器与内存序敏感，且跨 5 架构（x86_64/i386/aarch64/riscv64/loongarch64）需要每架构一份薄垫片。
- **用户态服务用 Rust 为主**：文件系统服务、网络栈、驱动框架、监督服务——既享受内存安全，又处于内核 TCB 之外，可独立编译、独立重启、独立升级（契合「升级=换一个 `.msys` 文件」）。

### 2.3 Linux ABI 兼容目标带来的张力

MeuOS 不是从零写应用的玩具内核，它要「让已有生态二进制可运行」。这带来两条硬性压力：

1. **热路径性能**：`read/write/mmap/clone/execve` 等 syscalls 在真实负载下极高频。纯微内核若要求每个 syscall 先陷入内核、再以 IPC 转给用户态兼容服务器、再返回，带来的上下文切换与 TLB/cache 压力在 I/O 密集负载上可能吃掉可观吞吐（见 3.2 的 L4 经验——正是为此 L4 把 IPC 做得极快并让 Linux 整系统跑在 L4 之上）。
2. **语义保真**：Linux 程序隐含假设 fd、UID/GID、信号、/proc 等。把这层语义完全搬到用户态服务器重建，既要保证行为一致，又要不引入「root 逃逸」——capability 模型与 Linux 语义的映射是本项目最棘手的设计问题之一（见第 5 节）。

这两条共同说明：MeuOS 不能走「每个 syscall 一次 IPC」的教科书微内核老路，而需要一个**内核态的轻量兼容转译层（mkit 子集）**作为混合内核的「务实让步」。

## 3. 业界方案对比

### 3.1 宏内核（Linux 为代表）

- **结构**：所有核心子系统（调度、VM、FS、网络、驱动、安全）共处于同一内核地址空间，syscall 是一次廉价的特权级陷入（trap），无进程间消息往返。
- **优势**：性能最佳、生态最完整、调试直观；Linux 本身就是 MeuOS 要兼容的对象，宏内核在 ABI 保真上零成本。
- **代价（与 MeuOS 目标冲突点）**：
  - **TCB 巨大**：整个内核是一个「全有或全无」的信任域，任一驱动/文件系统的缺陷都可危及整个系统（这正是方向③「最小 TCB」要回避的）。
  - **隔离缺失**：宏内核里没有天然的「进程监督」边界，故障会拖垮全局——与方向②「内建监督、局部故障可重启」相悖。
  - **验证几乎不可能**：千万行级代码无法像 seL4 那样端到端形式化验证。
- **结论**：作为「被兼容对象」是参照物；作为「要采用的结构」与三大方向直接冲突，排除。

### 3.2 微内核（seL4 / MINIX 3 / L4 为代表）

- **结构**：内核只保留最小机制——IPC、线程/地址空间、低级 VM、capability；文件系统等全部作为用户态服务，靠 IPC 协作。
- **seL4（第三代微内核，L4 谱系）**：
  - 世界上首个被**端到端形式化验证**的通用水套内核（Klein 等，SOSP'09；从抽象规约一路证明到 C 实现），且是「最快的高保障内核」。
  - **capability-based 是唯一授权模型**，权限可细粒度授予与吊销，天然契合方向③。
  - 内核极小（C 实现约一万行级），TCB 极小。
- **MINIX 3**：
  - 约 12k 行微内核跑在内核态，其余为**用户态服务**；其「转世服务器（reincarnation server）」定期 ping 驱动，死亡/超时就杀死并重启——把「局部故障自愈」做成系统级目标，是方向②「内建监督」的现成范例。
- **L4（Liedtke 等）**：
  - 证明了「微内核可以快」：寄存器直传的极速 IPC，使 **L4Linux**（把整个 Linux 跑在 L4 之上）性能接近原生 Linux（SOSP'95）。这正面反驳了「微内核必然慢」的旧论，但也提示：**性能靠 IPC 质量，而 IPC 质量靠内核工程投入**。
- **代价**：
  - **用户态服务的工程复杂度**：构建一个靠 IPC 协作、且故障可隔离/重启的健壮服务生态，难度高于宏内核里调一个函数。
  - **驱动性能**：存储/网络驱动在用户态受 IPC 与拷贝开销影响，达到线速需要共享内存/DDE 之类的高级驱动模型，并非免费。
  - **Linux ABI 兼容成本**：每 syscall 一次 IPC 往返在热路径上是真实负担（这正是 3.1 性能优势的反面）。
- **结论**：seL4 的 capability 内核 + MINIX 3 的驱动隔离/自愈，是 MeuOS 最想继承的基因；但「每 syscall 一次 IPC」对 Linux 兼容目标过于昂贵，需改造。

### 3.3 混合内核（Windows NT / XNU(macOS) 为代表）

- **Windows NT**：分层为**用户态**与**内核态**；内核态内含一个「简单内核 + HAL + 驱动 + Executive（对象管理器、虚拟内存、I/O 管理器、进程/线程、安全参考监视器、缓存管理器、即插即用/电源）」。性能关键的服务器（文件系统、网络、图形 `win32k.sys`）实际**跑在内核态**；只有少数（smss/lsass/services）在用户态。NT 是「混合」的典型：**结构上分层，但重服务仍在核内**，为的是性能。
- **XNU（macOS/iOS）**：由 Mach 微内核（IPC、task/thread、VM）+ BSD 层（POSIX、文件系统、网络）+ IOKit（驱动框架）组成，**三者编译进同一个内核镜像、同一地址空间**。因此 XNU 的「混合」是**内部结构上的混合**，并非「Mach 在核内、BSD 在核外」的隔离边界——它的 FS/网络仍在核内，隔离性弱于 seL4/MINIX。
- **代价**：NT/XNU 的「混合」为性能把 FS/网络/图形留在核内，TCB 仍大；这与 MeuOS「最小 TCB + FS 出核」的方向③①冲突。所以其**名称（混合）可借鉴，但其边界（重服务留核）不可照搬**。
- **结论**：借「混合」之名（内核态保机制、用户态放服务），但不借其「重服务留核」之实。

### 3.4 外核（Exokernel，MIT Xok/ExOS 为代表）

- **结构**：内核**只做保护与多路复用**，把硬件资源（物理页、磁盘块、数据包流）以「安全绑定（secure binding）」直接导出给用户态；抽象层（libOS）由应用自己在用户态定制（Kaashoek 等，SOSP'97）。核心是「把保护与管理分离」，遵循端到端论证。
- **优势**：极致性能与灵活性，应用可定制 OS 抽象；资源以 capability 式绑定授予，与方向③的精神相通。
- **代价**：
  - **没有现成通用 OS**：Exokernel 主要是研究原型，缺乏通用生态；要让「已有 Linux 二进制」跑起来，需要重建整套 libOS 语义，与「兼容 Linux ABI」目标南辕北辙。
  - **安全/策略难做**：把管理权完全下放后，跨应用的资源共享、安全策略集中裁决变得困难，与方向③「内核唯一裁决」相悖。
- **结论**：其「资源以 capability 式绑定导出」的思想可吸收进 MeuOS 的资源句柄设计，但作为**整体架构形态**过于激进、且与 Linux 兼容目标不兼容，排除。

### 3.5 取舍总表

| 维度 | 宏内核(Linux) | 微内核(seL4/MINIX3/L4) | 混合内核(NT/XNU) | 外核(Exokernel) |
|------|---------------|------------------------|------------------|-----------------|
| TCB 大小 | 极大 | 极小 | 中—大（NT/XNU 把重服务留核） | 极小（内核）但 libOS 散落 |
| 故障隔离 | 弱（全核共享） | 强（服务隔离） | 中（取决于哪些留核） | 强（按应用） |
| 形式化验证可行性 | 几乎不可行 | 可行（seL4 已证） | 难 | 难 |
| Linux ABI 兼容成本 | 零（本身就是） | 高（每 syscall IPC） | 中（留核部分零成本） | 极高（需重建 libOS） |
| 驱动可重启/自愈 | 难 | 易（MINIX3 范例） | 部分（NT 驱动在核内） | 应用自管 |
| 性能 | 最佳 | 依赖 IPC 质量（L4 接近原生） | 最佳（重服务留核） | 最佳（贴近硬件） |
| 与 MeuOS 三大方向契合 | 低 | 高（①②③基因都有） | 中（名合实不合） | 低（方向③/兼容冲突） |
| 对 MeuOS 的取舍结论 | 排除（做参照） | 继承基因，改造 IPC 成本 | 借名，不借实 | 排除（吸思想） |

## 4. MeuOS 选型建议

### 4.1 推荐：微内核取向的「务实混合内核（lean hybrid）」

**明确推荐 MeuOS 采用「微内核取向的混合内核」**，并给出精确界定，避免「混合内核」一词被理解成 NT/XNU 那种「重服务留核」的形态：

> MeuOS 的内核 = 一个**极小的、Rust 实现关键的、capability 裁决唯一的内核态 TCB**（低级 VM、线程调度、capability 监视器、IPC 端点、异常/中断派发、以及一层**内核态的 Linux 兼容转译薄层 mkit**），
> **加上**把文件系统、网络栈、设备驱动等**策略重、代码量大、需可重启**的子系统下沉为**用户态、capability 受控、由内建监督原语管理的服务**。
> 相对经典微内核的唯一「务实让步」：mkit 转译层留在内核态，避免每个 Linux syscall 一次 IPC 往返。

换言之，MeuOS 在「隔离谱系」上站在 seL4/MINIX3 一侧（FS/网络/驱动出核），在「性能谱系」上通过内核态 mkit 薄层吸收宏内核的 syscall 零往返优势——这就是「微内核基因 + 一处混合让步」的 lean hybrid。

**推荐理由（与整体架构耦合）**：
- 与方向③契合：capability 监视器在核内、是 TCB 核心，且是唯一裁决点；Rust 实现降低证明前错误率。
- 与方向①契合：统一文件系统作为用户态服务，可独立以 `.msys` 原子升级、独立重启，统一资源命名空间由该服务对外暴露，不污染内核。
- 与方向②契合：spawn/资源账本/监督**原语**在内核，监督**策略服务**在用户态、可重启——内核「内建监督机制、免 systemd 内核 blob」。
- 与 Linux ABI 目标契合：内核态 mkit 薄层保住热路径性能，同时把兼容语义的「重活」（FS/网络）委托给用户态服务，避免内核膨胀。

### 4.2 内核态 / 用户态边界划分（明确清单）

**必须留在内核态（TCB，Rust 关键 + C/asm 底层）：**
- 异常、中断、陷阱的派发与底层处理（C/asm）。
- 物理页帧分配器、内核页表、内核地址空间管理（C/asm）；用户态地址空间的 capability 受控创建/映射由内核执行。
- 线程/任务调度核心、上下文切换（C/asm）。
- **capability 系统 / 安全参考监视器**：capability 表的创建、派生、吊销与每次权限检查（Rust，TCB 核心）。
- **IPC 原语**：同步端点（seL4/Zircon 取向）、消息传递与权限随附（Rust + asm）。
- **mkit Linux 兼容转译薄层**：把 Linux syscall 子集解码、做必要的语义保真，并决定「内核直接处理」还是「通过 capability 指定的句柄转发给用户态服务」（Rust/C）。这是 lean hybrid 的唯一让步层，刻意保持薄。
- 启动早期（boot/平台初始化/HAL）与多架构入口垫片（每架构 C/asm）。

**应下沉为用户态服务（Rust 为主，capability 受控，可独立重启/升级）：**
- **统一文件系统服务**（方向①）：实现校验和/压缩/加密、`.msys` 原子更新、统一资源命名空间；通过内核提供的块设备能力句柄访问存储。
- **设备驱动服务**：块设备、网卡、串口、GPU 等，按 MINIX3 思路隔离；崩溃由内建监督原语检测并重启。存储/网络驱动可用共享内存式快速路径缓解 IPC 开销。
- **网络栈服务**：协议栈在用户态，经 capability 句柄收发数据包。
- **进程监督 / 服务管理策略服务**：消费内核的 spawn/账本/监督原语，落实重启策略、资源限额——即「免 systemd」的那一层，但它是**用户态可重启服务**，不是内核 blob。
- **pledge/unveil 沙箱策略代理**：沙箱**强制**在内核（capability 监视器），**策略**由用户态设定并托管。
- **kqueue 风格事件通知服务**、**Binder/XPC 风格服务间通信**的路由（见 `05-IPC机制.md`）。

**刻意不放入内核的（明确排除）：** 文件系统逻辑、网络协议、具体设备驱动逻辑、监督策略、图形栈——这些若进核即违背最小 TCB 与方向①②③。

### 4.3 与整体架构的耦合点

- 与 `02-内核语言策略.md`：本文的边界直接定义「TCB 内用 Rust、底层 C/asm、用户态 Rust」的分工落脚点。
- 与 `03-内存管理`/`04-进程与调度`：低级 VM 与调度是内核态 TCB 的硬边界；用户态服务的地址空间由内核按 capability 创建。
- 与 `05-IPC机制`：同步端点必须内核实现（本文已划入 TCB）；事件通知/服务间通信在用户态，依赖内核 IPC 原语。
- 与 `06-文件系统`：统一 FS 是用户态服务，本文为其「出核」提供架构背书。
- 与 `07-安全模型`：capability 监视器是内核 TCB 核心，本文确立其「唯一裁决点」地位；pledge/unveil 的强制/策略分离据此落地。
- 与 `08-Linux兼容层`：mkit 薄层是内核态，本文界定其「薄」与「转译后转发」的职责上限。
- 与 `10-设备驱动模型`：驱动全量用户态化、可重启，是本文边界的直接结论。
- 与 `11-自举验证`：lean hybrid 使 TCB（Rust 关键组件）成为形式化/半形式化验证的可达目标，区别于宏内核。

### 4.4 为什么不是另外三种（一句话收口）

- **不是纯宏内核**：TCB 过大、无隔离、不可验证，与①②③全冲突。
- **不是纯微内核（教科书式每 syscall IPC）**：Linux 热路径 IPC 往返代价不可接受，故保留内核态 mkit 薄层作为唯一让步。
- **不是外核**：需重建 libOS 才能使 Linux 二进制运行，与兼容目标南辕北辙；仅吸收其「资源以 capability 式绑定导出」的思想。
- **不是 NT/XNU 式混合**：其「重服务留核」与最小 TCB/FS 出核冲突，只借「混合」之名。

## 5. 关键开放议题 / 待决问题（诚实列不确定）

以下问题不属于本文能拍板，需后续子领域调研或工程实测后回填，列为「待百思」：

1. **mkit 薄层的「薄」到底多薄？** 哪些 syscall 必须内核直接处理（如 `exit`/`sched_yield`/基础 `mmap` 匿名映射），哪些必须经 capability 转发给用户态服务（如涉及具体文件/套接字的 I/O）？需对 mkit 子集做**实测**，在「性能」与「TCB 大小」间量化取点，而非拍脑袋。
2. **用户态驱动的线速达成路径未定**：存储/网络驱动出核后，是否采用共享内存零拷贝 + 内核旁路（类 DDE/io_uring 风格）？此模型与 capability 句柄如何衔接，需要原型验证，性能是否达标存疑。
3. **capability 与 Linux 语义的映射是头号难题**：Linux 程序假设 fd、UID/GID、pid namespace、`/proc` 等。如何把这些**无 root 逃逸地**映射为 capability 派生与吊销？pledge/unveil 作为桥接是否足够覆盖「传统程序期望的隐式权限」？这是方向③能否真正 Day 1 成立的关键风险。
4. **形式化验证的现实边界**：seL4 全量验证的代价极高；MeuOS 在 MVP 阶段是否只对 Rust TCB 关键组件（capability 监视器、IPC）做**半形式化或部分证明**，而非端到端？验证目标与工具链（mcc 是否支撑 Rust 验证生态）需评估。
5. **「内建进程监督」与「免 systemd」的精确边界**：内核提供哪些原语算「内建」、监督策略服务放用户态后如何保证「监督者自身」可被监督（自举环）？这条边界需 `04-进程与调度`/`07-安全模型` 共同收敛。
6. **五架构一致性成本**：内核 TCB 跨 x86_64/i386/aarch64/riscv64/loongarch64，需每架构一份 C/asm 垫片，且 Rust 核心要「同源码异架构」（呼应 mcc 原则）。架构间页表/中断语义差异会不会逼迫 TCB 出现架构特化分支，侵蚀「最小、统一」？需评估。
7. **统一资源命名空间与 capability 的关系**：方向①要用统一命名空间取代 /proc+/sys+/dev，而这些都是传统上由内核直接暴露的。统一命名空间作为用户态 FS 服务暴露时，其「句柄」如何与 capability 监视器一一对应、如何做权限随附，是耦合设计点，尚未定稿。
8. **原型期能否先「驱动留核」再迁移**：为加快首次自举，原型是否允许少量关键驱动（如串行、简单块设备）临时在内核态，待用户态驱动框架就绪再下沉？这会与「最小 TCB」原则产生暂时性张力，需在演进路径里明确「临时」的退出条件。

### 01.1 C1=折中C：内核态保留物理内存（MM）唯一真相源
- **采纳结论（引用 `13` §3.1）**：采用「折中 C」——内核 buddy **独占**物理页帧数据库（单一真相源），VMO/VMAR 作为对用户态/兼容层暴露的 **capability 视图**；device 内存按 seL4 device-untyped 思想建模为「不可写、只能 retype 为可映射 frame」的 **device VMO**。拒绝纯 seL4（B）整体方案（纯 A 仅作内部底座、不对外暴露 capability 视图）。
- **对 01 的具体修订点**：
  1. §4.2「必须留在内核态」清单中「物理页帧分配器、内核页表、内核地址空间管理」一项，明确补述：**内核态保留物理内存（MM）的唯一真相源地位**——buddy 是物理页帧数据库的唯一所有者；VMO/VMAR 仅是经 capability 监视器暴露给用户态/兼容层的**视图**，不持有物理页所有权；device 内存以「不可写 device VMO」这一 capability 视图表达，而非裸露 MMIO。
  2. §4.1 lean hybrid 定义补述：相对纯 seL4，MeuOS 把物理内存真相源留在内核态、仅对外暴露 VMO/VMAR capability 视图，以同时满足三条硬约束——Job 配额单一真相源（04）、revoke 真回收（07）、lean hybrid 热路径免 IPC（01 §4.1）。
  3. §5-1 开放议题「mkit 薄层多薄」维持待实测，但定位从「待拍板」改为「待量化（折中 C 框架内）」。
- **与 13/15 呼应**：呼应 `00` C1 推荐裁决、18 §1「C1=折中C」；落实 `13` §3.1 四约束锁定论证（Job 配额/revoke 真回收/lean hybrid 热路径/可自举+五架构）。

### 01.2 C4（部分·架构边界）：兼容层是 capability 模型的消费方，不击穿 Day1 安全边界
- **采纳结论（引用 `15` §3.1/§C4）**：兼容层**不击穿** Day1 安全边界——无任何全局/运行期「关闭沙箱」开关；放宽仅经 per-package manifest 的 broad-unveil/capability-grant，受「来源闸（包清单）+ 账本闸（Job 账本）+ 类上限闸（封顶）」三道封顶闸约束；兼容层自身运行在受限句柄集下，是 capability 模型的**消费方**，不是特权发放方。
- **对 01 的具体修订点**：
  1. §2.3「内核态的轻量兼容转译层（mkit 子集）」补述：mkit 薄层是 capability 模型的**消费方**——它把 Linux syscall 翻译成对统一命名空间/capability 的查找与转发，权限只能来自该 Job 的 capability 集合，兼容层不持有、不发放任何越界特权，fail-closed。
  2. §4.1「lean hybrid 唯一让步层」补述：mkit 薄层刻意保持薄的第二条理由——避免其成为新的特权面；其语义边界（哪些 syscall 内核直处理 vs capability 转发）依 `24` Q11 量化、且始终在 capability 模型内。
  3. §4.4「不是纯微内核」收口补一语：兼容层不击穿沙箱是 Day1 不可让渡的架构边界。
- **与 13/15 呼应**：呼应 `00` C4 推荐裁决、18 §1「C4=不击穿」；落实 `15` §3.1 D1 三道封顶闸。

### 01.3 C6：Rust 接管边界 = 单一 arch_boot→kernel_main()
- **采纳结论（引用 `15` §3.4/§C6）**：Rust 接管边界 = 单一 `arch_boot → kernel_main()`（采纳 09 §5.7 裁决 A）；此前仅 C/asm（极薄、固定、可审计），此后 Rust 把守 capability 监视器/IPC/调度/资源账本/syscall 路由/VFS 抽象；无论何架构，Rust 接管**前**禁止任何依赖 alloc/panic 的 Rust 路径（硬约束）；i386 本应 Rust 的 TCB 以 rustc 产 `#![no_std]` `.o` 由 C 链接交付，**非降级架构**。
- **对 01 的具体修订点**：
  1. §4.2「启动早期（boot/平台初始化/HAL）与多架构入口垫片」补述：启动早期 C/asm 止于 `arch_boot`；`kernel_main()` 是 Rust TCB 接管边界，此前禁止任何依赖 alloc/panic 的 Rust 路径（硬约束）。
  2. §2.2「内核态 TCB 用 Rust」补述：Rust 接管点统一为 `kernel_main()`，与 09 §5.7 对齐；i386 经「C 链接 Rust `.o`」交付，i386 非降级架构，TCB 内存安全不丢。
  3. §5-6 五架构一致性补述：i386 差异仅在构建管线（`.o` 链接），TCB 安全与 64 位等价。
- **与 13/15 呼应**：呼应 `00` C6 推荐裁决、18 §1「C6=单一边界」；落实 `15` §3.4。

### 01.4 C8（部分·架构边界）：监视器为设备 capability 唯一 mint 点
- **采纳结论（引用 `16` §C8 + `13` §1.1）**：当 01 描述 capability 流时，明确「安全参考监视器（capability 监视器，TCB 核心）是**设备 capability 的唯一 mint 点**」——设备 MMIO/IRQ/DMA/IO port 等能力由监视器在 Stage 4 从可信拓扑树直接 mint 出窄粒度 cap，驱动不自我 mint 设备权限（避免 capability 模型被驱动旁路）；早期串口 Stage 1 直写为生死相关快速路径，Stage 5 交用户态 console，仅留 panic 应急写。
- **对 01 的具体修订点**：
  1. §4.2「capability 系统 / 安全参考监视器」一项补述：监视器是**一切 capability（含设备 cap）的唯一 mint 权威**——设备能力由监视器从可信拓扑树直接派生窄粒度 cap，驱动/兼容层为消费方，不得自 mint。
  2. §4.3 与 `10-设备驱动模型` 耦合点补述：设备 cap mint 权威=监视器，呼应 16/C8。
- **与 13/15/16 呼应**：呼应 `00` C8 推荐裁决、18 §1「C8=监视器 mint」；落实 `16` §C8。
