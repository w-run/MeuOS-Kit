# 52 - 用户系统·方案 A：以 capability 身份为核心、无传统 UID/GID 的极简现代化身份模型

> 调研 / 设计文档，由 kernel-plan 团队的「内核规划调研 agent（lite/hy3）」产出。
> 工作树：`kernel-plan` / 分支：`worktree-kernel-plan`。
> 本文是**独立新增方案文档**，**不修改** `00`–`51` 任何章节；行文末尾单列「与现有规划的衔接」而非改动既有文件。
> 定位：为 MeuOS 的**用户系统 / 身份 / 会话 / 认证**提出一个从零设计、彻底摆脱 Unix `UID/GID / 权限位 / sudo / setuid` 历史包袱的**方案 A**——把 `07` 已经定稿的 capability 模型，从「权限原语」升维成「身份的一等公民」。

---

## 0. 一句话核心

> **在 MeuOS 中，身份不是「一个数字 UID」，而是一组「不可伪造的 capability（句柄 + rights）」外加一个供人类与策略可读的「符号名」；能做什么由手上的 capability 决定，能是谁由持有对应 Principal 私钥的证明决定——内核里不存在 UID、不存在 GID、不存在 root，只有 capability 集合与它的可读投影。**

本文把 `00`/`07` 已经分别采纳的「capability 即句柄、无 root、无 uid=0 逃生舱」点状决策，**显式升维成一套自洽的用户/身份/会话/认证范式**——并把它向前推一步，补上现有规划尚未闭合的一块：**「身份」如何在 capability 世界里成为可读、可审计、可委派、但绝不参与裁决的一等抽象**。

## 1. 方案核心思想

### 1.1 Unix 把「身份」做成了什么，又背了什么包袱

传统 Unix 的「身份」是一张数字表 + 一组叠加机制，每一层都为「兼容上一层的窟窿」而生：

| 本应统一的概念 | Unix 的拆法 | 各自包袱 |
|---|---|---|
| 「你是谁」（主体标识） | `uid` / `gid` 全局整数 + `/etc/passwd` / `/etc/group` | 数字名字无意义、无法表达「多个身份叠加」、改名/合并用户要全局改号、16-bit uid 溢出 |
| 「你能做什么」（授权） | 文件上的 `rwx` 三组权限位 + owner/group/other | 三组位表达力极弱（同组人 vs 其他人无法细分）、ACL 是打补丁、粘滞位/sticky 是补丁的补丁 |
| 「临时提权」 | `setuid`/`setgid` 位 + `sudo` + `su` | setuid 二进制是 confused deputy 温床、sudo 把「输入密码→拿到 root」当成授权模型、提权路径极难审计 |
| 「特权子集」 | Linux capabilities（`CAP_*`）+ bounding set | `CAP_SYS_ADMIN` 沦为「新 root」（见 `07` §3.1，占 45%+ 用例）、与 DAC 交互出洞 |
| 「特权逃生舱」 | `uid=0` | 一切安全模型的终极后门，能力模型沦为装饰（`07` §2 已论证必须从地基消灭） |

方案 A 的立场是：**「身份」与「授权」在 Unix 里被错误地耦合进数字表，再用一堆补丁抢救；应当把「你是谁」彻底降为「你持有什么 capability」的可读投影。**

### 1.2 核心命题：身份 = Capability-Set + 符号名

方案 A 把身份拆成两个正交的部分：

1. **Capability-Set（cap-set，执行层真相）**：主体能做什么，**完全**由其持有的 capability 集合（句柄 + rights，继承自 `07` §4.1）决定。这是内核裁决的唯一依据，没有数字、没有「身份」介入。
2. **符号名（symbolic name，可读投影）**：一个字符串（如 `alice`、`billing-svc`、`netstack`），只用于人类可读、审计日志、策略文档、以及 Linux 兼容层合成视图（`00` C4 已承接「uid/gid 仅为合成视图」）。**符号名不参与任何内核裁决**——它只是 cap-set 上贴的一张标签。

关键不变量：**符号名永远可由 cap-set 推断方向之外不可信；cap-set 永远不依赖符号名**。一个进程不会「因为自称 alice 就得到 alice 的权限」——它必须持有由登录/委派链路 mint 出的、实际携带那些 rights 的句柄。这正是补上 Plan 9「客户端自报 user 字符串」信任漏洞的地方（见 §3.5）。

### 1.3 范式的四条铁律

1. **无数字 UID/GID**：内核对象里没有 `uid_t` / `gid_t` 字段。进程、文件、会话都不携带数字身份。
2. **无 root、无 sudo、无 setuid**：不存在「万能身份」或「输入口令即提权」的逃生舱。任何「需要更多权限」都只能由持 `GRANT` 的 issuer **显式重新 mint 受限句柄**（`07` §4.5 派生树）。
3. **身份是可读投影，不是裁决依据**：符号名、Principal 标签只用于审计/策略可读化；真正裁决只看 capability。
4. **认证即 capability 派生**：登录/会话的本质，是登录服务（持专门 issuer 权）验证凭据后，向会话 mint 出一组初始 capability——认证不是「切换身份」，而是「派生出一组新句柄」。

## 2. 关键抽象：Principal / Capability-Set / Session / Realm

四个抽象层层包裹，构成方案 A 的骨架。它们**全部建立在内核既有对象（handle / Job / namespace）之上**，不引入新的内核特权机制。

### 2.1 Principal（主体）——身份的可读锚点

- **是什么**：一个 `Principal` = （公钥，`符号名`）。公钥是身份的真名（不可伪造），符号名是公钥的人类可读别名。
- **注册**：Principal 的公钥在「身份注册表（identity registry）」中登记，注册表的信任锚来自 `32-安全启动` 的公钥根（档 A/B/C 分档锁定）。与 `32` D-SB1 复用同一 `VERIFY`（bit 38），**不新增 bit**。
- **内核形态**：Principal **不是**内核里的新对象类型，而是 capability 上的一个**不可伪造属性（signed attribute）**——当一个句柄由登录服务 mint 时，登录服务（持专门 issuer 权）用其私钥在句柄的派生记录里签注「本 cap-set 断言属于 Principal `alice`」。内核的 capability 监视器（`07` §4.1）校验该签名，但**裁决时忽略签名内容、只看 rights**。
- **为何不直接用数字 id**：符号名是字符串、可改名、可多人共持一个 cap-set（服务账号）、可一个自然人持多个 Principal——数字 UID 表达不了这些；而且改名不需要「全局改号」。

### 2.2 Capability-Set（cap-set）——执行的唯一真相

- **是什么**：某主体（进程/会话/服务）当前持有的全部 capability（句柄 + rights）的集合，即 `07` §4.1 的 handle/rights 模型在其上的全集投影。
- **角色**：cap-set 是「你能做什么」的**唯一裁决依据**。文件访问、IPC、设备、网络、配置——一切皆走 `07` 统一 rights 位图（基础 7 + `KEY_*`（2）+ `DBG_*`（6）+ `CFG_*`（3）+ `NET_*`（4）+ `KERNEL_PRIV`，见 `07` §4.5/C16/C17）。
- **派生与收缩**：cap-set 的演化走 `07` §4.5 的受约束 mint——复制只能收窄、跨进程授予需 `GRANT` right、revoke 经派生树传播。本方案无新增权限传播规则，只把「身份」显式标注到派生树上。
- **无隐式权限**：与 `07` §4.2 一致——cap-set 在 spawn 时显式声明、运行期只能收窄（pledge/unveil 语义），不存在「身份默认带权」。

### 2.3 Session（会话）——一次认证生命周期的能力投影

- **是什么**：一个 `Session` = 一次「已认证交互」的载体，绑定到一个 `Realm`（§2.4），内部是一个 Job 子树（`04` §4.1）+ 一个 `Session` 内核对象句柄。
- **Session 对象**：内核新增一个轻量**对象类型** `koid=session`（不新增裁决权，只是组织与审计锚点），其句柄携带 `READ/WRITE/MANAGE` 等标准 rights（复用 `07` 基础位，不新增 bit）。持有 `Session` 句柄 = 「我是该会话的成员」的凭证。
- **能力派生**：登录成功后，登录服务为该 Session mint 出**初始 cap-set**（按身份策略取交集，见 `07` §4.5 受约束 mint），挂到该 Session 的 Job 上。会话内 spawn 的子进程继承该 Job 的 cap-set 派生树——**没有「切换用户」这一步，只有「派生出受限子 cap-set」**。
- **多会话/多身份**：同一 Principal 可同时持有多个 Session（每个 Session 一个 Realm/一个 Job 子树）；一个进程也可被多个 Session 的 cap-set 共同约束（取交集）。这天然表达「我以 alice 登录，但启动的 netstack 服务以 netstack Principal 跑」——而 Unix 要 setuid+sudo 才能勉强模拟。

### 2.4 Realm（域）——能力作用域与信任边界

- **是什么**：一个 `Realm` = 一个**能力命名与作用域的容器**，是 `06` 统一资源命名空间（`00` C3 每进程 namespace）在「身份/会话」维度的对齐物。Realm 界定「哪些 capability 在此可见、可被 reveal、可被 mint」。
- **与 namespace 的关系**：`06` 的每进程 namespace 是 Realm 的**资源投影**——`unveil(path, perm)` 本质是向进程 namespace 注入路径 capability，而该 namespace 属于某个 Realm。Realm 把「身份边界」与「资源可见性边界」绑成同一个可推理单元。
- **嵌套与委托**：Realm 可嵌套（Realm 树 ⊑ Job 树 ⊑ 取消树，`04` §4.3）。父 Realm 可向子 Realm 授予受限 cap-set（经 `GRANT` 派生），子 Realm 内的 mint 上限受其接收的 rights 约束——**破 confused deputy**（与 `07` §4.5 受约束 mint 同构）。
- **与信任域对齐**：Realm 也是信任边界——跨 Realm 的交互只能走显式 IPC 端点（capability 传递），没有「同 uid 即互信」这类隐式信任。

### 2.5 四者关系图

```
       Principal (公钥 + 符号名)            ← 身份锚点（不可伪造、可读投影）
            │  登录服务验证私钥后 mint
            ▼
       Session (koid=session + Job 子树)    ← 一次认证生命周期
            │  初始 cap-set 挂在 Job 上
            ▼
       Realm (能力命名/作用域容器)          ← 会话活动的域边界（⊑ namespace ⊑ Job 树）
            │  cap-set 在此 reveal / 派生 / 收窄
            ▼
       Capability-Set (句柄 + rights 全集)  ← 执行的唯一真相，裁决只看它
```

符号名贴在每个 cap-set 上仅供审计；内核裁决路径永远只走最底层的 capability，从不向上查 Principal。

## 3. 多系统参照：解构非缝合

方案 A 不是拍脑袋，而是把五个成熟系统的「对的部件」解构出来、按 MeuOS 的 capability 地基重组，**不缝合**它们的整体范式。

### 3.1 seL4 主体（subject）——「无身份层」的极致

- **可取**：seL4 根本没有「身份」概念，权限 = CSpace 树上的 capability（`07` §3.2 已采纳其「对象即 capability」）。这证明「无 UID 也能跑完整系统」是工程事实，而非空想。
- **解构**：我们**保留其「无身份裁决」**，但**补上 Principal 作为可读层**——seL4 的短板正是审计/策略完全不可读（你得读 CSpace 树才知道「谁」能干什么）。MeuOS 用符号名 + 派生树签名补这块，而不引入 seL4 的 CNode 基数树（见 `07` §5.1 已定 Zircon 风格句柄表）。

### 3.2 Fuchsia Component Framework——Realm 与 capability routing

- **可取**：Fuchsia 的 `Realm` 是 component 的能力路由边界；component 的 `manifest` 声明它**从哪些 Realm 拿什么 capability、向哪些子 Realm 暴露什么**（capability routing），runner 按 manifest 实例化（`07` §4 已借鉴其 handle/rights + Job 树）。
- **解构**：直接采用「Realm = 能力路由边界 + manifest 声明式 reveal」作为 §2.4 的原型。但 Fuchsia 仍有一个 `fuchsia.io` 的「组件身份」隐含层与 `runner` 特权，我们**不引入 runner 特权**——runner 也只是持受限 cap-set 的普通服务，实例化权限来自其被显式授予的 `GRANT` 派生。

### 3.3 macOS 沙盒身份——entitlements + 符号（非数字）

- **可取**：macOS 的沙盒身份是 **entitlements（权利声明）+ 代码签名**，身份是**符号的、声明式的**，没有「数字 uid 决定权限」；沙盒 profile 显式列出「能访问哪些资源」。这正合「权限不与数字身份耦合」。
- **解构**：采用「身份 = 符号名 + 声明式 cap-set 清单」的 ergonomics，但把 macOS 的「沙盒 profile 是独立策略层」合并进同一套 cap-set——不另起一套沙盒引擎，避免 `07` §3.1 批评的「多机制叠加」。

### 3.4 Windows 访问令牌（token）——「身份 + 特权列表」的内核，但剥离 SID/组

- **可取**：Windows 的 **access token** 把「身份（user SID）+ 特权列表（privileges）+ 组 SID」打包成进程持有的一等对象，且特权是**显式列表、可禁用**——这比 Unix root 更近 capability。
- **解构**：我们取「token = 进程持有的一等能力包」的内核，但**剥离其 SID / 组 / 数字身份**——MeuOS 的 Session 句柄就是「token」，其内容是 cap-set，而非 SID+组。这同时消灭了 Windows「同一 token 内多个组 SID 互相提权」的一类漏洞。

### 3.5 Plan 9 用户空间——符号名本身，但用 capability 取代「自报」

- **可取**：Plan 9 里每个人/进程有一个 `user` **字符串**（符号名），没有数字 uid；这是「身份可以是符号而非数字」的早期实践，且极简。
- **解构**：这是方案 A 符号名层的精神祖先——但 Plan 9 的致命伤是 **fileserver 信任客户端自报的 `user` 字符串**（靠网络边界而非密码学保护），于是「自称 alice 即得 alice 权」。
- **关键修正**：MeuOS 的符号名**不可自报**——它必须由登录服务（持 issuer 私钥）在 cap-set 派生时**密码学签注**，内核校验签名但不裁决。这样我们拿到 Plan 9 的极简符号身份，却不继承它的信任漏洞。这是方案 A 相对 Plan 9 的实质性进步点。

### 3.6 小结：各自取了什么、弃了什么

| 系统 | 取 | 弃 |
|---|---|---|
| seL4 | 无身份裁决、纯 capability | CNode 基数树、不可读审计 |
| Fuchsia | Realm 能力路由、manifest 声明式 | runner 特权层 |
| macOS | 符号身份 + 声明式权利 | 独立沙盒策略引擎（合并进 cap-set） |
| Windows token | 进程持有一等能力包 | SID / 组 / 数字身份 |
| Plan 9 | 符号名即身份 | 客户端自报 user（改为签名不可伪造） |

## 4. 与 00 / 07 的衔接

本方案是 `07` capability 模型的**升维与补全**，不是另起炉灶；与 `00` 已采纳裁决完全一致。

| 现有规划点 | 本文如何承接 |
|---|---|
| `00` A1「capability 即句柄」 | Principal/cap-set 全部落在 handle+rights 上，无新增内核特权类型 |
| `00` A2「Day 1 唯一安全模型」 | 身份/会话/认证 Day 1 即由 capability 表达，无「先 uid 再 capability」的回退路径（`07` §2.3） |
| `00` A4「统一资源命名空间」 | Realm（§2.4）= 命名空间在身份维度的对齐物；`unveil` 即向 Realm 注入路径 capability |
| `00` A5「Job 资源账本 Day 1」 | Session 内部即一个 Job 子树；cap-set 与资源账本同源挂在 Job 上（`04` §4.4） |
| `00` C3「每进程 namespace」 | Realm ⊑ namespace，同一套 reveal 机制 |
| `00` C4「uid/gid 仅为合成视图」 | 符号名是 cap-set 的可读投影；Linux 兼容层把数字 uid/gid 合成自 cap-set（`08` 承接） |
| `07` §4.1 handle/rights | cap-set 直接复用；Principal 属性只是句柄派生记录上的签名标注 |
| `07` §4.5 受约束 mint / 派生树 | 登录 mint、会话派生、Realm 委托全部走此机制；破 confused deputy |
| `07` C16 `CFG_*` / C17 `NET_*` | 身份/会话不新增 right bit，复用既有 rights 位图 |
| `07` D-T1 `KERNEL_PRIV` | 登录服务本身只是持受限 issuer cap-set 的用户态服务，绝不持 `KERNEL_PRIV`（与「无 root」同构） |
| `32` D-SB1 公钥根 | Principal 注册表信任锚复用 `32` 公钥根，验证权威复用 `VERIFY`（bit 38），无新增 bit |
| `04` §4.1 Job / §4.3 生命周期 | Session 绑定 Job 子树；取消/异常沿树传播（结构化并发，`46` 方案 A） |

**新增内核对象**：仅 `koid=session`（轻量组织/审计锚点，不携带新裁决权）。**新增 right bit**：**无**——全部复用 `07` 既有位图，符合 `07`「right 粒度落在 Zircon ~13 区间」的定稿。

## 5. Day 1 集：登录 / 会话 / 权限委派如何由 capability 表达

Day 1 必须能自举出「第一批身份令牌」，而非事后叠加（`00` A2）。以下给出最小可用集。

### 5.1 登录（login）——认证即 mint

1. 用户向 `logind`（持 `ID_ISSUER` 类 issuer cap-set 的用户态服务）呈递凭据：挑战-应答签名（用 Principal 私钥签随机数），或由 `32` 安全启动链传递的平台凭据。
2. `logind` 用身份注册表公钥验证签名 → 查该 Principal 的策略（允许哪些初始 rights、归入哪个 Realm）。
3. `logind` **mint 出该 Session 的初始 cap-set**（按策略取「issuer 上限 ∩ Principal 策略」交集，`07` §4.5 受约束 mint），挂到一个新建 Job 上，并返回 `Session` 句柄。
4. 内核在 cap-set 派生记录上**签注**「本 Session 断言 Principal `alice`」——仅供审计，不参与裁决。
5. 后续该 Session 内 spawn 的进程，继承该 Job 的 cap-set 派生树（只能收窄）。

> 没有「密码正确 → 变成 root」、没有 `setuid login`、没有 `/etc/shadow` 全局可读风险（凭据验证在服务内、受 cap-set 约束）。

### 5.2 会话（session）——一个带 cap-set 的 Job 子树

- 图形登录、SSH 登录、服务账号启动，在机制上**无差别**：都是「验证凭据 → mint Session cap-set → 挂 Job」。区别只在策略（人会话 vs 服务账号的 cap-set 宽度、Realm 归属）。
- 会话注销 = 取消该 Session 的 Job 子树（结构化取消，`46` 方案 A §1.3），所有子进程随 scope 退出被回收——无游离孤儿、无僵尸。
- 多会话切换：每个 Session 独立 Job 子树 + 独立 Realm；「切换用户」= 切到另一个 Session 的 `Session` 句柄，而非改全局 uid。

### 5.3 权限委派（delegation）——取代 sudo / setuid

- **传统 sudo**：「输入密码 → 拿到 root」。方案 A 里**不存在**：要「以 billing-svc 身份跑一个一次性任务」= 向 `ID_ISSUER` 申请 mint 一个「断言 Principal `billing-svc`、且 rights 受限」的临时 cap-set，由策略显式收窄、可 revoke、可审计。
- **传统 setuid 二进制**：映射为「该二进制以受限 spawn 启动 + 显式授予的受限 cap-set」（`00` C4 已定「setuid 映射为受限 spawn + 显式 capability，不引入提权」）。二进制本身不持任何隐式特权。
- **委派即 cap-transfer**：把某句柄经 IPC 发给对端即委派（`07` §4.5），接收方获得受 `GRANT` 约束的权限子集；无「提权后再降回」捷径。所有委派进 derivation tree，revoke 可沿树传播。
- **fail-closed**：任何未被显式授予的权限请求 → `EACCES` / 越界终止（`07` §4.2 pledge/unveil 语义），不存在「默认有权」。

### 5.4 Day 1 最小能力清单（自举）

- `logind`：持 `ID_ISSUER`（受约束 mint Principal cap-set）+ 访问身份注册表（经 `VERIFY`/`READ` 受限句柄）的 cap-set；**不持** `KERNEL_PRIV` / 任何「万能」right。
- 根 Job（`09` §6.3）：初始 rights 收敛到「能拉起监督者与必要服务」，符号名标注 `init-realm`；其下服务各自 mint 受限子 cap-set。
- 审计：登录 mint、会话派生、Realm 委托全部进 `07` §5 审计 schema（结构化事件），供 `12` 可观测性消费。

## 6. 相对 Unix 摆脱的包袱与代价

### 6.1 彻底摆脱的包袱

| 包袱 | 在方案 A 中的命运 |
|---|---|
| 数字 `UID` / `GID` | 内核无此字段；符号名是唯一身份可读形式 |
| 文件 `rwx` 三组权限位 | 由 per-object rights 取代，表达力细到句柄级 |
| `setuid` / `setgid` 位 | 映射为受限 spawn + 显式 cap-set（`00` C4），不引入提权 |
| `sudo` / `su` | 无「输入口令即提权」；委派走显式受限 mint |
| `root` / `uid=0` 逃生舱 | 从地基消灭（`07` §2.3） |
| Linux `CAP_*` / `CAP_SYS_ADMIN` 新 root | 拆到具体对象 rights，绝不被整体授予（`07` §4.5） |
| `/etc/passwd` / `/etc/group` / `/etc/shadow` 全局表 | 改为密码学身份注册表 + 每 Realm 策略 |
| 文件 owner/group/other + chown/chmod 语义 | 文件不记数字属主；「属主」= 持该对象 `MANAGE` right 的 cap-set，策略可读层用符号名标注 |
| ACL / facl 叠加 | 统一进 cap-set 派生树，单一模型 |
| sticky bit / umask 充当权限 | 由 reveal/命名空间+rights 表达，无需特殊位 |

### 6.2 付出的代价（必须正视）

1. **Linux 兼容层负担**：`08` 必须把「数字 uid/gid 语义」合成自 cap-set（`00` C4 已承接「仅为合成视图」）。`chown`/`chmod`/`sudo`/`setuid` 二进制在兼容层要翻译成「受限 cap-set 操作」，部分语义（如 `chmod 4777` 的 setuid 位）只能近似或返回 `ENOSYS`。这是为摆脱包袱付的兼容税。
2. **运维习惯重构**：管理员不再「`useradd` 一个数字账号」，而是「登记一个 Principal 公钥 + 写一份 cap-set 策略」。需要新的身份管理工具链（registry CLI、策略语言）。
3. **审计/策略可读性需主动建设**：纯 capability（如 seL4）审计不可读；方案 A 靠符号名 + 派生树签名补，但**签名标注本身需要工具链渲染**，否则退化成「读 CSpace 树」。
4. **多用户 shell 体验**：传统「谁在机器上」的概念变成「当前持有哪些 Session 句柄」；`who`/`w` 类工具要重写为「枚举 Session 对象 + 其断言的 Principal 符号名」。
5. **传统文件属主语义丢失**：文件不再有「数字属主」可被 `ls -l` 直接显示；需要新的「对象 capability 视图」工具替代 `ls -l` 的权限列。
6. **人员/服务身份治理**：没有中心数字表后，「禁用某人」= revoke 其 Principal 相关派生树上的 cap-set（`07` §4.5 revoke 传播），需要治理流程确保无遗漏派生。

### 6.3 代价是否值得

值得。上述代价**全部是兼容层与工具链的表面工程**，内核模型本身因此获得：无 root 后门、无 setuid confused deputy、无 CAP_SYS_ADMIN 膨胀、权限随句柄走可局部推理、审计是局部而非全局五套机制交叉。这正是 `07` §3.1 论证的「特权机制增量加上去就拆不掉」的反面——我们从地基就是 capability，代价只在边界处。

## 7. 开放议题（留待后续轮次，不阻塞 Day 1）

1. **`ID_ISSUER` 是否需独立 right bit**：当前设计把登录 issuer 权做成「受约束 mint 的专用 cap-set」而非新 bit（复用 `GRANT` 派生语义）。是否需单列 `ID_ISSUER` bit 以强化审计粒度，待 `07` rights 位图评审时定。
2. **Session 句柄是否可跨 Realm 持有**：多 Realm 协作（如「以 alice 登录但启动 netstack 服务」）的 cap-set 交集语义，需与 `06` namespace reveal 细化。
3. **身份注册表自身的可重启性**：注册表是用户态服务还是内核托管对象？建议用户态（缩 TCB）但其公钥根锁在 `32` 信任锚，待 `09` 启动链细化。
4. **Principal 符号名改名/轮换**：公钥轮换时旧 cap-set 的签注失效策略，需与 `32` 密钥生命周期对齐。
5. **审计 schema 扩展**：登录 mint / 会话派生 / Realm 委托事件的结构化字段，需并入 `07` §5 审计 schema 与 `12` 可观测性。
