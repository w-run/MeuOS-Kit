# 48 - 内存·方案 A：以 Region/能力为基本单位的单一内存抽象

> 调研 / 设计文档，由 kernel-plan 团队的「内核规划调研 agent（lite/hy3）」产出。
> 工作树：`kernel-plan` / 分支：`worktree-kernel-plan`。
> 本文是**独立新增方案文档**，**不修改** `00`–`47` 任何章节；行文末尾单列「与现有规划的衔接」而非改动既有文件。
> 定位：为 MeuOS 的**内存与虚拟内存管理**提出一个从零设计、不被 Unix/Linux（`mmap`/`munmap`、匿名映射、全局虚拟地址空间、`page cache`、OOM-killer）历史包袱束缚的**方案 A**。

---

## 0. 一句话核心

> **在 MeuOS 中，内存只有一种抽象：带权限的能力化 Region（一个挂接进地址空间视图的 VMO 句柄）；不存在 `mmap`、不存在"进程私有线性地址空间"、不存在匿名映射与全局 `page cache`——"映射"就是把一个 VMO 句柄以特定 right 挂接（attach）进某个 AddressSpace 视图，权限随 capability 走，回收随 revoke 走。**

本文把 `00`/`03`/`07`/`06` 中已经分别采纳的 VMO 视图（C1 折中）、pager 零拷贝（A7）、capability Day1、VMO child COW 等点状决策，**升维成一套自洽的「单一内存抽象」**——并把它向前推一步，补上现有规划尚未闭合的一块：**用可传递、可命名、可撤销的 Region 对象，彻底替代 `mmap` 对"地址空间区间"的操作语义**。

## 1. 方案核心思想

### 1.1 为什么是「Region/能力」一条路

传统 Unix/Linux 把「内存」这件事，按历史演进层层堆叠出了四套互相纠缠、各自带包袱的机制：

| 本应统一的概念 | Unix/Linux 的拆法 | 各自包袱 |
|---|---|---|
| 「一段可访问的内存」 | 匿名映射 / `brk` 堆 / `mmap` 文件 / `MAP_ANONYMOUS` | 匿名 vs 文件两套语义；`brk` 是历史遗留的"堆顶游标"伪概念 |
| 「把内存放进地址空间」 | `mmap` / `munmap` / `mprotect` 操作 VMA 区间 | VMA 红黑树管理、地址碎片、`MAP_FIXED` 强占、地址稳定性承诺 |
| 「全局页缓存」 | `page cache`（文件页统一缓存）+ `swap` | 多 VFS 缓存一致性、全局 LRU 启发式、OOM-killer 全局暴力回收 |
| 「共享内存」 | `shmget`/`mmap MAP_SHARED`/POSIX shm | 命名对象 + DAC 权限割裂；与 VMO/pager 双轨 |

方案 A 的立场是：**这四件事用同一个底层原子解决**——
- **VMO（Virtual Memory Object）** 是"内存数据本身"（一段可分页/物理/设备的字节序列），不绑定任何地址空间；
- **Region** 是"挂接进某地址空间视图的一段 VMO + 一组 right"，它**本身是 capability 对象**，可命名、可传递、可继承、可 revoke；
- **AddressSpace 视图** 是"一组 Region 句柄的集合"，不是"一段线性虚拟地址空间"；
- **attach（挂接）** 把 VMO 句柄以特定 right 加入某视图，**detach（摘下）** 把它移除。

四者由同一个对象——**Region 句柄**——串联：持有 Region 句柄才"看见"这段内存、才有权以该 right 访问；没有 Region 句柄，这段 VMO 对该视图不可见、不可寻址。这正是要消灭的"全局虚拟地址空间 + 全局 `page cache`"的反面。

### 1.2 方案的四条铁律

1. **无 `mmap`/`munmap`**：不存在"在地址空间切一段区间并返回地址"的操作。所有"可见性变更"都是 attach/detach 一个 Region 句柄到/出 AddressSpace 视图。
2. **无匿名映射 / 无 `brk`**："匿名内存" = 一个无 backing 的空 VMO；"堆" = 一个带 `WRITE` right 的空 VMO Region。不存在 `MAP_ANONYMOUS` 与 `sbrk` 这种伪概念。
3. **无全局虚拟地址空间**：用户态编程模型以 **Region 句柄 + offset** 为中心，不以"裸虚拟地址指针"为中心。虚拟地址只是内核页表的内部实现细节与链接期的产物，不对外承诺稳定、不跨 Region 解引用。
4. **无独立 `page cache` / 无 OOM-killer**：文件数据经 VMO + pager 表达（已是 `06`/`07` 采纳），VMO 本身就是缺页后端，无全局缓存结构；回收由 capability revoke + Job 配额账单驱动，不是启发式 LRU 全局暴力回收。

### 1.3 「Region 即能力对象」到底能力在哪

`mmap` 是"动词"——它对一个静态的地址空间做修改。Region 是"名词"——一个独立存活、可持有、可转交的内核对象。这一从动词到名词的转化，是整个方案 A 区别于 `03` 现有 VMO/VMAR 模型（VMAR 仍是"地址空间里的一段"，带 `mmap` 影子）的本质：

- 一个 VMO 可被同一进程以**多个不同 right 的 Region** 挂接（如只读+执行 Region 给代码、读写 Region 给数据）；
- 同一个 VMO 可被**多个进程的多个 Region** 挂接，天然就是"共享内存"，无需独立的 SHM 机制；
- 一个 Region 句柄可经 IPC（Channel，见 `05`）传给另一进程，对方 attach 进自己的视图——这就是 capability 化的内存委托；
- revoke 一个 Region 句柄 = 即时解除挂载、回收页表、按 COW 状态决定物理页去留；revoke 整条 VMO 派生树 = 整链回收（继承 `03` §4.4 的"revoke 即回收"）。

### 2.1 VMO（Virtual Memory Object，唯一数据持有者）

- **定义**：一段字节可寻址的内存数据对象，是"内存"本身；**不绑定任何地址空间**，因此可跨进程、跨视图自由出现（被任意多个 Region 引用）。它是 `03` §4.4「VMO 即命名空间对象」的继承与强化。
- **类型（可 retype，吸收 seL4 untyped 思想）**：
  - *空 VMO*：无 backing，"匿名内存"的本尊（无 `MAP_ANONYMOUS` 概念）；
  - *文件-backed VMO*：由用户态 FS 服务的 pager 提供页面（零拷贝，见 `06`/`07`）；
  - *物理连续 VMO*：DMA 缓冲，内核从 DMA32 zone 取连续页封成；
  - *device VMO*：MMIO/帧缓冲，继承 C1 折中 C 的"不可写"固有权限。
- **句柄即 capability**：每个 VMO 句柄带 rights（见 §2.5），`vmo_create_child` / `vmo_set_pager` / 授予都受 rights 约束。

### 2.2 Region（能力化的内存区间句柄，方案 A 新核心）

- **定义**：一个特定的 VMO 句柄 + 一段 `[offset, len)` 区间 + 一组 rights + "被挂接进某 AddressSpace 视图"这一事实。Region **本身是一个内核对象、一个 capability**（有独立 handle、有独立 rights），它把"VMO 的某个区间"以特定权限"挂接"进某个视图。
- **与 `03` 的 VMAR 本质区别**：VMAR 是"地址空间里的一段区域"，`mmap` 操作它（动词语义）；Region 是"可独立存活、可传递、可命名的能力对象"（名词语义）。多个 Region 可指向同一 VMO 的不同区间/不同 right，互不干扰。
- **生命周期**：`region_attach(as_view, vmo_handle, offset, len, rights)` 创建并挂接，返回 Region 句柄；`region_detach(region_handle)` 解除挂接、回收页表、按 COW 状态决定物理页去留。没有"返回虚拟地址"的语义。
- **可见性即 capability**：一个 VMO 对该视图是否"可见、可访问"，完全取决于该视图是否持有指向它的 Region 句柄。无 Region 句柄 = 不可见、不可寻址（消灭全局虚拟地址空间的"什么都映射在一起"）。

### 2.3 AddressSpace 视图（AS 视图）

- **定义**：一个进程"可见内存"的**Region 句柄集合**，而非"一段线性虚拟地址空间"。它是 `46` 方案 A 中 Process "地址空间"的精确落地（Process = AS 视图 + 句柄表 + Thread 集）。
- **本身即 capability**：持有 AS 视图的 `MANAGE` right 才能 attach/detach Region；普通代码只持有具体 Region 句柄，不直接操作整个视图。
- **虚拟地址去哪了**：CPU 执行仍须页表映射，内核内部仍把 Region 落到某段虚拟地址（兼容 C 程序指针语义，由 `mkit` 兼容层翻译）。但**原生编程模型不暴露裸指针地址**——以 Region 句柄 + offset 访问；地址不稳定、可重定位、不可跨 Region 解引用。这是把 Theseus"用类型表达 OS 状态"与 CHERI"能力化指针"在抽象层的精神结合（见 §3.3 / §3.4）。

### 2.4 页 ownership（页归属，继承 C1 折中 C）

- **物理真相源在内核 buddy**：`MmPage.refcount` 是页 ownership 的单一真相源（C1 已采纳折中 C，拒绝纯 seL4 式把物理内存整体交用户态）。
- **三层引用，清晰分工**：
  1. *逻辑引用*：VMO 持有一段 VMO 区间对物理页的逻辑所有权（refcount 决定"VMO 还存在"）；
  2. *派生引用*：子 VMO（COW 克隆）经 `vmo_create_child(SNAPSHOT)` 派生，写时复制，惰性提交；
  3. *映射引用*：Region 持有"该页当前被映射进某视图"的事实（决定页表项存在与否）。
- **Rust 所有权映射**（继承 `03` §4.5，但把 `MappedPages` 升级为 Region）：`OwnedFrame` 拥有物理页、Drop 归还 buddy；`Region` 借用 VMO 区间、生命周期 `'a` 绑定映射有效性；共享读用 `Arc<Vmo>`、写时 `make_mut` 触发 COW；页表位操作等不可避免的 unsafe 收敛在 `arch/mm` 与 `mm::raw`。

### 2.5 能力 right（权限随 capability）

继承 `07` §4.1 基础 right 集合 `{READ, WRITE, EXECUTE, MANAGE, GRANT, REVOKE, DUPLICATE}`，落到内存对象有两层：

| 对象 | right | 含义 |
|---|---|---|
| **VMO 句柄** | `READ`/`WRITE` | 能读/写该 VMO 数据（不涉地址空间） |
| | `MANAGE` | 能 `vmo_create_child`、设 pager、retype（空→文件/设备） |
| | `GRANT` | 能经 IPC 把该 VMO 句柄传给他人（受派生树约束收窄） |
| | `REVOKE` | 能撤销派生链上的下游句柄 |
| | `DUPLICATE` | 能复制句柄（同 right 克隆） |
| **Region 句柄** | `READ`/`WRITE`/`EXECUTE` | 该挂载点能以什么权限访问（可窄于 VMO right） |
| | `MANAGE` | 能调整本 Region 的挂接/区间（不可放宽父视图已收紧的权限，对齐 `03` §4.3.4 VMAR 层级收缩） |
| | `GRANT` | 能经 Channel 把该 Region 传给另一进程（对方 attach 进其视图 = 共享内存） |

- **派生树（derivation tree）**：继承 `07` §4.5，Region/VMO 的 grant/clone 都记入派生树。revoke 一个 Region 句柄 → 解除挂载并回收页表；revoke 一个 VMO 句柄 → 触发整条派生链（含所有下游 Region）回收（= seL4 `Revoke` + `03` §4.4「revoke 即回收」）。
- **权限随 capability，不可隐式提升**：任何"需要更多权限"的诉求，必须由持有 `GRANT` 的对端显式重新授予受限句柄——不存在"提权再降回"的捷径（与 `07` 同构）。

## 3. 多系统参照（解构非缝合）

> 原则：每个参照系统只取其"解构后的内核思想"，不与其它系统缝合；明确标注"借什么、不借什么"。

### 3.1 seL4 — Capabilities + Untyped

- **借**：① Region 句柄即 capability，权限随句柄、可 revoke（`03` §4.4 / `07` Day1 已采纳）；② "untyped → retype" 思想 → VMO 可从空 retype 为文件/物理/device 类型；③ `Revoke` 触发派生链回收（方案 A 的 revoke 即回收）。
- **不借**：纯 seL4 式"运行期物理内存整体交用户态内存服务"（C1 已明确拒绝折中 B）——它破坏 Job 配额单一真相源与 lean hybrid 热路径免 IPC。内核 buddy 仍是物理页真相源。

### 3.2 Fuchsia (Zircon) — VMO

- **借**：VMO 概念（数据持有者、不绑地址空间）、VMO child `SNAPSHOT` 的 COW 原语、pager 零拷贝（`06`/`07` A7 已采纳）。
- **不借**：VMAR 的"地址空间区间 + `mmap` 影子"语义。方案 A 以 Region（可传递能力对象）取代 VMAR（静态区间），更彻底地消去 `mmap`/`munmap` 动词。

### 3.3 CHERI — 能力化指针

- **借（可选硬件加速层）**：Region 是"对象级 capability"（bounds + rights 绑定到 VMO 区间）；若硬件支持 CHERI，Region 的 bounds/rights 可由 CHERI capability 指针在指令级强制——这是"权限随 capability"的极致形态，与 Region 抽象完美互补。
- **不借**：CHERI 的"指针级 capability"粒度（每条指针都是能力）在纯软件抽象层过重；方案 A 在 Region（对象级）落地，CHERI 作为底层可选强制，二者不重叠、可叠加。

### 3.4 Multics — 段（segmentation）

- **借（精神）**：回到"段"——每个内存对象是有名、有权限、可共享的独立段，而非"平坦线性地址空间的一段"。这正是 Region 的精神祖先，且天然支持"按段共享/保护"。
- **不借**：Multics 的全局段表 + 环保护（ring protection）带来的段膨胀与性能问题。方案 A 用分页底层承载（Region 内部仍是 4KB 页表映射），用 capability 取代全局段表与环号，避免 Multics 的历史代价。

### 3.5 Apple (XNU/macOS) — 跨区域共享内存

- **借**：Apple 把系统库做成"跨进程共享的不可变只读段"（shared cache / `vm_object` 共享）；`mach_port` 经 IPC 传递内存对象。方案 A 的"同一 VMO 多个只读 Region 跨进程 attach"正是其 capability 化版本——启动时把系统代码 VMO 以只读+执行 Region 共享给所有进程，零拷贝、零重复映射。
- **不借**：XNU 仍暴露 `vm_map`/`mmap` 式地址空间操作与 DAC 权限；方案 A 用 Region 句柄替代，权限走 capability 而非 UID/DAC。

## 4. 与 MeuOS 现有规划的衔接

> 本节只"引用 + 对齐"，不修改 `00`/`03`/`04`/`06`/`07` 任何章节。

### 4.1 继承 C1 折中 C（物理归属）

`03` 第三轮回写 C1 = 折中 C（已采纳）：内核 buddy **独占**物理页帧数据库，作为 Job 配额强制与 revoke 回收的**单一真相源**；VMO/VMAR 作为 capability 视图。方案 A **完全继承这一结论**，只是把"VMAR"解构为"Region"——物理归属真相源不变，视图对象更彻底能力化。device 内存仍走不可写 device VMO（C1 子思想，继承）。

### 4.2 继承 00 A7（VMO/VMAR + pager 零拷贝）

A7 采纳"VMO/VMAR + pager 零拷贝、fork 用 VMO CoW 快照"。方案 A 保留 VMO + pager，把 VMAR 替换为 Region：`fork`/`spawn` 时用 `vmo_create_child(SNAPSHOT)` 产生 COW 子 VMO，再各自 attach 为 Region（与 `46` 方案 A 的"无 fork、spawn 显式注入句柄"完全一致——共享内存 = 显式传递同一 VMO 的 Region 句柄）。

### 4.3 继承 07 capability Day1

Region 句柄 = capability，rights 随句柄、默认拒绝、可审计、可撤销（继承 `07` §4.1/`04` §4.5）。revoke 即回收的派生树语义与 `07` §4.5 完全一致。`unveil` 对内存映射的约束粒度（原 `03` §5 开放议题 8 待对齐 07），在方案 A 下自然落到 **Region 级**（挂接时即带 right，无"先映射后 mprotect"两步），与 `06` §4.1 "路径即 capability 命名维度"在内存侧同构。

### 4.4 与 46 进程管理方案 A 的对齐

`46` 中 Process = "根 AS 视图 + 句柄表 + Thread 集"、spawn 从空地址空间 + 显式句柄注入开始。方案 A 的 AddressSpace 视图 = "Process 的根 AS 视图"，由一组 Region 句柄组成；spawn 时父把要共享/克隆的 VMO 以相应 right 的 Region 注入子视图。两条方案 A 在"无 fork、显式句柄注入、无全局命名空间"上严丝合缝。

### 4.5 对 overcommit 的态度

- **默认惰性提交（天然 overcommit-by-default）**：VMO 在缺页时才从 buddy 取物理页，写时复制，不预占。
- **但 Job 配额是承诺上限，非无限 overcommit**：Job 资源账本（Day1，已采纳 A5 / `00` A5 / `04` §4.4）对每 Job 的内存量设硬上限；超配额即 fail-closed（分配失败返回错误，**不是** OOM-killer 启发式杀进程）。这继承 `00`/`46` 的"无全局关沙箱、配额账单"精神，从根上消除 Linux OOM-killer 的不可预测性。

### 4.6 对 swap 的态度

- **swap 不是全局机制，是 pager 的一类后端**：传统 swap 是全局 `page cache` 的延伸；方案 A 中 swap = "swap-backed VMO 的 pager"——把不活跃 VMO 的页面委托给 swap 后端 pager，缺页时换入。
- **Day1 不做 swap**（UMA 自举即可），演进期把 swap 表达为 pager 实现，保持"内存只有 VMO/Region 一种抽象"的单一性，不另立独立 swap 子系统（呼应 §1.2 铁律 4）。

### 4.7 对共享内存的态度

- **共享内存不是特殊机制**：就是"把同一 VMO 的两个 Region 分别 attach 到两个 AddressSpace 视图"。无 `shmget`/`MAP_SHARED` 双语义、无 POSIX shm 命名/DAC 割裂。
- **共享即传递 Region 句柄**：经 Channel（见 `05`）把 Region 句柄发给对端，对方 attach 即共享——天然 capability 化、可 revoke、可审计（与 `05` §4.4 capability 传递同构）。

## 6. 相对传统内存管理：摆脱的包袱与代价

### 6.1 摆脱的包袱

| 传统包袱 | 方案 A 如何消去 |
|---|---|
| `mmap`/`munmap` 操作 VMA 区间 | 改为 attach/detach Region 句柄（名词语义，可传递可撤销） |
| 匿名映射 / `brk` 堆 | "匿名内存" = 空 VMO；"堆" = 带 `WRITE` 的空 VMO Region；无 `sbrk` |
| 全局虚拟地址空间 | 用户态以 Region 句柄 + offset 为中心，虚拟地址降为内核实现细节 |
| 全局 `page cache` | 文件数据 = 文件-backed VMO + pager，无独立缓存结构 |
| `MAP_SHARED`/`MAP_PRIVATE` 双语义 | 共享 = 同 VMO 多 Region；私有 = `vmo_create_child(SNAPSHOT)` |
| `madvise` 启发式（MADV_DONTNEED 等） | 用 Region 级显式操作（detach / 收缩 VMO）替代模糊提示 |
| OOM-killer 全局暴力回收 | 惰性提交 + Job 配额硬上限 + revoke 派生树回收，fail-closed 无杀进程 |
| 独立 `swap` 子系统 | swap = swap-backed VMO 的 pager 实现（演进期） |

### 6.2 代价

1. **兼容层翻译成本**：`mkit` 必须把全部 `mmap`/`brk`/`mprotect`/`madvise` 语义翻译为 VMO+Region 操作，兼容层代码量上升；但这些包袱被隔离在 `mkit` 内，不污染原生 ABI（与 `00`/`08` "兼容层翻译 Linux 语义而非暴露特权"一致）。
2. **底层页表仍存在**：CPU 执行仍需虚拟地址，内核 `arch/mm` 仍建 4 级页表、仍需 ASID/PCID 切换——这部分 `03` M5/M7 不变，unsafe 收敛在 `arch/mm` 与 `mm::raw`（继承 `03` §4.5）。
3. **Region 句柄元数据开销**：每个 Region 是内核对象（句柄表槽 + right + 区间记录），相比 VMA 红黑树节点有轻微元数据成本；但换来"可传递/可撤销/权限随句柄"的能力化收益，且元数据量与原 VMA 同量级。
4. **工具链适配**：debugger / profiler / 自观测（`12`）需读取 Region 视图而非 `/proc/pid/maps`；但这与 `06` "inspect 树替代文本伪文件"、`46` "无全局 PID 表"方向一致，统一走 capability 受约束的 introspect 视图。

---

## 7. 小结

方案 A 把 MeuOS 的内存管理从"四套纠缠的 Unix 机制"收敛为"一个以 Region/能力为基本单位的单一抽象"：VMO 持有数据、Region 是挂接进视图的能力化区间、AddressSpace 视图是一组 Region 句柄、页 ownership 真相源在内核 buddy、权限随 capability、回收随 revoke。它继承 C1 折中 C（物理归属）、00 A7（VMO+pager）、07 capability Day1、46 进程方案 A（无 fork / 显式句柄注入），并把现有 `03` 的 VMAR 解构为更彻底能力化的 Region——既摆脱 `mmap`/匿名映射/全局地址空间/`page cache` 的历史包袱，又保持与已有裁决的自洽。
