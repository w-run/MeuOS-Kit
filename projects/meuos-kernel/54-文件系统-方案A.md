## 1. 解构：先推演「文件系统应该是什么样」

### 1.1 Unix 文件系统包袱清单（我们要甩掉的）

传统 FS 把四件本不该耦合的事焊死在一起，导致后续一切「安全 / 完整性 / 原子更新 / 统一命名」都成了外挂补丁：

| 包袱 | 它是什么 | 为什么是包袱 |
|------|----------|--------------|
| **inode** | 文件身份 = 一个全局唯一整数编号，元数据挂在编号上 | 编号与内容无关 → 无法自认证、无法去重、无法「名字→内容」直接寻址；硬链接=多个名字指向同一 inode，语义歧义 |
| **可变文件** | `write()` 原地改写同一身份的内容 | 破坏完整性（写一半的窗口）、破坏可回滚（没有旧版本）、破坏去重、迫使 fsck / 日志等一致性补丁 |
| **路径即位置** | `/a/b/c` 编码了「从根到磁盘块的物理寻址链」 | 路径与物理存储绑定 → 移动=改名、复制=再存一份、跨后端/跨网络无法自然表达 |
| **挂载点** | 不同「文件系统实例」拼到全局树的不同点，`mount` 全局可见 | 命名空间碎片化、可见性默认全局、缺乏每进程最小权限、与 capability 模型割裂 |

### 1.2 推演：剥离包袱后「应该是什么样」

从第一性原理重推：

1. **内容即身份**：文件的内容一旦确定，它的名字就应该由内容本身决定（哈希）。这样哈希同时是「地址 / 完整性校验和 / 去重键 / 自认证证明」——四个角色合一。这是甩掉 inode 与「可变文件」的直接后果。
2. **写 = 产新对象，而非改旧对象**：任何「修改」都产生一个**新的不可变对象**，旧对象继续存在（直到无人引用）。可变性从「对象内部」迁移到「指向对象的引用」。
3. **目录 ≠ 物理子树，目录 = 名字→引用 的映射（且自身也是不可变快照）**：目录可变性不靠原地改表，而靠「哪个快照是当前 head」这个可变绑定（head Ref 重绑）。
4. **路径 ≠ 地址，路径 = 命名空间里的 capability 遍历**：`/a/b/c` 是「从进程命名空间根 Ref 出发，沿名字 `a`→`b`→`c` 逐级 walk Tree 得到子 Ref」的 capability 路由，与物理位置彻底解耦。

> 一句话核心：**文件是内容哈希寻址的不可变对象；目录是名字→引用的不可变映射快照，其「可变」来自 head Ref 的重绑；统一命名空间以 capability 组合覆盖一切后端，路径只是引用链而非位置。**

## 2. 方案 A 核心模型

### 2.1 四大关键抽象

```
       进程命名空间 (每进程, capability 组合树, 见 §4)
            │  spawn 时注入 path→Ref 绑定 (C3)
            ▼
   ┌───────────────── Ref (不透明引用, 携带后端ID+逻辑定位+版本) ─────────────────┐
   │   Ref ──解析──▶  Blob (内容寻址, 不可变)   │   Ref ──解析──▶  Tree (名字→Ref 映射) │
   │                      ▲ 哈希即名/校验和          │   Tree 自身也是内容寻址快照         │
   │                      │ 加密/压缩在 blob 层       │   「当前目录」= head Ref → 某版 Tree │
   └──────────────────────────────────────────────────────────────────────────────┘
            每个 Ref 经 Capability 包裹 (rights + 密钥unwrap权, 见 C2)
```

#### (1) Blob —— 内容寻址的不可变对象（第一公民）

- **身份 = 内容哈希**（建议 BLAKE2b / BLAKE3 256-bit，非 SHA-1）。哈希同时承载四职：
  - **地址**：寻址靠哈希，不靠 inode 号、不靠路径；
  - **完整性校验和**：哈希即强校验和（覆盖明文），读路径确定性验证，天然防篡改；
  - **去重键**：相同内容只存一份（与 Fuchsia blobfs 同源思想）；
  - **自认证证明**：持有哈希即能验证对象真实，无需外部信任。
- **不可变（write-once）**：Blob 一旦写入永不更改。任何「改写」= 计算新内容哈希 → 写新 Blob → 更新指向它的 Ref。
- **大文件 = chunked Blob**：超过阈值（如 1 MiB）的文件拆为定长 chunk，每个 chunk 是独立 Blob；顶层用一个「聚合 Blob」存 `[chunk-hash, chunk-hash, ...]`，整体仍是内容寻址 Merkle 树（对齐 IPFS CID / ZFS ditto block 思想）。
- **加密 / 压缩落在 blob 层**（继承 `06` §4.2）：
  - 顺序 **compress → encrypt → 内容哈希**（哈希覆盖密文，与 `06` extent 校验和「覆盖密文」一致）；
  - per-Blob 密钥，密钥 `unwrap` 权 = 文件句柄 `READ`/`WRITE` right（对齐 C2：密钥材料永不出 pager，客户端只拿明文页）；
  - 对需防篡改的系统组件（`.msys` 内），附加文件级 AEAD 认证标签（fs-verity 思想），认证密钥由 root-of-trust 派生。

#### (2) Tree —— 名字→Ref 的不可变映射（目录）

- **Tree 本身是不可变快照**：内容是 `[(name, Ref, type), ...]` 的有序映射，由内容哈希寻址（与 Blob 同机制）。这保证目录也享受去重、完整性、CoW。
- **「目录可变」= head Ref 重绑**：每个可见目录有一个可变的 **head Ref**，指向「当前生效的 Tree 快照」。`mkdir` / `rename` / `unlink` / 写文件 = 构造新 Tree 快照（CoW 复用未改子树引用，O(共享深度)）→ 把 head Ref 原子重绑到新快照。
- 因而 **目录的任意历史版本都是一等对象**：快照、回滚、per-process 灰度都只是「指向不同 Tree 快照的 head Ref」——这正是 `06` §4.3 原子 `.msys` 更新在目录层的内建泛化。
- Tree 的子项 `Ref` 可指向 Blob（文件）、Tree（子目录）、或**跨后端 Ref**（见 §3 统一命名空间）。

#### (3) Ref —— 不透明引用 / 命名空间的「边」

- Ref 是命名空间里的有向边，携带：
  - **后端 ID**（local-extent / mem / net / ipfs-like / ...）—— 与物理位置解耦的关键；
  - **逻辑定位**（内容哈希，或后端内逻辑 ID；跨后端时后端解析器把 Ref 翻译成物理块）；
  - **版本/快照提示**（可选，用于表达「指向某历史 Tree 快照」）。
- **路径 ≠ Ref**：路径是名字链，Ref 是链上的每一跳结果。解析 `/a/b/c` = 从根 Ref 出发，取 head Tree → 查 `a` 得 Ref → 解析得 Tree → 查 `b`... 逐级 capability 路由（无全局表，对齐 `06` §4.1）。
- Ref 多别名天然表达「同一内容出现在多路径而物理只存一份」（替代硬链接的歧义语义）。

#### (4) Capability —— 访问权限凭证（继承 `06` / C2 / C3）

- Capability = `Ref` + `rights` 位图，是客户端持有的句柄。rights 复用 `06` §4.4.3 / C2：`READ` / `WRITE` / `EXECUTE` / `MANAGE`。
- **密钥 unwrap 权隐于 `READ`/`WRITE`**（C2 定稿）：客户端持 `READ`/`WRITE` 文件句柄即可解密读/加密写，但 `KEY_UNWRAP`/`KEY_WRAP` 为 FS 服务端专用位，永不出 pager；revoke 句柄即回收 VMO/pager 上下文、停止解密（无独立 KRL）。
- **路径即 capability 命名维度**（C3）：`unveil(path, rwc)` = 向进程命名空间注入一条 `path→Ref` 的 capability 绑定；进程没绑定的路径对其「根本不存在」（默认全不可见，显式 reveal）。
- 跨后端 Ref 同样受 capability 约束：访问远端后端需持有该后端的「后端能力」，由 mount-capability 委托（见 §3.2）。

### 2.2 写语义：不可变模型如何对外暴露「可写文件」

文件系统对外仍需支撑 Linux 兼容层（`08`）的 `open(O_RDWR)` / `write` / `mmap(PROT_WRITE)`。方案 A 内部全不可变，映射策略：

- **`write(fd, buf)`**：兼容层 / FS 服务在用户态持有「可写视图」句柄，累积写操作（delta buffer）；`close` / `fsync` 时把 delta 应用到原 Blob（或 chunked Tree）生成新内容 → 计算新哈希 → 写新 Blob → 更新父 Tree 的 head Ref。对外表现为「文件被改了」，内部是「换了不可变对象」。
- **`mmap(PROT_WRITE)`**：以 VMO 映射当前 Blob 页（零拷贝，依赖 `03` pager）；缺页由 FS 服务 pager 供页（解密后明文）。用户写脏页 → 触发 `close`/`msync` 时把脏页 commit 为新 Blob + 更新 head Ref（CoW 语义，旧 Blob 仍在，其他持有旧 Ref 的进程不受影响）。
- **随机改写 / 数据库类**：单 Blob 不适合原地随机写；用 chunked Tree，仅重写涉及 chunk 的新 Blob，父聚合 Blob 与上层 Tree 重绑（最小化写放大）。数据库 `O_DIRECT`/原子写由 `06` §3.4 F2FS 思想在 chunk 层处理。
- 该映射使「POSIX 可变语义」成为**命名空间层之上的投影**，内核对象模型始终保持不可变纯洁——这是方案 A 相对 `06`（内核仍见可变文件）的根本分野。

## 3. 统一命名空间覆盖所有存储后端（解构「挂载点」）

### 3.1 后端只是一池 Blob 的「存放处」

方案 A 把存储后端抽象为「能存 / 取 / 校验 Blob 的池」，与 POSIX 卷/分区概念解耦：

| 后端 | 角色 | Ref 后端 ID |
|------|------|-------------|
| local-extent | 本地磁盘，CoW extent 分配（继承 `06` §4.5） | `local` |
| mem | 内存盘（tmp / 启动早期） | `mem` |
| net | 网络块 / 对象存储（virtio-blk-over-net, 远程 FS） | `net` |
| ipfs-like | 内容寻址跨网络寻址（自认证命名） | `cid` |
| fsbridge | 兼容层桥接 ext4 / F2FS / 网络 FS（经 mount-capability） | `bridge` |

**池化（对齐 ZFS 存储池）**：所有本地容量是一个 blob 池，不预划卷/分区；Blob 按内容哈希散布到池（或按后端策略）。「文件系统」与「磁盘分区」解耦，彻底甩掉挂载点。

### 3.2 跨后端命名空间 = capability 注入，而非 mount

- 传统 `mount /dev/sdb1 /mnt` 是「把另一个 FS 实例拼到全局树、全局可见」。
- 方案 A：`/mnt` 只是进程命名空间里一条 `path → 后端根 Ref` 的绑定（capability 注入），由对应后端服务经 **mount-capability** 委托（继承 `06` §4.1 / C3：FS 服务做根聚合者 + 子树委托）。进程没该绑定就看不见 `/mnt`；可见性=权限，无全局挂载表。
- 跨后端 Ref 解析：本地 FS 服务遇到 `backend=cid` 的 Ref，经网络后端能力把哈希发给对应后端取 Blob——**路径语义对后端透明**，与 Plan 9 的「把远程树 bind 进本地命名空间」同源，但更彻底（连 Blob 级去重都跨后端生效）。

### 3.3 与 `06` 的统一命名空间同向

方案 A 的命名空间模型是 `06` §4.1（capability 组合树、每进程、FS 服务根聚合、mount-capability 委托、路径即 capability）的**强化版**：`06` 解决「统一资源层取代 /proc+/sys+/dev」；方案 A 进一步把「路径即位置」也解耦，使统一命名空间天然跨后端。`06` 已落定的 C2/C3 裁决在方案 A 中原样继承，无冲突。

## 4. 多系统参照（解构非缝合）

> 原则：逐项「借其思想 / 不借其实」，不做缝合怪。每个系统给「借鉴点 + 明确不借鉴点」。

### 4.1 Git（内容寻址 / 不可变对象模型）
- **借**：blob/tree/commit 的内容寻址（SHA 命名）、不可变对象、天然去重、内容即身份。方案 A 的 Blob/Tree 直接受此启发；head Ref 重绑 ≈ Git 的 HEAD 指针（目录可变性来自「指向哪版快照」）。
- **不借**：(a) 把「版本历史 commit DAG」作为 FS 主模型——对内核 FS 过重，每次写都记历史会爆炸；(b) O(n) 线性路径解析、慢对象库——方案 A 用 CoW B-tree 索引 Tree（继承 `06` §4.5）并保持路径 walk 可缓存；(c) 应用层、非内核零拷贝 mmap。历史由**可选**快照链承担（见 §2.1 Tree 历史即一等对象），非强制全量 DAG。

### 4.2 Plan 9（统一命名空间 / 一切皆按名寻址 / 9P）
- **借**：「一切皆文件、统一命名空间、按名寻址所有资源」；`bind` 把远程树纳入本地命名空间（即方案 A 的 mount-capability 委托前身）；walk 路径即能力遍历。这是方案 A「路径=capability 路由」的思想源头。
- **不借**：可变文件模型、fid 可变文件语义——方案 A 把文件改为不可变，可变性上移到 head Ref。

### 4.3 Fuchsia blobfs（内容寻址 / hash=完整性 / 不可变）
- **借**：blobfs「hash=名、不可变、自带完整性」是方案 A Blob 的直接范本；与 minfs 的「可读写小 FS」分工启发方案 A 的「Blob 不可变 + Tree 可写（head 重绑）」分工。
- **不借**：blobfs 纯只读、需 minfs 配可读写——方案 A 用 head Ref 重绑让 Tree 可写而不破坏 Blob 不可变性，无需独立可读写 FS；且方案 A 把加密/压缩/跨后端统一进 Blob 层（blobfs 无统一加密/跨后端）。

### 4.4 IPFS（CID / Merkle DAG / 自认证命名 / 跨网络寻址）
- **借**：CID（内容标识符）即地址、自认证命名（知道哈希即可寻址、可验证）、Merkle DAG 跨后端去重、内容寻址天然跨网络。方案 A 的 `backend=cid` Ref 与跨后端命名空间直接借鉴。
- **不借**：公网共识 / 激励层、高延迟 DHT、面向分布式存储而非本地内核 FS——方案 A 只取「内容寻址 + 自认证 + Merkle 去重」，后端解析器在信任域内（本地/受控网络），不引入公网共识。

### 4.5 ZFS（COW / 端到端校验和 / 存储池 / 快照克隆）
- **借**：(a) **存储池化**——甩掉卷/分区/挂载点，容量是一池 blob（§3.1）；(b) **端到端校验和**——Blob 哈希即端到端强校验和（ZFS 的「数据+元数据全校验和」思想推到极致：哈希即校验和，无独立 checksum 字段开销）；(c) **COW 克隆 / 快照**——Tree 快照与 head 重绑即 ZFS 克隆/O(1) 快照的内建泛化。
- **不借**：ZPL（POSIX 层）的可变文件语义、数据集/卷的层级管理——方案 A 用不可变 Blob + head Ref 取代。

### 4.6 Apple APFS 快照（O(1) 快照 + 原子 repoint / per-file 密钥）
- **借**：`06` §4.3 已采用「子树快照 + 命名空间原子 repoint + 监督灰度」；方案 A 把它推到目录层——**任意目录/Trees 的 head Ref 都能非破坏式原子重绑**（旧持有者续持旧 Tree、新进程切新视图、无需重启），正是 APFS repoint 的非破坏式内核态版本（修正 `06` §引用澄清失真 5：MeuOS repoint 非破坏）。
- **不借**：APFS 可变文件、HFS 残留、内核态实现——方案 A 不可变对象 + 用户态 FS 服务（lean hybrid）。

### 4.7 取舍总表

| 维度 | Git | Plan 9 | Fuchsia blobfs | IPFS | ZFS | APFS | **方案 A** |
|------|-----|--------|----------------|------|-----|------|-----------|
| 内容寻址 | ✓ | ✗ | ✓ | ✓ | 部分(checksum) | ✗ | **✓ Blob 哈希=名/校验和/去重** |
| 对象不可变 | ✓ | ✗ | ✓ | ✓ | ✗ | ✗ | **✓ Blob 不可变; Tree 以 head 重绑表达可变** |
| 路径=capability 路由 | ✗ | ✓(bind) | 部分 | 部分(cid) | ✗ | ✗ | **✓ 每进程 namespace + Ref 路由** |
| 跨后端统一 | ✗ | ✓(bind 远程) | ✗ | ✓(自认证) | 池化(本地) | ✗ | **✓ 后端池 + cid Ref 透明** |
| 加密/压缩内建 | ✗ | ✗ | ✗ | 可选 | 加密/压缩 | per-file key | **✓ blob 层, 密钥=capability(C2)** |
| 原子更新/回滚 | commit | 无 | 无 | 无 | 快照克隆 | repoint | **✓ head Ref 非破坏重绑 + 监督灰度** |

## 5. 与 `00` / `06` 的衔接（继承而非推翻）

| `00`/`06` 既有成果 | 方案 A 如何继承 / 强化 |
|--------------------|------------------------|
| `00` A4 统一资源命名空间 | 继承：每进程 capability 组合树；强化：路径与位置解耦，天然跨后端 |
| `06` §4.2 校验和/压缩/加密三层模型 | 继承：compress→encrypt→checksum（覆盖密文）；Blob 哈希即强校验和（更彻底，无独立 checksum 字段） |

> 关系定位：方案 A 不是 `06` 的替代，而是把 `06` 方向①推到「对象不可变」逻辑终点的**激进分支**。若工程上认为 POSIX 可变语义投影成本过高，可退回 `06` 的务实增量；两条路线共享 00/06 的全部已落定裁决，doc-sync 合成 pass 时再决定主线。

## 7. 相对传统 FS：甩掉的包袱与付出的代价

### 7.1 甩掉的包袱（收益）

- **无 inode 歧义**：身份=内容哈希，无硬链接/软链接语义分裂；多别名=多 Ref 指向同 Blob，物理一份。
- **无「写一半」窗口**：Blob 不可变，写操作要么产生新 Blob 要么不产生，崩溃一致性天然（CoW+事务，无 fsck，对齐 `06` §4.5）。
- **无路径即位置耦合**：移动/复制/跨后端都只是 Ref 操作，内容物理只存一份；统一命名空间天然跨后端。
- **无挂载点碎片化**：一切后端经 capability 注入命名空间，可见性=权限，每进程最小权限（C3）。
- **完整性 / 去重 / 自认证内建**：哈希四职合一，省去独立 checksum、去重扫描、外部信任。

### 7.2 付出的代价（需在 doc-sync / 原型基准中回填）

| 代价 | 说明 | 缓解 |
|------|------|------|
| **写放大 / GC 压力** | 每次「改写」产新 Blob；需可达性追踪 + 引用计数回收未引用 Blob（A10）。元数据/GC 是方案 A 独有负担 | Tree/聚合 Blob 的 CoW 共享复用未改子树；chunked 大文件仅重写涉及 chunk；GC 异步、低峰运行 |
| **路径解析间接** | 纯内容寻址下「按名找文件」需 walk Tree（沿 Ref 链），不如 inode 直接编号快 | Tree 是一等缓存对象，路径 walk 结果缓存于命名空间；热点路径直接 VMO 下发（对齐 `06` §6-4 pager 基准） |
| **随机改写不友好** | 数据库类原地随机写与不可变 Blob 冲突 | chunked Tree 仅重写脏 chunk；`O_DIRECT`/原子写在 chunk 层处理（`06` §3.4） |
| **POSIX 可变语义投影成本** | 兼容层 `write`/`mmap(PROT_WRITE)` 需经「可写视图→新 Blob→head 重绑」路径，比原地写多一次哈希+落盘 | 批量/延迟 commit；小文件热点仍走 VMO；与 `08` 兼容层协同基准 |
| **大文件哈希聚合开销** | 大文件拆 chunk + 聚合 Blob，哈希链更长 | chunk 阈值调优；聚合 Blob 本身内容寻址、可缓存 |
| **跨后端信任/延迟** | `backend=cid/net` 引入网络往返与信任域问题 | 信任域限定本地/受控网络；cid 自认证降低信任成本；A/B 防砖兜底（`06` §6-5 / `09`） |

### 7.3 与 `06` 的代价对比

`06` 的代价集中在「FS 用户态化 + pager 缺页 IPC 往返」（§6-4）与「A/B 防砖兜底」（§6-5）。方案 A **新增**的代价是「写放大 / GC / POSIX 投影成本」三类，但**消除**了 `06` 仍需处理的可变文件一致性窗口（方案 A 无此窗口）。整体：方案 A 用「GC + 投影」换「原生不可变带来的完整性 / 回滚 / 去重红利」——是否划算需在自举原型上用 `mcc` 真实工作负载基准判定（建议 doc-sync 时设对照实验：同一负载下 `06` 可变模型 vs 方案 A 不可变模型 的写放大与 P99 延迟）。

## 8. 待决清单（方案 A 特有，需后续回填）

1. **【架构级】head Ref 重绑的原子性边界**：目录可变性 = head Ref 重绑，重绑需是单条元数据事务（capability 级单点切换）。多进程并发改同一目录时，head 重绑的 CAS 语义与冲突解决（last-writer-win vs 合并）需与 `04`/`07` 协同定稿。
2. **【架构级】可写视图投影的 `rename`/`O_EXCL` 语义**：POSIX `rename` 原子性、`O_CREAT|O_EXCL` 在「写=新 Blob+重绑」模型下如何保证原子与无竞态，需 `08` 兼容层协同。
3. **【性能·实测】GC 开销基准**：可达性 GC（A10）在「频繁小改」负载下的 CPU/IO 峰值，是否需分代/增量 GC；与 `06` §6-4 pager 基准合并为方案 A 专属性能包。
4. **【存储·协同】跨后端 Ref 的信任模型**：`backend=cid/net` 的信任域边界、与 secure boot 根信任（`09`）如何挂钩；远端 Blob 的完整性与本地同源（哈希自认证）但可用性需兜底策略。
5. **【语言·协同】哈希/加密热路径 Rust/C 边界**：内容哈希（BLAKE3）与 per-Blob 加密热路径若 Rust throughput 不足，是否允许 C/内联汇编并经 Rust safe 封装（对齐 `02`/`06` §6-7）；密钥管理必须留 TCB 侧。
6. **【启动·协同】`.msys` 作为内容寻址 sysroot**：sysroot 本身是 Tree head Ref，`.msys` 镜像的「可启动边界」与 `09`/`11` 的 `.mimg` 关系是否沿用 `06` §6-5 结论，或改为「sysroot = 内容寻址 Tree 的可启动快照」（方案 A 倾向后者）。

> 上述为方案 A 独立待决项；`06` 已落定的 C2/C3 及 `06` §6 待决（pager 基准、A/B 兜底、mount-capability 组合语义等）在方案 A 中直接沿用，不重开。
