## 0. 一句话核心结论

> **MeuOS 的监控与审计应是 capability 模型的「镜像层」，而非第二套权限系统：审计日志本身是一个受 capability 约束的内核对象（Day1 复用 `DBG_INSPECT` 读、专属 `AUDIT` right 预留 bit48+ 待大喵拍板），由出核的审计服务消费；attestation 报告复用 `32` 度量基与 `61` `.mimg` 信任链、以 `ATTEST`=bit39 预埋远程证明、Day1 仅本地自检；运行期异常检测直接实例化 `07`/`20` 的 I1–I7 不变量与 `04` Job 账本配额——全程与 `29` 纵深第 0 层衔接、五架构同逻辑。**

## 1. 解构：「应该是什么样」——capability 世界的监控与审计

> 大喵铁律第一条：先问「应该是什么样」。在 `07` 的 capability 模型下，监控与审计的形态由底层约束直接决定，无需照搬 Linux auditd 的「全局内核审计 + root 可读」范式。

### 1.1 起点：审计是 capability 的「影子」，不是「超权视角」

`07` §1/§4 已定：权限 = 不可伪造的 handle + rights 位图；**无 root、无 uid=0 逃生舱**。这一地基对监控/审计提出两个尖锐约束：

- **审计者本身也必须持 capability**：不存在「内核审计子系统能看一切、却不受 capability 约束」的后门。审计日志的*读取*与*订阅*，与 `12` §4.2 的 inspect 树、`DBG_INSPECT` 同构——是受 rights 约束的内核对象，而非全局可读文件。
- **审计记录的是「授权事件」而非「身份行为」**：Linux auditd 记录「uid=0 做了什么」；MeuOS 没有身份，只能记录「哪个 handle（来自哪个 Job、持什么 rights）执行了什么 capability 操作」——审计的主键是**句柄 + 所属 Job + rights 摘要**，而非主体身份（`07` §4.3 三表现维度同源）。

### 1.2 监控/审计必须长在「已有地基」上，不另起炉灶

| 地基（已决） | 文档 | 监控/审计如何复用 |
|---|---|---|
| capability 监视器（唯一裁决点） | `07` §4.1 / `20` I1–I7 | 所有越权/越界在 `check_rights` 处**天然是审计事件源**——监控无需独立拦截，只需订阅裁决点的判定结果 |
| Job 资源账本（Day1 内建） | `04` §4.4 | 配额水位/超额是 DoS 探测信号；账本检查点（`20` I4）即配额异常的检测点 |
| 重服务出核（A6） | `00` A6 | 审计*消费者*（审计服务）是出核用户态服务，不进 TCB；仅「审计日志内核对象 + 事件发射」留内核，且极薄 |
| `KERNEL_PRIV` 自持权（D-T1） | `29` §3.1 / `07` §4.1 bit12 | 全局 IRQ mask、buddy 回收等内核态生死线操作若被显式授予用户态，必须记入审计（同 `DBG_POKE`/`KERNEL_PRIV`「高危权永不默认、可审计」范式） |
| 度量基双锚（第 0 层） | `32` §3.2 / `61` §3.3 | attestation 报告的输入即度量基；监控的「信任前提」由第 0 层提供，审计日志完整性可骑乘 `.msys` 校验 |

### 1.3 推演落点

1. **审计日志 = 能力受限内核对象**：一个结构化 ring（落 `kernel/audit` inspect 子树），由出核审计服务持对应 right 订阅/读取；内核侧只做「发射 + 截断 + 完整性保护」，不做策略。
2. **监控 = 不变量违反的运行时实例化**：`20` 的 I1–I7 是「设计不可违背」，`22` 的否定式测试是「实现没回归」，本文的运行时异常检测是「运行期实时发现违反苗头」——三者同构，监控规则直接翻译 I1–I7 + `04` 账本。
3. **attestation 不重造信任链**：报告格式直接引用 `32` 的 `PCR[0..4]` + `61` 的 `.mimg` 度量元数据，Day1 仅本地自检（D-SB7 已采纳），远程证明后置且依赖 `ATTEST`=bit39。

## 2. 多系统参照（聚焦「审计权模型」与「证明报告」两维）

> 横轴专看本维度关心的两维：**(a) 审计/监控的权限归属（root？capability？独立 ESF？）**；**(b) 证明报告是本地比对还是硬件 quote**。

| 系统 | 审计/监控权模型 | 证明报告形态 | 对 MeuOS 的借 / 不借 |
|---|---|---|---|
| **Linux auditd / IMA** | auditd 需 `CAP_AUDIT_WRITE`/`CAP_AUDIT_CONTROL`，但**内核审计本身全局可读、root 可改规则**；IMA 度量进 PCR 但依赖 TPM | IMA 度量日志 + TPM quote（远程证明需 TPM） | 借「度量即审计源」思想（IMA↔`32` 度量基）；**不借**「root 可改审计规则 / 全局可读」→ 代以 capability 约束 + 出核服务 |
| **Windows ETW + Defender ATP** | ETW 会话 ACL 约束；ATP 在独立安全世界做行为检测（行为审计范例） | Measured Boot 进 TPM PCR + VBS 隔离 | 借「行为检测独立于采集层」+「证明→安全世界消费」；权限模型换 capability，不换 ACL |
| **macOS Endpoint Security (ESF)** | **独立 ES 客户端**订阅内核安全事件（exec/mmap/文件），需持 ESF 授权**而非 root**——最接近「审计即 capability」 | `csreq` 代码签名 + T2/Secure Enclave 证明 | **强范本**：审计/监控 = 独立授权客户端订阅内核事件流，与 `12` 事件流 + 出核审计服务同构 |
| **Android** | 无独立审计框架；SELinux avc 拒绝日志 + `logd`；密钥证明用 **Titan M key attestation**（硬件签名 quote） | **Key/Test attestation**：由 Titan M 硬件签名声明「运行的是官方密钥/版本」 | 借「硬件签名 quote 作远程证明」范本（对应 `ATTEST`=bit39 + TPM/Titan 类芯片）；Day1 无硬件则仅本地 |
| **Fuchsia** | inspect 树（强类型、capability 守护）+ 事件流 + 用户态组件自报；**无全局审计后门** | Verified Boot 本地自检为主；证明走组件信任链 | **最贴近范本**：inspect/事件流即审计源、调试即 capability、无 TPM 强制（对齐 `32` §3.4 / D-SB7） |
| **seL4** | 证明即审计：I1–I7 机检命题使「权限语义不可违背」成为可证事实，运行期无需独立审计拦截 | 证明替代部分信任需求 | 借「不变量即审计」哲学——本文运行时检测直接实例化 I1–I7 |

> **非缝合怪宣言**：MeuOS 不拼接「Linux auditd（root 可读）+ Android Titan M quote + Windows ATP 安全世界」——而是取其**共同内核**：① macOS ESF 的「独立授权客户端订阅内核安全事件」；② Fuchsia 的「inspect/事件流即审计源、capability 守护、无 TPM 强制」；③ Android 的「硬件签名 quote 作远程证明」；④ seL4 的「不变量即审计」。落到由 `07`（capability）/ `12`（inspect+事件流）/ `32`（度量基）/ `61`（`.mimg` 信任链）唯一决定的 MeuOS 形态：审计对象 = 能力受限内核对象，证明报告 = 度量基快照。

## 3. 审计日志：能力受限的内核对象 + 出核服务消费

> 本节回答「审计日志是什么、谁读、谁写、完整性如何保」。核心命题：**审计日志是内核对象，权限随句柄走，与 `12` inspect 树同源；Day1 复用 `DBG_INSPECT` 读，专属 `AUDIT` right 预留 bit48+ 待裁决。**

### 3.1 审计日志作为内核对象（方案）

- **形态**：结构化 ring buffer，落 inspect 子树 `kernel/audit`（与 `12` §4.4 inspect 树同源，节点属性强类型：`seq` / `ts` / `origin_job` / `subject_handle` / `op` / `rights_mask` / `verdict` / `target`）。
- **发射点（内核侧，极薄）**：
  - capability 监视器 `check_rights` 的**每一次裁决**（通过 + 拒绝）— `07` §4.1 唯一裁决点天然是审计源；
  - 受约束 mint / grant / revoke（`07` §4.5 I5）— 记录 `(service, client_requested, issued)` 三元组，供后续越权探测检测；
  - `KERNEL_PRIV`（bit12）/ `DBG_POKE` 等高危权的**任何显式授予、使用、revoke**（`29` D-T1 / `17` C9-A）— 高危权永不默认、必留痕；
  - pledge 越界（`07` §4.2 → SIGABRT）、Job 账本超额（`04` §4.4 → EAGAIN）— 与异常检测（§5）共用事件；
  - `.msys` / `.mimg` 度量校验失败（`32` §3.x / `61` §3.3）— 第 0 层事件进审计。
- **截断与背压**：ring 满时按「保留拒绝类 + 高危权类、滚动丢弃 INFO 类」策略（fail-closed 不丢安全事件）；ring 配额计入**审计服务自身 Job 账本**（`04` §4.4，审计服务是出核服务、持受限句柄，不享 TCB 豁免）。

### 3.2 读取/订阅的权限模型（方案 / 权衡 / 推荐）

| 方案 | 权限归属 | 优点 | 缺点 / 取舍 | 推荐立场 |
|---|---|---|---|---|
| **A. 复用 `DBG_INSPECT`** | 审计子树即 inspect 节点，读受 `DBG_INSPECT`（bit13，子树粒度）约束（`12` §4.2） | 不引入新 right；与 `12` inspect 树完全同构；默认 deny、显式授予 | 审计读权与普通内核状态读权不区分——但审计日志含敏感句柄信息，理论上应比普通 inspect 更受限 | **Day1 推荐**：复用 `DBG_INSPECT` 子树授权，先把审计跑通；不新增原语 |
| **B. 专属 `AUDIT_READ` / `AUDIT_SUBSCRIBE`（bit48+）** | 审计对象独立 right，不复用 `MANAGE`/`GRANT`（与 `KEY_*`/`CFG_*`/`DBG_*` 同构） | 可把「审计消费者」与「普通 inspect 读者」分离；将来细粒度（如「可订阅安全事件但不可读历史 ring」） | 消耗 bit48+ 预留位（当前 `07` §4.1 注记 bit48+ 预留给 `MEDIA_CAPTURE` 等，挤占需裁决）；早期必要性不足 | **已闭环·第九轮采纳方案 A（专属 right 仅预留不分配）**：仅当确实需分离审计消费者时启用（见 §9 S1） |

> **推荐立场（百思·不引入新原语除非必要）**：Day1 采用**方案 A**——审计日志是 `kernel/audit` inspect 子树，读受 `DBG_INSPECT` 约束，由出核审计服务持有该子树粒度 handle 消费。**方案 B 的专属 `AUDIT` right 仅预留、不分配**（bit48+），待出现「普通 inspect 读者不应看到句柄级审计」的真实需求时再升格。这与 `32` D-SB7 预留 `ATTEST`=bit39 的「预埋不启用」纪律同构。

### 3.3 完整性保护（与 `.msys` 协同）

- 审计 ring 的**完整性**骑乘 `06`/`.msys` 校验：持久化审计段（或 crashdump 同载体，`12` §4.7）带 SHA-256，防静默篡改——与「文本 core 文件」反模式切割。
- 可选：审计段 Merkle 根（仿 `32` §3.2 双锚）进 `.msys` 度量基，使「审计日志未被篡改」可被下游 attestation 验证。是否独立 Merkle 还是复用 `.msys` 校验，见 §9 S3。

## 4. Attestation 报告格式（与 32 / 61 / ATTEST 协同）

> 本节定稿 attestation 报告的**字段结构**与**本地 vs 远程**两种消费模式，直接引用 `32` 度量基与 `61` `.mimg` 信任链，不重造。

### 4.1 报告字段（对齐 32 §3.1 / 61 §3.2–§5）

```
AttestationReport {
  boot_anchor_tier:    A | B | C            // 32 §3.3 / 61 §5.4 公钥根档
  pcr: {
    PCR[0] = hash(firmware→loader)          // 32 §3.1 跳 0
    PCR[1] = extend(hash(.mimg))             // 61 §5.1 跳 1，Item 0/4
    PCR[2] = extend(hash(monitor)            // 32 §3.1 跳 2 / 61 §5.2
                    || hash(init_caps_template))  // 32 D-SB4 待定输入
    PCR[3] = extend(hash(.msys volume root)) // 32 §3.1 跳 3 / 61 §5.3
    PCR[4..]= extend(hash(service_i))        // 32 §3.1 跳 4
  }
  mimg_measurement:     hash              // 61 §3.3 Item 4 内核 Merkle 根
  msys_volume_root:     hash              // 32 §3.2 双锚（ed25519 包签名 + extent Merkle）
  config_digest:        hash              // 58 §7.3 config-version 快照（配置漂移基）
  rollback_version:     u64               // 32 §3.2 版本号绑 Merkle root（防回滚）
  self_check_result:    PASS | FAIL       // 本地自检结论（软件度量寄存器冻结比对）
  signature: {                          // 见 4.2 两种模式
    local:  known_good_compare          // Day1：比对已知良值，无硬件签名
    remote: tpm_quote (signed PCR)       // 后置：硬件签名 quote
  }
}
```

### 4.2 本地自检（Day1，已采纳）vs 远程证明（后置，ATTEST=bit39）

| 维度 | 本地自检（Day1，`32` D-SB7 已采纳） | 远程证明（后置） |
|---|---|---|
| 触发 | boot 完成冻结 PCR → 向 `meu-supervisor` 报告度量值 = X；下游挂载/拉起服务前比对 | 验证者远程请求 quote |
| 签名 | **无硬件签名**，仅「比对已知良值」（`32` §3.4 软件度量寄存器） | 需 TPM/度量芯片对 PCR 签名 quote（`ATTEST`=bit39 服务读取冻结 PCR） |
| 失败处置 | 度量失败 → 拒绝挂载 `.msys` / 拒绝拉起服务（`32` §3.5 第 0 层） | 验证者拒信该节点 |
| 五架构覆盖 | **全部五架构成立**（含 i386 档 C，仅保证级别低） | 仅档 A/B（有硬件锚）可做强 quote；档 C 仅本地 |
| right 需求 | 无专属 right，度量逻辑属早期 C 薄层（`32` §3.4） | 预留 `ATTEST`=bit39，Day1 不启用、不分配句柄 |

> **协同点**：`ATTEST`=bit39 全程**预留不启用**（与 `32` 第五轮 D-SB7 采纳一致），专属 bit、不复用 `MANAGE`/`GRANT`（遵循 `07` 第三/第四轮回写先例）。远程证明服务（post-Day-1）持 `ATTEST`：默认 deny、可审计、可 revoke，与 `DBG_POKE`/`KERNEL_PRIV`「高危权永不默认」同构。报告格式在 Day1 本地自检与 post-Day-1 远程证明间**同构**——仅 `signature` 字段内容不同，下游消费者（审计/验证服务）逻辑五架构同源。

## 5. 运行时异常行为检测（实例化 I1–I7 + Job 账本）

> 本节把 `29` 威胁分类与 `20` 不变量翻译成**运行期可机检的异常检测规则**，全部落在已有裁决点，不新增内核拦截原语。

### 5.1 三类核心异常 + 检测点 + 与地基协同

| 异常类 | 检测信号（来自何处） | 对应不变量/威胁 | 与地基协同 |
|---|---|---|---|
| **权限提升尝试** | 频繁 `mint`/`grant` 请求逼近委托者 rights 上限；或试图发放超出 `service ∩ client_requested` 的句柄（`07` §4.5 I5） | T3/T4 confused deputy、`20` I5/I6 | 受约束 mint 已在监视器裁决（`29` §3.1 T3）；审计记录三元组，异常 = `issued` 反复贴近 `service` 上限或高频重试 |
| **capability 越权** | `check_rights` 拒绝（T2，`29` §3.2）；pledge 越界 → SIGABRT（`07` §4.2） | T1/T2、`20` I3/I7 | 裁决点即检测点；高频越权 = 探测/攻击信号；越界事件同时生成 CrashReport（`12` §4.3）进审计 |
| **Job 账本超配额** | 配额水位持续 ≥ 阈值；`alloc` 超额 EAGAIN 风暴（`04` §4.4） | T8 IPC 洪泛、`20` I4 | 账本检查点即检测点；超额风暴 = DoS 探测；OOM 归因（`04` §5 议题 5）进审计，供监督者策略 |

### 5.2 与 capability 不变量监控的衔接（I1–I7）

- **I1（无凭空 capability）/ I7（句柄不可伪造）**：表外句柄访问即审计拒绝事件；异常检测 = 单 Job 内「句柄创建速率」超基线（可能 mint 滥用）。
- **I3（rights 只减）/ I6（无隐式提权）**：任何 `rights(out) ⊋ rights(in)` 在数学上不可达（`20` 证明）；运行期若观测到「子句柄 rights 超父」= 监视器 bug，**直接升级为审计 CRITICAL + 触发 `22` 否定式测试回归**。
- **I2（revoke 全断）/ I5（受约束 mint）**：revoke 后 in-flight 派生句柄仍可用 = T5 竞态苗头；监听 revoke 时序异常（`20` Layer B TLA+）。

> 监控规则是 `20` 不变量与 `22` 否定式测试的**运行期实时版**：设计不可违背（证明）→ 实现没回归（测试）→ 运行期实时发现苗头（本文）。三者不重叠、同构。

### 5.3 自动响应边界（与 04 监督者协同）

- 检测到的异常**默认只记录 + 上报监督者**（`04` 监督者经 exception/事件 channel，`12` §4.3），**不**由监控子系统自行 kill/隔离（避免监控成为新的隐式特权面，违背 `07` 无 root 纪律）。
- 仅在**明确策略授权**下（监督者 manifest 声明），对「越权风暴 / 配额耗尽风暴」自动 `kill`+`restart` 对应 Job——与 `29` T7「监督者决策不可抑制」一致。自动响应的授权边界见 §9 S4。

## 6. 与 29 纵深第 0 层衔接

> `29` §4.1 把纵深定为四层（架构最小 → Rust 类型 → 形式证明 → 否定式测试）；`32` §3.5 把**度量**定为第 0 层（在四层之前挡「假内核」）。本文审计/监控在第 0 层之上、第 4 层之侧，是「运行期持续可观测」的延伸。

```
[第 0 层] 32 启动期信任（度量基 + .mimg 信任链）→ 挡「假内核 / 降级介质」（T0）
─────────────────────────────────────────────────────────────────────
[第 1 层] 29 架构最小 TCB（监视器+IPC+低级 VM/调度）
[第 2 层] 02 Rust TCB（消除内存安全类漏洞）
[第 3 层] 20 形式证明 I1–I7（capability 逻辑不变量）
[第 4 层] 22 否定式安全测试（越权必失败）
[运行期] 65 安全监控与审计（I1–I7 实时实例化 + 审计日志 + attestation 报告）← 本文
```

- **衔接点 1（信任前提）**：第 0 层度量失败 → `PCR[2]` 不可信 → `20` 证明的前置信任假设失效 → 本文 attestation 报告 `self_check_result=FAIL` → 下游审计/服务拒绝。审计/监控的*意义*建立在第 0 层成立的信任根上（`32` §3.5 第 2 点）。
- **衔接点 2（第 0 层事件进审计）**：`.mimg`/`.msys` 度量校验失败本身是最高危审计事件（可能 T0 攻击），必须由审计 ring 记录并触发监督者策略（`29` §5.1 把度量定位为第 0 层）。
- **衔接点 3（D-T1 全局 IRQ 进监控）**：`29` D-T1 已采纳 `KERNEL_PRIV`（bit12）含全局 IRQ mask；若 `KERNEL_PRIV` 被显式授予用户态诊断服务（`29` §8.1），其每次使用必记审计（与 `DBG_POKE` 同构），监控规则标记「内核态生死线权外流」为 CRITICAL。
- **衔接点 4（T9 驱动投毒）**：`29` T9 用户态驱动崩溃-重启投毒，由 `04`/`10` 看门狗重启；重启事件 + 重启后驱动能力集 diff 进审计，异常 = 重启后能力集扩大（投毒信号）。

## 7. 五架构同源（审计/监控逻辑无架构差异）

> 对齐 `01` §5「同源码异架构」与 `61` §7 收敛契约：架构差异封死在 `arch/<arch>/boot`，进入 `kernel_main` 后 TCB 同源。

- **审计发射与监控判定：纯软件、无架构差异**。所有检测规则（§5）作用在 capability 监视器、`04` 账本、`.msys`/`.mimg` 度量基——这些在五架构进入 `kernel_main` 后输入一致（`61` §7.2 不变量 1–5）。监控逻辑**不因 x86_64/i386/aarch64/riscv64/loongarch64 而异**。
- **唯一差异：attestation 强度（信任锚档）**。`32` §5 / `61` §7.1 已定：
  - 档 A/B（x86_64/aarch64/有锚 riscv64/loongarch64）→ 可做强远程证明（未来 `ATTEST`=bit39 + TPM quote）；
  - 档 C（i386 老 BIOS）→ **仅本地自检**（软件度量寄存器比对），远程证明不可达（`32` D-SB8 已采纳）。
  - 但**本地自检在五架构均成立**，故 Day1 监控/审计能力五架构同覆盖；差异仅在于「能否向远程验证者出示签名 quote」，不影响运行期异常检测。
- **i386 降级标注**：i386 的 attestation 强度降级（`29` D-T6 同类）须在审计/证明报告中显式标注 `boot_anchor_tier=C`，供消费者决策——与 `32` D-SB8「显式、有界、文档化降级」一致。

## 8. MeuOS 推荐（自主结论）

7. **五架构同源**：监控/审计逻辑无架构差异，仅 attestation 强度随信任锚档 A/B/C 变化；i386 档 C 显式标注降级。

## 11. 第九轮自主采纳·闭环 S1

> 修订式追加（第九轮）：本节省略不删 §1–§9 原文；S1 行状态已升级为「已裁决·闭环（第九轮自主采纳，方案 A）」，§3.2 方案 B 标注已同步升级。待大喵复核。

### 11.1 采纳结论（一句话）

**S1 采纳方案 A**：Day1 复用 `DBG_INSPECT`（bit13，子树粒度）读审计子树，专属 `AUDIT_READ`/`AUDIT_SUBSCRIBE` 仅作候选预留、占 `07` §4.1 的 bit48+ 预留区、不分配（不挤占 bit 0–47）。

### 11.2 采纳理由（三条）

1. **百思纪律「不引入新内核原语除非必要」**：Day1 审计消费者即出核审计服务，读审计子树本质上就是读 inspect 子树，与 `12` §4.2 inspect 树同构，无需新 right 即可跑通。
2. **早期必要性不足**：暂无「普通 inspect 读者不应看到句柄级审计」的真实隔离需求；方案 B 的细粒度分离（可订阅安全事件但不可读历史 ring）属未来需求，过早分配专属 right 反成负担。
3. **与 `32` D-SB7「预埋不启用」同构**：专属 `AUDIT` right 与 `ATTEST`=bit39 一样走「预留不分配」路径——先把坑位占在 bit48+ 预留区，待真实需求出现再升格，避免 Day1 决策锁定。

### 11.3 与既有地基的衔接

- **`12` §4.2 `DBG_INSPECT`**：审计日志 = `kernel/audit` inspect 子树，读/订阅受 `DBG_INSPECT`（bit13，子树粒度）约束；默认 deny、显式授予，与 inspect 树完全同构。
- **`32` D-SB7**：专属 `AUDIT` right 的「预埋不启用」纪律与 D-SB7 预留 `ATTEST`=bit39 同构——均为 bit48+ 预留、Day1 不分配句柄、未来按需升格。
- **`04` Job 账本**：审计消费者是出核审计服务，持 `DBG_INSPECT`（审计子树）订阅/读取；其 ring 配额计入**审计服务自身 Job 账本**（`04` §4.4），不享 TCB 豁免，受 `04` 配额约束。
- **`00` A6 重服务出核**：审计服务是出核用户态服务，不进 TCB；仅「审计日志内核对象 + 事件发射」留内核且极薄，对齐 A6 重服务出核立场。

### 11.4 bit48+ 预留不分配纪律注记

- `AUDIT_READ`/`AUDIT_SUBSCRIBE` 与 `MEDIA_CAPTURE` 等共用 `07` §4.1 的 **bit48+ 预留区**，遵循「预留不分配」：bit 0–47 不动，专属 right 仅挂名于 48+ 候选位，不占任何已分配位。

## 12. reasoning 决策（2026-08-03）

### 12.1 S1 — 审计读权（修正）

**reasoning 决策（2026-08-03）**：**Day1 复用 `DBG_INSPECT`（bit13）跑通（同方案 A），但专属 `AUDIT_READ`/`AUDIT_SUBSCRIBE` 不应被定性为"仅预留、不分配"——它是 Day1 之后的合理 landing 目标，须按 `45 §3` 纪律走 `07` 协同定稿正式分配。**

**对指挥官原占位的关系**：**修正**——保留"Day1 复用 `DBG_INSPECT` 跑通"的务实做法，但**更正对未来归属的判断**：「仅预留不分配」低估了审计读权与普通 inspect 读权的敏感级别差异。

**被否决选项**：
- **方案 A 强形态（永远复用 `DBG_INSPECT`，`AUDIT_*` 永不分配）**：把审计读权永久绑在低风险级 `DBG_INSPECT` 上，与审计子树内置的 cap 上下文高敏感度不匹配。
- **方案 B 早形态（Day1 即分配 `AUDIT_READ`/`AUDIT_SUBSCRIBE` bit48+）**：过早投入 bit 预算，Day1 范围无细分需求。

**被采纳的折中**：Day1 复用 `DBG_INSPECT` 跑通（务实，待真正有"隔离读者"需求时升级）+ 明确升级路径与触发条件（避免"永远不分配"导致语义过载被沉淀）。

**理由（深·reasoning 百思）**：

1. **审计读权与普通 inspect 读权是不同敏感级别——单 right 语义过载是隐患**。
   - `DBG_INSPECT`（bit13）风险级 = 低（`12` R3-5），用于读内核快照、调度队列、内存统计等诊断性状态。
   - 审计子树 `kernel/audit` 含 **`subject_handle` + `rights_mask` + `origin_job` + `verdict`**（§3.1）——这是**高敏感**的 capability 上下文，可被滥用做"哪些 Job 持哪些 rights"的全局探测。
   - 用低风险级 right 守高敏感子树 = **单 right 语义过载**。它本身不构成漏洞，但**违反 `07` "rights 命名应反映语义独立" 的纪律**。

2. **审计者本身必须可独立审计——`DBG_INSPECT` 难做到这一点**。
   - 审计读者（持 `DBG_INSPECT` 审计子树）本身是否被合规监控？——若审计读者是出核审计服务，正常情况下确实如此，因为审计服务的所有操作都进 `65` 审计流（§5.1 三类异常检测之 capability 越权）。
   - 但若 `DBG_INSPECT` 被借 `GRANT` 扩散（`29` T6 同构风险）或临时被某个调试工具持有，**审计读者与普通调试 reader 不可区分**——审计读权被滥用时无法在审计流里"识别这一读动作是审计读还是调试读"。
   - 独立 `AUDIT_READ` 让审计读动作在审计流里可被独立标记（"审计 ring 读写" vs "普通 inspect 读"），这是**审计者自身可审计**的最小前提。

3. **`59` 「语义独立即拆分」哲学应当延续**。
   - `59 §4.1` 把 `IRQ_WAIT`(bit52) / `IRQ_ACK`(bit53) / `IRQ_MASK`(bit54) 拆三 bit，理由是三者语义独立（等待/应答/屏蔽）。
   - 审计读 vs 普通 inspect 读 = 同样是语义独立（合规取证 vs 诊断调试）——按此哲学应当独立。
   - 反向论证：若 `MANAGE` 类的"管理权"硬塞进 `DBG_INSPECT`（"审计 reader 也是 inspect reader"），则类似 `BLOCK_MANAGE` 也会被思考"是否塞进 `DBG_READ`"——这违反 `07` 一直在做的"语义独立即拆分"。

4. **Day1 复用 `DBG_INSPECT` 跑通仍是务实选择**。
   - Day1 范围 = 单一出核审计服务 + 单一审计读者（监督者），**无细分需求**。
   - 复用 `DBG_INSPECT` 不需要新 bit 即可落地，符合"不引入新内核原语除非必要"。
   - 但这不等于"永远不分配"——升格触发条件应明文：**当出现"第二类审计读者"（如独立合规/取证服务）或"读权滥用需独立审计"需求时**，立即走 `07` 协同定稿分配 `AUDIT_READ`/`AUDIT_SUBSCRIBE` bit48+。

5. **bit48+ 预算纪律：升格时须走 `45 §3` 流程，不抢位**。
   - `06 §4.1` 当前 bit48+ 预留给 `MEDIA_CAPTURE` 等，**新增需大喵拍板**。
   - 但"预留给 `MEDIA_CAPTURE`"不等于"审计专用权不能开新位"——只意味着要走 bit 分配的正式流程。
   - 真正应规避的是**任意抢位**（如把 `AUDIT_RIGHT` 强塞 `MEDIA_CAPTURE` 占位）；按 `45 §3` `07` 协同定稿流程正常推进即可。

**TCB 体量评估**：
- Day1 方案 A：右侧零新增（仅在 inspect 树加 `kernel/audit` 子树）。
- 升级方案 B：新增两个 rights 检查点（`AUDIT_READ` / `AUDIT_SUBSCRIBE`），rights 表新增 2 项，开销极小。
- 显式独立带来的 TCB 收益 = 审计读权与普通 inspect 读权可独立审计、独立追责，**长期安全收益显著**。

**与既有地基协同**：
- **`12` §4.2 `DBG_INSPECT`**：Day1 审计子树挂在 inspect 树下，读受 `DBG_INSPECT` 约束——不是替代，是 Day1 临时复用。
- **`32` D-SB7**：升级路径与 `ATTEST`=bit39 预埋-升格模式同构，但**审计升格触发条件比 `ATTEST` 更明确**（"出现第二类审计读者"即可触发）。
- **`04` Job 账本**：审计服务仍是出核服务，受 `04` 配额约束，不享 TCB 豁免。
- **`00` A6**：审计服务进/出核 + 升级路径均沿 A6 原则。

**修正后的升格条件（明文）**：
- (a) 出现"第二类审计读者"（如独立合规/取证服务，须按 §3.1 读审计子树但不应被普通 inspect 守）。
- (b) 出现"审计读权滥用需独立审计"需求（如审计 ring 读须在审计流里独立标记）。
- (c) 出现"审计 ring 内容需要分级访问"（如部分子树含 PII 须更强 right）。

触发任一条件即走 `07` 协同定稿 + `45 §3` 流程分配 `AUDIT_READ`/`AUDIT_SUBSCRIBE` bit48+。

**与指挥官原占位的关系**：修正——保留 Day1 复用 `DBG_INSPECT` 跑通的务实结论，但**修正对未来权利分配的判断**：「仅预留不分配」低估了审计读权与普通 inspect 读权的敏感级别差异，明确为"待触发条件时正式分配"。
