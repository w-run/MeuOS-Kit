## 2. 第四轮 6 新维度一句话汇总（32–37）

- **32-安全启动与可信计算**：以 boot root-of-trust 链式验签（ed25519 + `.msys` v2 信封）自举内核/服务/卷，公钥根与信任链策略分架构落地，远程证明/降级边界列为架构级待决。
- **33-块设备与存储抽象**：块设备 = 用户态驱动经能力网关创建的 capability 对象，带 `BLOCK_*` right；分区/卷/RAID = capability 组合服务（整盘 cap 经 `BLOCK_SUBDIVIDE` 派生收窄子区间 cap），加密默认落 FS extent 层、块层只传 VMO。
- **34-显示与图形子系统**：合成器完全用户态（Scenic 式），内核只给 display/GPU 设备能力 + VMO 零拷贝 + surface 句柄能力 + EventPort 四机制；客户应用不直接持 GPU 全局能力，经受控 3D 服务（Magma 式）收窄 right 的 GPU 连接 capability 提交。
- **35-音频与多媒体**：音频隐私即 capability，麦克风/播放/设备/低延迟独占走 `AUDIO_*` right（默认 deny、与 DBG_*/KEY_* 同构），混音策略在用户态 `audio-service` 且可重启，stream 句柄为受限 capability。
- **36-内核动态加载与热升级**：内核 TCB 默认静态、不运行期加载、与 LKM/livepatch 决裂（消灭「运行期扩大 ring 0」的 root 逃生舱）；用户态组件热升级走 spawn + capability + repoint，内核仅 A/B 整镜像兜底。
- **37-开发者体验与SDK契约**：SDK 唯一出口原则（Single-Export-Gate）——系统能力只经机器可读 IDL（`meu-idldef`）生成的 SDK 暴露，capability/rights/IPC/Job manifest/设备能力单一真相源生成头/文档/版本元数据，根除「内核头即契约」。

## 3. ⚠️ 统一 rights bit 分配建议表（关键交付）

> **背景冲突**：通读 `07-安全模型.md` 全部 rights 章节，发现两处 bit 分配不自洽：
> 1. **bit 6 内部冲突**：`07` §4.1 基础 right 集合定义 7 个（`READ/WRITE/EXECUTE/MANAGE/GRANT/REVOKE/DUPLICATE`），D-T1/C16 又声称基础 right 占 `0–6` 且 `KEY_UNWRAP` 占 bit 6——`DUPLICATE` 与 `KEY_UNWRAP` 在 bit 6 重叠，`07` 自身 numbering 不自洽。
> 2. **bit 11 跨文档冲突**：`29` D-T1 采纳 `KERNEL_PRIV` 占 **bit 11**（`07` §第四轮裁决回写 D-T1 明示「bit 建议 11」），而 `35-音频与多媒体.md` §3.2 提议 `AUDIO_*` 占 **bit 11–14**（`AUDIO_PLAYBACK`=11 / `AUDIO_CAPTURE`=12 / `AUDIO_DEVICE_MGMT`=13 / `AUDIO_UNMUTE`=14）——**bit 11 被 `KERNEL_PRIV` 与 `AUDIO_PLAYBACK` 同时占用，直接重叠**。
>
> 本表为**统一、无重叠**的 right bit 重新编排建议，供后续回写 `07` 使用（**本表为建议，不直接改写 `07`**；回写时按本表冻结 bit 即可消除上述两冲突）。编排原则：
> - 基础 right 占低位 `0–6`（7 个，与 `07` §4.1 实际定义一致）；
> - 服务端/领域 right（KEY_*/CFG_*/KERNEL_PRIV/DBG_*/AUDIO_*/BLOCK_*/NET_*/GPU·DISPLAY_*/LOAD·VERIFY）按领域自低位向高位顺延，互不重叠；
> - 每领域**新增专属 bit**（不复用 `MANAGE`/`GRANT` 等通用生命周期 right），与已采纳的 `KEY_*`/`CFG_*`/`DBG_*` 先例一致（见 §3.1 关于 `BLOCK_*` 的说明）。

### 3.2 关键裁定：`BLOCK_*` / `GPU_*` / `NET_*` / 图形 right 是否复用 `MANAGE`/`GRANT`

- **裁定：各对象领域均新增专属 right bit，不复用 `MANAGE`/`GRANT`。** 理由：`MANAGE`/`GRANT`/`REVOKE`/`DUPLICATE` 是**句柄生命周期**通用 right（创建/授予/回收/复制），而 `BLOCK_*`/`NET_*`/`AUDIO_*`/`GPU_*`/`DISPLAY_*` 是**对象类型特定的 I/O 或能力权**（提交 I/O、录音、提交 GPU command、创建 surface）。若复用 `MANAGE` 表达「块设备 I/O 权」，会把「对象能做什么」与「句柄生命周期管理」混为一谈，破坏 `07` §4.1「句柄即 capability、权限随句柄走」的可审计粒度，也与已采纳的 `KEY_*`/`CFG_*`/`DBG_*` 先例（每个领域独立 bit）一致。
- 具体地，`33` D1 建议新增 `BLOCK_READ/WRITE/IO/SUBDIVIDE/MINT_SUBDEV` 专属 bit（本表 23–27）；`34` D-G3 的「图形 right 是否复用 `MANAGE`」裁定为**不复用**，新增 `GPU_SUBMIT`/`GPU_MANAGE`/`DISPLAY_MANAGE`/`SURFACE_CREATE`/`INPUT_RECEIVE`（本表 32–36）；`25` 的 `NET_*` 同构新增（本表 28–31）。

### 3.3 冲突解决小结

- **bit 11 冲突已解决**：`KERNEL_PRIV` 自原「建议 11」顺延至 **bit 12**，`AUDIO_*` 自原 11–14 顺延至 **19–22**，二者不再重叠。
- **bit 6 内部冲突已解决**：`DUPLICATE` 固定为 **bit 6**，`KEY_UNWRAP`/`KEY_WRAP` 顺延至 **7/8**，消除 `07` 自身的 numbering 重叠。
- **前置 frozen 位一致性**：`CFG_*`(9/10/11)、`DBG_*`(13–18)、`KERNEL_PRIV`(12) 与 `07` 已采纳结论语义完全一致，仅 bitmap 偏移因基础 right 占满 0–6 而整体 +1~+2；回写 `07` 时按本表冻结即可。
- **本表为建议表**，后续由第五轮/回写员据以更新 `07` §4.1 rights 位图全表与第三/第四轮回写中的 bit 编号（仅追加/修订式，不删既有结论）。

## 5. 残留最高优先待大喵拍板项

> 区别于第四轮**已自主采纳**的 6 项（C15/C16/V1/R1/D-T1/能耗-Job），以下为第四轮新提产出中真正仍需人拍板的少数几项：

1. **32-D-SB1（公钥根存放介质）**——跨架构信任锚策略（eFUSE/bootloader/软件根），决定安全启动根基，关联 i386 降级边界。
2. **C18（内核运行期加载策略/静态 TCB）**——是否锁死静态 TCB、彻底否决 LKM/livepatch，关乎最小 TCB 与未来可验证性的根基取舍（原 38 第四轮以「C17」记本议题，因与第五轮 C17=网络面边界撞号，改号 C18；见 §4 C18 行）。
3. **34-D-G1 / 34-D-G2（图形兼容 / GPU 模型）**——Wayland/X 兼容范围、客户是否直连 GPU，关乎生态兼容面与 capability 边界完整性。
4. **37-待决1（IDL 唯一出口）**——是否强制所有系统能力经 SDK 唯一出口，关乎开发者生态契约与「内核头即契约」教训能否根除。

此 4 类（含其下属子项）为第五轮真正需大喵/team-lead 拍板的最高优先项；其余第四轮产出（6 维度主体设计、10 候选推荐立场）均已收敛或可在后续轮次设计级回填。
