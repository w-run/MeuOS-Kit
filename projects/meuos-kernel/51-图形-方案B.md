## 1. 一句话核心

> **UI 的原生范式是「客户端持 window/surface 抽象、经 capability 作用域内的客户端-合成器协议提交内容、由用户态合成器 compositing、由独立用户态 GPU 服务（Magma 式）做 3D 提交」；保留 window/surface 传统概念但全部 capability 化（无全局窗口树、无全局 registry、客户端不持 GPU 全局权），GPU 走 `10` 网关下发的用户态服务而非 render node 直连。比方案 A 务实：客户端-合成器协议即现有 GUI 工具包已理解的 buffer-commit 语义，兼容层薄、对存量生态友好。**

---

## 2. 解构型推演：显示「应该是什么样」

> 先不问「MeuOS 的 GUI 怎么抄 Wayland/X」，而问「在 capability 世界、用户态驱动、最小 TCB 前提下，图形栈**应该**长什么样」。本推演承认 `50` 的现代化方向正确，但认为其范式迁移代价过高，故取一条更贴近现有生态的务实路径。

### 2.1 方案 A 的现代化代价（为什么需要方案 B）

`50` 把「声明式/保留模式场景图」设为原生唯一范式、合成器设为「唯一能力网关」持权威图。其收益（去 immediate 协议、去全局树、去 server 信任）真实，但代价是**范式迁移**：

1. **原生 SDK 成本高**：客户端不再「提交一块 buffer」，而是「提交声明式节点」。GTK/Qt/Flutter/Electron 等存量工具包的全部 Wayland/X11 后端无法直用，须重写一层「widget → SceneNode」映射；这与 `08`「mkit 子集优先、对存量生态友好」精神存在张力。
2. **客户端控制力被收得过紧**：动画/扫描线精确呈现、自管呈现时序等需求，在 A 中只能走 `GPU_SUBMIT`+`CAP_RT` 或 `DISPLAY_LEASE` 旁路，普通 surface 路径失去 buffer-commit 的熟悉自由度。
3. **合成器单点更重**：权威图在合成器，崩溃恢复须重建所有 session 子树（`50` A-D2），协议面比「客户端各自持 surface、合成器只 compositing」更重。

**方案 B 的务实判断**：上述收益（capability 化、GPU 不受控直连、无内核 DRM TCB）**不必依赖保留模式场景图即可得到**。把「客户端-合成器协议 + window/surface 传统概念 + 用户态 GPU 服务」capability 化，同样能去全局树、去 render node、去内核 GEM——且保留 buffer-commit 语义，**让现有 GUI 生态的 Wayland 后端几乎零成本映射**。

### 2.2 待摆脱的「包袱」精确界定（X11/Wayland 的历史债）

| 包袱 | X11 | Wayland | 方案 B 的处置 |
|------|-----|---------|---------------|
| **immediate-mode 绘制协议** | 逐 op「画点/画线/贴图」、XRender 逐命令 | 客户端逐帧 `commit` 一块 buffer + `damage` 矩形（已 retained 但带 per-frame dance） | **抛弃 X11 立即模式**；保留 Wayland 式「提交一块缓冲内容」的 buffer-commit 语义（存量工具包已懂），但**丢弃 damage 矩形簿记的强制复杂度**——合成器按 surface 内容就绪自行决定重绘区，客户端不负扫描线账 |
| **全局窗口树 / 全局 registry** | 全窗口挂 server 一处全局树，XID 全局可寻址（`XQueryTree`） | 全局 registry 枚举 server 所有 global（compositor/seat/output），客户端可枚举 | **capability 作用域取代全局 registry**：客户端只见其被 mint 的 surface 句柄，无全局枚举、无跨客户端寻址（`00` A4）。surface 是客户端私有 capability，不是全局可寻址对象 |
| **客户端直连 GPU（render node）** | 无；X 时代无 GPU 直连 | 经 `/dev/dri/cardN` render node 拿全局 GPU 提交权 | **Magma 式用户态 GPU 服务**：无 render node、无 raw MMIO/DMA；客户端持 `GPU_SUBMIT` 收窄连接，3D 服务校验 + IOMMU 隔离（`34` §8.3 已否决直连） |
| **server 信任假设** | X server 默认信任所有客户端，可 `XGrabKeyboard` 截获全局输入 | 改善但未根除：seat/compositor 隐式信任客户端不滥焦点/输入 | **合成器按 `INPUT_RECEIVE` 焦点授权路由输入**，客户端不能全局截获（呼应 `42` §3.3） |
| **内核态 modesetting + GEM** | DRM/KMS 内核态 | 同 | **modesetting 用户态**（合成器持 `DISPLAY_MODESET`），无 DRM/GEM TCB 膨胀（`00` A6） |

### 2.3 推演结论（解构型基线）

在 MeuOS 三条互锁地基（`00` §1：capability 唯一模型 / 重服务出核缩 TCB / spawn-Job 资源账本）之上，方案 B 主张显示应：

1. **UI 范式 = 客户端-合成器协议（buffer-commit 语义），而非保留模式场景图**：客户端持自己的 **window/surface**，把像素/纹理内容（graphic buffer VMO）经协议提交给合成器；合成器负责 compositing、焦点、输入路由。**客户端保留对其 window/surface 内容状态的所有权**——这与现有 GTK/Qt/Flutter 的 Wayland 心智模型一致。
2. **window/surface 是保留下来的传统概念，但全部 capability 化**：window/surface 不再是「全局树里的 XID」或「Wayland 全局 registry 里的 global」，而是**合成器 mint 给客户端的收窄 capability 句柄**（带 `SURFACE_SUBMIT`/`SURFACE_MANAGE`，不含 `DISPLAY_MODESET`/`GPU_MANAGE`）。概念传统，但权限模型彻底现代化。
3. **合成器 = 用户态协议对端 + compositing 权威，但不是场景图唯一所有者**：合成器持 display 设备能力、做合成与输入路由，但**不持有「客户端 UI 的权威场景图」**——那是各客户端自己维护、经协议增量提交的内容。合成器只做「把各客户端提交的 surface 合成到帧缓冲」这一件事。
4. **GPU = 用户态服务（Magma 式），非 render node 直连**：3D/加速合成由独立用户态 **GPU 服务**承担，经 `10` 网关持 GPU 设备能力、向客户端 mint 收窄 `GPU_SUBMIT` 连接。等价于 Fuchsia Magma 的「用户态 GPU 驱动 + 受约束连接」，但经 `10` 能力网关下发。

> **与 34/50 的关系**：34 落地「Wayland 兼容 + surface 即 capability + GPU 受限委托（D-G1/G2）」——这是兼容性基线。50 在其上把原生范式升级为「保留模式场景图」。本文取**第三条路**：原生范式 = 「客户端-合成器协议 + 传统 window/surface + 用户态 GPU 服务」，既继承 D-G1/G2 的能力边界，又**不**强制保留模式场景图。**与 50 是同一安全叙事下、取向不同的两条原生候选**（A=激进现代化，B=务实生态友好），供大喵/执行层二选一或取其公约数。

## 3. 关键抽象：Client / Surface / Compositor / GPU 提交句柄

> 四个一等公民：**Client（客户端）** / **Surface（表面句柄·传统 window 的能力化载体）** / **Compositor（合成器·用户态协议对端）** / **GPU 提交句柄（用户态 GPU 服务的收窄连接）**。内核只给四类机制（见 3.5），不实现任何合成/渲染逻辑。
>
> 注：相对 `50`，**本方案刻意不含 SceneNode / 保留模式场景图**——客户端自持其内容状态，合成器只 compositing。这是 B 与 A 的根本结构差异。

### 3.1 Client（客户端）—— 自持 window/surface 内容状态的一方

- **身份**：一个经 `meu-spawn` 启动、持若干 **surface 句柄（capability）** 与（可选）**GPU 提交句柄**的进程/Job。与传统 Wayland client 同构，但其在内核侧的权限表达是 capability 而非「连上 socket 即部分可信」。
- **职责（自持状态）**：
  - 维护自己的 window/surface 逻辑状态（尺寸、位置意图、内容）；
  - 把像素/纹理内容写入 **graphic buffer VMO**（`03`），经协议把 VMO 句柄 cap-transfer 给合成器（零拷贝，接 `03`/`05`）；
  - 经协议声明 surface 的呈现属性（z-order 意图、不透明度意图——由合成器按策略核准，非客户端单方面生效）；
  - （可选）经 **GPU 提交句柄** 把 3D command buffer 交 GPU 服务加速生成 surface 内容。
- **不持特权 right**：Client 只持合成器 mint 回的 `SURFACE_SUBMIT`(41)/`SURFACE_MANAGE`(42) 与（可选）`GPU_SUBMIT`(32)；**不持** `DISPLAY_MODESET`(43)/`DISPLAY_MANAGE`(34)/`GPU_MANAGE`(33)/`DISPLAY_LEASE`(44)。
- **隔离边界**：Client 只见自己的 surface 句柄，**无全局 registry 可枚举他人 surface**（与 `00` A4「无全局默认可见」、`42` §3.3「沙箱 = 受限 capability 集」一致）。

### 3.2 Surface（表面句柄）—— 传统 window 的能力化载体

- **身份**：承载一个 window 的像素/纹理内容的 **capability 句柄**（`07` §4.1：句柄即 capability）。由合成器 mint（持 `SURFACE_CREATE`(35) 授权，回传带 `SURFACE_SUBMIT`(41) 收窄句柄）回传给 Client。
- **与传统 window 的关系**：Surface 是「window」在 MeuOS 的能力化等价物——它代表一块可呈现的矩形内容区域。但与 X11 window（全局树节点、XID 全局可寻址）和 Wayland `wl_surface`（全局 registry 里的 global）不同，**Surface 是客户端私有的、capability 作用域内的句柄**，跨客户端不可寻址、不可枚举。
- **内容 = graphic buffer VMO**：
  - CPU 写路径：Client `vmo_create` 一块 VMO，map 后写像素，把 VMO 句柄经 `05` Channel cap-transfer 交给合成器 → 零拷贝合成（接 `03`/`05`）。
  - GPU 写路径：经 `03` device VMO（GPU 可映射、可 DMA，遵循 device 内存「不可写」right）；由 GPU 服务写入后共享给合成器。
- **关键约束（与 34 一致）**：surface 句柄即隔离边界（`34` §3.3 / `42` §3.3）。Surface 可独立存在于客户端侧（传统 window 概念保留），但**呈现生效须经合成器 compositing**——合成器按焦点/层级/策略决定其是否及如何上屏。崩溃/关闭时句柄 revoke 即回收（`07` §4.5）。

### 3.3 Compositor（合成器）—— 用户态协议对端 + compositing 权威

- **身份**：受 `meu-supervisor`（`04`）管理的用户态 Rust 系统服务，**持 display 设备能力**（`DISPLAY_MODESET`(43)/`DISPLAY_MANAGE`(34)/`DISPLAY_LEASE`(44)）+ GPU 委托权（`GPU_MANAGE`(33)）的实体；由 `10` 能力网关签发 display/GPU 设备能力（MMIO/IRQ/DMA），可重启、可灰度。
- **作为「协议对端」的职责（与 `50` 的「唯一能力网关」区别：B 不持客户端 UI 权威图）**：
  1. **mint 一切图形句柄**（受约束 mint，破 confused deputy，`07` §4.5）：surface 句柄（`SURFACE_CREATE`(35) → 回传 `SURFACE_SUBMIT`(41)）、GPU 提交句柄委托（`GPU_SUBMIT`(32) 经受控 GPU 服务 mint）。mint 权限受「自身 rights 上限 ∩ 客户端请求下限」交集约束。
  2. **compositing**：接收各 Client 经协议提交的 surface 内容（VMO），据焦点/层级/策略把多 surface 合成到帧缓冲 device VMO 或经 GPU 加速合成。**合成器只做「把已提交的 surface 合成」——不持有客户端 UI 的权威场景图**（那是 Client 自持）。
  3. **输入路由**：输入设备经 `10` 用户态驱动 → Channel/EventPort 上报合成器；合成器按 surface 焦点（capability 边界）把事件交付对应 surface 持有者（`INPUT_RECEIVE`(36) 按焦点授权），杜绝跨客户端输入劫持。
  4. **modesetting**：枚举/设模式经 `DISPLAY_MODESET` 能力，设备能力来自 `10`。
- **「协议对端」的含义（与 50 的差异）**：在 B 中合成器是客户端经协议交互的**对端服务**，不是「拥有整张 UI 图的唯一权威」。客户端自己管自己的 window/surface 内容状态，合成器只负责把这些 surface 合成上屏。这更接近 Wayland compositor 的实际角色，因而现有工具包映射自然。

### 3.4 GPU 提交句柄（GPU submit handle）—— 用户态 GPU 服务的收窄连接

- **身份**：= **GPU 连接 capability**（`GPU_SUBMIT`(32)，`07` §4.1 冻结 bit 32），由**受控 GPU 服务**（Magma 式，`34` §8.3）mint 给客户端，**不含 raw MMIO/DMA**。
- **用户态 GPU 服务（Magma 式）的承载者**：方案 B 明确把「GPU 服务」立为与合成器**并列**的独立用户态服务（而非合成器内嵌的 GPU 逻辑）。GPU 服务经 `10` 网关持 GPU MMIO/IRQ/DMA 设备能力，校验 Client 提交的 command buffer（边界/句柄引用/地址空间）后提交硬件；IOMMU（`10` §5-2）强制隔离 DMA。
- **工作流**：Client 向 GPU 服务请求一个 GPU 连接句柄 → 把 command buffer 写入 device VMO（`03`）经 `05` 交 GPU 服务 → 服务校验后提交硬件 → 生成的 surface 内容经 VMO 共享给合成器。
- **在方案 B 中的角色**：GPU 加速是 Surface 内容的「生产者」之一，但 **surface 句柄始终是 Client 与合成器之间的契约**；GPU 句柄不可越权触达他人 surface（`34` §8.3 双重防线：校验 + IOMMU）。Client 永不持 `GPU_MANAGE`(33)。

### 3.5 四抽象关系图（客户端-合成器协议 + 用户态 GPU 服务）

└──────────┬───────────────────┘                              └───────────┬──────────────┘

## 4. 多系统参照与取舍（解构非缝合）

| 系统 | 其 UI 范式 / GPU 模型 | 借鉴点 | 不选点 / 方案 B 取舍 |
|------|----------------------|--------|---------------------|
| **Fuchsia Magma** | **用户态 GPU 驱动**：客户持「GPU 连接」capability（驱动 mint，收窄到该客户上下文），command buffer 经 VMO 交驱动校验后提交；无内核 GPU 调度/渲染逻辑 | **直接对标 GPU 模型**：本文的「用户态 GPU 服务」即 Magma 思想的 MeuOS 落地——区别仅在经 `10` 能力网关下发 GPU 设备能力，而非 Magma 驱动直接持 | Magma 通常与 Scenic 合成器紧耦合；方案 B 把 GPU 服务**独立**于合成器，且 UI 范式不取 Scenic 保留模式场景图（取客户端-合成器协议） |
| **Wayland** | 客户端-合成器协议：客户端持 `wl_surface`、逐帧 `commit` buffer；合成器 compositing；但存在**全局 registry 枚举 global**、客户端经 render node 直连 GPU | **直接对标交互骨架**：客户端-合成器协议 + buffer-commit 语义是现有 GUI 工具包（GTK/Qt/Flutter/Electron）已理解的模型，兼容层最薄。方案 B 的原生范式即此协议的 capability 化版本 | **丢弃** Wayland 全局 registry（改 capability 作用域，无全局枚举）、**丢弃** render node 直连 GPU（改 Magma 式用户态 GPU 服务）。`34` D-G1 已采纳 Wayland 作为兼容层，方案 B 进一步把它作为**原生范式的近亲**而非仅兼容 |
| **X11** | immediate-mode 绘制协议 + 全局窗口树（XID 全局可寻址）+ server 默认信任客户端 | 仅作**反面教材**：逐 op 绘制协议、`XQueryTree` 跨客户端探测、`XGrabKeyboard` 全局输入截获 | **全否**：无 immediate 绘制命令流、无全局窗口树、无 server 信任假设；surface 是私有 capability 非 XID |
| **macOS Metal** | GPU 访问经 Metal 框架沙盒化，应用不直接持 GPU 全局能力；WindowServer 用户态合成；Surface 经 CoreGraphics | **借「沙盒化 GPU 访问」精神**：Metal 把 GPU 访问收口到框架、应用持受限命令队列——与方案 B 的 `GPU_SUBMIT` 收窄连接同构。WindowServer 用户态合成即合成器定位 | macOS 走 IOKit 内核驱动（我们走 `10` 用户态驱动 + 能力网关）；隔离靠 window/process 而非 capability 边界（我们取 capability） |
| **Android HWC** | SurfaceFlinger 合成 surfaces；Surface = Binder token（capability 式边界）；HWC 硬件合成；Gralloc 缓冲分配；应用隔离 = Binder token 边界 | **借「Surface = 对象级 token + 应用隔离 = token 边界」**：与方案 B 的「surface = capability 句柄、隔离 = capability 边界」同构。BufferQueue 的跨进程缓冲零拷贝即 VMO cap-transfer 等价 | HWC/HAL 是 Android 特定形态（我们走 `10` 用户态驱动）；不引入 Binder，用 `05` Channel/cap-transfer；GPU 走 Magma 式服务而非 HAL |

**取舍总纲（解构非缝合）**：
- **取** Wayland 的「客户端-合成器协议 + buffer-commit 语义」作为原生交互骨架（对存量生态友好、兼容层薄）；
- **取** Fuchsia Magma 的「用户态 GPU 服务 + 受约束连接 capability」作为 GPU 模型（杜绝 render node ring 0 逃逸）；
- **取** macOS Metal 的「沙盒化 GPU 访问」与 Android HWC 的「surface = token 边界」精神；
- **拒** X11 的 immediate 绘制 + 全局窗口树 + server 信任；
- **拒** Wayland 的全局 registry 枚举与 render node 直连；
- **拒** Linux DRM 内核态 modesetting/GEM（TCB 污染）；
- **与 50 的分叉**：不取 Fuchsia Scenic 的保留模式场景图作为原生范式——保留客户端自持 window/surface 内容状态的客户端-合成器协议，换取生态友好性。合成器是协议对端+compositing 权威，不是 UI 图唯一所有者。

## 5. 与 MeuOS 现有规划衔接（00 / 34 / 07 / 42）

### 5.1 继承 34-D-G1（Wayland 兼容）
- 方案 B 的原生范式即 Wayland 客户端-合成器协议的 capability 化近亲，故 **Wayland 兼容层极薄**：`wl_surface`/`wl_buffer` 几乎 1:1 映射为内部 surface 句柄 + graphic buffer VMO；`wl_compositor` 全局即合成器本身。这比 `50` 的「SceneNode 翻译」映射成本低得多——**这是 B 相对 A 的核心生态优势**。
- 兼容层自身只是普通客户端，持 `SURFACE_SUBMIT`/`INPUT_RECEIVE` 等收窄 right，**不持 `DISPLAY_MODESET`/`DISPLAY_LEASE`/`GPU_MANAGE`**（默认 deny），不击穿沙箱（`34` §8.2、`42` §4.3）。
- X11 仅经可选 X 服务器（XWayland 式），不进 Day 1 原生能力（`34` §8.1）。

### 5.2 继承 34-D-G2（GPU 访问模型）
- GPU 访问 = 用户态 GPU 服务 + Magma 式用户态驱动 + 收窄 right 的 GPU 连接 capability（`GPU_SUBMIT`(32)）；客户不直连 GPU、不经 raw MMIO/DMA（`34` §8.3）。
- 本文把「GPU 服务」明确立为**与合成器并列的独立用户态服务**（而非合成器内嵌），这是相对 `34`/`50` 的细化，但不改变 D-G2 的能力边界结论。

### 5.3 继承 07 冻结 rights 位图（不新增显示/GPU 域 right）
本文**完全复用 `07` §4.1 已冻结的显示/图形 right**，不重定义、不冲突：
- `SURFACE_CREATE`(35) / `SURFACE_SUBMIT`(41) / `SURFACE_MANAGE`(42) —— surface 内容提交与状态调整。
- `DISPLAY_MODESET`(43) / `DISPLAY_LEASE`(44) / `DISPLAY_MANAGE`(34) —— 仅合成器/服务持有。
- `INPUT_RECEIVE`(36) —— 由合成器按焦点授权（隐私敏感，默认 deny）。
- `GPU_SUBMIT`(32) / `GPU_MANAGE`(33) —— 客户/GPU 服务。
- **`CAP_RT`(45) 可组合使用**：对延迟敏感 surface（如 VR/实时仪表），客户端可持 `CAP_RT` 进入 RT 合成路径（`44` §4.4 RT 预算），与 `SURFACE_*` 正交组合，不新增显示专属 right。
- **与 50 的差异点**：方案 B **不需要** `50` 提议的 `SCENE_SESSION`（bit 48+ 预留）独立 right——因为 B 无「session 子树 / 保留模式场景图」概念，客户端持 surface 句柄即其全部图形 capability 边界，无需额外 session 令牌 right。这是 B 在 rights 面上的简化收益。

### 5.4 与 42 虚拟化/沙箱一致（隔离第一性 = capability 边界）
- **合成器与 GPU 服务各自是沙箱**：二者都是持特定 capability 集的 Job（合成器：`DISPLAY_*` + `GPU_MANAGE` + surface mint 权；GPU 服务：`GPU_*` + GPU 设备能力），受 `meu-supervisor` 管理、受 Job 账本约束（`42` §3.3、`04` §4.4）。
- **客户端 surface 隔离 = 其 surface capability 边界**：容器内图形应用的 surface 仍受容器 Job 的 capability set 约束（`42` §3.3、`34` §3.3）；无全局窗口树可探。
- **VM（L2）显示**：guest 想要显示，由合成器把 surface 句柄经 cap-transfer **委托进 guest**（等价 `03` device VMO / 句柄跨域授予），guest 不拿 raw GPU/display 设备能力——与 `42` §5.3「设备经 capability 授予 guest、IOMMU 隔离」同构。
- **输入隔离**：`INPUT_RECEIVE` 按 surface 焦点授权，沙箱内客户端只能收其自身 surface 输入，无 X11 式全局输入截获（呼应 `42` §3.3「攻击面 = 显式授予句柄集」）。

### 5.5 与 03 / 05 / 10 / 08 接口边界（声明依赖，不替其下结论）
- 图形缓冲 = VMO / device VMO（`03`），零拷贝经 `05` cap-transfer。
- 就绪通知复用 `05` EventPort（`EVFILT_CHAN` 帧就绪 / `EVFILT_USER` present done / GPU 完成）。
- display/GPU 经 `10` 能力网关出核；GPU DMA 受 IOMMU 强制隔离（`10` §5-2）。
- Wayland/X 兼容语义映射见 `08`（D-G1 已采纳，X 列入可选 shim）；方案 B 原生协议与 Wayland 同构，故兼容层成本最低。

## 7. 相对传统摆脱的包袱与代价

### 7.1 摆脱的包袱（主动丢弃的历史债）
1. **X11 immediate-mode 绘制协议**：无「画点/画线/贴图」逐 op 命令流，无 XRender 逐命令。客户端提交内容缓冲而非绘制命令，消除一整类协议重入/同步 bug。
2. **全局窗口树 / 全局 registry（X11+XWayland 共病）**：无 XID 全局可寻址、无 `XQueryTree` 式跨客户端探测、无 Wayland 全局 global 枚举。Surface 是 capability 作用域内的私有句柄，跨客户端不可寻址——与 `00` A4「无全局默认可见」、`42`「沙箱 = 受限 capability 集」一致。
3. **render node / 客户端直连 GPU**：无 `/dev/dri/cardN` 式全局 GPU 提交权；command-buffer 解析在用户态 GPU 服务校验 + IOMMU 隔离，消灭 ring 0 逃逸面（`34` §8.3）。
4. **server 信任假设**：输入路由由合成器按 `INPUT_RECEIVE` 焦点授权，客户端不能 `XGrabKeyboard` 式全局截获输入（呼应 `42` §3.3）。
5. **内核态 modesetting + GEM 缓冲管理**：modesetting 用户态（合成器持 `DISPLAY_MODESET`），无 DRM/GEM TCB 膨胀（`00` A6）。
6. **「保留模式场景图强制」的范式迁移成本**（相对 `50`）：本方案**不强制**客户端改投声明式场景图——保留 window/surface + buffer-commit 语义，使存量 GUI 工具包零成本迁移。

### 7.2 代价（须接受的设计权衡）
1. **合成器权威弱于方案 A**：B 中合成器不持「客户端 UI 权威图」，客户端自持内容状态——这意味着跨客户端的一致性约束（如统一动画时钟、全局布局策略）须由协议/约定协调，而非合成器强制。换取生态友好与客户端自由。
2. **damage/重绘协调责任部分回到客户端**：Wayland 式 buffer-commit 仍隐含「客户端何时提交新内容」的时序责任（虽方案 B 丢弃 damage 矩形簿记，但客户仍需在内容变更时提交）。`50` 的声明式图把该责任更多地收口到合成器。
3. **兼容层虽薄但仍需存在**：即便原生协议 ≈ Wayland，存量 Wayland 客户端仍需一层协议翻译前端（但比 `50` 的 SceneNode 翻译薄得多）。X11 仍需可选 X 服务器 shim。
4. **合成器与 GPU 服务双单点**：B 把 GPU 服务独立，故障域从 A 的单合成器变为「合成器 + GPU 服务」两个可独立重启的用户态服务——隔离更好，但需协调二者崩溃恢复（surface 句柄 vs GPU 连接句柄分别 revoke）。
5. **协议面仍大于纯内核机制**：客户端-合成器协议是「协议」，需版本化/演进纪律（`23` ABI 稳定性、`37` IDL 唯一出口）——但用 `meu-idldef` 生成、演化成本可控。

> **判语**：方案 B 的代价是「合成器权威弱于 A、damage 协调部分回客户端、仍薄兼容层、双单点、协议演化纪律」；收益是「去 X11 immediate、去全局树/registry、去 render node 逃逸、去内核 DRM TCB、**保 window/surface 传统概念使存量 GUI 生态零成本迁移**」。在 `00` A6「重服务出核缩 TCB」、`07` 最小权限、`42` 沙箱同源前提下，B 是「现代化」与「生态兼容」之间的务实折中——比 A 更友好、比传统 Wayland 更干净。

## 8. 与方案 A 的关键差异

> 两方案共享同一安全叙事（capability 唯一模型 / 重服务出核缩 TCB / GPU 不受控直连 / 无内核 DRM TCB），差异在**原生 UI 范式与抽象结构**。

| 维度 | 方案 A（50，激进现代化） | 方案 B（本文，务实生态友好） |
|------|------------------------|------------------------------|
| **原生 UI 范式** | 保留模式场景图（retained-mode scene graph） | 客户端-合成器协议（buffer-commit 语义） |
| **核心抽象** | SceneNode + Surface + Compositor(唯一网关) + GPU 句柄 | **Client + Surface + Compositor(协议对端) + GPU 句柄**（**无 SceneNode**） |
| **谁持 UI 权威图** | 合成器持有整张权威保留图（客户端只提交声明式节点） | 客户端自持 window/surface 内容状态；合成器只 compositing 已提交 surface |
| **window 概念** | 无游离窗口；Surface 必须被 SceneNode 引用才有意义 | **保留 window/surface 传统概念**（capability 化），surface 可独立存在于客户端侧 |
| **客户端自由度** | 低：一切经声明式节点，呈现时序由合成器求值 | 高：客户端自管内容状态与提交时序（熟悉于 GTK/Qt/Flutter） |
| **合成器角色** | **唯一能力网关 + UI 图唯一所有者** | **协议对端 + compositing 权威**（非 UI 图唯一所有者） |
| **GPU 服务位置** | 合成器内嵌的受控 3D 服务 | **与合成器并列的独立用户态 GPU 服务**（Magma 式） |
| **存量生态映射成本** | 高：需重写「widget → SceneNode」层；Wayland 兼容层是厚翻译 | **低**：原生协议 ≈ Wayland，`wl_surface`/`wl_buffer` 近 1:1 映射；兼容层极薄 |
| **rights 面** | 可能需 `SCENE_SESSION`(bit 48+) 独立 right | **不需** session right；surface 句柄即全部图形 capability 边界（更简） |
| **崩溃恢复** | 重建所有 session 子树（A-D2） | surface 句柄与 GPU 连接句柄分别 revoke（双单点独立重启） |
| **与 34/D-G1/D-G2 关系** | 是 34 的「保留模式纵深版」 | 是 34 的「客户端-合成器协议 + 用户态 GPU 服务纵深版」 |
| **适用取向** | 全新原生应用、愿接受新 SDK、追求最大确定性/可控 | **存量 GUI 生态优先、兼容层薄、渐进迁移、务实可自举** |

> **结论性差异一句话**：方案 A 把客户端降级为「声明式节点提交者」、合成器升为「UI 图唯一所有者」；方案 B 保留客户端自持 window/surface 的客户端-合成器协议、把 GPU 收口为独立用户态服务——**A 更激进现代化，B 更务实生态友好，二者安全边界（D-G1/D-G2/07 rights）完全一致**。
