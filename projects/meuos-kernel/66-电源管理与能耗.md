## 0. 与 27 / 40 的边界（本文定位）

`27-电源与热管理.md` 与 `40-电源管理与能耗.md` 已从两端给出完整结论，本文**不是**第三份重复文档，而是把二者「未显式成形的状态机与策略落点」做**百思式收口**：

- `27` = **控制面（机制层）**：内核只暴露 P-state/OPP、C-state、thermal zone/trip 原语 + 不可绕过热硬限；DVFS/idle 偏向/设备断电/休眠等**策略全部用户态 `powerd` 化**（Fuchsia powerman 范式）。那是「电源*怎么管硬件*」。
- `40` = **计量与协同面**：能耗只读计数器（`ENERGY_READ`）+ 用户态 `powerd` 聚合成 task packing 信号 + 调度器据 `Job` CPU 配额做弱耦合协同；强耦合留待 `04` §5 议题 6（异构核 EAS）。那是「能耗*作为量、作为信号*」。
- `66`（本文）= **状态机与策略落点面**：把「CPU 从运行到休眠再回来的整条状态链（idle/suspend/resume）」「governor 到底在内核还是用户态」「per-Job 能耗账本弱/强耦合的精确边界」「五架构功耗态差异如何关进薄后端」四个**尚未被 27/40 显式建模**的议题推演成形，并给出推荐立场与待决项。

> 非缝合怪宣言：本文不重述 `27` §3.2 P-state/OPP、`27` §4.2 热硬限、`40` §5 `cpu_power_state`、`40` §7 rights 提议——凡涉及机制/计量一律**引用** `27`/`40` 对应章节，只新增「状态机骨架 + 策略归属 + 账本边界 + 五架构功耗后端」的解构视角。

## 1. 「应该是什么样」——核心结论

**电源管理的正确内核职责 = 只实现 `running → idle → clock-gated → deep-idle → suspend → resume` 的最小状态原语与受控频压接口，suspend/idle 的「何时进哪档」决策与 DVFS governor 全部用户态 `powerd` 化；per-Job 能耗原型期严格弱耦合（与 `00` §3 能耗-Job 已采纳一致），强耦合待 `04` §5 议题 6 解锁；五架构功耗态差异关进统一 `arch/pm` 薄后端，不侵蚀统一状态机。**

## 2. idle / suspend / resume 状态机（内核最小职责）

### 2.1 解构推演：状态机应「内核持状态、用户态持决策」

把「CPU 功耗」从「一个全局 `cpu_idle()` 调用」中剥离，推演一个 capability 内核里它本应是什么：

1. 进入低功耗态 = 「让某核停止取指 + 关闭部分时钟」，这是一个**内核态原子动作**，必须由内核执行（硬件要求特权级 + 原子上下文）。
2. 「进哪一档、何时进、是否 suspend」 = **策略**，依赖电池/AC、 thermal headroom、`Job` 活跃度 —— 这些是 `powerd` 的用户态知识，不该写死内核。
3. 唤醒 = 「外部事件把核拉回 running」——唤醒源必须被内核识别并路由，但「允许谁唤醒」是 capability 问题（外部事件 = 设备 `Cap(IRQ n)` 或 timer 对象，见 §4）。

推演结论：**状态机 = 内核的最小「状态转换原语」集合 + 用户态编排策略**；内核不持有「电源策略状态机」，只持有「我能进/出这些硬件态」的薄层。

### 2.2 状态机骨架（分级）

```
  running ──(无就绪任务/主动 yield)──▶ idle(WFI/WFE/HLT)
     ▲                                     │
     │                                     ▼
  resume ◀── 唤醒源 ──  clock-gated(C1) ──▶ deep-idle(C2+)
  (恢复核心上下文)                          │
                                           ▼
                                    suspend-to-RAM(S3) ──▶ hibernate(S4)
                                           ▲                     │
                                           └──── resume ─────────┘
```

- **running → idle**：内核在调度器判定「本核无就绪任务」后执行架构 `WFI`/`WFE`/`HLT`（`28` §6 各架构的 idle 指令），并启用 `NOHZ` 式 tickless（`57` §5.1 / `40` §5.3）。
- **idle → clock-gated/deep-idle**：由 `powerd` 设的 idle 偏向（`40` §5.1 `avail_idle_depth` 上界）决定进 C1 还是 C2+；内核只负责执行对应架构进入指令（MWAIT/PSCI/DSU/SBI/HLT，见 §6）。
- **deep-idle → suspend(S3)**：内核提供 `request_suspend()` 最小原语（保存核心寄存器/页表基址等少量上下文），完整设备上下文保存由用户态驱动经 `Cap(IRQ n)` 收回重发（`59` §4.4 撤销锁序列同构）；**策略是否 suspend 归 `powerd`**。
- **resume**：内核从 `request_suspend()` 保存点恢复核心上下文，设备恢复由驱动重新 `wait` 自身 `Cap(IRQ n)`；不引入新内核对象。

### 2.3 内核最小职责清单（与 `00` A6 同构）

| 内核职责 | 不在内核（交用户态） |
|----------|----------------------|
| 执行 idle 进入/退出指令（每架构薄后端） | suspend/idle **何时进、进哪档**的决策（`powerd`） |
| 执行 clock-gating / C-state 进入原语 | DVFS 选频决策（`powerd`，见 §3） |
| 唤醒源识别与路由（timer/中断/外部事件 → 调度器） | 唤醒源注册策略（哪些外部事件允许唤醒） |
| 保存/恢复**核心**上下文（suspend 原语） | 设备上下文保存（`Cap(IRQ n)` 驱动自管） |
| **热硬限无条件执行**（fail-closed，不可绕过） | passive 节流软策略（`POWER_POLICY`） |

### 2.4 方案 / 权衡 / 推荐立场

- **方案 A（内核内嵌完整 suspend 状态机 + 策略）**：Linux 式 `cpuidle`/`autosleep`。**权衡**：策略与内核紧耦合、TCB 膨胀、违反 `00` A6「重服务出核」；且策略知识（电池/AC/`Job` 活跃度）本在用户态，硬塞内核是缝合。
- **方案 B（内核只留 idle + 最小 suspend 原语，状态编排归 `powerd`）**：Fuchsia powerman / ChromeOS `powerd` 范式。**权衡**：每次 suspend 决策走用户态→内核受控接口有一跳 IPC，但借 `00` A10 `mkit` 薄层规避每 syscall IPC 代价（`40` §3 关键观察）；TCB 最小、可重启、可灰度。
- **推荐立场**：**采纳 B**。原型期只实现 `running → idle → deep-idle` 全链 + `NOHZ` tickless；`request_suspend(S3)` 留内核**原语接口**但 Day 1 **不实现策略**（`40` §9.3 已定「suspend-to-RAM 不在 Day 1」）。内核绝不在 idle/suspend 路径持有「电源策略状态机」。

### 2.5 唤醒源（wakeup sources）

唤醒源三类，全部可映射到既有对象，**不引入新内核原语**：

1. **定时器唤醒**：`57` §3.4 timer 对象到期 → `TIMER_FIRED` 经 EventPort 唤醒绑定线程；与 `NOHZ` tickless 协同（`57` §5.1）。
2. **设备中断唤醒**：`59` §4.1 `Cap(IRQ n)` 对象被硬件 IRQ 命中 → `IRQ_WAIT` 返回唤醒驱动线程（`59` §5.3 合并+轮询降频）。
3. **外部事件唤醒**：AC 插拔 / RTC 闹钟 / 网络唤醒(WoL) / 键盘——本质仍是设备 `Cap(IRQ n)` 或专有 timer（RTC）；「是否允许某外部事件唤醒 suspend 系统」由持 `POWER_POLICY`（`40` §7.1）的 `powerd` 决定。

> 不引入「wakeup source」内核对象：外部唤醒统一收敛为 `Cap(IRQ n)` + timer 对象，复用 `59`/`57` 既有一等对象模型（对齐百思纪律「不引入新内核原语除非必要」）。

## 3. DVFS / 频压策略：governor 落点

### 3.1 解构推演：选频是「策略」不是「机制」

频压（P-state/OPP）硬件写入是内核特权动作（写 MSR/CPM/PMU/`arch_pm_set_freq`），但「选哪个频」依赖 `Job` 负载、`thermal_headroom`、电池/AC、性能策略——是典型用户态知识。故 **governor 取数在内核、决策在用户态**，与 `00` A6「重服务出核缩 TCB」同源。

### 3.2 方案对比

| 维度 | 方案 A：内核内 governor（schedutil 式） | 方案 B：用户态 governor + 内核受控接口（**推荐**） |
|------|----------------------------------------|--------------------------------------------------|
| TCB 影响 | 膨胀（governor 逻辑留核） | 最小（governor 在 `powerd`） |
| 与 A6 一致性 | 违（重服务留核） | 符（出核） |
| 选频 IPC 代价 | 无（零 IPC 取数+决策同址） | 每决策一跳；借 `mkit` 薄层（`00` A10）+ `cpu_power_state` 只读结构（`40` §5.1）把「热路径取数」留核、「决策」异步下发，规避 Fuchsia 每 syscall IPC |
| RT 频点保活 | 内核内易保证 RT 不降频 | 需显式 `CAP_RT`（`07` bit45）约束 `powerd` 不得对 RT 域降频 |
| 策略可灰度/可重启 | 难 | 易（`powerd` 可重启） |

### 3.3 推荐立场：用户态 governor + 内核受控接口

1. **内核暴露受控接口**：`arch_pm_get_freq()`（读当前档，进 `cpu_power_state` 只读结构，`40` §5.1）+ `arch_pm_request_freq(target_bin)`（受 `POWER_POLICY` 约束写 P-state/OPP）。**不新增内核对象**，复用 `27` §3.2 的 P-state/OPP 表 + `40` §5.1 `cpu_power_state`。
2. **governor 在 `powerd`**（用户态，持 `POWER_POLICY`）：聚合 `ENERGY_READ`/`THERMAL_READ`（`40` §7.1）+ `Job` CPU 配额（`04` §4.4）→ schedutil 式选频 → 经 `arch_pm_request_freq` 下发目标档。
3. **与 `CAP_RT`(bit45) 协同**：RT 域线程的频点保活由 `CAP_RT` 保证——`powerd` 不得对「含 RT 线程的核/簇」降频至破坏 `04` §5 实时预算；具体是「`CAP_RT` 隐含防降频」还是「需显式 right」见待决项 Pw2。
4. **`KERNEL_PRIV`(bit12) 边界**：若某架构紧急热压下需内核直写频/压 MSR（不可交用户态），归入 `29` D-T1 已采纳的 `KERNEL_PRIV`，与 `40` §7.1 同构——非新 right。
5. **零新内核原语**：不新建「governor 内核模块」，完全复用 `27`/`40` 已有接口 + `07` capability 模型。

### 3.4 与 `00` A6 协同声明

governor 出核是 `00` A6「尽快交权用户态缩 TCB」在电源域的直接落地——与 FS/网络/驱动出核同构；内核仅保留「机制（写频压/进 idle）+ 唯一裁决点（热硬限）」，策略（`powerd`）出核可重启。

## 4. per-Job 能耗账本（与 能耗-Job 已采纳协同）

### 4.1 与 `00` §3「能耗-Job」已采纳项的协同

第四轮已自主采纳：**能耗原型期不作为 `Job` 账本（`04` §4.4）的硬配额项，仅作 task packing 输入**（非第六类资源）。本文据该已采纳结论定稿：

- **弱耦合契约（原型期生效，与 `40` §4 同）**：`Job` 账本既有资源（CPU 时间 / 内存 / 句柄数 / IO 带宽 / 进程线程数）**不变**；能耗不进账本、不强制上限、不计入费。`powerd` 据某 `Job` 的 **CPU 配额余量**做同 `Job` 聚核、空闲核深 idle（`40` §4.1）。
- **调度器只读不写**：`04` §4.3 `sched_class` 的 EAS 子策略仅做聚核/偏向，不触碰账本写入（`40` §4.1 / §5.2）。

### 4.2 强耦合升级路径（待 `04` §5 议题 6 解锁）

把能耗升级为**硬配额**（超限则限流该 `Job` 的 CPU 功率或降其权重）须等 `04` §5 议题 6（NUMA / 异构核 big.LITTLE EAS）裁决——因为「能耗预算」如何与「小核省电/大核性能」的异构调度偏置交互，只有在异构核 EAS 定稿后才能定义清楚（`40` §4.3 / §10 阶段 B）。届时再扩展 `04` §4.4 账本对象与检查点，仍受 thermal 硬限压制。

### 4.3 fail-closed 不变量（强制边界）

- **热硬限始终为内核无条件边界**：无论弱/强耦合，`27` §4.2 critical thermal trip 无条件触发（passive 节流→critical 关断），任何用户态（含 `powerd`、含被攻破服务）**不可禁用或抬高** critical trip——等价于 `07` fail-closed（`40` §6）。
- **能耗账本不得突破热硬限**：即使强耦合下某 `Job` 能耗配额被放宽，内核热硬限仍优先于任何 `Job` 约束（`40` §6 不变量）。
- **读权轻量可授、写权受 capability**：能耗/`Job` 能耗聚合读数经 `ENERGY_READ`（观测服务 `12` 持有，`40` §7.1）；写权（`POWER_POLICY`/选频）受约束 mint、可审计、可 revoke（`07` 同构）。

### 4.4 方案 / 权衡 / 推荐立场

- **权衡**：强耦合（能耗硬配额）能在异构核场景做精确能效预算，但过早锁定一套**跨架构不齐**的会计语义（RAPL 完整 vs AMU/PMU 近似 vs SBI-PMU 碎片化 vs loongarch/i386 缺失，`40` §8），并迫使 `04` 账本复杂化。
- **推荐立场**：**原型期严格弱耦合**（与 `00` §3 已采纳、`40` §4 完全一致）；强耦合作为 B 阶段**选项**而非 Day 1 默认，解锁条件明确绑定 `04` §5 议题 6，不预设进 Day 1。fail-closed 热硬限为永久不可绕过边界。

## 5. 与 57 timer / 59 中断 的能耗协同（唤醒聚合是第一杠杆）

### 5.1 `57` timer：deadline + slack 合并 → 减少唤醒次数

- `57` §3.4 每定时器带 `slack`（最早触发窗 `[deadline, deadline+slack]`），调度器/时钟中断把同一 slack 窗内多个定时器**合并到同一 tick 触发**（Zircon `ZX_TIMER_SLACK_*` 同源）。slack 越大，唤醒越能对齐到 cache/核唤醒边界，**直接减少 CPU 被唤醒次数 → 省电**。
- `57` §5.1 tickless：无就绪任务时停周期 tick，靠下一次定时器/外设中断唤醒；这是 deep-idle（§2.2）能成立的前提。
- **协同点**：`powerd` 的 idle 偏向（`avail_idle_depth`）与 timer 的 slack 默认值应**联合标定**——slack 越大越能凑出长 idle 窗口，二者同为「唤醒聚合」杠杆（呼应 `57` §8.3 T4）。

### 5.2 `59` 中断：合并 + 轮询 → 降低能耗

- `59` §5.3 高频设备（virtio-net 10G+）用**中断合并 + 轮询混合**（`19` AP-2）：合并后的「就绪事件」仍经 EventPort 投递，中断频率与调度唤醒次数**解耦**，避免 IPC 风暴拖垮调度器、也避免每包中断唤醒 CPU。
- **协同点**：中断合并窗口与 timer slack 同源思想——都是「把零散唤醒聚成大块 idle 间隙」。三系统（timer / 中断 / 调度器）共用一套 slack/合并抽象，是能耗第一杠杆（`40` §3 关键观察）。

### 5.3 推荐立场

唤醒聚合（timer slack + 中断合并/轮询）是能耗优化**最高性价比**杠杆，优于频繁选频；`powerd` 与内核应在「slack 默认值 / 中断合并窗口 / idle 偏向」三参数上联合调参，且三者均经既有 `57`/`59`/`40` 接口暴露，**不新增内核原语**。

## 6. 五架构功耗差异与薄后端

### 6.1 差异点（功耗态视角）

复用 `28` §6 五架构计时/确定性差异的「硬件稳定性」视角，从**功耗态**补充（与 `40` §8 能耗计量视角正交）：

| 架构 | 低功耗态能力 | 功耗后端要点 | 对状态机的影响 |
|------|--------------|--------------|----------------|
| **x86_64** | `MWAIT` C1–C6 + package C-state(PC-state) + S3/S4；RAPL 完整 | `arch_pm_enter(state)` → MWAIT hint；S-states 经 ACPI `_CST` | 节能态最丰富，idle/suspend 收益最大；RT 双验证架构之一（`28` §6） |
| **aarch64** | PSCI `CPU_SUSPEND`（core/cluster power-down，retention/non-retention）；GICv3 redistributor 可 power-down；big.LITTLE 多簇 | `arch_pm_enter` → PSCI `SYSTEM_SUSPEND`/`CPU_SUSPEND`；GIC 节能态随核休眠 | **异构核 EAS 刚需**（`04` §5 议题 6）：小核深 idle 是大头省电；功耗协同价值最高 |
| **riscv64** | SBI Hart State Management（`SUSP`/`RETENTION`）+ `Sstc`；平台碎片化、标准化最弱 | `arch_pm_enter` → SBI `hart_suspend`；**统一 SBI 抽象屏蔽 SoC 差异**（`28` §6 R9 抖动来源同理） | 标准化弱：薄后端须统一 SBI 接口，差异不暴露给状态机 |
| **loongarch64** | 自有 idle/省电 CSR；成熟度待验 | `arch_pm_enter` 对齐自有 CSR；M5 后移（`11` §5-4） | 同构薄后端替换，先保证正确 |
| **i386** | `HLT` idle；无 RAPL、无现代 C-state；仅基础 idle + ACPI thermal | `arch_pm_enter` → HLT；无深度 C-state | **最小**：仅 idle + thermal，能耗会计基本放弃（`40` §8）；非重点架构 |

### 6.2 收敛原则：统一 `arch/pm` 薄后端（与 `00` §5-6 同构）

- **统一抽象**：状态机只认 `enter_idle(depth)` / `request_suspend(state)` / `wakeup_source_route()` 三个架构无关原语；`cpu_power_state`（`40` §5.1）统一暴露 `avail_idle_depth` / `cur_freq_bin` / `thermal_headroom` / `pkg_energy_rate`。
- **薄后端职责**：仅做「架构指令 ↔ 统一原语」映射（MWAIT/C-state ↔ GIC/PSCI ↔ SBI SUSP ↔ loongarch CSR ↔ HLT），**不含任何策略**（策略全在 `powerd` + 调度器）。
- **不侵蚀统一模型**：五架构差异关进薄后端，与 `00` §5-6「统一抽象 + 每架构薄后端」、 `27` §6 / `40` §8 收敛原则完全一致；i386/loongarch 的退化面以「最小 idle + 近似能耗」兜底，不阻塞 task packing（`40` §8 收敛原则）。

### 6.3 推荐立场

功耗态差异是「五架构一致性成本」（`00` §5-6）在电源域的表现，收敛方式与中断控制器（`59` §7）、时钟源（`57` §6）同构——**统一状态机 + 每架构 `arch/pm` 薄后端**，内核核心只持最小状态原语，差异不向上泄漏。

## 7. MeuOS 推荐（收口）

1. **状态机内核最小、决策出核**：内核只实现 `running→idle→clock-gated→deep-idle→suspend→resume` 的最小状态原语 + 受控频压接口；idle/suspend 的「何时进哪档」与 DVFS governor 全部用户态 `powerd` 化，与 `00` A6 重服务出核同构。
2. **governor 用户态 + 内核受控接口**：选频决策在 `powerd`（持 `POWER_POLICY`），内核只暴露 `arch_pm_get_freq`（读）/`arch_pm_request_freq`（写 P-state/OPP，受 `POWER_POLICY` 约束）；RT 域频点保活由 `CAP_RT`(bit45) 约束；不新增内核对象，复用 `27`/`40`/`07`。
3. **per-Job 能耗严格弱耦合（与已采纳一致）**：原型期能耗不进 `Job` 账本硬配额（`00` §3 能耗-Job / `04` §4.4 / `40` §4），仅作 task packing 输入；强耦合（第六类账本）作为 B 阶段选项，解锁绑定 `04` §5 议题 6（异构核 EAS）。
4. **热硬限 fail-closed 为永久边界**：无论弱/强耦合，critical thermal trip 始终内核无条件执行，任何用户态不可绕过（`27` §4.2 / `40` §6）。
5. **唤醒聚合是第一能耗杠杆**：timer slack 合并（`57` §3.4）+ 中断合并/轮询（`59` §5.3）+ tickless（`57` §5.1）三者联合标定，经既有接口暴露，不新增内核原语。
6. **五架构功耗态关进薄后端**：统一 `arch/pm` 抽象（`enter_idle`/`request_suspend`/`wakeup_source_route`）+ 每架构薄后端（MWAIT/PSCI/SBI/HLT），差异不侵蚀统一状态机（`00` §5-6 / `59` §7 / `57` §6 同构）。
