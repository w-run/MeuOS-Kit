## 1. 概述与目标

### 1.1 背景与缺口

MeuOS 前几轮已把「系统如何原子更新」「服务如何被监督重启」「驱动如何下沉用户态」「能力如何撤销」分别成篇，但**内核/服务的动态加载与热升级（可加载模块、热补丁、滚动更新不重启）尚未单独成篇**。它不是一个孤立主题——它与 `.msys` 原子更新（06）、capability 撤销（07）、Job 监督灰度（04）、整卷升级杠杆（23）紧密咬合：

- 06 的 `.msys` repoint 已经能「不重启地切换 sysroot 视图」——这本身就是一种「热升级」的底座；
- 04 的 Job 监督已经能「崩溃即重启、灰度即切割」——这本身就是服务热升级的执行器；
- 07 的 capability revoke 已经能「旧域关闭、新域授权、无悬垂」——这正是动态加载的安全收口；
- 23 的整卷升级杠杆已经论证「内核+libc+服务同 `.msys` 同版本演进」弱化了细粒度 ABI 冻结的必要性。

既然底座齐备，本文件要回答的是：**在 MeuOS 的 capability 世界、最小 TCB、原子 `.msys` 更新下，"动态加载/热升级"应当是什么形态？内核 TCB 是否允许运行期加载代码？用户态组件如何热升级？与传统 LKM 在哪里决裂？**

### 1.2 设计目标

| 编号 | 目标 | 说明 |
|------|------|------|
| G1 | **内核 TCB 默认静态、不运行期加载** | monitor / IPC / 低级 VM / 调度核心 / 异常派发 / mkit 薄层在运行期不可被注入新代码（对齐 seL4 静态验证心态、保护最小 TCB） |
| G2 | **升级 = capability 重定向 + 服务重启（辅），内核热补丁（主路径之外）** | 系统功能演进以「换一个用户态服务 + 命名空间 repoint + Job 重启」为主，而非传统可加载模块巨石 |
| G3 | **仅允许受严格约束的可加载组件** | 非 TCB 用户态服务、可选 Rust 组件可经签名验证后加载，且加载即新 capability 域，旧域 revoke 由 07 保证无悬垂 |
| G4 | **与传统 LKM 决裂** | 不提供内核符号导出式 LKM；内核扩展只能通过「新用户态服务 + capability 授权」实现 |
| G5 | **五架构一致** | 签名验证（ed25519，复用 `.msys` v2 信封）跨 x86_64 / i386 / aarch64 / riscv64 / loongarch64 一致 |
| G6 | **A/B 仅防砖兜底** | A/B 双 slot 不用于日常组件升级（那是 06 repoint 主路径），只用于内核镜像/引导/FS 服务自身损坏的最后防线 |

### 1.3 范围

- 覆盖：内核 TCB 运行期加载策略、用户态服务/驱动热升级模型、受约束可加载组件模型、与 04/06/07/09/23 的接口契约、A/B 兜底角色。
- 不涉及（见其他子领域文档）：具体 `.msys` 字节布局与签名算法（06/11）、capability rights 位图细节（07）、Job/资源账本原语（04）、驱动双轨与能力网关（10）、IPC 协议版本协商（23/05）、启动 Stage 细节（09）。

## 2. ①「应该是什么样」——解构型推演

### 2.1 还原「动态加载 / 热升级」的本质

传统内核语境里，「动态加载/热升级」被几种截然不同的机制混用，先把它拆开：

1. **LKM（可加载内核模块）**：把 `.ko` 注入 ring 0，扩展内核符号表、新增 syscall / FS 类型 / 设备驱动。本质是「在运行期扩大最被信任的组件」。
2. **livepatch / kpatch / kGraft**：运行期替换内核函数指针，做安全修复而不重启。本质是「在 ring 0 内打补丁」。
3. **kexec**：把新内核载入内存并跳转，绕过固件重启。本质是「换内核镜像但不走 bootloader」。
4. **initramfs / 早期模块**：启动早期从内存盘加载驱动再挂 rootfs。本质是「启动期的临时加载」。
5. **用户态服务热重启**（launchd / systemd 式）：替换二进制 + 重启进程。本质是「换用户态组件」，与内核无关。

这五种机制在「信任层级」「是否扩大 TCB」「是否需重启」上完全不同。MeuOS 必须先从第一性原理问：**在 capability + 最小 TCB + 原子 `.msys` 的世界里，哪些机制有存在必要、哪些应当被结构性消灭？**

### 2.2 在 MeuOS 约束下它应当是什么样

从 `00`/`01`/`07` 已定地基推演：

- **内核 TCB 应当是「构建期固定、运行期不可变」的**。理由分两层：
  - *最小 TCB 层*（`00` A3 / A6）：TCB = { capability 监视器、IPC 端点、低级 VM、线程调度、异常/中断派发、mkit 兼容转译薄层 }。这些组件一旦运行期被注入新代码，TCB 就不再是「最小且可审计」的，而是「随时膨胀」的——与 A3/A6 直接冲突。
  - *可验证性层*：seL4 的范式是**静态配置、几乎不支持运行期加载、证明态重铺**（见 §3.7）。要保留未来对内核 TCB 做形式化验证或强类型不变量证明的可能，TCB 的代码集必须在构建期闭合、运行期不可变。运行期向 ring 0 加载代码 = 把「不可验证的运行时可变」引入最该被信任的层。
  - *无 root 逃生舱层*（`07` §4.1）：任何 LKM / livepatch 机制实质都是「超级权限逃生舱」——它授予持有者在内核态执行任意新代码的权能，等价于 `CAP_SYS_MODULE` 的「新 root」。这与 Day 1 唯一 capability 模型、无隐式特权直接冲突。

  **推演结论 A**：内核 TCB 默认静态、不运行期加载。内核的「升级」只允许走「整镜像替换 + 引导级切换」，且频率被用户态下沉极大压低（因为绝大多数功能已不在内核）。

- **系统功能「演进/扩展」应当表达为「替换用户态组件」**。因为 FS（06）、网络栈（25，Day 1 全用户态）、驱动（10，用户态双轨）、监督策略（04）都已下沉用户态，「升级一个功能」=「用新版本的用户态服务替换旧版本」，而 06 的 `.msys` 原子 repoint + 04 的 Job 监督灰度已经提供了「不重启、可回滚、可灰度」的底座。这才是 MeuOS 真正意义的「热升级」——它是 capability 重定向 + 服务重启，不是内核代码注入。

  **推演结论 B**：用户态服务/驱动的热升级 = 包更新（进入新 `.msys` sysroot 子卷）+ 命名空间 repoint（06 §4.3d）+ Job 重启/灰度切割（04 §4.5 / 06 §4.3e）。旧进程续持旧能力、新进程用新 sysroot，无需全系统重启。

- **「动态加载」应当表达为「运行期 spawn 新版本化用户态组件」**。若确实需要运行期引入一个「之前不在 sysroot 里的」新组件（例如可选 Rust 组件、第三方非 TCB 服务），它应当在**用户态、作为新进程**被 spawn，且：① 经签名验证（链式到 boot root-of-trust，09 Stage 4 / 07）；② 得到一个**全新 capability 域**（新 Job / 新句柄集）；③ 旧版本（若存在）的 capability 经 07 的 revoke（derivation tree + close）回收，**无悬垂**。这根本不是「内核加载」，而是普通 spawn + capability 模型的正常用法。

  **推演结论 C**：受严格约束的可加载组件 = 用户态、签名验证、加载即新 capability 域、旧域由 07 revoke 闭环。内核态零参与、零特权扩张。

### 2.3 与传统 LKM 的决裂点（明确清单）

| 传统 LKM 能力 | MeuOS 对应物 | 决裂说明 |
|---------------|--------------|----------|
| `insmod` 注入 ring 0 代码 | 无对应物（内核不提供） | 内核 TCB 不运行期加载（结论 A） |
| 内核符号导出（`EXPORT_SYMBOL`）供模块链接 | 无 | 内核不向运行期代码暴露内部符号 |
| `module_init` 注册新 syscall / FS 类型 / 设备类 | 新用户态服务经 Service Registry（05）注册 + capability 授权 | 扩展点在用户态，经 07 授权（结论 B/C） |
| `request_module` 内核按需拉模块 | 监督者/包管理器按需 spawn 用户态组件 | 加载权在用户态、受 grant 约束 |
| `/proc/modules`、`/sys/module` | 无内核模块概念 | 内核无「模块」一等实体 |
| `CAP_SYS_MODULE` 特权 | 无（无 root 逃生舱） | 加载权 = 受约束的 `GRANT`/spawn 权，且只针对用户态 |

**一句话决裂**：MeuOS 不提供内核符号导出式 LKM；内核扩展只能通过「新用户态服务 + capability 授权」实现。内核永远不因「需要扩展功能」而 enlarge TCB。

### 2.4 三层模型雏形（详化见 §4）

```
┌──────────────────────────────────────────────────────────────┐
│ Tier A  静态内核 TCB（构建期固定，运行期不可加载新代码）          │
│         monitor / IPC / VM / 调度 / 异常派发 / mkit 薄层        │
│         升级 = 整镜像替换 + A/B 引导级切换（仅防砖兜底，§5.6）   │
├──────────────────────────────────────────────────────────────┤
│ Tier B  用户态服务/驱动热升级（主路径）                          │
│         包更新(新 .msys 子卷) → 命名空间 repoint(06) →          │
│         Job 重启/灰度(04) → 旧域 revoke(07)                     │
├──────────────────────────────────────────────────────────────┤
│ Tier C  受约束可加载用户态组件（按需动态加载）                    │
│         签名验证(root-of-trust) → spawn 新进程 = 新 capability  │
│         域 → 旧域 revoke(07) 无悬垂；内核零参与                 │
└──────────────────────────────────────────────────────────────┘
```

## 3. ② 多系统参照对比表

### 3.1 各系统机制梳理

- **Linux（LKM / livepatch / kexec / initramfs / A-B 分区）**：`insmod` 把 `.ko` 注入 ring 0，扩展符号表；`livepatch` 运行期替换函数指针做安全修复；`kexec` 载入新内核跳过固件重启；`initramfs` 启动早期加载驱动；Android 式 A/B 双分区用于系统更新防砖。代价：LKM 直接扩大 TCB、破坏可验证性，`CAP_SYS_MODULE` 等同新 root；livepatch 仍是对 ring 0 的热修补，审计难。
- **Windows（hotpatching / 服务重启 / CBS）**：用户态服务靠 SCM 重启升级（与 MeuOS Job 监督同思想）；内核 hotpatching 有研究但生产以补丁重启为主；驱动走 WDF 版本化（见 23 §4）。Windows 的「服务重启式升级」是 MeuOS Tier B 的正面范本，但其内核仍接受某些运行期补丁。
- **macOS（kext → DriverKit 退出内核 / 系统更新重启 / APFS 快照）**：传统 kext 是内核态驱动（类似 LKM，崩溃即内核崩溃）；现代 DriverKit 把驱动**移出内核**到用户态、可版本化（与 10 双轨 + 23 §4 同构）。系统更新多为重启 + APFS 快照回退（见 06 §4.3，但 APFS revert 是破坏式、需离线，MeuOS repoint 是非破坏式）。macOS 的「kext→DriverKit 退出内核」是 MeuOS Tier A 决裂 LKM 的最强工业佐证。
- **Android（动态分区 / super + 流式更新 / 模块化系统组件 / OTA）**：`super` 分区 + 动态分区表支持流式、不重启的 A/B 更新；系统组件模块化、经 OTA 整卷升级。其「模块化系统组件 + OTA 整卷升级」与 MeuOS 23 §5 整卷升级杠杆同源；A/B 防砖与 06 §4.3 兜底同思想。
- **塞班（软件安装/更新）**：平台安全能力模型下做应用/系统软件安装更新，进程级能力，无内核模块概念。其「无 LKM、靠签名软件包更新」取向与 MeuOS 一致，但粒度粗（进程级能力，非对象级 rights）。
- **ChromeOS / Fuchsia（包/组件原子更新、ZX 无传统 LKM、服务经包更新重启、pave 整盘更新、OTA）**：Fuchsia 的 Zircon **无传统 LKM**——所有功能以组件形式存在，驱动是 `driver_host` 用户态组件（10 §3.4），升级 = 包更新 + 组件重启，无内核运行期加载；ChromeOS 走 A/B 双 slot 签名更新（06 §3.6）。这是 MeuOS **三层模型最直接的范本**：内核静态、功能皆组件、升级皆包更新+重启。
- **seL4（静态证明配置、几乎不支持运行期加载、证明态重铺）**：能力微内核，配置在构建期静态确定，运行期几乎不加载新代码；要变更需重铺证明态。这是 MeuOS Tier A「静态 TCB + 可验证性」的哲学源头——MeuOS 不追求 seL4 的全证明，但继承「TCB 运行期不可变」以保住最小 TCB 与未来验证空间。

### 3.3 思想取长补短（非缝合）

- **借 Fuchsia / seL4**：内核静态、无传统 LKM、功能皆组件——这是 Tier A + Tier C 的骨架。
- **借 macOS DriverKit / Android 模块化 / Windows 服务重启**：功能扩展走用户态、走版本化、走重启——这是 Tier B 的工业印证。
- **借 ChromeOS / Android A/B**：防砖兜底形态——但 MeuOS 把它降级为「仅内核/引导层兜底」，主路径让位给 06 的 repoint（更细粒度、免重启、per-process 灰度）。
- **借 06 APFS 快照思想但修正**：MeuOS repoint 是**非破坏式、能力级、免重启、per-process 灰度**（06 §引用澄清 失真 5），不照搬 APFS 破坏式离线 revert。
- **不借**：Linux LKM 的「运行期扩大 ring 0 TCB」与 livepatch 的「ring 0 热补丁」——二者直接冲突最小 TCB 与无 root 逃生舱；seL4 的「全证明重铺」过重，MeuOS 仅取其「TCB 静态」精神。

## 4. ③ MeuOS 静态内核 + 组件化用户态热升级模型

### 4.1 Tier A：静态内核 TCB（不运行期加载）

- **范围**：`00` §1 定义的内核态「机制 + 唯一裁决点」——capability 监视器、IPC 端点、低级 VM（页表/ASID）、线程调度核心、异常/中断派发、mkit 兼容转译薄层（01 §4.1 唯一让步）、内核态快速驱动（10 §4.2：中断控制器/定时器/看门狗）。
- **铁律**：以上组件在运行期**不可被注入、替换、补丁化新代码**。内核镜像在构建期由单一工具链产出、经签名（链式到 root-of-trust），运行期只读映射（可设为 `prot_exec` 且不可写，或经 IOMMU/页表固化）。
- **内核「升级」通道**：内核镜像本身的变更**只允许整镜像替换**，经以下两种之一：
  1. **A/B 双 slot 引导级切换（兜底，§5.6）**：新内核镜像写入非活动 slot，签名校验后由 bootloader/09 切换，失败回退旧 slot。需重启。
  2. **`.msys` sysroot 内含内核镜像（可选，待决项 2）**：若内核镜像随 `.msys` 一同原子更新（06 §4.3 + 09 §6 待决 5），则内核更新也走 repoint，但仍需一次重启以加载新镜像——repoint 解决「视图一致性」，不解决「ring 0 代码替换需重启」的物理事实。
- **为何频率极低**：因 FS/网络/驱动/监督策略全在用户态（00 A6、25 C15、10），内核镜像的变更只涉及 TCB 自身 bug fix，**绝大多数「系统升级」落在 Tier B/C，不触内核**，故内核重启频率被结构性压低。

### 4.2 Tier B：用户态服务/驱动热升级（主路径，不重启）

这是 MeuOS 日常「热升级」的承载面，完全复用既有底座：

1. **新版本进入新 `.msys` sysroot 子卷**：包管理器把新版本服务/驱动写入 staging 克隆（06 §4.3c），签名校验（06 §4.3a）。
2. **原子 repoint**：`meu-supervisor` 决定切割时机（06 §4.3d/e），经单条命名空间能力事务把 `/msys` 别名从旧子卷重指向新子卷——这是 capability 级单点原子切换。
3. **Job 重启 / 灰度**：监督者按 manifest 对新 spawn 进程绑定新 sysroot（06 §4.3e per-process 灰度：先 10% 新进程用新 sysroot，观察崩溃率，再全量）；仍运行的旧进程续持旧 sysroot 能力（CoW 共享未改块）。
4. **旧域 revoke**：旧版本进程退出/被重启后，其句柄经 07 的 `close` + derivation tree 回收（07 §4.5），VMO/pager 上下文拆除（06 C2），**无悬垂**。
5. **回滚**：repoint 回备份快照即可（06 §4.3），同样原子、免重启。

驱动热升级特别说明：用户态驱动服务（10 §4.1 双轨隔离路径）天然支持此路径——新驱动经新 sysroot spawn，获新设备能力（10 §4.6），旧驱动经 10 §C8 撤销锁序列（IRQ 屏蔽→冻结→IOMMU 失效→revoke→kill）干净回收；协议版本差由 23 §6 协商吸收。

### 4.3 Tier C：受约束的可加载用户态组件（按需动态加载）

针对「运行期引入一个 sysroot 之外的新组件」（可选 Rust 组件、第三方非 TCB 服务）：

- **加载权威**：由一个持「spawn + grant + 验证」专属 capability 的服务（建议 `pkg-loader`，归属 supervisor 监管；具体权威归属见待决项 3）执行加载。普通进程无此权。
- **签名验证（跨架构一致）**：组件须携签名，链式到 boot root-of-trust（09 Stage 4 自举的 root-of-trust capability，07 消费）。验证算法复用 `.msys` v2 信封（SHA-256 + ed25519，见 11 §4.1 / 06 §4.3a），在 x86_64 / i386 / aarch64 / riscv64 / loongarch64 上**同一验证服务、同一根密钥**（待决项 4 确认信封复用）。
- **加载 = 新 capability 域**：验证通过后，`pkg-loader` 经 `meu_spawn`（04 §4.2）拉起新进程，归入一个**新 Job**（或显式子 Job），赋予**全新、受限的句柄集**（最小特权，07 §4.1）——这是一个独立的 capability 域，与任何旧实例不共享可写句柄。
- **旧域 revoke（无悬垂）**：若替换既有组件，旧实例句柄经 07 §4.5 `close`/derivation tree 回收；因加载即新域，旧域撤销不影响新域，且无「内核符号共享」类悬垂（那是 LKM 的特有风险，MeuOS 无此结构）。
- **内核零参与**：整个 Tier C 是用户态 spawn + capability 的正常用法，**内核不提供任何「运行期加载代码」原语**——这正是与 LKM 的本质区别（结论 C）。

### 4.4 签名验证与跨架构一致性（G5）

- **统一信封**：所有可加载组件（无论 Tier B 的 sysroot 内组件、Tier C 的 sysroot 外组件、乃至内核镜像本身）共用 `.msys` v2 式签名信封（SHA-256 校验 + 去重 + ed25519 签名 + 压缩，11 §4.1），由 boot root-of-trust 派生密钥验证。
- **跨架构**：验证服务本身是用户态（或由早期 Rust 运行时提供，09 Stage 3/4），五种架构后端**共用同一验证实现**（算法与架构无关）；仅被验证的**二进制**是 per-arch 的。i386 为甲等架构（09 C6），验证链路完整可用，不存在「i386 跳过验证」的退路。
- **失败即拒**：签名校验失败 → 组件拒绝加载 / 镜像拒绝切换，对齐 ChromeOS 签名校验 + TCB（06 §4.3a）。

### 4.5 与传统 LKM 的明确边界（G4）

MeuOS **不提供**以下内核机制（对应 §2.3 决裂表）：

- 无 `insmod`/`modprobe`、无内核模块对象、无 `/proc/modules`/`/sys/module`；
- 无内核符号导出表（`EXPORT_SYMBOL` 类）；无 `request_module`；
- 无 `CAP_SYS_MODULE` 或任何「运行期向 ring 0 注入代码」的 capability right；
- 无内核态 livepatch / ftrace 替换函数指针式热补丁（待决项 1 待架构裁决是否彻底关闭）。

若要「新增一个文件系统类型 / 网络协议 / 设备类 / 系统调用」，正确做法是：**写一个用户态服务**，经 Service Registry（05 §4.4）注册，并由监督者/包管理器经 07 授权所需 capability（如 06 的 mount-cap、10 的设备 cap、04 的 Job 创建权）。内核对此「扩展」**无需任何代码变更、无需暴露内部符号**——扩展点本就在用户态。

## 5. ④ 与 04 / 06 / 07 / 09 / 23 的接口契约

> 本节只声明依赖与协同点、不替其他子文档拍板；结论以其定稿为准。

### 5.1 与 06（`.msys` 快照 / repoint）

- **消费方**：本文件 Tier B 热升级直接消费 06 §4.3 的「子树级 CoW 快照 + 命名空间原子 repoint + 监督灰度」原语。
- **触发语义**：repoint（06 §4.3d）是 Tier B 的「切割开关」——单条 capability 级事务把 `/msys` 别名从旧子卷重指新子卷；本文件不重新定义 repoint，只规定「组件热升级 = repoint + Job 重启」。
- **回滚**：复用 06 §4.3 备份快照 repoint 回退，原子、免重启。
- **依赖 06**：签名校验用的根密钥能力（06 §4.3a / §4.4.3）由 07 root-of-trust 提供；VMO/pager 回收（旧域 revoke）见 5.2。

### 5.2 与 07（capability revoke 保无悬垂）

- **revoke 闭环**：Tier B/C 的旧域关闭靠 07 §4.5 的 `close` + derivation tree（07 自研增强，见 07 引用澄清 失真 4）+ VMO/pager 上下文回收（06 C2）闭环——旧进程句柄回收 → 内核拆除 VMO 派生链与 pager 注册 → 解密/访问停止，**无悬垂引用、无 KRL**。
- **新域隔离**：Tier C 加载即新 capability 域（新 Job + 全新句柄集），与 07 §4.1「无隐式权限、句柄即 capability」一致；最小特权由 spawn 时显式声明（04 §4.2）。
- **签名验证权**：验证服务消费 07 的 root-of-trust capability（09 Stage 4 自举），不内置信任根。
- **依赖 07**：rights 位图中是否需新增「加载/验证」专属 right（如 `LOAD`/`VERIFY`，区别于 `GRANT`/`MANAGE`）待 07 定稿（待决项 3 协同）。

### 5.3 与 04（Job 重启灰度）

- **执行器**：Tier B 的「切割 + 灰度 + 重启」由 `meu-supervisor`（04 §4.5）执行——监督者按 manifest 决定 per-process 灰度（06 §4.3e）、消费进程退出事件做重启/升级。
- **资源账本**：Tier B/C 新组件的 CPU/内存/句柄/IO 计入其所属 Job 账本（04 §4.4），与原生进程同构；升级期间双实例共存受 Job 配额约束（待决项 6 实测峰值）。
- **监督者自举环**：若 `meu-supervisor` 自身崩溃，内核自举重启（04 §5 待决 4 / 09 §6 待决 10）——保证 Tier B/C 的执行器不消失。

### 5.4 与 09（启动 / root-of-trust / A-B 兜底）

- **root-of-trust 自举**：09 Stage 4 自举第一批 capability 含 root-of-trust（签名验证根），供本文件 §4.3/§4.4 验证服务消费；capability 监视器先于任何非特权代码激活（09 §5.4），保证「加载权本身受能力约束」。
- **无 initramfs 模块加载**：09 §5.2 启动链**不在早期加载外部内核模块**（无 LKM 启动依赖）；内核静态构建，所需驱动经 10 用户态双轨在 Stage 5 由 devmgr 拉起。
- **A/B 兜底协同**：内核镜像/引导的 A/B 切换由 09 启动流程承载（06 §4.3 防砖兜底协同），与本文件 §5.6 一致。

### 5.5 与 23（整卷升级杠杆 / IPC 版本协商）

- **杠杆复用**：23 §5 论证「内核+libc+服务同 `.msys` 同版本演进」弱化了细粒度 ABI 冻结——本文件 Tier B 正是该杠杆的落实：组件热升级随 sysroot 同版本，无需逐接口 ABI 冻结。
- **IPC 版本协商**：Tier B/C 滚动更新期间新老组件共存（06 §4.3e），跨版本 IPC 互通由 23 §6 的 `protocol_version` + `min_compatible_version` 协商吸收；协商失败可观测、可回退（23 §6.2/§6.4）。
- **驱动 ABI**：用户态驱动热升级（Tier B + 10 §5.4）经 23 §4.2「用户态驱动可版本化稳定」——设备能力 schema + FIDL 风格 IPC 版本协商，天然比 Linux 内核模块易版本化。

### 5.6 A/B 防砖兜底的精确角色（G6）

- **A/B 不是日常组件升级路径**：日常组件/服务/驱动升级走 Tier B（06 repoint），免重启、per-process 灰度、细粒度——A/B 的双 slot、2x 空间、必重启代价在此被回避（06 §4.3 已论证）。
- **A/B 仅兜底「repoint 机制自身不可用」的场景**：当损坏严重到 FS 服务或 supervisor 自身起不来、连 repoint 都无法执行时，才由引导级 A/B 切回已知良好 slot。即 A/B 保护**引导 + 内核 TCB + FS/supervisor 自举链**这一层，而 06 repoint 保护**用户态组件层**。
- **分层兜底**：
  ```
  用户态组件损坏   → Tier B repoint 回退（06，免重启，细粒度）
  内核/FS/supervisor 自举链损坏 → A/B 切 slot（09，需重启，粗粒度，最后防线）
  ```

## 6. ⑤ 自主结论 + 待决项

### 6.1 核心结论

1. **内核 TCB 默认静态、不运行期加载**（结论 A / Tier A）——保护最小 TCB、保住未来可验证性、消灭「运行期扩大 ring 0」的 root 逃生舱，与 seL4 静态心态、07 无隐式特权同构。
2. **系统热升级 = capability 重定向 + 用户态服务/驱动经包更新 + 命名空间 repoint + Job 重启**（结论 B / Tier B）——主路径完全复用 06 + 04 底座，免重启、可灰度、可回滚。
3. **动态加载 = 运行期 spawn 签名验证过的用户态组件，加载即新 capability 域，旧域由 07 revoke 无悬垂**（结论 C / Tier C）——内核零参与、零特权扩张。
4. **与传统 LKM 决裂**：不提供内核符号导出式 LKM；内核扩展只能通过「新用户态服务 + capability 授权」（G4）。
5. **A/B 仅防砖兜底**，主升级路径是 06 repoint（G6）；签名验证跨五架构一致（G5）。

### 6.2 待决清单（标注是否需架构裁决）

1. **【架构级·需大喵裁决】是否允许任何形式的内核 TCB 运行期补丁（livepatch 类）？**
   推荐：**默认不允许**任何 ring 0 运行期代码替换（含 livepatch / ftrace 函数指针替换）；内核唯一升级通道 = Tier A 整镜像替换 + A/B（§4.1）。理由：运行期补丁即「向最小 TCB 注入不可审计代码」，与 A3/A6、07 无 root 逃生舱、seL4 静态心态三重冲突。若未来确需紧急内核安全修复且不重启，应优先评估「缩小内核 TCB 使修复落用户态」而非引入 livepatch。需大喵拍板是否将「内核零运行期代码加载」写入编译期固定安全参数清单（类比 07 C16 ② 不可运行期改写项）。
2. **【架构级】内核镜像本身是否纳入 `.msys` sysroot 原子更新，还是独立 A/B slot？**
   推荐：内核镜像走**独立 A/B slot**（09 启动层兜底，§5.4/§5.6），`.msys` 只承载用户态组件层；避免「内核+用户态强耦合进同一 repoint」导致内核升级也必须走用户态 repoint 路径的循环依赖。但「`.msys` 是否扩展承载内核/设备树/启动配置」（09 §6 待决 5）仍待决，需 09/06 协同裁决内核镜像更新通道归属。
3. **【设计协同】「加载权威」归属**：谁持有 spawn + grant + 验证权（Tier C 的 `pkg-loader`）？建议为受 supervisor 监管的独立服务，其 `LOAD`/`VERIFY` right 是否新增进 07 rights 位图（区别于 `GRANT`/`MANAGE`）需 07 定稿；与 04（监督树）/07 协同。
4. **【设计协同】组件签名信封复用**：Tier B/C 组件签名是否复用 `.msys` v2 的 ed25519 信封（11 §4.1），还是独立组件签名体系？与 07 root-of-trust / 23 协同；推荐复用以减少信任根种类。
5. **【设计协同】内核态快速驱动能否无停机热更新**：10 §5.4 已标原型期不做；本文协同确认内核态驱动随 `.msys` 同版本升级（23 §4.1），运行期不热更，损坏走 10 §C8 撤销锁 + panic/重启策略。与 10 协同闭环。
6. **【实测】双实例共存峰值**：Tier B 滚动更新期间新旧组件共存的资源/句柄峰值、repoint 原子性基准——需原型量化（关联 06 pager 缺页开销、04 Job 账本）。

### 6.3 与总览冲突表的衔接

- 本文结论 1/2（静态 TCB、无 livepatch）若被采纳，建议在总览冲突表追加一项（候选 **C17**）：「内核 TCB 运行期加载策略 = 默认静态、不提供 LKM/livepatch、仅 A/B 整镜像兜底」——性质为架构级裁决，待大喵拍板后回写。
- 本文与既有 C1–C16、31 无冲突；C2（密钥=capability）、C3（每进程 namespace）、C8（设备能力撤销锁）、C15（网络栈用户态）、C16（编译期固定安全参数）均为本文 Tier A/B/C 的支撑项，本文仅消费、不修改。
