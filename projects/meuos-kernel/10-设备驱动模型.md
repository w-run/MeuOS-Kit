# 10. 设备驱动模型

> 子领域：设备驱动模型 / Driver Model
> 团队：kernel-plan（调研员 k-driver）

## 1. 概述与目标

### 1.1 为什么驱动模型是内核设计的核心难点

设备驱动是内核中代码量最大、缺陷密度最高、与不可信硬件边界直接接触的部分。根据 Google 在 ACSAC 2024 对 Linux 内核的分析，设备驱动占内核代码量的相当比例，且是内存安全类漏洞（越界读写、UAF、空指针解引用、锁误用）的高发区 [Ref-11]。驱动同时面临两类压力：

- **性能/延迟压力**：中断处理、DMA、高频 I/O 路径对缓存局部性与上下文切换开销极其敏感。
- **稳定/安全压力**：单个驱动崩溃或越权不应拖垮整个系统；驱动只应触及它拥有的硬件。

这两类压力天然对立，决定了「驱动放内核还是用户态」是驱动模型的首要分界问题。

### 1.2 本文目标

本设计为 MeuOS 混合内核定义一套**分层、能力约束、Rust 友好**的驱动框架，明确回答：

1. 哪些驱动必须留内核态（性能/中断敏感），哪些下沉为独立用户态服务（稳定/安全隔离）。
2. 与 Linux 驱动模型、Windows WDM/WDF、macOS IOKit、Zircon 驱动框架的取舍差异。
3. Rust 写驱动的可行性与收益边界。
4. 设备树（DT）/ACPI 如何被解析、抽象为能力，并下发给驱动。
5. capability-based 安全如何约束驱动权限（驱动只拿到所需设备能力）。
6. 原型期最小驱动集（串口、virtio 块设备、virtio 网络等）。

### 1.3 设计目标（可衡量）

| 目标 | 说明 | 验收暗示 |
|------|------|----------|
| 故障隔离 | 单个用户态驱动崩溃可被重启，不污染内核与其他驱动 | 重启机制 + 看门狗 |
| 最小权限 | 驱动只持有其设备的 MMIO/IRQ/DMA/端口能力 | 能力表审计 |
| 内存安全 | 新写驱动默认 Rust，编译器消除整类漏洞 | 0 未定义行为类 bug（静态保证） |
| 性能可分级 | 中断敏感路径可留在内核态快速通道 | 中断延迟基准 |
| ABI 兼容不绑定驱动 | 兼容层只面向应用，不要求 Linux 二进制驱动 | 驱动为源码级自研 |

## 2. 设计约束与上下文

### 2.1 混合内核边界（来自 `01-内核架构选型.md`）

MeuOS 采用**混合内核**：核心（调度、内存、IPC、能力系统）在内核态；部分服务（文件系统、网络栈、部分驱动）可在用户态。驱动模型必须显式区分「内核快速路径」与「用户态隔离路径」：

- **内核态驱动（in-kernel driver）**：直接访问硬件、处理硬中断、参与调度关键路径。仍受能力约束（见 2.4），但运行在 ring 0。
- **用户态驱动服务（user driver service）**：作为独立进程/组件，通过 IPC 与内核及客户组件通信，硬件访问经由内核代理（MMIO 映射、IRQ 转发、DMA 缓冲区管理）。

混合内核的折中本质：比纯微内核少一次 IPC 往返（性能更好），比纯宏内核隔离更弱（故障面更大）。MeuOS 的差异化武器是**能力约束**——即便内核态驱动也只持有自己设备的能力，缩小了「宏内核全特权」的传统缺陷面。

### 2.2 Linux ABI 兼容层的影响（来自 `08-Linux兼容层.md`）

关键原则：**兼容层只面向应用程序，不面向设备驱动**。MeuOS 不追求加载 Linux 内核模块（`.ko`）二进制——那会与 capability 模型直接冲突（Linux 驱动默认内核全特权）。因此：

- 应用侧通过兼容层调用 `read/write/ioctl/open` 等，由 VFS/字符设备子系统路由。
- 驱动侧是 MeuOS 原生实现；若需复用 Linux 驱动逻辑，走**源码级移植 + 能力适配**，而非二进制兼容。

### 2.3 设备枚举来源：DT 与 ACPI

- **设备树（Device Tree, DT）**：ARM/RISC-V 等平台通常通过 `*.dtb` 描述静态硬件拓扑；绑定规范见 `devicetree.org` [Ref-12]。
- **ACPI**：x86 通过 ACPI 表（DSDT/SSDT）描述可枚举与热插拔硬件；规范由 UEFI Forum 维护 [Ref-13]。
- MeuOS 在启动早期（`09-启动与初始化.md`）解析 DT/ACPI，构建**设备拓扑树**，并将每个设备的物理资源（MMIO 基址区间、IRQ 号、DMA 窗口、IO 端口）登记为能力，后续由驱动管理器按「驱动声明所需资源」做匹配与授权。

### 2.4 capability-based 安全对驱动的约束（来自 `07-安全模型.md`）

能力是「不可伪造、可撤销的权限令牌」。对驱动而言：

- 内核在装载驱动前，依据设备拓扑为其签发**设备能力集合**：`Cap(MMIO range)`、`Cap(IRQ n)`、`Cap(DMA window)`、`Cap(IO port)`。
- 驱动发起的每一次硬件访问都需经能力校验；无能力则访问被拒绝（内核快速失败，而非段错误扩散）。
- 这等价于把 MINIX 3「用户态隔离驱动」的思路推进到「**即便在内核态也最小权限**」——这是 MeuOS 相对传统宏内核/微内核的增量创新点。
- 与 seL4 设备能力思路一致：设备资源作为能力对象被授权与回收 [Ref-14]。

## 3. 业界方案对比

### 3.1 Linux 驱动模型（宏内核，全驱动在内核态）

- 核心抽象：`bus` / `device` / `driver` / `class`，统一由 `kobject`/`kset` 引用计数与生命周期管理，经 `sysfs` 暴露给用户空间，`udev` 处理热插拔 [Ref-1][Ref-2]。
- 驱动全部运行于 ring 0，共享内核地址空间，性能最佳但**任一驱动缺陷即内核缺陷**。
- 近年引入 Rust 抽象层（Rust for Linux, RFL），用 safe 封装 unsafe 基础，提供 `Driver`/`Device` 等 trait，但仍是内核态、全特权上下文 [Ref-9][Ref-11]。

### 3.2 Windows WDM / WDF（分层 + 双模式框架）

- **WDM（Windows Driver Model）**：传统模型，IRP（I/O Request Packet）驱动栈，开发复杂、易错。
- **WDF** 分为 **KMDF**（内核模式，高性能、中断/DMA 敏感设备）与 **UMDF**（用户模式，USB/传感器等，崩溃隔离、易恢复）[Ref-3][Ref-4]。
- 关键启示：**同一框架内按风险分级**——UMDF 用于稳定性，KMDF 用于性能。这正是 MeuOS 混合边界可借鉴的「双轨」思想。

### 3.3 macOS IOKit（内核态，面向对象 C++）

- XNU 内核内的驱动框架，基于 C++ 子集（libkern），`IOService`/`IORegistry` 构成设备对象树，按 `probe`/`match`/`start` 生命周期匹配 [Ref-5][Ref-6]。
- 驱动运行于内核态，面向对象、继承体系清晰，但**崩溃即内核崩溃**，无用户态隔离。
- 启示：设备对象树 + 生命周期状态机是良好的建模范式，MeuOS 可在用户态复刻其 `IORegistry` 思路。

### 3.4 Zircon / Fuchsia 驱动框架（DFv2，组件化用户态驱动）

- 驱动作为**组件**运行在 `driver_host` 进程中，由 Driver Framework（驱动管理器/索引/主机）管理；驱动间、驱动与系统其余部分主要通过 **FIDL** 通信 [Ref-7][Ref-8]。
- DFv2 引入**实时驱动（live driver）**与统一绑定（bind），强调驱动是独立可重启的组件，隔离性强。
- 启示：把驱动视为一等公民组件 + 用强类型 IPC（FIDL 类比 MeuOS 的 IPC）解耦，是微内核化驱动的现代范本。MeuOS 混合内核可取其「组件化」而保留部分内核快速路径。

### 3.5 MINIX 3（微内核，用户态驱动 + 自愈）

- 每个驱动作为**独立非特权用户态进程**；Reincarnation Server（RS）定期 ping，驱动崩溃则杀掉并重启新副本，实现自愈 [Ref-10][Ref-15][Ref-16]。
- 最大程度隔离与稳定，但每次 I/O 需多次 IPC（性能损耗），且中断需经内核转发。
- 启示：用户态驱动 + 看门狗重启是稳定优先场景的标准答案；MeuOS 将其作为用户态驱动服务的蓝本。

### 3.6 取舍对比表

| 维度 | Linux (kobject/sysfs) | Windows WDF (KMDF/UMDF) | macOS IOKit | Zircon DFv2 | MINIX 3 | **MeuOS（建议）** |
|------|------|------|------|------|------|------|
| 驱动运行位置 | 全内核态 | 内核/用户双轨 | 内核态 | 用户态组件 | 全用户态 | **混合：内核快速路径 + 用户态隔离服务** |
| 故障隔离粒度 | 无（全内核共享） | UMDF 进程级 | 无 | 组件/进程级 | 进程级 | **进程级（用户态）+ 能力级（内核态）** |
| 自愈/重启 | 无 | UMDF 可重启 | 无 | 组件可重启 | RS 看门狗 | **RS 式看门狗（用户态驱动）** |
| 中断处理 | 直接硬中断 | KMDF 直接 | 直接 | 内核转发至驱动 | 内核转发 | **敏感设备直接；其余转发** |
| 权限模型 | 全特权 ring 0 | 内核态全特权 | 全特权 | capability/组件沙箱 | 非特权进程 | **能力约束（内核/用户皆最小权限）** |
| 语言 | C（部分 Rust） | C/C++ | C++ 子集 | C++/Rust | C | **Rust 优先，C 兼容** |
| 驱动间通信 | 内核内部函数 | IRP/框架 | C++ 虚表 | FIDL | IPC 消息 | **IPC（兼容层 FIDL 风格）** |
| 性能 | 最高 | 高（KMDF） | 高 | 中（IPC 开销） | 低（多 IPC） | **分级：敏感路径近 Linux，隔离路径近 Zircon** |
| 自愈复杂度 | — | 中 | — | 中 | 低（RS 简单） | 中 |

## 4. MeuOS 选型建议

### 4.1 总体架构：双轨驱动 + 能力网关

```
┌──────────────────────────────────────────────────────────┐
│ 用户态驱动服务 (Rust)        用户态驱动服务 (Rust)          │
│  serial / virtio-blk / ...    网络栈 / 文件系统(外部)       │
│       │  IPC (FIDL 风格)            │                        │
├───────┴──────────────────────┴────────────────────────────┤
│  驱动管理器 (Driver Manager)  —— 匹配 DT/ACPI 资源→能力     │
│  能力网关 (Capability Gateway): 校验 MMIO/IRQ/DMA 访问       │
├──────────────────────────────────────────────────────────┤
│  内核态快速驱动 (Rust/C): 中断控制器、定时器、关键 DMA       │
│  硬件抽象层 (HAL): 寄存器映射 / IRQ 分发 / DMA 缓冲          │
└──────────────────────────────────────────────────────────┘
```

### 4.2 内核态 vs 用户态的分界准则

**留内核态（快速路径）**：
- 中断控制器（GIC/APIC）、定时器、看门狗——参与调度与生死。
- 极高吞吐 / 极低延迟设备：NVMe 关键路径、GPU 提交 ring（原型后可评估下沉）。
- 任何需要亚微秒级中断响应、无法承受 IPC 往返的设备。

**下沉用户态服务（隔离路径）**：
- 串口（UART）、virtio 块设备、virtio 网络、USB 大类、传感器、显卡显示输出——崩溃可重启、可被能力沙箱约束。
- 遵循 MINIX 3 思路：驱动进程非特权，硬件访问经能力网关代理；RS 式看门狗监控。

### 4.3 驱动生命周期与匹配（借鉴 IOKit + Zircon）

1. **枚举**：启动早期解析 DT/ACPI，生成设备拓扑树（内存中的 `IORegistry` 风格节点）。
2. **匹配**：驱动声明 `bind` 规则（兼容字符串 / VID:PID / 类）；驱动管理器比对设备节点。
3. **授权**：匹配成功后，内核依据设备节点资源签发能力集合（MMIO/IRQ/DMA/端口）。
4. **启动**：用户态驱动以「仅持上述能力」的进程启动；内核态驱动经 HAL 注册中断/映射区。
5. **运行/重启**：看门狗 ping；异常则杀掉并重启（用户态）或降级（内核态关键驱动触发 panic+重启策略）。

### 4.4 Rust 写驱动：可行性与收益边界

- **收益**：编译期消除整类内存安全漏洞（越界、UAF、数据竞争），直接对应 ACSAC 2024 对驱动漏洞的量化结论 [Ref-11]；`Driver`/`Device` trait 提供与 IOKit 同级的面向对象建模且不牺牲安全。
- **可行性**：RFL 已证明内核态 Rust 抽象可行 [Ref-9]；用户态驱动用 Rust 更无阻碍，且可直接复用 `core`/`alloc` 与安全 crate 生态。
- **边界/保留 C 的场景**：
  - 与既有 C 组件（HAL、兼容层）的 FFI 边界仍需 `unsafe` 封装，须集中审计。
  - 极端性能路径可用 Rust `#[inline]` + 内联汇编，必要时极少量 C。
  - 原则：**新驱动默认 Rust；C 仅用于遗留接口适配**。

### 4.5 DT/ACPI 与能力的衔接

- DT 解析器输出「节点→资源区间」映射；ACPI 解析器同样输出资源列表。
- 二者统一归一化为**设备能力描述**（与 `07-安全模型.md` 能力对象同构）。
- 驱动只需声明「我需要哪个设备的哪些资源」，无需知道物理地址；能力网关负责映射与校验，实现**驱动与物理布局解耦**。

### 4.6 capability 如何约束驱动（最小权限落地）

- 每个用户态驱动进程启动时仅被授予其设备的：MMIO 能力（特定物理页区间，经 IOMMU/页表映射）、IRQ 能力（特定中断号，内核仅向该进程转发）、DMA 能力（特定 IOMMU 域/窗口）。
- 内核态驱动虽在 ring 0，仍通过 HAL 访问宏，所有 MMIO 经能力表校验（违规即快速失败），避免「一处越权、全内核沦陷」。
- 能力可撤销：设备拔出/驱动卸载时回收，杜绝悬垂硬件引用。

## 5. 开放议题

1. **中断转发开销**：用户态驱动的 IRQ 经内核转发 + IPC 通知，高频率设备（如网络 10G+）是否仍可接受？是否需「中断合并 + 轮询混合」？需基准量化。
2. **DMA 与 IOMMU 强制化**：是否对所有用户态驱动强制 IOMMU 域隔离？老旧平台无 IOMMU 时的退化策略（仅允许受信内核态驱动）。
3. **内核态 Rust 驱动与 panic 语义**：Rust panic 在内核态如何映射为「驱动隔离失败 + 重启」而非全内核 panic？需定义 `panic_handler` 与驱动故障域边界。
4. **驱动热更新/版本化**：用户态组件化驱动天然支持热替换；内核态快速驱动如何做无停机更新（暂定原型期不做）。
5. **Linux 驱动源码移植成本**：评估将关键 Linux 驱动（如特定网卡）源码级移植到能力模型所需的适配层规模；可能提供「兼容 shim」降低移植量，但须防止 shim 成为能力逃逸口。
6. **用户态驱动与兼容层的交互面**：应用经 Linux 兼容层 `ioctl` 进入用户态驱动时，能力校验点应设在哪一层（VFS 入口 or 驱动网关）？

| UART/串口 | 用户态（早期可内核态回退） | 早期调试输出、控制台 | 1 个 MMIO/端口区间 + 1 IRQ |
| virtio-blk | 用户态 | 根文件系统块设备 | MMIO/PCI 区间 + 1 IRQ + DMA 窗口 |
| virtio-net | 用户态 | 网络栈后端 | MMIO/PCI 区间 + 1 IRQ + DMA 窗口 |
| GIC/APIC 中断控制器 | 内核态 | 中断分发 | 全局 IRQ 能力（仅内核） |
| 定时器 | 内核态 | 调度时钟 | 特定 MMIO 区间 |
| virtio-console | 用户态 | 控制台/日志 | MMIO + IRQ |

> 注：virtio 1.2 通过 virtqueue 环形队列 + 通知机制抽象设备，天然适合「用户态驱动 + 内核代理通知」模型 [Ref-17][Ref-18]，是原型期首选，避免直接写复杂物理设备。
