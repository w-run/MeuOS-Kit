## 1. 一句话核心

> **UI 的唯一范式是「客户端提交声明式场景节点、由唯一用户态合成器持有权威保留模式场景图并据焦点/层级合成」；合成器是唯一能力网关，mint 一切 surface / node / GPU 提交句柄、收窄 right、路由输入；客户端只持被收窄的 surface 句柄与 session 令牌，不持任何显示/GPU 特权 right。无 immediate-mode 命令流，无全局窗口树，无客户端直连 GPU，无 server 信任假设。**

## 2. 解构型推演：显示「应该是什么样」

> 先不问「MeuOS 的 GUI 怎么抄 Wayland/X」，而问「在 capability 世界、用户态驱动、最小 TCB 前提下，图形栈**应该**长什么样」。

### 2.1 现状包袱（X11/Wayland 的历史债）

| 包袱 | X11 | Wayland | 本质缺陷 |
|------|-----|---------|----------|
| **immediate-mode 命令流** | 核心协议 = 客户端逐 op 发「画点/画线/贴图」；XRender/XCB 仍逐命令 | 客户端逐帧 `commit` 一块 buffer + `damage` 矩形 | 客户端掌握「何时重画、画什么」的每帧控制权，server 只被动合成；协议面巨大、重入/同步 bug 多 |
| **全局窗口树 / 全局 registry** | 全客户端窗口挂在 server 一处全局树，靠 XID（全局可寻址）互查（`XQueryTree`、`XGetWindowAttributes`） | 全局 registry 列举 server 所有 global（compositor/seat/输出），客户端可枚举 | 存在一个「server 全局命名空间」供任意客户端探测/引用他人对象——与 MeuOS「无全局默认可见」（00 A4）直接冲突 |
| **客户端直连 GPU** | 无（X 时代）；现代 Linux 经 `/dev/dri/cardN` render node 直连 | 同 Linux：客户端拿 render node 全局权 | 把 GPU 命令提交权直接给不可信进程，command-buffer 解析在内核/驱动侧，是 ring 0 逃逸面（34 §8.3 已否决） |
| **server 信任假设** | X server 默认信任所有连入客户端：任意客户端可 `XGrabKeyboard` 截获全局输入、`XQueryTree` 窥探他人窗口 | 改善但未根除：seat/compositor 仍隐式信任客户端不滥用焦点/输入 | 「连上了就部分可信」违背 07 最小权限——沙箱内的客户端也应被 input/surface 边界隔离（42 §3.3） |
| **内核态 modesetting + GEM 缓冲管理** | DRM/KMS 内核态 | 同 | DRM/GEM 代码量巨大、污染 TCB（00 A6 明确反对重服务留核） |

### 2.2 推演结论（解构型基线）

在 MeuOS 的三条互锁地基（00 §1：capability 唯一模型 / 重服务出核缩 TCB / spawn-Job 资源账本）之上，显示应：

1. **UI 范式 = 保留模式（retained-mode）而非 immediate-mode**：客户端描述「我要一棵什么样的场景树」（节点 + 变换 + 内容绑定），**不逐帧发绘制命令**；合成器持有这棵树的权威副本（retained graph），负责把它变成像素。树是状态、是真相源，不是一条命令流。
2. **合成器 = 唯一能力网关**：display 设备能力、GPU 能力、surface/node 句柄的 mint、输入的路由，**全部**收口到合成器这一个用户态服务（类比 `06` FS 服务、`25` netstack——重服务出核、受 `meu-supervisor` 管理、可重启）。客户端不直连 GPU、不碰 display MMIO、不枚举全局对象。
3. **无全局窗口树**：场景图不是「一个 server 全局树 + 全局可寻址 XID」。每个客户端持一个 **session 令牌**，其提交的节点只挂在该 session 的子树之下；合成器把各 session 子树组装成权威图。**跨 session 引用不存在**——焦点/层级/输入交互全部经合成器按 capability 裁决，等价于「窗口隔离 = capability 边界」（34 §3.3、42 §3.3）。
4. **客户端不持特权 right**：客户端创建 surface/node 时，由合成器 mint 回**已收窄**的句柄（`SURFACE_SUBMIT`/`SURFACE_MANAGE`，不含 `DISPLAY_MODESET`/`GPU_MANAGE`/`DISPLAY_MANAGE`）。`DISPLAY_*`/`GPU_MANAGE` 仅合成器/受控 3D 服务持有（07 §4.1 冻结位图）。

> **与 34 的关系**：34 落地了「Wayland 兼容 + surface 即 capability + GPU 受限委托（D-G1/G2）」——那是**兼容性基线**。本文把原生范式从「Wayland 式 surface commit」升级为「保留模式场景图」，但**完全继承 D-G1/G2 的能力边界**：Wayland 兼容层只是合成器之上的一个前端客户端（34 §8.2），GPU_SUBMIT 模型不变（34 §8.3）。本文是 34 的「原生现代化纵深」，不是推翻。

## 3. 关键抽象：定义与关系

> 四个一等公民：**SceneNode（场景节点）** / **Surface（表面句柄）** / **Compositor（合成器·能力网关）** / **GPU 提交句柄**。内核只给四类机制（见 3.5），不实现任何合成/渲染逻辑。

### 3.1 SceneNode（场景节点）—— 保留模式图的唯一节点

- **身份**：保留模式场景图的基本单元，是 UI 的**唯一一等公民**。客户端不直接画像素，而是提交/修改节点。
- **属性（声明式、确定性）**：
  - `local_transform`：仿射变换（平移/缩放/旋转），矩阵或分解参数。
  - `opacity` / `clip` / `visibility`：合成属性。
  - `content`：绑定一个 **Surface**（像素/纹理内容）或为空（纯容器）。
  - `children`：有序子节点列表（形成保留树）。
  - `hit_test_policy` / `focusable`：输入命中与焦点语义（供合成器路由 `INPUT_RECEIVE`）。
  - `semantics`：无障碍/角色标签（可选，供系统服务消费）。
- **生命周期由 capability 管**：客户端经其 **session 令牌**向合成器提交「创建/改属性/挂父/删」操作；节点对象由**合成器持有**（retained），客户端只持操作该 session 子树的授权。节点**不可被其他 session 寻址**（无全局 ID、无 `XQueryTree` 等价物）。
- **与 immediate 的区别**：客户端不「每帧重画」，而是「声明树应该是什么样」；改一个 opacity 即一次声明，合成器在下一合成周期据整图求值。状态在合成器侧保留，客户端崩溃不影响已呈现内容（fail-closed 时由合成器 drain）。

### 3.2 Surface（表面句柄）—— 内容载体，capability

- **身份**：承载像素/纹理内容的 **capability 句柄**（07 §4.1：句柄即 capability）。由合成器 mint（带 `SURFACE_CREATE` 授权回传 `SURFACE_SUBMIT` 收窄句柄）回传给客户端。
- **内容 = graphic buffer VMO**：
  - CPU 写路径：客户端 `vmo_create` 一块 VMO，map 后写像素，把 VMO 句柄经 `05` Channel cap-transfer 交给合成器 → 零拷贝合成（接 `03`/`05`）。
  - GPU 写路径：经 `03` device VMO（GPU 可映射、可 DMA，遵循 device 内存「不可写」right）。
- **关键约束（与 34 一致但更严）**：Surface **不独立浮在全局窗口树里**——它总是被某个 SceneNode 的 `content` 引用才有呈现意义。脱离场景图的 surface 无呈现语义（无 X11 式「游离窗口」）。surface 句柄即隔离边界（34 §3.3 / 42 §3.3）。

### 3.3 Compositor（合成器 / 能力网关）—— 唯一权威

- **身份**：受 `meu-supervisor`（`04`）管理的用户态 Rust 系统服务，**唯一**持 display 设备能力（`DISPLAY_MODESET`(43)/`DISPLAY_MANAGE`(34)/`DISPLAY_LEASE`(44)）+ GPU 委托权（`GPU_MANAGE`(33)）的实体；由 `10` 能力网关签发 display/GPU 设备能力（MMIO/IRQ/DMA），可重启、可灰度。
- **作为「唯一能力网关」的职责**：
  1. 持**权威保留模式场景图**：接收各客户端 session 提交的节点子树，组装成单一合成图。
  2. **mint 一切图形句柄**（受约束 mint，破 confused deputy，07 §4.5）：surface 句柄（`SURFACE_CREATE` 35 → 回传 `SURFACE_SUBMIT` 41）、session 令牌、GPU 提交句柄委托（`GPU_SUBMIT` 32 经受控 3D 服务 mint）。mint 权限受「自身 rights 上限 ∩ 客户端请求下限」交集约束。
  3. **合成**：据整图（变换/不透明度/裁剪/层级/焦点）求值，输出到帧缓冲 device VMO 或经 GPU 加速合成。
  4. **输入路由**：输入设备经 `10` 用户态驱动 → Channel/EventPort 上报合成器；合成器按场景图 hit-test 把事件交付对应 surface 持有者（`INPUT_RECEIVE`(36) 按焦点授权），**杜绝跨 session 输入劫持**。
  5. **modesetting**：枚举/设模式经 `DISPLAY_MODESET` 能力，设备能力来自 `10`。
- **「唯一」的含义**：客户端↔GPU 服务↔显示驱动之间的**所有图形能力流动**都经合成器裁决。没有第二个服务能直接拿 display/GPU 设备能力，没有客户端能绕开它直连 GPU。这就是「网关」——与 `06` FS 服务、`25` netstack 同构（重服务出核、内核只给机制）。

### 3.4 GPU 提交句柄（GPU submit handle）—— 受控 3D 服务的收窄连接

- **身份**：= **GPU 连接 capability**（`GPU_SUBMIT`(32)，07 §4.1 冻结 bit 32），由**受控 3D 服务**（Magma 式，34 §8.3）mint 给客户端，**不含 raw MMIO/DMA**。
- **工作流**：客户端向 3D 服务请求一个 GPU 连接句柄 → 把 command buffer 写入 device VMO（`03`）经 `05` 交 3D 服务 → 服务**校验**（边界/句柄引用/地址空间）后提交硬件 → IOMMU（`10` §5-2）强制隔离 DMA，杜绝越权显存/系统内存访问。
- **在 方案A 中的角色**：GPU 加速合成/3D 是 Surface 内容的「生产者」之一，但 **surface 句柄始终是客户端与合成器之间的契约**；GPU 句柄不可越权触达他人 surface（34 §8.3 双重防线：校验 + IOMMU）。客户端永不持 `GPU_MANAGE`(33)。

### 3.5 四抽象关系图（保留模式 + 网关）

## 4. 多系统参照与取舍（解构非缝合）

| 系统 | 其 UI 范式 | 借鉴点 | 不选点 / MeuOS 取舍 |
|------|-----------|--------|---------------------|
| **Fuchsia Scenic** | **保留模式场景图**：Session + Node + Resource（Image/Surface），客户端发命令**变更**图，合成器持权威图；系统合成器用户态、组件框架管理 | **直接对标**：retained-mode scene graph 即原生 UI 范式、Session 隔离、资源由合成器 mint（capability 式）。本文的 SceneNode/Session 即 Scenic 思想的 MeuOS 落地 | Scenic 仍用 FIDL「命令流」变更图；本文更彻底——客户端提交**声明式节点对象**、图是 capability 作用域内状态，无全局可寻址。GPU 走 `10` 网关而非 Magma 直持 |
| **macOS AppKit / SwiftUI** | View 层级 = 保留模式树；SwiftUI 声明式描述 UI、系统持有渲染；WindowServer 用户态合成 | 借「UI = 声明式保留树、系统拥有合成」精神；AppKit 的 view 即 retained node | macOS 走 IOKit 内核驱动（我们走 `10` 用户态驱动 + 能力网关）；隔离靠 window/process 而非 capability 边界（我们取 capability） |
| **Windows Composition（Visual / DWM）** | **保留模式 Visual 树**：Visual 是 retained 合成节点，DWM 拥有并合成；应用改 Visual 属性而非逐帧绘制 | 借「Visual = retained 合成节点、compositor 拥有树」思想——与 SceneNode 同构 | Windows 有内核 GPU 调度器（DXGKrnl，TCB 膨胀）；我们 GPU 调度全用户态（受控 3D 服务）。隔离靠 session/desktop（我们取 capability） |
| **Android View / Material** | View 层级 = 保留模式树；SurfaceFlinger 合成 surfaces；Surface = Binder token（capability 式边界）；HWC 硬件合成 | 借「保留 View 树 + Surface = 对象级 token + 应用隔离 = token 边界」——与 34 §3.3 / 42 §3.3 同构 | HWC/HAL 是 Android 特定形态（我们走 `10` 用户态驱动）；不引入 Binder |
| **Flutter** | 声明式 widget → 经 reconciliation 产出**保留 layer tree**，engine 持有并合成；「该显示什么」与「怎么合成」彻底解耦 | 借「单一保留 layer/scene tree 作为 app↔compositor 的唯一接口、声明与合成解耦」思想——这正是 方案A 的核心价值主张 | Flutter 是单进程框架内自建 layer tree；MeuOS 把该 tree 跨进程化、capability 化、由合成器持有（多客户端共享一张权威图） |
| **X11** | immediate-mode 绘制协议 + 全局窗口树 + server 信任 | 仅作**反面教材**：逐 op 绘制协议、XID 全局可寻址、server 默认信任客户端（输入可截获） | **全否**：无 immediate 命令流、无全局窗口树、无 server 信任假设 |
| **Wayland** | 客户端逐帧 commit buffer + 全局 registry 枚举 global | 仅作**兼容基线**（D-G1 已采纳）：Wayland 客户端协议天然契合「客户端只持 surface 句柄」——兼容层是合成器之上的前端 | 不把 Wayland 的「surface commit 即唯一抽象 + 全局 registry」焊成原生范式；原生范式是保留模式场景图（本文升级点） |

**取舍总纲（解构非缝合）**：
- **取** Fuchsia Scenic 的「保留模式场景图 + 合成器用户态 + 资源 capability mint」作为骨架；
- **取** SwiftUI / Windows Composition / Android View / Flutter 的「UI = 声明式保留树、系统拥有合成、声明与合成解耦」作为价值核心；
- **拒** X11 的 immediate 绘制协议 + 全局窗口树 + server 信任；
- **拒** Wayland 把「surface commit + 全局 registry」当原生唯一抽象（仅作兼容层）；
- **拒** Linux DRM 内核态 modesetting/GEM（TCB 污染）；
- **合成器即能力网关**是 MeuOS 自研综合：它把「Scenic 式用户态合成器」+「07 capability mint 网关」+「42 沙箱 = 受限 capability 集合」三者在显示域收口为**唯一权威**。

## 5. 与 MeuOS 现有规划衔接（00 / 34 / 07 / 42）

### 5.1 继承 34-D-G1（Wayland 兼容）
- Wayland 兼容层是合成器之上的**前端客户端**（34 §8.2）：`wl_surface`/`wl_buffer` 由兼容层翻译为「SceneNode + Surface 句柄」提交给合成器；`wl_compositor` 全局即合成器本身。
- 兼容层自身只是普通客户端，持 `SURFACE_SUBMIT`/`INPUT_RECEIVE` 等收窄 right，**不持 `DISPLAY_MODESET`/`DISPLAY_LEASE`/`GPU_MANAGE`**（默认 deny），不击穿沙箱（34 §8.2、42 §4.3）。
- X11 仅经可选 X 服务器（XWayland 式），不进 Day 1 原生能力（34 §8.1）。

### 5.2 继承 34-D-G2（GPU 访问模型）
- GPU 访问 = 受控 3D 服务 + Magma 式用户态 GPU 驱动 + 收窄 right 的 GPU 连接 capability（`GPU_SUBMIT` 32）；客户不直连 GPU、不经 raw MMIO/DMA（34 §8.3）。
- 本文的「GPU 提交句柄」= `GPU_SUBMIT` 句柄，语义与 34 §8.3 完全一致，无新增 GPU right。

### 5.3 继承 07 冻结 rights 位图（不新增显示/GPU 域 right）
本文**完全复用 07 §4.1 已冻结的显示/图形 right**，不重定义、不冲突：
- `SURFACE_CREATE`(35) / `SURFACE_SUBMIT`(41) / `SURFACE_MANAGE`(42) —— surface/node 内容提交与状态调整。
- `DISPLAY_MODESET`(43) / `DISPLAY_LEASE`(44) / `DISPLAY_MANAGE`(34) —— 仅合成器/服务持有。
- `INPUT_RECEIVE`(36) —— 由合成器按焦点授权（隐私敏感，默认 deny）。
- `GPU_SUBMIT`(32) / `GPU_MANAGE`(33) —— 客户/3D 服务。
- **`CAP_RT`(45) 可组合使用**：对延迟敏感 surface（如 VR/实时仪表），客户端可持 `CAP_RT` 进入 RT 合成路径（44 §4.4 RT 预算），与 `SURFACE_*` 正交组合，不新增显示专属 right。
- **session 令牌**：客户端 session 是合成器 mint 的句柄，其「能否提交场景节点」隐含于 session 授权（受 `SURFACE_CREATE` 上限约束）。若未来需显式区分，可于 bit 48+ 预留区新增 `SCENE_SESSION`（与 `MEDIA_CAPTURE` 同构扩展位，07 §4.1 预留），**不挤占已冻结位**。

### 5.4 与 42 虚拟化/沙箱一致（隔离第一性 = capability 边界）
- **合成器本身是沙箱**：它 = 一个持特定 capability 集的 Job（`DISPLAY_*` + `GPU_MANAGE` + surface mint 权），受 `meu-supervisor` 管理、受 Job 账本约束（42 §3.3、04 §4.4）。
- **客户端 surface 隔离 = 其 session capability 边界**：容器内图形应用的 surface 仍受容器 Job 的 capability set 约束（42 §3.3、34 §3.3）；跨 session 无全局窗口树可探。
- **VM（L2）显示**：guest 想要显示，由合成器把 surface 句柄经 cap-transfer **委托进 guest**（等价 `03` device VMO / 句柄跨域授予），guest 不拿 raw GPU/display 设备能力——与 42 §5.3「设备经 capability 授予 guest、IOMMU 隔离」同构。
- **输入隔离**：`INPUT_RECEIVE` 按场景图 hit-test 授权，沙箱内客户端只能收其自身 surface 输入，无 X11 式全局输入截获（呼应 42 §3.3「攻击面 = 显式授予句柄集」）。

### 5.5 与 03 / 05 / 10 / 08 接口边界（声明依赖，不替其下结论）
- 图形缓冲 = VMO / device VMO（03），零拷贝经 `05` cap-transfer。
- 就绪通知复用 `05` EventPort（`EVFILT_CHAN` 帧就绪 / `EVFILT_USER` present done）。
- display/GPU 经 `10` 能力网关出核；GPU DMA 受 IOMMU 强制隔离（10 §5-2）。
- Wayland/X 兼容语义映射见 08（D-G1 已采纳，X 列入可选 shim）。

## 7. 相对 X11/Wayland 摆脱的包袱与代价

### 7.1 摆脱的包袱（主动丢弃的历史债）

1. **immediate-mode 绘制协议**：无「画点/画线/贴图」逐 op 命令流，无 per-frame `commit`+`damage` 的客户端控制权。消除一整类协议重入/同步 bug 与「客户端决定何时重画」的复杂状态机。
2. **全局窗口树 / 全局 registry**：无 XID 全局可寻址、无 `XQueryTree` 式跨客户端探测、无 Wayland 全局 global 枚举。场景图是 capability 作用域内的 retained 状态，跨 session 不可寻址——与 00 A4「无全局默认可见」、42「沙箱 = 受限 capability 集」一致。
3. **server 信任假设**：输入路由由合成器按 `INPUT_RECEIVE` 焦点授权，客户端**不能** `XGrabKeyboard` 式全局截获输入；合成器是网关，客户端只持收窄 right——根治 X11「连上即部分可信」的 input-snoop  legacy。
4. **客户端直连 GPU / render node**：无 `/dev/dri/cardN` 式全局 GPU 提交权，command-buffer 解析在受控 3D 服务（用户态）校验 + IOMMU 隔离，消灭 ring 0 逃逸面（34 §8.3）。
5. **内核态 modesetting + GEM 缓冲管理**：modesetting 是合成器用户态职责（持 `DISPLAY_MODESET`），无 DRM/GEM TCB 膨胀（00 A6）。
6. **「游离窗口」概念**：Surface 必须被 SceneNode 引用才有意义，无 X11 式独立于合成图的窗口对象——状态归一处（合成器），简化生命周期与崩溃恢复。

### 7.2 代价（须接受的设计权衡）

1. **保留图内存模型更重**：合成器持整张权威场景图，RAM 占用高于「server 只存最小 surface 状态」的 Wayland 式；但换来确定性、简化输入 hit-test、崩溃可 drain——属「用内存换简洁与可控」。
2. **客户端控制力下降**：无 X11 式逐 op 重绘、无 Wayland 式「我自己管 buffer 提交时序」的完全自由；一切须经声明式节点表达。极致低延迟/扫描线精确呈现需走 `GPU_SUBMIT` + `CAP_RT` 路径或 `DISPLAY_LEASE`（VR），非普通 surface 路径。
3. **新 SDK 成本**：原生 API 既非 X11 也非 Wayland，需 `meu-idldef`（37 IDL 唯一出口）生成 SceneNode/Surface 契约；Wayland/X 经兼容层（D-G1），但原生生态需自建。
4. **合成器单点**：保留图权威在合成器，其 bug 影响显示全域；以 fail-closed + `meu-supervisor` 重启 + 客户端 surface 重建（D-G7，34 §6.2）缓解，不消除单点。
5. **协议面迁移**：从「命令流」到「节点对象提交」是范式迁移，调试/性能剖析工具链需重新适配（无 X 时代 `xev`/`xwininfo` 等价物，需新 inspect 视图，接 12）。

> **判语**：代价是「内存 + 控制力 + 新 SDK + 单点 + 工具链」，收益是「去 immediate 协议复杂度、去全局树探测、去 server 信任、去 GPU 直连逃逸、去内核 DRM TCB」——与 00 A6「重服务出核缩 TCB」、07「最小权限」、42「沙箱 = 受限 capability 集」同源同向，是 MeuOS 现代化取向的必然收敛。
