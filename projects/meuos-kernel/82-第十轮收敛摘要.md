### §2.1 78 - 加密与密钥管理深化

- **一句话定位**：**以 `07` 既有 `KEY_*` 专属 right 为密钥操作唯一能力门禁（不复用 `MANAGE`/`GRANT`）；密钥材料由 VMO/secure-memory 承载、按 capability 派生与回收；密钥生命周期与 `32` 度量基 + `61` `.mimg` 信任链协同；备份加密复用 `73` 导出路径；五架构薄后端同源**。
- **核心设计**：
  - **密钥 right 模型**：复用 `07 §4.1` 已冻结的 `KEY_UNWRAP`(bit7) / `KEY_WRAP`(bit8) 两 bit 纪律，永不出现在跨进程 grant / mint 给客户端的句柄上（内核 mint 强制）；密钥句柄即 capability，权限随句柄走；受约束 mint（`07 §4.5`）破 confused deputy；句柄不可伪造（Rust 类型层 `PhantomData<Rights>`）。
  - **密钥材料承载**：密钥材料永驻 secure-memory / VMO，不出 pager；secure-memory 区 no-swap/no-dump 标记由 `03` VMO 属性承载，不另立新内核标志。
  - **密钥生命周期**：与 `32 §3.2` 度量基双锚 + `61 C61-4` 引导级恢复指针 + `.mimg` 信任链协同；密钥后端（硬件密钥岛/TPM/软实现）差异封薄层，逻辑同源；密钥轮换走 derivation tree 全断 + re-wrap 完成前不 revoke 旧句柄的原子性（`07 §5-4`）。
  - **备份加密**：复用 `73 §4.3` 备份导出路径 + `06 C2` 密钥=capability 复用 + `32` 公钥根验签，不新增 `KEY_*` 子项。

### §2.2 79 - 用户态服务监督与生命周期框架

- **一句话定位**：**基于 Job 树的监督框架——监督者（meu-supervisor）是首个用户态服务、挂在根 Job 之下，负责 spawn / 监控 / 重启 / 降级、结构化取消上行（`00 A9`）、与 `.msys` A/B 回滚（`06 §4.3` / `61 C61-4`）协同；服务生命周期以 manifest 表达依赖与重启策略；与 `46`/`47`/`53`/`65`/`36` 同源**。
- **核心设计**：
  - **监督者模型**：监督者不是特权内核对象，而是根 Job 之下第一个用户态进程（launchd 式）；内核只负责① 启动早期创建根 Job、② 在根 Job 下 spawn 监督者、③ 保证根 Job 终止 ⇒ 级联终止其下全部 Job/Process；Job 树即监督树（父 Job 的监督者对其子树拥有 spawn / 取消 / 重启权）。
  - **监督者身份门禁**：监督者持 `JOB_CREATE` + 受约束 `GRANT` + 对子树 `DBG_INSPECT`/`DBG_CRASHDUMP`；普通进程无这些权，无法伪装监督者——是 `07`「无隐式特权」在监督层的直接落点。
  - **服务生命周期 manifest**：类比 systemd unit / Fuchsia component manifest / Kubernetes Deployment；字段全部映射到既有 Job/Channel/capability 原语；依赖、启动序、重启策略、降级、审计、跨 realm 边界。
  - **降级与重启风暴熔断**：三源触发降级（资源超额持续超阈值 + 依赖服务不可用 + 崩溃率超阈值）；重启带指数退避 + 熔断，连续失败 N 次转 `fail-closed` 或 `degrade_to`，避免拖垮 Job 账本。
- **与既有地基的同构点**：
  - 与 `04 §4.4` Job 资源账本 / `04 §4.5` 监督 / `04 §4.6` 结构化取消同构；
  - 与 `00 A6`「重服务出核」同构——S1 自主采纳「监督者=首个用户态服务」，不进 TCB；
  - 与 `00 A9` exception channel → 监督者同构——S2 `fail-closed` 服务异常经结构化取消上行；
  - 与第八轮多 realm 边界同构——S3 跨 realm 监督默认 deny（A7 已闭环，本文承接）；
  - 与 `36` 用户态组件热升级 / `06 §4.3` `.msys` repoint / `61 C61-4` 恢复指针同源——监督者执行 `.msys` repoint 完成回滚。
- **零新增 bit 论证**：本节自主采纳 S1 / S2 两项均不新增 bit——S1 监督者不进 TCB、不作成内核对象；S2 重启策略纯用户态策略。

### §2.3 80 - 设备热插拔与动态设备树

- **一句话定位**：**设备发现以动态设备树/ACPI 枚举为内核薄层、驱动经 capability 委托用户态（L3 优先）；热插拔事件经 `59` interrupt/event 对象上行、触发用户态驱动按需 attach/detach；device VMO + IRQ cap 经 capability 受约束委托（与 `60`/`10` 同构）；五架构枚举差异（DT/ACPI/PCIe）封薄后端**。
- **核心设计**：
  - **动态枚举薄层**：冷启动（`09` Stage 2 从 DT/ACPI 抽出拓扑）与运行期（总线热事件 / ACPI notify / DT overlay）写入**同一棵可信设备拓扑树**结构，避免第二真相源（与 `76 §1.1`「buddy 独占物理页、VMO 仅逻辑视图」的同构纪律）；枚举薄层只产「描述」、不授权，节点入树后须经 devmgr 匹配 + capability 监视器受约束 mint 才能成为 cap（`10 C8`）。
  - **三类枚举源与统一归一化**：DT（ARM64/RISC-V/LoongArch DT 变体）/ ACPI（x86_64/LoongArch）/ PCIe（全架构，含 native hotplug）→ 节点 = `{bus, addr, compatible/VID:PID, 资源区间(MMIO/IRQ/DMA/IO port)}`，五架构同源，差异封薄后端；NUMA 拓扑复用 `09 §6-9` 多架构 bootinfo 归一化结构。
  - **驱动 L3 用户态化**：热插拔设备天然落在 L3（`60 §2.3`）；attach/detach 路径走 `59 §4` interrupt/event 上行 → 用户态 devmgr 匹配 → 受约束 mint cap → spawn 驱动进程；驱动 attach 失败回滚复用 `10 C8` 撤销锁 + 进程死亡自动回收。
  - **热插拔事件门禁**：拓扑变更事件携带设备插入/移除语义（含资源区间等敏感信息），H2 自主采纳「hotplug 事件接收权默认仅 devmgr」防信息泄漏与 confused deputy。
- **与既有地基的同构点**：
  - 与 `60 §2.3` 决策框架 / `10 §2.3` 设备拓扑树 / `09 §5.4` 设备能力签发同构——H1 自主采纳「枚举薄层=devmgr 职责·非新内核对象」；
  - 与 `59 §4` interrupt/event 对象同构——热插拔事件复用既有对象、不新增原语；
  - 与 `60 E1` 早期串口 `UART_*`=bit49 冻结同构——H5 已随 E1 闭环、运行期新增串口复用 bit49 边界；

- **零新增 bit 论证**：本节自主采纳 H1 / H2 两项均不新增 bit——H1 枚举薄层非新内核对象；H2 hotplug 事件默认仅 devmgr 持有、不新增「拓扑可见性」bit。

### §2.4 81 - 凭证与认证 broker 深化

- **一句话定位**：**身份 = capability 集合 + 由 issuer 私钥签注的符号名（`52`/`53` 已采纳）；认证 broker 是受约束 issuer、经 `AUTH_ISSUE`(bit55) 受限委托（默认 deny、Day 1 不触发）；凭证 mint/revoke 与 capability 派生/回收同源（`07 §4.5`）；认证事件可审计（`65`）；五架构同源**。
- **核心设计**：
  - **身份模型回顾**：真实身份 = 持有的全部 `handle + rights` 集合（`07 §1`/`§4.1`）；符号名（`alice`/`svc-netstack`/`role-builder`）是 issuer 私钥签注的 capability 附属声明（`52`/`53` 已采纳）——签注不放大任何 rights，只把「可读标识」绑定到既有 capability 锚。
  - **认证 broker 角色**：受 `meu-supervisor` 管理的用户态服务，验证主体提交的秘密/证明（口令/硬件令牌/密钥/SPIFFE/macaroon 式 bearer），成功后 mint 一份受限 capability 集合 + issuer 签注的符号名，派生新会话 Job；不复用 `GRANT` 语义（`AUTH_ISSUE`=bit55 是受约束 issuer right）。
  - **`AUTH_ISSUE`=bit55（已冻结·默认 deny·Day 1 不触发）**：类比 `DBG_POKE`/`debug-issuer` 受约束 issuer；P2 自主采纳「issuer 根密钥托管于内核 secure-key 区、经 `AUTH_ISSUE` 受约束委托」。
  - **凭证吊销传播**：revoke 经 derivation tree 全量回收（`07 §4.5` / `29 I5`），与 capability 回收同源；不新增内核原语。
- **与既有地基的同构点**：
  - 与 `53 §2.5` 认证 broker 同构——broker 受监督、mint 受约束 capability；
  - 与 `53 §7.5` C-G4 / `06 C3` default-deny reveal/grant 同构——P5 自主采纳「跨 realm 认证默认 deny·须显式 realm 间信任约定」；
  - 与 `07 §4.5` 受约束 mint / `20` I1–I7 capability 不变量同构——派生即 scope 收窄、吊销即 capability 回收；
  - 与 `32 §3.3` 度量基双锚 / `61 C61-4` 引导级恢复指针同源绑点——issuer 根密钥生成在 `09 Stage 4` 信任锚初始化阶段。
- **零新增 bit 论证**：本节自主采纳 P2 / P5 两项均不新增 bit——P2 复用 `AUTH_ISSUE`=bit55（已冻结）受约束委托；P5 跨 realm 信任表存于用户态、不进内核。
