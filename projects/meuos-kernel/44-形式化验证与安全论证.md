## 2. ① 解构型推演：「被证明」与「被测试」的本质区别

### 2.1 测试的先天边界

Dijkstra 的论断仍是内核工程的第一性原理：**测试只能证明 bug 的存在，不能证明 bug 的不存在**。对 MeuOS 而言这尤其尖锐——capability 模型（07）的承诺是「无 root 逃生舱、越权必 fail-closed」，这是一个**否定式**全局性质：

- 测试能穷举「合法请求被正确放行」（正断言），但无法穷举「所有越权路径都被拒绝」（否断言）——越权路径空间随接口数组合爆炸。
- 一个未被测到的越权路径，在测试视角下「通过」；在论证视角下它是**论证的缺口**而非「安全」的证据。

因此安全关键的子系统不能只靠测试，必须把「它**不能**坏」落成可被机器检查的结构性断言。这正是本文立场：**从 `test that it works` 转向 `argue that it cannot break`**。

### 2.2 「被证明」的诚实形态

本文定义的「被证明」不是「证明了二进制」（那需要验证过的编译器，见 §5 与 `20` §6），而是**在明确模型上、对明确不变量给出机器可检查的证据**。它有三档强度：

1. **证明（proof）**：在数学模型上机械验证不变量（Coq/Lean/TLA+ 精化）——最高强度，仅给极小核心。
2. **论证（argument）**：把顶层安全声明（top-level claim）分解成可独立证据化的子声明，每层有证据（证明 / 类型强制 / 测试 / 审计）——中等强度，覆盖全 TCB 的「信心结构」。
3. **构造即证明（proof by construction）**：通过设计使某不变量在结构上不可能被破坏（如 Rust 类型、无全局特权）——零运行期成本的「被证明」。

### 2.3 最小 TCB 论证：论证成本 ∝ TCB 规模

安全论证的总成本，近似正比于「必须被信任的代码量 × 其接口复杂度」。第四轮采纳的「最小 TCB」不是一句口号，而是**论证可行性的前提**：

- TCB 越大 → 要写进论证的组件越多 → 证明/类型/审计面越广 → 论证越贵且越易有缺口。
- 因此「尽快交权用户态」（00 A6）不只是运行时缩爆炸半径，更是**把论证成本外推到 TCB 之外**——用户态服务靠 `22` 的 fuzz/测试即可，不进论证核心。
- 结论：MeuOS 的论证可行性，直接来自 `07` §4.4「最小 TCB + 关键组件 Rust」与 `00` A3「capability 监视器是唯一裁决点」。论证面 = 唯一裁决点 + 其直接支撑（句柄表、revoke、调度小核、内存隔离），这与 `20` Layer A/B 的聚焦完全一致。

## 3. ② 多系统参照对比（含 Frama-C / CompCert / Linux sparse·lockdep / Windows 驱动验证 / Fuchsia）

> 成本列为数量级/公开报道，仅供 ROI 比较，非精确报价。

| 系统 / 工具 | 验证/论证手法 | 证明到什么 | 投入成本（量级） | 对 MeuOS 的可借鉴点 | 与 MeuOS 现实的冲突 |
|---|---|---|---|---|---|
| **seL4（参照基线）** | Isabelle/HOL 端到端精化 + 信息流安全证明（access control + noninterference） | 8700 行 C 的功能正确性 + 隔离 + 无权限提升 | **~20 人年**（C 源证明，编译器在 TCB） | capability 模型 = 唯一授权；TCB 极小；**安全论证的范本**：把「隔离」与「行为正确」同时形式化 | 全量证明成本对独立项目不可承受；依赖验证编译器链，MeuOS 无 |
| **Frama-C（C 程序证明）** | ACSL 注解 +  weakest precondition（WP）/ 值分析（Eva）；对 C 函数证内存安全与功能规约 | 单函数/模块级：无溢出、无越界、规约满足 | 中（每函数需手写规约 + 证明，工程量大但可渐进） | **i386 纯 C TCB 的补偿手段**——seL4 用 C 写必须证内存安全，MeuOS 的 i386 C 组件可用 Frama-C 把「C 内存安全」补回来（`20` §6.3） | 需 C 在 TCB 内、规约手写；与 mcc 前端对接成本待评估 |
| **CompCert（验证编译器）** | 经 Coq 证明的 C→asm 翻译**保语义** | 编译产物 = 源语义的精化 | 极高（整个编译器被证明，多年工程） | **信任链闭环的远期选项**：若内核证明要「下推到二进制」，需 CompCert 式路径（`20` §6.2 translation validation 的同源思想） | MeuOS 用 mcc/QBE + rustc/LLVM，均无验证；远期重估，M6 前不投 |
| **Linux sparse + lockdep** | sparse：内核专用**类型/上下文静态分析**（`__user`/`__kernel` 地址空间、锁上下文）；lockdep：运行时**锁序图**检测，等价于「锁获取顺序无环」的构造性证明 | 编译期抓地址空间混用；运行期抓死锁类锁序违例 | 低（作为编译/启动期检查，零额外验证人力，长期维护） | **零成本论证增强**：MeuOS 可在 Rust 类型层复刻 sparse 思想（地址空间用类型标记），在启动期做 lockdep 式锁序断言 | 是「辅助论证」非「证明」；lockdep 有运行期开销，须受 `19` 预算约束 |
| **Windows Driver Verifier / DVL** | 驱动**强制插桩验证**：池损坏、死锁、IRQL、DMA 校验；WHCK 兼容性矩阵 + 签名关卡 | 驱动在受控注入故障下不崩、不越界 | 中（框架成熟、驱动须过关卡） | 取「非 TCB 组件须过强制验证关卡」思想，呼应 `10` 驱动模型——驱动虽排除出 TCB，但仍须强制验证闸门 | MeuOS 驱动多在用户态，关卡形态不同（capability 受控 + fuzz 关卡，见 `22` §4） |
| **Fuchsia / Zircon（可验证性设计取向）** | 不做形式化证明；靠 **FIDL 契约（可机检一致性）+ handle/rights 模型 + Inspect 强类型状态树 + 无全局特权**使系统「 inherently verifiable」 | 无证明；接口契约 + 结构化可观测性使测试/论证便宜 | 低（设计取向，非证明工程） | **最贴合 MeuOS 的「设计须可验证」取向**：`12` 的 inspect/事件流 = Fuchsia Inspect 同构；handle/rights（07）= Zircon 同构；「无全局 priv」=`07` §4.1 | 不提供证明，与本文「核心要论证」立场互补而非替代 |

**对比收口**：六类参照各守一层——
- seL4 守「核心功能正确性 + 信息流」的**完全证明**范本；
- Frama-C 守「C 组件内存安全/规约」的**模块级证明**（补 i386 缺口）；
- CompCert 守「编译器保语义」的**信任链闭环**（远期）；
- Linux sparse/lockdep 守「零/低成本的构造性静态检查」；
- Windows 驱动验证守「非 TCB 组件的强制验证闸门」；
- Fuchsia 守「设计取向层面的可验证性」（契约 + 结构化观测 + 无全局特权）。

MeuOS 应**组合**这六层（非缝合怪）：seL4 的论证结构 + Frama-C 补 C TCB + sparse/lockdep 式零成本检查 + Fuchsia 的设计取向 + Windows 的强制闸门 + CompCert 作远期信任链目标。

## 4. ③ 可验证面：哪些组件值得 / 可形式化验证（与最小 TCB 一致）

> 原则（来自 §2.3）：只验证**在 TCB 内**且是**单点故障**的组件；其余靠 `22` 测试/fuzz。

### 4.1 按 TCB 归属切分可验证面

| 组件 | TCB 内？ | 是否单点故障 | 形式化价值 | 处置（对齐 `20` Layer） |
|---|---|---|---|---|
| **capability 监视器 / rights 裁决**（07 §4.1） | 是（Rust） | **是，全局权限唯一裁决点**（00 A3） | 最高 | Layer A 完全证明：`check_rights` + revoke derivation tree（`20` §4.1） |
| **句柄表不可伪造 / 派生链**（07 §4.5、§5-1） | 是（Rust） | 是 | 最高 | Layer A/B：I1/I2/I7（`20` §5） |
| **调度小核心**（04，确定性 RT 域） | 是（Rust） | 中（实时性/公平性，非全局特权） | 高 | Layer A/B：WCET/优先级不变量（`19` §3.4(A)、`20` R1 呼应） |
| **内存隔离**（VMO/VMAR、ASID 唯一性、页帧归属） | 是（Rust + 少量 C/asm） | 中高（隔离失效 = 跨进程越权） | 高 | Layer B 模型检验 + 类型强制（`03` §5-7 不变量） |
| **IPC 协议 / cap transfer**（05） | 是（Rust） | 中（rendezvous 死锁、cap 丢失） | 高 | Layer B TLA+（`20` §4.2） |
| **supervisor 重启状态机**（04 §5-4、09 §6-10） | 是（Rust） | 中（自杀环死锁） | 高 | Layer B TLA+（优先级最高，`20` §7.1） |
| **FS 用户态服务 / 驱动 / mkit 兼容层** | **否**（排除出 TCB） | 否（爆炸半径由 capability 边界 + supervisor 重启兜底） | 低 | **不形式化**，仅 `22` 测试/fuzz/强制闸门 |

### 4.2 「与最小 TCB 一致」的两条硬规则

1. **可验证面 ⊆ TCB**。任何被形式化论证的组件，必须先被认定在 TCB 内；若某组件还想「既排除出 TCB 又想被证明」，是自相矛盾——排除出 TCB 的代价就是「只靠测试」，论证成本已外推出去，不应再花证明预算。
2. **可验证面止于单点故障**。TCB 内也要分优先级：capability 监视器是全局权限的 Single Point of Failure，值得最贵的 Layer A 证明；调度/内存/ IPC 是「局部失效不致死」的核心，值得 Layer B 模型检验；两者都不值得 Layer A 全量证明（状态空间过大、演进过快）。

### 4.3 capability 内核（07）的可证明隔离属性

capability 模型的隔离是**结构性**的——正因为「无身份、只有句柄」，隔离不依赖「策略是否正确配置」，而依赖「句柄是否可达」。这使下列隔离性质可证（对应 `20` I1–I7，此处以「隔离」视角重述）：

- **空间隔离（spatial isolation）**：无句柄 ⇒ 无访问。进程对任意内核对象的可达性 = 其句柄表中是否存在受权句柄。这把「跨进程越权」归约为「句柄是否可达」，是可机检的图论性质（I1/I7）。
- **权限单调不增（I3）**：沿派生链 rights 只减不增 ⇒ 任何 mint/grant 都不会产生比源更大的权限 ⇒ 「无隐式提权」（I6）是 I3 的推论。
- **撤销即断链（I2）**：revoke 节点 ⇒ 传递闭包内全部派生句柄失效 ⇒ 隔离可被**远程收回**，无悬垂授权（直接封堵 confused deputy，I5）。
- **无凭空产生（I1）**：任一可用句柄必沿派生链追溯到根 Job 初始令牌 ⇒ 不存在「私下构造的特权句柄」。

这四点正是 seL4 用 20 人年中最值钱的那一块（access control + info-flow），MeuOS 以「更小 TCB + Rust 类型」复现其论证精华（`20` §4.1 ROI 论据）。区别在于：seL4 还需额外证明 C 内存安全，MeuOS 由 Rust 吃掉了这一块（见 §5）。

## 5. ④ 与 Rust 关键组件（第四轮已采纳）协同：类型系统即轻量证明

第四轮已采纳「关键组件用 Rust 入 TCB」（00 A3、`07` §4.4）。这不是孤立的「用 Rust 写内核」，而是**论证成本的结构性转移**——Rust 类型系统是「免费」的证明层（`20` Layer C，本文扩展其论证学含义）。

### 5.1 哪些不变量被「构造即证明」

| 不变量（`20` 命题） | Rust 机制 | 论证强度 |
|---|---|---|
| I7 句柄不可伪造 | `Handle` 非 `Copy`、私有构造、进程私有表 | 编译期强制：表外句柄值无法构造 |
| I3 rights 只减不增（部分） | `Rights` 以类型层集合 / `PhantomData` 标记，`mint`/`duplicate` 返回收窄类型 | 编译期强制收窄，扩张在类型上不可表达 |
| Job 账本不可超额（I4，部分） | 账本生命周期由所有权/RAII 包裹，分配即借 | 编译期防泄漏/双释放 |
| 无 UAF / 越界 / 悬垂（内存安全） | borrow checker + 无 GC | 编译期消除整类缺陷（seL4 须人证的块） |

### 5.2 协同分工：Rust 吃内存安全，形式化吃权限语义

这是本文对 `20` Layer C 的关键补强——**论证职责的清晰切分**：

- **Rust 类型系统**负责「内存安全类」不变量（UAF/溢出/悬垂）。这部分在 seL4 要花大量人证，MeuOS 由编译期零成本获得。
- **形式化方法（Layer A/B）**只负责「权限语义类」不变量（I1–I3/I5/I6、revoke 传播、IPC 时序）。这部分 Rust 类型无法表达（涉及跨进程可达性、并发时序），必须上证明器/模型检验。

二者之和 = seL4 证明的主体价值，但 MeuOS 用极小代价复现。这就是第四轮「Rust 关键组件」与「形式化验证」的**互锁**：Rust 把论证面压到只剩权限语义，形式化只需攻这最后一小块。

### 5.3 i386 纯 C 的论证缺口与补偿

i386 全程纯 C（`02` C2、`00` C6），其 TCB 拿不到 §5.1 的类型层保证。这恰是 **Frama-C（§3）的补偿点**：i386 的 C TCB 组件须补「内存安全 + 规约」证明，以弥补缺失的 Rust 类型保护。这是 i386 相对 64 位目标的论证成本增量，应在 `02` C2「i386 是否永久纯 C」裁决中计入（`20` §6.3 D3）。

## 6. ⑤ capability 内核（07）的论证骨架（assurance case）

> 把 §4.3 的隔离性质上升为一个**可审计的论证结构**（assurance case），而非散落的命题。

### 6.1 顶层声明 → 子声明 → 证据的分解

```
顶层声明 CLAIM-0：MeuOS 内核满足「最小权限 + 隔离 + 无越权提权」
        │
        ├─ CLAIM-1 无特权逃生舱（无 root / 无全局关沙箱）
        │     └─ 证据：编译期固定安全参数清单（07 C16 ②，tunable 不含安全开关）
        │            + `KERNEL_PRIV` 永不默认外流（07 D-T1，`20` §4.1 不证此、仅类型/审计约束）
        │
        ├─ CLAIM-2 句柄不可伪造 / 来源可追溯（I1 + I7）
        │     └─ 证据：Rust 类型强制（§5.1）+ Layer A 参考模型证明（20 §4.1）
        │
        ├─ CLAIM-3 权限只减不增 / 无隐式提权（I3 + I6）
        │     └─ 证据：Rust 类型收窄（部分）+ Layer A 证明（20 §4.1）
        │
        ├─ CLAIM-4 撤销彻底（revoke 断全部派生链）（I2）
        │     └─ 证据：Layer A 证明 derivation tree 完整性（20 §4.1）
        │
        ├─ CLAIM-5 服务端 mint 不越权（防 confused deputy）（I5）
        │     └─ 证据：受约束 mint = rights_fs ∩ rights_requested（07 C2、00 C2）
        │
        └─ CLAIM-6 协议层无死锁 / 无丢失（IPC / revoke 时序 / supervisor 重启）
              └─ 证据：Layer B TLA+ 模型检验（20 §4.2）
```

### 6.2 论证的「可审计性」来自哪里

- **结构化可观测性（`12`）是论证的反馈通道**：`07` §5-6 的审计 schema（pledge 越界 / 句柄授予 / unveil 锁定事件）使 CLAIM-2/3/5 的运行时行为可被消费为断言信号——论证不止于「设计期证明」，还能被「运行期观测」持续校验。
- **编译期固定清单（C16 ②）是论证的硬锚**：它把「安全开关不可被运行期关闭」从「策略承诺」变成「build contract 不可改写」，使 CLAIM-1 在设计上即成立，不依赖运行期纪律。

### 6.3 与 seL4 论证的同构与差异

同构：都是「顶层安全声明 → 子声明 → 证据」的精化分解，都把 access control + 隔离作为核心被证性质。
差异：seL4 的证据几乎全是「机器证明」；MeuOS 的证据是「证明（Layer A 极小核心）+ 类型强制（Rust）+ 审计/测试（运行期观测）」的混合——因为 MeuOS 用 Rust 把内存安全证据前置到编译期，用 Fuchsia 式设计取向把接口契约前置到 FIDL/inspect，二者共同削减了「需机器证明」的比例。

## 7. ⑥ 与测试方法论（22-测试与验证策略）的分工

> 任务书中「测试方法论(41)」即规划轮次编号差异下的 `22-测试与验证策略`；本文以 `22` 为准做分工。

### 7.1 二者回答不同问题，不重叠

| 问题 | 形式化验证（本文 + `20`） | 测试（22） |
|---|---|---|
| 满足不变量吗？（模型上） | ✅ 是主场 | ❌ 不能证无 |
| 实践中有越权违例吗？（fuzz/集成） | ❌ 不覆盖模型外 | ✅ 是主场 |
| 抽象模型本身对吗？（设计错误） | ❌ 证明不了「错抽象」 | ✅ 实测暴露模型失配 |
| 运行期观测是否一致？（结构化断言） | 提供 oracle（不变量即断言） | ✅ 执行断言（消费 inspect/事件流） |

### 7.2 互补的三种具体机制

1. **形式化规约作测试 oracle**：`20` §6.2 的差分测试——参考模型（TLA+/证明器提取的可执行规约）vs 实际实现的「可观测迹等价」——正是把本文不变量变成 `22` L0–L2 的断言基准。证明定义「正确」，测试检查「实现 ≈ 正确」。
2. **否定式测试是论证的可执行影子**：`22` §1.2 的「越权必失败、fail-closed」否定式断言，正是 CLAIM-2/3/5 在运行期的可执行化身。论证说「不能越权」，测试穷举「试越权 → 必拒」。
3. **测试抓「错抽象」**：证明只在模型内有效；若 `07` 的 rights 位图本身漏了一项关键权限（模型失配），证明无能为力——此时 `22` 的 fuzz/集成测试（尤其 mkit 翻译面、cap revoke、FS extent）会暴露「设计层」缺口，反哺论证修正模型。

**分工纪律**：形式化负责「在模型内证明不变量」，测试负责「在模型外找违例与错抽象」。二者在 CI 门禁处交汇（`20` §7.2 差分测试常态化 + `22` G0–G4 门禁），互不替代。

## 8. ⑦ 代价与适用边界（务实 ROI）

### 8.1 何时形式化**不值得**

| 情形 | 理由 | 替代 |
|---|---|---|
| 设计仍在演进（M3 前、`20` §7.1） | 过早证明 = 证明随设计变动而作废 | 先 TLA+ 建模 + Rust 类型 + 测试 |
| 状态空间过大（FS 后端、驱动、调度全量） | 证明成本失控 | `22` fuzz/测试 + 强制闸门 |
| 已排除出 TCB 的组件 | 论证成本外推，不应再投证明预算 | `22` 测试/fuzz |
| 工具链未验证（mcc/QBE/rustc/LLVM） | 证明到源码 ≠ 证明到二进制（`20` §6.1） | 差分测试兜底 + 诚实声明 |

### 8.2 各技术代价量级（对齐 §3）

- **Layer A 完全证明（capability 核心）**：~1 核心算法级证明，ROI 极高（系统权限正确性的主体保证），但**仅限 §4.1 两处**。
- **Layer B TLA+ 模型检验**：每协议数周–数月，零运行期开销，性价比最高（`20` §4.2）。
- **Rust 类型强制（Layer C）**：近乎零额外成本（工程在 abstractions），持续收益。
- **Frama-C（i386 C TCB）**：每函数规约+证明，中成本，仅补偿 i386 缺口。
- **CompCert 式验证编译器**：极高，M6 前不投，仅远期目标。
- **sparse/lockdep 式静态检查**：低，作为编译/启动期检查长期维护。

### 8.3 适用边界的诚实声明

- **证明的是参考模型/算法，不是二进制**：在 mcc/QBE、rustc/LLVM 均未验证前，声称「证明了内核二进制」是伪命题（`20` §6.1）。我们证明算法正确 + 实现是其精化，编译器鸿沟由差分测试兜底。
- **证明不了「错抽象」**：模型本身的完备性需测试反哺（§7.2-3）。
- **拒绝 seL4 全量证明**：成本不可承受、工具链不支持、Rust 已免费吃最大头、聚焦唯一裁决点即够（`20` §7.4）。本文沿袭此明确保留。

## 9. Day1 起点：不要求全验证，但设计须可验证

第四轮已采纳「最小 TCB + Rust 关键组件 + capability 唯一模型」——这**本身就是 Day1 的「可验证性设计」**。Day1 不要求任何机器证明，但设计必须满足「可被论证」的硬约束：

### 9.1 Day1 必做的「零/低成本验证」

1. **架构锁定可验证核心**：capability 监视器作为唯一裁决点（00 A3），其接口小而边界清——这是论证可行性的地基，Day1 即定型。
2. **Rust 类型不变量 + unsafe 白名单门禁**（`02` §4.4）：`forbid(unsafe_op_in_unsafe_fn)`、`deny(clippy::all)`、`unsafe` 块双人评审清单、TCB 规模上限（`02` §5-6）。这是「免费」的 Layer C 验证，立即生效。
3. **TLA+ 参考模型先于代码**（高性价比）：写 IPC rendezvous / revoke 时序 / supervisor 重启状态机**之前**，先用 PlusCal 写模型穷尽状态空间抓设计 bug（`20` §7.1，优先级：重启状态机 > IPC > revoke）。
4. **I1–I7 编码为编译期/单测断言**：把 §4.3 的隔离性质落成 Rust 单测（句柄不可伪造、rights 收窄、revoke 断链、Job 账本超额拒），作为 `22` L0 的白盒断言。
5. **非 TCB 组件 fuzz-only**：mkit 翻译面、驱动、FS 后端按 `22` §4 走 fuzz + 强制验证闸门，不进论证核心。

### 9.2 「设计须可验证」的检查清单（Day1 架构评审项）

- [ ] 是否存在全局特权逃生舱？（应是「否」——`07` §4.1 无 root、`C16` ② 编译期固定）
- [ ] 权限裁决点是否单一且接口小？（应是「是」——capability 监视器）
- [ ] 越权断言是否为否定式 fail-closed？（应是「是」——pledge/unveil 越界即终止）
- [ ] TCB 组件是否 Rust 且 unsafe 受门禁？（应是「是」——`02` §4.4）
- [ ] 用户态服务是否排除出 TCB 且由 supervisor 兜底？（应是「是」——00 A6/A9）
- [ ] 结构化可观测性是否就位以消费论证信号？（应是「是」——`12` inspect/事件流 + `07` §5-6 审计 schema）

满足以上六条，Day1 即「设计可验证」——即便尚未写一行证明。

## 10. 演进路线：Day1 → 长期（务实、现代化）

```
Day1 (M0–M3)               Post-M3 (设计稳定)           长期 (M5/M6+)
─────────────────         ───────────────────         ──────────────────────
Rust 类型 + unsafe 门禁  →  Layer A 窄证明启动        →  CHERI 硬件兜底 I7
TLA+ 模型先于代码      →  (capability rights 检查    →  (RISC-V / Arm Morello,
I1–I7 单测断言         →   + revoke tree 参考模型,    →   指针级不可伪造)
非 TCB fuzz-only       →   Coq/Lean 证明, 精化桥接)  →
                       →  Layer B 扩展 (Service      →  重估验证编译器路径
                       →   Registry realm / reply)   →  (CompCert 式 mcc? 远期)
                       →  差分测试常态化进 CI        →  i386 C TCB 补 Frama-C
                                                →  (若 C2 保留纯 C)
```

- **Day1（M0–M3）**：验证预算 = 0 额外成本（Rust 类型）+ 低成本的 TLA+ 建模 + 单测断言。不做端到端证明、不做 translation validation。
- **Post-M3（L2 工具链自举完成、设计趋于稳定）**：对**已稳定**的 capability rights 检查 + revoke tree 启动 Layer A 窄证明（参考模型在 host 侧 Coq/Lean，Rust 实现作精化，差分测试桥接）；Layer B 扩到更多协议；差分测试进 CI 门禁。
- **长期（M5/M6+）**：CHERI 硬件能力在支持架构叠加为 I7 的硬件兜底；若 Rust 验证后端成熟（gccrs / `rustc_codegen_gcc`）或 mcc 出现 CompCert 式验证路径，**重估** Layer A 是否可下推到更接近二进制；i386 纯 C TCB 补 Frama-C/静态分析。

**明确非目标（NON-goals）**：seL4 式全量端到端证明、M6 前的 translation validation、把排除出 TCB 的组件纳入证明。
