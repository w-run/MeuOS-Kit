## 0. 一句话结论（先给答案）

在 MeuOS 的 capability 唯一模型下，**隔离的第一性不是「容器」也不是「VM」，而是 capability 边界本身**——`Job` 资源账本（04）+ `rights` 权限位图（07）+ 每进程统一命名空间（06，C3 已采纳每进程独立）三件套已经天然构成了「隔离单元」；传统容器只是这一单元受约束的实例化，传统 VM 只是 capability 经 **device VMO（03）** 与 **CPU 时间（04）** 授予后、用来跑**不可信 / 异构负载**（旧 OS、隔离测试、第三方内核）的一种**受限 guest**。兼容层（08）已定「薄翻译层非 VM」，故 VM **不**用于跑 Linux 二进制。原型期 VM 采用 **Fuchsia 式用户态 VMM + 极薄内核 guest 设施**（vCPU 对象 + 基于 VMO 的 guest 物理地址空间），而非 Linux KVM 式单体方案——是否提供「原生 KVM 兼容接口」列为架构级待决（见 §7）。

## 1. 「应该是什么样」——隔离在 capability 世界的推演

### 1.1 先问：隔离的「第一性」是什么

在 Linux 里，隔离是**事后拼装**出来的：root 万能、uid/gid、DAC、MAC、capabilities、seccomp、namespace、cgroups 七套机制正交叠加（见 07 §3.1），容器 = cgroups（资源）+ namespace（视图）+ seccomp（syscall 过滤）三件事后挂接。隔离的「第一性」模糊不清——它的边界是「我创建了哪些 namespace、挂进了哪个 cgroup」，而权限仍隐式来自身份。

在 MeuOS 里，权限**只**来自 capability 句柄（07 §4.1：句柄即 capability，无 root、无隐式权限）。由此推演：**隔离的第一性 = capability 边界**。一个主体能看到的资源、能用的对象、能占的 CPU/内存，完全由它持有的 capability 集合 + 它所属 Job 的账本决定。容器和 VM 只是 capability 边界的两种**实例化形态**：

- **容器形态**：同一内核地址空间谱系内，用「收窄的 capability 集 + 受限命名空间视图 + 资源账本上限」划出一个隔离域——域与域之间共享内核，但彼此不可越权。
- **VM 形态**：把一整块「guest 物理地址空间（GPA）+ vCPU 时间」作为 capability 授予一个 user-mode VMM，让**另一个内核**在内部跑；guest 与 host 内核之间只有 capability 一条信任边。

### 1.2 三个已经在地基里的事实（不必新建，只需组合）

| 地基（已有子文档结论） | 在隔离中的角色 | 来源 |
|---|---|---|
| `Job`（资源账本 + 生命周期单元） | 隔离的**资源与生命周期边界**——配额、句柄数、进程数 Day 1 内建，父 Job 终止传播杀死子树（04 §4.1/§4.4/§4.5） | 04 |
| `rights` 位图 + pledge/unveil | 隔离的**权限边界**——进程创建即最小权限，pledge 只能收缩、越界即终止、unveil 决定可见路径（07 §4.2/§4.3） | 07 |
| 每进程统一命名空间（默认全不可见、spawn 组装） | 隔离的**视图边界**——进程只看到显式 reveal 的路径能力，无全局 `/proc`（C3 已采纳每进程独立，06 §4） | 06 / 00-C3 |

> 关键判语：**容器 = Job 账本 ∩ rights ∩ namespace 视图**。这三者已在 07 §4.3「一个范式、三个表现维度」中互锁——本文第 4 节只是把这套互锁**提升为「容器级组合规范」**，而非引入新机制。

### 1.3 VM 在 MeuOS「应该」扮演什么角色

VM **不**用来跑 Linux 二进制——那是 08 兼容层的职责，且 08 已明确否决 WSL2 式「真 Linux 内核跑在 VM」（08 §1.1/§5 多系统参照表：WSL2 行标「无——与我们内部自主相悖」）。VM 在 MeuOS 的「应该」定位是**跑 capability 模型容纳不了的负载**：

- 不可信 / 来源不明的第三方内核或整 OS（安全研究、隔离测试、多租户沙箱）；
- 异构 ISA guest（如用 VM 跑一个不同于 host 的架构负载——虽然 MeuOS 五架构原生支持，但 guest 可承载更老的 / 不兼容的内部 ABI 的 OS）；
- 需要强故障封闭（guest 崩溃绝不波及 host 内核）的场景。

VM 的一切输入（CPU 时间、内存、设备）都**必须**经 capability 授予（接 03 device VMO、04 Job 账本），使 VM 与容器一样落在同一条 capability 信任边上——这是「非缝合怪、实现自主」的落点。

## 2. 多系统参照对比表

> 横轴：各系统「隔离第一性 / 容器实现 / VM 形态 / 边界信任模型」；纵轴：系统。结论列给 MeuOS 取舍。

| 系统 | 隔离第一性 | 容器 / 沙箱实现 | VM 形态 | 隔离的信任边界 | **MeuOS 取舍** |
|------|-----------|----------------|---------|---------------|----------------|
| **Linux** | 身份（uid/gid）+ 事后七机制叠加 | cgroups + namespace + seccomp（事后挂接，容器运行时组装） | KVM（单体内核子系统，原生硬件虚拟化） | 模糊（root 万能 + CAP_SYS_ADMIN 新 root） | **不借**身份模型与七机制叠加；**借**「KVM 的硬件虚拟化能力」但改其形态（见 §5） |
| **Windows** | 父分区 / 隔离用户态 + Job 对象 | Job 对象（资源/生命周期隔离）+ 容器（基于 Job + namespace 视图） | Hyper-V（父分区管理 guest 分区，VMBus 设备半虚拟化） | 分区边界 + 虚拟信任级别（VTL） | **借**「Job 对象作隔离单元」思想（与 04 同源）；**借**「父分区管 guest」的 VMM 拓扑 |
| **macOS** | Sandbox/seatbelt + App Sandbox（声明式） | sandboxd 规则 + entitlement（capability 式权限清单） | Hypervisor.framework（用户态 VMM 驱动，无单体 KVM） | 用户态 VMM 持有 VM 对象，设备经 entitlement | **最贴** VM 形态：Hypervisor.framework 即「用户态 VMM + 薄内核 guest 设施」，直接同构 §5 推荐 |
| **Android** | SELinux + Profile 隔离 + ART 沙箱 | 每 app 独立 UID + SELinux + 命名空间 | AVF（Android Virtualization Framework，基于 pKVM 的受保护 VM） | pKVM 受保护 VM，host 不可窥视 guest | **借**「受保护 VM（pKVM）」思想——guest 与 host 强隔离，对应 §5 的 restricted VM |
| **塞班** | 能力模型沙箱（平台能力即权限） | 进程级 capability 沙箱（粗粒度） | 无 | 能力边界 | **借**「能力即隔离边界」第一性（与 07 同源）；不借其粗粒度 |
| **ChromeOS** | 容器（LXC）→ 经 VM（crosvm）跑 Linux 兼容 | 用户态 container 运行时 | crosvm（Rust 用户态 VMM，基于 KVM） | 用户态 VMM + 设备经 VMO 直通 | **借** crosvm 式「Rust 用户态 VMM + 设备 VMO 直通」工程形态 |
| **Fuchsia** | capability（handle+rights）天然隔离 | 无传统容器；Component 经 namespace+rights 隔离；「受限 VM」跑不可信 guest | **受限 VM（restricted VM）**：guest 只拿 VMO，内核只给 vCPU + GPA 基于 VMO | 用户态 VMM 持 guest 对象；guest 触硬件须经 VMM 转发 | **最贴** 隔离第一性 + VM 形态：本文 §3/§5 直接同构 |
| **seL4** | capability（CSpace）形式化验证隔离 | 无容器；进程间仅靠显式 cap 委托 | guest 经 passthrough（iommu/设备 cap 交给 guest VM）；VM 控制块受 cap 约束 | 单一 cap 信任边，可形式化 | **借**「VM 也只是一等 cap 对象、可 revoke」思想（接 03 revoke 即回收） |
| **MeuOS（本文）** | capability 边界（Job+rights+namespace） | 容器 = Job ∩ rights ∩ namespace（§4） | 用户态 VMM + 薄内核 guest 设施；设备经 device VMO（§5） | 唯一 cap 信任边，VM 与容器同构 | 隔离第一性 = cap；VM 仅跑不可信/异构负载；兼容层非 VM（接 08） |

> 结论骨架：
> - **隔离第一性**借 seL4/塞班/Fuchsia/07 的「capability 即边界」——这是地基，已在 04/06/07 落地。
> - **容器**借 Windows Job 对象 + Fuchsia Component namespace + Android/iOS entitlement 的「声明式受限域」思想，但**组合**为 MeuOS 自有的 Job+capability+namespace 三元组。
> - **VM** 借 macOS Hypervisor.framework / Fuchsia restricted VM / Android pKVM / ChromeOS crosvm 的「用户态 VMM + 薄内核 guest 设施 + 设备 VMO 直通」形态，**不借** Linux KVM 的单体内核方案（除非 §7 架构裁决改为提供 KVM 兼容）。
> - **不借** Linux 的七机制叠加与「VM 跑兼容层（WSL2）」。
> 所有实现自主研究。

## 3. MeuOS 隔离分层模型

隔离按「信任距离」从近到远分三层，全部落在同一条 capability 信任边上：

```
  信任边（唯一）= capability 边界（handle + rights + Job 账本 + namespace 视图）
  ┌─────────────────────────────────────────────────────────────────┐
  │  L0  同内核内进程级隔离（默认，最轻）                              │
  │      = 单一进程/线程，靠 pledge/unveil + 句柄权限自然隔离          │
  │      来源：07 默认沙箱；不额外建域                                │
  ├─────────────────────────────────────────────────────────────────┤
  │  L1  容器级隔离（同内核、跨 Job 的受限域）★本文重点               │
  │      = 受限 Job + 收窄 rights + 独立 namespace 视图 + 可选子树     │
  │        CoW rootfs VMO（06 §4.3）                                   │
  │      共享内核，但域间不可越权、资源受限、视图受限、生命周期由 Job  │
  │      树传播控制                                                    │
  ├─────────────────────────────────────────────────────────────────┤
  │  L2  VM 级隔离（跨内核、强故障封闭）                               │
  │      = 用户态 VMM 持有 guest 对象（vCPU + GPA 基于 VMO）           │
  │      设备经 device VMO（03 §4.4）直通 / 经 VMM 半虚拟化转发        │
  │      CPU 时间来自 VMM 所属 Job 账本（04 §4.4）                     │
  │      guest 崩溃绝不波及 host 内核                                  │
  └─────────────────────────────────────────────────────────────────┘
```

- **L0→L1 是「同一内核内权限收窄」**，无需新机制，只是把 04/06/07 已有能力组合封装为「容器规范」（§4）。
- **L1→L2 是「跨越内核边界」**，需要内核提供极薄的 guest 设施（§5），但 guest 的输入仍走 capability 同一条边——故 L2 不是「另一种隔离哲学」，而是 L1 在「需要跑另一个内核」时的外推。
- **兼容层（08）不属于上述任何一层作为隔离手段**：它是在 L0 上跑 Linux 二进制的一张薄翻译面，其二进制所受隔离 = 它所在 Job 的 L0/L1 约束（08 §3.1/§3.2：root 是合成视图、open 受 unveil 约束）。**绝对不**把 Linux 二进制塞进 L2 VM（否决 WSL2，08 §5）。

## 4. capability 化容器规范（L1）

> 本节约把 07 §4.3「一个范式、三个表现维度」上升为可操作的容器组合规范。不引入新内核对象，只定义**组合契约**与**manifest 形态**。

### 4.1 容器的组成契约

一个容器 = 一个 **容器根 Job（container-root Job）**，其创建与组装必须满足：

| 维度 | 契约内容 | 来源 / 对齐 |
|------|----------|-------------|
| **资源账本** | 容器根 Job 带 CPU 权重/带宽上限、内存上限、句柄数上限、IO 带宽、进程/线程数上限（04 §4.4 全量表）。容器内所有进程共享此账本，超限在容器内归因（04 §5.5 待决）。 | 04 |
| **权限边界** | 容器根 Job 的 capability set 在 spawn 时即收窄（07 §4.3/§4.5：`GRANT` 受限、默认无特权 right）。容器内进程继承并只能进一步收缩。 | 07 |
| **视图边界** | 容器的统一命名空间在 spawn 时由 manifest 组装（C3 每进程独立已采纳），仅 reveal 容器所需的路径能力（unveil 锁定，07 §4.2）。无全局 `/proc`。 | 06 / 00-C3 |
| **沙箱基线** | 容器内进程默认应用 pledge/unveil 最小沙箱（07 §4.2，已采纳为默认）。放宽须显式清单、记入 Job 账本、可撤销（接 08 §3.5 逃生通道语义，但容器是原生概念非兼容层特例）。 | 07 / 08 |
| **文件系统根** | 可选：容器 rootfs = 一个子树级 CoW 快照 VMO（06 §4.3 `.msys` 原子更新机制复用），命名空间 repoint 到该快照，实现容器文件系统隔离与可回滚。 | 06 |
| **生命周期** | 容器根 Job 终止 → 传播杀死全容器（04 §4.5 lifetime control）。监督策略由 meu-supervisor 在用户态按容器 manifest 执行（重启/升级/降级）。 | 04 |

### 4.2 容器 manifest（声明式，类比 launchd plist / OCI config）

```
container_manifest := {
  job_quota:       { cpu_weight, cpu_bw_cap, mem_cap, handle_cap, io_bw, pids_cap }
  capability_set:  [ rights 收窄后的初始句柄清单 ]        # 接 07 §4.1
  namespace_view:  [ reveal(path, perm), ... ]            # 接 06 / C3，unveil 锁定
  pledge_default:  [ stdio, rpath, wpath, inet, ... ]     # 接 07 §4.2，只能收缩
  rootfs_vmo:      optional<vmo_capability>               # 接 06 §4.3 CoW 快照
  supervisor:      { restart_policy, deps[] }             # 接 04 §4.5
}
```

- manifest 本身是一份**声明式 capability 申请单**，由持有「创建容器 Job」专属 capability 的容器管理器（用户态服务）提交内核；内核据 manifest 签发受约束句柄。**无 manifest 即无容器**——杜绝隐式特权域。
- 与 OCI 运行时兼容：OCI `config.json` 可经兼容层/容器管理器**映射**为上述 manifest（接 04 §5.3 Job↔cgroup 兼容映射待决，本文建议：不模拟 cgroup 内核接口，而是把 OCI 字段**翻译**为 Job 账本 + namespace，避免引入 cgroup 兼容负担）。

### 4.3 容器 vs Linux 容器的本质差异（非缝合怪声明）

| 维度 | Linux 容器 | MeuOS 容器（本文） |
|------|-----------|-------------------|
| 隔离第一性 | namespace + cgroups 事后挂接 | capability 边界 Day 1（Job+rights+namespace 同源） |
| 权限来源 | uid/gid + capability bounding set + seccomp | 收窄的 capability set，无 root 逃生舱 |
| 资源账本 | cgroups 事后附加，可被「先越权再入笼」 | Job 固有属性，诞生即受限（04 §4.4） |
| 文件系统隔离 | overlayfs + mount namespace | 子树 CoW 快照 VMO + 命名空间 repoint（06） |
| 视图 | 全局 `/proc` 经 namespace 裁剪 | 每进程命名空间默认全不可见、显式 reveal（C3） |
| 容器运行时 | runc/containerd 依赖 cgroup/namespace | 容器管理器把 OCI 翻译为 Job manifest，无内核 cgroup 接口 |

> 结论：MeuOS 容器**不是** Linux 容器的移植，而是「capability 边界 + Job 账本 + 命名空间」的声明式实例化；OCI 仅是外部描述格式的翻译源。

## 5. 虚拟化方案与五架构差异（L2）

### 5.1 方案选型：用户态 VMM + 薄内核 guest 设施（Fuchsia/macOS 式）

**采纳**：MeuOS 原型期 VM = **用户态 VMM（crosvm 式，Rust 实现、排除出 TCB，见 02 §4.2 组件矩阵「用户态服务」）驱动 + 内核提供的极薄 guest 设施**：

- **内核 guest 对象（最小 TCB 内，Rust）**：
  - `guest` 对象：持有 guest 物理地址空间（GPA）根，GPA 由一组 **VMO** 支撑（MMIO/内存均经 VMO，接 03 §4.4 device VMO 思想）。
  - `vcpu` 对象：一个 vCPU 即一个可被宿主机调度的实体；其 CPU 时间计入 VMM 所属 **Job 账本（04 §4.4）**——VM 不是一个「偷走 CPU 的黑洞」，而是 Job 树下的一个重负载子 Job。
  - 第二阶段地址翻译（EPT/NPT/RVI 等）由内核 guest 设施管理，把 GPA→HPA 绑定到 VMO 的物理页（接 03 buddy/VMO 模型，C1 折中方案）。
- **用户态 VMM（排除出 TCB，Rust/C）**：负责设备模拟、guest 启动、缺页/缺 IO 的 trap 转发；需要访问 guest 对象时必须持有相应 capability（接 07：无 cap 则 `EPERM`）。
- **设备授予**：guest 要用的设备 = 内核签发 **device VMO（03 §4.4）** + 中断 capability，经 IPC 授予 VMM，VMM 再直通或半虚拟化给 guest。**未经 capability 的设备对 guest 不可见**——与容器同一条信任边。

**否决**：Linux KVM 式「单体内核虚拟化子系统 + `/dev/kvm` ioctl 大接口」——其 ioctl 面本身是一套需长期稳定的 ABI（与 23 冲突：内核内部接口本应可破），且把大量设备模拟逻辑拉进 TCB。除非 §7 架构裁决改为提供 KVM 兼容，否则内核只暴露 `guest`/`vcpu` 一等对象。

**为什么这是「非缝合怪」**：思想取自 Fuchsia restricted VM（guest 只拿 VMO）、macOS Hypervisor.framework（用户态 VMM）、Android pKVM（受保护 VM）、ChromeOS crosvm（Rust VMM + VMO 直通）、seL4（VM 也是可 revoke 的 cap 对象）；但接口与生命周期全部按 MeuOS 的 capability/Job/VMO 模型自主设计。

### 5.2 VM 经 capability 拿资源的接口（接 03/04）

| VM 所需资源 | 经 capability 的授予路径 | 对齐子文档 |
|-------------|--------------------------|-----------|
| CPU 时间 | VMM 进程属于某 Job；其 vCPU 线程由调度器按 Job 账本（权重/带宽上限）计量，超限限流不杀（04 §4.4） | 04 |
| 内存（GPA） | `guest` 对象的 GPA 由一组 VMO 支撑；VMO 来自 buddy（C1 折中），可经 03 §4.4 的 revoke 回收 | 03 |
| 设备 MMIO/IRQ/DMA | 内核在 Stage 4 签发 **device VMO + IRQ cap**（接 09 §5.4/C8），经 IPC `GRANT` 给 VMM；guest 直通须 IOMMU 隔离（10 §5.2 DMA 强制化） | 03 / 10 / 00-C8 |
| 撤销 | `close` guest/vcpu 句柄即触发派生链回收（07 §4.5 revoke；03 §4.4 revoke 即回收），等价于 seL4 `Revoke` | 07 / 03 |

> 由此 VM 与容器在 capability 模型下**完全同构**：都是「受约束 Job + 收窄 rights + （可选）device VMO」——只是 VM 额外持有一等 `guest`/`vcpu` 对象。这正面回应 1.1「隔离第一性 = capability 边界」。

### 5.3 五架构虚拟化支持差异

| 架构 | 硬件虚拟化扩展 | MeuOS 支持形态 | 备注 |
|------|---------------|----------------|------|
| **x86_64** | Intel VT-x（VMX）/ AMD AMD-V（SVM） | **原生 L2 VM 支持**（guest 设施 + vCPU） | 五架构中 virtualization 最成熟；第二阶段用 EPT（Intel）/ NPT（AMD） |
| **aarch64** | VHE（Virtualization Host Extensions，EL2 作 host）+ NV（Nested Virt， newer core） | **原生 L2 VM 支持**；host 跑在 EL2，guest EL1/EL0 | VHE 使 host 内核可直接用 EL2，免去 EL1 stub；NV 支持嵌套虚似化（后续） |
| **riscv64** | H-extension（hypervisor，2021 批准）+ vs-mode | **原型期可支持**（依赖 QEMU/硬件 H-ext）；优先级次于 x86/aarch64 | H-ext 硬件尚在普及；可先用 QEMU `virt` 的 H-ext 验证 guest 设施抽象 |
| **loongarch64** | LoongArch 虚拟化扩展（LSVZ / LVZ，龙芯） | **待评估**：扩展存在但工具链/验证成熟度较低 | 内核 guest 设施抽象需新增 arch 后端；原型期可后置 |
| **i386** | **无**（VT-x 仅 64 位；32 位 x86 无虚拟化扩展） | **不支持原生 VM**；仅能在其他架构 host 上以用户态 VMM 跑 i386 guest 映像，或 i386 完全不涉 VM | 接 02 §2.3 约束 C2：i386 纯 C，无 Rust 裸机 target，VM 后端更无硬件基础 |

**统一抽象原则**：内核 guest 设施抽象为 `arch/vm/` 接口（`guest_create` / `vcpu_run` / `ept_map` 等），各架构提供薄后端；无硬件虚拟化扩展的架构（i386）该后端直接返回 `ENOSYS`，不模拟。这延续 01 §5-6 / 03 §2.1「统一抽象 + 每架构薄后端」的既有约束。

### 5.4 VM 与 TCB（接 02）

- **内核 guest 设施核心（vcpu 调度、第二阶段页表、trap 分发）**：Rust 入 TCB（同 capability/IPC/调度，02 §4.2）。
- **用户态 VMM（设备模拟、BIOS/内核加载、IO 转发）**：Rust 实现但**排除出 TCB**（类比 02 §4.2 把 Linux 兼容层归 C 排除出 TCB）；以 fuzz/sandbox 补偿（接 02 §5.3 mkit 安全补偿的同等对待）。
- **理由**：guest 设施是「能力边界的延长线」，须编译期安全；VMM 是「兼容性/便利性适配」，可隔离、可重启（02 §4.5 用户态 Rust 服务由 supervisor 重启）。

## 6. 与 04 / 07 / 08 的接口边界

> 本节只画边界、列依赖与待协同点，不展开他域设计（遵循 08 §4 的同类写法）。

### 6.1 与 04（进程与调度）
- **依赖**：VM 的 vCPU 线程必须走 04 的调度器与 Job 账本——vCPU 是 Job 下的线程实体，CPU 时间由账本计量（§5.2）。
- **协同点**：`meu_spawn` 应暴露「创建容器 Job / 创建 guest 子 Job」入口，供容器管理器与 VMM 复用（接 04 §4.2 spawn 语义）。
- **待协同**：Job 账本 OOM 归因（04 §5.5）在「VM 吃掉大块内存」时如何归因到 VMM 子 Job；Job↔cgroup 映射（04 §5.3）是否承载 OCI 翻译（见 §4.2）。

### 6.2 与 07（安全模型）
- **依赖**：容器/VM 的一切权限都来自 07 的 `rights` 位图与 capability 派生规则；撤销（revoke）必须能精确传播到容器子树与 guest 句柄（07 §4.5，接 03 §4.4）。
- **协同点**：本文 §4 的容器规范是 07 §4.3「一个范式、三个表现维度」在容器粒度的实例化；是否需要新增 `right`（如 `GUEST_CREATE` / `VM_MANAGE`）作为创建 guest 的专属能力，待 07 定稿 rights 位图时回填（接 07 §5-2）。
- **待协同**：pledge/unveil 是否需新增「容器级」聚合 promise（如 `container` 维度）还是纯靠 namespace reveal 表达。

### 6.3 与 08（Linux 兼容层）——明确澄清（铁律）
- **澄清**：兼容层 = **薄翻译面，非 VM**（08 §0/§1/§5 已定）。**Linux 二进制在 L0/L1 上跑，不进 L2 VM**。任何「用 VM 跑 Linux 兼容」的设想均被 08 否决（WSL2 行标「无——与我们内部自主相悖」）。
- **依赖**：本文 VM 用途与 08 正交——VM 跑**非 Linux 兼容层职责的**负载（旧 OS、隔离测试、第三方内核）。两者不冲突、不重叠。
- **协同点**：若未来要在 VM 内跑一个「兼容层兼容不了的旧 Linux 发行版」，那是 L2 guest 自身的事，与 08 薄层无关；此时 guest 内部的 Linux 兼容由 guest 自己的内核负责，MeuOS host 只提供 guest 设施（§5）。
- **待协同**：无（本文与 08 边界清晰，仅需 08/本文互相引用，不修改对方）。

### 6.4 与 23（ABI 稳定性，若已回写）
- **依赖**：VM 的内核 guest 设施（`guest`/`vcpu` 对象语义、GPA 映射接口）属 23 的**② 原生 syscall/capability API**——演进期明确不稳，靠 libc/mkit 屏蔽，随 `.msys` 原子升级（23 §2/§3）。
- **版本化隔离接口**：容器的 manifest 形态（§4.2）与 guest 设施接口建议绑定 **`.msys` sysroot 版本**（23 §1.1 同版本整体升级杠杆），而非独立冻结——容器运行时/ VMM 与内核同 sysroot 演进，保留破坏权。
- **对外稳定部分**：若将来提供 KVM 兼容接口（§7 待决），该接口落入 23 的**① Linux 兼容 ABI** 范畴，须对外稳（仅声明子集）。

## 7. 自主结论 + 待决项

### 7.1 自主结论（调研员判断，非既定事实）

1. **隔离第一性 = capability 边界**，已在 04/06/07 落地；容器是三元组实例化，VM 是该边界在「跨内核」时的外推，二者同构。
2. **容器规范 = Job 账本 ∩ rights ∩ namespace 视图 ∩（可选）rootfs CoW 快照**，声明式 manifest 组装，不引入新内核对象。
3. **VM 采用用户态 VMM + 薄内核 guest 设施（Fuchsia/macOS/crosvm 式）**，设备经 device VMO 直通、CPU 时间走 Job 账本；**不跑 Linux 二进制**（接 08）。
4. **五架构差异**：x86_64 / aarch64 原生支持；riscv64 原型期可支持（H-ext）；loongarch64 后置；i386 不支持（无硬件虚拟化）。
