| # | 子领域 | 一句话定位 | 核心结论（一句话） | 与既有裁决衔接 |
|---|---|---|---|---|
| **57** | 时钟与时间子系统 | 「**单调钟唯一不可调、墙钟用户态化受控校准；clock 与 timer 都是 `07` §2 内核对象句柄；定时器以绝对 deadline 入红黑树 + 按 `slack` 合并唤醒 + 经 EventPort 投递；底层五架构差异由单一 `arch/timer` 后端屏蔽**」 | ① 单调与墙钟从内核对象层分离（Zircon 范本）；② clocksource 与 clock 视图解耦（`time = counter × scale + offset`，Mach timebase_info 同构）；③ 定时器 = 一等内核对象 + capability（继承 `07` §2）；④ 绝对 deadline + slack 合并取代 Linux `timeBeginPeriod`；⑤ 时间特权 = 对象级 right（`CLOCK_ADJUST`/`CLOCK_MINT`，建议 bit 48+ 预留，不复用 `MANAGE`/`GRANT`）。 | 与 `28` §6 五架构计时源互补；与 `04` 调度时基、`05` EventPort、`25` 网络 RTO/`25` C15 用户态 netstack 超时、`07` §2 timer 对象、`10` §4.2 定时器留核同构；7 项待决（T1–T7）均为执行层协同，无新增架构裁决。 |

### §3.2 落定模式总结

第七轮精细裁决的落定模式可归纳为**三类**：

1. **「B 主线 + A 长期/兼容投影」共存模式**（C-G1、C-G4、C-G5）：A 与 B 在内核层无冲突，差异仅在「兼容层是否暴露兼容投影」或「原生是否给另一范式留过渡原语」。这类裁决零新增 right、零新增内核机制，仅在兼容层或原生 ABI 层做语义细化。
2. **「公约数化解互斥」模式**（C-G2）：A 与 B 互斥（保留模式场景图 vs 客户端-合成器协议），精细裁决不取非 A 即 B，而取「协议层 B + 框架层可选 A」——从互斥降级为分层叠加，零新增机制。
3. **「right 不预留」模式**（C-G3）：在 B 主线下，A 范式特有的对象（scene session）不存在，无需为其预留 right；bit 48+ 维持冻结，防御性说明留给未来。

> 这三类落定模式共同点：**全部建立在 `56` §7.1「五方案统一在 capability+Job 地基上」的判断之上**——5 子系统 A/B 的分歧不发生在安全不变量之争，而发生在「同一 capability+Job 地基上的现代化程度光谱」，故精细裁决均能以「零新增 right / 零新增内核机制」收口，与 MeuOS「从零、现代化、capability Day 1、兼容渐进」立场严丝合缝。

> 本轮新提的 bit 48+ 候选集中在 **6 类**：① `SCENE_SESSION`（C-G3 已裁决不预留，bit 48 维持冻结）；② `CLOCK_ADJUST`/`CLOCK_MINT`（57 T1）；③ `IO_*`/`CONSOLE_*`/`UART_*`（60 E1）；④ `IRQ_WAIT`/`IRQ_ACK`/`IRQ_MASK`（59 开放议题 1）；⑤ `AUTH_ISSUE`（53 §8-5）；⑥ 防御性占位（如未来 `MEDIA_CAPTURE`、`NET_NEW_*` 等）。

**协调建议**：
- **bit 48–55 优先分配顺序**：按 `56` §8 优先级 + C-G3 防御性原则，bit 48 维持冻结（仅为 `SCENE_SESSION` 候选描述、不占位）；bit 49–55 按 `60` E1 → `57` T1 → `59` 开放议题 1 → `53` §8-5 顺序逐项冻结，每项需对应 owner（`07`/`34`/`60`/`59`/`53`）协同定稿；
- **冻结纪律**：按 `38` §3 / `45` §3 的「统一 rights bit 分配表」纪律——所有新增 bit 须先在本表登记、回写 `07` §4.1、由 `07` owner 与对应子系统 owner 联合定稿，不允许子系统 owner 单方面占用；
- **Day 1 触发原则**：C-G3 已确认 bit 48+ 维持冻结不为任何 Day 1 子系统占位；本轮新提的所有 bit 48+ 候选均**不阻塞 Day 1 自举**，属执行层定稿后逐项落位。

### §4.3 推荐立场（指挥官式）

1. **优先拍板 B-61-1/2/4**（`.mimg` 唯一载体 + 度量元数据分离 item + `.mimg` 携带恢复 `.msys` 指针）：这三项是 `61` 与 `11`/`21`/`32`/`06`/`09` 协同的**结构性枢纽**——若 `.mimg` 不定为唯一载体，多份格式将导致度量基分裂；若度量元数据不分离 item，bootloader 验签策略将被迫与内核解析耦合；若 `.mimg` 不携带恢复指针，A/B 防砖兜底将依赖运行时而非启动期。建议**在第八轮以独立裁决回写**（与 `11`/`21` 协同），本轮仅汇总。
2. **优先协同 E1**（早期串口第②层 right 命名）：早期串口是 M0 启动必需，若 right 命名未定，则 Stage 4 串口 cap mint 与 Stage 5 console 交权时序无法定稿；建议**在第八轮与 `07` 协同定稿**，bit 48+ 预留区按 §4.2 顺序分配。
3. **其余 7 项**（T1–T7 / E2–E5 / 59 开放议题 / 58 协同项 / `53`/`47` 议题）**均不需大喵拍板**，由对应 owner 据本轮裁决协同定稿，属执行层/原型实测项。

## §6 与既有地基的对齐（一句话总览）

> 第七轮精细裁决与拓展收敛**未引入任何新的内核裁决机制**、**未引入任何新的 right bit**（bit 48+ 维持冻结，不为 Day 1 任何子系统占位）、**未触碰既有 C1–C18 / V1 / R1 / D-T1 / 能耗-Job 等自主采纳项**——所有结论均建立在 `00` §2 A1–A12 地基之上：

- **capability 唯一权限源**（A1 / `07` §2.3）：5 项精细裁决（C-G1~C-G5）与 5 新维度（57–61）全部 Day 1 即由 capability 表达，零回退路径；
- **Day 1 唯一 capability 模型**（A2）：精细裁决未引入任何「先传统再 capability」回退；
- **Rust 管安全关键路径、最小 TCB**（A3）：57（clock/timer 句柄即 capability）、58（`CFG_*` 受界数据，非 TCB）、59（`interrupt` 对象即 capability，KERNEL_PRIV 仅内核自持）、60（驱动即用户态进程 + IOMMU 域 + device VMO）、61（`.mimg` 整体签名 + 四跳信任链）全部沿用此原则；
- **统一资源命名空间**（A4 / C3）：C-G5（A/B 并存命名空间边界）、59（capability 路由）均按此口径；
- **Job 资源账本 Day 1**（A5）：C-G1（子进程归入父 Job 投影继承）、C-G5（显式快照计入 Job 配额；自动版本链/Blob GC 不计入）、60（驱动即 Job，账本防 DoS/防爆炸半径）均按此口径；
- **重服务出核缩 TCB**（A6 / A11）：5 项精细裁决与 5 新维度均未把任何重服务拉回内核；C-G2/C-G3 GPU 服务独立用户态、C-G5 FS 用户态（不另起 FS 进程）、C-G4 认证 broker 用户态、58 配置 = 受界数据（不引入运行期关沙箱开关）、60 默认 L3 用户态驱动、61 早期 C/asm 不占信任跳；
- **结构化取消 / 异常上行**（A9 / `04` §4.6）：与 59（异常 = 线程级结构化事件、CrashReport 经 exception channel 上行）、C-G1（双轨创建的 Job 树结构化取消）同源；
- **C16 / CFG_***（`00` 第三/四轮）：58 把 `30` 的两层模型 operational 化为三格分类判定器 + Day 1 最小集 + 权限边界 + 误配置遏制 + `.msys` 协同协议；
- **D-T1 / `KERNEL_PRIV`**（`29` D-T1）：59 定稿其精确边界（全局 IRQ mask = `KERNEL_PRIV` 仅内核自持，用户态无全局关中断权），与 `33`-D1（`BLOCK_*`）/ `34`-D-G2（`GPU_SUBMIT`）/ `57` T1（`CLOCK_ADJUST`）同构「领域专属 right、不复用 MANAGE/GRANT」先例。
