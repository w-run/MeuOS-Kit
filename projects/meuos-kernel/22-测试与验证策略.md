## 1. 「应该是什么样」——测试与验证的解构推演

> 本节先于任何结构，回答一个根本问题：在一个**混合内核、Rust+C、capability 唯一模型、五架构、且没有 Linux 式海量回归基线**的项目里，测试与验证**应当**长成什么样子？

### 1.1 五个结构性约束决定了它的形状

MeuOS 不是任意 OS，它带着五条硬约束，每条都直接改写「测试该怎么设计」：

1. **没有现成回归基线**（见 `11` §2.3）。Linux 有 LTP / xfstests / kselftest 数十年沉淀的百万级用例；MeuOS 是从零的新内核。这意味着不能「假设一个基线然后验证偏差」，而必须**从第一个可累积的断言（绿光）起步，逐步建信心**——这一条是全文的脊梁（§5 专门处理）。

2. **capability 是 Day 1 唯一权限模型、无 root 逃生舱**（见 `07` §1、§4.1）。测试的重点不是「权限检查是否放行了合法请求」，而是 **「越权是否必然失败、且 fail-closed」**。安全测试的默认断言方向是**否定式**：尝试越权 → 必须 `EPERM` / 进程终止 / 句柄不可用，而非「授予后能用」。这是与 Linux（五套机制叠加、root 万能）测试哲学的根本反转。

3. **Rust+C 混合、最小 TCB**（见 `02` §4）。测试必须区分两层信任边界：
   - **TCB（Rust 安全关键）**：capability 判定 / IPC 端点 / syscall 路由 / 调度 / VFS 抽象。这里靠**编译期类型不变量 + 白盒单元测试**建信心，目标是从代码结构上消灭整类漏洞（`02` §4.4）。
   - **非 TCB（mkit C 兼容层）**：刻意排除出 TCB（`02` §4.2 矩阵）。这里**不靠证明、靠 fuzz + sandbox 补偿**（`02` §5-3、§5-3）——因为无法在编译期强制它的正确性，只能用经验性模糊测试兜底。

4. **结构化可观测性是一等公民**（见 `12` §1.2、§4）。这是 MeuOS 相对 Linux 的**独有优势**：inspect 树（强类型状态树）+ 事件流（带 schema 的结构化事件）+ CrashReport，全部经 capability 守护。测试应当**消费结构化数据做确定性断言**，而非像 Linux 那样 `grep` 串口文本日志（脆弱、易随排版漂移）。这一条把「没有基线」的劣势部分抵消——我们用稳定的结构化 schema 取代脆弱的文本基线。

5. **五架构 + i386 纯 C**（见 `02` §2.3 约束 C2）。测试矩阵不能「全架构全量一等」，否则成本爆炸。必须**分层**：主架构全量、辅架构编译+冒烟，且 i386 因无 Rust TCB，测试面与其他 64 位架构本质不同（§6）。

### 1.2 推演出的「应该」形态（测试金字塔）

把上述约束落成一张**倒金字塔**（底层快/多/便宜，顶层慢/少/贵，但每层都产出可累积断言）：

```
        ┌─────────────────────────────────────────────┐
 L4 五架构矩阵       每架构编译+冒烟(M0)；主架构全量      ← 贵/慢，nightly+release
        └───────────────────┬─────────────────────────┘
        ┌─────────────────────────────────────────────┐
 L3 系统级 .msys 启动+自举  M0–M4 / L0–L2 绿光闭环        ← 慢，里程碑+nightly (复用 11 方案 A)
        └───────────────────┬─────────────────────────┘
        ┌─────────────────────────────────────────────┐
 L2 跨服务集成        FS+VMO/命名空间、supervisor+Job、mkit+cap  ← 中，merge gate
        └───────────────────┬─────────────────────────┘
        ┌─────────────────────────────────────────────┐
 L1 IPC 协议一致性     Channel/EventPort/SHM/Registry、cap 拷贝语义、schema  ← 中，merge gate
        └───────────────────┬─────────────────────────┘
        ┌─────────────────────────────────────────────┐
 L0 内核单元测试(Rust 组件)  cap 判定/IPC/调度/VFS/Job   ← 快/多，per-PR
        └─────────────────────────────────────────────┘
           + 非 TCB 模糊测试(mkit/syscall 翻译面、cap revoke、FS extent)  ← 持续后台跑
```

**为什么是这个形状**：L0 用 Rust 类型系统 + 单元测试把 TCB 正确性前置到编译/单测期（最便宜、最确定）；L1/L2 在用户态 harness 里验证协议与跨服务契约（MeuOS 混合内核下大量逻辑在用户态，正好可用户态测）；L3 复用 `11` 的自举验证主路线作为「系统级绿光」；L4 把架构成本压到「编译+冒烟 + 主架构全量」。模糊测试横切 L0–L3 的非 TCB 面。

### 1.3 与「绿光起步」的闭环关系

「应该」的起点是一个最小可累积断言：**mcc + meuos-libc 在自研内核上自举成功（`11` M0–M4 / L0–L2）= 第一束绿光**。之后每修一个 bug 加一条回归、每加一个 syscall 加一条行为断言、每加一个 capability right 加一对「授予可用 / 越权失败」用例。信心是**边际累积**的，不是一次性获得的——这正是没有基线时的正确心态（详见 §5）。

## 2. 多系统参照对比（取长补短、实现自主）

围绕「如何分层、CI 何时介入、无基线如何建信心、模糊测试切入点」，对照七类参照系，取其思想、不缝合。

### 2.1 候选系统概览

| 系统 | 测试分层哲学 | CI/门禁介入 | 无基线应对 | 模糊测试切入点 | 对 MeuOS 的取舍 |
|---|---|---|---|---|---|
| **Linux** | kunit(内核单测)+kselftest(用户态 syscall/API)+xfstests(FS)+LTP(全量)+syzkaller(syscall fuzz) | 海量基线驱动，CI 跑全量回归 | 几十年累积，基线即真理 | syzkaller 覆盖 syscall 面；xfstests 覆盖 FS | 取分层思想；**弃**文本日志断言与权限分散测试 |
| **Fuchsia** | 单元+集成+系统三层；zircon 测试；fuzzing 进 CI；结构化断言（inspect/trace 本身可测） | 三层逐级门禁，集成/系统层按需 | 新系统从组件单测起，靠契约测试建信心 | Fuchsia fuzzer 覆盖 syscall/IPC/协议 | **主参考**：结构化断言 + 三层门禁 + capability 受控测试 |
| **seL4** | sel4test（功能回归）+ **证明回归**（精化证明与代码同步） | 证明即门禁，证明失败=CI 红 | 证明提供「零基线」信心来源 | 极少（形式化覆盖核心） | 取「证明即回归」思想，与 `20` 形式化互补 |
| **Redox** | 用户态测试多（relibc/驱动），**内核态测试薄弱** | 用户态 CI 充分，内核态弱 | 内核测试靠手测/启动 | 少 | **反面教训**：纯微内核易忽略内核态自身测试，MeuOS 混合内核须补 L0 内核单测 |
| **NT** | HDK / testsig（驱动签名+WDK 测试） | 驱动签名强制测 | WHCK 兼容性矩阵 | driver verifier | 取「驱动须过强制测试关卡」思想（呼应 `10` 驱动模型） |
| **Android** | VTS(硬件抽象)+CTS(兼容性套件) 矩阵 | 每设备/每架构跑兼容性矩阵 | CTS 即基线 | hwaddresssanitizer fuzz | 取「五架构兼容性矩阵」分层思想（呼应 §6） |
| **FreeBSD** | `tests` 套件（kyua）+ syscall 回归 | 提交门禁跑回归 | 累积用例库 | fuzz 渐进 | 取「syscall 行为断言累积」思想（呼应 §5 绿光累积） |

### 2.2 关键取舍结论

1. **分层取 Fuchsia、不取 Linux 文本基线**：Linux 的「grep 日志 + 海量 LTP」在 MeuOS 无基线且无意义；Fuchsia 的「结构化断言 + 三层门禁」与 `12` 的 inspect/事件流天然同构——这是 MeuOS 的差异化优势，应作为主参考。
2. **内核态单测必须存在（吸取 Redox 教训）**：Redox 因纯微内核把测试重心压到用户态，内核态薄弱。MeuOS 混合内核的关键组件（cap/IPC/调度/VFS）在**内核态 TCB**，必须在 L0 做白盒单测，不能等系统级才发现问题。
3. **证明即回归（取 seL4，交 `20`）**：capability 不变量（rights 不可伪造、revoke 传播完整）应由 `20` 形式化精化证明持续回归；本文 `22` 负责经验性/运行时证明，二者互补不重叠（§7）。
4. **五架构矩阵取 Android CTS/VTS 的分层思想**：不追求全架构全量一等，主架构全量 + 辅架构冒烟（§6）。
5. **模糊测试横切非 TCB**：取 syzkaller 的「syscall 面是最大攻击面」思想，但 MeuOS 的 fuzz 面更聚焦——mkit 翻译面、cap revoke、FS extent 解析（§4）。

## 3. 测试分层 + CI 门禁

### 3.1 五层测试定义与断言形态

#### L0 — 内核单元测试（Rust 组件，TCB 白盒）
- **对象**：capability 判定与传播（`07` §4.1/§4.5）、IPC 端点（`05`）、调度器 EEVDF/RT/work-stealing（`04` §4.3）、VFS 抽象与 extent 校验链（`06`/`01` 方向①）、spawn/Job 账本（`04` §4.4）。
- **框架**：内核态 `no_std` 下需要一个内核内单测 harness——参照 kunit 的 `#[cfg(test)]` + 自定义 test runner，或把 TCB Rust 组件编译为用户态 harness（链接 `core`/`alloc` + mock 底层）跑 `cargo test`。**优先用户态 harness**：因为 TCB 组件是纯 Rust、类型驱动，脱离内核态即可测，速度快、可调试。
- **断言形态**：纯函数/状态机断言（rights 位图运算、derivation tree、调度选程、配额强制）。编译期不变量由 `#![forbid(unsafe_op_in_unsafe_fn)]` + 类型系统兜底（`02` §4.4）。

#### L1 — IPC 协议一致性测试
- **对象**：Channel / EventPort / SHM / Service Registry 四大原语（`05`/`00` A8）；cap transfer 的 `cap_move`/`cap_copy` 与 Rust 所有权对齐（`05` §5-2）；事件流 / syscall trace 的 **schema 自描述性**（接 `12` §4.4）。
- **断言形态**：协议级——发送/接收/复用/EOF 语义；cap 跨进程授予后接收方权限 ≤ 发送方 `GRANT` 约束（`07` §4.5）；**schema 一致性**：同一事件在生产者与消费者侧解码一致（防 schema 漂移，这正是 Fuchsia FIDL 反射式自测的思想）。

#### L2 — 跨服务集成测试（用户态 harness）
- **对象**：FS 服务 + VMO/pager + 每进程命名空间（`06`）；supervisor + Job 树 + exception channel（`04` §4.5/§4.6）；mkit 兼容层 + syscall 翻译 + capability 映射（`08`）。
- **断言形态**：端到端行为——spawn 子进程持最小句柄集、unveil 后未 reveal 路径必失败、异常经 exception channel 上报 supervisor 且按策略重启/终止（`12` §4.3）。**消费 inspect 树做确定性断言**（如 `jobs/<id>/` 账本值、`services/<n>/` 指标），不 grep 日志。

#### L3 — 系统级 `.msys` 启动 + 自举（复用 `11` 主路线）
- **对象**：QEMU + 自研内核 + `.msys` rootfs（`11` §4.1 方案 A）；M0 启动到 init、M1(L0) 静态 hello、M2(L1) mcc 编译运行、M3(L2 工具链) mcc 重建 mcc/libc/meow、M4(L2 内核) 内核由自身工具链重建。
- **断言形态**：**绿光闭环**——stage-2 产物与宿主 golden（`check-sysroot-static`）在固定测试集（mcc `check-c11`/`check-targets`、libc 原子/线程/TLS 回归）上**功能等价**（`11` §4.3 黄金比对）。这是系统级唯一硬断言，其余以退出码 + inspect 子树为准。

#### L4 — 五架构矩阵（§6 详述）
- **对象**：x86_64/aarch64/riscv64/loongarch64/arm（64 位，Rust+rustc+LLVM + C+mcc 双工具链）+ i386（纯 C，`02` 约束 C2）。
- **断言形态**：主架构（x86_64 起步，aarch64 次之，`11` M5）跑通 L3 全量；其余架构编译通过 + M0 冒烟启动。跨架构**功能等价金标准**（`11` §5-5）。

### 3.2 CI 门禁分级（何时编译 / 何时跑 QEMU）

> 核心原则：**编译便宜、QEMU 贵且需内核可启动**；早期用 `11` 方案 B（qemu-user-static）并行做 ABI 回归，保「内核就绪前工具链不被破坏」。

| 门禁级 | 触发时机 | 动作 | 成本 | 对应层 |
|---|---|---|---|---|
| **G0 快速单测** | 每次 commit / PR | Rust `cargo test`（L0 用户态 harness）+ `cargo clippy`（`#![deny(clippy::all)]`）+ `unsafe` 行数/块数门禁（`02` §4.4/§5-6）+ C `mcc -Wall -Wextra` 编译 L0/L1 | 秒~分钟 | L0/L1 |
| **G1 跨服务集成** | PR merge 入主分支前 | L2 用户态 harness 全量跑（FS/supervisor/mkit 集成）；IPC schema 一致性 | 分钟级 | L2 |
| **G2 全架构编译** | merge 入 main / nightly | 五架构内核镜像交叉编译成功（不启动）；`qvm --kernel` 镜像产出就绪 | 分钟~十分钟 | L4(编译) |
| **G3 系统级自举** | nightly / 里程碑（M0–M4 解锁时） | 主架构 QEMU 跑 L3 全闭环 + 绿光断言 + 黄金比对 | 十分钟~数十分钟 | L3 |
| **G4 矩阵 + fuzz + 性能** | release / periodic | 五架构 L3/L4 + 长时间 fuzz（§4）+ 触发 `19` 性能基准 | 小时级 | L4 + §4 + `19` |

**关键决策**：
- **QEMU（G3/G4）不进 per-PR**：内核未可启动前 G3 必红，且慢；用 G0/G1 在用户态 harness 拦绝大多数回归，QEMU 留给 nightly/里程碑。
- **`11` 方案 B（qemu-user-static）进 G0 常驻**：内核就绪前就能持续验证 mcc 跨架构 ABI，是「无基线期」最便宜的信心来源。
- **G2 全架构编译进 merge gate**：编译失败（尤其 Rust+LLVM vs mcc+QBE 双工具链链接、`02` 约束 C1）必须早暴露，不等到 QEMU。
- **fuzz 常驻后台（§4）**，不阻塞合并，但 nightly 汇总覆盖率/崩溃报告。

## 4. 模糊测试与安全属性测试

### 4.1 模糊测试切入点（聚焦非 TCB 攻击面）

MeuOS 的 TCB 靠编译期类型 + 单测建信心；**模糊测试专攻「无法编译期强制」的非 TCB 面**，取 syzkaller「syscall 面是最大攻击面」思想，但更聚焦：

| 切入点 | 目标组件 | 验证意图 | 关联文档 |
|---|---|---|---|
| **syscall 翻译面（mkit 兼容层）** | 08 / C 兼容层（排除出 TCB） | fuzz Linux syscall 号 + 参数组合，验证 fail-closed、无越权、无能力逃逸；验证 `02` §5-3「排除出 TCB 须 fuzz 补偿」 | `02` §5-3、`08` |
| **capability revoke 传播** | 07 / derivation tree | fuzz 撤销序列（close/revoke 级联），验证派生句柄链在回收后**全部不可用**、无悬垂 | `07` §4.5、§5-4 |
| **FS extent 解析** | 06 / extent B-tree + 校验和/压缩/加密 | fuzz 损坏的 extent、畸形 B-tree、错误校验和/密钥，验证**损坏必被检测**（拒绝挂载/读失败），不静默破坏 | `01` 方向①、`06` |
| **IPC 消息边界** | 05 / Channel/SHM | fuzz 消息大小/类型/cap transfer 交错序列，验证端点不崩溃、权限不越界 | `05` |
| **bootinfo / 设备树解析** | 09 | fuzz 多架构 bootinfo（DT/ACPI/multiboot/OpenSBI，`00` C6），验证早期解析 fail-closed | `09` §6-9 |

**fuzz 与结构化可观测性的联动**：fuzz 触发的崩溃应经 `12` 的 CrashReport 结构化落盘（`.msys` 卷，带 SHA-256/加密，`12` §4.7），而非仅串口文本——fuzz 收敛报告直接消费结构化 CrashReport 队列。

### 4.2 安全模型（07）如何被测试「证明」

capability 是唯一模型，测试方向以**否定式**为主（§1.1 约束 2）：

| 安全属性 | 测试方式（经验性/运行时） | 预期断言 |
|---|---|---|
| **rights 越权必失败** | 负面测试：持最小句柄集的进程尝试 `READ`/`WRITE`/`EXECUTE`/`GRANT`/`MANAGE` 无 right 的对象 | 必须 `EPERM` 或进程 SIGABRT（fail-closed，`07` §4.2） |
| **revoke 后派生句柄不可用** | 授予派生句柄 → 父 revoke → 子尝试用派生句柄 | 操作必须失败；验证 derivation tree 回收完整性（`07` §4.5） |
| **pledge 越界即终止、只能收缩** | 进程 pledge 子系统 → 调用越界 syscall / 尝试扩张 promise | 越界必 SIGABRT（或 `error` promise 返回 `ENOSYS`）；扩张必 `EPERM`（`07` §4.2） |
| **unveil 锁定后不可扩展** | unveil 路径 + lock → 访问未 reveal 路径 / 尝试新增 reveal | 访问失败；新增被拒（`07` §4.2） |
| **confused deputy 防护** | FS 服务 mint 文件句柄时尝试越权（超出自身 rights ∩ 客户端请求） | 受约束 mint 模型拒绝越权（呼应 `00` C2 推荐裁决） |
| **无 root 逃生舱** | 任何进程尝试 uid=0 语义 / `CAP_SYS_ADMIN` 式大权 | 内核内部不识别，映射为「无对应句柄即 EPERM」（`07` §4.6） |
| **调试能力即 capability** | 无 `DBG_*` right 的进程尝试 attach/inspect/perf | 默认拒绝（`12` §4.2、§4.6） |

**与 `20` 形式化的互补边界**：本文 `22` 做**经验性/运行时黑盒+灰盒**证明（上述用例）；`20` 做**白盒精化验证 / 信息流安全**（rights 不可伪造、revoke 传播完整性的数学证明，呼应 seL4 + `07` §4.4）。二者**不重叠**：`22` 保证「实现没回归」，`20` 保证「设计不可违背」。证明改动时 `20` 的 CI 门禁同步回归，正是 seL4「证明即回归」思想（§2.2 结论 3）。

## 5. 没有现成回归基线怎么办：绿光起步 + 累积断言

> 这是 §1.1 约束 1 的落地。没有 LTP/xfstests 式基线，不能虚拟一个。

### 5.1 起点：第一束绿光
- 以 `11` 的 **M0–M4 / L0–L2 自举闭环成功**作为第一个可累积断言：mcc+meuos-libc 在自研内核上自举 = 系统级「绿光」。这是比任何单测都强的高级断言（它隐含了 MM/进程/IPC/兼容层/FS 的整体正确）。
- 绿光本身即回归基线：每次 L3 跑通即确认「自举没坏」，等价于 Linux 的 LTP 自举子集。

### 5.2 边际累积策略（信心是加出来的，不是一次获得的）
- **每修一个 bug → 加一条回归**：bug 修复 PR 必须带最小复现用例（L0 单测或 L2 集成），防止回流。
- **每加一个 syscall → 加一对行为断言**：mkit 子集每映射一个 Linux syscall，补「正确语义」+「越权/参数畸形 fail-closed」两条（呼应 §4.1 syscall fuzz 面）。
- **每加一个 right → 加一对用例**：granted 可用 + 越权必失败（`07` §5-2 rights 位图粒度演进时同步扩展）。
- **每加一个 capability 派生规则 → 加 revoke 回归**：派生链回收后派生句柄不可用（§4.2）。

### 5.3 用结构化可观测性做确定性断言（抵消无基线劣势）
- **不靠文本日志**：Linux 式 `grep` 串口是脆弱基线（排版一改就红）。MeuOS 用 `12` 的 **inspect 树 + 事件流** 做断言源：
  - 断言 inspect 子树某节点值（如 `jobs/<id>/cpu_quota`、`services/<n>/connections`），类型安全、稳定。
  - 断言事件流含某 schema 事件（如 `syscall_trace`、`exception`、`pledge_violation`），用 schema 解码而非字符串匹配。
- **效果**：即使没有历史基线，结构化 schema 本身就是稳定契约——schema 改动是有意为之、会被 code review 捕获，而非像日志文本那样悄悄漂移。这把「无基线」的脆弱性降到最低。

### 5.4 借 `11` 方案 B 维持「内核就绪前」信心
- 在 M0 之前，G0 常驻 qemu-user-static 跑 mcc 跨架构 ABI 回归（已有 6/6、3/3 基线，`11` §4.2），保证工具链不被破坏。这是无基线期最便宜的常驻门禁。

## 6. 五架构矩阵：可行性与成本

### 6.1 架构分群（决定测试成本不对称）

| 群 | 架构 | 语言/工具链 | 测试面差异 | 矩阵策略 |
|---|---|---|---|---|
| **主架构（全量）** | x86_64（起步）、aarch64（M5） | Rust(rustc+LLVM)+C(mcc+QBE) 双工具链 | 完整 TCB 单测(L0)+集成(L2)+系统级(L3) | 跑通 M0–M4 全闭环 + 绿光 |
| **辅架构（编译+冒烟）** | riscv64 / loongarch64 / arm | 同主架构（64 位有 Rust 裸机 target，`02` §2.3） | TCB 单测可复用（Rust 跨架构）；架构后端薄层（页表/中断/MM）需各自验证 | G2 编译通过 + G3 M0 冒烟启动；L3 渐近 |
| **纯 C 架构** | i386 | **纯 C（mcc+QBE），无 Rust TCB**（`02` 约束 C2） | **无 Rust 单测面**；TCB 组件在此架构以 C 实现，靠 `-Wall -Wextra` + fuzz + 用户态 harness 等价测试补偿 | 编译 + M0 冒烟；L0 以 C 等价 harness 替代 |

### 6.2 可行性判断
- **64 位五架构（x86_64/aarch64/riscv64/loongarch64/arm）**：Rust 均有 `*-unknown-none*` Tier 2 裸机 target（`02` §2.3），TCB 组件（cap/IPC/调度/VFS）是纯 Rust、与架构无关，**L0 单测一次编写、五架构复用**，仅架构后端薄层（页表游走、上下文切换 asm、中断分发）需每架构验证。可行性高。
- **i386 纯 C**：Rust 裸机 i386 缺稳定 target，TCB 组件须以 C 重写/保留 → **失去 Rust 编译期不变量红利**。应对：i386 的 TCB 逻辑以 C 实现并配等价单测 + 加强 fuzz；长期待 Rust i386 target 成熟再迁移 TCB 组件（`02` §5-2）。这是五架构中**成本与风险最高的点**，需在 §7 标为待决。
- **mcc/QBE 各后端稳定性不均**：x86_64/aarch64 后端较成熟；riscv64/loongarch64/arm/i386 待实测（`02` §2.2）。矩阵推进顺序建议 x86_64 → aarch64 → riscv64 → (loongarch64/arm) → i386，与 `11` M5 双架构优先一致。

### 6.3 成本压控
- **不在 per-PR 跑全架构 QEMU**：仅 G2 编译（便宜）+ 主架构 G3 自举（贵但必要）；辅架构 QEMU 留 nightly。
- **跨架构功能等价金标准**（`11` §5-5）：stage-1（宿主 golden）vs stage-2（MeuOS 内）在固定测试集上行为等价，化解「跨架构代码生成非确定」焦虑——测试集输出白名单即等价判据，无需 bit 级一致。
- **统一抽象 + 每架构薄后端**（呼应 `00` §5-6 五架构一致性成本）：in-kernel unwinder（`12` §4.5）、页表类型化封装（`02` §4.2）等统一抽象，使测试只需验证「薄后端契约」，而非每架构整套逻辑。

## 7. 分阶段落地（与 `11` M0–M6 对齐）

> 测试策略本身随内核成熟度演进，不追求一步到位。

| 阶段 | 内核成熟度（参照 `11`/`00` M0–M6） | 测试重点 | CI 门禁 |

## 8. 待决项（标注是否需架构裁决）

> 凡标注【架构裁决】者，需 team-lead 在合成 pass 拍板，并跨域回填；其余为本文内部/执行层待决。

1. **【架构裁决】i386 纯 C 下的 TCB 测试策略**：i386 无 Rust TCB（`02` 约束 C2），cap/IPC/调度/VFS 在 i386 以 C 实现，失去编译期不变量。裁决：i386 是否接受「C 等价单测 + 加强 fuzz」作为永久方案，还是要求 Rust i386 target 成熟前 i386 不进 TCB 关键路径？关联 `02` §5-2、`00` C6/C11。
2. **【架构裁决】五架构矩阵优先级与「全量」定义**：主架构是否仅 x86_64 + aarch64（`11` M5），其余架构的「通过」是否仅 = 编译 + M0 冒烟？需拍板矩阵成本上限。关联 `11` §5-4。
3. **【架构裁决】capability revoke 传播的测试覆盖深度**：`07` §5-4 开放「derivation tree 全量 vs 显式 close」。若原型期仅显式 close，则 §4.2「revoke 后派生句柄不可用」测试只能覆盖显式路径，全量派生链回收的测试需待 derivation tree 落地。需 `07` 定稿后回填。
4. **【本文内部】L0 单测 harness 形态**：内核内 kunit 式 `#[cfg(test)]` vs 用户态 harness 链接 `core`/`alloc` + mock。建议优先用户态 harness（快、可调试），但需执行层确认内核态是否能承载 test runner。关联 `02` `no_std`/`alloc` 约束。
5. **【本文内部】fuzz 与 `20` 形式化的接口**：fuzz 发现的「revoke 泄漏」类 bug，应同时沉淀为 `20` 形式化需覆盖的不变量。二者如何联动回归需在 `20` 产出后对齐接口。
6. **【跨域，关联 `19`】性能基准与正确性测试的边界**：本文 `22` 只做正确性/安全/协议测试；**性能基准（syscall 延迟、IPC 往返、EEVDF 尾延迟、VMO pager 缺页、mcc 自举耗时）归 `19-性能与可验证性`**。G4 触发 `19`，二者互不重叠。需 `19` 产出后确认边界无遗漏。
7. **【跨域，关联 `20`】形式化与经验测试的分工**：`20` 负责 rights 不可伪造 / revoke 完整性的精化证明；本文负责运行时/黑盒证明。需 `20` 产出后确认互补无重叠，并约定「`20` 证明改动即 CI 回归」机制。
8. **【跨域，关联 `12`】结构化断言的 schema 契约**：§5.3 用 inspect/事件流做确定性断言，前提是 schema 稳定。需 `12` 定稿 inspect 树节点 + 事件流 schema 后，测试框架才能消费。关联 `12` §4.4。
9. **【跨域，关联 `11`】绿光比对的「固定测试集」范围**：§5.1 绿光依赖 mcc `check-c11`/`check-targets` + libc 原子/线程/TLS 回归。需 `11` 明确测试集清单作为等价金标准。关联 `11` §4.3/§5-5。
