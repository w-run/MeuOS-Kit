# 11-自举验证方案（Bootstrap Verification Scheme）

> 子领域：自举验证方案。团队 kernel-plan 调研员（k-bootstr）产出。
> 目标：为「mcc + meuos-libc 在自研 MeuOS 内核上自举」设计可验证的目标、里程碑、策略与验收标准。
> 定位：本文件只做调研与设计，不改动任何其他文件、不运行 git。

---

## 1. 概述与目标

### 1.1 什么是「自举闭环」

MeuOS 的「自举闭环」（bootstrap closure）指：**MeuOS 自身及其工具链都可以在 MeuOS 上被重新构建出来**。具体到本子领域，就是要证明：

1. **内核自身**能在 MeuOS 上用 MeuOS 工具链重新编译（内核可由自己产出的编译器重建）；
2. **工具链自举**：`mcc`（及 `mt/as`、`mt/ld`、`meow`）能在 MeuOS 上重新编译 `mcc` / `meuos-libc` / `meow` 自身，且产物与宿主构建版行为等价；
3. **运行验证**：上述重建在真实的 MeuOS 执行环境（而非宿主或代理环境）中跑通。

这区别于当前 Kit 层已有的「宿主侧自举」：`bootstrap.sh` 的 Phase 1–5 在宿主上用宿主 `gcc`/`tcc` 或 `mcc` 自身完成工具链诞生与自重编译（`check-sysroot-static`），并通过 `env/bin/qvm` 在 QEMU 内用 **Alpine/linux-virt 6.6.142 内核**运行静态二进制做跨架构验收。该路径验证了「工具链能在真实内核上跑」，但没有验证「工具链能在 **MeuOS 内核** 上跑、且 MeuOS 内核本身可重建」——这正是本方案要补齐的缺口。

根据 `projects/meuos-kernel/README.md` 的路线，内核工程路线为：**技术选型 → 原型（内存+调度+IPC+Linux syscall 兼容层 mkit 子集）→ 验证（mcc+meuos-libc 在自研内核自举）**。本文件对应最后一环「验证」。

### 1.2 验证目标（三级）

| 级别 | 名称 | 含义 | 闭环意义 |
|------|------|------|----------|
| L0 | 静态二进制可运行 | 一个 `libc-meuos` 静态链接 ELF 在 MeuOS 上正常退出 | 内核/进程/内存/驱动最小可用 |
| L1 | mcc 可编译 | 宿主构建的 `mcc` 在 MeuOS 上能编译并运行一个 C 程序 | Linux ABI 兼容层对接成功 |
| L2 | 完整自举闭环 | MeuOS 内的 `mcc` 能重建 `mcc`/`meuos-libc`/`meow`，且内核本身可由该工具链重建 | 自举闭环达成 |

### 1.3 非目标

- 不在此定义内核内部子系统实现（见 03/04/05/06/07/08/09/10）。
- 不要求 bit 级一致（功能等价即可，与 `AGENTS.md` §3.2 Phase 4「比较两次产物的行为一致性（功能等价即可，不要求 bit 级相同）」一致）。
- QEMU 本身的 MeuOS 化重建（见 `env/QEMU_BOOTSTRAP.md` Phase 6）属于独立任务，不阻塞本方案，但可作为 L2 之上的延伸验收。

## 2. 设计约束与上下文

### 2.1 技术基线（来自 README 与 AGENTS.md）

- **混合内核**，Rust + C 混合实现；内核关键组件用 Rust。
- **外部兼容 Linux ABI**：经兼容层（mkit 子集）对接已有生态二进制；mcc 产物是标准 ELF/Linux-ABI，因此验证时重点在 syscall 兼容层而非重造二进制格式。
- **统一文件系统层**（设计方向 ①）：内置校验和/压缩/加密 + **原子 `.msys` sysroot 更新** + 统一资源命名空间。这是 `.msys` 成为可启动/可自举媒介的根基。
- **spawn 模型进程管理**（设计方向 ②）：内建监督、资源账本 Day 1、简化信号。
- **capability-based 安全**（设计方向 ③）：Day 1 唯一模型、pledge/unveil 沙箱、最小 TCB。

### 2.2 现有可复用资产（真实存在，禁止编造）

| 资产 | 路径/来源 | 与自举验证的关系 |
|------|-----------|------------------|
| `bootstrap.sh` Phase 0–5 | 仓库根 `bootstrap.sh` | 现有宿主侧自举与自重编译门禁；新内核验证阶段应与之衔接 |
| `check-sysroot-static` | `mcc` Makefile | 已有的「mcc 用 `libc-meuos.a` 自重编译并跑 hello」门禁（L2 的宿主侧等价物） |
| `env/bin/qvm` | `env/bin/qvm` | QEMU 多架构 VM 管理器（boot/console/stop/run/status），按 `QEMU_PREFIX/bin/qemu-system-<arch>` 解析；可直接复用承载 MeuOS 内核 |
| `env/bin/build-initramfs.sh` | `env/bin/build-initramfs.sh` | 用 Alpine minirootfs + 9p 模块组装 initramfs 的范式，可改造为打包 MeuOS rootfs |
| `env/README.md`、`env/QEMU_BOOTSTRAP.md` | `env/` | QEMU TCG-only、headless、`+9p` 的测试环境设计与「自建 qemu」里程碑 |
| `meuos-sysroot`（`.msys`） | `projects/meuos-sysroot/ARCHITECTURE.md` | v2 单文件 sysroot：SHA-256 校验、去重、ed25519 签名、Overlay、压缩；mcc/mt 原生读取 |
| 9p virtio 共享 | `qvm` 的 `-virtfs ... mount_tag=hostshare`，guest 挂 `/mnt/host` | 宿主⇄guest 文件传输通道，用于把待测二进制/源码送入 VM |
| 跨架构内核夹具 | `env/kernels/<arch>/vmlinuz` + `config`（Alpine linux-virt 6.6.142） | 当前过渡内核；MeuOS 内核就位前用于并行 ABI 验证 |

### 2.3 关键约束

- **禁止 glibc 专有符号/LLVM/GCC 代码**（`AGENTS.md` §4）：验证介质与运行环境必须保持「零 GNU / 零 LLVM / 零 glibc 依赖」的同构性，否则闭环证伪。
- **Kit 自身构建系统禁用 autotools/cmake/meson**（`AGENTS.md` §4）：验证脚本与镜像打包须用 Makefile/shell，与现有 `bootstrap.sh` 一致。
- **可重复、可自动化、可回退**：须能作为 `bootstrap.sh` 的一个可跳过阶段（`MEUOS_SKIP_*` 范式）接入，失败时回退到现有 Alpine 代理门禁。

## 3. 业界 / 项目内方案对比（≥3，取舍表）

围绕「如何在 MeuOS 上验证 mcc+meuos-libc 自举」，列出四种候选验证策略并取舍。

### 3.1 候选方案

**方案 A — QEMU 全 VM + 自研 MeuOS 内核（真实闭环）**
以自研 MeuOS 内核（multiboot/设备树加载）+ 一个最小用户空间在 QEMU（`qvm` 复用）内启动，在 VM 内完整运行「mcc 重建 mcc/libc/meow」链。rootfs 采用 `.msys`（见 §4）。

**方案 B — QEMU user-mode（qemu-user-static）跑静态二进制（ABI 级）**
用 `env/qemu/qemu-<arch>-static` 在宿主直接运行交叉架构的 `libc-meuos` 静态 ELF，验证 ABI/代码生成正确性，无需内核与启动流程。当前 `env/README.md` 已用此法做 6/6、3/3 测试。

**方案 C — 容器 / Alpine 代理用户空间（当前历史 Phase 4 做法）**
在 Alpine/musl 最小用户空间（或容器）中跑 `mcc` 自重编译与 libc 回归，`bootstrap.sh` 进度报告模板即描述「MeuOS Next 尚不可启动时，Alpine/musl 最小用户空间作为自举代理环境」。验证工具链但**不验证 MeuOS 内核**。

**方案 D — 真实硬件 / 裸金属（PC 或 virt 开发板）**
在物理机或开发板上启动 MeuOS 内核并跑自举链。最真实，但迭代慢、可观测性差、CI 难集成。

### 3.2 取舍表

| 维度 | A. QEMU+自研内核 | B. qemu-user 静态 | C. Alpine 代理 | D. 真实硬件 |
|------|------------------|-------------------|----------------|-------------|
| 是否真验 MeuOS 内核 | ✅ 是 | ❌ 否（仅 ABI） | ❌ 否 | ✅ 是 |
| 是否验 Linux ABI 兼容层 | ✅ 是 | ✅ 是（仅用户态 ABI） | ✅ 是（musl 代理） | ✅ 是 |
| 自举闭环完整度 | ✅ 完整（L0–L2） | ⚠️ 仅 L1 前置 | ⚠️ 仅工具链（L1 等价） | ✅ 完整 |
| 复用现有 env 资产 | ✅ 高（`qvm`/9p） | ✅ 高（已有） | ✅ 高（已有范式） | ❌ 低 |
| 迭代速度 / CI 友好 | 中（需先有内核） | ✅ 极快 | ✅ 快 | ❌ 慢 |
| 工作量 | 高（需内核+驱动+兼容层） | 低 | 低（已有） | 高（板级） |
| 可观测性 / 调试 | 中（串口+9p） | ✅ 宿主直接调试 | ✅ 宿主直接 | ❌ 受限 |
| 风险 | 中（依赖 03/04/05/08/09/10） | 低 | 低 | 高 |
| 能否证明「内核可重建」 | ✅ 能 | ❌ 不能 | ❌ 不能 | ✅ 能 |

### 3.3 结论性取舍

- **真实闭环只能由 A 或 D 提供**；D 不适合作为主验证手段（迭代/CI 成本过高）。
- **B 与 C 是廉价的前置与回退**：B 在「内核尚未可启动」阶段即可并行验证工具链跨架构 ABI；C 作为历史门禁保留为回退。
- 因此推荐 **A 为主、B 并行、C 回退** 的组合（见 §4）。

## 4. MeuOS 选型建议

### 4.1 主路线：QEMU + 自研内核 + `.msys` rootfs（方案 A）

将 MeuOS 内核与 `.msys` 组合成可启动/可自举媒介，建议形态：

```
可启动媒介 = MeuOS 内核镜像 (multiboot/Image/zImage)
           + initramfs 内含 .msys rootfs（或 .msys 直接作为根文件系统）
```

**为什么 `.msys` 天然适合做自举媒介**（结合设计方向 ① 与 `meuos-sysroot/ARCHITECTURE.md`）：

1. `.msys` v2 已具备 **SHA-256 内容校验 + 去重 + ed25519 签名 + Overlay + 压缩**，**无需解压即可被 mcc/mt 原生读取**（mmap + 索引二分查找）。把 sysroot 打包为 `.msys` 后，内核的统一文件系统层只要内置 `libmsys` 读取能力，即可将 `.msys` 直接挂载为根——这正是设计方向 ①「原子 `.msys` sysroot 更新」的运行期落地。
2. **原子更新**：内核以 Overlay `.msys`（base + signed overlay）方式更新 sysroot，失败可回滚到 base——为「自举媒介可安全更新」提供机制。
3. **零解压启动**：未压缩条目零拷贝，减小 initramfs 体积与启动时间；压缩条目按需解压。

**`.msys` 成为可自举媒介的最小改造清单：**
- 内核 fs 层移植 `libmsys`（或等价 Rust 实现），提供 `.msys` 挂载与 `open/read` 语义（设计方向 ① 的天然延伸）。
- `mkmsys` 增加「含内核模块/设备树/启动配置」的打包模式（当前 `.msys` 定位是开发工具链 sysroot，非通用系统镜像——`ARCHITECTURE.md` 已明示此局限；需补「可启动镜像」打包目标）。
- 提供 MeuOS 版 `init`（对应 `build-initramfs.sh` 的 `/init`）：挂载 `.msys` rootfs、挂 9p（`/mnt/host`）、拉起 `mcc` 自举脚本。

### 4.2 阶段化里程碑（先静态 → 再 mcc → 再闭环）

| 里程碑 | 目标 | 验收（可验证） | 依赖子领域 |
|--------|------|----------------|-----------|
| **M0** | MeuOS 内核在 `qvm x86_64` 启动到用户态 init | 串口打印内核 banner + init 就绪提示 | 09 启动与初始化、10 驱动（串口）、03 内存 |
| **M1 (L0)** | `libc-meuos` 静态 hello 在 MeuOS 运行退出 0 | `hello` 返回 0；`env/bin/qvm run x86_64 /mnt/host/hello` | 03 内存、04 进程/调度（至少单进程 exec）、08 兼容层（exit/write）、10 驱动（串口） |
| **M2 (L1)** | 宿主构建的 `mcc` 在 MeuOS 编译并运行程序 | `mcc` 在 VM 内 `cc -o t t.c && ./t` 退出 0 | 04 进程（fork/exec/spawn）、08 兼容层（完整 syscall 子集）、mt/as+mt/ld 可在 MeuOS 运行 |
| **M3 (L2 工具链)** | MeuOS 内 `mcc` 重建 mcc/libc/meow | 见 §1.2 L2；stage-2 `mcc` 与宿主 golden 在固定测试集上输出一致 | 05 IPC（mcc/meow 并发/管道）、04 调度、全部前述 |
| **M4 (L2 内核)** | MeuOS 内核本身由 MeuOS 内工具链重建 | 在 VM 内用 mcc 重新编译内核源码并产出可启动镜像，新镜像可再次启动 | 03/04/05/08/09/10 全闭环、mt 工具链自举 |
| **M5 (跨架构)** | x86_64 + aarch64 双架构通过 M0–M4 | 两架构均满足 AC1–AC7（见 §6） | 09/10 多架构启动与驱动 |
| **M6 (原子更新)** | `.msys` 签名 Overlay 在 MeuOS 内原子更新并回滚 | 应用 signed overlay 成功；base 损坏可回滚 | 06 文件系统、07 安全（ed25519 验签） |

> 临时并行手段：在 M0 之前，用 **方案 B（qemu-user-static）** 持续跑 mcc 跨架构 ABI 回归（已有 6/6、3/3 基线），保证「内核就绪前工具链不被破坏」。

### 4.3 与现有 `bootstrap.sh` 自举流程的衔接

建议新增一个**可跳过的「内核自举门禁」阶段**（沿用 `MEUOS_SKIP_*` 范式与幂等风格），不破坏现有 Phase 0–5：

```
Phase 0–3 : 现有（宿主诞生 mcc → libc → meow）
Phase 4   : 现有（宿主侧 check-sysroot-static 自重编译门禁；保留为回退）
Phase 5   : 现有（LFS 包 bzip2/binutils 验证）
Phase K   : 【新增】内核自举闭环门禁（默认开启，可 MEUOS_SKIP_PHASEK=1 跳过）
   1. 构建 MeuOS 内核（需内核源码，本 kernel-plan 项目产出）
   2. make -C projects/meuos-sysroot msys  生成 rootfs .msys
   3. 组装可启动媒介（内核 + .msys initramfs），复用 env/bin 的打包范式
   4. env/bin/qvm boot x86_64（内核路径指向 MeuOS 镜像，而非 Alpine vmlinuz）
   5. 在 VM 内运行 M1–M4 自举脚本，产出 stage-2 工具链
   6. 比对 stage-1（宿主 golden）与 stage-2 行为一致性
   7. 失败回退：MEUOS_SKIP_PHASEK=1 走现有 Phase 4 代理门禁
```

要点：
- **复用 `qvm`**：`qvm` 按 `QEMU_PREFIX/bin/qemu-system-<arch>` 解析二进制，只要把 MeuOS 内核路径与 initramfs 参数化（当前 `qvm` 内核路径硬编码 `env/kernels/<arch>/vmlinuz`），即可零改造复用其 boot/console/run/9p 通道。建议为 `qvm` 增加 `--kernel`/`--initrd` 覆盖参数（属 env 项目，不在本文件改动范围）。
- **复用 9p 共享**：宿主用 mcc 构建/下载源码放入 `env/share/`，VM 内从 `/mnt/host` 取用，与当前 `env/README.md` 工作流一致。
- **golden 比对**：以宿主 `check-sysroot-static` 产物为 golden，VM 内 stage-2 产物在固定测试集（如 mcc 的 `check-c11`/`check-targets`、libc 的原子/线程/TLS 回归）上比对输出，功能等价即通过。

### 4.4 依赖关系（须先完成哪些子领域）

```
自举验证 (本方案)
 ├─ 09 启动与初始化 : multiboot/设备树加载、早期串口控制台、init 拉起
 ├─ 10 设备驱动模型 : 至少 串口(NS16550/virtio-console) + virtio-blk 或 9p(virtio-9p) + 时钟
 ├─ 03 内存管理     : 物理/虚拟内存、用户态映射、栈/堆、mmap
 ├─ 04 进程与调度   : spawn/exec、地址空间、调度、基础信号
 ├─ 08 Linux 兼容层 : mcc 产物所需的 syscall 子集（read/write/open/close/mmap/
 │                   fork/execve/exit/stat/getdents64/socket 等，参见 bootstrap.sh 报告）
 ├─ 05 IPC 机制     : mcc/meow 并发、管道、用于构建并发 (-jN)
 ├─ 06 文件系统     : .msys 挂载为 rootfs、Overlay/原子更新
 ├─ 07 安全模型     : capability 启动、ed25519 验签（M6）
 └─ mt 工具链自举   : mt/as、mt/ld 必须能在 MeuOS 运行（否则 mcc 仍需宿主 as/ld）
```

**最小可启动依赖（M0–M1）**：09 + 10(串口) + 03 + 04(单进程 exec) + 08(exit/write)。
**完整闭环依赖（M2–M4）**：叠加 05 + mt 工具链自举 + 06(.msys rootfs)。

## 5. 开放议题

1. **`.msys` 作为通用可启动镜像的边界**：当前 `.msys` 明确定位为「开发工具链 sysroot，不是通用系统镜像格式」（`ARCHITECTURE.md` 局限性一节）。是否扩展 `.msys` 承载内核/设备树/启动配置，还是另建一层「MeuOS 可启动镜像（.mimg）」包装 `.msys`？需 06/09 子领域协同决策。
2. **mt/as、mt/ld 在 MeuOS 的自举**：L2 要求编译器/汇编器/链接器全部在 MeuOS 内运行。mt 工具链当前是否在 MeuOS 上验证过？若 mt 仍依赖宿主某些能力，则 M2–M4 会被阻塞，需提前排期。
3. **内核自身重建的交叉 vs 原生**：M4「内核由 MeuOS 内工具链重建」是否要求**原生**（在 MeuOS 内编译 MeuOS）还是允许**交叉**（宿主 mcc 交叉编译内核、仅用户态工具链在 MeuOS 内自举）？前者闭环更强但风险更高，建议 M4 先支持交叉重建、再攻原生。
4. **多架构优先级**：现有 env 资产覆盖 x86_64/i386/aarch64（riscv64/loongarch64 待实现）。M5 双架构建议 x86_64 + aarch64；loongarch64 因无 Alpine 端口、需自定义 init（`env/.todo/loongarch64.md`），优先级后移。
5. **验证确定性 / 可重现性**：跨架构代码生成（尤其 i386 变参、aarch64/AAPCS、RISC-V calling convention）是否会导致 stage-1/stage-2 输出非确定？需明确「功能等价」的判定金标准（测试集 + 输出白名单）。
6. **性能与资源**：MeuOS VM 当前 `qvm` 默认 `-m 256M`。mcc 自举（尤其编译 mcc 自身 + libc）内存峰值是否够？可能需要调整 M 参数或分段编译。
7. **安全模型对自举的影响**：capability Day 1 唯一模型下，mcc/meow 进行编译需要哪些 capability？pledge/unveil 是否会在自举脚本中过早收紧导致失败？需 07 子领域给出「构建型进程」的最小 capability 集合。

- `bootstrap.sh`（仓库根）—— Phase 0–5 全流程自举脚本，含 `check-sysroot-static` 自重编译门禁与进度报告模板中「Alpine/musl 代理环境」描述。
- `AGENTS.md` §3「自举流程」、§4「禁止事项」—— 组件构建依赖、Phase 0–7 阶段定义、零 GNU/LLVM/glibc 约束。
- `projects/meuos-kernel/README.md` —— 内核定位（兼容 Linux ABI、三大设计方向）、路线「验证：mcc+meuos-libc 在自研内核自举」。
- `projects/meuos-sysroot/ARCHITECTURE.md` —— `.msys` v2 格式、SHA-256/去重/ed25519/Overlay/压缩、当前「非通用系统镜像」局限。
- `env/README.md` —— QEMU 测试环境设计、qemu-user 静态验证基线（6/6、3/3）、9p 共享机制。
- `env/QEMU_BOOTSTRAP.md` —— QEMU TCG-only/headless/+9p 测试环境、自建 qemu 里程碑、依赖审计（glib2/zlib）。
- `env/bin/qvm` —— VM 管理器（boot/console/stop/run/status），按 `QEMU_PREFIX/bin/qemu-system-<arch>` 解析。
- `env/bin/build-initramfs.sh` —— Alpine minirootfs + 9p 模块组装 initramfs 的范式（`/init` 脚本、cpio+gzip 打包）。
