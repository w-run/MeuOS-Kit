## 1. 定位：验证方法论，而非测试策略

`22` 回答的是「测什么、怎么分层、CI 怎么分级」——那是**策略层（how-to）**。本文回答的是更前置的一问：**内核应该如何在「开发期」就被证明正确，而不只是「写完后跑测试」？** 这是**方法论层（why & first-principle）**。

二者关系如「宪法与行政法」：`41` 定「验证必须是设计的第一性约束」这一根本原则；`22` 是依此原则落地的具体门禁与矩阵。`22` 是本文的下游消费者，本文不重复其门禁分级细节。

### 1.1 解构型起点：把验证嵌进设计，而非挂在设计之外

> 核心命题：**一个接口在「被设计」的那一刻，就必须同时定义「如何证明它对」**。验证不是开发完成后的质检环节，而是接口契约的一部分。

传统内核开发（含 Linux）的隐含顺序是「先实现、后补测试、偶尔跑 fuzz」——验证是**外挂**的。MeuOS 因三条硬约束，**外挂式验证不可行**，必须把验证做成**内建**：

1. **capability 是 Day 1 唯一模型、无 root 逃生舱**（`07` §1）。安全属性（越权必失败、revoke 后派生不可用）无法靠「跑一遍看没崩」证明，必须在设计接口时就定义可判定断言（否则连「测对了」都无基准）。
2. **Rust 关键组件入 TCB、最小 TCB**（`02` §4、`00` A3）。Rust 类型系统是「编译期验证」——这是方法论优势：把整类漏洞的验证前置到编译期，而非留给运行期测试。
3. **无 Linux 式海量回归基线**（`11` §2.3）。不能假设「有个 baseline 然后比偏差」，必须从第一个可累积断言（绿光）起步，逐步建信心（`22` §5）——这要求方法论上「每条设计决策都自带可证伪的断言」。

### 1.2 方法论四原则（全文脊梁）

1. **契约优先（contract-first）**：设计接口时先写「它必须满足什么不变量、违反时如何 fail-closed」，再写实现。不变量即未来断言。
2. **验证分层叠加在设计层**：单元（编译期类型）→ 集成（用户态协议契约）→ 系统（自举绿光）→ 形式化（seL4 式证明），每层对应一类「可在哪一级证明正确」的设计约束。
3. **否定式为安全 Oracle**：capability 模型下，安全断言的默认方向是**否定式**——尝试越权必须 `EPERM`/终止/句柄不可用，而非「授予后能用」（`22` §1.1 约束 2）。
4. **文档即规格、规划即断言**：本规划 `01`–`38`（含 `00` 的 A1–A12 一致性矩阵、C1–C14 冲突裁决）本身就是可执行规格——它们的断言应被反转成验证用例（§7 专论）。

### 1.3 与 `22` 的边界（避免重复与越权）

| 维度 | 本文 `41`（方法论） | `22`（执行策略） |
|---|---|---|
| 关心 | 为什么验证必须是设计原语、有哪些第一性原则 | 测什么、分层、CI 分级、fuzz 切入点 |
| 产出 | 设计约束、契约清单、独特命题（capability 约束 fuzzer） | 五层金字塔、G0–G4 门禁、五架构矩阵 |
| 不覆盖 | 不重复门禁分级/矩阵成本 | 不上升到「验证为什么是设计第一性」 |

## 2. 多系统参照对比（六系对照，取其思想不缝合）

围绕「验证如何嵌入设计 / CI 何时介入 / 无基线如何建信心 / fuzz 与权限模型关系」，对照六类参照系。

### 2.1 候选系统概览

| 系统 | 验证方法论核心思想 | 与 MeuOS 的取舍 |
|---|---|---|
| **Google 测试之道**（Software Engineering at Google） | 测试是开发的一部分；小/中/大测试（small/medium/large）按依赖与速度分层；**测试占比**（代码审查强制测试随改）、flake 视为 bug、测试易写性优先 | **主参考（方法论）**：契约优先、测试随改、否定式/结构化断言思想 |
| **Linux kselftest / KUnit + syzkaller** | kunit 内核内单测（`#[test]` 式）、kselftest 用户态 syscall/API 回归；syzkaller 以 syscall 描述为语料做**无特权约束的系统调用模糊（常root/CAP_* 跑、触达全 syscall 面）** | 取分层（kunit/kselftest）；**弃** syzkaller「无 capability 约束、全 syscall 触达」模型，改用本文 §6 的 capability 约束 fuzzing |
| **Windows HLK**（Hardware Lab Kit） | 驱动/硬件兼容性**签名强制测试关卡**：设备须过 WHCK 矩阵才获签名；Driver Verifier 运行期 invariant 检查 | 取「关键组件（驱动）须过强制验证关卡」思想（呼应 `10` 驱动模型）；映射到 MeuOS 的 devmgr 准入测试 |
| **Fuchsia** 广泛自动化测试 + **确定性构建** | 组件单测/集成/系统三层全进 CI；**hermetic / 确定性构建**（同一输入恒等输出）；fuzzer 进 CI；结构化断言（inspect/trace 可测） | **主参考**：确定性构建 + 三层自动化 + capability 受控测试（与 `12` inspect 同构）；本文 §5 取确定性构建思想 |
| **seL4** 形式化验证 | **证明即回归**：精化证明与代码同步，证明失败=CI 红；8700 行 C 证明功能正确性+信息流安全 | 取「证明即回归」思想，交 `20` 形式化；本文 §3 把形式化列为验证分层的最高层 |
| **ChromeOS** 验证流水线 | 多层验证流水线：Tast/Autotest 系统测试、firmware 验证、OTA 升级验证、verified boot 签名链、canary/stable 通道渐进 | 取「端到端流水线 + 签名链 + 渐进通道」思想（呼应 `.msys` 原子更新 `06`/`11`）；用于本文 §8 演进的 release 通道验证 |

### 2.2 关键取舍结论

1. **方法论主取 Google 测试之道 + Fuchsia**：前者给「测试随改、易写优先、flake 即 bug」的工程纪律；后者给「确定性构建 + 三层自动化 + 结构化断言」的可验证底座。二者共同支撑 MeuOS「验证内建」原则。
2. **形式化取 seL4（交 `20`）**：capability 不变量（rights 不可伪造、revoke 传播完整）应由 `20` 精化证明持续回归；本文负责经验性/运行时证明，互补不重叠（`22` §4.2 同结论）。
3. **fuzz 必须改造 syzkaller 模型**：Linux 的 syzkaller 以 root/CAP_* 无差别触达全 syscall 面——这**违背** MeuOS 的 capability 模型。本文 §6 提出 **capability-aware fuzzing**：fuzzer 本身是被 capability 约束的 actor，攻击面 = 它持有的句柄集。这是对 `22` §4.1 的**方法论升华**，而非重复。
4. **硬件/驱动强制关卡取 HLK 思想**：用户态驱动（`10`）须过「准入测试关卡」方能加载，映射 HLK 的签名强制测试。
5. **release 通道验证取 ChromeOS**：`.msys` 原子更新（`06`/`11`）的验证不只「能启动」，还须 OTA/回滚通道的端到端验证（§8）。

## 3. 分层测试策略（设计期即分层，非运行期才分）

`22` §3 给出了 L0–L4 执行分层。本节的独特贡献是：**分层不只在「运行期怎么跑」存在，更在「设计期怎么写」存在**——每一层对应一类「可在哪一级被证明正确」的设计约束。

### 3.1 设计期分层（contract-first 落地）

| 层 | 设计期约束（方法论） | 证明「正确」发生在哪一级 | 对应 `22` 执行层 |
|---|---|---|---|
| **L0 编译期** | Rust 类型即规格：`rights` 位图运算、`cap_move`/`cap_copy` 所有权语义由类型强制；`#![forbid(unsafe_op_in_unsafe_fn)]`（`02` §4.4） | **编译期**——整类 UAF/溢出/悬垂被类型系统证明不可发生 | L0 用户态 harness 单测 |
| **L1 单元契约** | 内核对象（cap/IPC/调度/VFS/Job）的状态机在写实现前先写不变量（如「父 revoke → 派生句柄不可用」） | 单元单测断言状态机不变量 | L0/L1 |
| **L2 协议契约** | IPC 四原语（`05`/`00` A8）、事件流 schema（`12` §4.4）先定义**自描述 schema**，生产者/消费者共用 | schema 一致性断言（防漂移，Fuchsia FIDL 反射式自测思想） | L1 |
| **L3 集成契约** | FS+VMO/pager+命名空间（`06`）、supervisor+Job+exception channel（`04`）以「端到端行为契约」定义，消费 inspect 树做确定性断言 | 集成 harness 断言 inspect 子树值，不 grep 日志 | L2 |
| **L4 系统契约** | 自举绿光（`11` M0–M4）= 最高级系统契约：MM/进程/IPC/兼容层/FS 整体正确 | L3 绿光闭环 + 黄金比对 | L3 |
| **L5 形式化契约**（交 `20`） | capability 不可伪造、revoke 完整性的数学不变量，先于实现定义 | seL4 式精化证明，证明失败=CI 红 | `20` 门禁 |

**方法论要点**：L0–L5 不是「测试金字塔」，而是「**证明可信度逐层累积的 Spectrum**」——越底层越确定（编译期）、越顶层越综合（系统级）。设计者写每个模块时，先决定它该落在哪层被证明，再写实现。

### 3.2 内核自测框架的方法论选择

`22` §8 待决 4 悬而未决「内核内 kunit 式 `#[cfg(test)]` vs 用户态 harness」。本文给出方法论裁定：

- **优先用户态 harness（链接 `core`/`alloc` + mock 底层）**：TCB 组件（cap/IPC/调度/VFS）是纯 Rust、类型驱动、与架构无关，**脱离内核态即可测**——快、可调试、可并行，符合 Google 测试之道「测试易写性优先」。
- **内核内自测仅用于「必须触碰内核态不变量」者**：页表类型化封装（`02` §4.2）、上下文切换 asm、bootinfo 解析（`09` §6-9）等无法用户态 mock 的部分，用 `#[cfg(test)]` + 自定义 test runner（kunit 思想）。
- **裁定原则**：能用户态测的绝不进内核态测——这是对 `22` §8 待决 4 的方法论回答，与 `00` A3「最小 TCB、尽快交权」同源。

### 3.3 与统一文件系统层（01 方向①）/ spawn（04）的集成测试

方法论上，这两类集成测试是「**跨三个互锁维度的一致性格言**」的可执行化（`00` A1–A6 互锁矩阵）：

- **FS + VMO/pager + 每进程命名空间集成**：断言「`unveil(path,perm)` 本质 = 向命名空间注入路径 capability 绑定」（`07` §4.3/第三轮回写 C3）；未 reveal 路径必失败；CoW 命名空间模板随 spawn 复制（`07` C3 回写）。这是把 `00` A4/A6 互锁变成确定性断言。
- **spawn + supervisor + Job + exception channel 集成**：断言「子进程持最小句柄集 + 资源账本随 spawn 声明」（`00` A5）、「致命异常经 exception channel 上报 supervisor 按策略重启/终止」（`00` A9）。把 `00` A5/A9 互锁变成端到端行为契约。
- **方法论价值**：集成测试不是「测功能」，而是「**验证三个维度确实互锁而非叠加**」——这是 MeuOS 相对 Linux 五套机制堆叠的根本差异点，必须用集成测试固化。

## 4. 模糊测试（syscall fuzzing 的方法论定位）

`22` §4.1 已列 fuzz 切入点（mkit 翻译面、cap revoke、FS extent、IPC 边界、bootinfo）。本文在方法论上补充三点：

### 4.1 fuzz 是「非 TCB 面」的经验性兜底

TCB 靠编译期类型 + 单测建信心（`02` §4.4）；**fuzz 专攻「无法编译期强制」的非 TCB 面**（`02` §5-3）：mkit C 兼容层、FS extent 解析、bootinfo 解析。这是 methodology 上的「分层信任」——不浪费 fuzz 在已被类型证明的 TCB 上，集中火力于经验性攻击面。

### 4.2 否定式 Oracle 与结构化 CrashReport

- fuzz 的**安全 Oracle 是否定式**：越权尝试必须 `EPERM`/进程终止/句柄不可用（`22` §4.2），而非「fuzz 出来没崩就算过」。
- fuzz 触发的崩溃经 `12` 的 **CrashReport 结构化落盘**（`.msys` 卷、SHA-256/加密、`12` §4.7），fuzz 收敛报告消费结构化队列，**不 grep 串口文本**——与 `22` §5.3「结构化断言抵消无基线劣势」同构。

### 4.3 fuzz 发现的 bug 须回流为不变量（与 `20` 联动）

fuzz 暴露的「revoke 泄漏」「confused deputy」类 bug，须同时沉淀为：(a) `22` 的回归用例；(b) `20` 形式化需覆盖的不变量（rights 不可伪造、revoke 完整）。fuzz 不是终点，是**不变量发现器**——这是方法论上 fuzz 与形式化的闭环（`22` §8 待决 5 的回答）。

## 5. CI 矩阵（跨五架构的方法论：确定性构建 + 成本不对称）

`22` §6 给出五架构分群（主架构全量 / 辅架构编译+冒烟 / i386 纯 C）。本文补充方法论层两条：

### 5.1 确定性构建（Fuchsia hermetic 思想）是 CI 的地基

MeuOS 应要求**确定性/可重现构建**（Fuchsia hermetic builds 思想，`fuchsia.dev` 构建系统文档）：同一源码 + 同一 toolchain → 同一二进制，无时间戳/路径/排序噪声。这直接支撑：

- **跨架构功能等价金标准**（`11` §5-5）：stage-1（宿主 golden）vs stage-2（MeuOS 内）在固定测试集上行为等价——确定性构建让「等价」可重复验证，而非偶发通过。
- **fuzz 复现**：崩溃可确定性重放（崩溃输入 + 确定性构建 = 必现），flake 率趋零（呼应 Google 测试之道「flake 即 bug」）。

### 5.2 成本不对称的方法论裁定

- **不在 per-PR 跑全架构 QEMU**：仅主架构 G3 自举（贵但必要）+ 全架构 G2 编译（便宜）；辅架构 QEMU 留 nightly（`22` §3.2）。方法论依据：CI 反馈延迟 > 信心增益时，分层降级。
- **i386 纯 C 的 TCB 测试降级**：i386 无 Rust TCB（`02` 约束 C2），其 cap/IPC/调度/VFS 以 C 实现，失去编译期不变量——方法论上接受「C 等价单测 + 加强 fuzz」补偿，并在 `22` §8 待决 1 标注为架构裁决项。

## 6. 与 capability 协同：fuzzer 是否被 capability 约束（MeuOS 独特命题）

> 本节的命题是**本文相对 `22` 的最大原创贡献**：在 MeuOS，fuzzer 不是「以 root 触达全 syscall」的 syzkaller 式外挂，而是**运行在 capability 模型之内、被 capability 精确约束的 actor**。

### 6.1 命题：攻击面 = 持有的句柄集

在 MeuOS，所有 syscall 入口都经由「持有对应 capability 句柄的进程」（`07` §4.1）。fuzzer 作为用户态服务，**必须持有句柄才能调用 syscall**。因此：

- fuzzer 能探索的 syscall 面 **= 它被显式授予的句柄集**（rights 组合），而非全 syscall 表。
- 这是 capability 模型对模糊测试的**结构性增益**：攻击面被 capability 天然界定、可审计、可随场景收缩/扩张——比 syzkaller「root/CAP_* 无差别触达全 syscall」精确一个数量级。

### 6.2 capability-aware fuzzing：把句柄集作为 fuzz 语料维度

提出 **capability-aware fuzzer** 形态（方法论设计，非实现）：

1. **给定 spawn 时的一组句柄（rights 组合）**，fuzzer 自动枚举该 capability 投影下的 syscall 参数空间——而非盲目枚举全 syscall 号。
2. **越权尝试天然被 fail-closed 拒回**，fuzzer 以「拒绝即正确」作为 Oracle（`07` §4.2）：凡触及未持 right 的对象，必须 `EPERM`/终止，否则即 bug。
3. **revoke 中 fuzz**：在 fuzz 过程中动态 `close`/`revoke` 句柄，验证派生链回收后全部不可用（`07` §4.5、§5-4）——把 `22` §4.1 的「cap revoke 传播」fuzz 提升为「capability 生命周期 fuzz」。

### 6.3 反向命题：能否赋予 fuzzer「全句柄」做穷举？

可以，但**必须是显式、可审计、受 Job 账本约束的授权**，绝非隐式 root：

- 设计「capability 枚举器」——持有各类 rights 的合成句柄的服务，作为**被 capability 授予的特权测试 actor**。
- 其权限授予记入审计 schema（`07` §5-6）、可随时 revoke、计入 Job 资源账本（`00` A5）。
- **永不默认**：与 `DBG_POKE`/`KERNEL_PRIV` 同构（`07` 第三轮/第四轮回写）——fuzzer 的「全句柄」是显式授予，不是 `CAP_SYS_ADMIN` 式大权。这把 syzkaller 的「root 跑 fuzz」范式，改写为「capability 显式授权、全程可审计的测试 actor」。

### 6.4 与 `07` 的互锁闭环

fuzzer（无论受限还是全句柄）触发的 confused deputy / revoke 泄漏 / pledge 越界 bug，沉淀为 `07` 的不变量回归（`22` §4.2 安全属性表）+ `20` 形式化覆盖项。capability 模型既是「被测试对象」，又是「约束测试者（fuzzer）的边界」——**测试者与被测试者同源受 capability 约束**，这是 MeuOS 独有的方法论闭环。

## 7. 与文档驱动开发（本规划自身）的协同

> 本规划 `01`–`38`（含 `00` A1–A12、C1–C14）**本身就是可执行规格**——它们的断言应被反转成验证用例。这是「文档驱动开发 × 验证」的闭环，也是本文相对 `22` 的独有视角。

### 7.1 规划文档即断言源

| 规划断言（来自本规划） | 反转成的验证用例 |
|---|---|
| `00` A1–A12 跨域一致性矩阵（如 A1「handle=capability」、A4「每进程 namespace 默认全不可见」） | 一致性回归：任一子领域实现违反矩阵项即 CI 红 |
| `00` C1–C14 冲突裁决（如 C2「密钥=cap」、C4「默认不绕过沙箱」） | 裁决闭环断言：C4 → 兼容层默认不绕过 pledge；C2 → FS mint 不越权 |
| `07` §4.2 pledge/unveil 只能收缩、越界即终止 | 否定式安全断言（§1.2 原则 3） |
| `00` A5 Job 账本同源、A9 exception channel → supervisor | 集成契约断言（§3.3） |
| `11` M0–M4 绿光 + 黄金比对 | 系统级绿光断言（§8 Day1） |

### 7.2 方法论价值：spec 漂移 = 测试失败

传统项目「需求文档」与「测试」是两套平行物，文档改了测试不知道。MeuOS 因**规划即规格**，文档（本规划）的每次修订式追加（`00` §6 纪律）都携带新断言；验证框架消费这些断言，文档漂移即被测试捕获。这是 Google 测试之道「spec 与 test 同源」的极致形态。

### 7.3 与「修订式追加不删」纪律互锁

本规划铁律「修订式追加不删」（`00` §6）与验证协同：旧断言**永不删除**（只追加新断言），保证回归基线只增不减——与 `22` §5.2「边际累积策略」同源：信心是加出来的，不是重置的。

## 8. Day1 最小验证集

Day1（原型期，M0–M4 解锁前）验证集须**最小但自证**，对应 `11` 绿光 + `22` G0–G1。方法论上，Day1 验证集回答「在没有完整测试体系时，什么能证明内核『基本正确』」。

### 8.1 Day1 必含断言（最小可证伪集）

1. **capability 监视器单测（L0）**：`rights` 位图运算、`cap_move`/`cap_copy` 所有权语义、`revoke` 拒绝越权——编译期类型 + 用户态 harness（`§3.2`）。
2. **一个否定式安全断言（L0/L2）**：持最小句柄集的进程尝试越权必须 `EPERM`/终止（`§1.2` 原则 3、`07` §4.2）。
3. **spawn + Job 账本最小集成（L2）**：子进程持最小句柄集、资源账本随 spawn 声明（`00` A5）。
4. **L3 自举绿光（系统契约）**：mcc + meuos-libc 在自研内核自举成功 = 第一束绿光（`11` M0–M4、`22` §5.1）。这是比任何单测都强的系统级断言。
5. **G0 门禁常驻**：Rust `cargo test` + `cargo clippy`（`#![deny(clippy::all)]`）+ `unsafe` 行数/块数门禁（`02` §4.4/§5-6）+ `11` 方案 B qemu-user-static ABI 回归（内核就绪前最便宜的信心源，`22` §3.2/§5.4）。

### 8.2 Day1 不追求

- 不追求全架构 QEMU（`22` §6：仅主架构 x86_64 G3）。
- 不追求形式化证明（`20` 长期，Day1 仅预留接口）。
- 不追求长时 fuzz（G4 常态化期才进）。

## 9. 演进：从「验证外挂」到「验证内建」

方法论演进路径，与 `22` §7 P0–P5 阶段对齐但升维到「验证文化」：

| 阶段 | 验证成熟度（方法论视角） | 标志 |
|---|---|---|
| **P0 原型前** | 验证外挂 → 契约优先起步 | L0 harness 搭建、`11` 方案 B 常驻、规划即规格闭环（§7）生效 |
| **P1 M0–M1** | 编译期验证 + 首条否定式断言 | cap/IPC/调度单测 + spawn+exit 集成 + M0/M1 绿光 |
| **P2 M2–M3** | 协议契约（schema 自描述）+ capability-aware fuzz 起步 | L1 IPC schema 一致性、mkit fuzz（§4/§6） |
| **P3 M4** | 系统契约 + 确定性构建 + 五架构编译门禁 | L3 黄金比对、确定性构建（§5.1）、G2 全架构编译 |
| **P4 M5** | 五架构矩阵 + 跨架构等价金标准 | 主架构全量 + 辅架构冒烟（§5.2） |
| **P5 M6 + 常态化** | 验证内建文化成型：形式化回归（`20`）+ OTA 通道验证（ChromeOS 思想）+ fuzz 长时 | G4 release 通道、`.msys` 回滚验证（§2.2 结论 5） |

**终极形态**：验证不是「开发后的一道关卡」，而是「每个接口被设计时就自带的证明契约」——这正是 §1.1 解构型起点的闭环。
