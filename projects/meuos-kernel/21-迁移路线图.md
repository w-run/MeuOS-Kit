## 0. 一句话核心结论

> **Kit 与内核应当像「有机体的上下层」一样咬合：Kit 是内核的「母语编译器 + 母语 sysroot + 自举流水线」，内核是 Kit 产物的「运行期消费者 + 自举验证场」。迁移的本质，是把 Kit 当前「只产出 .msys 用户态 sysroot」的单通道，扩展为「同时产出内核镜像 + 运行时 .msys rootfs」的双通道，并以 `bootstrap.sh` 的 Phase K 把两者拼成可启动媒介。**

## 1. 「应该是什么样」推演 —— Kit 与内核的协同边界

> 大喵铁律第一条：先问「从 Kit 到内核的迁移/协同**应该是什么样**」——工具链与内核如何像一个有机体的上下层那样咬合，而非两个独立项目拼装。

### 1.1 现状拓扑（Kit 完成态）

Kit 层已交付一个**自洽的工具链闭环**：

```
mcc (C11, cproc+QBE 后端)  ──编译──▶  .o
meuos-libc (crt1/atomic/setjmp/tls/syscall gate) ──提供──▶  C 运行基座
mt/as, mt/ld (Kit 自带汇编/链接器)  ──链接──▶  静态 ELF
.meuos-sysroot (.msys v2: SHA-256/去重/ed25519/Overlay/压缩)  ──承载──▶  头文件+库
bootstrap.sh (Phase 0–5)  ──打包──▶  .msys rootfs + 宿主侧自重编译门禁
```

- mcc 跨 **x86_64 / aarch64 / riscv64 / i386 / loongarch64** 五架构 + arm 有完整代码生成（见 `mcc/TARGETS.md`，i386 为完整 target）。
- `.msys` v2 **零解压即可被 mcc / mt 原生读取**（mmap + 索引二分），且已具备签名、Overlay、压缩——天然可兼作「编译时 sysroot」与「运行期 rootfs」。

但**当前 Kit 不感知内核**：bootstrap.sh 用 Alpine/linux-virt 内核做跨架构验收，`.msys` 明确定位为「开发工具链 sysroot，不是通用系统镜像」（`meuos-sysroot/ARCHITECTURE.md` 局限性一节）。也就是说，Kit 目前只走到「用户态工具链自举」，尚未走到「把内核自身纳为产出物」。

### 1.2 应该态：三个咬合点

推演内核「应该」如何被 Kit 编译、被 sysroot 同时服务、被 bootstrap 拼成镜像：

#### 咬合点 A —— 编译边界：内核源码如何被 mcc / rustc 编译

内核是 **Rust + C 混合**（见 `01`/`02`）。「应该」的编译契约：

- **内核的 C 部分**（早期启动/asm 边界、mkit 兼容层）由 **mcc** 编译——这是 Kit 的母语路径，零 GNU/LLVM/glibc（`AGENTS.md` §4）。
- **内核的 Rust 部分**（capability 监视器、IPC、调度、VFS 抽象）由 **rustc + LLVM** 编译，走 `no_std` 裸机 target（`02` §2.3）。
- **最终合并**：两类 `.o` / `.rlib` 经**统一链接脚本**（内核自定义 linker script，freestanding）合并为单一内核镜像。`02` §4.3 已明确此 FFI 合并模型。
- **关键澄清（解构型）**：「自举」指**用户态 + libc 在自研内核上跑通**，**不要求内核自身由 mcc 单独编译**（`02` §2.2 约束 C1 已判定双工具链现实可接受）。因此 Kit 编译内核 = mcc 编译 C 部分 + rustc 编译 Rust 部分 + 链接器合并——Kit 是内核 C 部分的母语编译器，而非内核的全部编译器。

这就把 Kit 与内核的编译边界定义为**「mcc 是内核 C 子集的母语、rustc 是内核 Rust 子集的母语、链接器是汇合点」**，而非「Kit 单独编译整个内核」的误读。

#### 咬合点 B —— sysroot 双重身份：既服务「编译内核」又成为「内核运行时的 .msys」

`.msys` 在迁移后应同时扮演两个角色，且由**同一格式**承担：

| 角色 | 消费者 | 何时 | 内容 |
|------|--------|------|------|
| **编译时 sysroot** | mcc（头文件搜索）、mt/ld（库/对象读取） | 宿主/交叉编译内核时 | 内核 UAPI 头（mkit 兼容层 ABI 保真所需）、meuos-libc（hosted C 边界）、crt1/链接脚本样板 |
| **运行期 rootfs** | 内核 FS 服务的 `libmsys` 读取能力 | 内核启动后 | 用户态服务、mcc 自举脚本、工具链二进制（`11` §4.1） |

「应该」的状态：内核编译所需的头/库，与内核运行所需的 rootfs，来自**同一份 `.msys`**（或由 base `.msys` + 编译期 extend 派生）。这避免了「编译用一套 rootfs、运行用另一套镜像」的分裂，正是 Fuchsia/Redox「单一构建图」精神的取舍（见 §2）。

#### 咬合点 C —— bootstrap 边界：把 Kit 产物变成可启动内核镜像

`bootstrap.sh` 当前产出 `.msys`（用户态 sysroot）。「应该」扩展为：

```
Phase 0–5 : 现有（宿主诞生 mcc → libc → meow，check-sysroot-static 门禁）
Phase K    : 【新增】内核自举闭环门禁
   1. 取内核源码 → mcc 编译 C 部分 + rustc 编译 Rust 部分
   2. 统一链接脚本合并 → 内核镜像 (multiboot/Image/zImage)
   3. make -C projects/meuos-sysroot msys → 运行期 .msys rootfs
   4. 组装可启动媒介（内核 + .msys initramfs / 或 .msys 直作根）
   5. env/bin/qvm boot（--kernel/--initrd 覆盖）→ 在 VM 内跑 M0–M4
   6. golden 比对（宿主 stage-1 vs VM stage-2）
   7. 失败回退 MEUOS_SKIP_PHASEK=1 → 现有 Phase 4 代理门禁
```

即 **bootstrap 是 Kit→内核的「装配流水线」**：它消费 Kit 的三类产物（mcc 编译能力、mt/ld 链接能力、.msys 打包能力），吐出可启动的内核镜像。这是 Kit 与内核咬合最实在的落点。

### 1.3 「应该」的判据（解构型收口）

| 维度 | 应该态 | 反例（缝合怪） |
|------|--------|----------------|
| 编译 | mcc 管内核 C 子集，rustc 管 Rust 子集，链接器汇合 | 强求 mcc 单独编译整个内核（违背 C1 双工具链现实） |
| sysroot | 同一 `.msys` 既编译内核又运行内核 | 编译用目录 rootfs、运行用另一套 initramfs，两体分裂 |
| bootstrap | Phase K 把内核+sysroot 拼成可启动媒介 | 内核构建与 rootfs 构建完全解耦、各走各门禁 |
| 验证 | VM 内 L0–L2 自举闭环 + 宿主 golden 比对 | 只在 Alpine 代理环境验工具链、永不验内核 |

## 2. 多系统参照对比

> 大喵铁律第二条：多系统参照（Linux / Fuchsia / Android / NT / Redox / seL4），思想取长补短，实现自主研究。

| 系统 | 工具链 ↔ 内核 ↔ rootfs 的咬合方式 | 对 MeuOS「应该态」的可取 | 不可取（避免缝合） |
|------|-----------------------------------|--------------------------|--------------------|
| **Linux** | kbuild 独立构建内核（gcc/cross-gcc）；initramfs 单独打；发行版 rootfs 又一套。三者**解耦** | 交叉编译目标成熟、`make ... target=` 范式清晰；initramfs 思路可借鉴 | 内核构建与 rootfs 完全解耦、各走各门禁——非「有机咬合」 |
| **Fuchsia** | **单一 GN 构建图**：zircon 内核 + 用户态一套图同时产出，内核镜像与用户 package 同源构建 | **单一构建图**哲学——内核与 rootfs 由同一构建流产出，正是 §1.2 咬合点 B/C 的理想范本 | 直接搬 GN 不现实（Kit 是 Makefile 体系，`AGENTS.md` §4 禁 cmake/meson） |
| **Android** | AOSP + 内核 + vendor；内核单独构建后并入 `boot.img`（kernel + ramdisk + dtb） | 「内核镜像 + ramdisk 合并为单一可启动媒介」的装配范式，对应 Phase K 步骤 4 | vendor 垂直锁定，不具通用多架构适配性 |
| **Windows NT** | **单一构建系统（onebuild）**：内核 + 用户态同一构建 | 工具链与内核同源构建的组织形态 | 重服务留核、TCB 大（与 `01` 方向①③冲突） |
| **Redox** | **Cargo 统一构建**：kernel + 用户态同一 workspace；relibc 作为自托管 libc | 「单一构建产出内核+用户态 + 自托管 libc」的闭环精神，与 MeuOS 自举目标同构 | Rust-only 工具链，无法套用到 mcc C 路径 |
| **seL4** | 独立构建（C）+ Camkes；验证单独 | 内核与用户态明确分层、验证独立可测 | 构建与验证链条偏学术，无通用用户态工具链闭环 |

**取舍结论（非缝合怪）**：

- 取 **Fuchsia/Redox 的「单一构建流产出内核+rootfs」精神** → 落为 `bootstrap.sh` Phase K 把内核镜像与 `.msys` 同源装配（§1.2 咬合点 C）。
- 取 **Android 的「内核+ramdisk 合并为可启动媒介」范式** → 落为步骤 4 的媒介组装。
- 取 **Linux 的「交叉编译目标 + initramfs」工程范式** → 落为 mcc `--target` + `.msys` initramfs。
- **不取**：Linux 的三体解耦、NT 的重服务留核、Redox 的纯 Rust 工具链。
- 实现自主：Kit 是 Makefile/shell 体系（禁 cmake/meson，`AGENTS.md` §4），所以「单一构建图」在 MeuOS 落为 **`bootstrap.sh` 的有序 Phase 序列**，而非引入 GN/Cargo。

## 3. Kit ↔ 内核协同边界（精确契约）

### 3.1 编译边界

| 项 | 归属 | 说明 |
|----|------|------|
| 内核 C 部分编译 | **Kit (mcc)** | 早起启动/asm 边界、mkit 兼容层。mcc 五架构后端已具备（`mcc/TARGETS.md`）。 |
| 内核 Rust 部分编译 | **rustc + LLVM**（非 Kit） | `no_std` 裸机 target；i386 **无**裸机 target（`02` C2），i386 内核全程纯 C。 |
| 链接 | **统一链接脚本 + mt/ld（或系统 ld）** | 两类 `.o` 合并为单体内核镜像（`02` §4.3）。**待补**：mt/ld 是否支持 freestanding 内核链接脚本（见 §4 待补）。 |
| freestanding 约束 | 内核侧提供 | 内核是 freestanding 构建（不链 libc/crt1），需 mcc 支持「不自动链 libc」模式（见 §4 待补）。 |

### 3.2 sysroot 边界（双重身份）

- **编译时**：mcc `--sysroot=<base>.msys` 取内核 UAPI 头 + meuos-libc；mt/ld `-L <base>.msys` 取对象。
- **运行期**：内核 FS 服务内嵌 `libmsys`（或等价 Rust 实现，`11` §4.1）挂载 `.msys` 为 rootfs；`libmsys` 当前是 C 库（`meuos-sysroot/src/libmsys`），需向内核 Rust FS 服务移植（C 边界，`02` §4.2 允许「C 硬件读取」）。
- **同一格式**：编译时与运行期的 `.msys` 应是「同一 base + 不同 extend」，避免两体分裂（§1.2 咬合点 B）。

### 3.3 bootstrap 边界

- Phase 0–5 维持不变（用户态工具链自举），Phase K 为新增可跳过阶段（沿用 `MEUOS_SKIP_*`），不破坏现有流程（`11` §4.3）。
- Phase K 的直接产物 = **可启动媒介**（内核镜像 + `.msys` initramfs / 或 `.msys` 直作根）。
- Phase K 的验证载体 = `env/bin/qvm`（需 `--kernel`/`--initrd` 覆盖参数，属 env 项目）。

### 3.4 验证边界

- **B 方案（qemu-user-static）并行门禁**：M0 之前持续跑 mcc 跨架构 ABI 回归（已有 6/6、3/3 基线），保「内核就绪前工具链不被破坏」（`11` §3.2/§4.2）。这是 Kit 侧的**前置护栏**。
- **A 方案（QEMU + 自研内核）主门禁**：Phase K 在 VM 内跑 L0–L2 闭环（`11` §4.1）。
- **C 方案（Alpine 代理）回退**：Phase K 失败时回退到现有 Phase 4 代理门禁。

## 5. 自举闭环（吃自己狗粮路径）

> 任务要求：mcc + meuos-libc 在自研内核上重新编译 Kit 自身的「吃自己狗粮」路径（参照 `11` §1.1 / §4.2），以及 **i386 缺 Rust 目标对这条路径的影响**。

### 5.1 闭环分级（L0–L2 + L4 内核重建）

源自 `11` §1.2 / §4.2：

- **L0**：`libc-meuos` 静态 hello 在 MeuOS 运行退出 0。
- **L1**：宿主构建的 `mcc` 在 MeuOS 编译并运行程序。
- **L2**：MeuOS 内 `mcc` 重建 `mcc`/`meuos-libc`/`meow`，产物与宿主 golden 行为等价。
- **L4（M4）**：内核本身由 MeuOS 内工具链重建，新镜像可再次启动。

### 5.2 闭环的工具链构成与双工具链现实（C1）

- **L0–L2 全在 C 路径上**：`mcc` / `meuos-libc` / `meow` 都是 C 项目，可由 **mcc 在 MeuOS 内自举重建**（`11` §1.1）。这条闭环**不依赖 Rust**——所以「吃自己狗粮」的 L0–L2 在**全部五架构（含 i386）上都能由 mcc 单独完成**。
- **L4（内核重建）引入 Rust**：内核含 Rust TCB 组件，重建需 rustc。因此 L4 的闭环出现**分叉**：

| 架构 | 内核 Rust 部分 | L4 重建路径 | 影响 |
|------|----------------|-------------|------|
| x86_64 / aarch64 / riscv64 / loongarch64 / arm | ✅（rustc no_std target 具备） | mcc 重建 C 部分 + **host rustc 交叉重建 Rust 部分**（先交叉，`11` §5-3）；native rustc 自举为远期 | 分叉闭环：C 部分真自举，Rust 部分先交叉 |
| **i386** | ❌（无裸机 target，`02` C2） | 内核**全程纯 C**，mcc 重建**全部** C 部分 | i386 的 L4 闭环是**单一 mcc 路径，最干净** |

### 5.3 i386 缺 Rust 目标对自举路径的影响（重点）

1. **对 L0–L2 无影响**：i386 的 `mcc`/`libc`/`meow` 自举与 64 位架构完全一致（全 C）。
2. **对 L4 是「简化」也是「代价」**：
   - **简化**：i386 内核无 Rust 分叉，mcc 单一工具链即可重建整个内核——比 64 位架构的双工具链分叉更纯粹的「吃自己狗粮」。
   - **代价**：i386 内核 TCB 被迫 **C-only**，丢失 Rust 带来的编译期内存安全（capability 监视器/IPC/调度这些 TCB 核心在 i386 上是 C 实现）。这与 `02`/`07`「最小 TCB + 内存安全」目标在 i386 上产生张力——i386 是「能自举但 TCB 非内存安全验证」的特例。
3. **迁移顺序含义**：i386 可作为「先验证纯 C 自举闭环」的**快通道**（不依赖 rustc 自举），而 64 位架构的 L4 需先以「交叉重建」过渡（host rustc 编译 Rust 部分），native rustc 自举后置。这正好印证 `11` §5-3「M4 先交叉、再攻原生」的建议。
4. **架构裁决提示**：i386 是否永久纯 C、还是待 Rust i386 target 成熟后仅迁移 TCB 组件，属 `02` §5-2 / C11 范畴，需 `02` 协同定稿（见 §7）。

### 5.4 闭环的 Kit 侧护栏

- **宿主 golden 比对**：以宿主 `check-sysroot-static` 产物为 golden，VM 内 stage-2 在固定测试集（mcc `check-c11`/`check-targets`、libc 原子/线程/TLS 回归）比对，功能等价即通过（`11` §4.3）。
- **B 方案并行**：M0 前持续 qemu-user-static 跨架构 ABI 回归，保工具链不被内核进度破坏。
- **同构性约束**：验证介质与运行环境须零 GNU/LLVM/glibc（`AGENTS.md` §4），否则闭环证伪——Kit 全程满足。

## 6. 分阶段迁移路线（Kit 侧动作 ↔ 内核侧动作 ↔ 验证门禁）

> 对齐 `11` §4.2 的 M0–M6 与 `00` §4.2 依赖图，把「Kit 侧动作」显式析出。

### Phase 0（M0 前置，纯 Kit 护栏）

| 维度 | 动作 |
|------|------|
| **Kit 侧** | 持续 qemu-user-static 跨架构 ABI 回归（B 方案）；确认 mcc freestanding 模式可行性（§4.2 待补）；评估 mt/ld 内核链接脚本支持（§4.2 待补） |
| **内核侧** | Stage 0–1（架构相关早期 asm/C、建栈、开 MMU、早期串口）（`09` §5.2） |
| **验证门禁** | qvm 内核路径硬编码期：先用 `env/kernels/<arch>/vmlinuz`（Alpine）跑 B 方案护栏；内核早期串口打印可经 qvm 串口观测 |

### M0（内核启动到用户态 init）

| 维度 | 动作 |
|------|------|
| **Kit 侧** | bootstrap.sh Phase K 骨架（步骤 1–4：编译 C 部分 + 链接 + 打包 .msys + 组装媒介）；env 项目为 qvm 加 `--kernel/--initrd`（§4.2 待补） |
| **内核侧** | Stage 2–5（memblock、`kernel_main` Rust runtime、capability 自举、拉起 meu-supervisor/FS/devmgr）（`09` §5.2） |
| **验证门禁** | qvm x86_64 启动，串口打印内核 banner + init 就绪提示（`11` M0） |

### M1（L0，libc 静态 hello 退出 0）

| 维度 | 动作 |
|------|------|
| **Kit 侧** | 确保 mcc freestanding 产出的 `libc-meuos` 静态 ELF 可被内核加载运行 |
| **内核侧** | `03` 内存 + `04` 单进程 exec + `08` exit/write 最小集（`11` M1） |
| **验证门禁** | `hello` 返回 0（`env/bin/qvm run x86_64 /mnt/host/hello`） |

### M2（L1，宿主 mcc 在 MeuOS 编译运行）

| 维度 | 动作 |
|------|------|
| **Kit 侧** | 把宿主构建的 `mcc` + `mt/as` + `mt/ld` 打包进 `.msys` rootfs，送入 VM |
| **内核侧** | `04` fork/exec/spawn + `08` 完整 syscall 子集 + mt/as、mt/ld 可在 MeuOS 运行（`11` M2） |
| **验证门禁** | VM 内 `mcc -o t t.c && ./t` 退出 0 |

### M3（L2 工具链，mcc 重建 mcc/libc/meow）

| 维度 | 动作 |
|------|------|
| **Kit 侧** | **mt/as、mt/ld 在 MeuOS 自举**（§4.2 待补，阻塞项）；stage-2 mcc 产出 |
| **内核侧** | `05` IPC（管道/并发）+ `04` 调度（`11` M3） |
| **验证门禁** | stage-2 mcc 与宿主 golden 在固定测试集上输出一致（L2） |

### M4（L2 内核，内核由 MeuOS 工具链重建）

| 维度 | 动作 |
|------|------|
| **Kit 侧** | **交叉重建内核**（host rustc 编译 Rust 部分 + mcc 编译 C 部分，先交叉 `11` §5-3）；native rustc 自举后置；mt 工具链自举完成 |
| **内核侧** | `03/04/05/08/09/10` 全闭环（`11` M4） |
| **验证门禁** | VM 内用工具链重编译内核源码 → 产出可启动镜像 → 新镜像可再次启动（L4） |

### M5（跨架构，x86_64 + aarch64 双架构）

| 维度 | 动作 |
|------|------|
| **Kit 侧** | mcc 五架构已具备；为每架构构建内核镜像；i386 走纯 C 快通道（§5.3）；loongarch64 后移（`11` §5-4） |
| **内核侧** | `09/10` 多架构启动与驱动（DT/ACPI/multiboot/OpenSBI 归一化 bootinfo）（`09` §5.5） |
| **验证门禁** | 两架构均满足 AC1–AC7（`11` §6） |

### M6（原子更新，.msys 签名 Overlay）

| 维度 | 动作 |
|------|------|
| **Kit 侧** | `.msys` Overlay + ed25519 **已在 Kit 内具备**（`meuos-sysroot/ARCHITECTURE.md`）；libmsys 移植进内核 FS 服务（§4.2 待补） |
| **内核侧** | `06` 文件系统 + `07` ed25519 验签（`11` M6） |
| **验证门禁** | 应用 signed overlay 成功；base 损坏可回滚 |

### mkit 子集优先策略 → 迁移顺序映射

`00` A10 / `08` 的「mkit 子集优先」直接决定迁移先后：

1. **先让 mkit 子集直跑**：M0–M2 只要求 mkit 子集（open/read/write/close/mmap/基础进程/基础信号）在自研内核跑通——这是 L0–L1 的最小可用面，不依赖 glibc。
2. **再扩 glibc**：mkit 子集稳定后，按 `08` Phase 0→3 渐进扩展通用程序 syscall 子集（C12 基线），最后才追求更宽的 glibc 兼容。
3. **含义**：迁移顺序「mkit 子集 → 工具链自举（mcc 是 mkit 程序）→ 完整 syscall 子集 → 内核重建 → 原子更新」，与 M0–M6 同构，且保证「每一步都先有最小可运行面再扩展」。
