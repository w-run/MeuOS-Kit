# 07 - 安全模型（Capability-based Security）

> 子领域文档 · 团队 `kernel-plan` · 调研员 `k-sec`
> 关联设计文档：01-内核架构选型、02-内核语言策略、04-进程与调度、06-文件系统、08-Linux兼容层

---

## 1. 概述与目标

MeuOS 内核的安全模型以 **capability-based（能力/权能）** 作为 Day 1 的唯一权限模型，取代 Linux 上 DAC/MAC/Linux capabilities/seccomp/namespaces 五套机制的松散堆叠。

核心命题：**权限不是「你是谁」（主体身份），而是「你手上持有什么不可伪造的令牌」**。一个进程能做什么，完全由其持有的 capability 集合决定；没有任何「超级用户」可以绕过这一集合。这从架构上消灭了 Linux 中「root 万能」这一根本性缺陷。

本设计的目标：

1. **最小权限（least privilege）默认成立**：进程创建时即被限定在最小权限集，所需权限必须显式声明、显式持有。
2. **可推理（reason about）**：权限随对象（文件、IPC 端点、设备等）走，而非随身份走；审计和影响面分析是局部而非全局的。
3. **单一范式、三个表现维度**：同一个 capability 范式，在 (a) 进程沙箱、(b) spawn 资源账本、(c) 统一资源命名空间中以三种一致的方式呈现，互锁而非叠加。
4. **Day 1 即强制、无回退**：不存在「关掉 capability 退回 root」的兼容路径；Linux ABI 兼容层（08）在边界处做 capability 映射，而非在内核中保留特权后门。
5. **最小 TCB + 关键组件 Rust**：把安全关键代码量压到最小，并用 Rust 消除整类内存安全缺陷。

## 2. 设计约束与上下文

### 2.1 技术基线约束

- **混合内核（hybrid kernel）**，Rust + C 混合实现（见 01/02 设计文档）。
- **外部兼容 Linux ABI**：已有生态二进制应当可运行，但这是「兼容层」的职责，不是内核内部模型。内核内部不保留 uid=0 / capability bounding set 等 Linux 概念作为一等公民。
- **原型期路线**（见 README）：技术选型 → 原型（内存 + 调度 + IPC + Linux syscall 兼容层 mkit 子集）→ 验证（mcc + meuos-libc 在自研内核自举）。安全模型必须在原型期就以最小可运行集落地，否则兼容层与 spawn 账本会反向固化错误假设。

### 2.2 关联子系统的互锁需求

| 关联子系统 | 文档 | 与安全模型的互锁点 |
|---|---|---|
| spawn 进程管理 | 04 | 进程创建时声明资源配额与初始 capability 集（资源账本） |
| 统一资源命名空间 | 06 | 文件/资源访问须显式声明路径（路径即 capability 的命名维度） |
| IPC 机制 | 05 | 端点句柄本身就是 capability，权限随句柄传播 |
| Linux 兼容层 | 08 | 在 ABI 边界将 Linux 权限语义「翻译」为 capability |
| 内核语言策略 | 02 | 安全关键组件用 Rust，缩小 TCB |

这三者的耦合关系在 §4.3 展开：**一个范式、三个表现维度**。

### 2.3 为什么必须 Day 1 而非逐步迁移

Linux 的经验教训（见 §3.1）是：特权机制是「增量加上去、几乎永远拆不掉」的。若 MeuOS 先在内部用 root/uid 模型跑通原型，再回头「加 capability」，会遭遇 (a) 既有的特权代码路径难以枚举、(b) 兼容层依赖 uid=0 短路、(c) 自举链（mcc/meuos-libc）依赖超级权限——最终 capability 沦为装饰。因此 capability 必须是地基，而不是补丁。

## 3. 业界方案对比

### 3.1 Linux 五套机制的堆叠问题（反面教材）

Linux 没有统一模型，而是按历史需求逐步叠加了五套机制，彼此覆盖、难以推理：

1. **DAC（自主访问控制，基于 uid/gid/permission bits）**：权限挂在「身份」上。root（uid=0）可绕过一切。这是「root 万能」的根源。
2. **MAC（强制访问控制，如 SELinux/AppArmor）**：基于标签/策略的集中式规则。策略复杂、易出错、与 DAC 正交叠加；SELinux 的 `reference policy` 规则数以万计，可审计性极差。
3. **Linux capabilities**：把 root 拆成 ~40 个碎片。但实践证明划分失败——
   - `CAP_SYS_ADMIN` 成为「新 root」：Linux 3.2 内核中 1167 处 capability 用例有 451 处用 `CAP_SYS_ADMIN`（占超 1/3）；到 5.2 升至超 45%。原因：无中央统筹、无明确指引、名称误导，开发者遇到不确定就选它。一旦授出，目标「权限小于 root」即失效（Kerrisk, LWN 2012）。
   - 碎片之间仍可互相提权，DAC 与 capability 还存在交互漏洞。
4. **seccomp-bpf**：系统调用号 + 参数的 BPF 字节码过滤。写对极难——需枚举每个 syscall 及其参数布局，且存在 TOCTOU、参数间接解引用（如路径字符串）等无法在过滤器中安全处理的难题；与 ptrace 配合时还需用户态仲裁，复杂度上一个数量级。
5. **namespaces / cgroups**：隔离视图与资源，但本身不解决「进程被攻破后能做什么」，且与前面四套机制叠加形成组合爆炸。

**结论**：五套机制正交叠加 = 攻击面叠加、推理成本叠加。任何一处策略错配即可被绕过（「confused deputy」类问题在 DAC+capability 混合模型下尤其普遍）。

### 3.2 候选方案

| 方案 | 类型 | 核心思想 | 优点 | 缺点 / 取舍 | 权威来源 |
|---|---|---|---|---|---|
| **纯 capability 系统**（Hydra, CAP 计算机, EROS/KeyKOS） | OS 级能力 | 权限 = 不可伪造的、可传递的对象引用；无全局身份 | 最小权限天然成立；可推理；无 root | 传统 OS 兼容生态为零，难以承载 Linux ABI | Dennis & Van Horn 1966；Shapiro et al. EROS |
| **Capsicum**（FreeBSD/Chromium） | UNIX + 轻量 capability | 在 UNIX 上叠加 `capability mode` + `cap_*` 受限 fd；扩展而非替换 UNIX API | 提供现实迁移路径；Chromium 已适配，沙箱健壮 | 仍寄生在 UNIX 身份模型之上；capability 与 fd 概念耦合，进程级 capability 表达力有限 | Watson et al. USENIX Security 2010 |
| **seL4 capability 模型** | 微内核能力 | 所有内核资源都是 capability 对象，挂在 CSpace（能力空间）树；复制/删除/授予是显式系统调用；附权能与派生（derivation tree） | 形式化验证（8700 行 C，证明功能正确性 + 信息流安全）；最小 TCB 范本；权限传播可精确追踪 | 微内核范式，需自行构建服务；对混合内核需裁剪 | Klein et al. SOSP 2009 |
| **Fuchsia/Zircon** | 微内核 + handle/rights | 用户态几乎只通过 **handle** 访问内核对象；每个 handle 带 **rights**（对对象的细粒度权限位）；Job 树组织进程能力 | 句柄即能力、权限随句柄走；与 IPC/进程树天然统一；Google 工程化成熟 | 整体生态陌生；rights 是静态位图，动态派生/回收语义较简单 | fuchsia.dev Zircon docs；arXiv:2108.04183 |
| **OpenBSD pledge/unveil** | 进程沙箱（声明式） | 进程声明未来所需**子系统 promise**（约 36 个）与**可见路径**（unveil）；越界即 `SIGABRT` 杀进程；**只能收缩不能扩张** | 比 seccomp-bpf 简单一个数量级；开发者易用、可逐步加严；OpenBSD 基础系统广泛采用 | 是沙箱策略而非完整权限模型；不解决跨进程授权传播 | OpenBSD `pledge(2)`/`unveil(2)` man pages |
| **CHERI** | 硬件能力（MMU 级） | 指针即 capability：含地址 + 边界 + 权限位，由硬件强制；提供空间与引用安全 | 从硬件根除一整类内存破坏；可与软件 capability 互补 | 依赖特定硬件（Arm Morello / CHERI-RISC-V）；短期无法作为跨架构基线 | Watson et al. / Cambridge CTSRD |

### 3.3 取舍结论（用于 §4）

- **拒绝**「纯 capability OS」作为唯一路径：生态代价不可接受（MeuOS 必须兼容 Linux ABI）。
- **拒绝**「沿用 Linux 五套机制」：推理成本与攻击面均不可接受，且 root 模型与 Day 1 唯一模型目标冲突。
- **采纳** seL4/Zircon 的「内核对象即 capability、权限随句柄传播」作为**内核内部权限原语**。
- **采纳** OpenBSD pledge/unveil 的「声明式、只能收缩、越界即终止」作为**进程沙箱默认形态**（因为它比 seccomp-bpf 简单一个数量级，且符合最小权限）。
- **跟踪** CHERI 作为**可选硬件增强层**，在支持的架构（RISC-V / Arm Morello）上叠加指针级能力，但不作为跨架构基线。

## 4. MeuOS 选型建议

### 4.1 内核内部：万物皆对象，权限随句柄走（借鉴 seL4/Zircon）

- **内核对象（kernel object）**：进程、线程、地址空间、IPC 端点、文件/卷句柄、设备、timer、事件等，统一为带类型的内核对象。
- **句柄（handle）即 capability**：用户态几乎只通过 handle 访问内核对象（同 Zircon）。每个 handle 携带 **rights 位图**（如 `READ/WRITE/EXECUTE/MANAGE/GRANT/REVOKE/DUPLICATE`），决定能对该对象做什么。
- **能力空间（CSpace，借鉴 seL4）**：进程持有 handle 表；句柄的复制（`dup`/`duplicate`）、授予（跨进程通过 IPC 发送）、回收（close）都是**显式、可审计**的操作。不存在「通过身份隐式获得对象访问」。
- **无 root**：内核中没有 uid=0 逃生舱。即使是 init/兼容层服务，也只是持有一个较大的初始 handle 集合——这些 handle 仍受 rights 约束，且可按 §4.3 逐步收缩。

> 这一层直接回应 §3.1 的「root 万能」与「CAP_SYS_ADMIN 新 root」：权限不来自身份，而来自具体、可枚举、可收缩的句柄权限。

### 4.2 进程沙箱：pledge/unveil 风格，越界即终止

- **pledge 维度（子系统承诺）**：进程在生命周期早期声明未来所需子系统（语义对齐 OpenBSD `pledge(2)`）：
  - `stdio`（已开 fd 的读写/mmap 无 EXEC、timer、进程内查询）、`rpath`/`wpath`/`cpath`（只读/写/创建删除路径）、`inet`/`unix`/`dns`（网络）、`proc`/`exec`（进程派生）、`prot_exec`（映射可执行内存）、`unveil`、`error` 等。
  - **只能收缩不能扩张**：后续 `pledge()` 调用只能减少子系统，已撤销不可复活，违者 `EPERM`（对齐 OpenBSD 语义）。
  - 越界行为：**默认 `SIGABRT` 终止并留 core**（fail-closed），可选 `error` promise 改为返回 `ENOSYS`（便于渐进适配）。
- **unveil 维度（路径可见性）**：进程声明其可见的目录/文件及权限（r/w/x/c）；调用后**可锁定**（lock），之后不能再扩展。未 reveal 的路径访问直接失败。
- **为何优于 seccomp-bpf**：开发者只需声明「我需要哪些子系统、哪些路径」，无需编写 syscall 号与参数布局的 BPF 字节码，也不存在 TOCTOU/间接参数的处理难题。复杂度降低约一个数量级（OpenBSD 基础系统已在数百个程序中采用即证）。

> 沙箱越界即终止的 fail-closed 语义，正是 capability 模型「无隐含权限」的直接体现。

### 4.3 互锁设计：一个范式、三个表现维度

capability 是同一套原语，在三个子系统中一致地表现，彼此互锁而非叠加：

```
        ┌──────────────── 统一权限原语：capability(handle + rights) ────────────────┐
        │                                                                           │
   维度A：进程沙箱              维度B：spawn 资源账本              维度C：统一命名空间
   (pledge/unveil 风格)        (04 进程管理)                     (06 文件系统/资源)
   - 声明所需子系统 promise     - 创建时声明初始 capability 集     - 文件/资源访问须显式
   - 声明可见路径(unveil)        - 声明资源配额(cpu/内存/fd数)       声明路径(capability 的
   - 只能收缩、越界即终止        - 配额用尽→新分配失败/收缩         命名维度)
                                 - 账本与句柄权限同源               - reveal 即授予路径能力
        │                           │                                │
        └──────── 三者共享同一 handle/rights 内核对象层，互不重叠、可联合推理 ──────┘
```

- **与 spawn（04）互锁**：`spawn()` 创建子进程时，父进程不仅声明资源配额（cpu/内存/fd 上限），同时声明子进程**初始 capability 集与初始 pledge**。账本（资源）与权限（capability）同源——都是「创建时显式声明、运行期不可隐式扩张」。
- **与统一命名空间（06）互锁**：文件系统访问不依赖全局可见根，而依赖进程通过 spawn/unveil 显式获得的**路径 capability**。统一命名空间是 capability 的「命名维度」：`unveil("/var/lib/app", "rwc")` 本质上就是向进程授予一个受限的路径 capability。
- **联合推理优势**：审计一个进程时，只需看它的初始句柄集（来自 spawn）+ 运行时 pledge/unveil 收缩 + 命名空间 reveal，三者在同一个 handle/rights 模型下，无需像 Linux 那样去交叉核对 uid、capability bounding set、SELinux label、seccomp filter、namespace 五套东西。

### 4.4 最小 TCB 与关键组件 Rust

- **最小 TCB 原则（借鉴 seL4）**：把必须被信任的代码量压到最小。内核对象管理、句柄/rights 校验、pledge/unveil 裁决、IPC 端点授权——这些安全关键路径用 **Rust** 实现（见 02 语言策略），消除整类内存安全漏洞（UAF、缓冲区溢出、悬垂指针），从而把「能力令牌不可伪造/不可篡改」这一前提建立在内存安全之上。
- **非关键或需零成本抽象处用 C**（驱动、体系结构相关 glue、与现有 C 生态对接）。C/Rust 边界明确，Rust 侧对跨 FFI 的句柄做类型化封装，防止能力被 C 侧意外伪造。
- **形式化验证的可选路径**：长期可对 Rust 安全关键组件采用 seL4 式的精化验证思路（至少对 rights 裁决与句柄表不变量做形式化或强类型约束）。原型期不强求，但架构须预留（接口小而边界清）。
- **CHERI 作为可选硬件增强**：在 RISC-V / Arm Morello 上，将 handle 实现与 CHERI 指针能力对齐，从硬件层保证句柄不可越界/不可伪造；其他架构退化为软件权能。这不改变软件模型，只是加固。

### 4.5 权限传播与继承

- **句柄复制（duplicate）**：子进程/另一进程获得原句柄的**子集权限副本**（rights 只能收窄），派生关系可记录为 derivation tree（借鉴 seL4），用于撤销传播分析。
- **跨进程授予（grant via IPC）**：仅当发送方句柄含 `GRANT` right 时，才能通过 IPC 端点把句柄发给对端；接收方获得受 `GRANT` 约束的权限。
- **exec 继承**：对齐 OpenBSD `execpromises`——`execve` 后的新程序继承父进程声明的 `execpromises`（受限子系统集），且 setuid/setgid 位在新模型下被禁止（无 root 概念，setuid 无意义，遇之返回 `EACCES`）。
- **撤销（revoke）**：句柄持有者可随时 `close`/回收；服务端可在端点层批量撤销，配合 spawn 账本的资源回收。
- **无隐式提升**：任何「需要更多权限」的诉求，必须由持有 `GRANT` 的对端**显式重新授予**受限句柄——不存在「提权到特权再降回」的捷径。

### 4.6 Linux 兼容层（08）的边界映射（要点）

兼容层职责是把 Linux 二进制期望的权限语义**翻译**为 MeuOS capability，而非暴露 Linux 特权原语：

- Linux `uid=0` 的特权操作：在兼容层映射为「持有对应内核对象句柄 + rights」；无句柄则按 `EPERM`/越界终止处理，**内核内部不识别 root**。
- Linux `capability`（`CAP_NET_BIND_SERVICE` 等）：映射为对应 socket/文件句柄的 rights 位；`CAP_SYS_ADMIN` 这类「大杂烩」在兼容层被拆分到具体对象权限，**不被整体授予**。
- Linux `seccomp`/`namespaces`：在兼容层用 MeuOS 的 pledge/unveil 表达（如容器类程序 = 受限 spawn + 命名空间 reveal + 强 pledge）。
- 兼容层本身运行在一个受限句柄集下，避免其成为新的特权后门。

## 5. 开放议题

1. **handle 命名与跨进程发现**：句柄是「不透明整数 + 进程私有表」还是「全局可寻址能力 + 类型」？前者（Zircon 风格）简单但授予需 IPC 携带；后者（seL4 CSpace）表达力强但实现复杂。原型期建议采用 Zircon 风格（进程私有 handle 表 + IPC 携带），后续评估是否需要全局 CSpace。
2. **rights 位图的粒度**：需要多少个 right 位？过少则表达力不足（回到 capability 碎片问题），过多则难推理。建议以 Zircon 的 ~10 个基础 right 起步，按对象类型扩展。
3. **pledge 子系统清单与内核对象的对齐**：约 36 个 OpenBSD promise 如何映射到 MeuOS 的内核对象/rights？需要一份映射表（如 `inet` ≈ 网络 socket 句柄的 rights），原型期先实现最小子集。
4. **撤销传播的完整性 vs 性能**：derivation tree 全量记录可支持精确撤销，但有内存/性能成本。原型期是否只支持显式 close、推迟 derivation 追踪？
5. **CHERI 对齐的优先级**：是否值得在原型期就为 RISC-V CHERI 设计句柄表示？建议原型期保持软件权能、接口预留，待单架构跑通后再评估。
6. **审计与可观测性（12）**：权限决策（pledge 越界、句柄授予、unveil 锁定）需要结构化日志/事件，供 12-调试与可观测性 消费。需定义事件 schema。
7. **自举链的权限**：mcc/meuos-libc 自举（11）时，构建工具链本身需要的句柄集如何声明？避免自举依赖隐式特权。

## 第三轮裁决回写（已采纳，自主决策）

> 第三轮查缺补漏修订：将指挥官已自主采纳的 C2 / C3 / C9 裁决以「已裁决回写」形式追加于此，升级为「已采纳」状态。
> 来源裁决：`14-裁决-安全与命名空间.md` §③（C2 / C3）、`17-裁决-调试与兼容.md` §3（C9）。原 `07` 待开放议题、rights 位图据此落定。铁律：仅追加、不删改原章节。

### C2 采纳结论（07 rights 位图新增 KEY_UNWRAP / KEY_WRAP）

- **采纳**：密钥 unwrap 权走 capability，且**不复用 `MANAGE`**（`14` §③ 裁决 1）。
- **07 rights 位图新增服务端专用 right（与 `14` 呼应）**：
  - `KEY_UNWRAP`（建议 bit 6）：使用卷密钥 KEK unwrap 某文件的 file key（解密权威）。
  - `KEY_WRAP`（建议 bit 7）：wrap / re-wrap file key（加密写入、密钥轮换权威）。
  - 二者与 `MANAGE` **正交**，bitmap 中独立占位，紧邻 `MANAGE`/`EXECUTE` 之后。
- **约束**：
  - `KEY_UNWRAP`/`KEY_WRAP` **永不出现在跨进程 grant / mint 给客户端的句柄上**（内核 mint 强制）；客户端 `READ`/`WRITE` 的「解密读 / 加密写」为语义隐式，不为独立 right。
  - 二者仅出现在 FS 服务 / 密钥守护的服务端句柄上，由 boot 期 root-of-trust 派生（`09` §5.4）。
  - `CAP_MINT_FILEHANDLE` 的 issuance ceiling 默认 `{READ, WRITE, EXECUTE}`，由 capability 监视器在 mint 系统调用处强制——FS 服务即便被诱导也无法向客户端下发 `MANAGE`/`KEY_*`（`14` §③ 裁决 3，破 confused deputy）。
- **revoke 闭环**：`07` §4.5 / §5.4 的 derivation tree 追踪含 `READ`/`WRITE` 的句柄传播即足以覆盖「句柄→解密权」链，无需单独密钥节点；服务端 `KEY_UNWRAP` 独立于客户端 derivation tree（客户端 revoke 不剥夺 FS 服务卷级密钥权）。

**对本文的具体修订（定稿）**：
- §4.1 基础 right 集合 `{READ, WRITE, EXECUTE, MANAGE, GRANT, REVOKE, DUPLICATE}` 据此追加 `KEY_UNWRAP`（bit 6）/ `KEY_WRAP`（bit 7），并标注「仅服务端、永不跨进程 mint 给客户端」。
- §4.5 / §5.4 明确：derivation tree 来自 seL4、是 MeuOS 在 Zircon handle 模型之上的自研增强（见「引用澄清」失真 4）；revoke 链路覆盖「句柄→密钥 unwrap 权」由 `READ` 派生传播、服务端 `KEY_*` 独立于客户端 tree。

### C3 采纳结论（与 06 每进程 namespace 互锁——维度 C）

- **采纳**：统一命名空间内部模型 = 每进程独立 namespace（`14` §③ 裁决 4/5），与 `07` §4.3 维度 C「统一命名空间」完全互锁。
- **互锁定稿**：`unveil(path, perm)` 本质 = 向进程命名空间注入该路径的 capability 绑定；`pledge` 的 `rpath`/`wpath`/`cpath` 约束「该进程未来能否新增 reveal 绑定」。路径即 capability 的命名维度在此闭环。
- **spawn COW 继承模板**：spawn 时内核复制（COW）父 / Job 的 namespace 模板作为子进程初始绑定表（与句柄继承集协同，见 `04`）；`unveil` 是运行期追加绑定。
- **本文件需协同回填点（供 `04`/`08`）**：`04` spawn 输入清单显式加入 namespace 模板；`08` 全局路径树 = 每进程合成投影、无内核全局 `/`。`07` 仅确认互锁成立，具体映射见 `14` §③ 裁决 6。

### C9 采纳结论（调试权体系 DBG_* 增补 DBG_POKE 为第 6 right）

- **采纳**：调试权体系在 `12` 提出的 5 个 `DBG_*` right 基础上，**拆出最高风险子权限 `DBG_POKE`（内存 / 寄存器改写）**，构成 **6 个 right**（`17` §3.1）。
- **`DBG_*` 全表（建议并入 07 rights 位图）**：

  | right | 含义 | 风险级 | 默认 |
  |-------|------|--------|------|
  | `DBG_INSPECT` | 读 inspect 树（可按子树粒度授权） | 低 | deny |
  | `DBG_TRACE` | 订阅事件流 / syscall trace | 低 | deny |
  | `DBG_PROFILE` | 请求 HW counter 采样（侧信道风险） | 中 | deny |
  | `DBG_ATTACH` | attach 调试器：暂停/单步/读寄存器/读内存/设观察点 | 高 | deny |
  | `DBG_POKE` | **改写目标内存 / 写寄存器 / 写断点（in-process 修改）** | **最高（任意写后门）** | **deny，且绝不随 ATTACH 自动获得** |
  | `DBG_CRASHDUMP` | 读取 / 持久化崩溃报告 | 中 | 监督者对其监督 Job 默认持有 |

- **默认矩阵**：mkit 与 glibc 程序默认**全 deny**（无调试 root）；开发态差异靠 spawn / Job manifest 的 `debug_policy`（`deny`/`same-job`/`dev-session`）声明属性，**非全局开关**（强烈否决「系统 dev 模式」逃生舱）；监督者对其监督 Job 默认持 `DBG_CRASHDUMP`，不持 `DBG_ATTACH`/`DBG_POKE`。
- **异常 channel 仲裁（C9-B）**：异常事件内核一次性生成、多播副本给监督者 + 持权调试器；监督者持 `DBG_CRASHDUMP` 默认订阅、其 kill/restart 决策不可被抑制；调试器仅可请求**有界崩溃冻结窗口**（超时/detach 自动释放），**绝不可永久接管崩溃**（`17` §3.2）。
- **ptrace 边界（C10，关联）**：选档位 C——真 ptrace 式原语 + capability 守护；单步/读受 `DBG_ATTACH`，**任意内存改写受 `DBG_POKE`、永不默认**（`17` §3.3）。

**对本文的具体修订（定稿）**：
- 若 `07` 列出 rights 位图全表，应补 `DBG_*` 与 `KEY_*` 全表（见上），并标注 `DBG_POKE` 为第 6 个显式 right、永不默认。
- §4.5 明确 `debug_policy` manifest 属性与 `debug-issuer`（持 `GRANT` 派发 `DBG_*` 的专用权）作为 capability 子类型；`DBG_POKE` 的 revoke / 审计记入 §5 审计 schema。

> 与 `14`/`17` 呼应：C2/C3 采纳结论落实 `14` §③；C9 落实 `17` §3。原 `07` §5 开放议题（right 粒度、调试 default、CHERI）中，right 粒度与调试 default 已由 C9 落定；`KEY_*` 与 `DBG_*` 全表将 `07` rights 位图由「基础 ~10 个」扩展为「含密钥服务端权 + 调试权」的完整集合（与失真 6 的「Zircon ~13 right、MeuOS 取 ~10–13 子集」一致）。

## 引用澄清（来自24）

> 来源：`24-参考系统深度专项.md` §②「对 01–12 引用失真纠偏清单」。下列失真落在 `07` 范围内，按第三轮查缺补漏要求在此修正（仅追加澄清、不删改原章节）。

### 失真 4（中优先级）：Zircon 被暗示「有派生树 / revoke 传播」+ seL4 CSpace 用词混称
- **原 §4.1 / §4.5 / §5.1 说法**：§4.1 称「能力空间（CSpace，借鉴 seL4）：进程持有 handle 表…」；§4.5 称「派生关系可记录为 derivation tree（借鉴 seL4）」；而 §5.1 又采用「Zircon 风格（进程私有 handle 表 + IPC 携带）」——同一采纳模型在文中被同时标为 seL4 CSpace 与 Zircon 风格，自相矛盾。
- **真实机制**：
  - 实际采纳的模型是 **Zircon 式进程私有 handle 表 + IPC 携带**，**不是** seL4 的全局可寻址 CSpace（CNode 基数树）。MeuOS 选 Zircon 式、未采用 seL4 CSpace（`24` §1.5.6 / Q9）。
  - Zircon **没有** capability 派生树 / 递归 revoke 传播（rights 是静态位图）。`derivation tree` + revoke 传播是 **seL4 独有**，`07` §4.5 想引入它是 **MeuOS 自研增强**，不能归到 Zircon。
- **修正（统一术语）**：MeuOS 统一使用「**句柄表 = capability 表**」表述，**不混用 CSpace 一词**（CSpace 专指 seL4 的 CNode 基数树，MeuOS 未采用）。具体：
  - §4.1 的「能力空间（CSpace，借鉴 seL4）」应读作「**进程私有句柄表（Zircon 风格，可演进为全局 CSpace）**」，与 §5.1 对齐。
  - §4.5 明示「derivation tree 来自 seL4，是 MeuOS 在 Zircon handle 模型之上的**自研增强**（Zircon 本身无派生树）」——C2 的 revoke 闭环正依赖此自研增强。

### 失真 6（低优先级）：seL4「8700 行 C」与 Zircon「~10 right」的数字口径
- **原 §3.2 说法**：「形式化验证（8700 行 C）」「~10 个基础 right 起步」。
- **真实机制**：原始被证 seL4 内核约 8,700 行（Klein et al. 2009）；现代验证版（ARMv8/HYP）更大。Zircon 实际基础 right 约 **13** 个（含 INSPECT/MANAGE 类）。
- **修正**：补注「现代验证版内核规模更大（8,700 行指 2009 原始被证版）」；Zircon 实际 ~13 right，MeuOS 原型取 ~10–13 子集（本回写新增的 `KEY_*` + `DBG_*` 后即落在该子集区间内，与「含服务端密钥权 + 调试权」的完整位图一致）。

> 小结：失真 4 为术语一致性问题（影响 `07` 参照归属严谨性，C2 revoke 闭环仍成立）；失真 6 为数字口径（近似可接受，仅补注）。均不改动原章节，仅追加正确表述。
