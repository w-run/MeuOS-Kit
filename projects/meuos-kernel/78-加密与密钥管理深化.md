## 0. 核心结论（一句话）

> **以 `07` 既有的 `KEY_UNWRAP`/`KEY_*` 专属 right 为密钥操作唯一能力门禁（不复用 `MANAGE`/`GRANT`）；密钥材料由 VMO/secure-memory 承载、按 capability 派生与回收；密钥生命周期与 `32` 度量基 + `61` `.mimg` 信任链协同；备份加密复用 `73` 导出路径；五架构薄后端（硬件密钥岛/TPM/软实现）同源。**

## 1. 密钥 right 模型（复用 `07` `KEY_*`，不新增 bit；密钥句柄即 capability）

> 本节把「密钥操作」的能力门禁**完全收敛到 `07` 已冻结的 `KEY_*` right**，不引入任何新的 right bit、不复用通用 `MANAGE`/`GRANT`。密钥句柄作为 capability，其操作权限 = 句柄携带的 rights 位图 + 密钥后端派生约束。

### 1.1 复用 `07` §4.1 已冻结的密钥 right

| right | bit | 既有语义（据 `07` §4.1 / 第三轮回写 C2） | 密钥管理维度用途 |
|-------|-----|------------------------------------------|------------------|
| `KEY_UNWRAP` | 7 | 使用卷密钥 KEK unwrap 某文件的 file key（解密权威） | 密钥解密/解封操作的唯一门禁 |
| `KEY_WRAP` | 8 | wrap / re-wrap file key（加密写入、密钥轮换权威） | 密钥封装/重新封装操作的唯一门禁 |
| `DUPLICATE` | 6 | 句柄复制/收窄派生 | 派生受限密钥句柄（收窄 rights，不增权） |
| `MANAGE` | 3 | 对象生命周期（**密钥域不复用**） | 仅管密钥句柄对象生命周期，**不授予密钥操作权** |
| `GRANT` | 4 | 跨进程授予（**密钥域不复用**） | 仅管句柄传递，**不派生密钥操作权** |
| `VERIFY` | 38 | 签名验签权威（`32` D-SB1 复用） | 公钥根消费、密钥证书验签 |
| `ATTEST` | 39 | 远程证明预留（`32` D-SB7 预留，Day 1 不启用） | 密钥后端度量 quote（后置） |

> **关键裁定（与 `07` 同构纪律）**：
> - 密钥操作权 = `KEY_UNWRAP`/`KEY_WRAP`（bit 7/8），**永不出现在跨进程 grant / mint 给客户端的句柄上**（内核 mint 强制，对齐 `07` C2）——客户端以 `READ`/`WRITE` 触发「解密读 / 加密写」语义隐式，不为独立 right（对齐 `06` C2「客户端 unwrap 隐于 READ/WRITE」）。
> - 二者仅出现在 FS 服务 / 密钥守护（key daemon）的服务端句柄上，由 boot 期 root-of-trust 经 `09` Stage 4 派生（`07` C2 / `32` 跳 2）。
> - **不新增 `KEY_GENERATE`/`KEY_ROTATE`/`KEY_DERIVE` 等位**：生成/轮换/派生是 `KEY_WRAP`（封装新密钥）与 `KEY_UNWRAP`（解封派生材料）的组合语义，加受约束 mint（`07` §4.5）收窄，不另占 bit（与 `NET_*`/`BLOCK_*`/`KEY_*`「领域专属 bit、不复用 `MANAGE`/`GRANT`」先例一致，但若未来确实需要细分子项，须经 §7 K-78-1 待决项拍板，不私自扩展）。

### 1.2 密钥句柄即 capability（与 `07` §4.1 同构）

- **密钥句柄 = 一类内核对象句柄**：每个密钥（KEK / file key / 派生会话密钥）在内核表现为一个带类型的句柄，携带 rights 位图（`KEY_UNWRAP`/`KEY_WRAP`/`DUPLICATE`/`READ`/`WRITE` + 通用 `MANAGE` 仅管生命周期）。
- **权限随句柄走**：密钥操作权限不随身份，而随持有句柄的 rights（对齐 `07`「无 root」地基）。
- **受约束 mint（继承 `07` §4.5 / `20` I5）**：密钥守护/FS 服务派生子密钥句柄时，`rights_issued = rights_service ∩ rights_client_requested`，破 confused deputy（对齐 `07` T3/T4、C2「密钥 unwrap 权绑定句柄」）。
- **无隐式提升（对齐 `07` §4.5 / `20` I3/I6）**：任何「需要更多密钥操作权」的诉求，必须由持 `KEY_*` 的对端显式重发受限句柄——不存在「提权再降回」捷径。
- **句柄不可伪造（对齐 `07` T1 / `20` I7）**：密钥句柄非 `Copy`、私有构造、表外无效；Rust 类型层 `PhantomData<Rights>` 防伪造。

### 1.3 与威胁模型（`29`）的攻击面对应

| 威胁类（`29`） | 密钥维度挡点 | 归口 |
|----------------|--------------|------|
| T1（句柄伪造） | 密钥句柄表外无效、类型层防伪造（`07` §4.1 / `20` I7） | `07`/`20` |
| T2（rights 越界） | `check_rights()` 裁决点，密钥操作须 `KEY_UNWRAP`/`KEY_WRAP`（`07` §4.1 / `20` I3） | `07`/`20` |
| T3/T4（派生投毒/confused deputy） | 受约束 mint + 密钥 unwrap 权绑定句柄（C2 / `07` §4.5 / `20` I5） | `07`/`20` |
| T5（撤销竞态） | derivation tree revoke 后派生密钥句柄全断（`07` §5-4 / `20` I2） | `07`/`20` |
| T-A（密钥材料泄露） | 密钥材料永驻 secure-memory / VMO，不出 pager（`06` C2 / §2） | `06`/`03` |

## 2. 密钥材料承载（VMO/secure-memory，派生收窄、回收；与 `07` §4.5 同构）

> 本节把「密钥材料（raw key bytes）的存放与生命周期」建模为 **VMO / secure-memory 承载 + capability 派生 + revoke 回收**，与 `07` §4.5 的句柄派生/撤销机制同构，不引入新的内存对象类型。

### 2.1 密钥材料承载形态

| 承载形态 | 用途 | 复用地基 |
|----------|------|----------|
| **secure-memory（安全内存区）** | KEK / 根密钥等长期密钥材料；标记为不可换出（no-swap）、不可被非密钥守护进程映射 | `03-内存管理.md`（VMO 属性、`MANAGE` 仅管生命周期） |
| **VMO（普通内核对象）** | 派生会话密钥、临时封装材料；按 `03` `vmo_create_child` COW 语义派生受限视图 | `03` VMO/COW child、`07` 句柄即 capability |
| **device VMO（不可写）** | 密钥材料经硬件密钥岛/TPM 封装后导出的密文 blob，落外部介质（与 `73` §4.1 同构） | `03` device VMO、`73` §4 |

- **密钥材料永不出密钥守护 pager**：raw key bytes 只在密钥守护地址空间内（secure-memory）或被硬件后端（密钥岛/TPM）内部持有；**任何 unwrap/wrap 操作由密钥守护/后端代执行**，客户端只持「能触发解封的句柄 + rights」，不持 raw key（对齐 `06` C2「密钥材料永不出 FS 服务 pager」）。
- **不进 swap / 不落明文**：secure-memory 区标记为 no-swap、no-dump；临时 VMO 密钥视图在 revoke 时由内核回收（aligned `07` §4.5「revoke 即回收」），避免密钥残留于换页/崩溃转储（`29` T-A 防控）。

### 2.2 派生收窄（与 `07` §4.5 同源）

- **派生 = `DUPLICATE` + 收窄**：子密钥句柄由父密钥句柄经 `DUPLICATE` 派生，rights 只能收窄（只能 `{KEY_UNWRAP}` 或 `{KEY_WRAP}` 之一，或仅 `READ`/`WRITE` 触发隐式语义），不能增权（对齐 `20` I3）。
- **派生树（derivation tree，沿用 `07` §5-4 自研增强）**：密钥句柄派生的传递闭包可被 derivation tree 记录，供 revoke 传播分析（对齐 `07` C2 revoke 闭环——服务端 `KEY_*` 独立于客户端 tree，客户端 revoke 不剥夺服务端卷级密钥权）。
- **会话密钥生命周期绑定 Job**：派发给应用的会话密钥句柄计入所属 Job 资源账本（`04`/`07` §4.3），Job 取消时随句柄 `revoke` 自动回收（对齐 `63` §6.2「句柄 revoke 唤醒阻塞线程」同源）。

### 2.3 回收（revoke 全断，与 `07` §5-4 / `20` I2 同构）

- **显式 close / revoke**：密钥句柄持有者 `close`/服务端批量 `revoke` 即回收对应 raw key 在客户端视图的可用权（secure-memory 内材料由密钥守护统一销毁，`03` 回收 VMO 物理页）。
- **派生链全断（T5 挡点）**：若 derivation tree 全量记录，revoke 父密钥句柄 → 传递闭包内所有派生子句柄失效（`20` I2「revoke 后不存在可用派生句柄」）；原型期若仅显式 close（`07` §5-4 待决），退化为显式路径下 revoke 即失效（承接 `29` D-T3）。
- **与 `29` 纵深第 0 层衔接**：密钥守护自身由 `32` 信任链验签拉起，其持有的 `KEY_*` 服务端权来自真 monitor（`32` 跳 2 `PCR[2]`），避免「伪造密钥守护」发假 unwrap。

## 3. 密钥生命周期（生成/封装/unwrap/轮换/撤销；与 `32` 度量基绑定）

> 本节把密钥从「生成」到「撤销」的全生命周期落到 capability 模型上，并将度量锚定到 `32` 度量基双锚（`61` 信任链）。所有生命周期操作复用 `KEY_*` right，不新增 bit。

### 3.1 生命周期阶段与门禁

| 阶段 | 操作 | 能力门禁（复用 `07`） | 承载 / 度量 |
|------|------|----------------------|-------------|
| **生成（generate）** | 密钥材料由硬件后端（密钥岛/TPM/软 CSPRNG）产生，密钥守护 mint 句柄 | `KEY_WRAP`（封装新密钥） + 受约束 mint 收窄 | 落 secure-memory / 后端内部；公钥部分经 `VERIFY`=38 验签链锚定（`32` D-SB1） |
| **封装（wrap）** | 用 KEK 封装 file key / 会话密钥，产出密文 blob | `KEY_WRAP` | 密文 blob 进 VMO/device VMO（`02`/`73`） |
| **解封（unwrap）** | 用 KEK 解封 file key 供 FS pager 解密读 | `KEY_UNWRAP`（服务端） | 解封在密钥守护/后端内执行，raw key 不出 pager（`06` C2） |
| **轮换（rotate）** | 旧 KEK/file key 重新 wrap 到新 KEK，旧密文 re-wrap | `KEY_WRAP`（重新封装权威） + revoke 旧句柄 | 新密文 Merkle 根 extend 进度量基（`32` §3.2 / `61` §5.3） |
| **撤销（revoke）** | 密钥句柄 `revoke`/销毁 raw key 材料 | 服务端 `MANAGE`（仅管句柄对象生命周期，非密钥操作权） + revoke 派生链 | secure-memory 销毁、`03` VMO 回收 |

### 3.2 与 `32` 度量基绑定（密钥不可被静默替换）

- **密钥材料度量**：KEK / 根密钥的哈希作为「密钥状态指纹」，在生成/轮换时 extend 进软件度量寄存器（或真实 PCR，若硬件有 TPM，对齐 `32` §3.4）。
- **密钥证书度量**：密钥证书（公钥 + 签名）验签消费 `VERIFY`=38，验签通过的密钥材料指纹并入 `.msys` 度量基双锚（`32` §3.2），与 `.msys` 挂载（`32` 跳 3 / `61` §6.3）同一信任门槛。
- **引导期密钥可用性**：密钥岛/TPM/软实现的密钥材料根由 `32` 公钥根分档（A/B/C）锁定的信任链传入（`32` D-SB1/SB8），boot 期完成密钥后端初始化并 extend `PCR[2]`（monitor 自度量，对齐 `32` §3.1），保证「密钥操作权确由真 monitor/真密钥守护持有」。

### 3.3 轮换与 capability 回收协同（待决 K-78-5 详述）

- 轮换 = `KEY_WRAP` 重新封装（新 KEK）+ 旧密钥句柄 `revoke`（派生链全断）。二者必须原子：re-wrap 完成前不 revoke 旧句柄（防解密断链），re-wrap 完成后立即 revoke 旧句柄并 extend 新度量（`61` §5.3）。
- 与 `07` §5-4 derivation tree 全量与否的待决直接耦合（T5 挡点成熟度，承接 `29` D-T3）——若仅显式 close，轮换回收退化为显式路径。

## 4. 与 `.mimg`/`.msys` 信任链协同（密钥岛度量 extend、引导期密钥可用性）

> 本节把密钥后端（硬件密钥岛 / TPM）的度量与 `61` `.mimg` 信任链 + `32` 度量基衔接，声明密钥在 boot 期的可用性边界。不替 `61`/`32` 拍板块层格式，只声明协同点。

### 4.1 密钥岛度量 extend 点（与 `32` 信任链逐跳对齐）

| 跳（`32` §3.1 / `61` §5） | 密钥维度动作 | 度量 extend 点 |
|---------------------------|--------------|----------------|
| 跳 0–1（固件→bootloader→内核） | 公钥根分档锁定（A/B/C，`32` D-SB1） | `PCR[0]`/`PCR[1]`（既有） |
| 跳 2（monitor 自度量） | 密钥守护由真 monitor 派生 `KEY_*` 服务端权 | `PCR[2] = extend(hash(monitor) || hash(init caps))`（`32` §3.1） |
| **跳 2.5（密钥后端初始化，本文新增协同点）** | 密钥岛/TPM 自检 + 根密钥加载；或软实现载入档 C 公钥比对 | **`PCR[2]` extend 密钥后端状态**（或独立密钥度量寄存器，K-78-2 待决） |
| 跳 3（`.msys` 挂载） | FS 服务消费 `VERIFY` 验 `.msys`，密钥 unwrap 启用 | `PCR[3] = extend(hash(.msys volume root))`（`32` §3.2） |

> 关键：**密钥后端的可信状态必须 extend 进度量链**，使「引导期密钥可用性」可被下游密码学验证（对齐 `32` §1.2「度量累积而非孤立」）。密钥岛/TPM 的自检结果（固件版本、防回滚版本号）作为 extend 输入，防「降级密钥后端」（`32` §3.2 回滚保护同源）。

### 4.2 引导期密钥可用性（与 `61` `.mimg` 信任链）

- **`.mimg` 信任链承载密钥后端初始化**：`61` 把密钥后端初始化作为 `.mimg` 信任链的一环——bootloader 验签内核后即初始化密钥后端、加载根密钥（来自 `32` 公钥根分档），`.mimg` 携带的恢复指针（C61-4）在引导级恢复时同样先重建密钥后端再恢复 `.msys`（对齐 `73` P-73-5「引导级恢复与运行时 repoint 共用信任链」）。
- **五架构引导期密钥差异**：见 §6，密钥后端薄层在引导期的初始化差异封死在 `arch/<arch>` 与设备驱动薄层，密钥可用性语义（extend 点、unwrap 启用时机）五架构一致。
- **无密钥后端时的降级**：软实现（档 C，`32` D-SB8）在 i386 老 BIOS 下以「已知良值比对」载入密钥根，密钥后端度量退为 software 比对（与 `32` 第 0 层降级同源），威胁模型须显式标注（`29` D-T6 同类）。

### 4.3 与 `06` `.msys` 原子 repoint 的密钥协同

- 密钥轮换（§3.3）导致的密文变更 → 新 `.msys` 卷必须先过 Merkle 度量基（`61` §6.2）才能 repoint（`06` §4.3）——与 `73` §1「三层 repoint 同构」一致：密钥状态切换就是一次能力重绑 + 一次度量 extend，不引入第二种切换机制。

## 5. 备份加密协同（`73` 外部备份加密路径；离线介质密钥分离）

> 本节把「备份加密」完全收敛到 `73` §4.3 已定义的导出路径与 `06` C2 密钥=capability，不引入新密钥 escrow right、不新增 right bit。

### 5.1 复用 `73` §4.3 备份加密路径

- **静止即密**：备份落到外部介质前，按 `06` §4.2 per-extent 加密（密钥 unwrap 权 = 文件/卷句柄 right）。备份服务持 `WRITE` 句柄则写受加密语义覆盖；**密钥材料永不出 FS 服务 pager**（`06` C2），外部介质只剩密文 + 校验和（对齐 `73` §4.3）。
- **复用 `KEY_UNWRAP`/`KEY_WRAP`（服务端专用、已冻结）**：备份加密/解密复用既有 `KEY_*` right（与运行时文件加密完全同构），客户端仅以 `READ`/`WRITE` 触发，不新增 bit（对齐 `73` §4.3「不新增 right bit」铁律）。
- **device VMO 导出**：备份经 `03` device VMO（不可写）+ `60` 设备能力导出到离线介质，与 `73` §4.1 同构；离线介质拔出时句柄 `revoke`（`07` §4.5）即回收访问权。

### 5.2 离线介质密钥分离（与 `73` P-73-2 衔接，K-78-3 待决）

- **密钥分离策略**：离线备份的密钥根来自 `07` root-of-trust 能力（与 `.msys` 同源，`32` 跳 1/2）；恢复时由监督者/恢复服务经合法句柄 unwrap（对齐 `73` §4.3「离线介质密钥管理」）。
- **是否引入离线专属密钥 escrow**：本文建议**复用 `06` C2 卷密钥层次**，不引入离线专属密钥 escrow right（不新增 bit，与 `07`「领域专属 bit 不复用 `MANAGE`/`GRANT`」纪律一致）；是否支持「无密钥也能验签、需密钥才解密」的分层由 `73` P-73-2 协同定稿（本文不重复拍板）。
- **与 `32` 公钥根分档一致**：离线备份密钥的根锚定介质选择（硬件锚档 A/B vs 软实现档 C）与 `32` D-SB1/SB8 同源——高保障架构走硬件锚定、i386 走档 C 显式降级。

### 5.3 备份集的度量与可验证（与 `32`/`61` 同构）

- 每个备份集带「包级 ed25519 签名 + 卷 Merkle 根」（`73` §4.4），恢复前先验签 + 度量，与 `.mimg`/`.msys` 挂载同一信任门槛。
- 备份集 Merkle 根复用 `.msys` 度量基（`32` §3.2），不另建度量树（对齐 `73` §5.1）。

## 6. 五架构薄后端（硬件密钥岛 / TPM / 软实现差异封薄层）

> 本节把密钥后端的架构差异**封死在薄层**，逻辑（capability 门禁、生命周期、度量 extend、备份协同）五架构同源。对齐 `63` §7「netstack 仅 NIC 驱动层差异」与 `73` §6「仅设备驱动层差异」的同构纪律。

### 6.1 三类后端与差异封薄层

| 后端类型 | 适用条件 | 密钥材料承载 | 度量 extend 实现 | 薄层位置 |
|----------|----------|--------------|------------------|----------|
| **硬件密钥岛（key island / 安全飞地）** | 有硬件密钥岛架构（类 macOS SEP / Android Titan M 思想） | 密钥材料锁在硬件飞地，内核只持句柄 | 飞地自检结果 extend `PCR[2]`（或专属密钥 PCR） | `arch/<arch>` + 设备驱动薄层 |
| **TPM 2.0** | 有 TPM 的 x86_64/aarch64 等板 | 密钥材料由 TPM 内部持有，PCR 真实累积 | 真实 `PCR[2]` extend（`32` §3.4） | TPM 驱动薄层（排除出 TCB，用户态/早期 C 之外） |
| **软实现（software KMS）** | i386 老 BIOS（档 C）或无硬件锚架构 | 密钥材料落 secure-memory（no-swap） | 软件度量寄存器比对（档 C 降级，`32` D-SB8） | 纯 Rust 用户态密钥守护 |

> **五架构同源论断**：三类后端的**对外接口完全一致**——密钥守护向内核暴露的仍是 `KEY_UNWRAP`/`KEY_WRAP` 门禁的同一 capability 操作集合；差异只在「raw key 材料物理上由谁持有、度量 extend 落在真实 PCR 还是软件寄存器」。这与 Fuchsia「Zircon 无 TPM 依赖但支持」（`32` §3.4 引用）同源：后端可插拔、能力模型不变。

### 6.2 五架构收敛表（与 `32` §5 信任锚同源）

| 架构 | 后端类型（典型） | 信任锚分档（`32` D-SB1） | 密钥度量 sink | MeuOS 取舍 |
|------|------------------|--------------------------|---------------|-----------|
| x86_64 | 硬件密钥岛 / TPM 2.0 | 档 A（eFUSE/UEFI NVRAM 锁公钥哈希） | 真实 PCR | 标准 UEFI SB 链 + TPM PCR 累积；远程证明后置（`32` D-SB7） |
| aarch64 | 密钥岛 / TPM（可选） | 档 A（eFUSE）或 档 B（bootloader 内置） | 真实 PCR / 软件寄存器 | 类 x86_64；无 Titan M 类则用 bootloader 内置公钥（档 B） |
| riscv64 | 软实现 / OpenSBI 内置密钥 | 档 B（OpenSBI 内置公钥） | 软件寄存器为主 | OpenSBI 作为可信度量起点；无硬件锚时退档 B |
| loongarch64 | 软实现 / EFISTUB 内置 | 档 B（EFISTUB 内置） | 软件寄存器 | 同 aarch64 降级档 |
| i386（老 BIOS） | **软实现（档 C 降级）** | 档 C（软件可信根） | 软件度量寄存器 | 关键降级区：公钥硬编码比对、无密码学锚定（`32` D-SB8 / `29` D-T6 同类）；密钥材料落 secure-memory，威胁模型显式标注 |

### 6.3 薄层边界纪律（不引入新内核原语）

- **密钥后端驱动排除出 TCB**：硬件密钥岛/TPM 驱动作为用户态或早期 C 薄层（`02` 允许早期 C），**不进 Rust TCB 核心**；度量累积逻辑（extend = hash(prev||new)）极小可入早期层（`32` §3.4 DMZ 原则）。
- **i386 非降级密钥语义**：i386 走软实现，但密钥能力模型、生命周期、备份协同与 64 位**等价**（差异仅在信任锚级别 `32` 第 0 层降级，运行期 capability 模型完整 `29` D-T6）。不削弱密钥管理语义，只削弱 boot 溯源。
- **五架构二进制一致**：密钥守护逻辑（capability 门禁、派生收窄、revoke 回收、备份协同）为架构无关组件，与 `03`/`06`/`07` 抽象解耦；差异仅落在 `arch/<arch>` 后端薄层 + 设备驱动薄层（对齐 `63` §7、`73` §6.1）。

## §8 第十轮自主采纳裁决（待大喵复核）

> 第十轮收口期间，指挥官对文档内所有「需大喵拍板」架构级项一律先自主采纳、待大喵复核。本节记录 `78` 两项架构级待决项的采纳立场，待大喵复核闭环。

**K-78-1（密钥 right 细分子项）**：
- 默认不扩展 `KEY_*` right 子项，维持 `07` §4.1 已冻结的 `KEY_UNWRAP`(bit7) / `KEY_WRAP`(bit8) 两 bit 纪律（不复用 `MANAGE`/`GRANT`，不新增 bit）。
- 生成/轮换/派生等细分子项一律走「受约束 mint（`07` §4.5）收窄」实现，即 `KEY_WRAP`（封装新密钥）+ `KEY_UNWRAP`（解封派生材料）的组合语义，不私占 bit48+。
- 若未来执行层发现不可调和的混淆风险，再回到 `07` rights 冻结表走修订式追加流程，不在本轮自决新增 bit。

**K-78-2（密钥岛度量 extend 点）**：
- 默认密钥后端（硬件密钥岛 / TPM / 软实现）度量 extend 进**独立密钥度量寄存器**（如专属 `PCR[7]` 或软件等价寄存器），不挤占既有 `32` §3.2 度量基双锚的 `PCR[0]`–`PCR[4]` 槽位。
- 既保护 monitor 自度量 `PCR[2]` 与 `.msys` 挂载 `PCR[3]` 的既得语义（避免密钥后端状态污染 trust chain 跳 2/3 的度量指纹），又能让「引导期密钥可用性」被独立校验（对齐 `32` §1.2「度量累积而非孤立」）。
- 五架构收敛：x86_64/aarch64 走真实 TPM PCR（档 A），riscv64/loongarch64 走软件等价寄存器（档 B），i386 软实现走 software 比对（档 C 降级，与 `32` D-SB8/`29` D-T6 同源）；extend 接口一致、薄层封死。

**reasoning 决策（2026-08-03）—— K-78-1**：**维持不扩展 `KEY_*` right 子项**（同意指挥官原占位）。理由——(1) **TCB 体量**：每多一个 bit 都要在 capability 监视器 `check_rights`、rights 矩阵、inspects 子树、`65` 审计字段四处增加维护点，长期不变量的维护代价线性增长，而受约束 mint + derivation tree 已经用 O(2) 的语义覆盖了「生成/轮换/派生」三类操作，再加 bit 不带来表达力收益。(2) **安全模型自洽性**：`07` §4.1 的「不复用 `MANAGE`/`GRANT`、领域专属 bit」纪律在历史上对 `NET_*`/`BLOCK_*`/`GPU_*`/`KEY_*` 都成立——这些细分都**没有**再拆 `KEY_GENERATE`/`KEY_ROTATE`/`KEY_DERIVE`，一致性要求密钥域同样不拆；新增 bit 必须经 `07` 修订式追加流程（与 D-SB 系列同构），不应在 K-78 这种子文档里私自决定。(3) **五架构同源可行性**：密钥后端（硬件密钥岛 / TPM / 软实现）在五架构上的差异已经封死在 `78` §6 薄层，能力模型层面是同源的——细分子项会导致"在某架构上可拆、在另一架构上不可拆"的伪需求，五架构同源论证反而被破坏。(4) **长期可维护性**：未来若执行层发现真实不可调和的混淆风险，回到 `07` §4.1 走修订式追加流程——这是更稳的入口；本文 §7 K-78-6 的"密钥守护受约束 mint 默认封顶为 `{READ,WRITE,EXECUTE}`"已经给出"防服务端被诱导下发 `KEY_*`"的执行层兜底，与扩 bit 互不替代。被否决选项：新增 `KEY_GENERATE`/`KEY_ROTATE`/`KEY_DERIVE` 三 bit（增加 TCB 维护点 / 与既有领域专属 bit 纪律冲突 / 触发 `07` rights 修订流程）。

**reasoning 决策（2026-08-03）—— K-78-2**：**维持独立密钥度量寄存器**（同意指挥官原占位）。理由——(1) **PCR[2] 语义不可挤占**：`32` §3.2 已定 `PCR[2]` = `extend(hash(monitor) || hash(init caps))`，承载 monitor 自度量 + 初始 capability 集哈希，是真 monitor 与伪造 monitor 的分水岭（`32` D-SB1 同源）；把密钥后端状态塞进 `PCR[2]` 会让"密钥岛固件回滚"也变成"monitor 自度量变化"，污染下游 `.msys` 挂载校验（`32` 跳 3 误拒挂载）。(2) **度量正交性**：密钥后端状态与 `.msys` 挂载决策正交——密钥岛挂了 FS 该挂还得挂、密钥岛修好密钥 unwrap 可恢复；强行合并会让"密钥岛暂时不可用"被放大为"系统启动失败"，违反 `32` §1.2「度量累积而非孤立」原则。(3) **TPM 2.0 规范对齐**：TCG TPM 2.0 Part 1 §17 明确 `PCR[0..7]` 给平台/启动链、`PCR[8..15]` 给 OS/application、`PCR[16..22]` 给 debug / dynamic、`PCR[23]` 给 application-specific；选 `PCR[16]`（debug/dynamic 区）作为密钥后端度量 sink 既合规又不挤启动链，与五架构收敛（x86_64/aarch64 走真实 `PCR[16]`、riscv64/loongarch64 走软件等价寄存器、i386 软实现走 software 比对）路径一致。(4) **撤销/演进友好**：独立寄存器让"密钥后端升级/轮换"有独立的度量指纹可被远程证明（`32` D-SB7 后置 ATTEST 路径）消费，无需触动启动链度量。被否决选项：复用 `PCR[2]` 与 monitor 自度量合并（语义污染 / 放大启动失败半径 / 与 TPM 2.0 既有 PCR 分区冲突）。
