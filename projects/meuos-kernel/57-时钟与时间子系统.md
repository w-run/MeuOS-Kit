## 1. 「应该是什么样」推演（解构型）

### 1.1 总纲：内核应提供什么样的时间抽象

先不问「MeuOS 现在能多准」，而问「在一个 **capability 唯一、重服务出核、lean hybrid** 的内核下，一个进程**应该**如何获取时间、如何请求在未来被唤醒、如何不被时间抽象本身出卖」。

推演起点——MeuOS 已定架构（`00`/`01`/`04`/`07`/`10`）：
- `07` §2 已把 **timer 列为统一带类型内核对象**（与进程/线程/端点/设备同位）；句柄即 capability（`00` A1）天然继承——timer 句柄应当就是 capability。
- 调度器靠 `task_tick` 钩子实现异步抢占（`04` §4.3 `sched_class`），`tick` 的时基来自底层时钟源（`10` §4.2 定时器是内核态快速驱动、生死相关）。
- 单调钟与墙钟分离已是现代内核共识（`00` 三大方向均依赖「可预测 + 可校准」的时间）。

由此推演出理想时间画像的四条（解构型基线）：

1. **时间抽象 = 一组命名 clock，而非一个全局 `gettimeofday`**。内核应暴露 `CLOCK_MONOTONIC`（不受 NTP 跳变影响、只增不减、用于间隔测量与超时）、`CLOCK_REALTIME`/`WALL`（人类日历时间、可被校准、可回拨）、以及 `CLOCK_BOOTTIME`（含 suspend，用于 watchdog/uptime）等。单调与墙钟必须**从内核对象层面分离**，因为二者的不变性契约不同。
2. **时钟源（clocksource）= 与 clock 视图解耦的底层计数**。所有 clock 视图归一化到同一个稳定计数器（如 TSC / Generic Timer），clock 视图只是「计数器 × 标度 + 偏移」的投影；标度/偏移由校准守护进程经 capability 受控调整（墙钟可改，单调钟偏移恒为 0、标度恒为 1）。
3. **定时器 = 一等内核对象 + capability**，提交模型应是「句柄 + 相对/绝对 deadline + 松弛(slack)」，而非 POSIX `ITIMER`/`setitimer` 那种全局进程状态机。定时器触发经 EventPort/Channel（`05`）投递，与 IPC 通知同构，不引入第二套通知机制。
4. **时间相关特权 = capability，而非 uid/cap 提权**。调整墙钟（`clock_settime`）、设置高频/全局定时器应受特定 right 约束，等价 `CAP_SYS_TIME` 拆成 MeuOS 的对象级 right，避免「持 root 即改全网时间」的大权。

### 1.2 解构型反问：时间为什么是「两个钟」而非「一个钟」

为什么不能只给一个全局时间？因为**两种用途的不变性契约互相冲突**：

- **测量间隔**（「这段代码跑了多久」「这个锁等多久超时」）要求时间**只增不减、不被任何人改写**——否则 NTP 把墙钟回拨 1 秒会让一个 5 秒超时提前 1 秒触发，或让 `monotonic` 差值变负。
- **记录日历**（「日志打什么时间戳」「证书何时过期」）要求时间**可被校准到真实世界**——秒闰、NTP 步进、时区都需反映。

把两者压进一个钟，就必须让其中一种用途向另一种妥协（Linux 早年 `gettimeofday` 可被 `settimeofday` 回拨就是经典坑）。**解构结论**：单调钟与墙钟从内核对象起就是两个独立 clock，各自维护独立的「counter → time」映射；墙钟的 offset/scale 可变，单调钟的 offset 恒 0、scale 恒 1（永不步进、永不回拨）。这是非缝合怪的最低代价分离。

### 1.3 解构型反问：定时器是「内核对象」还是「capability」

定时器若只是一个「进程内的全局状态」（POSIX `timer_create` 挂到进程、`SIGALRM` 投递），则：
- 与 MeuOS `07` §2「timer 是统一内核对象」直接冲突——内核对象生来就带 handle、带 rights、可被 mint/revoke；
- 与 `05`「信号从零简化为 event 对象」冲突——定时器不应复用已废除的信号机制，而应经 EventPort 投递。

**解构结论**：定时器从出生就是带 handle 的内核对象（对齐 `07` §2 已列出的 timer 对象）；其提交模型应能独立于线程存在（挂在 Job 或特定线程上），触发时向一个 EventPort/Channel 投递一个 timer-fired 事件。这样既与 capability 模型同源，又与 IPC 通知机制合一，不造第二套异步机制。

## 2. 多系统参照对比表

### 2.1 时钟/时间抽象多系统参照

| 系统 | 时钟抽象（clock 视图） | 底层时钟源（clocksource） | 定时器模型（提交/投递） | 对 MeuOS 的取舍 |
|---|---|---|---|---|
| **Linux** | `clock_gettime` 多 clock：`CLOCK_MONOTONIC`/`REALTIME`/`BOOTTIME`/`MONOTONIC_RAW`/`TAIfs`；`CLOCK_MONOTONIC` 不受 NTP 影响 | `clocksource` 框架（TSC/HPET/ACPI_PM），`clocksource_register` 选最稳定者；`timekeeping` 维护 `xtime`/offset/raw；NTP 经 `ntp_*` 做 freq/offset 校准 | `hrtimer`（红黑树 + 绝对 deadline，纳秒级，取代旧 `timer_list` 粗粒度 tick）；POSIX `timer_create` + `SIGEV_THREAD`/`SIGEV_SIGNAL`；`timerfd` 把定时器变成可 poll 的 fd（与 epoll 合一） | **吸收**：多 clock 视图分层 + `hrtimer` 基于绝对 deadline 的红黑树 + `timerfd`「定时器即文件/可等待对象」思想（对标 MeuOS timer 即内核对象 + EventPort 投递）；**拒绝** `SIGEV_SIGNAL` 走信号（MeuOS 无信号，`05`） |
| **Windows** | `QueryPerformanceCounter`（QPC，单调高频）、`GetSystemTime`/`GetSystemTimePreciseAsFileTime`（墙钟，100ns 单位）、`QueryUnbiasedInterruptTime`（不含 suspend 的单调）；`GetTickCount64` 粗粒度 | `ACPI`/TSC/`HPET`；`QPC` 返回稳定单调计数器；系统时间由 `time` 服务维护 | `CreateWaitableTimer` + `SetWaitableTimer`（绝对/相对、周期、`APC`/`IoCompletion` 投递）；`timeBeginPeriod` 调整系统时钟分辨率（典型 1ms→0.5ms） | **吸收**：单调(QPC)与墙钟(GetSystemTimePrecise)显式分离；waitable timer 即可等待内核对象（对齐 timer 即内核对象）；**参照** 时钟分辨率调整（`timeBeginPeriod` 式全局分辨率协商是 DoS/能耗隐患，MeuOS 用 per-timer slack 取代） |
| **Fuchsia / Zircon** | `zx_clock_get_monotonic`（唯一单调钟，无墙钟 syscall——墙钟由用户态 `clock` 服务经 zircon clock handle 提供）；zircon **clock 本身是句柄对象**：`zx_clock_create` 可建受控时钟（含「时钟被冻结/调慢」的 `ZX_CLOCK_OPT_*` 选项，供测试/确定性回放） | 底层 `ticks`（`zx_ticks_get`，monotonic raw counter）+ `zx_ticks_per_second` 标度；zircon 把 raw counter 与 clock 视图解耦 | `zx_timer_create`（挂 Job 或线程）+ `zx_timer_set`（绝对/相对 deadline + `ZX_TIMER_SLACK_*` 松弛）+ `zx_timer_cancel`；触发经 `zx_object_wait_one`/port 投递 | **范本（最强）**：① 单调钟唯一、墙钟用户态化；② **clock 与 timer 都是句柄对象**，caps 可 mint/rights 约束；③ `slack` 松弛合并机制（节能 + 对齐）；④ clock 可「受控创建/冻结」用于确定性测试——直接成为 §3/§4 蓝本 |
| **seL4** | 无丰富时间抽象；时间主要服务于调度与确定性——计时靠平台 timer 设备，抽象极薄 | 平台 timer（ARM `CNTPCT`/x86 `TSC`/RISC-V `mtime`）；seL4 不替代 OS 时间服务 | 无内建 POSIX 定时器；用户态 OS 层（如 sel4utils/Genode）自建 timer 服务 | **参照**：时间抽象出核——内核只给「稳定计数器 + 触发中断的 timer 设备」，clock/timer 服务由用户态 OS 提供；与 MeuOS「重服务出核」同源，但 MeuOS 把 timer 对象留核（`07` §2）以保确定性唤醒 |
| **macOS / XNU（Mach）** | `mach_absolute_time`（单调，纳秒经 `mach_timebase_info` 标度）、`gettimeofday`/`clock_get_time`（墙钟，Mach `clock` 端口：`SYSTEM_CLOCK`/`CALENDAR_CLOCK`） | `TSC`/`PMU` 等，经 `mach_timebase_info` 的 `numer/denom` 标度把 tick 转 ns | `mk_timer_create`/`mk_timer_arm`（Mach timer，相对 deadline）+ `thread_call` 内核回调；用户态用 `dispatch_source`(GCD) 包裹 timer，经 runloop 投递 | **吸收**：`mach_absolute_time` 单调 + `mach_timebase_info` 标度（= 本文「counter × scale 投影」）；`dispatch_source` 把 timer 变成事件源（对标 EventPort 投递）；Mach `clock` 端口 = 把 clock 当对象（部分同源） |

### 2.2 取舍结论

- **拒绝**「Linux `settimeofday` 回拨式单钟」与「POSIX `SIGEV_SIGNAL` 定时器」：前者违背单调契约，后者与 MeuOS 无信号（`05`）冲突。
- **采纳** Zircon 的核心三件套作为蓝本：① 单调钟唯一、墙钟用户态化（capability 受控的 clock handle）；② **clock 与 timer 都是句柄对象**，可 mint/rights 约束；③ 每定时器 `slack` 松弛合并（节能、对齐唤醒）。
- **采纳** Mach「counter × timebase_info 标度」作为 clocksource→clock 视图的归一化公式（解耦底层计数器与上层 clock）。
- **采纳** Linux `hrtimer` 基于绝对 deadline 的红黑树 + `timerfd`「定时器即可等待对象」思想，但把「可等待对象」落为 MeuOS 的 EventPort/Channel 投递而非 fd。
- **跟踪** seL4「时间抽象出核」的极简态度：MeuOS 不把墙钟校准逻辑、NTP/PTP 协议留核，只留「稳定计数器 + 可设比较值的 timer 设备 + 受控 clock 句柄」；校准守护进程是用户态服务。

## 3. MeuOS 时钟与时间抽象设计

### 3.1 时钟分层：clocksource → clock 视图

```
┌──────────────────────────────────────────────────────────────┐
│  clock 视图（命名 clock，用户态经 syscall/handle 读取）          │
│  ├─ CLOCK_MONOTONIC   偏移=0 / 标度=1 / 永不步进 / 永不回拨      │
│  ├─ CLOCK_REALTIME    偏移/标度可变（经 clock handle 受控校准）  │
│  ├─ CLOCK_BOOTTIME    含 suspend 的 uptime 单调钟               │
│  └─ CLOCK_TAI         原子时（无闰秒跳变，可选，对标 Linux TAI） │
├──────────────────────────────────────────────────────────────┤
│  clock 句柄对象（07 §2 内核对象；wall 时钟的 offset/scale 由     │
│  持 CLOCK_ADJUST right 的校准守护进程经 handle 调，monotonic     │
│  句柄不可调）                                                    │
├──────────────────────────────────────────────────────────────┤
│  clocksource 抽象（arch/timer 后端：TSC/Generic Timer/rdtime…） │
│  time = counter × scale + offset  （Mach timebase_info 同构）  │
└──────────────────────────────────────────────────────────────┘
```

- **clocksource 是底层计数器的归一化层**：每个架构提供一个 `arch_cycle_now()` 与一个固定的 `numer/denom` 标度（`mach_timebase_info` 同源），把不同频率/不同语义的硬件计数器归一成纳秒。`28` §6 已列的五个架构时钟源（x86_64 invariant TSC / aarch64 Generic Timer / riscv64 time CSR+`Sstc` / loongarch64 稳定计数 / i386 TSC-or-HPET）即本层后端，本文不再复述，仅在 §6 讨论抽象层应如何**吸收**其差异而非暴露之。
- **clock 视图是投影**：任何 clock 的读数 = `clocksource_now() × scale + offset`。单调钟 `scale=1, offset=0` 且内核禁止改写；墙钟 `scale/offset` 由校准守护进程经 clock handle 调整。
- **墙钟用户态化**：内核只维护一个「单调基准 + 受控的墙钟 offset 句柄」；真正把 (offset, scale) 收敛到 UTC 的 NTP/PTP 协议栈是用户态服务（`10`/`25` 同构出核），它持 `CLOCK_ADJUST` right，定期 `clock_adjtime` 式微调。

### 3.2 单调钟与墙钟分离（本文核心）

| 维度 | `CLOCK_MONOTONIC` | `CLOCK_REALTIME`(WALL) |
|---|---|---|
| 单调递增的不变性 | 强制：只增不减，不受任何 settime 影响 | 不保证：可被校准步进/回拨 |
| 受 NTP 步进影响 | 否 | 是（freq 微调也只动 offset，不动 monotonic） |
| 用途 | 间隔测量、超时、调度时基、RT deadline（`28`）、性能剖析 | 日志时间戳、证书有效期、文件 mtime、人类展示 |
| 内核对象可写性 | 句柄不可调（offset 恒 0） | 句柄受 `CLOCK_ADJUST` right 约束可微调 |
| 闰秒/时区 | 无关 | 由用户态墙钟服务处理（内核只给 offset） |
| 回放/冻结（测试） | 派生测试钟可冻结（`ZX_CLOCK_OPT_*` 同源） | 派生测试钟可冻结 |

- **分离的内核契约**：单调钟读数是「counter 直接投影」，无任何可变 offset，因此任何代码都可以安全用它做 `deadline = now + interval` 而不担心被第三者改写。墙钟读数是「counter + 受控 offset」，校准守护进程的调整只改变墙钟视图、绝不改变单调钟。
- **派生时钟（determinism）**：采纳 Zircon——可 `clock_create` 出一个**派生的、受控的子时钟**（初始与父钟同相，之后可被持有者冻结/调慢），用于确定性回放测试与沙箱时间隔离。子时钟仍是句柄对象、受 rights 约束，不污染全局单调钟。
- **与 `05` 协同**：墙钟/单调钟读取是纯 syscall，不经过 IPC；但「等待直到某 wall 时刻」= 定时器（见 §3.4）而非轮询 `clock_gettime`。

### 3.3 时钟校准与漂移（calibration / drift）

- **频率漂移（drift）来自硬件**：晶振有 ppm 级误差，温度/老化使其变化。`clocksource` 标度 `numer/denom` 是出厂标称值，需运行时微调 `scale` 以跟踪真实频率——这与「墙钟 offset 调整」是两件事：频率微调动 `scale`（对所有 clock 视图同源），offset 调整动墙钟的 `offset`（仅墙钟）。
- **校准守护进程（用户态）**：持 `CLOCK_ADJUST` right 的用户态服务周期性读 NTP/PTP 参考，计算 (a) 频率校正（微调全局 `scale`）与 (b) 相位校正（步进/ slew 墙钟 `offset`）。**slew 优于 step**：墙钟相位用「渐进逼近」而非瞬间跳变，避免依赖墙钟的超时逻辑突跳（Linux `ntpd`/`chronyd` 的 `adjtime` 同构）。
- **单调钟永不漂移修正？** 单调钟 `offset=0`，但其「真实纳秒」精度仍受 `scale` 误差影响——即两个单调读数之差的纳秒值会因 `scale` 不准而带 ppm 误差。这是所有系统的共有局限；MeuOS 把 `scale` 微调留内核（clocksource 层），保证单调钟在「相对间隔」意义上单调且尽量准，但不虚构绝对精度。
- **跨架构标定差异**：`28` §6 已指出 i386 非 invariant TSC 需回退 HPET/PIT、riscv64 缺 `Sstc` 可能陷入 M 态。校准层必须**感知 clocksource 的稳定性等级**（invariant / 需外部标定 / 需陷入），对不稳定源用更高频的标定循环与更保守的 `scale` 收敛。

### 3.4 定时器提交模型（timer submission）

- **定时器 = 一等内核对象，挂 Job 或线程上**：`timer_create(clock, target)` 返回一个 timer 句柄（`07` §2 的 timer 对象）；`timer_set(timer, deadline, slack)` 提交绝对/相对 deadline；触发时向绑定的 EventPort/Channel 投递 `TIMER_FIRED` 事件（对齐 `05` 事件通知，不复用信号）。
- **绝对 deadline 优先于相对**：内部以绝对 tick 存于红黑树（`hrtimer` 同构），相对 deadline 在提交时由 `clock_now + interval` 转绝对。这样时钟校准（wall offset 调整）不会让已提交的单调定时器漂移（单调钟不变），而墙钟定时器在校准 slew 后应重新归一——实现上单调定时器挂在 `CLOCK_MONOTONIC`、墙钟定时器挂在 `CLOCK_REALTIME`，二者树分离。
- **slack 松弛合并（节能核心）**：每个 `timer_set` 带 `slack`（最早触发窗 `[deadline, deadline+slack]`）。调度器/时钟中断在处理到期时，把落在同一 slack 窗内的多个定时器合并到同一 tick 触发（Zircon `ZX_TIMER_SLACK_*` 同源）。slack 越大，唤醒越能对齐到 cache/核唤醒边界，省电且减抖动——**取代** Linux `timeBeginPeriod` 式全局分辨率协商（后者是全局 DoS/能耗隐患）。
- **一次性 vs 周期**：周期定时器 = 触发后按 `interval` 重新入树（或硬件周期比较值）；优先实现一次性，周期用「触发后用户态重设」起步，硬件周期比较（`TSC Deadline`/`CNTP_CVAL`）留给高频/RT 场景（`28` §3.2 留核路径）。
- **取消与幂等**：`timer_cancel` 从树摘除；句柄 `close`/`revoke` 自动取消（对齐 `07` 撤销传播）。

## 4. 定时器提交模型与 capability（07）兼容

### 4.1 timer 句柄 = capability（直接继承 `07` §2）

`07` §2 已把 **timer 列为统一带类型内核对象**；依 `00` A1「句柄即 capability，权限随句柄走」，timer 句柄天然是 capability：

- timer 句柄的默认 rights = `TIMER_SET` + `TIMER_CANCEL`（自身句柄只能设/取消自己的定时器），**不含** `TIMER_MINT`（派生子定时器句柄）与 `CLOCK_ADJUST`。
- timer 句柄可由持有者 `mint` 出受限子句柄（如只许 `TIMER_CANCEL`、不许 `TIMER_SET`），经 IPC 委托给协作方——与 `05` cap-transfer 同构。这与 Zircon「clock/timer 都是可 mint 的句柄」完全对齐。
- 定时器触发事件投递到 EventPort/Channel（`05`），EventPort 自身是 capability（`00` A8），故「谁收定时器事件」也受 capability 约束，无全局信号反弹。

### 4.2 时钟调整权 = 对象级 right（拒绝 `CAP_SYS_TIME` 大权）

调整墙钟是特权操作，但 MeuOS 不引入 `CAP_SYS_TIME` 式提权大权（`07` §4.6「Linux capability 拆到具体对象权限」同源）：

| 操作 | 所需 right | 对照 Linux |
|---|---|---|
| 读任意 clock | 无（syscall 默认开放） | `clock_gettime` 无 cap |
| 创建 timer 句柄 | 无（每进程廉价内核对象） | `timer_create` 无 cap |
| `CLOCK_ADJUST`（微调墙钟 offset/scale） | 墙钟 clock 句柄的 `CLOCK_ADJUST` right | `CAP_SYS_TIME` |
| 创建派生/可冻结子时钟 | clock 句柄的 `CLOCK_MINT` right | 无对应（Zircon 扩展） |
| 高频/全局分辨率强制 | 不提供（`slack` 取代） | `CAP_SYS_TIME` + `timeBeginPeriod` |

- **默认 deny**：任何进程（含兼容层旧二进制）调用 `clock_settime` 若无对应 clock 句柄的 `CLOCK_ADJUST` right，直接 `EPERM`（fail-closed，对齐 `07` pledge 越界即终止语义）。
- **与 `07` rights 位图的关系（待决）**：`CLOCK_ADJUST`/`CLOCK_MINT` 是否进 `07` §4.1 冻结的 right bit 表、占哪个 bit（`45` §3 已冻 bit 0–47、48+ 预留）——本文建议作为新 right 候选进 48+ 预留区，**不**复用 `MANAGE`/`GRANT`，与 `NET_*`/`BLOCK_*`/`AUDIO_*` 同构。具体 bit 待 `07` 协同定稿（见 §8.3 待决 T3）。

### 4.3 定时器与 Job 账本（04）的耦合

- **唤醒计数入账本**：定时器触发把线程从阻塞态变就绪态，这本身不消耗 CPU 预算，但**高频定时器是 wakeup 风暴的 DoS 向量**。建议 Job 账本（`04` §4.4）新增可选维度 `timer_wakeups`（单位时间最大唤醒次数），超限则节流后续 `timer_set`（对齐 QNX APS 式预算思想，`28` §4.2）。
- **RT 定时器走留核路径**：硬 RT 周期定时器（`28` §3.2）应直接用硬件周期比较（`TSC Deadline`/`CNTP_CVAL`），由内核态快速驱动（`10` §4.2 定时器留核）直接派发到 RT 线程，不经用户态 timer 服务 IPC 往返。
- **与 `28` `CAP_RT` 协同**：设置 RT 域定时器不引入新 right（RT 预算已由 `CAP_RT` + Job RT 带宽约束，`28` §4）；但普通定时器高频提交受 `timer_wakeups` 预算约束，避免饿死公平层。

## 5. 与调度（04 / 25）关系

### 5.1 时钟是调度的时基

- 调度器 `task_tick`（`04` §4.3 `sched_class` 钩子）的节拍来自底层 timer 设备（`10` §4.2）；无论是粗粒度 tick 还是 hrtimer 精确触发，时基都归一化到 §3.1 的 `clocksource` 纳秒。
- **tickless（无 Tick 空闲）**：采用 Linux `NO_HZ`/Zircon 同构——调度器在无就绪任务或单任务独享核时停止周期 tick，靠下一次定时器/外设中断唤醒（`27`/`40` 电源管理同源）。这要求定时器提交模型能直接驱动调度器下一个唤醒点（即 §3.4 红黑树取最早 deadline）。
- **EEVDF/RT 时间会计**：公平层虚拟时间、RT 带宽记账（`28` §4.2）都以单调钟为唯一时基——正因为单调钟不可被校准改写，调度会计不会被 NTP 步进污染。

### 5.2 定时器触发 → 调度就绪

```
timer_set(deadline) → 入 hrtimer 红黑树
        │  时钟中断/对比值命中最早 deadline
        ▼
   取到期定时器集合（slack 合并） → 向 EventPort 投 TIMER_FIRED
        │  绑定线程被唤醒
        ▼
   线程进入就绪态 → 调度器（04）按 EEVDF/RT 选 next
```

- 定时器是「未来某刻让线程就绪」的机制；它与 `meu_spawn`/`Job`（`04`）的关系是：定时器挂在 Job 或线程，Job 终止（`04` §4.5 根 Job 终止传播）时其下所有定时器随句柄回收自动取消。
- **与 `05` 协同**：TIMER_FIRED 走 EventPort/Channel，与 IPC 通知、IO 就绪通知共用同一事件多路复用（`05` §4 EventPort `CHAN` filter），用户态一个 `epoll`/port 等待即可同时收定时器、IPC、IO——对标 Linux `timerfd` + `epoll` 合一，但实现为 capability 对象而非 fd。

### 5.3 与网络栈（25）超时

- TCP RTO、keepalive、TIME_WAIT、`select`/`poll` 超时、DNS 解析超时全部建立在定时器之上。网络栈是用户态（`25` C15 已采纳），故它**自持定时器句柄**向内核 `timer_set` 请求超时，触发后经其 socket capability 关联的 EventPort 收 `TIMER_FIRED`，再驱动协议状态机——数据通路零 IPC（`25`/`19` 同构），超时控制平面走 EventPort。
- **与 `07` 协同**：网络栈持有的 timer 句柄只具 `TIMER_SET`/`TIMER_CANCEL`，无 `CLOCK_ADJUST`，无法借超时机制篡改系统时间。

## 6. 跨架构（五架构）计时源差异与抽象吸收

`28` §6 已详列五架构稳定计时源（x86_64 invariant TSC / aarch64 Generic Timer / riscv64 time CSR+`Sstc` / loongarch64 稳定计数 / i386 TSC-or-HPET）。本文从**抽象层**角度补述「如何吸收差异而非暴露之」：

| 架构 | 底层源 | 抽象层动作（arch/timer 后端职责） | 对 clock/timer 抽象的影响 |
|---|---|---|---|
| **x86_64** | Invariant TSC + LAPIC Timer + TSC Deadline | `arch_cycle_now`=`rdtsc`/`rdtscp`；TSC Deadline 作精确一次性触发；`numer/denom` 由 CPUID 标定 | 最佳基线：单调钟与 hrtimer 同源 TSC，slack 合并收益最大；RT 双验证架构之一（`28` §6） |
| **aarch64** | Generic Timer（`CNTPCT`/`CNTFRQ` + `CNTP_CVAL`） | `arch_cycle_now`=`CNTPCT`；物理计数器供内核、虚拟计数器供 VM（`26`）；`CNTP_CVAL` 比较触发 | 与 TSC 同级稳定；VM 用虚拟计数器天然隔离；RT 双验证架构之一 |
| **riscv64** | `rdtime`(time CSR) + CLINT/ACLINT `mtimecmp`；`Sstc` 提供 `stimecmp` | `arch_cycle_now`=`rdtime`；缺 `Sstc` 时设比较值需陷入 M 态（平台驱动）→ 抽象层须统一 `arch_timer_arm(deadline)` 并实测陷入开销 | 标准化较弱：`arch/timer` 抽象必须屏蔽「是否需陷入 M 态」，否则 RT 计时抖动（`28` §6 R9）泄漏进定时器精度；需双后端 |
| **loongarch64** | 稳定计数 CSR（`RDTIME`） | 自有体系，`arch_cycle_now` 对齐；成熟度待验 | M5 后移（`11` §5-4），先保证正确；抽象层同构，仅后端替换 |
| **i386** | TSC（老 CPU 可能非 invariant）+ 8254/PIT + HPET | `arch_cycle_now` 在 non-invariant TSC 时回退 HPET/PIT；`numer/denom` 须运行时标定；无 Rust TCB、纯 C（`02` C2） | RT/确定性最弱（`28` §6）；单调钟仍可用但 `scale` 标定误差更大、需更高频校准；非重点架构，定时器精度下限须文档化 |

**核心论断**：五架构差异在**时钟源稳定性与「设比较值是否需陷入」**，而非时钟抽象本身。MeuOS 用单一 `arch/timer` 后端接口（`arch_cycle_now` / `arch_timer_arm` / `arch_timer_cancel` + `numer/denom` 标度）屏蔽差异；上层 clock/timer 抽象（§3）五架构完全一致。riscv64 的 `Sstc` 缺失、i386 的 TSC 非不变性是各自定时器精度下限的**实测前置项**，应在 M5 实测而非预设。

## 8. MeuOS 推荐方案（收口）

### 8.1 推荐架构（一句话）

**单调钟唯一不可调、墙钟用户态化受控校准；clock 与 timer 都是 `07` §2 的内核对象句柄；定时器以绝对 deadline 入红黑树 + 按 `slack` 合并唤醒 + 经 EventPort 投递；底层五架构差异由单一 `arch/timer` 后端屏蔽。**

### 8.2 自主结论

1. **单调钟与墙钟从内核对象层分离**：单调钟 `offset=0/scale=1` 永不步进回拨，墙钟 `offset/scale` 经 clock handle 受控调整；NTP/PTP 校准逻辑出核为用户态服务。
2. **clocksource 与 clock 视图解耦**：所有 clock = `counter × scale + offset`（Mach timebase_info 同构），`arch/timer` 后端屏蔽五架构差异，`28` §6 的计时源即本层后端。
3. **定时器是一等内核对象 + capability**：直接继承 `07` §2 的 timer 对象与 `00` A1 句柄即 capability；提交模型 = `timer_create`/`timer_set(deadline, slack)`/`timer_cancel`，触发经 EventPort/Channel 投 `TIMER_FIRED`，不复用信号（`05`）。
4. **绝对 deadline + slack 合并**：内部红黑树按绝对 tick 存（`hrtimer` 同构）；`slack` 取代 Linux `timeBeginPeriod` 全局分辨率协商，节能且对齐唤醒。
5. **时间特权 = 对象级 right**：`clock_settime`/频率微调需墙钟句柄的 `CLOCK_ADJUST` right（拒绝 `CAP_SYS_TIME` 大权）；timer 创建默认无特权。
6. **与调度/网络同构**：时钟是 `04` `task_tick` 时基、tickless 唤醒源；网络栈（`25`）自持 timer 句柄做 RTO/keepalive，控制平面走 EventPort；定时器随 Job 终止自动回收（`04` §4.5）。
7. **五架构一致抽象**：上层 clock/timer 抽象五架构完全同构，差异仅在 `arch/timer` 后端（riscv64 `Sstc` 缺失、i386 TSC 非不变性为各自精度下限实测项，非抽象缺陷）。

### 8.3 待决项（标注是否需架构裁决）

| 编号 | 待决项 | 是否需架构裁决 | 关联 |
|---|---|---|---|

| T2 | **派生/可冻结子时钟的 rights 模型**（子时钟能否再 mint、冻结权是否独立于 `CLOCK_ADJUST`） | 否（执行层定稿，建议 `CLOCK_MINT` 涵盖） | §3.2、Zircon `ZX_CLOCK_OPT_*` |
