## 1. 为什么还需要一个「方案 B」：定位与取向

`06` 已经把「统一文件系统层」设计清楚了——但它是一份**地基性**文档，回答「FS 应该长什么样」。`00` 方向①也把「统一命名空间 + 校验和/压缩/加密 + 原子 `.msys` 更新」列为内核三大统一方向之一。本文要补足的是**第二条设计轴**：在同一地基上，给出**对存量生态最友好、最易从零渐进交付**的封装取向——这就是「方案 B」。

两条方案的本质分歧不在「存储对象要不要可验证」，而在**文件身份由什么定义**：

| | 方案 A（同僚·内容寻址 / 不可变） | **方案 B（本文·统一命名空间 + 可验证存储层）** |
|---|---|---|
| 文件身份 | 内容哈希（hash = 名），写入即新建不可变对象 | **路径（path）**，写入即把该路径指向一个新的「可验证版本」 |
| 可变性 | 不可原地变；变 = 新对象 + 引用切换 | **可写**（CoW 把每次写变成不可变 extent 版本，逻辑上仍是可变路径） |
| 工具生态 | 需内容寻址工具链 / ABI 适配 | **POSIX / 存量工具原样可跑**（open/read/write/rename/mmap 不变） |
| 验证层 | 哈希即完整性（寻址即校验） | 校验和/压缩/加密是**叠加在 extent 上的透明属性**，与应用 API 无关 |
| 去重 / 可复现 | 天然（同内容同哈希） | 间接获得（不可变 extent 内部按内容寻址去重，见 §8.2） |

**方案 B 的务实定义**：MeuOS 文件系统从零设计，但**不强制生态重写**——它保留「文件 = 一条可按名寻址、可读可写的可变路径」这一 POSIX 心智模型，把「可验证性」做成存储层的内禀属性而非寻址方式。这样 Day 1 即可让 `mcc`+`meuos-libc` 与海量 Linux 二进制以熟悉的语义运行，校验和/压缩/加密在其上**渐进叠加**，而非前置门槛。

> 一句话收口（方案 B 核心）：**统一命名空间聚合一切后端，文件走路径语义、可写，但每次写都生成一个内容可校验的不可变 extent 版本；校验和/压缩/加密对应用完全透明——既拿到内容寻址的完整性收益，又不逼生态换范式。**

## 2. 方案核心（解构型推演「应该是什么样」）

### 2.1 统一命名空间聚合所有后端（取代 /proc+/sys+/dev 拼凑）

先推演：在 capability 世界里，「文件系统」不该是「磁盘上的目录树」，而应是**一切可被按名寻址、按权访问的资源的统一平面**——普通文件、设备、进程视图、网络、服务、capability 对象，都是同一类「命名空间节点（ns-node）」。进程的「文件系统」不是全局共享树，而是它**在 spawn 时由 Job/manifest 注入的一组 `path → 节点能力` 绑定**；没被注入的路径对进程**根本不存在**（默认不可见、显式 reveal，对齐 `00` A4 / C3）。

后端（普通磁盘 FS、设备目录、进程目录、网络命名空间、挂载的 ext4/网络 FS/tmpfs）以 **mount-capability** 委托进这棵树——每个子树由对应服务经 Service Registry 注册目录能力，FS 服务作为「根聚合者」经 mount-capability 组装，**信任分散、各管各的子树**（最小 TCB）。这与 Fuchsia 的每进程 namespace 思想同源，但归属更清晰（FS 服务做根聚合 + 各服务直接暴露子树 cap）。

### 2.2 文件可写，但每次写产生一个「可验证版本」

这是方案 B 区别于方案 A 的关键工程点，也是它「保留路径语义」却能「自验证」的枢纽：

- **逻辑层（对应用）= 可变路径**：应用持有 `/home/u/f.txt` 的句柄，反复 `write` 是合法的，语义与 POSIX 一致。
- **存储层（对 FS 内部）= 不可变版本链**：每次写不是原地覆写块，而是 CoW 出一个**新 extent 版本**——该 extent 内容是写入数据的不可变快照，带自己的校验和（覆盖密文）。文件的「当前内容」= 路径指向的「最新版本指针」；旧版本 extent 仍保留（直到被快照/引用回收策略释放）。
- **版本 ≠ 快照**：版本是 CoW 写的自然副产物（细粒度、per-extent、零额外空间除非被引用）；快照（§2.4 / `06` §4.3）是用户/监督显式请求的命名空间级 O(1) 检查点，用于 `.msys` 回滚。两者共用同一套 extent 共享 + 写时复制原语。

> 推论：方案 B 的「可变文件」在存储上**其实是「路径 → 当前版本」的一层薄重定向 + 一堆不可变内容版本**。这恰好吸收了方案 A 的完整性（每个版本内容可校验），却把内容寻址藏在 API 之下，不暴露给应用。

### 2.3 校验和 / 压缩 / 加密为透明层（叠加在 extent 之上）

三者都是**存储对象的属性**，不是外挂层，对应用 API 不可见。自底向上（对齐 `06` §4.2，落点澄清）：

```
        文件 / 命名空间层（ns-node，句柄 rights）
                │
        ┌───────▼───────┐
        │ 加密层 (AEAD)  │  per-file/per-extent 密钥；密钥 unwrap 权 = 文件句柄 right（密钥即 capability，C2）
        ├───────────────┤
        │ 压缩层         │  per-extent，加密前压缩（compress → encrypt → checksum）
        ├───────────────┤
        │ 校验和层       │  per-extent 校验和，覆盖密文（检测 bit-rot）；可选文件级 AEAD 认证标签（防篡改）
        ├───────────────┤
        │ extent 分配层  │  映射 extent ↔ 物理块；CoW；引用计数；版本指针
        └───────┬───────┘
                │  块设备 capability（BLOCK_READ/WRITE/IO，由 `33` 经能力网关授予）
        块设备（用户态驱动，数据走 VMO 零拷贝）
```

- **校验和**：per-extent，覆盖**密文**（不依赖明文/密钥，密钥轮换也有效）；强校验和（BLAKE2b / xxHash3 类，非仅 crc32c）。对需防篡改的文件（`.msys` 系统组件）加文件级 AEAD 认证标签（fs-verity 思想，但认证密钥 = 文件 capability 派生，与 `06`/`07` 联动）。
- **压缩**：per-extent、加密**之前**（加密后数据不可压）；zstd 为主、lzo 备选；按文件类型/冷热策略决策。
- **加密**：per-file/per-extent 密钥，由卷密钥（secure boot / TPM 类根信任保护）或上级目录密钥派生包装；客户端句柄含 `READ`/`WRITE` 即隐式可 unwrap 该文件密钥（密钥材料永不出 FS 服务 pager，`06` C2 回写定稿）；**撤销句柄即撤销解密权**，无需独立 KRL。

### 2.4 原子 `.msys` 更新：子树快照 + 命名空间原子 repoint

sysroot 是命名空间子树（CoW 子卷）。更新 = 签名校验 → O(1) 备份快照 → 暂存克隆上应用 → **单条元数据事务原子 repoint** `/msys` 别名（capability 级单点切换，非多步改名）→ 监督者决定何时切割（新进程用新 sysroot、旧进程续持旧能力，**非破坏式、无需重启、可 per-process 灰度**）。A/B 双分区仅作引导级防砖兜底（`06` §4.3 / `09`）。

## 3. 关键抽象

方案 B 的代码/接口骨架由以下抽象组成（非字节级，留给执行层）：

1. **ns-node（统一资源节点）**：一切皆节点——`inode` 式元数据 + 类型标签（`file` / `dir` / `device-proxy` / `proc-dir` / `net-ns` / `service` / `cap-object`）。目录是「名字 → 节点能力」的映射（capability-backed，非裸 inode 号）。普通文件与设备/进程视图对客户端都是「命名空间节点 + 句柄」。
2. **verifiable version（可验证版本）**：逻辑文件 = `path → version-pointer`；每个版本 = 一组不可变 extent（带密文校验和 + 可选压缩/加密上下文）。写 = CoW 新版本 + 重定向指针。这是方案 B 的签名抽象。
3. **transparent storage stack（透明存储层）**：encrypt → compress → checksum 三层，以 extent 为作用单元，对应用全透明；层顺序固定（先压后加密再校验），密钥=capability。
4. **block-capability（块设备能力，`33`）**：底层介质以 `BLOCK_*` right（bit 23–27，第五轮采纳）的 capability 暴露；分区/卷/RAID 是消费子设备 cap、产出新 cap 的**用户态组合服务**（capability 组合树取代内核 device-mapper）。
5. **VMO + pager（零拷贝数据通路，`00` A7）**：FS 服务为打开文件创建 VMO 作视图，经 cap-transfer 交客户端；缺页时内核向 FS 服务 pager 请求页（读 extent → 解压 → 解密 → 校验 → 供页）。FS 逻辑全用户态、数据通路内核直连。
6. **mount-capability（子树委托）**：`/dev`/`/proc`/`/net`/ext4/tmpfs 等经 mount-capability 挂入统一命名空间，capability 来源与 revoke 进 `07` derivation tree。
7. **snapshot / repoint 原语**：`.msys` 原子更新的基石，由 FS 服务提供、监督者（`04`）决策切割时机。

## 4. 多系统参照（解构非缝合）

按方法论对六类现实系统做「思想取长补短」，结论在 §5 收敛为 MeuOS 自己的取舍。**只借思想、不缝合**。

### 4.1 ZFS（池化 + 块级校验和 + 集成压缩/加密）

- **思想**：彻底抹掉「卷管理 + 文件系统」的割裂——**一切是存储池（pool）里的对象**，文件系统只是 pool 上的 dataset；**每个块都带校验和**（覆盖数据+元数据），默认可检测/自愈 bit-rot；**透明压缩（lz4/zstd）与加密（AES-256-GCM，密钥在 dataset 挂载时装载）原生集成**；CoW + 事务，无 fsck；send/receive 做增量复制；ARC 做智能缓存。
- **可借**：「池化统一一切后端」正是方案 B「统一命名空间聚合所有后端」的终极范本；「块级校验和 + 原地不覆写（CoW）」是方案 B extent 校验和/可验证版本的直接祖先；压缩/加密原生集成是方案 B「透明层」的正例。
- **不借 / 警示**：ZFS 是**内核态巨石**（大 TCB、与 MeuOS 出核冲突）；加密是**dataset 级一密钥**（不与 per-file 句柄 right 联动，缺 capability 粒度，与 `06` C2 取向冲突）；dedup 表内存代价高、默认谨慎开。这些正是方案 B 用「用户态 FS + 密钥=capability + 可选 per-extent 去重」要避开的点。

### 4.2 Btrfs（extent 校验和 / 压缩 + 子卷快照）

- **思想**：CoW + **每 extent 校验和（crc32c/xxhash/blake2）覆盖数据与元数据** + **透明压缩（zstd/lzo/zlib）** + **子卷快照**（O(1) 共享 extent）；是「校验和/压缩在 extent 层、更新靠快照」的正面范本。
- **可借**：extent 级校验和/压缩是方案 B 透明存储层的主参考；子卷快照是 `.msys` 原子更新的原语参考。
- **不借**：Btrfs 加密仍依赖块层 dm-crypt（整盘一钥）或 fscrypt（per-file 但与快照/extent 割裂），**加密未与 extent/快照深度联动**——方案 B 把加密也下沉到 extent/per-file 且密钥=capability，补上此缺口。

### 4.3 Windows ReFS（integrity streams + 绝不原地覆写 + 损坏 salvage）

- **思想**：ReFS 以 **integrity streams** 实现「**CoW + 数据/元数据均带校验和**」，写入永不原地覆写；镜像配置下可** salvage**（复制完好数据、跳过/隔离损坏块）自愈；无传统 fsck（自修复）。
- **可借**：「**验证优先、绝不原地覆写**」是方案 B 可验证版本（CoW 写）的同构思想；salvage 是 bit-rot 应对的加分参考。
- **不借 / 警示（重要教训）**：ReFS **没有内建压缩与加密**（压缩/加密留在 NTFS/Storage Spaces，与 ReFS 割裂），且历史上被砍掉部分特性（如 Win10 家用版移除、部分版本无去重）——这恰恰是「**只做校验、不同步做压缩/加密**」会留下半个方案的反面教材。方案 B 据此**强制把压缩/加密与校验和同层叠加**，不重蹈 ReFS 的功能割裂。

### 4.4 Fuchsia minfs（用户态 r/w FS）+ 命名空间 + pager（及 blobfs = 方案 A 对照）

- **思想**：minfs 是 Fuchsia 的**小型可读写 FS**，本身走常规可变文件语义；其真正价值在**外围**——Fuchsia 的**每进程 namespace**（spawn 时注入 `path → 目录能力`，无全局 `/proc`）+ **pager** 让用户态 FS 经 VMO 零拷贝 mmap。Fuchsia 另一 FS **blobfs** 是**内容寻址（hash=名）的不可变 blob 存储、自带校验和**——这恰是**方案 A 的范本**。
- **可借**：minfs 证明「可写 FS + 用户态 + pager 零拷贝」工程可行，是方案 B「路径语义可变文件」的实现样例；Fuchsia namespace+pager 是方案 B 统一命名空间与数据通路的直标。
- **对照（方案 A 同源）**：blobfs=内容寻址/不可变=方案 A；minfs=路径语义/可变=方案 B。两者在 Fuchsia 里**并存**——这恰好印证 §8.3 的选型建议：**方案 B 为 Day1 主线，方案 A 作不可变系统组件子集（blobfs 式）**。

### 4.5 APFS（CoW 克隆/快照 + per-file 密钥层次）

- **思想**：APFS 的 **clone**（O(1) CoW 克隆）/ **snapshot**（O(1) 共享 extent）是原子更新的范本；**原生加密**支持无/单/多密钥且按**文件级密钥层次**（per-file key 由卷/用户密钥派生包装）；崩溃一致性靠 CoW + 事务。
- **可借**：`.msys` 的「快照 + 原子 repoint + per-file 密钥层次」直接借 APFS；但其回退是**破坏式**（删快照后所有写入、需离线），方案 B 因 capability 是**非破坏式**（旧持有者续持旧能力、无需重启、可灰度，`06` 引用澄清已点明）。
- **不借**：APFS 在内核态（XNU 混合）、DAC 模型、加密未挂 capability——方案 B 改用户态 + 密钥=capability。

### 4.6 Linux VFS（对象模型统一，但命名空间层碎片化——反面教材）

- **事实澄清（来自 `06` 引用澄清）**：VFS 在**对象模型层是真统一**的（procfs/sysfs/btrfs 都表现为同一套 `inode`/`dentry`/`file`），统一失败的不是对象层，是**命名空间/挂载层**——多个独立 FS 拼到全局树、可见性默认全局、`/proc+/sys+/dev` 各为政。
- **可借（反面教正）**：VFS 印证「everything is a file」的对象统一思想；但方案 B 要修的正是在**命名空间层**——用 capability 组合树取代「全局共享树 + 多伪 FS 拼凑」，把统一做到命名空间/capability 维度，而非只做到对象维度。
- **不借**：全局可见 + DAC + 默认可见性，与 `00` A4（默认不可见、显式 reveal）根本冲突。

### 4.7 取舍总表（解构非缝合）

| 命名空间 | pool/dataset | 全局树+子卷 | 对象命名空间(DAC) | **每进程 namespace=cap 组合** | 内核 VFS(DAC) | 对象统一/命名空间碎 | **每进程 namespace=cap 组合，FS 做根聚合 + mount-cap** |

## 7. 相对传统 FS 摆脱的包袱与付出的代价

### 7.1 摆脱的包袱（相对 ext4/NTFS/传统 VFS）

1. **fsck**：CoW + 元数据事务保证「最后一次提交要么完整要么不可见、挂载即一致」（`06` §4.5），无重放、无 fsck 长停机——对齐 ZFS/APFS/btrfs。
2. **全局可变命名空间 + DAC**：以每进程 capability 组合树取代 `/proc+/sys+/dev` 拼全局树 + 默认全局可见（对齐 `00` A4 / C3）；权限随句柄走、可审计、可 revoke，消灭 `CAP_*` 特权碎片。
3. **原地覆写（in-place overwrite）**：CoW 写使「可变文件」永不撕裂旧版本，bit-rot 可检测、回滚可细粒度。
4. **卷管理 / 分区 / RAID 的割裂工具链**：以 `33` 的用户态 capability 组合服务（分区/RAID/加密卷）取代内核 device-mapper/MD/LVM/BitLocker，每层独立可重启、受 capability 约束。
5. **整盘一密钥的块层加密（dm-crypt/BitLocker）**：改 per-file/extent 密钥且密钥=capability，撤销句柄即撤解密权，无独立 KRL。
6. **静默损坏（silent corruption）**：extent 级校验和覆盖密文，读路径确定性检测 bit-rot（对齐 ZFS/ReFS integrity streams）。
7. **系统更新非原子**：`.msys` 子树快照 + 命名空间原子 repoint 取代包管理就地改文件。

### 7.2 付出的代价（需原型实测量化，非凭空假设）

1. **写放大 / 空间放大（CoW 固有）**：每次写生成新 extent 版本，随机小写负载下元数据与空间开销上升——ZFS/btrfs 已知问题。缓解：热点小文件直下 VMO、写合并、引用计数共享未改 extent；**代价量级需基准**（待 `06` §6-4 pager 缺页基准同轮）。
2. **命名空间解析的 capability 路由成本**：路径解析从「全局树查表」变「capability 路由 + 多服务委托」，每跳一次能力查找。缓解：spawn 时 COW 继承父/Job 模板（`06` C3 回写）使常用绑定本地化；**延迟需实测**。
3. **pager 缺页往返 IPC 延迟**：用户态 FS + pager 使每次文件缺页至少一次 IPC 到 FS 服务，密集小文件随机读热路径延迟待验证（`06` §6-4 / `00` §5.5）；可能需内核页缓存旁路 / 热点文件直接 VMO 下发。
4. **压缩/加密 CPU 成本**：per-extent 压缩 + per-file AEAD 加密增加写路径 CPU；若 Rust 加密吞吐不足，热点函数允许 C/内联汇编经 Rust safe 封装（`06` §6-7 / `02`），但密钥管理/权限判定必留 Rust/TCB。
5. **legacy 工具范式偏移**：依赖「全局可见块设备 + 原地 raw 写」的工具（如直接 `dd` 裸盘、假定 `/dev/sda` 全局可写的诊断脚本）需改为持 `BLOCK_*` cap（`33` §3.2）——这是 capability 世界的普遍代价，非方案 B 独有。
6. **快照/版本回收策略复杂度**：可验证版本链 + 快照需引用计数与回收策略（GC/age-out），否则空间只增不减；策略归属（FS 服务 vs 监督者）需与 `04` 协同。

> 这些代价**没有一项是方案 B 独有**——它们是从 ZFS/Btrfs/APFS/ReFS 到 Fuchsia 所有现代 CoW + 验证型 FS 的共同账。方案 B 的「务实」正在于：用 capability 组合与用户态 FS 把 TCB 与故障域压到最小，使上述代价可在用户态独立迭代、不影响内核稳定性。

## 8. 与方案 A（内容寻址 / 不可变）的关键差异

### 8.1 差异总表

| 维度 | 方案 A（内容寻址/不可变） | **方案 B（统一命名空间 + 可验证存储层）** |
|------|--------------------------|------------------------------------------|
| 文件身份 | 内容哈希（hash = 名） | **路径**（path = 名） |
| 写语义 | 不可原地变；写 = 新对象 + 引用切换 | **可写**；写 = CoW 新「可验证版本」+ 指针重定向 |
| 寻址方式 | 内容寻址（按 hash 取对象） | **路径寻址**（按名取节点，内部版本内容寻址） |
| 工具/ABI | 需内容寻址工具链或适配层 | **POSIX / 存量工具原样可跑** |
| 完整性来源 | 哈希即完整性（寻址即校验） | extent 校验和（透明层，与寻址解耦） |
| 去重 / 可复现 | 天然（同内容同哈希） | 间接（不可变 extent 内部按内容去重，见 §8.2） |
| 适用面 | 系统组件、只读资产、可复现构建 | **通用读写 + 系统更新 + 兼容层** |
| 典型参照 | Fuchsia blobfs、git、Nix store、IPFS | ZFS/Btrfs/ReFS/APFS/minfs + capability 命名空间 |

### 8.2 为何方案 B 仍能吸收方案 A 的完整性收益

方案 B 不排斥内容寻址——它在**存储层内部**用内容寻址的不可变 extent 承载每个可验证版本：两个不同路径若写入相同内容，其底层 extent（同哈希）可共享去重（对齐 blobfs/Fuchsia `06` F11）。区别只在**寻址与身份暴露在哪一层**：

- 方案 A：内容寻址**穿透到应用 API**（应用须用 hash 或经 GC 引用对象）。
- 方案 B：内容寻址**封在存储层之下**，应用只见「可变路径」；去重/完整性是存储对象的内禀属性，不强迫生态换范式。

因此方案 B 几乎拿到方案 A 的全部完整性/去重收益，**唯一未直接获得的是「应用层可显式按内容寻址」的编程模型**——而那恰是方案 A 的生态摩擦来源。

### 8.3 选型建议（两者非零和）

- **方案 B 为 Day1 主线**：它保留路径语义、兼容 POSIX/存量工具，使 `mcc`+`meuos-libc` 与海量 Linux 二进制无需重写即可运行——这是 MeuOS「从零但兼容渐进」的务实核心。
- **方案 A 作不可变系统组件子集**：对 `.msys` 内系统组件、只读资产、可复现构建产物，采用方案 A 式内容寻址 blob（Fuchsia blobfs 思想，`06` F11），天然防篡改且省空间；其 hash 还可兼作 `.msys` 签名校验的内容指纹。
- **两者并存、统一命名空间收口**：Fuchsia 已是 minfs（可变，≈方案 B）+ blobfs（不可变，≈方案 A）并存——MeuOS 以统一命名空间把两类后端都聚合进来，由 `/msys` 子系统组件走方案 A、通用读写走方案 B，对应用通过同一套句柄/rights 访问。

## 9. 待决 / 协同点（仅声明，不拍板）

> 本节**只声明方案 B 引入的协同点与需裁决项**，不替其他子领域拍板，不修改 `06`/`33`/`00`。结论以各子领域文档与 `00` 冲突登记表为准。

5. **方案 A / 方案 B 并存时的 namespace 边界**：`/msys` 子系统组件（方案 A 子集）与通用读写（方案 B）在统一命名空间内的 reveal/revoke 语义——与 `06` §4.1 / `07` 协同。
