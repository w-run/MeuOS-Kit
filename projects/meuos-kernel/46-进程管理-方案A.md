# 46 - 进程管理·方案 A：消息传递 + 结构化并发作为唯一范式

> 调研 / 设计文档，由 kernel-plan 团队的「内核规划调研 agent（lite/hy3）」产出。
> 工作树：`kernel-plan` / 分支：`worktree-kernel-plan`。
> 本文是**独立新增方案文档**，**不修改** `00`–`45` 任何章节；行文末尾单列「与现有规划的衔接」而非改动既有文件。
> 定位：为 MeuOS 的**进程管理 / subprocess / spawn / 并发模型**提出一个从零设计、不被 Linux/Unix（fork/exec、pthread、信号、全局 PID 命名空间）历史包袱束缚的**方案 A**。

---

## 0. 一句话核心

> **在 MeuOS 中，进程不是「能 fork 出来的地址空间」，而是「一条由 Channel 挂接、由 Job 结构化scope 兜底的并发任务子树」；一切跨执行流交互只有消息传递，一切生命周期只有结构化并发（scope 退出即取消、异常沿树上报），没有 fork、没有全局 PID、没有信号。**

本文把 `00`/`04`/`05`/`07` 中已经分别采纳的 `meu_spawn`、Job 资源账本 Day1、Channel 原语、capability Day1 等点状决策，**升维成一套自洽的「唯一范式」**——并把它向前推一步，补上现有规划尚未闭合的两块：**「结构化并发作为组织原则」**与**「无全局命名空间下的进程寻址」**。

---

## 1. 方案核心思想

### 1.1 为什么是「消息传递 + 结构化并发」两条腿

传统 Unix 把三件本应统一的事拆成了三套互不相通的机制，且每套都带历史包袱：

| 本应统一的概念 | Unix 的拆法 | 各自包袱 |
|---|---|---|
| 「创建一个并发单元」 | `fork()` + `execve()` / `pthread_create` | fork 隐式复制整个地址空间（COW 账本灾难）、pthread 共享地址空间却要手动加锁 |
| 「并发单元之间通信」 | 共享内存 + pipe + socket + 信号 + futex… | 共享内存要自造同步；十几套 IPC 权限模型不统一（见 `05` §1.1） |
| 「并发单元的生命周期」 | `wait()`/`exit()`/`kill`/信号、`pthread_join` | PID 全局命名空间、信号异步可丢失、取消点是合作式的、僵尸进程 |

方案 A 的立场是：**这三件事用同一个底层原子解决**——
- **消息传递（Channel）**解决「通信」；
- **结构化并发（Job 子树 + scope 取消）**解决「生命周期」；
- **spawn（无 fork）**解决「创建」。

三者由同一个对象——**句柄 / Channel 端点 / Job capability**——串联：创建即拿到句柄，句柄即通信端点也即生命周期锚点，没有句柄就不存在「全局可见的进程」。这正是要消灭的「全局 PID 命名空间」的反面。

### 1.2 范式的四条铁律

1. **无 fork**：新执行流只能由 `meu_spawn` 显式构造（空地址空间 + 显式句柄/命名空间注入）。没有「复制父进程」这一步。
2. **无全局 PID**：进程没有全局整数名字。进程只对「持有其 Job/Channel 句柄者」可见、可寻址。寻址 = 持有 capability，不是查一张全局表。
3. **无信号**：不存在异步、可丢失、可屏蔽的 POSIX 信号。通知统一走 Channel/EventPort；取消走结构化取消；致命异常走 exception channel（copy 语义多播，见 `04` §4.6 / `17` C9-B）。
4. **结构化并发唯一**：spawn 出的子任务必须归属于某个结构化 scope（Job 子树的一个节点）。scope 取消时，子树内所有任务被取消、资源被回收——不存在「脱离父 scope 游离的孤儿进程」。

### 1.3 「结构化并发」到底结构化在哪

「结构化并发（structured concurrency）」来自 Trio / Kotlin coroutines / OCaml Eio / Go context 的工程经验，核心命题是：**一个并发任务的诞生与作用域（scope）绑定，任务只能在 scope 内运行，scope 退出前必须等其所有子任务结束（或显式取消）**。这把「谁该等谁、谁该被谁取消」从隐式约定变成了语言/内核级的强制不变量。

方案 A 把这一不变量**下沉到内核对象层**：

- **Job 节点 = 一个结构化 scope**。它在 `04` §4.1 的「资源/生命周期单元」基础上，再补一句：**Job 也是取消域（cancellation domain）**。
- spawn 必须指定「挂到哪个 Job 节点下」，于是每个任务天然处在某棵取消树里。
- 取消一个 Job 节点 = 向该节点及其全部子孙广播结构化取消；子任务收到取消后执行清理并退出；scope（父 Job）在全部子孙退出后才算「完全关闭」。
- 致命异常同理沿树上行（祖先 Job 的 exception channel 收到 `CrashReport`，由监督策略决定重启/终止传播）。

这就让「进程的生死」从「信号 + wait + 僵尸」变成「树上的取消/异常传播」——可推理、可组合、无竞态孤儿。

## 2. 关键抽象：定义与关系

```
                        ┌─────────────────────────────────────────┐
                        │  Job 节点（结构化 scope / 取消域 / 账本） │

                        │  - capability 边界（维度 B，见 07）        │
                        │  - 取消域：取消本节点 ⇒ 广播到整棵子树      │
                        │  - exception channel（CrashReport 多播）   │
                        │  - 子 Job / 子 Process 树（结构化子树）     │
                        └───────────────┬───────────────────────────┘
                                        │ 持有 job handle 才能 spawn
                 ┌──────────────────────┴───────────────────────┐
                 │                                              │
        ┌────────▼─────────┐                          ┌─────────▼─────────┐
        │  Process          │                          │  Process          │

        └────────┬──────────┘

   跨节点通信原语（唯一 IPC 范式，见 05）：

   │  Channel：带类型、可携带 capability 句柄的消息端点对        │
```

### 2.1 Process（进程）

- **定义**：一个独立地址空间（根 VMAR）+ 一张句柄表（CSpace）+ 一组 Thread。它是「资源隔离边界」与「capability 边界」，不是「可 fork 的单位」。
- **创建**：只能由 `meu_spawn` 在持有某 Job handle 的前提下构造，从空地址空间开始，由用户态 loader 显式映射（对齐 Zircon，`04` §4.2）。
- **可见性**：进程**没有名字**。它对「持有其 Job handle 或其某个 Channel 端点句柄」的主体可见；对其他主体完全不可见、不可寻址。**无全局 PID 表**（`ps` 不是查全局表，而是读监督者持有的 Job 子树 introspect 视图，受 `DBG_INSPECT` 约束，见 `05` §4.5 / `12`）。
- **线程**：一个 Process 可有多个 Thread；内核只调度 Thread。Thread 之间共享进程地址空间，但**进程间没有任何共享内存**，除非显式经 SHM capability（见 `05` §4.3）。

### 2.2 Thread（线程）

- **定义**：内核调度实体，绑定到某个 Process，持寄存器上下文与内核栈。
- **角色**：既承载「OS 级并行」（多核），也承载「运行时 M:N 调度」的地基（`04` §4.3/§4.7 借 Go GMP / Rust async 思路）。Go/Rust 运行时在其上做协程级 M:N，内核不感知 goroutine/async-task。
- **与并发范式的关系**：Thread 是「结构化并发树」的叶子执行点；它的生死由所属 Process/Job 的 scope 决定，不由 `pthread_detach` 式自由约定决定。

### 2.3 Job（作业节点 = 结构化 scope + 资源账本 + 取消域）

- **定义**：并发任务的**结构化作用域（scope）**、**资源账本（ledger）**、**取消域（cancellation domain）**三者合一（`04` §4.1/§4.4 + 本方案 §1.3）。它是方案 A 的脊柱。
- **三个身份的统一**：
  1. *结构化 scope*：spawn 必须挂到某 Job 节点；节点与其子孙构成一棵取消树。
  2. *资源账本*：配额（CPU/内存/句柄数/IO/进程线程数）是 Job 的固有属性 Day1（已采纳裁决 A5，见 `00` §A5 / `04` §4.4），与 capability 边界同源挂在 Job 上（维度 B，`07` §4）。
  3. *取消/异常域*：取消本节点 ⇒ 递归广播取消到子树；致命异常经 exception channel 多播给祖先监督者（`04` §4.6）。
- **创建**：必须持有父 Job handle + `JOB_CREATE` right（`07` rights 位图中可据 §5-7 协同补一位；当前由 supervisor 专属 capability 约束，`04` §4.5）。
- **生命周期铁律**：父 Job 关闭前，必须等全部子孙 Job/Process 退出（或被取消）。这从内核层消灭「僵尸进程」「孤儿进程被 init 接管」类 Unix 顽疾——因为没有全局 init 兜底，scope 自己兜底。

### 2.4 Channel（消息通道 = 唯一通信范式）

- **定义**：成对的内核对象端点，每一端都是 capability（句柄）。消息 = 数据载荷 + 可选携带的 capability 句柄数组（`05` §4.1）。
- **为什么是「唯一」**：方案 A 把「进程间/线程间/Job 间一切通信」都表达为 Channel 消息——RPC、流、能力委托、甚至「进程存在性/退出」本身也是经 Channel/EventPort 投递的事件（`04` §4.5 / `05` §4.2）。不再有 fork 共享内存、pipe、socket、信号、futex 的割裂。
- **同步语义**：`send`/`recv`/`call`/`reply`/`send_oneway`（`05` §4.1），rendezvous 保证「发即知被收」，天然消除「信号丢失」类问题。
- **capability 传递**：消息可携带另一 Channel / SHM / 服务连接句柄，接收方在其 CSpace 指定槽位收下——这是 Binder 式对象引用 + 事务语义的内核级干净实现（无 `SCM_RIGHTS`、无 broker，`05` §3.3/§4.4）。

### 2.5 Capability（能力句柄 = 寻址 + 权限 + 生命周期锚点）

- **定义**：`handle + rights` 位图，是进程访问一切内核对象的唯一凭证（`07` §4.1）。
- **在本方案中的三重角色**：
  1. *寻址*：持有某 Process 的 Job handle / 某 Channel 端点 = 能找到它、与它通信。**可见性即 capability**，无 capability 即不可见（消灭全局 PID）。
  2. *权限*：能对它做什么由 rights 位图决定（`READ/WRITE/MANAGE/GRANT/REVOKE/DUPLICATE…`，`07` §4.1 全表）。
  3. *生命周期锚*：句柄被 `close`/回收时，其指向的对象（含 Channel、Process 引用）引用计数减一；进程崩溃时内核自动回收其全部句柄（`05` §2.4）——无孤儿连接。
- **派生只能收窄**：`duplicate` 产生的子句柄 rights 只能 ≤ 父（`07` §4，seL4 derivation tree 思想）；任何提权必须持有 `GRANT` 的对端显式重新授予，无捷径。

### 2.6 五者关系小结

| 抽象 | 是什么 | 由谁创建 | 解决什么 | 关键不变量 |
|---|---|---|---|---|
| Process | 地址空间 + 句柄表 + 线程集 | `meu_spawn`（持 Job handle） | 资源/能力隔离 | 无全局名、无 fork、默认不继承句柄 |
| Thread | 内核调度实体 | Process 内 `meu_thread_create` | 并行执行 | 只在所属 Process/Job scope 内存活 |
| Job | scope + 账本 + 取消域 | 持父 Job handle + `JOB_CREATE` | 结构化并发 / 资源 / 取消 | 退出前等全部子孙；取消沿树广播 |
| Channel | 成对端点（capability） | `channel_create` | 一切通信 | 消息携带能力；rendezvous 不丢 |
| Capability | 句柄 + rights | 内核对象创建/派生 | 寻址 + 权限 + 生命周期 | 仅收窄派生；崩溃即回收 |

## 3. 多系统参照（解构而非缝合）

> 本节逐一对标成熟系统，**只抽取可复用的机制骨架，不堆砌特性**。每张表结尾给出「方案 A 取了什么、丢了什么」。

### 3.1 Erlang 轻量进程 + 监督树（OTP supervisor）

- **机制**：Erlang 进程是用户态轻量实体（非 OS 线程），创建极廉（`spawn` 函数）；进程间**只**靠异步消息（`!` / `receive`），无共享内存。Supervisor 行为把进程组织成监督树：「one_for_one / one_for_all / rest_for_one」决定子进程崩了父怎么重启；崩溃默认不拖垮整树。
- **可取**：①「进程间只走消息」是消息传递范式的教科书；②「监督树 = 结构化并发的雏形」，崩溃沿树上报、由策略决定重启——这正是方案 A 的 Job exception channel 思想来源；③「let it crash」把容错交给结构而非防御性编码。
- **不可取 / 改造**：Erlang 进程是**用户态**调度，内核无感知，无法直接映射到 OS 级资源账本与 CPU 隔离；其「进程无全局名但有 `pid` 可持有」与方案 A 的「无 PID、只持句柄」接近但 Erlang 的 pid 仍是全局可寻址的轻量引用。方案 A 把监督树**下沉为内核 Job 树**，并让账本与取消域同源挂在 Job 上（超越 Erlang 用户态局限）。

### 3.2 Go goroutine / channel + context

- **机制**：goroutine 是用户态 M:N 轻量线程；`channel` 是类型安全的消息管道；`context.Context` 实现结构化取消（cancel 沿调用树广播，`Done()` 关闭）。Go 的「不要通过共享内存通信，要通过通信共享内存」与方案 A 同声相应。
- **可取**：①`context` 是「结构化并发」的工程范本——scope 取消自动传导给所有子 goroutine，正是方案 A Job 取消域的内核级对应物；②goroutine 的廉价与 M:N 调度启示：内核只需提供廉价 Thread + 公平/RT 两层调度，协程级交给运行时（`04` §4.7）。
- **不可取 / 改造**：Go 的 `context` 是**库级约定**，可被人遗忘不传、可泄漏 goroutine（「goroutine leak」是真实痛点）；Go 的取消是**合作式**（子 goroutine 必须主动 `select { case <-ctx.Done()}`），不响应就永不退出。方案 A 把取消做成**内核强制**：Job 取消广播到所有子孙 Thread/Process，不合作的进程被强制终止（capability 强制力 > 约定）。

### 3.3 seL4 线程 + Endpoint IPC + CSpace

- **机制**：seL4 所有内核资源都是 capability，挂在 CSpace 树；线程间通信用 Endpoint（严格 rendezvous，`seL4_Call`/`ReplyRecv`，badge 多路复用，reply capability，fastpath）；权限传递是消息一等公民。形式化验证证明其功能正确性与信息流安全。
- **可取**：①「句柄即 capability、权限随句柄走、派生只能收窄」是方案 A capability 模型的范本（`07` §4.1 直接采纳）；②Endpoint 的 rendezvous + reply capability 是 MeuOS Channel 的同步骨架（`05` §3.1）；③badge 提供不可伪造的来源标识。
- **不可取 / 改造**：seL4 是纯微内核，IPC 承担几乎全部系统调用负载，fastpath 设计极重；MeuOS 是混合内核，不必为「所有驱动调用」走 IPC（见 `05` §2.1）。方案 A 复用 seL4 的 capability/IPC *模型*，但把 IPC 压力限制在「服务进程间通信」场景，保留内核态服务的零拷贝直连。

### 3.4 Fuchsia / Zircon（job / process / thread + channel + handle）

- **机制**：无 fork，进程由 `zx_process_create` 在**给定 job** 下从空地址空间构造；Job 天然承担资源限额与生命周期控制（父 job 死 ⇒ 杀子孙）；无 POSIX 信号，通知走 port/channel/event，异常经 exception channel 上报（`04` §3.1 B / `05` §3 多处采纳）。
- **可取**：这是方案 A **最接近的现成范本**——spawn-only、Job 账本 Day1、exception channel、handle=capability 几乎全被 `04`/`05`/`07` 采纳。Job 的「lifetime control」直接对应本方案的「结构化 scope」。
- **不可取 / 改造**：Zircon 的 Job 主要是「限额 + 生命周期容器」，其**取消语义偏「kill 传播」而非「结构化取消 + 协作清理」**；且 Zircon 仍允许进程「自行退出后由父 wait」的弱约束。方案 A 强化为：Job 是**强制结构化 scope**，退出前必须等全部子孙完成协作清理，取消是「先协作广播、超时再强制终止」两段式，把 Erlang/Go 的结构化不变量显式固化。

### 3.5 Plan 9（rfork + 每进程命名空间 + note）

- **机制**：`rfork(flags)` 用标志位显式选择「哪些资源被子进程共享/重置」（RFMEM 共享地址空间、RFNAMEG 新命名空间…），比 Linux clone 更早把「共享什么」显式化；命名空间每进程独立；通知用简化的 note 而非 POSIX 信号（`04` §3.1 C）。
- **可取**：①「每进程独立 namespace、默认全不可见、显式 reveal」直接对应 MeuOS 的 capability 命名空间（已采纳裁决 C3，`14`/`04` §第三轮）；②「共享什么由 spawn 标志显式声明」是「能力显性传递」（G4）的思想源头。
- **不可取 / 改造**：rfork 仍是 **fork 变体**——它复制当前进程再决定共享哪些部分，本质还是「先复制再裁剪」，留下 COW 账本与大页/多核隐患。方案 A 走 Zircon 式「从零 spawn」，**不复制父地址空间**（见 `04` §4.2），把「共享」变成「显式注入句柄/SHM」而非「复制后裁剪」。

### 3.6 macOS GCD（Grand Central Dispatch）

- **机制**：GCD 把并发抽象为「任务（block）提交到队列（serial/concurrent）」，由系统线程池调度；强调「不要自己管线程，把任务交给队列」；`dispatch_group` 提供结构化等待（一组任务全完成后继续）。是用户态结构化并发的工程范本。
- **可取**：①`dispatch_group` 是「结构化并发」在队列模型的实现——等一组子任务完成再继续，对应方案 A 的 Job scope 等待；②「系统托管线程池 + 任务提交」启示：内核不必让用户态自建线程池，可提供「轻量任务提交」原语。
- **不可取 / 改造**：GCD 是**纯用户态运行时**，无资源账本、无 capability 约束、任务逃逸出 group 仍可能游离；方案 A 把队列/group 的「结构化等待」下沉为内核 Job scope，并与资源账本、capability 同源——GCD 的 ergonomics + 内核级的强制力与可审计性。

### 3.7 综合取舍表

| 系统 | 抽取的机制骨架 | 方案 A 采用 | 方案 A 丢弃/改造 |
|---|---|---|---|
| Erlang | 进程只走消息；监督树崩溃上报 | 消息唯一通信；Job exception channel | 用户态调度 → 下沉为内核 Job 树 + 账本 |
| Go | channel；context 结构化取消 | Channel 原语；Job 取消域 | 库级合作式 → 内核强制取消 |
| seL4 | capability=内核对象；Endpoint rendezvous | 句柄即 capability；Channel 同步 | 纯微内核全 IPC 负载 → 混合内核限定场景 |
| Fuchsia | spawn-only；Job 限额+生命周期；exception channel | 几乎全采纳（04/05/07） | 取消偏弱 → 强化为强制结构化 scope |
| Plan 9 | 每进程 namespace；rfork 显式共享 | 每进程 namespace（C3） | rfork 复制 → 改为从零 spawn |
| GCD | dispatch_group 结构化等待 | Job scope 等待语义 | 用户态无账本 → 同源挂账本+capability |

**关键判断**：方案 A **不是缝合**——六套系统被「解构」为三条可复用的骨架（消息传递、capability 寻址、结构化 scope），再用 MeuOS 既有的 Channel/Job/capability 原语**重新组装**成单一范式。每条 Unix 包袱都有明确的对应替代，而非「加一层兼容」。

## 4. 与 MeuOS 现有规划的衔接

> 本节只说明「本方案如何继承 / 强化既有采纳」，不改动任何既有文档。

### 4.1 继承 `00` 已采纳裁决

- **A5（Job 资源账本 Day1）**：方案 A 的 Job 三合一（scope+账本+取消域）直接以 A5 为地基，账本仍是 `04` §4.4 的五类资源（CPU/内存/句柄/IO/进程线程数），能耗按第四轮裁决保持弱耦合（`04` §第四轮回写）。
- **A9（exception channel → 监督者）**：方案 A 的「异常沿 Job 树上行 + copy 语义多播」即 A9 的内核级落点；监督者（`meu-supervisor`）持 `DBG_CRASHDUMP` 默认订阅权、决策不可抑制（C9-B，`17`）。
- **「信号从零简化」**：`00` §18 已定「信号简化为 event 对象 + 极简 Terminate/Kill/Interrupt，致命异常经 exception channel」。方案 A 把这点推到极致——**彻底移除信号概念**，Terminate/Kill/Interrupt 改为「结构化取消的三种强度」而非信号（`04` §4.6 的 Terminate/Kill/Interrupt 在本方案中重新定义为取消指令，见 §6.2）。

### 4.2 强化 `04` 的进程/Job 模型

- `04` §4.1 已画 Job→Process→Thread 树；方案 A 补上 **「Job = 强制结构化 scope」** 这一未被 `04` 显式写死的不变量：spawn 必须挂 Job、Job 退出前等子孙、取消沿树广播。这是把 `04` 的「生命周期单元」升级为「结构化并发单元」。
- `04` §4.5 的「内核内建监督」与方案 A 的 Job 树天然契合：监督者即根 Job 之下的策略执行者，重启决策作用在 Job 节点而非 PID 上。

### 4.3 复用 `05` 的 IPC 原语

- 方案 A 的「消息传递唯一范式」== `05` §4.1–§4.4 的 Channel/EventPort/SHM/Service Registry 四原语。本文不重复设计 IPC，直接以 `05` 为通信地基；区别在于**态度**：`05` 把它作为「比 Linux 干净一个数量级的 IPC 集合」，方案 A 进一步宣布「这是进程模型的唯一通信方式，没有第二选项」。

### 4.4 对齐 `07` 的 capability 安全模型

- 维度 B（spawn 资源账本，`07` §4）是方案 A Job 账本的权威来源；句柄即 capability（`07` §4.1）、派生只能收窄、崩溃即回收，全部直接继承。
- **无全局 PID 的 capability 论证**：`07` 已立「权限来自句柄而非身份、无 root」。方案 A 把「进程的可见性」也纳入同一模型——进程无全局名，只有持其句柄者可见，使「进程寻址」成为 capability 的直接推论，而非另立一套 PID 命名空间。
- 待协同：spawn 资源账本的「句柄继承白/黑名单粒度」（`04` §5-7 / `07` §5-1）需跨子领域定稿；本方案建议**默认不继承任何句柄 + manifest 显式 reveal**（最小特权，对齐 C3/C4）。

## 6. 相对传统 Unix 进程模型：摆脱的包袱与付出的代价

### 6.1 摆脱的包袱（明确清单）

1. **fork + COW 账本地狱**：不再有「复制整个地址空间（哪怕 COW）」的语义。大页/多核/写时复制的正确性负担整体消失；无「多线程进程 fork 只有调用线程存活」的未定义雷区（C4 已采纳多线程 fork 显式拒绝）。
2. **全局 PID 命名空间**：无 `pid_t` 全局整数表、无 `init` 兜底孤儿、无「PID 重用导致的权限错配」、无 `/proc` 全局伪文件系统。进程寻址 = 持句柄，可见性 = capability。
3. **POSIX 信号整套**：无异步、可丢失、`signal mask`/`sigaction`/`tkill` 组合爆炸；无「信号处理器随意改写控制流」；无 SIGSEGV 处理器这类 footgun。取消/通知/异常全部结构化。
4. **`pthread` 共享地址空间 + 手动锁**：线程仍共享进程地址空间（这是合理的），但「跨进程」不再有共享内存默认通道，强制走 Channel——从架构上消灭「两块代码共享可变状态却忘了加锁」的整类并发 bug。
5. **僵尸进程 / `wait()` 轮询**：scope 自己兜底，父 Job 退出前等子孙，无僵尸。
6. **`setuid`/`setgid` 提权模型**：uid/gid 是纯合成视图、零权限附着（C4 已采纳），setuid 二进制 = 受限 spawn + 显式 capability，永不提权。
7. **cgroups 事后挂接**：账本是 Job 固有属性 Day1，进程诞生即受限（A5）。

### 6.2 付出的代价（必须诚实承认）

1. **旧生态二进制需要兼容层翻译**：fork/exec/信号/PID 丰富的 Linux 程序必须走 mkit（`08`）翻译为 spawn/Channel/取消指令。纯 fork 语义（如 JIT 写时复制依赖、部分调试器 `ptrace`）是兼容层难点（C4 已限多线程 fork 拒绝）。**代价**：并非所有 Linux 程序都能零修改运行，需 Spork/posix_spawn 式改写（见 `04` §5-2 / `06.7` 文献）。
2. **「快速 fork 一个自己」的 ergonomics 丧失**：shell 管道、测试脚本等习惯 `fork` 的场景，在原生模型下要走 `meu_spawn` + 显式句柄注入，代码更啰嗦。缓解：提供 libc 封装（如 `meu_spawn` 的 argv/env/继承集一键式 API）+ 兼容层保留 fork 视图。
3. **取消是强制的，协作清理需配合**：内核强制取消（不响应就杀）比 Go 合作式更「硬」，需要程序员在 scope 内正确响应取消、及时释放 SHM/Channel，否则被强杀。缓解：取消先广播「协作清理窗口」再强制终止（两段式，见 §3.4 改造）。
4. **调试/观测心智模型改变**：没有全局 `ps`/`kill -9`，观测靠监督者持有的 Job 子树 introspect 视图（受 `DBG_INSPECT`）。对习惯 Unix 运维的人是学习成本。
5. **无全局命名带来的「怎么找到服务」问题**：服务发现必须显式经 Service Registry（`05` §4.4）或持有其 Channel 句柄，不能「假设某 PID 在跑」。这是能力模型的内禀代价，由 lazy activation 缓解。
6. **capability 派生粒度需谨慎设计**：句柄继承白/黑名单、rights 收窄规则（`04` §5-7 / `07` §5-1）若设计不当会导致「要么过宽、要么太碎」。属开放议题，不阻塞 Day1（Day1 用「默认不继承 + 显式 reveal」最保守策略）。

### 6.3 代价 vs 收益的总账

| 维度 | 传统 Unix | 方案 A | 净效果 |
|---|---|---|---|
| 进程创建安全 | fork 隐式复制，易越权 | 显式 spawn，最小特权 | 收益 |
| 并发正确性 | 共享内存 + 手动锁 | 消息传递 + 结构化并发 | 收益（架构级） |
| 生命周期可推理 | 信号 + wait + 僵尸 | 树取消 + 异常上报 | 收益 |
| 旧生态兼容 | 原生 | 需 mkit 翻译 | 代价 |
| 开发 ergonomics（fork 习惯） | 顺手 | 需显式 | 代价（可封装缓解） |
| 可验证 TCB | 大（信号/fork/cgroup 交互） | 小（单一范式） | 收益（`20`/`44` 形式化利好） |

## 7. 方案 A 自身的开放议题（不阻塞 Day1，待原型验证）

1. **取消「协作窗口」时长与强制终止阈值**：两段式取消中，协作清理窗口默认多少？超时强杀是否可配？是否按 Job 账本区分「软实时 vs 批处理」？
2. **Job 树深度与取消广播的复杂度**：深度取消树在广播取消时的 O(子孙数) 开销是否需 lazy/incremental 标记？超大服务树（千级 Job）的取消是否要批量原语？
3. **「结构化并发」是否要暴露给用户态语言运行时作为一等原语**：Go/Rust 运行时当前用 `context`/Future 自管取消；是否要在 libc/ABI 层把 Job scope 直接映射为语言级 structured concurrency 原语（如 Rust 的 `scope`、Kotlin 的 `coroutineScope`），让「内核 Job = 语言 scope」？这关系到 `37` SDK 契约。
4. **无 PID 下的「用户可理解标识」**：运维/日志需要可读标识，是否引入「Job 路径式名字（如 `/svc/network/0`）」作为 capability 之上的**展示层**（非寻址层）？与 `12` 可观测性协同。
5. **跨 realm 的 Job 取消传播边界**：A7 多 realm 隔离若采纳，跨 realm 的取消/异常是否穿透？默认不穿透（capability 边界即 realm 边界）。
6. **与 `08` 兼容层的 fork 语义最终边界**：哪些 Linux 程序必须真 fork、是否要求改写 posix_spawn（C4 已定多线程 fork 拒绝，残留在单线程 fork 的 CoW 正确性）。
