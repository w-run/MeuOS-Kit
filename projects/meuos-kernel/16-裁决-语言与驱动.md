# 一、C5 裁决：内核 `panic=abort` vs 用户态 unwind

## 1.1 应该是什么样（解构推演）

问：在「混合内核 + capability 世界 + 用户态服务可自治重启」模型下，**panic / 展开（unwind）应该是什么样**？

1. **panic 的语义由「故障域」决定，而非由「语言」决定**。Rust 在内核态与用户态都可能出现，但二者落在不同的地址空间与重启语义中：
   - 内核态核心组件 panic = 整个内核停机（这些代码在 TCB 内，不可恢复即不应尝试恢复，否则可能带着内存破坏继续跑）。
   - 用户态 Rust 服务 panic = 一个「组件」死亡，由 supervisor 重启（对齐 Hubris `jefe` / Redox「组件 panic ≠ kernel panic」），系统继续运行。
   因此「abort 还是 unwind」的正确分界是**故障域（内核地址空间 vs 用户地址空间）**，不是「Rust 一律 abort」。
2. **调试者要 backtrace，panic 模型不应剥夺调试能力**。但 backtrace 的需求在两类故障域中权重不同：
   - 内核 panic = 停机事件，事后能拿到「现场寄存器 + 末几帧」已足够定位（且可经 `.msys` / 早期串口兜底）；全栈 unwind 对停机的边际收益低，却要付出镜像体积与 TCB 膨胀代价。
   - 用户态服务崩溃是「可重启的常态事件」，supervisor 需要完整 backtrace 才能决定 kill / dump / restart / 升级——此时 unwind 是**直接生产力**。
3. **二者应归一化为同一份结构化崩溃报告**（`CrashReport.stack_frames` 跨三类崩溃同构，见 12 §4.5），即「现场帧（内核 abort）」与「展开帧（用户态 unwind）」都落进 `StackFrame{ pc, symbol?, module, offset }`，调试者无感。

结论：C5 不是真矛盾——`02` §4.5 字面的「内核 Rust 统一 panic=abort」缺一句**显式区分用户态**的口子；补上即可与 `12` §4.5 自洽。

## 1.2 选项对比表（含多系统参照列）

| 方案 | 内核态 | 用户态 Rust 服务 | 二进制体积 | 五架构 unwind 后端 | 多系统参照 | 对 MeuOS 取舍 |
|---|---|---|---|---|---|---|
| **A. 全 abort（02 字面）** | abort | abort | 最小（无 unwind 表） | 无需 unwind | 早期 RFL、部分嵌入式 RT | ❌ 剥夺用户态 backtrace，与 12「supervisor 需完整 backtrace」冲突 |
| **B. 全 unwind** | unwind | unwind | 最大（TCB 也带 unwind 表/landing pad） | 需全部 5 架构一致 | 纯用户态 OS（Redox 全用户态） | ❌ 内核 TCB 膨胀、与「内核 panic=停机」语义相悖；违反最小 TCB |
| **C. 按故障域分（推荐）** | abort + 现场符号化 | unwind + 完整 backtrace 供 supervisor | 仅用户态服务带 unwind 表，TCB 不膨胀 | 用户态由 rustc+LLVM 全架构覆盖；C 侧走 FP 兜底 | RFL（内核 abort）+ Hubris/Redox（用户态重启 unwind） | ✅ 内核最小 TCB + 用户态可分析，二者归一 `StackFrame` |
| **D. abort + 内核也做有限 unwind** | abort 但 panic 时跑一次 in-kernel unwinder | unwind | 中（内核加 unwinder，但仍 abort 不恢复） | 需 5 架构一致 | seL4（证明与调试分离，内核不 unwind 业务栈） | △ 内核 panic 时 unwind 收益低、且要在已可能损坏的状态里遍历栈，风险大于收益；不推荐 |

> 对照 `12` §4.5 自主裁决：已选 C 路线（内核 abort+符号化、用户态 unwind），本文确认其正确并给出落点细节与回写文案。

## 1.3 明确推荐裁决

### 1.3.1 最终策略（一句话）

**内核态 TCB 内组件统一 `panic=abort`，靠panic 现场（寄存器+末几帧）+ 内核符号表做现场符号化；用户态 Rust 服务（受 supervisor 管理、可重启）启用 `panic=unwind`，产出完整 backtrace 供 supervisor 经 exception channel 分析重启；二者归一为 `StackFrame`。**

- **收益（用户态 unwind）**：完整 backtrace → supervisor 精准决策（kill/dump/restart/升级）；与 Hubris `jefe`/Redox 组件隔离哲学一致；Rust 的 unwind 是一等公民（DWARF personality + landing pad），无需自研。
- **代价（用户态 unwind）**：用户态服务镜像变大（`.eh_frame`/`.eh_frame_hdr`/personality/landing pad）；链接 `panic_unwind`（用户态可带更丰富 runtime，可行）；需五架构 unwind 后端一致（见 1.3.2）；unwind 与 capability 故障入口的衔接（用户态 panic → exception channel → supervisor，而非内核 fault entry）。

### 1.3.2 五架构 unwind 后端一致性风险

| 架构 | Rust unwind（用户态服务，rustc+LLVM） | C 侧 unwind（mcc/QBE 产 C 代码） | 一致性风险 |
|---|---|---|---|
| x86_64 | ✅ DWARF `.eh_frame`，LLVM 完整支持 | 取决于 mcc 是否吐 `.eh_frame`（见 1.3.3） | 低（Rust 侧）；C 侧走 FP 兜底 |
| i386 | ⚠️ Rust 无裸机 i386 target，用户态 Rust 服务在 i386 上本就缺位（02 C2：i386 全程纯 C） | 纯 C，靠 mcc 是否吐 unwind 信息 | 中（i386 用户态服务为 C，需 mcc 配合） |
| aarch64 | ✅ DWARF `.eh_frame`（ARM EH），LLVM 支持 | 同上 | 低（Rust 侧） |
| riscv64 | ✅ DWARF `.eh_frame`，LLVM 支持（注意 `z` 扩展 `unwind` 约定） | 同上 | 低（Rust 侧） |
| loongarch64 | ✅ DWARF（LoongArch 约定），LLVM 支持 | 同上 | 低（Rust 侧） |

**核心判断**：unwind 一致性风险**主要落在 C 代码（内核 C/asm 帧 + 用户态 C 服务）**，而非 Rust 用户态服务——后者由 rustc+LLVM 全架构覆盖，与 mcc 无关。因此：

- **推荐底座：帧指针（frame-pointer）链遍历作为跨架构通用兜底**。无论工具链是否吐 DWARF，只要保留帧指针（`-fno-omit-frame-pointer`），即可用 `FP/LR` 链做「末几帧→全栈」的可移植 unwind，统一 5 架构语义。
- **DWARF `.eh_frame` 作为 richer 路径**：在 rustc 已吐、或 mcc 后续支持吐 DWARF 的架构上启用，补全异常展开（如 Rust landing pad、C++ 风格析构）。
- **统一 in-kernel unwinder 抽象（12 §4.5）**：定义 `unwind(start_frame, arch) -> Vec<StackFrame>`，每架构一份薄后端，优先 DWARF、fallback FP-chain。内核 abort 现场只需 FP-chain 取末几帧；用户态完整 backtrace 优先 DWARF。

### 1.3.3 mcc/QBE 侧配合能力评估

- **mcc = cproc（C 前端）+ QBE（SSA 中端/后端）**。QBE 定位极简，历史上产出静态二进制、**调试信息（含 `.eh_frame`）支持有限**。这是 C5 真实风险点：`02`/`09`/`10` 中大量 C 代码（早期启动、asm 桥、Linux 兼容层 mkit、部分驱动）若需被 unwind，依赖 mcc 吐 DWARF。
- **但缓解明确**：
  1. 内核态 `panic=abort` → **根本不需要 C 侧 unwind**（只取现场寄存器 + FP 链末几帧）。
  2. 用户态 Rust 服务 unwind 由 **rustc+LLVM 独立完成**，与 mcc 正交，不受 QBE 限制。
  3. 用户态 **C** 服务（如 i386 上、或部分 C 驱动服务）若需完整 backtrace，依赖 mcc 吐 DWARF——**这是唯一硬依赖点**，需向 mcc 团队提需求（保留帧指针 + 吐 `.eh_frame`）。在 mcc 具备前，用户态 C 服务用 **FP-chain 兜底 unwinder**（牺牲个别异常展开细节，backtrace 主体可用）。
- **结论**：mcc/QBE 无需为 C5 的「推荐策略」做阻断性改动；仅需「保留帧指针」即可满足兜底，DWARF 为增强项。建议把「mcc 吐 `.eh_frame`」列为开放议题（非阻塞），并在 `02` §5 双工具链跟踪项中登记。

## 1.5 风险与退路

| 风险 | 退路 |
|---|---|
| rustc 某架构 unwind 行为不一致（如 loongarch64 LLVM 后端细节） | 以 FP-chain 兜底统一；原型期先验证 x86_64/aarch64 两架构（11 M5 优先级） |
| mcc 不吐 DWARF，用户态 C 服务 backtrace 不全 | FP-chain 兜底可用；将「mcc 吐 `.eh_frame`」列为非阻塞增强需求 |
| 用户态 unwind 被恶意利用做长展开（DoS） | unwind 在进程崩溃路径、由内核托底，不消耗正常服务配额；可设展开深度上限 |

# 二、C8 裁决：设备能力签发时序/撤销锁 + 早期串口能力归属

## 2.1 应该是什么样（解构推演）

问：在「capability Day 1 唯一模型 + 双轨驱动 + 尽早交权」模型下，**设备能力应该由谁在何时 mint、如何安全回收、早期串口归谁**？

1. **设备能力不是「从某个 root 设备能力派生」来的**。capability 世界里没有「root 硬件万能令牌」——那正是 Linux `CAP_SYS_RAWIO` 式大权。正确模型：**capability 监视器（TCB 内 Rust 组件）本身就是受约束的 mint 权威**；它在 Stage 4 直接从「内核内可信设备拓扑树」（由早期 C/asm 解析 DT/ACPI 得来，属 TCB）mint 出**窄粒度**的 `Cap(MMIO range)` / `Cap(IRQ n)` / `Cap(DMA window)` / `Cap(IO port)`。监视器自身不能做任何硬件操作，只负责 mint/check/revoke——这就是「无 root 逃生舱」在设备侧的体现。
2. **签发必须「声明即授权」且「先 revoke 旧、再 mint 新」**，杜绝悬垂/双持。驱动进程死亡（被 RS 重启）时，其持有的设备能力必须随进程消亡**自动回收**，重启的新实例拿**全新** mint 的能力。
3. **早期串口是「生死相关快速路径」，但应统一进 capability 模型**。最干净的做法：串口也在 Stage 4 被 mint 为设备能力，只是**内核 bootstrap 上下文持一份临时副本**用于早期诊断；到 Stage 5 用户态 console 服务接管时，内核撤销自己的临时副本（仅保留 panic 应急写这一窄路径）。这样「即便早期也必须经能力网关」的原则不被破坏，最小 TCB 也不被持续侵蚀。

## 2.2 选项对比表（含多系统参照列）

| 维度 | Linux（反面） | seL4 | Zircon/Fuchsia | MINIX 3 | **MeuOS（推荐）** |
|---|---|---|---|---|---|
| 设备能力来源 | 驱动内核全特权，无设备能力 | 所有设备资源为 cap，挂 CSpace | 句柄即 cap，devmgr 经驱动框架授 cap | 用户态驱动，无显式 cap | **监视器从可信拓扑 mint 窄粒度设备 cap（无 root 设备 cap）** |
| 签发时序 | 加载即全特权 | boot 期由 root task 持全 cap | devmgr 匹配后授 cap | 启动即赋权 | **Stage 4 mint → Stage 5 devmgr 按需下发** |
| 回收/撤销 | 卸载即解映射，无 cap 回收概念 | `cap_delete` 显式 | 进程死亡自动回收句柄 | RS 重启进程 | **撤销锁序列 + 进程死亡自动回收（双保险）** |
| 早期串口 | 内核永久直写 tty | 无此概念 | 内核早期 uart 后交 driver | 内核早期串口 | **Stage 1 内核临时持，Stage 5 交用户态 console，仅留 panic 应急写** |
| 多系统参照结论 | 反例 | cap 不可伪造/可撤销范本 | 组件化驱动 + cap 下发 | 看门狗自愈 | 取 seL4 的 cap 回收 + Zircon 的按需下发 + MINIX 的 RS 重启 |

## 2.3 明确推荐裁决

### 2.3.1 设备能力签发时序（含根设备能力自举）

```
[Stage 2 · C/asm · TCB]  解析 DT/ACPI → 设备拓扑树（仅「资源区间事实」，尚非能力）
        │                  · 每节点：MMIO 基址区间 / IRQ 号 / DMA 窗口 / IO 端口
        ▼
[Stage 4 · Rust TCB]  capability 监视器上线（先于任何非特权用户态代码）
        │              · 监视器作为受约束 mint 权威，从「可信设备拓扑树」直接 mint
        │                第一批设备能力——**无外部 root 设备 cap 需自举**：
        │                Cap(MMIO range) / Cap(IRQ n) / Cap(DMA window) / Cap(IO port)
        │              · 这些 cap 暂由监视器持有（待下发）；串口 cap 同时 mint，
        │                内核 bootstrap 上下文持一份「临时副本」用于早期诊断
        ▼
[Stage 5 · 交权]  spawn devmgr + console 服务（均受 supervisor 管理）
        │          · devmgr 匹配设备（bind 规则）→ 向监视器请求并获授权具体设备 cap
        │            （「声明即授权」：驱动声明所需资源，监视器 mint 恰好那些）
        │          · 串口：内核撤销自身临时副本 → 转交 console 服务（保留 panic 应急写）
        ▼
[运行期]  驱动进程持「仅自己设备」的受限 cap；新增/热插拔设备由 devmgr 重复上述下发
```

- **根设备能力如何自举（关键澄清）**：不存在「先 mint 一个 root 设备 cap 再派生」的环节。自举链是——(a) 早期 C/asm（TCB）把硬件事实登记为设备拓扑树；(b) Rust capability 监视器（TCB）上线后即具备 mint 职能（mint 是其作为 TCB 代码的固有职能，不依赖任何句柄）；(c) 监视器从拓扑树 mint 出窄粒度设备 cap。监视器是「受约束的 root-of-mint」，不是「持万能设备 cap 的主体」，与 `07` §4.1「无 root 逃生舱」一致。
- **签发原则**：devmgr 持「受约束的 mint/derive right（限定设备 cap 类、限定其自身 Job 子树）」；它请求监视器为某驱动 mint 具体 cap，监视器校验后下发。杜绝 confused deputy——devmgr 不能 mint 超出其 Job 边界的设备 cap（对齐 `00` C2 的受约束 mint 模型）。

### 2.3.2 撤销锁（revoke lock）机制

目标：驱动崩溃/卸载/设备拔出时，硬件引用（MMIO 映射、在飞 DMA、IRQ）安全回收，且**新实例重启前旧实例必已彻底失效，避免悬垂/双持**。

```
撤销锁序列（由 RS/supervisor 触发，内核 capability 监视器执行，持每设备 cap 记录自旋锁串行化）：

 1. 屏蔽 IRQ 转发：中断控制器停止向该驱动进程转发其 IRQ（防「revoke 后还来中断」竞态）
 2. 冻结驱动进程：挂起，使其不再发起新 MMIO 访问
 3. 撤销 DMA 窗口：IOMMU 域对该驱动失效 / 解映射，截断在飞 DMA
 4. 回收能力：revoke 该进程持有的设备 cap 句柄（从进程句柄表移除，能力记录标 dead）
 5. 回收进程：kill + 释放地址空间
 6. 仅在以上全部完成、硬件引用清零后，为新实例 fresh-mint 设备 cap 并 spawn
```

- **防双持（撤销锁的本质）**：capability 记录带「holder 回指 + 生命周期绑定到持有者进程」。持有者进程死亡 → 内核**自动回收其全部句柄**（对齐 Zircon handle-close-on-process-death），即便显式 revoke 被跳过也能回收。重启的新实例拿的是**重新 mint**的 cap，旧 cap 已随旧进程死亡 reclaim——**同一（设备, 资源区间）在任一时刻至多一个 live cap**（除非显式 duplicate-with-rights）。
- **串行化**：每设备 cap 记录持一把自旋锁，mint/revoke 互斥，杜绝「旧实例未 reclaim 完、新实例已持同资源 cap 且 DMA 在飞」的窗口。
- **与 watchdog 协同**：用户态驱动由 RS 式看门狗 ping；超时/崩溃即触发上述序列。内核态快速驱动（生死相关，如中断控制器）不在此列——其故障按 10 §4.2 走「内核 panic + 重启策略」。

### 2.3.3 早期串口控制台能力归属与交接时点（阶段表）

| 阶段 | 串口持有方 | 访问方式 | 是否经能力网关 | 说明 |
|---|---|---|---|---|
| Stage 1（boot 早期，cap 世界未起） | 内核 bootstrap 上下文（TCB） | 直写 MMIO/端口 | 否（此时无 cap 世界，且为生死相关快速路径） | 仅用于早期诊断 banner + 后续 panic 应急输出；串口为唯一早期可观测通道（12 §4.8） |
| Stage 4（cap 世界激活） | 监视器 mint 出串口 cap；内核 bootstrap 上下文持**临时副本** | 内核直写（临时副本） | 是（已 mint 为 cap，仅内核临时持） | 模型统一：串口也是设备 cap，不特殊化为「内核固有硬件」 |
| Stage 5（console 服务接管） | **用户态 console 服务**（经 cap 持有） | 用户态驱动经能力网关代理 | 是 | 内核**撤销自身临时副本**；正常控制台 I/O 归受 cap 约束、可被 RS 重启的用户态服务 |
| 运行期（panic 时） | 内核 panic 路径持**窄 emergency-write cap** | 内核直写（仅 panic 现场） | 是（应急窄权） | 即便 console 服务崩溃，内核 panic 仍能经串口兜底输出（12 §4.3 内核 panic 特殊性） |

**推荐裁决（一句话）**：早期串口 Stage 1 由内核直写（生死相关、cap 世界未起，可接受），但 Stage 4 即被 mint 为设备 cap、内核仅持临时副本，**Stage 5 用户态 console 服务接管时内核撤销临时副本、仅保留 panic 应急写窄权**——既满足最小 TCB（内核常态串口逻辑不留在 TCB），又统一进 capability 模型（无「内核固有硬件」特例）。

- **备选与取舍**：
  - 备选 X（内核永久自持串口）：最简单，但违反「即便内核态驱动也只持设备能力」且令串口逻辑常驻 TCB——**仅作原型期临时回退**（10 附录 A 已允许「UART 早期可内核态回退」），长期不推荐。
  - 备选 Y（无临时副本、Stage 1 即视为「内核固有」）：破坏统一 cap 模型，与 Day 1 唯一模型张力大——**不推荐**。
  - **推荐（临时副本 + Stage 5 撤销）**：最契合最小 TCB 与 capability 模型，本文定为裁决结论。

## 2.4 连带影响

- **`09-启动与初始化`**：其 §6 待决 4（设备能力签发时序/撤销）、待决 7（早期串口能力归属）可据此闭环；§5.4 第一批 capability 清单中「设备能力」条目补上「mint 权威=监视器、无需 root 设备 cap」的澄清。
- **`10-设备驱动模型`**：其 §4.3「授权」步骤、§4.6「能力可撤销」补上「撤销锁序列 + 进程死亡自动回收」机制；§5 开放议题（DMA/IOMMU、内核态 Rust 驱动 panic）与本文 C5/C8 协同。
- **`07-安全模型`**：设备 cap 的 mint 模型（监视器为受约束 root-of-mint、devmgr 持受约束 mint right）与 `07` §4.5 权限传播/受约束 mint 对齐；建议 `07` §5 开放议题补一条「设备 cap 的 mint right 粒度」。
- **`04-进程与调度`**：进程死亡自动回收句柄是撤销锁的「第二重保险」，需 `04` 的进程对象生命周期与 capability 监视器对接（已在 `04` §4.1 handle 模型框架内）。

## 2.5 风险与退路

| 风险 | 退路 |
|---|---|
| 撤销锁序列中 DMA 在飞、revoke 后仍写脏内存 | IOMMU 域失效优先于进程回收（步骤 3 先于 5）；无 IOMMU 平台按 10 §5-2 仅允许受信内核态驱动 |
| Stage 5 交接瞬间 console 服务尚未就绪、内核已撤销临时副本 → 控制台空窗 | 内核保留 panic 应急写窄权（不空窗）；正常日志空窗仅限 Stage 5 极短窗口，可接受 |
| 监视器 mint 被误用为「设备万能 cap」 | mint 职能仅对「可信拓扑树中的具体资源区间」生效，且 devmgr 持受约束 mint right（交集模型），无法越界 |
| 多架构早期串口访问差异（x86 端口映射 vs ARM/RISC-V MMIO） | 由设备拓扑树统一描述，驱动/内核按拓扑取访问方式，架构差异封死在早期层 |

## 2.6 残留需拍板项（C8）

1. **撤销锁序列中「冻结驱动进程」的内核原语**：需 `04`/`10` 明确由谁发起 freeze（RS 还是内核直接），本文建议内核 capability 监视器在 RS 请求下执行。
2. **devmgr 的 mint right 粒度与收窄规则**：是否复用 `07` 的 `GRANT`/`MANAGE` right，还是新增设备类专属 right？需 `07` 定稿 rights 位图后回填。
3. **无 IOMMU 平台的用户态驱动退化策略**：是否禁止用户态 DMA 驱动、仅留受信内核态驱动（10 §5-2 已提，需与本文撤销锁协同定稿）。
4. **早期串口「临时副本」的内核持有时长边界**：是否严格在 console 服务 `ready` 信号到达即撤销，还是允许一段宽限期？建议严格 `ready` 即撤销。
5. **热插拔设备的 cap mint/revoke 时序**：本文时序以启动期静态拓扑为主，热插拔（ACPI/PCIe 热插）的设备 cap 动态 mint 需 `10` 补充。

# 三、总结（两裁决一句话收口 + 残留需拍板项汇总）

- **C5 推荐一句话**：内核态 TCB 内组件统一 `panic=abort` + panic 现场符号化，**保留用户态 Rust 服务（受 supervisor 管理、可重启）启用 `panic=unwind` 产出完整 backtrace** 的口子，二者归一为 `StackFrame`；对 `02` §4.5 的精确回写文案见 §1.3.4（本文只建议、不真改 `02`）。
- **C8 推荐一句话**：设备能力由 capability 监视器（TCB）在 Stage 4 从可信设备拓扑树**直接 mint 窄粒度 cap（无 root 设备 cap 需自举）**、Stage 5 经 devmgr「声明即授权」下发，回收走「撤销锁序列 + 进程死亡自动回收」双保险防悬垂/双持；早期串口 Stage 1 内核直写、Stage 4 mint 为 cap 且内核仅持临时副本、**Stage 5 交用户态 console 服务后内核撤销临时副本、仅留 panic 应急写窄权**。

**残留需拍板项汇总（待大喵/协同方拍板）**：
- C5：① 02 §4.5 是否照 §1.3.4 回写；② 用户态 unwind 是否设深度上限；③ mcc 吐 `.eh_frame` 优先级；④ i386 用户态 C 服务 backtrace 策略。
- C8：① 撤销锁 freeze 发起方（内核 vs RS）；② devmgr mint right 粒度（是否新增设备类 right）；③ 无 IOMMU 平台用户态驱动退化策略；④ 早期串口临时副本撤销的严格 `ready` 边界；⑤ 热插拔设备 cap 动态 mint 时序。
