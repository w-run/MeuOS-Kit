## 0. 裁决摘要（先给结论）

- **C2 推荐**：密钥 unwrap 权**必须**走 capability，且**不复用 `MANAGE`**——在 `07` rights 位图中**新增显式 `KEY_UNWRAP` / `KEY_WRAP` 两个密钥管理 right**（服务端专用，永远不向客户端 mint）。客户端拿到的是 `READ`/`WRITE` 文件句柄，**解密动作在 FS 服务的 pager 内发生、密钥材料永不出 FS 服务**；因此「revoke 句柄 = 撤销解密权」链路通过「rights 派生树 + VMO/pager 上下文回收」**闭环成立**，无需独立 KRL。FS 服务作为委托人的 confused deputy 由 **受约束 mint（constrained mint）** 模型解决：FS 服务持有的是「签发上限被内核封顶为 `{READ,WRITE,EXECUTE}` 的 mint token」，其自身持有的 `MANAGE`/`KEY_UNWRAP` 仅用于内部 pager 与密钥轮换，**永远不能作为客户端句柄的 rights 被下发**。
- **C3 推荐**：统一命名空间内部模型采用 **每进程独立 namespace（Fuchsia / Plan 9 `RFNAMEG` 式）**，**拒绝**「共享可变全局根 + unveil 裁剪」作为内部模型；其工程便利（B 的 ergonomics）通过 **spawn 时 COW 继承父 / Job 的 namespace 模板**获得——模板是「被复制的」，不是「被共享的可变对象」。Linux 兼容层（08）看到的「全局路径树」是**每进程 namespace 绑定经 Linux 语义投影出的合成视图**，`/proc` `/sys` `/dev` 为按需生成的生成式目录 cap；内核**不存在全局 `/`**。

## ① 两项裁决「应该是什么样」推演

### 1. C2：密钥访问权「应该是什么样」

从 capability 哲学第一性原理推演：在纯 capability 系统里，**权威 = 不可伪造的令牌**，权限随令牌走，无「身份」、无「环境凭证」。

把这条原则落到「文件加密」上：

- 文件内容是密文，要读明文必须 unwrap 文件密钥（file key 由卷密钥 KEK 包装）。
- 谁能 unwrap？理想情况下，**能读文件的人就能解密，不能读的人就不能解密**——即「解密权」应是从「文件访问权」派生出来的，而非一份与环境（uid、keyring、会话）绑定的**环境凭证**。
- 进一步：撤销「解密权」应等价于撤销「文件访问权」。若密钥解锁是独立于文件句柄的环境凭证（如 Linux keyring），则 revoke 文件句柄后，持有 keyring 者仍能解密——这破坏了 capability 的「权限随令牌走」，也制造了一处 confused deputy 温床（任何能摸到 keyring 的进程都能解密）。
- 最干净的结构：**密钥 unwrap 权 = 文件句柄的 right 之一**；句柄即令牌，revoke 句柄即撤销解密。这与 `06` §4.2.3 的自述完全一致，是方向①③互锁的最高价值点。

但「密钥 unwrap 权 = 文件句柄 right」在落地时有两种截然不同的读法，必须区分：

- **读法 α（客户端侧）**：客户端持有 `READ` 文件句柄，自己执行 unwrap 拿到明文密钥，自行解密。→ **危险**：密钥材料进入客户端地址空间，违反「最小 TCB / 密钥不出受控域」，且客户端可缓存密钥绕过后续 revoke。
- **读法 β（服务端 pager 侧，推荐）**：客户端只持 `READ` 文件句柄；FS 服务作为 pager 在缺页时用**自己持有的服务端密钥权**解密该文件页面，把明文页经 VMO 交给客户端。**客户端拿到的永远是明文页，从不持有原始密钥**。→ 这正是 lean hybrid「数据通路在内核/受控域、逻辑在用户态」在加密上的体现（`06` §4.4.1）。revoke 客户端句柄 → VMO/pager 上下文回收 → 不再供页 → 解密停止。

推演结论：理想模型是 **β**。因此「密钥 unwrap 权 = 文件句柄 right」应理解为：
- 对**客户端**：unwrap 能力**隐式蕴含于 `READ`（解密读）/ `WRITE`（加密写）**，是语义后果，不是客户端直接持有的危险原语；
- 对**服务端（FS 服务 / 密钥守护）**：unwrap 是一个**显式的、独立的密钥管理权**，必须与 `MANAGE` 正交（否则 `MANAGE` 这个「大权」会像 Linux 的 `CAP_SYS_ADMIN` 一样悄悄携带加密权威，重演「新 root」）。

### 2. C3：命名空间「应该是什么样」

从 capability 哲学推演「命名空间应该是什么样」：

- 统一命名空间要取代 `/proc+/sys+/dev` 拼凑，覆盖设备 / 进程 / 网络 / 普通文件。
- 理想结构：**可见性即权限**。一个进程看不到某路径，不是因为「权限被拒（EACCES）」，而是因为它**根本没有通往那个节点的 capability**——路径根本「不存在」于它的世界。这比 Linux「全局树 + 多伪 FS + 访问被拒」严格得多，也天然契合 `07` 的最小权限。
- 由此推演：**命名空间不应是内核硬编码的全局共享树**（那是「隐式环境凭证」的命名空间版），而应是**每进程独立组装的一组 `path → 节点能力` 绑定**，在 spawn 时由 Job / 监督者 / manifest 注入，默认全不可见、unveil = 显式 reveal。

两种内部模型对比推演：

- **A（每进程独立 namespace）**：每个进程持有一张自己的绑定表；spawn 时组装；unveil 注入新绑定；revoke 一条绑定只影响该进程。隔离是**结构性的**——没有进程共享的可变命名空间对象。
- **B（共享根 + unveil 裁剪）**：存在一个（或 per-Job）全局共享命名空间树，各进程通过 unveil 把视图裁剪窄。其代价：共享根是一个**活的、可变的全局对象**（挂载/卸载有共享可变状态），本质上是一份「隐式 ambient capability」，与「无隐式权限」冲突；且裁剪语义需 COW 化才能不互相干扰，最终又退化成 A 的内部结构。

推演结论：**内部采用 A**。B 的工程便利（大家有个共同起点）并不要求「共享可变根」，而只需「spawn 时复制一份共同模板」——即 **COW 继承父 / Job 的 namespace 模板**。模板被复制后才属于子进程，子进程可独立裁剪/扩展，**既得 A 的隔离，又得 B 的便利**。

对 08 兼容层的投影推演：Linux 二进制期望「全局路径树」。但「全局」只是**该进程的命名空间绑定经 Linux 路径语义投影出的合成视图**——`/` 是该进程 Job 声明的 rootdir cap（多为 sysroot 子卷），`/proc` `/sys` `/dev` 是按需生成的生成式目录 cap（`08` §3.2 / §4.1 已预见）。内核**不存在全局 `/`**，兼容层负责把「我以为我是 root、我有整棵树」翻译成「我持有一组受限的 namespace 绑定」。

## ③ 明确推荐裁决（含对 07 rights 位图、06 命名空间的具体修订建议）

### C2 明确推荐

**裁决 1 — 密钥 unwrap 走 capability，且不复用 `MANAGE`。**

- 密钥访问权生命周期**绑定到文件句柄 capability**（方向①③互锁最高价值点，`06` §4.2.3 自述成立）。
- **否决「复用 `MANAGE`」**：`MANAGE` 是文件管理权（resize / 改元数据 / 销毁），属「大权」；把密钥权威并入它会重演 Linux `CAP_SYS_ADMIN`「新 root」之弊——一个只需 resize 文件的服务将静默获得解密权，破坏最小权限，并放大 confused deputy 爆炸半径。
- **新增两个显式 right（服务端专用）**：
  - `KEY_UNWRAP`：使用卷密钥 KEK unwrap 某文件的 file key（解密权威）。
  - `KEY_WRAP`：wrap / re-wrap file key（加密写入、密钥轮换权威）。
  - 二者与 `MANAGE` **正交**，bitmap 中独立占位（建议紧邻 `MANAGE`/`EXECUTE` 之后，见下）。
- **客户端侧 unwrap 隐式于 READ/WRITE**：客户端持有的 `READ` 文件句柄，其「解密读」是语义后果，**不**以 `KEY_UNWRAP` 位形式出现在客户端句柄上（客户端永不持 `KEY_UNWRAP`，密钥材料永不出 FS 服务 pager）。`WRITE` 同理隐含「加密写」。`KEY_UNWRAP`/`KEY_WRAP` **只出现在 FS 服务 / 密钥守护的服务端句柄上**，由 boot 期 root-of-trust 派生（`09` §5.4）。

**裁决 2 — revoke 链路闭环成立，无需独立 KRL。**

- 客户端 `READ`/`WRITE` 句柄 → 派生出 VMO 映射 + FS 服务 pager 上下文（`03` §4.4 / `06` §4.4.1）。
- revoke（close）该句柄 → 内核回收 VMO 派生链 + 拆除对应 pager 注册（`03` §4.4 已声明 revoke 即回收）→ FS 服务不再为该客户端供页 → 不再发生任何解密。**链路闭合。**
- `07` §5.4 的 **derivation tree** 追踪 `READ`→派生 `READ` 的权限传播；因 unwrap-for-read 蕴含于 `READ`，revoke 祖先 `READ` 句柄即级联杀死所有派生 `READ` 句柄及其 pager 上下文，解密随之停止。**无需在 derivation tree 里单独建「密钥 unwrap 节点」**——现有 rights 传播已覆盖。
- FS 服务的**服务端 `KEY_UNWRAP` 不在客户端 derivation tree 中**（它是服务端权威，独立）。故客户端 revoke **不会**剥夺 FS 服务的卷级密钥权（正确：FS 服务仍需为其他文件解密）。文件级密钥轮换 / 销毁由服务端 `KEY_WRAP` + 显式管理操作完成，属服务端职责，非客户端 revoke 范畴。

**裁决 3 — FS 服务 confused deputy 由「受约束 mint（constrained mint）」模型解决。**

- FS 服务在 spawn 时（由 root job / 监督者，经 `09` §5.4 第一批 capability 自举）获得两类能力：
  1. **`CAP_MINT_FILEHANDLE`**：一个 **mint token**，其**签发上限（issuance ceiling）被内核封顶为 `{READ, WRITE, EXECUTE}`**（数据面 right）。它**不含 `MANAGE` / `KEY_UNWRAP` / `KEY_WRAP` / `GRANT`**。
  2. **服务端内部权**：`MANAGE`（FS 树管理）+ `KEY_UNWRAP`/`KEY_WRAP`（卷密钥权），仅用于 pager 解密、元数据管理、密钥轮换，**绝不参与向客户端的 mint**。
- 客户端请求 `open(P, R)` 时，FS 服务签发的句柄 effective rights = **`R ∩ client_namespace_auth(P) ∩ mint_ceiling`**：
  - `client_namespace_auth(P)`：客户端在 spawn / unveil 时获得的、针对前缀 `P` 的命名空间授权（如 `unveil("/data","rwc")` → 客户端最多可请求 `/data` 下文件的 `rwc`）。
  - `mint_ceiling`：`{READ,WRITE,EXECUTE}`，由内核对 mint token 强制。
- 结果：即便恶意客户端谎报「我要 `MANAGE|KEY_UNWRAP`」，FS 服务的 mint token 上限不含这些位，**内核拒绝签发**——FS 服务无法成为 confused deputy。这正是 seL4 `CNode_Mint` / Zircon `zx_handle_duplicate` rights 缩减的工程先例，也是 Hardt 「confused deputy」论文的标准解（以「委托人能签发的权」受限于「客户被授权的权 ∩ 委托人被允许签发的权」）。
- 块设备能力同理：FS 服务只持 `READ`/`WRITE`/`block-io` 的块设备 cap（`06` §2.2 / `10`），其 mint token 不授予块设备 cap 给客户端。

**→ 对 `07` rights 位图的具体修订建议（供 07 定稿时回填，本文不改动 07）：**

- 在 `07` §4.1 基础 right 集合 `{READ, WRITE, EXECUTE, MANAGE, GRANT, REVOKE, DUPLICATE}` 中**新增**：
  - `KEY_UNWRAP`（位图建议值：紧邻 `MANAGE` 之后，如 bit 6）——解密 unwrap 权威，**仅服务端（FS 服务 / 密钥守护）持有**。
  - `KEY_WRAP`（bit 7）——加密 wrap / 密钥轮换权威，**仅服务端持有**。
- 在 `07` §4.5 / §5.2 明确：
  - `KEY_UNWRAP`/`KEY_WRAP` **永不出现在跨进程 grant / mint 给客户端的句柄上**（内核 mint 强制）。
  - 客户端 `READ` 句柄的「解密读」为语义隐式，不为独立 right；`WRITE` 的「加密写」同。
  - `CAP_MINT_FILEHANDLE` 的 issuance ceiling 默认 `{READ,WRITE,EXECUTE}`，由 capability 监视器在 mint 系统调用处强制（`07` §4.1 的「权限随句柄走」落点）。
- 在 `07` §5.4 明确：derivation tree 追踪含 `READ`/`WRITE` 的句柄传播即足以覆盖「句柄→解密权」链，无需单独密钥节点；服务端 `KEY_UNWRAP` 独立于客户端 derivation tree。

**→ 对 `06` §4.2.3 / §6 待决 1/2 的具体修订建议（供 06 回填，本文不改动 06）：**

- §4.2.3 明确「客户端 unwrap 隐式于 READ/WRITE，密钥材料不出 FS 服务 pager；显式 `KEY_UNWRAP`/`KEY_WRAP` 为服务端密钥权，由 boot root-of-trust 派生」。
- §6 待决 1 结论落定：**新增 `KEY_UNWRAP`/`KEY_WRAP`，不复用 `MANAGE`**；revoke 链路经 derivation tree + VMO/pager 回收闭环，无 KRL。
- §6 待决 2 结论落定：FS 服务 mint 受「客户端命名空间授权 ∩ mint token 封顶 `{READ,WRITE,EXECUTE}`」约束；服务端 `MANAGE`/`KEY_*` 不参与客户端 mint——此即 07 须定义的「受约束 mint」授权模型。

### C3 明确推荐

**裁决 4 — 内部模型 = 每进程独立 namespace；拒绝「共享可变全局根」。**

- 命名空间 = **每进程的 `path → 节点能力` 绑定表**，spawn 时组装，默认全不可见，unveil = 注入绑定（`06` §4.1 自述成立）。
- **否决「共享可变全局根 + unveil 裁剪」为内部模型**：共享根是一份 ambient capability，与 `07`「无隐式权限」冲突，且共享可变状态放大 TCB 与故障面。

**裁决 5 — B 的 ergonomics 经「COW 继承模板」获得（落地形态 = 对比表选项 C）。**

- spawn 新进程时，内核**复制（COW）父进程 / 所属 Job 的 namespace 模板**作为子进程的初始绑定表；子进程随后可独立 unveil / 裁剪，**互不影响**。
- 「共享」只发生在**模板来源**层（同 Job 的进程共享同一份模板副本起点），**不**发生在运行时可变对象层。这既给旧二进制「开箱即见类 Linux 整棵树」的便利，又保住 A 的隔离。
- 容器场景 = 受限 spawn + 全新（更窄）namespace 模板 + 强 pledge（`08` D1 / `00` C4），与 Fuchsia 组件框架、Plan 9 `RFNAMEG` 一致。

**裁决 6 — 与 08 兼容层的衔接规范（供 08 采纳，本文不改动 08）。**

定义「Linux 全局路径树」→「MeuOS 每进程 namespace」的**规范性映射**：

| Linux 语义 | MeuOS 内部 | 兼容层（08）动作 |
|------------|------------|------------------|
| `open("/abs/path", mode)` | 在当前进程的 namespace 绑定表中做 capability 查找 | 按进程 namespace 解析；未绑定前缀 → `ENOENT`/`EACCES`（`08` §3.2） |
| 全局可见 `/` | 进程 namespace 的 `/` 绑定 = 其 Job 声明的 rootdir cap（多为 sysroot 子卷 cap） | spawn 注入，非内核全局根 |
| `/proc` `/sys` `/dev` | 生成式目录 cap，由兼容层向统一命名空间注册 | 查询时按需生成 Linux 视图（`08` §4.1 / D5） |
| `chroot` / `pivot_root` | 重绑进程 namespace 的 `/` 绑定到某子目录 cap | 受 capability 约束，非全局操作 |
| `mount` | 注入一条 namespace 绑定（mount-capability） | 受 Service Registry + mount-cap 约束（`06` §4.4.2） |
| 原生 `unveil(path, perm)` | 注入 / 收窄一条 namespace 绑定 | 原生即此；Linux 二进制无对应则视为贯穿默认沙箱 |
| 容器 / namespace 隔离 | 新进程 spawn 时给全新受限 namespace 模板 | 容器 = 受限 spawn + 命名空间绑定 + 强 pledge（`00` C4） |
| `getuid()==0` | 合成视图，内部 authority = Job capability 集 | `08` §3.1（root 为视图非权限） |

- 关键：**兼容层对外呈现的「全局路径树」是每进程的合成投影**，内核无全局 `/`；两进程「共享某挂载」是通过各自 namespace 绑定指向**同一目录 cap**（capability 级共享）实现，而非共享一张可变表。
- `unveil` 与 spawn 绑定的来源/继承语义据此对齐：`04` spawn 的输入之一即为 namespace 模板（或继承自父/Job），`unveil` 是运行期追加绑定，`pledge rpath/wpath/cpath` 约束未来能否追加（`06` §4.1 / `07` §4.2）。

**→ 对 `06` §4.1 / §6 待决 3 的具体修订建议（供 06 回填，本文不改动 06）：**

- §4.1 明确：内部模型 = 每进程 namespace；spawn 时 **COW 继承父 / Job 的 namespace 模板**（非共享可变根）；「共享根 + unveil」仅作为被否决的内部备选记录。
- §4.1 补一段「与 08 兼容层的投影规范」，引用上表（或指向本文第 ③ 节裁决 6）。
- §6 待决 3 结论落定：**每进程独立 namespace（A），COW 继承模板得 B 的 ergonomics；08 全局路径树 = 每进程合成投影，无内核全局 `/`**。
- §6 待决 8（子树暴露者代理 vs 直露）：建议「`/dev` `/proc` `/net` 由对应服务**直接**暴露目录 cap，FS 服务经 mount-capability 委托为门面」——与每进程 namespace 一致（各服务自管子树，最小 TCB）。

**→ 对 `04` / `08` 的协同建议（供两文档回填）：**

- `04` §4.2 spawn 输入清单显式加入「namespace 模板 / 绑定集（或继承标记）」；明确 spawn 默认 COW 继承 Job 模板。
- `08` §3.2 / §4.1 采纳「全局路径树 = 每进程合成投影」规范；`08` D5（`/proc` `/sys` 生成策略）与 `06` §6 待决 8 协同定稿。

## ④ 连带影响

### C2 连带影响
- **`07` rights 位图扩展**：新增 `KEY_UNWRAP` / `KEY_WRAP`（影响 §4.1 / §5.2 / §4.5 / §5.4）。
- **`06` §4.2.3 厘清**：客户端 unwrap 隐式于 READ/WRITE，密钥不出 FS 服务 pager；显式 `KEY_*` 仅服务端。
- **`03` VMO / pager revoke**：revoke 必须拆除 pager 上下文（`03` §4.4 已声明，C2 使其成为加密撤销闭环的硬依赖）——实现层须保证 pager 注册随句柄 revoke 同步回收。
- **`09` Stage 4 自举**：root-of-trust capability → 派生 FS 服务的 `KEY_UNWRAP`/`KEY_WRAP` + `CAP_MINT_FILEHANDLE`（封顶 `{READ,WRITE,EXECUTE}`）；这是「第一批 capability」清单（`09` §5.4）需补的密钥权项。
- **`05` cap-transfer**：FS 服务经 channel 把「已解密明文 VMO」交给客户端，而非交密钥；cap-transfer 只传 VMO handle（含 `READ`/`WRITE`），符合 `05` §4.5「委托而非复制权限」。
- 与 **C1（物理内存归属，`00` §3）** 正交：VMO revoke 触发物理页回收（C1 折中方案），密钥 revoke 是服务端独立权威，二者不耦合。

### C3 连带影响
- **`04` spawn 原语**：namespace 模板成为 spawn 一等输入；COW 继承语义需与句柄继承集（`04` §4.2）协同定义。
- **`08` 兼容层**：全局路径树改为每进程合成投影，影响 `open`/`mount`/`chroot`/`pivot_root` 翻译（`08` §3.2 / §4.1）；`/proc` `/sys` 生成式视图成为必须（D5）。
- **`05` Service Registry / mount-capability**：namespace 绑定引用服务目录 cap；mount = 注入绑定，受 Service Registry 约束（`06` §4.4.2）。
- **`09` Stage 5**：FS 服务作为 namespace 根聚合者，按 mount-capability 委托 `/dev` `/proc` `/net`（`06` §4.1）——与每进程 namespace 自洽（每个进程持一份指向这些服务目录 cap 的绑定）。
- 与 **C4（沙箱默认 deny，`00` §3）** 强互锁：每进程 namespace 让「默认全不可见」成为结构事实，C4 的「默认不允许绕过 pledge」借此天然落地。

## ⑤ 风险与退路

### C2 风险与退路
- **风险 R2-1**：客户端持 `READ` 可迫使 FS 服务解密任意其有权读的文件页——但客户端**只拿到明文页、拿不到密钥**，fail-closed。退路：明文页经 VMO 交付，密钥缓存驻留 FS 服务且按 file id 索引，句柄 revoke 即逐出对应缓存项。
- **风险 R2-2**：FS 服务被攻破 → 卷级 `KEY_UNWRAP` 暴露，全卷明文风险。退路（缩小爆炸半径）：将密钥 unwrap 从 FS 服务**拆分**为一个极小的「密钥守护（keydaemon，TCB）」，FS 服务 pager 经 channel 向 keydaemon 请求单文件解密，自身不持 `KEY_UNWRAP`；keydaemon 是最小 TCB、可独立验证/重启（`01` 最小 TCB 精神）。此为可选演进，原型期可先让 FS 服务持 `KEY_UNWRAP`，但**架构须预留 keydaemon 拆分面**。
- **风险 R2-3**：per-page unwrap 热路径延迟。退路：对称解密极快；FS 服务维持「已 unwrap 的 file key」短期缓存（按 file id，随句柄 revoke 失效）；实测若仍瓶颈，密钥缓存前置或热点文件直接 VMO 下发（`06` §6 待决 4 pager 基准同路径）。
- **风险 R2-4**：`KEY_WRAP` 用于密钥轮换时若并发 revoke，可能写出新旧密钥混合状态。退路：密钥轮换是服务端事务操作，与 CoW 快照（`06` §4.3）同事务边界，原子 repoint 避免半轮换。

### C3 风险与退路
- **风险 R3-1**：每进程绑定表内存开销。退路：绑定表极小（`path → cap` 少量项），spawn 时 COW 继承模板，仅 unveil / 裁剪时真正分化；实测远小于 Linux 每进程 VFS 缓存占用。
- **风险 R3-2**：两进程「共享挂载」语义（Linux 程序假定全局 mount 可见）。退路：共享发生在 **capability 级**——两进程 namespace 各持一条指向**同一目录 cap** 的绑定；目录 cap 本身可变（由服务管理），但各自的绑定表独立，互不影响可见性判断。兼容层把「共同绑定」作为 Job 模板默认项注入，旧二进制无感。
- **风险 R3-3**：若每进程模型对复杂兼容程序（如容器运行时、需全局 `/proc` 遍历）成本过高。退路：**内部接口维持每进程**，工程上可退化为「per-Job 共享 namespace + per-process unveil 裁剪（选项 B）」作为**内部优化实现**——但呈现给进程的**仍是每进程视图**（兼容层照常投影），故外部模型不变、退路低风险。即 B 仅作为 A 的可选实现优化，而非模型回退。
- **风险 R3-4**：`/proc` `/sys` 生成式视图性能（`08` D5）。退路：原型期最小集（pid/self/stat/maps），按需生成不落地，与 `12` inspect 子树衔接（`00` C13）。

## ⑥ 残留需拍板项

### C2 残留需拍板
1. `KEY_UNWRAP` / `KEY_WRAP` 在 `07` rights 位图中的**具体 bit 位分配**（建议 bit 6/7，紧邻 `MANAGE`），及是否还需 `KEY_VERIFY`（AEAD / fs-verity 防篡改认证标签校验权，`06` §4.2.3 可选文件级 AEAD）。
2. **密钥守护是否独立为 TCB 微服务**（R2-2 退路），还是原型期由 FS 服务持 `KEY_UNWRAP`；若独立，keydaemon 与 FS pager 的 channel 协议需定。
3. FS 服务端「已 unwrap file key」缓存的**失效 / 驱逐策略**细则（revoke 触发逐出 vs LRU vs 配额）。
4. `CAP_MINT_FILEHANDLE` 的 issuance ceiling 是否允许**按文件类型/目录策略**细化（如某目录允许 mint `EXECUTE`，某目录仅 `READ`）——涉及与 `unveil` 权限的联动。
5. 文件级密钥层次（file key ← 卷 KEK ← root-of-trust）的**密钥派生函数 / 包装算法**选型（AEAD 套件），属 `06`/`07` 实现层，但影响 right 语义边界。

### C3 残留需拍板
1. namespace 模板的**默认来源**：由**监督者（meu-supervisor）按 Job manifest 定义**，还是**继承父进程**（spawn 时 COW 父表）？建议：**Job 定义基线模板 + spawn 默认 COW 父表**（二者一致时父表即 Job 模板副本）；需 `04` 与监督策略定稿。
2. `/proc` `/sys` / `/dev` 生成式视图的**性能边界与最小集**（`08` D5 / `00` C13）——仍开放，需与 `12` inspect 树协同基准。
3. `chroot` / `pivot_root` 与容器语义的**精确映射**（容器 = 受限 spawn + 全新 namespace 模板），与 `00` C4（沙箱默认 deny）协同拍板。
4. 多 realm / 多用户下 namespace 模板的**隔离边界**（与 `05` §5 待决 4 Service Registry realm 隔离同源），是否每 realm 独立模板根。
5. `unveil` 对内存映射约束的**粒度**（VMO 级 vs VMAR 级，`03` §5 待决 8）——C3 命名空间绑定与 `03` 映射约束待对齐。
