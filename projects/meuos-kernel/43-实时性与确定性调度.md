## 2. 多系统参照对比（调度内核视角）

以下对比**只取各系统的调度内核机制**，不重复 `28` §2 的广域 RT 表，而是把视角压到「调度类怎么组织、反转怎么防、抢占粒度怎么界、认证怎么要求」。

### 2.1 调度机制横向对比

| 系统 | 调度类组织 | 优先级反转防护 | 抢占粒度 / 关键段 | 对 MeuOS 的取舍 |
|---|---|---|---|---|
| **Linux PREEMPT_RT** | `sched_class` 层次：EEVDF(CFS) / RT(FIFO/RR 0–99) / DL(EDF)；完全可抢占内核（自旋锁改 rt_mutex、中断线程化） | **PIP**（`rt_mutex` 优先级继承，支持嵌套继承链） | 压缩关中断窗口至**无长不可抢占段**；PREEMPT_RT 把几乎全部自旋锁变可抢占互斥 | **吸收** `sched_class` 钩子分层思想；**不**全盘搬 PREEMPT_RT（MeuOS 已是 capability + 混合内核，RT 提权应是 capability 而非 `CAP_SYS_NICE`） |
| **SCHED_DEADLINE（EDF）** | `SCHED_DEADLINE`：GEDF/分区 EDF，三元组 `(runtime, deadline, period)` + **准入控制**（ΣU ≤ 1） | 与 PIP 同内核；deadline 任务间不依赖优先级 | 与 RT 类共存：DL > RT > CFS；带宽硬预留 | **直接对齐** Zircon 式 deadline——`28` §3.1 的双子类 RT 域即此；准入控制是 §4.3 的硬门禁 |
| **QNX Neutrino** | 优先级驱动抢占 + **自适应分区调度（APS）**：每个分区有**最小 CPU 带宽保证**（硬分区），分区内再优先级抢占 | 优先级继承（内核 mutex 内建 PIP） | 微核极小、关中断窗口以 µs 计；分区之间按带宽配额彼此隔离 | **范本**：APS = `04` Job RT 预算（QNX APS 式 CPU 带宽硬分区）的对标物；分区即 MeuOS 的 RT CPU 子集 |
| **Zephyr / 典型 RTOS** | Zephyr：协作线程 + 抢占线程 + **meta-IRQ 线程**（高于一切抢占线程）；调度后端可选（simple/multiq/meta-IRQ）。FreeRTOS：固定优先级抢占 | Zephyr `k_mutex` 提供**优先级继承**；FreeRTOS `configUSE_PRIORITY_INHERITANCE` | 协程级协作 + 可抢占；无 capability、无地址空间隔离 | **参照**「小核调度 + meta-IRQ 高优先级快路径」；但 RTOS 缺 capability，MeuOS 必须在其上叠加 `CAP_RT` 门禁 |
| **Windows 实时扩展** | Windows 自身**非 RTOS**，其「实时优先级」(16–31) 仅是软 RT；硬 RT 靠**第三方 co-kernel / 实时虚拟机监控器**（IntervalZero RTX64、TenAsys INtime、Kithara）在**专用核**上与 Windows 并列运行，**不是** Windows 内核变实时 | 取决于 co-kernel（多走固定优先级 + 天花板） | co-kernel 接管专核，Windows 不参与该核调度 → 隔离靠硬件核而非内核抢占 | **反面教材**：用「专用核跑 RT、通用 OS 跑尽力」规避内核改造——与 MeuOS RT CPU 子集（`28` §3.3）思想同源，但 MeuOS 用 capability 管子集而非靠第三方 co-kernel |
| **Fuchsia / Zircon（fuchsia.deadline 调度）** | Zircon 提供**优先级(0–31) + 公平权重 + deadline**；用户态经 **Profile / `fuchsia.scheduler.ProfileProvider`**（`GetDeadlineProfile(capacity, deadline, period)`、`GetCpuAffinityProfile`）声明调度画像，线程 `set_profile` 套用 | Zircon 对 **channel 端点 rendezvous** 用 PIP；内核锁协议进可验证 TCB | 调度画像与线程解耦（画像对象化、可共享、可审计）；RT 线程约束「禁分配/禁长锁」 | **范本**：deadline 表达 API 直接成为 `28` §3/§4 蓝本；**画像对象化 + capability 授予**即 `CAP_RT` 的落地方向 |
| **RTEMS** | 同时支持 **EDF 与 RMS（速率单调）**、POSIX 与经典任务；分区/多处理器；有**安全关键分支**（用于太空/航电） | 经典 RTEMS 用固定优先级 + **优先级天花板**；POSIX 层走 PIP | 可剥夺、确定；target 独立 BSP 抽象 | **范本**：EDF+RMS 双模可选 → MeuOS 亦可「固定优先级 + EDF 子类」双模；其安全关键分支对应 MeuOS 的「认证档（§10）」 |
| **航天/汽车分级（DO-178C / ISO 26262 ASIL / ARINC 653 / AUTOSAR）** | **ARINC 653**：分区固定**时间窗**调度（健康监控 + 时空隔离），APEX 接口；**AUTOSAR/OSEK**：固定优先级 + 报警/事件；**DO-178C**(A–E)/**ISO 26262 ASIL**(A–D) 不规定调度算法，但要求**确定性 + WCET 可分析 + 干扰自由（freedom from interference）** | 由分区时间窗天然杜绝跨分区反转；单分区内用固定优先级/天花板 | 关中断/抢占窗口**必须可上界且被认证**；无无界临界区 | **最高标杆（认证档）**：MeuOS 原型期不追认证，但 §4.4 的可测抢占上界 + §10 的「ARINC 653 分区模式（可选）」是通向认证档的演进落点 |

### 2.2 取舍结论（解构型）

- **拒绝**「把 PREEMPT_RT 全盘搬来」：MeuOS 已是 capability + 混合内核，RT 提权应是 capability 而非 `CAP_SYS_NICE`；调度核心要小、可验证（对齐 `19` §3.4(A)）。
- **采纳** Zircon/Fuchsia 的 **deadline 调度类 + 画像对象化**（作为 `04` RT 类的内置子类），并用「RT 线程内禁分配/禁长锁」约束防止反转与抖动。
- **采纳** QNX **APS 式 CPU 带宽硬分区**作为 Job 级 RT 预算的对标物（即 `04` §4.4 的 RT 预算维度，QNX APS 式最小带宽保证）。
- **采纳** RTEMS「固定优先级 + EDF 双模」与 ARINC 653「分区时间窗」作为**演进档**（不进 Day1）。
- **跟踪** seL4 式可验证确定性作为 §10「调度核心形式化」的候选；原型期不做端到端 WCET 证明。
- **关键修正**：Windows 的「硬 RT 靠专用核 co-kernel」印证了「RT 子集隔离」思想，但 MeuOS 用 **capability 管子集 + 内核内置 RT 域**，而非依赖第三方 co-kernel——这是混合内核相对「Windows + 外挂 RT」的架构优势。

## 3. 设计原则：确定性「提供到什么程度、以什么代价」（解构型）

先不问「MeuOS 能多实时」，而问「确定性**应该**提供到什么程度、以什么代价」——这是本维度的解构起点。

### 3.1 代价—收益解构

| 想要的能力 | 提供的**程度** | 必须付出的**代价** | MeuOS 立场（呼应 R1） |
|---|---|---|---|
| 可预期延迟（有界尾延迟） | **承诺**（圈定域内） | RT CPU 子集（核被独占/半独占）+ 关抢占短临界区 + 调度核心纳入可验证 TCB | 接受：牺牲部分核的通用吞吐换确定性 |
| 优先级保障（高 RT 不被低优先级抢占） | **承诺** | RT 域对公平层绝对压制 + `CAP_RT` 门禁 | 接受：RT 提权必须显式 capability |
| 周期可预测（deadline 不漏） | **承诺**（数据留核前提下） | 准入期 mlock + 带宽预留 + 禁分配/禁长锁 | 接受：运行期一次性付清不确定性 |
| 优先级反转防护 | **承诺**（RT 域内） | 锁协议（PIP/ICP）进可验证 TCB + 内核锁受限 | 接受：内核锁实现变复杂、须可证明 |
| 跨全系统硬实时 | **不承诺** | 需形式化 WCET + 全路径无无界临界区 | 拒绝：代价远超收益，且违反 R1 |
| 亚 µs 闭环（每次环需 IPC 往返） | **不承诺** | 需数据/控制全留核或判定「不在 MeuOS 硬 RT 域」 | 拒绝：`28` §1.3 已定边界 |
| 认证级（DO-178C A / ASIL D） | **不承诺**（原型期） | 需完整生命周期证据 + 分区时间窗 + WCET | 拒绝 Day1；列为 §10 演进档 |

### 3.2 解构型原则（六条基线）

1. **确定性是「圈定域」内的承诺，不是全系统承诺**：特定 Job + 特定 RT CPU 子集 + 固定内存 + mlock，四者齐备才谈确定性（对齐 `28` §1.1 原则 6）。
2. **优先级是 capability，不是提权通道**：任意进程不能靠 `CAP_SYS_NICE` 式大权把自己设为 RT 饿死系统（对齐 `28` §1.1 原则 3、`07` 无 root）。
3. **反转即违背确定性**：优先级反转 = 高 RT 被低优先级持锁阻塞 = 无界延迟 = 直接击穿 R1 边界。故**反转防护不是「优化」，是确定性的前提条件**，必须进可验证 TCB。
4. **不确定性在准入期一次性付清**：mlock、带宽预留、亲和绑定、锁协议选择都在 `spawn`/`set` 时确定，运行期不做可能失败/阻塞的分配（对齐 `28` §1.1 原则 4）。
5. **调度核心极小可验证**：RT 选择、deadline 会计、带宽记账、锁协议是确定性的「引擎」，须小到能进 `19` §3.4(A) 可验证小核心（移交 `20`），而非依赖运行期调参。
6. **代价透明、可审计**：每一项确定性能力都对应可观测的预算项（Job RT 预算）+ 可授予/可收回的门禁（`CAP_RT`），杜绝「隐形实时特权」。

### 3.3 与 `19` 基准的映射（硬 RT 可达边界）

`19` §1.2.2 锚定 IPC 快速路径 同核 ≤500ns / 跨核 ≤1–2µs；`28` §1.3 据此给出硬 RT 可达边界 = 数据留核 + 周期 ≥ 数十 µs + mlock + 非剥夺短临界区。本文在调度内核层落实为：
- 调度器的**非剥夺临界区长度上界**须 ≤ `19` §4.4 牵连 C8 的内核态驱动 check 量级（≤ 数十 ns 级），否则即破坏该边界；
- `cyc_lat`（cyclictest 等价）尾延迟分布 = RT 可达性门禁（接 `19` §3.1、`28` R8）。

## 4. 调度类设计：是否内置 deadline 类（与 04 协同）

### 4.1 结论：内置，作为 RT 域下的调度子类（复用 `04` `sched_class`）

`04` §4.3 已定「两层策略 + 调度类钩子」：`sched_class`（`enqueue_task` / `pick_next_task` / `task_tick` / `set_next_task`）。本文**采纳**：在 `04` 的 RT 类（`SCHED_FIFO/RR` 0–31）之下，**内置 `rt_deadline_class` 子类**，而非另起调度框架。

> 即回答任务所问「是否内置 deadline 调度类」：**是，内置**——以 `sched_class` 子类形式嵌入 RT 域，沿用 `04` 钩子不重写核心。

三层调度域（在 `04` §4.3 之上扩展，与 `28` §3.1 一致）：

```
┌──────────────────────────────────────────────────────────────┐
│  RT 域（非剥夺优先；须持 CAP_RT 才能进入）                      │
│  ├─ 固定优先级子类 (SCHED_FIFO/RR 0–31)：绝对不可被低优先级抢  │
│  │   → 硬 RT（控制环、音频回调）；关抢占临界区短              │
│  └─ deadline 子类 (Zircon 式 capacity/deadline/period)：       │
│      EDF 在子类就绪集内选最紧急者 → 周期/可预测预算的中软 RT   │
│  创建/提权经 CAP_RT（§6）；带宽挂在 Job RT 预算（§6）          │
├──────────────────────────────────────────────────────────────┤
│  公平层（EEVDF，`04` §4.3）：默认尽力而为；RT 域就绪时不被选    │
└──────────────────────────────────────────────────────────────┘
```

### 4.2 固定优先级 vs deadline 的仲裁顺序（深化 `28` R2）

`28` R2 把「deadline 子类与严格优先级的共存/映射细节」列为执行层定稿项。本文给出**推荐仲裁规则**（供执行层采用）：

1. **RT 域对公平层绝对压制**：只要 RT 域有就绪任务且未用尽其 RT 带宽，公平层不被选（对齐 Linux RT > CFS、QNX 实时优先级）。
2. **固定优先级为「硬地板」**：deadline 任务须映射到一个固定优先级带（建议 `04` 的 0–31 内划出上段，例如 16–31 专供 deadline 类，避免与裸 FIFO 任务混用）。在该带内：
   - 同带内**多 deadline 任务**用 EDF 选最紧急（`earliest deadline first`）；
   - 同带内 deadline 任务 vs 裸 FIFO 任务：**固定优先级数值高者胜**（FIFO 任务不参与 EDF，只比优先级号）；
   - 跨带：高固定优先级带整体压低固定优先级带（含其下 deadline 任务）。
3. **实现落点**：沿用 `04` `sched_class` 钩子——新增 `rt_deadline_class` 作为 RT 类下的子类，`pick_next_task` 在 RT 类内先按固定优先级带分层、带内再按 EDF 排序（deadline 就绪集用最小堆/红黑树按 absolute deadline 排序）。

> 此规则把 `28` R2 从「开放」收口为「固定优先级作硬地板 + 带内 EDF」，既保留硬 RT 的绝对性，又给周期任务可预测的 EDF 调度。

### 4.3 准入控制（EDF 的生命线，深化 `28` §4.2）

EDF 的安全前提是**准入控制**：只有 Σ 利用率 ≤ RT 分区带宽时，新 deadline 任务才被接纳，否则 `EAGAIN`/`EBUSY`（对齐 SCHED_DEADLINE 的 admission test、QNX APS 带宽）。

- 检查点：`meu_thread_set_deadline`（或 Fuchsia 式 `set_profile` 套用 deadline 画像）时，由调度器 + `04` Job RT 预算协同校验：
  - `U_job = Σ (capacity_i / period_i)` 对目标 Job ≤ 该 Job 的 RT 带宽预留；
  - 跨 Job 在**同一 RT CPU 子集**上的 ΣU ≤ 子集带宽（避免子集过载）；
- 两项任一超限 → 拒绝（fail-closed，对齐 `07` 越权即终止/拒绝语义），**不**靠运行期节流掩盖过载。
- 与 `28` §4.2 的 Job RT 预算（RT CPU 带宽 / 优先级上限 / 亲和集 / 预留数）同源——准入控制就是 Job RT 预算在调度器的硬门禁落地。

### 4.4 中断延迟与抢占粒度（调度器的可测上界契约）

本点是任务明确要求讨论的「中断延迟与抢占粒度」，作为调度类的**可量化契约**：

| 调度内核量 | 上界契约（Day1 目标） | 度量/门禁 | 关联 |
|---|---|---|---|
| **关抢占窗口**（RT 域内非剥夺临界区） | ≤ 数十 ns 级（对标 `19` §4.4 C8 内核态驱动 check ≤20ns 量级） | 静态审查 + `cyc_lat` 测；超界即设计缺陷 | `28` §3.3、`19` §3.4(A) |
| **关中断窗口**（硬件→RT 线程就绪） | RT 核上仅极短（调度器内部 + 环形缓冲 head/tail 更新） | 中断控制器为内核态（`10` 附录 A），可分析 | `10` §4.2、`28` §3.3 |
| **中断延迟**（中断触发→RT 线程被选中） | = 关中断窗口 + 调度选择开销；RT 核上可分析、可测 | `cyc_lat` under 负载尾延迟分布 | `19` §3.1 |
| **上下文切换代价** | 作为抢占粒度地板；RT 线程上下文切换须 eager（见 §8 FPU） | per-arch 实测基准（`19` §3.3 五架构） | §8 |
| **RT CPU 子集隔离** | 仿 `isolcpus`/`nohz_full`：子集只跑 RT 域 + 其绑定内核态驱动，公平层/出核服务默认不进入 | 静态配置 + 调度器拒绝越界入队 | `28` §3.3、`00` C1 |

> 契约精神：**抢占粒度不是「越小越好」的玄学，而是可声明、可测、可证的上界**。MeuOS 把「关抢占/关中断窗口上界」作为调度核心的不变量写进 `19` §3.4(A) 可验证小核心，而非靠 cyclictest 调参发现。

## 5. 优先级与反转防护（PIP / PCP / ICP）

### 5.1 问题：为什么反转防护是确定性的前提

优先级反转 = 高优先级 RT 任务因等待低优先级任务持有的锁而被中等优先级任务间接阻塞。在 RT 域内，这等于**无界延迟**——直接击穿 R1「提供确定性 RT」的承诺。因此反转防护**不是性能优化，是确定性能力的硬前提**，其锁协议本身必须进可验证 TCB（与 `19` §3.4(A) IPC 端点状态机/rights 检查同构）。

### 5.2 三种协议取舍（解构型）

| 协议 | 机制 | 优点 | 缺点 | MeuOS 取舍 |
|---|---|---|---|---|
| **PIP（优先级继承）** | 持锁的低优先级任务**临时继承**阻塞者的最高优先级；释放时还原 | 只在实际竞争时提升；Linux `rt_mutex`、Zircon channel 端点采用 | 嵌套锁形成**继承链**，链长无界时提升本身有代价；可能 chain deadlock（需 deadlock 检测） | **用于用户态 IPC 端点 rendezvous**（对齐 Zircon channel PIP），因为端点持锁时间不确定、需按需提升 |
| **PCP（优先级天花板协议）** | 每个锁有**静态天花板**=可能持该锁的最高任务优先级；进入即升到天花板，退出还原 | 无继承链、无 chain deadlock；一次提升到位 | 天花板须静态分析；可能过度提升（饿死中间优先级） | 备选；用于已知静态优先级图的场景 |
| **ICP / OCPP（立即优先级天花板，即最常用「优先级天花板」）** | 进入临界区**立即**提升到该锁的天花板（=系统内可能持锁的最高优先级），全程不变 | 最简单、无继承链、无死锁、阻塞时间有**单一上界**；RTOS/汽车界事实标准 | 同上（可能过度提升），但上界最干净 | **用于内核态 RT 锁**（调度核心、VMO 环形缓冲 head/tail、Job 账本 RT 字段）——确定性上界最易证明 |

### 5.3 推荐方案（分层）

1. **内核态 RT 锁 → 立即优先级天花板（ICP/OCPP）**：调度核心内部、RT 数据平面环形缓冲、Job RT 预算字段的锁统一用 ICP。理由：内核锁持有时长可静态界定，ICP 给出**单一可证上界**，且无继承链→无 chain deadlock→最易进可验证 TCB。这是汽车/航天界（OSEK/AUTOSAR、ARINC 653 单分区内）的事实标准。
2. **用户态 IPC 端点 rendezvous → PIP**：对齐 Zircon/Fuchsia channel 端点用 PIP；端点持锁时长取决于对端，需按需继承而非静态天花板。PIP 的继承链风险由 `05` 端点状态机约束（无环）化解。
3. **RT 线程内禁分配/禁长锁**：仿 Zircon/Fuchsia「RT 线程禁动态分配、禁长临界区」——从根上消除「持锁时分配导致反转/抖动」（`28` §5.2、`22` 待决）。这是反转防护的**前置纪律**，比任何锁协议都根本。
4. **反转防护只作用于 RT 域**：公平层任务是最佳努力，不参与 PIP/ICP（提升它们无意义，且不保证延迟）。

### 5.4 与可验证性的接口

锁协议（ICP/PIP）的选择、天花板计算、无 chain deadlock 证明，须进 `19` §3.4(A) 可验证调度小核心，移交 `20` 做精化证明（呼应 `28` R10）。这是 R1「不承诺 WCET 但提供确定性」在调度内核层的**可验证落点**——确定性来自「锁协议有证的上界」，而非来自调参。

## 6. 与 capability(07) / Job 账本(04) / 威胁模型(29) 的关系

> 任务所写「Job 账本(29)」系笔误：Job 账本本体在 `04` §4.4（`00` A5 亦指向 `04`）；`29` 是威胁模型。本节把三者关系一并理清：Job 账本是 RT 预算的**挂载点**（04）、capability 是 RT 提权的**门禁**（07）、威胁模型是 RT 特权外流的**攻击面收敛点**（29）。

### 6.1 实时优先级受 capability 守护（核心关系）

对齐 `04` §4.3「创建 RT 线程需特定 capability」与 `07`「无 root、权限随句柄走」：

- **`CAP_RT`（新增 right，挂在句柄/Job 上）**：持有者才能 (a) 把线程设为 RT 域（固定优先级或 deadline 子类）、(b) 提升 RT 优先级、(c) 声明 RT CPU 亲和集、(d) 套用 deadline 画像。无 `CAP_RT` 调用 `meu_thread_set_rt_*` / `set_profile` 直接 `EPERM`（fail-closed，对齐 `07` pledge 越界即终止语义）。
- **RT 提权不可经 Linux 兼容层逃逸**：兼容层 `sched_setscheduler`/`CAP_SYS_NICE` 映射为「持有 `CAP_RT` 受限句柄」（对齐 `07` §4.6：Linux capability 拆到具体对象权限，`CAP_SYS_ADMIN` 式大权不被整体授予）。
- **这避免 PREEMPT_RT 式风险**：任意进程不能靠 `CAP_SYS_NICE` 把自己设为 RT 饿死系统——RT 提权是显式、可审计、可收回的 capability。

### 6.2 ⚠️ 真缺口：`CAP_RT` 在 `07` / `38` 统一 rights 位图**尚未分配 bit**

本文调研发现一处需要回写的**不一致**：

- `28` §4.1 提出 `CAP_RT` 为新增 right，但 `07-安全模型.md` 全文（已 grep 核验）**未定义 `CAP_RT`**；
- `38-第四轮收敛摘要.md` §3.1 的「统一 rights bit 分配建议表」（bit 0–38，含 `KEY_*`/`CFG_*`/`KERNEL_PRIV`/`DBG_*`/`AUDIO_*`/`BLOCK_*`/`NET_*`/`GPU_*`/`DISPLAY_*`/`LOAD`/`VERIFY`）**亦未含 `CAP_RT`**。

即：`CAP_RT` 已在 `28` 提出、与 R1 的确定性 RT 强绑定，却**没有落进 capability 位图**——这是 R1 落地到 `07` 的悬空项。

> **回写建议（供第五轮/回写员）**：在 `07` §4.1 rights 位图新增 `CAP_RT` 专属 bit（不复用 `MANAGE`/`GRANT`，与已采纳的 `KEY_*`/`CFG_*`/`DBG_*` 先例一致）；并在 `38` §3.1 表中补 `CAP_RT` 行。建议 bit 取 `KERNEL_PRIV`(12) 与 `DBG_INSPECT`(13) 之间或紧邻领域 right 区段（如 bit 39+ 预留区起始），由 `07` 定稿冻结。本文只记录此缺口，**不改动 `07`/`38`**。

### 6.3 Job 账本是 RT 预算的挂载点（`04`）

`04` §4.4 的 Job 账本含 CPU 时间（公平权重 + 可选硬上限）。RT 预算作为**新增维度**挂在 Job 上（对齐 Zircon job 限额 + QNX APS 分区）：

| RT 预算项 | 含义 | 超限行为 | 对应系统 |
|---|---|---|---|
| **RT CPU 带宽**（capacity/period） | 该 Job 下 RT 任务窗口内可占 CPU 比例（QNX APS 式硬分区） | 超出则 RT 任务节流/挂起，不侵入公平层 | QNX APS、SCHED_DEADLINE 带宽 |
| **RT 优先级上限** | 该 Job 能设的最高 RT 优先级 | 超限 `EPERM` | Zircon priority 区间 |
| **RT CPU 亲和集** | RT 任务可绑定的核集合（须 ⊆ 系统 RT 子集） | 越界 `EPERM` | `isolcpus`/`sched_setaffinity` |
| **deadline 预留数** | 该 Job 允许并发的 deadline 任务数 / 总 capacity | 超限拒绝 spawn/set | Zircon deadline |

- 与 `04` 账本同源：RT 预算检查点分布在调度器（带宽/优先级）、`meu_thread_set_*`（CAP_RT + 优先级上限）、`meu_spawn`（亲和集校验）；账本由进程管理子系统持有、被 capability 系统校验（`04` §4.4）。
- 准入期一次性付清（§3.2 原则 4）：mlock、亲和、带宽预留都在 `spawn`/set 完成；Job 终止 → RT 预算与 RT 线程一并回收（`04` §4.5）；`CAP_RT` 句柄 close/revoke → 该 Job 后续无法新建/提权 RT 线程（`07` §4.5 撤销传播）。

### 6.4 威胁模型（29）：RT 特权的攻击面收敛

`29` 把 TCB 定义为「监视器 + IPC 端点 + 低级 VM/调度」，调度核心在 TCB 内。`CAP_RT` 与 `KERNEL_PRIV` 同构——都是「可被授予即等于后门、故必须显式单列、永不默认、可审计、可 revoke」的能力（`29` §8 D-T1）：

- **RT 提权若被越权授予/误用** → 归 `29` T-A 类（等价于获得饿死系统的能力）；其「永不默认、受 Job 账本约束、可 revoke」的挡点落在 `07` §5（rights 位图）+ `04` Job 账本。
- **调度核心作为 TCB 一部分**，其确定性不变量（关抢占上界、锁协议上界）是 T-A 攻击面收敛的**内部防线**——任意试图拉长关抢占窗口的漏洞都直接威胁 RT 确定性，故调度核心须与监视器/IPC 端点同批进 `19` §3.4(A) 可验证小核心。

## 8. 跨架构约束（五架构）

`28` §6 已覆盖时钟源差异。本文从**调度内核**补充三类约束：FPU 上下文、上下文切换代价、每架构中断控制器。

| 架构 | 稳定时钟源（deadline 会计基准） | FPU / lazy-FPU 对 RT 的影响 | 上下文切换代价（抢占粒度地板） | 中断控制器 / 抢占粒度 | RT 可达性 |
|---|---|---|---|---|---|
| **x86_64** | Invariant TSC + LAPIC Timer + TSC Deadline | 支持 eager-FPU（XSAVE eager）；RT 线程建议 eager-FPU 避免 lazy 换页式抖动 | 成熟、低；Rust TCB 统一 | LAPIC：本地中断、TSC Deadline 单次精确触发；关中断窗口最可控 | **RT 双验证架构之一**（对齐 `19` M5） |
| **aarch64** | Generic Timer（CNTFRQ/CNTPCT/CNTP_CVAL） | 支持 eager-FPU（SVE 亦 eager）；RT 线程 eager | 与 x86_64 同级 | GIC（v2/v3）：各自 CPU 接口、私有定时器；抢占粒度可控 | **RT 双验证架构之一** |
| **riscv64** | `rdtime` + CLINT/ACLINT `mtimecmp`；**Sstc**(`stimecmp`) 免陷入 M 态 | 依平台；eager-FPU 支持差异 | 依平台实现；标准化较弱 | PLIC/CLINT 或 APLIC/ACLINT；**缺 `Sstc` 时 RT 计时需陷入 M 态 → 抖动来源** | `Sstc` 可用性为前置实测项（`28` §6 R9） |
| **loongarch64** | 稳定计数 CSR（`RDTIME`） | 自有体系，成熟度待验 | 待验 | 自有中断控制器；M5 后移（`11` §5-4） | 先保证正确，RT 基线待实测 |
| **i386** | TSC 可能非 invariant，回退 HPET/PIT | 无 Rust TCB、纯 C（`02` C2）；FPU 为 x87 老式 | 最不可控；纯 C 路径 | 8254/LAPIC；计时源最不可靠 | **RT 确定性最弱**：非 invariant TSC 下 deadline 会计需校准；非 RT 重点架构（`19` §3.3 同调：慢/不确定来自计时硬件，非语言） |

**调度内核论断**：

1. **RT 验证基线 = x86_64 + aarch64**：二者因 invariant TSC / Generic Timer + 成熟中断控制器，可作 RT 双验证架构（对标 `19` M5 双架构）；其 FPU 支持 eager 模式，调度器可对 RT 线程**强制 eager-FPU**，消除 lazy-FPU 的「首次使用异常 → 上下文补全」引入的非确定抖动。
2. **RT 线程 FPU 策略**：建议在 RT 域线程**禁用 lazy-FPU**（eager 保存/恢复或为 RT 线程预分配 FPU 状态），否则一次 FPU 惰性加载即可破坏 µs 级截止期。这是调度器与 `03`/架构后端的协同点（每架构薄后端实现 eager-FPU 开关）。
3. **上下文切换代价 = 抢占粒度地板**：切换开销越低，RT 响应越细；riscv64/loongarch64/i386 的实测切换代价决定其能否进 RT 子集——调度器应在 RT 核上**最小化切换路径**（如 RT 线程栈/上下文常驻、避免切换期的额外分配）。
4. **中断控制器归内核态**：RT 中断的「硬件→RT 线程就绪」延迟依赖中断控制器抽象（`10` 附录 A），须每架构薄后端统一为「可分析、可测」的延迟上界（§4.4）。

## 9. Day1 可交付的确定性能力

Day1（原型期，呼应 R1 的「提供确定性 RT 能力」）**应交付**：

1. **RT 域 + 内置 `rt_deadline_class`**：固定优先级(0–31) 与 Zircon 式 deadline 子类共存，复用 `04` `sched_class`（`28` §3.1 / §7.1 结论 1）。
2. **RT CPU 子集（静态 `isolcpus` 式）**：若干核划为 RT 子集，只跑 RT 域 + 其绑定内核态驱动（`28` §3.3）。
3. **`CAP_RT` 门禁**（bit 待 §6.2 回写）：RT 提权/亲和/deadline 声明经其校验（§6.1）。
4. **Job RT 预算维度**：RT 带宽 + 优先级上限 + 亲和集 + 预留数（§6.3，对齐 QNX APS）。
5. **准入控制**：deadline 任务经 Job 带宽 + 子集 ΣU 双校验（§4.3）。
6. **反转防护**：内核锁 ICP + 用户态 IPC 端点 PIP + RT 线程禁分配/禁长锁（§5.3）。
7. **抢占上界契约**：关抢占/关中断窗口可测上界 + `cyc_lat` 尾延迟门禁（§4.4，接 `19`）。
8. **mlock 准入**：RT 线程地址空间与其 VMO 缓冲在 `spawn`/set 时固定，运行期禁缺页（`28` §5.1，接 `03`）。
9. **数据通路留核**：RT 数据平面走 VMO/SHM 环形缓冲，零 IPC（`28` §3.2，接 `05`/`19`）。

Day1 **不交付**（显式留给演进，呼应 §7.2 N）：WCET 证明、动态子集伸缩、GEDF 跨核、认证档（ARINC 653 分区）、seL4 式精化证明。

## 第五轮深化回写建议（修订式追加，不删）

> 本节记录本文作为独立调研一面发现的**待回写项**，供第五轮/回写员处理；本文本身只追加、不改动任何其他文档。

- **B1（`CAP_RT` 缺 bit）**：`28` §4.1 提出的 `CAP_RT` 未进入 `07` §4.1 rights 位图，也未进 `38` §3.1 统一 bit 表（bit 0–38 缺 `CAP_RT`）。建议 `07` 新增 `CAP_RT` 专属 bit（不复用 `MANAGE`/`GRANT`），并在 `38` §3.1 补行。此为 R1 落地 `07` 的悬空项，优先级高。
- **B2（调度类命名对齐）**：本文把「deadline 子类」定为 `04` RT 类下的 `rt_deadline_class`，并建议固定优先级作「硬地板 + 带内 EDF」仲裁——供 `04` §4.3 与 `28` R2 执行层定稿时采纳。
- **B3（反转协议分层）**：内核锁 ICP / 用户态 IPC 端点 PIP 的分层建议，供 `04`/`05`/`22` 协同落锁协议时采纳。
- **B4（RT 线程 eager-FPU）**：跨架构 RT 线程禁用 lazy-FPU 的建议，供 `02`/`03` 架构后端协同（§8）。
