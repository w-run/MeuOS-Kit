## 1. 概述与目标

### 1.1 为什么「调试与可观测性」必须在地基阶段设计

在宏内核（Linux）里，可观测性是被「事后补丁」上去的：printk（2001）→ ftrace（2008）→ perf（2009）→ eBPF（2013），每一层都是对既成事实的抢救。`/proc`、`/sys` 是文本伪文件系统，ptrace 是「任意进程默认可 attach 同 uid 进程」的隐式权限，perf 是全局能力——它们与「capability 之前的世界」同构。

MeuOS 的处境不同：capability 是 Day 1 唯一权限模型（见 `07-安全模型.md`），进程由 spawn 显式构建、由监督者按 Job 树重启（见 `04-进程与调度.md`），内核态是混合内核 + Rust/C 混合（见 `01/02`）。这带来一个**正面机会**而非负担：**可观测性应当是一等公民（first-class citizen），而非事后补丁**。也就是说，在「应该是什么样」的阶段就把它设计进 capability 与 spawn 模型里，而不是先写 printk 再补 debugfs。

### 1.2 「应该是什么样」（解构型思维，先于结构）

问：在「混合内核 + capability 世界 + 用户态服务自治重启」的模型下，调试/观测**应该**是什么样的？

1. **结构化的可观测性，而非文本日志海**：内核与服务的状态应当暴露为一棵**层次化、强类型、可被程序消费**的「inspect 树」；事件应当是一条**带 schema 的结构化事件流**，而非混进一条串口打印的 ASCII 河。任何「人类可读文本」都应是结构化数据的**一种渲染**，而不是数据源本身。（强烈参考 Fuchsia Inspect 与 ETW。）
2. **调试是受 capability 守护的能力，不是默认权利**：在 capability 世界，「谁可以 introspect 内核/他人进程」本身必须是一张 capability 令牌。不能让任意进程无代价地 attach 调试器、读内核内部、采样性能——那等于在 capability 模型上凿开一个隐蔽的「root 后门」。（非缝合怪原则：宁缺毋滥、默认拒绝。）
3. **三类崩溃统一上报，且与监督者联动**：内核 Rust panic、内核态 C fault（段错误/MMIO 越权）、用户态服务崩溃（Rust panic / C 段错误），应当汇聚到**同一个结构化崩溃报告**，经 exception channel 上报给监督者（meu-supervisor），由监督者按策略决定 kill / 留 dump / 重启 / 升级（接 `04/10`）。
4. **可观测性即协议，也走 capability**：调试/观测的控制通道（attach、订阅事件、读 inspect、采 sample）是内核对象 + capability，与 `05-IPC机制` 的 Channel/EventPort 同源，权限随句柄走。

### 1.3 本文目标

1. 定义 MeuOS 的**可观测性基线**：inspect 树（结构化状态）+ 事件流（结构化追踪）+ 崩溃报告（结构化故障）。
2. 定义**调试 capability 模型**：把「ptrace/perf/proc」翻译成 MeuOS 的 capability 原语，且不破坏 `07` 的内部模型。
3. 给出**统一崩溃模型**与监督者联动协议。
4. 处理**多架构回溯/符号化差异**与「Rust panic=abort 与 C 栈展开的统一」这一真实张力。
5. 与**统一文件系统（01 方向①）**对接：crashdump 如何经校验和/加密落到 `.msys` 卷。
6. 与**自举验证（11）**对接：QEMU 联调通道（gdbstub/串口）。
7. 给出**自主结论 + 参照差异表 + 待决清单（含架构裁决）**。

### 1.4 不在本文范围

- 具体驱动调试（见 `10`）；安全 capability 本身的派生/撤销算法（见 `07`）；IPC fastpath 性能（见 `05`）；具体崩溃转储文件格式字节布局（原型期再定）。

## 2. 设计约束与上下文

### 2.1 来自方法论铁律的硬约束

- **解构型**：先有「应该什么样」（§1.2），再推结构（§3–§5）。
- **多系统参照，不缝合**：Linux(printk/ftrace/perf/kprobe/crash/kgdb) 取其「广度」，Windows ETW/WinDbg 取其「事件 schema 化」，macOS(kdebug/os_log) 取其「结构化日志」，Android(systrace/atrace/perfetto) 取其「统一追踪时间线」，Fuchsia(inspect 树、zx_channel 调试协议、FIDL 反射) 强烈参考其「结构化 inspect 树 + 调试走 capability」哲学，seL4(证明与调试分离、sel4debug) 取其「调试是外部可控、不影响验证」的立场。
- **非缝合怪**：明确 MeuOS 自主取舍——capability 世界下，**调试权限本身即 capability**；不把 Linux 的「默认可 ptrace 同 uid 进程」「perf 全局采样」平移进来。

### 2.2 技术基线（来自既有文档）

| 约束 | 来源 | 对调试/观测的影响 |
|------|------|-------------------|
| 混合内核，Rust+C；内核态 TCB 用 Rust，底层 C/asm | `01/02` | 需同时处理 Rust panic 回溯与 C 栈展开；内核态与用户态故障域不同 |
| Rust `panic=abort`（内核核心组件，不展开栈） | `02` §4.5 | 内核 panic **无展开式 backtrace**，只能靠 panic 现场（PC/寄存器/少数帧）+ 符号化 |
| spawn 模型 + Job 树 + 监督者（meu-supervisor） | `04` §4.5 | 用户态服务崩溃由 supervisor 重启；崩溃报告是其输入 |
| exception channel 上报致命异常 | `04` §4.6、§5.8 | 调试器与监督者**竞争**同一 exception channel，需仲裁（见 §4 / 待决） |
| 句柄即 capability，权限随句柄走 | `07` §4.1 | 调试权限 = 一组受 rights 约束的 handle |
| 用户态驱动 + 看门狗重启（RS 式） | `10` §4.2 | 驱动崩溃走「用户态服务崩溃」分支，而非全内核 panic |
| 串口 / 9p / QEMU 作为自举联调通道 | `11` §4.3 | gdbstub/串口是原型期主线调试通道 |
| `.msys` 卷（校验和/加密/原子更新） | `01` 方向①、`11` §4.1 | crashdump 落盘介质 |

## 3. 业界/项目内方案对比

围绕「可观测性原语」与「调试权限模型」两个维度对比。

### 3.1 可观测性原语

| 系统 | 原语 | 结构化程度 | 权限模型 | 对 MeuOS 的取舍 |
|------|------|-----------|---------|----------------|
| **Linux** | printk 文本 ring + `/proc`/`/sys` 文本伪文件 + ftrace(文本/二进制) + perf(采样) + eBPF | 低（文本为主，需解析） | 隐式：root/同 uid 可读，perf 需 `CAP_PERFMON` | 广度足够但「非结构化、默认可读」与 capability 冲突 |
| **Windows ETW** | 统一事件追踪（provider/session/consumer，二进制 schema） | 高（强 schema、自描述） | 会话权限受 ACL | 取「事件 schema 化 + 会话订阅」 |
| **macOS XNU** | kdebug（内核事件流）+ os_log（结构化日志，隐私 redaction） | 高（os_log 强类型） | 沙箱约束 | 取「结构化日志 + 隐私脱敏」 |
| **Android** | systrace/atrace/perfetto（统一追踪时间线，protobuf schema） | 高 | 调试权限（adb/root） | 取「统一时间线 + 多源合并」 |
| **Fuchsia** | **Inspect**（层次化强类型 inspect 树）+ **trace**（Fuchsia trace 格式，带 schema）+ **zx_channel 调试协议** | 最高（树即状态、trace 自带 schema） | **调试协议走 capability**（调试 handle 显式授予） | **主参考**：inspect 树 + 调试即 capability |
| **seL4** | 证明内核对调试无依赖；sel4debug 作为外部可控调试扩展 | — | 调试为外部可选能力 | 取「证明与调试分离」立场 |

### 3.2 调试权限模型

| 维度 | Linux | Fuchsia/Zircon | seL4 | **MeuOS（建议）** |
|------|-------|----------------|------|-------------------|
| attach 调试器 | 默认同 uid 可 ptrace；root 万能 | **需持有目标进程/任务的 debug handle**（显式授予） | 调试为可选 capability | **debug capability（带 rights）**，默认拒绝 |
| 读内核状态 | `/proc`/`/sys` 默认可读（部分受限） | 经 inspect 树，按 handle rights 读 | 无 | **inspect 树按 rights 读**，无全局可读 |
| 性能采样 | `perf` 需 `CAP_PERFMON`（但历史上易过宽） | 采样需 specific capability | — | **profile capability** 显式授予 |
| 崩溃转储 | core dump 落盘（受 ulimit/路径约束） | 崩溃经 exception 上报，dump 由策略决定 | — | **崩溃报告经 exception channel → 监督者 → 可落盘（capability 约束）** |

### 3.3 关键结论（从对比中提炼）

1. **结构化优于文本**：文本日志（printk）只应作为结构化 inspect/事件数据的「一种渲染」，不应是调试的数据源。参照 Fuchsia Inspect + ETW/perfetto 的 schema 化。
2. **调试权限必须显式化**：Linux 的「默认可 ptrace 同 uid」「perf 全局」是 capability 模型的反面。MeuOS 用 debug capability（带 rights）取代，默认拒绝，显式授予。
3. **崩溃是统一的结构化事件，不是文件副作用**：core dump 的「默认落盘」改为「结构化崩溃报告 + 监督者策略决定落盘」，与 spawn 监督模型天然对接。
4. **证明与调试分离**（seL4 立场）：可观测性设施不应成为 TCB 的一部分，也不应削弱 capability 不变量——这正是「调试权限即 capability」的底气。

## 4. MeuOS 选型建议

### 4.1 三大可观测性基元（一等公民）

```
┌───────────────────────────────────────────────────────────────┐
│  MeuOS Observability                                         │
│                                                               │
│  (1) Inspect Tree   层次化强类型状态树（替代 /proc+/sys 文本） │
│       ├─ kernel/       调度/内存/IPC/capability 表快照        │
│       ├─ jobs/<id>/    每 Job 资源账本/进程树                  │
│       └─ services/<n>/ 用户态服务自报指标（histogram/lazy）   │
│                                                               │
│  (2) Event / Trace Stream   带 schema 的结构化事件流          │
│       ├─ syscall trace（strace 等价物）                       │
│       ├─ scheduler/exception/IO 事件                          │
│       └─ 用户态服务自定义事件（FIDL 反射式自描述）            │
│                                                               │
│  (3) Crash Report   统一结构化崩溃报告                       │
│       ├─ reason / offending PC / register set / stack frames │
│       └─ 经 exception channel → 监督者（kill/dump/restart）   │
└───────────────────────────────────────────────────────────────┘
        ↑ 三者全部经 capability 守护（见 4.2），无全局可读
```

### 4.2 调试/观测权限模型：调试即 capability

把 Linux 的「ptrace / perf / proc 可读」翻译成 MeuOS 的 capability 原语。**推荐细粒度 rights（非缝合怪、默认拒绝）**：

| MeuOS debug right | 含义 | 对应 Linux 概念（仅映射语义，不平移权限） |
|-------------------|------|-------------------------------------------|
| `DBG_INSPECT` | 读 inspect 树（可限定子树） | `/proc`、`/sys` 读 |
| `DBG_TRACE` | 订阅事件流 / syscall trace | `strace`（ptrace 变种） |
| `DBG_PROFILE` | 请求性能采样（HW counter） | `perf`（`CAP_PERFMON`） |
| `DBG_ATTACH` | attach 交互式调试器（pause/step/read-mem） | `ptrace` attach |
| `DBG_CRASHDUMP` | 读取/持久化崩溃报告 | `core_pattern` 落盘 |

- 这些 right 挂载在**目标对象**（某进程 handle、某 Job handle、内核 inspect root handle）上，由持有 `GRANT` right 的对端显式授予（对齐 `07` §4.5）。
- **默认拒绝**：spawn 出的进程不持有任何 `DBG_*` right；调试器必须先从监督者/同 Job 持有者处获得受 `DBG_*` 约束的 handle。
- **不引入「调试 root」**：不存在 uid=0 式全局调试权；即便 meu-supervisor 也只持有所需 right 子集。

### 4.3 统一崩溃模型与监督者联动（接 04/10）

三类崩溃汇聚为同一 `CrashReport`：

```
CrashReport {
  source:      KernelPanic | KernelCFault | UserServiceCrash
  faulting_pc
  register_set            // 现场寄存器
  stack_frames[]          // 统一帧格式（见 4.5）
  job_id / process_id     // 归属（接 04 Job 树）
  capability_context      // 崩溃时持有的 rights 摘要（供事后审计）
  symbolized: bool        // 是否已完成符号化
}
```

- **投递**：内核统一故障入口（见 `02` §4.5 `panic_handler` 单点）生成 `CrashReport`，经 **exception channel** 上报给目标 Job 的监督者（meu-supervisor）。这与 `04` §4.6「致命异常统一经 exception channel 上报监督者」一致。
- **监督者策略**（用户态，接 `04/10`）：按 manifest 决定 `kill` / `dump+restart` / `升级`（保留 dump 供分析）/ `降级`。用户态服务崩溃**不直接 panic 内核**（对齐 `02`：「组件 panic ≠ kernel panic」「由 supervisor 重启」）。
- **内核 panic 的特殊性**：内核核心 Rust 组件 panic（`02` §4.5）= 整体停机；此时 `CrashReport` 直接交付给**早期串口 +（若可用）`.msys` 持久化通道**，不再有 supervisor 介入（系统已停机）。

### 4.4 inspect 树与事件流（参照 Fuchsia）

- **Inspect 树**：内核与用户态服务各自挂载子树；节点属性为强类型（int/string/bytes/histogram/lazy）。读受 `DBG_INSPECT` right 约束，且可按子树粒度授权（如只授 `services/<n>/`）。替代 `/proc`/`/sys` 文本伪文件的「全局可读」反模式。
- **事件流**：内核（syscall/调度/异常/IO）与用户态服务（FIDL 反射式自描述事件） emitting 带 schema 的事件，进入 capability 约束的 ring buffer；消费者持 `DBG_TRACE` right 经 Channel 订阅。schema 自描述（对齐 perfetto/ETW），避免文本解析。
- **与 IPC 融合**：inspect 读取、事件订阅、崩溃报告查询，全部是内核对象 + capability，经 `05` 的 Channel/EventPort 传输，权限随句柄走，与 `07` 模型同源。

### 4.5 多架构回溯/符号化与「Rust panic=abort vs C 栈展开」的统一

**真实张力**：`02` §4.5 明确内核 Rust 用 `panic=abort`、`不展开调用栈`；传统「panic backtrace」依赖 unwind。如何在「内核 abort」与「调试者要 backtrace」之间统一？

**自主裁决（非缝合怪、与 `02` 自洽）：**

- **内核态（TCB，Rust/C 混合）**：坚持 `panic=abort`（安全理由：`02` 已论证）。因内核 panic = 停机事件，回溯需求较低；内核统一故障入口保存**完整寄存器现场 + 少量返回地址帧（PC/LR/FP 链）**，配合 `DBG_INSPECT` 暴露的**符号表**做 panic 现场符号化（panic site + 末几帧）。**不做全栈 unwind**——这是刻意的、与 `02` 一致的取舍。
- **用户态（Rust 服务 / C 进程）**：**启用 unwind**（与内核相反，但合理）——用户态服务崩溃需完整 backtrace 供 supervisor/dump 分析，且由 supervisor 重启而非停机（对齐 Hubris/Redox「组件 panic ≠ kernel panic」）。故用户态 Rust 服务**不使用** `panic=abort`，而用 unwind 生成完整 backtrace；内核 C 故障（段错误）用 unwind table 展开。
- **统一帧格式**：内核态现场帧、用户态 unwind 帧、C fault 帧，统一归一化为 `StackFrame{ pc, symbol?, module, offset }`，使 `CrashReport.stack_frames` 跨三类崩溃同构。

**多架构回溯/符号化差异处理：**

| 架构 | 展开机制 | 符号化来源 | MeuOS 处理 |
|------|----------|-----------|-----------|
| x86_64 | DWARF `.eh_frame` / 紧凑 unwind | 符号表（kernel + 用户 ELF） | 统一 in-kernel unwinder 抽象 |
| i386 | DWARF + 变参特殊处理（mcc 已知风险，见 memory） | 同上 | 同 x86_64，注意 cdecl 栈帧 |
| aarch64 | DWARF `.eh_frame`（ARM EH） | 同上 | 统一抽象 |
| riscv64 | DWARF `.eh_frame` + `z` 扩展考虑 | 同上 | 统一抽象 |
| loongarch64 | DWARF（LoongArch 约定） | 同上 | 统一抽象 |

- **统一 in-kernel unwinder**：定义 `unwind(start_frame, architecture) -> Vec<StackFrame>`，每架构提供一份薄后端，输出统一帧。避免「每种架构一套回溯代码散落」。
- **符号化**：内核维护自身符号表（链接期生成 `.symtab` 镜像内嵌或独立段）；用户态符号化需目标 ELF 的符号能力（受 `DBG_*` right 约束，仅对授权调试目标生效）。

### 4.6 与 Linux 兼容层（08）的关系（mkit/glibc 程序期望 ptrace/strace/perf）

mkit 程序期望 `ptrace`/`strace`/`perf`，但 MeuOS 内部无对应全局权限。**映射而非平移**（非缝合怪）：

| Linux 期望 | MeuOS 等价（capability 友好） |
|-----------|-------------------------------|
| `strace`（跟踪某进程 syscall） | 兼容层把 `ptrace(PTRACE_SYSCALL)` 重写为「向目标进程 attach 一个 `DBG_TRACE` 订阅」——syscall 事件从事件流取，而非 ptrace 单步陷阱。语义更干净、开销更低 |
| `ptrace` attach（读内存/暂停） | 需持有目标进程的 `DBG_ATTACH` handle（由监督者/同 Job 授予）。兼容层**不默认授予**——即 mkit 程序的 ptrace 默认被拒（fail-closed，与 `07` pledge 越界即终止一致），需显式调试授权 |
| `perf`（采样） | 映射为 `DBG_PROFILE` capability；HW counter 是内核对象，经 capability 访问。不平移 Linux `perf_event_open` 的全局语义 |
| `/proc/<pid>/` 读 | 映射为 inspect 树对应子树（`jobs/<id>/processes/<pid>/`）的 `DBG_INSPECT` 读。无全局 `/proc` 可读 |

**核心取舍**：mkit 程序的 `ptrace`/`perf` **默认不可用**，需显式调试授权——这保护了内部 capability 模型，又通过兼容层为「确实需要调试的旧二进制」提供等价路径（要求调用方持有相应 debug capability）。

### 4.7 与统一文件系统（01 方向①）：crashdump 落 `.msys` 卷

- 崩溃报告（或更完整的 crashdump：寄存器 + 关键内存页 + stack frames + symbol 上下文）经校验和/加密落到 `.msys` 卷：
  - **校验和**：每个 crashdump 条目带 SHA-256（复用 `.msys` v2 的校验机制，见 `11` §4.1），防静默损坏。
  - **加密**：敏感 dump（含进程内存）可选 ed25519/对称加密（复用 `.msys` 签名/加密能力），仅持 `DBG_CRASHDUMP` right 者可读。
  - **结构化落盘**：crashdump 是 inspect 树的一个节点（`kernel/crashdumps/<seq>/`），而非自由文本 core 文件——与「结构化优于文本」一致。
- 这也与 `11` §4.1「`.msys` 成为可自举/可回滚媒介」同源：崩溃记录与 sysroot 同介质、同校验链。

### 4.8 与自举验证（11）的 QEMU 联调通道

- **gdbstub**：QEMU 的 `gdbstub`（`-s`/`-S` 或 `chardev` 串口/TCP）提供早期内核调试。MeuOS 内核在 QEMU 下暴露 gdb 目标，需**调试 capability 协商**——即便在 VM 内，attach 也走 `DBG_ATTACH`（原型期可放宽到「串口控制台持有者即调试者」，但架构上仍经 capability）。
- **串口**：早期内核日志/panic 现场走 NS16550/virtio-console（见 `10` 附录 A），作为 inspect/事件数据的「文本渲染兜底」（最低限度可观测性）。
- **9p 共享**：`11` §4.3 的 9p（`/mnt/host`）用于宿主⇄guest 传符号表/源码，便于在宿主侧符号化 guest 崩溃。
- **联调闭环**：`11` 的 `qvm` 通道 + 本文件 inspect/事件/crashdump = 自举验证期的统一可观测面（内核 banner、init 就绪、mcc 自举结果、崩溃报告均经同一通道）。

## 5. 自主结论（非缝合怪总结）

1. **可观测性是一等公民，不是补丁**：以 inspect 树 + 事件流 + 崩溃报告三基元取代 printk/`/proc` 文本海；文本仅作结构化数据的渲染。
2. **调试权限即 capability**：以 `DBG_*` rights 取代 Linux 的「默认 ptrace/perf 全局」，默认拒绝、显式授予；无「调试 root」。
3. **三类崩溃统一上报，与监督者联动**：kernel panic / kernel C fault / 用户服务崩溃 → 同一 `CrashReport` → exception channel → meu-supervisor（kill/dump/restart）。
4. **Rust panic=abort 与回溯的统一**：内核态坚持 `panic=abort` + 现场符号化（与 `02` 自洽）；用户态启用 unwind 生成完整 backtrace 并由 supervisor 重启（与 Hubris/Redox 一致）；二者归一化为统一 `StackFrame`。
5. **Linux 兼容映射而非平移**：strace→事件订阅、ptrace→调试 capability、perf→profile capability、/proc→inspect 子树，默认拒绝、需显式授权。
6. **crashdump 经 `.msys` 校验/加密落盘**，与统一文件系统同源、受 `DBG_CRASHDUMP` 约束。
7. **QEMU 联调 = gdbstub + 串口 + 9p**，复用 `11` 的 `qvm` 通道作为原型期统一可观测面。

## 7. 待决清单（含架构裁决）

> 标注：本结论非最终，doc-sync 合成 pass 回填跨域一致性（与 `04` §5.8、`07` §5.6、`10` §5.3 交叉回填）。

1. **【架构裁决】调试 capability 的粒度与默认**：本文推荐**细粒度 rights**（`DBG_INSPECT/TRACE/PROFILE/ATTACH/CRASHDUMP`）。裁决点：是否进一步细分（如 TRACE 限定 syscall vs 全部事件）？还是原型期先用单一 `CAP_DEBUG` 粗粒度、后续细分？建议原型期用细粒度的最小子集（INSPECT+ATTACH），其余按需。需 team-lead 在合成 pass 拍板默认值**是否对 mkit 程序开放**（本文立场：默认拒绝，需显式授权）。
2. **【架构裁决】exception channel 的消费者仲裁**：`04` §5.8 已指出「exception channel 同时服务监督者与调试器，权限与冲突如何仲裁」。本文建议：监督者持有 `DBG_CRASHDUMP` 的**默认订阅权**（kill/restart 决策所需）；交互式调试器需持 `DBG_ATTACH` 且**不能阻断**监督者的崩溃处理（调试器 attach 期间崩溃仍先交付监督者，调试器读副本）。具体仲裁协议待 `04/12` 协同定稿。
3. **内核 panic 现场符号化的工程成本**：内核 `panic=abort` 下需保存「末几帧 + 符号表」。是否内嵌完整内核符号表（占内存）还是仅调试构建内嵌、发布构建外置？原型期建议调试构建内嵌、发布构建经 `.msys` 外置符号。
4. **用户态 unwind 与 `panic=abort` 的语言策略冲突**：`02` §4.5 写「内核 Rust 统一 panic=abort」；本文建议「用户态服务启用 unwind」。需 `02` 明确保留「用户态 Rust 服务可用 unwind」的口子（本文已据此设计），合成 pass 应回写 `02` 以免矛盾。
5. **多架构 unwind 后端一致性**：in-kernel unwinder 在 5 架构的 DWARF 解析是否统一实现，还是每架构一份？建议统一抽象 + 每架构薄后端（呼应 `01` §5.6 五架构一致性成本议题）。
6. **crashdump 落盘的触发条件**：默认「用户服务崩溃」是否自动 dump？推荐：仅 `dump+restart`/`升级` 策略触发落盘，普通 kill 不落盘（省 `.msys` 空间）；内核 panic 必落盘（系统已停机）。
7. **与 Linux 兼容层（08）的 ptrace 完整性**：旧二进制依赖 `ptrace` 写时复制/单步（如 `gdb` 调试 mkit 程序）能否经「事件订阅替换」完全等价？预计**不能完全等价**（单步/内存改写类调试），需在 `08` 明确「mkit 调试支持到哪一层」。
8. **perf HW counter 的 capability 暴露面**：HW 性能计数器在不同架构（PMU/PMUv3/HPM）差异大，统一为 capability 对象的成本待原型评估。

### R3-5 C9 回写：调试 capability 6 right + 默认全 deny + 异常多播仲裁（12 核心定稿）

- **6 个 `DBG_*` right**（在原文 5 个基础上拆出第 6 个 `DBG_POKE`）：

  | right | 含义 | 风险级 | 默认 |
  |-------|------|--------|------|
  | `DBG_INSPECT` | 读 inspect 树（按子树粒度授权） | 低 | deny |
  | `DBG_TRACE` | 订阅事件流 / syscall trace | 低 | deny |
  | `DBG_PROFILE` | HW counter 采样（侧信道风险） | 中 | deny |
  | `DBG_ATTACH` | attach：暂停/单步/读寄存器/读内存/设观察点 | 高（控制+读） | deny |
  | `DBG_POKE` | **改写目标内存 / 写寄存器 / 写断点** | **最高（任意写后门）** | **deny，且绝不随 ATTACH 自动获得** |
  | `DBG_CRASHDUMP` | 读取/持久化崩溃报告 | 中（含内存快照） | 监督者对其监督 Job **默认持有** |

- **mkit 与 glibc 默认完全一致：全 deny**。spawn 出的进程不持任何 `DBG_*`；调试权靠持 `GRANT` 的 `debug-issuer` 显式授予，与程序类型无关（非缝合怪、默认拒绝）。
- **dev/prod 差异不靠全局开关，靠 spawn/Job manifest 的 `debug_policy` 声明属性**：`deny`（默认，生产）｜`same-job`（同 Job 树内可相互 attach）｜`dev-session`（指定 dev-session issuer 可 attach）。**强烈否决全局「系统 dev 模式」开关**（= root 等价逃生舱，违背 `07` 铁律，与 C4「沙箱默认 deny」同理）。
- **异常 channel 消费者仲裁（C9-B）定稿**：① 内核一次性生成 `CrashReport`，以 copy 语义 fan-out 多播给所有注册消费者（监督者 + 持权调试器），无「谁先抢到独占」；② 监督者持 `DBG_CRASHDUMP` **默认订阅权**，其 kill / dump+restart / 升级决策**不可被抑制**（自治重启不变量永不破坏）；③ 调试器持 `DBG_ATTACH` 仅收副本、不阻断监督者落盘/重启；④ 有界崩溃冻结窗口（crash freeze）：调试器可请求冻结暂缓重启（调试 crash loop 刚需），须持 `DBG_ATTACH`、超时（默认建议 30–120s，待 A14 拍板）自动解除、detach/崩溃立即释放，**绝不可永久接管崩溃**。

### R3-6 C10 回写：ptrace 档位 C + 单步归 DBG_ATTACH（12 调试原语定稿）

- 原 §7-7「单步无法经事件订阅等价」的疑虑已解：单步是内核让目标线程每条指令停下的**原生控制能力**，属「观察/控制」而非「改写」，应归入 `DBG_ATTACH`（read-side），无需 `DBG_POKE`。这修订了原 §4.2/§7 中「预计不可完全等价」的保留。
- `DBG_POKE` 单列是 C10 安全性问题的钥匙：所有**写操作**单独校验 `DBG_POKE`；仅有 `DBG_ATTACH` 的调试器得到完整读/单步/观测能力但**无法改写**，故无「attach 即得任意写」后门。改写权永不在 `DBG_ATTACH` 内、永不默认、授予可审计可 revoke。
- **原型期以 QEMU gdbstub 作完整调试力替代通道（12 兜底说明）**：内核 bring-up 与 mkit 程序开发阶段经 QEMU gdbstub 获完整调试力（含内存写），因调试权位于 VM 边界、由 QEMU 控制方持有，**不进入 MeuOS capability 模型**；生产 in-guest 调试回到 capability 守护模型（ATTACH 级默认、POKE 级需授权）。此兜底与 `11` §4.3 联调通道一致，应在 12 定稿中明确为「原型期桥接，不污染内部模型」。
