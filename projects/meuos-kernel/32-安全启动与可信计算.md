## 0. 一句话核心结论

> **在「无 root、权限=不可伪造句柄」的 capability 内核里，信任根不是「一个超级用户」，而是「一段在启动期被逐跳验证、且自身只派生受限令牌的不可伪造代码」——MeuOS 的信任链必须把「身份根（这是真 MeuOS 代码）」与「权限根（这些令牌从 boot 期就受约束）」在固件→bootloader→内核 monitor→.msys rootfs 的每一跳都同时建立，且度量基直接复用 `.msys` 已具备的 ed25519 签名 + extent 校验和，长成一棵「签名 + Merkle 根哈希」双锚的度量树，而非另起一套 TPM 依赖的缝合怪。**

## 1. ①「应该是什么样」——从 capability 世界反推启动期信任

> 大喵铁律第一条：先问「MeuOS 的信任根与度量**应该是什么样**」——在 capability 世界、最小 TCB、自研工具链下，信任链如何既可验证启动、又不膨胀 TCB。

### 1.1 capability 内核把「信任」问题推到了最前面

`07` §1/§4 已定：**权限 = 不可伪造的句柄（handle = capability）+ rights 位图；无 root、无 uid=0 逃生舱**。这一地基对「安全启动」提出了一个 Linux 世界没有的尖锐问题：

- 在 Linux 里，「信任根」最终收敛为「内核信任了一个被签名的模块 / 一个具 CAP_SYS_ADMIN 的主体」——信任的尽头仍是一个**身份特权者**。
- 在 MeuOS 里，**没有任何身份特权者可以作信任的避难所**。capability 监视器（TCB 核心，`00` A3）本身就是「权限的唯一裁决点」，但监视器**自己凭什么被信任**？如果攻击者能在监视器上线之前替换内核镜像、或在 `meu-supervisor` 启动前注入一个伪造的监督者，那么监视器派生出的第一批令牌（根 Job、设备能力、`KEY_UNWRAP` 服务端权，`06`/`07` C2）就全是无源之水。

> **定义 0（启动期信任根）**：MeuOS 的信任根 = 「一段在 boot 期被逐跳密码学验证、且**只派生受约束令牌**的代码 + 其持有的不可伪造密钥材料」。它既是**身份根**（证明「这是真 MeuOS 代码」），又是**权限根**（声明「从这里派生出的令牌从 boot 期起就受 rights 约束」）——二者在 capability 模型下是同一个东西的两面，因为「无 root」意味着**启动即建立不可伪造的身份/权限根**，而非事后赋予某个主体特权。

### 1.2 信任链「应该」长这样（最短可验证、不膨胀 TCB）

把启动期信任还原为最小必要跳，每一跳回答「下一跳凭什么是可信的」：

```
[硅基/固件只读锚]  ──(公钥哈希锁在 ROM/eFUSE/OTP 或等价只读介质)──▶
  └─ 固件/引导器（UEFI/BIOS/SBI）    验签 bootloader（.mimg 或 multiboot）
        │  度量 = hash(firmware→bootloader) 写入「度量累积器」
        ▼
  └─ MeuOS boot（bootloader 阶段）   验签内核镜像（内核 C 部分 mcc 产 + Rust 部分 rustc 产，合并后整体签名）
        │  度量 = hash(kernel image) 累积
        ▼
  └─ 内核 monitor 自举（Stage 4）      自身度量 + 派生第一批 capability（根 Job / 设备 / 命名空间 / KEY_*）
        │  度量 = hash(monitor 代码 + 初始 capability 模板) 累积
        ▼
  └─ .msys rootfs 挂载（FS 服务）     验签 .msys（Kit 已 ed25519）+ 卷 Merkle 根哈希校验（dm-verity/AVB 式）
        │  度量 = hash(.msys volume root) 累积
        ▼
  └─ 用户态服务（meu-supervisor / FS / devmgr）  每个服务二进制签名验签 → 授予受约束初始句柄集
```

这条链的「应该」标准是：

1. **每一跳都验签 + 度量**（verify + measure）：不只「能跑就行」，而是「跑的是被签署的真货，且它的哈希被记录」。
2. **度量累积而非孤立**：每一跳把上一跳的度量 extend 进一个「度量累积器」（PCR 式），使最终状态能反映整条链——这是 Measured Boot 相对「仅 Secure Boot 布尔放行」的关键价值（`29` §5.1 把度量定位为纵深第 0 层）。
3. **权限根与身份根同源**：monitor 派生第一批令牌时，令牌的「受约束」属性来自 `07` rights 位图，而「这些令牌确实由真 monitor 派生」来自 boot 期对 monitor 代码的验签——**身份根保证权限根不被伪造**。
4. **不膨胀 TCB**：验证/度量逻辑尽量落在**早期 C/asm 薄层 + 一个极小的验签器**（ed25519，Kit 已有实现可复用），**不**把 TPM 驱动、证书链解析、复杂策略引擎塞进 TCB。TPM 是「可选度量 sink」，不是「必需信任依赖」（对齐 Fuchsia「Zircon 无传统 TPM 依赖但支持」）。

### 1.3 度量基「应该」是什么（复用 .msys，不另造）

`06` §4.2/§4.3 已定：`.msys` 卷有 **extent 级校验和（覆盖密文）**，且 `21` §4.1 确认 Kit 的 `.msys` v2 **已具备 SHA-256 + 去重 + ed25519 签名**。这天然就是度量基的雏形：

- **包级度量基（已有）**：`.msys` 整体 ed25519 签名 —— 回答「这个 rootfs 包是不是官方构建」。
- **块级度量基（需补）**：参照 dm-verity / AVB，在 extent 校验和之上构建一棵 **Merkle 树**，其根哈希由官方密钥签名（类比 AVB 的 `vbmeta`）——回答「rootfs 里每一块是不是未被篡改」，且支持**按需度量**（只读映射时才校验对应块），不必要全卷扫描。
- **内核组件度量基（需补）**：内核镜像（mcc C 部分 + rustc Rust 部分合并后）整体签名 + 各组件段哈希，供 bootloader 与 monitor 两处验证。

> **非缝合怪宣言**：MeuOS 不拼接「Linux shim/MOK + IMA + dm-verity」三件套，也不照搬「Windows BitLocker + VBS」或「Android AVB + TEE」——而是取其**共同内核**（签名验证每一跳 + 度量累积 + 块级 Merkle 根哈希 + 密钥根上锁），落到一个由 capability 模型（`07`）、最小 TCB（`02`）、`.msys` 已具备签名（`21`）唯一决定的 MeuOS 形态：密钥根 = 一段 boot 期锁定的只读公钥；度量基 = `.msys` 的「ed25519 签名 + extent Merkle 根」双锚。

## 2. ② 多系统参照对比表

> 大喵铁律第二条：多系统参照（Secure Boot / Measured Boot / TPM / 密钥根 的成熟实践），思想取长补短，实现自主研究。

| 系统 | 信任链 / 度量做法 | 密钥根位置 | 度量基形态 | 对 MeuOS 的可借鉴点 | 与 MeuOS 现实的冲突（避免缝合） |
|------|------------------|-----------|-----------|----------------------|-------------------------------|
| **Linux (UEFI SB)** | shim → MOK（用户可 enroll）→ GRUB → 内核；内核模块签名 (`CONFIG_MODULE_SIG`) | 平台 Key (PK)/KEK/db 在 UEFI NVRAM；MOK 在 shim 变量 | IMA 度量（文件哈希进 PCR）、dm-verity（块级 Merkle） | 「每一跳验签 + 块级 Merkle 度量基（dm-verity）」是直接范本；模块签名对应「用户服务二进制签名」 | MOK 允许用户 enroll = 信任后门；`CONFIG_MODULE_SIG` 的密钥仍隐含「内核特权者」；与「无 root」不符 |

| **塞班 (Symbian)** | 平台安全：可执行文件签名才能安装/运行（capability 绑定签名） | 厂商证书 + 设备烧录根 | 安装期签名校验 | 「二进制签名 = 运行许可」历史可行，验证「capability 模型 + 启动/安装期签名」可协同 | 已淘汰，无度量/T Mode 现代机制 |
| **ChromeOS** | 固件写保护（WP 跳线/寄存器）→ 固件验签内核 → 内核验证 ` rootfs`（dm-verity）→ **miniOS** 恢复；A/B 双 slot | 固件 RO 区 + 谷歌密钥 | dm-verity 块级 + A/B 签名 | 「固件写保护 + dm-verity 度量 rootfs + 防砖恢复（miniOS）」思想——对应 MeuOS `.msys` 度量基 + `06` A/B 防砖兜底 | A/B 2x 空间非 MeuOS 首选（`06` §4.3 以子树快照为主路径） |

## 3. ③ MeuOS 信任链与度量方案（自主收敛）

> 本节把 §1 的「应该」落到 MeuOS 自己的取舍。核心命题：**信任链逐跳验签 + 度量累积；度量基 = `.msys` 的「ed25519 签名 + extent Merkle 根」双锚；monitor 自身度量参照 Fuchsia verified boot；密钥根 = 一段 boot 期锁定的只读公钥。**

### 3.1 信任链逐跳（对齐 `09` Stage 0–5）

| 跳 | 阶段（`09`） | 验签对象 | 度量累积（PCR 式） | 密钥来源 |
|----|-------------|----------|-------------------|----------|
| 0 | 固件/引导器接入（Stage 0） | bootloader（`.mimg` 或 multiboot 入口） | `PCR[0] = hash(firmware)` → extend `hash(bootloader)` | 固件只读锚（ROM/eFUSE/OTP 或 §5 五架构降级方案） |
| 1 | 内核加载（Stage 1–3 边界） | 内核镜像整体（mcc C 部分 + rustc Rust 部分合并） | `PCR[1] = extend(hash(kernel image))` | bootloader 内置 MeuOS 代码签名公钥 |
| 2 | **monitor 自举（Stage 4）** | monitor 代码段 + 初始 capability 模板哈希 | `PCR[2] = extend(hash(monitor) || hash(init caps template))` | monitor 由 boot 期公钥派生自身度量，不持私钥 |
| 3 | **.msys rootfs 挂载（Stage 5）** | `.msys` 包签名（Kit ed25519）+ 卷 Merkle 根哈希 | `PCR[3] = extend(hash(.msys volume root))` | FS 服务消费 `07` 的 root-of-trust 能力（来自 boot 链） |
| 4 | 用户态服务（Stage 5+） | 每个服务 ELF 签名（mcc/rustc 产物） | `PCR[4..] = extend(hash(service_i))` | 服务签名公钥 = 系统代码签名公钥（同源） |

**关键设计点**：
- **monitor 自身度量（参照 Fuchsia verified boot）**：monitor 是 `07` 的 TCB 核心，也是权限根。`Stage 4` 激活时，monitor 用 boot 期传入的度量累积器**对自己做度量**（hash 自身代码 + 初始 capability 模板），并 extend 进 `PCR[2]`。这保证「即便攻击者替换了 monitor 代码，度量链会断裂、下游 .msys 校验会失败」——把 Fuchsia「内核自身验签」下沉为「monitor 自度量」，与 capability 模型精确咬合（monitor 不可伪造 = 第一批令牌不可伪造）。
- **权限根由 rights 位图保证、身份根由验签保证**：monitor 派生的根 Job / 设备 / 命名空间 / `KEY_UNWRAP` 服务端权（`06`/`07` C2），其「受约束」来自 `07` rights（不可扩张，`29` I3/I6）；其「确实来自真 monitor」来自 `PCR[2]` 对 monitor 的度量。二者缺一，下游服务拿到的就是不可信令牌。

### 3.2 度量基：`.msys` 的「双锚」结构（对齐 `06`/`21`）

`.msys` 已具备包级 ed25519 签名（`21` §4.1）。在其上构建度量基：

```
.msys 度量基（双锚）
┌─────────────────────────────────────────────┐
│ 锚 1：包级签名（已有，Kit ed25519）            │
│   · 回答「这是不是官方构建的 rootfs 包」        │
│   · FS 服务挂载前验签（06 §4.3(a)）            │
├─────────────────────────────────────────────┤
│ 锚 2：卷 Merkle 根哈希（需补，对齐 dm-verity/AVB）│
│   · 在 extent 校验和（06 §4.2，覆盖密文）之上   │
│     建 Merkle 树 → root hash 由官方密钥签名     │
│     （类比 AVB vbmeta）                        │
│   · 回答「rootfs 每块是否未被篡改」             │
│   · 按需度量：只读映射时才校验对应块，不必全扫  │
│   · 支持回滚保护：root hash 绑定 .msys 版本号   │
│     （防降级攻击，对齐 AVB 版本号）             │
└─────────────────────────────────────────────┘
```

- **与 `06` extent 校验和的协同**：`06` §4.2 的 extent 级校验和（覆盖密文）是 Merkle 树的叶子输入——我们不另造一层校验，而是把已有 extent 校验和聚合成树。叶子 = extent 密文校验和；内部节点 = 子节点哈希；根 = 卷 root hash（签名）。这复用 `06` 已有结构，不膨胀 FS 逻辑。
- **与 `06` 加密的协同**：Merkle 树覆盖**密文** extent（`06` 已定校验和覆盖密文），因此即便卷加密，度量基仍有效且密钥无关——验证完整性不需要持有卷密钥。
- **回滚保护（对齐 AVB 版本号）**：`.msys` 版本号写入 Merkle root 的签名域；旧版本即使签名有效也被拒绝（防攻击者把系统降级到已知漏洞版本）。这与 `06` §4.3 的「原子 repoint + 回滚」不冲突——回滚是**有意的、监督者授权的**同代回退，而降级防护挡的是**攻击者强制的旧代回退**。

### 3.3 密钥根：自研工具链产物的签名与公钥根存放

`02`/`21` 已定：mcc 产 C 部分、rustc 产 Rust 部分、合并为内核镜像；`.msys` 由 Kit 打包。这些二进制**如何签名、公钥根放哪**：

- **签名方**：构建期（Kit `bootstrap.sh` Phase K，`21` §1.2 咬合点 C）用**系统代码签名私钥**对内核镜像 + 每个用户态服务 ELF + `.msys` 包签名（ed25519，与 Kit 现有 `.msys` 签名同源算法）。mcc/rustc 只负责编译，签名是构建流水线的独立步骤（不污染编译器 TCB）。
- **公钥根（信任锚）的位置——分档**：

  | 档 | 公钥根位置 | 适用架构 | 安全级 | 说明 |
  |----|-----------|---------|--------|------|
  | A | 固件只读区（ROM/eFUSE/OTP 锁哈希） | 有 Secure Boot 的板（UEFI/SBI 设备） | 最高 | 公钥整体或哈希烧录，不可软件改写；对齐 Android Titan M / macOS SEP 思想 |
  | B | bootloader 内置（`.mimg` 镜像内的只读公钥段） | 无 eFUSE 但能保护 bootloader 只读 | 中 | 公钥随 bootloader 验签进入；依赖「bootloader 自身先被固件验签」 |
  | C | **软件可信根（降级档）** | i386 老 BIOS 等无硬件锚 | 低 | 无硬件信任根时，公钥作为「已知良值」硬编码进内核/bootloader，启动仅做「比对」而非「密码学锚定」；威胁模型须显式标注此降级区（见 `29` D-T6 同类降级） |

- **密钥层次（可选，对齐 Android 链式）**：厂商根密钥 → 构建密钥 → 组件密钥（内核/服务/.msys 各一把）。好处：组件密钥泄露可单独吊销，不必换厂商根。但原型期建议**单把系统代码签名密钥**（简单、TCB 小），层次化后置。
- **五架构差异**：见 §5。

### 3.4 度量 sink：TPM 可选，不强制

- **有 TPM/度量寄存器**：度量累积进真实 PCR，支持远程证明（attestation）——把 `PCR[0..4]` + 启动日志交给验证者。
- **无 TPM（Fuchsia 式）**：度量累积进内核内的**软件度量寄存器**（一个 boot 期锁定的哈希累积结构），启动完成即「冻结」并向 `meu-supervisor` 报告「度量值 = X」。无远程证明能力，但**本地完整性自检**成立（比对已知良值、失败即拒绝挂载/拒绝拉起服务）。这避免把 TPM 驱成 TCB 必需依赖（对齐 Fuchsia「Zircon 无 TPM 依赖但支持」）。
- **DMZ 原则**：TPM 驱动/远程证明协议**排除出 TCB**（用户态服务或早期 C 薄层之外），度量累积逻辑本身极小（extend = hash(prev||new)），可入 TCB 早期层。

### 3.5 与 `29` 威胁模型的衔接：度量是纵深第 0 层

`29` §4.1 给出四层纵深（架构最小 → Rust 类型 → 形式证明 → 否定式测试）。**度量/验证启动是这四层之下的第 0 层**：

```
[第 0 层] 32 启动期信任：代码/数据在加载即验签+度量 → 攻击者无法在 monitor 上线前植入伪造代码
─────────────────────────────────────────────────────────────────────
[第 1 层] 29 架构最小 TCB（监视器+IPC+低级VM/调度，主防线）
[第 2 层] 02 Rust TCB（消除整类内存安全漏洞）
[第 3 层] 20 形式证明 I1–I7（capability 逻辑不变量）
[第 4 层] 22 否定式安全测试（越权必失败）
```

- **为什么度量必须在 capability 之前**：`29` §1.1 的攻击面 = 显式授予的句柄集合。但若攻击者能在 monitor 上线前替换内核，则「句柄集合」根本不存在于真系统——T-A（获取未授权 capability）的种子在 boot 期就已埋下。度量是第 0 层，挡住「假内核」这一 capability 模型**无法自行防御**的威胁（capability 假设「运行的是真内核」，度量保证这个前提）。
- **新威胁类（供 `29` 后续补）**：T0「伪造/降级启动介质」——攻击者替换内核镜像、.msys、或回滚到漏洞版本。挡点 = 本维度 §3.1–3.2 的逐跳验签 + Merkle 度量基 + 版本防回滚。

| 协同点 | 说明 | 归属 |
|--------|------|------|
| **签名对象 = mcc C 部分 + rustc Rust 部分合并镜像** | `02` §4.3 合并模型 → 32 的签名/验签针对**合并后的单一内核镜像整体**（不分语言分别签，避免「半签名」缝隙） | 02 合并、32 整体签 |

### 4.4 与 `20`（形式化方法）的分工——本维度管「启动期信任」，不抢运行期验证

| 维度 | 管什么 | 验证对象 | 时点 |
|------|--------|---------|------|
| **32（本文）** | 启动期信任：代码/数据的**来源真实性与加载期完整性** | 「这是不是真 MeuOS 代码 / 这块数据是不是未被篡改」 | **加载时**（boot / mount / spawn 前） |
| **20（形式化）** | 运行期验证：capability 逻辑**行为正确性**（I1–I7） | 「权限语义是否可被违背」（无凭空 capability / revoke 全断 / rights 只减） | **运行期**（证明 + 机检） |

- **正交互补**：32 保证「跑的是真内核」，20 保证「真内核的 capability 逻辑无逻辑漏洞」。32 是**来源/完整性**维度（provenance/integrity at load），20 是**行为正确**维度（behavioral correctness at runtime）——二者不重叠、不竞争。
- **接口点**：32 的 `PCR[2]`（monitor 自度量）是 20 证明的**前置信任假设**——20 证明「若 monitor 代码 = 被度量的代码，则其 capability 不变量成立」。32 提供「monitor 代码确为被度量代码」的密码学保证；20 提供「该代码行为正确」的数学保证。组合 = 「真内核 + 真内核行为正确」的完整信任。
- **不越界**：32 不定义 rights 位图（归 `07`）、不定义 I1–I7（归 `20`）、不定义 derivation tree 全量与否（归 `07`/`20`），只把「验签后的代码」作为这些机制的信任输入。

### 4.5 与 `21`（迁移路线图）的协同

- `21` §4.1 确认 `.msys` v2 **已具备 ed25519 签名**——本维度直接复用，不重新发明签名格式。
- `21` §1.2 咬合点 C 的 `bootstrap.sh` Phase K 是**签名步骤的自然落点**（构建期对内核镜像 + 服务 ELF + `.msys` 签名）。建议 Phase K 增加「签名」子步骤（工程项，非架构级）。
- `21` §5.3 i386 纯 C 自举快通道：i386 内核镜像签名/验签与 64 位**无差别**（签名在合并镜像层，与内部语言无关）。

## 5. ⑤ 五架构启动信任差异

> 对齐 `09` §5.5 多架构表，补充每架构的**信任锚形态**与**降级处理**。

| 架构 | 固件/入口 | 原生 Secure Boot 能力 | 信任锚（公钥根档，§3.3） | 度量 sink | MeuOS 启动信任取舍 |
|------|-----------|----------------------|--------------------------|-----------|-------------------|
| **x86_64** | UEFI / multiboot2 | ✅ UEFI Secure Boot（PK/KEK/db） | **档 A**（eFUSE/UEFI NVRAM 锁公钥哈希） | 真实 TPM PCR（若板载）或软件寄存器 | 标准 UEFI SB 链；shim 类不需（无 MOK 后门，公钥直接锁固件）；TPM 可选做远程证明 |
| **aarch64** | UEFI + DT / PSCI | ✅ UEFI SB（部分板）+ 厂商锁 | **档 A**（eFUSE 锁根哈希）或 档 B（bootloader 内置） | TPM/信任区可选 | 类 x86_64；无 Titan M 类则用 bootloader 内置公钥（档 B） |
| **riscv64** | OpenSBI (M-mode) → S-mode | ⚠ 依赖具体实现（部分无 SB） | **档 B**（OpenSBI 内置公钥验签内核）或 档 A（若有硬件锚） | 软件寄存器为主 | OpenSBI 作为可信度量起点；无硬件锚时退档 B |
| **loongarch64** | UEFI/EFISTUB + CSR | ⚠ 视实现 | **档 B**（bootloader/EFISTUB 内置） | 软件寄存器 | 同 aarch64 降级档；公钥随 EFISTUB 验签进入 |
| **i386（老 BIOS）** | 32-bit BIOS / multiboot | ❌ **无原生 Secure Boot** | **档 C（软件可信根）** | 软件度量寄存器（无 TPM 假设） | **关键降级区**：无硬件信任锚，公钥硬编码进内核/bootloader 做「已知良值比对」；无密码学锚定，仅防「意外损坏/非官方镜像」，不防「持私钥者」——威胁模型须显式标注（`29` D-T6 同类）。可选补强：Coreboot + 自度量 bootloader + TPM 做 Measured Boot（有 TPM 时），但 BIOS 路径仍弱于 UEFI SB |

**五架构收敛结论**：
- **64 位四架构（x86_64/aarch64/riscv64/loongarch64）**：均能以「档 A 或档 B」建立真实密码学信任锚（UEFI SB / OpenSBI / EFISTUB 路径），度量 sink 可选 TPM。
- **i386 是启动信任的已知弱化点**：与 `02` C2（纯 C TCB）、`29` D-T6（纵深降级）同源——它是「能自举但**启动信任非密码学锚定**」的特例。建议：① 原型期 i386 接受档 C（软件可信根），威胁模型显式标注；② 若目标板有 TPM，用 Coreboot + Measured Boot 把 i386 升到「度量锚定」（仍非「验签锚定」）；③ 不要求 i386 达到 x86_64 的 UEFI SB 级，避免阻塞 M0–M4。

## 6. ⑥ 自主结论 + 待决项

### 6.1 自主结论

1. **capability 内核把「信任根」推到了 boot 期最前沿**：无 root 意味着信任不能寄托于任何身份特权者，monitor（权限根）自身必须被密码学锚定——「身份根」与「权限根」在 capability 模型下同源，都由 boot 期逐跳验签 + 度量保证。
2. **信任链 = 逐跳验签 + 度量累积（PCR 式）**：固件→bootloader→内核镜像→monitor 自度量→`.msys`→用户服务，每一跳既「放行真货」又「记录哈希」，下游验证可溯及整条链。
3. **度量基复用 `.msys`，长成「ed25519 签名 + extent Merkle 根」双锚**：不另造校验层——Merkle 树以 `06` 已有 extent 校验和（覆盖密文）为叶子，root hash 由官方密钥签名（对齐 AVB vbmeta），并绑版本号做防回滚；FS 服务消费 `07` root-of-trust 能力验签。
4. **monitor 自度量（参照 Fuchsia verified boot）是权限根不可伪造的关键**：`Stage 4` monitor 对自身代码 + 初始 capability 模板做度量并 extend `PCR[2]`，使「第一批令牌来自真 monitor」可被下游密码学验证。
5. **密钥根分三档，公钥根位置是核心待决**：档 A（固件 eFUSE/ROM 锁哈希，最高）、档 B（bootloader 内置，中）、档 C（i386 老 BIOS 软件可信根，低）——**「公钥根存放介质」是必须架构裁决的项**。
6. **TPM 可选不强制**：有则做真实 PCR + 远程证明，无则软件度量寄存器做本地完整性自检（对齐 Fuchsia「无 TPM 依赖但支持」），TPM 驱动排除出 TCB。
7. **度量是 `29` 纵深防御的第 0 层**：它在 capability 之前挡住「假内核」这一 capability 模型无法自防的威胁；新威胁类 T0（伪造/降级启动介质）归本维度挡。
8. **与 `20` 严格分工**：32 管「加载期来源/完整性」（这是真代码吗），20 管「运行期行为正确」（这代码逻辑对吗）——正交互补，不抢运行期验证；`PCR[2]` 是 20 证明的前置信任假设。

### 6.2 待决项（标注是否需架构裁决）

| # | 待决项 | 是否需架构裁决 | 关联 | 建议去向 |
|---|--------|----------------|------|----------|
| **D-SB1** | **公钥根存放介质**（档 A 固件 eFUSE / 档 B bootloader 内置 / 档 C 软件可信根）——尤其「无硬件锚架构（i386 老 BIOS）接受档 C 还是强制要求 TPM Measured Boot」 | **是（架构级，最高优先）** | `02` C2、`09` §6、`29` D-T6、`05` 五架构 | 需大喵拍板公钥根策略；建议 64 位走档 A/B、i386 走档 C 并显式标注降级 |
| **D-SB2** | **`.msys` 卷 Merkle 度量基是否纳入 `.msys` 格式本身，还是作为 `.mimg`/外部 vbmeta 侧载** | **是（架构级）** | `21` D1、06 §4.3 | 建议度量基作为 `.msys` 可选扩展段（不改 v2 主格式），与 `21` D1 合并裁决 |
