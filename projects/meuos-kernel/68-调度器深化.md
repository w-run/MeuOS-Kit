## 1. 概述与核心结论

### 1.1 一句话核心结论

**MeuOS 调度器应是「公平(EEVDF+权重) / 截止期(EDF 子类) / 实时(严格优先级, CAP_RT 门控)」三档同核、每核运行队列 + work-stealing 的同源调度器；时钟由 `57` 的单调钟绝对 deadline + slack 合并统一驱动，资源由 `04` Job 账本硬上限 fail-closed 兜底，RT 提权由 `07` bit45 的 CAP_RT 唯一门禁，五架构差异仅沉淀在 `arch/timer` 计时后端。**

### 1.2 推演起点（与已定地基对齐）

- 调度器基础已定：`04` §4.3 给出 EEVDF 公平层 + RT 固定优先级(0–31) + `sched_class` 钩子；RT 域已扩展为严格优先级 + Zircon 式 deadline 双子类（`28` §3.1 / `43`）。
- 时间抽象已定：单调钟唯一不可调、timer 即内核对象、绝对 deadline 红黑树 + slack 合并（`57` §3/§4）。
- 安全模型已定：capability Day 1、`CAP_RT` 冻结于 bit 45（default deny，`07` §4.1）、`KERNEL_PRIV` 覆盖全局 IRQ mask（`07` 第四轮回写 D-T1 / `59` §4.3）。
- 资源账本已定：Job 账本含 CPU 时间硬上限与 RT 预算（`04` §4.4 / `28` §4.2）。
- 结构化取消已定：致命异常 / 超限终止沿 Job 树上行监督者（`46`/`47` / `59` §6.3 / `00` A9）。

本文**不重述**上述已定结论，而是把它们**焊接成一份可执行的调度器深化蓝图**，补上 `04` 未展开的三档仲裁、runqueue 拓扑、与 timer/IRQ_MASK/CLOCK_MINT 的精确交互。

### 1.3 范围

覆盖：三档调度模型与仲裁顺序、与 `57` timer deadline/slack 协同、per-CPU vs 全局 runqueue 设计、与五架构 SMP 拓扑(`28` §6)协同、与 Job 账本(`04` §4.4)硬上限 fail-closed 协同、CAP_RT(bit45) 语义精确化及其与 `59` IRQ_MASK / `57` CLOCK_MINT 的交互、五架构同源(`57` §6 / `28` §6)。

不涉及（见既有文档）：进程对象模型 / spawn 语义（`04` §4.1/§4.2）、mlock 消缺页（`28` §5.1 / `03`）、数据通路 VMO/SHM 留核（`28` §3.2 / `05`）、调度核心形式化（`20` Layer A）、能耗硬配额（`27`/`04` 第四轮回写已定弱耦合）。

## 2. 多系统参照与取舍（解构型）

### 2.1 三档调度的业界参照

| 系统 | 公平层 | 截止期层 | 实时层 | 对 MeuOS 的取舍 |
|---|---|---|---|---|
| **Linux** | CFS→EEVDF（vruntime 红黑树） | `SCHED_DEADLINE`（EDF + 带宽预留） | `SCHED_FIFO/RR`（0–99 固定优先级） | **吸收** EEVDF 公平 + `SCHED_DEADLINE` 的 capacity/deadline/period 模型 + RT 固定优先级；三档各自独立 `sched_class` |
| **Zircon / Fuchsia** | 公平权重(0–31) | `zx_thread_set_deadline_params`（capacity/deadline/period, EDF 在子类内） | 严格优先级（0–31） | **范本**：deadline 是 RT 域内的子类而非独立类，本文沿用此结构（`28` §3.1） |
| **QNX** | 优先继承 + 自适应分区(APS) | — | 优先级驱动抢占 | **范本**：RT CPU 带宽硬分区 = `04`/`28` Job RT 预算的对应物 |
| **seL4** | 固定优先级 + 时间片（可验证） | — | 固定优先级 | **标杆**：调度核心可验证（§7 待决 Sc9 移交 `20`） |

### 2.2 取舍结论

- **拒绝**「单一优先级数字贯穿三档」：Linux `SCHED_FIFO` 用 0–99、CFS 用权重、deadline 用 bandwidth，三者语义不同；MeuOS 用**三档独立表达 + 统一仲裁顺序**，避免一个 magic priority 数字混用。
- **采纳** Zircon「deadline 是 RT 域子类」结构：`28` §3.1 的 `rt_deadline_class` 作为 RT 类下子类，沿用 `04` §4.3 `sched_class` 钩子，不重写核心。
- **采纳** EEVDF 公平层（`04` §4.3 已定）：虚拟截止期选 next，权重映射到 Job/进程组公平。
- **五架构同源**：算法层（`57`/`28` 已论证）五架构一致，差异仅计时源——见 §6。

## 3. 三档调度模型与 timer 协同

### 3.1 三档并列于同一调度核心

```
┌──────────────────────────────────────────────────────────────┐
│  RT 域（CAP_RT 门控，07 bit45）                                 │
│  ├─ 严格优先级子类 SCHED_FIFO/RR (0–31)：硬 RT，绝对不可被低优先级抢 │
│  └─ deadline 子类 (Zircon 式 capacity/deadline/period)：EDF 在子类内 │
│   - RT 域对 fair+deadline 绝对压制（见 3.3 仲裁）                  │
├──────────────────────────────────────────────────────────────┤
│  Deadline 档（独立可调度类，EDF，无 CAP_RT 也可声明周期预算）     │
│  - 中/软 RT：capacity/deadline/period，红黑树按绝对 deadline 排序   │
├──────────────────────────────────────────────────────────────┤
│  公平层（EEVDF，04 §4.3）：默认尽力而为，权重映射 Job 组间公平     │
└──────────────────────────────────────────────────────────────┘
```

- **公平档（fair）**：EEVDF 虚拟截止期 + 权重（继承 `04` §4.3）；纳秒级虚拟时间记账，时基 = `57` 单调钟。
- **截止期档（deadline / EDF）**：Zircon 式 `capacity/deadline/period`，EDF 在就绪集内选最紧急者。原语 `meu_thread_set_deadline(capacity, deadline, period)`（**不需 CAP_RT**，与严格优先级 RT 区分——deadline 是预算声明而非提权）。带宽由 Job 账本(`28` §4.2)约束。
- **实时档（RT）**：严格优先级 0–31，SCHED_FIFO/RR 语义（POSIX）。**进入/提升需 CAP_RT(`07` bit45)**（`04` §4.3 / `28` §4.1）。

### 3.2 与 `57` timer 绝对 deadline + slack 合并协同

- **deadline/RT 周期由 timer 对象驱动**：周期任务的 `period` 经 `57` §3.4 的 `timer_create`/`timer_set(deadline, slack)` 提交为绝对 deadline，挂在 `CLOCK_MONOTONIC`；触发经 EventPort 投 `TIMER_FIRED` 唤醒线程 → 调度器据其 deadline/优先级选 next（`57` §5.2）。
- **slack 合并对齐唤醒**：同 slack 窗内的多个周期 RT/deadline 唤醒合并到同一 tick（`57` §3.4），既节能又减抖动，取代 Linux `timeBeginPeriod` 式全局分辨率协商（`57` §2.2）。这对 RT 尾延迟门禁(`28` R8 / `19` `cyc_lat`)直接有利。
- **tickless 唤醒点 = 红黑树最早 deadline**：无就绪任务时停周期 tick（`57` §5.1 NO_HZ 同构），下一个唤醒点由 hrtimer 红黑树最早绝对 deadline 直接驱动调度器（`57` §5.2）。调度器的「下一个需重调度时刻」与 timer 的「最早 deadline」是**同一数据源**——避免两套并行时钟。
- **`task_tick` 仍是记账/抢占触发源**：时钟中断 → `04` §4.3 `task_tick` → EEVDF 记账 + 公平层时间片耗尽置重调度；RT 档不受时间片约束，仅受 RT 带宽(`28` §4.2)约束（`59` §5.1）。

### 3.3 三档仲裁顺序（pick_next 规则）

`pick_next_task` 固定顺序：**RT 严格优先级(最高 prio bitmap) > RT deadline 子类(EDF) > 独立 deadline 档(EDF) > 公平层(EEVDF 虚拟截止期)**。

- RT 域只要有就绪任务且未用尽 RT 带宽，公平层与独立 deadline 档不被选（对齐 Linux RT > CFS、`28` §3.1）。
- 独立 deadline 档优先于公平层：周期可预测任务不应被公平层长任务饿死。
- 同档内仲裁：RT 严格优先级用 0–31 bitmap 最高位；deadline 两档用 EDF 最早绝对 deadline；公平层用 EEVDF 虚拟截止期。

## 4. per-CPU vs 全局调度与 runqueue 设计

### 4.1 推荐：per-CPU 运行队列 + work-stealing

- **每核(runqueue) 独立**：避免全局锁争用（对齐 `04` §4.3、Linux `sched/fair` per-CPU rq）。每核 `rq` 含三个子结构：
  - `fair_rb`：EEVDF 虚拟截止期红黑树（权重就绪）；
  - `dl_rb`：deadline 档 + RT deadline 子类的绝对 deadline 红黑树；
  - `rt_bitmap`：RT 严格优先级 0–31 位图（O(1) 最高优先级选择，对齐 Linux `sched/rt.c` 100 队列简化版）。
- **pick_next = 跨三子结构按 §3.3 顺序取**：rt_bitmap 非空 → 最高 prio；否则 dl_rb 最早 deadline；否则 fair_rb 虚拟截止期。
- **负载均衡**：work-stealing（空闲核从最忙核偷任务）+ 周期性负载迁移（对齐 `04` §4.3）；NUMA 同节点优先，跨节点仅在必要（`04` §4.3）。

### 4.2 与五架构 SMP 拓扑(`28` §6)协同

- **同构多核（x86_64 / aarch64）**：标准 per-CPU rq + work-stealing；RT 双验证架构(`28` §6)上 RT 可达性最佳。
- **riscv64**：hart 拓扑可能含异构(`28` §6 标准化较弱)；runqueue 结构与架构无关，仅 `arch/timer` 后端差异（Sstc 缺失时 RT 计时回退 `28` R9）。调度核心无为。
- **loongarch64 / i386**：M5 后移 / 非 RT 重点（`28` §6 / `11`）；per-CPU rq 同构，i386 单/少核时 work-stealing 退化为空操作，无算法分支。

### 4.3 RT CPU 子集隔离

- **静态 `isolcpus` 式 RT 子集起步**（`28` §3.3 R6）：若干核划为 RT 子集，其上只跑 RT 域任务 + 绑定内核态快速驱动(`10` §4.2)，公平层与出核服务默认不进。
- **公平层能否临时借入 RT 核**：默认否（避免污染 RT 尾延迟）；动态 Job 声明借入为演进项（待决 Sc4）。
- **亲和集校验**：RT 任务的 CPU 亲和集 ⊆ 系统 RT 子集，且由 Job RT 预算(`28` §4.2)约束，越界 `EPERM`。

## 5. 与 Job 账本(`04` §4.4)协同：硬上限 / fail-closed / 超限

### 5.1 账本维度与检查点

| 账本维度（来源） | 含义 | 超限行为 | fail-closed 姿态 |
|---|---|---|---|
| CPU 时间硬上限（`04` §4.4） | Job 级 CPU 带宽硬上限 | 超限 → 触发 Job 终止传播（结构化取消） | **终止**（kill 沿 Job 树上行 `46`/`47`/`59` §6.3） |
| 公平权重+可选上限（`04` §4.4） | 公平层相对份额 | 超限 → 降权重/限流，不杀 | 限流（throttle） |
| RT CPU 带宽（`28` §4.2） | RT 任务窗口内可占 CPU 比例（QNX APS 式） | 超出 → RT 任务节流/挂起，不侵公平层 | 节流（throttle） |
| RT 优先级上限 / 亲和集 / deadline 预留数（`28` §4.2） | Job 可设 RT 边界 | 越界 `EPERM` | deny |
| timer_wakeups（`57` §4.3 T3） | 单位时间最大唤醒次数（防 DoS） | 超限 → 节流后续 `timer_set` | 限流 |

### 5.2 fail-closed 边界

- **两层超限语义不同**：
  - **throttle（限流，不杀）**：公平层权重上限、RT 带宽超限、timer_wakeups——这些是可恢复的资源挤压，只降速不终止，避免 RT/公平相互饿死引发级联 kill。
  - **terminate（终止，走结构化取消）**：CPU 时间**硬上限**超限（Job 彻底越权）→ 触发 Job 终止传播，由监督者(`04` §4.5)按策略在 Job 树内做结构化取消 + 重启/升级（`46`/`47`），异常经 exception channel 上行（`00` A9 / `59` §6.3）。这与 `07` pledge 越界即终止的 fail-closed 同源。
- **超限即记账、运行期不豁免**：准入期一次性付清不确定性（`28` §1.1 原则 4），运行期只做位运算 + 比较（`19` §1.1 原则 2），不引入可能失败的分配。

### 5.3 与结构化取消的焊接

Job 资源硬上限超限 = 结构化取消的**触发源之一**（与致命异常并列）。监督者收到「Job CPU 硬上限超限」事件后，执行与崩溃相同的 Job 树取消语义（`46`/`47`），保证无僵尸/孤儿、归因到 Job（对齐 `04` §4.4「谁该为超限负责」）。

## 6. CAP_RT(bit45) 语义精确化与 IRQ_MASK / CLOCK_MINT 交互

### 6.1 CAP_RT 语义精确化（已在 `07` bit45 冻结）

`CAP_RT`（`07` §4.1，bit 45，default deny，RT 提权门禁）精确覆盖：

1. **进入 RT 域**：把线程设为严格优先级子类（SCHED_FIFO/RR）或 RT deadline 子类；
2. **提升 RT 优先级**：在 0–31 内上调优先级（受 Job RT 优先级上限约束，`28` §4.2）；
3. **声明 RT CPU 亲和集**：绑定到 RT 子集（受 Job RT 亲和集约束）；
4. **设置 RT deadline 参数**：capacity/deadline/period（RT 子类内）。

无 `CAP_RT` 调用 `meu_thread_set_rt_*` → `EPERM`（fail-closed，`28` §4.1）。**注意区分**：独立 deadline 档（§3.1）声明周期预算**不需** CAP_RT——它是预算声明而非提权，由 Job 账本约束；只有「严格优先级 RT 域提权」需 CAP_RT。这避免把周期性软 RT 误升为特权操作。

### 6.2 与 `59` IRQ_MASK 的交互

- **两者正交、各管一层**：`CAP_RT` 决定**线程间**抢占优先级（谁能打断谁）；`IRQ_MASK`（`59` §4.1，per-IRQ 屏蔽权）决定**设备中断对驱动线程**的屏蔽，是设备能力家族(`10` §2.4)一员。
- **RT 线程不可借 RT 拿全局屏蔽**：`CAP_RT` **不含**全局 IRQ mask 权；全局关中断属 `KERNEL_PRIV`（`07` 第四轮回写 D-T1 / `59` §4.3），RT 提权线程绝不可借此制造全局 DoS（`59` §5.4 / `29` D-T1）。
- **「谁可打断谁」的精确语义**：
  - 高 CAP_RT 优先级线程可抢占低优先级线程（含公平层）；
  - 绑定的 RT 设备中断（留核快速路径，`10` §4.2）可打断 RT 线程（中断 > 线程，对齐 `59` §5.2「高优先级设备中断经 RT 运行队列」）；
  - RT 线程对自身设备中断仅能用 `IRQ_MASK`（per-IRQ）屏蔽，**不可**全局静默系统。
- **待决协同**：IRQ_MASK × CAP_RT 的联合仲裁细节（`59` §9.3 议题 2）需在 `43`/`59` 细化，本文引用不重复定稿。

### 6.3 与 `57` CLOCK_MINT 的交互（若需 RT 周期定时器）

- **标准 RT 周期定时器不需要 CLOCK_MINT**：RT 周期定时器走硬件比较值（TSC Deadline / CNTP_CVAL，`57` §4.3，留核路径）直接派发到 RT 线程，不经用户态 timer 服务 IPC 往返（`28` §3.2 / R1 已采纳）。设置 RT 域定时器**不引入新 right**——RT 预算已由 `CAP_RT` + Job RT 带宽约束（`57` §4.3）。
- **CLOCK_MINT 仅在「确定性回放测试钟」场景与 RT 协同**：`57` §3.2 / §4.2 提出 `CLOCK_MINT`（创建可冻结/受控派生子时钟，bit 48+ 待决 T1/T2）用于确定性回放与沙箱时间隔离。它是一个**测试/沙箱工具**，非 RT 调度必需原语；若 RT 任务需在冻结钟下做确定性 WCET 回放，则经 `CLOCK_MINT` 派生子钟挂 timer，但 CLOCK_MINT 本身**不赋予 RT 提权**。
- **结论**：CLOCK_MINT 与 CAP_RT 无依赖闭环——标准 RT 调度线不触碰 CLOCK_MINT；CLOCK_MINT 的 bit 分配仍待 `07` 协同定稿（`57` T1/T2），本文不预占 bit 0–47，不新设 right。

## 7. 五架构同源（算法一致，计时源差异关进 arch 薄后端）

### 7.1 核心论断

- **调度算法五架构完全一致**：EEVDF 选择、deadline EDF、RT 优先级 bitmap、带宽记账、锁协议（优先级继承/天花板 `28` §3.1）全部在 Rust TCB(`02`/`19`)内统一实现，与架构无关（`28` §6 结论、`57` §6）。
- **差异仅在计时源**：`arch/timer` 后端（`57` §6 / `28` §6）屏蔽五架构时钟差异：
  - x86_64 Invariant TSC + TSC Deadline；aarch64 Generic Timer(CNTPCT/CNTP_CVAL)；
  - riscv64 `rdtime` + Sstc(`stimecmp`)，缺 Sstc 时陷入 M 态回退（`28` R9）；
  - loongarch64 稳定计数 CSR；i386 TSC(可能非 invariant)→HPET/PIT。
- **runqueue / 调度核心零架构分支**：`task_tick` 时基来自 `arch_cycle_now()` 归一化纳秒（`57` §3.1），RT 可达性差异（Sstc 缺失/i386 非 invariant）是**计时精度下限**而非算法差异（`28` §6 / `57` T6）。

### 7.2 与 `19`/`20` 的可验证性

- 调度核心（RT 选择 / deadline 会计 / 带宽记账 / 锁协议）纳入 `19` §3.4(A) 可验证小核心，移交 `20` Layer A 做精化证明（`28` R10）。
- 五架构仅薄后端每架构验证（`00` §5-6「统一抽象 + 每架构薄后端」），调度算法本体不被架构稀释。

## 8. MeuOS 推荐方案（收口）

### 8.1 推荐架构（一句话）

**三档同源调度（公平 EEVDF+权重 / 截止期 EDF / 实时严格优先级 CAP_RT 门控）并列于每核运行队列 + work-stealing；timer 绝对 deadline + slack 合并(`57`)统一驱动唤醒，Job 账本硬上限(`04` §4.4) fail-closed 兜底（throttle 不杀 / 硬上限 terminate 走结构化取消 `46`/`47`），CAP_RT(bit45) 唯一门禁且与 IRQ_MASK(`59`) 正交、与 CLOCK_MINT(`57`) 无依赖；五架构算法同源、差异仅 `arch/timer` 计时后端。**

### 8.2 自主结论

1. **三档独立表达 + 统一仲裁**：公平(EEVDF)/截止期(EDF)/实时(严格优先级)各自独立语义，pick_next 顺序 = RT > deadline > fair；deadline 档不需 CAP_RT，RT 提权才需——避免 magic priority 混用。
2. **timer 与调度同一时钟源**：`57` 单调钟绝对 deadline + slack 合并驱动 deadline/RT 周期唤醒；tickless 唤醒点 = hrtimer 红黑树最早 deadline，与 `task_tick` 同源，无两套并行时钟。
3. **per-CPU runqueue + work-stealing**：每核 rq 含 fair_rb / dl_rb / rt_bitmap 三子结构，O(1) RT 选择 + EDF + EEVDF；NUMA 同节点优先；RT 子集静态隔离起步。
4. **Job 账本 fail-closed 两层语义**：throttle（不杀）用于可恢复挤压（权重上限/RT 带宽/timer_wakeups），terminate（走结构化取消）仅用于 CPU 硬上限越权；超限即记账、运行期不豁免。
5. **CAP_RT 精确语义且无新原语**：bit45 覆盖「进入 RT 域 / 提升优先级 / 亲和集 / RT deadline 参数」；与 IRQ_MASK 正交（RT 不拿全局屏蔽，仍属 KERNEL_PRIV）；标准 RT 周期定时器不触碰 CLOCK_MINT，CLOCK_MINT 仅确定性回放测试钟、待 `07` 协同 bit。
6. **五架构同源**：调度算法在 Rust TCB 内统一，差异仅 `arch/timer` 计时后端；riscv64 Sstc 缺失/i386 非 invariant 是精度下限非算法分支；调度核心移交 `20` 可验证。

## 9. 第九轮自主采纳·闭环 Sc5 / Sc9

> 修订式追加（不删改 §1–§8 原文，仅 §8.3 待决项表对应行状态列改写）。本两项为指挥官第九轮自主采纳裁决，待大喵复核。

### Sc5 — CPU 硬上限超限的 terminate 语义边界 → 采纳 fail-closed

**采纳结论**：CPU 硬上限超限走结构化取消（`00` A9 / `04` §4.6），terminate 经结构化取消优雅退出——异常上行至监督者；监督者默认 restart 策略；升级策略（如级联杀死父 Job）需显式 manifest 授权，不默认启用。

**理由与衔接**：与 `00` A9 结构化取消 + `04` §4.6 异常上行框架一致；与 `29` 第 0 层 fail-closed 原则同源（硬上限越权即终止，不隐式降级）；与 `46`/`47` 监督者 Job 树取消语义、`59` §6.3 异常上行焊接。默认 restart 而非默认级联升级，避免引入"隐式特权面"——升级杀伤半径（跨 Job 级联）属高危操作，须由 manifest 显式声明授权，与 `07` capability Day 1 / default-deny 同源。

### Sc9 — 调度核心是否移交 `20` 做端到端形式化 → 采纳移交

**采纳结论**：调度核心（RT 选择 / deadline 会计 / 带宽记账 / 锁协议）移交 `20` 形式化，作为 capability 核心形式化之后的第二优先级；落地于 `19` §3.4(A) 可验证小核心 Layer A；与 seL4 标杆一致（调度核心可验证）。

**理由与衔接**：RT 调度正确性可验证价值高，但优先级低于 capability 核心形式化（`28` R10 / `20` 落点）；与 `19` §3.4(A) 可验证小核心 Layer A 直接对齐（§7.2 已引用）；与 seL4 标杆一致——调度核心作为可验证小核心是可证正确性的黄金参照。五架构同源前提下，调度算法本体在 Rust TCB 内统一，形式化只针对算法本体，不稀释至每架构薄后端（`00` §5–6 统一抽象 + 每架构验证）。
