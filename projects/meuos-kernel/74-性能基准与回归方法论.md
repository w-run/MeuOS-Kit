## 1. 五架构 perf counters 薄后端（统一抽象）

### 1.1 推演：性能计数器「应该」是什么

解构型先看「在一个 capability、五架构、重服务出核的内核里，硬件性能计数器本应是什么」：

1. perf counters = **硬件计数器的只读读数**（指令 retired / 周期 / cache miss / 分支误预测 / TLB miss / 内存带宽 / 能耗），物理上只能由内核从 PMU MSR/系统寄存器读取——与 `40` §1.2「能耗计数器内核拥有原始读数」同源。
2. 它是**可观测性**而非**控制权**：读 perf counters 不应赋予任何提权（类比 `THERMAL_READ`/`ENERGY_READ` 只读、默认 deny），故**复用 `12` 既有 `DBG_PROFILE`/`DBG_TRACE` 消费面**，不新增 right bit（纪律铁律）。
3. 跨架构差异巨大（Intel PMU+RAPL / ARM PMUv3+AMU / RISC-V SBI PMU / LoongArch 自有 CSR / i386 legacy），须收敛为**统一事件 ID + 每架构薄后端**（对齐 `00` §5-6「统一抽象 + 每架构薄后端」、`59` §7.6 中断统一抽象、`27` §6 电源统一抽象）。

推演结论：**perf counters = 统一只读抽象层（事件 ID + 每 CPU/每 package 计数器），经 `12` 可观测权消费，差异仅关进 arch 薄后端；与计时（`28`）、能耗（`40`）、中断计数（`59`）同源暴露。**

### 1.2 统一抽象层（不新增内核对象，复用既有）

| 抽象层 | 形态 | 既有权/接口复用 | 说明 |
|--------|------|----------------|------|
| **统一事件 ID 表** | `PERF_INST`/`PERF_CYC`/`PERF_CACHE_MISS`/`PERF_BRANCH_MP`/`PERF_TLB_MISS`/`PERF_MEM_BW` 等归一事件 | 不新设 right；经 `12` inspect 子树 `kernel/perf/<event>` 暴露 | 同 `40` §5.1 `cpu_power_state` 的「内核维护只读结构」思想，零热路径 IPC |
| **arch 薄后端** | 把 PMU/RAPL/AMU/SBI-PMU/龙芯 CSR/i386 legacy 映射到统一事件 ID | 复用 `28` §6 `arch/timer` 计时后端同址 | x86_64 用 `RDMSR`(IA32_PERF_CTL/PERFEVTSEL/RAPL)、aarch64 用 PMEVCNTR/AMU、`riscv64` 用 SBI PMU extension、`loongarch64` 用自有 PMU CSR、`i386` 降级（多数无现代 PMU） |
| **消费面** | `DBG_PROFILE`/`DBG_TRACE`（`12` §4.2 既有）订阅计数器/直方图 | **不新增 right bit**（纪律） | 与 `19` §4.1「热路径延迟/计数内建」同构：lock-free per-CPU 计数器 + 直方图 + 采样，非逐操作事件（规避 `19` AP-5） |
| **能耗/热同源** | `ENERGY_READ`/`THERMAL_READ`（`40` §7）属同一只读可观测家族 | 已定、默认 deny | perf counters 与能耗/热读数共用一套 capability 守护骨架，扩事件不扩 right |

> **不引入新内核原语**：perf counters 不是新内核对象、不是新 right，而是 `12` 可观测框架上的一个**事件类别** + 一套每架构 PMU 映射薄后端。这与 `00` §5-6、纪律铁律一致。

### 1.3 与 `28` 五架构计时、`59` 中断计数的协同

- **与 `28` 计时同源**：perf counters 的「周期/指令」计数与 `28` §6 的 `arch_cycle_now()` / 单调钟后端**共享同一 arch 薄后端**——周期计数本就来自同一计时源（Invariant TSC / Generic Timer / `rdtime` / 龙芯稳定计数 / i386 TSC），避免两套并行计数抽象。
- **与 `59` 中断计数协同**：中断相关度量（每 IRQ 触发次数、Cap(IRQ n) wait→ack 时延、`IRQ_MASK` 切换次数）经同一统一抽象暴露为 `PERF_IRQ_*` 事件，与 `59` §4/§7 的中断对象模型同源；中断计数不引入新对象，复用 inspect 计数器。
- **统一落点**：`kernel/perf/` + `kernel/irq/` + `kernel/power/`（能耗/热，来自 `40`）三类只读子树，皆经 `12` 消费、皆由同一调度无关的可观测骨架承载。

### 1.4 五架构差异（perf counters 视角）

| 架构 | perf/能耗计数器可用性 | 原型期取值 |
|------|----------------------|------------|
| **x86_64** | Intel **PMU** + **RAPL** 最完整（指令/周期/cache/能耗全有） | 一等：完整 `kernel/perf/` + `ENERGY_READ` |
| **aarch64** | **PMUv3** + **AMU**；big.LITTLE 多簇 | PMUv3/AMU 近似；异构核 EAS 协同价值高（`40` §8） |
| **riscv64** | **SBI PMU** 扩展；平台碎片化 | SBI 抽象屏蔽差异；原型期 QEMU/virt 最小计数 |
| **loongarch64** | 自有 PMU CSR；未标准化 | 基础计数；原型期不追求精确 |
| **i386** | 无现代 PMU/RAPL；多数 legacy | **最小**：仅周期（若 TSC 可用）+ 降级，perf 子集可空缺 |

**收敛原则**：统一事件 ID + 每架构薄后端（对齐 `27` §6 / `59` §7.6）；允许「计数缺失」的架构以降级标记暴露（`kernel/perf/<event>: unsupported`），供门禁 fail-closed 识别（见 §3.3），而非伪造零值。

## 2. benchmark 套件（调度/网络/存储/中断 hot path）

### 2.1 总体定位：延伸 `19` meu-bench，分四大 hot path 家族

`19` §3.1 已定义 `meu-bench` 子项（`lat_syscall`/`lat_ipc`/`lat_ctx`/`lat_pagefault`/`lat_fork`/`bw_extent`/`cyc_lat`/`cap_check`）。本文在其上**补全四类子系统专项基准**，使每类 hot path 都有量化落点，并与既有专项文档的基准诉求一一衔接：

| hot path 家族 | meu-bench 子项（延伸 `19`） | 衔接的专项基准 | 测量对象 |
|---------------|----------------------------|----------------|----------|
| **调度** | `sc_pick`（EEVDF pick_next 延迟）、`sc_steal`（work-stealing 迁移成本）、`cyc_lat`（RT 尾延迟，承接 `28` R8 / `68` §8.2） | **`68 Sc` 调度基准** | EEVDF 虚拟截止期选程、跨核迁移、RT 尾延迟分布（同核/跨核）、CAP_RT 仲裁开销 |
| **网络** | `net_rx`/`net_tx`（device VMO 零拷贝吞吐）、`net_wake`（EventPort 唤醒延迟）、`net_irqpoll`（中断+轮询混合交叉点） | **`63 N` 网络基准** | 报文经 VMO 零拷贝 Rx/Tx 吞吐、socket 就绪 EventPort 唤醒、10G+ 中断合并 vs 轮询拐点（`63` §8 / `19` AP-2） |
| **存储** | 复用 `19` `lat_pagefault`/`bw_extent` | `19` §1.2.3/§1.2.5 | 文件冷/热缺页、COW、extent 读加密+校验和吞吐（各架构 crypto 加速差异，`19` §3.3） |
| **中断** | `irq_fwd`（Cap(IRQ n) → EventPort 唤醒延迟）、`irq_ack`（wait→ack 往返）、`irq_mask`（per-IRQ 屏蔽切换成本） | **`59` 中断基准** | 用户态驱动中断转发延迟、EOI 往返、中断+轮询混合拐点（`59` §5.3 / §9.3 议题 3） |

> **非缝合怪**：不另造一套与 `19` 平行的基准框架，而是把四类 hot path 落进同一 `meu-bench` 命名空间、同一 inspect/事件流输出（接 `12`）、同一 `.msys` 卷 CI 比对（接 `11` Phase K），与 `68`/`63`/`59` 的专项基准诉求**同构复用**而非重复定义。

### 2.2 调度 hot path 基准（与 `68 Sc` 衔接）

- **`sc_pick`**：测量 `68` §3.3 `pick_next_task` 跨三档（RT>deadline>fair）的选程延迟，重点量化 RT 严格优先级 bitmap O(1) 选择 vs EEVDF/EDF 红黑树查找的差异；与 `68` §8.2 结论 3 一致。
- **`sc_steal`**：测量 `68` §4.1 work-stealing 从最忙核偷任务的迁移成本（上下文切换 + 缓存冷启动），跨架构 NUMA 同节点优先的增益量化。
- **`cyc_lat`**：承接 `28` R8 / `68` §7.1 结论 6 的 RT 尾延迟门禁；在负载下测 EEVDF 与 RT 域的最坏情况尾延迟分布（µs/ms），与 `28` §2.1 cyclictest 等价锚点比对。

### 2.3 网络 hot path 基准（与 `63 N` 衔接）

- **`net_rx`/`net_tx`**：测量 `63` §4.3 device VMO 零拷贝路径吞吐（NIC DMA → device VMO → netstack → 应用 socket 接收 VMO），量化「数据通路留核」相对出核 IPC 搬运的优势（`19` AP-1）。
- **`net_wake`**：测量 `63` §8 网卡收包中断经 `59` Cap(IRQ n) EventPort 唤醒 netstack 的端到端唤醒延迟。
- **`net_irqpoll`**：定位 `63` §8 / `59` §5.3 中断合并+轮询混合的**量化拐点**——何种报文率下中断模式优于轮询（`59` §9.3 议题 3），为原型期 NIC 驱动配置提供数据。

### 2.4 中断 hot path 基准（与 `59` 衔接）

- **`irq_fwd`**：测量 `59` §5.3 用户态驱动 Cap(IRQ n) 中断转发延迟（硬件 IRQ → 内核派发 → EventPort 唤醒驱动线程），与 `59` §8.2 中 `10` §5-1「中断转发开销」待基准直接对应。
- **`irq_ack`**：测量 `IRQ_WAIT`→`IRQ_ACK`（EOI）往返（`59` §4.1 rights），量化 per-IRQ 应答开销（与全局关中断无关，仅 per-IRQ）。
- **`irq_mask`**：测量 `IRQ_MASK`（per-IRQ 屏蔽，非 `KERNEL_PRIV`）切换成本，验证「RT 线程只可 per-IRQ 屏蔽、不可全局静默」（`59` §4.3 / §6.2）的运行时开销边界。

## 3. 回归门禁（接入 `22` 测试验证策略；CI fail-closed）

### 3.1 接入 `22` 的 CI 门禁分级

`22` §3.2 定义 G0–G4 门禁。性能回归门禁的接入点：

| 门禁级 | 触发时机 | 性能回归动作 | 对应层 |
|--------|----------|--------------|--------|
| **G0 快速单测** | 每次 commit/PR | 仅单元级 microbench（如 `cap_check`/`sc_pick` 单次）随 `cargo test` 跑，作轻量回归嗅探 | L0 |
| **G1 跨服务集成** | merge 入主分支前 | 跑 `meu-bench` 子集（IPC/页缺/调度 pick），与 golden 比对 | L2 |
| **G2 全架构编译** | merge / nightly | 编译期检查 benchmark harness 跨架构可构建（不跑） | L4(编译) |
| **G3 系统级自举** | nightly / 里程碑 | 主架构 QEMU 跑 `meu-bench` 全量 + 绿光比对（`11` M0–M4） | L3 |
| **G4 矩阵 + fuzz + 性能** | release / periodic | **五架构矩阵 + 全量 `meu-bench` + 跨架构等价金标准比对 + 能耗协同基准（§4）** | L4 + §2 + `19` |

> 承接 `19` §3.1「门禁只观测、不阻塞构建（原型期），M2 之后逐步收紧」与 `22` §3.2「fuzz 常驻后台、不阻塞合并」——性能门禁在原型期同为**观测 + 告警**，随成熟度升级为**阻塞**。

### 3.2 阈值管理（绝对 + 相对，分架构基线）

- **golden 基线来源**：主架构（x86_64 起步，aarch64 次之，`11` M5）首次全量 `meu-bench` 结果作为 golden，落 `.msys` 卷（`11` Phase K）；跨架构功能等价金标准（`11` §5-5）延伸为「跨架构性能等价白名单」——同 benchmark 在不同架构的输出允许架构性差异（如 i386 无 AES-NI 致 `bw_extent` 低一个量级，`19` §3.3），但**禁止同架构同基准的意外回退**。
- **双阈值**：
  - **绝对阈值**：如 `IPC 同核往返 ≤ 500ns`（`19` §3.5）、`cyc_lat` RT 尾延迟红线（`28` R8）、`net_rx` 零拷贝吞吐下限——承接各专项文档的预算。
  - **相对阈值**：与 golden 比对，回归超相对幅度（如 IPC +20%、pager 冷缺页 +50%，承接 `19` §3.1）即告警/阻塞。
- **分架构基线**：主架构（x86_64/aarch64）全量绝对门禁；辅架构（riscv64/loongarch64/arm）仅比对自身历史 golden、不强制与主架构数值相等；i386 因纯 C + 无现代 PMU，仅跑可跑子集、缺失项标记 `unsupported`（见 §3.3）。

### 3.3 CI fail-closed 姿态（性能门禁的特殊 fail-closed）

> `22` §4.2 把 fail-closed 定义为「越权必失败、否定式断言默认红」。性能回归门禁的 fail-closed 是**对称但反向**的：正确性测试「默认拒绝非法」，性能门禁「默认拒绝无证据」——**缺失基线/无法度量 ≠ 通过，而是红**。

- **缺失基线即红**：某 benchmark 在目标架构无 golden（首次引入或未覆盖）→ 门禁**报红/阻塞**，而非静默绿。禁止「没数据就当没回归」。
- **不可度量即红**：perf counters 在该架构 `unsupported`（§1.4 i386）→ 相关基准标记为 `no-data`，门禁**不得**将其当 0 值通过；须显式降级该门禁为「人工复核」而非自动绿。
- **harness 失败即红**：`meu-bench` 自身崩溃/超时 → 门禁红，不跳过。
- **与 `22` fail-closed 同源**：安全测试「越权必失败」与性能门禁「无证据必红」都是「默认不信任、需显式证明」的姿态，二者共同构成 CI 的 fail-closed 双支柱（正确性 + 性能），呼应 `00` 的 fail-closed 总原则。

## 4. 能耗账本协同基准（per-Job 弱耦合能耗度量）

### 4.1 定位：能耗基准只做「信号」，不升级为「配额」

承接 `40` §1.3 / §4「能耗-Job 原型期弱耦合」已采纳结论——能耗**不进** `Job` 账本第六类资源、只作 task packing 输入。`27`/`40` 已把能耗读数（`ENERGY_READ`）与 `cpu_power_state` 只读结构（`40` §5.1）落地。本文补其**基准方法论**：

- **per-Job 弱耦合能耗度量**：`powerd`（`27` §3.3）读某 `Job` 的 `ENERGY_READ` 聚合 + CPU 配额余量（`04` §4.4），产出「聚核提示」；基准度量「聚核 vs 散核」下的 per-Job 能耗差异，验证 task packing 实际收益。
- **不引入新账本维度**：能耗基准**只读** `ENERGY_READ` 派生量，不写 `Job` 账本（强耦合留待 `04` §5 议题 6 裁决，`40` §4.3）。这保证本基准不触碰 `04` 账本对象，与纪律「不引入新内核原语」一致。

### 4.2 能耗协同基准项

| 基准（meu-bench 子项） | 测量对象 | 衔接 |
|------------------------|----------|------|
| `eng_pack` | 同 Job 任务聚核 vs 散核下的 per-package 能耗差（RAPL/AMU） | `40` §4.2 task packing 数据流、`27` §5.1 EAS |
| `eng_idle` | 空闲核进深 idle（NOHZ，`40` §5.3）后的 package 能耗下降 | `27` §3.2 idle 态、`40` §5.3 tickless |
| `eng_headroom` | thermal_headroom 压力下聚核/降频的能耗-温度联动 | `27` §4.2 热硬限、`40` §6 不变量 |
| `eng_arch` | 五架构 `ENERGY_READ` 可用性巡检（x86_64 完整 / aarch64 AMU / riscv64 SBI / loongarch64 基础 / i386 最小） | `40` §8 跨架构差异 |

> **不变量（从 `40` §6 继承）**：无论能耗基准如何，thermal 硬限始终为内核 TCB 无条件边界；能耗基准**不得**被用于突破热硬限，仅是调度器 EAS 子策略（task packing）的输入信号。

### 4.3 与 `27`/`40` 的协同边界

- 能耗基准**复用** `40` 的 `cpu_power_state` 只读结构与 `ENERGY_READ`/`THERMAL_READ` 同源可观测面，**不新建设备/能耗 right**（纪律）。
- 能耗基准结果经 `12` 消费（与 `40` §9.2 观测服务同源），落 `.msys` 卷供 CI 比对（接 `11` Phase K）。
- 强耦合（能耗硬配额）一旦由 `04` §5 议题 6 裁决升级，本基准可平滑扩展为「per-Job 能耗配额超限限流」度量，但原型期不预设。

## 5. 与否定式测试（`22`）互补的方法论

### 5.1 两种姿态的互补

`22` §1.1 约束 2 确立测试以**否定式**为主（越权必失败、revoke 后不可用）——这是**安全不变量**的证明。性能基准是**定量式/正向**的——证明「没变慢、没回退」。二者互补不重叠：

| 维度 | 否定式测试（`22`） | 性能基准（本文） |
|------|-------------------|------------------|
| 断言方向 | 「非法必失败」（EPERM/kill/不可用） | 「合法须达标」（延迟≤预算、吞吐≥下限、无回退） |
| 失败语义 | fail-closed（默认红） | fail-closed（无证据即红，§3.3） |
| 覆盖目标 | capability/安全/协议不变量 | hot path 性能、跨提交回归 |
| 与 `20` 形式化 | 运行时/黑盒证明（安全不可违背） | 经验性量化（性能可达），不证正确性 |

### 5.2 互补的方法论价值

- **安全回归 + 性能回归 = 双重 fail-closed**：`22` 保证「改坏了安全不漏过」，`74` 保证「改慢了性能不漏过」，二者在 CI（G1/G4）汇合，构成「既安全又不被悄悄劣化」的信心闭环。
- **绿光起步 + 基准基线同源**：`22` §5「绿光起步 + 累积断言」与本文 §3.2「golden 基线 + 相对阈值」是同一累积思想的两种体现——正确性靠断言累积、性能靠基线累积。
- **否定式防退化、定量式防劣化**：否定式测试防止「功能错误」，性能基准防止「功能对但变慢」（后者是混合内核出核化最易踩的隐性退化，`19` AP-1/AP-2）。

### 5.3 与 `20` 形式化的边界（互补不重叠）

- `22` §8 待决 7 已定：`20` 负责 rights 不可伪造/revoke 完整性的精化证明（白盒）；`22` 负责运行时/黑盒安全证明。
- 本文补：性能基准是**经验性量化**，与 `20` 的精化证明**正交**——`20` 证「调度核心算法正确」，`74` 证「调度核心实测不回退」。二者互补：形式化保证设计不可违背，基准保证实现未被悄悄劣化。跨越边界（如把「性能基准」误当「形式化证明」）是禁止的。

## 6. 五架构同源；与既有地基同构（不引入新内核原语）

### 6.1 同源论断

- **perf counters 抽象同源**：统一事件 ID + 每架构 PMU 薄后端（§1.2），与 `59` §7.6 中断统一 cap 面、`27` §6 电源统一原语、`28` §6 计时后端同源——差异**只**在薄后端，不侵蚀统一抽象。
- **benchmark harness 同源**：`meu-bench` 一次编写、五架构复用（承接 `22` §6.2「L0 单测五架构复用、仅后端薄层每架构验证」）；perf counters 缺失的架构以 `unsupported` 标记降级（§1.4），不分支化逻辑。
- **门禁同源**：回归门禁接入 `22` G0–G4 同一分级，不另起一套 CI 流。

### 6.2 与既有地基同构（零冲突、纯补齐）

- 复用 `12` 可观测权（`DBG_PROFILE`/`DBG_TRACE`）、inspect/事件流、`40` 的 `ENERGY_READ`/`THERMAL_READ` 同源只读抽象——**不新增 right bit、不新增内核对象**（纪律铁律）。
- 复用 `19` meu-bench 命名空间与热路径预算、复用 `11` Phase K / 绿光比对 / 跨架构金标准——**不新建基准框架**。
- 与 `68`/`63`/`59` 的专项基准诉求**同构对接**（§2），不重复定义。
- 能耗基准严格在 `27`/`40` 弱耦合结论内，**不升格**为 `Job` 账本硬配额（§4.1）。

### 6.3 不引入新内核原语的自我审查

| 候选「新原语」 | 处置 | 纪律符合性 |
|----------------|------|------------|
| perf counter 内核对象 / 新 right | **拒绝**；复用 `12` DBG_* + `40` ENERGY/THERMAL 同源 | ✅ 不新增 right/对象 |
| 能耗硬配额（第六类账本） | **拒绝**（原型期）；留 `04` §5 议题 6 | ✅ 不新增账本维度 |
| 独立 perf CI 流 | **拒绝**；接入 `22` G0–G4 | ✅ 不另起门禁 |
| 架构专属基准逻辑 | **拒绝**；统一抽象 + `unsupported` 降级 | ✅ 五架构同源 |
