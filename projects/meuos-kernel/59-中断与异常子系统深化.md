## 1. 概述与目标

### 1.1 背景：内核的「第一道门」为何是全局副作用的温床

中断与异常是 CPU 与内核交互的两条最根本的「异步/同步被迫切换」路径：

- **中断（interrupt）**：外部硬件（定时器、网卡、磁盘、串口）打断当前执行流，是**异步、可嵌套、可共享**的。
- **异常（exception / fault / trap）**：指令执行本身触发（缺页、除零、非法指令、断点、系统调用陷阱），是**同步、与当前线程强绑定**的。

在主流宏内核（尤其 Linux）里，这二者长期被实现为**全局副作用（global side-effect）**：

- 中断有全局的 `irq_desc[]` 数组、全局 `irq_disable()`、可无限共享的处理器链（`request_irq` 允许多个 handler 挂在同一 IRQ 上），关中断就是「让整个 CPU 安静」的全局动作。
- 异常被映射为全局信号（`signal`）机制，投递到进程、靠 `sigaction` 全局安装、可丢失、与线程交互脆弱（`04` §4.6 / `08` §3.4 已指出这是 POSIX 痛点）。

这种「全局副作用」模型与 MeuOS 的地基（万物皆对象、权限随句柄走、`00` §21「异常/中断派发」是内核 TCB 机制）天然张力。本文件要回答：**中断与异常在 MeuOS 里应被建模为一等 capability 对象，还是延续全局副作用？**

### 1.2 设计目标

| 编号 | 目标 | 说明 |
|------|------|------|
| G1 | **一等对象优先** | 中断/异常应作为可被命名、授权、撤销的内核对象（capability），而非全局隐式状态。 |
| G2 | **与 07 capability 模型同构** | `Cap(IRQ n)` 是 `07` §4.1「内核对象 = capability」的实例化，权限随句柄走、可审计、可派生、可 revoke。 |
| G3 | **抢占是中断的下游、不是独立机制** | 定时器中断只是「触发调度的事件源」；强制抢占经 `04` EEVDF `task_tick` 完成，不应另起一套全局抢占副作用（`04` §4.3 / `57-时钟与时间子系统.md` §3.4）。 |
| G4 | **异常上行 = 结构化取消** | 致命异常经 exception channel 上行监督者（`00` A9 / `04` §4.6），与 `46`/`47` 的 Job 树结构化取消同源，而非全局信号。 |
| G5 | **跨架构统一抽象 + 薄后端** | 五架构（x86_64/aarch64/riscv64/loongarch64/arm）中断控制器差异收敛到统一 cap 面 + 每架构薄后端（`00` §5-6「五架构一致性成本」同源）。 |
| G6 | **最小权限 + 最小 TCB** | 用户态驱动只收自身 `Cap(IRQ n)`；全局 IRQ mask 属内核态高危（深化 `29` D-T1 `KERNEL_PRIV`），绝不默认外流。 |

- **覆盖**：中断/异常的统一对象模型、capability 化、与调度/抢占/信号/结构化取消的接口、五架构控制器差异与统一抽象、Day 1 最小集。

## 2. 解构型思考：中断与异常应作为「一等对象」还是「全局副作用」

### 2.1 「应该是什么样」——从副作用模型推演对象模型

解构型方法先不问「Linux/Windows 怎么做的」，而是推演「一个以 capability 为一等公民的内核里，中断/异常本应是什么」：

1. 一个设备产生中断 = 「有个外部事件想被某个特定主体处理」。
2. 该事件**天然绑定一个对象**：产生它的硬件资源（即 `Cap(IRQ n)`，与 `Cap(MMIO range)`/`Cap(DMA window)` 同构于 `10` §2.4）。
3. 谁能处理它 = 「谁持有该对象的 capability」；持有即授权，不持有即内核快速失败——与 `07` §4.1「权限随句柄走」完全一致。
4. 它的生命周期 = 设备能力生命周期：设备拔出/驱动卸载 → 撤销锁序列回收（`10` 第三轮回写 C8）→ 中断对象随之 death。
5. 异常 = 「当前线程执行流被迫暂停，并带结构化原因」。它天然绑定「当前线程 + 一个 fault 类型 + 一个 PC」，最优表达是「向该线程所属 Job 的监督者投递一个结构化事件（CrashReport）」，即 `00` A9 的 exception channel。

推演结论：**在 capability 内核里，中断/异常「本应是」可命名、可授权、可撤销的对象，而非全局副作用**。全局副作用是宏内核「内核持有一切、进程共享一切」的历史债务，不是 capability 内核的应然。

### 2.2 全局副作用模型的根本缺陷（反面教材）

| 缺陷 | Linux 全局副作用表现 | 与 capability 模型冲突 |
|------|---------------------|------------------------|
| 全局性 | `local_irq_disable()` 让整颗 CPU 静默，是「影响所有主体」的全局动作 | 违反最小权限：一个驱动想静默自己设备的中断，却拿到了「静默全系统」的能力 |
| 共享堆 | `request_irq` 允许多个 handler 共享同一 IRQ（`IRQF_SHARED`），handler 链表全局可见 | 无法精确 revoke（撤一个驱动 ≠ 撤整条链）；confused deputy 温床 |
| 身份缺失 | ISR 不绑定「谁有权处理」，只绑定「一段全局注册的回调」 | 无 capability 边界，中断处理代码可触碰任意内核状态（T-A 爆炸半径大） |
| 信号全局性 | 信号是进程级全局投递、可丢失、`signal mask` 全局 | 与 `04` §4.6「无全局信号、事件对象唯一载体」冲突 |

> 这恰是 `29` D-T1 点出的「全局 IRQ mask 属内核态高危能力」在模型层的根因——全局副作用把「局部需求」和「全局权力」混为一谈。

### 2.3 一等对象模型的三个判据

一个「真·一等对象」须同时满足：

1. **可命名（identity）**：每个中断有稳定句柄（`interrupt` 对象 / `Cap(IRQ n)`），不是数组下标 + 全局锁。
2. **可授权（authorization）**：持有句柄才被允许注册 ISR / 应答 EOI，受 `GRANT` 约束跨进程转移（`07` §4.5）。
3. **可撤销（revocation）**：驱动死亡/设备拔出 → 句柄回收 → 中断不再投递，与 `10` C8 撤销锁序列同构。

MeuOS 的 `Cap(MMIO range)` 早已满足这三判据（`10` §2.4/§4.6）；`Cap(IRQ n)` 是其**对称补齐**——中断与 MMIO/DMA 同属「设备能力」家族，必须同一建模。

### 2.4 与「万物皆对象」的同构

`00` §21 收口「内核态只保留机制 + 唯一裁决点——…异常/中断派发…」，与 `07` §4.1「内核对象（kernel object）：…timer、事件…」一脉相承。本文件主张：**把 `interrupt` 显式列入 `07` 的内核对象清单，作为与 `timer`/`event` 同级的 capability 对象**。这与既有地基（GIC/APIC 控制器留核、`Cap(IRQ n)` 已提出、`KERNEL_PRIV` 已单列）**零冲突、纯补齐**。

## 3. 业界方案对比（多系统参照）

### 3.1 Linux（irq/vector/shared handler/softirq）

- **中断描述符全局数组** `irq_desc[NR_IRQS]`，每 IRQ 一串 `irqaction` handler（支持 `IRQF_SHARED`）。
- **向量（vector）层**：x86 用 `vector_irq[]` 映射 0–255 号中断门；`do_IRQ` → `handle_irq_event` 遍历共享链。
- **上下半部**：hardirq（关中断上下文）→ softirq/tasklet（开中断、仍可抢占）→ workqueue（进程上下文）。
- **关中断是全局**：`local_irq_save/restore` 是「本 CPU 静默」的粗粒度原语，无 per-IRQ 授权语义。
- 异常 → `do_page_fault`/`do_trap` → 信号投递（`send_signal` 到 `task_struct`）。

权威来源：Linux generic IRQ (core-api/genericirq)（见参考 6.1）、x86 APIC（6.2）。

### 3.2 Windows（IRQL / ISR / DPC）

- **IRQL（Interrupt Request Level）**：每 CPU 一个中断优先级阶梯（PASSIVE→APC→DISPATCH→DIRQL→HIGH），`KeRaiseIrql`/`KeLowerIrql` 控制当前处理器可接受的中断级别。这是「**抢占即中断优先级的同构**」——高 IRQL 代码天然屏蔽低 IRQL 中断，是一种**结构化、可推理的全局屏蔽**。
- **ISR（中断服务例程）**跑在设备 DIRQL（高 IRQL、关同级中断）；**DPC（Deferred Procedure Call）** 在 DISPATCH_LEVEL 延迟处理，把重活从 ISR 挪出。
- 异常走结构化异常（SEH），与 Mach 思路接近。

权威来源：Windows IRQL（6.3）、ISR/DPC（6.4）。

### 3.3 Fuchsia / Zircon（interrupt object + capability）

- **`zx_interrupt` 是内核对象**：由内核在资源发现时创建，句柄经 `zx_interrupt_create` 交给驱动；驱动 `zx_interrupt_wait()` 阻塞等中断，处理完 `zx_interrupt_ack()`（EOI）。
- **中断对象绑定虚拟中断号（Virq）**，由内核中断管理器路由硬件 IRQ → 对应 interrupt 对象；多个设备可共享同一物理 IRQ 但各有独立对象句柄（不共享 handler 链表）。
- **权限随句柄**：驱动只对自己设备的 interrupt 对象 wait/ack，无法触碰他人；revoke 即不再投递。
- 异常 → `zx_task_create_exception_channel` 上报（与 `00` A9 / `04` §4.6 同构）。

权威来源：Fuchsia interrupt objects（6.5）、Fuchsia interrupts（6.6）。

### 3.4 seL4（interrupt capability + IRQ IPC）

- 每个 IRQ 是一个 **capability**（CSpace 内的 IRQHandler cap），由 root task 在 `init` 时授予；未持 cap 的组件收不到该中断。
- 中断到达 → 内核向持有该 IRQ cap 的线程发 IPC（`seL4_IRQHandler_Ack` 应答）；无共享 handler 链。
- 形式化验证覆盖「无 cap 即不收中断」的不变量（`29` I7 句柄不可伪造同源）。

权威来源：seL4 manual（6.7）、seL4 interrupt tutorial（6.8）。

### 3.5 macOS（Mach exception model）

- **异常是 Mach 消息**：线程/任务/主机三级异常端口（`exception_port`），fault 触发时内核向对应端口发 Mach message（结构化、含 fault 类型/PC/线程），由异常处理服务决定杀/转内核外处理。
- 与 POSIX 信号解耦：signal 由 Libc 在 Mach 异常之上模拟（`08` §3.4 的「信号→异常 channel」即此思想）。
- 内核崩溃（panic）走独立机制，不进 Mach 异常端口。

权威来源：Apple Kernel Programming: Exceptions（6.9）。

### 3.6 Azure Sphere（capability 化中断 / secure world）

- Azure Sphere（MT3620，基于 Cortex-A7 + Pluton 安全子系统）把**中断按信任域划分**：安全世界（Pluton）与普通世界各有独立中断路由；应用核心只能通过受信任的运行时 API 间接响应设备中断，设备中断的「注册/应答」受平台安全策略约束，不可任意挂全局 handler。
- 这是「**中断作为受信任对象、应用层只见间接接口**」的高 assured 范本，与 MeuOS「用户态驱动只见自身 `Cap(IRQ n)`」同构。

权威来源：Azure Sphere documentation（6.10）、Azure Sphere architecture（6.11）。

### 3.7 取舍对比表

| 维度 | Linux | Windows | Fuchsia/Zircon | seL4 | macOS | **MeuOS（推荐）** |
|------|-------|---------|----------------|------|-------|-------------------|
| 中断模型 | 全局 `irq_desc`+共享链 | IRQL 优先级阶梯 | **interrupt 对象 + cap** | **IRQ capability + IPC** | Mach 异常消息 | **interrupt 对象（capability）** |
| 授权粒度 | 全局/共享 | DIRQL（CPU 级） | 句柄级 | cap 级 | 端口级 | **句柄级（Cap(IRQ n)）** |
| 全局关中断 | `local_irq_disable`（全局） | IRQL 升降（结构化全局） | 无用户态全局 | 无 | 无 | **仅 `KERNEL_PRIV` 内核态** |
| 异常 | 信号（全局、可丢失） | SEH | exception channel | — | **Mach 消息** | **exception channel（结构化）** |
| revoke | 难（共享链） | 卸载驱动 | 关句柄即停 | 撤 cap | 重置端口 | **撤销锁序列（C8 同构）** |
| TCB 面 | 大（全特权 handler） | 中 | 小 | 最小 | 中 | **最小（handler 在用户态驱动）** |

## 4. 中断作为 capability 对象（深化 `07`）

### 4.1 `Cap(IRQ n)` 与 MeuOS 能力模型同构

`Cap(IRQ n)` 是 `10` §2.4 已提出的设备能力四元组 `{MMIO, IRQ, DMA, IO port}` 中「IRQ」项的显式对象化。它应满足 `07` §4.1 的内核对象契约：

- **对象**：`interrupt` 内核对象，绑定「硬件 IRQ 号 / Virq / 路由目标」。
- **句柄即 capability**：驱动持有的 `Cap(IRQ n)` 句柄带 rights：
  - `IRQ_WAIT`（等待/消费该中断，等价于 Fuchsia `zx_interrupt_wait`）；
  - `IRQ_ACK`（应答 EOI，等价于 `zx_interrupt_ack`）；
  - `IRQ_MASK`（屏蔽/使能该中断，受约束的 per-IRQ 屏蔽，**非全局**）；
  - 不授 `IRQ_WAIT/ACK` 即内核不向该驱动转发——对齐 `10` §4.6「内核只向持该 cap 的进程转发」。

### 4.2 谁可注册 / 应答：mint 权威与受约束 mint（对齐 C8 / I5）

- **mint 权威**：capability 监视器（TCB）在 `09` Stage 4 从设备拓扑树直接 mint 出 `Cap(IRQ n)`（与 `Cap(MMIO)` 同序，`00` C8），**不存在「root 设备 cap 派生」环节**（对齐 `07` §4.1「无 root 逃生舱」）。
- **受约束 mint（防 confused deputy）**：devmgr（驱动管理器）持「受约束的 mint right（限定设备 cap 类、限定 Job 子树）」，请求监视器为驱动 mint 恰好其声明所需 IRQ（`29` I5：`rights_issued = rights_service ∩ rights_client_requested`）。这与 `07` §4.5 / `00` C2 受约束 mint 同源——杜绝「恶意驱动借 mint 拿到全局 IRQ 权」。
- **注册即授权**：「安装 ISR」=「持 `Cap(IRQ n)` 的驱动在用户态 `wait`，内核收到硬件 IRQ 后投喂该句柄持有者」。**没有全局 ISR 注册表**——这与 Linux `irqaction` 链表是根本区别。

### 4.3 全局 IRQ mask 与 `KERNEL_PRIV`（深化 `29` D-T1）

`29` D-T1 已采纳「全局 IRQ mask 属内核态高危能力」，并建模为 `KERNEL_PRIV`（`07` 第四轮回写）。本文件定稿其**精确边界**：

- **`KERNEL_PRIV` 覆盖的全局中断操作**（仅内核自持）：
  - `local_irq_save/restore` 级全局关中断（启动早期、临界原子区、panic 路径）；
  - 中断控制器（GIC distributor / APIC ICR）全局配置/广播；
  - 跨 IRQ 的优先级/路由重编程。
- **不在用户态暴露**：用户态驱动**只能** `IRQ_MASK`（per-IRQ 屏蔽自身中断），绝无 `KERNEL_PRIV`——否则受控用户态可制造全局 DoS / 抢占 TCB（`29` §5.2 第 2 点：「受控用户态可制造全局 DoS」）。
- 与 `DBG_POKE` 同构：`KERNEL_PRIV` 是「内核态生死线后门」，永不默认、显式授予、可审计、可 revoke（`07` 第四轮回写 D-T1）。

### 4.4 中断对象的生命周期与撤销（引用 C8 撤销锁序列）

中断对象的回收与 `10` 第三轮回写 C8 的「撤销锁序列」同构：

1. 屏蔽该 IRQ 转发（防 revoke 后还来中断）；
2. 冻结驱动进程（不再 wait）；
3. IOMMU 域对该驱动失效（截断在飞 DMA，若相关）；
4. revoke `Cap(IRQ n)` 句柄（从进程句柄表移除、记 dead）；
5. kill + 释放地址空间；
6. 仅全部完成后 fresh-mint 新 cap 并 spawn。

进程死亡自动回收（`10` C8 第二重保险）：持有者死亡 → 内核自动回收其全部句柄，旧 `Cap(IRQ n)` 已 reclaim，重启实例拿重新 mint 的 cap。这与 seL4「无 cap 即不收中断」不变量一致。

### 4.5 中断 vs 异常：两类「被中断」的统一与区分

| 类型 | 来源 | 绑定 | MeuOS 对象 | 路由目标 |
|------|------|------|-----------|----------|
| 硬件中断 | 外部设备 | 设备 `Cap(IRQ n)` | `interrupt` 对象 | 持 cap 的用户态驱动（或留核控制器） |
| 同步异常（fault/trap） | 当前线程执行流 | 当前线程 + PC | `CrashReport`（经 exception channel） | 该线程所属 Job 的监督者 |
| 系统调用（trap） | 当前线程 `syscall`/`int` | 当前线程 | IPC 端点（经 mkit 薄层 `08`） | 目标服务 |

三者都「被中断当前执行流」，但**对象模型不同**：中断是设备 capability 对象，异常是线程级结构化事件，syscall 是 IPC。`00` §21 把它们统称为「异常/中断派发」是派发层的统一，底层对象仍须分清晰——避免「异常也是全局中断」的混淆（Linux 把 syscall 当 trap 号、signal 当全局副作用，正是混淆之源）。

## 5. 与调度 / 抢占的关系（深化 `04` / `25` / `57`）

### 5.1 定时器中断 → 异步抢占（EEVDF task_tick，tickless）

- 定时器（留核，`10` §4.2）产生时钟中断 → 内核时钟中断处理 → 调 `04` §4.3 的 `task_tick` → EEVDF 记账 + 若当前线程用尽时间片则置「需重调度」标志。
- **抢占是中断的下游消费者，不是独立全局机制**：时钟中断只是「事件源」，真正的强制切换在 `task_tick` 内完成（`57` §3.4 红黑树取最早 deadline 驱动下一个唤醒点）。
- tickless（`57` §3.4）：无就绪任务时停周期 tick，靠下一次外设中断唤醒；这要求中断派发能直接驱动调度器下一个唤醒点——**中断与调度在同一派发链上**，而非两套并行副作用。

### 5.2 抢占作为 interrupt 派发的下游

- 关键澄清：**高优先级线程抢占低优先级线程，其触发源是定时器中断（或更高优先级设备中断经 `04` RT 运行队列）**，经统一的「中断 → 调度裁决点」完成。MeuOS **不引入** Linux 式 `preempt_disable()` 全局抢占屏蔽，而是用 per-IRQ 的 `IRQ_MASK`（§4.1）+ RT 域 `CAP_RT`（`07` bit 45）表达「谁能打断谁」——把 Windows IRQL 的「结构化优先级屏蔽」吸收为 capability 化的 per-object 屏蔽。

### 5.3 用户态驱动 IRQ 转发与调度唤醒（`10` + `05`）

- 用户态驱动的 `Cap(IRQ n)` 中断到达 → 内核转发 + 经 `05` EventPort（`EVFILT_IRQ` 类比 `EVFILT_READ`）唤醒对应驱动线程（`10` §5-1「中断转发开销」待基准）。
- 高频率设备（10G+ 网络）的中断风暴：用**中断合并 + 轮询混合**（见 `19-性能与可验证性.md` AP-2），合并后的「就绪事件」仍经 EventPort 投递——中断频率与调度唤醒次数解耦，避免 IPC 风暴拖垮调度器。

### 5.4 RT 与 `CAP_RT` / IRQL 借鉴

- Windows IRQL 的「DIRQL 屏蔽同级、高 IRQL 屏蔽低」是**可推理的嵌套屏蔽**；MeuOS 用 `CAP_RT`（`07` bit 45）门禁「进入 RT 域 / 提升优先级 / 绑定核 / deadline 调度」（`43-实时性与确定性调度.md`）。
- RT 设备中断（如音频/工业）若要亚微秒响应，可**留核快速路径**（`10` §4.2 准则）或经 `Cap(IRQ n)` + `CAP_RT` 高优先级线程处理；全局 IRQ mask 仍只属 `KERNEL_PRIV`，RT 线程不可借 RT 提权拿全局屏蔽（`29` D-T1 边界）。

## 6. 异常 / signal 与结构化取消（深化 `08` / `46` / `47`）

### 6.1 硬件 fault / 陷阱 → 统一故障入口 → CrashReport

- 三类崩溃（kernel Rust panic / kernel C fault / 用户态服务崩溃）汇聚到**同一结构化 `CrashReport`**（`12` §4.3 / §4.6），经 exception channel 上行监督者（`04` §4.6 / `00` A9）。
- 内核统一故障入口（`02` §4.5 `panic_handler` 单点）生成 `CrashReport{ faulting_pc, fault_type, stack_frames }`，与 `12` 的 `StackFrame` 归一化格式一致。

### 6.2 信号 → 异常 channel 映射（`08` §3.4）

- Linux 信号不对应内部真实异步中断模型；兼容层把**子集信号**映射为内部 exception channel 事件：`SIGSEGV` → 内存故障异常经 channel 回投为信号；`SIGINT` → 控制台中断事件转信号（`08` §3.4）。
- 原生程序不碰 signal（`04` §4.6）：保留 `Terminate`/`Kill`/`Interrupt` 三项最小类信号（`Kill` 不可屏蔽，对齐 SIGKILL），语义清晰、不可被用户态吞掉关键控制流。

### 6.3 结构化取消：Job 树取消沿异常上行传播（`46`/`47`）

- `46-进程管理-方案A.md` 主张「进程结构化并发唯一范式」：用户会话注销 = Job 树取消，异常沿树上行、无僵尸/孤儿。
- `47-进程管理-方案B.md`（Day 1 主线）同样把 Job 树作为取消域；致命异常经 exception channel 上行到监督者后，监督者据策略在 Job 树内做**结构化取消 + 重启/升级**（`04` §4.5）。
- 本文件定稿：**异常上行 = 结构化取消的触发源**，二者同一不变量（异常不丢失、沿 Job 树传播、监督者统一决策），与 `56` §2「结构化取消/异常上行（A9）」一致。

### 6.4 调试器 vs 监督者对异常的多播仲裁（`C9-B`）

- 异常事件内核一次性生成、**copy 语义多播**给监督者（持 `DBG_CRASHDUMP` 默认订阅，`07` bit 17）+ 持权调试器（持 `DBG_ATTACH` `07` bit 16，仅收副本）。
- 监督者 kill/restart 决策**不可被抑制**；调试器可请求**有界崩溃冻结窗口**（默认 30–120s，超时/detach 自动释放），绝不可永久接管（`04` §4.6 / `17` C9-B / `05` §4.2）。
- 本文件补充：异常多播的「源」就是 §2.4 / §4.5 的统一故障入口，中断对象与异常对象在派发层同源、在授权层各自独立（调试器不因此获得 `Cap(IRQ n)`）。

## 7. 跨架构（五架构）中断控制器差异与统一抽象

MeuOS 目标五架构（`22` §8：x86_64/aarch64/riscv64/loongarch64/arm，均 64 位有 Rust 裸机 target，`02` §2.3）。中断控制器差异是「五架构一致性成本」（`00` §5-6）的核心来源之一，须收敛到**统一中断 cap 面 + 每架构薄后端**。

### 7.1 x86_64：PIC(8259A) / APIC(IOAPIC + LAPIC)

- 传统 8259A 双片级联（IRQ 0–15，共享严重、不可 per-IRQ 路由）；现代用 **APIC**：`IOAPIC` 做中断路由重映射（vector → LAPIC），`LAPIC` 每核收中断、做 per-CPU 优先级（`TPR`/`PPR`）。
- **统一性要点**：物理 IRQ 号经 IOAPIC 重映射为「per-CPU vector」，MeuOS 的 `Cap(IRQ n)` 指向**重映射后的 Virq**（对齐 Fuchsia Virq 思路），屏蔽/应答操作经 LAPIC/IOAPIC MMIO，属 `KERNEL_PRIV` 控制器面。

### 7.2 aarch64：GICv2 / GICv3 / GICv4

- **GICv2**：`GICD`（distributor，全局路由）+ `GICC`（CPU 接口，每核）。
- **GICv3/v4**：`GICD` + `GICR`（每核 redistributor）+ `ITS`（消息中断 MSI 路由）；v4 增加虚拟中断（vLPI）支持。
- **统一性要点**：GIC 的 `interrupt ID`（SPI/PPI/SGI）天然就是「全局稳定的 IRQ 身份」，直接映射为 `Cap(IRQ n)` 的 `n`；per-IRQ 使能/优先级/路由是 GICD 寄存器写，归 `KERNEL_PRIV` 控制器面（留核）；驱动只 wait/ack 自己的 interrupt 对象。

### 7.3 riscv64：PLIC / APLIC + IMSIC（中断控制器）

- **PLIC（Platform-Level Interrupt Controller）**：经典 RISC-V 中断控制器，把多设备 IRQ 聚合并按阈值投到 hart 的 `sip.seip`；优先级粗粒度。
- **APLIC（Advanced PLIC）**：支持 MSI 化中断、per-hart 路由、可注入。
- **IMSIC（Incoming MSI Controller）**：配合 APLIC 实现「消息中断」（MSI），每个 hart 一个 IMSIC，中断以写内存方式送达。
- **统一性要点**：PLIC/APLIC 的 `source ID` 即 `Cap(IRQ n)` 的 `n`；IMSIC/MSI 使中断「像一次内存写入」——与 Fuchsia「中断对象 wait」模型天然契合（写内存触发对象就绪）。`sip/sie` 的全局使能位属 `KERNEL_PRIV`。

### 7.4 loongarch64：LIOINTC / EIOINTC / HTVEC / PCH-PIC / PCH-MSI

- LoongArch 中断呈**多级级联**：`LIOINTC`（CPU 内 legacy/IO 中断）→ `EIOINTC`（扩展中断，每 CPU）→ `HTVEC`（HyperTransport 向量）→ `PCH-PIC`（桥片 PIC）+ `PCH-MSI`（桥片 MSI）。
- **统一性要点**：多级级联使「物理 IRQ 号」需经多层映射；MeuOS 的 `Cap(IRQ n)` 指向**最终归一化后的设备源号**（类比 x86 IOAPIC 重映射），驱动不可见级联细节。控制器全局配置（EIOINTC/HTVEC 路由）属 `KERNEL_PRIV` 留核面。

### 7.5 arm（32-bit）：GICv1/v2 / VIC

- 32 位 ARM 传统用 **VIC（Vectored Interrupt Controller）** 或 **GICv1/v2**；VIC 支持硬件向量跳转（直接跳 ISR 入口），GICv2 与 aarch64 同构。
- **统一性要点**：GICv2 路径与 aarch64 共享薄后端；VIC 的向量跳转在 MeuOS 里只用于「早期启动到 capability 世界就绪前」的生死相关中断（类比 `09` Stage 1 早期串口直写），进入用户态后统一走 `Cap(IRQ n)` 对象模型。

### 7.6 统一中断抽象层（统一 cap 面 + 每架构薄后端）

```
              ┌──────────────── 统一中断 cap 面（架构无关） ────────────────┐
              │  interrupt 对象 = capability                                 │
              │  Cap(IRQ n): wait / ack / mask(per-IRQ)                      │
              │  内核中断派发器：硬件 IRQ → 路由 → 投喂 Cap(IRQ n) 持有者   │
              │  全局配置 / 广播 / 关中断 = KERNEL_PRIV（仅内核）           │
              └───────────────────────────┬────────────────────────────────┘
                                           │ 每架构薄后端（仅寄存器映射差异）
        ┌──────────────┬──────────────┬──────────────┬──────────────┬──────────────┐
       x86_64 APIC   aarch64 GIC    riscv64 PLIC/   loongarch64    arm GICv2/
       (IOAPIC+      (v2/v3/v4,     APLIC+IMSIC     LIOINTC/      VIC
        LAPIC)        GICD/GICR)                     EIOINTC/...
```

- **统一 cap 面**：`interrupt` 对象的语义（wait/ack/mask/revoke）五架构一致；驱动代码与架构无关（与 `22` §8「TCB 单测五架构复用、仅后端薄层每架构验证」同源）。
- **薄后端职责**：仅做「物理 IRQ 号 ↔ `Cap(IRQ n)` 的 `n`」映射、控制器初始化、EOI 寄存器写；不含任何策略（策略在用户态驱动 + 调度器）。
- 早期启动（cap 世界未起）允许控制器直控（`KERNEL_PRIV`），一旦 `09` Stage 4 监视器 mint 出 `Cap(IRQ n)`，常态路径即走对象模型——与 `09` 早期串口「Stage 1 直写 → Stage 4 mint → Stage 5 交用户态」的阶段演进同构（`09` C8 回写）。

### 7.7 五架构一致性成本（关联 `00` §5-6）

- 差异主要集中在「控制器寄存器布局 + IRQ 号映射」，统一抽象把差异关进薄后端，**不侵蚀**统一的 `interrupt` capability 模型（对齐 `00` §5-6「统一抽象 + 每架构薄后端」）。
- 待量化：每架构薄后端的代码量与验证成本（i386/arm 32 位纯 C 退化面，关联 `00` C6 / `29` D-T6，须以 fuzz 补偿）。

## 8. Day 1 最小集

### 8.1 内核态保留的中断面（生死相关，留核）

| 中断源 | 留核原因 | 对应 cap |
|--------|----------|----------|
| 中断控制器（GIC/APIC/PLIC/…） | 参与调度与生死，`10` §4.2 | `KERNEL_PRIV`（全局配置） |
| 定时器 | 驱动调度 `task_tick`，`10` §4.2 / `57` | 内核内部，非 cap 面 |
| 看门狗 | 生死相关，`10` §4.2 | `KERNEL_PRIV` |
| 早期串口（Stage 1） | 生死相关快速路径，`09` C8 | 临时直写 → Stage 5 交用户态 console 服务 |

### 8.2 用户态驱动可注册的中断对象最小集

- **原型期首批**（`10` 附录 A）：virtio-blk、virtio-net、virtio-console、UART 各持自身 `Cap(IRQ n)`；中断处理在用户态驱动内 `wait/ack`，经 `05` EventPort 唤醒。
- **最小操作集**：`IRQ_WAIT` / `IRQ_ACK` / `IRQ_MASK`（per-IRQ）；**无全局关中断**。
- 高频设备（virtio-net 10G+）：中断合并 + 轮询混合（`19` AP-2），合并后 EventPort 投递。

### 8.3 异常 / 信号最小集

- **CrashReport + exception channel**（`12`）：三类崩溃统一上行，监督者按策略 kill/dump/restart。
- **三类最小信号**（`04` §4.6）：`Terminate`/`Kill`/`Interrupt`，原生程序唯一信号面；旧二进制经 `08` 翻译。
- **调试多播仲裁**（`C9-B`）：监督者默认 `DBG_CRASHDUMP` 订阅，调试器有界冻结。

### 8.4 与 M0–M1 里程碑依赖

- M0（启动到用户态 init）：需中断控制器 + 定时器留核（`08.1`）+ 早期串口（`09` C8）。
- M1（libc hello 运行退出 0）：需异常/信号最小集（CrashReport + `Terminate`）+ 用户态驱动 `Cap(IRQ n)`（UART 控制台）。
- 依赖链：启动（`09` Stage 4 mint 设备 cap） → 驱动（`10` 双轨） → 中断对象模型 → 监督者异常上行（`04`/`12`）。

## 9. MeuOS 推荐（综合定稿）

### 9.1 核心推荐：中断 / 异常作为一等 capability 对象

1. **中断 = `interrupt` 内核对象，作为 capability 一等公民**（解构型结论 §2）：补 `07` §4.1 内核对象清单，与 `timer`/`event` 同级；`Cap(IRQ n)` 与 `Cap(MMIO)`/`Cap(DMA)` 同属设备能力家族、同一建模（`10` §2.4 已提、本文件补全授予/应答/撤销语义）。
2. **异常 = 线程级结构化事件（CrashReport），经 exception channel 上行**（深化 `04`/`12`/`08`）：不引入全局信号副作用；信号经异常 channel 翻译（`08` §3.4）；结构化取消沿 Job 树传播（`46`/`47`）。
3. **抢占是中断的下游消费者**：定时器中断 → `task_tick` → EEVDF 抢占（`04`/`57`），不另起 `preempt_disable` 全局屏蔽；per-IRQ 屏蔽用 `IRQ_MASK`，结构化优先级借鉴 Windows IRQL、capability 化。
4. **全局 IRQ 操作 = `KERNEL_PRIV`，绝不默认外流**（深化 `29` D-T1）：用户态只见 per-IRQ 屏蔽，绝无全局关中断权。
5. **五架构统一 cap 面 + 薄后端**（§7）：`interrupt` 对象语义五架构一致，控制器差异关进每架构薄后端，不侵蚀统一模型。

### 9.2 与既有地基的对齐（零冲突、纯补齐）

- 与 `00` A9（exception channel→监督者）、§21（异常/中断派发=TCB 机制）完全一致。
- 与 `00` C8（设备能力 mint 时序）、`10` §4.6（驱动最小权限）完全同构——`Cap(IRQ n)` 复用同一撤销锁序列。
- 与 `07` capability 模型（句柄即 cap、受约束 mint、revoke、KERNEL_PRIV）完全同构。
- 与 `29` D-T1（全局 IRQ mask 高危）定稿边界、不新增 right（`KERNEL_PRIV` 已单列）。
- 与 `04`/`12`/`08` 异常上行、信号翻译、CrashReport 一致，仅把「中断」侧显式对象化。
- 与 `19` AP-2（中断合并+轮询）、`57`（tickless 调度）接口一致。

### 9.3 开放议题 / 待回写点（修订式追加，不改动 01–58）

1. **`interrupt` 对象是否进 `07` §4.1 内核对象清单 + rights 位图新增 `IRQ_WAIT`/`IRQ_ACK`/`IRQ_MASK`**（建议 bit 48+ 预留区，与 `SCENE_SESSION` 同区，不挤占 0–47）：待 `07` 定稿时据 `38` §3.1 统一表冻结，本文件不预占 bit 0–47。**— 已裁决·闭环（`07` §4.1 第八轮冻结分配表）：`IRQ_WAIT`=bit52、`IRQ_ACK`=bit53、`IRQ_MASK`=bit54，三者拆分因语义独立（WAIT/ACK/MASK），均为 per-IRQ deny，进 48+ 预留区不挤占 0–47；`interrupt` 对象同步进 `07` §4.1 内核对象清单。**
2. **per-IRQ 屏蔽与 RT（`CAP_RT`）的交互语义**：`IRQ_MASK` 与 `CAP_RT` 如何共同决定「谁可打断谁」，待 `43` 实时调度细化。
3. **中断合并 + 轮询的量化基准**（继承 `10` §5-1 / `19` AP-2）：何种频率下中断模式优于轮询模式，需原型基准。
4. **i386/arm 32 位纯 C 中断薄后端的验证降级**（关联 `00` C6 / `29` D-T6）：以 fuzz 补偿内存安全退化，待 `22` L4 收敛。
5. **虚拟化场景的中断直通**（关联 `26`）：guest 经 VMM 拿 `Cap(IRQ n)` + device VMO 直通，中断对象模型在 guest 内如何投影（vCPU 注入），待 `26` 细化。
