# 04 - 进程与调度

> MeuOS 自研内核设计 / 规划文档（子领域：进程模型与调度器）
> 工作树：`kernel-plan` / 分支：`worktree-kernel-plan`
> 角色：调研员（k-proc）。本文只做调研与设计建议，不落地实现代码。

---

## 1. 概述与目标

### 1.1 背景

MeuOS 内核定位为「外部兼容 Linux ABI（经兼容层对接），内部自主设计」。进程与调度子系统是内核的「骨架」：它决定

- 一个新程序如何被创建（fork+exec 还是 spawn）；
- 几十到几千个执行流如何在有限 CPU 上分配时间；
- 资源（CPU、内存、句柄、IO 带宽）如何被计量与限制；
- 进程死亡 / 崩溃后由谁负责清理与重启；
- 进程之间如何被「打断」（信号 / 事件）。

这五个问题彼此耦合。本文件的目标是为 MeuOS 给出一套**自洽、可原型化、与 Rust/Go 运行时天然对齐**的进程与调度设计基线，并明确原型期（prototype）最小集。

### 1.2 设计目标

| 编号 | 目标 | 说明 |
|------|------|------|
| G1 | **spawn 优先** | Day 1 提供原生 `spawn` 原语；fork 仅作为兼容层（Linux ABI）的可选、受限实现，不进入原生编程模型。 |
| G2 | **资源账本 Day 1 内置** | 每个进程/进程组诞生即带配额（CPU、内存、句柄数、IO），而非 cgroups 那样事后挂接。 |
| G3 | **内核内建监督** | 进程监督（类似 launchd）是内核 + 一级用户态服务的能力，免外部 `init`/`systemd`。 |
| G4 | **能力显性传递** | 地址空间、句柄、资源不再是「fork 隐式全拷贝」，而是 spawn 时显式声明。 |
| G5 | **运行时友好** | 线程与协程（goroutine / async task）到内核调度实体的映射要廉价、可 M:N。 |
| G6 | **信号精简** | 从零重新设计通知机制，去掉 POSIX 信号的历史包袱，但保留兼容层语义。 |

### 1.3 范围

覆盖：进程模型、spawn 语义、调度策略（公平 / RT / 多核均衡）、资源账本、生命周期与监督、信号模型、与 Rust/Go 运行时对齐、原型最小集。

不涉及（见其他子领域文档）：内存分配器实现（03-内存管理）、IPC 原语（05-IPC机制）、安全能力模型细节（07-安全模型）、Linux 兼容层映射（08-Linux兼容层）。

## 2. 设计约束与上下文

### 2.1 技术基线（来自 IMA 知识库「MeuOS / 01-总体架构」）

- **混合内核**：核心在内核态，部分服务在用户态；调度器本身在内核态，但监督/服务编排在用户态。
- **Rust + C 混合**：调度器热点路径与进程对象可用 Rust 编写（内存安全），与 C 互操作通过 FFI。
- **capability-based 安全（Day 1 唯一模型）**：进程持有的不是 uid/gid，而是一组不可伪造的能力令牌；能力模型是 spawn 时句柄传递的基础。
- **Linux ABI 兼容层**：真实生态二进制经兼容层运行，所以 `fork`/`clone`/`signal`/`wait` 等必须可映射，但其语义由兼容层翻译，不污染原生模型。

### 2.2 硬约束

- C1：原型期目标架构至少覆盖 x86_64 + aarch64（Kit 已完成 5 架构工具链）。
- C2：调度器必须在多核（SMP）下正确且不过度复杂。
- C3：进程对象与账本必须可被 capability 系统校验（见 07-安全模型）。
- C4：原型期不追求与 Linux 完全同性能的 fork；兼容层 fork 可走 COW 近似，但原生路径不走 fork。

### 2.3 与相邻子系统的接口

| 接口方 | 关键契约 |
|--------|----------|
| 03-内存管理 | spawn 需要 `vmspace` 创建 / 映射；资源账本中的内存配额由 MM 强制执行。 |
| 05-IPC机制 | 句柄（handle）是进程间传递内核对象引用的统一载体；spawn 的句柄继承表依赖 IPC 句柄模型。 |
| 07-安全模型 | 每个进程绑定一组 capability；spawn 时显式传入/派生能力，监督域本身受 capability 约束。 |
| 08-Linux兼容层 | `fork`/`clone`/`vfork`/`posix_spawn`/`execve`/`wait4`/`kill` 在此翻译为原生 spawn/信号原语。 |

## 3. 业界方案对比

### 3.1 候选方案概览

#### A. Linux（fork + exec + CFS/EEVDF + cgroups + signal）

- **进程创建**：`fork()` 复制地址空间（COW），再 `execve()` 替换映像；`clone()` 通过 flags 细粒度共享（与 Plan 9 的 `rfork` 互相影响）。现代运行时普遍转向 `posix_spawn`（glibc 在多数平台已用 `clone` 而非真 fork 实现 spawn）。
- **调度**：`SCHED_NORMAL/SCHED_BATCH/SCHED_IDLE` 由 CFS 实现（基于红黑树 + `vruntime`，理想多任务 CPU 模型，纳秒级记账）；`SCHED_FIFO/_RR` 由 `sched/rt.c` 用 100 个 RT 优先级运行队列实现；`SCHED_DEADLINE` 用 EDF。近期主线正从 CFS 迁移到 **EEVDF**（Earliest Eligible Virtual Deadline First）。调度类（scheduling classes）以 `sched_class` 钩子层次化扩展，CFS/RT/Deadline 各自实现 `enqueue_task`/`pick_next_task`/`task_tick` 等。
- **CPU 公平分组**：`CONFIG_FAIR_GROUP_SCHED` + cgroups（`cpu.shares`）实现「先对用户公平，再对用户内任务公平」。
- **资源账本**：**cgroups v2** 是事后挂接的分层资源控制器（cpu、memory、pids、io 等），非进程固有属性；容器/系统d 在启动后才把进程移入 cgroup。
- **监督**：**无内建**；依赖用户态 `init`/`systemd`（或 macOS 的 launchd）。内核只提供 `wait*`/`ptrace`/`prctl`。
- **信号**：POSIX 信号（1–31 标准 + 实时信号），异步、可丢失、与线程交互复杂（`signal mask`/`sigaction`/`tgkill`），是长期被诟病的复杂度来源。

权威来源：Linux 内核文档 CFS（见参考 6.1）、EEVDF（6.2）、cgroups v2（6.3）、signal(7)（6.4）。

#### B. Zircon / Fuchsia（job/process/thread + handle + 用户态程序加载）

- **进程创建**：**无 fork**。进程由 `zx_process_create()` 在给定 **job** 下创建，得到空地址空间（一个根 VMAR），再由用户态 loader 把 VMO（虚拟内存对象）映射进 VMAR、准备句柄表、`zx_process_start()` 启动。这是教科书式的 **spawn**：地址空间、句柄、资源都从零显式构建。
- **进程/线程/作业层级**：`Process` 持有线程集合 + 根 VMAR + 句柄表；`Thread` 绑定到某个 Process；`Job` 是进程/子作业的容器，负责**资源限额（resource limits）**与**生命周期控制（lifetime control）**——父 job 终止会杀死其下进程。创建进程**必须持有 job handle**，没有 job handle 的进程无法自行创建子进程（除非经 Component Framework）。
- **调度**：Zircon 提供固定优先级 + 公平共享（fair scheduling）的线程调度，优先级 0–31，支持 `SCHEDULER_FLAG_*`；公平权重通过 `zx_thread_set_priority`/`zx_object_set_property`（`ZX_PROP_NAME` 等）与 job 级资源控制配合。调度器在内核态，多核上做全局/每核队列均衡。
- **资源账本**：**job 天然承担限额与权限**，是「Day 1 内置账本」的范本——限额是 job 的属性，而非事后附加。
- **信号/通知**：无 POSIX 信号；进程间通知通过 **port / channel / event** 等内核对象（与 IPC 统一），异常（exception）经 exception channel 上报到监督者。

权威来源：Fuchsia Processes（6.5）、Jobs（6.6）、Zircon kernel concepts（6.7）。

#### C. Plan 9（rfork + 每进程命名空间 + note）

- **进程创建**：`fork` 是**唯一**创建方式，但 `rfork(flags)` 用标志位选择**哪些资源被子进程共享、哪些被重置**（RFMEM 共享地址空间、RFPROC 建新进程、RFNAMEG 建新名字空间、RFNOTEG 脱离 note group 等）。这比 Linux `clone` 更早、更直接地把「共享什么」显式化；Linux `clone`（1996）受其影响。
- **命名空间**：每进程独立的文件系统/环境变量/文件描述符命名空间（`RFNAMEG`/`RFENVG`/`RFFDG`），这是容器式隔离的思想源头。
- **通知/信号**：用 **note**（类似信号但更简单，分 note group），由 `renegotiate`/note handler 处理；没有 POSIX 那套 mask/action 组合爆炸。
- **调度**：传统分时 + 优先级（`acid`/`prog` 调试器可见），并非现代 CFS 级精细，但其重点是「进程是资源容器的细粒度共享」而非「公平调度算法」。

权威来源：Plan 9 fork(2)（6.8）、rfork(3)（6.9）、Plan 9 from Bell Labs（6.10）。

#### D. launchd（macOS/iOS 内核外监督范式，作为监督子模块参照）

- 统一 `init` + 服务管理守护进程，取代 BSD `init` 与 `SystemStarter`；声明式 `plist` 描述服务（`KeepAlive`、`RunAtLoad`、`OnDemand` 按需启动、退出后按条件重启）。
- 内核只负责把 launchd 作为首个用户态进程拉起，之后**进程监督完全在用户态**由 launchd 用 `kqueue`/POSIX Spawn 等机制实现。这是「内核内建监督」的**反面教材**——监督本质是用户态策略，但由内核保证首进程的可靠启动与生命周期挂钩。

权威来源：launchd（Wikipedia/HandWiki 6.11）、Apple 开源 launchd（6.12）。

#### E. 运行时视角：Go GMP 与 Rust async（M:N 调度需求）

- **Go**：Goroutine 是用户态轻量线程，runtime 用 **G（goroutine）/M（OS 线程）/P（处理器上下文）** 的 M:N 调度，把海量 G 多路复用到少量 M 上；支持 work-stealing、基于信号的异步抢占、syscall handoff、netpoller。对内核的要求是：**内核线程创建/切换廉价、提供足够多的 OS 线程、提供公平调度**，runtime 自己处理 G 级调度。
- **Rust**：无内建运行时；`async/await` 编译为 `Future` 状态机，由 `tokio`/`smol` 等运行时在少量 OS 线程上做 M:N 调度（thread-per-core 或 work-stealing）。对内核的要求同样是「OS 线程廉价、调度公平」。
- 启示：内核只需提供**廉价的内核线程（kthread/lwp）**与**公平 + 可选固定优先级**两层调度；协程/任务层交给运行时。内核**不应**试图直接调度 goroutine/async-task——那是重复造轮子。

权威来源：Go GMP（6.13）、Go 官方并发文档（6.14）、Rust async book（6.15）。

### 3.2 取舍对比表

| 维度 | Linux | Zircon/Fuchsia | Plan 9 | MeuOS 取舍 |
|------|-------|----------------|--------|------------|
| 进程创建原语 | fork+exec + clone + posix_spawn | spawn-only（process_create + start） | rfork（唯一，flags 选共享） | **原生 spawn**，fork 仅兼容层 |
| 地址空间传递 | fork COW 隐式拷贝 | 显式 VMAR/VMO 构建 | rfork flags 显式选共享 | **显式构建（对齐 Zircon）** |
| 句柄/资源传递 | fd 继承表（execve 时按 FD_CLOEXEC） | 句柄表 + job 限额 | fd 表 + 命名空间 | **句柄表 + 显式继承集（对齐 Zircon）** |
| 调度公平算法 | CFS → EEVDF，红黑树 vruntime | 固定优先级 + 公平权重，0–31 | 分时 + 优先级 | **EEVDF 类公平 + RT 固定优先级**（吸收 Linux） |
| 资源账本 | cgroups v2，事后挂接 | job 限额，Day 1 内建 | 无统一账本 | **Day 1 内建（对齐 Zircon job）** |
| 进程监督 | 无（靠 systemd） | 无内建，Component Framework 用户态 | 无 | **内核拉起监督服务 + 用户态监督策略（融合 launchd 思想）** |
| 通知/信号 | POSIX 信号（复杂） | port/channel/event（与 IPC 统一） | note（简化） | **简化事件通知（吸收 Plan9 note + Zircon channel）**，signal 仅兼容层 |
| 多核均衡 | load balancing（sched/fair 重做） | per-CPU 队列 + 全局迁移 | 弱 | **每核运行队列 + work-stealing/负载均衡** |
| 安全模型 | uid/gid + capability + seccomp | handle=capability（能力即句柄） | 无现代能力 | **capability-based Day1（对齐 07-安全模型）** |

### 3.3 关键结论（从对比中提炼）

1. **spawn 优于 fork+exec**：Zircon 与 Linux 社区自身的 `posix_spawn` 趋势、2025–2026 年 Linux 内核「spawn templates」提案（Li Chen 提出，意图绕开 fork+exec 数十年包袱）都印证——原生 spawn 更现代、更安全、与 COW/大页/多核更友好。MeuOS 选 spawn 是顺势而为，非标新立异。
2. **资源账本必须内建**：cgroups 的「事后挂接」是 Linux 历史债务；Zircon 的 job 限额模型证明「限额即容器属性」可被干净实现。MeuOS 把账本放进进程/作业对象 Day 1。
3. **监督应在内核「启动」而非「实现」于内核**：launchd 模式表明监督策略是用户态的，但内核要保证首监督进程可靠、且作业生命周期与监督挂钩（吸收 Zircon job 的 lifetime control）。
4. **调度算法复用成熟方案**：EEVDF（Linux 主线最新）比 CFS 更简单且在尾延迟上更优；RT 用固定优先级（POSIX SCHED_FIFO/RR 语义）。不必自研公平算法。
5. **信号应从零简化**：POSIX 信号的异步/可丢失/mask 组合是公认痛点；用「受能力约束的事件对象 + 可选 note 语义」替代，兼容层再模拟 signal。

## 4. MeuOS 选型建议

### 4.1 进程对象模型（对齐 Zircon + capability）

```
┌─────────────────────────────────────────┐
│  Job (监督/账本/生命周期单元)            │
│  - 资源配额 (cpu/mem/handles/io)         │
│  - 子 Job / 子 Process 树                │
│  - 监督策略 (重启/终止传播)              │
│  - 能力边界 (capability set)             │
└───────────────┬─────────────────────────┘
                │ 持有 job handle 才能 spawn
┌───────────────▼─────────────────────────┐
│  Process                                  │
│  - 根 VMAR (地址空间)                    │
│  - 句柄表 (handle table)                 │
│  - 线程集合 (threads)                    │
│  - 派生自父的能力集                       │
└───────────────┬─────────────────────────┘
                │
┌───────────────▼─────────────────────────┐
│  Thread (内核调度实体)                   │
│  - 寄存器上下文 / 内核栈                 │
│  - 隶属 Process                          │
│  - 调度优先级 + 公平权重                 │
└─────────────────────────────────────────┘
```

- **Job 是资源与生命周期的一等公民**：配额、能力边界、监督策略都挂在 Job 上；Process 是 Job 的叶子。这与 Zircon 一致，也自然承接「资源账本 Day 1」。
- **Process 不直接持有「创建子进程」权**：必须持有某 Job 的 handle 才能 spawn，继承该 Job 的配额与能力边界（除非显式收窄）。这天然实现最小特权。
- **Thread 是内核调度实体**；一个 Process 可有多个 Thread。内核只调度 Thread，不调度用户态协程。

### 4.2 spawn 原语语义（G1/G4）

设计原生 `meu_spawn()`（兼容层把 `posix_spawn`/`execve`/`fork` 映射其上）：

**输入（全部显式）**：
1. **目标 Job handle**：新进程归入的作业（决定配额与能力）。
2. **可执行映像描述**：路径 / VMO / 兼容层 ELF 描述；加载在用户态 loader 完成（对齐 Zircon，内核不解析 ELF 格式细节）。
3. **句柄继承集（handle transfer list）**：父进程显式列出哪些句柄（文件、channel、event、device…）传给子进程，以及传递语义（move / duplicate-with-rights）。默认**不继承任何句柄**（最小特权）。
4. **资源覆盖**：可选覆盖 Job 默认配额（如内存上限、CPU 权重、句柄数上限）。
5. **能力集**：可选收窄父进程能力（drop 某些 capability）。
6. **启动参数 / 环境**：argv、env（与 Linux 一致）。

**语义保证**：
- 新进程从空根 VMAR 开始，由 loader 显式映射代码/数据/栈/堆——**没有「复制父地址空间」这一步**（这是与 fork 的根本区别，也是无 MMU 平台也能工作的原因）。
- 句柄按继承集移动/复制，离开父进程的句柄从父表移除（move 语义）。
- 配额与能力来自目标 Job（或显式覆盖），**可审计、可预测**。

**与原生 fork 的关系**：MeuOS 原生不提供 fork。Linux 兼容层在需要 `fork` 时，走「COW 近似 + 受限语义」：仅当目标进程未多线程、且调用方持有相应能力时，兼容层用 `meu_spawn` + 地址空间快照模拟；不鼓励、不保证 POSIX 全部 fork 语义。这避免了 fork 的 COW 账本复杂性与大页/多核隐患，同时让旧二进制「能跑」。

### 4.3 调度器设计（G5，吸收 Linux EEVDF + RT）

**两层策略 + 调度类**：

1. **公平层（默认）**：实现 **EEVDF**（Earliest Eligible Virtual Deadline First，Linux 6.x 主线取代 CFS 的算法）。理由：
   - EEVDF 用「虚拟截止期（virtual deadline）」选下一个任务，逻辑比 CFS 的 vruntime 红黑树更直接，尾延迟（tail latency）更可控，且无需 CFS 的 `sched_latency`/`min_granularity` 一堆启发式参数。
   - 保留「公平权重（weight）」概念，可映射到 Zircon 的公平权重与 Linux 的 `cpu.shares`，用于 Job/进程组间公平。
   - 记账用**纳秒级虚拟时间**，与 CFS 一致，不依赖 HZ/jiffies。
2. **实时层（可选、需能力）**：固定优先级 `SCHED_FIFO`/`SCHED_RR` 语义（POSIX），优先级 0–31（对齐 Zircon 区间）；用独立 RT 运行队列，遵守优先级抢占；**创建 RT 线程需特定 capability**（防 RT 饿死系统）。
3. **调度类钩子**：沿用 Linux `sched_class` 思路（`enqueue_task`/`pick_next_task`/`task_tick`/`set_next_task`），便于未来加 deadline 类（EDF）或能效类（EAS）而不改核心。

**多核均衡（C2）**：
- 每核（per-CPU）运行队列，避免全局锁争用。
- 负载均衡用 **work-stealing + 周期性负载迁移**（对齐 Linux `sched/fair` 的 load balance 但简化）：空闲核从最忙核「偷」任务；周期性把超额任务迁往较空核。
- NUMA 感知（原型期可后置）：优先在同 NUMA 节点内调度，跨节点迁移仅在必要时。

**与运行时的对齐（G5/E）**：
- 内核只提供**廉价的内核线程**与公平+RT 两层调度；Go/Rust 运行时在其上做 G/async-task 的 M:N 调度。
- 提供 `meu_thread_create`（轻量，仅建上下文不建地址空间）与 `meu_thread_set_priority`/`meu_thread_set_weight`，让运行时精确表达「这个 OS 线程该跑多快」。
- 异步抢占：内核用定时器/调度点实现线程级抢占，避免单协程长期霸占 M（对齐 Go 的异步抢占，但由内核完成）。

### 4.4 资源账本（G2，对齐 Zircon job，超越 cgroups）

**账本内建 Day 1**：每个 Job 创建即带配额，配额种类：

| 资源 | 计量方式 | 超限行为 |
|------|----------|----------|
| CPU 时间 | 公平权重 + 可选硬上限（带宽） | 降权重 / 限流，不杀进程 |
| 内存 | Job 级内存上限（VMAR 映射总量 + 内核对象占用） | 触发 OOM 在 Job 内选择性回收 / 通知监督者 |
| 句柄数 | 句柄表上限 | 拒绝新分配 |
| IO 带宽 | 按设备/层的配额（原型期可后置到 05-IPC/10-驱动） | 限流 |
| 进程/线程数 | pids/threads 上限 | 拒绝 spawn |

**与 cgroups 的区别（关键卖点）**：
- cgroups 是**事后**把已存在进程移入层级；MeuOS 配额是 **Job 的固有属性**，进程诞生即受限，无法「先越权再被关进笼子」。
- 限额与**能力边界**、**句柄表**三者同源挂在 Job 上，统一可审计（见 07-安全模型）。
- 层级天然是树（Job→子Job→Process），与监督树重合，简化「谁该为超限负责」的归因。

**实现位置**：配额的检查点分布在 MM（内存）、调度器（CPU）、句柄分配器（句柄数）；账本对象本身由进程管理子系统持有，被 capability 系统校验。

### 4.5 生命周期与内核内建监督（G3，融合 launchd + Zircon job）

**内核职责（最小、可靠）**：
- 启动早期创建**根 Job（root job）**，并 spawn **监督服务（meu-supervisor）**作为首个用户态进程（类比 launchd 作为首个用户进程，但监督的策略在用户态）。
- 内核保证：根 Job 终止 → 传播终止其下所有 Job/Process（lifetime control，对齐 Zircon）。
- 提供**进程退出事件对象**：进程死亡/崩溃时，内核向监管 Job 的 event/channel 投递事件（含退出码/异常原因），由监督服务消费——无需 `wait()` 轮询，天然对接 05-IPC 的 event 模型。

**监督服务（用户态，meu-supervisor）职责**：
- 读取声明式服务描述（类比 launchd 的 plist：`RunAtLoad`/`KeepAlive`/退出条件重启/依赖顺序）。
- 通过 `meu_spawn` 在指定 Job 下拉起服务，持有其 Job handle。
- 消费进程退出事件，按策略重启 / 升级 / 降级 / 告警。
- 自身受根 Job 约束，且持有「创建 Job/监督」专属 capability；普通进程无法冒充监督者。

**效果**：免外部 `init`/`systemd`；监督是内核「启动并保障」+ 用户态「策略」的组合，比纯 launchd（全用户态）更可靠，比纯 systemd（庞杂）更轻。

### 4.6 信号模型从零简化（G6，吸收 Plan 9 note + Zircon channel）

**问题**：POSIX 信号异步、可丢失、`signal mask`/`sigaction`/`tkill` 组合爆炸、与多线程交互脆弱（Linux `signal(7)` 长篇警告即是证明）。

**MeuOS 原生通知模型**：
- **事件对象（event）为唯一通知载体**：进程/线程可向某 event 对象注册；通知是「投递一个事件到 event/channel」，由接收方同步或异步消费（与 05-IPC 统一，对齐 Zircon port/channel）。
- **无「信号处理器」全局副作用**：不再有 `SIGSEGV` 处理器随意改写控制流；致命异常统一经 **exception channel** 上报监督者（对齐 Zircon exception 机制），由监督者决定 kill/debug/dump。
- **可取消 / 可过滤**：通知默认排队、可按类型过滤、可因能力缺失被拒绝（capability 约束谁能给谁发通知）。
- **兼容层**：把 POSIX 信号翻译为「向目标线程/进程 event 投递 + 兼容层 signal dispatcher 模拟 `sigaction` 语义」，旧二进制行为可用；但原生程序不碰 signal。

**保留的「类信号」最小集**（必要时）：`Terminate`（礼貌退出，对应 SIGTERM）、`Kill`（强制，对应 SIGKILL，仅监督者/同 Job 持有相应 capability 可发）、`Interrupt`（对应 Ctrl-C/可中断等待）。这三项足够覆盖 99% 的进程控制需求，且语义清晰、不可被用户态「吞掉」关键控制流（Kill 不可屏蔽，对齐 SIGKILL 不可阻塞）。

### 4.7 与 Rust/Go 运行时对齐小结（G5/E）

| 运行时概念 | MeuOS 内核实体 | 映射方式 |
|------------|----------------|----------|
| Go G（goroutine） | 用户态 runtime 结构 | Go runtime 在 M 上调度，内核不感知 |
| Go M（OS 线程） | Thread | `meu_thread_create` + 权重/优先级 |
| Go P（处理器） | 无对应（runtime 内部） | 由 Go runtime 管理 |
| Rust async task | 用户态 Future | tokio/smol 在 Thread 上多路复用 |
| 运行时调度决策 | 内核公平/RT 调度 | `set_weight`/`set_priority` 表达 |
| 阻塞 syscall | 内核线程阻塞 + 异步抢占 | 不让 M 长期霸占 CPU |

核心原则：**内核管「线程级」公平与实时，协程/任务级交给运行时**。内核不重复实现 M:N。

## 5. 开放议题

1. **EEVDF vs 自研轻量公平算法**：原型期是否直接上 EEVDF，还是先用更简单的时间片轮转（RR）+ 权重，待验证后再换 EEVDF？EEVDF 虽比 CFS 简单，仍有虚拟截止期计算成本。
2. **fork 兼容层的边界**：哪些 Linux 程序**必须**真 fork（如部分 shell、调试器 `ptrace`、JIT 的写时复制依赖）？兼容层 fork 的 COW 快照在「写时复制 + 大页 + 多核」下正确性如何保证？是否干脆要求这些程序走 `posix_spawn` 改写？
3. **Job 与 cgroup 兼容映射**：Linux 兼容层是否要把 cgroup 调用映射为 Job 配额操作？还是仅模拟接口、内部用单一默认 Job？影响容器运行时（Docker/containerd）可移植性。
4. **监督服务的故障域**：若 meu-supervisor 自身崩溃，内核是否自动重启它（自举监督）？如何避免「监督者监督自己」的死锁/循环？
5. **资源账本的 OOM 归因**：Job 级内存超限时，在 Job 内「选谁回收」的策略（最老？最大？最近活跃？）是否应暴露给监督者策略，还是内核默认 LRU？
6. **NUMA / 异构核（big.LITTLE）**：原型期是否支持异构核优先级（能效感知调度 EAS）？还是先假设同构多核？
7. **句柄继承与能力派生的粒度**：spawn 时「能力收窄」是用白名单还是黑名单？与 07-安全模型的 capability 派生规则如何对齐（需跨子领域协同）。
8. **异常上报与调试器**：exception channel 同时服务监督者与调试器（类似 `ptrace`），二者权限与冲突如何仲裁？
