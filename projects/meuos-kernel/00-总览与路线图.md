## 1. 总览：内核「应该是什么样」

MeuOS 内核**不是**把 Linux 搬进来，也**不是**从零另造一个玩具内核。它是一座**微内核取向的务实混合内核（lean hybrid）**，在「隔离谱系」上站在 seL4 / MINIX 3 一侧（文件系统、网络、驱动出核、可重启、可自愈），在「性能谱系」上通过一层**内核态 mkit 兼容转译薄层**吸收宏内核的 syscall 零往返优势——唯独这一处是相对纯微内核的故意让步。

在这副骨架上，三大内在统一方向**同时成立、彼此互锁**：

- **① 统一文件系统层**：文件系统逻辑整体下沉为用户态 Rust 服务，经 VMO + pager 实现零拷贝 mmap、数据通路在内核；统一命名空间 = `capability` 组合树（每进程独立、默认全不可见、显式 reveal），取代 `/proc+/sys+/dev` 的拼凑；extent 级校验和/压缩/加密内建于存储对象，且**密钥 unwrap 权 = 文件句柄 right**（capability 模型的一等公民）；`.msys` sysroot 以子树级 CoW 快照 + 命名空间原子 repoint 实现可灰度、可回滚的原子更新。
- **② spawn 模型进程管理**：原生 `meu_spawn` 取代 fork+exec；`Job` 是资源账本与生命周期的一等公民（配额 Day 1 内建）；内核只「启动并保障」监督者（meu-supervisor），监督策略在用户态、可重启——免 systemd 内核 blob；信号从零简化为 event 对象 + 极简 `Terminate/Kill/Interrupt`，致命异常经 exception channel 上报监督者。
- **③ capability-based 安全**：Day 1 唯一权限模型，无 root 逃生舱；句柄即 capability，权限随句柄走；pledge/unveil 沙箱 fail-closed（越界即终止、只能收缩）；安全关键路径（capability 监视器、IPC 端点、调度核心、VFS 抽象）用 Rust 入 TCB，把「权限令牌不可伪造」建立在内存安全之上。

**一句话收口**：内核态只保留「机制 + 唯一裁决点」——低级 VM、线程调度、capability 监视器、IPC 端点、异常/中断派发、内核态 mkit 薄层；其余一切「策略重、代码量大、需可重启」的子系统（FS、网络、驱动、监督策略、图形）下沉为用户态、capability 受控、由内建监督原语管理的服务。在能交权的地方尽早交权，是压缩 TCB、缩小故障爆炸半径、逼近可验证性的唯一窄路。

## 3. 跨域冲突登记表

> 凡各子文档 §待决 中标为「架构级 / 架构裁决」者，全部汇入本表（C1–C14）。每项给：**现状 + 推荐裁决 + 需拍板方**。
> C1–C10 为任务指定的核心跨域冲突；C11–C14 为 08 中另四项「架构级裁决」待决（依「凡架构级必须进此表」规则纳入）。

### C1（内存·架构级）物理内存归属
- **现状**：03 §5 开放议题 1 未决——物理内存「内核 buddy 独占」「seL4 式暴露 untyped 给用户态内存服务」「折中：内核 buddy 拥有物理页、VMO 为逻辑视图、revoke 触发回收」三选一未定；revoke 与 buddy 归还的时序与锁未明。
- **推荐裁决**：采用**折中**——内核 buddy 拥有物理页（务实、可自举），VMO 作为对用户态/兼容层暴露的 capability 视图；revoke 经 derivation tree 触发 VMO 派生链回收，再由 MM 回收物理页，保持单一真相源（refcount 在 MM）。
- **需拍板方**：01（架构层边界最终确认）。

### C2（安全·架构级）加密密钥是否走 capability 撤销 + FS 服务 confused deputy
- **现状**：06 §6 待决 1（密钥 unwrap 权 = 文件句柄 right，撤销句柄即撤销解密权）与待决 2（FS 服务作为 capability 委托人，如何防 confused deputy 越权 mint）均未定稿；rights 位图是否新增 `KEY_UNWRAP` 还是复用 `MANAGE`、`revoke` 的 derivation tree 是否覆盖「句柄→密钥 unwrap 权」链不明。
- **推荐裁决**：**是，密钥访问权生命周期绑定到文件句柄 capability**（方向①③互锁最高价值点）；FS 服务 mint 文件句柄时采用「FS 服务自身 rights 上限 ∩ 客户端请求下限」取交集的受约束 mint 模型，杜绝 confused deputy；`KEY_UNWRAP` 作为文件句柄的显式 right（与 `MANAGE` 区分，避免大权聚集）。
- **需拍板方**：07（安全模型定稿 rights 位图与受约束 mint 授权）。

### C3（进程/安全·架构级）命名空间「每进程独立 vs 共享根 + unveil 裁剪」
- **现状**：06 §6 待决 3 倾向「每进程 namespace 由 spawn 组装」（对齐 Fuchsia/Plan 9），但与 08 兼容层「全局路径」语义如何映射未定；unveil 与 spawn 时命名空间绑定的来源/继承语义未对齐。
- **推荐裁决**：采用**每进程独立 namespace，由 spawn/Job manifest 组装**（默认全不可见，unveil = 注入路径 capability 绑定）；Linux 兼容层把「全局路径假设」翻译为「进程 spawn 时获得的命名空间绑定 + 按需 reveal」，不在内核重建全局 `/proc`。
- **需拍板方**：04 / 07 / 08 协同（spawn 绑定来源、pledge/unveil 语义、兼容层路径投影）。

### C4（兼容·安全）Linux 二进制是否绕过默认沙箱
- **现状**：08 §6.1 D1（是否允许绕过 pledge 默认沙箱）、D2（fork 全量 CoW vs 受限）、D6（uid/gid↔capability 映射）未决；08 立场「默认不允许，仅经显式清单放宽」。
- **推荐裁决**：**默认不允许绕过**——即使逃生通道也只是「该 Job 的 capability 投影范围」显式扩大（可按包粒度 manifest 声明、记入 Job 账本、可撤销），绝不存在「root 万能」；fork 起步全量 CoW（语义完整），后续优化；uid/gid 仅为合成视图，单 Job 单 uid 视图起步，setuid 二进制映射为受限 spawn + 显式 capability（不引入提权）。
- **需拍板方**：07 / 08 裁决（沙箱边界为 Day 1 安全最高优先项，08 标注为「首要裁决项」）。

### C5（语言·调试·真实冲突）内核 `panic=abort` vs 用户态 unwind
- **现状**：02 §4.5 写「内核 Rust 统一 `panic=abort`，不展开调用栈」；但 12 §4.5 / §7 待决 4 裁决「用户态 Rust 服务启用 unwind 以产出完整 backtrace 供 supervisor 分析」。二者**并非同一对象**（内核态 abort vs 用户态 unwind），但若 02 字面未区分会造成表面冲突。
- **推荐裁决**：**02 应明确保留用户态 unwind 口子**——内核核心 Rust 组件 `panic=abort`（停机、不做全栈 unwind）；用户态 Rust 服务用 unwind 生成完整 backtrace，由 supervisor 重启而非停机（对齐 Hubris/Redox「组件 panic ≠ kernel panic」）。二者归一化为统一 `StackFrame` 格式，并不矛盾。
- **需拍板方**：02（回写澄清，见下方「待回写修订点」）。

### C6（启动·语言）Rust runtime 精确接管时刻 + i386 全程纯 C 下 Rust TCB 范围 + 双工具链张力
- **现状**：09 §5.7 裁决「`arch_boot → kernel_main()` 单一边界」；02 §2.2/§2.3 指 Rust 走 rustc+LLVM、C 走 mcc+QBE（双工具链），且 i386 无 Rust 裸机 target、全程纯 C；i386 下哪些 TCB 组件可走「C 链接 Rust `.o`」未定。
- **推荐裁决**：交接点定为**单一 `arch_boot → kernel_main()`**；i386 由 C 在 runtime 就绪后调用 Rust 编译出的 `.o`（`extern "C"` 入口，非裸机 target）；无论何架构，Rust 接管**前**禁止任何依赖 `alloc`/`panic` 的 Rust 路径。双工具链现实可接受（自举指用户态/工具链跑通，非内核须由 mcc 编译）。
- **需拍板方**：02 / 09 协同（边界与 i386 Rust 组件范围）。

### C7（启动·内存）memblock → buddy 转交原子性
- **现状**：09 §5.3 / §6 待决 8 指 Stage 2 `memblock` 在 03 `buddy` + SLUB 就绪时需把空闲区转交；页帧数据库衔接、地址空间无感切换的原子性未定。
- **推荐裁决**：采用 03 §4.2.1 的两阶段分配器设计——buddy/SLUB 建好后，memblock 把空闲区一次性转交 buddy，转交期间用临时锁/单线程启动期保证无并发；早期临时页表在 `kernel_main` 入口仍有效或能无感切换，Rust 接管后以 03 抽象为唯一真相源。
- **需拍板方**：03 / 09 协同。

### C8（驱动·启动）设备能力签发时序/撤销锁 + 早期串口能力归属
- **现状**：09 §5.4 / §6 待决 4、7——Stage 2 拓扑树 → Stage 4 签发设备能力 → 驱动卸载回收的锁与时机未定；Stage 1 直写串口是「内核内建生死相关快速路径」还是也应经能力网关未定。
- **推荐裁决**：设备能力（MMIO/IRQ/DMA/IO port）在 Stage 4 随根 Job 一同自举，驱动加载时按「声明即授权」经能力网关下发，卸载/拔出时回收（避免悬垂硬件引用）；早期串口在 Stage 1 作为内核内建快速路径直写（生死相关），进入用户态后由 devmgr 接管为受能力约束的用户态驱动。
- **需拍板方**：10 / 09 协同。

### C9（调试·安全/进程）调试 capability 默认开放 + exception channel 消费者仲裁
- **现状**：12 §7 待决 1（调试 capability 默认值是否对 mkit/glibc 开放）、待决 2（exception channel 同时服务监督者与调试器，权限与冲突仲裁）——04 §5 开放议题 8 亦指出此冲突。
- **推荐裁决**：**默认拒绝**——spawn 出的进程不持任何 `DBG_*` right，调试器须从监督者/同 Job 持有者处显式获授权（fail-closed）；exception channel 消费者仲裁：**监督者持 `DBG_CRASHDUMP` 默认订阅权**（kill/restart 决策所需），交互式调试器持 `DBG_ATTACH` 且**不能阻断**监督者崩溃处理——调试器 attach 期间崩溃仍先交付监督者，调试器读副本。
- **需拍板方**：04 / 12 协同（仲裁协议定稿）。

### C10（兼容·调试）ptrace 单步/内存改写无法用事件订阅等价
- **现状**：08 §7 / 12 §7 待决 7——旧二进制依赖 `ptrace` 单步、内存改写类调试（如 `gdb` 调试 mkit 程序），预计**不能完全**经「事件订阅替换」等价实现。
- **推荐裁决**：明确兼容层调试支持边界——`strace`/syscall trace → 事件订阅（可等价）；`ptrace` attach/读内存/暂停 → 需 `DBG_ATTACH`（可等价）；**单步执行、内存改写类**（write-breakpoint、in-process 修改）在 MeuOS 内部无对应全局权限，**显式不兼容、返回 ENOSYS**，由兼容层在文档中声明支持到哪一层。
- **需拍板方**：08 / 12 协同（明确 support level）。

### C11（兼容·架构级）32 位 Linux 二进制（i386/arm）支持范围
- **现状**：08 §6.1 D3 未决——WoW64 式独立翻译层 vs 仅 64 位；涉及五架构后端投入（02 约束 C2：i386 全程纯 C）。
- **推荐裁决**：原型期**仅 64 位 + mkit 子集直跑**；i386/arm 32 位 Linux 二进制支持后置，待 Rust 裸机 i386 target 成熟或 C 链接 Rust `.o` 路径验证后再评估 WoW64 式分层。
- **需拍板方**：08 / 02（架构级裁决）。

### C12（兼容·架构级）syscall 覆盖基线
- **现状**：08 §6.1 D4 未决——以哪个 glibc / 内核版本为「通用程序」目标；mkit 子集先行已定。
- **推荐裁决**：先固化 mkit 子集（direct-mapped 全集）为基线；通用程序目标定为「主流 glibc 静态/动态程序的常见 syscall 子集（IO/进程/基础信号/基础 IPC）」，按 08 Phase 0→3 渐进，不追求全量 syscall 号。
- **需拍板方**：08（架构级裁决）。

### C13（兼容·架构级）/proc /sys 伪文件系统生成策略与性能边界
- **现状**：08 §6.1 D5 未决——全量生成 vs 按需最小集、是否缓存。
- **推荐裁决**：伪文件系统由统一命名空间在查询时**按需生成** Linux 视图（不落地真实文件）；`/proc/<pid>/` 映射为 inspect 子树（12 §4.6）；原型期先做最小集（pid/self/stat/maps），性能边界待基准。
- **需拍板方**：08 / 06 / 12 协同（架构级裁决）。

### C14（兼容·架构级）对外 `uname` 版本/ABI 号
- **现状**：08 §6.1 D7 未决——声称为何值以最大化存量程序兼容而不误导。
- **推荐裁决**：声明一个固定、可控的版本/ABI 串（如报一个广泛兼容的 Linux 主版本区间），不暴露 MeuOS 内部版本；具体值由兼容层 manifest 配置，避免程序因版本探测走特殊分支。
- **需拍板方**：08（架构级裁决）。

### C16（安全·配置·架构级）`CFG_*` rights 并入 07 rights 位图 + 编译期固定安全关键参数清单——**已采纳**
- **现状**：30 §8 待决 1+2 未决——①是否存在「必须编译期固定的安全关键参数」清单（capability 检查 / `panic=abort` / 无调试 root 等）且运行期完全不可见；② `CFG_*` rights 是否并入 07 rights 位图还是独立维度。
- **已采纳结论（第四轮查缺补漏，指挥官自主采纳）**：
  1. **是**，配置权体系并入 07 统一 capability 模型，新增 `CFG_READ`/`CFG_WRITE`/`CFG_GRANT`（建议 bit 8/9/10，紧邻 `KEY_*`=6/7 之后、与 `DBG_*` 互不重叠），与 `DBG_*` 同构、句柄即 capability、默认拒绝。
  2. **是**，存在必须编译期固定的安全关键参数清单（capability 检查不可关、`panic=abort`、无配置 root、Day 1 安全边界）——运行期**不可见不可改**，是 15 D1「无全局关沙箱」在配置维度的同构延伸；清单由 07 与 30 共同定稿、写入内核 build 契约供审计。

## 4. 总路线图

### 4.1 原型路线（最小可运行集）
原型期目标 = 内存 + 调度 + IPC + Linux 兼容层 mkit 子集跑通，支撑 `mcc`+`meuos-libc` 在自研内核自举。各子领域已给出最小集：

| 子系统 | 原型最小集（来源） | 关键内容 |
|--------|-------------------|----------|
| 内存（03） | M1–M10 | memblock → buddy → SLUB、4 级页表、VMO/VMAR、VMA/mmap/COW |
| 进程/调度（04） | 核心原语 | `meu_spawn` + Job 账本、EEVDF（或先 RR+权重）、event 通知取代信号 |
| IPC（05） | 四原语 | Channel / EventPort / SHM / Service Registry，端点即 capability |
| 兼容层（08） | Phase 0 | mkit 子集 direct-mapped 直跑（open/read/write/close/mmap/基础进程/基础信号） |
| 启动（09） | Stage 0–5 | 两段式启动 + 早期 capability 自举 + 尽快交权 |
| 驱动（10） | 最小集 | 串口、virtio-blk、virtio-net、中断控制器、定时器 |
| 安全（07） | Day 1 最小集 | handle/rights、pledge/unveil、capability 监视器 |
| FS（06） | F1–F5 | 用户态 FS 骨架 + Channel 接口、extent+CoW B-tree、VMO+pager、每进程命名空间 |
| 调试（12） | 基元 | inspect 树 + 事件流 + CrashReport（原型期串口/9p/gdbstub 通道） |

### 4.2 里程碑 M0–M6 与跨子领域依赖（整合自 11）

```
[技术选型已定] 01-12 文档 → 进入执行
        │
        ▼
  M0  内核启动到用户态 init         依赖：09 + 10(串口) + 03 + 04(单进程exec) + 08(exit/write)
        │
        ▼
  M1 (L0) libc 静态 hello 运行退出0   依赖：03 + 04(调度/exec) + 08 + 10(串口)
        │
        ▼
  M2 (L1) 宿主 mcc 在 MeuOS 编译运行   依赖：04(fork/exec/spawn) + 08(完整syscall子集) + mt/as/ld 可运行
        │
        ▼
  M3 (L2 工具链) mcc 重建 mcc/libc/meow  依赖：05(IPC/管道/并发) + 04 + 前述全部
        │
        ▼
  M4 (L2 内核) 内核由 MeuOS 工具链重建   依赖：03/04/05/08/09/10 全闭环 + mt 工具链自举
        │
        ▼
  M5 (跨架构) x86_64 + aarch64 双架构     依赖：09/10 多架构启动与驱动
        │
        ▼
  M6 (原子更新) .msys 签名 Overlay 原子更新回滚  依赖：06(文件系统) + 07(ed25519 验签)
```

- **最小可启动依赖**（M0–M1）：09 + 10(串口) + 03 + 04(单进程 exec) + 08(exit/write)。
- **完整闭环依赖**（M2–M4）：叠加 05 + mt 工具链自举 + 06(`.msys` rootfs)。
- **前置并行**：在 M0 之前用 11 方案 B（qemu-user-static）持续跑 mcc 跨架构 ABI 回归，保「内核就绪前工具链不被破坏」。
- **依赖先后原则**：启动/内存/进程是地基（M0–M1）→ 兼容层+IPC 使工具链可跑（M2–M3）→ 全闭环重建内核（M4）→ 多架构（M5）→ 原子更新（M6，方向①落地）。

### 4.3 冲突对路线图的阻塞关系

> **统一结论**：5 子系统 B 务实线为 Day 1 主线、A 极简线为长期演进目标——**两者内核模型（capability 唯一、Job 账本 Day 1、Channel、VMO+pager、统一命名空间）完全一致**，A/B 差异仅在"Day 1 用户/应用/兼容层是否暴露更多兼容投影"。FS 是唯一例外，方案 A 不可变 Blob 子集被嵌入方案 B 内的 `/msys` 系统组件区，两者**并存而非互斥**（对齐 Fuchsia minfs+blobfs 范式）。

| 子系统 | Day 1 主线（推荐） | 长期演进（参考） | 一句话理由 |
|---|---|---|---|
| **进程管理** | **B 务实双轨**（fork_light + Job 命名可查询 + scoped 标识 + SHM 一等公民） | A 极简范式（无 fork / 无全局 PID / 无信号） | 自举需要 mcc/meuos-libc 与运行时友好；A 的"无 fork/无信号"通过 mkit 兼容层翻译即可让内核模型保持纯 |
| **内存** | **B 保留虚拟地址空间**（Region 带权区间 + 稳定指针） | A 消灭地址空间（CHERI 式精神） | C/Rust 运行时与存量 binary 依赖稳定指针；B 的 mkit 翻译路径最短；libc/`malloc`/TLS 零改造 |
| **图形** | **B 客户端-合成器协议 + 用户态 GPU 服务**（Magma 式） | A 保留模式场景图（声明式节点提交） | GTK/Qt/Flutter 存量工具包 Wayland 后端零成本迁移；D-G1/D-G2 兼容性基线天然支持 B |

| **文件系统** | **B 可变路径 + 可验证存储层**（POSIX 友好） | **A 不可变 Blob 子集嵌入 `/msys` 系统组件区**（两者并存） | Fuchsia minfs+blobfs 已证明可写 FS + 不可变 blob 并存可行；B 拿 A 完整性收益仅丢"应用层按内容寻址编程模型" |

### 7.2 5 个新维度（57–61）一句话汇总
