## 0. 一句话核心

> **在 MeuOS 中，真实身份 = 进程/会话持有的 capability 集合（句柄 + rights），内核中**永不**存在 uid/gid 概念、不存在 root；UID/GID 仅作为「兼容翻译层」在 Linux 兼容层（08）合成并展示——它是一张**无权限附着的投影视图**，所有权限判定走 capability。翻译发生在兼容层：Linux 二进制对 `uid==0`/权限位的检查，被映射为「是否持有对应 capability 句柄」；登录/认证则产生「受约束的 capability 集合 + 一张合成凭据视图」，而非「变成某个 uid」。**

本文把 `00`/`07`/`04` 中已采纳的「capability Day1 唯一模型、无 root、合成 uid（C4）、Job 资源账本（A5）」等点状决策，**升维成一套自洽的「身份 = capability + 合成凭据视图」务实模型**——内核内部与方案 A 完全一致（纯 capability、无 uid），差异只在**兼容层多保留一层 UID/GID 投影 + 一套凭据翻译规则**，以换取 POSIX 多用户生态与存量二进制的最大友好度。

## 1. 方案核心思想

### 1.1 与方案 A 的根本分叉点

方案 A 的立场是「无 UID/GID 能力身份」：内核里**连合成的 UID/GID 视图都不提供**，进程身份就是 capability 集合本身，找不出任何 `uid_t`。这是最干净、对形式化最友好的极简主义，但 POSIX 多用户语义（`getuid`/`chown`/`setuid`/`/etc/passwd` 直觉、按 uid 记账、容器/守护进程以 uid 区分主体）要全部在更深一层重写或彻底舍弃。

方案 B 认同 A 的**全部内核级不变量**（capability 唯一权限源、无 root、权限随句柄走），但认为 A 在「用户态呈现 / 多用户生态」上有两处成本过高、且并非安全所必需：

1. **POSIX 多用户语义的兼容成本**：大量 Linux 程序、库、运维脚本、容器镜像依赖 `uid/gid` 作为「主体标识」与「记账/隔离键」。A 彻底移除 uid 后，这些程序要么改写、要么在兼容层做更深的语义模拟。B 主张**把 UID/GID 显式建模为「兼容翻译层的一张合成视图」**——内核不知 uid 为何物，但兼容层能给每个进程一个稳定的合成 `{uid,gid,groups,…}` 供 `getuid` 等返回、供 `/var/log`/容器/工具按 uid 记账、供 human-readable 展示；这张视图**零权限附着**，不进入内核裁决。
2. **「登录 = 提权为某 uid」的直觉成本**：Linux 的 `login`/`su`/`sudo` 本质是「认证后改变 uid（常到 0）」。A 把认证直接做成 capability minting，完全没有 uid 叙事。B 主张**保留「登录 → 获得一份身份 + 一份 capability 集合」的叙事**，只是这份「身份」是合成 uid 标签、「capability 集合」才是真实权限——既贴合运维直觉，又不引入 root 后门。

> **一句话区分**：方案 A = 内核连合成 uid 都不给、身份即 capability 本身（最极简、对存量生态最不友好）；方案 B = 内核同样无 uid、但兼容层务实保留 UID/GID 合成视图与凭据翻译，身份仍是 capability、uid 只是「给人类与旧程序看的投影」。二者**内核模型完全相同**，分歧只在「兼容层要不要呈现 UID/GID」。

### 1.2 方案 B 的四条务实原则

1. **capability 是唯一真实权限源**：进程/会话能做什么，100% 由其持有的 `handle + rights` 集合决定。内核对象访问、文件系统、网络、设备——全部走 `07` 的 capability 模型，**无 uid 短路、无 `CAP_SYS_ADMIN` 式大杂烩**。
2. **UID/GID 仅作合成投影（零权限附着）**：每个进程/会话可被兼容层赋予一张合成凭据视图 `{ruid,euid,suid,fsuid, rgid,egid,sgid,fsgid, groups[]}`，但它是 **cosmetic + display + accounting 键**，**绝不参与任何内核裁决**。内核不认识 `uid=0`，只认识句柄。
3. **翻译发生在兼容层（08），不污染内核**：`getuid`/`chown`/`setuid`/`access`/权限位检查等，由兼容层翻译成 capability 操作或纯返回合成值；需要「特权的含义」时，映射为「是否持有对应 capability 句柄」。内核内部无 `struct cred`、无 `current_uid()`。
4. **认证 = 受约束的 capability minting + 合成身份标签**：登录/认证由用户态 broker 完成——验证秘密后，**显式 mint 一份受限 capability 集合**（来自策略清单）并**贴上一张合成 uid 标签**给新会话，而非「切换到 uid」。无「成为 root」路径；若某身份需要特权操作，必须在策略清单里显式授予对应 capability。

### 1.3 UID/GID「合成投影」到底合成在哪（与 Unix 的差异）

| 维度 | Unix | 方案 A | 方案 B |
|---|---|---|---|
| 内核是否知 uid | 是（`struct cred`，全局身份） | 否（纯 capability） | **否（纯 capability，与 A 同）** |
| 兼容层是否呈现 uid | 是（原生） | 否（连合成视图都无） | **是（合成视图，零权限附着）** |
| `uid==0` 的含义 | root 万能后门 | 无此概念 | **合成视图里可标 0，但内核不认；实际特权 = 显式 capability 句柄** |
| 权限判定依据 | uid + DAC bits + cap bounding | capability 集合 | **capability 集合（与 A 同）** |
| 多用户隔离 | DAC（uid 不同 → 文件隔离） | 靠 namespace/capability 作用域 | **靠 Job/namespace/capability 作用域；合成 uid 仅作展示/记账键** |

B 的设计动机：**让「身份/多用户」与「真实权限」彻底解耦**——身份是给人看、给旧程序看、给日志看的；权限是 capability 给内核裁决的。这张解耦让 MeuOS 既能跑「认 uid」的存量生态，又从架构上消灭 Linux「root 万能」「setuid 提权」「permission bit 即裁决」三处根本性缺陷。

### 2.1 Capability 身份（真实身份 = capability 集合）

- **定义**：一个主体（进程/会话）的真实身份 = 它持有的全部 `handle + rights` 集合（`07` §4.1）。这是权限的唯一真相源，与方案 A 完全相同。
- **寻址/权限/生命周期**：继承 `07` 全部不变量——句柄即 capability、派生只能收窄、崩溃即回收、无 root、无隐式提升。
- **B 的立场**：capability 身份是内核**唯一认知**的身份，UID/GID 完全不在此层出现。

### 2.2 合成凭据视图 Synthetic Credential View（兼容层投影，B 新增）

- **定义**：一个**每进程/每会话**的合成结构，形如 POSIX `{ruid,euid,suid,fsuid, rgid,egid,sgid,fsgid, groups[N]}`，由兼容层在 spawn/登录时按 manifest/策略清单赋予。它是兼容层内部状态（或进程私有元数据），**不进入内核对象、不参与任何 capability 裁决**。
- **三个用途（全部 cosmetic/accounting）**：①`getuid()` 等 syscall 的返回值（让旧程序不崩）；②human-readable 展示与 `/var/log/*`、`wtmp`、进程记账的 uid 键；③容器/多用户工具「按 uid 区分主体」的兼容键。
- **零权限附着铁律**：内核任何代码路径都**读不到**这张视图；它既不能开特权、也不能关特权。`access()` 的「当前 uid 能否访问」语义，在 B 中被翻译为「当前进程是否持有对应 capability 句柄」，而非查视图。
- **单 Job 单 uid 视图起步（继承 C4）**：原型期每个 Job/会话持一张合成视图；同一 Job 内进程共享该视图，跨会话视图自然不同（由各自会话的 capability 模板 + 标签决定）。这正是 C4「单 Job 单 uid 视图起步」的落地。

### 2.3 身份清单 / 令牌 Identity Manifest（spawn 声明，B 新增）

- **定义**：`spawn`/会话派生时，manifest 同时声明两件事：①**真实 capability 集合**（与 `04`/`07` 维度 B 一致，最小特权）；②**合成凭据视图**（一个或一组 uid/gid 标签，纯展示）。
- **与 macOS entitlements 的类比**：manifest 声明 capability 集合 ≈ macOS 的 entitlements（二进制/身份附带的 capability 清单）；差别是 MeuOS 的清单是 capability（句柄+rights），不是 entitlement 字符串。
- **策略来源**：谁决定「身份 alice → 哪些 capability + 哪个合成 uid」？由**认证 broker + 策略清单**决定（见 §2.6），不是由内核魔法或 `/etc/passwd` 决定。

### 2.4 会话 Session（capability 作用域 + 合成身份 + 生命周期）

- **定义**：一个会话 = 一棵 **Job 子树** + 一张**合成凭据视图** + 一段**生命周期（取消域）**。它把「身份标记」「资源账本（A5）」「生命周期（A9）」「capability 模板」四者绑定到同一作用域。
- **多用户隔离的实现**：传统 Unix 用「不同 uid 的 DAC」隔离多用户；B 用「不同会话 Job 树的 capability/namespace 作用域」隔离多用户——合成 uid 只是这两棵会话树的**可读标签**，隔离本身由 capability/namespace 提供（与 `06` 每进程 namespace（C3）、`07` 维度 C 一致）。
- **会话派生**：登录/启动一个新会话 = 认证 broker 派生一个 Job 子树 + 贴上该会话的 capability 模板与合成视图；会话关闭 = Job 树结构化取消（无僵尸、无 init 兜底）。

### 2.5 认证 broker（用户态，受约束 issuer）

- **定义**：一个受 `meu-supervisor` 管理的用户态服务，持有**受限 `GRANT`** 能力——能 mint 的 capability 集合被策略清单严格上限约束（「自身 rights 上限 ∩ 策略清单下限」交集，破 confused deputy，`07` §4.5）。它负责验证秘密并发放会话。
- **认证即 minting**：验证口令/令牌/密钥（经其持有的校验句柄，如密钥守护）成功后，broker 据策略清单 mint 一份**受限 capability 集合**，并给新会话贴一张**合成 uid 标签**——**全程无「切换到 uid」、无 root**。
- **与 Linux PAM 的差异**：PAM 的 `pam_setcred` 最终改变进程 uid；B 的 broker 是「验证 → 受约束 mint capability + 贴标签」。若策略清单未授予某 capability，即使合成 uid 标成 0，该会话也拿不到任何特权——`uid==0` 在 B 里**不是权限**。

### 2.6 翻译层 Translation Layer（兼容层组件，B 相对 A 的核心增量）

- **定义**：位于 `08` 兼容层内的一组映射规则，把 Linux 凭据/权限语义 ↔ capability 语义双向翻译。**翻译层本身运行在一个受限句柄集下**，避免成为新的特权后门（`07` §4.6）。
- **关键映射规则（见 §4 衔接 07 §4.6）**：
  - `getuid/geteuid/getgid/getgroups` → 返回该进程的合成视图值（纯投影）。
  - `setuid/setresuid/setfsuid/setreuid` → **仅修改合成视图**（允许进程「换展示身份」，如 daemon 降权展示），**不产生任何 capability 变化、不提权**；若目标是 `0` 且二进制逻辑是「我是 root 就干特权事」，后继特权 syscall 仍按 capability 裁决——无 capability 句柄即 `EPERM`。
  - `chown/chmod/umask/access` 权限位 → 权限位作为**合成属性**存储（供 `stat` 展示、供 `access()` 返回值的「兼容模拟」），**真实文件访问仍走 06/07 的 capability**；若旧程序据 `access()` 返回值短路逻辑，翻译层据「进程 capability 集合」模拟返回值。
  - `setuid` 二进制（文件 SUID 位）→ 映射为「受限 spawn + 显式 capability」（`07` §4.5 / C4）：运行时不提权，所需 capability 由该二进制 manifest 显式声明并经 broker/策略清单授予。
  - `capset/capget`（Linux capability）→ 映射为对句柄 rights 的查询/收窄；`CAP_SYS_ADMIN` 等「大杂烩」被拆分到具体对象 rights，**不被整体授予**（`07` §4.6）。

### 2.7 抽象关系小结与相对方案 A 的差异

| 抽象 | 方案 A 的立场 | 方案 B 的立场（差异化点） |
|---|---|---|
| 真实身份 | capability 集合（纯） | **capability 集合（与 A 完全相同）** |
| UID/GID | 内核与兼容层均无 | **兼容层合成视图（零权限附着、展示/记账键）** |
| 身份清单 | 仅 capability 集合 | capability 集合 + **合成凭据视图标签** |
| 会话 | capability 作用域 + 生命周期 | capability 作用域 + 生命周期 + **合成身份标签（多用户可读键）** |
| 认证 | capability minting（无 uid 叙事） | capability minting + **合成 uid 标签（贴合 login 直觉）** |
| 翻译层 | 不存在（无 uid 可翻） | **08 内一组凭据↔capability 双向翻译规则（B 核心增量）** |
| 内核模型 | 纯 capability，无 root，无 uid | **纯 capability，无 root，无 uid（与 A 完全一致）** |

> 关键结论：**方案 A 与 B 在内核层 100% 一致**——都是纯 capability、无 root、无 uid。分歧只在「兼容层是否呈现并翻译 UID/GID」。B 用一层合成视图 + 翻译规则，换取 POSIX 多用户生态的友好落地。

## 3. 多系统参照（解构而非缝合）

> 本节逐一对标成熟系统，**只抽取可复用的机制骨架**，并明确「B 取了什么、相对 A 多取了什么、丢了什么」。每个系统都点明 B 与 A 在此系统上的分叉。

### 3.1 Linux credentials（struct cred + DAC + capabilities）

- **机制**：内核用 `struct cred` 挂 `{uid,gid,groups,cap_eff,cap_inh,cap_amb,cap_bnd,securebits}`；DAC 权限位（rwx + suid/sgid/sticky）挂在 inode 上，由 `fs/namei.c` 据 uid 判定；`CAP_SYS_ADMIN` 成为「新 root」（LWN 2012：5.2 内核中 45% 的 capability 用例是它）；`setuid` 二进制经文件系统 SUID 位在执行时提权到文件 owner uid。
- **B 取了（解构后）**：①「权限位 = 文件的访问控制属性」这一**展示语义**——但把它降级为合成属性，真实访问走 capability；②「capability 是细粒度特权」这一方向——但把 capability 上升为**唯一真实源**，且 `CAP_SYS_ADMIN` 式大杂烩被拆到具体对象 rights（`07` §4.6）。
- **B 丢了/改造**：①`uid=0` root 万能后门——B 内核不认 uid，合成 `0` 无特权；②`struct cred` 全局身份——B 内核无 cred，身份=capability；③`setuid` 提权——B 映射为受限 spawn + 显式 cap（C4）；④`cap_bounding/securebits`——被 capability 集合 + manifest 取代。
- **为什么 A 没取这一层**：A 认为连「合成 uid 视图」都不要，避免任何 uid 语义泄漏到程序心智；B 认为「呈现合成 uid」是 POSIX 多用户生态的低成本友好项，且零权限附着、不回退。

### 3.2 Windows 访问令牌 + ACL（Token + ACL + Privileges + Logon Session）

- **机制**：每个进程/线程持一个 **Access Token**（内核对象，含 User SID、Group SIDs、Privileges 列表、Integrity Level）；对象授权 = 其 DACL 与令牌的 SID/Privileges 比对；令牌可经 `DuplicateToken`/`Impersonate` 复制/模拟（`SeImpersonatePrivilege`）；**Logon Session** 把「一次登录」建模为带有令牌的作用域。令牌本质是一个「capability-like 的内核对象」，不是裸 uid。
- **B 取了（关键增量）**：①**身份 = 令牌式对象而非裸 uid**——B 的合成凭据视图 ≈ 令牌上的 User/Group SID（纯标识），capability 集合 ≈ 令牌上的 Privileges + 对象真实 rights；②**Logon Session 抽象**——B 的 Session 即「一次登录/启动派生的作用域」，与 Windows Logon Session 同构；③令牌「复制/模拟」对应 B 的 capability 派生只能收窄（`07` §4.5）。
- **B 改造**：Windows 令牌的 Privileges 仍有「特权」概念且 `SeDebugPrivilege`/`SeTcbPrivilege` 接近后门；B 的 capability 模型里**无特权位**（高危权 `KERNEL_PRIV`/`DBG_POKE` 永不默认，`07`），令牌/视图层不授予任何内核裁决权。Windows 令牌是「身份+特权一肩挑」，B 把它**拆成两半**：视图（标识）与 capability（权限）彻底分离。
- **相对 A 的分叉**：A 连「令牌式标识」都不要；B 借 Windows 令牌思想，但只借其「标识部分」做成合成视图，权限部分仍归纯 capability。

### 3.3 Fuchsia / Zircon（无 uid、纯 capability、Boot/Verity 身份）

- **机制**：Fuchsia 内核**没有用户/uid 概念**——进程身份完全由 Job/handle/rights 决定；`fuchsia.io` 用 per-handle rights 做文件访问；「组件实例」由 component framework 赋予 capability 路由；认证/身份在用户态 component manager 层，不在内核。Fuchsia 文档明确「the kernel has no notion of a user」。
- **B 取了**：Fuchsia 即方案 A 的现成范本，B 的**内核层与 Fuchsia 完全相同**——纯 capability、无 uid、身份=句柄。B 的会话/Job 树、capability 派生、受约束 mint 全部对齐 Fuchsia/Zircon。
- **B 相对 A 多取了**：Fuchsia 也**没有**合成 uid 视图；B 在此之上**额外加一层兼容层合成 uid**，专门为了跑「认 uid」的 Linux 二进制与多用户工具。这是 B 相对 A（及相对 Fuchsia 原生）的唯一实质增量。
- **B 丢了**：Fuchsia 把身份完全交给 component framework 的 capability 路由；B 保留这一内核模型，但兼容层补 uid 投影以满足 POSIX 直觉。

### 3.4 macOS（entitlements + sandbox + Authorization Services + per-user launchd）

- **机制**：macOS 仍是 BSD 衍生，内核有 uid/gid + POSIX DAC + MAC 框架（Sandbox/seatbelt，强制 scheme）；但**真正有价值的权限模型是 entitlements**——二进制/身份附带的一份 capability 清单（如 `com.apple.security.network.server`），由签名绑定、在沙箱里被授予；认证走 Authorization Services（`AuthorizationCreate` + 右键规则），launchd 为每个登录用户起一个 **per-user session/launchd**（多用户会话作用域）。
- **B 取了（关键增量）**：①**entitlements ≈ 身份 manifest 的 capability 集合**——B 的「spawn 声明 capability 集合」直接对标 entitlements 的「身份附带 capability」；②**Authorization Services 的「认证 → 受约束授权」**——B 的认证 broker 即其用户态版，只是产出 capability 而非 Mach 端口权；③**per-user launchd session ≈ B 的会话 Job 树**——多用户隔离 = 每用户一棵 capability 作用域树。
- **B 改造**：macOS 内核仍用 uid 做 DAC 裁决（我们不用，内核无 uid）；macOS sandbox 是 scheme 强制、entitlements 是补充，B 反过来——**capability 是唯一源、scheme/权限位是兼容投影**。
- **相对 A 的分叉**：A 不要 entitlements 之外的 uid 叙事；B 借 macOS 的「entitlements = 身份 capability + 每用户 session」做务实落地，并把 uid 做成 entitlement 之外的展示标签。

### 3.5 综合取舍表

| 系统 | 抽取的机制骨架 | 方案 B 采用 | 方案 B 相对 A 多取 / 改造 |
|---|---|---|---|
| Linux cred | DAC 位 + cap 拆分 | 权限位→合成属性；cap→唯一源、大杂烩拆细 | **加合成 uid 视图 + 凭据翻译层**（A 无） |
| Windows | Token（SID+Priv）+ Logon Session + ACL | 视图≈SID；cap≈Priv+rights；Session≈Logon | 拆「标识/权限」两半（A 只留权限） |
| Fuchsia | 无 uid、纯 capability、Job 路由 | 内核层全采纳（同 A） | **加兼容层合成 uid（A/Fuchsia 原生无）** |
| macOS | entitlements + Authorization + per-user session | manifest cap + broker + 会话树 | 借 entitlements/session 做 POSIX 多用户友好（A 不借 uid 叙事） |

**关键判断**：方案 B **不是缝合**——四套系统被「解构」为四条可复用骨架（真实权限=capability、身份=令牌/entitlement 式对象、登录=受约束授权、会话=作用域树），再用 MeuOS 既有的 Job/capability/兼容层原语**重新组装**成「capability + 合成 uid 投影」模型。方案一层的「合成视图 + 翻译层」有清晰系统来源（Windows 令牌标识部分 / macOS entitlements/session / Linux 凭据兼容性），且**零权限附着、不回退到 root**——是「同一安全不变量的务实外扩」，不是「加一层 Unix 兼容后门」。

## 4. 与 MeuOS 现有规划的衔接（00 / 07 / 04 / 06 / 08）

> 本节只说明「本方案如何继承 / 强化 / 分歧于既有采纳」，不改动任何既有文档。

### 4.1 继承 `00` 已采纳裁决（与 A 完全一致）

- **A1（句柄即 capability）**、**A2（Day1 唯一 capability 模型）**：B 的真实身份=capability 集合，完全继承；无 root、无隐式权限。
- **A4（每进程 namespace）**、**A5（Job 资源账本 Day1）**：B 的会话=Job 子树 + capability 模板，多用户隔离经由 namespace/capability 作用域实现，合成 uid 仅作标签。
- **C4（合成 uid、单 Job 单 uid 视图、setuid 映射为受限 spawn+显式 cap、多线程 fork 拒绝）**：B 是 C4 的**完整操作化**——把「uid/gid 仅为合成视图」落地为「合成凭据视图 + 翻译层 + 身份清单」三件套。`07` §4.6 / 00 §C4 已写明「uid/gid 仅为合成视图」，B 把它从一句话扩展为可执行设计。
- **07 §4.5 / §4.6（setuid 禁止、uid=0 映射为句柄+rights）**：B 直接采用并补完其翻译细则。

### 4.2 与 `07` 安全模型的衔接（capability 是唯一裁决点）

- 维度 B（spawn 资源账本）是 B 会话 capability 模板的权威来源；句柄即 capability、派生只能收窄、崩溃即回收，全部继承。
- **B 对 07 §4.6 的补完**：把「Linux uid=0 / capability / seccomp / namespaces 翻译」**具体化**为 §2.6 的映射规则表——`getuid` 返回合成值、`setuid` 仅改视图、`chown/chmod` 权限位降级为合成属性、真实访问仍走 capability。内核内部`07` 模型零改动。
- **高危权永不默认**：`KERNEL_PRIV`/`DBG_POKE` 等（`07` 第五轮/第四轮回写）在 B 中同样绝不随任何合成 uid 视图像征性授予——`uid=0` 视图与这些 right 完全脱钩。
- **受约束 mint（破 confused deputy）**：认证 broker mint 会话 capability 集合时，严格「自身 rights 上限 ∩ 策略清单下限」交集（`07` §4.5），合成 uid 标签不参与交集计算。

### 4.3 与 `04` 进程/Job 模型的衔接

- B 的「会话 = Job 子树 + 合成视图 + 生命周期」直接建立在 `04` §4.1 的 Job 树之上；结构化取消（A9）、资源账本（A5）原样复用。
- B 与 `47`（进程管理·方案 B）天然契合：`47` 的 Job 命名可查询沙箱单元 + scoped 可读标识，可承载 B 的「合成 uid 标签」——scoped 标识是进程级展示键，合成 uid 是用户/会话级展示键，二者同源（都是 capability 之上的展示层，受 `DBG_INSPECT` 约束）。

### 4.4 与 `06` 文件系统 / 统一命名空间的衔接

- `06`/`07` 维度 C：文件访问 = capability（句柄 + rights），无全局 DAC。B 的 `chown/chmod` 权限位作为**合成属性**挂在文件对象上供展示，真实读写由文件句柄 rights 裁决——与 `06` 的用户态 FS + capability 模型一致。
- 多用户文件隔离：传统 Unix 靠「不同 uid 的 DAC」；B 靠「每会话不同的 namespace 投影 + 不同的文件句柄 capability 模板」（C3 每进程 namespace 的自然结果），合成 uid 只是这两者的可读标签。

### 4.5 与 `08` Linux 兼容层的衔接（翻译层落点）

- §2.6 的翻译规则全部位于 `08` 兼容层内，是 `08` 既有的「边界映射」职责的扩展；翻译层自身运行在受限句柄集下（`07` §4.6 末条），避免成为特权后门。
- `08` 现有 D 类待决（D1 沙箱默认 deny、D6 uid/gid↔capability 映射、D2 fork 边界）中，**D6 即本方案的直接落点**——B 把 D6 从「映射」升级为「合成视图 + 双向翻译规则」，且明确「映射不发生提权」。

### 4.6 与方案 A 的衔接（同一内核模型、不同兼容层外扩）

B 与 A 共享 `00`/`04`/`06`/`07`/`08` 的全部内核级地基；二者分歧仅在「兼容层是否呈现并翻译 UID/GID」。B 不否认 A 的极简价值——在形式化/TCB 极致场景 A 更优；B 选择「务实保留 UID/GID 合成投影」以换取 POSIX 多用户生态落地速度。两条方案是**同一内核模型的不同兼容层解法**，可由大喵按「优先极简可验证」还是「优先 POSIX 生态友好」拍板。

## 6. 相对传统 Unix 用户模型：摆脱的包袱与付出的代价

### 6.1 摆脱的包袱（明确清单，B 在 07 基础上操作化）

1. **`uid=0` root 万能后门**：内核不认 uid，合成 `0` 视图无任何特权；`07` 根除了「root 万能」，B 把它落到兼容层——旧程序以为自己是 root，实则只拥有被显式授予的 capability 句柄。
2. **`setuid`/`setgid` 提权模型**：SUID 位不再在执行时提权；映射为受限 spawn + 显式 capability（C4）。无「执行某二进制即变 root」的整类本地提权向量。
3. **DAC 权限位即裁决机制**：rwx/suid/sgid/sticky 不再是内核访问裁决依据，降级为合成属性（展示用）；真实访问走 capability——消灭「权限位配置错误即越权」与「DAC+capability 交互漏洞」。
4. **内核全局身份（`struct cred` / `current_uid()`）**：内核无全局身份概念，身份=句柄集合，可推理、可审计、无全局表。
5. **特权 bounding set / securebits / ambient cap**：由 capability 集合 + 身份 manifest 取代，无「关掉 bounding 即提权」类 footgun。
6. **`/etc/passwd`/`/etc/shadow` 进内核**：用户数据库是用户态认证 broker 的职责，内核不持任何账户表。

### 6.2 付出的代价（必须诚实承认，B 比 A 多一层翻译成本）

1. **兼容层翻译面是 B 相对 A 的实质新增审计面**：`getuid/setuid/chown/chmod/access/capset` 等映射规则必须正确、可审计——错译可能让旧程序「以为自己有权」而实际被 `EPERM`（功能 bug）或反之（极少，因真实裁决仍是 capability，难以错出「多给权」）。B 用「翻译层自身受限 + 真实裁决只走 capability」把风险压到最低，但翻译面本身需测试覆盖。**实质成本之一。**
2. **`geteuid()==0` 守卫逻辑无法总是完美翻译**：部分程序写 `if (geteuid() == 0) { do_privileged_thing(); } else { degrade(); }`，其中 `do_privileged_thing` 未走某个可映射的具体 syscall。B 只能让 `geteuid()` 返回合成 `0` 让分支进入特权路径，再在该路径的真实 syscall 处按 capability 裁决——若程序假定「root 必成功」而默默依赖，则仍会 `EPERM`。这类程序需要兼容层/打包层标注。**实质成本之二（轻，属兼容层固有难点）。**
3. **多用户文件隔离需重建为 capability/namespace 作用域**：传统「不同 uid 的 DAC 自动隔离文件」在 B 中要由「每会话不同的 namespace 投影 + 不同文件句柄 cap 模板」显式构造。若某遗留程序假设「别人的文件被 DAC 挡住」，该保护必须由会话的 capability/namespace 边界提供——配置成本高于「天然 DAC」。**实质成本之三。**
4. **按 uid 的审计/记账需合成 uid 层**：`wtmp`、进程记账、容器按 uid 区分——这些要基于 B 的合成 uid 标签重建一套审计视图（受 `DBG_INSPECT`），比内核原生 uid 记账多一层映射状态。**实质成本之四（轻）。**
5. **容器 uid 映射复杂度**：Linux userns 的「容器内 uid ↔ 宿主 uid」映射，在 B 中变为「容器内部合成 uid 视图 ↔ 真实 capability 作用域」的兼容投影，需谨慎设计避免「映射即越权」。但真实隔离始终由 capability 兜底，不会因映射错误而突破内核不变量。**实质成本之五（轻）。**

### 6.3 代价 vs 收益的总账

| 维度 | 传统 Unix | 方案 A（无 uid 极简） | 方案 B（uid 合成投影） |
|---|---|---|---|
| 真实权限源 | uid + DAC + cap 混杂 | capability 集合 | **capability 集合（同 A）** |
| root 后门 | 存在 | 无 | **无（同 A；合成 0 无特权）** |
| POSIX 多用户生态 | 原生 | 需深改/重写 | **兼容层翻译即可跑（友好）** |
| 内核 TCB | 大（cred/DAC/cap 交互） | 最小（纯 cap） | **最小（同 A；uid 在兼容层）** |
| 兼容层审计面 | — | 小（无 uid 可翻） | **略大于 A（翻译层），仍远小于 Unix** |
| 运维/多用户直觉 | uid 原生 | 纯 capability 视图（学习成本） | **capability + 合成 uid（更可落地）** |

**净判断**：B 用「一层零权限附着的合成 uid 视图 + 一套兼容层翻译规则」换取「POSIX 多用户生态与存量二进制的最大友好度」，内核安全不变量零退让（与 A 完全相同）；代价是兼容层翻译面比 A 略大，但远小于 Unix 的 cred/DAC/cap 混杂 TCB。选择 A 还是 B，是大喵在「极简可验证优先」与「POSIX 多用户生态友好优先」之间的权衡。

## 7. 与方案 A（52-用户系统-方案A）的关键差异（专节）

> 本节把 B 与同僚并行的方案 A「无 UID/GID 能力身份」做正面对比，便于拍板。

### 7.1 相同点（内核级，100% 一致）

1. **真实权限源都是 capability 集合**（句柄+rights），无 root、无隐式权限。
2. **内核都无 uid/gid 概念**：无 `struct cred`、无 `uid==0` 裁决、无 DAC 权限位裁决。
3. **setuid 提权都禁止**：都映射为受限 spawn + 显式 capability（C4）。
4. **会话都=Job 作用域 + 生命周期 + 资源账本**（A5/A9），多用户隔离都靠 capability/namespace 作用域。
5. **认证都=受约束 capability minting**（用户态 broker，破 confused deputy）。
6. **高危权永不默认**（`KERNEL_PRIV`/`DBG_POKE` 等）在两者中一致。

### 7.2 分歧点（仅兼容层 / 呈现层）

| 维度 | 方案 A（无 UID/GID 能力身份） | 方案 B（UID/GID 合成投影 + capability 叠加） |
|---|---|---|
| 兼容层是否呈现 uid/gid | **否**（连合成视图都无） | **是**（合成视图，零权限附着） |
| `getuid()` 等返回值 | 无此语义（需改写/兼容层深模拟） | 返回合成 uid/gid（兼容层直接给） |
| 多用户「主体标识」 | 仅 capability 句柄 / scoped 标识 | 合成 uid 标签（可读、可记账） |
| 凭据翻译层 | 不存在 | **存在（08 内双向映射规则）** |
| 登录叙事 | 仅「mint capability」 | 「mint capability + 贴合成 uid 标签」 |
| POSIX 多用户生态友好度 | 低（需深改） | **高（翻译层覆盖）** |
| 兼容层审计面 | 小 | 略大（翻译规则） |
| 内核 TCB | 最小 | **最小（与 A 同；uid 全在兼容层）** |
| chown/chmod 权限位 | 视为无（或直接 ENOSYS/忽略语义） | 作为**合成属性**存储/展示，真实访问走 cap |

### 7.3 一句话差异

- **方案 A**：内核纯 capability、连「合成 uid」都不给——身份即 capability 本身，最极简、对存量多用户生态最不友好。
- **方案 B**：内核同样纯 capability、但兼容层务实保留 UID/GID 合成视图与凭据翻译——身份仍是 capability、uid 只是「给人类与旧程序看的投影」，对 POSIX 多用户生态最友好，代价是兼容层多一层零权限附着的翻译面。

### 7.4 推荐拍板视角

- 若优先**极简可验证 TCB / 形式化友好 / 不打算跑认 uid 的存量生态** → 选 A。
- 若优先**POSIX 多用户生态 / 容器 / 守护进程以 uid 区分主体 / 按 uid 运维记账** → 选 B（且 B 与 `07` 已采纳的「合成 uid」C4 立场天然同源，落地阻力更小）。
- 二者可共存于路线图：内核模型完全一致，B 仅是 A 之上「加一层兼容投影」——若未来决定走 A，只需不启用 B 的翻译层与合成视图即可，无架构返工。

## 8. 方案 B 自身的开放议题（不阻塞 Day1，待原型验证）

1. **合成视图的「稳定 uid 分配」权威**：多用户场景下，合成 uid（如 alice=1000）由谁分配？建议由认证 broker + 策略清单持有一张「身份名 ↔ 合成 uid ↔ capability 模板」映射，用户态、不在内核。是否需监督者 `GRANT` 类权做受约束 mint（对齐 `07` §4.5）？
2. **`chown/chmod` 合成属性的存储归属**：权限位作为合成属性挂在文件对象上，由 `06` FS 服务存储还是兼容层缓存？真实访问仍走 capability，合成属性仅展示——需与 `06` 协同定义存储点。
3. **容器 uid 映射的兼容投影边界**：Linux userns 的「容器内 uid ↔ 宿主」映射，在 B 中如何不越权地投影为合成视图？真实隔离由 capability 兜底，映射错误不应突破内核不变量（C4/D6 协同）。
4. **`access()` 模拟返回值的正确性**：旧程序据 `access()` 返回值短路，翻译层需据「进程 capability 集合」模拟返回值；何时返回真、何时模拟、何时直接 `EPERM`，需基准与测试覆盖（§6.2 成本之二）。
5. **认证 broker 的 `AUTH_ISSUE` 是否独立 right（bit 48+ 预留）**：broker 持受限 `GRANT` 即可 mint 会话集合；是否需一个专属 `AUTH_ISSUE`（类比 `debug-issuer`，`17` C9）做受约束 issuer，避免普通 `GRANT` 被复用为「认证授权」语义？建议 bit 48+ 预留区，不挤占已冻结位。
6. **按合成 uid 的审计/记账与 `DBG_INSPECT` 对齐**：`wtmp`/进程记账/容器按 uid 区分，需基于合成 uid 标签 + `DBG_INSPECT` 子树粒度（`12`）重建审计视图，避免「标识复用导致日志串扰」（与 `47` scoped 标识同议题）。

## 第七轮精细裁决（C-G4）：是否启用合成 uid/gid 兼容层 —— **采纳 B（启用零权限附着的合成 uid 视图 + 翻译层）**

> 本节为第七轮「先细后精」对 `00` 第六轮 §6.3 架构级冲突 **C-G4**（`56` §7.3 冲突 4）的精细裁决回写。原 §7/§8 开放议题（合成 uid 稳定分配、chown 合成属性归属、容器 uid 映射、`access()` 模拟返回值、`AUTH_ISSUE` right 等）保留为待原型验证项；本裁决只锁定「是否启用合成 uid/gid 兼容层」这一架构级分歧，并以**修订式追加**落定，不删改 §1–§9 既有内容。

### 1. 裁决结论（默认采纳 56 推荐 = B，并补精细边界）

**采纳方案 B（本文）立场：内核保持纯 capability、无 root、无 uid（与方案 A 内核模型 100% 一致）；兼容层启用 UID/GID 合成视图 + 凭据翻译层，零权限附着。** 方案 A（52）的「无合成 uid 极简身份」作为**长期极简目标**（不可逆方向）保留，但 Day 1 主线为 B 的合成投影。

判定依据（与 `56` §5.2 推荐一致，并据必读文档收紧边界）：

1. **内核真相与 A 100% 一致，分歧仅在外层投影**：`56` §5.1 已确认 A 与 B 在内核层完全相同（纯 capability、无 root、无 uid）；B 不是 A 的对手，而是 A 的兼容层扩展。启用 B 仅是「启用一层零权限附着的翻译/展示面」，不引入任何内核特权原语，无架构返工。
2. **与 C4（合成 uid 立场）同源承接**：`00` §3 C4 已定稿「uid/gid 仅为合成视图，单 Job 单 uid 视图起步，setuid 二进制映射为受限 spawn + 显式 capability（不引入提权）」；`07` §4.6 进一步将 Linux `uid=0` 特权操作映射为「持有对应内核对象句柄 + rights」、内核内部不识别 root。本文（B）是 C4 + `07` §4.6 的完整操作化——合成视图 + 翻译规则 + 身份清单 + broker 受约束 mint，把一句话立场展开为可执行设计。
3. **真实裁决只走 capability，零权限附着**：合成 uid/gid 是「给人类与旧程序看的投影/记账键」，绝不携带任何内核权限；`getuid`/`setuid`/`chown`/`access` 由 `08` 翻译层映射为 capability 操作或返回合成值，真实访问裁决仍由 capability 集合完成。故启用 B **不侵蚀任何内核安全不变量**（无 root 后门、无 setuid confused deputy、无 DAC 权限位裁决）。
4. **生态 / 自举阻力最小**：POSIX 多用户语义（容器/守护进程以 uid 区分主体、按 uid 记账）、`mkit`(`08`) 兼容层翻译面更小，单用户自举即可、多用户登录/认证 broker 后置——与 MeuOS「从零、现代化、capability Day 1、兼容渐进」立场严丝合缝（`56` §5.2 / `00` §6.2）。

### 2. 微调项（相对 `56` 推荐的精化）

- **兼容层范围定稿（直接回应 `56` §7.3 冲突 4 待裁定项「兼容层范围待决 + C4 已部分定、操作化待决」）**：启用 B 的翻译层，范围为「UID/GID 合成视图 + 凭据双向映射 + 合成属性存储/展示」，覆盖 `geteuid()==0` 守卫逻辑与容器 uid 映射；真实访问裁决一律回落 capability（C4/D6 协同）。`access()` 模拟返回值须基于「进程 capability 集合」据 `56` §8 优先级 4 给出测试基准，避免旧程序据错误返回值短路。
- **合成视图权威归属定稿**：合成 uid 的「稳定分配」权威（身份名 ↔ 合成 uid ↔ capability 模板映射）归属**认证 broker + 策略清单**（用户态、不在内核），由受约束 `GRANT` 派生 mint 会话集合（`07` §4.5），不新建内核对象、不引入新 right bit（bit 48+ 维持预留，不与 `GRANT` 语义复用）。
- **Day 1 落地口径**：对齐 `56` §5.2 / `00` §6.2，合成 uid 视图建议 Day 1 轻量落地（单 Job 单 uid 视图起步），不阻塞启动；多用户登录/认证 broker 后置演进。
- **与方案 A 的关系定稿**：内核模型 A/B 完全一致，本裁决**不引入任何专属内核机制**；若未来评估降级为 A（无合成 uid 极简身份），只需不启用 B 的翻译层与合成视图，即回退为 A，**无架构返工**（M2+ 评估，见 `00` §6.3 C-G4 原推荐）。

### 3. 永不退化的不变量

无论采纳 B，内核内部模型**永不识别 root、永不引入 uid 数字作为权限裁决源、永不允许 setuid 提权**（`07` §4.5 / `07` §4.6 / C4 铁律）。合成 uid/gid 仅作零权限附着的展示/记账/兼容投影，真实权限裁决 100% 由 capability 集合完成。方案 A 的「无 uid 极简身份」仍是 TCB 极致与形式化友好的长期方向，B 只是把兼容投影启用的务实取径——本裁决不关闭该收敛路径（M2+ 评估降级为 A）。
