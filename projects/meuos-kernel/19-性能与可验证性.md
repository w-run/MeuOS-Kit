## 1. 「应该是什么样」推演（解构型）

### 1.1 总纲：理想 lean hybrid 的性能与可验证性画像

先不问「MeuOS 现在能多快」，而问「在『缩 TCB 与性能』之间，理想的务实混合内核**应该**如何既小、又可验证、又可接受地快」。

推演结论（解构型基线）：

1. **机制在内核、策略出核，但数据通路留在内核**。FS/网络/驱动逻辑出核以缩 TCB，但页面数据、报文缓冲区、能力判定走内核直连——避免把每一次字节搬运都变成一次 IPC。这是 lean hybrid 相对纯微内核的性能正当性，也是「应该是什么样」的核心。
2. **权限检查应「在获取句柄时一次性完成，而非每次操作都重做」**。capability 的 `rights` 在 `mint`/`open` 时已收窄并固化为句柄属性；运行期热路径只做「句柄存在 + 权限位命中」的 O(1) 位运算，不该回溯 derivation tree 或重新 unwrap 密钥。这是把安全成本从第 4 节反模式中挪出热路径的关键设计原则。
3. **可观测性是一等公民，且零成本采样**。inspect 树与事件流（`12`）应让每个热路径的延迟、拒绝、缺页、crypto 成本**可量化且默认内建**，而非事后 printk。但度量本身不得成为热路径瓶颈——采用「计数器 + 直方图（lock-free / per-CPU）+ 采样」而非「每次操作写一条事件」。
4. **可验证性按「不变量价值」分层**：极小、边界清、不可错的组件（capability 监视器、IPC 端点状态机、rights 检查）值得形式化；其余靠强类型 + 测试 + fuzz。Rust 类型系统承担「权限不可伪造、所有权不变量」这一整类验证负担，使形式化只需覆盖 TCB 中剩余的少量 unsafe 与算法核心。

### 1.2 五大关键热路径的「应该是什么样」

#### 1.2.1 syscall → capability 检查

**现状对照**：mkit 薄层（`01` §4.2）把 Linux syscall 子集解码后，分两类——(a) 内核直接处理（如 `exit`/`sched_yield`/匿名 `mmap`），应零 IPC；(b) 转发给用户态服务（涉及具体文件/套接字）。两类都要先过 capability 检查。

**应该是什么样**：
- 能力检查 = 一次句柄表查（进程私有 handle 表，`07` §5.1 Zircon 风格）+ 一次 `rights` 位与运算。纯 Rust TCB 内，目标 **< 20 ns**（量级，含 TLB/缓存暖态）。
- 检查失败（越界）直接走 fail-closed（`07` pledge 越界即终止 / IPC 拒绝），且**必须**作为一条结构化事件落入 `12` 的事件流（`cap_check: denied, right=WRITE, handle=<id>`），供安全审计，不得静默。
- 内建可观测性：`kernel/cap/checks`（总数）、`kernel/cap/denials`（拒绝数）、`kernel/cap/check_latency_ns`（直方图）。这正是 §4.4 量化 C2「每次 unwrap 的 check 成本」的取数点。

#### 1.2.2 IPC 跨服务

**现状对照**：`05` 定义 Channel / EventPort / SHM / Service Registry，端点即 capability。跨服务调用 = `channel_call`（rendezvous + badge）。

**应该是什么样**：
- 快速路径（`channel_call`，无 cap 转移、小消息入寄存器）应达到 **seL4 级 fastpath**：同核往返量级 **≤ 500 ns**，跨核量级 **≤ 1–2 µs**（以 §2 锚点为参照，需在 MeuOS 硬件复测）。
- 大数据走 SHM（capability 句柄经一条小 Channel 消息传递 + EventPort `CHAN` filter 通知就绪），**零拷贝**，不占 IPC 快速路径带宽。
- 内建可观测性：`kernel/ipc/call_latency_ns`（按对端服务分桶）、`kernel/ipc/fastpath_hits`、`kernel/ipc/cap_transfer_count`（cap 转移次数，昂贵路径计数器）。

#### 1.2.3 缺页 pager（文件映射）

**现状对照**：`06` §4.4.1 的 VMO + pager 模型——FS 服务是文件 VMO 的 pager，客户端缺页时内核向 FS 服务发页请求，FS 服务读 extent → 解压 → 解密 → 校验 → 供页。数据通路在内核，逻辑在用户态。

**应该是什么样**：
- **冷缺页（pager 往返一次 + extent I/O）**：量级 **≤ 2–5 µs**（含一次 IPC 往返 + 一次 extent 读 + 解密/校验）。文件系统热页由内核 VMO 页缓存驻留，避免每次 pager 往返——即 FS 服务**供页后页面留在内核 VMO**，后续同页命中走内核缓存（量级 **≤ 200 ns**），不再触达 FS 服务。
- **COW 缺页（写时复制）**：纯页表写保护 + refcount（来自 `03` §4.3.3），量级 **≤ 200 ns**，无 IPC。
- 内建可观测性：`kernel/mm/pagefault/cold_pager_us`、`kernel/mm/pagefault/warm_cache_ns`、`kernel/mm/pagefault/cow_ns`、`kernel/mm/pagefault/by_type`（直方图）。这是 §4.2 量化「出核代价」的核心指标。

#### 1.2.4 fork 仿真 CoW

**现状对照**：原生 `meu_spawn` 无 fork（`04` §4.2）；Linux 兼容层 fork 走「VMO child 快照 + 受限语义」仿真（`00` C4）。

**应该是什么样**：
- fork 仿真的成本应与**页面数解耦**，只与「地址空间对象数（VMO/VMAR 数量、句柄表、命名空间绑定）」成正比——因为 CoW 是惰性的，不复制物理页。典型进程的快照量级 **≤ 数十 µs**（元数据操作），而非 ms 级物理复制。
- 真正的代价在**之后**：若子进程写穿整个堆，触发 COW 缺页风暴（§4.3 反模式 4）。故应鼓励 `posix_spawn` 改写（`04` §5.2），fork 仅作受限兜底。
- 内建可观测性：`kernel/proc/fork_emu_us`、`kernel/proc/cow_faults`（fork 后写时复制缺页总数）。

#### 1.2.5 加密 / 校验和 extent 读写

**现状对照**：`06` §4.2 的 extent 级校验和（覆盖密文）+ 压缩（加密前）+ per-file/extent AEAD 加密，密钥 unwrap 权 = 文件句柄 right（C2）。

**应该是什么样**：
- **校验和验证**（BLAKE2b / xxHash3，覆盖密文）：量级 **~ 0.5–1 周期/字节**，4KB extent 约 **1–3 µs** CPU。
- **AEAD 解密**（ChaCha20-Poly1305 / AES-GCM）：硬件加速下（AES-NI / ARM CryptoExt / RISC-V Zk+Vector crypto）量级 **~ 0.5–2 周期/字节**，4KB 约 **1–8 µs**；**i386 无硬件 AES**时为软件路径，量级高一个数量级（**~ 10–30 µs/4KB**），见 §3.3。
- **关键设计原则（接 C2）**：密钥 unwrap / 派生**只在 `open`/mint 时发生一次**，结果缓存于 VMO/pager 上下文；稳态的每次 extent 读/每页缺页**不重新 unwrap**，只做「解密 + 校验和」。若错误地做到「每次读页都 unwrap 密钥」，会在 pager 热路径上叠加一次 µs 级密钥操作，直接击穿 §1.2.3 的冷缺页预算——这是 §4.4 必须标红的架构要求。
- 内建可观测性：`kernel/fs/extent/read_crypto_us`、`kernel/fs/extent/checksum_fail`（静默损坏检测数）、`kernel/fs/extent/throughput_mb_s`。

### 1.3 目标预算表（含可观测性内建点）

| 热路径 | 应该的延迟/吞吐预算（量级，暖态） | 是否走 IPC | 内建可观测性落点（接 `12`） |
|---|---|---|---|
| syscall → capability 检查 | **≤ 20 ns**（位运算） | 否 | `kernel/cap/check_latency_ns` + `denials` |
| IPC 快速路径 `channel_call` 同核往返 | **≤ 500 ns** | 是（同核 rendezvous） | `kernel/ipc/call_latency_ns` + `fastpath_hits` |
| IPC 跨核往返 | **≤ 1–2 µs** | 是 | 同上（按对端分桶） |
| 文件冷缺页（pager 往返） | **≤ 2–5 µs** | 是（一次） | `kernel/mm/pagefault/cold_pager_us` |
| 文件热缺页（内核 VMO 缓存命中） | **≤ 200 ns** | 否 | `kernel/mm/pagefault/warm_cache_ns` |
| COW 缺页 | **≤ 200 ns** | 否 | `kernel/mm/pagefault/cow_ns` |
| fork 仿真（CoW 快照元数据） | **≤ 数十 µs** | 否（内核内快照） | `kernel/proc/fork_emu_us` |
| extent 读：校验和（4KB） | **~ 1–3 µs** | 否 | `kernel/fs/extent/read_crypto_us` |
| extent 读：AEAD 解密（4KB，硬件加速） | **~ 1–8 µs** | 否 | 同上 + `checksum_fail` |
| extent 读吞吐（硬件 crypto/核） | **≥ 1 GB/s** | 否 | `kernel/fs/extent/throughput_mb_s` |

> 注：上表为「应该的」量级目标，非承诺值。所有数字须在 §3 的 `meu-bench` 套件上于 MeuOS 硬件复测后方可定为门禁；参照锚点见 §2.1。

## 3. MeuOS 性能 / 可验证性目标与度量方案

### 3.1 benchmark 套件（自主改造 lmbench / cyclictest）

**命名**：`meu-bench`（内核内建 + 用户态运行，结果经 `12` 的 inspect/事件流暴露，亦可落 `.msys` 卷供 CI 比对）。

自主改造，不平移 lmbench/cyclictest 语义，而是对齐其度量维度：

| 基准（meu-bench 子项） | 对应 lmbench/cyclictest 维度 | 测量对象 | 输出 |
|---|---|---|---|
| `lat_syscall` | lmbench `lat_syscall` | null syscall / `read` / `mmap` / `exit`（分 mkit 直处理 vs 转发） | 延迟直方图（ns） |
| `lat_ipc` | lmbench `lat_pipe`/`lat_unix` | `channel_call` 同核 / 跨核 / 带 cap 转移 | 往返延迟（ns）+ fastpath 命中率 |
| `lat_ctx` | lmbench `lat_ctx` | 线程上下文切换（接 `04` 调度器） | 切换延迟（ns） |
| `lat_pagefault` | lmbench `lat_pagefault` | 匿名缺页 / 文件冷 pager 缺页 / 文件热缓存缺页 / COW 缺页 | 各类型延迟（ns/µs） |
| `lat_fork` | lmbench `lat_fork`/`lat_proc` | 原生 `meu_spawn` vs 兼容层 fork 仿真 | 创建延迟（µs）+ 之后 COW 缺页数 |
| `bw_extent` | lmbench `bw_mem`/`bw_file_rd` | extent 读/写吞吐：crypto on/off、校验和 on/off、各架构 | 吞吐（MB/s）+ 单 extent crypto 耗时 |
| `cyc_lat`（cyclictest 等价） | cyclictest | 调度最坏情况延迟（EEVDF `04` §4.3） under 负载 | 尾延迟（µs/ms）分布 |
| `cap_check` | （新增，自主） | capability 检查延迟 + 拒绝计数（量化 C2） | `check_latency_ns` + `denials` |

**门禁形态**：`meu-bench` 作为 `bootstrap.sh` Phase K（`11` §4.3）的可选回归子门禁；结果与上一次 golden 比对，回归超阈值（如 IPC 往返 +20%、pager 冷缺页 +50%）则告警。门禁只观测、不阻塞构建（原型期），M2 之后逐步收紧。

### 3.2 IPC 往返基准（锚点）

- **同核快速路径目标**：`channel_call`（无 cap 转移、小消息入寄存器）往返 **≤ 500 ns**，对齐 seL4 公开 microbench 量级。
- **跨核快速路径目标**：**≤ 1–2 µs**（对齐 seL4 跨核量级与 `00` 总览提到的 1.2 µs 量级）。
- **带 cap 转移路径**：明确更慢（需 CSpace 槽位分配 + derivation 记录），目标 **≤ 数 µs**，且**不作为高频路径优化目标**——批量授权应在 `open`/mint 时一次完成（呼应 §1.1 原则 2）。
- **锚点复现要求**：在 x86_64 / aarch64 两架构（M5，`11`）上分别复测 seL4/Zircon 同级基准作「同硬件对照」，确保 MeuOS 数字有可比基线，而非孤立自报。

### 3.3 五架构差异

| 架构 | Rust TCB 状态 | 性能特征与风险 | crypto 加速 | 对性能/可验证性的影响 |
|---|---|---|---|---|
| **x86_64** | Rust TCB（Tier 2 `no_std`） | 基准架构，AES-NI 成熟 | AES-NI / PCLMUL **≥ 1 GB/s** | 主验证架构；形式化/基准最完整 |
| **aarch64** | Rust TCB（Tier 2） | ARM CryptoExt（AES/SHA/PMULL） | **≥ 1 GB/s** | 与 x86_64 同为双架构重点（M5）；crypto 路径对等 |
| **riscv64** | Rust TCB（Tier 2） | 向量 crypto 扩展（Zk/Zvkn）依实现；标量软路径慢 | 取决于实现，**可能 < x86/aarch** | 若缺硬件 crypto，extent 读走软 AES，pager 冷缺页预算上调；需实测 |
| **loongarch64** | Rust TCB（Tier 2） | 自有 crypto 指令；成熟度待验 | 中等 | M5 后移（`11` §5.4）；先保证正确后优化 |
| **i386** | **纯 C（无 Rust 裸机 target，`02` C2）** | **无 Rust 性能惩罚**（TCB 本就是 C）；但**丢失 Rust 类型系统的验证负担承担** | **无 AES-NI，软件 AES ~ 100–300 MB/s** | 1) extent 读吞吐较其他架构低一个数量级 → §1.2.5 预算对 i386 单列；2) capability 不可伪造性只能靠运行时检查 + 人工审计（无 Rust 私有构造/非 Copy 强制）→ 02 §5-2 的 TCB 审计须对 i386 C 实现加倍；3) 不引入「为性能引入 Rust」的动机，i386 路径反而更简单 |

**核心论断**：i386 是「无 Rust 性能惩罚、但有验证负担代价」的架构——它的慢来自 crypto 硬件缺失，而非 Rust 缺失；而 Rust 缺失带来的是**可验证性退化**（需更多运行时/人工保障），不是性能退化。这一区分对 §3.4 的「Rust 类型承担哪部分验证」与 §4.2 的「缩 TCB 代价」都关键。

### 3.4 可验证性分层策略（接 `20-形式化方法.md`）

**分层原则**：按「不变量价值 × 边界清晰度 × 代码量」三因子决定验证手段。

**(A) 值得形式化（移交 `20` 做精化/模型验证）**——TCB 中极小且不可错者：
1. **capability 监视器**：句柄表不变量（无悬垂、无伪造）、`rights` 位运算语义、`revoke` 的 derivation tree 传播完整性（与 `07` §5.4 对齐，默认显式 close、可选 derivation 追踪）。
2. **IPC 端点状态机**：rendezvous 语义、badge 多路复用、cap transfer 的所有权转移（move/copy 语义对齐 `05` §5-2）。
3. **rights 检查**：`mint` 时权限收窄（交集语义，防 confused deputy，`06` §6-2）、运行期位检查的正确性。

> 移交 `20` 的接口契约：上述三者的**抽象规约（状态 / 不变量 / 操作前置后置条件）**由本文件 §4.1 暴露，形式化方法文档负责选工具（Rust 内联证明 / 模型检测 / 精化证明）与产出证明脚手架。MeuOS 不追求 seL4 级端到端，但求「小核心可被证明」。

**(B) 靠强类型 + 单元测试 + 集成测试覆盖**——TCB 中较大但边界清者：
- 调度器 EEVDF 虚拟截止期计算（`04` §4.3）、资源账本配额强制（`04` §4.4）、MM buddy/COW refcount 单一真相源（`03` §5-2）、VMO/VMAR 权限层级（不可放宽父 VMAR 已收紧权限，`03` §4.3.4）、pager 协议（缺页→供页→映射闭环，`06` §4.4.1）。

**(C) 靠 fuzz / sandbox 补偿**——**排除出 TCB 的高风险面**（刻意不入 TCB）：
- **mkit Linux 兼容层（`02` §4.2 排除出 TCB）**：因与 Linux UAPI 逐字段对齐、表面积大，用 fuzz（syscall 模糊）+ sandbox（capability 受限运行）+ 回归测试补偿，而非形式化。这正是「排除出 TCB 不是免验证，而是换更便宜的验证手段」。

**(D) Rust 类型系统承担的验证负担**（量化）：
- **句柄不可伪造**：`Handle` 类型非 `Copy`、私有构造、借用检查 → 编译期消除「伪造/复制逃逸」类错误，运行期仅做存在性检查（`02` §4.4）。
- **所有权不变量**：`OwnedFrame`（Drop→归还 buddy）、`MappedPages<'a>`（生命周期绑定映射有效性）、`Arc<Vmo>`（COW `make_mut`，`03` §4.5）。
- **VMAR 权限层级**：类型区分「可收紧/已收紧」状态，编译期阻止权限放宽。
- **EEVDF 虚拟截止期**：safe Rust 计算，无裸指针。
- **目标度量**（`02` §5-6）：TCB 内 safe Rust 占比 **> 90%**；剩余 unsafe 仅位于 arch/asm 边界与 abstractions 层，逐块双人评审。`meu-bench` + CI 统计 `unsafe` 行数/块数作为 TCB 规模回归门禁。

### 3.5 度量门槛（regression gate，雏形）

| 指标 | 原型期门禁（观测） | M2+ 收紧目标 |
|---|---|---|
| IPC 同核往返 | 报告值，不阻塞 | ≤ 500 ns，回归 > 20% 告警 |
| pager 冷缺页 | 报告值 | ≤ 5 µs |
| TCB 内 safe Rust 占比 | ≥ 80% | ≥ 90% |
| `unsafe` 行数（TCB） | 仅统计 | 超阈值阻塞合并 |
| fork 仿真延迟 | 报告值 | ≤ 数十 µs + COW 缺页计数 |

### 4.2 缩 TCB 的代价量化

缩 TCB 的本质是把「代码量/信任」从内核搬到用户态，换取可验证性与故障隔离，**代价是跨地址空间的 IPC / pager 往返与 crypto CPU**。量化框架：

| 出核动作 | 缩小的 TCB | 付出的性能代价 | 缓解手段（已在本文/他文） |
|---|---|---|---|
| FS 逻辑出核（`06`/`01`） | FS 代码（巨量）移出 TCB | 冷缺页 +1 次 pager IPC（≤ 2–5 µs）；元数据 `open`/`read` +1 次 Channel 往返 | 数据通路走内核 VMO（零拷贝）、热页内核缓存（§1.2.3） |
| 网络栈出核（`01`） | 协议栈移出 TCB | 报文经 SHM + 一次通知 IPC | SHM 零拷贝 + EventPort `CHAN` filter |
| 驱动出核（`10`） | 驱动代码移出 TCB | 中断转发 + IPC 通知；高 IRQ 设备 IPC 风暴 | 中断合并 + 轮询混合（`10` §5-1）、敏感设备留核 |
| 监督策略出核（`04`） | 策略引擎移出 TCB | 仅崩溃/事件经 exception channel（低频） | 低频，代价可忽略 |

**量化结论**：缩 TCB 的代价绝大多数是「**低频控制路径 + 一次 IPC**」与「**crypto CPU（可硬件加速）**」，均非持续吞吐瓶颈——前提是数据通路留在内核（VMO/pager/SHM）。一旦把数据通路也搬出核（错误做法），代价才变成持续带宽损耗。

### 4.3 反模式清单（何时出核反而更慢）

| 编号 | 反模式 | 为何更慢 | 规避 |
|---|---|---|---|
| AP-1 | **数据通路出核**：把文件/网络字节搬运也走 IPC 而非 VMO/SHM | 每次字节搬运一次拷贝 + 上下文切换，吞吐塌缩 | 数据走内核 VMO/SHM，逻辑走用户态（`06` §2.3） |
| AP-2 | **用户态驱动无中断合并**：高 IRQ 设备（10G+ 网络）每中断一次 IPC 通知 | IRQ 转发 IPC 风暴，CPU 空转 | 中断合并 + 轮询混合（`10` §5-1）；或敏感设备留核 |
| AP-3 | **过细粒度 capability 检查**：每字节/每操作重做 derivation tree 回溯或重新 unwrap 密钥 | 把 µs 级密钥/派生操作塞进热路径 | 权限在 `mint`/`open` 一次收窄；运行期只位运算（§1.1 原则 2、§4.4 C2） |
| AP-4 | **fork 仿真后全堆写穿**：多线程大进程 fork 后大量 COW 缺页 | COW 风暴，延迟从数十 µs 退化到 ms | 鼓励 `posix_spawn`（`04` §5.2）；fork 仅受限兜底（C4） |
| AP-5 | **可观测性本身成瓶颈**：每个操作写一条结构化事件 | 事件写入压垮热路径，观测反成瓶颈 | 计数器/直方图/采样，非逐操作事件（`12` 事件流仅订阅消费） |
| AP-6 | **i386 上强制 extent 级硬件 crypto 假设** | 无 AES-NI，软件 AES 慢 5–10×，pager 读路径击穿预算 | i386 单列预算（§3.3）；或用 C 内联汇编软实现 + 接受降级 |
| AP-7 | **该用 SHM 却用 Channel 传 bulk** | 大块数据走 Channel 内核拷贝，浪费快速路径 | 大数据 SHM + 小消息 Channel 通知（`05` §4.3） |
| AP-8 | **revoke 全量 derivation 追踪常开** | 每次派生记录 derivation tree，热路径分配/追踪开销 | 默认显式 close（`07` §5.4），derivation 追踪按需开启 |

### 4.4 跨域冲突对性能的牵连（接 `00` C1–C14）

| 冲突 | 性能牵连点 | 本文量化/要求 |
|---|---|---|
| **C1（物理内存归属）** | buddy vs untyped 影响分配器在缺页/转交热路径的延迟；untyped 式全用户态管理增加分配 IPC | 推荐折中（内核 buddy 拥有物理页，VMO 为视图）：分配器延迟留在内核、可控；`03` §5-1 待定，需测 buddy 热路径 |
| **C2（密钥=capability）** | 每次 extent 读/缺页若都 unwrap 密钥 → 热路径叠加 µs 级密钥操作 | **架构要求**：密钥 unwrap 只在 `open`/mint 一次，稳态读只解密+校验和（§1.2.5）；该 cost 用 `kernel/cap/check_latency_ns` + `kernel/fs/extent/read_crypto_us` 量化。若执行层做成「每次读都 unwrap」，则直接违反 §1.3 预算 |
| **C3（命名空间模型）** | 每进程 namespace 在 `spawn` 时组装，增加 spawn 一次性延迟（非热路径） | 一次性成本，可接受；Spawn 延迟由 `lat_fork` 的 spawn 分支观测 |
| **C4（fork 仿真）** | CoW 快照元数据成本 + 之后写穿 COW 风暴 | §1.2.4 预算 + AP-4；多线程序 fork 仿真受限（`04` §5.2） |
| **C8（设备能力签发/网关）** | 内核态驱动每次 MMIO 经能力网关 check（数指令）；用户态驱动每次访问 IPC | 内核态驱动 check 成本 ≈ capability 检查（§1.2.1 ≤ 20 ns）；用户态驱动走 AP-2 规避 |
| **C11–C14（兼容层范围）** | 兼容表面越大，mkit 解码成本在 syscall 热路径越高 | mkit 直处理类须对齐 Linux syscall 量级（§1.3）；大兼容面下的 decode 开销由 `lat_syscall`（mkit 直处理 vs 转发）分项观测 |

## 5. 自主结论 + 待决项

### 5.1 自主结论

1. **lean hybrid 的性能正当性 = 数据通路留核、逻辑出核**。只要 VMO/pager/SHM 把字节搬运留在内核，缩 TCB 的代价就收敛为「低频控制 IPC + 可硬件加速的 crypto CPU」，而非持续带宽瓶颈——这是 MeuOS 相对纯微内核（Redox/MINIX3 出核过头的代价）的关键差异化取舍。
2. **capability 检查必须「获取时一次、运行期位运算」**，否则 C2 的密钥 unwrap 与过细粒度检查（AP-3）会击穿热路径预算。这是本文对 `07`/`06` 的硬接口要求。
3. **可观测性零成本内建**：每个热路径的延迟/拒绝/缺页/crypto 成本默认暴露为 inspect 节点 + 采样事件流（接 `12`），且本身不得成为瓶颈（AP-5）。这把「性能目标」与「可验证度量」合成一体。
4. **可验证性分层**：极小且不可错的 capability 监视器 / IPC 端点 / rights 检查值得形式化（移交 `20`）；其余靠 Rust 类型系统 + 测试；mkit 兼容层排除出 TCB 后用 fuzz/sandbox 补偿。Rust 类型承担「句柄不可伪造 + 所有权不变量 + VMAR 权限层级」整类验证，目标 TCB 内 safe Rust > 90%。
5. **五架构差异的本质是验证负担而非性能**：i386 无 Rust 性能惩罚但有可验证性退化（需加倍运行时/人工保障）；crypto 加速差异（i386 无 AES-NI）使 extent 读预算需单列，但不影响架构正确性。
6. **反模式清单（AP-1~AP-8）是可执行的「出核红线」**：尤其 AP-1（数据通路出核）与 AP-3（热路径重 unwrap）是 lean hybrid 最容易踩的坑，应在执行层作为设计评审清单。
