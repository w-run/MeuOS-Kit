# 23 - ABI 稳定性与版本（API/ABI 稳定性策略）

> 子领域调研 / 规划设计文档，由 kernel-plan 团队「新维度调研员」（general-purpose-15，lite/hy3）产出。
> 适用范围：MeuOS 自研内核的「对外/对内接口稳定性分级」与「版本协商/弃用机制」设计提案。
> 关联约束（来自 `00-总览与路线图.md` 与各子文档）：外部兼容 Linux ABI（兼容层）、内部自主设计；务实混合内核；Rust+C；capability-based 安全 Day 1；三大方向 = ①统一 FS 层（06）+ ② spawn 进程管理（04）+ ③ capability 安全（07）。

## 0. 一句话结论（先给答案）

MeuOS 的稳定性承诺应当是**三层分级、且明确「保留破坏权」的**：Linux 兼容 ABI 对外必须稳（但只稳 08 声明的覆盖子集）、原生 syscall/capability API 演进期明确不稳（靠 mkit/libc 屏蔽）、用户态服务间 IPC 协议靠**版本协商**稳（参照 FIDL）。而 `.msys` 整卷原子切换（06 §4.3）让内核+服务+用户态**同版本整体升级**，结构性弱化了内核↔在树服务间细粒度 ABI 冻结的必要性——这是 MeuOS 相对 Linux 发行版的根本杠杆。

## 1. 「应该是什么样」——稳定性策略推演

### 1.1 先问：一个还在演进的自研内核，稳定性承诺「应该」在哪划界

解构 Linux 的隐含契约可见：Linux 对**用户态 syscall ABI** 承诺「绝不破坏」（Linus 铁律），却对**内核内部 API**（含内核模块接口）随意变更，且**从未承诺稳定驱动 ABI**。这套「对外刚性、对内柔性」的二分，是因为 Linux 内核与用户态（glibc/systemd/发行版包）是**独立版本化**的——内核无法假设用户态跟自己一起升级，故必须冻结 syscall 契约。

但 MeuOS 的结构不同（总览 §1、06 §4.3）：
- 内核、libc、监督服务、在树用户态服务，**全部封装在一个可原子切换的 `.msys` sysroot** 内（06 §4.1/F9）；
- 唯一「独立版本化、内核无法控制」的外部实体是**未改写的 Linux 二进制**（经 08 兼容层）。

由此推演「应该是什么样」：稳定性承诺不应是一刀切的「全稳」或「全不稳」，而应**按「调用方是否在 .msys 版本边界之内」分级**——边界之内的组件可随 sysroot 同版本演进（保留破坏权），边界之外的外部二进制必须被稳稳托住。这正是本文三层分级的根本理由，而非照抄 Linux 的「绝不破坏用户空间」。

### 1.2 三种「接口边界」对应三种稳定性命运

| 接口 | 调用方是否随 .msys 同版本升级 | 应当的稳定承诺 |
|------|--------------------------------|----------------|
| Linux 兼容 ABI（08 翻译面） | **否**——外部二进制独立版本，内核控制不了 | **必须稳**（仅限声明子集） |
| MeuOS 原生 syscall / capability API | 是——在树服务+libc 同 sysroot | **演进期明确不稳**，靠 libc/mkit 屏蔽 |
| 用户态服务间 IPC 协议（05 Channel） | 多数是，但存在跨版本共存（06 §4.3e 灰度）+ 第三方服务 | **版本协商式稳**（FIDL 式） |

### 1.3 与「非缝合怪」对齐：借谁、不借谁

- **借 Fuchsia**：FIDL 版本化、明确「不承诺 syscall 稳定」、用 system ABI revision number 表达演进——与本文「原生 API 不稳、IPC 靠版本协商」完全同构，是最贴切参照。
- **借 Android Treble / vendor HAL**：把「稳定接口」只画在**必要边界**上（vendor 分区 ↔ system 分区），其余内部自由演进——对应本文把稳定承诺只落在兼容层与 IPC 协议。
- **借 Windows NT / macOS DriverKit**：对驱动提供**版本化 ABI**（WDF / DriverKit），而非 Linux 的「无稳定驱动 ABI」——本文 §4 据此主张「用户态驱动经版本化 IPC 天然可版本化」。
- **不借**：Linux 的「syscall 永不破坏」整体套用（会锁死自研内核演进）；塞班式全局 BC break 管理委员会（过重，MeuOS 用 .msys 同版本升级替代其大部分职能）。

## 2. 三层接口稳定性分级表

> 核心交付物。每一层给出：受众、稳定承诺、演进规则、版本锚点、破坏权归属。

| 维度 | **① Linux 兼容 ABI**（对外） | **② 原生 syscall / capability API**（对内演进） | **③ 用户态服务间 IPC 协议**（内部 ABI） |
|------|------------------------------|-----------------------------------------------|------------------------------------------|
| 受众 | 未改写 Linux 二进制（出树、独立版本） | 在树服务 / mkit / meuos-libc / 原生 app | 在树服务 + 第三方服务 + 跨版本共存期服务 |
| 稳定承诺 | **必须稳**（这是兼容层的存在意义） | **演进期明确不稳**（Day1–M4+ 保留破坏权） | **版本协商式稳**（每版本内稳，跨版本协商） |
| 稳定范围 | **仅 08 声明的覆盖子集**（Phase0-3：mkit direct-mapped + emulated + synthesized）；子集外 → `ENOSYS`（08 §7） | 无对外稳定子集；原生程序**不应发裸 syscall**，只经 libc/mkit 间接调用 | Channel 消息 schema / 类型化协议（FIDL 风格，05 §4.1） |
| 破坏权 | 内核/兼容层实现方**不得**破坏已声明子集语义 | 实现方**明确保留**破坏权，自由变更 syscall 号、capability rights 位、句柄语义 | 实现方保留变更权，但须**升版本号 + 协商兼容** |
| 版本锚点 | 绑定 `uname` 报告值（总览 C14）+ syscall 覆盖基线（总览 C12） | 内部 revision number，**不**绑定 uname；随 `.msys` 版本走 | 协议 `protocol_version` + `min_compatible_version`（声明于 manifest / Service Registry，05 §4.4） |
| 演进规则 | 可**扩**覆盖（加 syscall）；**删/改已声明 syscall = BC break**，需弃用窗口（§6） | 随 `.msys` 原子升级**整卷同变**（06 §4.3）——内核+libc+服务同版本，无需逐接口冻结 | 新版本协商降级；旧服务遇新客户端按 §6 策略回退/拒绝 |
| 屏蔽层 | 兼容层自身（08 翻译面，权威只来自内部 capability） | **mkit / meuos-libc** 吸收破坏——app 面向 libc ABI 而非裸 syscall | 协议库（stub/proxy 生成）吸收版本差 |
| 验收暗示 | 声明子集内的 Linux 程序跨 MeuOS 升级可跑 | 同 `.msys` 内重编即通过；跨 `.msys` 未重编的原生二进制不保证 | 协商成功即互通；协商失败可观测、可回退 |

**关键判语**：三层里，**只有 ① 是唯一「对外刚性」的承诺**，② 是「对内柔性、靠 libc 屏蔽」，③ 是「版本化柔性」——这恰是「该稳的稳、该破的明破」的解构型落点。

## 3. 多系统参照对比表

> 横轴：各系统对三类边界的稳定性策略；纵轴：系统。结论列给 MeuOS 取舍。

| 系统 | 用户态 syscall ABI | 内核内部 API | 驱动 ABI | 内部组件 IPC | **MeuOS 取舍** |
|------|--------------------|--------------|----------|--------------|----------------|
| **Linux** | 永不破坏（铁律） | 随意变 | **无稳定驱动 ABI**（驱动须追内核） | 无统一（ioctl/净肉） | ① 借「对外刚性」，但**不**借「整体 syscall 永不破坏」；驱动 ABI 见 §4 |
| **Windows NT** | 极强稳定承诺（用户态） | 相对稳定 | **WDF 版本化驱动模型**（KMDF/UMDF 分轨） | 弱（COM/私有） | 借「强对外稳定 + 版本化驱动」思想；② 不借「内核内稳定」 |
| **macOS** | syscall 不稳定，**强制走 libSystem** 屏蔽 | 随意变 | **DriverKit 取代 kext**（用户态、可版本化） | XPC（强类型） | 借「libSystem 屏蔽 + DriverKit 用户态化 + XPC 强类型」→ 对应 ②③ |
| **Android** | NDK 版本化 | 随意变 | **Treble / vendor HAL 稳定接口**（vendor 分区隔离） | Binder（版本化接口） | 借「仅在必要边界画稳定接口」思想 → 对应 ①③ 边界化 |
| **塞班** | 严格 BC break 管理流程 | 平台安全能力约束 | 粗粒度进程级能力 | 会话/消息 | 不借其全局 BC 委员会；以 .msys 同版本升级替代其职能 |
| **Fuchsia** | **明确不承诺稳定** | 随意变 | **DFv2 组件化 + FIDL** | **FIDL 版本化 + system ABI revision** | **最贴切**：② 不稳 + ③ FIDL 版本化 + revision number 直接同构 |
| **MeuOS（本文）** | ① 兼容子集稳 | ② 原生 API 不稳 | §4 双轨（内核态不稳、用户态可版本化） | ③ IPC 版本协商 | 三层分级 + .msys 同版本升级杠杆（§5） |

> 结论骨架：Fuchsia 的「原生不稳 + FIDL 版本化 + ABI revision」是③的直接范本；Android Treble 的「只在必要边界画稳定接口」是①③边界化的范本；NT WDF / macOS DriverKit 的「版本化驱动」是§4 用户态驱动可版本化的范本。实现全部自主研究，不缝合。

## 4. 驱动 ABI：双轨驱动的承诺差异

> 依赖 `10-设备驱动模型.md` §2.1/§4.1（双轨：内核快速路径 + 用户态隔离服务）+ §4.6（能力网关）。本文只定**稳定性承诺**，不替 10 定驱动内部设计。

### 4.1 双轨与两套 ABI 命运

MeuOS 驱动分两轨（10 §4.1/4.2）：

- **内核态快速驱动**（中断控制器/定时器/关键 DMA，ring 0）：与内核**同版本、同 `.msys`**，是内核 TCB 的一部分。
- **用户态驱动服务**（virtio-blk/net、串口、USB、显示，经 10 §4.6 能力网关拿 MMIO/IRQ/DMA 能力）：独立进程，经 IPC（Channel，FIDL 风格，10 §3.4/表 3.6）与系统通信。

据此，**两套驱动 ABI 承诺应不同**：

| 驱动轨 | ABI 稳定承诺 | 理由（解构） |
|--------|--------------|--------------|
| 内核态快速驱动 | **不承诺稳定**（同 Linux「无稳定驱动 ABI」） | 它是内核 TCB 子集，随 `.msys` 同版本升级（§5 杠杆）；源码级自研（10 §2.2），不加载外部 `.ko` |
| 用户态驱动服务 | **可版本化稳定**（经 ③ IPC 协议版本协商） | 它经能力网关 + 版本化 IPC 与外界通信（10 §4.1），天然比内核模块易版本化——见下 |

### 4.2 为什么用户态驱动天然比内核模块易版本化（相对 Linux 痛点的结构性答案）

Linux 的核心痛点：**无稳定驱动 ABI** → 外部驱动须追内核版本、DKMS 脆弱、厂商痛苦（10 §1.1）。其根因是驱动在 ring 0、与内核内部符号强耦合、无版本协商面。

MeuOS 的结构性解法（非缝合、自主）：
1. 用户态驱动**不链接内核内部符号**，只持「设备能力」（10 §4.6）——设备能力语义由 capability 模型（07）定义，比内核函数签名稳定得多；
2. 驱动与驱动管理器 / 客户组件的通信走 **⑤ Channel + 类型化协议（FIDL 风格）**（10 §3.4/表 3.6），协议可**版本协商**（§6）；
3. 因此一个用户态驱动可**独立升级**并与驱动管理器协商协议版本，无需与内核符号严格同步——等价于 NT WDF / macOS DriverKit 的「版本化驱动 ABI」，但由「用户态 + 能力网关 + FIDL 风格 IPC」自然达成，而非另造驱动框架 ABI。

> 与 10 的协同点：10 §5.4 已列「驱动热更新/版本化」开放议题——本文主张该议题的结论方向是「内核态不做、用户态走 IPC 版本协商」，与 §6 机制同源。

### 4.3 待协同（非本文拍板）

- 内核态驱动是否**永不**对外暴露可加载 ABI（与 10 协同，确认「不加载外部 ring0 驱动」Day1）。
- 用户态驱动的「设备能力 schema」版本是否并入 ③ IPC 协议版本体系，还是独立编号（§7 待决）。

## 5. `.msys` 整体升级杠杆（MeuOS 相对 Linux 发行版的结构性优势）

> 依赖 `06-文件系统.md` §4.3（子树级 CoW 快照 + 命名空间原子 repoint + 监督灰度）。本节把该机制对 ABI 策略的杠杆**讲透**。

### 5.1 杠杆的本质

Linux 发行版的困境：内核、glibc、systemd、各 daemon **独立版本化**且独立升级——因此内核必须冻结 syscall ABI、glibc 必须冻结符号 ABI，否则任意一方升级都会摔死另一方。这是「独立版本化」逼出的「刚性稳定承诺」。

MeuOS 的 `.msys` sysroot（06 §4.1/F9）把**内核 + libc + 监督服务 + 在树用户态服务**打包为**单一可原子切换的版本单元**。一次更新 = 单条命名空间 repoint（06 §4.3d），旧进程持旧能力、新进程用新 sysroot，监督者做 per-process 灰度切割（06 §4.3e）。

**因此：在 `.msys` 边界之内，组件间不需要「逐接口 ABI 冻结」**——它们永远是「同版本、一起升级」。这正是 §1 推演「原生 API 可明不稳」的物质基础，也是 MeuOS 相对 Linux 发行版的核心杠杆。

### 5.2 杠杆的三重削弱效应

| 被削弱的需求 | 传统 Linux 为何需要 | MeuOS 为何不需要（靠 .msys） |
|--------------|---------------------|------------------------------|
| 内核↔libc 的 syscall ABI 冻结 | 二者独立升级，版本错配 | 同 `.msys`，一起变（② 不稳可行） |
| 内核↔在树服务的内核 API 冻结 | 服务独立打包 | 同 sysroot，一起变 |
| 内核↔驱动的驱动 ABI 冻结（内核态） | 外部 `.ko` 须追内核 | 内核态驱动源码级随 sysroot（§4.1） |

### 5.3 杠杆**不**覆盖的边界（稳定性承诺仍必要之处）

杠杆只在 `.msys` 边界内有效。以下三类**仍须稳定/版本化**，对应 §2 三层里被保留的承诺：

1. **① Linux 兼容 ABI**：外部二进制不在 `.msys` 内，内核控制不了其版本 → 必须稳（仅声明子集）。
2. **③ 用户态服务间 IPC**：即使同 sysroot，更新存在**滚动/灰度窗口**（06 §4.3e 新老共存），且存在**第三方服务**在 sysroot 之外 → 须版本协商。
3. **跨 `.msys` 的原生程序**：若用户未在升级后重编原生二进制，它面对的是新内核+旧 libc 假设 → 故 §2 ② 强制「原生程序经 libc/mkit，不发黑 syscall」，把破坏权关在 libc 内。

> 一句话收口：`.msys` 同版本升级让「内部柔性」成为可能，但「外部二进制」与「跨版本/第三方 IPC」两道边界仍要求稳定——这就是三层分级的全部正当性。

## 6. 版本协商与弃用机制

> 面向 ③ IPC 协议（及 §4.2 用户态驱动协议）。这是 MeuOS **唯一主动承诺版本稳定**的机制。

### 6.1 协议如何声明版本

- 每个服务在 `service_register`（05 §4.4）或 manifest 中声明：
  - `protocol_version`：本服务实现的协议版本；
  - `min_compatible_version`：本服务仍能接受的**最低**对端版本。
- 协议定义放在**类型化 schema**（FIDL 风格，05 §1.2/§4.1 的 `type tag`）中，由协议库生成 stub/proxy，屏蔽版本差。

### 6.2 协商流程（老服务遇新客户端怎么办）

```
客户端 service_connect(name)
   → 拿到服务端 listener endpoint（badge 化，05 §4.4）
   → channel_call 首发 handshake：客户端报 {want: Vc, min: Vc_min}
   → 服务端据自身 {have: Vs, min: Vs_min} 选 max(Vc_min..Vc ∩ Vs_min..Vs)
       - 交集非空 → 选定版本，后续按该版本 schema 通信
       - 交集空   → 协商失败：返回 ENOTSUP / 特定「协议不兼容」码，客户端可观测、可回退
```

- **老服务遇新客户端**（服务端 Vs < 客户端 Vc）：只要 `Vc_min ≤ Vs`，老服务仍按旧版本服务，新客户端的「新特性」请求若旧版不支持 → 服务端回 `ENOTSUP`，客户端**降级或放弃该特性**（server-authored 向后兼容）。
- **新服务遇老客户端**：同理，新服务端保留对 `Vs_min` 的兼容路径直到弃用窗口结束。

### 6.3 弃用窗口策略

| 项 | 策略 |
|----|------|
| 窗口长度 | 与 `.msys` 发布节奏绑定：声明弃用于 N 版，移除于 **N+2** 版（留一个完整升级周期给第三方适配） |
| 遥测 | 协商失败时记录到兼容性遥测（08 §6.2 的 ENOSYS 策略可复用），量化谁还在用旧版 |
| 灰度友好 | 因 `.msys` 支持新老进程共存（06 §4.3e），弃用期内可先灰度新服务、观察旧客户端失败率再切 |
| 兼容层（①）例外 | ① 的「已声明 syscall 被删/改」是**对外 BC break**，窗口应严于 ③（类比 Linux「绝不破坏用户空间」）——具体值由 08 在 C12/C14 框架内定，本文不替其下结论 |

### 6.4 跨版本 IPC 共存（滚动更新场景）

- 监督者灰度期间（06 §4.3e），同一服务的 N 版与 N+1 版进程可短暂并存，二者经 §6.2 协商互通；
- 协议库负责在边界做**字段补齐/裁剪**，使跨一版的互通零成本、跨多版失败可观测。

## 7. 与 08 兼容层 `uname`（C14）/ syscall 覆盖基线（C12）的关系

> 只声明依赖，不替 08 下结论（遵守硬约束）。

- **`uname` 报告版本（总览 C14）** 是 ① Linux 兼容 ABI 的**对外稳定锚点**：外部二进制据此做版本探测（08 §6.1 D7 推荐「报固定可控串、不暴露内部版本」）。本文仅依赖「该值存在且可控」，其具体取值由 08 在 C14 框架内裁决。
- **syscall 覆盖基线（总览 C12）** 定义了 ① 的**稳定表面积**：只有被 C12 纳入「声明支持」的 syscall，才进入 §2 ① 的「必须稳」集合；子集外一律 `ENOSYS`（08 §7）。本文依赖 C12 的边界划定，不替其选 glibc/内核版本基线。
- **原生 API revision（②）与 `.msys` 版本（§5）**：二者随 sysroot 走，**不**绑定 `uname`——避免外部二进制从 `uname` 误读内部稳定性。
- **IPC 协议版本（③）**：独立于 `uname` 与 `.msys` 版本号，自成 `protocol_version` 体系（§6.1），与 Fuchsia 的 system ABI revision 思路同构但不混用。

## 8. 待决清单（标注是否需架构裁决）

> 凡需 team-lead / 大喵拍板者标「**架构级**」，其余为设计/实测协同项。

1. **【架构级】原生 API（②）是否存在「亚稳子面」？** 例如 capability rights 位语义（07 §5.2）、Job 账本字段（04 §4.4）是否应比裸 syscall 更稳定？若全不稳，跨 `.msys` 调试/审计工具（12）如何对齐？需 07/04 协同裁决。
2. **【架构级】IPC 协议版本号的归属与分配权**：版本号是**每服务自管**还是**系统统一分配**（类比 Fuchsia 平台 FIDL vs 服务私有 FIDL）？影响 §6.1 的 `protocol_version` 权威来源。需 05 协同裁决。
3. **【架构级】第三方原生服务走 ② 还是 ③ 契约**：出树第三方服务若发裸原生 syscall（②），将失去 `.msys` 同版本保护 → 是否强制第三方只经 libc（② 屏蔽）或只经 IPC（③）？需 08/05 协同。
4. **【设计协同】用户态驱动协议版本是否并入 ③ 体系**：§4.2 主张用户态驱动经版本化 IPC，但其设备能力 schema 是否复用 ③ `protocol_version` 还是独立编号（§4.3）。需 10/05 协同。
5. **【设计协同】跨版本 IPC 共存的上限**：§6.4 允许 N 与 N+1 共存，是否支持 N 与 N+2 直连（需协议库双向兼容）？与 `.msys` 弃用窗口（§6.3）对齐。需 05/06 协同。
6. **【设计协同】兼容层（①）弃用窗口严于 ③ 的具体数值**：§6.3 仅给方向，具体「N+? 移除」与 `uname` 兼容性承诺由 08 在 C12/C14 定。本文不替其裁决。
7. **【实测】IPC 版本协商握手开销**：§6.2 的 handshake 是否每次 `service_connect` 都做，还是缓存于 Service Registry（05 §4.4）？需原型基准（关联 05 §5.7 fastpath）。
