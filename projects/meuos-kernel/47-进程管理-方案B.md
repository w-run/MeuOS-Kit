# 47 - 进程管理·方案 B：能力受限轻量进程 + 结构化资源树（Job 即资源树）的务实混合模型

> 调研 / 设计文档，由 kernel-plan 团队的「内核规划调研 agent（lite/hy3）」产出。
> 工作树：`kernel-plan` / 分支：`worktree-kernel-plan`。
> 本文是**独立新增方案文档**，**不修改** `00`–`46` 任何章节；行文末尾单列「与现有规划的衔接」而非改动既有文件。
> 定位：为 MeuOS 的**进程管理 / spawn / 并发模型**提出一个与 `46`（方案 A）**取向不同**的方案——更务实、更渐进、对既有生态与语言运行时更友好，但核心安全不变量（capability、Job 账本、结构化取消、无全局 root）与 `46` 完全一致。
> 方法论：解构型思维（先推演「应该是什么样」）、多系统参照、非缝合怪、修订式追加不删——与 `46` 同纪律。

---

## 0. 一句话核心

> **在 MeuOS 中，进程是「受 capability 约束的轻量执行单元」，Job 是「结构化资源/生命周期树（资源账本 + 取消域 + 命名可查询的沙箱单元）」，结构化取消为默认；在方案 A 的极简范式之上，务实保留三条渐进旁路——受限快照派生（fork-light）、well-known 名字服务注册、scoped 可读标识——以换取语言运行时、shell 与既有守护进程的友好落地，但不引入全局 PID、POSIX 信号或 root 提权。**

本文把 `00`/`04`/`05`/`07` 中已采纳的 `meu_spawn`、Job 资源账本 Day1、Channel 原语、capability Day1 等点状决策，**升维成一套「务实双轨」模型**——主轨从零 spawn、辅轨受限派生；主 IPC 是 Channel、大数据走显式 SHM；寻址主用 capability、运维用 scoped 标识。它和 `46` 共享地基，但在「是否允许 fork 式入口、是否给服务起名字、是否给进程可读标识」三件事上做出**相反的务实让步**。

---

## 1. 方案核心思想

### 1.1 与方案 A 的根本分叉点

方案 A 的立场是「消息传递 + 结构化并发作为**唯一范式**」，四条铁律（无 fork、无全局 PID、无信号、结构化并发唯一）**永不退化**。这是干净、可验证、对形式化友好的极简主义。

方案 B 认同 A 的**所有安全不变量**，但认为 A 在工程落地上有三处成本过高、且并非安全所必需：

1. **启动多样性成本**：强制一切从零 `meu_spawn` + 显式句柄/命名空间注入，对语言运行时（Go/Rust 全局态、JIT 代码缓存）、shell 管道、继承当前环境的工具极不友好——代码啰嗦且会破坏依赖「继承当前进程状态」的程序。A 把这些需求推给兼容层（CoW 近似），但 B 认为**把受限派生提升为原生一等原语、显式标注、受 capability 与 Job 双重约束，比藏进兼容层更可审计、更友好**。
2. **服务可发现性成本**：A 仅用 Service Registry + capability 句柄传递做服务发现；移植 Linux 守护进程（socket activation、DBus well-known name）时缺一个稳定名字锚点。B 引入 **well-known name + socket activation**（systemd 式）作为 capability 传递的补充。
3. **可观测性成本**：A 完全无 PID、可见性=capability，运维/日志/调试缺可读标识。B 把 A 的开放议题 4（展示层）**提前明确化**为 scoped 可读标识（job-path + ephemeral tag），受 `DBG_INSPECT` 约束——是展示层，不是寻址层。

> **一句话区分**：A 是从零设计的「洁癖极简范式」；B 是同一组安全不变量下的「务实双轨」，主动为生态/运行时留三条渐进旁路，但每条旁路都被 capability 与 Job 约束，不回退到 Unix 包袱。

### 1.2 方案 B 的四条务实原则

1. **能力受限轻量进程为基础**：Process 仍是「独立地址空间 + 句柄表 + 线程集」的隔离边界，但**刻意做轻**——创建成本向 goroutine 量级靠拢，鼓励按任务拆进程（process-per-task）；**Job 才是安全/资源/生命周期的粗边界（沙箱单元），进程在其内可密集**。这从架构上压低「为共享状态而滥用 pthread 共享内存」的诱惑（A 的目标），同时不强制每任务一个重地址空间。
2. **Job 即资源树（结构化 scope + 账本 + 取消域 + 命名可查询）**：继承 A 的 Job 三合一，并补强一项 A 弱化处理的工程属性——**Job 可被命名、可被监督者/持权者查询**（借鉴 Windows Job Object 的命名容器与 systemd scope），使「资源树」同时是可管理的运维单元，而非纯内核内部树。
3. **结构化取消为默认**：同 A——scope 退出即取消、异常沿树上报、无僵尸/孤儿。B 在取消语义上更强调「**协作优先、强制兜底、超时可配**」，并把超时/策略暴露给 Job 账本（软实时 vs 批处理），比 A 的「两段式」更显式工程化。
4. **双轨启动、显式标注**：主轨 `meu_spawn`（从零，精确）；辅轨 `meu_fork_light`（受限快照派生，单线程、显式标注、capability/Job 约束）。两条轨道都是「创建即挂 Job、创建即受限」，区别仅在「从零构建」还是「从自身快照派生」。

### 1.3 「轻量进程」到底轻在哪（与 A/Unix 的差异）

| 维度 | Unix 进程 | Unix 线程(pthread) | 方案 A 的 Process | 方案 B 的 Process |
|---|---|---|---|---|
| 隔离边界 | 地址空间 | 无（共享） | 地址空间 | 地址空间 |
| 安全/资源边界 | uid/cgroup（弱、外置） | 同进程 | Job | **Job（同 A，但 B 强调 Job 是粗沙箱、进程可密）** |
| 创建成本 | fork COW（隐性、重） | 轻（但共享可变状态） | spawn 从零（中等） | **spawn 从零 + fork-light 快照（双轨，刻意做轻）** |
| 密度 | 低 | 高 | 中（重隔离） | **高（轻进程 + Job 内多进程）** |
| 共享内存默认 | 否（fork 后 COW） | 是（footgun） | 否（显式 SHM） | 否（显式 SHM，但 SHM 是一等非默认通道） |

B 的设计动机：**让「隔离」与「轻量」不再二选一**——用 Job 承担沙箱/资源/生命周期（粗边界），用轻量进程承担执行（细边界），从而既避免 pthread 共享可变状态的整类 bug（A 的目标），又不必为每任务付出「完整重地址空间 + 全量 manifest」的代价。

### 2.1 Process（能力受限轻量进程）

- **定义**：一个受 capability 约束的轻量执行单元 = 独立地址空间（根 VMAR）+ 一张句柄表（CSpace）+ 一组 Thread。它是**细粒度隔离边界**，但刻意做轻、可在同一 Job 内密集存在。
- **轻量化的实现支点**：`meu_spawn` 从零构建时不强制全量 manifest（默认-deny 句柄 + 继承所属 Job 的 namespace 模板，见 `04` §4.2 第三轮回写 C3），把「新建进程」的成本压到接近「新建一个带地址空间的 task」；`meu_fork_light` 复用父进程已映射的 VMO 子快照，省去 loader 重映射。
- **可见性**：**无全局 PID**。它对「持有其 Job handle / 某 Channel 端点句柄」的主体可见、可寻址（同 A 的 capability 寻址）。**B 增量**：额外携带一个 *scoped 可读标识*（job-path + ephemeral tag），受 `DBG_INSPECT` 约束，仅供日志/运维/调试**展示**，不参与寻址、不可被拿来「假设某标识在跑」——这是方案 A 开放议题 4 的提前落点。
- **线程**：一个 Process 可有多个 Thread；内核只调度 Thread。同 A/04。

### 2.2 Job（结构化资源/生命周期树 = scope + 账本 + 取消域 + 命名可查询）

- **定义**：并发任务的**结构化作用域（scope）**、**资源账本（ledger）**、**取消域（cancellation domain）**、**命名可查询沙箱单元**四者合一。前三者与 A 同（`04` §4.1/§4.4 + `46` §1.3）；第四者是 B 的务实补强。
- **命名可查询（B 增量）**：Job 可被赋予一个 **well-known name**（如 `svc/network`、`session/user/alice`），名字解析受 capability 与命名空间约束——持权者（监督者、同 realm 内指定消费者）可经 Service Registry 按名查询 Job 的「状态/资源用量/子节点」，但**名字只是查询键、不是越权凭证**（解析结果仍需持有对应 capability 才能操作）。这借鉴 Windows Job Object 的命名容器与 systemd scope 的「可管理单元」直觉，让「资源树」同时也是运维单元。
- **三个（＋一）身份的统一**：①结构化 scope；②资源账本（A5 Day1，五类资源）；③取消/异常域（A9）；④命名可查询沙箱单元（B 新增）。
- **生命周期铁律**：同 A——父 Job 关闭前必须等全部子孙退出（或被取消）；无僵尸、无全局 init 兜底。

### 2.3 Channel（消息通道 = 主 IPC 范式）

- **定义**：同 A/05——成对内核对象端点，每端是 capability，消息 = 数据 + 可选 capability 句柄数组，rendezvous 不丢。
- **B 的态度差异**：A 宣布 Channel 是「**唯一**通信方式，没有第二选项」；B 保留 Channel 为**主范式**，但明确把 **SHM 提为一等非默认的显式大数据通道**（见 §2.5），因为语言运行时、图形合成、AI 张量搬运等场景的零拷贝共享是真实刚需，强行「一切走消息」会逼出畸形的分块拷贝。B 与 A 的底线一致：**跨进程默认无共享内存，SHM 必须显式经 capability 授予**——区别仅在「SHM 是禁用/不鼓励」还是「SHM 是一等公民但受门控」。

### 2.4 Capability（能力句柄 = 寻址 + 权限 + 生命周期锚点）

- **定义**：`handle + rights` 位图（`07` §4.1），同 A。寻址=持句柄、权限=rights、生命周期=引用计数/崩溃回收。
- **B 的增量 1（well-known name 作为一种受约束委托）**：Service Registry 中的名字绑定本质是「把某 Channel/服务连接句柄**以受约束方式**关联到名字」——名字解析 = 一次受 capability 约束的句柄查询，等价于「能力委托的可发现包装」。这比纯句柄传递对生态更友好，但不削弱 capability 模型（名字不是凭证，解析结果仍是句柄）。
- **B 的增量 2（scoped 标识是 capability 之上的展示层）**：进程可读标识受 `DBG_INSPECT` 约束生成，是 capability 可见性的**投影**，不是独立寻址维度。

### 2.5 SHM（显式大数据通道，B 提为一等非默认公民）

- **定义**：一个内核 VMO 对象 + 两端 `MAP` capability，显式经 `channel_create`/`grant` 授予，零拷贝共享一大块内存。
- **为什么 B 把它从「不鼓励」提为「一等公民」**：图形 framebuffer、音视频缓冲、AI 张量、大型 IPC payload 的零拷贝是工程硬需求；A 的「一切消息」在这些场景会退化成「先拷贝进 Channel 再拷贝出」的双拷贝。B 的约束：**SHM 从不默认共享、必须显式授予、受 rights 门控、其生命周期由两端句柄引用计数管理（崩溃即回收，无孤儿）**——即保留 A 的「默认不共享」安全不变量，只是把 SHM 从「兼容层/特殊通道」升级为「原生一等公民」，让运行时/图形/张量能直接表达零拷贝共享。

### 2.6 创建双轨：meu_spawn vs meu_fork_light

| 维度 | `meu_spawn`（主轨） | `meu_fork_light`（辅轨，B 新增原生原语） |
|---|---|---|
| 地址空间来源 | 空根 VMAR，loader 显式映射 | **自身当前地址空间快照**（COW VMO 子，见 `04` §4.2 / C4） |
| 句柄/命名空间 | 显式注入（默认不继承） | 默认继承父**快照时刻**的句柄表与 namespace 模板（默认-deny，可显式裁剪） |
| 线程约束 | 新进程从入口点起 | **仅调用线程存活**（单线程限定，多线程调用返回 `EINVAL`/`ENOSYS`，同 C4） |
| 资源/生命周期 | 归入指定 Job | 归入父 Job（资源账本投影继承，同 `04` §4.2 第三轮回写） |
| capability | 由 Job/显式覆盖决定 | 合成 uid 零权限、无提权（同 C4） |
| 用途 | 服务、工具、从零程序 | 语言运行时派生、shell 管道、继承当前态的工具 |
| 审计 | 显式、清晰 | **显式标注 `fork_light` 标志**，比藏在兼容层更可审计 |

> **关键立场**：`meu_fork_light` 不是 POSIX fork 逃逸——它是「spawn-from-snapshot」：单线程、COW VMO 子、归入父 Job、默认-deny 句柄、合成 uid。它满足 C4 的全部约束，只是 B 主张把它**从兼容层慢路径提升为原生双轨之一**，理由是「显式标注比隐藏更可审计、对运行时更友好」。这与 A 的「原生无 fork、fork 仅兼容层」是 B 相对 A 的**唯一实质分歧**。

### 2.7 五者（＋一）关系小结与相对方案 A 的差异

| 抽象 | 方案 A 的立场 | 方案 B 的立场（差异化点） |
|---|---|---|
| Process | 重隔离边界，从零 spawn | **轻量、可密集、Job 内多进程**；双轨创建 |
| Job | scope+账本+取消域 | **+命名可查询沙箱单元**（well-known name） |
| Channel | **唯一** IPC 范式 | **主** IPC 范式（保留 SHM 一等公民地位） |
| Capability | 寻址+权限+生命周期 | 同 A + 名字绑定=受约束委托、scoped 标识=展示层 |
| SHM | 显式、不鼓励默认 | **显式、一等公民**（仍受 capability 门控） |
| 创建原语 | 仅 `meu_spawn` | `meu_spawn` + `meu_fork_light` |
| 进程标识 | 无 PID，纯 capability | capability + **scoped 可读标识（展示层）** |

## 3. 多系统参照（解构而非缝合）

> 本节逐一对标成熟系统，**只抽取可复用的机制骨架**，并明确「B 取了什么、相对 A 多取了什么、丢了什么」。每个系统都给 B 的取舍，并点明 B 与 A 在此系统上的分叉。

### 3.1 Fuchsia / Zircon（job / process / thread + channel + handle）

- **机制**：无 fork，进程由 `zx_process_create` 在**给定 job** 下从空地址空间构造；Job 承担资源限额与生命周期控制（父 job 死 ⇒ 杀子孙）；无 POSIX 信号，异常经 exception channel 上报（`04` §3.1 B）。
- **B 取了**：spawn-only 主轨、Job 账本 Day1、exception channel、handle=capability——与 A 同，完全继承 `04`/`05`/`07` 已采纳点。
- **B 相对 A 多取了**：①把 Job 的「命名/可查询」维度显式化（Zircon 的 Job 也有 `ZX_PROP_NAME` 但 B 把它上升为可查询的运维单元，对齐 Windows Job Object）；②接纳一个受限快照派生原语（Zircon 无，但 B 认为对运行时友好）。
- **B 丢了/改造**：Zircon 仍允许进程自行退出后由父 wait 的弱约束——B 同 A 强化为强制结构化 scope。

### 3.2 Plan 9（rfork + 每进程命名空间 + note）

- **机制**：`rfork(flags)` 用标志位显式选择「哪些资源被子进程共享/重置」（RFMEM 共享地址空间、RFNAMEG 新命名空间…），是「共享什么由 spawn 标志显式声明」的思想源头（`04` §3.1 C）。
- **B 取了**：每进程独立 namespace（C3 已采纳）、「共享什么显式声明」（G4）。
- **B 相对 A 多取了**：B 的 `meu_fork_light` 是对 Plan 9「显式选共享」精神的**务实复活**——但 B 不是复制整个进程再裁剪（rfork 的 COW 账本隐患），而是「**从自身快照派生 + 单线程 + 显式标注**」的受约束变体，规避 COW/大页/多核雷区。**这是 B 与 A 的分叉点**：A 把 rfork 类思路全盘拒为「fork 变体」，B 取其「显式共享」内核、做成原生双轨之一。
- **B 丢了**：rfork 的「复制后裁剪」语义（避免 COW 账本），改用 VMO 子快照 + 单线程限定（与 C4 一致）。

### 3.3 Windows Job Object（命名容器 + 资源限制 + 生命周期）

- **机制**：Windows Job 是一组进程的**命名容器**，可设 CPU/内存/IO/句柄限额、进程数上限，关闭 Job 即终止其下所有进程；Job 可被命名、被外部查询（Job 名是管理锚点）；`AssignProcessToJobObject` 把进程挂入 Job。这是 OS 级「资源树 + 生命周期树 + 可查询单元」的工程范本。
- **B 取了（相对 A 的关键增量）**：①Job **命名可查询**——B 把 Windows Job 的「名字 + 可查询」引入 MeuOS Job，使资源树同时是运维/管理单元（对齐 systemd scope 直觉）；②资源限额 + 生命周期控制与 A 的 Job 账本/取消域同构。
- **B 改造**：Windows Job 名字是**全局可查**的（靠特权）；B 的 well-known name 受 **capability + 命名空间约束**——名字解析不授予越权，只是受控查询键（破 Windows「命名即部分凭证」的隐含特权）。
- **为什么 A 没取这一点**：A 追求极简、把 Job 仅作内核内部结构化 scope，不引入任何「名字」概念（怕滑向全局命名空间）。B 认为「命名可查询」是运维现实需求、且可用 capability 约束得不回退到全局 PID，故务实采纳。

### 3.4 Linux namespaces + cgroups（视图隔离 + 事后资源挂接）

- **机制**：namespaces 提供每进程/每容器的视图隔离（mount/pid/net/…）；cgroups v2 是**事后挂接**的分层资源控制器（先有进程再移入 cgroup）。
- **B 取了**：①每进程 namespace 视图（C3 已采纳，拒绝全局 `/`）；②「资源账本内建」——但 B 同 A 拒绝 cgroups 的「事后挂接」，坚持 Job 配额 Day1 内建（A5）。
- **B 相对 A 的务实补充**：明确**兼容层映射策略**——把 `cgroup` 调用映射为 Job 配额操作、把 Linux namespace 映射为每进程 namespace 投影（`04` §5 议题 3 的容器可移植性）；B 比 A 更明确「兼容层不是重写，是投影」。
- **B 丢了**：cgroups 事后挂接、全局 PID namespace（B 的标识是 scoped/可撤销/非全局）。

### 3.5 Go runtime（goroutine M:N + context 结构化取消）

- **机制**：goroutine 是用户态轻量线程，runtime 做 G/M/P 的 M:N 调度；`context.Context` 实现结构化取消（cancel 沿调用树广播）。Go 的「不要通过共享内存通信」与方案 A 同声相应。
- **B 取了（相对 A 的关键增量）**：**「轻量进程」对齐 goroutine 的成本量级**——B 主张内核提供**廉价进程**，让 Go/Rust 运行时可在 OS 层做细粒度并发（process-per-task），而不必把全部并发压在用户态协程；Job 树 = `context` 的内核级强制版（取消沿树广播、不响应则强杀）。
- **B 相对 A 的差异**：A 的 Process 是「重隔离边界」（与 Zircon 同构），对「按任务拆进程」不够轻；B 强调 Job 是粗沙箱、进程可轻可密，更贴合运行时「海量轻量并发单元」的直觉——这是 B 对「轻量进程」的独有主张。
- **B 改造**：Go 的 `context` 是库级合作式（可泄漏 goroutine）；B 同 A 把取消做成内核强制（Job 取消广播到所有子孙，不响应则终止）。

### 3.6 综合取舍表

| 系统 | 抽取的机制骨架 | 方案 B 采用 | 方案 B 相对 A 多取 / 改造 |
|---|---|---|---|
| Fuchsia | spawn-only；Job 限额+生命周期；exception channel | 几乎全采纳（04/05/07） | 把 Job 命名/可查询维度显式化 |
| Plan 9 | 每进程 namespace；rfork 显式共享 | 每进程 namespace（C3） | **复活受限快照派生（fork_light）**，规避 COW 账本 |
| Windows Job | 命名容器 + 资源/生命周期 + 可查询 | Job 命名可查询沙箱单元 | 名字受 capability 约束（不回退全局 PID） |
| Linux ns+cgroup | 每进程视图；资源账本 | 每进程视图（C3）；Job 内建账本 | 明确兼容层投影映射策略 |
| Go runtime | 轻量并发；context 结构化取消 | 轻量进程 + Job 取消域 | 轻量进程对齐 goroutine 量级（A 偏重隔离） |
| Erlang（参考） | 进程只走消息；监督树 | 消息主范式；Job exception channel | 同 A（未采用用户态调度） |

**关键判断**：方案 B **不是缝合**——六套系统被「解构」为四条可复用骨架（轻量执行单元、Job 资源/生命周期树、capability 寻址、结构化取消），再用 MeuOS 既有的 Channel/Job/capability 原语**重新组装**成务实双轨。三条旁路（fork_light / well-known name / scoped 标识）各自有清晰的系统来源（Plan 9 / Windows·systemd / A 开放议题 4），且全部被 capability 与 Job 约束——是「同一安全不变量的务实外扩」，不是「加一层 Unix 兼容」。

## 4. 与 MeuOS 现有规划的衔接

> 本节只说明「本方案如何继承 / 强化 / 分歧于既有采纳」，不改动任何既有文档。

### 4.1 继承 `00` 已采纳裁决（与 A 完全一致）

- **A5（Job 资源账本 Day1）**：B 的 Job 四合一直接以 A5 为地基，账本仍是 `04` §4.4 的五类资源，能耗弱耦合（第四轮裁决）。
- **A9（exception channel → 监督者）**：B 的异常沿 Job 树上行 + copy 语义多播 = A9 落点；监督者持 `DBG_CRASHDUMP` 默认订阅（C9-B）。
- **「信号从零简化」**：B 同 A 移除信号概念，Terminate/Kill/Interrupt 作为取消指令（见 §6.2）。
- **C3（每进程 namespace）**、**C4（合成 uid、多线程 fork 拒绝、CoW 语义）**：B 全部继承——`meu_fork_light` 正是 C4 语义的**原生化**，不违反任何 C4 约束。

### 4.2 与 `04` 进程/Job 模型的衔接

- B 继承 `04` §4.1 的 Job→Process→Thread 树，并补强两点：`04` 已把 Job 画为「资源/生命周期单元」，B 把其显式升级为「**命名可查询沙箱单元**」；`04` §4.2 把 fork 定为「兼容层慢速路径、全量 CoW、单线程限定」，B 建议**把同一语义提升为原生 `meu_fork_light` 原语**（显式标注、可审计），不改动 `04` 的约束口径，只改变其「所属层」。
- `04` §4.5 的「内核内建监督」与 B 的命名 Job 天然契合：监督者即根 Job 下的策略执行者，且现在能按 well-known name 编排/查询服务（systemd 式）。

### 4.3 复用 `05` 的 IPC 原语（补 SHM 一等地位）

- B 的「Channel 主 + SHM 一等公民」== `05` §4.1–§4.4 的 Channel/EventPort/SHM/Service Registry 四原语。B 不改 `05` 设计，只在**态度**上把 SHM 从「不鼓励」提为「原生一等、受门控」，并明确 Service Registry 扩展 well-known name + socket activation。

### 4.4 对齐 `07` 的 capability 安全模型

- 维度 B（spawn 资源账本）是 B Job 账本的权威来源；句柄即 capability、派生只能收窄、崩溃即回收，全部继承。
- **B 的 scoped 标识论证**：标识是 capability 可见性的展示投影，受 `DBG_INSPECT` 约束——与 `07` 的「调试即 capability（默认拒绝）」同源，不引入全局 PID 命名空间（07 §5-1 的 handle 命名议题在此给出「进程私有 handle + scoped 可读标识」的务实解）。
- **B 的 well-known name 论证**：名字绑定 = 受约束的能力委托（`07` §4.5 的受约束 mint），解析不授予越权。

### 4.5 与方案 A 的衔接（同一地基、不同外扩）

B 与 A 共享 `00`/`04`/`05`/`07` 的全部地基；二者分歧仅在「是否把 fork_light / well-known name / scoped 标识 提升为原生务实旁路」。B 不否认 A 的极简价值——在形式化/TCB 极致场景 A 更优；B 选择「务实双轨」以换取生态/运行时落地速度。两条方案是**同一任务的不同解法**，可由大喵按「优先极简可验证」还是「优先生态友好」拍板。

## 6. 相对传统 Unix 进程模型：摆脱的包袱与付出的代价

### 6.1 摆脱的包袱（明确清单，与 A 同基线）

1. **全局 PID 整数命名空间**：无 `pid_t` 全局表、无 init 兜底孤儿、无 PID 重用权限错配、无 `/proc` 全局伪文件。B 的标识是 scoped/可撤销/非全局的展示层。
2. **POSIX 信号整套**：无异步可丢失的 signal mask/sigaction/tkill 组合；取消/通知/异常全部结构化。
3. **cgroups 事后挂接**：账本是 Job 固有属性 Day1（A5）。
4. **setuid/setgid 提权**：uid/gid 纯合成视图、零权限附着（C4），setuid 二进制 = 受限 spawn + 显式 capability。
5. **pthread 共享地址空间 + 手动锁的默认通道**：跨进程默认无共享内存，强制走 Channel/显式 SHM——消灭「共享可变状态忘加锁」整类 bug。
6. **僵尸进程 / `wait()` 轮询**：scope 自己兜底，无僵尸。
7. **fork 的「全量 COW 复制整个地址空间」语义**：B 只取「受限快照派生（fork_light）」——单线程、COW VMO 子、归入父 Job，不是 POSIX fork 逃逸。

### 6.2 付出的代价（必须诚实承认，B 比 A 多三条旁路成本）

1. **旧生态二进制仍需兼容层翻译**（同 A）：fork/exec/信号/PID 丰富程序走 mkit（`08`）；纯 fork 语义难点同 A（C4 多线程 fork 拒绝）。B 的 `fork_light` 让兼容层实现更顺、但内核仍不原生支持 POSIX fork 全语义。
2. **`fork_light` 仍是快照——比纯 spawn 重**：需 VMO 子快照 + COW 正确性（写时复制 + 大页 + 多核，见 `04` §5-2 开放议题）；密集 `fork_light` 的快照账本压力需基准。**这是 B 相对 A 引入的实质成本之一**，换取运行时/ shell 友好。
3. **well-known name 引入「名字解析」攻击面**：名字是查询键但解析服务本身需防欺骗/ squatting；B 用 capability 约束 + 命名空间隔离 + 监督者授权缓解，但比 A 的「纯句柄无名字」多一层需审计的解析面。**实质成本之二**。
4. **scoped 标识引入「标识稳定期」管理**：标识是展示层但日志/调试依赖其稳定；需定义 tag 生命周期与回收，避免「标识复用导致日志串扰」。受 `DBG_INSPECT` 约束。**实质成本之三（轻）**。
5. **SHM 一等公民扩大共享内存面**：比 A 的「不鼓励默认」更易被误用为共享可变状态；B 用 capability 门控 + rights 约束 + 崩溃回收兜底，但审计面略大于 A。**实质成本之四（轻）**。
6. **调试/观测心智模型改变**（同 A）：没有全局 `ps`/`kill -9`，观测靠监督者持有的 Job 子树 introspect 视图（受 `DBG_INSPECT`）；B 的 scoped 标识降低了这一成本，但未消除。

### 6.3 代价 vs 收益的总账

| 维度 | 传统 Unix | 方案 A（极简） | 方案 B（务实双轨） |
|---|---|---|---|
| 进程创建安全 | fork 隐式复制易越权 | 显式 spawn 最小特权 | 显式 spawn + 受限 fork_light（仍最小特权） |
| 并发正确性 | 共享内存 + 手动锁 | 消息 + 结构化并发 | 消息 + 结构化并发 + 显式 SHM（受门控） |
| 生命周期可推理 | 信号 + wait + 僵尸 | 树取消 + 异常上报 | 同 A + Job 命名可查询 |
| 运行时/生态友好 | 原生 fork 顺手 | 需显式、兼容层翻译 | **双轨：原生友好 + 兼容层顺** |
| 旧生态兼容 | 原生 | 需 mkit 翻译 | 同 A，但 fork_light 让翻译更顺 |
| 可验证 TCB | 大 | 最小（单一范式） | 略大于 A（三条旁路 + 解析面），仍远小于 Unix |
| 运维可观测 | 全局 ps/PID | 纯 capability 视图（学习成本） | capability + scoped 标识（更可落地） |

**净判断**：B 用「三条受约束的务实旁路」换取「生态/运行时/运维落地速度」，安全不变量零退让；代价是 TCB 与审计面略大于 A，但远小于 Unix。选择 A 还是 B，是大喵在「极简可验证优先」与「生态友好优先」之间的权衡。

### 7.8 已裁决·闭环 A7：多 realm 边界（落定 §7-6 开放议题）

> **状态：已裁决·闭环（指挥官自主采纳）** —— 修订式追加，不删改 §7-6 既有开放议题文本。

- **裁决结论**：realm = namespace 之上的**隔离域**（isolation domain above namespace）。跨 realm 的**取消 / 能力 / 命名传播默认 deny、不穿透**；**capability 边界即 realm 边界**；仅显式 `grant` 才允许跨域（well-known name 的解析同样受 realm 作用域约束，同 realm 内仍由 Service Registry + `GRANT` 类权做受约束 mint，对齐 `07` §4.5）。
- **与 06 C3 同构**：C3 已定「每进程 namespace = capability 组合树、默认全不可见、显式 reveal」（`06` §4.1 与 C3 采纳结论）。realm 是把同一 default-deny 原则从「**文件路径可见性**」提升到「**跨域取消/能力/命名传播**」维度——`reveal`(06 C3) ↔ `grant`(A7) 同构，namespace 闭包 ↔ realm 闭包同构；二者共用同一 capability 地基，不另立机制。
- **与 C-G1~C-G5 一致（尤其 C-G5 命名空间边界）**：第七轮 5 项精细裁决均建立在 capability(`07`)+Job 账本(A5)+结构化取消(A9)+每进程 namespace(C3) 地基之上、零新增内核原语、零新增 right bit（bit 48+ 维持预留）。A7 与 C-G5「A/B 并存命名空间边界、reveal/revoke 与 C3 一致」同一口径——命名空间边界的 default-deny 纪律直接外推为 realm 边界纪律。
- **与 Job 账本协同**：父 realm 的 Job 树**不跨 realm 投影**；跨 realm 取消/well-known name 解析不穿透；监督者对 Job 子树的 introspect 视图（`12` `DBG_INSPECT`）受 realm 作用域约束。
- **明确边界**：**不引入新的统一跨 realm 层**——realm 隔离完全由既有 capability 派生 + namespace 作用域承载，无新增内核对象、无新增 right。

## 第七轮精细裁决（C-G1）：`meu_fork_light` 是否进原生 ABI —— **采纳 B 双轨**

> 本节为第七轮「先细后精」对 `00` 第六轮 §6.3 架构级冲突 **C-G1**（`56` §7.3 冲突 1）的精细裁决回写。原 §7 开放议题（fork_light 快照账本基准等）保留为待原型验证项；本裁决只锁定「是否进原生 ABI」这一架构级分歧，并以**修订式追加**落定，不删改 §1–§8 既有内容。

### 1. 裁决结论（默认采纳 56 推荐 = B，并补精细边界）

**采纳方案 B（本文）立场：`meu_fork_light` 提升为原生双轨创建原语，与 `meu_spawn` 并列进入原生 ABI。** 方案 A（46）的「fork 仅留兼容层」作为**长期演进方向**（不可逆方向）保留，但 Day 1 主线为 B 的双轨。

判定依据（与 `56` §2.2 推荐一致，并据必读文档收紧边界）：

1. **语义零新增，仅提层不扩语义**：`meu_fork_light` 不是新增 POSIX fork 行为，而是把 `04` 第三轮回写 **C4** 已定稿的「全量 CoW（VMO 子快照 + 单线程限定）、多线程显式拒绝、归入父 Job、合成 uid 零权限」语义，从「兼容层慢路径」提升为「原生一等入口 + 显式 `fork_light` 标注」。这正是 `56` §2.2「显式标注比藏进兼容层更可审计」的落地——内核没多出一条 Unix 包袱，只是把已有受限派生从隐藏处提到明面。
2. **与 C4 完全兼容**：`meu_fork_light` 满足 C4 全部约束（见 `47` §2.6 / §4.1）。内核安全不变量——无 root、无全局 PID、无信号、结构化取消唯一、SHM 显式 capability 门控、合成 uid 零权限——**零退让**。
3. **Job 账本投影继承定稿**：子进程归入父 Job，其资源账本继承 = 父 Job 账本投影继承（对齐 `04` 第三轮回写 C4：「fork 产生的子进程仍归入某 Job，其资源账本继承 = Job 账本投影继承」），不另建账本、不引入新配额项，与 `04` §4.4 五类资源账本口径一致。

### 2. 微调项（相对 `56` 推荐的精化）

- **兼容层边界定稿（直接回应 `56` §7.3 冲突 1 待裁定项「与 mkit 兼容层是否共用快照机制」）**：原生 `meu_fork_light` 已提供单线程受限派生原语，故 **mkit 兼容层 `fork` 对单线程进程直接映射 `meu_fork_light`**，不再走独立的 CoW 近似慢路径；多线程 `fork` 仍返回 `EINVAL`/`ENOSYS`（C4 拒绝保持）。即：原生双轨与兼容层**共用同一套 VMO 子快照机制**，消除「内核原生 + 兼容层各实现一份 fork 语义」的重复替换面。此微调把 `56` §2「fork_light 让 mkit 翻译更顺」升级为「兼容层 fork 直接复用原生 `meu_fork_light`」。
- **Day 1 落地口径**：对齐 `47` §5.1 / `56` §2，`meu_fork_light` 建议 Day 1 同期落地（M0–M1 不强制、M2 起由语言运行时 / shell 大量使用），**不阻塞启动**。
- **ABI 版本契约（待办，不阻塞本裁决）**：`meu_fork_light` 作为原生 ABI 符号须进入 `23-ABI稳定性与版本` 的版本槽位；本次仅裁决「进原生 ABI」，具体编号由 `23` owner 协同落定。
- **密集 fork_light 快照账本基准（开放议题，不阻塞采纳）**：`47` §7 议题 1 / `04` §5-2 的「VMO 子快照 + COW 写时复制 / 大页 / 多核正确性、lazy snapshot 阈值」仍待原型基准验证；属 `56` §8 优先级 3 的精细项，与本「是否进原生 ABI」裁决解耦。

### 3. 永不退化的不变量

无论采纳 B，`meu_fork_light` 始终约束在 capability + Job 账本之内：**单线程限定、COW VMO 子、归入父 Job、默认-deny 句柄集、合成 uid 零权限**。内核内部模型**永不引入 POSIX fork 全语义**（C4 铁律）。方案 A 的「无 fork 原生 / 纯句柄寻址 / 结构化并发唯一范式」仍是形式化与 TCB 极致场景的长期方向，B 只是把受限派生提升为原生过渡原语，最终收敛到 A 的洁癖是可预期的——本裁决不关闭该收敛路径。
