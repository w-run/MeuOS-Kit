## 1. 「应该是什么样」推演（解构型）

> 先不问「MeuOS 的显示/图形怎么抄 Linux 的 DRM」，而问「在 capability 世界、用户态驱动、最小 TCB 的前提下，显示与图形**应该**是什么样」。

### 1.1 图形不是「内核必须内置的渲染引擎」，而是一组 capability 守护的资源

在 MeuOS 的既定取向下，内核 Day 1 的权限模型是 capability（`07`），一切资源访问由不可伪造的句柄（handle）+ rights 表达，无 root、无全局命名空间默认可见（`00` A1/A4）。把这个前提推到图形：

1. **每一个图形对象——surface（表面）、graphic buffer（图形缓冲）、display（显示输出）、framebuffer（帧缓冲）、GPU context（GPU 上下文）——都应是 capability**，而非「全局可见、靠 uid/permission bit 保护」的内核对象。一个进程之所以能「把像素画到屏幕上」，不是因为它「碰巧跑在有权限的内核里」，而是因为它**持有对应的图形 capability 句柄**且句柄带 `DISPLAY_PRESENT` / `SURFACE_SUBMIT` 之类 right。
2. **合成器（compositor）是「策略重、代码量大、迭代快、健壮性关键」的子系统**——这正是 `00` 总览 §1 中「重服务出核缩 TCB」原则的典型适用对象，与文件系统（`06`）、网络栈（`25`）、驱动（`10`）同源。把它塞进内核即污染 TCB（合成器崩溃会拖垮整个显示子系统，且代码量巨大、攻击面大）。把它作为用户态系统服务，崩溃可由 `meu-supervisor`（`04`）重启、客户端连接可重建。
3. **客户应用不直接持 GPU 全局能力**。在 Linux 中应用经 `/dev/dri/cardN` render node 直接拿 GPU 命令提交权（配合 group 成员或 `CAP_SYS_ADMIN` 碎片，`07` §3.1 已批）；在 MeuOS 中，**GPU 的设备能力（MMIO/IRQ/DMA）由 capability 监视器（`07`/TCB）签发，经 `10` 能力网关受限委托给合成器或一个受控 3D 服务**，客户应用只持「surface」抽象 capability，把像素内容经 VMO 提交给合成器——绝不直接碰 GPU 全局能力。这正面回应任务约束的「客户应用不直接持 GPU 全局能力」。

### 1.2 合成器 = 用户态系统服务（参照 Scenic），应用经 capability 持「表面」而非直连 GPU

- **合成器（显示服务器）运行在用户态**，是 `meu-supervisor`（`04`）管理的 Rust 组件，可重启、可灰度；它持有 **display 设备能力**（来自 `10` 能力网关：显示控制器的 MMIO/IRQ），负责模式设置（modesetting）、窗口合成、焦点/输入路由。
- **应用持 surface 抽象 capability**：应用向合成器请求一个 surface（等价于 Fuchsia Scenic 的 `View`/`Surface`、Android 的 `Surface` Binder token），句柄带 `SURFACE_SUBMIT`（提交像素内容）、`SURFACE_RESIZE` 等收窄 right；应用把像素写入一个 **graphic buffer VMO**（`03`），经 `05` Channel 的 cap-transfer 把 VMO 句柄交给合成器，合成器映射同一 VMO（零拷贝）并合成到帧缓冲/显示。
- **GPU 能力经 `10` 网关受限委托给合成器 / 受控 3D 服务**：GPU 的命令提交权不在应用侧；要么合成器自己持 GPU 能力做合成（GPU 加速合成），要么一个独立的**受控 3D 服务**持 GPU 能力，应用把 command buffer 经 VMO + IPC 交给该服务校验并提交（防止命令缓冲区成为 sandbox escape 向量）。应用侧永不持 raw MMIO/DMA。

### 1.3 图形缓冲走 VMO/SHM 零拷贝（接 03 / 05）

图形是「大数据零拷贝」的典型场景（一帧 4K RGBA ≈ 33 MB）。MeuOS 已有 VMO/VMAR（`03`）+ SHM/Channel（`05`）零拷贝基元，图形缓冲直接复用：

- **CPU 写入的 surface**：应用 `shm_create`/`vmo_create` 一块 VMO，map 后写像素，把 VMO 句柄经 Channel cap-transfer 交给合成器 → 合成器 map 同一 VMO，零拷贝合成。
- **GPU 写入的 surface**：graphic buffer 经 `03` device VMO（GPU 可映射、可 DMA）承载，VMO 句柄在应用 ↔ 受控 3D 服务 ↔ 合成器间经 cap-transfer 共享，等价于 Linux DMABUF 的「缓冲跨进程/跨驱动共享」，但表达为 capability 而非 fd + `dma_buf` 全局对象。

### 1.4 推演结论（解构型基线）

> **MeuOS 的显示/图形应参照 Fuchsia（Scenic 系统合成器用户态 + Magma 用户态 GPU 驱动 + 图形缓冲经 VMO 共享 + GPU 能力受限委托）：合成器为受 `meu-supervisor`（`04`）管理的用户态 Rust 系统服务，应用经 capability 持「surface」而非直连 GPU；GPU 设备能力经 `10` 能力网关受限委托给合成器 / 受控 3D 服务；图形缓冲走 VMO/SHM 零拷贝（接 `03`/`05`）。内核只保留「display/GPU 设备能力（`10`）+ VMO/device VMO 零拷贝数据通路（`03`）+ capability 守护的 surface/buffer 句柄（`07`）+ EventPort 就绪通知（`05`）」四类机制，内核**不实现任何合成/渲染逻辑**。这与「重服务出核缩 TCB」原则（`00` A6）及 `06` FS、`25` netstack、`10` 驱动出核形成同一套架构叙事。**

## 3. MeuOS 显示/图形模型（用户态合成器 + capability + VMO）

### 3.1 总体架构：三层，内核只给「机制」

```
┌─────────────────────────────────────────────────────────────────┐
│ 用户态显示服务 (Rust, Scenic 式系统合成器)                          │
│  场景图 · surface/window · 焦点 · 输入路由 · 模式设置(modesetting)    │
│  持 display 设备能力(来自 10 网关) · 持 GPU 能力做加速合成            │
│  由 meu-supervisor(04) 管理，可重启、可灰度                         │
│       │ 经 VMO 零拷贝收像素/command      │ 经 Channel 暴露 surface API │
├───────┴──────────────────────────────┴────────────────────────────┤
│ 用户态受控 3D / GPU 服务 (Rust, Magma 式)                          │
│  持 GPU MMIO/IRQ/DMA 能力(来自 10 网关) · 校验 command buffer       │
│  向客户 mint 收窄 right 的 GPU 连接 capability · 提交硬件           │
├───────┴──────────────────────────────┴────────────────────────────┤
│ 用户态 GPU/显示 驱动 (Rust/C, 接 10 双轨·默认出核)                  │
│  display controller / GPU 经 10 能力网关获 MMIO/IRQ/DMA 能力         │
│       │ 设备能力经能力网关(10)        │ 缓冲 VMO + EventPort 通知     │
├───────┴──────────────────────────────┴────────────────────────────┤
│ 内核态（仅机制，Rust TCB）                                          │
│  ① display/GPU 设备能力句柄（来自 10 能力网关，仅 READ/WRITE/DMA 权）│
│  ② VMO/VMAR + device VMO（接 03）：图形缓冲零拷贝数据通路           │
│  ③ surface/buffer 句柄 = capability + rights 强制（接 07）           │
│  ④ EventPort（接 05）：present/帧就绪/输入事件通知（CHAN filter）    │
│  —— 内核不实现任何合成/渲染/ GPU 命令语义 ——                       │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 分层职责

**内核层（机制，Rust TCB，零图形逻辑）**：
- 提供 display/GPU **设备能力**（由 `10` 能力网关签发，合成器/3D 服务只拿所需 MMIO/IRQ/DMA 权）。
- 提供 VMO/VMAR 与 device VMO 原语（`03`），使 graphic buffer 可在 应用 ↔ 3D 服务 ↔ 合成器 间零拷贝传递；帧缓冲 MMIO 走 `03` device VMO（不可写 right，接 `03` §4.4 device 内存隔离）。
- 提供 surface/buffer 句柄这一 capability 类型，并在 `mint`/`open` 时按合成器委托人授权收窄 rights（接 `07` 受约束 mint，避免 confused deputy，呼应 `06` §6-2）。
- 提供 EventPort 就绪通知（接 `05`）：present 完成 / 帧就绪 / 输入事件 → `EVFILT_CHAN` filter。

**显示服务层（合成器，Rust，出 TCB）**：
- 实现场景图、surface/window 管理、焦点、输入路由、modesetting（经 display 设备能力）。
- 作为 surface 句柄的 **mint 委托人**：应用 `create_surface()` → 兼容层/`05` → 显示服务请求内核 mint 一个带受限 rights 的 surface 句柄回传。
- 持有 GPU 能力做加速合成（或直接 compositing 到帧缓冲 device VMO）。
- 可由 `meu-supervisor` 重启（崩溃由监督者拉起新副本，客户端 surface 句柄可重建或 fail-closed）。

**受控 3D / GPU 服务层（Magma 式，Rust，出 TCB）**：
- 持有 GPU MMIO/IRQ/DMA 能力（来自 `10`），校验客户提交的 command buffer，向客户 mint 收窄 right 的 **GPU 连接 capability**（客户持该 connection 提交 command buffer，但**不持 raw MMIO/DMA**）。
- 这是「客户不直接持 GPU 全局能力」的落地：客户经 VMO 交 command buffer，服务校验后提交硬件，IOMMU（`10` §5-2）隔离 DMA，杜绝客户越权访问他人显存或系统内存。

**统一命名空间子树 `/display`（接 `06`）**：
- `/display` 由显示服务经 **mount-capability** 委托（对齐 `06` §4.1「挂载能力委托子树」与 F5 最小集），如 `/display/eDP0`、`/display/HDMI0`、`/display/compositor`。
- 每进程 namespace 经 spawn 组装（`06` C3 已采纳「每进程独立 namespace」），只 reveal 其允许看到的 `/display` 视图（对齐 `26` 容器隔离 = capability 视图同构）。

### 3.3 应用隔离 = capability 边界（与 26 容器隔离同构）

- 窗口/应用隔离不是「Linux 的 namespace/cgroup 事后拼装」，而是 **surface capability 边界**：应用只持自己 surface 的句柄，跨 surface 访问须经合成器授权（focus/输入路由）。
- 这与 `26` §1.1「隔离第一性 = capability 边界」完全同构——surface 句柄即 capability，窗口隔离 = capability 边界。容器内的图形应用，其 surface 句柄仍受容器 Job 的 capability set 约束（`26` §4）。

### 3.4 多架构（五架构）一致性初步策略

显示/GPU 硬件访问同样走 `10` 能力网关，跨架构的「设备能力 + VMO 零拷贝」抽象一致；差异仅在**驱动后端（C 或 Rust）**与**原生 GPU 能力**：

| 架构 | 显示/GPU 形态 | MeuOS 策略 |
|------|--------------|------------|
| **x86_64** | 现代 GPU（Intel/AMD/NVIDIA）+ 通用显示控制器；QEMU `virtio-gpu` | **原生 + 完整**：合成器用户态、`virtio-gpu` 走 `10` 用户态驱动、GPU 加速经受控 3D 服务；KMS-lease 思想用于 VR/headless 转租 |
| **aarch64** | GPU（Mali/Adreno）+ 简单帧缓冲/面板；QEMU `virtio-gpu` | **原生**：同 x86_64 抽象；显示后端多为 `simplefb`/`efifb` 式线性帧缓冲 device VMO + 可选 GPU 加速 |
| **riscv64** | 原生 GPU 稀缺，多 `virtio-gpu` / 帧缓冲 | **原型期 `virtio-gpu` + 帧缓冲**；原生 GPU 驱动后置，抽象不变 |
| **loongarch64** | 视硬件，后置 | **后置**：先 `virtio-gpu`/帧缓冲验证，原生驱动待评估（与 `26` §5.3 loongarch64 后置一致） |
| **i386** | 老 GPU（多为线性帧缓冲，无现代 GPU 栈） | **仅帧缓冲（线性 VMO，无 GPU 3D）**：显示驱动走 `10` 用户态 + **纯 C 后端**（接 `02` C2 约束 i386 全程纯 C）；软件合成（llvmpipe 式）或 `virtio-gpu`；i386 不涉现代 GPU 命令提交、不引入 i386 版 Magma 后端 |

**统一抽象原则**：显示/GPU 驱动抽象为 `arch/display/` + `arch/gpu/` 接口（modeset / buffer import / command submit 等），各架构提供薄后端；无硬件能力/无现代 GPU 的架构（i386 老 GPU）该后端返回 `ENOSYS` 或走纯帧缓冲降级，不模拟。这延续 `01` §5-6 / `03` §2.1「统一抽象 + 每架构薄后端」约束。i386 的 C 后端仅影响驱动侧，不影响合成器 Rust 主体（与 `25` §5.6 netstack 同构）。

## 4. capability 化方案

### 4.1 surface/buffer 句柄即 capability（接 `07`）

- 创建 surface = 向内核请求 `mint` 一个 **surface 句柄**（内核对象，带 rights），由显示服务作为委托人按客户端权限设置子集（显示服务自身持 `MANAGE`）。与 `25` §4.1 socket 句柄、`06` §4.4.2 文件句柄同构，复用 `07` 的 rights 位图模型。
- 句柄的复制（`dup`）、跨进程授予（经 `05` Channel cap-transfer）、回收（`close`）均为显式、可审计操作（接 `07` §4.1/§4.5）。
- **权限在 `mint`/`open` 时一次收窄**（呼应 `19` §1.1 原则 2）：`create_surface`/`present` 的策略判定只在创建/提交时发生一次，运行期 compositing 只做 rights 位运算 + EventPort 通知，不重做策略判定。

### 4.2 图形相关 right 位（建议，接 `07` §5.2 / C2 待定）

| 操作（语义） | 建议 right | 默认 |
|--------------|-----------|------|
| 创建 surface | `DISPLAY_CREATE_SURFACE` | deny（需显示服务 mint） |
| 向 surface 提交像素内容 | `SURFACE_SUBMIT` | 由显示服务 mint 给客户端 |
| 调整 surface（resize/opacity/z-order） | `SURFACE_MANAGE` | 仅合成器/持权客户端 |
| 接收输入事件（焦点窗口） | `INPUT_RECEIVE` | 由合成器按焦点授权 |
| 模式设置 / 枚举显示 | `DISPLAY_MODESET` | deny（仅显示服务） |
| 转租显示资源（VR/headless，KMS-lease 思想） | `DISPLAY_LEASE` | deny |
| 持 GPU 连接提交 command buffer | `GPU_SUBMIT`（由 3D 服务 mint 给客户端，不含 raw MMIO/DMA） | deny |
| 管理 GPU/显示设备（mint 他人句柄） | `GPU_MANAGE` / `DISPLAY_MANAGE` | deny（仅服务） |

- **与 NET_* / KEY_* / DBG_* / CFG_* 同构**：图形 right 并入 `07` 统一 rights 位图（与 `25` §4.2 `NET_*`、`07` 第四轮 `CFG_*` 同构），默认 deny，显式授予，无「显示 root」。
- **confused deputy 防护**：显示服务/3D 服务作为句柄 mint 委托人，其 mint 权限受「自身 rights 上限 ∩ 客户端请求下限」交集约束（接 `06` §6-2 / `07` §4.5 受约束 mint）。

### 4.3 GPU 能力受限委托（接 `10` 能力网关）

- GPU 的 MMIO/IRQ/DMA 设备能力由 capability 监视器（TCB）在 Stage 4 从可信设备拓扑树 mint（`10` C8 已采纳），经 `10` 能力网关**仅下发给显示服务 / 受控 3D 服务**，不下发客户应用（正面落实「客户应用不直接持 GPU 全局能力」）。
- 客户应用要 3D：向 3D 服务请求一个 **GPU 连接 capability**（由服务 mint，收窄到该客户上下文、无 raw MMIO/DMA right），经 VMO 交 command buffer，服务校验 + 提交；IOMMU（`10` §5-2）强制隔离 DMA，防止越权显存/内存访问。
- 撤销（revoke）：client 崩溃/`close` surface 或 GPU 连接句柄 → 派生链回收（`07` §4.5 revoke 即回收），等价于 seL4 `Revoke`；3D 服务回收该客户 GPU 上下文，避免悬垂显存引用。

### 4.4 输入子系统边界（与合成器协同）

- 输入设备（键盘/鼠标/触控）经 `10` 用户态驱动 → 事件经 `05` Channel/EventPort 上报显示服务；显示服务按 surface 焦点（capability 边界）路由输入事件给对应客户 surface 句柄持有者。
- 窗口隔离 = 输入路由隔离：客户仅接收其自身 surface 的输入（持 `INPUT_RECEIVE` 的上下文），跨窗口输入劫持在 capability 层被杜绝（与 `26` 隔离第一性同构）。

## 5. 与 03 / 05 / 08 / 10 接口边界

> 本节只声明依赖与协同点、不替他域拍板；结论以各子领域文档为准，跨域一致性由 doc-sync 合成 pass 回填。

### 5.1 与 内存管理（03）：graphic buffer = VMO / device VMO，零拷贝数据通路
- **graphic buffer = VMO**：CPU 写入 surface 用普通 VMO（可 map 可写）；GPU 扫描输出用 **device VMO**（GPU 可映射、可 DMA，遵循 `03` §4.4 device 内存隔离「不可写」right）。
- **零拷贝共享**：VMO 句柄经 `05` Channel cap-transfer 在 应用 ↔ 3D 服务 ↔ 合成器 间传递（等价于 DMABUF 跨驱动共享），映射同一物理页，零拷贝。
- **COW child**：surface 快照/截图用 `03` VMO child（`ZX_VMO_CHILD_COPY_ON_WRITE` 式），与 `04` spawn 快照同基元。
- **待协同**：device VMO 是否需新增 `GPU_DMA` 专属 right（`03` §5-6 device 内存建模已定 device VMO 不可写，GPU 导入是否需细粒度 right 待 `07` 定稿）。

### 5.2 与 IPC（05）：surface/buffer 句柄 = capability，就绪复用 EventPort
- **边界**：`05` §1.3 已排除「网络协议栈」但图形亦非 IPC 原语；surface/buffer 句柄与 Channel endpoint / socket 句柄同为 capability（rights 同构）。
- **就绪通知复用 EventPort**：present 完成 / 帧就绪 / 输入事件 → `05` 的 `EVFILT_CHAN`（frame ready）/ `EVFILT_USER`（present done）filter；epoll/kqueue 兼容层直接覆盖。
- **零拷贝**：大块像素经 VMO/SHM（`05` §4.3 / `03` §4.4），小消息（surface 创建/属性变更）经 Channel；与 `05`/网络共用同一套零拷贝基元。
- **待协同**：surface 句柄与 Channel endpoint/socket 句柄在 cap-transfer 上的 type tag 区分（接 `05` §5-2）。

### 5.3 与 Linux 兼容层（08）：呈现 Wayland / X 语义映射
- **native surface API（mkit 子集）**：MeuOS 原生 surface 操作 direct-mapped（`08` §2.2 类别一），mkit 程序零成本直跑。
- **Wayland / X 兼容映射**（待决，见 §6 D-G1）：
  - Wayland client 协议 → 内部 surface capability 操作；wl_surface/wl_buffer 映射为 surface 句柄 + graphic buffer VMO；compositor 内部即 MeuOS 显示服务（或兼容层在显示服务之上呈现 Weston 式 Wayland 前端）。
  - X11（Xlib/XCB）→ 由兼容层/可选 X 服务器翻译为内部 surface 语义；**是否提供原生 X 兼容列为架构级待决**（§6 D-G1）。
  - DMABUF/GBM 语义 → 内部 VMO 共享（`05` §4.3 / `03` §4.4），不引入 Linux `dma_buf` 全局对象。
- **待协同**：`/display` 伪文件视图由 `06` 向统一命名空间生成（`08` D5）；X/Wayland 是否纳入 mkit 子集优先或显式不兼容清单（`08` §7 铁律）。

### 5.4 与 设备驱动（10）：display / GPU 经能力网关出核
- **display controller + GPU = 用户态驱动**（接 `10` §4.2/附录 A）：经 `10` 能力网关获 MMIO/IRQ/DMA 能力；高刷显示可按 `10` 双轨准则评估内核快速路径（优化项，非 Day 1 必需）。
- **GPU 命令提交**：由受控 3D 服务（用户态）持 GPU 能力提交，客户不直连（`10` §5-2 IOMMU 强制化对 GPU DMA 同样适用）。
- **数据通路零拷贝**：驱动 ↔ 3D 服务 ↔ 合成器 经 VMO/SHM（`03`/`05`）。
- **待协同**：GPU 驱动 crash 重启与合成器重连协议（`04` 监督）；多 GPU（独显/核显）的能力委托拓扑（`10` §4.3 匹配/授权）。

### 5.5 与 网络（25）/ 虚拟化（26）的协同（复用同一叙事）
- 与 `25` netstack 同构：都是「重服务出核、内核只给机制、句柄即 capability、VMO 零拷贝」——图形子系统是 `00` A6「重服务出核缩 TCB」原则在显示域的落定，与 `06`/`10`/`25` 同叙事。
- 与 `26` 隔离同构：应用窗口隔离 = surface capability 边界 = `26` 的「capability 边界即隔离第一性」；容器内图形应用仍受容器 Job 的 capability set 约束。

## 6. 自主结论 + 待决项（标注是否需架构裁决）

### 6.1 自主结论

1. **显示合成器应完全用户态（Scenic 式），内核只给四类机制**：display/GPU 设备能力（`10`）+ VMO/device VMO 零拷贝数据通路（`03`）+ capability 守护的 surface/buffer 句柄（`07`）+ EventPort 就绪通知（`05`），**内核零合成/渲染逻辑**。这与 `00`「重服务出核缩 TCB」原则（A6）及 `06` FS、`10` 驱动、`25` netstack 出核形成同一架构叙事。
2. **客户应用不直接持 GPU 全局能力**：GPU 设备能力经 `10` 能力网关受限委托给合成器 / 受控 3D 服务；应用只持 surface 抽象 capability，像素/command 经 VMO + IPC 提交，3D 服务校验后提交硬件，IOMMU 隔离 DMA（正面落实任务约束）。
3. **surface/buffer 句柄即 capability**，rights 在 `mint` 时一次收窄，运行期只位运算（呼应 `19` §1.1 原则 2）；图形 right 并入 `07` 统一位图（与 `NET_*`/`CFG_*`/`DBG_*` 同构），默认 deny。
4. **图形缓冲走 VMO/SHM 零拷贝**（接 `03`/`05`），等价于 DMABUF 跨驱动共享但表达为 capability；帧缓冲走 `03` device VMO（不可写 right）。
5. **应用窗口隔离 = capability 边界**（与 `26` 容器隔离同构）：surface 句柄即隔离边界，输入路由经 capability 焦点授权。
6. **多架构一致**：五架构走同一「设备能力 + VMO」抽象，差异仅驱动后端（C/Rust）与原生 GPU 能力；i386 老 GPU 仅帧缓冲 + 纯 C 后端，无现代 GPU 3D。
