# 49 - 内存·方案 B：分页 + 区域混合的务实模型（保留虚拟地址空间与渐进落地）

> 调研 / 设计文档，由 kernel-plan 团队的「内核规划调研 agent（lite / hy3）」产出。
> 工作树：`kernel-plan` / 分支：`worktree-kernel-plan`。
> 本文是**独立新增方案文档**，**不修改** `00`–`48` 任何章节；行文末尾单列「与现有规划的衔接」而非改动既有文件。
> 定位：为 MeuOS 的**内存与虚拟内存管理**提出**方案 B**——一个从零设计、但**保留进程虚拟地址空间与硬件分页原生语义**的务实模型。它同样不被 Linux 传统（过度匿名映射、全局 `page cache` 语义、OOM-killer）束缚，但**取向与同僚的「方案 A（Region/能力单一抽象、消灭虚拟地址空间）」刻意相反**：方案 B 认为 C/Rust 运行时与存量二进制对**稳定指针 / 线性地址空间**的依赖是现实约束，不应强行重写为"句柄 + offset"模型，而应在保留地址空间的前提下，把"地址空间里的每一段区间"重定义为带 capability 权限的 Region 内核对象。体现"同一任务、不同解法"。

---

## 0. 一句话核心

> **在 MeuOS 中，进程保留一段稳定、线性的虚拟地址空间（由 CPU 分页硬件原生承载），但把"地址空间里的每一段区间"重新定义为带 capability 权限的 Region 内核对象——一段 `(vaddr, len)` + 绑定的 VMO + rights；以 Region 为权限与管理粒度、以 VMO 为数据持有者、`mmap` 不进入原生内核 ABI（由 `mkit` 兼容层翻译为 Region 映射）。既摆脱 Linux 的过度匿名映射 / 全局 page cache / OOM-killer，又不牺牲 C/Rust 运行时与存量二进制对稳定指针的依赖。**

与方案 A 的一句话对照：
- **方案 A**：消灭"虚拟地址空间"这一概念本身，用户态以 **Region 句柄 + offset** 为中心，虚拟地址降为内核实现细节、不对外承诺稳定。
- **方案 B（本文）**：**保留**虚拟地址空间这一一等公民，Region 是"地址空间中带权的一段区间"，权限随 capability；指针稳定、可被运行时依赖。

---

## 1. 方案核心思想

### 1.1 为什么"保留虚拟地址空间"才是务实解（与方案 A 的根本分叉）

方案 A 的洞见——"把 `mmap` 动词改写为 Region 名词、权限随 capability"——是成立的。但它的进一步推论——"虚拟地址只是实现细节、用户态不该依赖裸指针"——对 MeuOS 的**自举终点**（`mcc` + `meuos-libc` 在自研内核上跑通）是过高代价：

| 现实约束 | 方案 A 的代价 | 方案 B 的取舍 |
|---|---|---|
| C 运行时（libc / `malloc` / `setjmp` / TLS）依赖稳定指针 | 需把整套 libc 重写为"句柄 + offset"访问模型，脱离上游 | 保留线性地址空间，`malloc` 仍可返回 `void*`、`setjmp` 仍存指针 |
| Rust 裸机目标（x86_64-unknown-meuos）假定 `usize` 即有效地址 | 需为 MeuOS 定制"非指针内存模型"，破坏与上游 Rust 生态对齐 | 标准 `rustc` 裸机模型直接成立，指针即地址 |
| 存量 Linux binary（经 `mkit` 兼容层）以 `mmap` 返回值做指针运算 | 兼容层必须把"返回 vaddr"伪装成"返回句柄+offset"，每处解引用都要翻译 | 兼容层 `mmap` 直接映射为"返回 vaddr 的 Region 映射"，翻译量最小 |
| 调试器 / profiler 读取内存 | 只能走 Region 句柄视图 | 可走稳定 vaddr + 受约束 inspect，与现有工具心智一致 |

方案 B 的立场是：**解构 Linux 内存管理的目标，不是"消灭虚拟地址"，而是"消灭虚拟地址之上的错误抽象"**——即过度匿名映射、`page cache` 全局语义、权限来自 DAC/地址位置而非 capability、OOM-killer 启发式。这些才是包袱；线性地址空间与分页硬件本身不是包袱，反而是 C/Rust 生态的承重墙。

### 1.2 方案的四条立场（非"铁律"——B 比 A 更贴近硬件现实）

1. **保留进程虚拟地址空间**：每个进程拥有自己的一段线性虚拟地址空间（像 Linux 的"低半用户空间"，但布局由内核 Region 分配器管理、默认全宽 ASLR）。指针是该空间的稳定地址，在 Region 生命周期内不变；不跨 Region 的"裸地址语义"仍然成立（这与 A 的"虚拟地址不可跨 Region 解引用"相反——B 允许，因为 Region 在 B 中是地址空间里**连续且不重叠**的区间，指针在同一空间内可运算，权限由 Region 的 right 在页表级强制）。
2. **保留硬件分页原生语义**：CPU 页表是映射的**一等实现机制**，不是"内部细节"。Region 直接驱动页表项（PTE）的填充与权限位；大页、ASID/PCID、写保护 COW 全部走原生页表。这与 A 一致（A 也保留页表），但 B 不假装"地址对用户态不可见"。
3. **Region 是权限与管理粒度**：地址空间由一组**不重叠、带权、可命名**的 Region 组成；Region 是内核对象、是 capability（有 handle、有 rights、可传递、可 revoke）。但它**锚定在地址空间里**（携带 `vaddr`），而不是像 A 那样"脱离地址空间漂浮"。Region 取代的是 VMA 红黑树作为"权限与管理单元"的角色——权限不再由"区间位置 + DAC"派生，而由 Region 句柄的 right 显式携带。
4. **`mmap` 由兼容层翻译，不进入原生 ABI**：原生内核 ABI 提供 `region_map` / `region_unmap` / `region_protect`（返回稳定 `vaddr`，受 rights 约束）。Linux `mmap` / `munmap` / `mprotect` / `brk` / `madvise` 全部在 `mkit` 内翻译为 Region 操作——这些 Unix 语义不污染原生内核，但原生原语在**语义上等价于一个 capability 化的 mmap**，因此对兼容层与存量 binary 的翻译成本最小。

### 1.3 Region 在方案 B 里到底是什么

方案 A 的 Region = "可独立存活、漂浮于地址空间之外的名词对象"，访问靠"句柄 + offset"。
方案 B 的 Region = "地址空间里的一段连续、带权区间"，定义即：

```
Region := {
    vaddr_base : 虚拟地址（在所属 AddressSpace 内唯一、与同空间其他 Region 不重叠）
    len        : 长度（页对齐）
    vmo        : 绑定的 VMO 句柄（数据来源）
    vmo_offset : VMO 内偏移（页对齐，支持"映射 VMO 中间一段"）
    rights     : {READ, WRITE, EXECUTE, MANAGE, GRANT, REVOKE, DUPLICATE}（可窄于 VMO right）
    name       : 可选调试名（替代 /proc/pid/maps 的文本段名）
}
```

- **与 VMA 的本质区别**：VMA 是红黑树里的一个"区间节点"，权限来自地址位置 + `vm_flags` + 进程 DAC，无独立 handle、不可传递、不可按 capability revoke。`Region` 是带 handle 的 capability 对象——多个 Region 可指向同一 VMO 的不同区间/不同 right；一个 Region 句柄可经 IPC 传给另一进程（对方 attach 进自己的地址空间 = 共享内存）；revoke 一个 Region = 即时解映射 + 回收物理页（按 COW 状态）。
- **与方案 A 的 Region 的本质区别**：A 的 Region 不携带 `vaddr`（地址对用户态不可见）；B 的 Region **携带稳定 `vaddr`**（地址对用户态可见、可运算）。这是两方案唯一的、但决定性的分叉点。

> 图示重点：方案 B 把"线性地址空间"放在图中央（与 A 把它边缘化为"实现细节"相反），Region 是空间里带权的铺砖，页表是 Region 权限的物理落地。

### 2.1 VMO（Virtual Memory Object，数据持有者）

与方案 A §2.1 完全相同继承 `03` 的 VMO：不绑定地址空间的数据对象；类型（空 / 文件-backed / 物理连续 / device 不可写）；句柄即 capability；`vmo_create_child(SNAPSHOT)` 提供 COW。本方案**不重复其定义**，仅强调：VMO 在 B 中仍是"纯粹的数据"，地址相关的一切都在 Region 侧，二者职责清晰分离（VMO 管"有什么数据"，Region 管"放在地址空间哪里、以什么权限可见"）。

### 2.2 Region（地址空间内带权的连续区间，方案 B 新核心）

- **定义**：见 §1.3。`Region` 是 `AddressSpace` 中一段连续、不与同空间其他 Region 重叠的虚拟区间，绑定一个 VMO（含偏移），携一组 rights，并有独立 handle（capability）。
- **与 VMA 区别**（见 §1.3）：VMA 无 handle、权限来自地址位置 + DAC；Region 是 capability 对象、权限显式随句柄。
- **与方案 A 的 Region 区别**：A 的 Region 不携带 `vaddr`、漂浮于地址空间之外、访问靠句柄+offset；B 的 Region **携带稳定 `vaddr`**、锚定在地址空间内、指针可运算。这是两方案决定性分叉。
- **生命周期**：`region_map(as, vmo_handle, vmo_offset, len, rights, [hint_vaddr])` 在地址空间分配一段不重叠区间、建立 VMO 绑定、返回稳定 `vaddr`；`region_unmap(region_handle)` 解映射、回收页表；`region_protect(region_handle, new_rights)` 改权限（只能收窄或持平父 VMO right，对齐 `03` §4.3.4 层级收缩）；`region_resize`（仅允许堆类空 VMO Region 向上增长，替代 `brk` 语义）。
- **可见性即 capability**：一个 VMO 对该进程是否"可见、可访问"，取决于该进程地址空间是否含指向它的 Region；但不同于 A，B 中"可见"还意味着"有一个稳定的 `vaddr` 可以解引用"。

### 2.3 AddressSpace（线性虚拟地址空间 = Region 集合）

- **定义**：一个进程**拥有的一段线性虚拟地址空间**，由一组**不重叠、各带权**的 Region 铺满（含 guard hole 与内核/用户分界）。它是 `46`/`47` 进程方案的精确落地（Process = AddressSpace + 句柄表 + Thread 集），但**保留线性地址空间的语义**（与 A 把 AS 视图降级为"句柄集合"相反）。
- **本身是 capability**：持有 AddressSpace 的 `MANAGE` right 才能 `region_map` / `region_unmap`；普通代码持有具体 Region 句柄做访问与传递。
- **地址稳定性**：Region 在其生命周期内 `vaddr` 不变（除显式 `region_unmap` 后重映射）；ASLR 在 `region_map` 分配区间时一次性随机化，之后稳定。这让 C 运行时、`malloc` 返回指针、共享库 GOT/PLT、Rust 裸机目标全部直接成立。
- **页表是 Region 的物理落地**：切换进程 = 切换 AddressSpace 的页表基址 + ASID/PCID（同 `03` §4.3.2）；Region 的 right 直接映射为 PTE 的 R/W/X 位。

### 2.4 页表（硬件分页，原生一等机制）

- **保留 `03` §4.3.1 的 `arch/mm/pagetable` 抽象**（`map`/`unmap`/`walk`/`set_flags`），方案 B 不边缘化页表——它是权限的物理强制点。
- **大页**：2MB/1GB 大页作为 Region 的"连续对齐映射优化"（Phase 2），Region 接口不变，内核在 `region_map` 时若区间/对齐满足则升级为 huge PTE。
- **COW**：`MAP_PRIVATE` / `vmo_create_child(SNAPSHOT)` 写时，PTE 标记为只读 + `MmPage.refcount>1`，写入触发缺页 → 分配新页复制（同 `03` §4.3.3）。B 与 A 在 COW 实现上一致，差异仅在"是否暴露地址"——B 暴露。

### 2.5 capability right（权限随 capability）

继承 `07` §4.1 / 冻结位图（bit 0–6 基础 right，已与方案 A §2.5 一致，不与 `CFG_*`/`KEY_*`/`NET_*`/`BLOCK_*`/`GPU_*`/`LOAD` 等 bit 9+ 冲突）：

| 对象 | right | 含义 |
|---|---|---|
| **VMO 句柄** | `READ`/`WRITE` | 读/写 VMO 数据（不涉地址空间） |
| | `MANAGE` | `vmo_create_child`、设 pager、retype |
| | `GRANT` | 经 IPC 把 VMO 句柄传给他人 |
| | `REVOKE` | 撤销派生链下游句柄 |
| | `DUPLICATE` | 复制句柄（同 right 克隆） |
| **Region 句柄** | `READ`/`WRITE`/`EXECUTE` | 该段地址空间以何权限访问（可窄于 VMO right，落 PTE R/W/X） |
| | `MANAGE` | 调整本 Region 区间/right（不可放宽父 VMO 已收紧者） |
| | `GRANT` | 经 Channel 把 Region 句柄传给另一进程（对端 attach = 共享内存，携带其 vaddr 重新分配） |

- **派生树（derivation tree）**：同 A / `07` §4.5，revoke 一个 Region 句柄 → 解映射 + 回收页表；revoke 一个 VMO 句柄 → 触发整条派生链（含所有下游 Region）回收。
- **权限随 capability，不可隐式提升**：任何提权诉求必须由持有 `GRANT` 的对端显式重新授予受限句柄。

### 2.6 与方案 A 的抽象层差异（速查表）

| 维度 | 方案 A | 方案 B（本文） |
|---|---|---|
| 虚拟地址空间 | 被消灭，降为"实现细节" | **保留为一等公民**，线性、稳定、可运算 |
| Region 本质 | 漂浮于地址空间之外的名词对象 | **锚定在地址空间内的带权区间**（携带 `vaddr`） |
| 用户态访问模型 | Region 句柄 + offset（CHERI 式） | 稳定指针 + capability right（C/Rust 原生） |
| 原生映射原语返回值 | 无 vaddr（句柄） | **返回稳定 `vaddr`**（capability 化 mmap） |
| 对 libc/`malloc`/TLS 的影响 | 需重写内存模型 | 直接成立，零改造 |
| 与 Fuchsia VMAR 的距离 | 远（取代 VMAR） | **近（Region ≈ 带 right 的 VMAR）** |
| 与方案 A 的共性 | VMO 数据持有者、COW child、pager、`mmap` 仅在兼容层、revoke 派生树回收、C1 折中 C 物理归属 | 同左 |

## 3. 多系统参照（解构非缝合）

> 原则：每个参照系统只取其"解构后的内核思想"，不与其它系统缝合；明确标注"借什么、不借什么"。方案 B 的参照重心与方案 A 不同——A 借 Multics 段 / CHERI 指针；**B 借 Linux vm_area 的"地址区间"、Fuchsia VMAR 的"地址空间层级"、Windows section 的"可映射视图 + 保护属性"**，并保留分页硬件。

### 3.1 Linux `vm_area_struct` — 连续虚拟区间 + 缺页 + 保护位

- **借**：① "地址空间由一组连续虚拟区间构成、缺页按需填充"这一**务实骨架**；② PTE 的 R/W/X 保护位作为权限的物理强制点；③ 大页 / ASLR / guard page 的区间级机制；④ `fork` 用页表写保护 COW（而非整段拷贝）。B 继承的是 Linux 内存管理的**骨架**，剔除其**语义包袱**。
- **不借**：① VMA 用红黑树"管理地址区间"且**权限来自地址位置 + `vm_flags` + DAC**——B 把权限改为 Region 句柄的 capability right，与 DAC/uid 解耦（对齐 `07`）；② **全局 `page cache`**——B 中文件数据 = 文件-backed VMO + pager，无独立全局缓存结构（继承 A7）；③ **过度匿名映射**——Linux 把"堆/栈/一切临时内存"默认做成 `MAP_ANONYMOUS` 海洋；B 中"匿名内存" = 显式创建的空 VMO Region，且堆是可 `region_resize` 的具名空 VMO 段（非 `sbrk` 游标）；④ **OOM-killer**——B 用 Job 配额 + revoke 派生树，fail-closed（分配失败返回错误，不杀进程）。

### 3.2 Fuchsia (Zircon) — VMO + **VMAR**

- **借（B 与 VMAR 高度同构）**：① VMO 数据持有者、child `SNAPSHOT` COW、pager 零拷贝（同 A7）；② **VMAR 的"地址空间中的连续区域 + 随机化 + 层级权限收缩"**——这正是 B 的 Region 的精神原型！B 的 Region ≈ "带 capability right 位图的 VMAR"。③ `ZX_VM_COMPACT` / specific 映射做 guard page 的区间分配思想。
- **不借**：① Zircon VMAR **不携带 capability rights 位图**——它靠进程对 root VMAR 的 handle rights 间接约束，区间自身无独立 right。B 给每个 Region 句柄挂 `07` 的 right 位图（更细、可独立传递/revoke）。② Zircon 把"映射"做成 VMAR 的动词操作（`zx_vmar_map`），仍带 `mmap` 影子；B 把"映射"做成返回 `vaddr` 的 `region_map` 原语，且 `mmap` 只在兼容层。

### 3.3 Windows — Section Object + View（最被忽视的参照）

- **借**：① **Section Object** ≈ VMO——它是"可被映射到地址空间的文件/内存对象"，与 VMO 的"数据持有者、不绑地址空间"高度同构；② **View of Section** ≈ Region——把 Section 映射进某进程地址空间的一段视图，携带 `PAGE_READ`/`PAGE_READWRITE`/`PAGE_EXECUTE` 等**保护属性**（即 B 的 right 落 PTE）；③ Windows 把"映射视图"与"对象本身"分离（Section ↔ View），与 B 的 VMO ↔ Region 分离同构；④ `SEC_IMAGE` 把 PE 映像直接映射为可执行视图——对应 B 把 ELF/PE 加载为"只读+执行 Region"。
- **不借**：① Windows 的 `DACL`/`SID` 全局 DAC 权限——B 用 capability right 替代（对齐 `07`）；② Windows 的 session/desktop 隔离与全局命名 section（`\BaseNamedObjects`）——B 无全局命名空间，共享内存 = 显式传递 Region 句柄（对齐 `00` A4 每进程 namespace）；③ Windows 的 `MEM_RESERVE`/`MEM_COMMIT` 两阶段与 `VirtualAlloc` 习惯——B 用惰性提交（缺页才取物理页），语义更近 Linux/Fuchsia。

### 3.4 seL4 — Capabilities + Untyped

- **借**：① Region 句柄即 capability，权限随句柄、可 revoke（`07` Day1 已采纳）；② "untyped → retype" → VMO 可从空 retype 为文件/物理/device；③ `Revoke` 触发派生链回收（方案 B 的 revoke 即回收）。
- **不借**：纯 seL4 式"运行期物理内存整体交用户态内存服务"（C1 已明确拒绝折中 B）——内核 buddy 仍是物理页真相源（与 A 一致）。

### 3.5 CHERI — 能力化指针（可选硬件加速层）

- **借（可选）**：Region 的 `(vaddr 区间, rights)` 是"对象级 capability"；若硬件支持 CHERI，Region 的 bounds/rights 可由 CHERI capability 指针在指令级强制——这是"权限随 capability"的极致形态，与 B 的 Region 抽象完美互补（且 B 已保留线性地址空间，CHERI 指针即"带 bounds 的 vaddr"，无缝叠加）。
- **不借**：CHERI 的"每条指针都是能力"粒度在纯软件层过重；B 在 Region（区间级）落地，CHERI 作为底层可选强制，二者不重叠、可叠加（与 A 同构，但 B 因保留地址空间而更自然）。

## 4. 与 MeuOS 现有规划的衔接

> 本节只"引用 + 对齐"，不修改 `00`/`03`/`04`/`07`/`08` 任何章节。本节以 `03`（内存管理现状，任务所指"04-内存与虚拟内存"的实际落盘文件）、`04`（进程/调度）、`00`（路线图）、`07`（安全模型）、`08`（Linux 兼容层）为衔接对象。

### 4.1 继承 C1 折中 C（物理归属）

`03` 第三轮回写 C1 = 折中 C（已采纳）：内核 buddy **独占**物理页帧数据库，作为 Job 配额强制与 revoke 回收的**单一真相源**；VMO 作为 capability 视图。方案 B **完全继承**——Region 只是"地址空间里的 VMO 视图 + 权限"，物理归属真相源不变；device 内存仍走不可写 device VMO（C1 子思想）。

### 4.2 继承 00 A7（VMO/VMAR + pager 零拷贝）

A7 采纳"VMO/VMAR + pager 零拷贝、fork 用 VMO CoW 快照"。方案 B 保留 VMO + pager，把 **VMAR 升级为带 capability right 的 Region**（B 比 A 更接近原 VMAR 语义，只是补上 right 位图）。`fork`/`spawn` 时用 `vmo_create_child(SNAPSHOT)` 产生 COW 子 VMO，再各自 `region_map` 为 Region（与 `47` 进程方案 B 的"spawn 显式注入句柄、fork 走 COW 近似"一致——共享内存 = 显式传递同一 VMO 的 Region 句柄）。

### 4.3 继承 07 capability Day1

Region 句柄 = capability，rights 用 `07` 冻结位图 bit 0–6，默认拒绝、可审计、可撤销（继承 `07` §4.1 / `04` §4.5）。revoke 即回收的派生树语义与 `07` §4.5 完全一致。`unveil` 对内存映射的约束粒度自然落到 **Region 级**（映射时即带 right，无"先映射后 mprotect"两步），与 `06` "路径即 capability 命名维度"在内存侧同构。

### 4.4 与 04 进程 spawn / Job 对齐

`04` / `46` / `47` 中 Process = "AddressSpace + 句柄表 + Thread 集"、spawn 从空地址空间 + 显式句柄注入开始、Job 是资源账本与生命周期单元。方案 B 的 AddressSpace = "进程拥有的线性 VA 空间（Region 集合）"，由一组 Region 铺满；spawn 时父把要共享/克隆的 VMO 以相应 right 的 Region 注入子地址空间（子空间重新分配 `vaddr`，但数据/权限不变）。Job 内存配额是 Region 提交物理页的硬上限（`03` §5 开放议题的逻辑闭环：配额 = 承诺上限，超则 fail-closed）。

### 4.5 与 03 现状的差异（替换 VMA 的"权限管理"角色，保留地址空间）

`03` §4.3.3/§4.3.4 用 VMA 红黑树 + `mmap`/`mprotect`/`munmap` 管理地址区间，权限来自 `vm_flags` + DAC。方案 B 的变更：
- **保留** `03` M5（页表 arch 抽象）、M6（地址空间布局）、M7（ASID/PCID）、M9（匿名缺页）、M10（COW）——这些是"分页硬件原生语义"，B 全盘继承。
- **替换** `03` M8（VMA + mmap/munmap/mprotect）的管理语义：以 **Region 对象**取代 VMA 作为权限与管理单元；`mmap` 系列语义下放到 `mkit` 兼容层，原生 ABI 用 `region_map` / `region_unmap` / `region_protect`（返回稳定 vaddr）。
- **保留** `03` M11/M12（VMO/VMAR + 文件映射）的 VMO 部分，把 VMAR 升级为 Region。

### 4.6 与 08 兼容层 mmap 翻译

`08` 要求 MM 至少语义支持 `mmap`/`munmap`/`mprotect`/`brk`/`madvise`/`MAP_FIXED`/`MAP_SHARED`/`MAP_PRIVATE`/`MAP_ANONYMOUS`。方案 B 的翻译路径**比方案 A 更短**（因原生 `region_map` 返回 vaddr，与 `mmap` 语义几乎同构）：
- `mmap(addr, len, prot, flags, fd, off)` → `vmo = (fd? vmo_from_file(fd, off) : empty_vmo()); region_map(as, vmo, off, len, prot→rights, hint=addr)` → 返回 `vaddr`（直接满足 `mmap` 返回指针的契约）。
- `MAP_ANONYMOUS` → 创建空 VMO 再映射（显式、有类型，非"匿名海洋"）。
- `MAP_SHARED`/`MAP_PRIVATE` → 共享 = 同 VMO 多 Region；私有 = `vmo_create_child(SNAPSHOT)`。
- `brk`/`sbrk` → 对"堆 Region"调用 `region_resize`（向上增长具名空 VMO 段）。
- `madvise(MADV_DONTNEED)` → `region_unmap` 该区间（显式，非模糊提示）。
- `MAP_FIXED` → `region_map` 带 `hint_vaddr` 强制（受不重叠约束，越界即失败，不静默强占）。

### 4.7 对 overcommit / swap / 共享内存 的态度

- **overcommit**：默认惰性提交（缺页才取物理页），但 Job 配额是硬上限（非无限 overcommit），超配额 fail-closed（同 `00`/`46` 无全局关沙箱精神，根上消除 OOM-killer 不可预测性）。
- **swap**：不是全局机制，是 pager 的一类后端（swap-backed VMO 的 pager），Day1 不做，演进期表达为 pager 实现，不另立独立 swap 子系统。
- **共享内存**：不是特殊机制 = "把同一 VMO 的两个 Region 分别映射进两个 AddressSpace"（各自有 `vaddr`）；经 Channel 传 Region 句柄 = 对端 attach 进自身空间（新 `vaddr`，数据/权限不变），天然 capability 化、可 revoke。

## 6. 相对传统内存管理：摆脱的包袱与代价

### 6.1 摆脱的包袱

| 传统包袱 | 方案 B 如何消去 |
|---|---|
| 过度匿名映射（`MAP_ANONYMOUS` 海洋） | "匿名内存" = 显式创建的具名空 VMO Region（有类型、有权限），非默认海洋；堆是可 `region_resize` 的空 VMO 段（无 `sbrk` 游标伪概念） |
| 全局 `page cache` | 文件数据 = 文件-backed VMO + pager，无独立全局缓存结构（继承 A7） |
| VMA 权限来自 DAC/地址位置 | 权限 = Region 句柄的 capability right，与 uid/DAC 解耦（对齐 `07`） |
| OOM-killer 全局暴力回收 | 惰性提交 + Job 配额硬上限 + revoke 派生树回收，fail-closed 无杀进程 |
| `madvise` 启发式（MADV_DONTNEED 等） | 用 Region 级显式操作（`region_unmap` / `region_resize`）替代模糊提示 |
| `MAP_SHARED`/`MAP_PRIVATE` 双语义 | 共享 = 同 VMO 多 Region；私有 = `vmo_create_child(SNAPSHOT)` |
| 独立 `swap` 子系统 | swap = swap-backed VMO 的 pager 实现（演进期） |

> 与方案 A 的区别：B **保留**线性虚拟地址空间与指针语义（不把"虚拟地址"列入包袱），只清除其上的错误抽象。A 把"虚拟地址空间本身"也列为包袱。

### 6.2 代价

1. **保留地址空间的管理成本**（比 A 高、比 Linux 低）：B 仍需管理地址空间布局、区间分配（不重叠约束）、ASLR、碎片——但由 Region 分配器统一管，且因 Region 携带 right 与 name，元数据比 VMA 红黑树更利于审计。换来的是 **libc/运行时/存量 binary 零改造**，这是 B 相对 A 的核心务实收益。
2. **兼容层翻译成本**（比 A 低）：因 `region_map` 返回稳定 vaddr，与 `mmap` 语义近同构，`mkit` 翻译量小于方案 A（A 需把"返回句柄+offset"伪装成"返回指针"）。但 Unix 语义不进入原生 ABI，隔离在 `mkit` 内（与 `00`/`08` 一致）。
3. **底层页表仍存在**：CPU 执行需虚拟地址，内核 `arch/mm` 仍建页表、仍需 ASID/PCID 切换——这部分 `03` M5/M7 不变，unsafe 收敛在 `arch/mm` 与 `mm::raw`（继承 `03` §4.5）。
4. **Region 句柄元数据开销**：每个 Region 是内核对象（句柄表槽 + right + 区间记录），与 VMA 节点同量级，但换来"可传递/可撤销/权限随句柄"的能力化收益。
5. **工具链适配**：debugger / profiler / 自观测（`12`）可走稳定 vaddr + 受约束 inspect，比 A 更贴近现有工具心智；但仍需从 Region 视图而非 `/proc/pid/maps` 读取（与 `06` inspect 树、`46` 无全局 PID 表一致）。

## 7. 与方案 A 的关键差异（决策速查）

| 决策点 | 方案 A（同僚） | 方案 B（本文） | 对 MeuOS 的含义 |
|---|---|---|---|
| **虚拟地址空间** | 消灭，降为内核实现细节 | **保留为一等公民**，线性、稳定、可运算 | B 对 C/Rust 运行时与存量 binary 友好，自举阻力最小 |
| **Region 本质** | 漂浮于地址空间之外的名词对象 | **锚定在地址空间内的带权区间**（携 `vaddr`） | B 的 Region ≈ 带 right 的 Fuchsia VMAR；A 的 Region 更像 CHERI 段 |
| **用户态访问** | Region 句柄 + offset | 稳定指针 + capability right | B 让 `malloc`/TLS/`setjmp`/GOT 直接成立 |
| **原生映射原语** | 返回句柄（无 vaddr） | **返回稳定 `vaddr`**（capability 化 mmap） | B 的 `mkit` 翻译路径最短 |
| **与既有参照距离** | 近 Multics 段 / CHERI 指针 | **近 Linux vm_area / Fuchsia VMAR / Windows section** | B 借"地址区间 + 保护属性"骨架，剔其语义包袱 |
| **libc/`malloc`/TLS 改造** | 需重写内存模型 | **零改造** | B 务实，直跑上游生态 |
| **共性（两方案一致）** | VMO 数据持有者、COW child、pager、`mmap` 仅在兼容层、revoke 派生树回收、C1 折中 C 物理归属、07 capability Day1 | 同左 | 两方案在"数据模型/回收/物理归属/安全"上同构，仅"地址空间是否对用户态可见"分叉 |

> **一句话给指挥官的取舍**：若 MeuOS 的首要目标是"用最小阻力自举 `mcc`+`meuos-libc` 并直跑存量 Linux binary"，选 **方案 B**（保留地址空间，Region 是带权的地址区间）；若首要目标是"从根上演示一个无裸指针、CHERI 友好的能力化内存范式"，选 **方案 A**（消灭地址空间，Region 是漂浮名词）。两方案在 VMO / COW / pager / revoke / 物理归属 / capability 上完全兼容，可视为"同一数据模型上的两种用户界面"。

## 8. 小结

方案 B 把 MeuOS 的内存管理从"Linux 四套纠缠机制"解构为"分页硬件原生承载 + Region 带权区间 + VMO 数据持有 + capability 权限"的务实混合模型：进程拥有稳定的线性虚拟地址空间（C/Rust 生态的承重墙），地址空间由一组不重叠、带 capability right、可命名、可传递、可 revoke 的 Region 铺满；VMO 持有数据、COW child 表达私有、pager 表达文件、revoke 派生树表达回收；`mmap` 不进入原生 ABI，由 `mkit` 翻译为 `region_map`（返回稳定 vaddr）。它继承 C1 折中 C（物理归属）、00 A7（VMO+pager）、07 capability Day1、04/`46`/`47` 进程 spawn/Job，并把 `03` 的 VMAR 升级为带 right 的 Region——既摆脱过度匿名映射 / 全局 page cache / OOM-killer / DAC 派生权限，又**保留虚拟地址空间与硬件分页原生语义**，对现有二进制与运行时最友好。与方案 A 的唯一决定性分叉是"虚拟地址空间是否对用户态可见、Region 是否携带 `vaddr`"——其余抽象完全兼容，可视为同一内核数据模型的两种用户界面。
