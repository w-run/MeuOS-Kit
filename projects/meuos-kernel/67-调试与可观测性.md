## 0. 一句话核心结论

> **MeuOS 的调试与可观测性必须建成「以 `12` 的 inspect 树 / 事件流 / 崩溃报告三基元为地基、以 6 个 `DBG_*` right 为统一 capability 门控、按 Job/进程粒度受 namespace 约束、五架构同源、自举期以串口+`.mimg` 自检兜底」的受控可观测面——不引入任何新内核原语（kdebug 会话=既有 `DBG_*` right 的组合，不进 bit 48+ 专属位），所有观测动作均可经 `65` 能力审计 replay，且 `DBG_INSPECT` 不变量由监督者持续监控，绝不退化成「默认可读」后门。**

## 1. 范围与地基：本文与 `12` / `39` 的分工边界

## 2. inspect 层级：受控可读子树（与 `12` / `47` / `06` 协同）

### 2.1 方案：三层 inspect 子树 + 按子树粒度授权

`12` §4.4 已定义 inspect 树（kernel / jobs / services 三层）。本文把「可控子树」收口为**按命名空间投影的读边界**，与 `06` C3（每进程独立 namespace、无全局 `/`）同源：

```
inspect root（受 capability 约束，无全局可读）
├─ kernel/            内核快照（调度/内存/IPC/能力表）—— 受 DBG_INSPECT（限 kernel 子树）
│    ├─ scheduler/     每 CPU 运行队列、EEVDF 账本（接 04 §4.3 / 57）
│    ├─ memory/        buddy/VMO/VMAR 统计（接 03）
│    ├─ ipc/           Channel/EventPort 句柄计数（接 05，受 Job 账本约束）
│    └─ capability/    能力表摘要（接 07，仅类型/数量，不泄露句柄值）
├─ jobs/<id>/         每 Job 资源账本 + 进程树（接 04 §4.4）—— 受 DBG_INSPECT（限该 Job 子树）
│    ├─ ledger/        CPU/内存/句柄数/IO 配额与用量
│    ├─ processes/     子进程列表（含 47 scoped 标识 job-path+tag）
│    └─ children/      子 Job 递归
└─ services/<n>/       用户态服务自报指标（histogram/lazy）—— 受 DBG_INSPECT（限该服务子树）
```

**关键粒度**：授权不是「持有 `DBG_INSPECT` 即读全树」，而是**持有「某 Job handle + 限定该 Job 子树的 `DBG_INSPECT` right」**——与 `47` §2.7「scoped 标识是 capability 之上的展示层」一致：`DBG_INSPECT` 读的是进程/Job 自身的 inspect 子树，无全局可读（`12` §引用澄清（来自24）`/`47` §4.4）。

### 2.2 约束：namespace 投影 + scoped 标识 + 默认 deny

- **namespace 投影（接 `06` C3 / `14` C3）**：inspect 子树的可见节点本身是每进程 namespace 的投影（`47` §4.4），「内核无全局 `/`」意味着也不存在「全局 inspect 根可读」——持权者只能读自己被授权投影出的那部分（`12` R3-6 呼应 `14` C3）。
- **scoped 标识（接 `47` §1.1 / §2.7）**：`job-path + ephemeral tag` 是 inspect 节点的展示标签，受 `DBG_INSPECT` 约束生成，是 capability 可见性的投影而非独立寻址维度——运维/日志可读，但不参与 spawn/寻址（`47` §6.3 代价清单第 6 点）。
- **默认 deny（接 `12` R3-5）**：spawn 出的进程不持任何 `DBG_*`；读 inspect 必须持受 `GRANT` 的 `debug-issuer` 显式授予的受限 handle。

### 2.3 权衡与推荐立场

| 方案 | 优点 | 风险 | **本文推荐** |
|------|------|------|------|
| A. 单一 `DBG_INSPECT` 读全树 | 简单 | 违反最小特权（读 services 即能读 kernel 能力表） | 否 |
| B. 每子树独立 right（INSPECT_KERNEL / INSPECT_JOB / INSPECT_SVC） | 最细 | right 位爆炸、与 `12` 6 right 体系冲突 | 否（不新增 right） |
| **C. 单 `DBG_INSPECT` right + 按目标对象（Job/进程 handle）限定子树**（本文） | 复用 `12` 体系、粒度靠「授权时绑定的对象」实现、不新增 right | 授权时需显式绑定子树范围 | **是** |

> **推荐立场**：采用方案 C——`DBG_INSPECT` 的粒度由「被授予的 handle 所指向的对象（某 Job / 某进程 / 某服务）」决定，而非新增 right 位。这与 `07`「权限随句柄走、rights 只减不增」同构，且是 `12` 已定稿姿态的自然延伸。

## 3. kdebug 协议：capability 门控的内核调试会话

### 3.1 方案：调试会话 = 受权 handle 组合，不经新对象

「交互式内核/进程调试会话」（pause / step / read-mem / set-bp / write-mem）在 capability 世界应被建模为一组**受权 handle 的组合**，而非一个新内核对象：

- **会话建立**：调试器持目标进程/Job 的 `DBG_ATTACH` handle（读侧：暂停/单步/读寄存器/读内存/设观察点，`12` R3-6 单步归 `DBG_ATTACH`）即建立调试会话；`DBG_POKE` 单独授予才允许改写目标内存/寄存器/断点（`12` R3-5，绝不随 ATTACH 自动获得）。
- **内核态调试会话**：经 QEMU gdbstub 的完整调试力（含内存写）是原型期桥接通道（`12` §4.8），位于 VM 边界、由 QEMU 控制方持有，**不进入 MeuOS capability 模型**——生产 in-guest 调试回到 `DBG_ATTACH`/`DBG_POKE` 守护模型。
- **会话即 capability，非全局权**：不存在 uid=0 式「调试 root」；监督者 meu-supervisor 也只持所需 `DBG_*` 子集（`12` §4.2）。

### 3.2 门控：复用既有 `DBG_*` 还是新增 bit 48+ 专属 right（权衡）

`59` §9.3 开放议题 1 已确立：`Cap(IRQ n)` 的 `IRQ_*` right 进 **bit 48+ 预留区**（与 `SCENE_SESSION` 同区，不挤占 0–47）。这引出一个类比问题：**kdebug 会话是否需要一个专属的「调试会话 right」落到 bit 48+，还是完全复用 0–47 的 6 个 `DBG_*`？**

| 维度 | 复用 0–47 的 `DBG_*`（本文推荐） | 新增 `DBG_SESSION` 进 bit 48+ |
|------|------|------|
| 与 `12` 体系一致性 | 完全复用已定稿 6 right，零新增 | 与 `12` R3-5 已定稿的 6 right 并列，需 `12`/`07` 二次回写 |
| 表达力 | 「会话」= `DBG_ATTACH`(+可选`DBG_POKE`) 的持有状态，足够区分「能调试」vs「不能」 | 可区分「会话持有」vs「单次操作授权」，粒度更细 |
| bit 预算 | 0–47 的 `DBG_*` 簇（ATTACH=bit16 / CRASHDUMP=bit17 / INSPECT/TRACE/PROFILE/POKE 同簇）已覆盖 | 占 48+ 预留区，与 `IRQ_*`/`SCENE_SESSION` 同位段 |
| 风险 | 无新增面 | 新 right = 新攻击面（`29` §1.3 公理 4「调试权=后门级面」），须单列建模、永不默认 |
| 是否复用 `MANAGE`/`GRANT` | 否——调试权不借 `MANAGE`/`GRANT` 扩散（`29` T6 同构） | 同样须显式授予，不借 `MANAGE`/`GRANT` |

> **不复用 `MANAGE`/`GRANT`**：无论选哪条路，调试会话权都**绝不**借 `MANAGE`（管理权）或 `GRANT`（派生权）隐式扩散——这与 `29` T6（DBG_POKE 绝不随 ATTACH）/ `29` D-T1（`KERNEL_PRIV` 不随普通 `GRANT` 扩散）的「高危权永不默认、显式单列」一致策略同源。

### 3.3 推荐立场 + 待决 D1

**推荐立场**：kdebug 会话 = 既有 `DBG_ATTACH`（+ 可选 `DBG_POKE`）handle 的持有状态，**不新增 bit 48+ 专属 right**。理由：① 百思纪律「不引入新内核原语除非必要」——6 `DBG_*` 已能完整表达调试会话；② 与 `12` 定稿体系零冲突；③ 避免新增后门级攻击面（`29` §1.3 公理 4）。

**已闭环·第九轮采纳不新增**（原待决 D1，原需大喵拍板，见 §9）：若未来确需区分「会话持有」与「单次操作授权」（如细粒度审计/计费），是否新增 `DBG_SESSION` 专属 right 落 bit 48+ 预留区（与 `IRQ_*`/`SCENE_SESSION` 同位段）——本文推荐**不新增**，但 reserved 区已为这种演进留好位置，不阻塞。

## 4. tracing：ftrace 式低开销追踪 + Job 账本配额（与 `39` 协同）

### 4.1 方案：结构化事件流 + per-Job 配额开关

`12` §4.4 的事件流（syscall/调度/异常/IO 事件，带 schema）与 `39` 的 ftrace 式 tracing 是同一机制的两面：内核/用户态经**结构化事件缓冲区**（capability 约束的 ring buffer）emit 带 schema 的事件，消费者持 `DBG_TRACE` right 经 Channel 订阅（`12` §4.2）。本文把「低开销」与「配额」收口：

- **低开销开关**：tracing 默认**off**（零开销），持 `DBG_TRACE` 者开启后，事件经 per-CPU 无锁 ring buffer 写入，避免全局锁（`39` 新维度）。开销与 `19-性能与可验证性.md` 的 tracing 基准同源量化。
- **随 Job 账本配额（接 `04` §4.4 / `07` §4.3 / `00` A5）**：tracing 缓冲区大小、事件速率上限计入**目标 Job 的资源账本**——调试者订阅他人 Job 的 trace 时，开销由**被观测 Job** 的账本承担（防 `29` T8 IPC 洪泛式 DoS），而非无界占用内核内存。

### 4.2 与 `39` 协同 + 用户态自描述

- **schema 自描述（接 `12` §4.4）**：事件带 protobuf/ETW 式 schema，避免文本解析；用户态服务经 FIDL 反射式自描述事件（`12` §3.1 取 Fuchsia/perfetto），跨架构同源（`00` §5-6 五架构一致性）。
- **统一时间线（接 `39` / `57-时钟与时间子系统.md`）**：所有事件打 monotonic 钟（`57` 单调钟/墙钟分离），与 perfetto 式统一追踪时间线对齐。

### 4.3 权衡：开销 vs 侧信道（待决）

| 维度 | 推荐 | 待决 |
|------|------|------|
| 跨 Job 追踪 | 原型期 `DBG_TRACE` 限同 Job 内；跨 Job 订阅需更高权（侧信道，`29` T12 同 `DBG_PROFILE`） | 跨 Job trace 是否需独立 right？归 `12`/`39` 协同（D2） |
| 采样 vs 全量 | 默认全量事件（低开销开关），`DBG_PROFILE` 单独管 HW counter 采样 | `DBG_PROFILE` 跨 Job 侧信道评级（接 `29` D-T7） |

> **推荐立场**：tracing 复用 `DBG_TRACE`，配额计入被观测 Job 账本；跨 Job 追踪与 `DBG_PROFILE` 侧信道同待 `12`/`39`/`29` 协同定稿，本文不预占。

## 5. crashdump 格式：与 `12` / `59` / `61` 协同

### 5.1 方案：CrashReport 落盘格式 + `.msys` 校验/加密

`12` §4.3 的 `CrashReport{ source, faulting_pc, register_set, stack_frames[], job_id, capability_context, symbolized }` 是统一崩溃报告；`59` §6.4 规定其经 exception channel **copy 语义多播**给监督者（`DBG_CRASHDUMP` 默认订阅）+ 持权调试器（`DBG_ATTACH` 仅收副本）。本文收口**落盘字节布局**：

```
crashdump 条目（= inspect 树节点 kernel/crashdumps/<seq>/，接 12 §4.7）
├─ header:    source 枚举 / 版本号 / 时间戳（monotonic+wall，接 57）
├─ identity:  job_id / process_id / 47 scoped 标识（job-path+tag）
├─ fault:     faulting_pc / fault_type / register_set（现场）
├─ frames:    stack_frames[]（统一 StackFrame{ pc, symbol?, module, offset }，接 12 §4.5）
├─ cap_ctx:   capability_context（崩溃时持有 rights 摘要，供事后审计，接 65）
├─ symbol:    symbolized 标志 + 符号上下文指针（内核符号表/目标 ELF，接 12 §4.5）
└─ integrity: SHA-256（条目级，复用 .msys v2 校验，接 11 §4.1 / 61 §3.3）
              + 可选 ed25519/对称加密（敏感内存快照，仅 DBG_CRASHDUMP 可读，接 06）
```

- **结构化落盘**（非自由文本 core）：crashdump 是 inspect 树节点，与「结构化优于文本」（`12` §5 结论 1）一致；与 `.msys` 原子更新同源（`61` §6）。
- **触发条件**（接 `12` §7-6）：仅 `dump+restart` / `升级` 策略触发落盘，普通 kill 不落盘；**内核 panic 必落盘**（系统已停机，`12` §4.3）。

### 5.2 与 `61` 早期自检协同

- **自举期崩溃**：Stage 1–3（cap 世界未起）的 panic 无 `CrashReport` 通道，直接经**早期串口 emergency-write 窄 cap**（`61` §4.4 / `60` E1）输出 banner + 现场寄存器，并（若可用）写入 `.mimg`/`.msys` 自检区（`61` §8.1 Day1 本地自检）。进入 Stage 4 后，统一故障入口（`02` §4.5 `panic_handler`）生成标准 `CrashReport` 走 exception channel（`59` §6.1）。
- **符号化分级**（接 `12` §7-3）：调试构建内嵌内核符号表；发布构建经 `.msys` 外置符号（与 `61` `.mimg` 度量基/`.msys` 双锚同构）。

### 5.3 与 `32` 度量/attestation 协同

- crashdump 的 `cap_ctx` 与现场经 `VERIFY`=bit38 / `ATTEST`=bit39（`32`）可纳入远程证明链——崩溃时的 capability 上下文成为「崩溃可归因」的密码学证据，供 `65` 审计 replay。

## 6. 自举期早期调试：`.mimg` / early C-asm / 串口（与 `60` 协同）

### 6.1 方案：Stage 1–5 诊断输出阶段演进

`61` §4 定义早期页表「临时→接管」契约与早期串口直写（Stage 1 cap 未起）。本文把「自举期诊断输出」收口为五阶段演进，与 `61` 信任链 4 跳对齐：

```
Stage 1  早期 C/asm 引导：诊断输出经**内核直写 MMIO/端口**（cap 未起，不经能力网关）
         · 仅 banner + 致命错误 PC/寄存器（最低限度可观测，接 61 §4.4 / 12 §4.8）
Stage 2  memblock 临时环境：仍直写，无 inspect/event 通道
Stage 3  kernel_main（Rust 接管）：monitor 自度量 PCR[2]（61 §5.2）；
         故障入口开始能生成结构化 CrashReport，但仍经串口兜底输出
Stage 4  monitor mint 串口 cap（61 §4.4 / 60 §8.2）：串口从「bootstrap 直写」过渡到「受能力约束」
Stage 5  用户态 console 服务接管：内核撤销串口临时副本、仅留 emergency-write 窄 cap（60 E1 / 09 C8）
         · 完整 inspect/event/crashdump 通道此时才可用
```

> **与 `61` 一致**：早期 C/asm 直写**不占信任跳**（`61` §1.2/§1.3），它是被验签映像的执行器；诊断输出的「成熟度」随 Stage 递增，但**不引入新信任源**。

### 6.2 与 `60` 早期串口 right 协同

`60` §8.1 / E1 提出「早期串口 mint `IO` 类（待定）」并建议新增独立 bit（与 `BLOCK_*`/`GPU_*` 同构，不复用 `MANAGE`/`GRANT`）。本文衔接：

- **early 串口 right 与 `DBG_*` 正交**：早期串口的 emergency-write 窄 cap 是 `KERNEL_PRIV` 同构的内核态高危窄权（`29` D-T1 / `61` §4.4），**不属于** `DBG_*` 调试权簇——它服务于「系统已停机时的最后诊断输出」，不是「交互式调试会话」。
- **待决 E1 归口**：早期串口 right 命名（是否新增 `UART_*`/`CONSOLE_*` bit）由 `60` E1 定稿，本文仅确认其**不挤占 `DBG_*` 簇、不复用 `MANAGE`/`GRANT`**（`60` E1 同立场）。

### 6.3 与 QEMU gdbstub 兜底（`12` §4.8）协同

- 自举期（Stage 1–4）内核 bring-up 经 QEMU gdbstub 获完整调试力（含内存写），因调试权位于 VM 边界、不进入 MeuOS capability 模型（`12` §4.8 / §R3-6）。这与 §6.1 的串口兜底共同构成「自举期统一可观测面」（`12` §4.8 联调闭环）。

## 7. 与能力审计（65）/ `DBG_INSPECT` 不变量监控衔接

### 7.1 调试操作可审计（前向引用 `65-安全监控与审计.md`）

`65-安全监控与审计.md`（能力/安全审计专项）承载「capability 派生/撤销/使用的全量审计」。本文把调试面显式接入：

- **每次 `DBG_*` 授权/使用/撤销都记审计事件**：谁（issuer Job）、授予谁（target Job）、哪个 right、哪个子树范围、何时、是否含 `DBG_POKE`（`29` T6 最高危）——供 `65` replay 与事后归因（`12` §4.7 crashdump 的 `cap_ctx` 即崩溃时刻的审计快照）。
- **与 `29` 纵深同构**：调试权滥用（T6 `DBG_POKE` 任意写后门 / T7 崩溃冻结窗口劫持）的挡点 = `65` 审计 + `17` C9-A/C9-B 裁决 + `07` §5 rights 位图，四层纵深（`29` §4）。

### 7.2 `DBG_INSPECT` 不变量监控（与 `29` / `07` / `65` 协同）

**不变量**：「`DBG_INSPECT` 永不默认持有、读范围严格限于被授予的子树、不泄露句柄值/未授权命名空间节点」。

- **监督者持续监控**：meu-supervisor 周期性校验各 Job 的 `DBG_*` handle 集合是否符合 `debug_policy`（`12` R3-5：`deny`/`same-job`/`dev-session`），越界即触发 pledge 越界 `SIGABRT` 式终止（`07` §4.2 fail-closed）。
- **与 `29` D-T1 同构**：`DBG_INSPECT` 虽是低危 right（`12` R3-5 风险级=低），但其「读内核状态」能力一旦被错误授予（如借 `GRANT` 扩散），即违反「无全局可读」不变量——故监控逻辑与 `KERNEL_PRIV`/`DBG_POKE` 同为「高危权永不默认」一致策略的落点（`29` §8.2）。
- **审计闭环**：不变量违例事件进 `65` 审计流，与 `22-测试与验证策略.md` 否定式测试（「调试能力即 capability、越权必失败」）互为白盒/黑盒印证。

## 8. MeuOS 推荐（综合收口）

1. **inspect 层级 = 三层子树（kernel/jobs/services）+ 按目标对象限定粒度**：复用单一 `DBG_INSPECT` right，粒度靠「授权时绑定的 Job/进程 handle」实现，不新增 right；读受 namespace 投影约束，无全局可读（§2 / 接 `12`§4.4 / `47`§2.7 / `06` C3）。
2. **kdebug 会话 = 既有 `DBG_*` right 组合，不新增内核原语**：会话=持 `DBG_ATTACH`（+可选`DBG_POKE`）handle 的状态；内核态经 QEMU gdbstub 兜底（`12`§4.8）；调试权绝不借 `MANAGE`/`GRANT` 扩散（§3 / 接 `12`R3-5 / `29`T6）。
3. **tracing 低开销 + 配额计入被观测 Job 账本**：默认 off、per-CPU 无锁 ring buffer；开销由被观测 Job 承担，防 DoS；schema 自描述、统一 monotonic 时间线（§4 / 接 `39` / `04`§4.4 / `57`）。
4. **crashdump = 结构化 inspect 节点 + `.msys` 校验/加密**：统一 `CrashReport` 经 exception channel 多播（`59`§6.4）；落盘格式含 SHA-256 + 可选加密；内核 panic 必落盘、普通 kill 不落盘（§5 / 接 `12`§4.3/§4.7 / `61` / `32`）。
5. **自举期早期调试 = 串口+`.mimg` 自检兜底，Stage 1–5 阶段演进**：early C-asm 直写不占信任跳；串口 emergency-write 窄 cap 与 `DBG_*` 正交、归 `KERNEL_PRIV` 同构（`60` E1）；完整可观测通道 Stage 5 才可用（§6 / 接 `61`§4 / `60`）。
6. **调试面全量可审计 + `DBG_INSPECT` 不变量监控**：每次 `DBG_*` 授权/使用/撤销记 `65` 审计；监督者持续校验 `debug_policy` 不变量、fail-closed（§7 / 接 `29` / `07` / `65`）。
7. **五架构同源**：inspect/tracing/crashdump/kdebug 的语义五架构一致，差异仅关进 per-arch unwinder 薄后端（`12`§4.5）与早期引导垫片（`61`§7），不侵蚀统一 capability 模型。

## 11. 第九轮自主采纳·闭环 D1

> 修订式追加（第九轮）：本文 §9 D1 待决表行、§3.3 标注已就地升级。本节约为收口记录，不删改 §1–§9 原文。

### 11.1 采纳结论（一句话）

**不新增**调试专属 right 进 bit 48+ 预留区（如 `DBG_SESSION`）。kdebug 会话 = 既有 `DBG_*`（含 `DBG_ATTACH` + 可选 `DBG_POKE`）handle 组合，等价于「会话持有」状态，无需新内核原语。

### 11.2 采纳理由（三条）

1. **百思纪律「不引入新内核原语除非必要」**：`12` 已定稿的 6 个 `DBG_*`（`DBG_INSPECT`/`DBG_TRACE`/`DBG_PROFILE`/`DBG_ATTACH`/`DBG_POKE`/`DBG_CRASHDUMP`）已能完整表达「调试会话」语义——`DBG_ATTACH` 表征会话持有，`DBG_POKE` 单独授予才表征写能力，二者组合即可区分「能调试」vs「不能」，无需第 7 个 right。
2. **与 `12` 定稿体系零冲突**：不新增 bit 48+ right，即无需回写 `12` R3-5 / `07`§4.1 rights 位图二次改判，避免对既成 capability 体系造成扰动；五架构同源不变（`00`§5-6）。
3. **避免新增后门级攻击面**：新增 `DBG_SESSION` 即新增一个可单列建模的高危权面，`29` §1.3 公理 4 明确「调试权=后门级面」；不新增即不扩大 T6/T7（调试权滥用）的纵深入口。

### 11.3 与既定体系的衔接

- **`12` 6 `DBG_*`**：本采纳是 `12` R3-5「默认全 deny、显式授权」铁律的直接延伸；会话门控完全落在该 6 right 之上（§3.1），无外溢。
- **`29` §1.3 公理 4**：不新增 right 即不新设「后门级面」，与公理 4 同构一致；若未来确需细粒度「会话持有 vs 单次操作授权」区分，仍走预留区演进路径（见 §11.4），不破坏当前零冲突态。
- **`00` A12「调试即 capability 默认拒绝」**：`DBG_ATTACH`/`DBG_POKE` 均不随 `MANAGE`/`GRANT` 隐式扩散（`29` T6 / `29` D-T1 同源），本采纳使 A12 立场在预留区问题上彻底闭环——「调试」始终是显式单列、默认拒绝的 capability，不因「会话」概念而被隐式化。

### 11.4 预留区留位不阻塞（注记）

`59`§9.3 已确立 `IRQ_*` / `SCENE_SESSION` 落 bit 48+ 预留区；该预留区与本文 D1 同源段，已为「若未来确需 `DBG_SESSION` 级区分」留好位置。**本采纳不阻塞该演进**——一旦大喵在后续轮次认定需细粒度会话权，可直接在预留区同位段回写，无需重构 0–47 的 `DBG_*` 簇。

## 12. reasoning 决策（2026-08-03）

### 12.1 D1 — kdebug 会话 = 既有 `DBG_*` 组合，不新增 `DBG_SESSION`（同意）

**reasoning 决策（2026-08-03）**：**不新增** bit 48+ 调试专属 right（如 `DBG_SESSION`）。kdebug 会话 = 既有 `DBG_ATTACH`（+ 可选 `DBG_POKE`）handle 的持有状态，等价于"会话持有"，无需新内核原语。

**被否决选项**：
- **新增 `DBG_SESSION` 进 bit 48+**：理由是"区分会话持有 vs 单次操作授权"。

**理由（深·reasoning 百思）**：

1. **"会话"在 capability 体系里就是 capability 本身——`DBG_SESSION` 不增加表达力**。
   - 在 capability 世界里，"会话"不是一个独立抽象——它是**句柄（handle）的持有状态**。持 `DBG_ATTACH` handle 即持有"调试会话"；释放即结束。
   - §3.1 已明确：会话建立 = 持目标进程/Job 的 `DBG_ATTACH` handle；会话结束 = 句柄 close/revoke。
   - **"单次操作授权"在 capability 体系里 = 受约束 mint 派生的受限句柄**（`07 §4.5`），不需要新 right。
   - 新增 `DBG_SESSION` 仅是"语义重命名"——把"持 `DBG_ATTACH`"换个名字叫"持 `DBG_SESSION`"，**不增加任何能力**。

2. **`29 §1.3` 公理 4："调试权=后门级面"——少一个 right 即少一个 T6/T7 入口**。
   - `29 T6`（`DBG_POKE` 任意写后门）与 `29 T7`（崩溃冻结窗口劫持）是调试权滥用的两条主要威胁路径。
   - 每一 bit 调试 right = 一个潜在"调试 root"后门候选。bit 越少、入口越少、纵深越少、T6/T7 攻击面越小。
   - 不新增 `DBG_SESSION` = **直接缩窄 §1.3 公理 4 的"后门级面"**，是百思纪律"不引入新内核原语除非必要"的最强论据。

3. **与 `12` 定稿体系零冲突 = 形式化负担为零**。
   - `12` R3-5 已定稿 6 个 `DBG_*`（`DBG_INSPECT`/`DBG_TRACE`/`DBG_PROFILE`/`DBG_ATTACH`/`DBG_POKE`/`DBG_CRASHDUMP`），并冻结进 `07` rights 位图。
   - 新增 `DBG_SESSION` = 回写 `12` R3-5 + `07 §4.1` rights 位图二次改判 = 触发 `20` 形式化 capability 核心再次扩展。
   - 零新增 = 零形式化扩展 = 不侵蚀 `20` 已有的 I1–I7 证明。

4. **未来真需"会话 vs 单次操作"细粒度，仍可通过受约束 mint 实现，不需新 right**。
   - 若未来确需"细粒度审计/计费"区分"会话持有"与"单次操作授权"，可经 `07 §4.5` 受约束 mint 派生**受限会话句柄**（如"一次性 ATTACH handle，会话结束自动 revoke"）。
   - 这是 capability 体系已有的能力，**不依赖新 right**。
   - 由此：升格路径不需回写 `12`/`07`，零形式化负担。

5. **`bit 48+` 纪律严格控制**。
   - `59 §9.3` 已确立 `IRQ_*`（52–54）/ `SCENE_SESSION` 候选位占 bit 48+ 预留区。
   - 调试权不与设备能力（`IRQ_*`）/场景会话（`SCENE_SESSION`）混用 = 语义独立即拆分的反向应用。
   - 不新增 `DBG_SESSION` = 让 bit 48+ 预留区留给真正需要语义独立的 right，不被调试权"顺手占位"。

**TCB 体量评估**：
- 零新增 right = rights 表零增长、内核 rights 检查点零增长。
- 已有的 `DBG_ATTACH` / `DBG_POKE` 体系 = 调试会话的完整表达力。
- TCB 净增 = 0。

**五架构同源**：
- 调试权模型在五架构一致（`12 §R3-5` 跨架构），不新增 bit = 不引入架构分支。
- 调试会话 = 句柄持有状态 = 架构无关。

**与既有地基协同**：
- **`12` R3-5**：6 `DBG_*` 已能完整表达调试会话（`DBG_ATTACH` 持 = 会话持；`DBG_POKE` 单独授予 = 写能力；二组合 = "能调试 vs 不能"），无需第 7 个 right。
- **`29 §1.3` 公理 4**：不新增 right = 不新设"后门级面"，与公理 4 同构。
- **`00` A12 调试即 capability 默认拒绝**：`DBG_ATTACH`/`DBG_POKE` 均不随 `MANAGE`/`GRANT` 隐式扩散，不新增 `DBG_SESSION` 使 A12 立场在预留区问题上彻底闭环。
- **`59 §9.3` 预留区纪律**：`bit 48+` 已为 `IRQ_*` / `SCENE_SESSION` 留位，本采纳不抢占同位段。

**升格路径（明文）**：
- 若未来出现"细粒度会话权"真实需求（必须经 §3.1 的 `DBG_ATTACH` + 受约束 mint 派生无法满足），**方可启动 §11.4 预留区回写路径**——`DBG_SESSION` 进 bit 48+ 候选位（建议 bit 56+），同步 `12`/`07`/`29` 三处二次改判，并触发 `20` 形式化扩展。
- 但本轮不启动——零证据显示 §3.1 的 `DBG_ATTACH` + 受约束 mint 派生表达力不足。

**与指挥官原占位的关系**：**同意**。理由（1）（2）（3）（5）由指挥官 §11.2 三条已覆盖；本 reasoning 决策额外补强了「受约束 mint 已能实现细粒度」（理由 4）与「升格路径明文化」（升格路径段）。
