# MeuOS 内核语言策略（Rust vs C）设计 / 规划

> 子领域：内核语言划分方案（Rust 与 C 的边界、共存机制、安全审计）。
> 团队：`kernel-plan`；调研员：k-lang。
> 配套文档：`01-内核架构选型.md`（混合内核）、`07-安全模型.md`（capability / 最小 TCB）。
> 本文档为「设计 / 规划」，结论在第 4 节，取舍依据见第 2、3 节。

---

## 1. 概述与目标

### 1.1 背景

MeuOS 内核当前处于「规划中」。其总体定位（来自 IMA 知识库「MeuOS / 01-总体架构」）为：

- **外部兼容 Linux ABI**：经兼容层（`mkit`）对接，既有的 Linux 生态二进制可直接运行；
- **内部自主设计**：Linux 是参照物，不是目标；
- **三大内在统一的设计方向**：① 统一文件系统层；② spawn 模型进程管理（内建监督、资源账本 Day 1）；③ **capability-based 安全（Day 1 唯一模型、内核关键组件用 Rust、最小 TCB）**。

其中第三方向直接对语言策略提出了硬约束：**内核关键组件必须用 Rust 实现，且安全相关代码必须纳入最小 TCB**。本文档在此约束下，给出 Rust 与 C 在内核镜像中的具体划分。

### 1.2 目标

1. 给出一份可落地的「哪些组件用 Rust、哪些用 C」的划分建议；
2. 设计 FFI 边界、unsafe 范围控制与审计策略；
3. 明确内核态 `panic` / OOM 处理模型；
4. 说明 `no_std` / `alloc` 约束，以及 Rust 与 C 如何共存于同一内核镜像（链接、调用约定、panic 边界）；
5. 阐明该划分与三大方向（尤其最小 TCB / 安全）的关系。

### 1.3 范围之外

- 不决定具体 `syscall` 编号与语义（见 `08-Linux兼容层.md`）；
- 不展开调度算法与内存布局本身（见 `03-内存管理.md`、`04-进程与调度.md`）；
- 不规定用户态运行时（libc / Rust std 用户态）的实现分工。

## 2. 设计约束与上下文

### 2.1 技术基线约束

| 约束项 | 现状 / 要求 | 对语言策略的影响 |
|---|---|---|
| 内核形态 | 混合内核（见 `01-内核架构选型.md`），非纯微内核 | Rust 既用于内核态关键组件，也可用于用户态监督服务；与 Redox 纯微内核不同 |
| 混合语言 | Rust + C 混合 | 必须设计明确的 FFI 边界与调用约定统一的 ABI |
| 安全方向 | capability Day 1、关键组件 Rust、最小 TCB | 安全关键路径（capability 判定、syscall 路由、IPC）优先 Rust，并计入 TCB |
| 兼容性 | 外部兼容 Linux ABI | Linux 兼容层（mkit）必须与 Linux UAPI 头结构逐字段对齐，是 C 的强理由 |
| 工具链 | **Kit 层已完成**：`mcc`（C11 编译器，cproc+QBE）+ `meuos-libc` + 多架构后端 | **关键张力**：mcc 自举走的是 C 路径，而 Rust（rustc）当前依赖 LLVM 后端，两条工具链不同源 |

### 2.2 关键张力：Rust 工具链与 mcc 自举路径不重合

MeuOS 的自举验证路线（README）是「`mcc` + `meuos-libc` 在自研内核上自举」。这条链路本身是 C 的：

- `mcc` 生成 C 代码的目标文件（x86_64 / aarch64 / riscv64 / loongarch64 / arm / i386 均已有后端或运行时验证）；
- `meuos-libc` 是 C 库，提供 crt1 / 原子 / setjmp / tls / syscall gate。

而主流 Rust（rustc）的工具链是 **rustc 前端 + LLVM 后端**。`mcc` 基于 QBE，并不理解与生成 LLVM IR，**二者在 2026 年的现实下无法同源**：

- `gccrs`（GCC 前端的 Rust）截至 2025 年仍主要面向 Rust 1.49 语义，距内核可用（需要 `core`/`alloc`、稳定 `extern "C"` ABI、panic 处理、const 泛型等大量现代特性）仍有显著差距（[rust-gcc.github.io](https://rust-gcc.github.io/)，[Phoronix 2025-09](https://www.phoronix.com/news/gccrs-August-2025)）；
- `rustc_codegen_gcc`（libgccjit AOT）能在 GCC 上复用 rustc 前端，但仍需 rustc 本体，且对裸机/内核场景的成熟度不足以作为 MeuOS 近期的唯一后端。

**结论（约束 C1）**：内核中凡是引入 Rust 的部分，在可预见的周期内必须接受「**双工具链**」现实——Rust 走 rustc+LLVM，C 走 mcc+QBE，最终由系统链接器（或内核自定义链接脚本）合并为一个内核镜像。MeuOS 的「自举」指用户态与 libc 在自研内核上跑通，并不要求内核自身由 mcc 单独编译；因此该张力是可接受的，但应在 5.3 列为开放议题持续跟踪。

### 2.3 Rust 裸机平台支持现状

rustc 对 MeuOS 目标架构的裸机（`*-unknown-none*`）支持如下（[rustc platform-support](https://doc.rust-lang.org/nightly/rustc/platform-support.html)）：

| MeuOS 目标 | Rust 裸机 target | Tier | 备注 |
|---|---|---|---|
| x86_64 | `x86_64-unknown-none` | Tier 2 (no host tools) | 仅 `no_std` |
| aarch64 | `aarch64-unknown-none` | Tier 2 | 仅 `no_std` |
| riscv64 | `riscv64gc-unknown-none-elf` | Tier 2 | 仅 `no_std` |
| loongarch64 | `loongarch64-unknown-none` | Tier 2 | LP64D ABI，仅 `no_std` |
| arm | `armv7a-none-eabi` | Tier 2 | 仅 `no_std` |
| i386 | `i686-unknown-none` / `i386-unknown-none` | **无稳定裸机 target** | 裸机 32 位 x86 在 rustc 官方表中缺位 |

**结论（约束 C2）**：i386 是 `mcc` 的「完整代码生成 target」，但 Rust 在 i386 裸机侧缺乏稳定支持。MeuOS 应在 64 位目标（x86_64 / aarch64 / riscv64 / loongarch64 / arm）上启用 Rust，i386 维持纯 C 实现，待 Rust 裸机 i386 target 成熟后再评估迁移。这与「i386 经 `CONFIG_IA32_EMULATION` 直接执行静态 32 位 ELF」的兼容路径互不冲突（兼容层为 C，与内核态 Rust 无关）。

## 3. 业界方案对比

### 3.1 Rust for Linux（RFL）

- **定位**：在既有宏（单块）内核中增量引入 Rust，作为第二语言（[kernel.org Rust 文档](https://www.kernel.org/doc/html/v6.13/rust/index.html)）。
- **`no_std`**：内核 Rust 仅链接 `core`，不链接 `std`，用 `#![no_std]`（[general-information](https://www.kernel.org/doc/html/v6.13/rust/general-information.html)）。
- **abstractions vs bindings**：把对 C 侧内核 API 的直接访问全部封装进经过严格评审的「abstractions」层；下层是 `bindgen` 自动生成的「bindings」，加上手写的 `rust/helpers/` 包装（同上）。用户（驱动 / 文件系统）**禁止直接使用 C bindings**，只能通过 safe 抽象访问。
- **分配器**：内核提供 `Kmalloc` / `Vmalloc` / `KVmalloc` 等分配器，`Box`/`Vec` 等通过 `KBox` 携带 `GFP` 标志，分配失败走 **fallible** 路径（`try_new` 返回 `Result`），而非隐式 panic（[kernel kbox.rs](https://github.com/torvalds/linux/blob/master/rust/kernel/alloc/kbox.rs)，[LWN 2024](https://lwn.net/Articles/966701/)）。
- **`panic` 模型**：内核 Rust 采用 `panic=abort`，不展开（unwind）调用栈，以匹配内核不可恢复语义与减小体积；分配失败在稳定版后由 `alloc_error_handler` 统一兜底（[alloc::handle_alloc_error](https://doc.rust-lang.org/alloc/alloc/fn.handle_alloc_error.html)）。
- **价值**：把内存安全类漏洞的修复前移到了编译期，是其核心动机（[Prossimo 2025 更新](https://www.memorysafety.org/blog/linux-kernel-2025-update/)）。
- **坑**： abstractions 覆盖不全、跨语言构建复杂（bindgen 依赖 libclang）、维护者文化摩擦、Rust 版本与内核长期支持分支的绑定。

### 3.2 Redox OS

- **定位**：用 Rust 从零编写、运行在用户态的**微内核**操作系统（[Redox book](https://doc.redox-os.org/book/microkernels.html)）。
- **内核规模**：Redox 内核 **少于 40,000 行 Rust**；对比 Minix 约 6,000 行 C（[Redox microkernels](https://doc.redox-os.org/book/microkernels.html)）。内核只保留 IPC、进程隔离、线程管理、资源管理等最小抽象。
- **隔离模型**：驱动 / 文件系统 / 窗口系统等全部运行在**独立地址空间的用户态**，组件 panic 不会拖垮内核；「组件 panic」远多于「kernel panic」，且日志可独立保存，便于真机调试。
- **C 的角色**：Redux 通过 `relibc`（C 库，部分用 Rust 实现）提供 POSIX 兼容；纯内核侧几乎不用 C。
- **与 MeuOS 的差异**：MeuOS 是**混合内核**而非纯微内核，且必须兼容 Linux ABI（Redox 仅 POSIX-ish）。Redox 的价值在于证明「用 Rust 写内核可把内核 C 代码量压到极低、且天然获得地址空间隔离带来的稳定性」，但其微内核 + 全用户态驱动模型不能直接套用到 MeuOS。

### 3.3 Theseus OS

- **定位**：Rice / Yale 的研究型 OS，提出 **intralingual design**（语言内化设计）——用 Rust 的语言级机制（所有权、类型、trait、模块）直接表达 OS 语义，把原本靠运行时 / 内核机制维护的不变量交由编译器强制执行（[OSDI 2020 论文](https://www.usenix.org/conference/osdi20/presentation/boos)）。
- **核心思想**：① 大量「cell / crate」式小单元，单元间不互相持有对方状态，状态边界在编译期由 Rust 类型系统强制；② 该结构 + 语言级隔离使核心组件具备 **live evolution（热更新）与 fault recovery（故障恢复）** 能力，且超越既有方案。
- **对 MeuOS 的启发**：`spawn` 模型 + 资源账本 Day 1 与 Theseus 的「不持有对方状态、状态边界编译期可验证」高度契合；可借鉴其「用 Rust 类型系统把资源生命周期变成编译期不变量」的做法，特别是 capability 与资源账本。

### 3.4 Hubris（Oxide Computer）

- **定位**：面向深度嵌入式、具备可靠性要求的**内存保护、消息传递微内核**（[oxidecomputer/hubris](https://github.com/oxidecomputer/hubris)）。
- **静态任务**：任务在编译期通过 `app.toml` 静态声明，固定 `flash` / `ram` 配额，无运行期动态创建任务。
- **无动态分配倾向**：资源配额写死、镜像编译期定型，符合嵌入式可靠性导向（默认不依赖运行期堆）。
- **调试与恢复**：与 `Humility` 调试器紧耦合；存在 `jefe` 监管任务，负责监测系统组件健康并在故障时重建（重启）任务。
- **对 MeuOS 的启发**：`jefe` 式 supervisor 重启语义与 MeuOS 的 spawn 监督模型一致——用户态 Rust 服务 panic 后可由 supervisor 重启，而非整系统崩溃。该模式是「Rust panic 边界」在用户态的成熟实践。

### 3.5 取舍对照表

| 维度 | Rust for Linux | Redox | Theseus | Hubris | 对 MeuOS 的启示 |
|---|---|---|---|---|---|
| 内核形态 | 宏内核增量 | 微内核 | 单地址空间语言级隔离 | 嵌入式微内核 | 混合内核 → 取 RFL 的「abstractions 封装 C 边界」+ Theseus 的「类型系统强制状态边界」 |
| C 的角色 | 存量主体 + bindings | 极少（relibc） | 极少（仅 asm 边界） | 内核侧基本无 C | C 用于 asm 边界 + Linux 兼容层（ABI 保真），Rust 用于安全关键组件 |
| unsafe 控制 | abstractions 层隔离 + 评审 | 内核小、unsafe 少 | 用 safe Rust 表达 OS 语义 | 静态、小、可审计 | 设「abstractions 层」+ unsafe 计数审计 + lint |
| 分配失败 | `KBox` + GFP，fallible | 用户态可堆 | 自定义 alloc | 基本不用堆 | 内核态用 fallible alloc，OOM 走 abort/panic 边界 |
| panic 模型 | `panic=abort` | 组件隔离 | fault recovery | supervisor 重启 | 内核核心 abort；用户态 Rust 服务由 supervisor 重启 |
| 自举/工具链 | 依赖 LLVM | 依赖 rustc | 依赖 rustc | 依赖 rustc | MeuOS 双工具链（Rust=LLVM，C=mcc），见 2.2 |
| 最小 TCB | 仅安全关键 Rust 入 TCB | 内核整体即 TCB | 小 kernel cell | 小内核 + 监管 | Rust 关键组件入 TCB，C 兼容层排除出 TCB |

## 4. MeuOS 选型建议

### 4.1 总体原则

1. **安全关键路径用 Rust，且计入最小 TCB**；性能 / 兼容性 / 底层 asm 边界用 C（mcc）。
2. **C 仅出现在两条边界**：① 架构相关 asm 与早期启动；② Linux ABI 兼容层（保真需要）。
3. **所有 C↔Rust 交互必须经「abstractions 层」**，禁止 Rust 侧直接 `#[link]` 到 C 内部符号（仿 RFL）。
4. **i386 纯 C**；64 位目标引入 Rust（受 2.3 约束 C2）。

### 4.2 组件划分矩阵

| 组件 | 语言 | 是否计入 TCB | 理由 |
|---|---|---|---|
| 早期启动 / 体系结构入口（boot、异常向量、上下文切换 asm） | **C (mcc)** | 否（极小、固定） | 需用内联 / 裸 asm，Rust 裸机 i386 缺位；此层极薄、可形式化审计 |
| 中断 / 异常底层分发（到 Rust 处理器的桥） | **C→Rust 封装** | 否 | asm 入口用 C，立即上抛给 Rust 中断管理器 |
| **syscall 分发核心 / 路由表** | **Rust** | **是** | 直接决定「谁能调什么」，是能力边界，必须编译期安全 |
| **capability 判定与传播** | **Rust** | **是** | 安全模型 Day 1 唯一模型，所有资源访问的门；用 Rust 类型把 capability 不可伪造性变成不变量（借鉴 Theseus） |
| **IPC 端点（同步端点 seL4/Zircon 风格）** | **Rust** | **是** | 跨进程消息的边界与权限校验，安全关键 |
| **调度器 / 资源账本** | **Rust** | **是** | spawn 模型 Day 1 内建监督与资源账本，状态边界编译期可验证 |
| **统一文件系统抽象层（VFS/checksum/compress/encrypt 接口）** | **Rust** | **是（接口）/ 否（具体 fs 驱动）** | 抽象与校验链是安全关键；具体存储后端可 C |
| **spawn / supervisor 模型（含 jefe 式监管）** | **Rust** | **是** | 监督重启语义（借鉴 Hubris）须可靠、可审计 |
| 内存管理核心（页分配、页表游走） | **Rust（逻辑）+ C（页表刷写 asm）** | 逻辑部分**是** | 页表类型化封装进 Rust，底层 TLB/刷写走 C asm |
| 设备驱动（性能敏感、寄存器搬运） | **C (mcc) 为主** | 否（尽量隔离） | 寄存器级操作多 unsafe；优先用户态 / 隔离，避免进 TCB |
| 具体文件系统后端（磁盘布局、压缩 / 加密原语调用） | **C (mcc)** 或 Rust 均可 | 否 | 经 VFS 抽象接入，不在 TCB |
| **Linux ABI 兼容层（mkit）** | **C (mcc)** | **否（兼容面，受控隔离）** | 必须与 Linux UAPI 头逐字段对齐，C 保真度最高；以 fuzz / sandbox 控制风险，刻意排除出 TCB |
| 内核内部调试 / 可观测性（与 `12-调试与可观测性.md` 协同） | **Rust（结构）+ C（硬件读取）** | 否 | — |

> 说明：将 mkit（Linux 兼容层）归为 C 且**排除出 TCB**，并非因为它不重要，而恰恰是为了最小 TCB——它是一块「为兼容而存在的、可被隔离 / 模糊测试 / 沙箱化」的表面，不应与安全关键判定同处信任边界内。这与总体方向「内核关键组件用 Rust」并不冲突：mkit 不是「关键安全组件」，而是「兼容性适配组件」。

### 4.3 FFI 边界设计

1. **统一 ABI**：Rust 侧一律 `extern "C"` 暴露给 C；C 侧调用 Rust 也走 `extern "C"`。调用约定以目标平台 SysV / AAPCS / LP64D 为准（mcc 各后端已对齐，见 `mcc/TARGETS.md`）。
2. **符号导出 / 导入**：
   - Rust 提供给 C 的函数用 `#[no_mangle] pub extern "C" fn`；
   - C 提供给 Rust 的符号由 `bindgen` 生成 `bindings`（仅声明，不含实现），或手写薄 `helpers`（仿 RFL 的 `rust/helpers/`）。
3. **abstractions 层（关键）**：所有对 C 内部数据结构 / 函数的访问，封装进一个经评审的 Rust 抽象层；Rust 业务代码（capability、IPC、调度）**不得**直接持有裸 C 指针。对应 RFL 的「bindings 之下、abstractions 之上」结构。
4. **数据交换**：跨边界传递优先用 `#[repr(C)]` 结构体与句柄（capability 句柄为整数 / 不透明指针），避免跨边界传递 Rust 所有权对象（如 `Box`）。
5. **链接共存**：Rust 编译为 `.o` / `.rlib`，C 由 `mcc` 编译为 `.o`，二者经统一链接脚本（内核自定义 linker script）合并进单一内核镜像；Rust `panic_handler` / `alloc_error_handler` 最终落到内核统一故障入口（见 4.5）。

### 4.4 unsafe 范围控制与审计策略

1. **默认 safe**：Rust 业务代码禁止 `unsafe`；`unsafe` 仅出现在 abstractions 层与 asm 边界。
2. **编译期闸门**：
   - `#![forbid(unsafe_op_in_unsafe_fn)]`（要求 unsafe fn 体内显式 `unsafe {}`）；
   - `#![deny(clippy::all)]`（CI 开启 `CLIPPIES=1`，仿 RFL 的 `CLIPPY=1`；注意 clippy 不改变代码生成，仅评审）；
   - `#![deny(warnings)]` 于内核构建。
3. **审计策略**：
   - 维护 `unsafe` 块清单（位置 + 安全契约 + 评审人），纳入代码评审门禁；
   - 统计每个子系统的 `unsafe` 行数 / 块数，作为 TCB 规模指标；TCB 内 `unsafe` 必须逐块双人评审；
   - C 侧（mcc）的兼容层虽排除出 TCB，但仍需 `-Wall -Wextra` 与静态分析 / fuzz 作为补偿控制。
4. **能力不变量**：capability 句柄的「不可伪造 / 不可复制逃逸」由 Rust 类型（非 `Copy`、私有构造、借用检查）强制，使大部分权限校验在编译期成立，运行时仅做存在性检查。

### 4.5 内核态 panic / OOM 处理模型

| 场景 | 行为 |
|---|---|
| **内核核心 Rust 组件 panic**（capability / IPC / 调度 / VFS 抽象） | 映射为 **kernel panic**，按 `panic=abort` 终止并进入内核故障入口（仿 RFL）。因这些组件在 TCB 内，不可恢复即整体停机，避免内存破坏 |
| **内核态 OOM** | 分配失败走 **fallible** 路径（`KBox` 式 + GFP 标志），返回 `Err` 由调用方处理；若确属不可恢复分配，由 `alloc_error_handler` 落到内核故障入口 |
| **用户态 Rust 服务 panic**（spawn 出的监督服务） | 由 **supervisor（jefe 式）重启**该任务（借鉴 Hubris），不拖垮内核（仿 Redox「组件 panic ≠ kernel panic」） |
| **用户态 C 进程崩溃** | 经信号 / spawn 模型由 supervisor 处理（见 `04-进程与调度.md`、`07-安全模型.md`） |

要点：
- 内核 Rust 统一 `panic=abort`，**不展开调用栈**（减小体积、匹配内核不可恢复语义，仿 RFL）。
- `alloc` 以 fallible 为主；`handle_alloc_error` 兜底路径接入内核故障入口（[alloc::handle_alloc_error](https://doc.rust-lang.org/alloc/alloc/fn.handle_alloc_error.html)）。
- panic 边界是「Rust panic_handler → 内核统一故障入口」单点，无论 Rust 还是 C 触发的致命错误都汇聚于此，保证日志 / 重启语义一致。

### 4.6 `no_std` / `alloc` 约束

- 内核 Rust **仅链接 `core`**（必要时 `alloc`），`#![no_std]`，不依赖 `std`（仿 RFL general-information）。
- 提供内核自有分配器（实现 `Allocator` trait 或等价 `GlobalAlloc`），背后接 MeuOS 页分配器；所有内核分配须带 `GFP` 类标志与 fallible 语义。
- 禁用需 `std` 的设施（线程、文件系统、网络、环境变量）；内核同步原语（自旋锁 / 互斥）自实现或复用 C 侧（经 abstractions）。
- 栈上对象优先；长期 / 大对象才走堆，且必须处理 `Err`。

### 4.7 与三大方向的关系

| 方向 | 语言策略如何支撑 |
|---|---|
| ① 统一文件系统层 | VFS / 校验和 / 压缩 / 加密**接口**用 Rust 入 TCB，保证数据完整性链的类型安全；具体存储后端可用 C，经抽象隔离 |
| ② spawn 模型进程管理 | 调度器、资源账本、supervisor 均 Rust 入 TCB，使「内建监督 + 资源账本 Day 1」的状态边界编译期可验证（借鉴 Theseus）；用户态 Rust 服务 panic 由 supervisor 重启（借鉴 Hubris） |
| ③ capability / 最小 TCB | capability 判定 / IPC 端点 / syscall 路由用 Rust，把权限不变量编译期化；C 仅保留 asm 边界与 Linux 兼容层，且兼容层刻意排除出 TCB，从而真的「最小」化了可信代码量 |

## 5. 开放议题

1. **双工具链的长期可行性（约束 C1）**：内核 Rust 依赖 rustc+LLVM，C 依赖 mcc+QBE。远期是否评估 `rustc_codegen_gcc` / `gccrs` 以与 mcc（GCC/QBE 系）靠拢？当前判定：近期不阻塞，但列为跟踪项。
2. **i386 与 Rust（约束 C2）**：i386 是 mcc 完整 target，但 Rust 裸机 i386 缺稳定支持。是否对 i386 永久纯 C，或待 Rust target 成熟后仅迁移 TCB 组件？
3. **mkit（Linux 兼容层）的安全补偿**：将兼容层归 C 且排除出 TCB，需要明确的隔离 / fuzz / sandbox 方案（与 `08-Linux兼容层.md`、`07-安全模型.md` 协同），否则「排除出 TCB」仅是名义上的。
4. **capability 与 Rust 类型的映射粒度**：哪些 capability 不变量可纯编译期强制、哪些必须运行时校验，需在 `07-安全模型.md` 定稿后回填本策略。
5. **Rust 版本与内核长期支持**：RFL 的经验表明 Rust 版本绑定是维护负担；MeuOS 需固定一个 Rust 工具链版本并明确升级流程。
6. **TCB 度量与回归**：`unsafe` 行数 / 块数的 CI 门禁阈值、TCB 规模上限，需在原型阶段实测后定量化。

### A. C5 回写（关键）：内核 `panic=abort` 与用户态 `unwind` 并存

**采纳结论**：C5 采用 `16` §1.3 推荐方案 C（按故障域区分），采纳为**已采纳裁决**。内核态 TCB 内组件统一 `panic=abort` + panic 现场符号化；**保留用户态 Rust 服务（受 meu-supervisor 管理、可重启）启用 `panic=unwind` 产出完整 backtrace**；二者归一为统一 `StackFrame`；mcc/QBE 侧 C 代码以帧指针（frame-pointer）链遍历作跨架构兜底，DWARF `.eh_frame` 作 richer 展开路径。区分依据是**故障域（内核地址空间 vs 可重启用户态故障域）**，而非语言。

**对 §4.5 的具体修订（可直接采纳段落，替换/补充 §4.5「要点」第 1 条并新增用户态口子）**：

> **§4.5 要点（第三轮回写修订版）**
> - 内核态（TCB 内 Rust/C 组件：capability 监视器 / IPC 端点 / 调度核心 / VFS 抽象 / 内核态快速驱动生死相关路径）统一 `panic=abort`，不展开调用栈——内核 panic 即停机事件，全栈 unwind 收益低且增大 TCB/镜像体积；内核统一故障入口保存完整寄存器现场 + 末几返回地址帧（PC/LR/FP 链），配合内核符号表做 panic 现场符号化（见 `12-调试与可观测性.md` §4.5）。
> - 用户态 Rust 服务（受 meu-supervisor 管理、崩溃可重启的 spawn 服务）**不使用 `panic=abort`，启用 `panic=unwind`**，以产出完整 backtrace 供 supervisor 经 exception channel 分析并重启（对齐 Hubris `jefe` / Redox「组件 panic ≠ kernel panic」）。用户态 C 进程崩溃经 DWARF / 帧指针 unwind 表展开。
> - 二者归一化为统一 `StackFrame{ pc, symbol?, module, offset }` 格式，`CrashReport.stack_frames` 跨三类崩溃同构（内核现场帧 + 用户态展开帧无感）。
> - 区分依据是「是否在可重启的用户态故障域内」，而非「是否用 Rust」：内核态即便用 Rust 也 abort；用户态即便用 C 也走 unwind（在工具链支持下）。
> - **unwinder 策略（mcc/QBE 侧兜底）**：跨架构通用兜底为**帧指针链遍历**（`-fno-omit-frame-pointer` 保留 FP/LR，统一 5 架构语义）；DWARF `.eh_frame` 作 richer 展开路径（rustc 已吐，mcc 后续增强）。内核 abort 现场只需 FP-chain 取末几帧；用户态完整 backtrace 优先 DWARF。统一 in-kernel unwinder 抽象见 `12` §4.5。
