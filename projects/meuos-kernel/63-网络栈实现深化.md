## 1. 核心结论（一句话）

> **Day 1 的网络栈实现是「协议栈全在用户态 netstack 进程 + 内核只给四类机制」的落地契约：BSD socket 经 mkit 兼容层映射为内核 mint 的 socket 句柄（带 `NET_*` rights、不回内核）；TCP/UDP 状态机全在 netstack、零拷贝经 device VMO + 能力传递；多队列/RSS/vlan/多播按 Day 1 最小边界收口；socket 就绪与收包唤醒统一经 `05` EventPort，RTO/重传超时统一经 `57` timer（netstack 自持 timer 句柄），网卡收包中断经 `59` `Cap(IRQ n)` 经 EventPort 唤醒 NIC 驱动再透传 netstack。**

## 2. 地基与约束（非缝合怪的边界）

### 2.1 已决地基（直接继承，不重判）

| 地基项 | 来源 | 对本文的硬约束 |
|--------|------|----------------|
| capability Day 1 唯一权限模型 | `07` §1 / §4.1 | socket 句柄 = capability；所有网络操作经 rights 位运算，无 uid/root 兜底 |
| Job 资源账本 | `04` §4.4 | netstack / NIC 驱动作为用户态服务归入某 Job，受 CPU/内存/句柄/IO 配额约束；`timer_wakeups` 预算可后续约束（`57` §4.3） |
| 重服务出核（网络栈用户态） | `00` A6 / `25` C15 | 协议逻辑（TCP/UDP/IP/ICMP/ARP/NDP/DHCP/DNS）、NIC 驱动、防火墙全在用户态；**内核零协议语义** |
| 结构化取消 | `04` §4.6 / `00` A9 | netstack 崩溃 → 经 exception channel 上行监督者（`04` §4.5），已建 socket 句柄随 Job 取消/重绑 |
| `NET_*` rights 冻结 | `07` §4.1 / `38` §3 / `45` §3 | bit 28–31 + 39 已定，本文**不新增**网络 right；offload 归 `10` 设备能力域（`25` C17 §4） |

### 2.2 内核暴露的最小网络面（复述 C17，落地视角）

与 `25` C17 §2 严格一致，本文从「实现深化」角度复述内核四机制的实现契约：

1. **NIC 设备能力**（`10` §2.4）：`Cap(MMIO range)`+`Cap(IRQ n)`+`Cap(DMA window)`，由 capability 监视器在 `09` Stage 4 mint、devmgr 经受约束 mint 下发 NIC 驱动（`10` C8）。
2. **VMO/VMAR + pager 数据通路**（`03`）：报文缓冲区 = device VMO（不可写 right，`10` 第三轮回写 B），在 NIC 驱动 ↔ netstack ↔ 应用间零拷贝传递。
3. **socket 句柄 = capability**（`07` / `25` §4.1）：由 netstack 作 mint 委托人、内核按受约束 mint 收窄 `NET_*` rights（`07` §4.5）。
4. **EventPort 就绪通知**（`05`）：`EVFILT_READ`/`WRITE`/`CHAN` filter，socket 就绪与收包唤醒统一走此。

**内核明确不实现**（边界红线，`25` C17 §2）：无 IP/TCP/UDP 路由/防火墙/NAT/桥/隧道；无全局混杂 `AF_PACKET`（`NET_RAW` 限定单 socket 句柄，`25` C17 §3）；无内核 netfilter/eBPF 钩子 ABI。

## 3. socket API 兼容层（mkit）映射：BSD socket → 用户态 netstack + capability

### 3.1 映射总览（不回内核）

> **方案**：`08` §2.2 类别一（mkit 子集 1:1 direct-mapped）——`socket/bind/connect/listen/accept/send/recv/sendto/recvfrom/setsockopt/getsockopt/shutdown/close` 经兼容层**翻译为内部 socket capability 操作**，全部请求最终落到用户态 netstack，内核不参与协议语义。

映射链路（`AF_INET*` 路径）：

```
应用 (mkit/glibc 二进制)
   │ BSD socket 调用（08 兼容层翻译）
   ▼
mkit 兼容层（薄蹦床，用户态）
   │ 经 05 Channel 向 netstack 服务发请求
   ▼
netstack 服务（用户态）
   │ 请求内核 mint 一个 socket 句柄（作为 mint 委托人，受约束 mint）
   ▼
内核（仅）mint socket 句柄 + 按 07 §4.5 收窄 NET_* rights ──→ 句柄回传应用
```

- **`socket()`**：兼容层经 `05` Channel 向 netstack 请求；netstack 作为 mint 委托人请求内核 `mint` 一个带 `NET_*` rights 子集的 socket 句柄（`25` §4.1）。句柄默认随对象 rights（如 `NET_CONNECT`/`NET_LISTEN` 随对象、`NET_BIND`/`NET_RAW`/`NET_MANAGE` deny，`07` §4.1）。
- **`bind()`/`connect()`/`listen()`**：权限判定**只在此时做一次**（rights 位运算 `NET_CONNECT`/`NET_BIND`/`NET_LISTEN` + 每进程 `/net` 命名空间视图约束，`25` §4.2）；运行期 `send/recv` 只做 rights 位运算 + EventPort 通知，**不重做策略**（呼应 `19` §1.1 原则 2、AP-3 热路径不重策略）。
- **`accept()`**：netstack 派生新 socket 句柄（受约束 mint，子类化 client 连接），rights 由「accept 监听句柄 ∩ 客户端连接策略下限」交集约束（`07` §4.5 防 confused deputy）。
- **`send/sendto`/`recv/recvfrom`**：经 VMO 零拷贝 + EventPort 就绪（`25` §5.4），见 §4.3。
- **`setsockopt/getsockopt`**：socket 句柄附属属性（netstack 连接表项），非内核全局（`25` §5.4）：
  - `SO_REUSEADDR`/`SO_REUSEPORT` → netstack 协议配置；
  - `SO_KEEPALIVE`/`SO_LINGER`/`SO_RCVBUF`/`SO_SNDBUF`/`SO_TIMESTAMP` → netstack 连接表项属性；
  - `SO_BROADCAST` → 需 `NET_BIND` 或派生 right；
  - `IP_TRANSPARENT`/`SO_MARK`/`PACKET_ADD_MEMBERSHIP` 等深度耦合内核 → **ENOSYS**（`08` §7 显式不兼容，不造假兼容）。
- **`shutdown/close`**：句柄 `close`/`revoke`（`07` §4.5），连接权回收。
- **`select/poll/epoll/kqueue`**：→ EventPort `EVFILT_READ`/`WRITE`/`CHAN`（`05` §4.6 已把 epoll 映射；`kqueue` 本即 EventPort 模型），网络 socket 直接复用，**零额外机制**。

### 3.2 权限收窄时机（推荐立场）

**推荐**：`NET_*` rights 在 `socket()`/`bind()`/`connect()` 发生时刻由内核一次性收窄到句柄；运行期热路径仅做 `rights & MASK` 位测试 + EventPort 投递。这把「µs 级策略判定」从热路径剥离，对齐 `25` §4.1 与 `07` §4.5 受约束 mint。

**权衡**：一次性收窄意味着「运行期提权」（如先无 `NET_BIND` 再请求绑特权端口）不可行——必须重新 `socket()` 或由持有 `GRANT` 的对端显式重发受限句柄（`07` §4.5 无隐式提升）。这与 capability 模型「无隐式提升」同源，非缺陷。

### 3.3 netlink 与伪文件系统（与 08 协同，不造假）

- `netlink`（路由/邻接/防火墙查询）：`08` §7 已列全量显式不兼容。本文建议经 `/net` 命名空间视图（`06`） + netstack 服务 `05` Channel 提供等价能力查询接口（路由表/邻居表/防火墙规则读），**不伪造 netlink 全量语义**（呼应 `25` §5.4 D7）。
- `/proc/net`、`/sys/class/net`：`06` 向统一命名空间生成 Linux 视图，netstack 提供底层数据（`25` §5.2）。

### 3.4 与 C15 严格一致性的校验点

- 内核**不**出现任何 `sys_socket`/`sys_connect` 式协议语义入口；所有协议判定在 netstack。
- 兼容层是「用户态蹦床」，不是「内核 ABI 后门」（`08` §5.6 边界）。
- socket 句柄与 `05` IPC 端点同为 capability，但需 type tag 区分（见 N2）。

## 4. TCP/UDP 状态机位置与零拷贝路径

### 4.1 TCP/UDP 状态机全在用户态 netstack 进程

> **方案**：TCP（SYN/SYN-ACK/ESTABLISHED/FIN_WAIT/TIME_WAIT/CLOSE_WAIT…）、UDP（无连接表项、仅端点绑定）、ICMP、ARP/NDP、DHCP、DNS resolver 的全部状态机在 netstack 用户态进程内（`25` §3.2）。**内核不持有任何连接状态**。

- netstack 维护每接口状态、路由表、邻居表、连接表 —— 这些是 netstack **内部状态**，不暴露为全局内核表（`25` §3.2）。
- `TIME_WAIT`/`FIN_WAIT` 计时由 netstack 用 `57` timer 句柄驱动（§6.3），不占内核连接槽。
- **内核最小收发**的准确含义：内核**不实现**收发包逻辑；「收发」的最小机制 = NIC 驱动经 device capability 编程 ring + 报文经 VMO 流动 + EventPort 通知。即「内核只搬运 VMO 报文 + 投通知」，协议解析归 netstack（`25` C17 §2 红线）。

### 4.2 内核最小收发 vs netstack 状态机（边界澄清）

| 环节 | 用户态 netstack | 用户态 NIC 驱动 | 内核（仅机制） |
|------|----------------|----------------|----------------|
| 接收：中断→取包→协议解析 | 协议解析/状态迁移 | 收中断、从 ring 取 DMA 报文入 VMO | 投 `Cap(IRQ n)` 中断 + EventPort 唤醒（`59` §5.3） |
| 接收：递交给应用 | 查 socket 表、填 VMO、EventPort `READ` | — | VMO 句柄传递（cap-transfer） |
| 发送：应用→协议封装 | 封装 TCP/UDP/IP 头、查路由 | 从 VMO 取报文入 ring 触发 DMA | VMO 句柄传递 |
| 发送：触发硬件 | — | 写设备寄存器触发 TX（经 `Cap(MMIO)`） | device capability 校验 |

### 4.3 零拷贝路径（device VMO / shared memory 经 capability 传递）

> **方案**：报文缓冲区 = **device VMO**（来自 NIC 驱动 DMA 区，`10` 第三轮回写 B「不可写 right」）。数据通路三段零拷贝：

```
NIC 硬件 ──DMA──▶ device VMO（NIC 驱动持有，内核经 IOMMU 域约束）
                        │ cap-transfer（05）共享 VMO 句柄
                        ▼
                  netstack（解析/重组/分段，原地或 COW 子 VMO）
                        │ cap-transfer（05）共享 socket 接收 VMO 句柄
                        ▼
                  应用 recv 缓冲区（VMO 映射，无 memcpy）
```

- **NIC 驱动 ↔ netstack**：经 VMO/SHM（`03`/`05`），报文缓冲区不跨地址空间拷贝；就绪经 EventPort `CHAN`/`READ` filter（`25` §5.5）。
- **netstack ↔ 应用**：socket 收发缓冲区映射为 VMO（`03`），`send/recv` 经 VMO + EventPort `CHAN` 通知（`25` §5.4）。小消息可经 `05` Channel，但 bulk 必须走 VMO（避免 `19` AP-7「该用 SHM 却用 Channel 传 bulk」反模式）。
- **capability 传递**：VMO 句柄与 socket 句柄均经 `05` cap-transfer 在 NIC 驱动/netstack/应用间授予；跨进程授予需发送方持 `GRANT` right（`07` §4.5）。
- **所有权与回收**：device VMO 由 NIC 驱动经 `10` C8 撤销锁序列回收；socket 接收 VMO 随 socket 句柄 `close`/`revoke` 自动回收（`07` §4.5）。

### 4.4 AF_UNIX 分叉（与 05 协同，非 netstack）

- `AF_UNIX` 域套接字 → 直接映射到 `05` 的 Channel（语义纯净、零协议开销，`25` §1.2 / `08` §4.3）。**不走 netstack**，由 `05` IPC 原语承载。
- `loopback`（`127.0.0.0/::1`）→ **走 netstack 本地回环**（保持协议路径统一、防火墙一致性，`25` §6.2 D6 建议）。二者 backend 不同，但共用 socket API 表面与 EventPort 就绪（`25` §1.2）。

## 5. 多队列 / RSS / vlan / 多播的 Day 1 范围与边界

> **总则**：协议相关项（vlan 标签、IGMP/MLD、多播路由）属 netstack 用户态逻辑；硬件相关项（多队列配置、RSS hash、MAC 多播过滤）属 NIC 驱动经 device capability 编程（`10`）。内核均不介入。

### 5.1 多队列 / RSS（NIC 驱动层，Day 1 最小）

- **位置**：队列数量、RSS indirection table、RSS hash 类型（Toeplitz 等）由 NIC 驱动经 `Cap(MMIO)` 编程设备寄存器（`10` §4.2）；netstack 收到的是已按流归并的单条报文流，**无感知队列拓扑**。
- **Day 1 边界**：基础单队列/少量多队列可启用；**高级 RSS（可配 hash key、对称哈希、ACE/RSS  steer）Day 1 后置**（优化项，非正确性必需）。`NET_*` 不覆盖 RSS 配置——它归 `10` 设备能力域（`25` C17 §4，不新增 `NET_OFFLOAD`）。
- **权衡**：RSS 把多流分散到多核，但 netstack 单进程若单线程则 RSS 收益受限；多队列 + netstack 多 worker 的协同为执行层定稿（见 N6）。

### 5.2 vlan（netstack 协议逻辑，Day 1 基础）

- 802.1Q tag 解/封 = 协议逻辑，在 netstack 内处理（内核不碰）。
- Day 1 支持**基础 vlan 子接口视图**（`/net/eth0.100` 经 `06` 每进程命名空间 reveal，`25` §4.4）；vlan  trunk 的 PCP/DEI 优先级映射后置。
- **边界**：vlan 间路由（inter-VLAN routing）属 netstack 路由逻辑，Day 1 可后置（非单机必需）。

### 5.3 多播（IGMP/MLD 在 netstack + MAC 过滤在驱动）

- **协议层**：IGMPv2/v3、MLDv1/v2 属 netstack 用户态逻辑（成员关系、查询响应），内核不实现。
- **硬件层**：NIC 驱动经 `Cap(MMIO)` 编程 MAC 多播过滤表（hash/精确表）；驱动需「该接口是否加入某多播组」的决策来自 netstack 经 `05` Channel 下发（netstack 持接口管理权）。
- **Day 1 边界**：链路层多播接收 + IGMP/MLD 基础成员关系可用；**多播路由协议（PIM/IGMP proxy）Day 1 不做**（路由协议非单机必需）。
- **权限边界**：多播 MAC 过滤编程权归属「接口管理」——本文建议并入 `NET_MANAGE`（bit 39，已 freeze），不另设 right（与 `25` C17 §3 防火墙规则归属同构）。

### 5.4 范围收口表

| 特性 | Day 1 范围 | 归属层 | 后置项 |
|------|-----------|--------|--------|
| 多队列 | 基础多队列（可选） | NIC 驱动（设备能力） | 高级 RSS/hash key 配置 |
| RSS | 硬件默认（若驱动开） | NIC 驱动 | 可配 RSS indirection/对称哈希 |
| vlan | 基础子接口 + tag 解封 | netstack 协议 | inter-VLAN 路由、PCP 映射 |
| 多播 | L2 接收 + IGMP/MLD 基础 | netstack + NIC 驱动 MAC 过滤 | PIM/IGMP proxy 多播路由 |

## 6. 与 C15 / EventPort / 57 timer 的协同

### 6.1 与 C15 严格一致（用户态 netstack 边界）

本文一切条目都落地 `25` C15「网络栈 Day 1 完全用户态」与 C17「内核最小网络面」——不引入内核协议语义、不新增 `NET_*` 之外的 right、offload 归 `10` 设备能力域。任何「临时把某协议留核」的退出条件**明确拒绝**（`25` C15 采纳理由 4）。

### 6.2 与 `04`/`05` EventPort 异步 I/O 衔接

> **方案**：socket 就绪与收包唤醒统一经 EventPort（`05` §4），与 IPC/定时器通知共用同一多路复用（`57` §5.2）。

- socket 可读 → `EVFILT_READ`；可写 → `EVFILT_WRITE`；对端关闭/异常 → `EVFILT_CHAN`（`25` §5.1）。
- 应用一个 `epoll`/port 等待即可同时收 socket IO、IPC、timer（`57` §5.2），对标 Linux `timerfd`+`epoll` 合一但实现为 capability 对象而非 fd。
- **异步发送完成**：`send` 经 VMO 写入后，TX 完成由 NIC 驱动经 EventPort 通知 netstack，netstack 再向应用 socket 投 `EVFILT_WRITE`（流控/缓冲区回收）。
- 与 `04` 结构化取消同源：socket 句柄随持有进程/Job 取消而 `revoke`（`07` §4.5），阻塞在 EventPort 的线程被唤醒并收 `revoke` 事件（`05`/`04` §4.6）。

### 6.3 与 `57` timer 协同（RTO / 重传超时 / keepalive / TIME_WAIT）

> **方案**：netstack 自持 timer 句柄（`07` §2 timer 对象 / `57` §3.4），向内核 `timer_set(deadline, slack)` 请求超时，触发后经其 socket 句柄关联的 EventPort 收 `TIMER_FIRED`，再驱动协议状态机（`57` §5.3 已定此范式）。

- **RTO（重传超时）**：netstack 按 RFC 6298 维护 `SRTT`/`RTTVAR`，计算 `RTO = SRTT + max(G, 4*RTTVAR)`；初始 RTO = 1s、最小 RTO = 1s（RFC 6298）、指数退避上限由执行层定稿（见 N9）。RTO 计算与重传判定全在 netstack，内核只提供单调钟 `CLOCK_MONOTONIC`（`57` §3.2，不受 NTP 步进影响，保证 RTO 不被校准改写）。
- **keepalive / TIME_WAIT / 重传计时器 / DNS 解析超时**：均建立在 netstack 自持 timer 句柄之上（`57` §5.3）。
- **slack 合并**：netstack 的 `timer_set` 可带 `slack`（`57` §3.4），把落在同一 slack 窗的多个连接计时器合并触发，节能且对齐唤醒（替代 Linux `timeBeginPeriod` 全局分辨率协商，`57` §2.2）。
- **权限边界**：netstack 持有的 timer 句柄只具 `TIMER_SET`/`TIMER_CANCEL`，**无 `CLOCK_ADJUST`**（`57` §5.3），无法借超时机制篡改系统时间。
- **与 Job 账本协同**：高频重传/keepalive 定时器可计入 `04` Job 账本 `timer_wakeups` 预算（`57` §4.3 T3），防 wakeup 风暴 DoS。

## 7. 五架构差异（仅 NIC 驱动层，netstack 同源）

> **论断**：netstack 是纯 Rust 用户态组件，跨五架构二进制一致（不依赖架构页表/中断语义），与 `03`/`05`/`10` 的架构无关抽象解耦。差异**只在 NIC 驱动层**。

| 架构 | netstack | NIC 驱动层差异（薄后端） |
|------|----------|--------------------------|
| x86_64 | 同源 Rust | virtio-net 经 PCI MMIO/IO + `Cap(IRQ n)`（APIC 路由，`59` §7.1） |
| aarch64 | 同源 Rust | virtio-net 经 PCI/MMIO + GIC（`59` §7.2） |
| riscv64 | 同源 Rust | virtio-net 经 PCI/MMIO + PLIC/APLIC+IMSIC（`59` §7.3） |
| loongarch64 | 同源 Rust | virtio-net 经 PCI/MMIO + LIOINTC/EIOINTC/PCH-MSI 级联（`59` §7.4） |
| i386 | 同源 Rust | 仅 NIC 驱动 C 后端受 `02` C2 纯 C 约束；netstack Rust 主体不受影响（`25` §5.6 / `19` §3.3） |

- 数据通路 VMO 抽象屏蔽架构差异（`03`）；`Cap(IRQ n)` 统一 cap 面（`59` §7.6）使 NIC 驱动中断处理与架构无关。
- i386 纯 C 约束（`02` C2）**只影响 NIC 驱动 C 后端**，不侵蚀 netstack Rust 主体（`19` §3.3「i386 验证负担仅落于驱动 C 侧」）。

## 8. 与 `59` 中断：网卡收包中断 → 用户态 netstack 经 EventPort 唤醒

> **方案**：网卡收包中断 → 内核向持 `Cap(IRQ n)` 的 NIC 驱动转发 → 驱动经 EventPort（`EVFILT_IRQ`，`59` §5.3）被唤醒 → 从 ring 取 DMA 报文入 device VMO → 经 EventPort 通知 netstack（`EVFILT_READ`/`CHAN`）→ netstack 解析并投递应用 socket。

```
NIC 硬件 IRQ
   │ 内核中断派发器（59 §4，按 Cap(IRQ n) 路由）
   ▼
NIC 驱动线程（用户态，持 Cap(IRQ n)）── wait/ack ──▶ 取 ring 报文入 device VMO
   │ 经 05 EventPort EVFILT_READ/CHAN 通知
   ▼
netstack（用户态）── 协议解析、查 socket 表、填应用接收 VMO
   │ 经 05 EventPort EVFILT_READ 通知
   ▼
应用 recv 唤醒
```

- **中断合并 + 轮询混合**（高频 NIC，10G+，`19` AP-2）：合并后的「就绪事件」仍经 EventPort 投递，中断频率与调度唤醒次数解耦，避免 IPC 风暴拖垮调度器（`59` §5.3 / `10` §5 开放议题 1）。
- **per-IRQ 屏蔽**：NIC 驱动只可 `IRQ_MASK`（per-IRQ），**无全局关中断**（`KERNEL_PRIV` 仅内核，`59` §4.3）；与 netstack 崩溃恢复互不污染（`10` C8 撤销锁序列）。
- **五架构一致**：中断对象语义（wait/ack/mask/revoke）五架构一致（`59` §7.6），NIC 收包唤醒路径与架构无关。

## 9. MeuOS 推荐（收口）

### 9.1 推荐架构（一句话）

**socket API 经 mkit 薄层映射为内核 mint 的 socket capability（带 `NET_*` rights、不回内核）；TCP/UDP 状态机全在用户态 netstack、零拷贝经 device VMO + 能力传递；多队列/RSS/vlan/多播按 §5 最小边界收口；socket 就绪与收包统一经 `05` EventPort，RTO/重传经 `57` timer（netstack 自持 timer 句柄），网卡收包中断经 `59` `Cap(IRQ n)` EventPort 唤醒 NIC 驱动再透传 netstack；五架构仅 NIC 驱动薄后端差异。**

### 9.2 自主结论

1. **mkit 兼容层是用户态蹦床**：BSD socket 全集 1:1 映射为 netstack 请求 + socket 句柄 capability；`NET_*` rights 在 `socket/bind/connect` 时一次性收窄，运行期热路径仅位运算 + EventPort（`25` §4.1 / `07` §4.5）。
2. **协议状态机全在 netstack**：TCP/UDP/ICMP/ARP/NDP/DHCP/DNS 状态机不占内核任何连接槽；内核「最小收发」= 搬运 VMO 报文 + 投通知，零协议语义（`25` C15/C17）。
3. **零拷贝经 device VMO + 能力传递**：NIC 驱动 ↔ netstack ↔ 应用三段零拷贝；VMO/socket 句柄均经 `05` cap-transfer；bulk 必走 VMO、小消息可走 Channel（`19` AP-7）。
4. **多队列/RSS/vlan/多播按 Day 1 最小边界**：硬件项归 NIC 驱动设备能力、协议项归 netstack；高级 RSS、inter-VLAN 路由、PIM 多播路由后置（`25` C17 §4 不新增 right）。
5. **异步 I/O 与 `05` EventPort 同源**：socket 就绪/收包/异步 TX 完成统一 EventPort filter，与 IPC/timer 共用多路复用；与 `04` 结构化取消同构（句柄 `revoke` 唤醒阻塞线程）。
6. **RTO/重传与 `57` timer 协同**：netstack 自持 timer 句柄，`timer_set(deadline, slack)` 驱动 RTO/keepalive/TIME_WAIT；单调钟保证 RTO 不受 NTP 改写；`TIMER_FIRED` 经 EventPort 回 netstack。
7. **收包中断经 `59` `Cap(IRQ n)` EventPort 唤醒**：NIC 驱动 wait/ack 自身中断、取包入 VMO、通知 netstack；高频走中断合并+轮询混合；per-IRQ 屏蔽、无全局关中断。
8. **五架构仅 NIC 驱动层差异**：netstack 同源 Rust 二进制；i386 纯 C 约束仅落 NIC 驱动 C 后端（`02` C2）。

## 11. 第九轮自主采纳·闭环 N13（netstack 单例系统服务）

> 本回写为「修订式追加」：不删改 §1–§9 既有原文，仅升级 §9.3 待决表中 N13 行状态字段为「已裁决·闭环」；N14 行不变。未引入新内核原语、未新增 `NET_*` right（`NET_*=bit28–31` + `NET_MANAGE=bit39` 冻结于 `07` §4.1 / `38` §3 / `45` §3）。

### 11.1 裁决结论（一句话）
**netstack 采纳「单例系统服务」：唯一的用户态系统服务（单例）持有 `NET_*` rights（bit28–31）与 `NET_MANAGE`(bit39)，socket/handle 由该单例经 capability mint 给请求方；不允许多 netstack 实例并存。**

### 11.2 采纳理由（4 条）
1. **与 `00` A6 重服务出核一致**：网络栈已是唯一用户态系统服务，单例模式不引入第二套协议语义实体，保持「重服务出核」收口干净，内核仍零协议语义。
2. **避免 `/net` 视图不唯一与 socket handle mint 委托人身份歧义**：多实例会导致每进程 `/net` 命名空间视图来源不明、socket 句柄的 mint 委托人身份（netstack 单例）无法唯一锚定，capability 链溯源失真。
3. **Fuchsia netstack3 单例标杆**：直接对标 Fuchsia netstack3 由组件框架以单例组件管理的既成范式（见 §10 参考文献），非缝合怪。
4. **多实例需虚拟交换层反而增大 TCB**：若允许多实例并存，需额外虚拟交换/转发层在实例间路由，增大内核或中间层 TCB，与「缩 TCB」目标相悖。

### 11.3 多 namespace 网络视图的落地（不靠多实例）
每进程/每 Job 的网络可见性（多 namespace 网络视图）通过 **`06` C3 每进程 namespace 作用域** + **netstack 在 mint 时 consult 请求方 Job 的 namespace 上下文**实现：netstack 单例在 mint socket/handle 时读取请求方 Job 的 namespace 标签，按该上下文投影 `/net` 视图，而非起多个 netstack 实例。

### 11.4 与既有地基的衔接
- **`00` A6（重服务出核）**：netstack 单例是 A6 的落地实体，未新增内核协议语义。
- **`06` C3（每进程 namespace）**：多网络视图的唯一来源，与单例不冲突。
- **`04` 监督（§4.5 exception channel）**：netstack 单例崩溃仍经 exception channel 上行监督者，已建 socket 句柄随 Job 取消/重绑（承接 N10），单例不影响故障隔离。
- **`25` C15（用户态 netstack 边界）/ C17（内核最小网络面）**：单例持 `NET_*`/`NET_MANAGE`，内核只 mint 收窄句柄，未引入新 right（`07` §4.1 冻结域不变）。

### 11.5 跨架构同源说明
五架构（x86_64/i386/aarch64/riscv64/loongarch64）netstack 逻辑同源（§7），单例系统服务是用户态组件实例数约束，与 NIC 驱动层架构差异解耦；单例策略在五架构上一致生效，不新增架构分支。

### 11.6 N14 状态说明
N14（loopback 走 netstack 本地回环）维持协同 `05`/`08` 定稿，本轮回写不改动。

## 12. reasoning 决策（2026-08-03）

### 12.1 N13 — netstack 单例系统服务（同意）

**reasoning 决策（2026-08-03）**：**采纳「netstack 单例系统服务」**——唯一的用户态系统服务（单例）持有 `NET_*`（bit28–31）与 `NET_MANAGE`(bit39)；不允许多 netstack 实例并存。

**被否决选项**：
- **多实例并存**：允许多 netstack 进程同时运行，各持 socket 句柄。

**理由（深·reasoning 百思）**：

1. **多 namespace 网络视图已被 `06` C3 + mint consult 覆盖，多实例是伪需求**。每进程/每 Job 的网络可见性差异（"多 namespace 网络视图"）已经由 `06` C3 每进程独立 namespace + netstack 在 mint socket 时 consult 请求方 Job namespace 上下文化（§11.3 已说明）实现。**多实例并不增加视图多样性**，反而把"哪一份视图归哪个实例"的元问题塞进 capability 链溯源里，徒增 `04` 监督者的故障归因负担。

2. **多实例的"隔离性"对 netstack 本身是伪安全收益**。Netstack 是出核用户态服务（`00` A6、`25` C15），其安全边界由 capability（`07` §4.5 约束式 mint）+ Job 账本（`04` §4.4）提供，**不由"实例数"提供**。多实例间的"隔离"在 capability 体系里是 capability 边界本身——再起多个 netstack 进程不会让边界更牢，反而让每进程自带一份 TCP/IP/ICMP 状态机副本，**内存/线程占用倍增却没有对应安全收益**。

3. **多实例需"虚拟交换/转发层"反而增大 TCB**。若允许多实例并存（如"host netstack" + "guest netstack"），则跨实例通信必须经某种虚拟交换/转发层——这层要么跑在用户态（再次侵蚀 TCB）、要么跑在内核（**直接违背 `00` A6 与 `25` C15 "内核零协议语义"红线**）。两种路径都比单例差。

4. **多实例与 `04` 监督者/socket 句柄 `revoke` 语义并不同构**。单例崩溃 → 整系统网络暂停，`meu-supervisor` 启动新单例替回，期间已建 socket 句柄随 Job 取消/重绑（结构化取消，`04` §4.6 + `46`/`47`）。多实例则需"局部隔离性"——单实例崩溃只影响局部子网，**但这正是 capability 边界与 namespace 投影应当提供的局部性**，无须通过"实例数"实现。

5. **Fuchsia netstack3 单例是成熟范本**（已采纳理由 3）——非缝合怪。Fuchsia 组件框架以单例组件管理 netstack3，能力边界由 capability 守护，不依赖多实例。

**与既有地基协同**：
- **`00` A6 重服务出核**：单例是 A6 落地形态，零新增内核协议语义。
- **`06` C3 每进程 namespace**：多视图的**唯一来源**，与单例不冲突——单例 + namespace 投影 = 完整多视图。
- **`25` C15 用户态 netstack / C17 内核最小网络面**：单例持 `NET_*`/`NET_MANAGE`，内核只 mint 收窄句柄，未引入新 right（`07` §4.1 冻结域不变）。
- **五架构同源**：单例策略是用户态组件实例数约束，与 NIC 驱动层架构差异（`25` §5.6）解耦，五架构一致。

**TCB 体量评估**：单例 = 1 套协议栈状态机；多实例 = N 套状态机 + 跨实例转发层。**单例 TCB 占内存/线程显著更小**。

**长期可维护性**：单套代码路径；多实例需"实例间转发协议"，增加维护负担。

**结论**：同意指挥官第九轮自主采纳「netstack 单例系统服务」。**未引入新内核原语、未新增 `NET_*` right**。
