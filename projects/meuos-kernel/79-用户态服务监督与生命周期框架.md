## 0. 一句话核心结论

> **用户态重服务（FS / 网络 / 驱动 / 监督 / 合成器 / GPU / 审计等）统一由基于 Job 树的监督框架管理：监督者（meu-supervisor）是 Job 树的根监督者，负责 spawn / 监控 / 重启 / 降级、结构化取消上行（`00` A9）、与 `.msys` A/B 回滚（`06` §4.3 / `61` C61-4）协同；服务生命周期以 manifest 表达依赖与重启策略；与 `46`/`47`/`53`/`65`/`36`/`06`/`61` 同源——它是 Job 树、capability、结构化取消这些既有地基的「编排层」，而非新内核原语。**

## 1. 监督者模型（根监督者 + Job 树；衔接 `04` §4.1 / §4.4）

### 1.1 解构：「应该是什么样」——capability 世界的服务监督

> 大喵铁律第一条：先问「应该是什么样」。在 `04` 的 Job 树 + `07` 的 capability 地基下，服务监督的形态由两条约束直接决定，无需照搬 systemd 的「PID 1 + 单元文件 + cgroup」范式。

监督者存在的唯一理由：**让一组由它 spawn 的进程/Job 拥有统一的生命周期与策略边界**。在 MeuOS 中，这一职责被「拆回」到 Job 树本身：

- **监督者不是特权内核对象**，而是挂在**根 Job 之下**的第一个用户态进程（`04` §4.5）。内核只负责：① 启动早期创建**根 Job**；② 在根 Job 下 spawn 监督者；③ 保证根 Job 终止 ⇒ 级联终止其下全部 Job/Process（lifetime control，对齐 Zircon）。其余监督策略全在用户态。
- **Job 树即监督树**：`46`/`47` 已把 Job 升格为「结构化 scope + 资源账本 + 取消域（+ 命名可查询沙箱单元）」。`79` 只是在此之上补一句——**Job 的父子关系 = 监督的父子关系**：父 Job 的监督者对其子树拥有 spawn / 取消 / 重启权，子 Job 不能反向影响父。这与 `46` §1.3「结构化并发」同构，监督只是该范式在「服务编排」维度的展开。
- **监督者持专属 capability，普通进程不可冒充**：监督者持 `JOB_CREATE`（建子 Job）+ 受约束 `GRANT`（派生 service capability）+ 对子树 `DBG_INSPECT`/`DBG_CRASHDUMP`（订阅 exception channel，`04` §4.5 / `17` C9-B）。普通进程无这些权，无法把自己伪装成监督者来拉起/重启他人服务——这是 `07`「无隐式特权」在监督层的直接落点。

### 1.2 监督者身份：内核对象 vs 首个用户态服务（待决项 S1）

本文**倾向**采纳 `04` §4.5 的既有口径——监督者是**首个用户态服务**（launchd 式），内核仅保证其可靠启动与自愈（监督者自身崩溃，由内核自举重启，见 `04` §5 待决 4 / `09` §6 待决 10 / `36` §5.3）。这条路径与 `00` A6「重服务出核」一致：监督策略是用户态策略，不进 TCB。

但「监督者是否为内核对象」是架构级待决（见 §8 S1）——若未来评估把监督核心做成内核内薄层，须重新评估 TCB 边界，且与 A6 冲突，故本文默认不采用。

### 1.3 监督职责清单（与既有地基同构）

| 职责 | 落点（不新造） | 说明 |
|------|----------------|------|
| spawn 服务 | `meu_spawn` 归入目标 Job（`04` §4.2） | 监督者持目标 Job handle，显式声明句柄/命名空间/能力集 |
| 监控存活 | 消费进程退出事件 / exception channel（`04` §4.5 / `04` §4.6） | 内核向监管 Job 的 event/channel 投递退出原因，无需 `wait()` 轮询 |
| 重启 / 升级 | Job 重启 / `.msys` repoint（`36` Tier B / `06` §4.3） | 由监督者按 manifest 策略执行，非内核决策 |
| 降级 | manifest 声明的降级链（§2.4） | 监督者策略，纯用户态 |
| 结构化取消上行 | Job 取消广播 + exception channel 多播（`00` A9） | 异常经 exception channel 上行到祖先监督者 |
| 审计自身动作 | 审计日志内核对象（`65` §3） | 监督者的 spawn/重启/降级/回滚动作可审计 |

### 1.4 五架构同源

监督者本身是用户态 Rust 组件（与 `63` netstack、`36` pkg-loader 同构），其逻辑跨五架构一致：Job 树、exception channel、repoint 原语均在进入 `kernel_main` 后输入一致（`61` §7）。**监督逻辑不因架构而异**；差异仅落在被监督的驱动/后端组件（如 `63` §7 NIC 驱动层），与监督框架无关。

## 2. 服务生命周期 manifest（依赖、启动序、重启策略 fail-closed、降级）

> 本节定义服务「如何被描述」——一份声明式 manifest，类比 systemd unit、Fuchsia component manifest、Kubernetes Deployment。manifest **只声明策略**，不携带内核新语义；其字段全部映射到既有 Job/Channel/capability 原语。

### 2.1 manifest 的组成

```
service_manifest {
  name:            "netstack"              // well-known name（47 命名可查询，受 cap 约束）
  job_path:        "/svc/network"          // 在监督树中的位置（job-path，47 scoped 标识）
  image_ref:       hash(".msys" 子卷/组件)  // 指向 .msys 内的版本化二进制（00 A11 / 06 §4.3）
  capability_set:  [NET_*, NET_MANAGE]     // 启动时显式授予的最小特权集（07 §4.1，已冻结）
  namespace_tmpl:  "network-realm"         // 继承/绑定的 namespace 模板（06 C3）
  depends_on:      ["devmgr", "fs-root"]   // 依赖的服务（启动序约束）
  startup_order:   10                       // 同层内的启动先后（拓扑排序输入）
  restart_policy:  fail-closed | restart | never   // 失败策略（§2.3）
  degrade_to:      "netstack-lite"         // 降级目标（§2.4）
  watchdog:        { timeout_ms, action }  // 心跳超时动作（10 看门狗思想）
  audit:           enabled                  // 该服务动作是否进审计（65）
}
```

### 2.2 依赖与启动序（拓扑排序，非 cgroup 式事后挂接）

- **依赖表达为监督树边的约束**：`depends_on` 决定「被依赖服务 `Running` 后，本服务才可 spawn」——这是 `04` Job 父子/兄弟关系的策略化，不引入新机制。
- **启动序 = 拓扑排序**：监督者在 boot / 热升级时按 `depends_on` + `startup_order` 做 DAG 排序，逐层 spawn；环依赖由监督者拒绝（fail-closed，不静默打破环）。
- **与 `04` Job 账本的衔接**：依赖边不携带资源语义，资源语义仍由目标 Job 的账本（CPU/内存/句柄/IO/进程线程数，`04` §4.4）Day 1 内建承担——manifest 不重复账本，只引用 Job。

### 2.3 重启策略 fail-closed（默认立场）

| 策略 | 语义 | 适用 | 是否默认 |
|------|------|------|----------|
| `restart` | 崩溃即重启（带退避/熔断，防重启风暴） | netstack / fs / 驱动等可恢复服务 | **推荐默认（多数重服务）** |
| `fail-closed` | 失败即**停止该子树并上报监督者/审计**，不自动重启 | 安全敏感/认证类服务（如 `53` 认证 broker 自身）、度量校验失败的服务 | **安全敏感类默认** |
| `never` | 退出不重启，仅记录 | 一次性工具 / 批处理 | 显式声明 |

- **fail-closed 的语义**：当服务失败涉及「信任前提受损」（如 `.msys`/`.mimg` 度量校验失败，`65` §6 衔接点 2、`61` 跳 1–3），监督者**不**自动重启到损坏镜像，而是冻结该子树并上报——与 `65` 第 0 层「度量失败 ⇒ 服务拒绝」一致；回滚须由 `.msys` repoint（`§4`）触发，而非盲目重启。
- **重启风暴防护**：`restart` 须带指数退避 + 熔断（连续 N 次失败转 `fail-closed` 或 `degrade_to`），避免「崩溃-重启-再崩溃」循环拖垮 Job 账本（`04` §4.4 配额）。

### 2.4 降级（degrade_to）

- 降级 = 监督者在「完整服务不可用」时切到**功能子集更小但更稳**的替身（如全功能 netstack → `netstack-lite` 仅 loopback；完整合成器 → 软件合成器）。
- 降级链在 manifest 声明，监督者决策；降级目标同样是受 capability 约束的普通服务，不享特权。
- 降级是**用户态策略**，不引入内核机制；与 `63` N10「netstack 崩溃恢复：重建 vs 重绑」协同——降级是重绑失败后的兜底。

### 2.5 与 `46`/`47` 监督树语义对齐

`46` §1.3 把 Erlang OTP supervisor 的「one_for_one / one_for_all / rest_for_one」下沉为 Job 树。本节 manifest 的 `depends_on` + 重启策略即该思想的声明式表达：
- `one_for_one` ⇔ 单服务 `restart`；
- `one_for_all` ⇔ 兄弟服务共享「任一失败 ⇒ 整组重启」策略；
- `rest_for_one` ⇔ `depends_on` 拓扑中「上游失败 ⇒ 下游重启」。
本文不另立监督策略原语，仅把它们映射为 manifest 字段 + 既有 Job 取消/重启语义。

## 3. 结构化取消上行（`00` A9 / `04` §4.6；异常经 exception channel 上行）

> 本节把 `00` A9 与 `04` §4.6 的「exception channel → 监督者」在监督框架下具体化，明确异常如何沿监督树上行、由谁决策。

### 3.1 取消/异常的双通道

| 通道 | 触发 | 上行路径 | 消费方 |
|------|------|----------|--------|
| **结构化取消** | 父 Job 取消 / 监督者主动停止 | Job 取消广播到全部子孙（`46` §1.3 两段式：先协作清理窗口，超时强杀） | 子树内各进程协作退出 |
| **致命异常** | 进程崩溃 / 越权 / 度量失败 | exception channel **copy 语义多播**给祖先监督者 + 持权调试器（`04` §4.5 / `17` C9-B） | 监督者（持 `DBG_CRASHDUMP` 默认订阅，决策不可抑制）+ 调试器（有界冻结窗口） |

### 3.2 exception channel 上行的监督语义

- **上游即监督者**：因为监督树 = Job 树，异常多播的「祖先监督者」就是 Job 树的父/祖节点持有者——监督者天然在 exception channel 的消费端，无需额外注册机制。
- **决策不可抑制**：监督者持 `DBG_CRASHDUMP` 默认订阅，其 kill/restart/升级决策**不可被调试器或其他消费者抑制**（`17` C9-B）；调试器仅持 `DBG_ATTACH` 收副本，可有界冻结（默认 30–120s）暂缓重启，但**绝不可永久接管**。
- **异常即结构化 `CrashReport`**（`12` §4.3）：含 `origin_job` / `subject_handle` / `op` / `rights_mask` / `verdict` / `target`——主键是句柄+Job+rights 摘要（`65` §1.1），与 audit 日志同主键，天然可被审计消费（§5）。

### 3.3 与 `00` A9 的衔接

`00` A9 已定「致命异常统一经 exception channel 上报 meu-supervisor，由策略决定 kill/dump/restart/升级」。本文 §3 是其**监督框架内的操作化**：异常沿监督树（= Job 树）上行，决策作用在 Job 节点而非全局 PID；跨 realm 的取消/异常默认不穿透（`46` §7.7 / `47` §7.8 / `53` §7.5 已闭环 A7，capability 边界即 realm 边界）。

## 4. 与 `.msys` A/B 回滚协同（`06` §4.3 repoint + `61` C61-4 恢复指针；监督者触发的原子回滚）

> 本节定义监督者如何驱动「回滚」——主路径是 `06` §4.3 的命名空间原子 repoint，兜底路径是 `61` C61-4 引导级 A/B。监督者是这两个路径的**用户态执行器**。

### 4.1 三层回滚与监督者角色

```
[运行时组件损坏]  → .msys 子树级 repoint 回退（06 §4.3，免重启，per-process 灰度）
                   执行器 = meu-supervisor（按 manifest 决策何时切、灰度多少）
                   ── 能力级单点原子切换：/msys 别名从新子卷重指备份子卷
[内核/FS/supervisor 自举链损坏] → .mimg 携恢复 .msys 指针的 A/B 切 slot（61 C61-4，需重启）
                   执行器 = bootloader/09 启动流程；supervisor 自身亦受此兜底保护
```

- **主路径（repoint，由监督者驱动）**：`06` §4.3 已定——staging 克隆签名校验 → 单条 capability 级事务把 `/msys` 别名重指新子卷 → 监督者按 manifest 绑定新 sysroot、per-process 灰度（`63` N13 单例 netstack 的 `/net` 视图投影亦随之切换）。**回滚 = repoint 回备份快照**，同样原子、免重启。监督者持有「何时切割 / 灰度比例」的策略权（用户态），FS 只暴露 repoint 原语（`06` §4.3e / §5 `依赖 04`）。
- **兜底路径（引导级 A/B，由 61 C61-4 提供）**：`.mimg` Item 3 扩展携带「恢复 `.msys`」指针（`61` §3.2 / C61-4 已裁决·闭环）。当损坏严重到连 repoint 都执行不了（FS 服务/supervisor 起不来），引导级切回已知良好 slot。这是**最后防线**，日常组件升级不走的路径（`36` §5.6 同构）。

### 4.2 监督者触发的原子回滚契约

1. 监督者消费服务崩溃/度量失败事件（`§3` / `65` §6）；
2. 若策略判定需回滚（如新 sysroot 下某重服务崩溃率超阈值），监督者发起 repoint 回退到备份 `.msys` 子卷（`06` §4.3）；
3. repoint 是**能力级单点原子事务**——旧持有者续持旧能力、新进程切回旧视图、无需重启、支持 per-process 灰度（`06` §4.3 修正：非破坏式，区别于 APFS revert）；
4. 仅当 repoint 机制自身不可用，才降级到 `61` C61-4 引导级 A/B，此时需重启且由 bootloader 执行，supervisor 不在场但受保护。

### 4.3 与 `36` 热升级的闭环

`36` Tier B 已把「用户态服务热升级 = 包更新（进新 `.msys` 子卷）+ 命名空间 repoint + Job 重启/灰度 + 旧域 revoke（07）」定为日常演进主路径。本文 §4 即该路径的**监督编排视角**：监督者持有 repoint 决策权与灰度策略，是 `36` Tier B 的执行器；回滚是 repoint 的逆操作，二者共用同一原子原语，零新增内核机制。

## 5. 认证 broker 与审计协同（`53` 认证 broker、`65` 审计；监督动作可审计）

> 本节把 `53` 的认证 broker（本身即受监督服务）与 `65` 的审计可观测，在监督框架下衔接：监督者拉起/重启/回滚的动作，与认证 broker 的 mint 动作，同进审计。

### 5.1 认证 broker 是监督树中的普通被监督服务

- `53` §2.5 定义认证 broker 为「持受限 `GRANT` 的受约束 issuer」——它**本身**由监督者经 `meu_spawn` 拉起、归入某 Job、受 `04` 账本约束，与其他重服务无特殊地位。
- broker 认证成功后 mint 会话 capability 集合（`53` §2.6），该集合即新会话 Job 的能力模板（`53` §2.4 会话 = Job 子树 + 合成视图 + 生命周期）。**监督者不介入 mint 语义**，只负责 broker 自身的存活/重启（`fail-closed` 适用，见 §2.3）。
- broker 自身若失败（如策略清单损坏），按 `fail-closed`：不自动重启到损坏策略，上报监督者 + 审计，由 `.msys` 回滚（`§4`）或人工介入恢复。

### 5.2 监督动作可审计（与 `65` 衔接）

- `65` §3 定义审计日志 = 能力受限内核对象（落 `kernel/audit` inspect 子树），由出核审计服务持 `DBG_INSPECT`（审计子树）订阅/读取；专属 `AUDIT` right 仅预留 bit48+（`65` §11 已闭环方案 A）。
- **监督者的 spawn / 重启 / 降级 / 回滚动作**是最高价值审计事件：谁（监督者 Job）、对谁（目标服务 Job）、做了什么（restart/fallback/degrade）、依据哪份 manifest 策略——全部进审计 ring，主键与 `CrashReport` 同构（句柄+Job+rights 摘要，`65` §1.1）。
- **审计订阅边界**：审计服务的读取权受 `DBG_INSPECT` 子树粒度约束；监督者自身也可订阅审计以做「重启风暴 / 越权探测」检测（`65` §5.3），但**审计/监控子系统不自行 kill/隔离**（避免新隐式特权面，`65` §5.3）——自动响应需监督者 manifest 授权，与 `00` A9 监督者决策不可抑制同源。

### 5.3 认证 + 审计 + 监督的同构闭环

```
认证 broker（53，受监督） mint 会话 cap → 会话 Job 受监督者生命周期管辖
        │                                      │
        │ mint 事件进审计（65）                │ 会话内服务崩溃 / 取消经 exception channel（00 A9）→ 监督者
        ▼                                      ▼
   审计 ring（kernel/audit，DBG_INSPECT）   监督者决策 kill/restart/降级/回滚（本文 §1–§4）
        │                                      │
        └──────────── 同主键（句柄+Job+rights）可关联溯源 ────────────┘
```

## 6. 热升级协同（`36` 用户态组件热升级；监督者零停机切换）

> 本节把 `36` 的三层模型（Tier A 静态 TCB / Tier B 用户态热升级 / Tier C 受约束可加载组件）在监督框架下收口：监督者是 Tier B/C 的统一执行器，实现零停机切换。

### 6.1 监督者 = 热升级执行器（Tier B）

- `36` §4.2/§5.3 已定 Tier B 热升级由 `meu-supervisor` 执行：决定切割时机、per-process 灰度、消费退出事件做重启。本文 §2 manifest 的 `image_ref` + `restart_policy` + `degrade_to` 即 supervisor 执行 Tier B 的**策略输入**。
- **零停机切换**：旧进程续持旧 sysroot 能力（CoW 共享未改块），新进程按 manifest 绑定新 sysroot；监督者先灰度 10% 观察崩溃率再全量（`06` §4.3e / `36` §4.2）。双实例共存受目标 Job 账本约束（`04` §4.4 / `36` 待决 6 实测峰值）。

### 6.2 受约束可加载组件（Tier C）的监督归属

- `36` §4.3 Tier C：运行期引入 sysroot 外的新组件，由 `pkg-loader`（受 supervisor 监管）签名验证后 `meu_spawn` 为新 Job、加载即新 capability 域、旧域由 `07` revoke 无悬垂。
- **监督框架视角**：`pkg-loader` 本身是被监督服务；它 spawn 出的新组件**归入监督树**（其 Job 是 supervisor 子树下的子 Job），享受统一的取消/重启/审计——Tier C 不游离于监督框架之外。
- 内核零参与（`36` 结论 C）：Tier C 是用户态 spawn + capability 的正常用法，监督者只是其编排层，无新增内核原语。

### 6.3 内核 TCB 静态（Tier A）与监督者的边界

- `36` C18（已裁决·闭环）：内核 TCB 默认静态、不运行期加载 LKM/livepatch，仅 `.mimg` A/B 兜底。故监督者**不**负责「热补丁内核」——内核升级走 `61` A/B（§4.2 兜底路径），与用户态组件热升级（Tier B/C，监督者主路径）分层清晰。
- 监督者与内核 TCB 的边界 = `00` A6 重服务出核边界：监督策略在用户态，内核只提供 Job/Channel/capability/repoint 原语。

### 7.1 与既有地基的同构关系

本文**不引入任何新内核原语、不新增 right bit**。下表逐项标注本文每个概念如何映射到已决地基：

### 7.2 五架构同源

- 监督框架的全部逻辑（Job 树、manifest 解释、重启/降级决策、exception channel 上行、repoint 驱动）是**纯用户态 Rust**，跨 x86_64 / i386 / aarch64 / riscv64 / loongarch64 二进制一致（`61` §7 收敛契约）。
- 唯一差异落在被监督组件的后端（如 `63` §7 NIC 驱动 C 后端仅 i386 受 `02` C2 纯 C 约束），与监督框架无关——监督逻辑不因架构分支。
- i386 在 attestation 强度上的降级（`65` §7 档 C 仅本地自检）已由审计报告显式标注，**不影响监督框架运行期行为**。

### 7.3 不变量（永不退化）

无论演进，以下不变量与 `04`/`07`/`46`/`47` 一致、**永不退化**：capability 唯一权限源、无 root、无全局 PID、结构化取消唯一、Job 账本 Day 1、`.msys` repoint 非破坏式、exception channel 上行监督者、审计可观测受 `DBG_INSPECT` 约束。**监督框架是这些不变量的编排层，不新增任何可绕过它们的机制。**
