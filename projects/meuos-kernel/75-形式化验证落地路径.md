## 0. 核心结论（一句话）

> **与 `20` 形式化方法衔接，Layer A 可验证小核心（`19 §3.4(A)`）承载 capability 核心正确性证明 + `68 Sc9` 调度核心移交证明；proof-carrying 内核模块边界（哪些模块须证明、哪些仅测试）；工具链选型以 Rust 验证生态为主、Lean / Coq 精化为辅（与 `02` Rust 管安全关键路径同源）；端到端精化证明落点为「spec → kernel 实现」精化链；与 `22` 否定式测试互补（设计不可违背 vs 实现不回归），二者不重叠、共同构成内核正确性论证。**

## 1. 与 `20` 形式化方法衔接（优先级：capability 核心第一、调度核心第二）

### 1.1 衔接定位：本文是 `20` 的「落地路径」而非新策略

`20` 已给出四层验证策略（Layer A 完全证明 / Layer B 模型检验 / Layer C Rust 类型 + unsafe 白名单 / Layer D 仅测试）与核心安全不变量命题（I1–I7）。本文**不重述也不改写 `20` 的策略结论**，而是把 `20` 中「Layer A 仅限 capability rights 检查 + revoke derivation tree」这一收敛结论**向外延伸为一条可执行落地路径**，并显式纳入 `68 Sc9` 已裁定「待移交 `20`」的调度核心。

- `20 §4.1` 把 Layer A 严格限定为 capability 监视器的两处极小核心（rights 检查 + revoke tree），理由是其为 `00` A3 所述「唯一裁决点」的数学内核，一个逻辑错误即等于全局权限失效。
- `20 §7.4` 明确「不做 seL4 全量证明」，把证明预算投到「权限正确性」这一 Single Point of Failure。
- `68 §7.2` / §8.3 Sc9 已把「调度核心（RT 选择 / deadline 会计 / 带宽记账 / 锁协议）移交 `20` 做端到端形式化」列为**待大喵拍板**项，且优先级**低于** capability 核心形式化（`28` R10）。

本文据此确立**两层证明优先级**：

```
 优先级 ①（最高，Day 1 即论证主体）
   └─ capability 核心正确性证明 〔承接 `20 §4.1` Layer A，已收敛〕
        · rights 检查语义（I3 rights 只减不增，不可伪造 I7）
        · revoke 派生/回收完整性（I2 revoked 后派生链全断）
        · 受约束 mint 防 confused deputy（I5，含 `07` C2 密钥=capability）

 优先级 ②（M3 后，设计稳定后启动，低于 ①）
   └─ 调度核心移交证明 〔承接 `68 Sc9`，待大喵拍板〕
        · RT 严格优先级选择（bit45 CAP_RT 门禁 `07 §4.1`）
        · deadline EDF 会计（绝对 deadline 红黑树，`57`）
        · Job RT 带宽记账 + fail-closed（throttle / terminate，`68 §5`）
        · 锁协议（优先级继承/天花板，`28 §3.1`）
```

### 1.2 为什么 capability 核心排第一、调度核心排第二

1. **权限是 Single Point of Failure**：capability 监视器是 Day 1 唯一权限裁决点（`00` A3），其正确性决定整个系统的安全边界；调度核心出错后果是「性能/实时性退化」而非「全局特权失效」。ROI 上 capability 核心证明最值钱（`20 §2.2`）。
2. **capability 核心状态空间极小、纯算法、与硬件无关**（`20 §4.1`），可证明性强；调度核心虽也属 Rust TCB（`68 §7.1`），但其涉及 `arch/timer` 计时精度下限（`28 R9` / `57 T6`）与运行期账本状态，证明须待计时后端接口稳定。
3. **与 `20 §7` 分阶段路线一致**：原型期 Layer A 仅建模不证明，M3 后先启动 capability 窄证明，调度核心移交（`68 Sc9`）排在其后——本文的优先级排序与 `20 §7` 的「先 capability、后扩展」完全对齐。

### 1.3 衔接的边界声明

- 本文**不替 `20` 拍板**「是否进入 Layer A / 投入阈值」（那是 `20 §8` D1 的职责）。
- 本文**不替 `68` 拍板** Sc9（那需大喵架构裁决，见 §7 P1）；本文仅把 Sc9 当作「已声明的移交目标」纳入落地路径。
- `20` 的 I1–I7 命题草案是本文 §2–§5 的**机器可检查命题来源**，本文在其上补「承载范围 / 模块边界 / 工具 / 精化链」，不新造不变量。

## 2. Layer A 可验证小核心（`19 §3.4(A)`）承载范围

### 2.1 承载范围的双层结构

`19 §3.4(A)` 已列出移交 `20` 的三类极小核心：capability 监视器、IPC 端点状态机、rights 检查。`68 §7.2` 补入调度核心。本文据 §1 优先级，把 Layer A 承载范围收敛为**两层、共五类对象**，且明确「每类对象移交的是其抽象规约（状态 / 不变量 / 操作前置后置条件），而非实现源码」：

| 层 | 承载对象（`19 §3.4(A)` / `68 Sc9`） | 来源不变量（`20` I1–I7） | 移交形态 |
|---|---|---|---|
| ① capability 核心 | (a) capability 监视器：句柄表不变量（无悬垂、无伪造）、`revoke` 派生链传播完整性 | I1（无凭空产生）、I2（revoke 断派生）、I7（句柄不可伪造） | 参考模型 + 精化证明 |
| ① capability 核心 | (b) rights 检查：`mint` 收窄（交集语义、防 confused deputy）、运行期位检查正确性 | I3（只减不增）、I5（受约束 mint）、I6（无隐式提权） | 参考模型 + 精化证明 |
| ② 调度核心（`68 Sc9`） | (c) RT 严格优先级选择 + deadline EDF 会计 + Job RT 带宽记账 + 锁协议 | 由 `68 §5` fail-closed 两层语义派生（throttle / terminate），非 `20` I1–I7 但同源 | 参考模型 + 精化证明（M3 后） |
| ① capability 派生/回收（本文聚焦） | (d) capability **派生（duplicate/grant/mint）语义**：派生链构造、rights 沿链单调收窄 | I3 + I5（派生即收窄） | 参考模型 + 精化证明 |
| ① capability 派生/回收（本文聚焦） | (e) capability **结构化取消回收**：Job 树上行 revoke，异常/超限触发，与监督者重启状态机协同 | I2（回收必彻底）+ `00` A9（异常上行） | 参考模型 + 精化证明 |

> 说明：(a)(b) 直接沿用 `19 §3.4(A)` 与 `20 §4.1`；(c) 为 `68 Sc9` 移交；(d)(e) 是本文对 `19 §3.4(A)` 第 (a) 项的**聚焦展开**——把「capability 派生 / 回收」从监视器整体中拆出为独立可证子命题，与 `00` A9 结构化取消、监督者重启状态机（`20` Layer B）焊接。

### 2.2 capability 派生（duplicate / grant / mint）的可证语义

- **派生即收窄**：沿任意 `duplicate`/`grant`/`mint` 路径，`rights(child) ⊆ rights(parent)`（`20` I3）。这是 `07 §4.5` 「无隐式提升」的代数形式。Layer A 须证明：**不存在**任一派生操作使 `rights(out) ⊋ rights(in)`。
- **受约束 mint 防 confused deputy**（`20` I5 / `07` C2）：FS 服务等代理 mint 时，`rights_issued = rights_service ∩ rights_requested_client`。Layer A 须证明 mint 委托人**无法超出自身 authority** 发权——这是 capability 核心证明的高价值子目标，直接封堵 confused deputy。
- **派生链构造可追踪**：默认显式 close（`07 §5-4`、`19` AP-8），derivation 追踪按需开启；Layer A 参考模型覆盖「显式 close 路径下派生句柄的可用性边界」与「derivation 追踪开启时传递闭包回收」。

### 2.3 capability 回收与结构化取消（与 `00` A9 焊接）

- **回收 = 结构化取消的触发源之一**：`68 §5.3` 把「Job CPU 硬上限超限」列为结构化取消触发源（与致命异常并列）；`07 §4.5` 把 `revoke`/`close` 列为句柄回收主操作；二者在「Job 树上行取消」语义下汇合。
- **Layer A 须证明**（接 `20` I2）：对任意句柄 `h`，执行 `Revoke(h)`（或 Job 树因异常/超限触发取消）→ 删除 `h` 及全部 `h'` s.t. `Derive*(h, h')` → 此后 `¬∃ h'. 派生路径经过 h ∧ usable(_, h')`。即「取消必定彻底、无悬垂、无孤儿」。
- **与监督者重启状态机协同**：监督者收到 Job 取消事件后按策略重启/升级（`46`/`47`），其状态机本身归 `20` Layer B（TLA+ 模型检验，`20 §4.2`），Layer A 只证明「取消后派生句柄集合的数学闭合性」，不证重启时序——范围清晰、不与 Layer B 重叠。

### 2.4 不在 Layer A 承载的对象（边界红线）

- 不在：(a) 数据通路（VMO/pager/SHM 字节搬运，`19 §1.2`）、(b) IPC 协议并发时序（归 Layer B TLA+，`20 §4.2`）、(c) 调度器运行期与 `arch/timer` 的耦合（`68 §7.1` 算法同源、后端差异归 §6）、(d) mkit 兼容层（排除出 TCB，归 Layer D fuzz / `22`）、(e) 驱动 / FS 后端（归 Layer D）。
- 纪律：Layer A 承载范围严格受 §1 优先级约束——capability 核心 + `68 Sc9` 调度核心，**不扩张到其余子系统**，与 `20 §4.1`「把最贵的证明留给最小的面」一致。

## 3. proof-carrying 内核模块边界（哪些模块需证明、哪些仅测试）

### 3.1 模块边界矩阵

「proof-carrying」在此指：**模块交付时携带其正确性论证（证明 / 强类型契约 / 测试证据），CI 门禁据模块所属层验收**。据 `20` 四层与 §2 承载范围，给出内核模块的「证明义务」划分：

| 模块 | 所属层 | 证明义务（proof-carrying 要求） | 验收证据形态 |
|---|---|---|---|
| capability 监视器 / rights 检查 | Layer A | **须机器检查证明** | Lean/Coq 精化证明 + 差分测试迹等价（`20 §6.2`） |
| 调度核心（RT 选择 / deadline 会计 / 带宽记账 / 锁协议） | Layer A（`68 Sc9`，M3 后） | **须机器检查证明**（待大喵拍板） | 同上 |
| IPC 端点状态机 | Layer A（`19 §3.4(A)`） | **须证明或强模型检验**（ rendezvous / cap transfer 所有权） | TLA+ 模型 + Rust 精化（`20 §4.2`） |
| 监督者重启 / revoke 时序 / 账本一致性 | Layer B | **模型检验**（TLA+ / `stateright`） | 状态空间穷尽报告 + 可执行模型测试 |
| 全部 Rust TCB 组件（syscall 路由 / VFS / spawn / 账本类型层） | Layer C | **强类型契约**（非 Copy 句柄、`PhantomData<Rights>`、unsafe 白名单） | `deny(clippy::all)` + `forbid(unsafe_op_in_unsafe_fn)` + unsafe 块双人评审（`02 §4.4`） |
| mkit 兼容层（C，排除出 TCB） | Layer D | **仅测试**（不证明） | fuzz（syscall 面）+ sandbox + `22` 否定式回归 |
| 驱动 / FS 后端 / 网络栈协议 | Layer D | **仅测试** | fuzz + 集成测试 + `22` L2 |

### 3.2 proof-carrying 的「携带」形态

- **Layer A 模块**：参考模型（在 Lean/Coq 中）与其 Rust 实现之间的**精化证明**作为模块交付物；CI 门禁在证明脚本随代码同步回归（呼应 `22 §2.2` 结论 3「证明即回归」）。差分测试（`20 §6.2`）作为证明与实现的桥接证据。
- **Layer B 模块**：TLA+ 模型 + 模型检验报告（无死锁、无丢失消息）作为交付物；实现须通过差分测试证明「行为被模型覆盖」。
- **Layer C 模块**：不携带独立证明，但以**编译期类型不变量 + unsafe 审计清单**作为「轻量 proof-carrying」——`02 §5-6` 的 `unsafe` 行数/块数门禁 + `#![forbid(unsafe_op_in_unsafe_fn)]` 即其携带的正确性证据。
- **Layer D 模块**：携带 fuzz 语料 + 否定式测试用例集（`22 §4`）作为交付物，**明确不携带形式化证明**（诚实声明：状态空间大、已隔离在 TCB 外，失效爆炸半径由 Layer C 边界 + 监督者重启兜底）。

### 3.3 边界划定的纪律

- **不越界证明**：Layer A 不外溢到 Layer B/D 模块（§2.4 红线）；Layer D 模块不强行形式化（成本不可承受，`20 §7.4`）。
- **不新增 right 支撑 proof-carrying**：模块边界是「验证手段」划分，不涉及 `07 §4.1` rights 位图（bit 0–47 已冻结，bit 48+ 预留）——本文零新增 right bit。
- **不新增内核原语**：proof-carrying 是**组织/CI 纪律**，不是新内核机制；它对内核 ABI 零侵入。

## 4. 工具链选型（Rust 验证生态 / Lean / Coq 精化；与 `02` Rust 管安全关键路径同源）

### 4.1 选型前提：工具链信任鸿沟（`20 §6`）

- mcc/QBE 与 rustc/LLVM **均未验证**（`02 §2.2` C1、§2.3 C2）。因此「证明到源码级」与「信任编译器」之间存在不可闭合鸿沟（`20 §6.1`）。
- 诚实姿态（`20 §6.2`）：我们不声称证明内核二进制；证明覆盖「参考模型 / Rust 实现是算法精化」，编译器鸿沟由差分测试兜底。
- **选型纪律**：工具链必须为「host 侧、对 Rust 源码/参考模型证明」的工具，**不依赖验证过的 C 编译器**（MeuOS 无 CompCert 式链）。

### 4.2 与 `02` Rust 管安全关键路径同源（核心论点）

`02 §4.2` 确立「关键组件用 Rust、内存安全类缺陷编译期消除、TCB 以 Rust 关键组件为主」；`02 §4.4` 的 unsafe 白名单 + 类型强制是主力控险手段。本文工具链选型**与此同源**：

- 因为 TCB 主体是 Rust（`19 §3.4`、Layer A 承载对象均为 Rust TCB），验证工具应**直接作用于 Rust 源码**——Rust 验证生态（Verus / Kani / Prusti / Crux）与「Rust 管安全关键路径」是同一事实的两面：**用 Rust 写 TCB ⇒ 用 Rust 验证生态证 TCB**。
- 这使 MeuOS 相对 seL4 的杠杆最大化：`20 §2.2` 指出 seL4 花在 C 内存安全证明上的工作量，MeuOS 由 Rust 编译期免费获得；剩余需人证的「权限语义」用 Rust 验证生态精化证明，而非再走 C 证明链。

### 4.3 候选工具与取舍

| 工具 | 形态 | 适用对象 | 取舍 |
|---|---|---|---|
| **Verus**（AWS，Rust 验证 DSL，Dafny-like） | 在 Rust 中嵌入 `spec`/`proof` 注释，生成 Rust 代码 + 证明义务送 SMT | Layer A 的 rights 检查、revoke tree、受约束 mint（纯算法、状态空间小） | **首选**：对 Rust 源码直接验证、与 `02` 同源、SMT 自动、与 `20 §4.1` 极小核心匹配 |
| **Kani**（model checking，Rust） | 有界模型检验 / CBMC 后端，对 Rust 函数做断言证明 | Layer A 的句柄表不变量、派生链收窄、IPC 端点 move/copy 所有权 | **次选/补充**：自动、覆盖 Rust 语义（含 unsafe 边界），适合「无悬垂/无伪造」类断言 |
| **Prusti**（Viper，Rust 过程验证） | 基于 Rust 类型/契约的过程验证 | rights 类型层契约（`PhantomData<Rights>`、`non-Copy` 句柄）的前推证明 | **协同**：与 Layer C 类型强制互补，把类型不变量升为机器检查 |
| **Coq + Rust 提取（或 RefinedRust）** | 交互式证明器，Rust 程序逻辑精化 | 端到端精化证明（`spec → Rust 实现`，§5）、调度核心移交（`68 Sc9`） | **远景/可选**：交互式、可证明最强（seL4 式精化），但人力成本高；适合 M3 后对最贵命题下推 |
| **Lean 4** | 交互式证明器 + 元编程，可定义参考模型并精化 | 参考模型定义（I1–I7 的代数形式）、spec → imp 精化链（§5） | **可选**：作为「参考模型宿主」（类似 `20 §4.1` 建议的 host 侧证明器），与 Coq 二选一 |
| **TLA+ / `stateright`** | 协议级模型检验 | Layer B：IPC 时序、监督者重启状态机、revoke 并发 | **必选（Layer B）**：零运行期开销、`20 §4.2` 已定，与 Layer A 工具正交 |
| **CompCert（对照，非采用）** | 验证过的 C 编译器 | — | **仅作对照**：MeuOS 无此链（`20 §6.1`），不采用；归 `20 §6.2` translation validation 远景 |

### 4.4 选型推荐（落地姿态）

1. **Layer A 主工具：Verus**（对 Rust TCB 直接精化证明）+ **Kani**（自动覆盖句柄/派生类断言）组合。二者均作用于 Rust 源码、与 `02` 同源、不需验证过的 C 编译器。
2. **参考模型宿主：Lean 4 或 Coq（二选一，host 侧）**。承载 I1–I7 的代数形式与端到端精化链（§5）。优先 Lean 4（元编程友好、可定义 MeuOS 权限代数），若团队 Coq 经验更足则选 Coq。
3. **Layer B：TLA+ / `stateright`**（`20 §4.2` 已定），与 Layer A 工具并行不冲突。
4. **拒绝 seL4 全量证明 / 拒绝 translation validation 前置投入**（`20 §7.4` / §6.2）：工具链选型只覆盖「源码/模型级」，不试图闭合到二进制。

### 4.5 工具链选型的待决（见 §7 P2）

- 主工具 Verus vs Kani 的**优先级与分工**，及参考模型宿主 Lean vs Coq，**需大喵在工具链投入上拍板**（涉及人力/学习曲线，关联 `02` C1 双工具链约束）。

## 5. 端到端精化证明落点（spec → 实现精化链；与 `22` 否定式测试互补）

### 5.1 精化链形态（spec → 参考模型 → Rust 实现）

端到端精化证明的落点是一条三级链，每层之间可机器检查「精化关系（simulation / refinement）」：

```
  L0  spec（抽象规约）
      ├─ capability 核心：I1–I7 的代数命题（`20 §5`），以 Lean/Coq 定义
      └─ 调度核心：pick_next 仲裁 / deadline 会计 / 带宽 fail-closed（`68 §3.3/§5`）
            │  ◀── 精化（refinement）：实现行为 ⊆ 规约行为
  L1  参考模型（host 侧，Lean/Coq/Verus spec）
      ├─ 句柄表 + Derive 边 + Rights 序的抽象状态机
      └─ 操作的显式前置/后置条件（mint/grant/revoke/duplicate）
            │  ◀── 精化（simulation）：Rust 实现 step ⟹ 模型 step
  L2  Rust TCB 实现（内核内，禁 unsafe 白名单 + 类型强制）
      ├─ capability 监视器（`07 §4.1`）
      └─ 调度核心（`68 §7.1`）
```

- **落点定义**：「端到端」在此指**从抽象规约到内核 Rust 实现**的精化链，而非「到二进制」（`20 §6.1` 诚实声明）。每级精化关系可被证明器检查。
- **差分测试桥接**（`20 §6.2`）：L1 参考模型与 L2 实现以同一组操作序列驱动，断言可观测迹等价——把「编译器未偷偷改变可观测行为」收缩为差分测试门禁。

### 5.2 与 `22` 否定式测试的互补边界（不重叠）

`22 §4.2` 与 §2.2 结论 3 已声明本文与 `22` 的分工；本文据 §5.1 精化链**显式闭环**这一互补：

| 维度 | `20`/本文（形式化） | `22`（否定式测试） | 互补关系 |
|---|---|---|---|
| 断言方向 | **设计不可违背**（白盒精化：rights 不可伪造、revoke 必彻底） | **实现不回归**（否定式黑盒：越权必 `EPERM`、revoke 后派生句柄不可用） | 前者证「不可能错」，后者证「没改坏」 |
| 对象 | Layer A/B 参考模型 + Rust 实现 | Layer A–D 运行期（尤其非 TCB fuzz 面） | 覆盖不同层，不重叠 |
| 回归机制 | 证明脚本随代码同步回归（「证明即回归」，seL4 范式） | L0–L4 CI 门禁 + 绿光累积（`22 §5`） | 二者门禁并存、互不替代 |
| 成本 | 高（人机交互/证明工程） | 低（经验性、可自动化） | 贵证明守核心、廉价测试守全量 |

- **闭环要点**：`22 §8` 待决项 7（`20` 与经验测试的分工）由本文 §5.2 落定——`22` 负责运行时/黑盒否定式证明，本文/`20` 负责白盒精化证明；fuzz 发现的「revoke 泄漏」类 bug 同时沉淀为 Layer A 须覆盖的不变量（`22 §8` 待决 5），形成「测试发现 → 形式化固化」的反馈环。

### 5.3 精化证明的落地阶段（与 `20 §7` / `11` M0–M6 对齐）

- **原型期（M0–M3）**：仅写 L0 spec + L1 参考模型（capability 核心），**不投证明器**（设计仍可能变动，`20 §7.1`）；同时 `22` L0 单测 + 否定式回归起步。
- **M3 后（设计稳定）**：启动 Layer A 窄证明（Verus/Kani 对 capability 核心 Rust 实现精化），差分测试常态化（`20 §7.2`）。
- **M5/M6+**：若 `68 Sc9` 已拍板，调度核心移交 `20` 精化证明；Lean/Coq 端到端精化链下推到更接近实现（`20 §7.3`）。

## 6. 五架构同源（证明不依赖架构细节；薄后端正确性归约）

### 6.1 核心论断：证明对象与架构无关

- 本文 §2 承载的 Layer A 对象（capability 监视器 / rights 检查 / 调度核心）全部是**架构无关 Rust TCB**（`02 §4.2`、`19 §3.4`、`68 §7.1`）：句柄表、rights 位运算、派生树、EEVDF/deadline 会计、RT 带宽记账均为纯 Rust、与页表/中断/MM 语义解耦。
- 因此**证明不依赖任何架构细节**：五架构上 Layer A 的精化证明是**同一份**——证明一次、五架构共用，与 `22 §6.2` 「64 位五架构 L0 单测一次编写、五架构复用」同源。

### 6.2 薄后端正确性归约（仅每架构验证后端契约）

- **差异只在薄后端**：`arch/timer`（`57`/`28 §6`）、页表封装（`02 §4.2`）、上下文切换 asm、中断分发（`59 §7.6`）是每架构差异点（`00 §5-6` 统一抽象 + 每架构薄后端）。
- **归约方法**：把「架构相关正确性」归约为「薄后端契约」的验证——
  1. 薄后端向架构无关核心暴露**统一抽象接口**（如 `arch_cycle_now()` 归一化纳秒、`Cap(IRQ n)` 统一 cap 面、页表类型化封装）；
  2. 证明只假设「薄后端满足其接口契约」（pre/post 条件），**不展开后端内部**；
  3. 每架构薄后端的契约由该架构专属验证承担（汇编级 review / 模型检验 / `22 §6.3` 等价单测），且范围被统一抽象**收窄到最小面**。
- **i386 纯 C 降级区**（`02` C2）：i386 的 TCB C 实现失去 Rust 类型保护，其薄后端 + C TCB 须额外上模型检验/fuzz 补偿（`20 §6.3`、`22 §6.3`）；但 Layer A 的**证明对象本身仍是架构无关逻辑**，i386 只影响「实现侧可信度」，不要求重写证明。

### 6.3 与 `19`/`68`/`22` 的五架构一致性对齐

- 调度核心五架构同源（`68 §7.1`）：算法一致、计时源差异关进 `arch/timer` 薄后端——Layer A 调度证明只证「算法层」，不计「计时精度下限」（那是 `28 R9`/`57 T6` 实测项，非证明项）。
- capability 核心五架构同源：句柄/rights/派生树无架构分支，与 `22 §6.2` 一致。
- **结论**：五架构同源使「形式化验证」的边际成本极低——核心证明一次投入、`arch/timer` 等薄后端仅每架构验证契约，不重复证明核心逻辑。
