## 0. 核心结论（一句话）

> **MeuOS 的持久化快照与备份是「`.msys` A/B 原子 repoint（`06` §4.3）+ C61-4 引导级恢复指针（`61`）」这一防砖兜底的**上层可枚举资源面**：fs 持久化语义以 crash-consistent 写入 + fsync 经 capability 句柄（复用 `07` rights，不新增 bit）为边界、与 `54`/`55` 方案 A/B 的 VMO+pager 数据通路同构；增量快照以 `03` VMO child（COW 写时复制）为唯一真相源、与 C-G1 `fork_light` 子快照同源（同一 COW 原语、同一大页/多核正确性约束）；备份到外部介质经 `03` device VMO 导出 + `60` 设备能力 + 离线加密（复用 `06` C2 密钥=capability）；快照/备份的 Merkle 根统一进 `.msys` 度量基（`32` §3.2），与 `61` 信任链衔接——全程零新增内核原语、零新增 right bit、五架构同源。**

## 1. 与 `.msys` A/B repoint 及 C61-4 恢复指针衔接（原子切换、防砖兜底）

> 本节把本文件定位为「`.msys` 原子更新机制的上层可枚举资源面」——原子切换的语义与防砖兜底完全复用 `06` §4.3 与 `61` C61-4，本文不重新发明 repoint。

### 1.1 三层「可回滚状态」的同源抽象

`06` §4.3 把 sysroot 更新建模为「子树级快照 + 原子 repoint + 监督协同」，C61-4 把同一 repoint 延伸到引导级（`.mimg` Item 3 携带恢复 `.msys` 指针）。本文件主张：**持久化快照与备份是同一 repoint 抽象在三个粒度上的投影**，共用一套能力切换语义：

| 粒度 | 触发者 | repoint 载体 | 信任前提 | 来源 |
|------|--------|--------------|----------|------|
| **sysroot 级**（`.msys` head Ref） | 监督者（`meu-supervisor`，运行时）/ 引导器（防砖） | 命名空间 `/msys` 别名重绑（`06` §4.3(d)） | 新卷先过 Merkle 度量基（`61` §6.2） | `06` §4.3、C61-4 |
| **应用/用户态快照级**（本文 §3） | 应用/服务经 cap 请求 | 命名空间子树别名重绑到快照子卷 | 同源验签/度量/能力链 | 本文 §3.4 |
| **备份级**（本文 §4，离线/外部介质） | 备份服务经 cap 请求 | 外部介质 device VMO 导出的不可变 Blob 集 | 同源加密/度量（`32` §3.2） | 本文 §4.5 |

> 关键点：**三层的 repoint 都是「一次能力重绑，非多步文件改名」**（`06` §4.3(d) 的 capability 级单点原子切换）。本文不引入第二种原子切换机制——快照/备份的「生效/回滚」就是一次命名空间别名重绑或一个 device VMO 句柄的授予/撤销，与 sysroot repoint 在语义与信任门槛上完全同构。

### 1.2 防砖兜底的上下贯通

- **运行时主路径**：本文的快照/备份均为「sysroot 之上的可枚举资源」，不替代 `06` §4.3 的 sysroot 主更新路径。FS 服务对已挂载 `.msys` 暴露「创建快照 / 导出备份」原语（经 `05` Channel 请求到 FS 服务，FS 服务作为受约束 mint 委托人下发受限句柄，`06` C3 回写），但不决定「何时切」。
- **引导级兜底协同（C61-4）**：当 `.msys` 损坏到 FS 服务都起不来，引导级 A/B slot（`61` §6.2）作最后防线——本文的「备份到外部介质」（`§4`）在引导可达时可被恢复服务消费以重建主 `.msys`，其信任前提与运行时 repoint **完全一致**（同样经 ed25519 验签 + 卷 Merkle 根度量，`32` 跳 3 / `61` §6.3）。**不降级信任**：引导级恢复同样消费 `VERIFY`=bit38，不新增 right bit。
- **非破坏式回退（区别于 APFS revert）**：与 `06` §4.3 一致——旧持有者续持旧能力、新进程/新恢复视图切新状态，无需重启、支持 per-process 灰度。本文快照/备份的回滚同理，撤销新句柄即回退，旧句柄不受影响（`06` 引用澄清「失真 5」已显式标注此差异，本文继承）。

### 1.3 与监督协同（方向②）

快照/备份的生命周期决策（何时建、保留几个、谁可授权恢复）由 `meu-supervisor`（`04`）做出，FS/备份服务只暴露原语：
- 显式命名空间快照的空间占用计入所属 Job 账本（继承 `06` 第七轮 C-G5 回写：显式快照归 supervisor 经 Job 账本管辖）；
- 自动 CoW 版本链 + 不可变 Blob 的 GC 归 FS 服务自管（同 `06` C-G5，不进 Job 账本）；
- 备份集的存储配额同样计入发起备份的 Job（与 `04` 资源账本同构）。

## 2. fs 持久化语义（crash-consistent、fsync 经 capability handle；与 `54`/`55` 方案 A/B）

> 本节只声明持久化语义边界，不替 `54`/`55` 拍板块层格式。两者均建立在 `06` §4.2「CoW + 事务日志保证崩溃一致性、无 fsck」之上，本文把「fsync 如何经 capability 句柄落地」补完。

### 2.1 crash-consistent 写入（继承 `06` §4.5）

- **COW 即事务**：每次写产生不可变 extent 版本（`06` §4.5），元数据以 COW B-tree 事务提交——「最后一次提交的事务要么完整可见、要么不可见」，挂载即一致，无传统 fsck 重放（对齐 APFS/btrfs 的「写时复制即一致性」）。
- **重命名/链接的原子性**：`rename`/硬链接等操作在单次元数据事务内完成，崩溃点落在事务边界之外即无半完成态——这是 fsync 之前「尽量不丢不损」的基础。
- **与 `54`/`55` 同构**：方案 A（内容寻址 Blob 子集，`54` §2）的不可变 extent 版本天然 crash-consistent（写一次即不可变、hash 即指纹）；方案 B（可验证版本链，`55` §2.2）的 per-extent CoW 版本同样 immutable——**两者在「崩溃一致性」上机制同源，本文不引入第三种一致性模型**。

### 2.2 fsync 经 capability handle（不新增 right bit）

- **语义**：`fsync(fd)`/`fdatasync` 在 MeuOS 映射为「对文件 VMO/文件句柄这个 capability 显式发出『落盘并等待完成』请求」。该请求经 `05` 向 FS 服务发，FS 服务作为 pager，把该 VMO 的脏页经 `03` device VMO 刷到块设备能力句柄（`10`/`60`）。
- **权限判定复用 `07` rights**：能 fsync = 持该文件的 `WRITE` right（写后即落盘是 `WRITE` 的语义后果）。**不新增 `FSYNC`/`FDATASYNC` right bit**——与 `06` C2「客户端 unwrap 隐于 READ/WRITE、不新增 bit」同源纪律一致：fsync 是 `WRITE` 句柄的「强制持久化」操作，不是新权限类。
- **capability 层面的顺序保证**：fsync 完成 = FS 服务向客户端回「持久化确认」消息（经 `05` Channel），客户端在收到确认前不认为该写已持久——这与 capability「句柄即授权、消息即完成」模型一致，不需要额外同步原语。
- **与 `54`/`55` 方案 A/B 的接口同一性**：无论底层走 A 的不可变 Blob 提交还是 B 的版本链提交，fsync 对客户端暴露的都是「同一文件句柄 + `WRITE` right + 一次落盘确认」——差异只在 FS 服务内部 extent 归属，对应用透明（`06` C-G5 第七轮裁决已落定「两者经统一命名空间对应用透明并存」）。

### 2.3 范围收口表

| 语义 | 落地 | 复用/不新增 |
|------|------|------------|
| crash-consistent 写入 | COW 事务（`06` §4.5） | 复用，不新增机制 |
| fsync/fdatasync | 文件句柄 `WRITE` right + 落盘确认消息（`05`） | 复用 `07` rights，无新 bit |
| 命名空间 repoint | 子树别名重绑（`06` §4.3） | 复用，不新增切换机制 |
| 加密落盘 | per-extent 密钥=capability（`06` C2） | 复用 `KEY_UNWRAP`/`KEY_WRAP`（服务端），客户端隐于 READ/WRITE |
| 度量 | extent Merkle 根（`32` §3.2） | 复用双锚 |

## 3. 增量快照（VMO 快照 + COW 写时复制；大页/多核正确性；与 C-G1 `fork_light` 子快照同源）

> 本节把「增量快照」定义为 **VMO 层 COW 子（clone）+ FS 层命名空间子树快照** 的协同，二者共用 `03` 的同一 COW 原语，并继承 C-G1 `fork_light` 已识别的大页/多核正确性约束。

### 3.1 两层快照的同一真相源

| 层 | 快照原语 | 触发 | 物理本质 |
|----|----------|------|----------|
| **内存/VMO 层** | `vmo_create_child(COPY_ON_WRITE/SNAPSHOT)`（`03` §4.3.3） | 进程 fork_light / 应用显式请求 | 共享物理页 + 页表写保护 + `MmPage.refcount`，写时惰性复制 |
| **FS/命名空间层** | 命名空间子树 O(1) CoW 快照（`06` §4.3(b)(e)） | 监督/应用经 cap 请求到 FS 服务 | extent 共享 + 写时复制（对齐 APFS clonefile / btrfs subvolume） |

> **同源论断**：VMO 快照与 FS 命名空间快照在「写时复制 + 引用计数 + 惰性复制」上是**同一 COW 抽象在两个平面的投影**。FS 层快照其底层 extent 的不可变性，正是由 `03` 的 `vmo_create_child`/`MmPage.refcount` 单一真相源保障（复用 `03` §5 开放议题「COW 与 VMO child 语义一致性」结论，避免双计数）。本文不引入第三种 COW 实现。

### 3.2 增量语义（与 btrfs/ZFS 思想对齐，但复用已有原语）

- **O(1) 快照创建**：对当前命名空间子树（或某 VMO）做 CoW 克隆，仅复制元数据/页表项，共享未改 extent/物理页——与 `06` §4.3(b) 备份快照同机制。空间随写分化，几乎零额外空间。
- **增量 diff**：快照间差异 = 「被写时复制的 extent/页集合」。因为底层是不可变 extent + 引用计数（`06` C-G5 / `03` refcount），计算两快照间增量只需比对 extent 引用集合的差异（类似 ZFS `zfs diff` / btrfs `send` 的接收端逻辑），无需全量比对。
- **可验证版本链 vs 显式快照**（继承 `06` C-G5 回收纪律）：自动 CoW 版本链由 FS 服务自管、不进 Job 账本；**显式命名空间快照（含本文定义的用户/应用快照）归 supervisor 经 Job 账本管辖**，其引用 extent 的存储计入所属 Job 配额，supervisor 可设 age-out/保留上限，避免空间只增不减。

### 3.3 大页/多核正确性（继承 C-G1 雷区）

`70` §4.3 已把「密集 `fork_light` VMO 子快照 + COW 写时复制/大页/多核正确性」登记为 **C-G1**（源自 `47` §7 议题 1 + `04` §5-2）。本文快照与此**同源同雷区**，逐项对齐：

1. **大页（hugepage）COW 正确性**：快照共享的大页在写时复制时，必须按页内偏移切分为基页粒度复制（不能整大页复制造成空间爆炸，也不能整大页写保护导致误触发）。继承 C-G1 对 `fork_light` 的大页 COW 约束，本文快照复用同一内核页表 COW 机制（`03` §4.3.3），不另设快照专属大页路径。
2. **多核/并发写可见性**：快照创建是「瞬间冻结视图」——创建后对新写的可见性由 COW 保证（旧页不动、新写去新页）。多核并发写同一页时，依赖 `03` refcount 的原子性与页表写保护的 TLB 广播（ASID/PCID，`03` §4.3）保证快照视图一致。本文不引入新的锁，复用 `03` 既有 COW 并发不变量。
3. **TLB/ASID 收敛**：五架构 ASID/PCID 差异（`03` §4.3 / `61` §7.3 表）封死在 `arch/<arch>` 页表层；快照的 COW 语义对五架构一致（`00` A1–A12 同源码异架构）。

### 3.4 快照的命名空间表达（与 C3 每进程 namespace 一致）

- 快照作为命名空间节点（ns-node，类型 = snapshot）暴露，经 C3 的「每进程独立 namespace + 显式 reveal」规则——进程没绑定快照路径则对其「根本不存在」（`06` C3 回写）。
- 应用读快照 = 打开该快照节点 → FS 服务 mint 受限文件/VMO 句柄（受约束 mint，上限 `{READ, EXECUTE}`，含 `WRITE` 仅当该快照被显式标记为可写克隆，`06` C2 回写 constrains mint 封顶）。
- 快照回滚 = 把命名空间别名从「当前」重绑到「某快照」（`§1.1` 三层 repoint 同构），非破坏式。

## 4. 备份到外部介质（device VMO 导出、加密、离线介质；与 `60` 设备驱动）

> 本节把「外部备份」建模为 **device VMO 导出的不可变 Blob 集**，复用 `03` device VMO（不可写）+ `60` 设备能力 + `06` C2 密钥=capability，不引入新内核原语。

### 4.1 device VMO 导出（与 `03`/`60` 协同）

- **备份目标 = 外部块设备/可移动介质的 device VMO**：`60` 设备驱动框架经 capability 网关授予备份服务「目标介质的块设备能力句柄（仅 `READ`/`WRITE`/`block-io` 权，对齐 `06` §4.4.5 / `10`）」。备份服务把本地快照/文件集经 `03` device VMO 导出到该介质——数据通路与网络栈零拷贝（`63` §4.3）同源：VMO 句柄经 `05` cap-transfer 在 FS 服务 ↔ 备份服务 ↔ 设备驱动间传递，bulk 走 VMO、控制走 Channel。
- **离线介质语义**：U 盘/外置 SSD/光盘等离线介质，其 device VMO 在拔出时句柄 `revoke`（`07` §4.5）即回收访问权——与 `03`「revoke 即回收」同构，无需独立卸载协议。
- **五架构差异仅在设备驱动层**：device VMO 抽象屏蔽 USB/NVMe/eMMC 控制器差异（`60`/`10`），备份逻辑本身五架构同源（对齐 `63` §7「仅驱动层差异」）。

### 4.2 增量备份格式（复用 §3 增量 diff）

- 备份集 = 「基准快照 + 增量 extent 差」（`§3.2` 增量 diff 直接复用为备份增量格式），避免每次全量拷贝——与 restic/borg 的「去重 + 增量」思想同源，但建立在 MeuOS 不可变 extent + 内容寻址（`06` C-G5 A 子集、hash=名）之上，去重天然内禀。
- **离线去重**：不可变 Blob 以内容哈希命名（`54` §2），备份到外部介质时重复内容自动去重，空间最优（对齐 Fuchsia blobfs `61` §6.3）。

### 4.3 加密（复用 `06` C2 密钥=capability，无新 bit）

- **静止即密**：备份落到外部介质前，按 `06` §4.2 per-extent 加密（密钥 unwrap 权 = 文件/卷句柄 right）。客户端/备份服务持 `WRITE` 句柄则其写受加密语义覆盖；**密钥材料永不出 FS 服务 pager**（`06` C2 回写），外部介质上只剩密文 + 校验和。
- **离线介质密钥管理**：离线备份的密钥根来自 `07` 的 root-of-trust 能力（与 `.msys` 同源，`32` 跳 1/2）；恢复时由监督者/恢复服务经合法句柄 unwrap，无独立 KRL（revoke 链路经 derivation tree + VMO/pager 回收闭环，`06` C2）。
- **不新增 right bit**：备份加密复用 `KEY_UNWRAP`/`KEY_WRAP`（服务端专用、已冻结，`06` C2），客户端仅以 `READ`/`WRITE` 触发，与运行时文件加密完全同构。

### 4.4 备份的「可验证」属性（与 `32`/`61` 同构）

- 每个备份集带「包级 ed25519 签名 + 卷 Merkle 根」（见 §5），恢复前先验签 + 度量，与 `.msys` 挂载（`32` 跳 3 / `61` §6.3）同一信任门槛。
- 引导级恢复（C61-4）消费该备份集时，同样走 ed25519 + Merkle，不降级信任。

### 4.5 备份生命周期决策（与监督协同）

- 备份集的「保留几个、何时导出、谁可授权恢复」由 `meu-supervisor` 决策（`04`/`06` §4.4.4），备份服务只暴露「导出到 device VMO / 从 device VMO 恢复」原语。
- 备份存储配额计入发起 Job（`04` 资源账本），与快照同构（`§1.3`）。

## 5. 度量/完整性协同（快照/备份 Merkle 根进 `.msys` 度量基；与 `32` §3.2 / `61` 信任链）

> 本节把快照/备份纳入 `32` 度量基双锚，不另造度量体系。

### 5.1 快照/备份的 Merkle 根进度量基

- **复用 `.msys` 双锚（`32` §3.2）**：锚 1 = 包级 ed25519 签名（已有）；锚 2 = 卷 Merkle 根哈希（需补，对齐 dm-verity/AVB）。快照/备份集作为「内容寻址的不可变 Blob 集」（`06` C-G5 / `54` §2），其 Merkle 根由同一官方密钥签名，直接并入 `.msys` 度量基——**不另建度量树**。
- **度量衔接信任链（`61` §5 / `32` §3.1）**：快照/备份在创建时计算 Merkle 根，作为新卷/新 Blob 集的「内容指纹」；当该快照经 repoint 生效（`§1.1`）或备份经恢复生效（`§4.4`）时，其 Merkle 根 extend 进度量累积器（类比 `PCR[3] = extend(hash(.msys volume root))`，`61` §5.3），使「固件→内核→monitor→rootfs→快照/备份」全链可溯。
- **A 不可变子集 hash 兼作启动指纹（`61` §6.3）**：`/msys` 子树即 A 子集（内容寻址 head Ref），其 hash 既是 `.msys` 签名内容指纹，也是该系统快照的基指纹——快照/备份与启动指纹共用同一指纹，度量基不分裂。

### 5.2 防篡改与回滚保护（与 `32` D-SB2/D-SB3 一致）

- **回滚保护（版本号绑 Merkle root，`32` §3.2 / `61` §3.3）**：快照/备份的 Merkle 根绑定版本号，旧版本即使签名有效也被拒（防降级攻击），与 `06` §4.3 同代回退豁免规则一致（监督授权的同代回退豁免于版本防回滚）。
- **防篡改**：extent 级校验和覆盖密文（`06` §4.2）+ 可选文件级 AEAD 认证标签（`06` §4.2.1），快照/备份继承该完整性，篡改块在 pager 供页时被确定性检测。

### 5.3 度量基与 repoint 的闭环

> 一句话闭环：**快照/备份创建的 Merkle 根 → 并入 `.msys` 度量基（`32` §3.2）→ 经 repoint/恢复生效时 extend 进信任链（`61` §5.3）→ 旧视图 revoke 即退出、新视图度量钉入**。全程复用 `32`/`61` 既有度量结构，零新增度量原语。

## 6. 五架构同源；与既有地基同构（不引入新内核原语）

### 6.1 五架构同源收敛

- **快照/备份逻辑五架构二进制一致**：VMO child COW（`03`）、命名空间 repoint（`06` C3）、device VMO 导出（`03`/`60`）、度量（ed25519/Merkle，`32`）均为架构无关抽象。差异**只在设备驱动层**（`60`/`10` 的 USB/NVMe/eMMC 控制器），与 `63` §7「netstack 仅 NIC 驱动层差异」同构。
- **i386 非降级**：i386（档 C 软件可信根，`32` D-SB8 / `61` §7.3）在快照/备份的信任与 COW 机制上与 64 位等价，差异仅在构建管线（`02` C2），不削弱持久化语义。

### 6.2 与既有地基同构（不引入新内核原语 / 不新增 right bit）

| 本文机制 | 复用的既有地基 | 是否新增 |
|----------|----------------|----------|
| 原子切换/回滚 | `06` §4.3 repoint + C61-4 恢复指针 | 否（复用） |
| 增量快照 | `03` `vmo_create_child` COW + `06` 子树 CoW | 否（复用） |
| fsync 落盘 | `07` `WRITE` right + `05` 确认消息 | 否（无新 bit） |
| 备份导出 | `03` device VMO（不可写）+ `60` 设备能力 | 否（复用） |
| 备份加密 | `06` C2 `KEY_UNWRAP`/`KEY_WRAP`（已冻结） | 否（无新 bit） |
| 度量/完整性 | `32` §3.2 双锚 + `61` 信任链 | 否（复用） |
| 大页/多核正确性 | C-G1 `fork_light` COW 约束（`47`/`04`） | 否（复用） |

> **铁律自检**：本文全程未提出任何新内核对象类型、未提出任何新 right bit（bit 49–55 按 `38`/`45`/`70` 纪律冻结区，未被触碰）。所有能力均落在 `00` A1–A12 / C1–C18 / C-G1~C-G5 既定框架内。
