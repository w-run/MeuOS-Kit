## 1. 定位：tracing 数据面 ≠ 调试（与 12 的边界）

### 1.1 为什么 tracing 需要独立成维度

`12` 已把「可观测性」立为一等公民：inspect 树（强类型状态）、事件流（带 schema）、崩溃报告（结构化故障），并把调试权限建模为 `DBG_*` capability（默认全 deny）。但 `12` 的「事件流」只是作为三基元之一被点到，**未下沉到数据面设计**——它没回答：事件从哪来（静态/动态探针）、写往哪（ring buffer 还是 malloc 字符串）、用户态怎么零拷贝消费、always-on 时开销从哪省、与 capability 模型如何既兼容又不牺牲性能。

这正是本维度的独立价值：**tracing 是「持续、低开销、可程序化消费的事件流」**，与 debugging（「按需、高权限、attach 单个目标」）在工程约束上根本不同：

- 调试是**事件驱动、偶发、高特权**（持 `DBG_ATTACH` 才 pause/读内存）——能力检查在每一次操作上发生，性能不是首要约束。
- tracing 是**常驻、低特权订阅、海量吞吐**——消费者只持有 `DBG_TRACE` 订阅权，**每一行事件都不该做 capability 检查**（否则高速路径被拖垮），能力检查只在「订阅建立 / 缓冲区挂载」这一刻发生。

若把两者缝合进同一套机制，要么 tracing 被调试的「每次操作鉴权」拖慢，要么调试被 tracing 的「无鉴权常驻」扯开能力后门。**解构结论：tracing 是独立数据面，与 `12` 的 inspect/崩溃/调试权限三层互补。**

### 1.2 「应该是什么样」（解构型，先于结构）

在「混合内核 + capability 世界 + 用户态服务自治重启 + 五架构统一 TCB」模型下，tracing **应该**：

1. **结构化、语义化、自描述**：事件是带 schema 的强类型记录（如 `sched_switch{old_pid, new_pid, cpu, reason}`），不是 `printk` 文本。任何「人类可读」是追踪数据的**一种渲染**，不是数据源（与 `12` §1.2 同构）。
2. **always-on 而近乎零成本**：未订阅时，一条热点事件的成本应压到「几次指令 + 一次 per-CPU 写」（类别掩码判断 + 无锁环形缓冲写入），**绝不**在 emit 路径做任何 capability 检查、绝不分配、绝不系统调用。
3. **用户态零拷贝消费**：内核把事件写进一块与消费者共享的 ring buffer（VMO mmap），消费者在用户态直接读，内核不拷贝、不 syscall 拉取。
4. **能力仅在订阅侧生效**：emission 无鉴权；但「谁能挂载缓冲区、谁能读跨 Job 的语义事件」受 `DBG_TRACE`/`DBG_PROFILE` capability 约束（与 `07` 同构）。
5. **暴露调度与内存的真实可见性**：调度器（04）的切换/唤醒/运行队列延迟、内存（03）的分配/缺页/CoW/回收，都应作为一等事件类别，而非事后靠 `/proc` 采样反推。
6. **五架构一致**：事件 schema 与架构无关；PMU 差异、回溯差异（见 `12` §4.5）在薄后端吸收，统一事件格式跨 x86_64 / i386 / aarch64 / riscv64 / loongarch64 同构。

### 1.3 本文目标

1. 定义 MeuOS 的 **tracing 数据面**：事件模型（静态/动态探针）、环形缓冲与零拷贝消费、类别式使能。
2. 给出与 **capability 安全模型（07）** 的兼容方案：emit 无鉴权、订阅侧鉴权、语义化数据不泄露跨域内存。

## 2. 参照系统对比（六类，必覆盖）

### 2.1 横向对比表

| 系统 | 事件/探针模型 | 缓冲与用户态消费 | 使能与权限 | 结构化/语义化程度 | 对 MeuOS 的取舍 |
|------|--------------|------------------|-----------|------------------|----------------|
| **Linux ftrace** | 静态 tracepoint（SDT 式）+ 动态 kprobe/function tracer；文本 + 二进制 | 每 CPU 环形缓冲（`ring_buffer`，mmap `trace_pipe`/read） | `tracefs` 文件权限；root 可读写 | 中（tracepoint 强类型，kprobe 任意） | 取「每 CPU ring buffer + 静态 tracepoint」，**不取**文本 tracefs 默认可读 |
| **Linux perf** | `perf_event_open` 采样（PMU/软件/断点）；无持久事件 schema | `perf ring buffer`（mmap，无锁）；`perf.data` | `CAP_PERFMON`/`CAP_SYS_ADMIN` | 低（原始样本，靠外部解析） | 取「mmap 无锁 ring buffer + 采样即一种事件」，**不取**全局 `CAP_PERFMON` 平移 |
| **Linux eBPF** | 动态、可程式化探针；BPF 程序在内核运行、BPF maps 存聚合 | 经 BPF map / ringbuf（mmap）消费 | `CAP_BPF`/`CAP_SYS_ADMIN`；verifier 强约束 | 高（可编程，但模型极重） | **谨慎**：仅长期作为「可选、受约束的可程式聚合」候选，绝不 Day1，且非 Linux eBPF ABI 移植 |
| **Windows ETW** | Provider/Session/Consumer；provider 自描述 manifest；内核+用户 provider 统一 | 内核写进 session 缓冲，实时 forward 给 consumer（或落 .etl） | Session 权限受 ACL/ACL'd handle | **最高**（强 schema、自描述） | **主参考 1**：事件 schema 化 + 会话订阅模型 |
| **macOS Instruments / DTrace** | DTrace：静态 SDT + 动态 FBT + D 脚本聚合；Instruments：kdebug + os_signpost + Time Profiler | DTrace 消费者读；Instruments 经 `ktrace` 缓冲 | 沙箱/权限约束；DTrace 在 macOS 默认移除 | 高（D 聚合 + signpost 语义化） | 取「signpost/os_log 语义化标注 + kdebug 内核事件流」哲学 |
| **Fuchsia tracing** | **类别化（category）结构化事件**：duration / instant / counter / async / flow，强类型 payload | **per-provider 进程内共享缓冲（VMO）+ trace manager 收集** | **类别使能 + provider 注册；consumer 经 trace manager；权限走 capability** | **最高**（自描述 fxt 格式、类别即能力边界近似） | **主参考 2**：类别使能 + per-provider 共享 VMO 缓冲 + trace manager 模型 |
| **Android systrace / atrace / perfetto** | atrace 开启 ftrace + atrace 类别；perfetto 统一多源（ftrace、进程、GPU） | **perfetto 共享内存 ring buffer（in-process shmem）+ traced 守护落盘** | 调试权限（adb/root） | 高（protobuf schema，统一时间线） | 取「共享内存 ring buffer + 多源合并到统一时间线」 |
| **seL4** | 被验证内核**无内建 tracing**；sel4debug 为外部可选扩展 | — | 调试为外部可控能力 | — | 取「**证明与追踪分离**」立场：tracing 设施不进 TCB、不削弱 capability 不变量 |

### 2.2 提炼出的四条铁律（来自对比，非缝合）

1. **结构化 > 文本**（ETW/Fuchsia/perfetto 共识）：事件自带 schema，消费者解析而非 grep。MeuOS 事件用自描述二进制格式（类 Fuchsia fxt / perfetto proto），非 ASCII。
2. **类别使能 > 全局开关**（Fuchsia/perfetto/atrace 共识）：运行时按「类别集合」开启一组事件，未开启类别的 emit 成本为 1–2 条指令的掩码判断。类别天然映射「谁能看什么」——近似 capability 边界，但不替 capability 做鉴权。
3. **每 CPU / 共享内存 ring buffer > 系统调用拉取**（ftrace/perf/perfetto/Fuchsia 共识）：内核只写共享缓冲，消费者 mmap 零拷贝读，避免每条事件一次上下文切换。
4. **证明/验证与追踪分离**（seL4 立场，与 `12` §3.3 同构）：tracing 代码**不进入 TCB**，不持有任何 capability 派生权，不修改被追踪对象的内存安全不变量——这是「emit 无鉴权」能成立的安全底气。

### 2.3 关键差异：emit 侧鉴权与否

| 系统 | emit 是否每次鉴权 | 订阅侧是否鉴权 | 备注 |
|------|------------------|----------------|------|
| Linux ftrace / perf | 否（root 已开 tracefs） | 文件系统权限 | 全局 root 隐含「可读一切」 |
| ETW | 否（provider 无条件写） | Session ACL | 写无鉴权、读靠会话 |
| Fuchsia | 否（provider 无条件写已使能类别） | trace manager 授权 consumer | 写无鉴权、读靠 manager |
| **MeuOS（建议）** | **否（emit 无 capability 检查）** | **挂载缓冲/读跨域事件需 `DBG_TRACE`/`DBG_PROFILE`** | 与 ETW/Fuchsia 同构，且 capability 只在订阅侧生效 |

## 3. 设计原则（解构推演）

### 3.1 事件模型：静态为主，动态为辅

- **静态结构化 tracepoint（Day1 主路径）**：在源码中以声明式宏注册，编译期分配**稳定事件 ID + 强类型 payload schema**（如 `MEU_TRACE(sched_switch, old:u32, new:u32, cpu:u8, reason:u8)`）。稳定 ID 是 ABI 契约——消费者靠 ID + schema 解析，内核升级 payload 字段也向后兼容（新增字段不破坏旧消费者）。热点路径（syscall 进出、调度切换、IPC 收发、缺页、异常）一律用静态点。
  - **优势**：零解析歧义、编译期类型检查、可常驻 always-on、开销可预测。直接对标 Linux tracepoint 与 Fuchsia 静态事件。
- **动态探针（长期，非 Day1）**：对标 kprobe/FBT/DTrace，允许在任意指令边界挂点。风险高（需内核地址空间写权限、稳定性、被滥用为后门），故**严格受 `KERNEL_PRIV`（07，bit 11）门控**，且只在内核诊断模式（非生产默认）可用。
- **不引入 Linux eBPF 式内核程式化（Day1 及可预见长期均不采）**：eBPF 的 verifier + JIT + maps 是一整套「在内核跑用户代码」的巨型机制，攻击面巨大、与「最小 TCB / 证明与追踪分离（§2.3 铁律 4）」正面冲突。**若未来确需可编程聚合**，应走「用户态 trace manager 内做流式聚合」或「受严格约束的、MeuOS 自研的轻量 safe-aggregator（绝不暴露指针/任意内存）」，而非 Linux eBPF ABI 移植（与 `23-ABI稳定性`「保留破坏权」、V1「不提供 KVM ABI」同构的「不背 ABI 债务」立场）。

### 3.2 缓冲与零拷贝消费模型

```
           内核态（per-CPU 写者）                  用户态（消费者）
┌─────────────────────────────┐         ┌─────────────────────────────┐
│ per-CPU ring buffer (VMO)   │  mmap   │  meu-trace 消费者           │
│  ├─ cpu0 buf  ──────────────┼────────>│  直接读共享 VMO，零拷贝     │
│  ├─ cpu1 buf  ──────────────┼────────>│  (同一块物理页，内核写用户读)│
│  └─ cpuN buf  ──────────────┼────────>│                             │
│  写者：无锁、只追尾指针       │         │  按 (cpu, seq) 排序合并     │
│  emit: 类别掩码? → 写记录    │         │  → 全局时间线 → 导出格式    │
└─────────────────────────────┘         └─────────────────────────────┘
        ↑ 缓冲区本身是 VMO（capability 对象）
        ↑ 挂载/读需持目标 job/process/内核的 DBG_TRACE handle（订阅侧鉴权）
```

- **每 CPU 环形缓冲**：避免跨核锁（对标 ftrace/perf per-CPU buffer）。写者只推进本地尾指针，单生产者（内核写者）单消费者（该 CPU 的消费者线程）模型可做到无锁。
- **共享 VMO + mmap 零拷贝**：缓冲区由内核以 VMO 形式创建，消费者持 `DBG_TRACE` handle 经 IPC 获得该 VMO 的映射权（`MAP` right），mmap 进自身地址空间直接读。内核**不**在每次事件做 copy_to_user（对标 perf ring buffer / perfetto shmem / Fuchsia per-provider VMO）。
- **两种写满策略**：① overwrite（环形覆盖最旧，适合 always-on 生产追踪，丢旧保新）；② discard（写满即丢新，保完整片段，适合调试采样）。Day1 用 overwrite（更契合 always-on）。
- **全局时间戳**：每 CPU 缓冲带本地单调时钟；消费者合并时以「(cpu_id, 序列号, 全局时钟)** 三元组排序，得到统一时间线（对标 perfetto 多源合并）。

### 3.3 类别使能与订阅协议

- 事件按**类别（category）**分组：`sched`、`ipc`、`mem`、`syscall`、`io`、`exception`、`net` 等。每个类别有全局 per-CPU 的「使能掩码」。
- emit 路径：`if (enabled_mask[category] & BUFFER_ATTACHED) { write_record(); }` —— 典型 1–2 条指令（位测试 + 条件跳），**无函数调用、无分配、无 capability 检查**。
- 使能切换：消费者持 `DBG_TRACE` 向内核请求「开启类别集合 + 挂载 VMO 缓冲」，内核更新 per-CPU 掩码并绑定缓冲。关闭同理。**能力检查只在此刻发生**，之后海量事件零鉴权流动。
- 这把「谁能看什么」的语义钉在 capability（`DBG_TRACE` 挂在哪个 job/process/kernel handle 上），而「哪类事件在流」由类别掩码表达——二者正交、互不污染（呼应 §2.3 铁律 2/3）。

### 3.4 profiling（采样）作为「一类特殊事件」

- HW 计数器（PMU / PMUv3 / HPM，跨架构差异见 §6）采样**不**单独造一套管道：采样命中时，内核写一条 `sample` 事件进**同一个** per-CPU ring buffer（或同类专用采样缓冲），payload 含 `(pc, cpu, period, callchain[])`。
- 使能采样需 `DBG_PROFILE` capability（07，deny-by-default，侧信道风险中），与 `DBG_TRACE` 区分——读流 vs 采样本就是两种权限（与 `12` §4.2 / C9 同构）。
- 采样权也**只在订阅侧鉴权**；采样命中后的事件写入同样走无锁 ring buffer，不拖慢被采样任务。

## 4. 事件与缓冲模型（MeuOS 推荐方案）

### 4.1 事件格式（自描述、稳定 ID）

```
TraceRecord {
  event_id:   u16        // 编译期分配，稳定 ABI；schema 由单独元数据段描述
  category:   u8         // sched/ipc/mem/syscall/io/exception/net/...
  flags:      u8         // 0=instant 1=duration-begin 2=duration-end
                         // 3=async 4=flow 5=sample(perf) 6=counter
  timestamp:  u64        // 本地单调时钟
  cpu:        u8
  payload_len:u16
  payload:    bytes      // 强类型字段，依 event_id 的 schema 解释
}
```

- **元数据自描述**：内核在构建期导出一份「`event_id → 字段类型/名称`」schema 表（类似 Fuchsia fxt 的声明、perfetto 的 proto descriptor、ETW 的 manifest）。消费者拿到 schema 即可解析任意事件，无需与内核版本硬绑定——这是「结构化优于文本」的落地。
- **稳定 ID 是契约**：新增字段只允许**追加**到 payload 尾部，旧消费者忽略未知尾部字段；**禁止**重用/改义旧 ID（与 `23-ABI稳定性` 的「保留破坏权」在内部事件 ABI 上取「尽量稳定、破坏需升版」的务实立场）。

### 4.2 与 inspect（12）/ 崩溃报告（12）的三面互补

```
  ┌──────────── 流数据面（本文）───────────┐
  │  持续事件流（sched/ipc/mem/syscall...）   │  → 回答「系统正在发生什么（时序）」
  └────────────────────────────────────────┘
  ┌──────────── 状态面（12 inspect 树）──────┐
  │  层次化强类型快照（kernel/jobs/services） │  → 回答「系统此刻是什么样（状态）」
  └────────────────────────────────────────┘
  ┌──────────── 故障面（12 CrashReport）─────┐
  │  统一结构化崩溃报告 → exception channel   │  → 回答「哪里坏了（失败）」
  └────────────────────────────────────────┘
        三者全经 capability 守护（DBG_TRACE/INSPECT/CRASHDUMP），无全局可读
```

- trace 是**时序维度**、inspect 是**状态维度**、crash 是**失败维度**；三者经 `05` Channel/EventPort 同源传输、权限随 handle 走（与 `12` §4.4 一致）。本文不重复 inspect/crash 设计，只在缓冲与权限层面与其对齐。

### 4.3 调度可见性（对接 04-进程与调度）

暴露为一等事件类别 `sched`（均走静态 tracepoint，常驻低开销）：

| 事件 | payload 示例 | 用途 |
|------|-------------|------|
| `sched_switch` | `{cpu, old_pid, new_pid, old_prio, new_prio, reason}` | 上下文切换因果、CPU 时间归属 Job（接 04 Job 账本） |
| `sched_wakeup` | `{cpu, pid, target_cpu, prio}` | 唤醒延迟、调度时延瓶颈 |
| `sched_block` | `{cpu, pid, reason}` | 阻塞原因分布 |
| `runq_latency` | `{cpu, pid, waited_ns}` | 运行队列等待尾延迟（接 `19` 性能门禁 / `28` 实时性） |
| `cpu_migrate` | `{pid, from_cpu, to_cpu}` | 负载均衡、NUMA 亲和（接 04 §5.6） |

- 这些事件直接喂给 `04` 的 Job 账本可视化与 EEVDF/RT 调度类性能分析；always-on 时它们是「调度器公开账本」，不需 cgroups 式事后采样。

### 4.4 内存可见性（对接 03-内存管理）

暴露为类别 `mem`：

| 事件 | payload 示例 | 用途 |
|------|-------------|------|
| `page_alloc` / `page_free` | `{order, vmo_id, flags}` | buddy/SLUB 吞吐、碎片（接 03 §5.3） |
| `page_fault` | `{vaddr, pid, kind:minor/major}` | 缺页来源、pager 往返开销（接 06 §6-4） |
| `vmo_cow` | `{vmo_id, vaddr, old_page, new_page}` | CoW 写时复制热点（接 03 §5.2） |
| `vmo_map` / `vmo_unmap` | `{vmo_id, vmflags}` | 地址空间生命周期 |
| `reclaim` | `{pressure, reclaimed_pages, target}` | 回收压力、OOM 前兆（接 04 §5.5 OOM 归因） |

- 内存事件同样常驻、零拷贝；它们是 `03` 内部不变量（refcount 单一真相源、CoW 语义）的**外部可观测投影**，但不反向修改 MM 不变量（满足 §2.3 铁律 4「证明与追踪分离」）。

### 4.5 profiling / HW counter（对接 12 §7-8、07）

- PMU 抽象为** capability 对象**（per `12` §7-8 待决项）：不同架构 PMU/PMUv3/HPM 的差异由每架构薄后端吸收，向上暴露统一的「采样配置 handle」。
- 采样事件 `sample` 写入 ring buffer，payload 含 `(pc, cpu, period, callchain[])`；callchain 经 `12` §4.5 的统一 in-kernel unwinder 展开（五架构共用抽象）。
- 使能需 `DBG_PROFILE`（deny-by-default，侧信道风险中），与 `DBG_TRACE` 分离。

## 5. 安全与能力边界（对接 07-安全模型）

### 5.1 核心命题：emit 无鉴权，订阅侧鉴权

这是 tracing 与 `12` 调试模型最大的工程分野，也是与 capability 模型兼容的关键：

- **emit 路径零 capability 检查**：热点事件每秒可达成百万级，若每次做 `handle→rights` 校验将直接拖垮系统。MeuOS 选择「内核无条件写已使能类别的事件进共享缓冲」（与 ETW/Fuchsia 同构，§2.3）。
- **能力仅在「挂载缓冲 / 读跨域事件」时校验**：消费者须持目标的 `DBG_TRACE` handle（挂在某 process / job / 内核 inspect-root handle 上），经 `05` IPC 获得该 ring buffer VMO 的 `MAP` right。无 handle 即无缓冲区、无数据。
- **与 `07` 同源**：`DBG_TRACE`/`DBG_PROFILE` 是 `07` rights 位图中 deny-by-default 的调试权（见 `07` 第三轮回写 C9 六 right 表），无「追踪 root」、无全局可读；dev/prod 差异由 spawn/Job manifest 的 `debug_policy`（`deny`/`same-job`/`dev-session`，见 `12` R3-5）声明，**非全局开关**（否决「系统 trace 模式」逃生舱，与 C4 沙箱默认 deny 同理）。

### 5.2 隐私边界：语义化数据不泄露跨域内存

- trace 事件是**结构化语义字段**（如 `pid`、`vaddr`、`reason`），**不是**原始内存 dump。即使持 `DBG_TRACE`，也不因此获得读他人地址空间之权——那仍归 `DBG_ATTACH`/`DBG_POKE`（`12` C9/C10）。
- **敏感字段默认脱敏**：任何可能跨 Job 泄露信息的 payload（如用户态缓冲区内容、密钥句柄值）默认**不**进事件；确需时须目标对象显式 `DBG_INSPECT` 授权且字段白名单化（对标 macOS `os_log` 隐私 redaction、`12` §3.1 os_log 取舍）。
- **内核内部地址**：`KERNEL_PRIV`（07 bit 11）持有者的诊断追踪可带内核地址；普通 `DBG_TRACE` 消费者看到的 kernel 类事件只含符号化后的语义字段（pc 可经符号表映射为符号，但原始地址对无 `KERNEL_PRIV` 者隐匿）。

### 5.3 追踪设施不进 TCB（seL4 立场的落地）

- tracing 代码路径**不持有**任何 capability 派生/撤销权、不修改被追踪对象内存安全不变量、不在热点路径引入可被利用的状态。它只是「旁路观察者」。
- 即便 tracing 子系统自身有 bug，也**不能**成为提权或 capability 逃逸的通道（缓冲区是受 `MAP` right 约束的 VMO，写者不能借 tracing 越权读他人内存）——满足 §2.3 铁律 4「证明与追踪分离」。

### 5.4 与 Linux 兼容层（规划中 08）的关系

| Linux 期望 | MeuOS 等价（capability 友好） |
|-----------|-------------------------------|
| `strace`（跟踪某进程 syscall） | `DBG_TRACE` 订阅 `syscall` 类别事件（比 ptrace 单步陷阱更干净、更低开销，见 `12` §4.6） |
| `perf record/report` | `DBG_PROFILE` 采样 → `sample` 事件 → 同一导出管线 |
| `ftrace` 函数图 | 长期经静态 tracepoint + 动态探针（`KERNEL_PRIV` 门控）近似，非 Day1 |
| `/proc` 时序统计 | 由 `sched`/`mem` 事件在用户态聚合得出，非内核维护文本文件 |

## 6. 跨架构一致性（五架构）

| 架构 | 时间源 | PMU 抽象 | 回溯（callchain） | 缓冲实现 |
|------|--------|----------|------------------|----------|
| x86_64 | TSC | PMU（Intel/AMD 统一抽象层） | DWARF `.eh_frame`（见 `12` §4.5） | 统一 per-CPU VMO ring buffer |
| i386 | 低频时钟/TSC（若无） | legacy PMU 薄后端 | DWARF + cdecl 栈帧 | 同上 |
| aarch64 | CNTVCT / generic timer | PMUv3 抽象层 | DWARF ARM EH | 同上 |
| riscv64 | rdtime（mtime） | 标准 HPM 抽象层 | DWARF | 同上 |
| loongarch64 | 稳定计数器 | 自有 HPM 薄后端 | DWARF（LoongArch 约定） | 同上 |

- **事件 schema 与架构无关**：所有 payload 用中性整数/枚举，架构相关量（如 PMU 事件号）在每架构薄后端翻译为统一语义事件，消费者只看统一字段（呼应 `01` §5.6 五架构一致性成本议题、与 `12` §4.5 统一 unwinder 同构）。
- **统一抽象 + 每架构薄后端**：ring buffer 写入逻辑、类别掩码、导出格式全架构共用一份实现；仅「时钟读数 / PMU 配置 / 回溯」三处提供每架构薄后端，避免「每种架构一套追踪代码散落」。

## 7. Day1 最小可用集 vs 长期目标

### 7.1 Day1 最小可用集（与 M0–M2 里程碑对齐）

**内核侧（Rust/C 混合，入 TCB 仅缓冲与 emit 薄层）：**
1. 每 CPU ring buffer（VMO 支持，overwrite 模式，无锁单生产者单消费者）。
2. 类别使能掩码 + 挂载/卸载协议（需 `DBG_TRACE` handle 鉴权于订阅侧）。
3. **静态 tracepoint 最小集**：`syscall_enter` / `syscall_exit`、`sched_switch`、`exception`（接 `12` 统一崩溃入口）、`ipc_send`/`ipc_recv`（接 `05`）。
4. 自描述 schema 元数据段（构建期导出）。

**用户态侧（最小 meu-trace 消费者，复用 `11` 联调通道）：**
5. 持 `DBG_TRACE` 挂载缓冲、按 `(cpu, seq)` 合并、导出为最简文本/二进制转储。
6. 在 QEMU 下经串口 / 9p（`11` §4.3）把追踪转储吐到宿主侧，作为 bring-up 期统一可观测面（与 `12` §4.8 gdbstub+串口+9p 联调闭环同构）。

**Day1 明确不做**：profiling/HW counter 采样（留待 7.2）、动态探针（留待 7.2）、GUI/Instruments 式可视化、eBPF 式可编程、持久化长追踪落盘。

### 7.2 演进路径（长期目标）

```
Day1  ── 静态 tracepoint 最小集 + per-CPU VMO ring buffer + 串口/9p 转储
  │
  ▼
L2    ── 完整类别集（sched/ipc/mem/syscall/io/exception/net）+ 用户态 trace manager
  │         （meu-trace 守护收集多 CPU 缓冲、合并时间线、导出 fxt/perfetto 式格式）
  ▼
L3    ── profiling（DBG_PROFILE）+ HW counter 抽象（五架构 PMU 统一）
  │         + 用户态流式聚合（可选 safe-aggregator，非 eBPF）
  ▼
L4    ── always-on 生产级低开销追踪（类 continuous profiling / GWP）
  │         + Fuchsia 式 async/flow 事件（因果链可视化，跨 IPC/进程）
  ▼
L5    ── 动态探针（KERNEL_PRIV 门控，仅诊断模式）+ 长追踪持久化（落 .msys，
           接 12 §4.7 校验/加密）+ 与 inspect/crash 三面联动分析工具
```

- **profiling 与动态探针后置的理由**：HW counter 跨架构差异大（`12` §7-8 待决），动态探针引入稳定性/安全面风险，二者均非自举必需；ring buffer 与静态点先就位，可为后续采样事件直接复用同一管线（§4.4 profiling 即「一类特殊事件」）。
- **绝不背 ABI 债务**：导出格式自描述、事件 ID 稳定；即便长期引入可编程聚合，也走 MeuOS 自研受约束方案，不移植 Linux eBPF ABI（与 V1「不提供 KVM ABI」、`23`「保留破坏权」一致）。

## 8. 自主结论（非缝合怪总结）

1. **tracing 是独立数据面，与 `12` 互补**：流（时序）/ inspect（状态）/ crash（失败）三面正交，全经 capability 守护，不缝合进调试器。
2. **emit 无鉴权、订阅侧鉴权**：热点事件零 capability 检查（1–2 指令掩码判断），`DBG_TRACE`/`DBG_PROFILE` 只在挂载缓冲/读跨域时校验——这是与 capability 模型（07）兼容且保住低开销的唯一窄路。
3. **静态结构化 tracepoint 为主、动态探针为辅且 `KERNEL_PRIV` 门控**：稳定事件 ID + 强类型 schema 是 ABI 契约；eBPF 式内核程式化 Day1 及可预见长期**不采**，若需聚合走用户态或受约束自研方案。
4. **每 CPU VMO ring buffer + mmap 零拷贝**：对标 ftrace/perf/perfetto/Fuchsia 共识；写满用 overwrite（always-on 生产友好）。
5. **类别使能近似能力边界但不替 capability 鉴权**：运行时按类别集合开事件流，权限语义由 handle 上的 `DBG_*` right 最终裁定。
6. **调度（04）/ 内存（03）可见性是一等事件类别**：`sched_*`/`mem_*` 常驻低开销，是 Job 账本与 MM 不变量的外部可观测投影，且不反向修改不变量（seL4 式证明与追踪分离）。
7. **五架构一致**：事件 schema 中性、PMU/时钟/回溯差异在薄后端吸收；统一 ring buffer 实现跨 x86_64/i386/aarch64/riscv64/loongarch64 同构。
8. **Day1 只做最小集**：静态点 + VMO ring buffer + 串口/9p 转储；profiling、动态探针、GUI、长追踪落盘均后置，但管线已为它们预留（sample 即一类事件）。
9. **隐私边界**：trace 是语义字段非内存 dump；跨 Job 敏感字段默认脱敏，原始内核地址对无 `KERNEL_PRIV` 者隐匿。

## 10. 待决清单（含架构裁决）

1. **【架构裁决】`sample` 事件与 `DBG_TRACE` 同缓冲还是分缓冲**：建议同缓冲（简化管线、统一时间线），但 profiling 的 `DBG_PROFILE` 鉴权独立——即「缓冲共享、使能权独立」。需 team-lead 在合成 pass 与 `07`/`12` 协同定稿 rights bit 归属（`DBG_PROFILE` 已在 `07` C9 表内，bit 待冻结）。
2. **【架构裁决】动态探针是否最终纳入及门控强度**：本文建议 `KERNEL_PRIV`（07 bit 11）门控、仅内核诊断模式可用、非生产默认。需 `07`/`29-威胁模型` 协同确认「动态探针」是否在威胁模型内列为 `KERNEL_PRIV` 子类。
3. **事件 ID 与 schema 的版本/兼容策略**：稳定 ID 是 ABI 契约，但「内部事件 ABI」是否纳入 `23-ABI稳定性` 的「保留破坏权」范围？建议：内部事件 ABI 取「尽量稳定、破坏需升版并附迁移说明」的务实立场，不享对外 ABI 的「任意破坏权」。
4. **perfetto / fxt / 自研格式的选择**：导出格式是兼容生态（perfetto 生态工具）还是自研紧凑格式（类 fxt）？建议长期对齐 perfetto proto（生态复用最大），Day1 可用最简二进制转储过渡。
5. **长追踪落 `.msys` 的触发与开销**：always-on 生产追踪的落盘（L5）何时触发、是否受 `DBG_CRASHDUMP` 约束（与 `12` §4.7 同介质同校验链）？建议落盘事件经 `DBG_TRACE` 持有者策略决定，复用 `.msys` 校验/加密。
6. **跨架构 PMU 统一抽象成本**：`12` §7-8 已列 HW counter capability 暴露面为待决；本文建议 PMU 差异在每架构薄后端吸收、向上暴露统一采样配置 handle，具体抽象层设计待原型评估。
7. **与 inspect 树（12）的重复/边界**：trace 是流、`sched_*`/`mem_*` 事件是否也镜像进 inspect 树作状态快照？建议：inspect 树放「聚合后状态」、trace 放「原始时序」，二者由 meu-trace 在用户态联动，内核不双写。
