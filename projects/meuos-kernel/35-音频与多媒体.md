## 1. 「应该是什么样」推演（解构型）

### 1.1 总纲：在 capability 世界、用户态驱动、实时要求下，音频「应该」是什么样

先不问「MeuOS 现在能多低延迟」，而问「在『重服务出核 + capability Day 1 + 用户态驱动』的务实混合内核下，一个**音频子系统应该**如何既低延迟又隔离——应用不直接持音频全局能力——并与 `28` 实时性天然协同」。

推演起点——MeuOS 已定架构（`00`/`01`/`07`/`10`/`28`）：

- 安全模型 = capability Day 1 唯一模型；句柄即 capability，无 root 逃生舱（`07` §4.1）。
- 驱动模型 = 双轨（内核快速路径 + 用户态隔离服务）+ 能力网关（`10` §4.1）；设备资源（MMIO/IRQ/DMA）作为 capability 经能力网关下发（`10` §2.4/§4.6）。
- 实时性 = 严格优先级（0–31）+ Zircon 式 deadline 双子类 RT 域；关键路径数据通路留核（VMO/SHM 直连、零 IPC）免疫 IPC 击穿（`28` §3.2）。
- 内存 = VMO/VMAR 作为对用户态/兼容层暴露的 capability 视图；device 内存走不可写 device VMO（`03` §4.4 + C1 折中 C 采纳）。

由此推演出理想音频画像的七条（解构型基线）：

1. **音频服务是用户态系统服务（类比 AudioFlinger / Fuchsia audio_core），而非内核子系统**。混音、路由、音量、策略（哪个应用能播、能否录音）全部在用户态 `audio-service` 中决策；内核只保留「机制」：VMO 零拷贝数据通路、RT 调度接入点、设备能力下发。这与 `00` 方向③「尽快交权用户态缩 TCB」、FS/网络全部出核同构。
2. **应用不直接持音频全局能力，只持「音频流句柄（stream handle）」与（可选地）「设备句柄（device handle）」**。应用向 `audio-service` 请求一条播放/录音流，得到的是受 `rights` 约束的 stream capability（如「只能写 48kHz 双声道播放缓冲」），而非任何 HW 寄存器访问权。这与 `07`「权限随句柄走、应用不持 root 设备 cap」直接同构——音频 HW 注册访问权只留在用户态音频驱动（`10` 能力网关下发），混音服务只持 stream 级 cap。
3. **音频缓冲走 VMO/SHM 零拷贝**：生产者（应用 RT 回调）与消费者（`audio-service`/音频驱动）映射同一 VMO 环形缓冲，数据平面零 IPC（`28` §3.2 数据通路留核原则）。麦克风采样、扬声器播放的样本在 VMO 内流转，不经 Channel 往返。
4. **低延迟路径借 `28` 的 RT 域 + 数据通路留核 + mlock 消缺页**：音频回调是典型的硬 RT 用例（macOS Core Audio、Android AAudio 均用 RT 线程）。音频流可声明为 RT 流（需 `CAP_RT`，见 `28` §4.1），其回调线程进入 RT 域、缓冲区在准入期 `mlock` 固定（`28` §5.1），采样周期（如 5.3ms / 256 帧 @48kHz）远 ≥ `28` §1.3 划定的「数十 µs」硬 RT 可达边界——**现在就该承诺**。
5. **麦克风等敏感设备默认 deny，需显式授权（隐私即 capability）**。麦克风/摄像头本质与「调试权 `DBG_*`、文件密钥 `KEY_*`」同构——是**高风险、默认拒绝**的 capability。应用录音须持 `AUDIO_CAPTURE` right（本文建议新增，对齐 `07` `DBG_*`/`KEY_*` 同构的「默认 deny + 显式授予」），与 `07` pledge 越界即终止语义同源。系统策略（谁能在何时录音、是否亮灯指示）由 `audio-service` 集中裁决，杜绝「任意应用直采麦克风」。
6. **音频 HW 驱动走 `10` 用户态驱动双轨 + 能力网关**：声卡（如 virtio-sound、HDA、USB audio）作为用户态音频驱动，经能力网关持 MMIO/IRQ/DMA capability（`10` §4.6）；其内部与 HW 的数据交换（DMA 描述符环、采样缓冲）用 device VMO（`03` C1 折中 C）。音频驱动不直接对每个应用暴露，而是只与 `audio-service` 对接——应用永不接触声卡原始 cap。
7. **多媒体（视频/编解码）复用同一「用户态服务 + capability + VMO」骨架**：视频合成（compositor）、编解码（codec）是 CPU/GPU/专用加速器上的用户态服务，帧缓冲/码流走 VMO/SHM；与显示（14）、用户态驱动（10）、GPU（待建）协同。本文聚焦音频为主、多媒体为延伸视角，避免与显示子系统（14）重复——显示/合成归 14，音频/媒体管线归本文。

### 1.2 解构型反问：为什么音频在 MeuOS 下比 Linux 更该「出核」

- **Linux（ALSA/PulseAudio/PipeWire）**：内核 `snd` 子系统持全部声卡能力；PulseAudio/PipeWire 在用户态做混音策略，但应用常直接 `open("/dev/snd/...")` 持 HW 设备节点（`plughw` 直连），权限靠 `/dev/snd/*` 的 Unix 文件权限位 + 组成员（audio group）粗粒度控制。麦克风隐私靠 `audio` 组 + 桌面策略守护（如 `xdg-desktop-portal`），**无内核级 capability 强制**——任意在 `audio` 组的进程可直采。
- **MeuOS 的差异化**：把 Linux 的「`audio` 组 + 文件权限位」替换为**内核级 `AUDIO_*` capability**（默认 deny、显式授予、可撤销、与 `DBG_*`/`KEY_*` 同构）。应用绝不直接持声卡 cap；混音策略在用户态 `audio-service` 且可重启（故障域小）。这是 capability 模型在音频隐私上的最高价值点，与 `07` 方向③互锁。

### 1.3 音频低延迟与 `28` RT 的可达边界映射

`28` §1.3 锚定硬 RT 可达边界 =「数据通路留核 + 周期 ≥ 数十 µs + mlock + 非剥夺短临界区」。映射到音频：

- 典型音频周期 5.3ms（256 帧 @48kHz）、2.7ms（128 帧）、乃至 1.3ms（64 帧）——均 ≥ 数十 µs 量级，**完全落在 MeuOS 现在就该承诺的 RT 域内**。
- 音频回调数据平面走 VMO 环形缓冲（零 IPC），控制平面（建流、改音量、路由切换）走 Channel/EventPort IPC，不进入硬截止期预算（`28` §3.2 原则 2 直接适用）。
- 结论先行：**音频低延迟（≤10ms 甚至 ≤5ms 端到端）是 `28` RT 域的天然受益者，不应另造一套延迟机制**——只须把音频流接入 `28` 已定的 RT 预算 + VMO 留核 + mlock。

### 2.2 取舍结论

- **拒绝**「应用直持声卡设备节点（Linux `/dev/snd` plughw 模式）」：这与 `07` Day 1 唯一 capability 模型根本冲突（应用持 HW MMIO 即绕过一切权限策略）。声卡 cap 只下发给用户态音频驱动，驱动只与 `audio-service` 对接。
- **采纳** Fuchsia/Android 的「三层分离」：①用户态 `audio-service`（混音/路由/隐私策略）②用户态音频驱动（经 `10` 能力网关）③低延迟直连路径（AAudio 式、VMO 共享 + RT 域）。三者经 VMO/SHM 与 Channel 协作。
- **采纳** macOS TCC / Android permission 的「麦克风默认 deny、显式授权」——落地为 `07` rights 位图新增 `AUDIO_CAPTURE`（与 `DBG_*`/`KEY_*` 同构的默认 deny right），隐私即 capability。
- **跟踪** seL4 式「音频数据通路端到端可验证」作为长期目标（与 `07` §4.4 形式化路径、`20` 形式化方法呼应）；原型期不强制，但接口设计须预留（VMO + cap 委托的不变量的可验证性）。

## 3. MeuOS 音频/多媒体模型

### 3.1 总体架构：用户态服务 + capability + VMO + RT 协同

```
┌──────────────────────────────────────────────────────────────────┐
│  应用进程（音频生产者/消费者）                                       │
│   持：stream capability（受 rights 约束，如「写 48k 双声道播放」）  │
│   不持：任何声卡 HW cap                                            │
│   RT 音频回调线程（可选，需 CAP_RT）→ 写/读 VMO 环形缓冲           │
├─────────── Channel/EventPort（控制平面：建流/路由/音量）───────────┤
│  用户态 audio-service（混音/路由/隐私策略，可重启）                  │
│   - 持 stream cap 的「服务侧」视图 + 与音频驱动的 device cap 对接   │
│   - 麦克风 capture 需应用持 AUDIO_CAPTURE right，服务集中裁决        │
│   - 常驻 + mlock + RT 优先级（混音器自身是 RT 任务，见 28 §3.2.3） │
├─────────── VMO/SHM 环形缓冲（数据平面，零 IPC）────────────────────┤
│  用户态音频驱动（经 10 能力网关持声卡 MMIO/IRQ/DMA capability）      │
│   - 设备数据经 device VMO（03 C1 折中 C）与 audio-service 共享缓冲  │
│   - 敏感的采样完成/完成中断留核（28 §3.3）或轮询+零拷贝（10 §5-1） │
└──────────────────────────────────────────────────────────────────┘
```

- **数据平面（零 IPC）**：应用 RT 回调 ↔ `audio-service` ↔ 音频驱动，三者映射同一 VMO 环形缓冲链；就绪通知用 EventPort `CHAN` filter 或轮询（`28` §3.2 原则 1）。**不走 `channel_call`**。
- **控制平面（低频 IPC）**：建流、路由切换、音量、设备热插拔通知走 Channel/EventPort，发生在 RT 周期之外（`28` §3.2 原则 2）。

### 3.2 capability 化：stream/device 句柄即 capability，麦克风默认 deny

与 `07` 句柄即 capability、rights 位图同源，本文建议在 `07` rights 位图新增音频类 right（对齐 `DBG_*`/`KEY_*` 的「默认 deny + 显式授予 + 永不随其他 right 自动获得」）：

| right | 建议 bit | 含义 | 默认 | 同构对象 |
|-------|----------|------|------|----------|
| `AUDIO_PLAYBACK` | 11 | 请求播放流（持 stream cap 写缓冲） | deny | 基础能力 |
| `AUDIO_CAPTURE` | 12 | 请求录音流（麦克风采集，**隐私敏感**） | **deny** | `DBG_ATTACH`/`DBG_POKE` 同级风险 |
| `AUDIO_DEVICE_MGMT` | 13 | 枚举/选择音频设备、设默认路由（策略权） | deny | `CFG_*` 同构 |
| `AUDIO_UNMUTE` / `AUDIO_BYPASS_MIX` | 14 | 独占模式/绕混音直连 HW（低延迟路径授权） | deny | `CAP_RT` 同构（高权限） |

- **麦克风隐私即 capability**：`AUDIO_CAPTURE` 与 `DBG_*`/`KEY_*` 同构——默认 deny，应用须在 spawn/Job manifest 声明或运行时经 `audio-service` 显式授权；授权时 `audio-service` 可强制「录音指示」（如系统级亮灯/通知）后再 mint 受限 stream cap。无 `AUDIO_CAPTURE` 的应用调用录音 API 直接 `EPERM`（fail-closed，对齐 `07` pledge 越界即终止）。
- **stream 句柄 = 受限 capability**：`audio-service` 发给应用的 stream handle 带 `rights`（如只能写特定格式/设备/时长的播放缓冲），应用无法借此越权访问其他设备/流。与 `07` §4.5「句柄复制只能收窄」一致。
- **声卡 HW cap 永不发给应用**：声卡 MMIO/IRQ/DMA capability 经 `10` 能力网关只下发给用户态音频驱动；音频驱动与 `audio-service` 间经受 `GRANT` 约束的 device cap 对接。应用持的是 stream cap，不是 device cap——与 `07` §4.1「无 root 设备 cap」同构。

### 3.3 VMO/SHM 零拷贝数据通路（接 03/05）

- **环形缓冲 = 共享 VMO**：每条音频流对应一个 VMO（由 `audio-service` 创建或驱动侧 device VMO 共享），应用侧映射为 producer/consumer 环形缓冲；多 client 混音时 `audio-service` 在中间层持各 client VMO + 一个 master VMO（`03` §4.4 VMO 即命名空间对象）。
- **就绪通知 = EventPort**：缓冲水位经 EventPort `CHAN`/`USER` filter 通知 RT 回调，或 RT 回调轮询 head/tail（lock-free SPSC/MPSC，对齐 `28` §3.2.1）。不走 `channel_call`。
- **与 `03` device VMO 协同**：音频驱动的 DMA 采样缓冲 = `03` C1 折中 C 的 device VMO（不可写，由驱动持有），与 `audio-service` 的 master VMO 经内核 pager/映射共享（数据通路留核，零拷贝）。

### 3.4 低延迟路径与 `28` RT 协同

- **RT 流接入 `28` RT 域**：低延迟音频流（如 AAudio 式独占、音乐制作、游戏）可申请 RT 回调线程——需 `CAP_RT`（`28` §4.1），进入严格优先级或 deadline 子类（`28` §3.1）。音频周期（≥ 数十 µs）落在 `28` 硬 RT 可达边界内。
- **mlock 消缺页**：RT 流缓冲区与其 VMO 在准入期 `mlock` 固定（`28` §5.1，对应 `03` 页帧 `RT_LOCKED`），运行期禁缺页。
- **混音器自身是常驻 RT 任务**：`audio-service` 的混音线程以常驻 + mlock + RT 优先级形态存在（`28` §3.2.3），其数据平面同样 VMO 化，避免把 RT 应用拖入 IPC 抖动。
- **敏感中断留核**：采样完成/DMA 完成中断由内核态快速路径派发到音频 RT 线程（`28` §3.3/§3.2.4），不经理 `10` 的中断转发 IPC。

### 3.5 多媒体（视频/编解码）延伸视角

- 复用同一骨架：视频合成（compositor）、编解码（codec）为**用户态服务**，帧缓冲/码流走 VMO/SHM；与 `14`（显示）协同——显示/合成归 `14`，媒体管线（解码、采集、跨应用媒体路由）归本文。
- 编解码加速器（GPU/VPU/DSP）作为用户态驱动经 `10` 能力网关持设备 cap；媒体服务持受约束的 device cap，应用持 stream cap。
- 摄像头（video capture）的隐私授权与麦克风同构：同样走默认 deny 的 `AUDIO_CAPTURE` 式能力（建议扩展为 `MEDIA_CAPTURE` 或复用 `AUDIO_CAPTURE` 语义位），不在此展开细节。

### 3.6 五架构差异初步策略

音频/多媒体对架构差异的敏感度低于 RT 时钟源，但 DMA/IOMMU 与中断控制器差异仍影响音频驱动与 VMO 通路：

| 架构 | 音频/多媒体相关差异 | 对本文模型的影响 | 协同点 |
|------|---------------------|------------------|--------|
| **x86_64** | HDA/USB-Audio 成熟；IOMMU（VT-d）强制隔离 DMA；APIC 中断 | 音频驱动走 `10` 用户态 + VT-d 域；最佳基线 | `10` §5-2 强制 IOMMU、C8 撤销锁 |
| **aarch64** | 板载音频编解码（I2S/codec）+ USB；SMMU 等价 IOMMU；GIC 中断 | 与 x86_64 同构；设备树（DT）描述音频 codec（`10` §2.3） | DT 枚举 → 能力网关下发（`10` §4.3） |
| **riscv64** | 平台音频差异大（多为 USB/PCIe 声卡或定制 codec）；IOMMU 依平台 | 原型期以 virtio-sound（QEMU）为主（`10` 附录 A virtio 思路），规避物理codec 差异 | virtio 抽象（`10` §附录 A） |
| **loongarch64** | 自有体系，音频后端待验 | M5（`11` §5-4）后移，先保证正确；音频非 M0 阻塞项 | 同 riscv64 先 virtio-sound |
| **i386** | 无 Rust TCB、纯 C（`02` C2）；老硬件音频 | 非音频重点架构；音频驱动可用 C（对齐 `10` §4.4「C 仅用于遗留适配」） | `02` C2 / `10` §4.4 |

**核心论断**：五架构的音频差异集中在「声卡枚举来源（DT/ACPI/PCIe）+ IOMMU 隔离 + 中断控制器」，全部已由 `10` 双轨驱动 + 能力网关 + C8 撤销锁覆盖——本文模型在五架构上**无需新增架构特例**，只需音频驱动接入 `10` 既有的设备能力下发与 VMO 通路。原型期首选 **virtio-sound**（跨架构一致、避免物理 codec 碎片化），物理 HDA/codec 作演进。

## 4. 与 03 / 05 / 10 / 28 的接口

| 本文件诉求 | 接入点 | 契约 |
|---|---|---|
| 音频缓冲 = 共享 VMO | `03` §4.4 VMO 即命名空间对象 + C1 折中 C（device VMO 不可写） | 每条流一个 VMO（或 device VMO 共享）；stream cap 携带该 VMO 的 map/读写 right；device VMO 不可写（防应用改 HW 缓冲） |
| 缓冲零拷贝映射 | `03` §3.3 VMO/VMAR 分层 + §4.3 mmap | `audio-service`/应用/驱动 map 同一 VMO；VMAR 层级权限收敛（应用只 RW 其流缓冲，禁 EXEC） |
| RT 流 mlock | `03` §4.3 缺页 + `28` §5.1（mlock 式固定） | RT 音频流缓冲区与其 VMO 在准入期 `RT_LOCKED` 固定，运行期禁缺页 |
| 控制平面 IPC | `05` §4.1 Channel + §4.2 EventPort + §4.4 Service Registry | `audio-service` 经 Service Registry 注册；应用 `service_connect` 后 `channel_call` 建流；水位就绪走 EventPort `CHAN` filter（不走 `channel_call` 数据面） |
| 大数据零拷贝 = SHM cap transfer | `05` §4.3 SHM + cap transfer | 音频 VMO 句柄经 Channel 消息 cap_transfer 发给应用（类比 Binder 大数据零拷贝，`05` §3.3） |
| 声卡设备能力下发 | `10` §2.4/§4.6 capability 约束驱动 + C8 撤销锁 | 声卡 MMIO/IRQ/DMA capability 经能力网关只下发给用户态音频驱动；驱动只与 `audio-service` 对接，应用永持 device cap |
| 用户态音频驱动 RT 改造 | `10` §4.2/§5-1 双轨驱动 + `28` §5.2 | 音频驱动做 RT 时须轮询 + 零拷贝 + lock-free 环形缓冲 + 禁分配/禁长锁；敏感中断留核 |
| 低延迟 = RT 域 | `28` §3.1 RT 域 + §4.1 `CAP_RT` + §4.2 Job RT 预算 | 低延迟音频流申请 RT 回调线程需 `CAP_RT`；音频周期进 RT 预算（QNX APS 式带宽预留）；与 `28` §7.1 结论一致 |
| 隐私 = capability | `07` §4.1 rights 位图 + §4.2 fail-closed | 新增 `AUDIO_CAPTURE`/`AUDIO_PLAYBACK`/`AUDIO_DEVICE_MGMT`/`AUDIO_UNMUTE` right（默认 deny，与 `DBG_*`/`KEY_*`/`CFG_*` 同构）；麦克风无授权直接 `EPERM` |
| 音频服务可重启/故障域 | `00` 方向③ + `10` RS 看门狗 | `audio-service` 为用户态可重启服务；崩溃由 meu-supervisor 重启，不拖内核（对齐 `10` §4.2 用户态服务） |

### 4.1 与 `00` 总览的互锁

- **方向③（尽快交权用户态缩 TCB）**：音频服务化是 FS/网络出核后的自然延伸；声卡驱动出核（`10`）与音频策略出核（本文）共同压缩内核 TCB。
- **A1/A7/A8（capability 即句柄 / VMO 零拷贝 / IPC 统一）**：本文的 stream cap、VMO 缓冲、Channel/EventPort 控制面分别落在这三条已对齐地基上，无新范式。
- **C8（设备能力撤销锁）**：音频驱动的设备 cap 回收走 C8 撤销锁序列（IRQ 屏蔽 → 冻结 → IOMMU 失效 → revoke → 回收），与 `10` §第三轮回写一致。

## 5. 自主结论 + 待决项（标注是否需架构裁决）

### 5.1 自主结论

1. **音频服务是用户态系统服务（`audio-service` 混音/路由/隐私策略 + 用户态音频驱动经 `10` 能力网关）**，不内建内核音频子系统；与 `00` 方向③、FS/网络出核同构——故障域小、可重启、TCB 小。
2. **应用只持 stream/device capability 句柄，绝不持声卡 HW cap**——声卡 MMIO/IRQ/DMA 经 `10` 能力网关只下发给音频驱动；与 `07`「无 root 设备 cap」同构，杜绝 Linux `/dev/snd` plughw 直连式粗授权。
3. **音频缓冲走 VMO/SHM 零拷贝**：数据平面（应用 RT 回调 ↔ 服务 ↔ 驱动）映射同一 VMO 环形缓冲、走 EventPort/轮询就绪，不走 `channel_call`；直接复用 `03` VMO + `05` SHM cap transfer，无新机制。
4. **低延迟路径完全借 `28` RT 域，不另造延迟机制**：音频周期（≥ 数十 µs）落在 `28` 硬 RT 可达边界内；RT 流需 `CAP_RT` + mlock 固定缓冲 + 敏感中断留核，与 `28` §3/§5 一致。
5. **麦克风隐私即 capability**：新增 `AUDIO_CAPTURE`（与 `DBG_*`/`KEY_*` 同构）默认 deny、显式授权益、fail-closed；录音指示由 `audio-service` 集中裁决——这是 capability 模型在音频上的最高价值点。
6. **多媒体（视频/编解码）复用同一骨架**，与 `14`（显示）分工：媒体管线（采集/解码/路由）归本文，显示/合成归 `14`；摄像头隐私授权与麦克风同构。
7. **五架构无需新增音频特例**：差异（DT/ACPI 枚举、IOMMU、中断控制器）已由 `10` 双轨驱动 + C8 撤销锁覆盖；原型期首选 virtio-sound 跨架构一致，物理 HDA/codec 演进。
