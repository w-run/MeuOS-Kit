# 17 - 裁决：调试与兼容（C9 / C10）

> 裁决员：kernel-plan 第二轮架构裁决（general-purpose-10，lite / hy3）。
> 输入：本轮已落盘的 `00-总览与路线图.md`、`12-调试与可观测性.md`、`08-Linux兼容层.md`、`07-安全模型.md`、`04-进程与调度.md`。
> 性质：**架构裁决建议**——针对 C9（调试↔安全/进程）与 C10（兼容↔调试）两个架构级冲突给出明确推荐，供大喵最终拍板。后续可修订式追加，不删。

## 0. 一句话结论（先给答案）

- **C9-A（调试 capability 粒度与默认）**：维持 12 提出的 5 个 `DBG_*` right，但**将 `DBG_ATTACH` 拆出最高风险子权限 `DBG_POKE`（内存/寄存器改写）**——构成 6 个 right；**mkit 与 glibc 程序默认完全一致：全 deny**；开发态/生产态差异**不靠全局开关**，而靠 spawn/Job manifest 的 `debug_policy` 声明属性（对齐 Android `debuggable`、macOS `get-task-allow` entitlement）。
- **C9-B（exception channel 消费者仲裁）**：异常事件**内核一次性生成、多播（fan-out）给所有注册消费者（copy 语义）**；**监督者持 `DBG_CRASHDUMP` 默认订阅权、其 kill/restart 决策不可被抑制**；调试器持 `DBG_ATTACH` 仅收到副本、可请求**有界「崩溃冻结窗口」**（`crash freeze`，超时/ detach 自动释放）暂缓重启，但**绝不可永久接管崩溃、绝不可阻断监督者兜底面**。
- **C10（ptrace 支持边界）**：选**第三档——提供真 ptrace 式原语但全部受 capability 守护**；单步/读内存/读寄存器/读栈**归入 `DBG_ATTACH`**；**任意内存改写= `DBG_POKE`，永不默认、永不捆绑进 `DBG_ATTACH`、须显式授予**；`strace` 由事件订阅等价实现，`gdb/lldb` 在 `DBG_ATTACH` 下可观测/单步、仅「写断点/set 变量」需 `DBG_POKE`；**原型期以 QEMU gdbstub 作为完整调试能力的替代通道**（调试权位于 VM 边界，不进入 MeuOS capability 模型）。

## 1. 「应该是什么样」——推演（解构型思维）

在「混合内核 + capability Day 1 唯一模型 + spawn/Job 监督自治重启 + 信号简化为异常 channel」的底座上，先抛开 Linux 现状，推演调试与兼容**应该**长什么样：

### 1.1 调试权限的「应然」形态
- 权限**不是身份而是令牌**：谁调试谁，取决于调试者持有目标对象的哪种 `DBG_*` right——不存在「同 uid 默认可 ptrace」或「perf 全局采样」这类隐式全局权（Linux 的反面教材，见 07 §3.1）。
- **默认拒绝是 capability 模型的自洽要求**：spawn 出的进程不持任何 `DBG_*` right，与「无 root、无隐式权限」同源（07 §4.1 A12 一致）。
- **风险分层**：「读/观察」与「改写」是两种不可混淆的权。改写目标内存/寄存器等于获得一个**针对他人地址空间的任意写后门**——在 capability 世界这是最高危权限，必须被**单列、显式、可审计、绝不默认**。这正是 C10 中「不给出任意内存改写逃生舱」的应然解法：**把改写权从 attach 权中剥离出来**。
- **开发态不是「放宽内核」，而是「声明属性」**：参照 Android `debuggable`（manifest 标志，决定 adb 能否 debug）与 macOS `get-task-allow`（entitlement，决定 task_for_pid 能否授权），开发友好性应当是一个**写在 spawn/Job manifest 里的声明属性**，而非一个全局「系统处于 dev 模式」开关（后者等于一个 root 等价逃生舱，违背 07 铁律）。

### 1.2 异常 channel 的「应然」形态
- 致命异常是**一个结构化事件**，由内核故障入口一次性生成，应当可以被**多个关心方同时收到副本**（监督者要决策、调试器要观察），而不是「谁先抢到谁独占」。
- **监督者是进程的所有者/重启决策者**，其 kill/restart/升级策略是**主决策、不可被第三方抑制**——否则自治重启（04 §4.5）被调试器架空，系统自愈能力被破坏。
- **调试器的真实刚需**：调试 crash loop 时，确实需要「先别重启，让我看现场」。但这是「暂缓」而非「接管」——应当是**有界的、可被收回的、不破坏监督者兜底权**的冻结，而不是 Linux ptrace 那种「attach 即吞掉默认信号处置」的独占式接管（Zircon 的 exception 处理也是 bounded resume/handle，超时会回到系统默认）。

### 1.3 兼容层 ptrace 的「应然」形态
- 兼容层**不默认授予调试权**（与 08 D1「Linux 二进制默认不绕过沙箱」同构）：`ptrace` 在 MeuOS 内部没有「全局默认」对应物。
- **可等价实现的部分**（事件订阅/只读 introspect）应当真支持；**不可等价的部分**（单步、内存改写）要么作为受 `DBG_*` 守护的原生能力提供，要么显式 `ENOSYS`（08 §7「翻译/不翻译」原则）。
- 关键认知修正：**单步执行（single-step）并非「只能靠事件订阅」或「完全不可等价」**——它是内核让目标线程在每条指令处停下的**原生控制能力**，属「观察/控制」而非「改写」，应归入 `DBG_ATTACH`（read-side），无需 `DBG_POKE`。12 §7-7 的担忧（单步无法经事件订阅等价）成立，但解法是「提供受 `DBG_ATTACH` 守护的真单步原语」，而非「干脆不支持」。

## 2. 选项对比表（含多系统参照）

### 2.1 C9-A：调试 capability 粒度与默认

| 维度 | Linux（反面） | Fuchsia/Zircon | Android | macOS(XNU) | seL4 | **MeuOS 推荐裁决** |
|------|---------------|----------------|---------|-----------|------|-------------------|
| 粒度 | `ptrace` 全局 + `CAP_PERFMON` 过宽 | debug handle 单一对象，right 随 handle | `debuggable` 标志位（粗） | `get-task-allow` entitlement（中） | 外部可选 capability | **6 right：`DBG_INSPECT/TRACE/PROFILE/ATTACH/POKE/CRASHDUMP`**；ATTACH 与 POKE 分离 |
| 默认（一般程序） | 同 uid 默认可 ptrace；perf 历史过宽 | 需显式授予 debug handle | `debuggable=false` 默认不可 | 无 entitlement 默认不可 | 默认无 | **全 deny：mkit 与 glibc 一致，spawn 不持任何 `DBG_*`** |
| 开发态 vs 生产态 | 无区分（靠 uid） | 无区分（靠授权） | `debuggable` 由 manifest 决定 | entitlement 由签名决定 | 无 | **靠 spawn/Job manifest `debug_policy`：`deny` / `same-job` / `dev-session`，非全局开关** |
| 内存改写权 | `ptrace(POKEDATA)` 随 attach 即得 | 无独立写权（调试器 controlled by channel） | 无 | 无独立写权 | 无 | **`DBG_POKE` 单列、绝不进 ATTACH、绝不默认** |

> 多系统参照结论：Fuchsia 把「调试即 capability」做到极致但粒度偏粗（debug handle 一体）；Android/macOS 用**声明属性**区分 dev/prod 的思路最值得借鉴。MeuOS 取其「capability + 声明属性」并补上「改写权单列」这一 capability 世界必需的刀刃细分。

### 2.2 C9-B：exception channel 消费者仲裁

| 维度 | Linux(ptrace) | Zircon exception | macOS(WER/崩溃报告) | **MeuOS 推荐裁决** |
|------|---------------|------------------|---------------------|-------------------|
| 谁收异常 | ptrace 父独占，可吞掉默认处置 | exception 经 channel 上报 job 监督者；debugger 经 handle 介入 | 崩溃报告上报系统，开发者可取副本 | **内核一次性生成、多播副本给监督者 + 持权调试器** |
| 默认处理能否被抑制 | 父进程可 `PTRACE_CONT` 吞掉信号 | 超时会回到系统默认处理 | 系统策略主导 | **监督者决策不可抑制；调试器仅可请求有界冻结** |
| 调试器能否「接管」崩溃阻止重启 | 能（attach 即阻止默认） | 否（bounded handle，超时回默认） | 否 | **否；仅「有界崩溃冻结窗口」，超时/ detach 自动释放，监督者兜底仍成立** |
| 调试器读现场 | 直接读 | 经 debug handle 读 | 经 entitlement 读 | **读副本，不阻断监督者落盘/重启** |

### 2.3 C10：ptrace 支持边界

| 档位 | 含义 | strace | gdb 观测/单步/backtrace | gdb 写断点/set 变量 | 工具链体验 | **裁决** |
|------|------|--------|------------------------|--------------------|-----------|---------|
| A 完全不支持 ptrace | 仅事件订阅 | 可（事件订阅） | 不可 | 不可 | 差（gdb 基本不可用） | 否决 |
| B 仅只读 introspect 子集 | 读寄存器/内存，无单步/无写 | 可 | 部分（无单步） | 不可 | 中（缺单步伤体验） | 否决（单步应原生支持） |
| **C 真 ptrace + capability 守护** | 单步/读写受 `DBG_ATTACH`，写受 `DBG_POKE` | 可（事件订阅，更优） | **可（DBG_ATTACH）** | **可（需 DBG_POKE）** | **好（观测全开，改写需授权）** | **选定** |

> QEMU gdbstub（11 §4.3）作为**原型期替代**：调试权位于 VM 边界（谁控制 QEMU 谁有完整调试力），不进入 MeuOS capability 模型——故原型/内核 bring-up 阶段开发者拿到的调试体验与 Linux gdb 等价，且不污染内部模型。

## 3. 明确推荐裁决

### 3.1 C9-A 推荐：rights 清单与默认矩阵

**（1）right 清单（6 个，在 12 的 5 个基础上拆出 `DBG_POKE`）**

| right | 含义 | 风险级 | 挂载对象 | 默认 |
|-------|------|--------|----------|------|
| `DBG_INSPECT` | 读 inspect 树（可按子树粒度授权） | 低 | 目标进程/Job/kernel inspect root handle | deny |
| `DBG_TRACE` | 订阅事件流 / syscall trace | 低 | 目标进程 handle | deny |
| `DBG_PROFILE` | 请求 HW counter 采样（侧信道风险，见 12 §7-8） | 中（侧信道） | PMU capability 对象 | deny |
| `DBG_ATTACH` | attach 交互式调试器：暂停/单步/读寄存器/读内存/设观察点 | 高（控制+读） | 目标进程 handle | deny |
| `DBG_POKE` | **改写目标内存 / 写寄存器 / 写断点（in-process 修改）** | **最高（任意写后门）** | 目标进程 handle | **deny，且绝不随 ATTACH 自动获得** |
| `DBG_CRASHDUMP` | 读取/持久化崩溃报告 | 中（含内存快照） | crashreport 对象 | 监督者对其监督 Job **默认持有**（见 C9-B） |

> 粒度裁决说明：5 个过粗（把"改写"藏进 ATTACH 等于默认送后门），过多（每个 syscall 一类）会崩塌易用性。6 个 right 中**唯一新增的 `DBG_POKE` 是 C10 安全性问题的钥匙**——它把"任意内存改写"从 attach 中剥离，使"读/单步观测"与"改写"成为两个可被独立授予/审计的权限。

**（2）默认矩阵**

| 场景 | 默认 `DBG_*` 持有情况 | 说明 |
|------|----------------------|------|
| 生产态 spawn 任意进程（mkit 或 glibc） | **全 deny** | capability 模型自洽，无调试 root |
| 开发态、由 dev 工具链（持 debug-issuer 权）拉起 | 调试器（同 dev session）经 issuer 获 `DBG_ATTACH`(+`DBG_TRACE`/`INSPECT`) | mkit 与 glibc **一致**，差异来自 `debug_policy` 而非程序类型 |
| 开发态需要写断点/set 变量 | 需 issuer **额外**显式授 `DBG_POKE` | 即便 dev 也不自动给；可审计 |
| 监督者（meu-supervisor） | 对其监督 Job 默认持 `DBG_CRASHDUMP`（决策所需） | 不持 `DBG_ATTACH`/`DBG_POKE`——监督者不顺便成调试器 |

**（3）dev/prod 差异机制：`debug_policy`（声明属性，非全局开关）**

- 写在 spawn/Job manifest：`deny`（默认，生产）｜`same-job`（同 Job 树内进程可相互 attach）｜`dev-session`（指定 dev-session issuer 可 attach）。
- **强烈否决**全局「系统 dev 模式」开关：那是一个 root 等价逃生舱，违背 07 铁律（与 C4「沙箱默认 deny」同理）。
- `same-job` / `dev-session` 仍是**显式授予**（由持 `GRANT` 的 issuer 在 spawn 时绑定），非隐式权限——符合 07 §4.5「无隐式提升」。

### 3.2 C9-B 推荐：exception channel 仲裁规则

明确规则（按优先级）：

1. **生成一次、多播副本**：内核故障入口生成唯一 `CrashReport`，以 **copy 语义 fan-out** 给所有注册消费者（监督者 + 持权调试器）。不存在「谁先抢到独占」。
2. **监督者决策不可抑制**：meu-supervisor 持 `DBG_CRASHDUMP` 默认订阅权，其 kill / dump+restart / 升级决策是**主决策、最终决策**；任何调试器不得取消、不得改写该决策。
3. **调试器只读副本**：持 `DBG_ATTACH` 的调试器收到 `CrashReport` 副本并可 inspect/step 冻结中的进程，但**不阻断**监督者落盘与（冻结外的）重启。
4. **有界崩溃冻结窗口（crash freeze）**：调试器可**请求**冻结以暂缓重启（调试 crash loop 刚需），约束：
   - 须持 `DBG_ATTACH`；
   - **有界**：超时（默认建议 30–120s，待拍板）后自动解除，或由 supervisor 策略配置上限；
   - **自动释放**：调试器 detach / 崩溃，冻结立即解除；
   - 冻结解除后监督者按其策略执行——**自治重启不变量永不破坏**。
5. **无永久接管**：调试器**绝不能**以「持有 ATTACH」为由永久阻止重启；若需更长停摆，必须由持权方显式续期（仍受上限约束），且监督者始终保留兜底权。

> 与多系统对齐：Zircon exception 的 bounded handle + 系统默认回退、macOS WER 系统策略主导，均支持此模型；Linux ptrace「attach 即吞默认处置」的独占式接管**不采纳**。

### 3.3 C10 推荐：支持档位与实现边界

**选定档位 C——真 ptrace 式原语 + capability 守护**，具体边界：

| 操作 | 所需 right | MeuOS 支持性 |
|------|-----------|--------------|
| 读寄存器 / 读内存 / 读栈 | `DBG_ATTACH` | 支持 |
| 单步执行（arch 调试寄存器/trap flag 停每条指令） | `DBG_ATTACH` | **支持**（原生控制能力，非事件订阅） |
| 设观察点 / 读断点（纯观察） | `DBG_ATTACH` | 支持 |
| syscall trace（strace 等价） | `DBG_TRACE`（事件订阅，更优） | 支持，且优于 ptrace 变种 |
| **写内存 / 写寄存器 / 写断点（patch 代码）** | **`DBG_POKE`** | **支持，但须显式授予；缺则 `EPERM`** |
| perf 采样 | `DBG_PROFILE` | 支持（HW counter 为 capability 对象） |

**如何在不给「任意内存改写逃生舱」前提下实现**：关键即 3.1 的 `DBG_POKE` 单列——内核 ptrace 原语对所有**写操作**单独校验 `DBG_POKE`；无此 right 的调试器（仅有 `DBG_ATTACH`）得到**完整读/单步/观测**能力但**无法改写**，因此不存在"attach 即得任意写"的后门。改写权永不在 `DBG_ATTACH` 内、永不默认、授予可审计、可随时 revoke（07 §4.5 derivation tree）。

**工具链可用性影响**：
- `strace`：经 `DBG_TRACE` 事件订阅**完全等价甚至更优**（开销低、语义干净）。
- `gdb/lldb`：在 `DBG_ATTACH` 下**可读/回溯/单步/观测**——覆盖绝大多数调试工作流；仅「写断点插入指令」「`set variable`/`print x=...`」需 `DBG_POKE`，缺失时这些具体操作返回 `EPERM` 但 gdb 仍可加载与观测。
- **QEMU gdbstub（11 §4.3）作为原型期替代**：内核 bring-up 与 mkit 程序开发阶段，经 QEMU gdbstub 获得**完整**调试力（含内存写），因为该调试权位于 VM 边界、由 QEMU 控制方持有，**不进入 MeuOS capability 模型**。原型期开发体验与 Linux gdb 等价；生产 in-guest 调试则回到 capability 守护模型（ATTACH 级默认、POKE 级需授权）。

## 5. 风险与退路

| 风险 | 影响 | 缓解 / 退路 |
|------|------|------------|
| right 过多伤易用性 | 开发者需逐个申请 | 用 `debug_policy` + `debug-issuer` 让 dev 工具链一次性批量授权；生产仍 deny。无需人工逐个 juggle。 |
| `DBG_POKE` 成新后门 | 持权者改写任意进程内存 | 永不默认、永不捆绑 ATTACH、授予可审计、可 revoke；与 `CAP_SYS_ADMIN` 教训（07 §3.1）对照——把它**显式单列**正是避免「大杂烩」的反面。 |
| 崩溃冻结窗口拖垮自治重启 | 调试器挂着导致进程永不重启 | 有界超时 + detach 自动释放 + 监督者兜底权；冻结不是所有权转移。 |
| `DBG_PROFILE` 侧信道（Spectre 类） | 采样泄露跨进程数据 | 原型期 `DBG_PROFILE` 限定同 Job 内；跨 Job 采样需更高权，待 12 §7-8 评估。 |
| 原生 ptrace 写路径实现复杂 | 阻塞原型进度 | **退路**：原型期只走 QEMU gdbstub（档位 C 的 VM 边界版）+ `DBG_TRACE`/`DBG_INSPECT` 只读子集；`DBG_POKE` 与 in-guest 写断点推迟到 capability 模型稳定后落地。 |

## 6. 残留需拍板项（请大喵最终决断）

1. **`DBG_POKE` 是否作为第 6 个显式 right 单列**（本裁决强烈推荐单列；替代方案是把它压进 `DBG_ATTACH` 的高位子权，但会削弱「改写=高危」的语义清晰度）。
2. **`debug_policy` 取值是否允许 `dev-session` 跨 Job 调试**，还是仅 `same-job` 与 `deny` 两档（跨 Job dev 调试更方便但有扩大攻击面风险）。
3. **崩溃冻结窗口默认时长与上限**（建议 30–120s，是否可配置、由谁配置）。
4. **`DBG_PROFILE` 原型期是否限制为同 Job 内**（防侧信道），还是开放。
5. **QEMU gdbstub 之外的「生产环境内核 panic 现场」是否允许经 `DBG_INSPECT` 在运行系统内符号化**（12 §7-3 符号表内嵌成本与此关联）。
