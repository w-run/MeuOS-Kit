> 子领域：内核启动与初始化流程设计 / 规划。
> 团队：`kernel-plan`；调研员：general-purpose-2（k-boot）。

## 1. 概述与目标

### 1.1 背景

MeuOS 当前处于「规划中」。内核定位（来自 `projects/meuos-kernel/README.md` 与 IMA 知识库「MeuOS / 01-总体架构」）：

- **外部兼容 Linux ABI**（经兼容层 `mkit` 对接，已有生态二进制可运行），内部**自主设计**——Linux 是参照物，不是目标；
- **三大内在统一方向**：① 统一文件系统层（校验和/压缩/加密 + 原子 `.msys` sysroot 更新 + 统一资源命名空间）；② spawn 模型进程管理（内建监督、资源账本 Day 1）；③ capability-based 安全（Day 1 唯一模型、pledge/unveil、内核关键组件 Rust、最小 TCB）；
- 内核工程路线：技术选型 → 原型（内存+调度+IPC+Linux syscall 兼容层 mkit 子集）→ 验证（`mcc`+`meuos-libc` 在自研内核自举）。

启动与初始化（Boot & Init）是这条路线的「第一道门」：它决定从**复位向量到 capability 世界就绪**这条链有多短、多可验证、多不破坏最小 TCB（方向③）。Kit 工具链层（mcc + 5 架构后端 + libc + sysroot + bootstrap 自举）已完成，本文件设计**从零**的内核启动/初始化流程，并声明与现有 `bootstrap.sh` / `.msys` 的接入点。

### 1.2 设计目标

| 编号 | 目标 | 说明 |
|------|------|------|
| B1 | **最快交权用户态** | 内核态仅完成「足以把控制权交给第一批用户态监督者」的最小工作；FS/网络/驱动/监督策略尽早下沉（对齐 `01` lean hybrid 边界与方向①③） |
| B2 | **最小、可审计的早期 TCB** | 早期阶段**只使用 C/asm**（Rust 裸机在 i386 等架构不可用、且早期无堆/无 runtime，见 `02`），Rust 仅在具备 runtime 后接管安全关键路径 |
| B3 | **capability 世界 Day 1 激活** | capability 是启动早期就要自举出的「第一批令牌」——不是启动完成后再叠加；（`07` Day 1 唯一模型） |
| B4 | **多架构收敛** | x86_64/i386/aarch64/riscv64/loongarch64 的架构相关差异在**极薄**的早期层收敛，进入架构无关的 Rust `kernel_main` |
| B5 | **可自举、可回退** | 启动链须能被 `11` 的 M0–M6 验证驱动；与现有 `bootstrap.sh` 衔接，失败可回退到 Alpine 代理门禁 |
| B6 | **解耦于具体引导器/固件** | 不直接绑定某一固件，经统一的 `bootinfo` 抽象对接 UEFI/multiboot/设备树/OpenSBI |

### 1.3 范围之外

- 不展开内存分配器、页表游走的具体算法（见 `03`）；
- 不规定进程/调度/信号的具体语义（见 `04`）；
- 不规定 capability 位图与 pledge/unveil 清单（见 `07`）；
- 不规定具体驱动实现（见 `10`）；
- 不拍板 M0–M6 的验收标准（见 `11`，本文仅声明依赖）；
- 不定义具体 syscall 编号（见 `08-Linux兼容层.md`）。

## 2. 设计约束与上下文

### 2.1 技术基线（来自 `01`/`02`/`README`）

- **lean hybrid 内核**：内核态 TCB = 低级 VM、线程调度、capability 监视器、IPC 端点、异常/中断派发、mkit 兼容转译薄层；FS/网络/驱动/监督策略下沉用户态（`01` §4.2）。
- **Rust + C 混合**：关键组件 Rust，底层/性能热点 C/asm；**早期启动（复位向量→runtime 就绪）必须用 C/asm**（`02` §1.1/§4.1/§4.2 明定：早期启动与体系结构入口只走 C(mcc)+asm，i386 甚至全程纯 C）。
- **三大方向**：①②③ 必须在启动设计里落地——尤其「尽早交权用户态」直接压缩 TCB、「capability Day 1」直接决定启动早期就要有 capability 自举。

### 2.2 语言边界硬约束（C/asm ↔ Rust 的精确交接）

来自 `02-内核语言策略.md` 的铁律（须在本文件体现）：

- **复位向量之后、runtime 就绪之前**：只有 C(mcc) + 裸 asm。理由有两重：① Rust 裸机 target 在 i386 缺位（`02` 约束 C2），而 mcc 对 i386 是完整代码生成 target；② 早期无堆、无 Rust runtime（`alloc_error_handler`/`panic_handler` 尚未链接），Rust 的 `#![no_std]` 安全前提不满足。
- **runtime 就绪之后**：Rust 接管页表类型化封装、capability 监视器、IPC、调度核心——这些入 TCB 的组件用 Rust（消除整类内存安全缺陷）。
- 交接点须是**单一、明确、可审计**的 `arch_boot → kernel_main()` 边界（见 §5.7 架构裁决）。

### 2.3 与三大方向的关系

| 方向 | 启动/初始化如何支撑 |
|------|-------------------|
| ① 统一文件系统层 | 内核**不**内建文件系统逻辑；启动早期只需能挂载 `.msys`（经 `libmsys` 或等价 Rust 实现，见 `11` §4.1）作为根，随后把 FS 服务作为第一批用户态进程交出控制权 |
| ② spawn / Job 监督 | 内核启动早期创建**根 Job（root job）**与**监督服务（meu-supervisor）**作为首个用户态进程；监督策略在用户态、可重启（`04` §4.5） |
| ③ capability Day 1 | 启动早期就要自举出**第一批 capability**（根 Job 的句柄集、设备能力、命名空间能力），capability 监视器是 TCB 核心且须**先于**任何非特权用户态代码激活（`07` §4.1） |

## 3. 方法论：解构型思维——「启动与初始化应该是什么样」

> 大喵增补铁律之「解构型思维」：先问**应该**是什么样，再决定怎么落地。以下从第一性原理推演，不直接复述任一现有系统的启动流程。

### 3.1 解构：复位向量 → capability 世界就绪的「最短可验证链」

把启动/初始化还原为**最小必要阶段**，每一阶段只回答「下一步还差什么才能让用户态接管」：

1. **固件/引导器已交出的状态**：CPU 处于某种特权模式、内存可见、固件把控制权交给内核入口，并留下「机器长什么样」的描述（DT/ACPI/multiboot info）。
2. **架构相关早期（仅 C/asm）**：建栈、开 MMU/页表、初始化 bss/数据段、早期串口控制台——**到此为止仍无 Rust runtime、无堆**。
3. **早期分配器（C）**：`memblock` 式 boot allocator 接管物理内存，供后续页表/内核结构使用（衔接 `03`）。
4. **Rust runtime 接管（架构无关）**：`core`/`alloc` 就绪、`panic_handler` 链接、调用 `03` 的类型化页表/VMAR 抽象；安全关键路径自此由 Rust 把守。
5. **capability 世界激活（Day 1）**：内核自举出**第一批 capability**——根 Job 句柄、设备能力、命名空间能力；capability 监视器在**任何非特权用户态代码运行前**已在线。
6. **第一批用户态服务接管**：内核 spawn 出 FS 服务、驱动管理器/devmgr、进程监督 `meu-supervisor` 等，把「机器的大部分管理权」交出去。
7. **交权完成**：内核退居「机制提供者 + 唯一裁决点」，进入多服务运行态。

这条链的「应该」标准是：**在能交权的地方尽早交权**——因为每多留一个子系统在内核态，就多一分 TCB、多一分不可验证（方向③），也多一分故障爆炸半径（方向①②）。

### 3.2 最小 TCB 视角：内核态「只做多少」

| 内核态**必须**做（启动期） | 内核态**不应**做（尽快交权） |
|---------------------------|---------------------------|
| 开 MMU/页表、建立内核地址空间 | 解析/实现具体文件系统格式 |
| 早期物理内存登记（memblock） | 网络协议栈 |
| 拉起 capability 监视器（TCB 核心） | 具体设备驱动逻辑（除中断控制器/定时器/看门狗等生死相关快速路径） |
| 拉起 IPC 端点（同步端点） | 监督策略/重启策略 |
| 内核态 mkit 兼容转译薄层（唯一让步） | 图形栈、shell、登录 |

即：**内核启动到「能 spawn 一个受 capability 约束的用户态进程」即止**，其余全部交给用户态服务。这与 Fuchsia/Zircon「内核只做最小事、尽快交权用户态」哲学一致，但**不照搬**其「每 syscall 一次 IPC」——我们保留内核态 mkit 薄层（lean hybrid 取舍，见 `01` §4.1）。

### 3.3 多系统参照（少走弯路，不缝合）

| 系统 | 启动/初始化要点 | 对 MeuOS 的「可取」 | 对 MeuOS 的「不可取（避免缝合）」 |
|------|----------------|--------------------|--------------------------------|
| **Linux (x86_64)** | real→protected→long mode、initramfs、PID1（systemd/init） | 早期「最小必要」分层清晰；initramfs 思路可借鉴 | PID1 是庞杂用户态 blob，非「监督策略可重启服务」；宏内核 TCB 巨大 |
| **Windows NT** | UEFI/WinLoad → Phase0（HAL/内核初始化）/Phase1（加载驱动、会话管理）、SMSS/CSRSS | Phase0/Phase1 的「先机制后策略」分阶段思想 | 重服务（FS/网络/图形）留核内，TCB 大；与方向①③冲突 |
| **macOS (XNU)** | iBoot/BootX → 内核（Mach+BSD+IOKit 同影像）→ launchd 作为首个用户进程 | 内核只拉起 launchd、监督全在用户态（`04` 借鉴） | IOKit 驱动全在内核态，无隔离；「混合」实为重服务留核 |
| **Android** | bootloader→kernel→init→zygote（预孵进程池） | zygote「预建地址空间、spawn 复用」与 MeuOS spawn 原语契合 | init 仍承袭 Linux PID1 模式 |
| **Symbian EKA2** | 纳内核（nanokernel）启动 → 用户态执行体（EKA2 的「内核态极少」） | 手机场景对「极小内核 + 尽快用户态」的极致追求 | 单设备垂直优化，不具通用多架构适配性 |
| **Fuchsia/Zircon** | bootfs → **userboot**（首个用户态进程，由内核直接拉起）→ devmgr/userboot 此后用户态接管 | **「内核只做最小事、尽快交权用户态」哲学**（强参考）；userboot 即「首批用户态接管」范本 | 每 syscall IPC 往返代价高，MeuOS 以 mkit 薄层规避 |

> **非缝合怪宣言**：MeuOS 不拼接「Linux 的 x86 启动 + NT 的 Phase 分层 + macOS 的 launchd + Fuchsia 的 userboot」——而是取其**共同内核**（尽快交权、监督在用户态、capability 早激活），落到一个由三大方向（①②③）与 lean hybrid 边界（`01`）唯一决定的 MeuOS 形态。

## 4. 业界方案对比

### 4.1 候选形态（按「交权时刻」与「早期 TCB」两轴）

| 方案 | 早期语言 | 交权时刻 | 早期 TCB 规模 | 与 MeuOS 目标契合度 |
|------|----------|----------|--------------|-------------------|
| **A. Linux 式**（宏内核渐入） | asm→C（全程 C） | 很晚（PID1 时 FS/网络/驱动已全在内核） | 极大 | 低（TCB/隔离/验证全冲突） |
| **B. NT 式**（Phase0/1 + 重服务留核） | asm→C | 中（SMSS 时仍大量留核） | 大 | 低（名合实不合，见 `01` §3.3/§4.4） |
| **C. macOS 式**（内核拉 launchd） | asm→C/ObjC++ | 较早（launchd 后监督在用户态） | 中—大（IOKit 留核） | 中（监督思路可取，驱动留核不可取） |
| **D. Fuchsia/Zircon 式**（userboot 尽快接管） | asm→C++→用户态 | **最早**（内核只做最小事） | 小（能力内核） | **高**（哲学契合，但需加 mkit 薄层让步） |
| **E. Symbian EKA2 式**（纳内核） | asm→C++ | 极早（手机垂直场景） | 极小 | 中（哲学可取，通用性不足） |

### 4.2 取舍结论（用于 §5）

- **拒绝 A/B/C 的内核态扩张**：它们的 FS/网络/驱动/监督逻辑滞留内核，与方向①③（最小 TCB / FS 出核）直接冲突。
- **采纳 D 的「尽快交权」哲学**作为主骨架：内核启动到「能 spawn 受 capability 约束的用户态进程」即交权，FS/驱动/监督下沉。
- **保留 lean hybrid 的唯一让步**：内核态保留 mkit 兼容转译薄层（`01` §4.1），避免「每 syscall 一次 IPC」的 Linux 热路径代价——这是与纯 Fuchsia 的**唯一偏差**，且正是 MeuOS「外部兼容 Linux ABI」目标所要求的。
- **吸收 C 的「内核只拉起监督、监督策略在用户态」**（即 `04` 的 `meu-supervisor` 思路）与 E 的「极小早期内核」精神。

## 5. MeuOS 选型建议（自主结论）

### 5.1 总体立场：两段式启动 + 早期 capability 自举

> **MeuOS 启动链 = 一段「架构相关、仅 C/asm 的早期 stage」+ 一段「架构无关、Rust 接管后的 capability 就绪 stage」+ 一次「尽快的用户态交权」。**
> 内核在 capability 监视器与 mkit 薄层就绪后**立即** spawn 出 FS 服务 / 驱动管理器 / 进程监督服务，把机器管理权交出去；内核不再做「第二个 systemd」。

理由：最短可验证链（§3.1）+ 最小 TCB（§3.2）+ 三大方向全部落地（§2.3）。

### 5.2 阶段化启动链（详细）

```
[固件/引导器] ──(bootinfo: DT/ACPI/multiboot)──▶
  └─ Stage 0  架构无关接入：解析 bootinfo，归一化机器描述
        │
        ▼
  Stage 1  架构相关早期（仅 C/asm，无 runtime/无堆）
           · 建栈、清 bss、初始化数据段
           · 临时/最终页表、开 MMU（long mode / EL1 / S-mode / LoongArch CSR）
           · 早期串口控制台（NS16550/virtio-console 的早期直写）
        │
        ▼
  Stage 2  早期 C 运行环境（仍 C，无 Rust）
           · memblock boot allocator 接管物理内存（衔接 03 §4.2.1）
           · 内核静态结构（page 数组、早期堆）占位
           · 设备拓扑树雏形（DT/ACPI → 设备节点 + 资源区间）
        │
        ▼
  Stage 3  Rust runtime 接管（架构无关 kernel_main）
           · core/alloc 就绪，panic_handler / alloc_error_handler 链接
           · 调用 03 的类型化页表/ASID/VMAR 抽象，接管地址空间
           · 调度核心、IPC 端点、mkit 薄层就位（均 Rust，入 TCB）
        │
        ▼
  Stage 4  capability 世界激活（Day 1 唯一模型）
           · 自举第一批 capability：根 Job 句柄集、设备能力、命名空间能力
           · capability 监视器上线（先于任何非特权用户态代码）
        │
        ▼
  Stage 5  第一批用户态服务接管（尽快交权）
           · spawn 根 Job 下的 meu-supervisor（进程监督，04 §4.5）
           · spawn FS 服务（挂载 .msys rootfs，方向①）
           · spawn 驱动管理器/devmgr（加载用户态驱动，10 §4.3；RS 看门狗）
        │
        ▼
  Stage 6  交权完成 → 多服务运行态（内核退居机制+裁决）
```

各阶段要点：

- **Stage 0 — 固件/引导器接入**：统一 `bootinfo` 抽象屏蔽 UEFI/multiboot/OpenSBI/DT/ACPI 差异。x86 走 UEFI 或 multiboot2；aarch64 走 UEFI + 设备树（或 spin-table/PSCI）；riscv64 走 OpenSBI（M-mode 固件）→ S-mode 内核；loongarch64 走 UEFI/EFISTUB + CSR；i386 走 32-bit 保护模式（无 long mode）。
- **Stage 1 — 架构相关早期（仅 C/asm）**：这是 TCB 中**唯一允许纯 asm/C 的硬边界**。负责把 CPU 带到一个「C 能跑、但还不是 Rust」的态：栈、页表、MMU on、bss/数据、串口。此层**极薄**、可形式化审计（`02` §4.2 把早期启动归入「极小、固定、可审计」的 C 部分）。
- **Stage 2 — 早期 C 运行环境**：`memblock` 式分配器（临时 reserve/alloc，待 buddy 就绪转交 `03`）。此时**仍无 Rust**——因 `alloc`/`panic` 基础设施需在 Stage 3 才链接。设备拓扑树在此刻从 DT/ACPI 抽出「节点→资源区间」，供 Stage 4 签发设备能力。
- **Stage 3 — Rust runtime 接管**：进入架构无关的 `kernel_main()`。这是 §2.2 约定的**语言边界交接点**：此前是 C/asm 世界，此后是 Rust 把守的安全关键世界。页表类型化封装（`03` §4.5）、capability 监视器（`07`）、IPC（`05`）、调度（`04`）、mkit 薄层（`01`/`08`）均在此时就位。
- **Stage 4 — capability 世界激活**：见 §5.4。
- **Stage 5 — 第一批用户态服务接管**：见 §5.1 与 §2.3。这是「尽快交权」的落点，对应 `11` 的 **M0**（内核启动到用户态 init）。
- **Stage 6 — 交权完成**：内核只保留「机制 + 唯一裁决点」，符合 lean hybrid（`01` §4.1）。

### 5.3 早期内存/页表与 `03-内存管理`（VMO/VMAR）的衔接

- **Stage 1–2 的页表是「临时/最小」的**：仅映射内核映像 + 早期串口 + 后续页表自身所需内存。它们由 C/asm 直接写出，**不经过** `03` 的类型化 Rust 页表抽象（此时 Rust 尚未接管）。
- **Stage 3 Rust 接管后**：调用 `03` 的 `arch/mm/pagetable`（`map/unmap/walk/set_flags`，`03` §4.3.1）重建/接管页表，并把早期临时映射提升为 `03` 的「内核高半直接映射 + 用户态布局」（`03` §4.3.2）。**衔接契约**：Stage 1–2 的临时页表必须在 `kernel_main` 入口处仍有效（或能无感切换），Rust 接管后以 `03` 抽象为唯一真相源。
- **capability 化的终点在 `03` 的 VMO/VMAR**：用户态进程持有 VMO capability 才能 map/unmap/clone（`03` §4.4）。这些 VMO/VMAR 对象的**根**在 Stage 4 随根 Job 一同自举，是「统一资源命名空间」的内存侧入口。
- **memblock → buddy 的转交**：Stage 2 的 `memblock` 在 `03` 的 buddy（`03` §4.2.3）与 SLUB（`03` §4.2.4）建好后，把空闲区交还 buddy——这是 `03` §4.2.1 明确的两阶段分配器设计，本文不重述，仅声明调用顺序。

### 5.4 capability 世界的「激活时刻」与第一批 capability 自举（Day 1 唯一模型）

关键命题（`07` §2.3）：capability 必须是地基而非补丁——因此启动早期就要有 capability，而非启动完成后叠加。

- **激活时刻 = Stage 4，且先于任何非特权用户态代码**（B3）。即在 `kernel_main` 内、spawn 第一个用户态进程**之前**，capability 监视器已在线、根 Job 已存在、设备/命名空间能力已签发。
- **第一批 capability 清单（自举顺序）**：
  1. **根 Job 句柄集**：内核创建 root job（`04` §4.5），其句柄带「创建子 Job / spawn / 监督」专属 capability——`meu-supervisor` 必须持有它才能拉起其他服务，普通进程无法冒充（呼应 `04` §4.5「监督者自身受根 Job 约束」）。
  2. **设备能力**：Stage 2 抽出的设备拓扑树（DT/ACPI → 资源区间）在此签发为 `Cap(MMIO/IRQ/DMA/IO port)`（`10` §2.4/§4.6），供驱动管理器在加载驱动时按「声明即授权」下发。
  3. **命名空间能力 / 根 FS 能力**：向 FS 服务授予「`.msys` rootfs 的块设备读 + 命名空间根」能力（`06`/`11` §4.1），使统一文件系统层作为用户态服务对外暴露统一命名空间。
  4. **内核对象句柄表种子**：root job 下的首个进程（meu-supervisor）继承一份**显式声明、可收窄**的初始句柄集（`04` §4.2「默认不继承任何句柄」）——这正是 capability「无隐式权限」的体现。
- **无 root 逃生舱**：即便根 Job/监督服务也持「较大的初始句柄集」，仍受 rights 约束、可逐步收缩（`07` §4.1）——启动自举出的第一批 capability **不是**超级权限，而是「可审计、可撤销」的受约束令牌。

### 5.5 多架构启动差异的收敛点

| 架构 | 复位/固件入口 | 特权级过渡 | Stage 1 关键差异 | Rust 裸机就绪 | 收敛点 |
|------|--------------|-----------|------------------|---------------|--------|
| **x86_64** | UEFI/PE 或 multiboot2 | real→protected→long mode | 4 级页表 PML4、PCID | ✅ (`02` §2.3) | `bootinfo` 归一化后统一进 `arch_boot` |
| **i386** | multiboot（32-bit） | 保护模式（无 long） | 2/3 级 32-bit 页表、无 PCID | ❌ 纯 C（`02` C2） | **全程 C**，`kernel_main` 仍由 C 调 Rust 桩 |
| **aarch64** | UEFI + DT / PSCI | EL2→EL1 | TTBRx 4 级、ASID | ✅ | `bootinfo`（DT）归一化 |
| **riscv64** | OpenSBI（M-mode）→ S-mode | M→S mode | Sv39/48、ASID | ✅ | `bootinfo`（DT）经 SBI 传递 |
| **loongarch64** | UEFI/EFISTUB + CSR | 特权级 → 内核态 | 多級页表、ASID | ✅ | `bootinfo`（DT/ACPI）归一化 |

**收敛架构（架构相关 vs 架构无关分层）：**

```
arch/<arch>/boot/        ← 仅 C/asm：复位向量、页表模板、MMU on、早期串口（Stage 1）
arch/<arch>/memmap.c     ← 仅 C：探测物理内存、填 memblock（Stage 2）
kernel/boot.c            ← C 桩：调用 memblock、建设备拓扑树、跳 kernel_main（Stage 2→3 桥）
kernel/main.rs           ← Rust：kernel_main()，接管页表/调度/IPC/capability（Stage 3+）
```

- **架构相关层（Stage 1–2 前半）**：每架构一份极薄 C/asm 垫片；i386 因无 Rust 裸机 target，**Stage 2 之后仍由 C 调用 Rust 编译出的 `.o` 入口**（Rust 部分以 `extern "C"` 暴露 `kernel_main`，C 侧在 runtime 就绪后调用——这是 `02` §4.3 的 FFI 边界在启动期的直接应用）。
- **架构无关层（Stage 3+）**：所有安全关键逻辑进入 Rust `kernel_main`，五架构**同源码**（`01` §5 待决议题 6「同源码异架构」）。
- **收敛契约**：无论何种架构，进入 `kernel_main` 时必须满足同一组不变量（MMU on、内核地址空间有效、memblock 可用、bootinfo 已解析）。这把架构差异封死在 Stage 1–2，使 TCB 的 Rust 核心不被架构特化侵蚀。

### 5.6 与 `bootstrap.sh` / `.msys` sysroot 的接入点（参照 `11` M0–M6，仅声明依赖）

- **启动媒介形态**（`11` §4.1）：`可启动媒介 = MeuOS 内核镜像 + initramfs（内含 .msys rootfs 或 .msys 直接作根）`。本文确认该形态与 Stage 0/5 一致：Stage 0 解析 bootinfo 拿到内核与 rootfs 位置，Stage 5 由 FS 服务挂载 `.msys`。
- **`bootstrap.sh` 衔接**（`11` §4.3）：在现有 Phase 0–5 之后新增可跳过的「内核自举门禁」（沿用 `MEUOS_SKIP_*`）。本文**不下结论**其具体实现，仅声明依赖：本文件的 Stage 0–5 须能被该门禁驱动触发，且 M0 验收（内核启动到用户态 init）对应本文 Stage 5 完成。
- **`.msys` 作为 rootfs 的最小改造**（`11` §4.1）：内核 FS 层需 `libmsys` 读取能力——该能力在 Stage 5 由 FS 服务（用户态）提供，内核本身只需能把控制权交给它。本文不决定 `.msys` 是否扩展为通用可启动镜像（属 `06`/`11` 开放议题）。
- **`qvm` 复用**（`11` §4.3）：`qvm` 的 `--kernel`/`--initrd` 覆盖参数化属 env 项目，本文仅标注为启动链的验证承载手段。
- **依赖里程碑映射（声明，非结论）**：

| 本文 Stage | `11` 里程碑 | 说明 |
|-----------|-------------|------|
| Stage 0–1 | M0 前置 | 内核在 `qvm` 启动、早期串口打印 |
| Stage 1–3 | M0 | Rust runtime 接管、capability 监视器在线 |
| Stage 4–5 | M0（用户态 init 就绪） | 首批用户态服务接管、`.msys` 挂载 |
| （后续由 `03/04/08/10` 补全） | M1–M6 | 本文只负责到 M0 的启动链 |

### 5.7 语言边界的精确交接点（架构裁决）

这是本文的**核心裁决项**：C/asm 早期世界与 Rust runtime 世界的**唯一交接边界**。

- **裁决 A（推荐）**：交接点为单一 `arch_boot → kernel_main()`（Rust `extern "C"` 入口）。Stage 1–2 全在 C/asm，Stage 3 起全在 Rust；i386 由 C 在 runtime 就绪后调用 Rust 的 `kernel_main` 入口（`02` C2 的应对）。
- **裁决 B（备选）**：若可行，i386 也可先 C 跑完 Stage 1–2，再以「Rust 编译为 `.o`、C 链接进内核」方式接入（双工具链，`02` §2.2 C1）——此时 i386 的 Rust 部分**不是裸机 target**，而是被 C 链接器合并的普通 `no_std` 对象，受 `kernel_main` 契约约束。
- **硬性约束**：无论 A/B，Rust 接管**之前**禁止任何依赖 `alloc`/`panic` 的 Rust 代码路径（即 Stage 1–2 不可触及 Rust 安全关键组件）。这保证「早期无堆/无 runtime 也能启动」与「Rust 仅在具备 runtime 后把守 TCB」两条铁律同时成立。

## 6. 待决清单（含架构裁决项）

1. **【架构裁决】Rust runtime 何时精确接管**（§5.7）：推荐 `arch_boot → kernel_main()` 单一边界；i386 的 C→Rust 链接策略（A vs B）需原型实测后定。
2. **i386 全程 C 的 Rust 部分范围**：i386 下哪些 TCB 组件可走「C 链接 Rust `.o`」、哪些被迫维持纯 C？需 `02` 协同回填。
3. **capability 自举的「根 Job 句柄集」具体权限**：根 Job 初始拥有哪些 rights、监督服务收窄到何程度，需 `07` 定稿位图后回填（§5.4）。
4. **设备能力签发的时序与撤销**：Stage 2 拓扑树 → Stage 4 签发 → 驱动卸载回收的锁与时机，需 `10` 协同（§5.4/§5.3）。
5. **`.msys` 作为可启动镜像的边界**：是否扩展 `.msys` 承载内核/设备树/启动配置，还是另建一层封装（`11` 开放议题 1）。
6. **`qvm` 的 `--kernel`/`--initrd` 参数化**：属 env 项目，启动链依赖其落地（`11` §4.3）。
7. **早期串口控制台的设备能力归属**：Stage 1 直写串口是「内核内建生死相关快速路径」（对齐 `10` §4.2 内核态），还是也应经能力网关？需 `10` 协同。
8. **memblock → buddy 转交的原子性**：Stage 2 到 `03` buddy 就绪时的页帧数据库衔接、地址空间无感切换，需 `03` 协同（§5.3）。
9. **多架构 bootinfo 归一化格式**：五架构的 DT/ACPI/multiboot/OpenSBI 信息如何统一为 `bootinfo` 结构体（含 NUMA/保留内存/内核位置），需原型验证。
10. **监督者自身的自举环**：`meu-supervisor` 崩溃时内核是否自动重启（自举监督），避免「监督者监督自己」死锁（`04` §5 开放议题 4）。
