## 4. 第一轮文档（01–12）引用失真清单（提取自 `24` §②）

> 来源：`24-参考系统深度专项.md` §2「对 01–12 引用失真纠偏清单」，共 7 条 + Top3 小结。以下逐条给出「文档:位置 → 失真点 → 建议修正」并标注是否影响结论。

### 4.1 Top3 失真（影响 `06` 对参照系统取舍判断，建议回写 `06`）

- **失真 1（最高优先级）— `06` §3.2**：NTFS「**无原生透明压缩**」事实错误。
  → 失真点：NTFS 自 NT 3.51 起即支持 per-file/dir 原生透明压缩（LZNT1）；其真正缺项是**数据校验和**（在 ReFS integrity streams，非 NTFS）。
  → 建议修正：改为「有原生透明压缩（LZNT1, per-file），但**无数据校验和**（数据完整性在 ReFS）」。
  → 影响结论：**影响**——削弱 `06` 对 NT 的准确取舍（NT 压缩能力其实可借鉴，`06` §4.2 extent 压缩与 NT 思想一致）。

- **失真 2（高优先级）— `06` §3.1**：ext4 校验和「**默认无 / 可选**」表述误导。
  → 失真点：ext4 `metadata_csum`（crc32c）自 e2fsprogs 1.43（2016）起新建文件系统**默认开启**；真实缺口是**数据层无校验和**（非「整个无校验和」）。
  → 建议修正：改为「ext4 元数据校验和（crc32c）默认开启，但**数据层无校验和**；无透明压缩、无原生加密（fscrypt 在 VFS 之上）」。
  → 影响结论：**影响**——使 `06` 与 btrfs 对比更精准（btrfs 强在「数据」extent 校验和+压缩+快照，ext4 弱在「数据无校验和」）。

- **失真 3（中优先级）— `06` §3.1**：VFS「**统一只到文件系统类型层**」表征偏差。
  → 失真点：VFS 在**对象模型层是真正统一的**（procfs/sysfs/devtmpfs/btrfs 均表现为同一套 inode/dentry/file 内核对象）；真正的碎片化发生在**命名空间/挂载层**（多伪 FS 挂全局树、可见性默认全局）。
  → 建议修正：改为「**对象模型层统一（一切皆 inode），但命名空间/挂载层碎片化**（多伪 FS 拼全局树、可见性默认全局）」。
  → 影响结论：**不影响核心结论**——`06`「capability 组合命名空间优于 VFS」仍成立，但理由应落在「命名空间层」而非「对象层」，避免低估 VFS。

### 4.2 其余失真（4–7）

- **失真 4（中优先级）— `07` §4.1 / §4.5**：Zircon 被暗示「有派生树/revoke 传播」+ seL4 CSpace 用词混称。
  → 失真点：实际采纳模型是 **Zircon 式进程私有 handle 表 + IPC 携带**（非 seL4 全局可寻址 CSpace）；Zircon **无** capability 派生树/递归 revoke 传播，derivation tree 是 **seL4 独有 + MeuOS 自研增强**。
  → 建议修正：`07` §4.1 把「CSpace（借鉴 seL4）」改为「**进程私有 handle 表（Zircon 风格，可演进为全局 CSpace）**」；§4.5 明示「derivation tree 来自 seL4，是 MeuOS 在 Zircon handle 模型之上的自研增强」。
  → 影响结论：**不影响核心裁决**（C2 revoke 闭环仍成立），但影响 `07` 术语一致性与参照归属严谨性。

- **失真 5（低优先级）— `06` §4.3**：APFS 快照「回退」语义被静默假设为非破坏式。
  → 失真点：macOS APFS「恢复到快照」是**破坏式**（删除快照后所有写入、需重启/离线）；MeuOS repoint 因 capability 是**非破坏式**（旧持有者续持旧能力、新进程切新视图、无需重启）。
  → 建议修正：`06` §4.3 补一句「与 APFS 破坏式 revert 不同，MeuOS repoint 因 capability 非破坏式、支持 per-process 灰度」。
  → 影响结论：**不影响**——属 `06` 已声明的自研点（§4 自研点 3），仅澄清避免误读为照搬 APFS。

- **失真 6（低优先级）— `07` §3.2 / §5.2**：seL4「8700 行 C」与 Zircon「~10 right」数字口径。
  → 失真点：原始被证 seL4 约 8,700 行（现代 ARMv8/HYP 验证版更大）；Zircon 实际基础 right 约 **13** 个。
  → 建议修正：`07` 补注「现代验证版内核规模更大」「Zircon 实际 ~13 right，MeuOS 原型取 ~10–13 子集」。
  → 影响结论：**不影响**（近似可接受）。

> （第八轮核查·引用校正）本「失真 6」标注 `07 §3.2 / §5.2` 中的 `07 §5.2` 为「right 粒度」历史开放议题章节号，现已折叠入 `07 §4.1` 冻结表；rights 位图（bit 0–47 + bit 48+ 预留）已于 `07 §4.1` 定稿（`38` §3 / `45` §3 回写闭环），本节对 `07 §5.2` 的引用应读作 `07 §4.1`。

- **失真 7（低优先级）— `06` §4.1 / §3.6**：Fuchsia namespace「由 FS 服务组装」归属。
  → 失真点：Fuchsia 每进程命名空间由**组件框架（component framework）**组装，非 FS 服务；`06` §4.1 已自陈差异但 §3.6 对比表未显式点出。
  → 建议修正：`06` §3.6/§5 补注「Fuchsia 由组件框架组装；MeuOS 改为 FS 服务根聚合 + mount-capability 委托（语义等价、归属更清晰）」。
  → 影响结论：**不影响**（已自陈），仅外显差异避免读者误判。

> 小结：Top3（失真 1/2/3）均指向 `06` 对参照系统的取舍判断准确性，**建议后续轮次回写 `06`**；失真 4 指向 `07` 术语一致性；失真 5/6/7 为低优先澄清项。
