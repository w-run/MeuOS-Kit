## 0. 裁决口径与边界

- **C1** 问的是「物理页帧数据库（page frame database）的所有权与控制权落在哪一层」：内核 buddy 独占 / seL4 式交用户态（Untyped/Retype）/ 折中。它直接决定最小 TCB、分配热路径性能、DMA、Job 资源账本（04）、VMO/VMAR（03）、五架构可移植性。
- **C7** 问的是「早期 C/asm 阶段（`09` Stage 1–2）用 memblock 式引导分配器，Rust runtime 接管（`09` Stage 3）后转交给正式分配器（buddy+SLUB）」这条边界的**原子性、认领语义、失败诊断**，以及它与 C1 选择的**强耦合**。
- 本文不重新设计分配器算法（属 `03`），只裁决「归属」与「转交边界」两层架构决策，并显式标注需要其他子领域回填的依赖。

## 1. 「应该是什么样」——解构型推演

> 先于任何现成系统回答：MeuOS 的 capability 内核 + 最小 TCB + Job 账本 Day 1 + lean hybrid 这四条硬约束，**共同逼出**物理内存的哪种归属形态？

### 1.1 C1 推演：物理内存「应该」归谁

按方向③（capability Day 1、内核唯一裁决点）与方向②（Job 资源账本 Day 1 内建）倒推：

1. **单一真相源（single source of truth）是硬前提**。一个进程能占用多少物理内存，必须由内核在「分配发生的那一瞬间」从它所属 Job 的配额里扣减（否则配额形同虚设）。这意味着**分配决策点 = 配额强制点**必须同处一层——而这一层只能是内核（用户态内存服务无法在自身被配额约束前、先于内核做无可伪造的扣减）。
2. **revoke 必须能真正回收物理页**。方向③的「句柄可撤销」要求：撤销一个 VMO capability 后，其背后的物理页必须回到可用池（否则 capability 撤销只是名义上的）。这要求回收动作能触达物理页帧数据库——即物理所有者必须能响应 revoke。
3. **lean hybrid 拒绝「每内存操作一次 IPC」**。Linux 兼容热路径（匿名 `mmap`、缺页）若每次都要陷入用户态内存服务取物理页，就退回了纯微内核「每 syscall 一次 IPC」的老路，与 `01` §4.1 的唯一让步（内核态 mkit 薄层）精神相悖。

由此推演出的「应该」形态：

> **内核掌握物理页帧数据库（buddy）的所有权与分配决策权——这是配额强制与 revoke 回收的唯一真相源；但内核把「一段内存」以 VMO/VMAR 这种 capability 视图暴露给用户态/兼容层，而非裸露的页。device 内存按 seL4 device-untyped 思想建模为「不可写、只能 retype 为可映射 frame」的 device VMO。**

这恰好是「折中（C）」——但推演给出它**不是和稀泥，而是四约束共同锁定的唯一自洽解**：纯内核 buddy 独占（A）缺 capability 视图、纯 seL4（B）把真相源与配额强制拆到用户态、且强制缺页走 IPC，二者都破坏上述前提之一。

### 1.2 C7 推演：转交「应该」在哪里原子完成

按 `09` 启动链 Stage 1–2（仅 C/asm、无 runtime/无堆）→ Stage 3（Rust runtime 接管）倒推：

1. **启动早期是单线程、关中断、无其他分配器并发的世界**。因此「原子性」在这里**不是锁竞争意义上的原子，而是「逻辑单一切换点」**：在某一行代码之后，memblock 不再是物理内存的权威；在它之前，buddy 还不存在。二者不能「同时为真」。
2. **认领不丢失/不重复的唯一办法是「全量对账」**：把「检测到的全部物理内存」切成三类——保留（内核镜像/早期页表/页帧数组/设备树/MMIO 空洞）、已分配（早期堆等仍存活对象）、空闲——并保证 `保留 + 已分配 + 空闲 == 检测到的物理总量` 作为不变量。buddy 只收「空闲」类；「保留/已分配」类在 `MmPage[]` 中标记为 RESERVED 后由内核永久持有。
3. **地址空间必须无感切换**：Stage 1–2 的早期页表在切换瞬间仍有效；Rust 建好完整内核地址空间（直接映射全部物理 + vmalloc）后，一次性换顶表（x86 `mov cr3` / ARM `TTBR`），旧表页本身属于「保留」类，不会被回收。

由此推演出的「应该」形态：

> **转交在 Stage 3 的 `buddy_init()` 单一调用内、单线程、关中断下完成；以「全量物理内存三类对账」为原子边界；早期仍存活对象被 buddy 以 RESERVED 认领；旧页表在换顶表后才允许释放；任何对账失败 → 结构化 panic（接 `12` CrashReport），绝不让内存状态处于「部分转交」的中间态。**

**C7 与 C1 的耦合点（推演即浮现）**：上述「memblock→buddy」转交，只有在 C1=C（内核拥有 buddy）时才成立。若 C1=B（seL4 untyped，用户态拥有物理内存），则**根本没有 buddy 可转交**——memblock 的空闲区要打包成 untyped capability 发给用户态内存服务，转交语义整体改写（见 §2.2、§3.2）。

## 2. 各选项对比表（含多系统参照）

### 2.1 C1 对比表：物理内存归属三选项 × 多维度 × 多系统参照

| 维度 | **A. 内核 buddy 独占**（Linux 式） | **B. seL4 式 untyped 交用户态**（Untyped/Retype） | **C. 折中（推荐）**：内核 buddy 拥有物理页 + VMO capability 视图 + device-untyped 思想 |
|------|-----------------------------------|--------------------------------------------------|----------------------------------------------------------------------------------------|
| **物理页所有权** | 内核 buddy 唯一所有 | 内核不在运行期分配；全部物理内存以 untyped cap 交 root task/内存服务 | 内核 buddy 唯一所有（单一真相源） |
| **最小 TCB** | 中（buddy+页故障在核内，但集中在小、良约束的分配器） | 极小（内核零运行期动态分配，可验证面最小） | 中（同 A，但 VMO/VMAR 视图增加少量 TCB） |
| **缺页 / 分配热路径性能** | 最优：内核直接 buddy 分配，无 IPC | 劣：major fault 需 external pager IPC 往返（Mach/seL4 式） | 最优：匿名缺页内核直接 buddy 分配（保留 lean hybrid 热路径） |
| **Job 资源账本（04）** | ✅ 分配点即配额扣减点，单一真相源 | ❌ 配额强制被拆到用户态内存服务，内核需信任其记账 | ✅ 同 A，分配点强制配额 |
| **VMO/VMAR（03）** | ❌ 内核内部 VMA，无用户态 capability 视图 | 部分：frame 由 retype 出，但「能力」语义需自建 | ✅ VMO/VMAR 即暴露给用户的 capability 视图 |
| **revoke 回收（07）** | 需自建「revoke→派生树→buddy 归还」链路 | 天然：`Retype` 可逆、`Revoke` 回收派生 | ✅ revoke 经派生树回收 VMO 链 → refcount 归零 → buddy 归还 |
| **驱动 DMA（10）** | 内核从 DMA32 zone 取连续页，封 VMO 授予驱动 | device untyped 直给驱动，retype 为 frame | ✅ device 内存按 seL4 device-untyped 建模为不可写 device VMO |
| **五架构可移植性** | 高：buddy 与架构无关（仅 zone/DMA 差异） | 高：untyped 与架构无关 | 高：同 A；device 视图抽象为 arch 无关 |
| **Linux ABI 兼容** | 原生 | 需完整 external pager + libOS | 原生（内核态 mkit 薄层直跑） |
| **多系统参照（可取/避坑）** | Linux buddy+slab（成熟、可自举）；NT PFN database、XNU vm_page（内核持页帧库，可借鉴其 zone/页表模型） | seL4 Untyped/Retype/Revoke（TCB 极小、可验证、device 隔离优雅）；**避坑**：其「每内存操作 IPC」对 Linux 热路径过贵 | Zircon PMM 拥有物理页 + VMO 对用户态（最贴近 MeuOS：内核管物理、VMO 作 cap）；Theseus 所有权类型（refcount 用 Rust `Arc<Vmo>` 表达）；Symbian EKA2 极小内核精神 |

**结论性判读**：A 与 C 的唯一实质差异是「是否暴露 VMO capability 视图」——而 `03` §4.4 已承诺 VMO/VMAR，故**内部底座必是 A，对外必是 C 的视图层**。B 在「可验证 TCB」上极致，但它在 MeuOS 语境下同时破坏「Job 配额单一真相源（04）」「revoke 真回收（07）」「lean hybrid 热路径免 IPC（01）」三条硬约束，因此**对 MeuOS 不成立**，仅其 *device-untyped 子思想* 可被 C 吸收。

### 2.2 C7 对比表：转交语义 × 与 C1 的耦合

| 维度 | **方案 X（推荐，绑定 C1=C）**：memblock→buddy 内核内单一切换 | **方案 Y（绑定 C1=B）**：memblock→untyped cap 发用户态内存服务 |
|------|------------------------------------------------------------|--------------------------------------------------------------|
| **转交目标** | 内核 buddy + `MmPage[]` | 用户态 root 内存服务的 untyped capability 集合 |
| **原子性边界** | `buddy_init()` 单调用、Stage 3、单线程、关中断 | Stage 4/5 签发 untyped cap 时，单线程建表后一次性下发 |
| **认领不丢失/不重复机制** | 全量物理内存「保留/已分配/空闲」三类对账不变量 | 每空闲帧恰好签发一个 untyped cap；保留帧=内核静态池或 device-untyped cap |
| **早期存活对象处理** | 标 RESERVED 由内核永久持有；早期堆数据在 Stage 3 拷入 Rust 分配缓冲后释放 | 内核仅留极小静态池；其余在早期即规划为用户态所有，无「早期堆」概念 |

| **失败诊断（接 12）** | 对账失败 → 内核 panic + 结构化 CrashReport（物理区间/不变量/检测到的 memmap）→ 早期串口 + `.msys` 持久化 | 内存服务起不来 → Stage 4 panic，CrashReport 标注「untyped 下发失败」 |
| **与 C1 耦合** | 仅当 C1=C 成立 | 仅当 C1=B 成立（本裁决**不推荐**此路径） |

## 3. 明确推荐裁决

### 3.1 C1 推荐裁决 ✅

> **采用「折中 C」**：内核 buddy **独占**物理页帧数据库（单一真相源），VMO/VMAR 作为对用户态/兼容层暴露的 **capability 视图**；device 内存按 **seL4 device-untyped** 思想建模为「不可写、只能 retype 为可映射 frame」的 **device VMO**。拒绝纯 B（seL4 untyped 交用户态），纯 A 仅作为内部底座（不对外暴露 capability 视图即不满足 `03` §4.4）。

**理由（四约束锁定，非和稀泥）**：
1. **Job 配额单一真相源（04 §4.4）**：内存配额是 Job 固有属性、Day 1 内建。若物理内存归用户态（B），内核无法在分配点无可伪造地扣减配额——配额沦为「用户态内存服务自报」。`02`/`07` 的「内核唯一裁决点」被架空。⇒ 必须内核持 buddy。
2. **revoke 真回收（07）**：撤销 VMO 派生链必须触达物理页并归还 buddy（单一 refcount 在 MM）。B 下回收语义变为 untyped retype，与 `03` §5-2「refcount 单一真相源、避免双计数」冲突。
3. **lean hybrid 热路径（01 §4.1）**：匿名 `mmap`/缺页在内核内由 buddy 直接满足，免 IPC。B 强制 external pager IPC，退回纯微内核老路，与「唯一让步是内核态 mkit 薄层」矛盾。
4. **可自举 + 五架构（03/09）**：buddy+SLUB 是 `09` Stage 2→3 已规划的底座，`03` M1–M4 已落地路径；seL4 式需先建一个可验证的用户态内存服务，自举门槛陡增。

**对反对意见的回应**：
- *「seL4 把物理内存交用户态，TCB 最小、可验证，MeuOS 为何不学？」* — MeuOS 用 Rust 换取「证明前先少错」，但 TCB 已含 capability 监视器/IPC/调度；把物理分配也赶出内核，省下的 TCB 极小，却**被迫引入一个需被验证的用户态内存服务 + 每缺页 IPC 路径**，后者验证成本与故障域大于 in-kernel buddy。且 seL4 无 Linux ABI 兼容包袱；MeuOS 有。`03` §5-7 的「值得形式化」清单（页帧归属、ASID 唯一性）本就在内核内，与 C 一致。
- *「纯 A 更简单，为何要多一层 VMO 视图？」* — 因为方向③要求内存成为「可传递、可撤销的 capability」接入统一资源命名空间（`03` §4.4、`00` A4/A7）。裸露 buddy 页无法表达权限收缩、派生、revoke；VMO 视图是 capability 模型的必要接口，不是锦上添花。
- *「device untyped 是否过度设计？」* — 否。它直接服务 `10` 的用户态驱动 DMA 隔离：device VMO 不可写、只能映射，普通进程无 cap 则无法触碰 MMIO，缩小 TCB 暴露面（`03` §4.4）。这是 C 从 B **精准吸收**的子思想，不引入 B 的整体代价。

**若选错的退路（fallback）**：C→B 不是推倒重来，而是**非破坏性演进**——在 C 框架内，额外划出一块「用户态托管的 untyped 区域」专供驱动 DMA 池（复用 device-untyped/VMO 机制）。即：若未来发现内核 buddy + 配额强制确实过重，可局部下沉 DMA 区域管理，而不必改写整个物理内存归属。反之若选 B 后再退回 C，则需把用户态内存服务整体回收进内核，**改写成本极高**——这是选 C 而非 B 的额外保险。

### 3.2 C7 推荐裁决 ✅

> **采用「方案 X」（绑定 C1=C）**：转交在 `09` Stage 3 的 `buddy_init()` **单一调用**内完成，单线程、关中断；以「检测到的全部物理内存 = 保留 + 已分配 + 空闲」的全量对账为**原子边界**；早期仍存活对象由 buddy 以 `MmPage[].flags=RESERVED` 认领、永久持有；旧早期页表在换顶表后才允许释放；**任一阶段对账失败 → 结构化 panic（接 `12` CrashReport），绝不留「部分转交」中间态**。

**理由**：
1. **单线程启动期无需锁**：Stage 1–2 仅 boot CPU、中断未开、无其他分配器，所谓「原子性」是逻辑切换点，不是并发临界区——用「一次性全量对账 + 单点切换」比引入锁更简单、更可审计（对齐 `09` §5.3「单线程启动期保证无并发」）。
2. **认领不丢失/不重复靠不变量而非运气**：`buddy_init()` 遍历全物理地址空间逐页定类；`MmPage[]` 在切换前覆盖全物理范围；切换后 memblock 结构自身内存回收进 buddy。启动期做一次断言：`∑free + ∑reserved + ∑holes == detected_physmem`，失败即 panic。
3. **地址空间无感**：Rust 建好「直接映射全部物理 + vmalloc + 固定映射」的完整内核空间后，单次写顶表寄存器换表；早期页表页属保留类，换表后存活，避免「切换瞬间旧映射蒸发」。
4. **可诊断 panic（接 `12`）**：对账失败属于内核 panic（系统停机，supervisor 尚未起），CrashReport 落**早期串口 +（若可用）`.msys` 持久化通道**（`12` §4.5），含：失败的不变量名、 offending 物理区间（base/len）、`bootinfo` 报告的全部内存区间、触发阶段（Stage 2/3）。保证「转交失败 = 立即、可读、可定位」，不静默 corrupt。

**与 C1 的耦合（必须明示）**：本 C7 设计**仅在 C1=C 时成立**。若改选 C1=B，则 C7 整体替换为「方案 Y」：memblock 空闲区打包为 untyped cap 在 Stage 4/5 下发用户态内存服务，无 buddy 可转交；此时「认领」变为「每帧恰好一个 untyped cap」、「失败诊断」变为「内存服务起不来→Stage 4 panic」。本裁决推荐 C1=C，故以方案 X 为准，但方案 Y 已记录在 §2.2 供耦合追溯。

## 5. 风险与退路

### 5.1 C1 风险与退路
- **风险 R1（TTT 偏差）**：内核持 buddy 使可验证 TCB 大于纯 seL4。→ 退路：buddy 收敛为小、良约束、可单测的分配器；优先对「页帧归属 / refcount」做形式化/模糊测试（`03` §5-7），不追求端到端证明。
- **风险 R2（配额与分配耦合过紧）**：buddy 分配点强扣 Job 配额，可能使跨 Job 共享（如共享库 VMO）计费歧义。→ 退路：以「VMO 持有者 Job」为计费主账、共享映射按引用计数分摊，规则在 04 细化（`04` §5-5 OOM 归因）。
- **风险 R3（误选 B 的诱惑）**：若某架构 DMA 隔离压力极大，可能想整体改 B。→ 退路：如 §3.1 fallback，局部引入「用户态托管 untyped 区域」而非整体改写，保 C 框架。

### 5.2 C7 风险与退路
- **风险 R4（早期堆数据未迁移即丢）**：Stage 3 拷数据前若 memblock 已废弃，早期堆中设备树/cmdline 丢失。→ 退路：Stage 2→3 桥显式「先拷后弃」顺序；且 DT/cmdline 所在页标 RESERVED 永久持有直至 Rust 结构接管。
- **风险 R5（对账不变量漏检 → 静默 corrupt）**：若 `buddy_init` 未校验 `free+reserved+holes==total`，保留区被当空闲 → 双重映射。→ 退路：强制启动期断言，失败走 §3.2 结构化 panic（绝不跳过）。
- **风险 R6（换顶表瞬间 TLB/ASID 错位）**：新页表未含早期映射导致换表后跳飞。→ 退路：换表前新表**必含**早期映射（内核镜像+串口+早期页表自身），换表后旧表页保留至确认稳定；ASID 分配在 `03` §4.3.2 抽象层统一。
- **风险 R7（C1 改选 B 导致 C7 失效）**：若大喵最终拍 B，本文 C7=方案 X 作废。→ 退路：§2.2 方案 Y 已备，转交语义整体切换为 untyped cap 下发，本文记录即衔接点。
