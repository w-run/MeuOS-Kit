# 56 - 核心子系统现代化方案对比与合成（第六轮·粗合 pass）

> 合成 / 合并 agent 产出，kernel-plan 团队。
> 工作树：`kernel-plan` / 分支：`worktree-kernel-plan`。
> 输入：`46`–`55` 共 10 份方案文档（5 大核心子系统 × 2 方案）+ `00`-`07`/`34` 基线 + `29` 威胁模型 + `32` 信任根。
> 性质：**粗粒度合成 pass**——对 5 子系统 A/B 两两对比并给指挥官式粗决策推荐，**不修改** 46–55 任何内容；为后续「先细后精」轮次（fine pass）铺垫。
> 纪律：解构型（先推演应该是什么样）、非缝合怪、修订式追加不删、与 `00` A1–A12 地基严格对齐。

## 0. 一句话收口

> **5 大子系统（进程/内存/图形/用户/FS）经过 A/B 对比后，推荐取「**B 务实线**」作为 Day 1 主线、「**A 极简线**」作为长期演进目标——但内核模型（capability 唯一、Job 账本、Channel、VMO+pager、统一命名空间）在两条线上**完全一致**，A/B 差异仅在「Day 1 落地层」是否对存量生态暴露更多兼容投影；FS 是唯一例外，方案 A 不可变子集被嵌入方案 B 内的 `/msys` 系统组件区，两者并存而非互斥。**

## §1 总览：5 子系统 × 2 方案矩阵

> 每个 cell 一句话定位；细节见 §2–§6。

| 子系统 | 方案 A（极简/激进现代化） | 方案 B（务实/生态友好） | 共同地基（与 `00` A1–A12 对齐） |
|---|---|---|---|
| **进程管理**（46/47） | 消息传递 + 结构化并发**唯一范式**；无 fork、无全局 PID、无信号；`meu_spawn` 单轨（46） | 能力受限轻量进程 + 双轨（`meu_spawn` 主 + `meu_fork_light` 辅）+ Job 命名可查询 + scoped 可读标识 + SHM 一等公民（47） | `meu_spawn`、Job 资源账本 Day 1（A5）、Channel 唯一 IPC、capability 寻址、exception channel → 监督者（A9）、结构化取消 |
| **内存**（48/49） | **消灭**虚拟地址空间；Region 是漂浮于地址空间之外的能力化区间，访问靠"句柄 + offset"；CHERI 式精神（48） | **保留**进程线性虚拟地址空间；Region 是锚定在地址空间内的带权区间（携带 `vaddr`），稳定指针 + capability right；mkit 翻译路径最短（49） | VMO 数据持有者、VMO child COW 快照、pager 零拷贝、C1 折中 C（buddy 拥有物理页、refcount 单一真相源）、`mmap` 仅在兼容层、revoke 派生树回收、capability Day 1 |
| **图形**（50/51） | **保留模式场景图**（retained-mode scene graph）：客户端提交声明式 SceneNode，合成器持权威图并为**唯一能力网关**；与 Fuchsia Scenic 同构（50） | **客户端-合成器协议**（buffer-commit 语义）：客户端自持 window/surface 内容状态；合成器是协议对端+compositing 权威，**不**持 UI 权威图；GPU 走独立用户态服务（Magma 式）（51） | 合成器用户态、`SURFACE_*`/`DISPLAY_*`/`INPUT_RECEIVE`/`GPU_*` rights 冻结位（07 §4.1）、`DISPLAY_MODESET`/`GPU_MANAGE` 仅合成器与 3D 服务持有、VMO/device VMO 零拷贝、EventPort 就绪通知、无内核 DRM/GEM、Wayland 兼容层（D-G1 已采纳） |
| **用户系统**（52/53） | **无 UID/GID** 能力身份：身份 = capability 集合 + 符号名（不可自报、由 issuer 私钥签注）；内核、兼容层均无 uid 视图（52） | **最小传统兼容**：内核仍无 uid，但兼容层保留 UID/GID **合成视图**（零权限附着、纯展示/记账）+ 翻译层；真实身份仍是 capability 集合（53） | 句柄即 capability、无 root、`setuid` 禁止（C4）、setuid 映射为受限 spawn + 显式 capability、认证 = 受约束 capability minting（破 confused deputy，`07` §4.5）、Principal 公钥注册表信任锚复用 `32` 公钥根（`VERIFY`，bit 38，无新增 bit） |
| **文件系统**（54/55） | **内容寻址/不可变**：Blob 身份 = 内容哈希、不可变；目录 = 不可变 Tree 快照 + head Ref 重绑；路径与位置解耦，跨后端统一寻址（54） | **统一命名空间 + 可验证存储层**：文件走路径语义、可写，但每次写 CoW 出不可变 extent 版本；校验和/压缩/加密为透明层；POSIX 友好（55） | 统一命名空间 = capability 组合树（C3 已采纳）、每进程独立、默认不可见、显式 reveal；extent 级校验和/压缩/加密（覆盖密文）；`KEY_UNWRAP` 隐于 `READ`/`WRITE`（C2 已采纳、密钥 = capability）；`.msys` 原子更新 = 子树快照 + 命名空间原子 repoint（监督灰度）；VMO+pager 零拷贝 mmap；CoW B-tree、无 fsck；`BLOCK_*` rights（bit 23–27，第五轮） |

> **矩阵观察**：5 子系统的 A/B 在"抽象极简度"上**同向**——A 都更激进（无 PID/无地址/无 uid/无 uid/无路径语义/无 uid）；B 都更兼容（fork-light/线性 vaddr/window 概念/合成 uid 视图/路径语义）。两者**内核模型一致**，分歧只在"Day 1 用户/应用/兼容层对外暴露面"。

## §2 进程管理（46 vs 47）

### 2.1 A vs B 对比表

| 维度 | 方案 A（46·消息+结构化并发唯一） | 方案 B（47·能力受限轻量+务实双轨） |
|---|---|---|
| **核心抽象差异** | 进程 = 「Channel 挂接、Job 结构化 scope 兜底的并发任务子树」；**唯一范式**：消息传递 + 结构化并发 + capability 寻址；**四条铁律**：无 fork、无全局 PID、无信号、结构化并发唯一（46 §1.2） | 进程 = 「受 capability 约束的轻量执行单元」；Job 四合一（scope+账本+取消域+**命名可查询**）；**双轨创建**：`meu_spawn`（主轨，从零）+ `meu_fork_light`（辅轨，单线程 COW VMO 子、显式标注）；**SHM 提为一等非默认公民**；**scoped 可读标识**（展示层，非寻址层）（47 §1–§2） |
| **对传统 Unix 包袱的摆脱程度** | **彻底**：消灭 fork + COW 账本地狱、全局 PID 命名空间、POSIX 信号整套、cgroup 事后挂接、setuid 提权、僵尸进程、`/proc` 全局伪文件（46 §6.1） | **同基线 + 务实保留**：同摆脱全局 PID/信号/cgroup/setuid/僵尸；但保留"受限 fork 入口"（仅 `fork_light`、单线程、显式标注、不藏在兼容层）作为**显式旁路**而非 fork 逃逸（47 §6.1） |
| **生态/兼容代价** | **高**：所有 fork/信号/PID 丰富的 Linux 程序必须经 mkit（08）翻译；shell 管道、Go/Rust 全局态、JIT 代码缓存的"快速 fork"场景需重写为 `meu_spawn`+显式句柄注入（46 §6.2） | **中**：双轨降低运行时/工具落地阻力；`fork_light` 显式标注比藏进兼容层更可审计、对比 A 给兼容层实现更顺；scoped 标识降低运维学习成本（47 §6.2）。代价：TCB 与审计面略大于 A（fork_light 快照账本 + well-known name 解析面 + scoped 标识 tag 管理） |
| **与 capability 模型（07）的耦合** | 高度同构：可见性 = capability 句柄、无 capability 即不可见；"无全局 PID" = capability 寻址的直接推论（46 §4.4）；spawn 资源账本继承 `07` 维度 B | 高度同构 + 增量：scoped 标识是 capability 之上的**展示投影**（受 `DBG_INSPECT` 约束、非寻址层）；well-known name 绑定 = 受约束的 capability 委托（`07` §4.5），名字不是越权凭证（47 §4.4）；其它与 A 同 |
| **Day 1 可行性** | **脊柱必须 Day 1**：`meu_spawn`、结构化取消、exception channel、Channel 都在 M0–M1 落地（46 §5.1）；纯范式意味着所有应用必须按新范式写 | **脊柱必须 Day 1 + 务实旁路后置**：`meu_spawn`+Job 账本+结构化取消+Channel Day 1 必做（与 A 一致）；`fork_light` / well-known name / scoped 标识 / SHM 一等建议 Day 1 轻量起步，M2+ 大量使用（47 §5.1） |
| **TCB 量级** | **最小**（单一范式、单一创建原语） | **略大**（双轨 + 解析面 + 标识管理），仍远小于 Unix；`fork_light` 单线程+COW 子限定避免 C4 多线程 fork 雷区 |

### 2.2 推荐取向（粗决策）

> **B 作 Day 1 务实主线，A 作长期演进目标**——两者共享 capability + Job 账本 + Channel + 结构化取消地基，差异仅在"是否原生支持受限 fork 入口 / 命名可查询 / 显式 SHM / scoped 标识"四条务实旁路。Day 1 阶段 B 的双轨与展示层使 `mcc`+`meuos-libc` 与既有运行时/工具能以最小阻力落地；A 的「无 fork/无全局 PID/无信号/结构化并发唯一」四条铁律通过 mkit 兼容层翻译实现「内核纯、边界脏」的同向收敛，演进期可逐步把 B 的旁路收窄至 A 形态（无 breaking change，因 A 内核模型本就是 B 的子集）。

**支持论据**：
1. **自举终点优先**（`00` §1 / `11` §5）：`mcc`+`meuos-libc`+`mt`/`as`/`ld` 在 MeuOS 自举需要 mkit 兼容层广覆盖；B 的双轨让 mkit 翻译更顺、运行时/工具改写更少。
2. **Job 账本 Day 1 不变**（A5 已采纳）：B 的 Job 四合一只在 A 三合一上加"命名可查询"，不新增内核裁决权，与 A 的 Job scope 完全同源。
3. **结构化取消不被 B 削弱**：`fork_light` 单线程限定、归入父 Job、结构化取消照旧；不会出现 fork 出来的游离孤儿。
4. **A 的精神内核已被 B 吸收**：可见性=capability、句柄即能力、崩溃即回收、无 root、setuid 禁止——这些不变量 B 全保留，A 不变量 = B 不变量 ∩ A 旁路集 = 仍 B 不变量；故 A 形同 B 的"收紧形态"，演进时收旁路即可，无架构返工。

**风险与代价**：
- 需承担 B 的 4 条旁路 TCB：fork_light 快照账本（多核/大页/COW 正确性）、well-known name squatting 防护、scoped 标识 tag 生命周期、SHM 一等共享可变状态误用——这些 **P-G1** 须在后续 fine pass 基准化（见 §8）。

## §3 内存（48 vs 49）

### 3.1 A vs B 对比表

| 维度 | 方案 A（48·Region/能力单一抽象） | 方案 B（49·分页+区域混合·保留虚拟地址） |
|---|---|---|
| **核心抽象差异** | **消灭虚拟地址空间**：用户态以"Region 句柄 + offset"为中心；Region = 漂浮于地址空间之外的 capability 对象；虚拟地址 = 内核页表实现细节，**不对外承诺稳定**（48 §1.2）；精神近 Multics 段 + CHERI 指针 | **保留进程线性虚拟地址空间**：Region = 锚定在地址空间内的带权区间（携带 `vaddr`）；稳定指针 + capability right；`region_map` 返回稳定 vaddr（capability 化 mmap）（49 §1.2）；精神近 Linux vm_area + Fuchsia VMAR + Windows Section View |
| **对传统 Unix 包袱的摆脱程度** | **彻底**：消灭 `mmap`/`munmap`、匿名映射/`brk`、全局虚拟地址空间、全局 `page cache`、`MAP_SHARED/PRIVATE` 双语义、`madvise` 启发式、OOM-killer、独立 swap 子系统（48 §6.1） | **同基线 + 保留地址空间**：同摆脱过度匿名映射、全局 page cache、DAC 派生权限、OOM-killer、`MAP_*` 双语义；但**保留**线性地址空间与硬件分页原生语义（C/Rust 生态的承重墙）（49 §6.1） |
| **生态/兼容代价** | **高**：C 运行时（`malloc`/`setjmp`/TLS）、Rust 裸机目标、存量 Linux binary 的"返回指针"语义必须重写为"句柄+offset"；调试器/profiler 需读取 Region 视图而非 `/proc/pid/maps`（48 §6.2 / 49 §1.1 对照表） | **低**：`region_map` 返回 vaddr，与 `mmap` 语义近同构；mkit 翻译路径最短；libc/`malloc`/TLS/GOT 零改造（49 §1.1 对照表 / §6.2）；debugger/profiler 可走稳定 vaddr + 受约束 inspect |
| **与 capability 模型（07）的耦合** | 高度同构：Region 句柄 = capability、rights 随句柄、revoke 派生树回收；`unveil` 自然落到 Region 级（48 §4.3） | 高度同构：Region 句柄 = capability、`region_map`/`region_protect` 返回 vaddr 时即带 right（一步到位，无"先映射后 mprotect"两步）；同样落到 Region 级（49 §4.3）；rights 复用 `07` bit 0–6 基础位 |
| **Day 1 可行性** | Day 1 = M1–M5 + N1–N5（VMO/Region/AddressSpace/缺页+COW/rights），与 `03` 既有 VMO/VMAR 模型平行；mkit 翻译全部 `mmap`/`brk`/`mprotect`/`madvise` 为 VMO+Region（48 §5） | Day 1 = M1–M7 + N1–N5，**对 libc/运行时零改造**；mkit 翻译 `mmap` → `region_map` 路径最短（49 §5 / §4.6） |
| **TCB 量级** | **最小**（Region 漂浮、地址不出用户态、access 路径最短） | **略大**（保留地址空间布局、Region 分配器、ASLR、碎片管理），但 Region 携带 right 与 name 利于审计；unsafe 仍收敛在 `arch/mm` 与 `mm::raw`（49 §6.2.3） |

### 3.2 推荐取向（粗决策）

> **B 作 Day 1 主线，A 作长期演进目标**——两者共享 VMO 数据持有者、COW child、pager、`mmap` 仅在兼容层、revoke 派生树回收、C1 折中 C 物理归属、07 capability Day 1 的全部地基，差异仅在"虚拟地址空间是否对用户态可见、Region 是否携带 `vaddr`"。

**支持论据**：
1. **自举阻力最小**（`00` §1 / `11`）：`mcc`+`meuos-libc` 的 libc/`malloc`/TLS 全部依赖稳定指针，B 的"线性 VA 空间 + Region 携带 vaddr"是 **零改造**；A 需把整套 libc 重写为"句柄 + offset"模型，脱离上游——Day 1 不可接受。
2. **mkit 翻译路径最短**：B 的 `region_map` 返回 vaddr，与 `mmap` 语义近同构，08 翻译成本最低；A 需把"返回句柄+offset"伪装成"返回指针"，每处解引用都要翻译。
3. **与 `03` 现状最贴近**：B 把 VMAR 升级为"带 capability right 的 Region"——`03` M5/M6/M7（页表/地址空间布局/ASID）全盘继承；A 把 VMAR 解构为"漂浮 Region"——需重写地址空间模型。
4. **与进程 B 务实取向同向**：进程 B 的"轻量进程 + Job 内可密集"依赖于进程地址空间稳定；A 的"句柄+offset"模型与 B 的双轨创建存在语义摩擦。
5. **A 的精神内核已被 B 吸收**：B 的 Region 仍带 rights（capability 落 PTE R/W/X）、仍可命名可传递可 revoke——A 不变量 ⊂ B 不变量；演进时把"虚拟地址对外可见"收紧为"内部细节"是同向收敛，无架构返工。

**风险与代价**：
- B 仍管理地址空间布局（不重叠约束、ASLR、碎片），需 Region 分配器统一管。
- B 的 Region 句柄元数据（handle 槽 + right + 区间 + vaddr + name）比 A 略多，但与 VMA 红黑树同量级。
- 长期若想走 CHERI 硬件加速，A 抽象层（CHERI 段）更自然；B 仍可在 Region（对象级）落地，CHERI 作为底层强制，二者不重叠、可叠加——B 不阻塞 A 长期目标。

## §4 图形（50 vs 51）

### 4.1 A vs B 对比表

| 维度 | 方案 A（50·保留模式场景图+合成器唯一网关） | 方案 B（51·客户端-合成器协议+用户态 GPU 服务） |

| **生态/兼容代价** | **高**：原生 SDK 范式迁移——客户端不再"提交一块 buffer"，而是"提交声明式节点"；GTK/Qt/Flutter/Electron 等存量工具包全部 Wayland/X11 后端需重写"widget → SceneNode"映射（50 §2.1.1 / §7.2.3） | **低**：原生协议 ≈ Wayland `wl_surface`/`wl_buffer`，`wl_compositor` 全局即合成器本身；存量 Wayland 后端工具包**近 1:1 映射**；兼容层极薄（51 §5.1/§7.2）；Day 1 即可让 mkit 兼容 Wayland 客户端 |
| **与 capability 模型（07）的耦合** | 高度同构：客户端只持收窄 right（`SURFACE_SUBMIT`/`SURFACE_MANAGE`，无 `DISPLAY_*`/`GPU_MANAGE`）；session 令牌隔离；可能需新增 `SCENE_SESSION` 独立 right（bit 48+ 预留）以表达"session 令牌是否独立"（50 §A-D1） | 高度同构：客户端只持收窄 right（同 A）；**不需** `SCENE_SESSION` 独立 right——surface 句柄即全部图形 capability 边界（更简，51 §5.3）；rights 面比 A 略简 |
| **Day 1 可行性** | 合成器服务 + session mint + SceneNode 提交 + surface 句柄 + 零拷贝内容 + 输入路由；GPU 加速可软件合成后置（50 §6） | 合成器服务 + surface 句柄 + 客户端-合成器协议 + 零拷贝 + 输入路由 + GPU 服务（独立、Magma 式、软件起步）；兼容层极薄（51 §6） |
| **TCB 量级** | **最小**（单一能力网关、单张权威图、状态归一处） | **略大**（合成器 + GPU 服务双单点、协议面大于纯内核机制、需 ABI 演化纪律）——但故障域隔离更好，崩溃恢复 surface 句柄与 GPU 连接句柄可独立 revoke（51 §7.2.4） |

### 4.2 推荐取向（粗决策）

> **B 作 Day 1 务实主线，A 作长期演进纵深**——两者共享 D-G1（Wayland 兼容）/D-G2（GPU 受限委托）的 07 冻结 rights（`SURFACE_*` 35/41/42、`DISPLAY_*` 43/44/34、`INPUT_RECEIVE` 36、`GPU_*` 32/33、`CAP_RT` 45）。Day 1 走"客户端-合成器协议 + 用户态 GPU 服务"是**生态摩擦最小**的路径；A 的保留模式场景图作为长期演进方向，可与 B 在不同应用层共存（重度原生应用走 A 范式获得确定性、绝大多数应用走 B 范式获得生态兼容）。

**支持论据**：
1. **D-G1/D-G2 已采纳**：34 §8 落地"Wayland 兼容 + surface=capability + GPU 受限委托"是**兼容性基线**；B 是其"客户端-合成器协议 + 用户态 GPU 服务"纵深版，**零返工**。
2. **生态友好 = 自举阻力最小**（与 §2/§3 B 取舍同源）：GTK/Qt/Flutter/Electron 的 Wayland 后端直跑，Day 1 即可让既有 GUI 工具链落地。
3. **GPU 服务独立 = 故障域更好**：B 把 GPU 服务从合成器内嵌拆为独立用户态服务，与合成器可独立重启（surface 句柄 vs GPU 连接句柄分别 revoke）；A 的"合成器持权威图"是单点，崩溃恢复须重建所有 session 子树（50 A-D2）。
4. **rights 面更简**：B 不需 `SCENE_SESSION` 独立 right（surface 句柄即全部边界），rights 编排更收敛；A 提议的 `SCENE_SESSION` 占用 bit 48+ 预留位（50 A-D1）——可后置。
5. **A 的精神内核已被 B 吸收**：B 的合成器仍是"唯一能力网关"（mint surface 句柄、`SURFACE_*` 收窄、输入路由、`DISPLAY_MODESET`）；客户端不持特权 right；server 信任假设已除——A 不变量 ⊂ B 不变量。

**风险与代价**：
- B 协议面大于纯内核机制（client↔compositor 协议），需版本化/演进纪律（接 23 ABI 稳定性、37 IDL 唯一出口）。
- 合成器权威弱于 A：跨客户端一致性（统一动画时钟、全局布局策略）须由协议/约定协调。
- 长期若想推 A 的声明式场景图，需在 B 协议之上扩展"场景图增量子集"——是叠加而非替换。

**待精细裁决冲突**（C-G3，见 §7）：`SCENE_SESSION` 独立 right（bit 48+ 预留）vs surface 句柄即全部边界的取舍——B 不需、A 可能需——建议 **Day 1 不预留**，M2+ 若 A 范式应用增多再评估。

### 5.2 推荐取向（粗决策）

> **B 作 Day 1 务实主线，A 作长期演进目标**——**两者内核模型完全一致**（纯 capability、无 root、无 uid），差异只在"兼容层是否呈现并翻译 UID/GID"。推荐 B 是因为 C4 已采纳"uid/gid 仅为合成视图"作为 Day 1 立场，B 是该立场的完整操作化；A 形同"完全不启用 B 的翻译层"——若未来要走 A，只需不启用 B 的翻译层与合成视图，无架构返工。

**支持论据**：
1. **与既有裁决 C4 同源**（`00` §3 C4 / `08` D6）：B 是 C4 "uid/gid 仅为合成视图" 的**完整操作化**——把"一句话立场"扩展为"可执行设计"（合成视图 + 翻译规则 + 身份清单 + broker 受约束 mint）。
2. **POSIX 多用户生态友好**（与 §2/§3/§4 B 取舍同源）：容器运行时、守护进程以 uid 区分主体、按 uid 运维记账、`/var/log` 工具——B 让这些零改造落地。
3. **A 的精神内核已被 B 吸收**：内核都无 uid、capability 都是唯一真实权限源、`setuid` 都映射为受限 spawn + 显式 capability、认证都是受约束 capability minting（53 §7.1）；A 提议的"符号名不可自报、由 issuer 签注"在 B 中可作为合成 uid 标签的可信性保障（同源）。
4. **翻译面风险可控**：翻译层自身受限（`07` §4.6）；真实裁决只走 capability，错译最严重后果是"旧程序以为自己有权而 EPERM"（功能 bug，非安全洞）。

**风险与代价**：
- B 的翻译面需测试覆盖：`getuid`/`setuid`/`chown`/`chmod`/`access`/`capset` 映射规则必须正确、可审计（53 §6.2.1）。
- `geteuid()==0` 守卫逻辑无法总是完美翻译：部分程序写 `if (geteuid() == 0) do_privileged_thing()`，B 让 `geteuid()` 返回合成 0 让分支进入，再在该路径真实 syscall 处按 capability 裁决——若程序假定"root 必成功"而默默依赖，则仍 EPERM（53 §6.2.2）。
- 容器 uid 映射：Linux userns 的"容器内 uid ↔ 宿主"映射在 B 中变为"容器内合成 uid 视图 ↔ 真实 capability 作用域"的兼容投影，**真实隔离由 capability 兜底**，映射错误不应突破内核不变量（53 §8.3）。

**UID 兼容层启用与否**（待精细裁决冲突 C-G4）：B 的合成视图与翻译层建议 Day 1 启用（POSIX 多用户友好）；若 mkit 兼容层覆盖证明合成视图无显著价值，M2+ 可不启用、退回 A 形态。

2. **自举阻力最小**（与 §2/§3/§4/§5 B 取舍同源）：B 的路径语义让 `mcc`+`meuos-libc` 与海量 Linux binary 直跑；A 需"可写视图投影"层在 mkit 中实现，翻译成本大。
3. **A 的完整性收益已被 B 吸收**（55 §8.2）：B 在存储层内部用内容寻址的不可变 extent 承载每个可验证版本——两个不同路径若写入相同内容，底层 extent（同哈希）可共享去重（对齐 blobfs）。B 几乎拿到 A 全部完整性/去重收益，**唯一未获得的是"应用层可显式按内容寻址"的编程模型**——而那恰是 A 的生态摩擦来源。
4. **M6 路线图对齐**（`00` §4.2 M6）：`.msys` 签名 Overlay 原子更新回滚是方向①的落地峰；B 的 sysroot = 子树快照 + 原子 repoint 是 M6 的直接落点；A 的内容寻址在 `.msys` 内系统组件区做"防篡改 + 去重 + 内容指纹"增强。
5. **故障域最小**：B 把 FS 全用户态化（对齐 `06` §1.4、`00` A6），用户态独立迭代、不影响内核稳定性；A 的 GC 与 POSIX 投影是用户态 FS 内的成本，不污染内核 TCB。

**风险与代价**：
- B 的写放大/空间放大（CoW 固有）、命名空间 capability 路由成本、pager 缺页往返 IPC 延迟、压缩/加密 CPU——与 ZFS/Btrfs/ReFS/APFS 同量级（55 §7.2），需原型基准化（与 `06` §6-4 pager 基准同轮）。
- A 作为不可变子集需新增 GC 机制（A10，可达性 GC + 引用计数回收）；chunked 大文件 / 数据库 O_DIRECT 原子写需在 chunk 层处理。
- A/B 并存时命名空间 reveal/revoke 语义需协同 `06` §4.1 / `07` 定稿（**待精细裁决冲突 C-G5**）。

## §7 跨子系统综合（capability 地基 + Job 账本之上的统一）

### 7.1 5 子系统方案如何统一在 capability（07）+ Job 账本（29）地基上

5 子系统 A/B 的"内核模型"完全一致，都建立在以下六条不变量的互锁之上（与 `00` A1–A12 地基严格对齐）：

1. **句柄即 capability**（`00` A1 / `07` §4.1）：进程/线程/Job/Channel/Surface/Region/VMO/Ref/Principal/Session/Realm 全部是 capability 句柄；权限随句柄走、默认拒绝、崩溃即回收。
2. **Day 1 唯一 capability 模型**（`00` A2 / `07` §2.3）：内核不认 UID、不认虚拟地址（实现细节）、不认 POSIX 信号、不认全局 PID；任何"对应传统语义"都在兼容层（08）翻译。
3. **Rust 管安全关键路径**（`00` A3 / `02`）：cap 监视器、IPC 端点、调度核心、VFS 抽象、Region 分配、surface mint 监视器都用 Rust 入 TCB；C/asm 仅早期启动/asm 边界/Linux 兼容层。
4. **统一资源命名空间 = capability 组合树**（`00` A4 / C3）：每进程独立、默认全不可见、显式 reveal；`unveil` = 注入路径 capability 绑定；命名空间 = Realm 的资源投影。
5. **Job 资源账本 Day 1**（`00` A5 / `04` §4.4）：配额（CPU/内存/句柄/IO/进程线程数）内建于 Job；与 capability 边界同源挂在 Job 上；能耗弱耦合（第四轮已采纳）。
6. **尽快交权用户态缩 TCB**（`00` A6 / A11）：FS/网络/驱动/监督策略/合成器/GPU 服务出核（用户态 Rust，受 `meu-supervisor` 管理、可重启、可灰度）；内核只做最小事（机制 + 唯一裁决点）。

5 子系统的 A/B 分歧**全部在"是否对 Day 1 用户/应用/兼容层暴露兼容投影"**——B 多暴露一层（fork_light 入口 / 线性 vaddr / window 概念 / 合成 uid 视图 / POSIX 路径语义），A 一律不暴露。这层投影**只活在兼容层（08）+ 用户态服务（合成器/FS/监督者/身份 broker）**，**不进入内核裁决路径**——故 B 务实线不侵蚀 A 极简线的任何不变量，A 是 B 的"收紧形态"，演进无架构返工。

### 7.2 共性的"摆脱 Unix 包袱"主题（5 子系统同向收敛）

| 包袱 | 进程 | 内存 | 图形 | 用户 | FS |
|---|---|---|---|---|---|
| **全局可寻址命名空间** | A 无全局 PID；B 句柄 + scoped 标识（展示层） | A 句柄+offset；B 稳定 vaddr + right | A 无全局窗口树/registry；B surface=私有 capability | A 无 uid 字段；B 合成视图（兼容层） | A 路径=capability 路由；B 路径=capability 命名维度（C3） |
| **过度暴露/可达** | 句柄=唯一寻址 | 内存=Region 句柄 | surface=唯一引用 | 真实身份=cap-set | 文件=Ref 句柄 |
| **可变/原地改写** | 不可变派生树（grant 只能收窄） | VMO 不可变 + CoW child | 不可变 SceneNode + 不可变 surface VMO | capability 不可隐式提升 | 不可变 extent 版本 + head Ref 原子重绑 |
| **共享内存/通信** | Channel 唯一 IPC（rendezvous 不丢） | Region 共享=同 VMO 多 Region | surface content 共享=VMO cap-transfer | 会话 capability 模板继承 | Ref + mount-capability |
| **特权逃生舱** | 无 root（07 §2.3） | 无内核态匿名海洋 | 无 client 直连 GPU（render node 否决） | 无 uid=0 后门 | 无 global page cache 全局可写 |
| **DAC 派生权限** | rights 随句柄 | rights 随句柄 | rights 随句柄 | rights 随句柄 | rights 随句柄 |
| **O(n) 启发式调度** | Job 取消广播（结构化） | 惰性提交 + Job 配额硬上限（无 OOM-killer） | 合成器权威图（无 input snoop） | fail-closed pledge/unveil | extent 校验和（无 bit-rot 静默） |

> **同向收敛**：5 子系统都把"全局可寻址"压到 capability 句柄作用域内；都把"可变"压到"引用/head Ref"层；都把"特权"压到 capability 集合；都把"启发式"压到 capability 显式裁决。这是 00 §1「内核态只保留机制 + 唯一裁决点」在 5 子系统的具体落地。

### 7.4 仍待精细裁决的架构级冲突（C-G1 ~ C-G5）

> 5 项架构级冲突已识别，建议升级 `00` 冲突登记表为 C-G1 ~ C-G5；每项给"现状 + 推荐 + 需拍板方"，与 `00` §3 C1–C14 风格一致。

#### C-G1（进程·架构级）`meu_fork_light` 是否进原生 ABI
- **现状**：47 §2.6 主张把受限 fork 派生从兼容层慢路径提升为原生双轨之一（单线程、COW VMO 子、显式标注、归入父 Job、合成 uid 零权限）；§5.1 建议 Day 1 轻量起步；§7.1 列为 B 务实核心；与 C4（D2 fork 全量 CoW、多线程 fork 拒绝）完全兼容。
- **推荐裁决**：**进原生 ABI，作为 `meu_spawn` 的辅轨**——单线程限定、显式 `fork_light` 标注、归入父 Job、合成 uid 零权限。**理由**：（1）显式标注比藏进兼容层更可审计；（2）让 mkit 兼容层 fork 实现复用同一快照机制（VMO 子 + COW），无需双套代码；（3）满足语言运行时/工具落地的"快速派生"刚需；（4）C4 全部约束不破坏。
- **需精细定稿**：快照账本开销基准（P-G1.1，多核/大页/COW 正确性）；与 mkit 兼容层 fork 的接口边界（是否共用同一快照机制）；多线程调用返回 `EINVAL`/`ENOSYS` 的明确语义。
- **需拍板方**：04（`meu_fork_light` 原语边界）/ 08（兼容层 fork 翻译路径）。

#### C-G2（图形·架构级）A vs B 互斥候选拍板
- **现状**：50（A 保留模式场景图 + 合成器唯一网关）与 51（B 客户端-合成器协议 + 用户态 GPU 服务）是同一安全叙事（capability + 重服务出核 + GPU 不受控直连 + 无内核 DRM TCB）下取向不同的两条原生范式候选；51 §B-D6 显式列为**架构级待决**。
- **推荐裁决**：**B 作 Day 1 主线，A 作长期演进纵深**——两者 rights 面（D-G1/D-G2 已冻结）完全一致；A 的"合成器持权威图"可在 B 协议之上扩展"场景图增量子集"作为可选叠加；不强制二选一，原生应用可按需走 A 范式获得确定性、绝大多数应用走 B 范式获得生态兼容。
- **需精细定稿**：原生协议是否直接复用 Wayland wire 协议 + capability 作用域化，还是定义新的 `meu-idldef` 协议（与 `37` IDL 唯一出口协同，P-G3.1）；GPU 服务与合成器同 Job 还是分立 Job（故障域 + capability 委托拓扑，P-G3.2）；跨 session/surface 共享语义（cap 委托的拖拽/共享画布，P-G3.3）。
- **需拍板方**：34（图形主文档）/ 37（IDL 唯一出口）/ 50 与 51 owner 协同。

#### C-G3（图形·架构级）`SCENE_SESSION` 独立 right（bit 48+ 预留）vs surface 句柄即全部边界
- **现状**：50 §A-D1 提出"`SCENE_SESSION` 独立 right（bit 48+ 预留）"以显式区分"session 令牌"与 `SURFACE_CREATE` 上限；51 §5.3 主张**不需**（B 无 session 子树概念，surface 句柄即全部边界，rights 面更简）。
- **推荐裁决**：**Day 1 不预留**——B 主线不需 `SCENE_SESSION`；M2+ 若 A 范式应用增多、session 令牌需独立审计粒度，再评估是否占用 bit 48+ 预留位。**理由**：（1）rights bit 越收敛越好（45 第五轮已冻结 39–47，48+ 预留区是更长期资源）；（2）B 的"surface 句柄即全部"已足够审计（`DBG_INSPECT` 子树粒度可表达 session 视图）；（3）A 的 `SCENE_SESSION` 可在 `meu-idldef` 派生而非内核 right 实现。
- **需拍板方**：07（rights 位图）/ 34（图形主文档）。

#### C-G4（用户系统·架构级）合成 uid 兼容层启用 vs 极简身份
- **现状**：52（A 无 uid 字段、连合成视图都无）vs 53（B 兼容层保留 UID/GID 合成视图 + 翻译层）；C4 已采纳"uid/gid 仅作合成视图"作为 Day 1 立场；B 是该立场完整操作化。
- **推荐裁决**：**Day 1 启用 B 的合成视图 + 翻译层**（POSIX 多用户友好落地）；**M2+ 评估是否降级为 A 形态**（若 mkit 兼容层覆盖证明合成视图无显著价值、或 0 配置 footprint 优先）。**理由**：（1）C4 立场已为 Day 1 接纳合成视图铺路；（2）合成视图"零权限附着"安全无虞；（3）若未来决定走 A 形态，只需不启用 B 的翻译层，无架构返工。
- **需精细定稿**：合成 uid 稳定分配权威（P-G4.1，身份 broker + 策略清单持 "身份名 ↔ 合成 uid ↔ capability 模板" 映射）；`chown`/`chmod` 合成属性的存储归属（P-G4.2，FS 服务还是兼容层缓存）；容器 uid 映射的兼容投影边界（P-G4.3，Linux userns → 合成视图 + capability 兜底）。
- **需拍板方**：07（rights 位图）/ 08（兼容层翻译规则）/ 53 owner 协同。

#### C-G5（文件系统·架构级）A 不可变子集 + B 可变主线在统一命名空间的并存策略
- **现状**：54（A 内容寻址/不可变）与 55（B 路径语义/可写）非零和，55 §8.3 建议"方案 B 为 Day 1 主线、方案 A 作不可变系统组件子集、两者并存于统一命名空间"；Fuchsia minfs+blobfs 已证明此模式可行。
- **推荐裁决**：**B 为 Day 1 主线，A 仅在 `/msys` 系统组件区采用**（`/msys` 子树走 A 式内容寻址 Blob，天然防篡改 + 天然去重，且 hash 可兼 `.msys` 签名内容指纹）；通用读写走 B 路径语义可写。**理由**：（1）Fuchsia minfs+blobfs 范式已工程验证；（2）B 的"可变路径 + 不可变 extent 版本"在存储层内部已吸收 A 的完整性收益（55 §8.2）；（3）`.msys` 内系统组件天然适合不可变（启动/工具链/库文件不需写）；（4）两者在统一命名空间内通过 capability reveal/revoke 隔离，互不污染。
- **需精细定稿**：A/B 并存时命名空间 reveal/revoke 语义（与 `06` §4.1 / `07` 协同）；A 的 GC 机制（可达性 GC + 引用计数，P-G5.1）；A 的 head Ref CAS 冲突解决（多进程并发改同一目录的语义，P-G5.2）；A 不可变 Blob 的 `.msys` 签名内容指纹接入（`32` D-SB1 信任锚）。
- **需拍板方**：06（文件系统主文档）/ 07（命名空间 capability reveal/revoke）/ 54 与 55 owner 协同。
