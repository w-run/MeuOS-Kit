## 0. 合成说明与方法

- **输入**：`46`–`55` 共 10 份方案文档（逐子系统 A/B 对照），并读 `00`（总览与路线图）、`07`（安全模型·capability 基线）、`34`（显示与图形·D-G1/D-G2 已采纳）、`03`/`04`（内存 / 进程现状）、`06`（文件系统现状）做对齐。
- **方法**：解构型立场——先抽取每个方案「相对 Unix 包袱摆脱什么、付出什么代价、与 capability(07) 如何耦合、Day1 是否可行」，再逐子系统给出 A vs B 对比表与指挥官式粗决策。**本轮回合只做粗合层**，精细裁决留给第七轮「先细后精」。
- **一贯地基（5 子系统全部继承，无一例外）**：
  - `07` capability Day1 强制、无 root、句柄即 capability、派生只能收窄、崩溃即回收；
  - `04` Job 资源账本 Day1（A5）+ 结构化取消 / 异常上行（A9）；
  - `06`/`00` 每进程 namespace（C3，默认不可见、显式 reveal）；
  - `00` A2（Day1 唯一安全模型）、A4（统一资源命名空间）、A6（重服务出核缩 TCB）。
- **核心观察（贯穿全文）**：5 子系统 × 2 方案的「分歧」几乎**全部发生在「务实双轨 / 兼容层 / 子集并存」与「极简洁癖 / 长期愿景」之间**，而非安全不变量之争——所有方案都把 capability(07)+Job 账本当作唯一真相源，分歧只是「内核该把 Unix 包袱甩多干净」。这与 MeuOS「从零、现代化、capability Day1、兼容渐进」的既定立场严丝合缝。

## §1 总览矩阵：5 子系统 × 2 方案定位

| 子系统 | 方案 A 一句话定位 | 方案 B 一句话定位 |
|---|---|---|
| **进程管理**（46 / 47） | 消息传递 + 结构化并发作为**唯一范式**：无 fork、无全局 PID、无信号，Job = scope+账本+取消域三合一 | 能力受限**轻量进程** + Job 即资源树（命名可查询）的**务实双轨**：主轨 spawn、辅轨 `meu_fork_light`，外加 well-known name / scoped 标识三条旁路 |
| **内存**（48 / 49） | 以 **Region / 能力为单一抽象**：消灭虚拟地址空间概念，用户态以「Region 句柄 + offset」为中心，无 `mmap`/无匿名映射/无全局 `page cache` | 分页 + 区域**混合务实模型**：保留线性虚拟地址空间与硬件分页，Region 是「地址空间内带权的连续区间（携稳定 vaddr）」，`mmap` 仅在兼容层翻译 |
| **图形**（50 / 51） | **保留模式场景图** + 合成器即**唯一能力网关**：UI 唯一范式 = 声明式 SceneNode，合成器持权威图，无全局窗口树、无 window | **客户端-合成器协议** + 用户态 GPU 服务（Magma 式）：保留 window/surface 传统概念（capability 化），客户端自持内容状态，兼容层近乎零成本映射 Wayland |
| **用户系统**（52 / 53） | **capability 身份为核心、无传统 UID/GID** 的极简身份模型：内核连合成 uid 都不给，身份即 capability 集合本身 | **最小传统兼容 + capability 叠加**：内核同样纯 capability、无 uid，但兼容层保留 **UID/GID 合成视图 + 凭据翻译层**（零权限附着） |
| **文件系统**（54 / 55） | **内容寻址 / 不可变** + 统一命名空间：文件 = 内容哈希寻址的不可变 Blob，目录 = 不可变 Tree 快照 + head Ref 重绑 | **统一命名空间 + 可验证存储层**：文件走路径语义、可写，每次写产生一个可验证版本（CoW extent），校验和/压缩/加密为透明层 |

> 矩阵读法：A 列普遍是「更激进现代化 / 更极简 / 对存量生态更不友好」；B 列普遍是「更务实 / 兼容渐进 / 对 POSIX 与存量二进制更友好」。两者安全地基（capability(07)+Job 账本）完全相同，分歧只在外扩程度。

## §2 进程管理（46 A / 47 B）

### §2.1 A vs B 对比表

| 维度 | 方案 A（46·极简唯一范式） | 方案 B（47·务实双轨） |
|---|---|---|
| 核心抽象差异 | 消息传递 + 结构化并发**唯一范式**；Job = scope+账本+取消域三合一；无 fork / 无全局 PID / 无信号 | 轻量进程（Job 内可密集）+ Job 命名可查询沙箱单元；双轨创建（`meu_spawn` + `meu_fork_light`） |
| 对传统包袱的摆脱程度 | **最彻底**：四条铁律永不退化（无 fork / 无 PID / 无信号 / 结构化并发唯一）；僵尸/孤儿/signal 竞态整体消灭 | **同基线但留三条原生旁路**：fork_light（受限快照派生）、well-known name、scoped 标识；包袱基本消灭，但保留「可寻址名字」「可读标识」 |
| 生态 / 兼容代价 | 最高：fork/exec/信号/PID 丰富程序只能走 mkit 翻译；shell 管道/JIT 写时复制依赖需改写 | 较低：fork_light 让语言运行时/shell 友好，well-known name 让守护进程 socket-activation 式落地；mkit 翻译更顺 |
| 与 capability 模型(07) 的耦合 | 完全一致：可见性=capability、无 PID 即 capability 推论、无 root | 完全一致 + 把名字绑定建模为「受约束的能力委托」、scoped 标识建模为「capability 之上的展示层」 |
| Day1 可行性 | 可行但自举阻力大（句柄显式注入啰嗦、运行时友好度低） | **Day1 阻力更小**（fork_light + Job 命名 + scoped 标识对自举与运维更友好，建议 Day1 同期落地） |

### §2.2 推荐取向（指挥官式粗决策）

> **推荐 B 作 Day1 务实主线，A 作长期演进目标。**

- **主线（B）**：`meu_fork_light` 双轨 + Job 命名可查询 + scoped 可读标识，对语言运行时、shell、存量守护进程与运维观测最友好；其三条旁路均被 capability 与 Job 双重约束，**不回退任何安全不变量**（无 root、无全局 PID、无信号、结构化取消唯一）。
- **长期目标（A）**：A 的「无 fork 原生 / 纯句柄寻址 / 结构化并发唯一范式」是形式化与 TCB 极致场景的理想终点，其四条铁律应作为**不可逆方向**写进进程模型定稿——B 只是把 fork_light 提升为原生过渡原语，最终收敛到 A 的洁癖是可预期的。
- **判断依据**：MeuOS 既定「spawn 模型 + 兼容层对接已有生态二进制」（README 三大方向②），B 的务实双轨与「兼容渐进」立场一致，自举阻力最小。

## §3 内存（48 A / 49 B）

### §3.1 A vs B 对比表

| 维度 | 方案 A（48·Region/能力单一抽象） | 方案 B（49·分页+区域混合） |
|---|---|---|
| 核心抽象差异 | **消灭虚拟地址空间**：用户态以「Region 句柄 + offset」为中心，虚拟地址降为内核实现细节、不对外承诺稳定 | **保留线性虚拟地址空间**：Region 是地址空间内带权的连续区间，**携稳定 vaddr**，指针可运算 |
| 对传统包袱的摆脱程度 | 最彻底：无 `mmap`/`munmap`、无匿名映射/`brk`、无全局 `page cache`、无 OOM-killer | 同样摆脱过度匿名映射/`page cache`/DAC 派生权限/OOM-killer，但**不把「虚拟地址空间」列为包袱**（只清其上的错误抽象） |
| 生态 / 兼容代价 | 高：libc/`malloc`/`setjmp`/TLS 需重写为「句柄+offset」模型，脱离上游；Rust 裸机 target 假定 `usize`=地址需定制 | **低**：保留地址空间，`malloc` 返回 `void*`、TLS/GOT/PLT 直接成立，Rust 标准模型直接成立，`mkit` 翻译路径最短 |
| 与 capability 模型(07) 的耦合 | 完全一致：Region 句柄=capability、权限随句柄、revoke 派生树回收 | 完全一致（同 A），仅 Region 额外携带 vaddr（权限仍落 PTE R/W/X） |
| Day1 可行性 | 可行但**自举阻力最大**（工具链/运行时全改） | **Day1 阻力最小**（对 libc·运行时·存量 binary 零改造，M1–M7+N1–N5 即可自举） |

> 两方案**数据模型完全兼容**：VMO 持有数据、COW child、pager 零拷贝、revoke 派生树回收、C1 折中 C 物理归属——唯一决定性分叉是「虚拟地址空间是否对用户态可见 / Region 是否携带 vaddr」。

### §3.2 推荐取向（指挥官式粗决策）

> **推荐 B 作 Day1 主线，A 作长期 / CHERI 友好 / 形式化愿景。**

- **主线（B）**：保留稳定 vaddr，使 `mcc`+`meuos-libc`、Rust 裸机 target、海量 Linux 二进制以熟悉语义零改造自举；`mmap` 由 `mkit` 翻译为 `region_map`（返回 vaddr），翻译路径最短。
- **长期愿景（A）**：A 的「Region 漂浮名词 + CHERI 式对象级 capability」是去裸指针、形式化友好、硬件能力化（CHERI）的极致方向；待工具链/CHERI 就绪可作为可选内存模型并存（内核数据模型不变，只是「用户界面」切换）。
- **判断依据**：自举终点是 `mcc`+`meuos-libc` 在自研内核跑通（README），B 对自举阻力最小，与「从零但兼容」一致。

## §4 图形（50 A / 51 B）

### §4.1 A vs B 对比表

| 维度 | 方案 A（50·保留模式场景图） | 方案 B（51·客户端-合成器协议） |
|---|---|---|
| 核心抽象差异 | UI 唯一范式 = **保留模式场景图**（SceneNode）；合成器持**权威图**且为唯一能力网关；无全局窗口树、无游离 window | UI 原生范式 = **客户端-合成器协议（buffer-commit）**；保留 window/surface 传统概念（capability 化），客户端自持内容状态 |
| 对传统包袱的摆脱程度 | 最彻底：去 immediate 协议、去全局树探测、去 server 信任、去 GPU 直连逃逸、去内核 DRM TCB | 同去 X11 immediate / 全局 registry / render node / 内核 DRM TCB，但**不强制保留模式场景图**（保留 window/surface 传统概念） |
| 生态 / 兼容代价 | 高：GTK/Qt/Flutter/Electron 需重写「widget→SceneNode」层；Wayland 兼容层是厚翻译 | **低**：原生协议 ≈ Wayland `wl_surface`/`wl_buffer` 近 1:1 映射，兼容层极薄 |
| 与 capability 模型(07) 的耦合 | 一致（复用 07 冻结位图，可能需新增 `SCENE_SESSION` bit 48+） | 一致（**不需** `SCENE_SESSION`，surface 句柄即全部图形 capability 边界，rights 面更简） |
| Day1 可行性 | 可行但新 SDK 成本高、合成器单点更重 | **Day1 阻力更小**（与 D-G1 Wayland 兼容天然契合，GPU 服务与合成器并列可独立重启） |

> 两方案共享同一安全叙事（capability 唯一 + 重服务出核 + GPU 不受控直连 + 无内核 DRM TCB），差异在**原生 UI 范式与抽象结构**——A 把客户端降为「声明式节点提交者」、合成器升为「UI 图唯一所有者」；B 保留客户端自持 window/surface 的协议。

### §4.2 推荐取向（指挥官式粗决策）

> **推荐 B 作 Day1 主线，A 作全新原生 app 的长期方向；但 A/B 原生范式互斥，需补登架构裁决 C-G3。**

- **主线（B）**：客户端-合成器协议 ≈ Wayland 近亲，存量 GUI 生态（GTK/Qt/Flutter/Electron）Wayland 后端近乎零成本映射，且与 `34` 已采纳的 D-G1（Day1 Wayland 兼容）天然契合；GPU 服务独立可重启，故障域更清晰。
- **长期方向（A）**：保留模式场景图是确定性/可控/新原生 SDK 的极致现代化方向，适合「愿接受新 SDK 的全新原生应用」；其 `SCENE_SESSION` 待决项（bit 48+）需与 07 协同定稿。
- **必须补登裁决**：A/B 是**互斥候选**（50 §9 A-D1 / 51 §9 B-D6 已呼吁），建议按 `00` 冲突登记表纪律新增 **C-G3（图形原生 UI 范式：保留模式场景图 vs 客户端-合成器协议）**，由指挥官拍板「取一或取公约数（如客户端-合成器协议 + 可选保留模式扩展）」。

## §5 用户系统（52 A / 53 B）

### §5.1 A vs B 对比表

| 维度 | 方案 A（52·无 UID/GID 能力身份） | 方案 B（53·UID/GID 合成投影 + capability） |
|---|---|---|
| 核心抽象差异 | 身份 = capability 集合本身；内核**连合成 uid 都不给**，无数字 UID/GID、无 root | 内核**同样纯 capability、无 uid**；兼容层保留 **UID/GID 合成视图 + 凭据翻译层**（零权限附着） |
| 对传统包袱的摆脱程度 | 最彻底：无 uid=0 后门、无 setuid 提权、无 DAC 权限位裁决、无 `/etc/passwd` 全局表 | 同甩 uid=0/setuid/DAC 裁决（内核不变），仅把 uid/gid 建模为「零权限附着的展示/记账键」 |
| 生态 / 兼容代价 | 高：POSIX 多用户语义（`getuid`/`chown`/`sudo`/按 uid 记账）需深改或彻底舍弃 | **低**：翻译层把 `getuid`/`setuid`/`chown`/`access` 映射为 capability 操作或返回合成值，容器/守护进程以 uid 区分主体直接兼容 |
| 与 capability 模型(07) 的耦合 | 完全一致（新增内核对象仅 `koid=session`，无新增 right） | 完全一致（内核模型与 A 100% 相同，仅兼容层增量；与 C4「uid 仅为合成视图」同源） |
| Day1 可行性 | 可行但多用户生态需重写 | **Day1 阻力更小**（单用户自举即可；多用户登录/认证 broker 后置，合成 uid 视图建议 Day1 轻量落地） |

> **关键结论**：A 与 B 在**内核层 100% 一致**（都是纯 capability、无 root、无 uid）。B 不是 A 的对手，而是 A 的**兼容层扩展**——分歧只在「兼容层是否呈现并翻译 UID/GID」。

### §5.2 推荐取向（指挥官式粗决策）

> **推荐「两者共存」：内核走 A 的纯 capability 身份模型（无 uid、无 root），兼容层启用 B 的合成 UID/GID 视图 + 凭据翻译层。**

- **内核真相（A）**：身份 = capability 集合，无 uid、无 root、无 setuid 提权，Session 绑定 Job 子树——这是不可退让的安全地基。
- **兼容投影（B）**：B 是 C4「uid/gid 仅为合成视图」的操作化落地（C4 已承接，B 把它从一句话扩展为可执行设计）；启用 B 的翻译层后，POSIX 多用户/容器/守护进程以 uid 区分主体直接兼容，**零权限附着、不侵蚀任何内核不变量**。
- **判断依据**：两者内核模型完全相同，不存在「选 A 就必须弃 B」；启用 B 只是「不启用 B 的翻译层」的逆操作，**无架构返工**。故推荐「A 为内核真相 + B 为兼容投影」共存，而非二选一。

## §6 文件系统（54 A / 55 B）

### §6.1 A vs B 对比表

| 维度 | 方案 A（54·内容寻址 / 不可变） | 方案 B（55·统一命名空间 + 可验证存储层） |
|---|---|---|
| 核心抽象差异 | 文件身份 = **内容哈希**（hash=名/校验和/去重）；写 = 新不可变 Blob + 引用切换；目录 = 不可变 Tree 快照 + head Ref 重绑 | 文件身份 = **路径**；文件可写，每次写产生一个**可验证版本**（CoW extent）；校验和/压缩/加密为透明层 |
| 对传统包袱的摆脱程度 | 最彻底：无 inode 歧义、无「写一半」窗口、无路径即位置耦合、无挂载点碎片化 | 同甩 fsck/全局可变命名空间/DAC/原地覆写/整盘一密钥，但**保留路径语义与可变文件**（写=CoW 版本链） |
| 生态 / 兼容代价 | 高：需内容寻址工具链 / ABI 适配，POSIX 可变语义需经「可写视图→新 Blob→head 重绑」投影 | **低**：POSIX / 存量工具原样可跑（open/read/write/rename/mmap 不变），验证层渐进叠加 |
| 与 capability 模型(07) 的耦合 | 一致（路径=capability 维度、密钥=capability(C2)、每进程 namespace(C3)） | 一致（更强：路径=cap 维度、密钥=cap，继承 `06` 全部 C2/C3 定稿） |
| Day1 可行性 | 可行（A1–A6 即可自举）但写放大/GC 压力为独有代价 | **Day1 阻力更小**（B1–B5+F1–F5+F6 即得 POSIX 可变文件 + CoW + extent 校验和，全程不改应用 API） |

> 两方案**非零和**：B 在存储层内部仍用内容寻址的不可变 extent 承载每个可验证版本（同内容同哈希可去重），只是不把内容寻址暴露到应用 API；A 的完整性/去重收益 B 几乎全拿，唯一未直接获得的是「应用层显式按内容寻址」的编程模型（而这恰是 A 的生态摩擦源）。

### §6.2 推荐取向（指挥官式粗决策）

> **推荐「两者共存于不同层」：B 作 Day1 主线（通用读写），A 作不可变系统组件子集（/msys、只读资产、可复现构建）。**

- **主线（B）**：保留路径语义、对 POSIX/存量工具友好，使 `mcc`+`meuos-libc` 与海量 Linux 二进制无需重写即可运行；校验和/压缩/加密在其上渐进叠加，非前置门槛。
- **不可变子集（A）**：对 `.msys` 内系统组件、只读资产、可复现构建产物，采用 A 式内容寻址 blob（Fuchsia blobfs 思想），天然防篡改且省空间；其 hash 还可兼作 `.msys` 签名校验内容指纹。
- **统一收口**：以统一命名空间把两类后端聚合并存（Fuchsia 已是 minfs 可变 + blobfs 不可变并存先例）——`/msys` 子系统组件走 A、通用读写走 B，应用经同一套句柄/rights 访问。需细化两者在统一命名空间内的 reveal/revoke 边界（见 §7.3 冲突 5）。

## §7 跨子系统综合

### §7.1 五方案统一在 capability(07) + Job 账本地基上

所有 10 份方案（5 子系统 × 2）都在**同一组不可退让的地基**上展开，分歧只是「外扩到哪一层」：

| 地基（已采纳，非本轮议题） | 来源 | 在 5 子系统方案中的体现 |
|---|---|---|
| capability Day1、无 root、句柄即 capability、派生收窄、崩溃回收 | `07` §4.1 / §4.5 | 进程：可见性=capability；内存：Region/VMO 句柄=capability；图形：surface/node 句柄=capability；用户：身份=cap-set；文件：Ref+rights=capability |
| Job 资源账本 Day1（配额硬上限、fail-closed 无 OOM-killer） | A5 / `04` §4.4 | 进程 Job=账本+scope+取消域；内存 Job 内存配额=提交上限；用户 Session=Job 子树+cap 模板；文件版本/快照回收可计入 Job 账本 |
| 结构化取消 / 异常上行（无僵尸/孤儿） | A9 / `04` §4.6 | 进程结构化并发唯一范式；用户会话注销=Job 树取消；文件快照/回滚=命名空间 repoint |
| 每进程 namespace（默认不可见、显式 reveal） | C3 / `06` | 进程无全局 PID 表；内存 Region 可见性=capability；图形无全局窗口树；用户 cap-set 作用域=Realm；文件路径=capability 路由 |
| 重服务出核缩 TCB（用户态合成器/FS/网络/GPU） | A6 / `00` | 图形合成器·GPU 服务用户态；文件 FS 用户态+pager；用户认证 broker 用户态；进程监督者用户态 |

> 结论：5 子系统方案**不是互相冲突的安全模型之争**，而是「同一 capability+Job 地基上的现代化程度光谱」——A 普遍在光谱极简端（甩包袱最干净），B 普遍在务实端（留兼容旁路/子集）。

### §7.2 共性主题与共性代价

**共性「摆脱 Unix 包袱」主题（5 子系统同构）**：
1. 全局整数命名空间（PID / uid / inode / XID）整体消亡，改为「持句柄即可见、可见性=capability」。
2. 隐式提权路径（root / setuid / CAP_SYS_ADMIN / 全局 DAC）整体消亡，改显式受限 mint + 派生收窄。
3. 事后挂接式资源治理（cgroups / mount 全局树 / `/proc` 全局伪文件）整体消亡，改 Job 账本 Day1 内建 + 每进程 namespace。
4. 内核态巨型服务（DRM/GEM / 内核 FS / 内核网络）整体出核，改用户态受监督服务 + capability 网关。

**共性代价（5 子系统同构，必须在精细阶段量化）**：
- **兼容层翻译成本**：所有「原生不提供 Unix 语义」的方案都依赖 `mkit`(`08`) 翻译 fork/信号/PID/mmap/uid/inode 等；A 取向翻译面更大，B 取向更小，但都存在。
- **运维 / 心智模型改变**：无全局 `ps`/`kill`/`ls -l` 权限列/`who`，观测走监督者持有的 Job/Realm 子树 introspect 视图（受 `DBG_INSPECT`）——学习成本客观存在。
- **新 SDK / 工具链成本**：图形新原生 IDL（`meu-idldef`）、用户系统身份治理 CLI、文件系统 inspect 视图等需新建。
- **TDB / 验证红利**：单一范式、小 TCB、可联合推理（审计只需看句柄集+rights，而非 uid+cap bounding+SELinux+seccomp+namespace 五套交叉）是共性收益，对 `20`/`44` 形式化利好。

## §8 后续精细（fine）阶段建议

第七轮「先细后精」应优先深入以下点（按依赖与风险排序）：

1. **图形 C-G3 补登与裁决**（最高优先）：把 50/51 的 A/B 互斥候选按 `00` 冲突登记表纪律登记为 C-G3，明确「取一或取公约数」，并定 `SCENE_SESSION` 取舍（冲突 3 / 7）。
2. **内存 vaddr 承载对工具链的精确 ABI 影响**（冲突 2）：以 `mcc`+`meuos-libc` 与 Rust 裸机 target 为基准，验证 B 的 `region_map` 返回 vaddr 是否零改造；同时评估 A 的「句柄+offset」模型作为可选 CHERI 友好内存界面的可行性。
3. **进程 fork_light 快照账本基准**（冲突 1）：在原型上测密集 `fork_light` 的 VMO 子快照 + COW 正确性（写时复制/大页/多核），定默认-deny 句柄继承粒度。
4. **用户系统 B 翻译层规则基准**（冲突 4）：把 `getuid`/`setuid`/`chown`/`access` 映射为 capability 操作或合成值，覆盖 `geteuid()==0` 守卫逻辑与容器 uid 映射，给出测试基准。
5. **文件系统 A/B namespace 边界与回收归属**（冲突 5）：定 `/msys`(A) 与通用(B) 在统一命名空间内的 reveal/revoke 语义；定可验证版本链/快照的引用计数与 age-out 归属（FS 服务自管 vs 计入 Job 账本 `04`）。
6. **跨子系统展示层标识统一 IDL**（冲突 6）：把进程 `scoped 标识`、用户 `合成 uid 视图`、图形 `session 令牌` 统一为「capability 之上的展示层」设计语言，明确 tag 生命周期与 `DBG_INSPECT` 约束，避免三套碎片（协同 `37` IDL 唯一出口）。
7. **bit 48+ 新增 right 统一评审**（冲突 7）：`SCENE_SESSION` / `AUTH_ISSUE` / `ID_ISSUER` 是否新增，统一进 `07` rights 位图预留区纪律。
8. **A7 多 realm 边界**（冲突 8）：定跨 realm 取消/能力/命名传播的默认不穿透策略（capability 边界即 realm 边界）。
