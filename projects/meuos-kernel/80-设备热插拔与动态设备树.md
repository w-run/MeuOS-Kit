## 0. 核心结论（一句话）

> **设备发现以动态设备树/ACPI 枚举为内核薄层、驱动经 capability 委托用户态（L3 优先）；热插拔事件经 `59` interrupt/event 对象上行、触发用户态驱动按需 attach/detach；device VMO + IRQ cap 经 capability 受约束委托（与 `60`/`10` 同构）；五架构枚举差异（DT/ACPI/PCIe）封薄后端。**

## 1. 动态枚举薄层（DT / ACPI / PCIe 发现；与 `09` 自举期静态设备树衔接）

### 1.1 解构型推演：「枚举」在 capability 内核里应该是什么

不问「MeuOS 怎么抄 Linux 的 `device_add` / udev uevent 链路」，而问：在 `09` 已把「设备发现」定为「**可信设备拓扑树 → capability 监视器 mint 设备 cap**」的模型里，**运行期动态发现**本应是什么。

推演结论：

1. 冷启动时的设备树（`09` Stage 2 从 DT/ACPI 抽出的「设备节点 + 资源区间」）是**启动期快照**——它本质上就是运行期枚举薄层的**一次性输入**。
2. 运行期插入一个设备 = 向**同一棵可信设备拓扑树**追加一个节点；拔出 = 删除一个节点。枚举薄层的职责**只是**「把硬件可观测事实（总线扫描结果）归一化为节点结构」，**不**是「建模一个复杂的内核设备对象」。
3. 归一化后的节点结构与 `10` §2.3 的「设备拓扑树」、与 `09` §5.2 Stage 2 的「设备拓扑树雏形」**同一数据模型**——运行期枚举 = 该数据模型的**增量写入者**，而非新抽象。

> 核心判据：**枚举薄层不引入新内核对象**。它只是 `09` Stage 2 拓扑抽取逻辑的「运行时可重入版本」+ capability 监视器在 `09` Stage 4 已 mint 设备 cap 所用的「可信设备拓扑树」的增量维护者。这与 `59` §2.4「把 interrupt 显式列为 `07` 内核对象清单、零冲突纯补齐」的纪律同源——能复用既有结构就不另立原语。

### 1.2 三类枚举源与统一归一化

| 枚举源 | 主要架构 | 探测机制（薄后端职责） | 归一化输出 |
|--------|----------|------------------------|------------|
| **DT（设备树）** | ARM64 / RISC-V /（LoongArch DT 变体） | 解析 `*.dtb` 的节点树（`compatible`/`reg`/`interrupts` 属性）；运行期 DT overlay 追加节点 | 节点 = `{bus, addr, compatible, 资源区间(MMIO/IRQ/DMA/IO port)}` |
| **ACPI** | x86_64 / LoongArch | 解析 DSDT/SSDT 的 `Device()` 对象 + `_CRS` 资源；命名空间遍历 | 同上，节点结构同源 |
| **PCIe（含根复合体扫描）** | 全架构（virtio/真实 NIC/存储均走 PCIe） | 枚举根总线 → 配置空间遍历 → VID:PID/类代码/Bar 区间；**native hotplug** 经 Presence Detect / Attention Button / PME 中断 | 节点 = `{bus:dev:func, VID:PID, class, BAR 区间, 链路能力}` |

- **统一归一化结构**：无论来源，枚举薄层产出`{bus, addr, compatible/VID:PID, 资源区间}`四元组，与 `10` §2.3「设备拓扑树」、与 `09` §5.4「设备能力签发所用的资源区间」**同构**——驱动只需声明「我绑定哪个 compatible / 哪条 VID:PID」，无需知道物理布局（`10` §4.5 解耦）。
- **探测向后端收敛**：DT 解析器、ACPI 命名空间 walker、PCIe 配置扫描器是**三个薄后端**，差异封死在 `arch`/`platform` 层；上层的「节点 → 资源区间 → 入可信拓扑树」逻辑五架构同源（`00` §5.3 一致性成本）。
- **NUMA 拓扑复用**：枚举同时记录设备所属 NUMA node（`76` §2.1 `numa_topo`），供 `76` §5 device VMO 后端按 node 取连续页；该信息直接从 `09` §6-9「多架构 bootinfo 归一化含 NUMA」结构继承，不另立。

### 1.3 与 `09` 自举期静态设备树的衔接（单一真相源）

| 阶段 | 拓扑来源 | 枚举薄层角色 |
|------|----------|--------------|
| `09` Stage 2（冷启动） | bootinfo（DT/ACPI/multiboot）一次性解析 | 抽静态快照 → 填可信设备拓扑树 |
| `09` Stage 4 | 监视器从拓扑树 mint 设备 cap | 消费静态快照 |
| 运行期（本文） | 总线热事件 / ACPI notify / DT overlay | **同一薄层增量写**同一棵拓扑树 → 触发按需 attach |

- **单一真相源不破**：运行期枚举与冷启动枚举写入**同一个**可信设备拓扑树结构（`09` 已建），不另开「动态设备表」——避免 `03`/`76` 反复强调的「第二真相源」反模式（对齐 `76` §1.1「buddy 独占物理页、VMO 仅逻辑视图」的同构纪律）。
- **fail-closed 枚举**：枚举薄层只产出「**描述**」，不自行授权；节点入树后须经 devmgr 匹配 + capability 监视器受约束 mint 才能成为 cap（`10` C8）。误报/恶意枚举（如虚构一个不存在的 MMIO 区间）在 mint 环节被监视器校验拒绝，**不**直接获得硬件访问权（最小权限，`07` A1）。

## 2. 驱动用户态化（L3 优先；热插拔触发按需 attach/detach；与 `60` L1+L3、`10` 双轨衔接）

### 2.1 热插拔设备天然落在 L3（与 `60` §2.3 决策框架同构）

`60` §2.2 决策表把「延迟预算/故障域/IOMMU/TCB」作为驱动位置的四判据。热插拔设备（USB/网卡/存储/显示/串口扩展/部分 PCIe 功能卡）几乎全部满足「崩溃可重启、毫秒级可接受的 I/O、有 IOMMU 域隔离」→ **默认 L3 用户态驱动**（`60` §2.3 L3 档位）。生死相关设备（中断控制器/定时器/看门狗）**不参与热插拔**，维持 L1 内核态（`60` §2.3 L1）。

> 与 `10` 双轨同构：热插拔 attach/detach 复用 `10` §4.3 的「匹配 → 授权 → 启动 → 看门狗」状态机与「驱动管理器 devmgr + 能力网关」，**不**新建设备管理原语。差异仅在「触发源从冷启动变为运行时枚举事件」。

### 2.2 按需 attach（枚举 → 匹配 → 授权 → spawn）

```
枚举薄层产出节点（§1）
   │ devmgr 比对驱动 bind 规则（compatible / VID:PID / class）
   ▼
匹配成功 → devmgr 请求 capability 监视器（受约束 mint right）为驱动 fresh-mint 第①层设备 cap
   │ {Cap(MMIO range), Cap(IRQ n), Cap(DMA window)}（10 §2.4 / 60 §3.1）
   ▼
驱动进程以「仅持上述 cap」spawn（受 04 §4.4 Job 账本约束：CPU/内存/句柄/IO 配额）
   │ 经 05 EventPort 收 IRQ（§3）/ 经 device VMO 走数据通路（§5）
   ▼
运行（看门狗 ping；exception channel 上行 04/12）
```

- **受约束 mint（防 confused deputy）**：devmgr 持「受约束的 mint right（限定设备 cap 类、限定 Job 子树）」（`10` C8 / `07` §4.5），请求监视器 mint 恰好驱动声明所需资源——与冷启动授权**同一路径**（`60` §4.2），不引入「热插拔专用授权」。
- **声明即授权**：驱动 `bind` 声明的资源 ⊂ 枚举节点资源区间；越界请求在 mint 环节被拒（`10` §4.6 最小权限）。

### 2.3 按需 detach（拔出/失效 → 撤销锁序列 → 回收）

设备移除（PCIe Presence Detect 失活 / ACPI 拔出 notify / DT overlay 删除节点）→ 触发与 `10` C8 撤销锁序列**完全同构**的回收（`60` §3.5 / `59` §4.4）：

1. 屏蔽该设备 IRQ 转发（防 revoke 后还来中断）；
2. 冻结驱动进程（不再发起新 MMIO）；
3. IOMMU 域对该驱动失效/解映射（截断在飞 DMA，`76` §5.1）；
4. revoke 设备 cap 句柄（从进程句柄表移除、记 dead）；
5. kill + 释放地址空间；
6. 仅全部完成后，该（设备, 资源区间）的 cap 记录 reclaim——**同一区间任一时刻至多一个 live cap**（`10` C8 第二重保险）。

> **进程死亡自动回收（第二重保险）**：持 cap 的驱动进程异常死亡 → 内核自动回收其全部句柄（`10` C8 / `59` §4.4），旧 cap 已 reclaim，新实例拿重新 mint 的 cap——与冷启动路径同源，热插拔只是把「spawn」变为「按需」。

## 3. 热插拔事件通路（`59` interrupt/event 对象上行；用户态驱动生命周期）

### 3.1 事件源与统一上行通道

热插拔的「物理触发」因架构/总线而异，但一律收敛到 `59` 已定义的**一等对象模型**：

| 热插拔事件源 | 物理机制 | 上行通道（复用 `59`） |
|--------------|----------|------------------------|
| PCIe native hotplug | Presence Detect / Attention Button / PME 中断 | `Cap(IRQ n)` 中断对象（`59` §4.1，bit52–54）经内核中断派发器转发 |
| ACPI 热插拔 | GPE（General-Purpose Event）/ `_EJ0`/`_OST` notify | 同 `Cap(IRQ n)`，或经 `event` 内核对象（与 `interrupt`/`timer` 同级，`59` §2.4） |
| DT 平台热插拔 | GPIO 中断 / 外部中断线 | `Cap(IRQ n)` 转发（与 `59` §7 五架构薄后端同） |

- **不新增事件原语**：`59` 已把 `interrupt` 与 `event` 列为 `07` §4.1 内核对象清单的同级 cap 对象。热插拔事件**二选一复用**：
  - 经 **`interrupt` 对象**：硬件热插拔 IRQ → 内核派发器按 `Cap(IRQ n)` 路由 → 投喂持 cap 的 hotplug 管理者（devmgr 子组件）；
  - 经 **`event` 对象**：内核把「拓扑变更」封装为结构化 event 投递（类比 Fuchsia `fuchsia.hardware` 的 device 变更通知），供 devmgr 消费。
  - 二者语义已在 `59` 定义，本文**不预占新 right**、**不新建对象类型**（待决项 H3 仅定「选哪条通道」，非新原语）。

### 3.2 上行后的用户态驱动生命周期

```
硬件热插拔 IRQ / ACPI notify / DT overlay
   │ 内核派发器（59 §4）按 Cap(IRQ n)/event 路由
   ▼
devmgr（或 hotplug 子组件，持对应 cap）被唤醒（05 EventPort）
   │ 读事件：设备节点 + 插入/移除语义
   ▼
插入 → §2.2 attach（mint + spawn）     移除 → §2.3 detach（撤销锁 + 回收）
   │                                        │
   ▼                                        ▼
驱动运行（IRQ 转发 + EventPort + device VMO）   回收完成，拓扑树节点删除
```

- **与 `59` 中断转发 + 合并 + 轮询三态一致**：热插拔事件**低频**，直接转发即可，无需合并/轮询混合（`59` §5.3 / `10` §5 开放议题 1 的合并+轮询仅针对高频数据 IRQ，如 10G+ 网卡）。
- **与 `04` 结构化取消 / `00` A9 exception channel 同源**：驱动 attach 后运行期崩溃 → exception channel 上行监督者（`04` §4.6 / `60` §6.3），走看门狗重启，不拖内核。
- **权限默认 deny（待决项 H2）**：持有「能收到热插拔事件」的主体**默认仅 devmgr**（系统级），普通驱动/应用**不**自动获得拓扑变更通知权——避免信息泄漏（如探测到某加密设备已插入）与权限提升。

### 3.3 与 `09` 早期串口（bit49）的协同边界

早期串口在 `09` C8 / `60` E1 已闭环：Stage 5 交用户态 console 服务，持 `UART_*`（bit49，已冻结）第②层领域 I/O cap；运行期若经热插拔新增串口设备，则**走本文 §2 的 L3 按需 attach 路径**，由 devmgr mint 新的 `Cap(UART MMIO/IRQ)` + `UART_*` 第②层 cap——与冷启动串口**同构**，不另立 right（bit49 已覆盖）。早期串口（Stage 1 内核直写）本身不参与热插拔（生死相关通道），与本文解耦（待决项 H5 仅定「新增串口设备的第②层 cap 复用 bit49 的精确边界」，非新 bit）。

## 4. capability 委托（device VMO + IRQ cap 受约束 mint/revoke；与 `60`/`10` C8 撤销锁同构）

### 4.1 与 `60` §3.1 两层能力模型同构

热插拔 attach 的授权**完全复用** `60` §3.1 的两层能力模型，不新增层次：

```
┌─ 第①层：设备资源 cap（由 capability 监视器从可信拓扑树 mint）──────┐
│  Cap(MMIO range) / Cap(IRQ n)(bit52–54) / Cap(DMA window)        │
│  持有者 = 驱动进程；物理访问权，与 BLOCK_*/GPU_*/NET_*/UART_* 正交  │
└────────────────────────────────────────────────────────────────┘
              │ 驱动把硬件封装为领域对象，mint 第②层（受约束）
              ▼
┌─ 第②层：领域 I/O cap（BLOCK_*/GPU_*/NET_*/AUDIO_*/UART_* 已冻结）─┐
│  持有者 = 上层服务（FS/网络栈/图形服务/console 服务）              │
│  逻辑 I/O 语义权，与硬件布局解耦；revoke 第②层即切 I/O 不动硬件   │
└────────────────────────────────────────────────────────────────┘
```

- **第①层 cap 的 mint 权威**：capability 监视器（TCB）在 attach 时从可信拓扑树 fresh-mint，**无「root 设备 cap 派生」环节**（`10` C8 / `59` §4.2 对齐 `07` §4.1「无 root 逃生舱」）。
- **受约束 mint（防 confused deputy）**：devmgr 仅持「受约束 mint right（限定设备 cap 类、限定 Job 子树）」（`07` §4.5），`rights_issued = rights_devmgr ∩ rights_driver_requested`，杜绝热插拔路径被借作越权跳板。
- **IRQ cap 精确语义**：`IRQ_WAIT`=bit52 / `IRQ_ACK`=bit53 / `IRQ_MASK`=bit54（均 per-IRQ deny，已冻结于 `07` §4.1 / `59` §9.3 闭环）；用户态驱动只 `wait/ack` 自身中断，**绝无全局关中断**（`KERNEL_PRIV` 仅内核，`59` §4.3）。

### 4.2 revoke 与撤销锁序列（与 `60`/`10` C8 同构）

detach / 拔出 / 驱动崩溃的回收走 `10` C8 撤销锁六步（`60` §3.5 / `59` §4.4），本文不重述步骤，仅补热插拔特有的两点：

1. **surprise 移除的原子性**：PCIe surprise 移除（设备物理抽走、无优雅通知）要求「屏蔽 IRQ → IOMMU 域失效截断在飞 DMA」**先于**任何驱动代码访问已消失的 MMIO——与 `60` §3.5 步骤①→③次序一致，撤销锁天然覆盖（待决项 H8 定「surprise 移除与撤销锁的精确时序边界」，属执行层协同，非新原语）。
2. **同一区间至多一个 live cap**：hotplug 反复插拔同一槽位时，旧 cap 必须先 fully reclaim（步骤④完成）才允许新 mint——复用 `10` C8 第二重保险，防悬垂硬件引用/双持。

> **零新 right bit 校验**：本文全程复用已冻结的 `IRQ_*`(52–54)、`UART_*`(bit49)、`BLOCK_*`(23–27)、`NET_*`(28–31,39)、`GPU_*`(32–36)、`AUDIO_*`(19–22)；device VMO 不可写 right 来自 `07`（折中 C，`76` §5）。**本文不新增任何 right bit**。

## 5. 设备内存协同（`76` device VMO 物理后端、IOMMU domain）

### 5.1 device VMO 物理后端的动态供给（与 `76` §5 同构）

热插拔设备的 DMA 缓冲与冷启动设备**同一供给路径**（`76` §5.1）：

- **来源 zone**：DMA 缓冲从 `DMA32`/`CMA` zone 取连续物理页（`76` §5.1；CMA 为演进项，`76` P6）。
- **封 device VMO**：连续页封为**不可写 device VMO**（right 来自 `07`，已冻结），经第①层 DMA cap 下发驱动（`10` C8 / `60` §3.2）。
- **IOMMU 域协同**：device VMO 物理页同时登记进持有驱动的 IOMMU 域（`60` §3.4）；revoke 前先使域失效截断在飞 DMA（`60` §3.5 步骤③），与 PMM 归还 buddy 串成原子序列（`76` §5.1）。

> 热插拔的「动态」只在**时机**（attach 时按需分配、detach 时归还），**不在机制**——机制完全是 `76` §5 既有供给层，本文不重定义。

### 5.2 IOMMU 域动态绑定（与 `60` §3.4 / `76` §5 协同）

| 操作 | 时机 | 动作（复用既有） |
|------|------|------------------|
| 域创建 | attach（`§2.2`） | 为 L3 驱动分配独立 IOMMU 域（VT-d/SMMU/RISC-V IOMMU），DMA 窗口仅覆盖其 device VMO 物理页（`60` §3.4） |
| 域绑定 | attach 完成前 | device VMO 物理页登记进该域；在飞 DMA 越界即被 IOMMU 拦截 |
| 域失效 | detach（`§2.3` 步骤③） | 撤销锁先使域失效/解映射，截断在飞 DMA，再 revoke cap |
| 域回收 | detach 完成 | 域释放，物理页归还 buddy（`76` §5.1 原子序列） |

- **无 IOMMU 平台退化**（`60` §2.2 决策表第 3 条）：仅 L1 受信内核态驱动可碰 DMA，用户态 DMA 退化（C1 折中不破）；热插拔用户态驱动在无 IOMMU 平台**默认禁止** DMA，fail-closed（`76` §5.2）。
- **NUMA 亲和**：热插拔设备接入的 NUMA node 由枚举阶段记录（`§1.2` / `76` §2.1），device VMO 后端按 node 取连续页，跨 node 回退用 SLIT 代价模型（`76` §2.2），不新增 right。

### 5.3 与 `76` L1·L3 双轨供给差异一致

| 驱动档位 | device VMO 物理后端 | 热插拔语义 |
|----------|---------------------|------------|
| **L1（生死相关，内核态）** | 早期 memblock 预留（`76` §5.2），不进通用 buddy | **不参与热插拔**（中断控制器/定时器/看门狗） |
| **L3（默认，用户态）** | DMA32/CMA 连续页 → 不可写 device VMO → IOMMU 域 | attach 时按需分配、detach 时经撤销锁回收（`§2`/`§4`） |

## 6. 五架构同源（枚举/事件薄后端差异）；与既有地基同构（不引入新内核原语）

### 6.1 枚举与事件的薄后端差异（封进 `arch`/`platform` 层）

本文所有机制（枚举归一化、事件上行、cap 委托、device VMO 后端、IOMMU 动态域）**逻辑同源**，差异仅封在薄后端：

| 架构 | 枚举薄后端 | 热插拔事件薄后端（复用 `59` §7.6） |
|------|------------|--------------------------------------|
| **x86_64** | ACPI DSDT/SSDT + PCIe 根总线扫描 | IOAPIC 路由热插拔 IRQ（`59` §7.1），ACPI GPE notify |
| **aarch64** | DT `#numa-node-id` + PCIe 扫描 | GIC（`59` §7.2）路由；DT overlay 追加节点 |
| **riscv64** | DT + PCIe 扫描 | PLIC/APLIC+IMSIC（`59` §7.3）路由 MSI 化热插拔中断 |
| **loongarch64** | ACPI（LoongArch 自有）+ DT 变体 + PCIe | LIOINTC/EIOINTC/PCH-MSI 级联（`59` §7.4）路由 |
| **i386（32 位）** | 单 node UMA 退化 + PCIe 扫描（纯 C 后端，`02` C2） | 纯 C 中断薄后端（`59` §7.5），逻辑与 64 位同源 |

> 论断（同 `63` §7 / `76` §7 / `28` §6）：枚举与事件逻辑跨五架构二进制一致，差异只在 `arch`/`platform` 的探测器与中断控制器后端。i386 纯 C 约束（`02` C2）只影响早期枚举/中断 C 后端，不侵蚀 Rust 主体（`19` §3.3）。

### 6.2 与既有地基同构（铁律校验）

- **不引入新内核原语**：枚举薄层 = `09` Stage 2 拓扑抽取逻辑的运行时增量 + 可信拓扑树的增量维护者（§1）；热插拔事件 = `59` 已定义的 `interrupt`/`event` 对象（§3）；attach/detach = `10` C8 状态机 + 撤销锁（§2/§4）；device VMO 后端 = `76` §5 既有供给层（§5）。**全篇零新抽象类型**。
- **不新增 right bit**：复用 `IRQ_*`(52–54)、`UART_*`(bit49)、`BLOCK_*`/`NET_*`/`GPU_*`/`AUDIO_*` 已冻结位（`07` §4.1 / `38` §3 / `45` §3）；device VMO 不可写 = `07` 已冻结 device right。
- **跨域冲突以 `00` A1–A12 / C1–C18 为准**：
  - `A1` 句柄即 capability → 枚举节点须经 mint 才成 cap、事件经 cap 对象上行；
  - `A6` 交权缩 TCB → 热插拔驱动默认 L3 出核（`60` §2.3）；
  - `A9` exception channel → 驱动崩溃上行监督者（`§3.2`）；
  - `C1` 折中 C → 设备内存走不可写 device VMO（`§5`）；
  - `C8` 设备能力签发时序 / 撤销锁 / 早期串口 → 本文 attach/detach 与之同构（`§2`/`§4`/`§3.3`）；
  - `C2` 受约束 mint → devmgr 受约束 mint 设备 cap（`§2.2`/`§4.1`）；
  - `§5.3` 五架构一致性成本 → 枚举/事件薄后端差异封死（`§6.1`）。

## §8 第十轮自主采纳裁决（待大喵复核）

> 本节为修订式追加（铁律：不删不改既有章节，仅末尾追加）。第十轮收口阶段，指挥官对本文所有「需大喵拍板」项先自主采纳、待大喵复核。

裁决立场：

- **H1：采纳「枚举薄层 = 用户态 devmgr 职责、非新内核对象」**。理由与 `60` / `10` L3 用户态驱动模型同源——枚举薄层只是 `09` Stage 2 拓扑抽取逻辑的运行时增量 + 可信设备拓扑树的增量维护者，不引入新的内核对象类型，与 `59` §2.4「不引入新原语」纪律一致；否则需新增枚举对象类型，越过「不引入新内核原语」铁律并扩大 TCB。
- **H2：采纳「热插拔事件接收权默认仅 devmgr（系统级），普通驱动/应用默认 deny，不自动授予拓扑变更通知权」**。理由：拓扑变更事件携带设备插入/移除语义（含可选探测到的设备类型、资源区间等敏感信息），若默认放开将造成两类风险——(a) **信息泄漏**：普通应用可探测到某敏感外设（加密狗/受控存储/安全令牌）是否在线；(b) **权限提升跳板**：持事件 cap 后再尝试 mint 设备 cap 构成 confused deputy。`07` §4.1 权利最小化与 `29` 威胁模型均要求 default-deny；devmgr 作为唯一受信持有者按需将「拓扑变更」二次封装为受约束通知分发（如 console 服务仅收新增串口事件），保持单一受信通道。

**reasoning 决策（2026-08-03）—— H1**：**维持「枚举薄层 = devmgr 职责、非新内核对象」**（同意指挥官原占位）。理由——(1) **TCB 体量**：枚举本身只是"硬件可观测事实 → 节点结构"的归一化（DT 解析 / ACPI 命名空间 walk / PCIe 配置空间扫描），不携带权限语义——"描述"与"能力"必须分层（`07` A1 句柄即 capability 纪律）；做成内核对象意味着引入"枚举对象类型 + 受约束 mint 入口 + revoke/reclaim 路径"三层新原语，每一层都要进 capability 监视器 `check_rights` 与 `65` 审计 schema，长期 TCB 维护代价线性增长。(2) **安全模型自洽性**：fail-closed 枚举（§1.3）——节点入树后须经 devmgr 匹配 + capability 监视器受约束 mint 才能成 cap（`10` C8 / `60` §3.1），枚举薄层不授权、不持权、不决策；这是 `59`「不引入新原语」纪律的直接落点，与 `07`「无 root」自洽——枚举薄层若做成内核对象反而会隐含"内核可单方面授权"的歧义。(3) **五架构同源可行性**：DT/ACPI/PCIe 三类枚举薄层已经封死在 `arch`/`platform`（§6.1），枚举节点的写入路径与冷启动 `09` Stage 2 拓扑抽取逻辑共用同一薄层——若做成内核对象，五架构的内核对象 ABI 一致性成本反而上升（每架构要单独维护 enum object 的句柄格式、inspects 字段、撤销语义）。(4) **与既有地基同构**：devmgr/驱动管理器 + 能力网关（`10` §4.3 + `60` §2.3 L3 双轨）已经是"匹配 → 授权 → 启动 → 看门狗"的标准流程，热插拔 attach/detach 只是把"触发源从冷启动变为运行时事件"，零新原语。被否决选项：枚举薄层做成新内核对象（扩 TCB / 突破 `59`「不引入新原语」纪律 / 与 devmgr + 能力网关同构流程冲突）。

**reasoning 决策（2026-08-03）—— H2**：**维持「热插拔事件接收权默认仅 devmgr、普通 deny」**（同意指挥官原占位）。理由——(1) **TCB 体量**：若默认放开热插拔事件 cap 到普通驱动/应用，capability 监视器需要在"事件分发路径"上加复杂的策略引擎——「哪些设备类型 → 哪些主体可收」，等价于把"拓扑可见性"塞进内核；default-deny + 单一受信持有者（devmgr）让 capability 监视器只对 devmgr 一个主体做事件 cap 授权，路径极简。(2) **安全模型自洽性**：热插拔事件携带"设备插入/移除语义"——攻击者拿到事件 cap 后可推断敏感外设在线状态（`29` T-A 信息泄漏类），亦可借事件触发 + mint 请求构成 confused deputy（T4 跳板）；`07` §4.1「最小权限」与 `29` 威胁模型均要求 default-deny；devmgr 作为唯一受信持有者按需二次分发受约束通知（如 console 服务仅收新增串口事件、密钥守护仅收新增密钥岛事件）复用 `07` §4.5 受约束 mint 范式（"通知范围 × 通知对象类型"交集），单一受信通道不破。(3) **五架构同源**：default-deny 路径跨五架构一致；devmgr 二次分发受约束通知的语义（受约束 mint + capability 收窄）是架构无关的，与 `63` §7「netstack 单例监督服务」同口径。(4) **长期可维护性**：未来若需要"特定设备类型对特定主体的细粒度可见性"，由 devmgr 在用户态做策略、不动内核 rights——避免每加一类策略就动一次 `07` §4.1。被否决选项：默认放开（信息泄漏面 / confused deputy 跳板 / capability 监视器扩点）。
