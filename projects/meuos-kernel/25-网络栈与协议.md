## 1. 「应该是什么样」推演（解构型）

> 先不问「MeuOS 的网络栈怎么抄 Linux」，而问「在 capability 世界、用户态服务化、最小 TCB 的前提下，网络**应该**是什么样」。

### 1.1 网络不是「内核必须内置的协议堆」，而是一组 capability 守护的资源

在 MeuOS 的既定取向下，内核 Day 1 的权限模型是 capability（`07`），一切资源访问由不可伪造的句柄（handle）+ rights 表达，无 root、无全局命名空间默认可见（`00` A1/A4）。把这个前提推到网络：

1. **每一个网络对象——socket、网络接口、路由表项、防火墙规则——都应是 capability**，而非「全局可见、靠 uid/permission bit 保护」的内核对象。一个进程之所以能 `connect` 出去，不是因为它「碰巧跑在有权限的内核里」，而是因为它**持有对应的网络 capability 句柄**且句柄带 `NET_CONNECT` right。
2. **协议处理逻辑（IP/TCP/UDP/ICMP/ARP/NDP、DHCP、DNS resolver）是「策略重、代码量大、迭代快」的子系统**——这正是 `00` 总览 §1 中「重服务出核缩 TCB」原则的典型适用对象，与 FS（`06`）、驱动（`10`）同源。把它塞进内核即污染 TCB（`19` §4.2 把「网络栈出核」列为缩 TCB 的三类动作之首）。
3. **内核只保留「机制 + 唯一裁决点」**：网卡设备能力（来自 `10` 能力网关）、零拷贝数据通路（VMO/VMAR + pager，接 `03`）、受 capability 守护的 socket 句柄（接 `07`）、就绪通知（EventPort，接 `05`）。内核**不实现任何 IP/TCP/UDP 协议语义**。

### 1.2 网络与 IPC（05）的边界：socket 是「跨机 IPC」的一种，但 backend 不同

`05-IPC机制.md` §1.3 已明确把网络协议栈划在 IPC 原语之外：「**不重新设计网络协议栈 / 跨机 RPC（跨主机通信仍走 socket 兼容层，不在本原语内）**」。但 `05` §1.1 又说 socket 是一种「跨进程/跨机 IPC」。这看似矛盾，实则定义了清晰的分界：

- **IPC（05）原语**负责**同机、近内核、受 capability 直接寻址**的消息传递（Channel / EventPort / SHM / Service Registry），端点即 capability，靠 badge/Service Registry 寻址，无需路由、无需协议可靠性。
- **网络栈（本文）**负责**跨网络、带协议语义**的通信：TCP 的可靠有序、UDP 的数据报、IP 的路由寻址、ICMP 的控制面。它产出的 **socket 句柄也必须是 capability**（与 `05` 端点同构），但 socket 的「对端」不是 capability 直接寻址的本地端点，而是经路由 + 协议栈可达的网络地址。
- **分工落地**：
  - `AF_UNIX` 域套接字 → 直接映射到 `05` 的 Channel（语义纯净、零协议开销；`08` §4.3 已列 `domain socket → IPC channel`）。
  - `AF_INET`/`AF_INET6` → 网络栈（本文）；loopback 也走网络栈本地回环（保持协议路径统一，便于测试与防火墙一致性）。
  - 二者**共用同一套 socket API 表面与 EventPort 就绪通知**，对应用不可见 backend 差异。

### 1.3 推演结论（解构型基线）

> **MeuOS 的网络栈应参照 Fuchsia 完全用户态（netstack3 Rust 风格）：协议栈是受 `meu-supervisor`（`04`）管理的用户态 Rust 组件，可重启、可灰度；内核只提供「网卡设备能力 + VMO 零拷贝数据通路 + capability 守护的 socket 句柄 + EventPort 就绪通知」四类机制，并强制 rights。这与「重服务出核缩 TCB」原则（`00` A6）完全一致，且与 FS/`06`、驱动/`10` 出核形成同一套架构叙事。**

## 3. MeuOS 网络栈归属与分层

### 3.1 总体架构：三层，内核只给「机制」

```
┌─────────────────────────────────────────────────────────────────┐
│ 用户态 netstack 服务 (Rust, netstack3 风格)                        │
│  TCP/UDP/ICMP / IPv4/IPv6 / ARP·NDP / DHCP / DNS resolver         │
│  连接表 · 路由表 · 邻居表 · 防火墙策略 · socket 句柄 mint 委托人     │
│  由 meu-supervisor(04) 管理，可重启、可灰度                         │
│       │ 经 VMO/SHM 零拷贝收发报文        │ 经 Channel 暴露 socket API │
├───────┴──────────────────────────────┴────────────────────────────┤
│ 用户态 NIC 驱动服务 (Rust, 接 10 双轨·默认出核)                     │
│  virtio-net 等：MMIO/IRQ/DMA 能力(来自 10 网关) → ring 收发         │
│       │ 设备能力经能力网关(10)        │ 报文 VMO + EventPort 通知     │
├───────┴──────────────────────────────┴────────────────────────────┤
│ 内核态（仅机制，Rust TCB）                                          │
│  ① NIC 设备能力句柄（来自 10 能力网关，仅 READ/WRITE/DMA 权）       │
│  ② VMO/VMAR + pager（接 03）：报文缓冲区零拷贝数据通路              │
│  ③ socket 句柄 = capability + rights 强制（接 07）                  │
│  ④ EventPort（接 05）：socket 就绪通知（READ/WRITE/CHAN filter）    │
│  —— 内核不实现任何 IP/TCP/UDP 协议语义 ——                          │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 分层职责

**内核层（机制，Rust TCB，零协议逻辑）**：
- 提供 NIC 设备能力（由 `10` 能力网关签发，netstack/NIC 驱动只拿所需 MMIO/IRQ/DMA 权）。
- 提供 VMO/VMAR 与 pager 原语（`03`），使报文缓冲区可在 NIC 驱动 ↔ netstack ↔ 应用间零拷贝传递。
- 提供 socket 句柄这一 capability 类型，并在 `mint`/`open` 时按 netstack 委托人授权收窄 rights（接 `07` 受约束 mint，避免 confused deputy，呼应 `06` §6-2）。
- 提供 EventPort 就绪通知（接 `05`）：socket 可读/可写/对端关闭 → `EVFILT_READ`/`WRITE`/`CHAN` filter，使 epoll/kqueue 兼容零成本。

**netstack 用户态服务层（策略，Rust，出 TCB）**：
- 实现全部协议：TCP/UDP/ICMP、IPv4/IPv6、ARP/NDP、DHCP client、DNS resolver。
- 维护每接口状态、路由表、邻居表、连接表（这些**是 netstack 内部状态，不暴露为全局内核表**）。
- 作为 socket 句柄的 **mint 委托人**：应用 `socket()` → 兼容层/`05` → netstack 请求内核 mint 一个带受限 rights 的 socket 句柄回传。
- 持有 NIC 设备能力，经 VMO 收发报文；可重启（崩溃由 `meu-supervisor` 拉起新副本，连接表可重建或由对端重连，fail-closed）。

**统一命名空间子树 `/net`（接 `06`）**：
- `/net` 由 netstack 服务经 **mount-capability** 委托（对齐 `06` §4.1 的「挂载能力委托子树」与 F5 最小集），如 `/net/tcp`、`/net/udp`、`/net/route`、`/net/eth0` 等。
- 每进程 namespace 经 spawn 组装（`06` C3 已采纳「每进程独立 namespace」），只 reveal 其允许看到的 `/net` 视图（对齐 Android 按应用隔离出网）。

### 3.3 与「重服务出核缩 TCB」原则的自洽

- `00` §1 收口：「FS/网络/驱动/监督策略/图形下沉为用户态、capability 受控、由内建监督原语管理的服务」。本文把「网络」这一项**首次落定为具体归属**——netstack 完全用户态，与 FS/`06`、驱动/`10` 同构。
- `19` §4.2 已把「网络栈出核」列为缩 TCB 动作之一（协议栈移出 TCB，报文经 SHM + 一次通知 IPC），本文为其补完接口契约。
- `10` 附录 A 已把 `virtio-net` 列为用户态驱动、网络栈列为用户态服务——本文与其一致，并细化零拷贝数据通路。

## 4. capability 化方案

### 4.1 socket 句柄即 capability（接 `07`）

- 创建 socket = 向内核请求 `mint` 一个 **socket 句柄**（内核对象，带 rights），由 netstack 作为委托人按客户端权限设置子集（netstack 自身持 `MANAGE`）。这与 `06` §4.4.2 的文件句柄 mint 同构，并复用 `07` 的 rights 位图模型。
- 句柄的复制（`dup`）、跨进程授予（经 `05` Channel cap-transfer）、回收（`close`）均为显式、可审计操作（接 `07` §4.1/§4.5）。
- **权限在 `mint`/`open` 时一次收窄**（呼应 `19` §1.1 原则 2、AP-3）：`connect`/`bind` 的策略判定只在 `socket()`/`bind()`/`connect()` 发生时做一次，运行期 `send`/`recv` 只做 rights 位运算 + EventPort 通知，不重做策略判定，避免把 µs 级策略/unwrap 塞进热路径。

### 4.2 connect / bind 权限如何表达

在 Linux 中，`bind` 到 <1024 端口需 `CAP_NET_BIND_SERVICE`，raw socket 需 `CAP_NET_RAW`，改接口/路由需 `CAP_NET_ADMIN`——这些正是 `07` §3.1 批评的「capability 碎片 / 新 root」来源。MeuOS 改以**对象级 rights** 表达（建议新增网络 right 位，接 `07` §5.2 / C2 待定）：

| 操作（Linux 语义） | Linux capability | MeuOS socket 句柄 right（建议） |
|---------------------|------------------|----------------------------------|
| `connect()` 出站 | （默认允许，靠防火墙） | `NET_CONNECT` |
| `bind()` 任意端口 | — | `NET_BIND` |
| `bind()` 特权端口 <1024 | `CAP_NET_BIND_SERVICE` | `NET_BIND_PRIV`（仅此 right 可绑低位端口） |
| `listen()` 接受入站 | — | `NET_LISTEN` |
| raw / packet socket（嗅探） | `CAP_NET_RAW` | `NET_RAW`（**默认 deny**，显式授予） |
| 管理接口/路由/防火墙 | `CAP_NET_ADMIN` | `NET_MANAGE`（或独立 firewall capability） |

- **命名空间约束 × 句柄 right 双重判定**：进程能否连出去，既取决于 socket 句柄是否带 `NET_CONNECT`，也取决于其每进程 `/net` 命名空间视图（是否 reveal 了该接口/路由）。例如沙箱进程只获 `NET_CONNECT` 且 namespace 仅 reveal 一条 tunnel 接口 → 只能经该隧道出网，物理接口对它「根本不存在」（unveil 反面：默认全不可见）。
- `pledge` 子系统（`07` §4.2 已列 `inet`/`unix`/`dns`）直接映射：`pledge("inet")` ≈ 授予 `NET_CONNECT`/`NET_LISTEN` 类 rights 的声明；越界即 fail-closed 终止（接 `07` pledge 语义）。

### 4.3 防火墙 / 策略是否 capability 门控

- **是**。防火墙规则本身应是 capability 对象：只有持有 `NET_MANAGE`（或专门 firewall capability）的进程才能安装/移除过滤规则，规则附加到 netstack 的「分层钩子」（借 WFP/netfilter 钩子思想，但实现在用户态 netstack 内）。
- 过滤规则对未授权进程**不可绕过**（fail-closed）：netstack 在协议路径上强制规则，无 `NET_MANAGE` 的进程无法注入「放行自己」的规则。
- 规则的表达与审计：规则作为 netstack 内部 capability 对象，安装/命中/丢弃作为结构化事件落入 `12` 事件流（借 `19` §1.2.1 的 fail-closed 审计思想），不静默。
- 与 `07` 的「最小权限 + 可推理」一致：防火墙策略不再依赖全局 `CAP_NET_ADMIN`，而是「谁能装规则 = 谁持 firewall capability」，可局部审计。

### 4.4 网络命名空间并入 `06` 统一命名空间（每进程独立 namespace 已采纳）

- `06` §4.1 已规定每进程 namespace 由 spawn 组装、默认全不可见、显式 reveal；`/net` 是其中一个可委托子树（由 netstack 经 mount-capability 提供）。
- 由此「网络命名空间」不是 Linux 式独立 `CLONE_NEWNET` 维度，而是**统一命名空间里 `/net` 子树的一个视图**——天然并入 `06` C3「每进程独立 namespace」结论，无需另立机制。
- 多网络/VPN 隔离（借 Android 思想）：某进程的 `/net` 视图只 reveal 隧道接口 → 该进程所有出网流量天然走隧道，等价于 Android `VpnService` 全流量拦截，但表达为 capability 视图而非内核策略。

## 5. 与 05 / 06 / 07 / 08 / 10 接口边界

> 本节只声明依赖与协同点、不替他域拍板；结论以各子领域文档为准，跨域一致性由 doc-sync 合成 pass 回填。

### 5.1 与 IPC（05）：socket 不是 IPC 原语，但共用 capability 与就绪模型
- **边界**：`05` §1.3 已排除网络协议栈；`AF_UNIX` → `05` Channel，`AF_INET*` → 本文 netstack。二者 backend 不同，但 **socket 句柄与 IPC endpoint 同为 capability**（rights 同构）。
- **就绪通知复用 EventPort**：socket 可读/可写/对端关闭 → `05` 的 `EVFILT_READ`/`EVFILT_WRITE`/`EVFILT_CHAN` filter（`05` §4.2）。epoll 兼容层（`05` §4.6 已把 epoll 映射到 EventPort READ/WRITE）**直接覆盖网络 socket**，无需新增机制。
- **零拷贝**：大块数据经 VMO/SHM（`05` §4.3 / `03` §4.4），小消息经 Channel；与 `05`/网络共用同一套零拷贝基元。
- **待协同**：loopback 与 `AF_UNIX` 的精确分工（§1.2）、socket 句柄与 Channel endpoint 在 cap-transfer 上的 type tag 区分（接 `05` §5-2）。

### 5.2 与 文件系统（06）：`/net` 是命名空间子树，socket 句柄与文件句柄同构
- **`/net` = mount-capability 委托子树**：netstack 经 `05` Service Registry 注册目录能力，FS 服务（`06` 根聚合者）经 mount-capability 委托 `/net`（对齐 `06` §4.1、§4.4.2）。
- **句柄同构**：socket 句柄与文件句柄同为 capability，rights 位图复用 `07`；密钥=capability 思想（`06` §4.2.3）与「网络句柄=capability」同一范式。
- **待协同**：`/proc/net`、`/sys/class/net` 等伪文件系统由 `06` 向统一命名空间生成 Linux 视图（接 `08` D5），netstack 提供底层数据；`/net` 代理 vs 直露边界（接 `06` §6-8）。

### 5.3 与 安全模型（07）：socket 句柄 = capability，新增 NET_* rights
- **句柄即能力**：socket 句柄的生命周期（mint/duplicate/grant/revoke）全部走 `07` 模型；`revoke` 即回收连接权。
- **新增 rights 位**（§4.2 表）：`NET_CONNECT`/`NET_BIND`/`NET_BIND_PRIV`/`NET_LISTEN`/`NET_RAW`/`NET_MANAGE`，接 `07` §5.2 rights 位图粒度与 C2 待定。
- **pledge 子系统对齐**：`inet`/`unix`/`dns`（`07` §4.2 已列）直接对应网络能力声明。
- **confused deputy 防护**：netstack 作为 socket 句柄 mint 委托人，其 mint 权限受「自身 rights 上限 ∩ 客户端请求下限」交集约束（接 `06` §6-2 / `07` §4.5 受约束 mint）。
- **待协同**：right 位精确集合（接 `07` §5-2）；防火墙规则是否独立 right 还是 `NET_MANAGE` 子集（§6 D3）。

### 5.4 与 Linux 兼容层（08）：BSD socket API 经 mkit 子集优先
- **BSD socket API 呈现**：`socket/bind/connect/listen/accept/send/recv/sendto/recvfrom/setsockopt/getsockopt/shutdown/close` 经兼容层翻译为内部 socket capability 操作（mkit 子集 1:1 direct-mapped，`08` §2.2 类别一）。
- **socket 选项映射**（哪些需映射）：
  - `SO_REUSEADDR`/`SO_REUSEPORT` → 协议配置由 netstack 承载，作为 socket 句柄的附属属性（非内核全局）；
  - `SO_KEEPALIVE`/`SO_LINGER`/`SO_RCVBUF`/`SO_SNDBUF`/`SO_TIMESTAMP` → netstack 连接表项属性；
  - `SO_BROADCAST` → 需 `NET_BIND` 或专门 right 派生；
  - `IP_TRANSPARENT`/`SO_MARK`/`PACKET_ADD_MEMBERSHIP` 等深度耦合内核的 → **ENOSYS**（接 `08` §7 显式不兼容，不制造假兼容）。
- **零拷贝对接**：socket 收发缓冲区映射为 VMO（接 `03`），`send`/`recv` 经 VMO + EventPort `CHAN` filter 通知就绪（接 `19` §4.2 报文经 SHM + 一次通知 IPC）。
- **IO 多路复用（epoll/kqueue）对接**：epoll → EventPort READ/WRITE（已由 `05` §4.6 覆盖，网络 socket 直接复用）；`kqueue` 本就是 MeuOS EventPort 模型（`05` §3.2），零成本；`select`/`poll` → EventPort 多 filter 注册。`08` §4.3 已列 `socket` 需映射，本文补全网络态语义。
- **待协同**：`netlink`（路由/邻接/防火墙查询）——`08` §7 已列 `netlink` 全量为显式不兼容；本文建议经 `/net` 命名空间视图 + netstack 服务 Channel 提供等价能力查询接口，而非伪造 netlink 全量语义（避免缝合怪，呼应 `08` 铁律）。

### 5.5 与 设备驱动（10）：NIC 驱动经能力网关出核，协议栈经 VMO 零拷贝收发
- **NIC 驱动用户态**（接 `10` §4.2/附录 A）：`virtio-net` 等作为用户态 Rust 驱动，经 `10` 能力网关获 MMIO/IRQ/DMA 能力；高吞吐 NIC 可按 `10` 双轨准则评估内核快速路径（优化项，非 Day 1 必需）。
- **数据通路零拷贝**：NIC 驱动 ↔ netstack 经 **VMO/SHM**（接 `03`/`05`），报文缓冲区不跨地址空间拷贝；就绪经 EventPort `CHAN` filter 通知。
- **中断处理**（接 `10` §5-1 / `19` AP-2）：高频率 NIC 用「中断合并 + 轮询混合」避免 IPC 风暴，与 `10` 驱动模型一致。
- **待协同**：DMA 与 IOMMU 强制化（`10` §5-2）对 NIC 驱动同样适用；NIC 驱动 crash 重启与 netstack 重连协议（`04` 监督）。

### 5.6 多架构（五架构）一致性 + 性能（接 `19`）
- **五架构一致**：netstack 是纯 Rust 用户态组件，跨五架构二进制一致（不依赖架构页表/中断语义），与 `03`（`VMO` 抽象）、`05`（EventPort）、`10`（能力网关）的架构无关抽象解耦。NIC 驱动需每架构后端（`10` 已覆盖 virtio 通用路径 + 每架构薄后端），数据通路 VMO 抽象屏蔽差异。i386 纯 C 约束（`02` C2）**只影响 NIC 驱动 C 后端**，不影响 netstack Rust 主体（`19` §3.3 的「i386 验证负担」仅落于驱动 C 侧）。
- **性能目标（接 `19`）**：
  - 出核代价 = 「报文经 SHM + 一次通知 IPC」（`19` §4.2），前提**数据通路走 VMO/SHM，逻辑走用户态**（对齐 AP-1 红线）。
  - 就绪通知经 EventPort（同 `05` IPC 快速路径 ≤ 0.5 µs 同核）触发 `recv`，不引入独立 poll 系统调用热路径。
  - crypto（`19` §1.2.5 / §3.3）：TLS 不在内核；若用户态 TLS（如 rustls）走硬件加速 ≥ 1 GB/s，i386 降级需接受（与 `19` §3.3 一致）。
  - 反模式规避：数据通路出核（AP-1）、该用 SHM 却用 Channel 传 bulk（AP-7）、就绪通知 IPC 风暴（AP-2）均须在执行层作为设计评审清单。

## 6. 自主结论 + 待决项（标注是否需架构裁决）

### 6.1 自主结论

1. **网络栈应完全用户态（netstack3 Rust 风格），内核只给四类机制**：NIC 设备能力（`10`）+ VMO 零拷贝数据通路（`03`）+ capability 守护的 socket 句柄（`07`）+ EventPort 就绪通知（`05`），**内核零协议逻辑**。这与 `00`「重服务出核缩 TCB」原则（A6）及 `06` FS 出核、`10` 驱动出核形成同一架构叙事，是三大方向中「出核」原则在网络子系统的首次落定。
2. **socket 句柄即 capability**，rights 在 `mint` 时一次收窄，运行期只位运算（呼应 `19` §1.1 原则 2），杜绝 AP-3 热路径重策略。
3. **防火墙/策略 capability 门控**：规则是不可绕过的 capability 对象，`NET_MANAGE`/独立 firewall capability 才允许安装，fail-closed + 结构化审计（接 `07`/`12`）。
4. **网络命名空间并入 `06` 统一命名空间的 `/net` 子树**（每进程独立 namespace 已采纳，C3），不另立 `CLONE_NEWNET` 维度；多网络/VPN 隔离表达为 capability 视图。
5. **与 IPC（05）边界清晰**：网络不是 IPC 原语，`AF_UNIX→05`、`AF_INET*→netstack`，但共用 capability 与 EventPort 就绪模型，epoll/kqueue 兼容零成本。
6. **Linux 兼容层经 mkit 子集优先呈现 BSD socket API**，零拷贝走 VMO，IO 多路复用走 EventPort，`netlink` 全量显式不兼容（不造假兼容）。

## 第四轮裁决回写（C15 已采纳）

> 本节约追加自第四轮查缺补漏「决策-回写」环节（general-purpose-31，lite / hy3，指挥官模式采纳）。修订式追加，不删改 §1–§7 既有内容。

### C15 采纳结论
**C15 = 网络栈 Day 1 即完全用户态（netstack3 风格）已采纳。**

原 §6.2 待决项 **D1（候选 C15）** 现升级为「**已采纳**」——网络栈 Day 1 即完全用户态，D1 关闭，不再作为待决项。本裁决已同步汇入 `00` 总览 §3 冲突登记表末尾新增的 `C15` 行。

### 采纳理由（指挥官自主决策）
1. **纯软件协议栈无硬件理由留核**：TCP/UDP/IP/ICMP/ARP/NDP/DHCP/DNS 全是软件逻辑，不触及 MMIO/IRQ/DMA 等硬件原语，留核没有任何性能或正确性的硬约束理由。
2. **留核代价远高于驱动且违背「重服务出核缩 TCB」（00 A6）**：协议栈代码量极大、迭代快、是典型「策略重、代码量大」子系统；塞进内核即污染 TCB（`19` §4.2 已把「网络栈出核」列为缩 TCB 三类动作之首）。内核只保留四类机制——NIC 设备能力（`10`）+ VMO 零拷贝数据通路（`03`）+ capability 守护的 socket 句柄（`07`）+ EventPort 就绪通知（`05`），**内核零协议逻辑**。
3. **与 FS/驱动出核同构，统一架构叙事**：与 `06` FS 用户态、`10` 驱动用户态形成同一套「机制在内核、策略在用户态、meu-supervisor 可重启」的 lean hybrid 叙事。
4. **明确拒绝「netstack 临时留核」退出条件**：鉴于网络栈纯软件、无硬件理由留核，留核代价远高于驱动且违背 A6，不采纳任何「临时留核过渡」例外——不存在 Day 1 先留核、后续迁移的折中路径。

### 与总览原则 / 子领域呼应
- **00 A6（尽快交权用户态缩 TCB）**：网络栈出核是该原则在网络子系统的首次落定，与 FS/`06`、驱动/`10` 同构。
- **10 设备驱动模型**：NIC 驱动经能力网关出核，netstack 经 VMO 零拷贝收发；`10` 附录 A 已列 `virtio-net` 用户态。
- **03 内存管理**：报文缓冲区 VMO/VMAR + pager 零拷贝数据通路。
- **07 安全模型**：socket 句柄 = capability，新增 `NET_*` rights，防火墙 capability 门控 fail-closed。
