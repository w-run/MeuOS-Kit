## m++ C++11 lambda（877beed）
- 机制：`[captures](params) -> ret { body }` 由 cpp_lambda_expr 解析（primaryexpr 的 `[` 入口，primary 位置 `[` 恒为 lambda——数组下标是 postfix）。闭包合成**文件作用域匿名类 `__lambdaN`**（经 cpp_class_decl 重放，复用成员/构造/运算符机制）：值捕获为成员 + 合成构造函数（按捕获 DECLTYPE 类型化成员与 ctor 参数）；lambda 体为 `operator()`（显式 `-> ret` 或 auto 推导）；`obj(args)` 经既有成员调用路径降级为 `obj.operator()(args)`（functor 支持，含重载）。`operator()` mangle 为 `Class_operator_cl`（cpp_op_mangle TLPAREN）。

- 已知限制：无 `[&x]` 引用捕获、无 `[=]`/`[&]` 默认捕获、无 init-capture、无泛型 lambda（`auto` 参数）、无跨函数传递捕获；引用捕获明确报错（最小集）。
- 下一步（roadmap）：constexpr 求值器。

## 缺陷 Q：`delete nullptr` / `delete[] nullptr` 运行期段错误（worker-test-2，2026-08-03）
- 最小复现：
  ```c
  int *p = 0;
  delete p;     // rc=139
  delete[] p;   // rc=139
  ```
  按 C++ 标准 `delete nullptr` 应为 no-op；当前 m++ 生成代码段错误。
- 影响面：`delete` 与 `delete[]` 两条路径都有；现有 `new_delete*.cc` 正向测试未覆盖 nullptr 释放，因此一直没暴露。
- 探测：`new int[0]; delete[] z;` 通过；`delete nul` / `delete[] nul` 在 nul==0 时崩溃。
- 推测根因：codegen 在 `delete(ptr)` 时无条件走 `dtor+free` 而未先判空；待对应 worker 修复（`delete nullptr` 直接 return；数组同）。
- 测试：本期提交的 `new_delete_runtime_boundary.cc` 已剔除 nullptr 断言（避免 CI 红）；修复后回归并补 canary。

## 缺陷 R：concept 体内形参名 ≠ `T` 时被误判 undeclared（worker-test-2，2026-08-03）
- 最小复现：
  ```c++
  template <typename X> concept Four = sizeof(X) == 4;   // 期望 OK
  ```
  → `error: undeclared identifier: X`（指向概念体里的 `X`）。已对照 concepts.cc 中 `concept FourByte = sizeof(T) == 4`（用 `T`）正常。
- 影响面：所有 concept 形参名若不是字面 `T`（常见：教学示例/库代码用 `T`/`U`/`V`/…）一律被拒。多模板参数约束函数需要第二个模板参数命名时也连带受限（concepts_combo_boundary.cc 已 `#if 0` 掉相关断言）。
- 推测根因：概念体折叠器用硬编码 `T`（或固定映射）替代形参名，而非按 `concept C = body` 的模板参数表查实际名。
- 测试：concepts_combo_boundary.cc 已将 `mix<A,B>` 用 `Four<A>` 部分 `#if 0` 隔离；修复后回归并删除 `#if 0` 块。
