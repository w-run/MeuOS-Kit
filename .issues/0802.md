## m++ C++11 lambda（877beed）

## 缺陷 W（c-00）：`u8"..."` 字面量元素类型为 `unsigned char`，应为 `char`（worker-mir-tests，2026-08-03）

## 缺陷 X（c-01）：`inline` 定义 + `extern` 声明未产生外部定义（worker-mir-tests，2026-08-03）

- **严重性**：一致性缺陷（合法 C99/C11 代码链接失败）。
- **标准依据**：C99/C11 §6.7.4p7 —— 若函数在本 TU 内有 `inline` 定义，且**存在不带 `inline` 的外部声明**（如 `extern int f(int);`），则该定义**是**外部定义，编译器必须发出符号。
- **最小复现**：
  ```c
  inline int f(int x) { return x + 1; }
  extern int f(int);                    /* 使上面的定义成为外部定义 */
  int main(void) { return f(1) == 2 ? 0 : 1; }
  ```
  mcc：`undefined reference to 'f'`（链接失败）。gcc `-std=c11`：通过。
- **对照（正常路径）**：`static inline` 定义正常（内联展开 + 必要时发本地符号）；纯 `inline` 无 extern 声明时不发符号 —— 这**符合**标准，不是缺陷。问题只在「inline 定义 + extern 声明」这一组合。
- **位置线索**：`projects/mcc/src/c/parse/decl.c:512` 计算 `d->u.func.inlinedefn`（`linkage == LINKEXTERN && fs & FUNCINLINE && !(sc & SCEXTERN) && (!prior || prior->u.func.inlinedefn)`）。该式只看**先前**声明（`prior`），**后续**出现的 `extern` 声明无法回溯清除 `inlinedefn` 标记 → 定义已按「仅内联」处理，符号被丢弃。
- **修复建议**：在后续 `extern` 声明合并到已有 decl 时，若该 decl 已带函数体且原判为 inlinedefn，需清除 `inlinedefn` 并补发外部定义（或在 TU 结束时统一裁决 inlinedefn，而非在声明点即时定夺）。
- **测试**：本期新增 `test/c99/inline.c` 覆盖 `static inline`（定义/嵌套调用/取地址/函数指针间接调用），文件头注释已标注本缺陷不在覆盖范围。修复后应补 extern-inline 正向断言。
- 状态：✅ **closed**（e9fae35：decl.c 延迟发射 inline 定义 + extern 声明 promote + TU 末尾释放；inline.c 已补 extern-inline 双向断言；自举通过）。

## 缺陷 Y（cpp-0f）：`delete (T*)expr` 解析失败（delete operand 用 unaryexpr，不含 cast-expression）（worker-q，2026-08-03）

- **严重性**：一致性缺陷（合法 C++ 代码被拒，非误编译），优先级 **low**（既有小缺陷，`delete` 后直接强转的写法少见）。
- **位置**：`projects/mcc/src/cpp/parse/cpp_parse.c` `cpp_parse_delete_expr`（2687 行起）。两路操作数解析都走 `unaryexpr(s)`：
  - 数组路 `delete[] ...`：2714 行 `e = unaryexpr(s);`
  - 标量路 `delete ...`：2825 行 `e = unaryexpr(s);`
  C++ 语法中 `delete` 操作数应为 **cast-expression**（含 `(T)expr` 强转），`unaryexpr` 只收 `* / & / ++ / -- / ! / ~` 前缀与 postfix，cast 表达式落空。
- **最小复现**（均为缺陷 Q 修复后实测，HEAD 0aa19bd）：
  ```c++
  class E { public: ~E() { } int v; };
  int main(void) {
      delete (E *)0;    // error: undeclared identifier: E
      return 0;
  }
  ```
  - `delete (E *)0`（标量，类指针）：`error: undeclared identifier: E`
  - `delete[] (E *)0`（数组，类指针）：`error: undeclared identifier: E`
  - `delete (int *)0`（标量，内置类型）：`error: expected primary expression`
  - **对照（正常路径）**：`E *p = (E *)0; delete p;` 编译通过、运行正常（cast 在变量初始化里解析）→ 问题只在 delete 操作数内嵌 cast 的写法。
- **根因**：delete 操作数解析粒度不足。`unaryexpr` 遇到 `(` 时按「括号内 primary/postfix 表达式」处理，`(E *)0` 中的 `E` 被当表达式求值 → 报未声明标识符。
- **修复建议**（第二轮再改，本轮只登记）：两处 `unaryexpr(s)` 改为 `castexpr(s)`（`src/c/parse/expr_unary.c` 已有该函数，未定义时落到 postfix）。注意与 S/T 的 lambda 区域不同文件位置，但同在 cpp_parse.c，避免并发，W 修复放到第二轮。
- **影响面**：`delete (T*)expr` 这类强转写法一律被拒；常规 `delete ptr`（指针变量/成员访问/下标等 unary 能覆盖的形态）不受影响，缺陷 Q 修复未引入此问题（原实现即如此）。
- 状态：✅ **closed**（9e43494：delete/delete[] operand 改 castexpr；新增 test/cpp/new_delete_cast.cc）。

## 缺陷 cpp-10：constexpr 模板函数体 `sizeof(T)` 常量求值报 undeclared T（worker-cpp23 登记，2026-08-03）

- **复现**（最小，单 return 体）：
  ```c++
  template <typename T> constexpr int h(T x) { return sizeof(T); }
  constexpr int a = h(5);    // error: undeclared identifier: T
  ```
  多语句体 + `if constexpr (sizeof(T))` 同样复现（G2 测试期间发现）。
- **精确触发面**：仅**常量求值**路径。对照已验证：
  - 值用法正常：`constexpr T m2(T x){ return x*2; }` + `constexpr int a = m2(21)` ✅；
  - 运行期实参调用正常：`h(g)`（g 为运行期变量）✅——说明运行时定义解析的模板实例化会正确重写 `T`；
  - 非 constexpr 模板 `sizeof(T)` 正常 ✅。
- **根因假设**：`cpp_buffer_constexpr_body`（cpp_parse.c）在**模板定义时**缓冲 `{...}` 体 token（含 `T`）；模板实例化的 token 重写只作用于运行期定义解析路径，而 `cpp_constexpr_eval` 的临时 scope 仅为 filescope 普通子作用域 + 形参绑定，不含模板参数 `T` 的类型绑定 → `sizeof(T)` 中 T 无法解析。
- **既有性**：单 return 体在 G1（多语句解释器）之前同样失败（旧求值器假定 `{ return expr; }`，expr 含 `sizeof(T)` 时同样 undeclared T）→ **非 G1/G2 引入的回归**，是模板 × constexpr 交互的既有限制，被 G1 后多语句体更清晰地暴露。
- **修复方向**：① constexpr 体缓冲在模板实例化时重新缓冲/重写（复用实例化 token 重写机制）；或 ② 求值器临时 scope 继承模板参数绑定（DECLTYPE）。
- **复现文件**：`test/cpp/pending/constexpr_tmpl_sizeof.cc`（不接入 CI）。
- 状态：🔄 **open**（本轮只登记，未改代码）。
